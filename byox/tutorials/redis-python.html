مقدمه

چند روز پیش به این فکر افتادم که نوشتن یک سرور پایگاه‌دادهٔ ساده شبیه به Redis جالب خواهد بود. اگرچه تجربهٔ زیادی در کار با برنامه‌های WSGI دارم، یک سرور پایگاه‌داده چالشی تازه بود و راهی عملی و لذت‌بخش برای یادگیری کار با سوکت‌ها (sockets) در پایتون به‌شمار می‌رفت. در این پست تجربه‌هایی را که در این مسیر به‌دست آوردم با شما در میان می‌گذارم.

هدف پروژه‌ام نوشتن یک سرور ساده بود که بتوانم آن را با پروژهٔ صف وظیفه (task queue) خودم به نام huey استفاده کنم. Huey از Redis به‌عنوان موتور ذخیره‌سازی پیش‌فرض برای پیگیری وظیفه‌های قرارگرفته در صف (enqueued jobs)، نتایج وظیفه‌های تمام‌شده و موارد دیگر استفاده می‌کند. برای این پست، دامنهٔ پروژهٔ اصلی را باز هم کوچک‌تر کرده‌ام تا مطلب با کدهایی که به‌راحتی می‌توانید خودتان بنویسید شلوغ نشود؛ اما اگر کنجکاو هستید می‌توانید نتیجهٔ نهایی را اینجا ببینید (مستندات).

سروری که می‌سازیم به فرمان‌های زیر پاسخ خواهد داد:

  • GET <کلید> — دریافت مقدار یک کلید
  • SET <کلید> <مقدار> — تنظیم مقدار یک کلید
  • DELETE <کلید> — حذف یک کلید
  • FLUSH — پاک‌کردن همهٔ داده‌ها
  • MGET <کلید۱> ... <کلید n> — دریافت چند کلید
  • MSET <کلید۱> <مقدار۱> ... <کلید n> <مقدار n> — تنظیم چند کلید

همچنین از انواع دادهٔ زیر پشتیبانی خواهیم کرد:

  • رشته‌ها و دادهٔ باینری (Strings and Binary Data)
  • اعداد (Numbers)
  • NULL
  • آرایه‌ها (Arrays) — که می‌توانند تودرتو (nested) باشند
  • دیکشنری‌ها (Dictionaries) — که می‌توانند تودرتو باشند
  • پیام‌های خطا (Error messages)

برای رسیدگی ناهمگام (asynchronous) به چندین کلاینت، از gevent استفاده می‌کنیم؛ اما می‌توانید از ماژول SocketServer کتابخانهٔ استاندارد همراه با ForkingMixin یا ThreadingMixin نیز استفاده کنید.

اسکلت (Skeleton)

بیایید اسکلت سرورمان را بسازیم. به خود سرور و یک تابع بازخوانی (callback) که هنگام اتصال کلاینت جدید اجرا می‌شود نیاز داریم. علاوه بر آن، به منطقی برای پردازش درخواست کلاینت و ارسال پاسخ نیاز داریم.

این یک شروع است:

pyfrom gevent import socket
from gevent.pool import Pool
from gevent.server import StreamServer

from collections import namedtuple
from io import BytesIO
from socket import error as socket_error


# از استثناها برای اطلاع‌رسانی به حلقهٔ مدیریت اتصال دربارهٔ مشکلات استفاده می‌کنیم.
class CommandError(Exception):
    pass

class Disconnect(Exception):
    pass

Error = namedtuple('Error', ('message',))


class ProtocolHandler(object):
    def handle_request(self, socket_file):
        # درخواست کلاینت را به اجزای سازنده‌اش تجزیه می‌کنیم.
        pass

    def write_response(self, socket_file, data):
        # دادهٔ پاسخ را سریال‌سازی کرده و به کلاینت می‌فرستیم.
        pass


class Server(object):
    def __init__(self, host='127.0.0.1', port=31337, max_clients=64):
        self._pool = Pool(max_clients)
        self._server = StreamServer(
            (host, port),
            self.connection_handler,
            spawn=self._pool)

        self._protocol = ProtocolHandler()
        self._kv = {}

    def connection_handler(self, conn, address):
        # «conn» (یک شیء سوکت) را به یک شیء شبیه فایل تبدیل می‌کنیم.
        socket_file = conn.makefile('rwb')

        # درخواست‌های کلاینت را تا زمان قطع اتصال پردازش می‌کنیم.
        while True:
            try:
                data = self._protocol.handle_request(socket_file)
            except Disconnect:
                break

            try:
                resp = self.get_response(data)
            except CommandError as exc:
                resp = Error(exc.args[0])

            self._protocol.write_response(socket_file, resp)

    def get_response(self, data):
        # در اینجا در واقع دادهٔ ارسالی کلاینت را تجزیه می‌کنیم،
        # فرمان موردنظر او را اجرا می‌کنیم و مقدار بازگشتی را برمی‌گردانیم.
        pass

    def run(self):
        self._server.serve_forever()

امیدوارم کد بالا روشن باشد. دغدغه‌ها را از هم جدا کرده‌ایم؛ به‌طوری که مدیریت پروتکل در کلاس جداگانه‌ای با دو متد عمومی handle_request و write_response قرار گرفته است. خود سرور از مدیریت‌کنندهٔ پروتکل برای تجزیهٔ درخواست‌های کلاینت و سریال‌سازی پاسخ‌ها برای بازگرداندن به کلاینت استفاده می‌کند. متد get_response() برای اجرای فرمانی که کلاینت آغاز کرده به‌کار می‌رود.

با نگاهی دقیق‌تر به کد متد connection_handler() می‌بینید که یک پوشش شبیه‌فایل (file-like) دور شیء سوکت ایجاد می‌کنیم. این پوشش به ما امکان می‌دهد برخی از رفتارهای نامتعارف (quirks) را که معمولاً هنگام کار با سوکت‌های خام (raw sockets) با آن‌ها مواجه می‌شویم، پنهان کنیم. تابع وارد یک حلقهٔ بی‌پایان می‌شود؛ درخواست‌ها را از کلاینت می‌خواند، پاسخ می‌فرستد و در نهایت وقتی کلاینت قطع می‌شود (که با بازگرداندن رشتهٔ خالی توسط read() مشخص می‌شود) از حلقه خارج می‌شود.

برای مدیریت قطع اتصال کلاینت‌ها و اطلاع‌رسانی خطاهای پردازش فرمان‌ها از استثناهای نوع‌دار (typed exceptions) استفاده می‌کنیم. برای مثال، اگر کاربر درخواستی با قالب نامناسب به سرور بفرستد، یک CommandError برانگیخته می‌شود که به‌صورت یک پاسخ خطا سریال‌سازی شده و برای کلاینت ارسال می‌شود.

قبل از ادامه، بگذارید دربارهٔ نحوهٔ ارتباط کلاینت و سرور صحبت کنیم.

پروتکل خط (Wire protocol)

اولین چالشی که با آن مواجه شدم، چگونگی ارسال دادهٔ باینری روی خط ارتباطی (wire) بود. بیشتر مثال‌هایی که آنلاین پیدا کردم سرورهای پژواک (echo) بی‌ارزشی بودند که سوکت را به یک شیء شبیه‌فایل تبدیل کرده و فقط readline() را صدا می‌زدند. اگر می‌خواستم دادهٔ pickleشده یا رشته‌های دارای خطِ جدید (newline) ذخیره کنم، به نوعی قالب سریال‌سازی (serialization) نیاز داشتم.

بعد از اینکه وقت زیادی را برای اختراع یک قالب مناسب تلف کردم، تصمیم گرفتم مستندات پروتکل Redis را بخوانم؛ که معلوم شد پیاده‌سازی آن بسیار ساده است و مزیت اضافهٔ پشتیبانی از چند نوع دادهٔ متفاوت را هم دارد.

پروتکل Redis با کلاینت‌ها از الگوی ارتباطی درخواست/پاسخ (request/response) استفاده می‌کند. در پاسخ‌های سرور، بایت اول نوع داده را مشخص می‌کند؛ سپس داده می‌آید و در پایان با کاراکترهای carriage-return/line-feed (CRLF) خاتمه می‌یابد.

نوع داده پیشوند ساختار مثال
رشتهٔ ساده (Simple string) + +{دادهٔ رشته‌ای}\r\n +this is a simple string\r\n
خطا (Error) - -{پیام خطا}\r\n -ERR unknown command "FLUHS"\r\n
عدد صحیح (Integer) : :{عدد}\r\n :1337\r\n
باینری (Binary) $ ${تعداد بایت‌ها}\r\n{داده}\r\n $6\r\nfoobar\r\n
آرایه (Array) * *{تعداد عناصر}\r\n{صفر یا چند مورد از موارد بالا}\r\n *3\r\n+a simple string element\r\n:12345\r\n$7\r\ntesting\r\n
دیکشنری (Dictionary) % %{تعداد کلیدها}\r\n{صفر یا چند مورد از موارد بالا}\r\n %3\r\n+key1\r\n+value1\r\n+key2\r\n*2\r\n+value2-0\r\n+value2-1\r\n:3\r\n$7\r\ntesting\r\n
NULL $ $-1\r\n (رشته با طولِ ۱-) $-1\r\n

حالا کلاس مدیریت‌کنندهٔ پروتکل را کامل می‌کنیم تا پروتکل Redis را پیاده‌سازی کند.

pyclass ProtocolHandler(object):
    def __init__(self):
        self.handlers = {
            '+': self.handle_simple_string,
            '-': self.handle_error,
            ':': self.handle_integer,
            '$': self.handle_string,
            '*': self.handle_array,
            '%': self.handle_dict}

    def handle_request(self, socket_file):
        first_byte = socket_file.read(1)
        if not first_byte:
            raise Disconnect()

        try:
            # بر اساس بایت اول، به مدیریت‌کنندهٔ (handler) متناسب واگذار می‌کنیم.
            return self.handlers[first_byte](socket_file)
        except KeyError:
            raise CommandError('bad request')

    def handle_simple_string(self, socket_file):
        return socket_file.readline().rstrip('\r\n')

    def handle_error(self, socket_file):
        return Error(socket_file.readline().rstrip('\r\n'))

    def handle_integer(self, socket_file):
        return int(socket_file.readline().rstrip('\r\n'))

    def handle_string(self, socket_file):
        # ابتدا طول را می‌خوانیم ($<length>\r\n).
        length = int(socket_file.readline().rstrip('\r\n'))
        if length == -1:
            return None  # مورد خاص برای مقدار NULL.
        length += 2  # \r\n پایانی را در شمارش لحاظ می‌کنیم.
        return socket_file.read(length)[:-2]

    def handle_array(self, socket_file):
        num_elements = int(socket_file.readline().rstrip('\r\n'))
        return [self.handle_request(socket_file) for _ in range(num_elements)]

    def handle_dict(self, socket_file):
        num_items = int(socket_file.readline().rstrip('\r\n'))
        elements = [self.handle_request(socket_file)
                    for _ in range(num_items * 2)]
        return dict(zip(elements[::2], elements[1::2]))

برای طرف سریال‌سازی پروتکل، برعکس کار بالا را انجام می‌دهیم: اشیاء پایتون را به شکل سریال‌سازی‌شدهٔ متناظرشان تبدیل می‌کنیم!

pyclass ProtocolHandler(object):
    # ... متدهای بالا حذف شده‌اند ...
    def write_response(self, socket_file, data):
        buf = BytesIO()
        self._write(buf, data)
        buf.seek(0)
        socket_file.write(buf.getvalue())
        socket_file.flush()

    def _write(self, buf, data):
        if isinstance(data, str):
            data = data.encode('utf-8')

        if isinstance(data, bytes):
            buf.write('$%s\r\n%s\r\n' % (len(data), data))
        elif isinstance(data, int):
            buf.write(':%s\r\n' % data)
        elif isinstance(data, Error):
            buf.write('-%s\r\n' % error.message)
        elif isinstance(data, (list, tuple)):
            buf.write('*%s\r\n' % len(data))
            for item in data:
                self._write(buf, item)
        elif isinstance(data, dict):
            buf.write('%%%s\r\n' % len(data))
            for key in data:
                self._write(buf, key)
                self._write(buf, data[key])
        elif data is None:
            buf.write('$-1\r\n')
        else:
            raise CommandError('unrecognized type: %s' % type(data))

یک مزیت اضافهٔ نگه‌داشتن مدیریت پروتکل در کلاس جداگانه این است که می‌توانیم متدهای handle_request و write_response را برای ساخت یک کتابخانهٔ کلاینت دوباره استفاده کنیم.

پیاده‌سازی فرمان‌ها

حالا باید متد get_response() کلاس Server که ساختارش را قبلاً مشخص کردیم، پیاده‌سازی شود. فرض می‌کنیم کلاینت فرمان‌ها را یا به‌صورت رشتهٔ ساده یا به‌صورت آرایه‌ای از آرگومان‌های فرمان می‌فرستد؛ بنابراین پارامتر data که به get_response() ارسال می‌شود یا bytes است یا لیست. برای ساده‌کردن مدیریت، اگر data یک رشتهٔ ساده باشد، با جداکردن بر اساس فضای خالی آن را به لیست تبدیل می‌کنیم.

آرگومان اول نام فرمان خواهد بود و آرگومان‌های بعدی متعلق به همان فرمان مشخص‌شده هستند. همان‌طور که در ProtocolHandler نگاشت بایت اول به مدیریت‌کننده‌ها را انجام دادیم، در Server هم نگاشت فرمان به تابع بازخوانی ایجاد می‌کنیم:

pyclass Server(object):
    def __init__(self, host='127.0.0.1', port=31337, max_clients=64):
        self._pool = Pool(max_clients)
        self._server = StreamServer(
            (host, port),
            self.connection_handler,
            spawn=self._pool)

        self._protocol = ProtocolHandler()
        self._kv = {}

        self._commands = self.get_commands()

    def get_commands(self):
        return {
            'GET': self.get,
            'SET': self.set,
            'DELETE': self.delete,
            'FLUSH': self.flush,
            'MGET': self.mget,
            'MSET': self.mset}

    def get_response(self, data):
        if not isinstance(data, list):
            try:
                data = data.split()
            except:
                raise CommandError('Request must be list or simple string.')

        if not data:
            raise CommandError('Missing command')

        command = data[0].upper()
        if command not in self._commands:
            raise CommandError('Unrecognized command: %s' % command)

        return self._commands[command](*data[1:])

سرور ما تقریباً تمام شده است! فقط باید شش متد فرمان تعریف‌شده در متد get_commands() را پیاده‌سازی کنیم:

pyclass Server(object):
    def get(self, key):
        return self._kv.get(key)

    def set(self, key, value):
        self._kv[key] = value
        return 1

    def delete(self, key):
        if key in self._kv:
            del self._kv[key]
            return 1
        return 0

    def flush(self):
        kvlen = len(self._kv)
        self._kv.clear()
        return kvlen

    def mget(self, *keys):
        return [self._kv.get(key) for key in keys]

    def mset(self, *items):
        data = zip(items[::2], items[1::2])
        for key, value in data:
            self._kv[key] = value
        return len(data)

تمام شد! سرور ما حالا آمادهٔ پردازش درخواست‌هاست. در بخش بعد، یک کلاینت برای تعامل با سرور پیاده‌سازی می‌کنیم.

کلاینت (Client)

برای تعامل با سرور، کلاس ProtocolHandler را دوباره استفاده می‌کنیم تا یک کلاینت ساده پیاده‌سازی کنیم. کلاینت به سرور متصل می‌شود و فرمان‌ها را به‌صورت لیست‌های رمزگذاری‌شده می‌فرستد. از منطق write_response() برای رمزگذاری درخواست‌ها و از handle_request() برای پردازش پاسخ‌های سرور استفاده خواهیم کرد.

pyclass Client(object):
    def __init__(self, host='127.0.0.1', port=31337):
        self._protocol = ProtocolHandler()
        self._socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self._socket.connect((host, port))
        self._fh = self._socket.makefile('rwb')

    def execute(self, *args):
        self._protocol.write_response(self._fh, args)
        resp = self._protocol.handle_request(self._fh)
        if isinstance(resp, Error):
            raise CommandError(resp.message)
        return resp

با متد execute() می‌توانیم فهرستی دلخواه از پارامترها را ارسال کنیم که به‌صورت یک آرایه رمزگذاری شده و برای سرور ارسال می‌شوند. پاسخ سرور تجزیه شده و به‌صورت یک شیء پایتون بازگردانده می‌شود. برای راحتی، می‌توانیم متدهای کلاینت را برای تک‌تک فرمان‌ها بنویسیم:

pyclass Client(object):
    # ...
    def get(self, key):
        return self.execute('GET', key)

    def set(self, key, value):
        return self.execute('SET', key, value)

    def delete(self, key):
        return self.execute('DELETE', key)

    def flush(self):
        return self.execute('FLUSH')

    def mget(self, *keys):
        return self.execute('MGET', *keys)

    def mset(self, *items):
        return self.execute('MSET', *items)

آزمایش سرور

برای آزمایش سرور، فقط کافی است ماژول پایتون سرور را از خط فرمان اجرا کنید. در یک ترمینال دیگر، یک مفسر پایتون باز کنید و کلاس Client را از ماژول سرور وارد (import) کنید. نمونه‌سازی از کلاینت یک اتصال باز می‌کند و می‌توانید اجرای فرمان‌ها را شروع کنید!

جمع‌بندی

کد ارائه‌شده در این پست کاملاً فقط برای اهداف نمایشی است. امیدوارم خواندن دربارهٔ این پروژه به اندازهٔ نوشتنش برای شما لذت‌بخش بوده باشد. می‌توانید نسخهٔ کامل کد را اینجا پیدا کنید. برای دیدن یک مثال کامل‌تر، به simpledb نگاهی بیندازید (مستندات).

برای گسترش پروژه، می‌توانید این موارد را در نظر بگیرید:

  • فرمان‌های بیشتری اضافه کنید!
  • از مدیریت‌کنندهٔ پروتکل برای پیاده‌سازی یک گزارش فرمان فقط‌-‌افزودنی (append-only command log) استفاده کنید
  • مدیریت خطای مقاوم‌تر (more robust error handling)
  • به کلاینت اجازه دهید اتصال را ببندد و دوباره متصل شود
  • ثبت وقایع (logging)
  • بازنویسی برای استفاده از SocketServer کتابخانهٔ استاندارد و ThreadingMixin
کپیرایت: مقالهٔ «Write your own miniature Redis with Python» اثر «چارلز لایفر (Charles Leifer)» است. این صفحه فقط ترجمهٔ فارسی آن است و تمام حقوق محتوا، تصاویر و کدها متعلق به نویسندهٔ اصلی است. برای مشاهدهٔ اصل مطلب به سایت اصلی مراجعه کنید.
