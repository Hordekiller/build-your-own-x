باکر: پیاده‌سازی داکر در حدود ۱۰۰ خط bash

⚙ زبان: Shell 📁 دسته: داکر ✅ ترجمه شده 🔗 منبع اصلی
منبع اصلی: این صفحه ترجمه فارسی پروژهٔ «bocker» نوشتهٔ «پیتر ویلموت (Peter Wilmott)» (نام کاربری گیت‌هاب p8952) است — داکر (Docker) که در حدود ۱۰۰ خط bash پیاده‌سازی شده است. کد کامل اسکریپت، فایل واگنت (Vagrantfile) و نمونهٔ استفادهٔ مندرج در مخزن، همگی در این صفحه ترجمه و تشریح شده‌اند. نسخهٔ کامل و به‌روز را از مخزن اصلی بخوانید.
↗ مشاهده منبع اصلی

مقدمه

پروژهٔ باکر (bocker) یکی از معروف‌ترین پروژه‌های آموزشی «خودت بساز» در دنیای لینوکس است: پیاده‌سازی کامل داکر در حدود ۱۰۰ خط اسکریپت bash. نویسندهٔ آن، پیتر ویلموت (Peter Wilmott)، با این پروژه نشان می‌دهد که کانتینرها (containers) هیچ جادویی در کار نیستند؛ بلکه حاصل کنار هم قرارگرفتن چند ابزار اصلی هستهٔ لینوکس (kernel) هستند: فضاهای نام (namespaces)، چروت (chroot)، گروه‌های کنترل (cgroups) و فایل‌سیستم کپی‌هنگام‌نوشتنِ btrfs.

مخزن اصلی این پروژه در github.com/p8952/bocker قرار دارد، دارای بیش از ۱۲ هزار ستاره است، تحت پروانهٔ GPL-3.0 منتشر شده و یک فایل واگنت (Vagrantfile) برای راه‌اندازی خودکار محیط آزمایش همراه دارد. در این صفحه، کل اسکریپت به‌صورت خط‌به‌خط ترجمه و تشریح می‌شود تا ببینید موتور کانتینری داکر در ساده‌ترین شکل ممکن چگونه کار می‌کند.

هشدار مهم: باکر باید به‌عنوان کاربر ریشه (root) اجرا شود و از جمله به رابط‌های شبکه، جدول مسیریابی (routing table) و قواعد دیوار آتش (firewall) سیستم شما تغییراتی اعمال می‌کند. نویسنده تأکید می‌کند که بهترین کار، اجرای باکر داخل یک ماشین مجازی (virtual machine) است و ضمانتی نمی‌دهد که سیستم شما را نابود نکند!

پیش‌نیازها

برای اجرای باکر به بسته‌های زیر در یک توزیع گنو/لینوکس (GNU/Linux) نیاز دارید:

  • btrfs-progs — ابزارهای فایل‌سیستم btrfs (ساب‌وولوم و عکس‌فوری)
  • curl — دریافت تصاویر از رجیستری داکر
  • iproute2 — دستور ip برای شبکه و فضاهای نام شبکه
  • iptables — دیوار آتش برای انتقال بسته‌ها از پل شبکه
  • libcgroup-tools — ابزار گروه‌های کنترل (cgroup): cgcreate، cgset، cgexec و cgdelete
  • util-linux نسخهٔ ۲.۲۵.۲ یا بالاتر — برای دستور unshare
  • coreutils نسخهٔ ۷.۵ یا بالاتر

چون بیشتر توزیع‌ها نسخهٔ به‌اندازه‌ای جدید از util-linux را ارائه نمی‌کنند، احتمالاً باید کدهای منبع آن را از kernel.org بگیرید و خودتان کامپایل کنید.

علاوه بر بسته‌ها، سیستم شما باید به‌صورت زیر پیکربندی شده باشد:

  • یک فایل‌سیستم btrfs که روی مسیر /var/bocker سوار شده باشد.
  • یک پل شبکه (network bridge) به نام bridge0 با آدرس IP برابر 10.0.0.1/24.
  • ارسال بسته (IP forwarding) در /proc/sys/net/ipv4/ip_forward فعال باشد.
  • یک دیوار آتش که ترافیک را از bridge0 به یک رابط فیزیکی هدایت کند (در نمونهٔ واگنت با MASQUERADE انجام می‌شود).
نکته: برای سهولت کار، یک Vagrantfile در مخزن گنجانده شده است که کل این محیط را خودکار می‌سازد؛ بخش «نحوهٔ نصب و استفاده» آن را نشان می‌دهد.

نحوهٔ نصب و استفاده

ساده‌ترین راه، ساخت محیط آماده با واگنت (Vagrant) است. فایل Vagrantfile مخزن یک ماشین مجازی CentOS 7 بالا می‌آورد، فایل تصویر btrfs ساخته و روی /var/bocker سوار می‌کند، از undocker برای آماده‌کردن یک تصویر پایهٔ centos استفاده می‌کند، نسخهٔ موردنیاز util-linux را برای دستور unshare کامپایل می‌کند، اسکریپت bocker را در /usr/bin قرار می‌دهد و در نهایت پل bridge0، مسیریابی و قواعد NAT را برپا می‌کند. محتوای کامل این فایل:

ruby$script = <<SCRIPT
(
rpm -i https://dl.fedoraproject.org/pub/epel/7/x86_64/e/epel-release-7-5.noarch.rpm
yum install -y -q autoconf automake btrfs-progs docker gettext-devel git libcgroup-tools libtool python-pip

fallocate -l 10G ~/btrfs.img
mkdir /var/bocker
mkfs.btrfs ~/btrfs.img
mount -o loop ~/btrfs.img /var/bocker

pip install git+https://github.com/larsks/undocker
systemctl start docker.service
docker pull centos
docker save centos | undocker -o base-image

git clone https://github.com/karelzak/util-linux.git
cd util-linux
git checkout tags/v2.25.2
./autogen.sh
./configure --without-ncurses --without-python
make
mv unshare /usr/bin/unshare
cd ..

ln -s /vagrant/bocker /usr/bin/bocker

echo 1 > /proc/sys/net/ipv4/ip_forward
iptables --flush
iptables -t nat -A POSTROUTING -o bridge0 -j MASQUERADE
iptables -t nat -A POSTROUTING -o enp0s3 -j MASQUERADE

ip link add bridge0 type bridge
ip addr add 10.0.0.1/24 dev bridge0
ip link set bridge0 up
) 2>&1
SCRIPT

همان‌طور که می‌بینید، جریان کار دقیقاً همان‌ند داکر است: تصویری را می‌کشیم (pull)، کانتینری از آن می‌سازیم (run)، تغییرات را به‌صورت تصویر جدید ثبت می‌کنیم (commit) و در پایان، سهم پردازنده و حافظهٔ هر کانتینر با متغیرهای محیطی BOCKER_CPU_SHARE و BOCKER_MEM_LIMIT قابل تنظیم است.

تشریح کامل اسکریپت bocker

در مخزن، فایل اصلی با نام bocker (بدون پسوند) قرار دارد. اسکریپت را بخش‌به‌بخش می‌خوانیم؛ هر بخش، هم کد واقعی و هم شرح فارسی آن را همراه دارد.

پیش‌درآمد اسکریپت: تنظیمات و پارس گزینه‌ها

sh#!/usr/bin/env bash
set -o errexit -o nounset -o pipefail; shopt -s nullglob
btrfs_path='/var/bocker' && cgroups='cpu,cpuacct,memory';
[[ $# -gt 0 ]] && while [ "${1:0:2}" == '--' ]; do OPTION=${1:2}; [[ $OPTION =~ = ]] && declare "BOCKER_${OPTION/=*/}=${OPTION/*=/}" || declare "BOCKER_${OPTION}=x"; shift; done
  • #!/usr/bin/env bash — شِبنگ (shebang): اجرای اسکریپت با مفسر bash.
  • set -o errexit -o nounset -o pipefail — با اولین خطا خارج شو، متغیر تعریف‌نشده را خطا بگیر و اگر یکی از دستورهای یک خط لوله (pipe) شکست خورد، نتیجهٔ کل خط شکست‌خورده باشد.
  • shopt -s nullglob — اگر الگوی glob به چیزی نیافت، به‌جای ارسال خودِ الگو، لیست خالی بفرست (در حلقه‌های for روی img_* مهم است).
  • btrfs_path='/var/bocker' — مسیر ریشه‌ای که همهٔ تصاویر و کانتینرها به‌صورت ساب‌وولوم (subvolume) در آن ساخته می‌شوند.
  • cgroups='cpu,cpuacct,memory' — زیرسیستم‌های گروه کنترل که باکر استفاده می‌کند: پردازنده، حساب‌رسِ پردازنده و حافظه.
  • حلقهٔ while — هر آرگومانی که با -- آغاز شود، پارس می‌شود: اگر شکل --نام=مقدار باشد، متغیر محیطی BOCKER_نام=مقدار تعریف می‌شود و در غیر این‌صورت BOCKER_نام=x. به این ترتیب گزینه‌هایی مانند --cpu-share=1024 به متغیر BOCKER_CPU_SHARE تبدیل می‌شوند.

فایل‌سیستم btrfs: ساب‌وولوم‌ها و عکس‌فوری‌ها

نکتهٔ کلیدی درک باکر، فهم فایل‌سیستم btrfs است. هر تصویر و هر کانتینر یک ساب‌وولوم (subvolume) در /var/bocker است و کانتینرها با عکس‌فوری (snapshot) از تصویر ساخته می‌شوند. چون عکس‌فوری در btrfs با مکانیزم کپی‌هنگام‌نوشتن (copy-on-write / CoW) انجام می‌شود، کانتینرها تقریباً هیچ فضای اضافه‌ای مصرف نمی‌کنند و لایه‌بندی تصویر/کانتینر دقیقاً به همین شکل کار می‌کند (نقشی که در داکر واقعی بر عهدهٔ overlayfs است). تابع bocker_check بررسی می‌کند که آیا ساب‌وولومی با شناسهٔ داده‌شده وجود دارد یا نه:

shfunction bocker_check() {
	btrfs subvolume list "$btrfs_path" | grep -qw "$1" && echo 0 || echo 1
}

فهرست ساب‌وولوم‌های /var/bocker را می‌گیرد و با grep -w به‌دنبال شناسهٔ موردنظر (مثلاً img_42150) می‌گردد؛ اگر یافت شد 0 وگرنه 1 چاپ می‌کند (این 1 خروجیِ «صادقانهٔ» خودِ echo است، نه کد خروجی دستور!).

حذف تصویر یا کانتینر نیز یک‌پارچه است — حذف ساب‌وولوم و حذف گروه کنترل متناظر:

shfunction bocker_rm() { #HELP حذف یک تصویر یا کانتینر:\nBOCKER rm <image_id or container_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	btrfs subvolume delete "$btrfs_path/$1" > /dev/null
	cgdelete -g "$cgroups:/$1" &> /dev/null || true
	echo "Removed: $1"
}

با btrfs subvolume delete ساب‌وولوم حذف و با cgdelete گروه کنترلش پاک می‌شود. همین یک تابع هم دستور docker rm و هم docker rmi را پوشش می‌دهد؛ چون تفاوتی نمی‌کند که شناسه مربوط به تصویر باشد یا کانتینر.

تصاویر: init، pull، images و commit

ساخت تصویر از یک پوشه (معادل بسیار محدودِ docker build):

shfunction bocker_init() { #HELP ساخت تصویر از یک پوشه:\nBOCKER init <directory>
	uuid="img_$(shuf -i 42002-42254 -n 1)"
	if [[ -d "$1" ]]; then
		[[ "$(bocker_check "$uuid")" == 0 ]] && bocker_run "$@"
		btrfs subvolume create "$btrfs_path/$uuid" > /dev/null
		cp -rf --reflink=auto "$1"/* "$btrfs_path/$uuid" > /dev/null
		[[ ! -f "$btrfs_path/$uuid"/img.source ]] && echo "$1" > "$btrfs_path/$uuid"/img.source
		echo "Created: $uuid"
	else
		echo "No directory named '$1' exists"
	fi
}

شناسهٔ تصویر به‌صورت تصادفی با img_ به‌علاوهٔ یک عدد بین ۴۲۰۰۲ تا ۴۲۲۵۴ ساخته می‌شود (باکر «ps_» و «img_» را به‌همراه همین بازهٔ عددی به‌کار می‌برد؛ منبع الهام هم‌نامیِ آنها با شناسه‌های واقعی داکر است). سپس یک ساب‌وولوم جدید ساخته و محتوای پوشهٔ ورودی با cp --reflink=auto در آن کپی می‌شود؛ reflink یعنی کپی هم در btrfs با مکانیزم کپی‌هنگام‌نوشتن انجام می‌شود. منبع تصویر در فایل img.source ذخیره می‌شود تا بعداً در bocker images نمایش داده شود.

کشیدن تصویر از داکر هاب (Docker Hub): شاید شگفت‌انگیزترین بخش باکر — تصاویر واقعی از رجیستری عمومی داکر با پروتکل قدیمی v1 دانلود می‌شوند:

shfunction bocker_pull() { #HELP دریافت تصویر از داکر هاب:\nBOCKER pull <name> <tag>
	token="$(curl -sL -o /dev/null -D- -H 'X-Docker-Token: true' "https://index.docker.io/v1/repositories/$1/images" | tr -d '\r' | awk -F ': *' '$1 == "X-Docker-Token" { print $2 }')"
	registry='https://registry-1.docker.io/v1'
	id="$(curl -sL -H "Authorization: Token $token" "$registry/repositories/$1/tags/$2" | sed 's/"//g')"
	[[ "${#id}" -ne 64 ]] && echo "No image named '$1:$2' exists" && exit 1
	ancestry="$(curl -sL -H "Authorization: Token $token" "$registry/images/$id/ancestry")"
	IFS=',' && ancestry=(${ancestry//[\[\] \"]/}) && IFS=' \n\t'; tmp_uuid="$(uuidgen)" && mkdir /tmp/"$tmp_uuid"
	for id in "${ancestry[@]}"; do
		curl -#L -H "Authorization: Token $token" "$registry/images/$id/layer" -o /tmp/"$tmp_uuid"/layer.tar
		tar xf /tmp/"$tmp_uuid"/layer.tar -C /tmp/"$tmp_uuid" && rm /tmp/"$tmp_uuid"/layer.tar
	done
	echo "$1:$2" > /tmp/"$tmp_uuid"/img.source
	bocker_init /tmp/"$tmp_uuid" && rm -rf /tmp/"$tmp_uuid"
}

مراحل این تابع به‌ترتیب:

  1. با یک درخواست اولیه، نشانهٔ دسترسی (token) از index.docker.io گرفته می‌شود (awk مقدار سرآیند X-Docker-Token را استخراج می‌کند).
  2. با آن نشانه، شناسهٔ لایهٔ بالا (که هش ۶۴ کاراکتری sha256 است) برای برچسبِ خواسته‌شده پرس‌وجو می‌شود؛ اگر طولش برابر ۶۴ نباشد یعنی تصویری با آن نام/برچسب وجود ندارد.
  3. با آدرس /images/$id/ancestry فهرست کامل شجرهٔ لایه‌ها (ancestry) گرفته می‌شود و به‌کمک دستکاری IFS به آرایه تبدیل می‌شود.
  4. هر لایه به‌صورت یک آرشیو tar دانلود و به‌ترتیب روی همدیگر از بسته خارج می‌شود — یعنی دقیقاً همان کاری که ران‌تایم داکر هنگام پیمایش لایه‌های یک تصویر انجام می‌دهد.
  5. در پایان، پوشهٔ حاصل به bocker_init سپرده می‌شود تا به‌صورت ساب‌وولوم img_* دربیاید.
نکته: رجیستری v1 داکر سال‌هاست منسوخ شده و داکر هاب دیگر از آن پشتیبانی نمی‌کند؛ پس در دنیای امروز، bocker pull عملاً به‌کار نمی‌آید و برای تجربهٔ کار واقعی، بهتر است تصاویر را با bocker init از یک پوشهٔ آماده (مثل خروجیِ undocker در Vagrantfile) بسازید. بااین‌حال، منطق آن آموزشِ بسیار خوبی است برای این‌که ببینید «کشیدن تصویر» در اصل یعنی چه.

فهرست تصاویر:

shfunction bocker_images() { #HELP فهرست تصاویر:\nBOCKER images
	echo -e "IMAGE_ID\t\tSOURCE"
	for img in "$btrfs_path"/img_*; do
		img=$(basename "$img")
		echo -e "$img\t\t$(cat "$btrfs_path/$img/img.source")"
	done
}

همهٔ ساب‌وولوم‌های شروع‌شونده با img_ را فهرست می‌کند و کنار هر شناسه، محتوای img.source (منبع تصویر، مثلاً centos:7) را چاپ می‌کند. nullglob تضمین می‌کند اگر هیچ تصویری وجود نداشته باشد، حلقه اصلاً اجرا نشود.

ثبت تغییرات کانتینر به‌عنوان تصویر (معادل docker commit):

shfunction bocker_commit() { #HELP ثبت کانتینر به‌صورت تصویر:\nBOCKER commit <container_id> <image_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	[[ "$(bocker_check "$2")" == 1 ]] && echo "No image named '$2' exists" && exit 1
	bocker_rm "$2" && btrfs subvolume snapshot "$btrfs_path/$1" "$btrfs_path/$2" > /dev/null
	echo "Created: $2"
}

تصویر قدیمی حذف می‌شود و از ساب‌وولوم کانتینر یک عکس‌فوری (snapshot) گرفته می‌شود که همان شناسهٔ تصویر را یدک می‌کشد. به این ترتیب کل لایهٔ تغییرات کانتینر، «تصویرِ» جدید می‌شود — مفهوم commit در داکر، عیناً همین عکس‌فوری است.

کانتینرها: قلب باکر در bocker_run

تابع bocker_run همهٔ کارهای اصلی را انجام می‌دهد: ایجاد شبکه، ساخت عکس‌فوری، تخصیص سهم منابع و اجرای دستور داخل فضای ایزوله. کد کامل آن:

shfunction bocker_run() { #HELP ساخت یک کانتینر:\nBOCKER run <image_id> <command>
	uuid="ps_$(shuf -i 42002-42254 -n 1)"
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No image named '$1' exists" && exit 1
	[[ "$(bocker_check "$uuid")" == 0 ]] && echo "UUID conflict, retrying..." && bocker_run "$@" && return
	cmd="${@:2}" && ip="$(echo "${uuid: -3}" | sed 's/0//g')" && mac="${uuid: -3:1}:${uuid: -2}"
	ip link add dev veth0_"$uuid" type veth peer name veth1_"$uuid"
	ip link set dev veth0_"$uuid" up
	ip link set veth0_"$uuid" master bridge0
	ip netns add netns_"$uuid"
	ip link set veth1_"$uuid" netns netns_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev lo up
	ip netns exec netns_"$uuid" ip link set veth1_"$uuid" address 02:42:ac:11:00"$mac"
	ip netns exec netns_"$uuid" ip addr add 10.0.0."$ip"/24 dev veth1_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev veth1_"$uuid" up
	ip netns exec netns_"$uuid" ip route add default via 10.0.0.1
	btrfs subvolume snapshot "$btrfs_path/$1" "$btrfs_path/$uuid" > /dev/null
	echo 'nameserver 8.8.8.8' > "$btrfs_path/$uuid"/etc/resolv.conf
	echo "$cmd" > "$btrfs_path/$uuid/$uuid.cmd"
	cgcreate -g "$cgroups:/$uuid"
	: "${BOCKER_CPU_SHARE:=512}" && cgset -r cpu.shares="$BOCKER_CPU_SHARE" "$uuid"
	: "${BOCKER_MEM_LIMIT:=512}" && cgset -r memory.limit_in_bytes="$((BOCKER_MEM_LIMIT * 1000000))" "$uuid"
	cgexec -g "$cgroups:$uuid" \
		ip netns exec netns_"$uuid" \
		unshare -fmuip --mount-proc \
		chroot "$btrfs_path/$uuid" \
		/bin/sh -c "/bin/mount -t proc proc /proc && $cmd" \
		2>&1 | tee "$btrfs_path/$uuid/$uuid.log" || true
	ip link del dev veth0_"$uuid"
	ip netns del netns_"$uuid"
}

جریان اجرا، گام‌به‌گام:

  1. شناسه و آرگومان‌ها: شناسهٔ کانتینر ps_ به‌علاوهٔ یک عدد تصادفی است. اگر تصویرِ منبع وجود نداشته باشد خطا می‌دهد؛ اگر شناسهٔ کانتینر تکراری از آب دربیاید، تابع خودش را دوباره فراخوانی می‌کند (retry). دستورِ کانتینر در cmd و یک IP و یک آدرس MAC جعلی از سه رقم آخر شناسه ساخته می‌شود (اعداد صفر حذف می‌شوند تا آدرس ۱۰.۰.۰.X معتبر بماند).
  2. شبکه: یک جفت رابط مجازی veth (کابل مجازی) ساخته می‌شود: سرِ اول (veth0_…) به پل bridge0 میزبان متصل می‌شود و سرِ دوم (veth1_…) به داخل فضای نام شبکهٔ تازه‌ساخته‌شده‌ی کانتینر منتقل می‌شود (جزئیات در بخش شبکه).
  3. فایل‌سیستم: از ساب‌وولوم تصویر، یک عکس‌فوری به‌عنوان ساب‌وولوم کانتینر ساخته می‌شود؛ فایل /etc/resolv.conf به سرور نام دامنهٔ ۸.۸.۸.۸ اشاره می‌کند و دستور کانتینر در فایل $uuid.cmd ذخیره می‌شود تا bocker ps بتواند آن را نمایش دهد.
  4. منابع: گروه کنترل (cgroup) ساخته و سهم پردازنده و سقف حافظه روی آن تنظیم می‌شود (بخش cgroups).
  5. اجرای ایزوله: با cgexec کل زنجیرهٔ ip netns exec → unshare → chroot اجرا می‌شود تا فرایند هم در گروه کنترل، هم در فضای نام شبکه، هم در فضاهای نام تازه و هم در ریشهٔ فایل‌سیستم کانتینر بیفتد. خروجی و خطاها با tee در فایل $uuid.log ذخیره می‌شوند (|| true جلوی خروج زودهنگام به‌خاطر set -e را می‌گیرد؛ اجرای دستور می‌تواند عمداً با خطا تمام شود).
  6. پاک‌سازی: پس از پایان کار، رابط veth0_… و فضای نام شبکه حذف می‌شوند. ساب‌وولوم کانتینر باقی می‌ماند تا با logs، exec یا commit دوباره به کار بیاید.

فضاهای نام (namespaces): ایزوله‌سازی با unshare

خطِ محوریِ اجرای کانتینر در باکر:

sh	unshare -fmuip --mount-proc \
		chroot "$btrfs_path/$uuid" \
		/bin/sh -c "/bin/mount -t proc proc /proc && $cmd" \

unshare با این پرچم‌ها، فضاهای نام جدیدی برای فرایند فرزند می‌سازد:

  • -f (fork) — ابتدا یک فرایند فرزند بساز تا فضاهای نام فقط به آن و فرزندانش تعلق داشته باشند.
  • -m (mount) — فضای نام سوارسازی (mount namespace): هر تغییر سوارسازی داخل کانتینر، در میزبان دیده نمی‌شود.
  • -u (UTS) — فضای نام نام میزبان؛ کانتینر می‌تواند نام میزبانِ مستقل داشته باشد.
  • -i (IPC) — فضای نام پیام‌رسانی بین‌فرایندی جدا.
  • -p (PID) — فضای نام شناسهٔ فرایند؛ کانتینر فرایند خودش را با PID یک می‌بیند و از سایر فرایندهای میزبان خبر ندارد.
  • --mount-proc — به‌طور خودکار /proc را در فضای نام PID تازه سوار می‌کند تا ps و مانند آن درست کار کنند.

و سپس chroot "$btrfs_path/$uuid" ریشهٔ فایل‌سیستم را به ساب‌وولوم کانتینر تغییر می‌دهد و در پایان، /bin/sh -c اول proc را سوار می‌کند و بعد دستورِ کاربر را اجرا می‌کند. جمع همهٔ این‌ها یعنی: شبکهٔ جدا (namespace شبکه)، سیستم فایل جدا (chroot)، سربندیِ جدا (mount namespace)، درخت فرایند جدا (PID namespace) — یعنی همان تعریف سطح بالای یک کانتینر. توجه کنید که -u و -i در باکر فقط برای رفع نیازِ پرچم‌هاست و عملاً مورداستفاده قرار نمی‌گیرند.

شبکه: veth، bridge و فضای نام شبکه

باکر برای هر کانتینر یک «کابل مجازی» (veth pair) می‌سازد — دو رابط که از یک سر، یکی در میزبان و دیگری در فضای نام شبکهٔ کانتینر است و هر بسته‌ای که از یکی وارد شود از دیگری خارج می‌شود. سپس سمت میزبان را به پل bridge0 وصل می‌کند و سمت کانتینر را به داخل فضای نام شبکهٔ اختصاصی کانتینر (netns_…) می‌فرستد. داخل آن فضای نام، رابط حلقه (loopback) و رابط veth بالا آورده می‌شود، به آن آدرس MAC جعلی و IP از زیرشبکهٔ ۱۰.۰.۰.۰/24 داده می‌شود و مسیر پیش‌فرض به سمت 10.0.0.1 (خودِ پل روی میزبان) تنظیم می‌گردد:

sh	ip link add dev veth0_"$uuid" type veth peer name veth1_"$uuid"
	ip link set dev veth0_"$uuid" up
	ip link set veth0_"$uuid" master bridge0
	ip netns add netns_"$uuid"
	ip link set veth1_"$uuid" netns netns_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev lo up
	ip netns exec netns_"$uuid" ip link set veth1_"$uuid" address 02:42:ac:11:00"$mac"
	ip netns exec netns_"$uuid" ip addr add 10.0.0."$ip"/24 dev veth1_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev veth1_"$uuid" up
	ip netns exec netns_"$uuid" ip route add default via 10.0.0.1

به این ترتیب همهٔ کانتینرها از طریق پل bridge0 به یک شبکهٔ داخلی وصل می‌شوند و «آدرس ۱۰.۰.۰.۱» (میزبان) نقش دروازهٔ پیش‌فرض را دارد. اما این‌که بسته‌های کانتینرها چگونه به اینترنت می‌رسند؟ در Vagrantfile دو قانون NAT این‌گونه برقرار شده است:

shelliptables --flush
iptables -t nat -A POSTROUTING -o bridge0 -j MASQUERADE
iptables -t nat -A POSTROUTING -o enp0s3 -j MASQUERADE

یعنی ترافیک خروجی از bridge0 و از رابط فیزیکی enp0s3 با ترجمهٔ آدرس مبدأ (MASQUERADE) به بیرون می‌رود و پاسخ‌ها دوباره به کانتینرِ درخواست‌دهنده برمی‌گردد. این دقیقاً همان الگویی است که داکر با «شبکهٔ پیش‌فرض بریج» خود پیاده می‌کند، فقط در این‌جا حدوداً با ۱۰ خط iproute2 ساخته شده است.

سهم منابع با cgroups

باکر با گروه‌های کنترل (control groups) برای هر کانتینر محدودیت منابع می‌گذارد — سهم پردازنده با cpu.shares و سقف حافظه با memory.limit_in_bytes:

sh	cgcreate -g "$cgroups:/$uuid"
	: "${BOCKER_CPU_SHARE:=512}" && cgset -r cpu.shares="$BOCKER_CPU_SHARE" "$uuid"
	: "${BOCKER_MEM_LIMIT:=512}" && cgset -r memory.limit_in_bytes="$((BOCKER_MEM_LIMIT * 1000000))" "$uuid"
	cgexec -g "$cgroups:$uuid" \
		ip netns exec netns_"$uuid" \

cgcreate گروه را می‌سازد؛ مقادیر پیش‌فرض ۵۱۲ برای سهم پردازنده و ۵۱۲ مگابایت برای حافظه است (با الگوی ${VAR:=default} در صورت نبودِ متغیر محیطی). سپس cgexec دستور را داخل آن گروه اجرا می‌کند؛ یعنی هر سهمی که فرایند مصرف کند، توسط همان محدودیت‌ها مهار می‌شود. این‌ها همان مقادیری‌اند که در نمونهٔ استفاده می‌بینیم:

  • پیش‌فرض: cpu.shares برابر ۵۱۲ و memory.limit_in_bytes برابر ۵۱۲۰۰۰۰۰۰ (۵۱۲ مگابایت).
  • با BOCKER_CPU_SHARE=1024 و BOCKER_MEM_LIMIT=1024: سهم پردازنده ۱۰۲۴ و سقف حافظه ۱۰۲۴۰۰۰۰۰۰ (یک گیگابایت) می‌شود.

این همان «سهم‌ها و سقف‌ها»یی است که داکر با گزینه‌های --cpu-shares و --memory در اختیار می‌گذارد.

سایر دستورها: ps، logs، exec و help

فهرست کانتینرها:

shfunction bocker_ps() { #HELP فهرست کانتینرها:\nBOCKER ps
	echo -e "CONTAINER_ID\t\tCOMMAND"
	for ps in "$btrfs_path"/ps_*; do
		ps=$(basename "$ps")
		echo -e "$ps\t\t$(cat "$btrfs_path/$ps/$ps.cmd")"
	done
}

معادلِ docker ps: همهٔ ساب‌وولوم‌های ps_* را می‌گردد و کنار شناسهٔ هر کانتینر، دستوری را که هنگام run در فایل $uuid.cmd ذخیره شده، چاپ می‌کند. (البته برخلاف داکر، این‌جا همهٔ کانتینرها — در حال اجرا یا متوقف — فهرست می‌شوند؛ چون باکر کانتینرها را در پایان اجرا متوقف/حذف نمی‌کند.)

مشاهدهٔ گزارش‌ها:

shfunction bocker_logs() { #HELP مشاهدهٔ گزارش‌های کانتینر:\nBOCKER logs <container_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	cat "$btrfs_path/$1/$1.log"
}

خروجیِ ذخیره‌شدهٔ هر کانتینر را با cat نشان می‌دهد — همان فایلی که هنگام اجرا توسط tee نوشته شد. به همین سادگی، docker logs!

اجرای دستور در کانتینرِ در حال اجرا (معادل docker exec):

shfunction bocker_exec() { #HELP اجرای یک دستور در کانتینر در حال اجرا:\nBOCKER exec <container_id> <command>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	cid="$(ps o ppid,pid | grep "^$(ps o pid,cmd | grep -E "^\ *[0-9]+ unshare.*$1" | awk '{print $1}')" | awk '{print $2}')"
	[[ ! "$cid" =~ ^\ *[0-9]+$ ]] && echo "Container '$1' exists but is not running" && exit 1
	nsenter -t "$cid" -m -u -i -n -p chroot "$btrfs_path/$1" "${@:2}"
}

این تابع به‌طرز خنده‌داری ظریف است: اول با یک grep روی خروجی ps، فرایندی را پیدا می‌کند که با unshare و شناسهٔ همان کانتینر اجرا شده (یعنی فرایند در حال اجرای کانتینر)، سپس cid را از ستون PIDِ والدش استخراج می‌کند. اگر عددی معتبر پیدا نشود یعنی کانتینر در حال اجرا نیست. در نهایت با nsenter -t "$cid" -m -u -i -n -p به همان فضاهای نامِ mount، UTS، IPC، شبکه و PIDِ کانتینر «وارد» می‌شود و بعد از chroot، دستورِ داده‌شده در همان فایل‌سیستم اجرا می‌شود. یعنی: پیدا کن، وارد شو، اجرا کن.

راهنمای استفاده:

shfunction bocker_help() { #HELP نمایش این راهنما:\nBOCKER help
	sed -n "s/^.*#HELP\\s//p;" < "$1" | sed "s/\\\\n/\n\t/g;s/$/\n/;s!BOCKER!${1/!/\\!}!g"
}

با sed، همهٔ کامنت‌های #HELP از متن خودِ اسکریپت استخراج می‌شوند و به‌صورت راهنما چاپ می‌شوند — یعنی راهنمای پروژه در خودِ کد «تعبیه» شده و هرگز از کد فاصله نمی‌گیرد.

نقطهٔ ورود و توزیع فرمان‌ها:

sh[[ -z "${1-}" ]] && bocker_help "$0"
case $1 in
	pull|init|rm|images|ps|run|exec|logs|commit) bocker_"$1" "${@:2}" ;;
	*) bocker_help "$0" ;;
esac

اگر هیچ آرگومانی نیامده باشد راهنما چاپ می‌شود؛ در غیر این‌صورت، اولی‌ن آرگومان نام یک دستور است و تابعی با همان نام (bocker_$1) با بقیهٔ آرگومان‌ها فراخوانی می‌شود. دستورهای شناخته‌شده‌اند: pull، init، rm، images، ps، run، exec، logs و commit؛ هر چیز دیگری هم به راهنما ارجاع داده می‌شود.

کد کامل اسکریپت

در ادامه، کل اسکریپت bocker را یک‌جا می‌بینید (کامنت‌های راهنمای #HELP به فارسی برگردانده شده‌اند؛ بقیهٔ کد عیناً از مخزن است):

sh#!/usr/bin/env bash
set -o errexit -o nounset -o pipefail; shopt -s nullglob
btrfs_path='/var/bocker' && cgroups='cpu,cpuacct,memory';
[[ $# -gt 0 ]] && while [ "${1:0:2}" == '--' ]; do OPTION=${1:2}; [[ $OPTION =~ = ]] && declare "BOCKER_${OPTION/=*/}=${OPTION/*=/}" || declare "BOCKER_${OPTION}=x"; shift; done

function bocker_check() {
	btrfs subvolume list "$btrfs_path" | grep -qw "$1" && echo 0 || echo 1
}

function bocker_init() { #HELP ساخت تصویر از یک پوشه:\nBOCKER init <directory>
	uuid="img_$(shuf -i 42002-42254 -n 1)"
	if [[ -d "$1" ]]; then
		[[ "$(bocker_check "$uuid")" == 0 ]] && bocker_run "$@"
		btrfs subvolume create "$btrfs_path/$uuid" > /dev/null
		cp -rf --reflink=auto "$1"/* "$btrfs_path/$uuid" > /dev/null
		[[ ! -f "$btrfs_path/$uuid"/img.source ]] && echo "$1" > "$btrfs_path/$uuid"/img.source
		echo "Created: $uuid"
	else
		echo "No directory named '$1' exists"
	fi
}

function bocker_pull() { #HELP دریافت تصویر از داکر هاب:\nBOCKER pull <name> <tag>
	token="$(curl -sL -o /dev/null -D- -H 'X-Docker-Token: true' "https://index.docker.io/v1/repositories/$1/images" | tr -d '\r' | awk -F ': *' '$1 == "X-Docker-Token" { print $2 }')"
	registry='https://registry-1.docker.io/v1'
	id="$(curl -sL -H "Authorization: Token $token" "$registry/repositories/$1/tags/$2" | sed 's/"//g')"
	[[ "${#id}" -ne 64 ]] && echo "No image named '$1:$2' exists" && exit 1
	ancestry="$(curl -sL -H "Authorization: Token $token" "$registry/images/$id/ancestry")"
	IFS=',' && ancestry=(${ancestry//[\[\] \"]/}) && IFS=' \n\t'; tmp_uuid="$(uuidgen)" && mkdir /tmp/"$tmp_uuid"
	for id in "${ancestry[@]}"; do
		curl -#L -H "Authorization: Token $token" "$registry/images/$id/layer" -o /tmp/"$tmp_uuid"/layer.tar
		tar xf /tmp/"$tmp_uuid"/layer.tar -C /tmp/"$tmp_uuid" && rm /tmp/"$tmp_uuid"/layer.tar
	done
	echo "$1:$2" > /tmp/"$tmp_uuid"/img.source
	bocker_init /tmp/"$tmp_uuid" && rm -rf /tmp/"$tmp_uuid"
}

function bocker_rm() { #HELP حذف یک تصویر یا کانتینر:\nBOCKER rm <image_id or container_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	btrfs subvolume delete "$btrfs_path/$1" > /dev/null
	cgdelete -g "$cgroups:/$1" &> /dev/null || true
	echo "Removed: $1"
}

function bocker_images() { #HELP فهرست تصاویر:\nBOCKER images
	echo -e "IMAGE_ID\t\tSOURCE"
	for img in "$btrfs_path"/img_*; do
		img=$(basename "$img")
		echo -e "$img\t\t$(cat "$btrfs_path/$img/img.source")"
	done
}

function bocker_ps() { #HELP فهرست کانتینرها:\nBOCKER ps
	echo -e "CONTAINER_ID\t\tCOMMAND"
	for ps in "$btrfs_path"/ps_*; do
		ps=$(basename "$ps")
		echo -e "$ps\t\t$(cat "$btrfs_path/$ps/$ps.cmd")"
	done
}

function bocker_run() { #HELP ساخت یک کانتینر:\nBOCKER run <image_id> <command>
	uuid="ps_$(shuf -i 42002-42254 -n 1)"
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No image named '$1' exists" && exit 1
	[[ "$(bocker_check "$uuid")" == 0 ]] && echo "UUID conflict, retrying..." && bocker_run "$@" && return
	cmd="${@:2}" && ip="$(echo "${uuid: -3}" | sed 's/0//g')" && mac="${uuid: -3:1}:${uuid: -2}"
	ip link add dev veth0_"$uuid" type veth peer name veth1_"$uuid"
	ip link set dev veth0_"$uuid" up
	ip link set veth0_"$uuid" master bridge0
	ip netns add netns_"$uuid"
	ip link set veth1_"$uuid" netns netns_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev lo up
	ip netns exec netns_"$uuid" ip link set veth1_"$uuid" address 02:42:ac:11:00"$mac"
	ip netns exec netns_"$uuid" ip addr add 10.0.0."$ip"/24 dev veth1_"$uuid"
	ip netns exec netns_"$uuid" ip link set dev veth1_"$uuid" up
	ip netns exec netns_"$uuid" ip route add default via 10.0.0.1
	btrfs subvolume snapshot "$btrfs_path/$1" "$btrfs_path/$uuid" > /dev/null
	echo 'nameserver 8.8.8.8' > "$btrfs_path/$uuid"/etc/resolv.conf
	echo "$cmd" > "$btrfs_path/$uuid/$uuid.cmd"
	cgcreate -g "$cgroups:/$uuid"
	: "${BOCKER_CPU_SHARE:=512}" && cgset -r cpu.shares="$BOCKER_CPU_SHARE" "$uuid"
	: "${BOCKER_MEM_LIMIT:=512}" && cgset -r memory.limit_in_bytes="$((BOCKER_MEM_LIMIT * 1000000))" "$uuid"
	cgexec -g "$cgroups:$uuid" \
		ip netns exec netns_"$uuid" \
		unshare -fmuip --mount-proc \
		chroot "$btrfs_path/$uuid" \
		/bin/sh -c "/bin/mount -t proc proc /proc && $cmd" \
		2>&1 | tee "$btrfs_path/$uuid/$uuid.log" || true
	ip link del dev veth0_"$uuid"
	ip netns del netns_"$uuid"
}

function bocker_exec() { #HELP اجرای یک دستور در کانتینر در حال اجرا:\nBOCKER exec <container_id> <command>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	cid="$(ps o ppid,pid | grep "^$(ps o pid,cmd | grep -E "^\ *[0-9]+ unshare.*$1" | awk '{print $1}')" | awk '{print $2}')"
	[[ ! "$cid" =~ ^\ *[0-9]+$ ]] && echo "Container '$1' exists but is not running" && exit 1
	nsenter -t "$cid" -m -u -i -n -p chroot "$btrfs_path/$1" "${@:2}"
}

function bocker_logs() { #HELP مشاهدهٔ گزارش‌های کانتینر:\nBOCKER logs <container_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	cat "$btrfs_path/$1/$1.log"
}

function bocker_commit() { #HELP ثبت کانتینر به‌صورت تصویر:\nBOCKER commit <container_id> <image_id>
	[[ "$(bocker_check "$1")" == 1 ]] && echo "No container named '$1' exists" && exit 1
	[[ "$(bocker_check "$2")" == 1 ]] && echo "No image named '$2' exists" && exit 1
	bocker_rm "$2" && btrfs subvolume snapshot "$btrfs_path/$1" "$btrfs_path/$2" > /dev/null
	echo "Created: $2"
}

function bocker_help() { #HELP نمایش این راهنما:\nBOCKER help
	sed -n "s/^.*#HELP\\s//p;" < "$1" | sed "s/\\\\n/\n\t/g;s/$/\n/;s!BOCKER!${1/!/\\!}!g"
}

[[ -z "${1-}" ]] && bocker_help "$0"
case $1 in
	pull|init|rm|images|ps|run|exec|logs|commit) bocker_"$1" "${@:2}" ;;
	*) bocker_help "$0" ;;
esac

نگاشت دستورها با داکر

بر اساس فهرست «عملکردهای پیاده‌سازی‌شده» در README مخزن، ارتباط دستورهای باکر با داکر به این صورت است:

  • bocker init <پوشه> — پیاده‌سازی بسیار محدودی از docker build †
  • bocker pull <نام> <برچسب> — معادل docker pull
  • bocker images — معادل docker images
  • bocker ps — معادل docker ps
  • bocker run — معادل docker run
  • bocker exec — معادل docker exec
  • bocker logs — معادل docker logs
  • bocker commit — معادل docker commit
  • bocker rm — معادل docker rm / docker rmi (هر دو با یک تابع)
  • شبکه (networking) و پشتیبانی سهم‌ها/گروه‌های کنترل (Quota Support / CGroups)

† در README تأکید شده که bocker init فقط پیاده‌سازی «بسیار محدودی» از docker build ارائه می‌دهد. همچنین دستورهایی مانند docker push، docker start و docker stop در باکر اصلاً وجود ندارند؛ کانتینرها فقط با run اجرا می‌شوند (اجرا و اتمام در یک گام) و به‌صورت ساب‌وولوم باقی می‌مانند.

محدودیت‌ها

خودِ README مخزن، صادقانه فهرست مواردی را که هنوز پیاده‌سازی نشده‌اند اعلام کرده است:

  • کانتینرهای حجم داده (Data Volume Containers) — پیاده‌سازی‌نشده.
  • حجم‌های داده (Data Volumes) — پیاده‌سازی‌نشده.
  • انتقال پورت (Port Forwarding) — پیاده‌سازی‌نشده (مثلاً -p 80:80 داکر معادلی در باکر ندارد؛ همهٔ کانتینرها از طریق پل به شبکهٔ ۱۰.۰.۰.۰/24 وصل می‌شوند).

محدودیت‌های دیگری که از بررسی کد و README برمی‌آید:

  • باکر باید به‌عنوان ریشه (root) اجرا شود و به شبکه، مسیریابی و قواعد iptables میزبان دست می‌زند؛ اجرای آن خارج از ماشین مجازی ریسک دارد.
  • جداسازی کامل‌تر مثل فضای نام کاربر (user namespace)، سوارسازی‌های /sys و /dev سفارشی و سیگنال‌های مدیریت چرخهٔ حیات (start/stop) ندارد.
  • آدرس‌دهی IP از سه رقم آخر شناسهٔ تصادفی کانتینر مشتق می‌شود؛ تعداد کانتینرهای هم‌زمانِ شبکه‌دار عملاً محدود و با ۲۵۲ آدرس زیرشبکهٔ ۱۰.۰.۰.۰/24 محدود است.
  • رجیستری v1 داکر (که bocker pull به آن متکی است) سال‌هاست بازنشسته شده؛ در عمل باید تصاویر را با bocker init از پوشهٔ محلی ساخت.

جمع‌بندی

باکر نشان می‌دهد که «کانتینر» یک فناوری عجیب و دست‌نیافتنی نیست؛ صرفاً ترکیب چند قابلیت قدیمی و سادهٔ هستهٔ لینوکس است:

  • فایل‌سیستم: ساب‌وولوم و عکس‌فوریِ btrfs با کپی‌هنگام‌نوشتن — لایه‌بندی تصویر/کانتینر (نقش overlayfs در داکر).
  • ایزوله‌سازی: unshare -fmuip --mount-proc برای فضاهای نام mount، UTS، IPC و PID + chroot برای ریشهٔ فایل‌سیستم.
  • شبکه: جفت‌رابط veth، فضای نام شبکه با ip netns، پل bridge0 و NAT با iptables.
  • منابع: cgroups با سهم پردازنده و سقف حافظه.
  • تصاویر: دانلود لایه‌های tar از رجیستری (protocol v1) و بازسازی شجرهٔ لایه‌ها.

هر یک از این مؤلفه‌ها در داکر واقعی بسیار کامل‌تر، امن‌تر و بهینه‌تر شده است؛ اما بذر اصلی همهٔ آن‌ها همین است. اگر می‌خواهید بفهمید داکر واقعاً چطور کار می‌کند، باکر بهترین نقطهٔ شروع است: ۱۰۰ خط bash که تمام استادان این حوزه توصیه می‌کنند یک‌بار بخوانیدش.
