شبیه‌سازی GameBoy در جاوااسکریپت

منبع اصلی: این صفحه ترجمهٔ فارسی سری «GameBoy Emulation in JavaScript» نوشتهٔ «عمران نظر (Imran Nazar)» است — یک سری ده‌قسمتی که از CPU شروع می‌کند و تا تایمرها پیش می‌رود. شبیه‌ساز کامل این سری در گیت‌هاب موجود است. نسخهٔ کامل و به‌روز را از سایت اصلی بخوانید.

مقدمه

اغلب گفته می‌شود که جاوااسکریپت یک زبان تخصصی است که برای وب‌سایت‌ها طراحی شده تا تعامل پویا را ممکن کند. اما جاوااسکریپت یک زبان شیءگرای کامل است و در عرصه‌هایی غیر از وب هم استفاده می‌شود: ویجت‌های نسخه‌های جدید ویندوز و macOS مک با جاوااسکریپت پیاده‌سازی شده‌اند، همان‌طور که GUI مجموعهٔ برنامه‌های Mozilla.

با معرفیِ اخیرِ تگ <canvas> به HTML، این سؤال مطرح می‌شود که آیا یک برنامهٔ جاوااسکریپتی قادر است سیستمی را شبیه‌سازی کند؛ درست مثل برنامه‌های دسکتاپی که برای شبیه‌سازی Commodore 64، GameBoy Advance و کنسول‌های بازی دیگر موجودند. ساده‌ترین راه برای چک‌کردن امکان‌پذیری این کار، نوشتن چنین شبیه‌سازی در جاوااسکریپت است.

این مقاله قصد دارد پایهٔ شبیه‌سازی گیم‌بوی را پیاده‌سازی کند، با فراهم‌کردن زمینهٔ شبیه‌سازی هر بخش از ماشین فیزیکی. نقطهٔ شروع، CPU است.

بخش ۱: CPU

مدل سنتی یک کامپیوتر، یک واحد پردازش است که برنامه‌ای از دستورالعمل‌ها به آن می‌گوید چه کند؛ برنامه ممکن است با حافظهٔ ویژهٔ خودش خوانده شود یا در همان ناحیهٔ حافظهٔ معمولی باشد. هر دستورالعمل مدت کوتاهی برای اجرا نیاز دارد و همه یکی‌یکی اجرا می‌شوند. از دیدگاه CPU، به محض روشن‌شدن کامپیوتر حلقه‌ای شروع می‌شود که دستورالعملی را از حافظه می‌گیرد، می‌فهمد چه می‌گوید و اجرایش می‌کند.

برای اینکه CPU بداند در برنامه کجاست، عددی به نام Program Counter (PC) نگه می‌دارد. بعد از گرفتن دستورالعمل از حافظه، PC به اندازهٔ بایت‌های سازندهٔ دستورالعمل جلو می‌رود.

شکل ۱: حلقهٔ fetch-decode-execute

CPU گیم‌بوی اصلی یک Zilog Z80 اصلاح‌شده است؛ بنابراین موارد زیر مطرح هستند:

  • Z80 یک تراشهٔ ۸ بیتی است؛ پس همهٔ کارهای داخلی یک بایت در یک زمان انجام می‌شود.
  • رابط حافظه می‌تواند تا ۶۵٬۵۳۶ بایت را آدرس‌دهی کند (گذرگاه آدرس ۱۶ بیتی).
  • برنامه‌ها از همان گذرگاه آدرسِ حافظهٔ معمولی خوانده می‌شوند.
  • یک دستورالعمل می‌تواند بین یک تا سه بایت باشد.

علاوه بر PC، اعداد دیگری داخل CPU نگه داشته می‌شوند که برای محاسبات قابل استفاده‌اند و «رجیستر» نامیده می‌شوند: A، B، C، D، E، H و L. هرکدام یک بایت‌اند؛ پس هرکدام می‌توانند مقداری از ۰ تا ۲۵۵ را نگه دارند. بیشتر دستورالعمل‌های Z80 برای کار با مقادیر این رجیسترها استفاده می‌شوند: بارگذاری مقداری از حافظه در یک رجیستر، جمع یا تفریق مقادیر و غیره.

اگر ۲۵۶ مقدار ممکن در بایت اول یک دستورالعمل وجود داشته باشد، یعنی ۲۵۶ دستورالعمل ممکن در جدول پایه وجود دارد. هرکدام را می‌توان با یک تابع جاوااسکریپتی شبیه‌سازی کرد که روی مدل داخلی رجیسترها کار می‌کند و روی مدل داخلی رابط حافظه اثر می‌گذارد.

رجیسترهای دیگری هم در Z80 وجود دارند که با وضعیت سروکار دارند: رجیستر پرچم (F) که عملیاتش را جلوتر بررسی می‌کنیم؛ و اشاره‌گر پشته (SP) که همراه دستورالعمل‌های PUSH و POP برای مدیریت سادهٔ LIFO مقدارها استفاده می‌شود. مدل پایهٔ شبیه‌سازی Z80 پس به این مؤلفه‌ها نیاز دارد:

  • یک وضعیت داخلی:
    • ساختاری برای نگهداشتن وضعیت فعلی رجیسترها.
    • مقدار زمان صرف‌شده برای اجرای آخرین دستورالعمل.
    • مقدار زمان کل اجرای CPU.
  • توابعی برای شبیه‌سازی هر دستورالعمل.
  • جدولی که این توابع را روی نقشهٔ اپ‌کد نگاشت کند.
  • یک رابط شناخته‌شده برای گفتگو با حافظهٔ شبیه‌سازی‌شده.

وضعیت داخلی را می‌توان این‌گونه نگه داشت:

Z80.js: مقادیر وضعیت داخلی

jsZ80 = {
    // ساعت: Z80 دو نوع ساعت دارد (m و t)
    _clock: {m:0, t:0},

    // مجموعه رجیستر
    _r: {
        a:0, b:0, c:0, d:0, e:0, h:0, l:0, f:0,    // رجیسترهای ۸ بیتی
        pc:0, sp:0,                                // رجیسترهای ۱۶ بیتی
        m:0, t:0                                   // ساعت برای دستور آخر
    }
};

رجیستر پرچم (F) برای عملکرد پردازنده مهم است: به‌صورت خودکار بیت‌های خاصی یا «پرچم»ها را بر اساس نتیجهٔ آخرین عملیات محاسبه می‌کند. چهار پرچم در Z80 گیم‌بوی وجود دارد:

  • Zero (0x80): اگر آخرین عملیات نتیجه‌ای برابر ۰ تولید کرده باشد تنظیم می‌شود.
  • Operation (0x40): اگر آخرین عملیات تفریق بود تنظیم می‌شود.
  • Half-carry (0x20): اگر در نتیجهٔ آخرین عملیات، نیمهٔ پایین بایت از ۱۵ سرریز کرده باشد تنظیم می‌شود.
  • Carry (0x10): اگر آخرین عملیات نتیجه‌ای بالای ۲۵۵ (برای جمع‌ها) یا زیر ۰ (برای تفریق‌ها) تولید کرده باشد تنظیم می‌شود.

چون رجیسترهای پایهٔ محاسبات ۸ بیتی‌اند، پرچم carry به نرم‌افزار اجازه می‌دهد بفهمد اگر نتیجهٔ یک محاسبه از رجیستر سرریز کند چه اتفاقی برای مقدار افتاده. با توجه به این مسائل پرچم، چند مثال از شبیه‌سازی دستورالعمل در زیر نشان داده شده است. این مثال‌ها ساده‌شده‌اند و پرچم half-carry را محاسبه نمی‌کنند.

Z80.js: شبیه‌سازی دستورالعمل‌ها

jsZ80 = {
    // وضعیت داخلی
    _clock: {m:0, t:0},
    _r: {a:0, b:0, c:0, d:0, e:0, h:0, l:0, f:0, pc:0, sp:0, m:0, t:0},

    // E را به A اضافه کن، نتیجه در A (ADD A, E)
    ADDr_e: function() {
        Z80._r.a += Z80._r.e;                      // انجام جمع
        Z80._r.f = 0;                              // پاک کردن پرچم‌ها
        if(!(Z80._r.a & 255)) Z80._r.f |= 0x80;    // چک برای صفر
        if(Z80._r.a > 255) Z80._r.f |= 0x10;       // چک برای carry
        Z80._r.a &= 255;                           // ماسک به ۸ بیت
        Z80._r.m = 1; Z80._r.t = 4;                // ۱ M-time گرفته
    }

    // B را با A مقایسه کن، پرچم‌ها را تنظیم کن (CP A, B)
    CPr_b: function() {
        var i = Z80._r.a;                          // کپی موقت از A
        i -= Z80._r.b;                             // کم کردن B
        Z80._r.f |= 0x40;                          // تنظیم پرچم تفریق
        if(!(i & 255)) Z80._r.f |= 0x80;           // چک برای صفر
        if(i < 0) Z80._r.f |= 0x10;                // چک برای زیرریز
        Z80._r.m = 1; Z80._r.t = 4;                // ۱ M-time گرفته
    }

    // بدون عملیات (NOP)
    NOP: function() {
        Z80._r.m = 1; Z80._r.t = 4;                // ۱ M-time گرفته
    }
};

رابط حافظه

پردازنده‌ای که بتواند رجیسترهای داخل خودش را دستکاری کند همهٔ خوب و خوش است، اما برای مفید بودن باید بتواند نتایج را در حافظه بگذارد. به همین ترتیب، شبیه‌سازی CPU بالا هم به رابطی با حافظهٔ شبیه‌سازی‌شده نیاز دارد؛ این رابط را یک واحد مدیریت حافظه (MMU) فراهم می‌کند. چون خود گیم‌بوی MMU پیچیده‌ای ندارد، واحد شبیه‌سازی‌شده می‌تواند خیلی ساده باشد.

در این نقطه، CPU فقط باید بداند رابطی وجود دارد؛ جزئیات اینکه گیم‌بوی چطور بانک‌های حافظه و سخت‌افزار را روی گذرگاه آدرس نگاشت می‌کند، برای عملکرد پردازنده بی‌ربط است. چهار عملیات مورد نیاز CPU است:

MMU.js: رابط حافظه

jsMMU = {
    rb: function(addr) { /* خواندن بایت ۸ بیتی از آدرس داده‌شده */ },
    rw: function(addr) { /* خواندن کلمهٔ ۱۶ بیتی از آدرس داده‌شده */ },

    wb: function(addr, val) { /* نوشتن بایت ۸ بیتی در آدرس داده‌شده */ },
    ww: function(addr, val) { /* نوشتن کلمهٔ ۱۶ بیتی در آدرس داده‌شده */ }
};

با این‌ها سر جایش، بقیهٔ دستورالعمل‌های CPU شبیه‌سازی می‌شوند. چند مثال دیگر در زیر:

Z80.js: دستورالعمل‌های مدیریت حافظه

js    // رجیسترهای B و C را روی پشته بگذار (PUSH BC)
    PUSHBC: function() {
        Z80._r.sp--;                               // پایین آمدن در پشته
        MMU.wb(Z80._r.sp, Z80._r.b);               // نوشتن B
        Z80._r.sp--;                               // پایین آمدن در پشته
        MMU.wb(Z80._r.sp, Z80._r.c);               // نوشتن C
        Z80._r.m = 3; Z80._r.t = 12;               // ۳ M-time گرفته
    },

    // رجیسترهای H و L را از پشته بردار (POP HL)
    POPHL: function() {
        Z80._r.l = MMU.rb(Z80._r.sp);              // خواندن L
        Z80._r.sp++;                               // بالا رفتن در پشته
        Z80._r.h = MMU.rb(Z80._r.sp);              // خواندن H
        Z80._r.sp++;                               // بالا رفتن در پشته
        Z80._r.m = 3; Z80._r.t = 12;               // ۳ M-time گرفته
    }

    // خواندن یک بایت از مکان مطلق در A (LD A, addr)
    LDAmm: function() {
        var addr = MMU.rw(Z80._r.pc);              // گرفتن آدرس از دستور
        Z80._r.pc += 2;                            // جلو بردن PC
        Z80._r.a = MMU.rb(addr);                   // خواندن از آدرس
        Z80._r.m = 4; Z80._r.t=16;                 // ۴ M-time گرفته
    }

Dispatch و ریست

با سرجای‌بودن دستورالعمل‌ها، قطعات باقی‌ماندهٔ پازل CPU این است که CPU هنگام راه‌اندازی ریست شود و دستورالعمل‌ها به روال‌های شبیه‌سازی تغذیه شوند. داشتن روال ریست به CPU اجازه می‌دهد متوقف و به شروع اجرا «برگشت» شود؛ مثالش در زیر:

Z80.js: ریست

js    reset: function() {
        Z80._r.a = 0; Z80._r.b = 0; Z80._r.c = 0; Z80._r.d = 0;
        Z80._r.e = 0; Z80._r.h = 0; Z80._r.l = 0; Z80._r.f = 0;
        Z80._r.sp = 0;
        Z80._r.pc = 0;      // شروع اجرا از 0

        Z80._clock.m = 0; Z80._clock.t = 0;
    }

برای اجرای شبیه‌سازی، باید توالی fetch-decode-execute که قبلاً توضیح داده شد شبیه‌سازی شود. «Execute» را توابع شبیه‌سازی دستورالعمل بر عهده دارند، اما fetch و decode به یک قطعهٔ کد تخصصی نیاز دارند که «حلقهٔ dispatch» نام دارد. این حلقه هر دستورالعمل را می‌گیرد، می‌فهمد برای اجرا باید به کجا فرستاده شود و آن را به تابع مربوطه dispatch می‌کند.

Z80.js: Dispatcher

jswhile(true)
{
    var op = MMU.rb(Z80._r.pc++);              // گرفتن دستورالعمل
    Z80._map[op]();                            // dispatch
    Z80._r.pc &= 65535;                        // ماسک PC به ۱۶ بیت
    Z80._clock.m += Z80._r.m;                  // افزودن زمان به ساعت CPU
    Z80._clock.t += Z80._r.t;
}

Z80._map = [
    Z80._ops.NOP,
    Z80._ops.LDBCnn,
    Z80._ops.LDBCmA,
    Z80._ops.INCBC,
    Z80._ops.INCr_b,
    ...
];

بخش ۲: حافظه

حافظهٔ کامپیوتر تقریباً همیشه ناحیهٔ سادهٔ پیوسته‌ای نیست؛ گیم‌بوی هم از این قاعده مستثنا نیست. چون CPU گیم‌بوی می‌تواند به ۶۵٬۵۳۶ مکان جداگانه روی گذرگاه آدرس دسترسی داشته باشد، می‌توان یک «نقشهٔ حافظه» از همهٔ ناحیه‌هایی که CPU به آن‌ها دسترسی دارد رسم کرد.

شکل ۱: نقشهٔ حافظهٔ گذرگاه آدرس گیم‌بوی

نگاهی دقیق‌تر به نواحی حافظه:

  • [0000-3FFF] ROM کارتریج، بانک ۰: ۱۶٬۳۸۴ بایت اول برنامهٔ کارتریج همیشه در این نقطه از نقشهٔ حافظه در دسترس است. شرایط خاص:
    • [0000-00FF] BIOS: وقتی CPU روشن می‌شود، PC از 0000h شروع می‌شود که شروع کد BIOS گیم‌بوی (۲۵۶ بایت) است. بعد از اجرای BIOS، از نقشهٔ حافظه حذف می‌شود و این ناحیه از ROM کارتریج قابل آدرس‌دهی می‌شود.
    • [0100-014F] هدر کارتریج: این بخش از کارتریج حاوی داده‌هایی دربارهٔ نام و سازندهٔ آن است و باید با فرمت خاصی نوشته شود.
  • [4000-7FFF] ROM کارتریج، سایر بانک‌ها: هر ۱۶ هزار «بانک» بعدی برنامهٔ کارتریج را می‌توان یکی‌یکی اینجا در دسترس CPU گذاشت؛ معمولاً تراشه‌ای روی کارتریج برای جابه‌جایی بین بانک‌ها و در دسترس‌کردن یک ناحیهٔ خاص استفاده می‌شود. کوچک‌ترین برنامه‌ها ۳۲ هزار‌اند، یعنی نیازی به تراشهٔ انتخاب بانک نیست.
  • [8000-9FFF] RAM گرافیک: داده‌های لازم برای پس‌زمینه‌ها و اسپرایت‌های زیرسیستم گرافیک اینجا نگهداری می‌شود و برنامهٔ کارتریج می‌تواند آن را تغییر دهد.
  • [A000-BFFF] RAM کارتریج (خارجی): مقدار کمی حافظهٔ نوشتنی در گیم‌بوی موجود است؛ اگر بازی‌ای به RAM بیشتری از موجود در سخت‌افزار نیاز داشته باشد، تکه‌های اضافی ۸ هزار RAM می‌توانند اینجا قابل آدرس‌دهی شوند.
  • [C000-DFFF] RAM کاری: ۸ هزار RAM داخلی گیم‌بوی که CPU می‌تواند آن را بخواند یا بنویسد.
  • [E000-FDFF] RAM کاری (سایه): به دلیل سیم‌بندی سخت‌افزار گیم‌بوی، یک کپی دقیق از RAM کاری ۸ هزار بالاتر در نقشهٔ حافظه موجود است.
  • [FE00-FE9F] گرافیک: اطلاعات اسپرایت: داده‌های اسپرایت‌های رندر شده توسط تراشهٔ گرافیک اینجا نگهداری می‌شود، از جمله موقعیت و ویژگی‌های اسپرایت‌ها.
  • [FF00-FF7F] I/O نگاشت‌شده به حافظه: هرکدام از زیرسیستم‌های گیم‌بوی (گرافیک، صدا و غیره) مقادیر کنترلی دارند تا برنامه‌ها بتوانند افکت بسازند و از سخت‌افزار استفاده کنند.
  • [FF80-FFFF] RAM صفحهٔ صفر: ناحیه‌ای پرسرعت از ۱۲۸ بایت RAM بالای حافظه است. عجیب اینکه با اینکه این «صفحهٔ» ۲۵۵ حافظه است، به آن صفحهٔ صفر می‌گویند چون بیشتر تعامل بین برنامه و سخت‌افزار گیم‌بوی از طریق همین صفحه انجام می‌شود.

رابط با CPU

برای اینکه CPU شبیه‌سازی‌شده بتواند به این نواحی جداگانه دسترسی داشته باشد، هرکدام باید در واحد مدیریت حافظه به‌صورت یک مورد خاص (special case) مدیریت شوند. پرکردن رابط می‌تواند به سادگی یک دستور switch باشد.

MMU.js: خواندن نگاشت‌شده

jsMMU = {
    // پرچم نشان‌دهندهٔ نگاشت BIOS
    // BIOS با اولین دستور بالای 0x00FF از نقشه حذف می‌شود
    _inbios: 1,

    // نواحی حافظه (در زمان ریست مقداردهی می‌شوند)
    _bios: [],
    _rom: [],
    _wram: [],
    _eram: [],
    _zram: [],

    // خواندن یک بایت از حافظه
    rb: function(addr)
    {
        switch(addr & 0xF000)
        {
            // BIOS (256b)/ROM0
            case 0x0000:
                if(MMU._inbios)
                {
                    if(addr < 0x0100)
                        return MMU._bios[addr];
                    else if(Z80._r.pc == 0x0100)
                        MMU._inbios = 0;
                }

                return MMU._rom[addr];

            // ROM0
            case 0x1000:
            case 0x2000:
            case 0x3000:
                return MMU._rom[addr];

            // ROM1 (بدون بانک) (16k)
            case 0x4000:
            case 0x5000:
            case 0x6000:
            case 0x7000:
                return MMU._rom[addr];

            // گرافیک: VRAM (8k)
            case 0x8000:
            case 0x9000:
                return GPU._vram[addr & 0x1FFF];

            // RAM خارجی (8k)
            case 0xA000:
            case 0xB000:
                return MMU._eram[addr & 0x1FFF];

            // RAM کاری (8k)
            case 0xC000:
            case 0xD000:
                return MMU._wram[addr & 0x1FFF];

            // سایهٔ RAM کاری
            case 0xE000:
                return MMU._wram[addr & 0x1FFF];

            // سایهٔ RAM کاری، I/O، RAM صفحهٔ صفر
            case 0xF000:
                switch(addr & 0x0F00)
                {
                    // سایهٔ RAM کاری
                    case 0x000: case 0x100: case 0x200: case 0x300:
                    case 0x400: case 0x500: case 0x600: case 0x700:
                    case 0x800: case 0x900: case 0xA00: case 0xB00:
                    case 0xC00: case 0xD00:
                        return MMU._wram[addr & 0x1FFF];

                    // گرافیک: حافظهٔ ویژگی اشیاء
                    // OAM ۱۶۰ بایت است؛ بقیهٔ بایت‌ها ۰ خوانده می‌شوند
                    case 0xE00:
                        if(addr < 0xFEA0)
                            return GPU._oam[addr & 0xFF];
                        else
                            return 0;

                    // صفحهٔ صفر
                    case 0xF00:
                        if(addr >= 0xFF80)
                        {
                            return MMU._zram[addr & 0x7F];
                        }
                        else
                        {
                            // مدیریت I/O
                            // فعلاً مدیریت نشده
                            return 0;
                        }
                }
        }
    },

    // خواندن یک کلمهٔ ۱۶ بیتی
    rw: function(addr)
    {
        return MMU.rb(addr) + (MMU.rb(addr+1) << 8);
    }
};

در بخش کد بالا باید توجه کرد که ناحیهٔ حافظه بین 0xFF00 و 0xFF7F مدیریت نشده است؛ این مکان‌ها به عنوان I/O نگاشت‌شده به حافظه برای تراشه‌های مختلفی که I/O فراهم می‌کنند استفاده می‌شوند و وقتی این سیستم‌ها در بخش‌های بعدی پوشش داده شوند تعریف خواهند شد.

نوشتن یک بایت به‌صورت بسیار مشابهی مدیریت می‌شود؛ هر عملیات برعکس می‌شود و مقادیر به‌جای برگرداندن از تابع، در نواحی مختلف حافظه نوشته می‌شوند. به همین دلیل نیازی به ارائهٔ بسط کامل تابع wb اینجا نیست.

بارگذاری ROM

درست همان‌طور که شبیه‌سازی CPU بدون عناصر پشتیبانش یعنی دسترسی حافظه، گرافیک و... بی‌فایده است، خواندن برنامه از حافظه هم بدون برنامهٔ بارگذاری‌شده بی‌فایده است. دو راه اصلی برای کشیدن برنامه به داخل شبیه‌ساز هست: سخت‌کدکردن آن در کد منبع شبیه‌ساز، یا اجازهٔ بارگذاری فایل ROM از یک مکان خاص. نقطه‌ضعف آشکار سخت‌کدکردن برنامه این است که ثابت است و نمی‌توان به‌راحتی عوضش کرد.

در مورد این شبیه‌ساز جاوااسکریپتی، BIOS گیم‌بوی در MMU سخت‌کد شده چون قرار نیست تغییر کند؛ اما فایل برنامه بعد از مقداردهی شبیه‌ساز، به‌صورت ناهمگام (asynchronous) از سرور بارگذاری می‌شود. این کار از طریق XMLHTTP با یک خوانندهٔ فایل باینری مثل BinFileReader اندی نا انجام می‌شود؛ نتیجهٔ آن رشته‌ای حاوی فایل ROM است.

بخش ۳: زمان‌بندی GPU

با اتصال پردازندهٔ شبیه‌سازی‌شده به ساختار نگاشت حافظه، حالا امکان اتصال جانبی‌ها به سیستم فراهم شده. یکی از جانبی‌های اصلی گیم‌بوی و هر کنسول بازی، پردازندهٔ گرافیک (GPU) است: روش اصلی خروجی کنسول است و بخش زیادی از کار پردازنده صرف تولید گرافیک برای GPU می‌شود.

شبیه‌سازی صفحه

نام داخلی نینتندو برای گیم‌بوی «Dot Matrix Game» است؛ نمایشگر آن یک LCD پیکسلی با ابعاد 160x144 است. اگر هر پیکسل LCD را یک پیکسل در یک <canvas> اچ‌تی‌ام‌ال۵ در نظر بگیریم، می‌توان نگاشت مستقیمی به کانواسی با عرض ۱۶۰ و ارتفاع ۱۴۴ ایجاد کرد. برای آدرس‌دهی مستقیم هر پیکسل LCD، محتوای کانواس را می‌توان به‌صورت «framebuffer» دستکاری کرد: یک بلوک واحد از حافظه شامل کل کانواس، به‌صورت یک سری مقدارهای RGBA چهاربایتی.

jsGPU = {
    _canvas: {},

گرافیک رستر

با وجود کانواسی برای دریافت خروجی گرافیکی گیم‌بوی، قدم بعدی شبیه‌سازی تولید گرافیک است. سخت‌افزار گیم‌بوی اصلی در زمان‌بندی‌هایش یک لامپ پرتوسوژه (CRT) را شبیه‌سازی می‌کند: در CRT، صفحه در ردیف‌ها توسط پرتو الکترونی اسکن می‌شود و فرایند اسکن بعد از پایان اسکن به بالای صفحه برمی‌گردد.

شکل ۱: اسکن‌لاین‌ها و دوره‌های blanking

همان‌طور که در بالا دیده می‌شود، CRT برای کشیدن یک اسکن‌لاین به زمان بیشتری از صرفاً عبور از روی پیکسل‌های مورد نظر نیاز دارد: یک دورهٔ «horizontal blanking» لازم است تا پرتو از انتهای یک خط به شروع خط بعدی برود. به همین ترتیب، پایان هر فریم یک دورهٔ «vertical blanking» دارد در حالی که پرتو به گوشهٔ بالا-چپ برمی‌گردد. چون پرتو در vertical blanking باید مسافت بیشتری طی کند، این دوره معمولاً خیلی طولانی‌تر از زمان blanking افقی است.

به همین ترتیب، نمایشگر گیم‌بوی دوره‌های blanking افقی و عمودی دارد. علاوه بر آن، زمان صرف‌شده در خودِ اسکن‌لاین به دو بخش تقسیم می‌شود: GPU بین دسترسی به حافظهٔ ویدیویی و دسترسی به حافظهٔ ویژگی اسپرایت در حین کشیدن اسکن‌لاین جابه‌جا می‌شود. برای این شبیه‌سازی، این دو بخش متمایزند و دنبال هم می‌آیند. جدول زیر نشان می‌دهد GPU در هر دوره چقدر می‌ماند، بر حسب ساعت T پردازنده که با فرکانس ۴٬۱۹۴٬۳۰۴ هرتز کار می‌کند:

برای حفظ این زمان‌بندی‌ها نسبت به CPU شبیه‌سازی‌شده، باید تابع به‌روزرسانی زمان وجود داشته باشد که بعد از اجرای هر دستورالعمل صدا زده شود. این کار را می‌توان از نسخهٔ بسط‌یافتهٔ فرایند dispatch CPU که در بخش ۱ پوشش داده شد انجام داد.

بخش ۴: گرافیک

درست مثل بیشتر کنسول‌های آن دوران، گیم‌بوی حافظهٔ کافی برای نگهداشتن framebuffer مستقیم در حافظه نداشت. در عوض، سیستم تایل به کار گرفته می‌شود: مجموعه‌ای از بیت‌مپ‌های کوچک در حافظه نگهداری می‌شود و نقشه‌ای با ارجاع به این بیت‌مپ‌ها ساخته می‌شود. مزیت ذاتی این سیستم این است که یک تایل را می‌توان بارها در نقشه استفاده کرد، فقط با ارجاع به آن.

سیستم گرافیک تایل‌محور گیم‌بوی با تایل‌های 8x8 پیکسلی کار می‌کند و ۲۵۶ تایل یکتا را می‌توان در یک نقشه استفاده کرد؛ دو نقشه از تایل‌های 32x32 را می‌توان در حافظه نگه داشت و یکی از آن‌ها در هر زمان برای نمایش استفاده می‌شود. جایی در حافظهٔ گیم‌بوی برای ۳۸۴ تایل هست؛ پس نیمی از آن‌ها بین نقشه‌ها مشترک‌اند: یک نقشه از شماره‌های تایل ۰ تا ۲۵۵ و دیگری از اعداد بین ۱۲۸- تا ۱۲۷ برای تایل‌هایش استفاده می‌کند.

شکل ۱: نگاشت پس‌زمینه

نقشهٔ پس‌زمینه همان‌طور که قبلاً اشاره شد 32x32 تایل است؛ یعنی 256 در 256 پیکسل. نمایشگر گیم‌بوی 160x144 پیکسل است، پس جا برای جابه‌جایی پس‌زمینه نسبت به صفحه هست. GPU این کار را با تعریف نقطه‌ای در پس‌زمینه که با گوشهٔ بالا-چپ صفحه متناظر است انجام می‌دهد: با جابه‌جایی این نقطه بین فریم‌ها، پس‌زمینه روی صفحه اسکرول می‌شود. به همین دلیل، تعریف گوشهٔ بالا-چپ توسط دو رجیستر GPU نگه داشته می‌شود: Scroll X و Scroll Y.

پالت‌ها

گیم‌بوی اغلب به‌عنوان ماشینی تک‌رنگ توصیف می‌شود که فقط سیاه و سفید را نمایش می‌دهد. این کاملاً درست نیست: گیم‌بوی می‌تواند خاکستری روشن و تیره را هم مدیریت کند؛ مجموعاً چهار رنگ. نمایش یکی از این چهار رنگ در دادهٔ تایل دو بیت می‌گیرد؛ پس هر تایل در مجموعهٔ دادهٔ تایل در (8x8x2) بیت یا ۱۶ بایت نگهداری می‌شود.

پیاده‌سازی: دادهٔ تایل

همان‌طور که در بالا گفته شد، هر پیکسل در مجموعهٔ دادهٔ تایل با دو بیت نمایش داده می‌شود: این بیت‌ها وقتی تایل در نقشه ارجاع داده شود توسط GPU خوانده، از پالت عبور داده و به صفحه فرستاده می‌شوند. سخت‌افزار GPU طوری سیم‌کشی شده که یک ردیف کامل از تایل همزمان قابل دسترسی است و پیکسل‌ها با عبور از بیت‌ها چرخانده می‌شوند. تنها مشکل این است که یک ردیف تایل دو بایت است: از همین‌جا طرح کمی پیچیدهٔ ذخیره‌سازی بیت‌ها نتیجه می‌شود که در آن بیت پایین هر پیکسل در یک بایت و بیت بالا در بایت دیگر نگهداری می‌شود.

شکل ۴: ساختار بیت‌مپ دادهٔ تایل

چون جاوااسکریپت برای دستکاری سریع ساختارهای بیت‌مپی مناسب نیست، زمان‌کارآمدترین راه برای مدیریت مجموعهٔ دادهٔ تایل، نگهداشتن یک مجموعهٔ دادهٔ داخلی در کنار حافظهٔ ویدیویی است، با نمایی بسط‌یافته که مقدار هر پیکسل از قبل محاسبه شده. برای اینکه این دقتاً منعکس‌کنندهٔ مجموعهٔ دادهٔ تایل باشد، هر نوشتن در RAM ویدیویی باید تابع را برای به‌روزرسانی دادهٔ تایل داخلی GPU تحریک کند.

            }
        }
    },

    // مجموعهٔ دادهٔ تایل داخلی را به‌روز می‌کند
    updatetile: function(addr, val)
    {
        // گرفتن «آدرس پایه» برای این ردیف تایل
        addr &= 0x1FFE;

        // محاسبهٔ اینکه کدام تایل و ردیف به‌روز شده
        var tile = (addr >> 4) & 511;
        var y = (addr >> 1) & 7;

        var sx;
        for(var x = 0; x < 8; x++)
        {
            // پیدا کردن ایندکس بیت برای این پیکسل
            sx = 1 << (7-x);

            // به‌روزرسانی مجموعه تایل
            GPU._tileset[tile][y][x] =
                ((GPU._vram[addr] & sx)   ? 1 : 0) +
                ((GPU._vram[addr+1] & sx) ? 2 : 0);
        }
    }

پیاده‌سازی: رندر اسکن

با سرجای‌بودن این قطعات، امکان شروع رندر صفحهٔ گیم‌بوی فراهم شده. چون این کار خط‌به‌خط انجام می‌شود، تابع renderscan که در بخش ۳ به آن ارجاع شد باید قبل از رندر یک اسکن‌لاین بفهمد روی صفحه کجاست. این کار شامل محاسبهٔ مختصات X و Y موقعیت در نقشهٔ پس‌زمینه با استفاده از رجیسترهای اسکرول و شمارندهٔ اسکن‌لاین فعلی است. وقتی مشخص شد، رندرکنندهٔ اسکن می‌تواند از هر تایل آن ردیف از نقشه عبور کند و هنگام رسیدن به هر تایل، دادهٔ تایل جدید را وارد کند.

GPU.js: رندر اسکن

js    renderscan: function()
    {
        // آفست VRAM برای نقشهٔ تایل
        var mapoffs = GPU._bgmap ? 0x1C00 : 0x1800;

        // کدام خط تایل در نقشه استفاده شود
        mapoffs += ((GPU._line + GPU._scy) & 255) >> 3;

        // با کدام تایل در خط نقشه شروع شود
        var lineoffs = (GPU._scx >> 3);

        // کدام خط پیکسل در تایل‌ها استفاده شود
        var y = (GPU._line + GPU._scy) & 7;

        // از کجای خط تایل شروع کنیم
        var x = GPU._scx & 7;

        // کجا روی کانواس رندر شود
        var canvasoffs = GPU._line * 160 * 4;

        // خواندن ایندکس تایل از نقشهٔ پس‌زمینه
        var colour;
        var tile = GPU._vram[mapoffs + lineoffs];

        // اگر مجموعهٔ تایل در حال استفاده شمارهٔ ۱ است،
        // ایندکس‌ها علامت‌دارند؛ آفست تایل واقعی را محاسبه کن
        if(GPU._bgtile == 1 && tile < 128) tile += 256;

        for(var i = 0; i < 160; i++)
        {
            // پیکسل تایل را از پالت عبور بده
            colour = GPU._pal[GPU._tileset[tile][y][x]];

            // رسم پیکسل روی کانواس
            GPU._scrn.data[canvasoffs+0] = colour[0];
            GPU._scrn.data[canvasoffs+1] = colour[1];
            GPU._scrn.data[canvasoffs+2] = colour[2];
            GPU._scrn.data[canvasoffs+3] = colour[3];
            canvasoffs += 4;

            // وقتی این تایل تمام شد، یکی دیگر بخوان
            x++;
            if(x == 8)
            {
                x = 0;
                lineoffs = (lineoffs + 1) & 31;
                tile = GPU._vram[mapoffs + lineoffs];
                if(GPU._bgtile == 1 && tile < 128) tile += 256;
            }
        }
    }

بخش ۵: یکپارچه‌سازی

در بخش ۴ زیرسیستم گرافیک گیم‌بوی با جزئیات بررسی و شبیه‌سازی شد. بدون مجموعه‌ای از نگاشت رجیستر برای GPU که در نرم‌افزار مدیریت شود، زیرسیستم گرافیک نمی‌تواند توسط شبیه‌ساز استفاده شود؛ وقتی این رجیسترها در دسترس قرار گیرند، شبیه‌ساز عملاً برای استفادهٔ پایه آماده است.

جدول ۲: رجیستر کنترل GPU

در جدول بالا ویژگی‌های اضافهٔ GPU ظاهر می‌شوند: لایهٔ «ویندو» که می‌تواند بالای پس‌زمینه ظاهر شود، و اشیاء اسپرایت که می‌توانند نسبت به پس‌زمینه و ویندو جابه‌جا شوند. این ویژگی‌های اضافه وقتی نیازشان پیش آمد پوشش داده می‌شوند؛ فعلاً پرچم‌های پس‌زمینه برای توابع رندر پایه مهم‌ترین‌اند. مخصوصاً اینجا دیده می‌شود که چطور می‌توان نقشهٔ تایل و مجموعهٔ تایل پس‌زمینه را صرفاً با چرخاندن بیت‌ها در رجیستر 0xFF40 تغییر داد.

پیاده‌سازی: رجیسترهای GPU

با داشتن چیدمان مفهومی رجیستر GPU، می‌توان شبیه‌سازی را به‌سادگی با افزودن مدیریت‌کننده‌هایی برای این آدرس‌ها به MMU پیاده کرد. این کار یا با سخت‌کدکردن به‌روزرسانی‌های GPU در MMU انجام می‌شود، یا با تعریف بازه‌ای از رجیسترها که در آن GPU از MMU صدا زده شود تا مدیریت تخصصی‌تر از آنجا انجام شود. در راستای پیمان‌گرایی (modularity)، رویکرد دوم انتخاب شده.

اجرای یک فریم

در حال حاضر حلقهٔ dispatch پردازندهٔ شبیه‌ساز برای همیشه و بدون توقف اجرا می‌شود. ساده‌ترین رابط برای یک شبیه‌ساز اجازهٔ ریست یا توقف (pause) شبیه‌سازی را می‌دهد؛ برای این منظور، باید مقدار زمان مشخصی به‌عنوان واحد پایهٔ رابط شبیه‌ساز استفاده شود. سه واحد زمان ممکن است برای این کار استفاده شود:

  • دستورالعمل: فراهم‌کردن امکان توقف بعد از هر دستورالعمل CPU. این کار سربار زیادی دارد چون تابع dispatch باید برای هر گامی که CPU برمی‌دارد صدا زده شود؛ در ۴/۱۹ مگاهرتز، برای اینکه اتفاق قابل توجهی بیفتد باید گام‌های زیادی برداشته شود.
  • اسکن‌لاین: توقف بعد از رندر هر خط توسط GPU. سربار کمتری دارد، اما dispatcher باید هنوز چند هزار بار در ثانیه صدا زده شود؛ علاوه بر آن، شبیه‌سازی می‌تواند در حالتی متوقف شود که نمایش کانواس با اسکن‌لاین فعلی مطابقت ندارد.
  • فریم: اجازهٔ توقف شبیه‌سازی بعد از شبیه‌سازی، رندر و ارسال یک فریم کامل به کانواس. بهترین سازش دقت زمان‌بندی و سرعت بهینه را فراهم می‌کند، در حالی که مطمئن می‌شود کانواس شبیه‌سازی‌شده با وضعیت GPU سازگار است.

چون یک فریم از ۱۴۴ اسکن‌لاین و ۱۰ خط vertical blank ساخته شده و هر اسکن‌لاین ۴۵۶ چرخهٔ ساعت طول می‌کشد، طول یک فریم ۷۰٬۲۲۴ ساعت است. همراه با یک تابع ریست در سطح شبیه‌ساز که هر زیرسیستم را در شروع شبیه‌سازی مقداردهی می‌کند، خود شبیه‌ساز قابل اجراست و رابط اولیه‌ای فراهم می‌شود.

بخش ۶: ورودی

با شبیه‌ساز و رابط کارکننده که در پنج بخش قبلی توسعه یافته، سیستم شبیه‌سازی قادر است یک ROM تست پایه را اجرا و خروجی گرافیکی تولید کند. کاری که شبیه‌ساز فعلاً قادر به انجامش نیست این است که فشردن کلیدها را به‌عنوان ورودی صفحه‌کلید بگیرد و آن‌ها را به ROM در حال تست تحویل دهد؛ برای این کار، باید تأثیر صفحه‌کلید روی رجیسترهای I/O شبیه‌سازی شود.

صفحه‌کلید

گیم‌بوی یک روش ورودی دارد: یک صفحهٔ هشت‌کلیدی که هر تعداد کلید آن می‌تواند فشرده باشد. در بیشتر صفحه‌کلیدها، کلیدها در شبکه‌ای از ستون‌ها و ردیف‌ها چیده شده‌اند: این‌ها را می‌توان سیم‌هایی در نظر گرفت که یک کلید می‌تواند بین آن‌ها اتصال برقرار کند. وقتی یکی از ستون‌ها فعال می‌شود، هر ردیفی که به آن ستون متصل است هم فعال می‌شود و سخت‌افزار می‌تواند ردیف‌های فعال را برای تعیین کلیدهای فشردهٔ فعلی شناسایی کند.

در گیم‌بوی، شبکهٔ صفحه‌کلید دو ستون و چهار ردیف دارد، که مزیتش این است که همهٔ اتصال‌های لازم را می‌توان در یک رجیستر I/O هشت‌بیتی برقرار کرد.

شکل ۲: سیم‌بندی صفحه‌کلید

چون هر شش خط به یک رجیستر بسته شده‌اند، رویهٔ گیم‌بوی برای خواندن یک کلید کمی پیچیده است:

  • 0x10 یا 0x20 را به JOYP بنویس: این کار بیت ۴ یا ۵، یکی از خطوط ستون، را فعال می‌کند.
  • چند چرخه صبر کن تا اتصال‌های ردیف به JOYP منتشر شود.
  • چهار بیت پایین JOYP را چک کن تا بفهمی کدام ردیف‌ها برای این ستون فعال بودند.

پیاده‌سازی صفحه‌کلید

نوشتن کدی برای شبیه‌سازی فشردن کلیدها نسبتاً ساده است، اما دو عامل کار را پیچیده می‌کند: اجازه برای تنظیم یک ستون در شبکه قبل از خواندن ردیف‌ها، و کدهای فشردن کلید که جاوااسکریپت استفاده می‌کند. برای تطبیق دو ستون، باید دو مقدار توسط شبیه‌سازی استفاده شود که هرکدام محل تلاقی‌های آن ستون با ردیف‌ها را نگه می‌دارند. یک عامل اضافه که باید در نظر گرفته شود این است که مقادیر برای صفحه‌کلید معکوس‌اند: یک ردیف به‌طور پیش‌فرض در ولتاژ بالا رها شده و وقتی با یک ستون تلاقی می‌کند به ولتاژ صفر می‌رسد. رجیستر I/O این را به‌صورت بیت‌های ردیفِ ۱ برای کلید فشرده‌نشده و ۰ برای فشردن کلید تفسیر می‌کند.

از رویدادهای جاوااسکریپتی keydown و keyup می‌توان برای فهمیدن زمان فشرده یا رهاشدن کلید استفاده کرد؛ وصل‌کردن این‌ها به مدیریت‌کنندهٔ صفحه‌کلید به شکل زیر انجام می‌شود:

بخش ۷: اسپرایت‌ها

قبلاً در این سری، شبیه‌ساز بسط یافت تا ورودی صفحه‌کلید را ممکن کند، یعنی بازی دوز قابل انجام شد. مشکلی که از این جا ماند این بود که بازی باید کورکورانه انجام می‌شد: هیچ نشانه‌ای از اینکه حرکت بعدی کجا انجام می‌شود نبود، نه اینکه فشردن کلید شما را در بازی به کجا می‌برد. کنسول‌های بازی دو بعدی سنتی این مسئله را با استفاده از اسپرایت‌ها حل کرده‌اند: بلوک‌های شیء متحرکی که می‌توانند مستقل از پس‌زمینه قرار بگیرند و داده‌ای جدا از دادهٔ پس‌زمینه دارند.

گیم‌بوی هم از این قاعده مستثنا نیست: امکان قراردادن اسپرایت‌ها بالای یا پایین پس‌زمینه و چند اسپرایت همزمان روی صفحه را فراهم می‌کند.

مقدمه: اسپرایت‌های گیم‌بوی

اسپرایت‌های گیم‌بوی تایل‌های گرافیکی‌اند، درست مثل تایل‌های استفاده‌شده برای پس‌زمینه: یعنی هر اسپرایت 8x8 پیکسل است. همان‌طور که در بالا گفته شد، اسپرایت را می‌توان هرجای صفحه قرار داد، از جمله نیمه‌راه یا کاملاً خارج از صفحه، و می‌توان آن را بالای یا پایین پس‌زمینه قرار داد. معنای فنی این چیز آن است که اسپرایت‌های زیرِ پس‌زمینه جایی که پس‌زمینه مقدار رنگ ۰ دارد، نمایان می‌شوند.

شکل ۲: اولویت‌های اسپرایت

در شکل بالا، اسپرایت بالای پس‌زمینه، پس‌زمینه را از وسطش نشان می‌دهد چون این پیکسل‌های اسپرایت روی رنگ ۰ تنظیم شده‌اند؛ به همین ترتیب، پس‌زمینه اجازه می‌دهد اسپرایت‌های زیر آن جایی که رنگ پس‌زمینه ۰ است عبور کنند. برای شبیه‌سازی این در یک شبیه‌ساز، ساده‌ترین رویه رندر اسپرایت‌های زیر پس‌زمینه، سپس خود پس‌زمینه و در نهایت اسپرایت‌های بالای آن است. اما این الگوریتم تا حدی ساده‌لوحانه است چون فرایند رندر اسپرایت را تکرار می‌کند؛ ساده‌تر است که اول پس‌زمینه کشیده شود و بعد بر اساس اولویت اسپرایت و رنگ پس‌زمینه در آن موقعیت، مشخص شود آیا پیکسل مورد نظر از اسپرایت باید ظاهر شود یا نه.

رندر اسپرایت‌ها

سیستم گرافیک گیم‌بوی هر خط صفحه را در حالی که به آن می‌رسد رندر می‌کند: این شامل نه‌تنها پس‌زمینه، بلکه اسپرایت‌های زیر و بالای آن می‌شود. به عبارت دیگر، رندر اسپرایت‌ها باید به رندرکنندهٔ اسکن‌لاین اضافه شود، به‌عنوان فرایندی که بعد از کشیدن پس‌زمینه اتفاق می‌افتد. درست مثل پس‌زمینه، سوئیچی برای فعال‌کردن اسپرایت‌ها در رجیستر LCDC هست و باید به مدیریت I/O برای GPU اضافه شود.

چون اسپرایت می‌تواند هرجای صفحه باشد، از جمله خارج از صفحه، رندرکننده باید چک کند کدام اسپرایت‌ها در محدودهٔ اسکن‌لاین فعلی قرار دارند. ساده‌ترین الگوریتم این است که موقعیت هرکدام چک و اگر در محدودهٔ اسکن‌لاین بود، خط مناسبِ اسپرایت رندر شود. دادهٔ اسپرایت را می‌توان به همان روشِ پس‌زمینه، از طریق مجموعهٔ تایلِ از پیش محاسبه‌شده، بازیابی کرد. نمونه‌ای از کنارهم‌چیدن این موارد:

                GPU._scrn.data[canvasoffs+2] = colour[2];
                GPU._scrn.data[canvasoffs+3] = colour[3];
                canvasoffs += 4;

                // ذخیرهٔ پیکسل برای چک‌کردن بعدی
                scanrow[i] = GPU._tileset[tile][y][x];

                // وقتی این تایل تمام شد، یکی دیگر بخوان
                x++;
                if(x == 8)
                {
                    x = 0;
                    lineoffs = (lineoffs + 1) & 31;
                    tile = GPU._vram[mapoffs + lineoffs];
                    if(GPU._bgtile == 1 && tile < 128) tile += 256;
                }
            }
        }

        // رندر اسپرایت‌ها اگر روشن هستند
        if(GPU._switchobj)
        {
            for(var i = 0; i < 40; i++)
            {
                var obj = GPU._objdata[i];

                // چک کن این اسپرایت روی این اسکن‌لاین می‌افتد یا نه
                if(obj.y <= GPU._line && (obj.y + 8) > GPU._line)
                {
                    // پالتی که برای این اسپرایت استفاده شود
                    var pal = obj.pal ? GPU._pal.obj1 : GPU._pal.obj0;

                    // کجا روی کانواس رندر شود
                    var canvasoffs = (GPU._line * 160 + obj.x) * 4;

                    // دادهٔ این خط از اسپرایت
                    var tilerow;

                    // اگر اسپرایت Y-flip شده،
                    // از طرف مقابل تایل استفاده کن
                    if(obj.yflip)
                    {
                        tilerow = GPU._tileset[obj.tile]
                                          [7 - (GPU._line - obj.y)];
                    }
                    else
                    {
                        tilerow = GPU._tileset[obj.tile]
                                          [GPU._line - obj.y];
                    }

                    var colour;
                    var x;

                    for(var x = 0; x < 8; x++)
                    {
                        // اگر این پیکسل هنوز روی صفحه است، و
                        // رنگ ۰ (شفاف) نیست، و
                        // این اسپرایت اولویت دارد یا زیر پس‌زمینه نمایش داده می‌شود
                        // آنگاه پیکسل را رندر کن
                        if((obj.x + x) >= 0 && (obj.x + x) < 160 &&
                           tilerow[x] &&
                           (obj.prio || !scanrow[obj.x + x]))
                        {
                            // اگر اسپرایت X-flip شده،
                            // پیکسل‌ها را به ترتیب معکوس بنویس
                            colour = pal[tilerow[obj.xflip ? (7-x) : x]];

                            GPU._scrn.data[canvasoffs+0] = colour[0];
                            GPU._scrn.data[canvasoffs+1] = colour[1];
                            GPU._scrn.data[canvasoffs+2] = colour[2];
                            GPU._scrn.data[canvasoffs+3] = colour[3];

                            canvasoffs += 4;
                        }
                    }
                }
            }

بخش ۸: وقفه‌ها

در بخش قبلی، پایه‌های شبیه‌سازی یک بازی با معرفی اسپرایت‌ها فراهم شد. اما یک جنبه از شبیه‌ساز جا مانده بود: وقفهٔ vertical blanking. در این بخش، وقفه‌ها به‌طور کلی معرفی و وقفهٔ blanking به‌طور خاص پیاده می‌شود؛ وقتی این کار انجام شود، شبیه‌ساز تتریس را اجرا خواهد کرد.

تصور کنید کامپیوتری با کارت شبکه دارید و نرم‌افزاری که داده‌های شبکه را پردازش می‌کند. از دیدگاه کامپیوتر، داده فقط هر چند وقت یک بار می‌آید، پس به راهی نیاز دارید که نرم‌افزار بفهمد دادهٔ جدید رسیده. دو راه برای این اتفاق وجود دارد:

  • Polling: نرم‌افزار هر چند وقت یک بار از کارت شبکه می‌پرسد دادهٔ جدید رسیده یا نه. این روش ساده‌لوحانه‌ای است اما معایبی دارد:
    • نرم‌افزار تا چک دوره‌ای‌اش از دادهٔ جدید بی‌خبر است، یعنی تأخیر بین رسیدن داده به کامپیوتر و مدیریت آن توسط نرم‌افزار هست.
    • باید به‌صورت دوره‌ای زمان برای چک‌ها کنار گذاشته شود، که حتی اگر داده‌ای نرسیده باشد وقت را از کارهای دیگر می‌گیرد.
    • اگر فرایند polling هر بار که چک می‌کند یک قطعه دادهٔ جدید را مدیریت کند اما داده با سرعت بیشتری می‌رسد، پشت‌کار در کارت شبکه ایجاد می‌شود و احتمال از دست رفتن داده هست.
    • اگر کار دیگری نباشد، نرم‌افزار همچنان باید چک کند، که کامپیوتر را با سرعت کامل و بدون کاری نگه می‌دارد.
  • وقفه‌ها (Interrupts): کارت شبکه به نرم‌افزار خبر می‌دهد دادهٔ جدید رسیده. این روش دریافت دادهٔ پیچیده‌تری است و مراحل بیشتری دارد، اما همهٔ معایب polling را برطرف می‌کند:
    • دادهٔ جدید به محض رسیدن قابل پردازش است، بدون تأخیر بین رسیدن و مدیریت.
    • نرم‌افزار فقط وقتی باید وقت صرف کند که قطعاً داده‌ای برای مدیریت هست، و روال‌های پردازش را می‌توان به هر تعداد لازم برای پاک‌کردن پشت‌کارها صدا زد.
    • اگر کار دیگری نباشد، کامپیوتر می‌تواند وارد حالت کم‌مصرف شود تا کارت شبکه برای دادهٔ جدید بیدارش کند.

وقفه‌ها و مدیریت‌کننده‌های وقفه

واضح است که مفهوم وقفه‌ها مفید است، اما هم سخت‌افزار و هم نرم‌افزار باید شرایطی برای کارکردن وقفه‌ها داشته باشند. از نظر سخت‌افزار، CPU باید وقتی وقفه‌ای می‌رسد موقتاً اجرای کارش را متوقف کند و به‌جایش اجرای یک مدیریت‌کنندهٔ وقفه (گاهی روال سرویس وقفه یا ISR نامیده می‌شود) را شروع کند. در سناریوی بالا، سیمی بین کارت شبکه و CPU کشیده می‌شود تا کارت بتواند وقتی داده رسیده به CPU خبر دهد.

شکل ۲: پیاده‌سازی سخت‌افزاری وقفه‌ها

CPU ورودی‌های وقفه‌اش را در پایان هر دستورالعمل چک می‌کند. اگر سیگنال وقفه توسط جانبی متصلی مثل کارت شبکه داده شده باشد، CPU برای شروع مدیریت‌کنندهٔ وقفه گام‌هایی برمی‌دارد: CPU جایی که اجرای عادی را رها کرده ذخیره می‌کند، واقعیتِ وقوع وقفه را ثبت می‌کند و به سمت مدیریت‌کننده پرش می‌کند.

بیشتر CPUها یک «پرچم اصلی» برای وقفه‌ها دارند: وقفه‌ها فقط وقتی CPU آن‌ها را مدیریت می‌کند که این پرچم فعال باشد. Z80 گیم‌بوی هم از این قاعده مستثنا نیست، اما رجیسترهای اضافه‌ای هم وجود دارند که با وقفه‌های منفرد گیم‌بوی سروکار دارند. این‌ها رجیسترهای حافظه‌اند، پس توسط واحد مدیریت حافظه مدیریت می‌شوند:

با سرجای‌بودن پرچم‌های وقفه، حلقهٔ اجرای اصلی را می‌توان دوباره توسعه داد تا بیشتر با مسیر اجرا از شکل ۳ هماهنگ شود. بعد از اجرا، پرچم‌های وقفه باید چک شوند تا ببینیم وقفهٔ فعال‌شده‌ای رخ داده یا نه؛ اگر رخ داده، مدیریت‌کننده‌اش فراخوانی می‌شود.

بخش ۹: بانک‌بندی حافظه

تا اینجا در این سری، با بارگذاری و شبیه‌سازی یک نقشهٔ حافظهٔ ساده برای گیم‌بوی سروکار داشتیم، با کل ROM بازی که در نیمهٔ پایین حافظه جا می‌شد. بازی‌های زیادی نیستند که کامل در حافظه جا شوند (تتریس یکی از معدودهاست)؛ بیشتر بازی‌ها بزرگ‌تر از این‌اند و باید از مکانیزمی مستقل برای جابه‌جا کردن «بانک»های ROM بازی در دید CPU گیم‌بوی استفاده کنند.

بعضی از اولین بازی‌های کتابخانهٔ گیم‌بوی با یک کنترل‌کنندهٔ بانک حافظه (MBC) داخل کارتریج ساخته شده‌اند که این کارِ جابه‌جایی بانک‌های ROM در دید را انجام می‌دهد؛ در طول سال‌ها نسخه‌های مختلفی از MBC کارتریج برای بازی‌های به‌طور فزاینده بزرگ ساخته شده. در مثال خاص دموی مرتبط با این بخش، از نسخهٔ اول MBC برای مدیریت بارگذاری یک ROM 64kB استفاده می‌شود.

بانک‌بندی و توسعهٔ حافظه

در طول سال‌ها، بسیاری از سیستم‌های کامپیوتری مجبور بوده‌اند با مشکلِ زیادیِ برنامه برای جا‌شدن در حافظه کنار بیایند. سنتی، دو راه برای حل این مشکل بوده:

  • افزایش فضای آدرس: ساخت CPU جدید با خطوط آدرس بیشتر، که به آن اجازه دهد حافظهٔ بزرگ‌تری را ببیند و بفهمد. این راه‌حل ترجیحی است، اما زمان قابل توجهی برای توسعهٔ دوبارهٔ سیستم کامپیوتری مورد نظر نیاز دارد و ممکن است به تغییرات بیشتری در چیپ‌ست پشتیبان CPU نیاز باشد.
  • حافظهٔ مجازی: این می‌تواند به نگهداشتن تکه‌های RAM روی دیسک و جابه‌جا کردن آن‌ها در صورت نیاز اشاره کند؛ یا جابه‌جا کردن تکه‌های ROMِ از پیش نوشته‌شده در صورت نیاز. در هر دو مورد، سخت‌افزار سیستم نیاز کمی به بسط دارد اما هر نرم‌افزاری برای سیستم باید از سیستم صفحه‌بندی/بانک‌بندی آگاه باشد تا بتواند از آن استفاده کند.

چون گیم‌بوی یک پلتفرم سخت‌افزاری ثابت با توزیع گسترده است، وقتی بازی‌های بزرگ‌تری تولید می‌شوند راهی برای افزایش فضای آدرس نیست؛ در عوض، کنترل‌کنندهٔ بانک حافظهٔ ساخته‌شده در کارتریج راهی برای جابه‌جا کردن بانک‌های 16kB از ROM در دید ارائه می‌دهد. علاوه بر این، MBC1 از حداکثر 32kB «RAM خارجی» پشتیبانی می‌کند که حافظهٔ نوشتنی کارتریج است؛ اگر موجود باشد می‌تواند در فضای [A000-BFFF] نقشهٔ حافظه بانک‌بندی شود.

برای تسهیل نرم‌افزاری که از MBC1 استفاده می‌کند، اولین بانک 16kB از ROM (بانک ۰) در آدرس 0000 ثابت است؛ نیمهٔ دوم فضای ROM را می‌توان پنجره‌ای روی هر بانک ROM بین ۱ و ۱۲۷ کرد، برای حداکثر اندازهٔ ROM 2048kB. یکی از عجیب‌غریب‌های MBC1 این است که داخلی با ۳۲ها سروکار دارد: بانک‌های شمارهٔ ۳۲، ۶۴ و ۹۶ غیرقابل دسترسی‌اند چون در سیستم بانک‌بندی به‌عنوان بانک ۰ رفتار می‌شوند. یعنی ۱۲۵ بانک به‌جز بانک ثابت ۰ قابل استفاده‌اند.

چهار رجیستر در تراشهٔ MBC1 وجود دارد که امکان جابه‌جا کردن بانک‌ها برای ROM و RAM را می‌دهند؛ این‌ها را می‌توان با نوشتن در فضای (معمولاً فقط‌خواندنی) ROM در هر جای یک محدودهٔ خاص تغییر داد. جزئیات در جدول زیر:

کنترل‌کننده‌های بانک حافظه دستکاریِ بدیهی حافظه‌اند و بنابراین به‌خوبی در MMU جا می‌شوند. چون اولین بانک ROM (بانک شمارهٔ ۰) ثابت است، فقط باید آفستی برای MBC نگهداری شود که مشخص کند برای بانک دوم از کجا می‌خواند. برای اینکه بعداً مدیریت MBC بیشتری اضافه شود، می‌توان از آرایه‌ای از داده برای نگهداشتن وضعیت یک کنترل‌کنندهٔ مشخص استفاده کرد:

بخش ۱۰: تایمرها

از وقتی اولین کامپیوترها ساخته شدند، یکی از کارکردهای پایه‌شان نگهداشتن زمان بوده: هماهنگ‌کردن کارها بر اساس تایمرها. حتی ساده‌ترین بازی‌ها هم عنصری از زمان دارند: پونگ مثلاً باید توپ را با نرخ مشخصی روی صفحه حرکت دهد. برای مدیریت این مسائل زمان‌بندی، هر کنسول بازی نوعی تایمر دارد تا چیزها در یک لحظهٔ مشخص یا با نرخ مشخصی اتفاق بیفتند.

گیم‌بوی هم از این قاعده مستثنا نیست و مجموعه‌ای رجیستر دارد که بر اساس برنامه‌ای قابل برنامه‌ریزی به‌صورت خودکار افزایش می‌یابد. در این بخش، ساختار و عملکرد تایمر بررسی می‌شود و اینکه چطور می‌توان از آن برای seed کردن مولدهای عدد شبه‌تصادفی استفاده کرد، مثل مولد موجود در تتریس و کلون‌هایش.

ساختار تایمر

CPU گیم‌بوی، همان‌طور که در بخش اول این سری توضیح داده شد، با ساعتی ۴٬۱۹۴٬۳۰۴ هرتزی کار می‌کند و دو اندازهٔ داخلی زمانِ صرف‌شده برای اجرای هر دستورالعمل دارد: ساعت T که با هر گام ساعت افزایش می‌یابد، و ساعت M که با یک‌چهارم سرعت (۱٬۰۴۸٬۵۷۶ هرتز) افزایش می‌یابد. این ساعت‌ها به‌عنوان منبع تایمر استفاده می‌شوند که به نوبهٔ خود با یک‌چهارم نرخ ساعت M شمارش می‌کند: ۲۶۲٬۱۴۴ هرتز. در این مقاله به این مقدار آخر «سرعت پایهٔ» تایمر می‌گویم.

سخت‌افزار تایمر گیم‌بوی دو رجیستر تایمر جداگانه ارائه می‌دهد: سیستم با افزایش مقدار هرکدام از این رجیسترها با نرخ از پیش تعیین‌شده کار می‌کند. تایمر «تقسیم‌کننده» (divider) به‌طور دائم روی افزایش با 16384Hz تنظیم شده، یک‌شانزدهم سرعت پایه؛ چون فقط یک رجیستر هشت‌بیتی است، مقدارش بعد از رسیدن به ۲۵۵ به صفر برمی‌گردد. تایمر «شمارنده» (counter) برنامه‌پذیرتر است: می‌توان آن را روی یکی از چهار سرعت (سرعت پایه تقسیم بر ۱، ۴، ۱۶ یا ۶۴) تنظیم کرد و می‌توان آن را طوری کرد که وقتی از ۲۵۵ سرریز می‌شود به مقداری که صفر نیست برگردد. علاوه بر این، سخت‌افزار تایمر هر وقت «شمارنده» سرریز شود یک وقفه به CPU می‌فرستد، همان‌طور که در بخش ۸ توضیح داده شد.

چهار رجیستر توسط تایمر استفاده می‌شود؛ این‌ها به‌عنوان بخشی از صفحهٔ I/O در دسترس سیستم قرار می‌گیرند، درست مثل رجیسترهای گرافیک و وقفه:

آدرسرجیسترجزئیات
0xFF04تقسیم‌کننده (Divider)با نرخ ثابت 16384Hz شمارش می‌کند؛ با هر نوشتن به 0 ریست می‌شود
0xFF05شمارنده (Counter)با نرخ مشخص‌شده شمارش می‌کند؛ هنگام رفتن از 255 به 0 وقفهٔ INT 0x50 را تحریک می‌کند
0xFF06مدولو (Modulo)وقتی شمارنده به 0 سرریز می‌شود، برای شروع از Modulo ریست می‌شود
0xFF07کنترل (Control)بیت‌های 0-1: سرعت (00: 4096Hz، 01: 262144Hz، 10: 65536Hz، 11: 16384Hz)؛ بیت 2: در حال اجرا (1 = اجرای تایمر، 0 = توقف)؛ بیت‌های 3-7: استفاده‌نشده

جدول ۱: رجیسترهای تایمر

چون تایمر «شمارنده» وقتی سرریز می‌شود وقفه‌ای تحریک می‌کند، اگر بازی نیاز داشته باشد چیزی در بازهٔ منظم اتفاق بیفتد می‌تواند مخصوصاً مفید باشد. اما یک بازی گیم‌بوی عموماً می‌تواند از vertical blank به همان شکل استفاده کند، چون با سرعت منظمِ تقریباً ۶۰ هرتز رخ می‌دهد؛ مدیریت‌کنندهٔ vertical blanking را می‌توان نه‌تنها برای بازنشانی محتوای صفحه، بلکه برای چک صفحه‌کلید و به‌روزرسانی وضعیت بازی استفاده کرد. بنابراین در بازی‌های سنتی گیم‌بوی چندان نیازی به استفاده از تایمر نیست، اگرچه در دموهای گرافیکی می‌تواند مؤثرتر استفاده شود.

پیاده‌سازی شبیه‌سازی تایمر

شبیه‌سازی توسعه‌یافته در این سری مقاله‌ها از ساعت CPU به‌عنوان واحد پایهٔ زمان استفاده می‌کند. به همین دلیل، ساده‌ترین کار نگهداشتن ساعتی برای تایمر است که همگام با ساعت CPU کار می‌کند و توسط تابع dispatch به‌روز می‌شود. راحت است در این مرحله رجیستر DIV را به‌عنوان موجودیتی جدا از تایمر کنترل‌شدنی نگه داریم که با یک‌شانزدهم سرعتِ سریع‌ترین گام تایمر افزایش می‌یابد:

Timer.js: افزایش ساعت

jsTIMER = {
    _clock: {
        main: 0,
        sub:  0,
        div:  0
    },

    _reg: {
        div:  0,
        tima: 0,
        tma:  0,
        tac:  0
    },

    inc: function()
    {
        // افزایش بر اساس زمان آخرین اپ‌کد
        TIMER._clock.sub += Z80._r.m;

        // هیچ اپ‌کدی بیشتر از ۴ M-time طول نمی‌کشد،
        // پس فقط یک‌بار چک سرریز لازم است
        if(TIMER._clock.sub >= 4)
        {
            TIMER._clock.main++;
            TIMER._clock.sub -= 4;

            // رجیستر DIV با یک‌شانزدهم نرخ افزایش می‌یابد،
            // پس شمارنده‌ای برای این نگه دار
            TIMER._clock.div++;
            if(TIMER._clock.div == 16)
            {
                TIMER._reg.div = (TIMER._reg.div+1) & 255;
                TIMER._clock.div = 0;
            }
        }

        // چک کن آیا گامی در تایمر لازم است
        TIMER.check();
    }
};

Seed کردن یک مولد عدد شبه‌تصادفی

مؤلفهٔ اصلی بسیاری از بازی‌ها غیرقابل پیش‌بینی بودن است: تتریس مثلاً الگوی ناشناخته‌ای از قطعات را به داخل چاه پرتاب می‌کند و بازی از ساختن ردیف‌ها با این قطعات تشکیل شده. در حالت ایده‌آل، کامپیوتر با تولید اعداد تصادفی غیرقابل پیش‌بینی بودن را فراهم می‌کند، اما این برخلاف ماهیت منظم کامپیوتر است؛ امکان ندارد کامپیوتر الگوی واقعاً تصادفی از اعداد تولید کند. الگوریتم‌های مختلفی برای تولید دنباله‌هایی از اعداد وجود دارد که سطحی شبیه تصادفی به نظر می‌رسند؛ به این‌ها الگوریتم‌های مولد عدد *شبه*تصادفی (PRNG) می‌گویند.

PRNG معمولاً به‌صورت فرمولی پیاده می‌شود که با دریافت عدد ورودی خاص، عدد دیگری با تقریباً هیچ رابطه‌ای با ورودی تولید می‌کند. برای تتریس، چیز پیچیده‌ای لازم نیست؛ در عوض، کد زیر برای تولید یک بلوک به‌ظاهر تصادفی استفاده می‌شود:

Tetris.asm: انتخاب بلوک جدید

asmBLK_NEXT = 0xC203
BLK_CURR = 0xC213
REG_DIV  = 0x04

NBLOCK: ld hl, BLK_CURR        ; بلوک بعدی را
        ld a, (BLK_NEXT)       ; به جلو به بلوک فعلی بیاور
        ld (hl),a
        and 0xFC               ; هر چرخش‌ای را پاک کن
        ld c,a                 ; و قبلی را نگه دار

        ld h,3                 ; ۳ بار زیر را امتحان کن

.seed:  ldh a, (REG_DIV)       ; یک seed «تصادفی» بگیر
        ld b,a
.loop:  xor a                  ; در هفت‌تایی‌ها پایین بیا
.seven: dec b                  ; تا به صفر برسیم
        jr z, .next            ; این حلقه معادل
        inc a                  ; (a%7)*4 است
        inc a
        inc a
        inc a
        cp 28
        jr z, .loop
        jr .seven

.next:  ld e,a                 ; مقدار جدید را کپی کن
        dec h                  ; اگر این آخرین
        jr z, .end             ; تلاش است، همین را استفاده کن
        or c                   ; وگرنه با بلوک قبلی
        and 0xFC               ; چک کن
        cp c                   ; اگر دوباره همان است،
        jr z, .seed            ; عدد تصادفی دیگری امتحان کن
.end:   ld a,e                 ; کپی را برگردان
        ld (BLK_NEXT), a       ; این بلوک بعدی ماست

پایهٔ انتخاب‌کنندهٔ بلوک تتریس رجیستر DIV است: چون روال انتخاب فقط هر چند ثانیه یک بار اجرا می‌شود، رجیستر در هر اجرای مشخص مقدار ناشناخته‌ای خواهد داشت و بنابراین تقریب منصفانه‌ای از منبع عدد تصادفی می‌سازد. با شبیه‌سازی سیستم تایمر، تتریس و کلون‌هایش را می‌توان با عملکرد کامل شبیه‌سازی کرد.

یک جنبه از شبیه‌سازی بازی که تا حالا نادیده گرفته شده، تولید صدا و همگام‌سازی صدا با سرعت شبیه‌سازی است. بخش بعدی این سری مسائل مربوط به سازوکارهای خروجی صدا را بررسی می‌کند.
