پایگاه دادهٔ اختصاصی خودت را با C# بساز

مقدمه

با مشکلی مواجه شدم: باید یک میلیون رکورد از داده‌های دلخواه با اندازه‌های بین ۱ تا ۸ کیلوبایت را طوری ذخیره می‌کردم که بتوانم در سریع‌ترین زمان ممکن — درست مثل دسترسی مستقیم به دیسک — داده‌هایم را پیدا کنم، جست‌وجو کنم، بخوانم و روی آن‌ها پیمایش کنم.

هرچند Sqlite در ابتدا بسیار سریع است، اما به‌دلیل استفادهٔ ناکارآمد از فضا از آن خوشم نمی‌آید؛ ضمن اینکه وقتی داده‌های زیادی نوشته و/یا حذف می‌شوند، به‌مرور زمان به‌شدت کند می‌شود. Sqlite همچنین داده‌ها و نمایه‌ها (indexes) را در یک فایل واحد با هم ترکیب می‌کند و این موضوع پیمایش خطی را به تجربه‌ای وحشتناک تبدیل می‌کند؛ به‌ویژه وقتی رکوردها حذف می‌شوند، حفره‌هایی باقی می‌مانند که تا زمانی که دستور vacuum() را فراخوانی نکنید هرگز پر نمی‌شوند. دربارهٔ مشکلات sqlite در این مقالهٔ موزیلا بیشتر بخوانید.

پس تصمیم گرفتم پایگاه داده‌ای بسازم که به اندازهٔ Sqlite سریع باشد، اما با گذشت زمان کند نشود، فضای حذف‌شده را بهتر بازیافت کند و به vacuum() هم نیازی نداشته باشد.

کد منبع کامل پیاده‌سازی‌شده در این‌جا در گیت‌هاب قابل دانلود است (البته پیشنهاد می‌کنم قبل از نگاه کردن به کد، مقاله را کامل بخوانید).

اهداف (Goals)

  1. برای ساده‌تر شدن کار، هدف بسیار مشخصی تعیین کردم: پایگاه داده‌ای برای ذخیرهٔ گاوها ساختم که در آن CowModel این‌گونه تعریف شده است:
csharppublic class CowModel
{
    public Guid Id { get; set; }
    public string Breed { get; set; }
    public int Age { get; set; }
    public string Name { get; set; }
    public byte[] DnaData { get; set; }
}

همان‌طور که می‌بینید، اندازهٔ ویژگی‌های Breed، Name و DnaData ناشناخته است؛ این موضوع پروژه را چالش‌برانگیزتر می‌کند، زیرا پایگاه داده باید با داده‌های طول‌متغیر (variable-length) کار کند.

  1. نتیجهٔ نهایی یک DLL سی‌شارپ واحد خواهد بود که می‌توانیم مستقیماً در هر پروژهٔ اصلی به آن وصل شویم؛ با رابط (interface) زیر که به ما امکان تعامل با پایگاه داده را می‌دهد.

توجه کنید که همهٔ عملیات خواندن/جست‌وجو/حذف، موردی (ad-hoc) هستند (یعنی از نمایه‌ها استفاده می‌کنند):

csharppublic interface ICowDatabase
{
    void Insert (CowModel cow);
    void Delete (CowModel cow);
    void Update (CowModel cow);
    CowModel Find (Guid id);  // موردی (Adhoc)
    IEnumerable<CowModel> FindBy (string breed, int age); // موردی (Adhoc)
}

قلمرو پروژه (Scope)

این یک پایگاه دادهٔ ساده است که تنها ۲۴ تا ۳۲ ساعت کار می‌برد؛ هدف اصلی آن کارایی و یادگیری نحوهٔ کار پایگاه داده‌هاست، تا بتوانید نمونهٔ اختصاصی خودتان را بسازید.

ویژگی‌هایی مانند سازگاری ACID، نوشتن تراکنشی/اتمی (transaction/atomic write) و پشتیبانی از چند کاربر در این نسخه گنجانده نشده‌اند؛ اما طراحی به‌گونه‌ای است که راه برای پیاده‌سازی آن‌ها باز است.

طراحی (The Design)

A. ذخیره‌سازی بلوکی (Block Storage)

داده‌های خود را در یک فایل واحد ذخیره می‌کنیم. نمایه‌ها به‌صورت جداگانه و هرکدام در یک فایل مستقل نگهداری می‌شوند.

برای اینکه پایگاه داده بتواند فضای داده‌های حذف‌شده را بازیافت کند، به‌جای آنکه فایل پایگاه داده را به‌صورت یک جریان (Stream) ببینیم، داده‌ها را به‌صورت بلوک‌های (blocks) منفرد با اندازهٔ یکسان در نظر می‌گیریم. این کار حداقل اندازه‌ای را تضمین می‌کند که فضای استفاده‌نشده قابل بازیافت باشد.

اندازهٔ یک بلوک انتخاب شماست؛ اما اندازهٔ بلوک معمول در سیستم‌های فایل ۴ کیلوبایت است که سیستم‌عامل داده‌ها را در بلوک‌های ۴ کیلوبایتی می‌خواند و می‌نویسد؛ بنابراین اندازهٔ بلوک خود را ۲۵۶ بایت، ۵۱۲ بایت، ۱۰۲۴ بایت و... انتخاب کنید تا پایگاه داده شما با اندازهٔ بلوک سیستم فایل زیرین هم‌تراز (aligned) باشد.

ما به این لایه BlockStorage می‌گوییم. من اندازهٔ بلوک را ۴ کیلوبایت انتخاب می‌کنم، چون داده‌های دی‌ان‌ای گاوهای من نسبتاً حجیم است.

محتوای یک بلوک می‌تواند هر چیزی باشد؛ یک بلوک کاری به چیزی که ذخیره می‌کند ندارد. بلوک از سرآیند (header) فراداده (metadata) هم پشتیبانی می‌کند، تا بعداً بتوانیم چیزهایی مانند ارجاع به بلوک‌های دیگر، اندازهٔ محتوای واقعیِ در حال استفادهٔ یک بلوک و موارد مشابه را در آن ذخیره کنیم.

به لایهٔ ذخیره‌سازی بلوکی با استفاده از رابط زیر دسترسی خواهیم داشت:

csharppublic interface IBlockStorage
{
    /// <summary>
    /// تعداد بایت‌های دادهٔ سفارشی در هر بلوک که این مخزن می‌تواند مدیریت کند
    /// </summary>
    int BlockContentSize {
        get;
    }

    /// <summary>
    /// تعداد کل بایت‌های سرآیند
    /// </summary>
    int BlockHeaderSize {
        get;
    }

    /// <summary>
    /// اندازهٔ کل بلوک، برابر با اندازهٔ محتوا + اندازهٔ سرآیند؛ باید مضربی از 128B باشد
    /// </summary>
    int BlockSize {
        get;
    }

    /// <summary>
    /// پیدا کردن یک بلوک با شناسهٔ آن
    /// </summary>
    IBlock Find (uint blockId);

    /// <summary>
    /// تخصیص بلوک جدید؛ طول مخزن زیرین را افزایش می‌دهد
    /// </summary>
    IBlock CreateNew ();
}

public interface IBlock : IDisposable
{
    /// <summary>
    /// شناسهٔ بلوک؛ باید یکتا باشد
    /// </summary>
    uint Id {
        get;
    }

    /// <summary>
    /// یک بلوک ممکن است یک یا چند فرادادهٔ سرآیند داشته باشد؛
    /// هر سرآیند با یک عدد و یک مقدار ۸ بایتی شناسایی می‌شود
    /// </summary>
    long GetHeader (int field);

    /// <summary>
    /// تغییر مقدار سرآیند مشخص‌شده
    /// داده نباید تا قبل از آزادسازی (dispose) بلوک روی دیسک نوشته شود
    /// </summary>
    void SetHeader (int field, long value);

    /// <summary>
    /// خواندن محتوای این بلوک (src) در بافر داده‌شده (dst)
    /// </summary>
    void Read (byte[] dst, int dstOffset, int srcOffset, int count);

    /// <summary>
    /// نوشتن محتوای بافر داده‌شده (src) در این بلوک (dst)
    /// </summary>
    void Write (byte[] src, int srcOffset, int dstOffset, int count);
}

B. ذخیره‌سازی رکورد (Record Storage)

ذخیره‌سازی بلوکی نیاز «متغیر بودن طول داده‌ها» را برآورده نمی‌کند.

برای پشتیبانی از رکوردهای طول‌متغیر — مانند CowModel که طول ویژگی‌های Breed، Name و DnaData ناشناخته است — لایهٔ دیگری روی ذخیره‌سازی بلوکی اضافه می‌کنیم که «ذخیره‌سازی رکورد» نامیده می‌شود.

در این‌جا، یک رکورد از یک یا چند بلوک ساخته می‌شود که به‌صورت مرتب در کنار هم قرار می‌گیرند. به عبارت دیگر، یک Record یک فهرست پیوندی (linked list) از بلوک‌هاست.

یک رکورد ممکن است از کل یک بلوک برای ذخیرهٔ داده‌هایش استفاده کند یا فقط بخشی از یک بلوک را؛ که در میدان length سرآیند فرادادهٔ بلوک تعریف می‌شود. (بعداً به پیاده‌سازی آن می‌رسیم.)

یک رکورد همچنین دارای یک شناسه (ID) است که همان شناسهٔ اولین بلوکی است که رکورد از آن ساخته شده است.

یک بلوک را می‌توان با استفاده از یکی از میدان‌های سرآیند فراداده‌اش، به‌صورت منطقی حذف‌شده علامت‌گذاری کرد. همچنین از یک رکورد ویژه، یعنی رکورد شمارهٔ ۰ (اولین رکورد) برای نگهداری یک پشته (stack) از شناسه‌های بلوک‌های حذف‌شده استفاده خواهیم کرد. حذف یک رکورد با علامت‌گذاری منطقی بلوک‌هایش به‌عنوان حذف‌شده انجام می‌شود و سپس شناسهٔ آن بلوک‌ها روی پشتهٔ رکورد شمارهٔ ۰ «فشارده» (push) می‌شود. این امکان بازیافت فضای بلوک‌های استفاده‌نشده را فراهم می‌کند: هنگام ساخت رکورد جدید، رکورد شمارهٔ ۰ خوانده می‌شود و یک شناسهٔ آزاد (اگر موجود باشد) از پشته «بیرون کشیده» (pop) شده و دوباره استفاده می‌شود.

روش استفاده از ذخیره‌سازی رکورد به این صورت است:

csharppublic interface IRecordStorage
{
    /// <summary>
    /// به‌روزرسانی مؤثر یک رکورد
    /// </summary>
    void Update (uint recordId, byte[] data);

    /// <summary>
    /// گرفتن داده‌های یک رکورد
    /// </summary>
    byte[] Find (uint recordId);

    /// <summary>
    /// ساخت یک رکورد جدیدِ خالی
    /// </summary>
    uint Create ();

    /// <summary>
    /// ساخت یک رکورد جدید با دادهٔ داده‌شده و بازگرداندن شناسهٔ آن
    /// </summary>
    uint Create (byte[] data);

    /// <summary>
    /// مشابه Create(byte[] data)، اما با dataGenerator که داده را
    /// پس از تخصیص رکورد تولید می‌کند
    /// </summary>
    uint Create (Func<uint, byte[]> dataGenerator);

    /// <summary>
    /// حذف یک رکورد با شناسهٔ آن
    /// </summary>
    void Delete (uint recordId);
}

C. نمایه‌سازی (Indexing)

نمایه‌سازی امکان جست‌وجوی رکوردها بر اساس ویژگی‌هایشان را فراهم می‌کند (مثلاً پیدا کردن گاو با Id، پیدا کردن گاوها با breed)؛ البته می‌توانید با پیمایش در رکوردها آنچه می‌خواهید را پیدا کنید، اما وقتی بیش از چند صد رکورد داشته باشید این کار بسیار ناکارآمد خواهد بود.

درخت B (B-Tree) محبوب‌ترین ساختار داده برای ساخت نمایه در یک پایگاه داده است. اگر با درخت B یا ساختار درخت به‌طور کلی آشنایی ندارید، می‌توانید مزایای آن را به‌صورت یک List<Tuple<K, V>> که بر اساس K مرتب شده است تجسم کنید؛ در آن K کلید نمایه (مانند ID یا Breed گاو) و V شناسهٔ رکوردها در RecordStorage است که در بالا ذکر شد. این به شما امکان می‌دهد روی کلید K یک جست‌وجوی دودویی (BinarySearch) انجام دهید و بلافاصله موقعیت V را برگردانید؛ صرف‌نظر از اینکه فهرست چقدر بزرگ است.

برای اطلاعات بیشتر دربارهٔ درخت B یا ساختار درخت، خواندن این موارد را پیشنهاد می‌کنم: درخت دودویی (Binary Tree)، درخت جست‌وجوی دودویی (Binary Search Tree)، درخت جست‌وجوی دودویی خودمتعادل (Self-Balance Binary Search Tree)، درخت قرمز-سیاه (Red Black Tree) و درخت B (B-Tree).

فعلاً تنها چیزی که باید بدانیم این است که نمایه‌ها جفت‌های کلید-مقدار (Key-Value) ذخیره می‌کنند؛ در آن‌ها Key ویژگی‌های CowModel ما و Value شناسهٔ رکورد داده‌های ماست. این کار نه‌تنها امکان جست‌وجوی فوری مقدار به‌ازای کلید را فراهم می‌کند (مثل یک Dictionary)، بلکه می‌توان موقعیت یک کلید دلخواه K را پیدا کرد و از K به همهٔ کلیدهای دیگر، چه با ترتیب صعودی چه نزولی، پیمایش کرد.

درخت B از گره‌های (nodes) منفردی ساخته می‌شود و هر گره ارجاعاتی به گره‌های دیگر نگه می‌دارد. ما نمایه را با سریال‌سازی (serialize) هر گره به یک رکورد ذخیره می‌کنیم و از RecordStorage طراحیشدهٔ خودمان استفاده می‌کنیم. هر نمایه در یک فایل جداگانه قرار دارد.

وقتی به یک Node نیاز داریم، محتوای باینری آن را می‌خوانیم و آن را در یک Node سریال‌زدایی (deserialize) می‌کنیم، تغییرات را اعمال می‌کنیم و سپس آن را دوباره به آرایهٔ بایتی سریال‌سازی کرده و به‌صورت رکورد ذخیره می‌کنیم.

برای بهترین کارایی، یک Node باید دقیقاً در یک بلوک ۴ کیلوبایتی جا شود. برای این کار می‌توانیم تعداد ورودی‌های هر Node را تنظیم کنیم.

روش استفاده از نمایه (Index) به این صورت است:

csharppublic interface IIndex<K, V>
{
    /// <summary>
    /// ساخت ورودی جدید در این نمایه که کلید K را به مقدار V نگاشت می‌کند
    /// </summary>
    /// <param name="key">کلید</param>
    /// <param name="value">مقدار</param>
    void Insert (K key, V value);

    /// <summary>
    /// پیدا کردن یک ورودی با کلید
    /// </summary>
    /// <param name="key">کلید</param>
    Tuple<K, V> Get (K key);

    /// <summary>
    /// پیدا کردن همهٔ ورودی‌هایی که کلیدشان بزرگ‌تر یا مساوی کلید مشخص‌شده است
    /// </summary>
    IEnumerable<Tuple<K, V>> LargerThanOrEqualTo (K key);

    /// <summary>
    /// پیدا کردن همهٔ ورودی‌هایی که کلیدشان بزرگ‌تر از کلید مشخص‌شده است
    /// </summary>
    IEnumerable<Tuple<K, V>> LargerThan (K key);

    /// <summary>
    /// پیدا کردن همهٔ ورودی‌هایی که کلیدشان کوچک‌تر یا مساوی کلید مشخص‌شده است
    /// </summary>
    IEnumerable<Tuple<K, V>> LessThanOrEqualTo (K key);

    /// <summary>
    /// پیدا کردن همهٔ ورودی‌هایی که کلیدشان کوچک‌تر از کلید مشخص‌شده است
    /// </summary>
    IEnumerable<Tuple<K, V>> LessThan (K key);

    /// <summary>
    /// حذف یک ورودی از این نمایه؛ به‌صورت اختیاری با IComparer مشخص‌شده برای مقایسهٔ مقادیر
    /// </summary>
    /// <param name="key">کلید</param>
    /// <param name="value">مقدار</param>
    /// <param name="valueComparer">مقایسه‌کنندهٔ مقدار؛ مقدار پیش‌فرض Comparer[k].Default است</param>
    bool Delete (K key, V value, IComparer<V> valueComparer = null);

    /// <summary>
    /// حذف همهٔ ورودی‌های کلید داده‌شده
    /// </summary>
    /// <param name="key">کلید</param>
    bool Delete (K key);
}

D. کنار هم گذاشتن قطعات (Putting Things Together)

IRecordStorage و یک یا چند IIndex را کنار هم قرار می‌دهیم تا یک پایگاه دادهٔ کامل بسازیم. چون این دو رابط پیاده‌سازی شده‌اند، کار چندانی باقی نمانده است:

  1. درج یک رکورد در پایگاه داده با ساخت یک رکورد در IRecordStorage.Create() انجام می‌شود که یک uint ID برمی‌گرداند؛ سپس از این شناسه برای نمایه‌سازی در IIndex استفاده می‌شود.
  2. به‌روزرسانی یک رکورد، نمایهٔ مربوطه را نیز به‌روز می‌کند.
  3. حذف یک رکورد، ورودی آن را نیز از IIndex حذف می‌کند.
  4. جست‌وجوی یک رکورد هر زمان که ممکن باشد از IIndex استفاده می‌کند. وقتی هیچ‌کدام از نمایه‌ها قابل استفاده نباشند، در همهٔ ورودی‌های نمایهٔ اصلی پیمایش می‌کنیم (پیمایش کامل نمایه).

پیاده‌سازی (Implementation)

کد منبع ضمیمه شده است. همچنین می‌توانید پیاده‌سازی من را در گیت‌هاب پیدا کنید.

بیایید پایگاه داده را «FooDB» بنامیم؛ کد منبع اصلی آن در FooCore قرار دارد و همراه آن تست‌های واحد (unit tests) در FooTest است؛ برنامهٔ Cow ما که از FooDB برای ساخت CowDatabase خود استفاده می‌کند نیز در FooApplication است.

A. پیاده‌سازی BlockStorage

کلاس‌های جالب برای بررسی:

  1. FooCore/BlockStorage.cs
  2. FooCore/Block.cs

از آنجا که BlockStorage هیچ وابستگی‌ای ندارد، پیاده‌سازی آن ساده و سرراست است.

ساخت بلوک‌های جدید (Creating New Blocks)

  • BlockStorage فقط با یک Stream به‌عنوان وابستگی مقداردهی اولیه می‌شود.
  • BlockStorage طول stream را هنگام مقداردهی اولیه، مضربی از blockSize مشخص‌شده نگه می‌دارد. وقتی کلاینت درخواست ساخت یک بلوک جدید می‌کند، صرفاً طول Stream زیرین را افزایش می‌دهد.

پیدا کردن یک بلوک (Finding a Block)

  • هر بلوک با یک شناسهٔ یکتا شناسایی می‌شود که همان موقعیت آن درون Stream است. برای مثال، اگر طول Stream شما ۴۰۹۶ بایت و blockSize برابر ۱۰۲۴ بایت باشد، ۴ بلوک خواهید داشت: ۰، ۱، ۲ و ۳.
  • به‌سادگی می‌توانید به بلوک شمارهٔ ۳ بروید: با تنظیم موقعیت stream روی ۳ × ۱۰۲۴ = ۳۰۷۲.

خواندن و نوشتن در یک بلوک (Reading and Writing to a Block)

  • پیاده‌سازی بلوک، متدهای Read() و Write() را برای کار با محتوای بلوک فراهم می‌کند. آن‌ها صرفاً پوسته‌های ساده‌ای دور خواندن و نوشتن آرایهٔ بایتی از/به Stream زیرین هستند.
  • چند بایت ابتدایی هر بلوک برای سرآیندها رزرو شده است. یک سرآیند صرفاً یک مقدار LONG (۸ بایت) است و می‌تواند هر چیزی باشد؛ بلوک کاری به سرآیندهایش ندارد، جز اینکه به کلاینت‌ها امکان خواندن و نوشتن در آن را می‌دهد.
  • وقتی کلاینت کارش با یک بلوک تمام شد، باید Dispose را فراخوانی کند تا همهٔ کش‌ها تخلیه (flush) شوند.

نکات (NOTES)

در این پیاده‌سازی، ۴ کیلوبایت ابتدایی را که معمولاً هم سرآیند و هم بخشی از بدنهٔ محتوا را در بر دارد، کش می‌کنم تا کارایی را بهینه کنم؛ چون سیستم فایل معمولاً داده‌ها را در بلوک‌های ۴ کیلوبایتی می‌خواند و می‌نویسد، این کار برخی فراخوانی‌های نوشتن را حذف می‌کند. با این حال، برای بلوک‌های بزرگ‌تر از ۴ کیلوبایت، این کار منجر به نوشتن غیرخطی می‌شود (زیرا دادهٔ کش‌شدهٔ ۴ کیلوبایت اول همیشه در آخر نوشته می‌شود).

این مشکل باید در برنامه‌های حساس به نوشتن برطرف شود؛ یا با تخلیهٔ هوشمندتر کش، یا با کش کردن کل بلوک در حافظه و نوشتن آن‌ها به‌صورت متوالی هنگام آزادسازی (Dispose) بلوک.

B. پیاده‌سازی RecordStorage

کلاس‌های جالب برای بررسی:

  1. FooCore/RecordStorage.cs

همان‌طور که می‌بینید، RecordStorage با IBlockStorage به‌عنوان وابستگی مقداردهی می‌شود؛ چون ما RecordStorage را روی BlockStorage طراحی کردیم.

ساخت رکوردها (Creating Records)

  • RecordStorage با تقسیم دادهٔ مشخص‌شده به چند بلوک، یک رکورد برای هر آرایهٔ بایتی دلخواه می‌سازد؛ درست مثل یک فهرست پیوندی.
  • بلوک‌ها را با استفاده از سرآیندهای فراداده (میدان شمارهٔ ۰ با نام kNextBlockId و میدان شمارهٔ ۳ با نام kPreviousBlockId) به یکدیگر پیوند می‌زند تا بلوک قبل و بعد از یک بلوک مشخص را که یک رکورد منفرد را می‌سازند، شناسایی کند.
  • از سرآیند بلوک (میدان شمارهٔ ۲ با نام kBlockContentLength) برای علامت‌گذاری دادهٔ واقعاً قابل استفادهٔ یک Block استفاده می‌کند. این امکان را می‌دهد که یک رکورد هر اندازه‌ای داشته باشد، نه فقط مضربی از اندازهٔ بلوک خاص.
  • تخصیص رکورد جدید هر زمان که ممکن باشد با بازیافت بلوک‌های حذف‌شده انجام می‌شود (یعنی «بیرون کشیدن» یک uint از رکورد شمارهٔ ۰)، یا در غیر این صورت از BlockStorage زیرین درخواست تخصیص بلوک می‌شود.

پیدا کردن رکوردها (Finding Records)

  • پیدا کردن یک رکورد آسان است، چون شناسهٔ رکورد همان شناسهٔ اولین بلوکی است که رکورد از آن ساخته شده است.
  • اگر اولین رکورد بلوک بعدی داشته باشد، آن بلوک را می‌گیریم و این کار را تا رسیدن به آخرین بلوک ادامه می‌دهیم.

حذف رکوردها (Deleting Records)

  • حذف یک رکورد با علامت‌گذاری رکورد و همهٔ بلوک‌هایش به‌عنوان حذف‌شده (میدان شمارهٔ ۴ با نام kIsDeleted) انجام می‌شود.
  • برای پیگیری بلوک‌های حذف‌شده از یک رکورد ویژه، یعنی رکورد شمارهٔ ۰، استفاده می‌کند. این رکورد مانند یک پشته از uint است؛ وقتی یک رکورد حذف می‌شود، یک عدد uint روی پشته «فشارده» می‌شود.

به‌روزرسانی رکوردها (Updating Records)

  • اگر دادهٔ رکورد جدید از همان تعداد بلوک‌های دادهٔ قدیم استفاده کند، RecordStorage محتوای بلوک‌های موجود را به‌روز می‌کند.
  • اگر دادهٔ رکورد جدید به بلوک‌های بیشتری نسبت به دادهٔ قدیم نیاز داشته باشد، RecordStorage به تعداد لازم بلوک تخصیص می‌دهد (یا بازیافت می‌کند).
  • اگر دادهٔ رکورد جدید به بلوک‌های کمتری نسبت به دادهٔ قدیم نیاز داشته باشد، بلوک‌های استفاده‌نشده به‌عنوان حذف‌شده علامت‌گذاری می‌شوند.

C. پیاده‌سازی درخت B (روی دیسک) (B-Tree (on disk))

کلاس‌های جالب برای بررسی به این شرح است:

  1. FooCore/Tree.cs
  2. FooCore/TreeDiskNodeManager.cs
  3. FooCore/TreeDiskNodeSerializer.cs
  4. FooCore/TreeEnumerator.cs
  5. FooCore/TreeHelper.cs
  6. FooCore/TreeMemoryNodeManager.cs
  7. FooCore/TreeNode.cs
  8. FooCore/TreeTraverser.cs

پیاده‌سازی درخت B قبلاً توسط افراد دیگر انجام شده است؛ فقط کافی بود الگوریتم‌های آن‌ها را به کد تبدیل کنیم. من از این مقالات برای پیاده‌سازی درخت B پیروی کردم — این، این و این (به هر حال بیش از ۱۸ ساعت از من وقت گرفت).

قسمت دشوار این است که درخت باید از روی هارد دیسک قابل دسترسی باشد، نه از حافظه. وقتی به بخشی از درخت دسترسی پیدا می‌کنیم، فقط همان بخش از هارد دیسک به حافظه بارگذاری می‌شود، نه کل درخت.

برای این کار فقط باید دو چیز را تضمین کنیم:

  1. TreeNode قابل سریال‌سازی باشد (بتواند به آرایهٔ بایتی تبدیل شود و از آن ساخته شود). از آنجا که یک Tree از چند TreeNode ساخته می‌شود، یک درخت اگر گره‌هایش قابل سریال‌سازی باشند، قابل سریال‌سازی خواهد بود.
  2. دسترسی به هر TreeNode باید از طریق یک نمونهٔ ITreeNodeManager انجام شود؛ یعنی یک TreeNode نباید ارجاع مستقیم درون‌حافظه‌ای به TreeNode دیگر نگه دارد؛ در عوض باید شناسهٔ دیگران را نگه دارد.

برای توسعه و تست واحد، یک پیاده‌سازی آزمایشی از ITreeNodeManager یعنی TreeMemoryNodeManager شبیه‌سازی کردم. بعداً TreeDiskNodeManager را برای استفادهٔ تولیدی نوشتم، همراه با کمکی به نام TreeDiskNodeSerializer برای سریال‌سازی TreeNode.

D. پیاده‌سازی CowDatabase

ساخت CowDatabase در این مرحله نسبتاً آسان و سریع است، چون RecordStorage و نمایه‌سازی را ساخته‌ایم.

لطفاً پیاده‌سازی CowDatabase من را ببینید:

  1. FooApplication/CowDatabase.cs
  2. FooApplication/CowSerializer.cs

مقداردهی اولیه (Initialization)

FooDatabase با یک مسیر به پایگاه داده به‌عنوان آرگومان مقداردهی می‌شود و از یک قرارداد نام‌گذاری برای یافتن دو نمایهٔ دیگر استفاده می‌کند (نمایهٔ اصلی cow Guid و نمایهٔ فرعی Breed و Age).

سپس یک نمایهٔ اصلی، یک Tree<Guid, uint> (نگاشت GUID گاو به شناسهٔ رکوردش) و یک نمایهٔ فرعی Tree<Tuple<string, int>, uint> (نگاشت Breed و Age گاو به شناسهٔ رکوردش) می‌سازد.

درج، حذف و به‌روزرسانی گاوها (Insertion, Deletion and Update of Cows)

CowDatabase از یک نمونهٔ RecordStorage برای ذخیرهٔ داده‌های سریال‌سازی‌شدهٔ گاوها استفاده می‌کند و از CowSerializer کمک می‌گیرد. هر بار که یک گاو درج، حذف یا به‌روزرسانی می‌شود، به‌ترتیب متدهای Create()، Remove() و Update() را روی RecordStorage فراخوانی می‌کند و همچنین نمایهٔ موردنیاز را می‌سازد و تغییر می‌دهد.

جست‌وجوی یک گاو یا چند گاو (Searching for a Cow or Cows)

جست‌وجوی یک cow یا چند cow با نگاه کردن به نمایهٔ اصلی یا فرعی برای یافتن شناسهٔ رکوردهای واقعی انجام می‌شود؛ سپس از آن شناسه‌ها با RecordStorage برای خواندن دادهٔ گاو استفاده می‌شود.

حالا می‌توانیم ذخیره‌سازی و پرس‌وجوی cowهای خود را همان‌طور که در FooApplication/Program.cs آمده شروع کنیم؛ از پایگاه دادهٔ سفارشی‌سازی‌شدهٔ خود لذت ببرید!

نکات مورد علاقه (Point of Interests)

برای نوشتن این برنامهٔ نمونه از mono روی مک استفاده کردم؛ کارایی بسیار رضایت‌بخش بود؛ اگرچه حدود ۳۰ تا ۴۰ درصد از زمان CPU صرف اجرای کد سی‌شارپ می‌شد به‌جای انجام عملیات واقعی ورودی/خروجی (انتظار داشتم حدود ۱۰ تا ۲۰ درصد باشد). با این حال، فکر می‌کنم سی‌شارپ بهتر است روی ویندوز اجرا شود.

همچنین با مشکلی مواجه شدم: مک همهٔ فراخوانی‌های نوشتن را در حافظه کش می‌کند و راهی برای تخلیهٔ آن نداشتم، حتی با FileStream.Flush(bool true). فکر می‌کنم این یک باگ mono باشد.

به هر حال، یک پروژهٔ سرگرم‌کننده برای آخر هفته بود؛ امیدوارم همه از آن لذت ببرند.
