مقدمه

احتمالاً در کار روزمرهٔ خود از ابزارهای زیادی استفاده می‌کنید؛ مانند webpack، typescript، babel، tslint، eslint، prettier و موارد دیگر. به همهٔ این ابزارها می‌توانید از خط فرمان (command line) دسترسی داشته باشید و ما قرار است دقیقاً ببینیم این کار چگونه انجام می‌شود.

دربارهٔ جنبه‌های مختلف چنین ابزاری صحبت خواهیم کرد: ساخت فایل اجرایی (executable)، تجزیهٔ آرگومان‌های خط فرمان (parsing command line arguments)، مدیریت پیکربندی (configuration)، گزارش‌گیری (logging) منعطف و تجربهٔ کلی توسعه‌دهنده (Developer Experience).

در پایان این آموزش، یک اسکلت (skeleton) کارآمد از یک ابزار خط فرمان (CLI tool) خواهیم داشت. تنها کاری که باقی می‌ماند اضافه‌کردن منطق خاص خود شماست.

راهنمای مطالعه: این آموزش در سایت اصلی تعاملی است و محتوای آن در سه سطح «استاندارد»، «مفصل (Verbose)» و «داخلی (Internals)» ارائه می‌شود. در این صفحه همهٔ سطوح به‌صورت یکپارچه ترجمه شده‌اند تا هیچ بخشی از آموزش حذف نشود.

بیایید شروع کنیم.

راه‌اندازی پروژه‌ها (Setting Up the Projects)

دو دایرکتوری بسازید؛ یکی به نام tool و دیگری به نام testProject:

shell$ mkdir tool-tutorial
$ cd tool-tutorial
tool-tutorial$ mkdir tool
tool-tutorial$ mkdir testProject

در هر دو دایرکتوری دستور npm init -y را اجرا کنید تا فایل‌های package.json خالی ایجاد شوند:

shelltool-tutorial$ cd tool
tool-tutorial/tool$ npm init -y
// ...
tool-tutorial/tool$ cd ../testProject
tool-tutorial/testProject$ npm init -y
// ...

در پروژهٔ tool، یک دایرکتوری به نام bin و فایلی به نام index.js بسازید:

shelltool-tutorial/tool$ mkdir bin
touch bin/index.js

این دایرکتوری فقط برای راحتی ساخته می‌شود؛ اسکریپت باینری (binary script) ما می‌تواند هر جای پروژه قرار بگیرد.

در فایل index.js فعلاً عبارت hello tool را چاپ می‌کنیم:

jsconsole.log('hello tool');

برای اجرای یک اسکریپت node باید دستور node SCRIPT_NAME را اجرا کنیم. در مورد ما، می‌خواهیم بتوانیم ابزار را بدون فراخوانی صریح node اجرا کنیم؛ همان‌طور که webpack، tsc یا eslint را اجرا می‌کنیم.

یک دستورالعمل هش‌بنگ (hashbang) در بالای فایل قرار می‌دهیم که مشخص می‌کند از کدام مفسر (interpreter) برای اجرای اسکریپت استفاده می‌شود:

js#!/usr/bin/env node
console.log('hello tool');

به‌جای مسیر مستقیم فایل اجرایی node از دستور env استفاده می‌کنیم؛ زیرا ممکن است چند نسخهٔ node نصب شده باشد.

پیکربندی باینری (Configuring the Binary)

در فایل package.json ابزار، باید اسکریپت نقطهٔ ورود (entry point) که همین الان ساختیم را به‌عنوان باینری پکیج تعریف کنیم:

json{
  "name": "tool",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}

یک ویژگی bin ایجاد می‌کنیم و مقدار آن را برابر فایلی که باید اجرا شود — همان اسکریپت نقطهٔ ورودی که قبلاً ساختیم — قرار می‌دهیم. نام پکیج ما یعنی tool، نام فایل اجرایی‌ای (executable) خواهد بود که ساخته می‌شود:

json{
  "name": "tool",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "bin": "./bin/index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}

برای ساخت چند باینری برای پکیج، bin را به‌صورت یک شیء (object) با چند ویژگی تعریف کنید:

json{
  "name": "tool",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "bin": {
    "binary1": "./bin/index.js",
    "binary2": "./some-other-file.js",
    "binary3": "./some/subdirectory/and-another.js"
  },
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}

اتصال پروژه‌ها (Linking the Projects)

می‌خواهیم ابزار خود را در پروژهٔ تستی که قبلاً ساختیم امتحان کنیم. برای این کار باید پکیج tool را در دایرکتوری testProject نصب کنیم. برای شبیه‌سازی نصب از npm link استفاده می‌کنیم:

shelltool-tutorial$ cd tool
tool-tutorial/tool$ npm link
// ...
tool-tutorial/tool$ cd ../testProject
tool-tutorial/testProject$ npm link tool
// ...

اگر به دایرکتوری node_modules/.bin پروژهٔ testProject نگاه کنیم، می‌بینیم که نصب، فایل جدیدی به نام tool ایجاد کرده است که با استفاده از یک پیوند نرم‌افزاری (symlink) به اسکریپت نقطهٔ ورودی که قبلاً ساختیم اشاره می‌کند:

shelltool-tutorial/testProject$ ll node_modules/.bin
lrwxr-xr-x 1 user 361602828 23 Nov 10 11:06 tool -> ../tool/bin/index.js

اگر tool را اجرا کنیم، می‌بینیم که به‌درستی اجرا می‌شود:

shelltool-tutorial/testProject$ tool
hello tool

تجزیهٔ آرگومان‌های خط فرمان (Parsing Command Line Arguments)

می‌خواهیم ابزار ما بتواند چند دستور (command) مختلف را اجرا کند. برای این کار باید بتوانیم ابزار را با آرگومان‌های مختلف اجرا کنیم.

می‌توانیم از ویژگی داخلی node یعنی process.argv برای مدیریت آن‌ها استفاده کنیم. console.log خود را با یکی دیگر جایگزین می‌کنیم:

js#!/usr/bin/env node
console.log(process.argv);

اگر حالا ابزار را اجرا کنیم، خروجی مشابهی می‌بینیم. process.argv یک آرایه برمی‌گرداند که عضو اول آن فایل اجرایی node است، عضو دوم نام فایل اجراشده و عضو سوم به بعد، آرگومان‌هایی هستند که به اسکریپت داده‌ایم:

shelltool-tutorial/testProject$ tool --start
[
  '/Users/user/.nvm/versions/node/v12.16.1/bin/node',
  '/Users/user/tool-tutorial/tool/bin/index.js',
  '--start'
]

می‌توانیم از ویژگی process.argv استفاده کنیم، اما کتابخانه‌های متعددی وجود دارند که کار ما را با آرگومان‌های CLI آسان‌تر می‌کنند. یکی از ساده‌ترین کتابخانه‌ها در این حوزه arg است.

کتابخانه‌های پیشرفته‌تر عبارت‌اند از commander و yargs.

arg یک شیء پیکربندی دریافت می‌کند که مشخص می‌کند چه آرگومان‌هایی را می‌تواند دریافت کند و نوع آن‌ها چیست. انواع می‌توانند boolean (بولی)، string (رشته)، number (عدد)، array (آرایه) و counter (شمارنده) باشند. در مورد ما از boolean استفاده می‌کنیم؛ زیرا می‌خواهیم بدانیم کاربر پرچم (flag) را ارسال کرده است یا نه:

js#!/usr/bin/env node
const arg = require('arg');

const args = arg({
  '--start': Boolean,
  '--build': Boolean,
});

console.log(args);

حالا اگر ابزار را اجرا کنیم، خروجی زیر را دریافت می‌کنیم. توجه کنید که پرچم --start شناسایی و برابر true قرار داده شده است:

shelltool-tutorial/testProject$ tool --start
{ _: [], '--start': true }

حالا می‌توانیم آرگومان start خود را بر همین اساس مدیریت کنیم:

js#!/usr/bin/env node
const arg = require('arg');

const args = arg({
  '--start': Boolean,
  '--build': Boolean,
});

if (args['--start']) {
  console.log('starting the app');
}

و اگر دوباره آن را اجرا کنیم، می‌بینیم که پیام ما چاپ می‌شود:

shelltool-tutorial/testProject$ tool --start
starting the app

اما اگر آرگومان ناشناخته‌ای به آن بدهیم چه اتفاقی می‌افتد؟ می‌بینیم که arg یک خطا پرتاب (throw) می‌کند:

shelltool-tutorial/testProject$ tool --publish
/Users/user/tool-tutorial/tool/node_modules/arg/index.js:90
            throw err;
            ^

Error: Unknown or unexpected option: --publish
//...

می‌توانیم فراخوانی arg را با try/catch بپوشانیم و آن را بر همین اساس مدیریت کنیم:

js#!/usr/bin/env node
const arg = require('arg');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    console.log('starting the app');
  }
} catch (e) {
  console.log(e.message);
}

خروجی جدید کمی کم‌ریخت‌تر خواهد بود، اما همچنان به‌اندازهٔ کافی خوب نیست:

shelltool-tutorial/testProject$ tool --publish
Unknown or unexpected option: --publish

علاوه بر نشان‌دادن اینکه چطور از ابزار استفاده نکنیم، باید نشان دهیم که چگونه می‌توان از آن استفاده کرد. برای این کار یک تابع usage اضافه می‌کنیم:

js#!/usr/bin/env node
const arg = require('arg');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    console.log('starting the app');
  }
} catch (e) {
  console.log(e.message);
  console.log();
  usage();
}

function usage() {
  console.log(`tool [CMD]
  --start\tStarts the app
  --build\tBuilds the app`);
}

حالا اگر دستور را اجرا کنیم، خروجی بسیار واضح‌تری می‌بینیم:

shelltool-tutorial/testProject$ tool --publish
Unknown or unexpected option: --publish

tool [CMD]
  --start		Starts the app
  --build		Builds the app

تجربهٔ توسعه‌دهنده (Developer Experience)

همان‌طور که تجربهٔ کاربری (UX) ستون باربر در اپلیکیشن‌های بصری است، تجربهٔ توسعه‌دهنده (Developer Experience) یا به‌اختصار DX، هنگام ساخت ابزارهایی برای توسعه‌دهندگان چنین نقشی دارد.

DX جلوه‌های زیادی دارد؛ مانند لذت‌بخشی هنگام استفاده از ابزار، پیام‌های خطای بهتر، نیاز کمتر به حدس‌زدن، مستندات خوب و پاسخ‌گویی سریع. در نهایت، DX به حداکثر رساندن ارزش و حداقل رساندن زمان تلف‌شده خلاصه می‌شود.

در صفحهٔ قبل دیدیم که چگونه یک پیام خطای واضح برگردانیم و علاوه بر آن مشخص کنیم که فرد باید به‌درستی از ابزار استفاده کند. در ادامه می‌خواهیم آن را کمی بیشتر برجسته کنیم.

کمی رنگ (A Splash of Color)

در پروژهٔ tool خود، پکیج chalk را نصب کنید (npm i chalk). chalk به ما امکان می‌دهد به عبارت‌های console.log خود رنگ اضافه کنیم؛ این کار به واضح‌ترشدن خروجی کمک می‌کند:

js#!/usr/bin/env node
const arg = require('arg');
const chalk = require('chalk');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    console.log(chalk.bgCyanBright('starting the app'));
  }
} catch (e) {
  console.log(chalk.yellow(e.message));
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

خروجی شما باید رنگارنگ، حرفه‌ای به نظر برسد و مهم‌تر از همه، ساده‌تر قابل فهم باشد. (حالا تصور کنید که نمایشگر کد آموزش از رنگ‌های سفارشی پشتیبانی می‌کرد 😛)

shelltool-tutorial/testProject$ tool --publish
Unknown or unexpected option: --publish

tool [CMD]
  --start		Starts the app
  --build		Builds the app

پیکربندی (Configuration)

بیشتر ابزارها را کاربر می‌تواند پیکربندی کند. یک روش خوب این است که ابزار از طریق ویژگی‌های موجود در package.json پیکربندی شود.

در فایل package.json پروژهٔ testProject ویژگی‌های زیر را اضافه کنید:

json{
  "name": "testProject",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC",
  "tool": {
    "port": 9999
  }
}

حالا می‌خواهیم پیکربندی را از package.json پروژهٔ testProject بخوانیم. نمی‌توانیم فقط فایل package.json را require کنیم؛ زیرا آن فایل در testProject قرار دارد و ما در بستر (context) ابزار خودمان یعنی tool هستیم:

js#!/usr/bin/env node
const arg = require('arg');
const chalk = require('chalk');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    const pkg = require('./package.json'); // <-- کار نخواهد کرد
    console.log(chalk.bgCyanBright('starting the app'));
  }
} catch (e) {
  console.log(chalk.yellow(e.message));
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

برای اینکه فایل را به‌درستی require کنیم، می‌توانیم از متد process.cwd() استفاده کنیم تا مسیری را که کاربر باینری ما را از آنجا اجرا کرده است به دست آوریم. این مسیر را با نام فایل با استفاده از متد path.join ترکیب می‌کنیم:

js#!/usr/bin/env node
const arg = require('arg');
const chalk = require('chalk');
const path = require('path');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    const pkg = require(path.join(process.cwd(), 'package.json'));
    // TODO: با pkg کاری انجام بده
    console.log(chalk.bgCyanBright('starting the app'));
  }
} catch (e) {
  console.log(chalk.yellow(e.message));
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

اگر کاربر ابزار ما را از یک زیرشاخه (subdirectory) اجرا کند چه اتفاقی می‌افتد؟ ما به‌دنبال package.json در دایرکتوری اشتباه می‌گردیم و شکست می‌خوریم:

shelltool-tutorial/testProject/src$ tool --start
Cannot find module '/Users/user/tool-tutorial/testProject/src/package.json'
Require stack:
- /Users/user/tool-tutorial/tool/bin/index.js

برای یافتن فایل package.json از پکیجی به نام pkg-up استفاده خواهیم کرد. pkg-up در درخت دایرکتوری به بالا می‌رود، به‌دنبال فایل package.json می‌گردد و مسیر آن را برمی‌گرداند:

js#!/usr/bin/env node
const arg = require('arg');
const chalk = require('chalk');
const pkgUp = require('pkg-up');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    const pkgPath = pkgUp.sync({cwd: process.cwd()});
    const pkg = require(pkgPath);
    if (pkg.tool) {
      console.log('Found configuration', pkg.tool);
      // TODO: با پیکربندی کاری انجام بده
    } else {
      console.log(chalk.yellow('Could not find configuration, using default'));
      // TODO: دریافت پیکربندی پیش‌فرض
    }
    console.log(chalk.bgCyanBright('starting the app'));
  }
} catch (e) {
  console.log(chalk.yellow(e.message));
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

Sindresorhus پکیج عمومی‌تری نیز در اختیار ما قرار می‌دهد به نام find-up.

بازآرایی کد (Refactor)

برای یک لحظه از بحث پیکربندی فاصله بگیریم تا کمی کد خود را بازآرایی (refactor) کنیم.

یک دایرکتوری src در پروژهٔ tool ایجاد می‌کنیم و داخل آن دو دایرکتوری می‌سازیم: commands و config. در commands فایلی به نام start.js ایجاد می‌کنیم و در config فایلی به نام config-mgr.js:

shelltool-project/tool$ mkdir src
mkdir src/commands
mkdir src/config
touch src/commands/start.js
touch src/config/config-mgr.js

در فایل start.js تابع start خود را می‌سازیم که یک شیء پیکربندی دریافت می‌کند:

jsconst chalk = require('chalk');

module.export = function start(config) {
  console.log(chalk.bgCyanBright('  Starting the app  '));
  console.log(chalk.gray('Received configuration in start -'), config);
}

در فایل config-mgr.js کد پیکربندی‌ای را که قبلاً ساختیم کپی می‌کنیم:

jsconst chalk = require('chalk');
const pkgUp = require('pkg-up');

module.exports = function getConfig() {
  const pkgPath = pkgUp.sync({cwd: process.cwd()});
  const pkg = require(pkgPath);
  if (pkg.tool) {
    console.log('Found configuration', pkg.tool);
    return pkg.tool;
  } else {
    console.log(chalk.yellow('Could not find configuration, using default'));
    return { port: 1234 };
  }
}

و فایل bin/index.js خود را ساده‌تر می‌کنیم:

js#!/usr/bin/env node
const arg = require('arg');
const chalk = require('chalk');
const getConfig = require('../src/config/config-mgr');
const start = require('../src/commands/start');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  if (args['--start']) {
    const config = getConfig();
    start(config);
  }
} catch (e) {
  console.log(chalk.yellow(e.message));
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

پیکربندی، قسمت دوم (Configuration Part Deux)

قبلاً ابزار خود را از طریق فایل package.json پیکربندی کردیم؛ اما بیشتر ابزارها راه‌های متعددی برای پیکربندی دارند. یکی از این راه‌ها فایل پیکربندی جاوااسکریپت (JavaScript configuration file) است.

مزیت فایل پیکربندی جاوااسکریپت نسبت به فایل JSON این است که می‌توانید منطق سفارشی اضافه کنید و حتی از کتابخانه‌های شخص ثالث استفاده کنید.

می‌توانیم یک شرط دیگر در config-mgr اضافه کنیم تا فایل پیکربندی جاوااسکریپت را جست‌وجو کند و بخواند. این کار جواب می‌دهد، اما برای راه‌حلی محکم‌تر ادامهٔ مطلب را بخوانید:

jsconst chalk = require('chalk');
const pkgUp = require('pkg-up');

module.exports = function getConfig() {
  const pkgPath = pkgUp.sync({cwd: process.cwd()});
  const pkg = require(pkgPath);
  if (pkg.tool) {
    console.log('Found configuration', pkg.tool);
    return pkg.tool;
  } else if (hasJSConfigFile()) { // <- شبه‌کد
    return loadJSConfigFile(); // <- شبه‌کد
  } else {
    console.log(chalk.yellow('Could not find configuration, using default'));
    return { port: 1234 };
  }
}

منطق pkgUp خود را با استفاده از پکیج cosmiconfig جایگزین می‌کنیم. cosmiconfig از جنبه‌های مختلف مدیریت پیکربندی پشتیبانی می‌کند؛ مانند قالب‌های فایل اضافی، جست‌وجوی ناهمگام (async search)، کش‌کردن (caching) و موارد دیگر:

jsconst chalk = require('chalk');
const { cosmiconfigSync } = require('cosmiconfig');
const configLoader = cosmiconfigSync('tool');

module.exports = function getConfig() {
  const result = configLoader.search(process.cwd());
  if (!result) {
    console.log(chalk.yellow('Could not find configuration, using default'));
    return { port: 1234 };
  } else {
    console.log('Found configuration', result.config);
    return result.config;
  }
}

حالا می‌توانیم فایل پیکربندی به نام tool.config.js در پروژهٔ testProject خود ایجاد کنیم:

jsmodule.exports = {
  port: 6666
}

cosmiconfig به پیکربندی تعریف‌شده در فایل package.json اولویت می‌دهد. بنابراین، اگر پیکربندی را از package.json حذف کنیم، می‌بینیم که فایل جدید tool.config.js را برمی‌گزیند:

shelltool-tutorial/testProject$ tool --start
Found configuration { port: 6666 }
  Starting the app
Received configuration in start - { port: 6666 }

اعتبارسنجی (Validation)

از آنجا که پیکربندی از ورودی کاربر می‌آید، نمی‌توانیم به اعتبار آن اعتماد کنیم. یک راه برای اعتبارسنجی، بررسی هر ویژگی و زیرویژگی در شیء پیکربندی با استفاده از کد سفارشی است. اما، مثل همیشه، اگر با یک مسئلهٔ عمومی روبه‌رو هستید — مانند اعتبارسنجی پیکربندی — مطمئن باشید شخص دیگری هم به همان مسئله برخورده و کتابخانه‌ای برای مدیریت آن توسعه داده است.

از کتابخانه‌ای به نام ajv استفاده خواهیم کرد که پیکربندی را بر اساس یک شمای JSON (JSON schema) اعتبارسنجی می‌کند.

اول بیایید شمای (schema) را بسازیم. فایل جدیدی در دایرکتوری tool/src/config به نام schema.json ایجاد کنید و کد زیر را وارد کنید. ما تعریف می‌کنیم که تنها نوع معتبر ویژگی port، عدد (number) است:

json{
  "properties": {
    "port": {
      "type": "number"
    }
  }
}

سپس از ajv برای اعتبارسنجی پیکربندی خود استفاده می‌کنیم. توجه کنید که از process.exit(1) برای خروج از فرایند استفاده می‌کنیم؛ زیرا نمی‌خواهیم با پیکربندی نامعتبر ادامه دهیم:

jsconst chalk = require('chalk');
const { cosmiconfigSync } = require('cosmiconfig');
const schema = require('./schema.json');
const Ajv = require('ajv').default;
const ajv = new Ajv();
const configLoader = cosmiconfigSync('tool');

module.exports = function getConfig() {
  const result = configLoader.search(process.cwd());
  if (!result) {
    console.log(chalk.yellow('Could not find configuration, using default'));
    return { port: 1234 };
  } else {
    const isValid = ajv.validate(schema, result.config);
    if (!isValid) {
      console.log(chalk.yellow('Invalid configuration was supplied'));
      console.log(ajv.errors);
      process.exit(1);
    }
    console.log('Found configuration', result.config);
    return result.config;
  }
}

در فایل testProject/tool.config.js مقدار port را از عدد به رشته تغییر می‌دهیم:

jsmodule.exports = {
  port: "6666"
}

حالا اگر ابزار را اجرا کنیم، می‌بینیم که خطای مورد انتظار خود را دریافت می‌کنیم:

shelltool-tutorial/testProject$ tool --start
Invalid configuration was supplied
[
  {
    keyword: 'type',
    dataPath: '/port',
    schemaPath: '#/properties/port/type',
    params: { type: 'number' },
    message: 'should be number'
  }
]

اطلاعات درستی به دست آوردیم اما با تجربهٔ توسعه‌دهنده‌ای (DX) وحشتناک. بیایید از کتابخانهٔ better-ajv-errors استفاده کنیم تا خطاها کمی قابل‌درک‌تر شوند:

jsconst chalk = require('chalk');
const { cosmiconfigSync } = require('cosmiconfig');
const schema = require('./schema.json');
const betterAjvErrors = require('better-ajv-errors');
const Ajv = require('ajv').default;
const ajv = new Ajv({ jsonPointers: true });
const configLoader = cosmiconfigSync('tool');

module.exports = function getConfig() {
  const result = configLoader.search(process.cwd());
  if (!result) {
    console.log(chalk.yellow('Could not find configuration, using default'));
    return { port: 1234 };
  } else {
    const isValid = ajv.validate(schema, result.config);
    if (!isValid) {
      console.log(chalk.yellow('Invalid configuration was supplied'));
      console.log();
      console.log(betterAjvErrors(schema, result.config, ajv.errors));
      process.exit(1);
    }
    console.log('Found configuration', result.config);
    return result.config;
  }
}

اگر ابزار را دوباره اجرا کنیم، می‌بینیم که پیام خطا بسیار کاربرپسندتر، واضح‌تر است و به وقت کاربران احترام می‌گذارد:

shelltool-tutorial/testProject$ tool --start
Invalid configuration was supplied

  TYPE should be number

> 1 | {"port":"6666"}
    |         ^^^^^^ 👈🏽  type should be number

گزارش‌گیری (Logging)

تا به این‌جا، کد خود را با عبارت‌های مختلف console.log پاشیده‌ایم. برخی از console.logها روبه‌روی کاربرند، برخی برای اشکال‌زدایی (debug) هستند، برخی اطلاع‌رسان و برخی هشدار. بیایید به این بی‌نظمی سر و سامانی بدهیم.

کتابخانه‌های گزارش‌گیری عالی مانند winston و bunyan وجود دارند؛ اما در این مورد می‌خواهیم ببینیم پشت صحنه چه اتفاقی می‌افتد؛ بنابراین گزارش‌گیر (logger) را خودمان پیاده‌سازی می‌کنیم.

فایلی در tool/src به نام logger.js ایجاد کنید. این فایل یک تابع سازندهٔ گزارش‌گیر برمی‌گرداند که یک نام دریافت می‌کند و یک شیء گزارش‌گیر برمی‌گرداند:

jsconst chalk = require('chalk');

module.export = function createLogger(name) {
  return {
  };
}

انواع مختلفی از پیام‌ها می‌سازیم که هرکدام رنگ متفاوتی دارند. کمی بعد به تابع debug برمی‌گردیم. شروع می‌کنیم به مهاجرت عبارت‌های console.log خود به گزارش‌گیر جدید:

jsconst chalk = require('chalk');

module.export = function createLogger(name) {
  return {
    log: (...args) => console.log(chalk.gray(...args)),
    warning: (...args) => console.log(chalk.yellow(...args)),
    highlight: (...args) => console.log(chalk.bgCyanBright(...args)),
    debug: console.log
  };
}

از config-mgr.js شروع می‌کنیم:

jsconst logger = require('../logger')('config:mgr');
const { cosmiconfigSync } = require('cosmiconfig');
const schema = require('./schema.json');
const betterAjvErrors = require('better-ajv-errors');
const Ajv = require('ajv').default;
const ajv = new Ajv({ jsonPointers: true });
const configLoader = cosmiconfigSync('tool');

module.exports = function getConfig() {
  const result = configLoader.search(process.cwd());
  if (!result) {
    logger.warning('Could not find configuration, using default');
    return { port: 1234 };
  } else {
    const isValid = ajv.validate(schema, result.config);
    if (!isValid) {
      logger.warning('Invalid configuration was supplied');
      console.log();
      console.log(betterAjvErrors(schema, result.config, ajv.errors));
      process.exit(1);
    }
    logger.debug('Found configuration', result.config);
    return result.config;
  }
}

بعد، start.js:

jsconst logger = require('../logger')('commands:start');

module.export = function start(config) {
  logger.highlight('  Starting the app  ');
  logger.debug('Received configuration', config);
}

و فایل bin/index.js:

js#!/usr/bin/env node
const logger = require('../src/logger')('bin');
const arg = require('arg');
const chalk = require('chalk');
const getConfig = require('../src/config/config-mgr');
const start = require('../src/commands/start');

try {
  const args = arg({
    '--start': Boolean,
    '--build': Boolean,
  });

  logger.debug('Received args', args);

  if (args['--start']) {
    const config = getConfig();
    start(config);
  }
} catch (e) {
  logger.warning(e.message);
  console.log();
  usage();
}

function usage() {
  console.log(`${chalk.whiteBright('tool [CMD]')}
  ${chalk.greenBright('--start')}\tStarts the app
  ${chalk.greenBright('--build')}\tBuilds the app`);
}

اگر ابزار را دوباره اجرا کنیم، همان گزارش‌های قبلی را می‌بینیم. هرچند عالی است که منطق را یکپارچه کردیم، می‌توانیم یک قدم فراتر برویم:

shelltool-tutorial/testProject$ tool --start
Received args { _: [], '--start': true }
Found configuration { port: 6666 }
  Starting the app
received configuration { port: 6666 }

فراخوانی console.log تابع debug خود را با کتابخانهٔ debug جایگزین می‌کنیم (npm i debug) و نامی را که دریافت کرده‌ایم به آن پاس می‌دهیم. debug به ما امکان می‌دهد یک گزارش را به فضای نام (namespace) خاصی محدود کنیم (همان نامی که دریافت کرده‌ایم):

jsconst chalk = require('chalk');
const debug = require('debug');

module.export = function createLogger(name) {
  return {
    log: (...args) => console.log(chalk.gray(...args)),
    warning: (...args) => console.log(chalk.yellow(...args)),
    highlight: (...args) => console.log(chalk.bgCyanBright(...args)),
    debug: debug(name)
  };
}

حالا وقتی ابزار را اجرا می‌کنیم، فقط همین پیام واحدِ روبه‌روی کاربر را می‌بینیم. گزارش‌های debug تا زمانی که نیاز به اشکال‌زدایی کدمان داشته باشیم پنهان هستند:

shelltool-tutorial/testProject$ tool --start
  Starting the app

اگر ابزار را با متغیر محیطی به نام DEBUG اجرا کنیم، می‌توانیم گزارش‌های پکیج debug را فعال کنیم:

shelltool-tutorial/testProject$ DEBUG=* tool --start
bin Received args { _: [], '--start': true } +0ms
config:mgr Found configuration { port: 6666 } +0ms
  Starting the app
commands:start received configuration { port: 6666 } +0ms

توجه کنید که گزارش‌های debug به نام خودشان محدود شده‌اند: bin، config:mgr و commands:start. همچنین، در انتهای هر خط، اختلاف زمانی (به میلی‌ثانیه) نسبت به گزارش قبلی آمده است. چقدر جالب!

اما صبر کنید، ادامه دارد! debug همچنین به ما امکان می‌دهد گزارش‌ها را با فضانام‌گذاری (namespacing) متغیر محیطی فیلتر کنیم. می‌توانیم آن را با commands:* صدا بزنیم تا فقط گزارش‌های commands را شامل شود:

shelltool-tutorial/testProject$ DEBUG=commands:* tool --start
  Starting the app
commands:start received configuration { port: 6666 } +0ms

یا آن را با commands:*,bin صدا بزنیم تا هم گزارش‌های commands و هم bin شامل شوند:

shelltool-tutorial/testProject$ DEBUG=commands:*,bin tool --start
bin Received args { _: [], '--start': true } +0ms
  Starting the app
commands:start received configuration { port: 6666 } +0ms

همچنین می‌توانیم آن را با *,-bin صدا بزنیم تا همه‌چیز به‌جز گزارش‌های bin شامل شود:

shelltool-tutorial/testProject$ DEBUG=*,-bin tool --start
config:mgr Found configuration { port: 6666 } +0ms
  Starting the app
commands:start received configuration { port: 6666 } +0ms

به‌طور خلاصه، گزینه‌های فیلتر debug منعطف، قدرتمند و استفاده از آن‌ها آسان است.

پکیج debug پشت صحنه در بسیاری از پکیج‌های مختلف استفاده می‌شود؛ مانند express.
