مقدمه

مدت زیادی است که اینجا مطلبی ننوشته‌ام؛ مشغله‌های کاری و توسعهٔ برنامه‌های iOS مرا به خود مشغول کرده بودند. دو سال پیش یک شناسهٔ توسعه‌دهنده (Developer ID) خریدم (هم برای iOS و هم برای مک) و به خودم قول دادم که برای هر دو پلتفرم، حداقل دوبار در سال اپ بسازم؛ فقط برای اینکه پولی را که خرج کرده‌ام برگردانم.

خلاصه، چندی پیش Raspberry Pi که سفارش داده بودم به دستم رسید و دنبال کارهایی برای انجام‌دادن با آن می‌گشتم. اولین چیزی که به ذهنم رسید، بدیهی است که بازی‌کردن بود! اما آن دستگاه کوچک مبتنی بر معماری ARM است و شبیه‌سازهای زیادی برای بهره‌برداری حداکثری از GPU قدرتمند آن ساخته نشده‌اند.

این فکر مرا به اینجا رساند — چه می‌شد اگر شبیه‌سازهای خودم را برای آن می‌نوشتم؟ یک پردازندهٔ تقریباً ۷۰۰ مگاهرتزی به‌اندازهٔ کافی سریع است و این تجربه می‌تواند چیزهای زیادی به من یاد بدهد. ضمناً، روی آن پایتون هم نصب است. چه کسی پایتون را دوست ندارد؟ هرچه کمتر به کدهای تکراری (boilerplate) فکر کنم، کارهای بیشتری انجام می‌دهم.

پس بیایید شروع کنیم.

پردازنده: CHIP8

برای شروع شبیه‌سازی، بیایید از یک ماشین کوچک شروع کنیم. بله، فرض کنید یک ماشین نظری (theoretical). با کمتر از ۵۰ دستورالعمل (اگر گیم‌بوی را انجام می‌دادیم که مبتنی بر Z80 است، حدود ۲۵۰ دستورالعمل می‌شد — کمی زیاد برای یک مقالهٔ وبلاگی. یا شاید فقط من تنبلم).

آها! یک ماشین واقعاً این معیارها را دارد — CHIP8. CHIP8 در معنای فیزیکی واقعاً یک ماشین نیست؛ در حقیقت یک مفسر (interpreter) است که برنامه‌هایش را در یک ماشین مجازی (virtual machine) اجرا می‌کند. این ماشین توسط زنده‌یاد جوزف وایسبکر (Joseph Weisbecker) ساخته شد. نخستین بار در ماشین‌حساب‌های نموداری (graphing calculators) ظاهر شد — و دلیل افت بهره‌وری آن‌ها به‌خاطر بازی بیش از حد PONG بود!

اولین قدم در شبیه‌سازی، تلاش برای درک اجزای درونی سخت‌افزار است. خوشبختانه برای ما، CHIP8 به‌خوبی مستند شده است؛ مورد علاقهٔ من مرجع فنی CHIP-8 کاگوود (Cogwood) است. حتی دستورالعمل‌های افزونهٔ SuperChip را هم شامل می‌شود. ویکی‌پدیا نیز منبع عالی دیگری برای این کار است — توصیف‌های اپ‌کد (opcode) آن در واقع همان چیزهایی هستند که قبل از کشف مقالهٔ کاگوود از آن‌ها استفاده می‌کردم.

پس بیایید شروع کنیم. اول سخت‌افزار را بفهمیم. اساساً همهٔ ماشین‌ها از ۳ بخش تشکیل شده‌اند (حداقل از نگاه من :)):

  1. ورودی (Input)
  2. خروجی (Output)
  3. CPU
  4. حافظه (Memory)

ورودی‌ها (Inputs)

برای ماشین مجازی CHIP8، ورودی از یک صفحه‌کلید ۱۶ دکمه‌ای می‌آید (خیلی به‌جاست که تعداد کلیدها در یک نیبل (nibble) جا می‌شود). ماشین همچنین با برنامه‌هایی که قرار است اجرا کند تغذیه می‌شود.

در پایتون فقط باید وضعیت‌های کلیدهای ورودی را ذخیره کنیم و در هر چرخه آن‌ها را بررسی کنیم:

py  self.key_inputs = [0]*16

خروجی (Output)

برای خروجی، ماشین از یک نمایشگر ۶۴×۳۲ و یک بوزر صدای ساده استفاده می‌کند. نمایشگر اساساً فقط یک آرایه از پیکسل‌هاست که هرکدام در یکی از حالت‌های روشن یا خاموش هستند:

py  self.display_buffer = [0]*32*64 # 64*32

CPU و حافظه

حالا بخش «سخت» ماجرا. پردازندهٔ Chip 8 چند بخش قابل توجه دارد و درک همگی آن‌ها برای فهمیدن نحوهٔ کار آن مهم است. من آن‌ها را اینجا مرور می‌کنم؛ اما برای اطلاعات بیشتر به مرجع کاگوود که قبلاً لینکش را دادم مراجعه کنید.

حافظه (Memory)

CHIP8 حافظه‌ای دارد که می‌تواند تا ۴۰۹۶ بایت را نگه دارد. این حافظه شامل خود مفسر، فونت‌ها (بعداً بیشتر دربارهٔ آن صحبت می‌کنیم) و جایی است که برنامه‌ای که قرار است اجرا شود (از ورودی) در آن بارگذاری می‌شود. در پایتون، این‌گونه خواهد بود:

py  self.memory = [0]*4096 # max 4096

ثبات‌ها (Registers)

CHIP8 دارای ۱۶ ثبات ۸ بیتی است (در مرجع کاگوود معمولاً با Vx نامیده می‌شوند که x شمارهٔ ثبات است). این‌ها عموماً برای ذخیرهٔ مقادیر در عملیات‌ها به کار می‌روند. آخرین ثبات، Vf، بیشتر برای پرچم‌ها (flags) استفاده می‌شود و باید در برنامه‌ها از آن اجتناب شود. در پایتون، مقادیر ثبات‌های خود را این‌گونه ذخیره خواهیم کرد:

py  self.gpio = [0]*16 # 16 zeroes

همچنین ۲ ثبات زمان‌سنج (timer) دارد که اساساً فقط با کاهش‌یافتن به صفر در هر چرخه، تأخیر ایجاد می‌کنند و در این فرایند یک عملیات را هدر می‌دهند. باز هم، در پایتون، این کار به سادگی تعریف دو متغیر است که در هر چرخه کاهششان می‌دهیم.

py  self.sound_timer = 0
  self.delay_timer = 0

یک ثبات ایندکس (index) دارد که ۱۶ بیتی است.

py  self.index = 0

ثبات شمارندهٔ برنامه (program counter) نیز ۱۶ بیتی است.

py  self.pc = 0

یک اشاره‌گر پشته (stack pointer) هم هست که آدرس بالاترین عنصر پشته را نگه می‌دارد. پشته در هر زمان حداکثر ۱۶ عنصر دارد. از آنجا که این کار را با پایتون انجام می‌دهیم که لیستی دارد و می‌توانیم روی آن pop/append کنیم، می‌توانیم این را نادیده بگیریم. در پایتون فقط یک لیست می‌سازیم:

py  self.stack = []

به سراغ کد!

برای ورودی/خروجی خود، از pyglet استفاده می‌کنیم؛ ماژولی برای پایتون که کدهای تکراری OpenGL را می‌پوشاند تا به‌سادگی بتوانیم گرافیک خروجی بگیریم. این ماژول می‌تواند خروجی صدا را هم مدیریت کند. و آه، ورودی صفحه‌کلید را هم انجام می‌دهد! حالا فقط CPU باقی مانده است.

نکات کوچکی دربارهٔ پیاده‌سازی من. از آنجا که از pyglet روی پایتون ۲.۶ استفاده می‌کنیم و pyglet با نخ‌ها (threads) کار نمی‌کند، اساساً کاری که می‌کنیم این است که از کلاس Window مربوط به pyglet زیرکلاس می‌سازیم و مفسر CHIP8 خود را از همان‌جا اجرا می‌کنیم:

py  class cpu (pyglet.window.Window)

مزیت افزوده این است که مجبور نیستیم کنترل‌کننده‌های ورودی خودمان را بسازیم — فقط باید متدهای ورودی صفحه‌کلید را بازنویسی (override) کنیم:

py  def on_key_press(self, symbol, modifiers):


  def on_key_release(self, symbol, modifiers):

اساساً همهٔ شبیه‌سازها ساختار حلقهٔ اصلی این‌گونه دارند:

py  def main(self):

    self.initialize()

    self.load_rom(sys.argv[1])

    while not self.has_exit:

      self.dispatch_events()      

      self.cycle()

      self.draw()

بیایید کمی در این کد بچرخیم. اولین قدم، مقداردهی اولیهٔ متغیرهای ماست. همهٔ ثبات‌ها را صفر کنید، همهٔ ورودی‌های کلید را بازنشانی کنید و شمارندهٔ برنامه (self.pc) را بازنشانی کنید. یک رام بارگذاری کنید، سپس هر چرخه را انجام دهید و نمایشگر را در صورت نیاز به‌روزرسانی کنید.

شمارندهٔ برنامه؟! این دیوانگی چیست؟ خوب، اساساً شمارندهٔ برنامه یک اشاره‌گر به آدرس حافظه‌ای از دستورالعمل است که قرار است در مرحلهٔ بعد پردازشش کنیم. در CHIP8، چون مفسر بخش ابتدایی حافظه را اشغال می‌کند، باید این را به آفست (offset) که برابر 0x200 است اشاره دهیم (به مرجع کاگوود مراجعه کنید؛ زیاد به آن مراجعه خواهیم کرد). بیشتر این کارها در متد cycle() انجام می‌شود که بعداً به آن خواهیم پرداخت.

ولی صبر کن! مگر من نگفتم فونت‌ها هم قرار است در حافظه ذخیره شوند؟ بله، و شاید اگر حرفم را قطع نمی‌کردی، دوست خیالی من، به آن هم می‌رسیدم. اساساً CHIP8 از «اسپرایت» (sprite)ها برای گرافیک استفاده می‌کند. اسپرایت‌ها اساساً مجموعه‌ای از بیت‌ها هستند که وضعیت روشن/خاموش مجموعه‌ای متناظر از پیکسل‌ها را نشان می‌دهند. برای مثال، اسپرایت عدد صفر این‌گونه به نظر می‌رسد (برگرفته از مرجع کاگوود، همان منبع عالی):

«0» باینری هگز
**** 11110000 0xF0
*  * 10010000 0x90
*  * 10010000 0x90
*  * 10010000 0x90
**** 11110000 0xF0

حالا، CHIP8 (حداقل پیاده‌سازی اصلی) اسپرایت‌های ۱۶ رقم هگزادسیمال را در حافظه دارد. چون هر کاراکتر فونت ۸×۵ بیت است، برای هر کاراکتر به ۵ بایت حافظه نیاز داریم. پس تابع init ما حالا این‌گونه خواهد بود، با بارگذاری فونت:

py  def initialize(self):

    self.clear()

    self.memory = [0]*4096 # max 4096

    self.gpio = [0]*16 # max 16

    self.display_buffer = [0]*64*32 # 64*32

    self.stack = []

    self.key_inputs = [0]*16    

    self.opcode = 0

    self.index = 0

    self.delay_timer = 0

    self.sound_timer = 0

    self.should_draw = False

    self.pc = 0x200

    i = 0

    while i < 80:

      # load 80-char font set

      self.memory[i] = self.fonts[i]

      i += 1

من یک پرچم should_draw آن‌جا گذاشتم تا فقط وقتی لازم است نمایشگر را به‌روزرسانی کنیم. همچنین self.clear() فقط پنجرهٔ pyglet را پاک می‌کند.

با این دانش، حالا می‌توانیم بارگذاری ROM را در حافظه شروع کنیم. ROMها به‌سادگی با باز کردن آن‌ها به‌صورت باینری می‌توانند در حافظه خوانده شوند:

py  def load_rom(self, rom_path):

    log("Loading %s..." % rom_path)

    binary = open(rom_path, "rb").read()

    i = 0

    while i < len(binary):

      self.memory[i+0x200] = ord(binary[i])

      i += 1

در ضمن، تابع log() که آن‌جا گذاشتم، به این دلیل است که کاربر هنگام اجرا گزینهٔ روشن/خاموش‌کردن پیام‌های لاگ را داشته باشد.

حالا شروع به پردازش می‌کنیم!

متد cycle()

هر چرخه این کار را می‌کند:

py  def cycle(self): 

    self.opcode = self.memory[self.pc]

    #

    # TODO: process this opcode here

    #

    # After 

    self.pc += 2

    # decrement timers

    if self.delay_timer > 0:

      self.delay_timer -= 1

    if self.sound_timer > 0:

      self.sound_timer -= 1

      if self.sound_timer == 0:

        # Play a sound here with pyglet!

اپ‌کد (opcode) اساساً دستورالعملی است که باید انجام دهیم. بنابراین در قلب ماجرا، ما اساساً باینری را خط‌به‌خط می‌خوانیم و اقدامات مرتبط با هر خط را انجام می‌دهیم (این کار در واقع خیلی کند است — CHIP8 ساده است، بنابراین ما متوجهش نمی‌شویم؛ اما برای سایر ماشین‌های شبیه‌سازیشده، رویکردهای دیگری ممکن است که خارج از حوصلهٔ این مقاله است). حالا کمی به TODO فکر کنیم.

هر اپ‌کد در CHIP8 دو بایت طول دارد. شمارندهٔ برنامه به اپ‌کدی که باید پردازش کنیم اشاره می‌کند؛ پس از دریافت و پردازش اپ، شمارندهٔ برنامه دو بایت افزایش می‌یابد. سپس این فرایند تا پایان برنامه تکرار می‌شود.

اینجا بخش پیچیدهٔ ماجراست. در C می‌توانیم به‌راحتی برای اپ‌کدها یک دستور switch بسازیم تا هر کاری که می‌خواهیم انجام دهد. اما ما از پایتون استفاده می‌کنیم. پایتون دستور switch ندارد — باید از if-else ترکیبی استفاده کنیم. از آنجا که CHIP8 بسیار ساده است، در واقع می‌توانیم این کار را انجام دهیم، اما کد بسیار زشتی خواهد بود و ما این را نمی‌خواهیم. خوشبختانه، در پایتون می‌توانیم از دیکشنری‌ها برای ذخیرهٔ جفت‌های اپ‌کد-متد استفاده کنیم. پس بخش TODO به‌سادگی این‌گونه خواهد بود:

py    self.vx = (self.opcode & 0x0f00) >> 8

    self.vy = (self.opcode & 0x00f0) >> 4

    self.pc += 2

    # 2. check ops, lookup and execute

    extracted_op = self.opcode & 0xf000

    try:

      self.funcmap[extracted_op]() # call the associated method

    except:

      print "Unknown instruction: %X" % self.opcode

اطلاعات کوچکی دربارهٔ اپ‌کدهای CHIP8. آن‌ها معمولاً در قالب XXXX هستند. معمولاً می‌توانید دستورالعمل را از اولین نیبل (سمت چپ) آن رمزگشایی کنید؛ پس اپ را با یک AND بیتی استخراج می‌کنیم و آن را در نقشهٔ توابع خود (self.funcmap) جست‌وجو می‌کنیم. اگر آن‌جا نبود، فقط یک خطا پرتاب می‌کنیم. توجه: مقدار self.pc قبل از اجرای دستور افزایش می‌یابد؛ بنابراین هر تغییر در آن (مثلاً در پرش‌ها) حفظ می‌شود.

همین! ما دیگر اسکلت پایهٔ شبیه‌ساز خود را داریم. حالا فقط باید همهٔ دستورالعمل‌ها را یک‌به‌یک پیاده‌سازی کنیم (بخش «باحال» ماجرا).

نمونه دستور: پاک‌کردن صفحه با 00E0 و بازگشت با 00EE

مرجع عالی کاگوود همهٔ دستورالعمل‌های لازم را در سندی که قبلاً لینک شد فهرست کرده است. در اینجا اولین و ساده‌ترین دستور را پیاده‌سازی می‌کنیم — دستور پاک‌کردن صفحه. این با اپ‌کد 0x00E0 مطابقت دارد. اما صبر کن؛ از آنجا که در cycle() ما فقط از نیبل سمت چپ استفاده کردیم، این احتمال وجود دارد که با دستورالعمل دیگری که در قالب 0x0XXX قرار می‌گیرد تداخل پیدا کنیم: 0x00EE یا اپ‌کد «بازگشت از زیربرنامه». پس کاری که می‌توانیم بکنیم این است که استخراج دیگری انجام دهیم:

py  def _0ZZZ(self):

    extracted_op = self.opcode & 0xf0ff

    try:

      self.funcmap[extracted_op]()

    except:

      print "Unknown instruction: %X" % self.opcode

در اینجا، وقتی با اپ‌کدی مواجه می‌شویم که نیبل سمت چپش 0 است، دو نیبل اول و آخر را استخراج می‌کنیم و متد متناظر را در نقشهٔ توابع جست‌وجو می‌کنیم. 0x00E0 باید به CLS نگاشت شود و 0x00EE باید به بازگشت از زیربرنامه:

py  def _0ZZ0(self):

    log("Clears the screen")

    self.display_buffer = [0]*64*32 # 64*32

    self.should_draw = True

برای بازگشت از یک زیربرنامه، فقط باید بالاترین آدرس را از پشتهٔ خود pop کنیم:

py  def _0ZZE(self):

    log("Returns from subroutine")

    self.pc = self.stack.pop()

و در self.funcmap:

py    self.funcmap = {0x0000: self._0ZZZ,

                    0x00e0: self._0ZZ0,

                    0x00ee: self._0ZZE,

    ....

که در آن self._0ZZE متد «بازگشت» خواهد بود. چرا فقط 0x00E0 و 0x00EE را مستقیماً به متدهای لازم تنظیم نمی‌کنیم؟ خوب، در واقع می‌توانستیم، اما دستورالعمل‌های 0x0xxx در واقع موارد خاصی هستند، چون ورودی ندارند. معمولاً سه نیبل آخر حاوی ورودی‌های عملیات‌اند و ثابت نیستند؛ بنابراین نمی‌توانند همان‌طور که هستند نگاشت شوند. برای مثال، به دستورالعمل بعدی نگاه کنید که یک پرش (JUMP) انجام می‌دهد:

نمونه دستور: پرش با 1XXX

اپ‌کد پرش (JUMP)، که با 1 شروع می‌شود، با سه نیبل متناظر با آدرس دستورالعملی که باید بعداً اجرا شود دنبال می‌شود. حالا می‌بینید که چرا باید نیبل‌ها را به‌صورت بیتی استخراج کنیم — آدرس پرش تغییر می‌کند، اما شناسهٔ اپ‌کد تغییر نمی‌کند و ما می‌توانیم از آن برای شناسایی دستورالعمل استفاده کنیم.

برای انجام یک پرش، به‌سادگی شمارندهٔ برنامه را روی آدرس دستورالعمل بعدی تنظیم کنید تا در چرخهٔ بعدی اجرا شود:

py  def _1ZZZ(self):

    log("Jumps to address NNN.")

    self.pc = self.opcode & 0x0fff

و در نقشهٔ توابع ما:

py    self.funcmap = {0x0000: self._0ZZZ,

                    0x00e0: self._0ZZ0,

                    0x00ee: self._0ZZE,

                    0x1000: self._1ZZZ,

    ....

همین است! حالا برای هر یک از اپ‌کدهای تعریف‌شده در مجموعهٔ دستورالعمل‌ها این کار را تکرار (بشویید و تکرار کنید) کنید و وویلا! شبیه‌ساز CHIP8 خودتان.

نکاتی دربارهٔ اپ‌کدهای مهم

اپ‌کدهایی که از ثبات‌های V0 تا VF استفاده می‌کنند

نکته دربارهٔ پیاده‌سازی cycle() من. این دو خط را خواهید دید:

py    self.vx = (self.opcode & 0x0f00) >> 8

    self.vy = (self.opcode & 0x00f0) >> 4

برخی اپ‌کدها از ثبات‌های همه‌کاره (general purpose) استفاده می‌کنند. برای مثال، 0x4XNN که «اگر VX برابر NN نبود، دستورالعمل بعدی را رد می‌کند (skip)». برای مدیریت این، دستورالعمل‌های بالا فقط نیبل‌ها را با عملیات بیتی استخراج می‌کنند تا ثبات‌های مرتبط را بگیرند (که معمولاً در نیبل دوم و سوم ذخیره شده‌اند). سپس می‌توانم از این برای انجام skip استفاده کنم:

py  def _4ZZZ(self):

    log("Skips the next instruction if VX doesn't equal NN.")

    if self.gpio[self.vx] != (self.opcode & 0x00ff):

      self.pc += 2

همین موضوع برای مقایسه صادق است:

py  def _5ZZZ(self):

    log("Skips the next instruction if VX equals VY.")

    if self.gpio[self.vx] == self.gpio[self.vy]:

      self.pc += 2

استفاده از پرچم حمل (carry flag)

هنگام خواندن مرجع کاگوود باید مراقب باشید، چون برخی عملیات‌ها به تنظیم پرچم VF نیاز دارند. برای مثال، عملیات 0x8XX4 از VF به‌عنوان پرچم حمل (carry flag) در جمع استفاده می‌کند. چرا این لازم است؟ یادتان می‌آید که گفتیم ثبات‌ها فقط مقادیر ۸ بیتی ذخیره می‌کنند؟ اگر دو مقدار ۸ بیتی را جمع کنیم، احتمال دارد نتیجه سرریز (overflow) شود (۱ بایت حداکثر مقدار 0xFF را دارد). اگر نتیجه از حداکثر بزرگ‌تر باشد، پرچم حمل تنظیم می‌شود.

py  def _8ZZ4(self):

    log("Adds VY to VX. VF is set to 1 when there's a carry, and to 0 when there isn't.")

    if self.gpio[self.vx] + self.gpio[self.vy] > 0xff:

      self.gpio[0xf] = 1

    else:

      self.gpio[0xf] = 0

    self.gpio[self.vx] += self.gpio[self.vy]

    self.gpio[self.vx] &= 0xff

همچنین در تفریق به‌عنوان پرچم «قرض» (borrow) استفاده می‌شود:

py  def _8ZZ5(self):

    log("VY is subtracted from VX. VF is set to 0 when there's a borrow, and 1 when there isn't")

    if self.gpio[self.vy] > self.gpio[self.vx]:

      self.gpio[0xf] = 0

    else:

      self.gpio[0xf] = 1

    self.gpio[self.vx] = self.gpio[self.vx] - self.gpio[self.vy]

    self.gpio[self.vx] &= 0xff

رسم (Drawing)

حالا برای دشوارترین بخش. خوب، در واقع نه. رسم در CHIP8 کاملاً سرراست است. یک پیکسل یا روشن است یا خاموش، و ما حالت‌ها را در display_buffer که قبلاً تعریف کردیم ذخیره می‌کنیم. دو اپ‌کد رسم وجود دارد: 0xDXXX که اسپرایت‌های بارگذاری‌شده از ROM را رسم می‌کند و 0xFZ29 که فقط یک کاراکتر رسم می‌کند. بیایید اول ساده‌تر را پیاده‌سازی کنیم؛ رسم یک کاراکتر.

py  def _FZ29(self):

    log("Set index to point to a character")

    self.index = (5*(self.gpio[self.vx])) & 0xfff

بله، همین است. این اپ فقط ثبات ایندکس را روی آدرس اولین بایت کاراکتر متناظر تنظیم می‌کند. این به این دلیل است که کد اصلی رسم، که حالا آن را پیاده‌سازی می‌کنیم، از این ثبات برای یافتن اسپرایتی که باید رسم شود استفاده می‌کند. برای درک بهتر، بیایید دوباره مستندات را بخوانیم. طبق گفتهٔ کاگوود، DXYN یعنی:

مستندات: «Display n-byte sprite starting at memory location I at (Vx, Vy), set VF = collision.» — اسپرایت n بایتی را که از محل حافظهٔ I در (Vx, Vy) شروع می‌شود نمایش بده؛ VF = برخورد (collision).

بحث اسپرایت‌های فونت را از قبل به خاطر دارید؟ برای اسپرایت‌های سفارشی هم صدق می‌کند. هر سطر (بایت) با یک سطر ۸ پیکسلی روی صفحه متناظر است. اما در اینجا، به‌جای اینکه ۵ بایت ثابت باشد، مقدار N می‌تواند با ارتفاع اسپرایت سفارشی متناظر باشد. همچنین، بایت‌ها روی صفحه XOR می‌شوند. این در واقع مبتکرانه است — چون منابع CHIP8 محدود است، از خود نمایشگر برای ذخیرهٔ وضعیت اسپرایت‌ها استفاده می‌کند! پس XOR کردن یک پیکسل با مقدار جدید به شما می‌گوید که وضعیت تغییر کرده است یا نه و بنابراین برخورد را نشان می‌دهد. در اینجا، برخورد در VF علامت‌گذاری می‌شود: اگر پیکسلی از ۱ به ۰ تغییر کند، VF برابر ۱ تنظیم می‌شود. حالا برای پیاده‌سازی کد به‌روزرسانی بافر:

py  def _DZZZ(self):

    log("Draw a sprite")

    self.gpio[0xf] = 0

    x = self.gpio[self.vx] & 0xff

    y = self.gpio[self.vy] & 0xff

    height = self.opcode & 0x000f

    row = 0

    while row < height:

      curr_row = self.memory[row + self.index]

      pixel_offset = 0

      while pixel_offset < 8:

        loc = x + pixel_offset + ((y + row) * 64)

        pixel_offset += 1

        if (y + row) >= 32 or (x + pixel_offset - 1) >= 64:

          # ignore pixels outside the screen

          continue

        mask = 1 << 8-pixel_offset

        curr_pixel = (curr_row & mask) >> (8-pixel_offset)

        self.display_buffer[loc] ^= curr_pixel

        if self.display_buffer[loc] == 0:

          self.gpio[0xf] = 1

        else:

          self.gpio[0xf] = 0

      row += 1

    self.should_draw = True

اینجا داریم چه کار می‌کنیم؟ اساساً به پیکسل نشان‌داده‌شده در x,y می‌رویم — سپس هر پیکسل در اسپرایت خود را با بافر مقایسه می‌کنیم و در صورت نیاز XOR می‌کنیم. سپس فقط پرچم رسم خود را روی True تنظیم می‌کنیم تا فراخوانی draw() آن را بگیرد.

نکاتی دربارهٔ متد draw() من. من از pyglet استفاده کردم که یک پوشش‌دهندهٔ OpenGL است، اما در کارهای سطح پایین، مثل رسم پیکسل‌به‌پیکسل، واقعاً کند است. پس در اینجا آن را شبه‌پیکسل‌به‌پیکسل رسم می‌کنم — یک پیکسل ۱۰×۱۰ دارم (که پنجرهٔ من را ۶۴۰×۳۲۰ می‌کند) و پیکسل را در x*10 و y*10 رسم می‌کنم:

py  def draw(self):

    if self.should_draw:

      # draw

      self.clear()

      line_counter = 0

      i = 0

      while i < 2048:

        if self.display_buffer[i] == 1:

          # draw a square pixel

          self.pixel.blit((i%64)*10, 310 - ((i/64)*10))

        i += 1

      self.flip()

      self.should_draw = False

این برای سایر کاربردها کند خواهد بود، اما برای اهداف نمایش ما به‌اندازهٔ کافی سریع است.

ورودی صفحه‌کلید (Keyboard input)

از آنجا که از Window مربوط به pyglet زیرکلاس ساخته‌ایم، فقط می‌توانیم متدهای ورودی صفحه‌کلید را بازنویسی کنیم:

py  def on_key_press(self, symbol, modifiers):

    log("Key pressed: %r" % symbol)

    if symbol in KEY_MAP.keys():

      self.key_inputs[KEY_MAP[symbol]] = 1

      if self.key_wait:

        self.key_wait = False

    else:

      super(cpu, self).on_key_press(symbol, modifiers)


  def on_key_release(self, symbol, modifiers):

    log("Key released: %r" % symbol)

    if symbol in KEY_MAP.keys():

      self.key_inputs[KEY_MAP[symbol]] = 0

کد بالا کاملاً خودتوضیح است — ما فقط حالت‌های کلید را مطابق ورودی صفحه‌کلید به‌روزرسانی می‌کنیم. در شبیه‌ساز، فقط می‌توانیم مقادیر را در صورت نیاز بخوانیم. ورودی با صفحه‌کلید توسط 0xExxE و 0xExx1 مدیریت می‌شود:

py  def _EZZE(self):

    log("Skips the next instruction if the key stored in VX is pressed.")

    key = self.gpio[self.vx] & 0xf

    if self.key_inputs[key] == 1:

      self.pc += 2
py  def _EZZ1(self):

    log("Skips the next instruction if the key stored in VX isn't pressed.")

    key = self.gpio[self.vx] & 0xf

    if self.key_inputs[key] == 0:

      self.pc += 2

BCD: FX33

این دستورالعمل همان جایی است که بیشتر مردم به مشکل برمی‌خورند، و من آن را به‌عنوان تمرینی برای خواننده می‌گذارم. اما اساساً، فقط باید مقدار VX را به‌صورت BCD سه‌رقمی ذخیره کنید، از memory[self.index] به‌عنوان مهم‌ترین رقم تا memory[self.index+2] به‌عنوان کم‌اهمیت‌ترین رقم. برای مثال، اگر:

pyself.gpio[self.vx] = 123

آنگاه:

pyself.memory[self.index] = 1

self.memory[self.index+1] = 2

self.memory[self.index+2] = 3
