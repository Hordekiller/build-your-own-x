یک سرویس چت چه چیزی می‌خواهد؟

چت جمعی مشکل دوگانه دارد: پخش پیام به همهٔ کاربران (broadcast) و قالب پیام که بین سرور و کلاینت ثابت بماند. راه‌حل‌های استاندارد: یک الگوی انتشار/اشتراک (PUB/SUB) مثل ZeroMQ برای بخش اول، و Protocol Buffers برای بخش دوم. این آموزش هر دو را در Rust پیاده می‌کند.

معماری: زمگ و PUB/SUB

ZeroMQ یک کتابخانهٔ سوکت است که الگوهای پیام‌رسانی دارد؛ PUB/SUB یعنی «ناشر» پیام را روی یک موضوع می‌فرستد و همهٔ مشترکانِ آن موضوع می‌گیرند. در چت: سرور PUB است، کلاینت‌ها SUB:

Rust// سمت سرور (پخش)
let ctx = zmq::Context::new();
let publisher = ctx.socket(zmq::PUB).unwrap();
publisher.bind("tcp://*:5555").unwrap();

// سمت کلاینت (دریافت همهٔ پیام‌ها)
let subscriber = ctx.socket(zmq::SUB).unwrap();
subscriber.connect("tcp://server:5555").unwrap();
subscriber.set_subscribe(b"").unwrap();   // همهٔ موضوع‌ها

loop {
    let msg = subscriber.recv_string(0).unwrap();
    println!("{}", msg.unwrap());
}

مزیت زمگ: بدون منطق اتصال/اتصال مجدد دستی؛ پیام‌ها صف‌بندی و قابل‌بازیابی‌اند، و مقیاس‌پذیری خوبی دارد.

قالب با Protocol Buffers

پیام چت فقط متن نیست: نام کاربر، زمان، آیدی اتاق. Protocol Buffers (از گوگل) قالب‌بندی فشرده و توسعه‌پذیری می‌دهد — تعریف در فایل `.proto` و کد تولیدشده تایپ‌ایمن:

Protomessage ChatMessage {
  required string username = 1;
  required string content = 2;
  required int64 timestamp = 3;
}
Rust// رمزگذاری پیام قبل از PUB کردن
let mut msg = ChatMessage::new();
msg.set_username(user);
msg.set_content(text);
let bytes = msg.write_to_bytes().unwrap();
publisher.send(bytes, 0).unwrap();

چون شماره‌گذاری فیلدها صریح است، نسخه‌های بعدی proto می‌توانند فیلد اضافه کنند بدون شکستن کلاینت‌های قدیمی — مشکل همیشگی APIهای متنی.

مقیاس‌پذیری واقعی

بعد از MVP: کلاینت بتواند پیام را به سرور بفرستد (REQ/REP جدا از PUB/SUB)، اتاق‌ها با موضوع‌های زمگ مجزا شوند، و تاریخچه در دیتابیس ذخیره شود. هستهٔ «انتشار به مشترکان» همان الگوی پایه است که الان دارید — همین است که در MQTT و Socket.IO هم نقش اصلی را بازی می‌کند.
