فصل اصلی: Introduction

با ساختن پایگاه دادهٔ خودتان اصول را مسلط شوید

چه چیزی یاد بگیریم؟

سیستم‌های پیچیده مانند پایگاه‌های داده بر پایهٔ چند اصل ساده ساخته شده‌اند:

  1. اتمیک بودن و ماندگاری (Atomicity & durability). یک پایگاه داده چیزی فراتر از فایل‌هاست!
    • ماندگار کردن داده با fsync.
    • بازیابی از خرابی (crash recovery).
  2. ذخیره‌گاه کلید-مقدار (KV store) مبتنی بر درخت B.
    • ساختارهای دادهٔ مبتنی بر دیسک.
    • مدیریت فضا با یک لیست آزاد.
  3. پایگاه دادهٔ رابطه‌ای روی KV.
    • نحوهٔ نگاشت جدول‌ها و ایندکس‌ها به درخت‌های B سطح پایین.
    • زبان پرس‌وجوی شبیه به SQL؛ پارسر و مفسر.
  4. کنترل همروندی برای معاملات.

با انجام‌دادن یاد بگیرید: اصول به‌جای اصطلاحات

فاینمن گفته: «آنچه نمی‌توانم بسازم، نمی‌فهمم». پس آیا می‌شود با خواندن دربارهٔ پایگاه داده، پایگاه داده ساخت؟ متأسفانه ادبیات پایگاه داده پر از اصطلاحات گیج‌کنندهٔ چندمعناست. بنابراین مهم است که با انجام‌دادن یاد بگیریم.

هرچند چیزهای زیادی برای یادگیری هست، هستهٔ یک پایگاه داده فقط از چند اصل تشکیل شده است.

موضوع ۱: ماندگاری و اتمیک بودن

پایگاه داده چیست؟

در بازاریابی هر چیزی «پایگاه داده» نامیده می‌شود: صفحه‌گسترده، سرورهای کش و... ما فقط به چیزی که به‌طور سنتی پایگاه داده نامیده می‌شود علاقه‌مندیم؛ یعنی MySQL، Postgres، SQLite و مانند آن. وجه اشتراک آن‌ها چیست؟

  • می‌توانند داده را روی دیسک ماندگار کنند.
  • مبتنی بر دیسک‌اند و می‌توانند با دادهٔ بزرگ‌تر از حافظه کار کنند.
  • از صفر پیاده شده‌اند، نه به‌صورت wrapper روی پایگاه‌های دادهٔ دیگر.

تنها چند کدبیس بالغ این معیارها را دارند و همگی بزرگ‌اند. مثلاً کد منبع SQLite3 بر حسب مگابایت، حتی فشرده‌شده، اندازه گرفته می‌شود. یک پایگاه دادهٔ واقعی بهترین مکان برای یادگیری اصول نیست. به‌جایش، ما یک پایگاه داده را از صفر در ۳۰۰۰ خط کد می‌نویسیم.

یک پایگاه داده چیزی فراتر از یک قالب داده است

ماندگار کردن داده روی دیسک (durability) معیار شمارهٔ ۱ یک پایگاه دادهٔ سنتی است. به همین دلیل گوشی‌های موبایل از SQLite استفاده می‌کنند؛ یک پایگاه دادهٔ فایل‌محور. اما اگر پایگاه داده هم به هر حال یک فایل است، چرا فقط از فایل‌ها استفاده نکنیم؟ چون «ماندگار کردن» الزامات مشخصی دارد: در برهه‌ای از زمان، دادهٔ اضافه‌شده به پایگاه داده تضمین شده حتی اگر ماشین خراب شود (مثلاً به دلیل قطع برق) ماندگار بماند.

۲ الزام وجود دارد: جان‌به‌دربردن از خرابی‌ها؛ و تأیید وضعیت ماندگاری. با توجه به اینکه بیشتر پایگاه‌های داده روی سیستم‌های فایل اجرا می‌شوند، سیستم فایل نیز باید این الزامات را برآورده کند. پس سیستم‌های فایل تا حدی شبیه پایگاه داده‌اند. اما تفاوت بزرگ این است که استفادهٔ معمول از سیستم فایل (نوشتن در فایل‌ها) هیچ تضمین ماندگاری‌ای ندارد و پس از قطع برق به ازدست‌رفتن یا خراب‌شدن داده می‌انجامد؛ در حالی که استفادهٔ معمول از پایگاه داده، ماندگاری را تضمین می‌کند.

ماندگار کردن فایل‌ها یعنی پیاده‌سازی نیمی از یک پایگاه داده؛ که ما یاد خواهیم گرفت.

فراخوان سیستمی fsync

fsync عملیات سیستم فایلی است که همهٔ داده‌های قبلاً نوشته‌شده را ماندگار می‌کند. برای درخواست و تأیید ماندگاری استفاده می‌شود؛ یک پایگاه داده فقط بعد از fsync موفقیت را به کلاینت برمی‌گرداند. اما اگر پایگاه داده قبل یا در حین fsync خراب شود چه؟ ممکن است تازه‌ترین داده از دست برود، اما نباید نیمه‌ازدست‌رفته و نیمه‌ماندگار باشد. این «همه‌یا-هیچ» را اتمیک بودن می‌نامند.

یک پایگاه داده باید از خرابی به وضعیتی منطقی برگردد؛ که سخت‌تر از استفاده از fsync است.

موضوع ۲: ساختارهای دادهٔ ایندکس‌گذاری

کنترل تأخیر و هزینه با ساختارهای داده

یک پایگاه داده پرس‌وجو را بدون اینکه کاربر بداند چگونه، به نتیجه تبدیل می‌کند. اما نتیجه تنها دغدغه نیست؛ تأخیر و هزینه (حافظه، ورودی/خروجی، محاسبات) هم مهم‌اند؛ از این رو تمایز بین تحلیلی (OLAP) و تراکنشی (OLTP):

  • OLAP می‌تواند حجم عظیمی از داده را با تجمیع و join درگیر کند. ایندکس‌گذاری می‌تواند محدود یا وجود نداشته باشد. بیشترشان ذخیره‌گاه‌های ستون‌محورند. برای پرس‌وجوهای «تحلیلی» بی‌درنگ و آفلاین استفاده می‌شوند که به تأخیر حساس نیستند.
  • OLTP حجم کمی از داده را با ایندکس لمس می‌کند. تأخیر و هزینهٔ کم. مبتنی بر B+tree یا LSM-tree. برای پرس‌وجوهای از پیش برنامه‌ریزی‌شدهٔ کاربرمحور استفاده می‌شود که به نتیجهٔ فوری نیاز دارند.

کلمهٔ «تراکنشی» دربارهٔ تراکنش‌های پایگاه داده نیست؛ فقط اصطلاح است.

هر ۳ پایگاه دادهٔ سنتی (MySQL، Postgres، SQLite) OLTP هستند. پایگاه‌های دادهٔ OLTP اگر داده کوچک باشد می‌توانند کمی OLAP هم انجام دهند. اما استفاده از پایگاه‌های دادهٔ جدا برای موارد استفادهٔ جدا مؤثرتر است. پس برخی از پایگاه‌های دادهٔ جدید فقط OLAP هستند، مثل ClickHouse، DuckDB و همهٔ پایگاه‌های دادهٔ «کلان‌داده».

OLAP و OLTP دو مسیر متفاوت برای پایگاه داده‌اند. ما OLTP را انتخاب می‌کنیم و OLAP را نادیده می‌گیریم؛ پس ساختارهای دادهٔ ایندکس‌گذاری حیاتی‌اند و join و تجمیع بی‌ربط‌اند.

ساختارهای دادهٔ درون‌حافظه در برابر مبتنی بر دیسک

گذاشتن یک ساختار دادهٔ ایندکس روی دیسک چالش‌های بیشتری دارد. اولین آن، انتخاب ساختار دادهٔ مناسب است. RAM و دیسک ویژگی‌های متفاوتی دارند؛ به‌خصوص تأخیر. حتی با بهترین SSDها، تأخیر ۳ مرتبهٔ بزرگی بزرگ‌تر از RAM است. بررسی این ویژگی‌ها به فقط ۲ ساختار داده می‌انجامد: B+tree و LSM-tree. پس پایگاه‌های داده از نظر ساختار داده بسیار محدودند.

چالش دوم، ماندگار کردن داده روی دیسک است. یک پایگاه داده فقط یک ساختار داده روی دیسک است؛ پس ساختار داده پیش‌نیاز است. (برای تمرین ساختارهای داده کتاب «Build Your Own Redis» نویسنده را ببینید.) می‌توانید ساختارهای داده را از کتاب‌های درسی یاد بگیرید، اما بخش گم‌شده، گذاشتن آن‌ها روی دیسک و به‌روزرسانی تدریجی آن‌ها ضمن حفظ اتمیک بودن و ماندگاری است.

چالش سوم همروندی است. برای دادهٔ درون‌حافظه معمولاً سریال‌سازی دسترسی به ساختار داده با یک mutex کافی است. برای دادهٔ مبتنی بر دیسک، تأخیر ورودی/خروجی این را غیرعملی می‌کند و کنترل همروندی پیشرفته‌تری لازم است.

موضوع ۳: پایگاه دادهٔ رابطه‌ای روی KV

دو لایه از رابط‌های پایگاه داده

SQL تقریباً مترادف پایگاه داده است. اما SQL فقط یک رابط کاربری است؛ برای پایگاه داده بنیادی نیست. آنچه مهم است، قابلیت‌های زیربنایی است.

رابط بسیار ساده‌تر دیگر، کلید-مقدار (KV) است. می‌توانید یک کلید را بگیرید، بگذارید یا حذف کنید و مهم‌تر از همه، فهرستی از یک بازهٔ کلید به‌صورت مرتب بخوانید. KV ساده‌تر از SQL است چون یک لایه پایین‌تر است. پایگاه‌های دادهٔ رابطه‌ای روی رابط‌های شبیه به KV ساخته می‌شوند که موتورهای ذخیره‌سازی (storage engines) نامیده می‌شوند.

gotype KV interface {
    // get, set, del
    Get(key []byte) (val []byte, ok bool)
    Set(key []byte, val []byte)
    Del(key []byte)
    // range query
    FindGreaterThan(key []byte) Iterator
    // ...
}
type Iterator interface {
    HasNext() bool
    Next() (key []byte, val []byte)
}

نیمهٔ اول کتاب یک KV است که نیمهٔ دوم بر آن بنا می‌شود.

زبان‌های پرس‌وجو: پارسرها و مفسرها

قدم آخر آسان است، با وجود خطوط کد بیشتر. هم پارسر و هم مفسر فقط با بازگشت (recursion) کدنویسی می‌شوند! این درس تقریباً برای هر زبان برنامه‌نویسی، یا ساخت زبان برنامه‌نویسی یا DSL خودتان کاربرد دارد.

خلاصهٔ مقدمه

کتاب از یک KV مبتنی بر درخت B+ شروع می‌کند و بعد آن را به پایگاه دادهٔ رابطه‌ای با زبان پرس‌وجوی شبیه به SQL ارتقا می‌دهد. در ۳۰۰۰ خط کد.

فصل ۱: از فایل‌ها تا پایگاه داده

فصل اصلی: From Files To Databases

با یک مسئلهٔ به‌ظاهر ساده شروع می‌کنیم: ذخیرهٔ داده در یک فایل و تلاش برای اتمیک و ماندگار کردن آن؛ یعنی مقاوم در برابر خرابی.

۱.۱ به‌روزرسانی درجا (In-place) فایل‌ها

روش معمول ذخیره و بازنویسی یک فایل به این شکل است:

gofunc SaveData1(path string, data []byte) error {
    fp, err := os.OpenFile(path, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0664)
    if err != nil {
        return err
    }
    defer fp.Close()

    _, err = fp.Write(data)
    if err != nil {
        return err
    }
    return fp.Sync() // fsync
}

این روش استفاده از سیستم فایل به‌عنوان یک KV است، با نام فایل به‌عنوان «کلید» و دادهٔ فایل به‌عنوان «مقدار». پرچم O_CREATE فایل را اگر وجود ندارد می‌سازد و پرچم O_TRUNC دادهٔ قبلی را اگر فایل وجود دارد دور می‌ریزد.

fsync فراخوان سیستمی است که درخواست و تأیید می‌کند که دادهٔ فایل واقعاً نوشته شده است. این لازم است چون ممکن است سطوح زیادی از بافر وجود داشته باشد: کش صفحهٔ سیستمعامل؛ RAM دستگاه. بعد از یک fsync موفق، داده روی رسانهٔ نهایی ماندگار فرض می‌شود. در زبان Go، Sync() فقط fsync را صدا می‌زند.

این روش در الزامات اتمیک بودن و ماندگاری شکست می‌خورد:

  • کوتاه‌کردن (truncate) فایل یعنی امکان دارد به یک فایل خالی برسیم.
  • کوتاه‌نکردن یعنی امکان دارد به یک فایل نیمه‌نوشته‌شده برسیم.

این مسئلهٔ به‌روزرسانی داده درجا است.

۱.۲ تغییر نام اتمیک (Atomic Renaming)

جایگزینی اتمیک داده با تغییر نام فایل‌ها

برای اجتناب از به‌روزرسانی درجا، باید یک تکهٔ دادهٔ جدید بنویسیم و به‌صورت اتمیک به آن سوئیچ کنیم. عملیات «سوئیچ» همان rename() در سیستم فایل است که به‌طور خاص برای ممکن‌کردن فایل‌های اتمیک طراحی شده است.

text┌───┐  create   ┌───┐    ┌───┐  rename   ┌───┐
│ 1 │ ────────→ │ 1 │ +  │ 2 │ ────────→ │ 2 │
└───┘           └───┘    └───┘           └───┘
 old             old     temp            new
gofunc SaveData2(path string, data []byte) error {
    tmp := fmt.Sprintf("%s.tmp.%d", path, randomInt())
    fp, err := os.OpenFile(tmp, os.O_WRONLY|os.O_CREATE|os.O_EXCL, 0664)
    if err != nil {
        return err
    }
    defer func() { // 4. discard the temporary file if it still exists
        fp.Close() // not expected to fail
        if err != nil {
            os.Remove(tmp)
        }
    }()

    if _, err = fp.Write(data); err != nil { // 1. save to the temporary file
        return err
    }
    if err = fp.Sync(); err != nil { // 2. fsync
        return err
    }
    err = os.Rename(tmp, path) // 3. replace the target
    return err
}

«اتمیک بودن» در زمینه‌های مختلف معنای متفاوتی دارد. حداقل ۲ نوع اتمیک بودن وجود دارد:

  • اتمیک در برابر قطع برق (power-loss atomic): آیا خواننده بعد از خرابی وضعیت بدی مشاهده می‌کند؟
  • اتمیک خواننده-نویسنده (readers-writer atomic): آیا خواننده با یک نویسندهٔ هم‌زمان وضعیت بدی مشاهده می‌کند؟

SaveData1 در هر دو اتمیک بودن شکست می‌خورد؛ خواننده می‌تواند یک فایل خالی را با یا بدون خرابی مشاهده کند.

SaveData2 در برابر خواننده-نویسنده اتمیک است اما در برابر قطع برق اتمیک نیست. این تعجب‌آور است و بعداً توضیح داده می‌شود.

چرا تغییر نام کار می‌کند؟

سیستم‌های فایل نگاشتی از نام فایل‌ها به دادهٔ فایل نگه می‌دارند؛ پس جایگزینی یک فایل با تغییر نام فقط نام فایل را به دادهٔ جدید اشاره می‌کند بدون اینکه دادهٔ قدیمی را لمس کند. این نگاشت فقط یک «دایرکتوری» است. نگاشت چند-به-یک است؛ نام‌های متعدد می‌توانند به یک فایل ارجاع دهند، حتی از دایرکتوری‌های مختلف؛ این مفهوم «هاردلینک» است. فایلی با ۰ ارجاع به‌طور خودکار حذف می‌شود.

اتمیک بودن و ماندگاری rename() به به‌روزرسانی‌های دایرکتوری وابسته است. اما متأسفانه به‌روزرسانی یک دایرکتوری فقط در برابر خواننده-نویسنده اتمیک است؛ در برابر قطع برق اتمیک یا ماندگار نیست. پس SaveData2 همچنان نادرست است.

تله‌های fsync

هم ساختن یک فایل و هم تغییر نام فایل، دایرکتوریِ دربرگیرنده را به‌روزرسانی می‌کنند. پس باید راهی برای ماندگار کردن دایرکتوری‌ها وجود داشته باشد؛ بنابراین fsync را می‌توان روی دایرکتوری‌ها هم صدا زد. برای این کار باید یک دسته (file descriptor) از دایرکتوری به دست آورید. اصلاح کردن SaveData2 تمرینی برای خواننده است.

مسئلهٔ دیگر fsync مدیریت خطاست. اگر fsync شکست بخورد، به‌روزرسانی پایگاه داده شکست می‌خورد، اما اگر بعداً فایل را بخوانید چه؟ ممکن است دادهٔ جدید را حتی اگر fsync شکست خورده باشد بگیرید (به دلیل کش صفحهٔ سیستمعامل)! این رفتار به سیستم فایل بستگی دارد.

۱.۳ لاگ‌های فقط-الحاقی (Append-only Logs)

مسئلهٔ بازنویسی فایل، مشکل به‌روزرسانی‌های درجا و تله‌های fsync را نشان داد. با این حال، این به پایگاه‌های داده نزدیک نیست؛ چون ما نمی‌دانیم داده را به‌صورت افزایشی به‌روزرسانی کنیم.

به‌روزرسانی‌های افزایشی با لاگ‌ها

یک لاگ را می‌توان برای به‌روزرسانی‌های افزایشی استفاده کرد؛ فهرستی مرتب از توصیف‌های هر به‌روزرسانی ذخیره می‌کند. کل وضعیت را می‌توان با تفسیر هر ورودی لاگ بازسازی کرد. مثلاً یک لاگ برای به‌روزرسانی‌های KV:

text     0         1         2        3
| set a=1 | set b=2 | set a=3 | del b |

وضعیت نهایی a=3 است.

به‌روزرسانی اتمیک لاگ با چک‌سام‌ها (checksums)

بیایید مشکل دور انداختن ورودی‌های قدیمی لاگ را نادیده بگیریم و فرض کنیم لاگ فقط می‌تواند رشد کند. این را لاگ «فقط-الحاقی» می‌نامند؛ به‌روزرسانی درجا اجتناب می‌شود. مسئلهٔ بعدی، اتمیک کردن «الحاق» (append) است.

هر الحاق لاگ با fsync ماندگار می‌شود. اما اگر پایگاه داده بین الحاق و fsync خراب شود، آخرین ورودی ممکن است نیمه‌نوشته باشد. ورودی‌های خراب لاگ اجتناب‌ناپذیرند؛ راه‌حل این است که آخرین ورودی خراب را تشخیص دهیم و در بازیابی از خرابی آن را نادیده بگیریم.

تشخیص با افزودن یک چک‌سام به هر ورودی لاگ انجام می‌شود. یک ورودی لاگ می‌تواند با یک هدر با اندازهٔ ثابت شامل اندازهٔ ورودی و چک‌سام شروع شود. پایگاه داده در شروع‌به‌کار آخرین ورودی لاگ را بررسی می‌کند؛ اگر اندازه یا چک‌سام اشتباه بود، به‌سادگی آن را نادیده می‌گیرد.

چک‌سام‌ها ممکن است کاربردهای دیگری هم داشته باشند، مثل تشخیص خرابی بی‌صدای داده، اما خرابی بی‌صدای داده دغدغهٔ پایگاه داده نیست؛ چک‌سام‌های موجود در لاگ‌ها فقط برای تشخیص نوشتن‌های ناقص (در اصطلاح پایگاه داده: torn writes) در نظر گرفته شده‌اند.

لاگ به‌عنوان یک مؤلفهٔ پایگاه داده

یک لاگ هنوز پایگاه داده نیست؛ باید با ساختار دادهٔ ایندکس‌گذاری ترکیب شود. وقتی لاگ خیلی بزرگ می‌شود، ورودی‌های لاگ با ساختار داده ادغام می‌شوند. این مشکل رشد بی‌نهایت را حل می‌کند. مشکل باقی‌مانده نحوهٔ به‌روزرسانی اتمیک ساختار دادهٔ اصلی است. لاگ‌ها می‌توانند بخشی از راه‌حل باشند؛ که بعداً یاد می‌گیریم.

لاگ‌ها در پایگاه‌های داده کاربردهای دیگری هم دارند که فعلاً دربارهٔ آن‌ها بحث نمی‌کنیم. بیشتر پایگاه‌های داده از لاگ استفاده می‌کنند؛ MySQL حتی از ۲ لاگ استفاده می‌کند. اما پایگاه‌های داده بدون لاگ هم ممکن‌اند؛ که یاد خواهیم گرفت.

۱.۴ خلاصهٔ چالش‌های پایگاه داده

آنچه یاد گرفتیم:

  1. مشکلات به‌روزرسانی درجا.
    • با تغییر نام فایل‌ها از به‌روزرسانی درجا اجتناب کنید.
    • با لاگ‌ها از به‌روزرسانی درجا اجتناب کنید.
  2. لاگ‌های فقط-الحاقی.
    • به‌روزرسانی‌های افزایشی.
    • راه‌حل کامل نیست؛ ایندکس‌گذاری و استفادهٔ مجدد از فضا ندارد.
  3. استفاده از fsync.
    • هم دادهٔ فایل و هم دایرکتوری به fsync نیاز دارند.

آنچه همچنان پرسش است:

  1. ساختارهای دادهٔ ایندکس‌گذاری.
  2. ترکیب یک لاگ با یک ساختار دادهٔ ایندکس‌گذاری.
  3. همروندی.

۲.۱ انواع پرس‌وجوها

قبل از بحث دربارهٔ چالش‌های پایگاه داده باید ساختار داده را انتخاب کنیم؛ چون ساختار داده تعیین می‌کند چه نوع پرس‌وجوهایی پشتیبانی می‌شوند. SQL ظاهراً از پرس‌وجوهای دلخواه پشتیبانی می‌کند. اما فقط زیرمجموعهٔ کوچکی از پرس‌وجوها می‌توانند از ساختارهای داده بهره‌مند شوند؛ به همین دلیل کتاب روی OLTP تمرکز دارد. پرس‌وجوهای OLTP دنیای واقعی در یکی از ۳ نوع قرار می‌گیرند:

  1. پیمایش کل مجموعهٔ داده بدون ایندکس اگر جدول کوچک باشد.
  2. پرس‌وجوی نقطه‌ای (point query): پرس‌وجوی ایندکس با یک کلید تکی.
  3. پرس‌وجوی بازه‌ای (range query): پرس‌وجوی یک بازه از کلیدها به‌صورت مرتب.

سریع‌کردن پیمایش‌های بدون ایندکس دغدغهٔ OLAP است؛ پس آن را نادیده می‌گیریم و پرس‌وجوهای نقطه‌ای و بازه‌ای را در نظر می‌گیریم. پرس‌وجوهای بازه‌ای ایجاب می‌کنند ساختار داده کلیدها را مرتب نگه دارد. ساختار داده ۲ عملیات پشتیبانی می‌کند:

  1. Seek: یافتن کلید شروع بازه.
  2. Iterate: بازدید از کلید قبلی/بعدی به‌صورت مرتب.

پرس‌وجوهای نقطه‌ای فقط «seek» بدون «iterate» هستند. پس یک ساختار دادهٔ مرتب‌ساز تنها چیزی است که نیاز داریم.

۲.۲ جدول‌های درهم‌سازی (Hashtables)

اگر فقط پرس‌وجوهای نقطه‌ای (get، set، del) را در نظر بگیرید، جدول‌های درهم‌سازی قابل‌دوام‌اند؛ پس به دلیل نداشتن ترتیب، به آن‌ها کاری نداریم.

با این حال، کدنویسی یک جدول درهم‌سازی، حتی درون‌حافظه‌ای، هنوز تمرین ارزشمندی است. خیلی آسان‌تر از درخت B است که بعداً کدنویسی می‌کنیم، هرچند چند چالش باقی می‌ماند:

  • چگونه یک جدول درهم‌سازی را بزرگ کنیم؟ وقتی ضریب بار خیلی زیاد شد، کلیدها باید به جدول درهم‌سازی بزرگ‌تری منتقل شوند. انتقال همه‌چیز یک‌جا به‌طور منع‌کننده‌ای O(N) است. درهم‌سازی مجدد باید به‌صورت تدریجی انجام شود، حتی برای برنامه‌های درون‌حافظه مثل Redis.
  • چیزهای دیگری که قبلاً ذکر شد: به‌روزرسانی درجا، استفادهٔ مجدد از فضا و غیره.

۲.۳ آرایه‌های مرتب

با حذف جدول‌های درهم‌سازی، با ساده‌ترین ساختار دادهٔ مرتب‌ساز شروع می‌کنیم: آرایهٔ مرتب. می‌توانید در آن با جست‌وجوی دودویی در O(log N) جست‌وجو کنید. برای دادهٔ طول‌متغیر مثل رشته‌ها (KV)، از آرایه‌ای از اشاره‌گرها (آفست‌ها) برای جست‌وجوی دودویی استفاده کنید.

به‌روزرسانی یک آرایهٔ مرتب O(N) است، چه درجا چه نه. پس کاربردی نیست، اما می‌توان آن را به ساختارهای دادهٔ به‌روزشدنی دیگر تعمیم داد.

یک راه کاهش هزینهٔ به‌روزرسانی، تقسیم آرایه به چند آرایهٔ غیرهمپوشان (آرایه‌های مرتب تودرتو) است. این به B+tree (درخت n-تایی چندسطحی) می‌انجامد، با چالش اضافی نگه‌داشتن این آرایه‌های کوچک (گره‌های درخت).

شکل دیگری از «آرایهٔ به‌روزشدنی» درخت ادغامی ساختار-لاگ (LSM-tree) است. به‌روزرسانی‌ها ابتدا در یک آرایهٔ کوچک‌تر (یا ساختار دادهٔ مرتب‌ساز دیگر) بافر می‌شوند و وقتی خیلی بزرگ شد در آرایهٔ اصلی ادغام می‌شوند. هزینهٔ به‌روزرسانی با انتشار آرایه‌های کوچک‌تر به آرایه‌های بزرگ‌تر مستهلک می‌شود.

۲.۴ درخت B

درخت B یک درخت n-تایی متوازن است، قابل مقایسه با درخت‌های دودویی متوازن. هر گره تعداد متغیری کلید (و شاخه) تا n ذخیره می‌کند و n > ۲ است.

کاهش دسترسی تصادفی با درخت‌های کوتاه‌تر

یک دیسک فقط می‌تواند تعداد محدودی ورودی/خروجی در ثانیه (IOPS) انجام دهد که عامل محدودکنندهٔ جست‌وجوهای درختی است. هر سطح درخت یک خواندن دیسک در جست‌وجو است و درخت‌های n-تایی برای همان تعداد کلید کوتاه‌تر از درخت‌های دودویی‌اند (lognN در برابر log2N)؛ پس درخت‌های n-تایی خواندن دیسک کمتری برای هر جست‌وجو دارند.

پس به نظر می‌رسد n بزرگ مزیت دارد. اما مبادله‌هایی هست:

  • گره‌های بزرگ‌تر درخت به‌روزرسانی‌شان کندتر است.
  • تأخیر خواندن برای گره‌های بزرگ‌تر افزایش می‌یابد.

در عمل اندازهٔ گره فقط چند صفحهٔ سیستمعامل انتخاب می‌شود.

ورودی/خروجی بر حسب صفحه

هرچند فایل‌ها بایت‌آدرس‌پذیرند، واحد پایهٔ ورودی/خروجی دیسک بایت نیست، بلکه سکتور است؛ که بلوک‌های پیوستهٔ ۵۱۲ بایتی در HDDهای قدیمی‌اند. اما این دغدغهٔ برنامه‌ها نیست چون ورودی/خروجی‌های معمول فایل مستقیم با دیسک تعامل ندارند. سیستمعامل خواندن/نوشتن دیسک را در کش صفحه (page cache) بافر می‌کند که از بلوک‌های حافظهٔ ۴K بایتی به نام صفحه تشکیل شده است.

به هر حال، یک واحد حداقلی ورودی/خروجی وجود دارد. پایگاه‌های داده هم می‌توانند واحد ورودی/خروجی خودشان را (که آن هم صفحه نامیده می‌شود) تعریف کنند که می‌تواند بزرگ‌تر از صفحهٔ سیستمعامل باشد.

واحد حداقلی ورودی/خروجی دلالت بر این دارد که گره‌های درخت باید در مضرب واحد تخصیص یابند؛ یک واحد نیمه‌استفاده نیمه‌هدررفتهٔ ورودی/خروجی است. دلیل دیگری علیه n کوچک!

نوع B+tree

در زمینهٔ پایگاه داده، درخت B به معنای نوعی از درخت B به نام B+tree است. در B+tree گره‌های داخلی مقدار ذخیره نمی‌کنند؛ مقادیر فقط در گره‌های برگ وجود دارند. این به درخت کوتاه‌تر می‌انجامد چون گره‌های داخلی فضای بیشتری برای شاخه‌ها دارند.

B+tree به‌عنوان ساختار دادهٔ درون‌حافظه هم منطقی است چون واحد حداقلی ورودی/خروجی بین RAM و کش CPU برابر ۶۴ بایت (خط کش) است. مزیت عملکردی به بزرگی دیسک نیست چون در ۶۴ بایت چیز زیادی جا نمی‌شود.

سربار فضای ساختار داده

دلیل دیگر غیرعملی بودن درخت‌های دودویی تعداد اشاره‌گرهاست؛ هر کلید حداقل ۱ اشاره‌گر ورودی از گرهٔ والد دارد، در حالی که در B+tree چند کلید در یک گرهٔ برگ ۱ اشاره‌گر ورودی را به اشتراک می‌گذارند.

کلیدهای یک گرهٔ برگ را هم می‌توان در قالبی فشرده بسته‌بندی کرد یا فشرده کرد تا فضا بیشتر کاهش یابد.

۲.۵ ذخیره‌سازی ساختار-لاگ (Log-structured Storage)

به‌روزرسانی با ادغام: مستهلک‌کردن هزینه

معمول‌ترین نمونهٔ ذخیره‌سازی ساختار-لاگ، درخت ادغامی ساختار-لاگ (LSM-tree) است. ایدهٔ اصلی آن نه لاگ است نه درخت؛ «ادغام» است!

با ۲ فایل شروع می‌کنیم: یک فایل کوچک که به‌روزرسانی‌های اخیر را نگه می‌دارد و یک فایل بزرگ که بقیهٔ داده را نگه می‌دارد. به‌روزرسانی‌ها اول به فایل کوچک می‌روند، اما نمی‌تواند برای همیشه رشد کند؛ وقتی به آستانه رسید در فایل بزرگ ادغام می‌شود.

textwrites => | new updates | => | accumulated data |
               file 1               file 2

ادغام ۲ فایل مرتب به یک فایل جدیدتر و بزرگ‌تر می‌انجامد که جایگزین فایل بزرگ قدیمی می‌شود و فایل کوچک را کوچک می‌کند.

ادغام O(N) است اما می‌تواند هم‌زمان با خواننده‌ها و نویسنده‌ها انجام شود.

کاهش تقویت نوشتن (write amplification) با چند سطح

بافر کردن به‌روزرسانی‌ها بهتر از بازنویسی کل مجموعهٔ داده در هر بار است. اگر این طرح را به چند سطح تعمیم دهیم چه؟

text                 |level 1|
                    ||
                    \/
           |------level 2------|
                    ||
                    \/
|-----------------level 3-----------------|

در طرح ۲ سطحی، فایل بزرگ هر بار که فایل کوچک به آستانه می‌رسد بازنویسی می‌شود؛ نوشتن دیسک اضافی را تقویت نوشتن می‌نامند و با بزرگ‌تر شدن فایل بزرگ بدتر می‌شود. اگر سطح بیشتری استفاده کنیم، می‌توانیم سطح ۲ را با ادغام در سطح ۳ کوچک نگه داریم؛ مشابه اینکه سطح ۱ را کوچک نگه می‌داشتیم.

به‌طور شهودی سطوح به‌صورت نمایی رشد می‌کنند و رشد توانی دو (ادغام سطوح با اندازهٔ مشابه) کمترین تقویت نوشتن را دارد. اما بین تقویت نوشتن و تعداد سطوح (عملکرد پرس‌وجو) مبادله وجود دارد.

ایندکس‌های LSM-tree

هر سطح حاوی ساختارهای دادهٔ ایندکس‌گذاری است که می‌تواند صرفاً یک آرایهٔ مرتب باشد، چون سطوح (به‌جز سطح ۱) هرگز به‌روزرسانی نمی‌شوند. اما جست‌وجوی دودویی از نظر دسترسی تصادفی بهتر از درخت دودویی نیست؛ پس انتخاب معقول استفاده از درخت B داخل یک سطح است؛ این همان بخش «درخت» LSM-tree است. به هر حال، ساختارهای داده به دلیل نبودِ به‌روزرسانی بسیار ساده‌ترند.

برای درک بهتر ایدهٔ «ادغام» می‌توانید آن را روی جدول‌های درهم‌سازی اعمال کنید؛ معروف به جدول‌های درهم‌سازی ساختار-لاگ.

پرس‌وجوهای LSM-tree

کلیدها می‌توانند در هر سطحی باشند؛ پس برای پرس‌وجوی یک LSM-tree، نتایج هر سطح ترکیب می‌شوند (ادغام n-طرفه برای پرس‌وجوهای بازه‌ای).

برای پرس‌وجوهای نقطه‌ای می‌توان از فیلترهای بلوم به‌عنوان بهینه‌سازی برای کاهش تعداد سطوح جست‌وجوشده استفاده کرد.

چون سطوح هرگز به‌روزرسانی نمی‌شوند، ممکن است نسخه‌های قدیمی کلیدها در سطوح قدیمی‌تر وجود داشته باشند و کلیدهای حذف‌شده در سطوح جدیدتر با یک پرچم خاص علامت‌گذاری شوند (به نام tombstone). پس سطوح جدیدتر در پرس‌وجوها اولویت دارند.

فرایند ادغام به‌طور طبیعی فضا را از کلیدهای قدیمی یا حذف‌شده بازپس می‌گیرد؛ به همین دلیل به آن فشرده‌سازی (compaction) هم می‌گویند.

LSM-tree دنیای واقعی: SSTable، MemTable و لاگ

این‌ها اصطلاحاتی دربارهٔ جزئیات پیاده‌سازی LSM-tree هستند. برای ساختن یکی از اصول، نیازی به دانستن آن‌ها نیست، اما چند مشکل واقعی را حل می‌کنند.

سطوح به‌جای یک فایل بزرگ به چند فایل غیرهمپوشان به نام SSTable تقسیم می‌شوند تا ادغام به‌صورت تدریجی انجام شود. این نیاز فضای آزاد هنگام ادغام سطوح بزرگ را کاهش می‌دهد و فرایند ادغام در طول زمان پخش می‌شود.

سطح ۱ مستقیماً به‌روزرسانی می‌شود؛ یک لاگ انتخاب قابل‌اجرا می‌شود چون سطح ۱ از نظر اندازه محدود است. این بخش «لاگ» LSM-tree است؛ مثالی از ترکیب یک لاگ با سایر ساختارهای دادهٔ ایندکس‌گذاری.

اما حتی اگر لاگ کوچک باشد، یک ساختار دادهٔ ایندکس‌گذاری مناسب هنوز لازم است. دادهٔ لاگ در یک ایندکس درون‌حافظه به نام MemTable تکرار می‌شود که می‌تواند B-tree، skiplist یا هر چیز دیگری باشد. مقدار کمی دادهٔ درون‌حافظهٔ محدود است و مزیت اضافهٔ شتاب‌دادن به سناریوی «خواندن به‌روزرسانی‌های اخیر» را دارد.

۲.۶ خلاصهٔ ساختارهای دادهٔ ایندکس‌گذاری

۲ گزینه وجود دارد: B+tree و LSM-tree.

LSM-tree بسیاری از چالش‌های فصل قبل را حل می‌کند، مثل به‌روزرسانی ساختارهای دادهٔ مبتنی بر دیسک و استفادهٔ مجدد از فضا. در حالی که این چالش‌ها برای B+tree باقی می‌مانند؛ که بعداً بررسی می‌شوند.

فصل ۳: درخت B و بازیابی از خرابی

فصل اصلی: B-Tree & Crash Recovery

۳.۱ درخت B به‌عنوان یک درخت n-تایی متوازن

درخت متوازن از نظر ارتفاع

بسیاری از درخت‌های دودویی کاربردی، مانند درخت AVL یا درخت قرمز-سیاه، درخت‌های متوازن از نظر ارتفاع نامیده می‌شوند؛ یعنی ارتفاع درخت (از ریشه تا برگ‌ها) به O(log N) محدود است، پس جست‌وجو O(log N) است.

درخت B هم متوازن از نظر ارتفاع است؛ ارتفاع برای همهٔ گره‌های برگ یکسان است.

تعمیم درخت‌های دودویی

درخت‌های n-تایی را می‌توان از درخت‌های دودویی تعمیم داد (و برعکس). یک مثال درخت 2-3-4 است؛ که درخت B با گره‌هایی است که می‌توانند ۲، ۳ یا ۴ فرزند داشته باشند. درخت 2-3-4 معادل درخت قرمز-سیاه است. اما وارد جزئیات نمی‌شویم چون برای درک درخت B لازم نیستند.

تجسم یک B+tree دوسطحی از دنبالهٔ مرتب [1, 2, 3, 4, 6, 9, 11, 12]:

text     [1,   4,   9]
     /     |     \
    v      v      v
[1, 2, 3] [4, 6] [9, 11, 12]

در B+tree فقط گره‌های برگ مقدار دارند؛ کلیدها در گره‌های داخلی تکرار می‌شوند تا محدودهٔ کلیدی زیردرخت را نشان دهند. در این مثال، گرهٔ [1, 4, 9] نشان می‌دهد ۳ زیردرختش در بازه‌های [1, 4)، [4, 9) و [9, +∞) هستند. اما فقط ۲ کلید برای ۳ بازه لازم است؛ پس اولین کلید (1) را می‌توان حذف کرد و ۳ بازه (−∞, 4)، [4, 9) و (9, +∞) می‌شوند.

۳.۲ درخت B به‌عنوان آرایه‌های تودرتو

آرایه‌های تودرتوی دوسطحی

بدون دانستن جزئیات درخت قرمز-سیاه یا درخت 2-3-4، درخت B را می‌توان از آرایه‌های مرتب فهمید.

مشکل آرایه‌های مرتب به‌روزرسانی O(N) است. اگر آرایه را به m آرایهٔ کوچک‌تر غیرهمپوشان تقسیم کنیم، به‌روزرسانی O(N/m) می‌شود. اما باید بفهمیم کدام آرایهٔ کوچک را اول به‌روزرسانی/پرس‌وجو کنیم. پس به آرایهٔ مرتب دیگری از ارجاع به آرایه‌های کوچک‌تر نیاز داریم؛ که همان گره‌های داخلی در B+tree هستند.

text[[1,2,3], [4,6], [9,11,12]]

هزینهٔ جست‌وجو با ۲ جست‌وجوی دودویی همچنان O(log N) است. اگر m را √N انتخاب کنیم، به‌روزرسانی O(√N) می‌شود؛ که به همان خوبیِ بهترین حالت آرایه‌های مرتب دوسطحی است.

چند سطح آرایهٔ تودرتو

O(√N) برای پایگاه داده غیرقابل‌قبول است، اما اگر با شکافتن بیشتر آرایه‌ها سطح بیشتری اضافه کنیم، هزینه بیشتر کاهش می‌یابد.

فرض کنیم به شکافتن سطوح ادامه می‌دهیم تا همهٔ آرایه‌ها بزرگ‌تر از یک ثابت s نباشند؛ با log(N/s) سطح تمام می‌کنیم و هزینهٔ جست‌وجو O(log(N/s) + log(s)) است که همچنان O(log N) است.

برای درج و حذف، بعد از یافتن گرهٔ برگ، به‌روزرسانی گرهٔ برگ در بیشتر مواقع ثابت O(s) است. مشکل باقی‌مانده حفظ ناورداهای (invariants) بزرگ‌ترنبودن گره‌ها از s و خالی‌نبودن آن‌هاست.

۳.۳ نگه‌داشتن یک B+tree

۳ ناوردا که هنگام به‌روزرسانی یک B+tree باید حفظ شوند:

  1. ارتفاع یکسان برای همهٔ گره‌های برگ.
  2. اندازهٔ گره به یک ثابت محدود است.
  3. گره خالی نیست.

رشد درخت B با شکافتن گره‌ها

ناوردای دوم با درج در یک گرهٔ برگ نقض می‌شود که با شکافتن گره به گره‌های کوچک‌تر ترمیم می‌شود.

text    parent              parent
   /  |  \     =>      /  | |  \
L1   L2   L6         L1  L3 L4  L6
     *                   *  *

بعد از شکافتن یک گرهٔ برگ، گرهٔ والدش یک شاخهٔ جدید می‌گیرد که ممکن است از حد اندازه تجاوز کند؛ پس ممکن است آن هم شکافته شود. شکافتن گره می‌تواند تا گرهٔ ریشه انتشار یابد و ارتفاع را ۱ واحد افزایش دهد.

text                        new_root
                          / \
    root                 N1 N2
   /  |  \     =>      /  | |  \
L1   L2   L6         L1  L3 L4  L6

این ناوردای اول را حفظ می‌کند، چون همهٔ برگ‌ها هم‌زمان ۱ واحد ارتفاع می‌گیرند.

کوچک‌شدن درخت B با ادغام گره‌ها

حذف ممکن است به گره‌های خالی بینجامد. ناوردای سوم با ادغام گره‌های خالی در یک گرهٔ خواهر/برادر ترمیم می‌شود. ادغام عکس شکافتن است. می‌تواند تا گرهٔ ریشه انتشار یابد، پس ارتفاع درخت می‌تواند کاهش یابد.

هنگام کدنویسی درخت B، ادغام را می‌توان زودتر برای کاهش فضای هدررفته انجام داد: می‌توانید یک گرهٔ غیرخالی را وقتی اندازه‌اش به یک کران پایین می‌رسد ادغام کنید.

۳.۴ درخت B روی دیسک

با این اصول می‌توانید درخت B درون‌حافظه را کدنویسی کنید. اما درخت B روی دیسک ملاحظات اضافه‌ای لازم دارد.

تخصیص مبتنی بر بلوک

یک جزئیات گم‌شده، محدودکردن اندازهٔ گره است. برای B+tree درون‌حافظه می‌توانید حداکثر تعداد کلیدهای یک گره را محدود کنید؛ اندازهٔ گره بر حسب بایت دغدغه نیست چون می‌توانید هر تعداد بایت که نیاز است تخصیص دهید.

برای ساختارهای دادهٔ مبتنی بر دیسک، نه malloc/free هست نه garbage collector؛ تخصیص و استفادهٔ مجدد فضا کاملاً با خود ماست.

اگر همهٔ تخصیص‌ها هم‌اندازه باشند، استفادهٔ مجدد فضا را می‌توان با یک لیست آزاد انجام داد؛ که بعداً پیاده می‌کنیم. فعلاً همهٔ گره‌های درخت B هم‌اندازه‌اند.

درخت B کپی-هنگام-نوشتن برای به‌روزرسانی امن

۳ روش مقاوم در برابر خرابی برای به‌روزرسانی دادهٔ دیسک دیدیم: تغییر نام فایل‌ها، لاگ‌ها، LSM-treeها. درس مشترک این است: در هنگام به‌روزرسانی هیچ دادهٔ قدیمی را نابود نکنید. این ایده را می‌توان روی درخت‌ها اعمال کرد: از گره یک کپی بسازید و کپی را تغییر دهید.

درج یا حذف از یک گرهٔ برگ شروع می‌شود؛ بعد از ساخت کپی با تغییر، گرهٔ والد باید به‌روزرسانی شود تا به گرهٔ جدید اشاره کند؛ که روی کپی خودش انجام می‌شود. کپی‌کردن تا گرهٔ ریشه انتشار می‌یابد و به یک ریشهٔ جدید می‌انجامد.

  • درخت اصلی دست‌نخورده می‌ماند و از ریشهٔ قدیمی قابل‌دسترس است.
  • ریشهٔ جدید، همراه با کپی‌های به‌روزشده تا برگ، همهٔ گره‌های دیگر را با درخت اصلی به اشتراک می‌گذارد.
text    d           d         D*
   / \         / \       / \
  b   e  ==>  b   e  +  B*  e
 / \         / \       / \
a   c       a   c     a   C*
            original  updated

این تجسم به‌روزرسانی برگِ c است. گره‌های کپی‌شده با حروف بزرگ (D, B, C) و زیردرخت‌های به‌اشتراک‌گذاشته‌شده با حروف کوچک (a, e) نشان داده شده‌اند.

این ساختار دادهٔ کپی-هنگام-نوشتن نامیده می‌شود. همچنین به‌صورت تغییرناپذیر (immutable)، فقط-الحاقی (به معنای واقعی نه)، یا مانا (persistent؛ ربطی به ماندگاری ندارد) توصیف می‌شود. آگاه باشید که اصطلاحات پایگاه داده معانی یکنواختی ندارند.

۲ مشکل دیگر برای درخت B کپی-هنگام-نوشتن باقی می‌ماند:

  1. چگونه ریشهٔ درخت را پیدا کنیم، چون بعد از هر به‌روزرسانی تغییر می‌کند؟ مسئلهٔ ایمنی خرابی به یک به‌روزرسانی اشاره‌گر واحد کاهش می‌یابد؛ که بعداً حل می‌کنیم.
  2. چگونه گره‌های نسخه‌های قدیمی را استفادهٔ مجدد کنیم؟ کار یک لیست آزاد است.

مزایای درخت B کپی-هنگام-نوشتن

یک مزیت نگه‌داشتن نسخه‌های قدیمی این است که ایزولهٔ اسنپ‌شات (snapshot isolation) را رایگان می‌گیریم. یک تراکنش با یک نسخه از درخت شروع می‌شود و تغییرات نسخه‌های دیگر را نمی‌بیند.

و بازیابی از خرابی آسان است؛ فقط از آخرین نسخهٔ قدیمی استفاده کنید.

مزیت دیگر این است که با مدل همروندی چند-خواننده-تک-نویسنده سازگار است و خواننده‌ها نویسنده را مسدود نمی‌کنند. این‌ها را بعداً بررسی می‌کنیم.

جایگزین: به‌روزرسانی درجا با double-write

هرچند بازیابی از خرابی در ساختارهای دادهٔ کپی-هنگام-نوشتن واضح است، آن‌ها می‌توانند به دلیل تقویت نوشتن بالا نامطلوب باشند. هر به‌روزرسانی کل مسیر را کپی می‌کند (O(log N))، در حالی که بیشتر به‌روزرسانی‌های درجا فقط ۱ گرهٔ برگ را لمس می‌کنند.

به‌روزرسانی درجا با بازیابی از خرابی بدون کپی-هنگام-نوشتن ممکن است:

  1. کپی همهٔ گره‌های به‌روزشده را جایی ذخیره کنید. مثل کپی-هنگام-نوشتن است، اما بدون کپی‌کردن گرهٔ والد.
  2. fsync کپی‌های ذخیره‌شده. (در این نقطه می‌توان به کلاینت پاسخ داد.)
  3. واقعاً ساختار داده را درجا به‌روزرسانی کنید.
  4. fsync به‌روزرسانی‌ها.

بعد از خرابی، ساختار داده ممکن است نیمه‌به‌روزرسانی‌شده باشد؛ اما واقعاً نمی‌دانیم. کاری که می‌کنیم این است که کپی‌های ذخیره‌شده را کورکورانه اعمال می‌کنیم تا ساختار داده به وضعیت به‌روزرسانی‌شده برسد، فارغ از وضعیت فعلی‌اش.

text| a=1 b=2 |
    ||  1. Save a copy of the entire updated nodes.
    \/
| a=1 b=2 |   +   | a=2 b=4 |
   data           updated copy
    ||  2. fsync the saved copies.
    \/
| a=1 b=2 |   +   | a=2 b=4 |
   data           updated copy (fsync'ed)
    ||  3. Update the data structure in-place. But we crashed here!
    \/
| ??????? |   +   | a=2 b=4 |
   data (bad)     updated copy (good)
    ||  Recovery: apply the saved copy.
    \/
| a=2 b=4 |   +   | a=2 b=4 |
   data (new)     useless now

کپی‌های به‌روزرسانی‌شدهٔ ذخیره‌شده در اصطلاح MySQL double-write نامیده می‌شوند. اما اگر خود double-write خراب شود چه؟ مثل لاگ‌ها با چک‌سام رسیدگی می‌شود.

  • اگر چک‌سام یک double-write بد تشخیص دهد، آن را نادیده بگیرید. این قبل از اولین fsync است؛ پس دادهٔ اصلی در وضعیت خوب و قدیمی است.
  • اگر double-write خوب است، اعمال آن همیشه دادهٔ اصلی خوب می‌دهد.

برخی پایگاه‌های داده در واقع double-writeها را در لاگ‌ها ذخیره می‌کنند؛ که physical logging نامیده می‌شود. دو نوع لاگ‌نگاری هست: منطقی (logical) و فیزیکی (physical). لاگ‌نگاری منطقی عملیات‌های سطح بالا مثل درج یک کلید را توصیف می‌کند؛ چنین عملیاتی فقط وقتی پایگاه داده در وضعیت خوب است قابل اعمال‌اند؛ پس فقط لاگ‌نگاری فیزیکی (به‌روزرسانی‌های صفحهٔ دیسک سطح پایین) برای بازیابی مفید است.

اصل بازیابی از خرابی

double-write را با کپی-هنگام-نوشتن مقایسه کنیم:

  • double-write به‌روزرسانی‌ها را idempotent می‌کند؛ پایگاه داده می‌تواند با اعمال کپی‌های ذخیره‌شده به‌روزرسانی را دوباره امتحان کند چون آن‌ها گره‌های کامل‌اند.
  • کپی-هنگام-نوشتن به‌صورت اتمیک همه‌چیز را به نسخهٔ جدید سوئیچ می‌کند.

آن‌ها بر اساس ایده‌های متفاوتی‌اند:

  • double-write اطلاعات کافی برای تولید نسخهٔ جدید را تضمین می‌کند.
  • کپی-هنگام-نوشتن حفظ نسخهٔ قدیمی را تضمین می‌کند.

اگر با double-write به‌جای گره‌های به‌روزشده، گره‌های اصلی را ذخیره کنیم چه؟ این سومین راه بازیابی از خرابی است و مثل کپی-هنگام-نوشتن به نسخهٔ قدیمی برمی‌گردد. می‌توانیم ۳ راه را در ۱ ایده ترکیب کنیم: در هر نقطه، اطلاعات کافی برای وضعیت قدیمی یا وضعیت جدید وجود دارد.

همچنین مقداری کپی‌کردن همیشه لازم است؛ پس گره‌های درختی بزرگ‌تر به‌روزرسانی‌شان کندتر است.

ما از کپی-هنگام-نوشتن استفاده می‌کنیم چون ساده‌تر است، اما می‌توانید در اینجا منحرف شوید.

۴.۱ گرهٔ B+tree

داخل یک گره چیست؟

یک گرهٔ B+tree فهرستی از کلیدهای مرتب‌شده با اشاره‌گرهای فرزند یا مقدار است:

go// pseudo code
type Node struct {
    keys [][]byte
    // one of the following
    vals [][]byte   // for leaf nodes only
    kids []*Node    // for internal nodes only
}

در B+tree فقط گره‌های برگ مقدار ذخیره می‌کنند و فقط گره‌های داخلی فرزند دارند. اما برای ساده نگه‌داشتن کار، از همان قالب برای هر دو نوع گره استفاده می‌کنیم.

جای دادن یک گره در یک صفحه

یک گره وقتی خیلی بزرگ می‌شود به گره‌های کوچک‌تر شکافته می‌شود. اما «خیلی بزرگ» را چگونه تعریف کنیم؟ برای B+tree درون‌حافظه می‌توانیم تعداد کلیدهای یک گره را محدود کنیم. اما برای B+tree مبتنی بر دیسک، گرهٔ سریال‌شده باید در یک واحد با اندازهٔ ثابت به نام صفحه (page) جا بگیرد.

gofunc Encode(node *Node) []byte
func Decode(page []byte) (*Node, error)

صفحه‌های با اندازهٔ ثابت تخصیص و استفادهٔ مجدد فضا را آسان‌تر می‌کنند، چون همهٔ گره‌های حذف‌شده قابل تعویض هستند؛ که می‌توان آن‌ها را با یک لیست آزاد مدیریت کرد به‌جای اینکه malloc() را دوباره اختراع کنیم.

اما اندازهٔ سریال‌شده را از کجا بدانیم؟ فرض کنیم گره با JSON سریال می‌شود؛ اندازه فقط بعد از سریال‌شدن مشخص می‌شود، یعنی گره در هر به‌روزرسانی فقط برای دیدن اندازه‌اش سریال می‌شود.

برای اینکه اندازهٔ گره به‌سادگی قابل پیش‌بینی باشد، می‌توانیم قالب سریال‌سازی گرهٔ ساده‌تری خودمان طراحی کنیم؛ مثل هر پیاده‌سازی B+tree دیگری.

طراحی قالب یک گره

قالب گرهٔ ما این است. ردیف دوم اندازهٔ میدان رمزگذاری‌شده بر حسب بایت است:

text| type | nkeys |  pointers  |  offsets   | key-values | unused |
|  2B  |   2B  | nkeys × 8B | nkeys × 2B |     ...    |        |

قالب با یک هدر ۴ بایتی شروع می‌شود:

  • type نوع گره است (برگ یا داخلی).
  • nkeys تعداد کلیدها (و تعداد اشاره‌گرهای فرزند) است.
goconst (
    BNODE_NODE = 1 // internal nodes with pointers
    BNODE_LEAF = 2 // leaf nodes with values
)

سپس یک آرایه از اشاره‌گرهای فرزند و زوج‌های کلید-مقدار (KV) می‌آید. قالب برای گره‌های برگ و داخلی یکسان است؛ پس آرایهٔ اشاره‌گر برای گره‌های برگ به‌سادگی استفاده نشده است.

هر زوج KV با اندازهٔ خودش پیشوندگذاری می‌شود. برای گره‌های داخلی، اندازهٔ مقدار ۰ است.

text| key_size | val_size | key | val |
|    2B    |    2B    | ... | ... |

زوج‌های KV رمزگذاری‌شده به هم چسبانده می‌شوند. برای یافتن زوج KV ام، باید همهٔ زوج‌های قبلی خوانده شوند. این کار با ذخیره‌کردن آفست (offset) هر زوج KV اجتناب می‌شود.

مثلاً یک گرهٔ برگ {"k1":"hi", "k3":"hello"} این‌گونه رمزگذاری می‌شود:

text| type | nkeys | pointers | offsets |            key-values           | unused |
|   2  |   2   | nil nil  |  8 19   | 2 2 "k1" "hi"  2 5 "k3" "hello" |        |
|  2B  |  2B   |   2×8B   |  2×2B   | 4B + 2B + 2B + 4B + 2B + 5B     |        |

آفست اولین زوج KV همیشه ۰ است، پس ذخیره نمی‌شود. برای یافتن موقعیت زوج nام از offsets[n-1] استفاده کنید. در این مثال، ۸ آفست زوج دوم و ۱۹ آفستِ بعد از پایان زوج دوم است.

یک بازه با کلیدها به زیربازه‌ها تقسیم می‌شود

کلیدهای یک گرهٔ داخلی محدودهٔ هر فرزند را نشان می‌دهند. محدودهٔ گرهٔ ریشه [−∞, +∞) است. محدوده به‌صورت بازگشتی از ریشه تا برگ‌ها تقسیم می‌شود. برای تقسیم یک محدوده به n زیرمحدوده به n − ۱ کلید نیاز داریم. مثلاً گرهٔ ["p", "q"] محدودهٔ خودش [a, z) را به ۳ زیرمحدوده تقسیم می‌کند: [a, p)، [p, q) و [q, z).

اما قالب ما در عوض از n کلید استفاده می‌کند. هر کلید شروع زیرمحدوده را نشان می‌دهد. مثلاً گرهٔ ["p", "q"] محدودهٔ خودش [p, z) را به ۲ زیرمحدوده تقسیم می‌کند: [p, q) و [q, z).

این تجسم را آسان‌تر و برخی موارد لبه را حذف می‌کند؛ اما اولین کلید یک گرهٔ داخلی اضافه است، چون شروع محدوده از گرهٔ والد به ارث می‌رسد.

محدودیت اندازهٔ KV

اندازهٔ گره را 4K می‌گذاریم که اندازهٔ معمول صفحهٔ سیستمعامل است. اما کلیدها و مقادیر می‌توانند دلخواه بزرگ باشند و از یک گرهٔ واحد عبور کنند. باید راهی برای ذخیرهٔ KVهای بزرگ خارج از گره‌ها یا متغیر کردن اندازهٔ گره وجود داشته باشد. این قابل‌حل است، اما بنیادی نیست. پس فقط اندازهٔ KV را طوری محدود می‌کنیم که همیشه در یک گره جا بگیرند.

goconst BTREE_PAGE_SIZE = 4096
const BTREE_MAX_KEY_SIZE = 1000
const BTREE_MAX_VAL_SIZE = 3000

func init() {
    node1max := 4 + 1*8 + 1*2 + 4 + BTREE_MAX_KEY_SIZE + BTREE_MAX_VAL_SIZE
    assert(node1max <= BTREE_PAGE_SIZE) // maximum KV
}

محدودیت اندازهٔ کلید همچنین تضمین می‌کند که یک گرهٔ داخلی حداقل می‌تواند ۲ کلید را میزبان باشد.

شمارهٔ صفحه

یک اشاره‌گر درون‌حافظه، آدرس صحیحِ محل یک بایت است. برای دادهٔ روی دیسک، یک اشاره‌گر می‌تواند یک آفست فایل باشد. در هر صورت فقط یک عدد صحیح است.

در B+tree مبتنی بر دیسک، گره‌ها صفحه‌های با اندازهٔ ثابت هستند و کل فایل آرایه‌ای از صفحه‌های با اندازهٔ ثابت است. پس یک اشاره‌گر گره نیازی به آدرس‌دهی بایت‌ها ندارد، بلکه ایندکس صفحه‌ها را می‌دهد؛ که به آن شمارهٔ صفحه (page number) می‌گویند؛ یعنی آفست فایل تقسیم بر اندازهٔ صفحه.

خلاصهٔ قالب گرهٔ B+tree ما

  • پایگاه داده را به‌صورت آرایه‌ای از صفحه‌های با اندازهٔ ثابت پیاده‌سازی می‌کنیم.
  • هر صفحه شامل یک گرهٔ B+tree سریال‌شده است.
  • یک گرهٔ برگ B+tree فهرستی از زوج‌های KV مرتب است.
  • یک گرهٔ داخلی B+tree فهرستی از زوج‌های مرتب کلید-اشاره‌گر است.

قالب گره فقط یک جزئیات پیاده‌سازی است. تا زمانی که گره‌ها اطلاعات لازم را داشته باشند B+tree کار می‌کند؛ لازم نیست دقیقاً از آنچه ما انجام می‌دهیم پیروی کنید.

۴.۲ رمزگشایی گره‌های B+tree

رمزگشایی گره در لحظه

قالب ساده است؛ می‌توانیم داده را مستقیماً از روی آن بخوانیم بدون اینکه آن را در یک نوع دادهٔ جداگانهٔ فقط-درون‌حافظه بی‌سریال کنیم. پس نوع دادهٔ گرهٔ ما یک آرایهٔ بایت است.

gotype BNode []byte // can be dumped to the disk

فقط به چند تابع کمکی برای استفاده از آن نیاز داریم؛ یعنی getter و setter.

go// getters
func (node BNode) btype() uint16 {
    return binary.LittleEndian.Uint16(node[0:2])
}
func (node BNode) nkeys() uint16 {
    return binary.LittleEndian.Uint16(node[2:4])
}

اعداد صحیح در قالب little-endian رمزگذاری می‌شوند که فقط یک بارگذاری یا ذخیرهٔ حافظه است. این تفاوت چندانی با استفاده از struct ندارد.

go// setter
func (node BNode) setHeader(btype uint16, nkeys uint16) {
    binary.LittleEndian.PutUint16(node[0:2], btype)
    binary.LittleEndian.PutUint16(node[2:4], nkeys)
}

به‌جز اینکه struct نمی‌تواند با طول متغیر باشد، در حالی که یک آرایهٔ بایت می‌تواند.

go// read and write the child pointers array
func (node BNode) getPtr(idx uint16) uint64 {
    assert(idx < node.nkeys())
    pos := 4 + 8*idx
    return binary.LittleEndian.Uint64(node[pos:])
}
func (node BNode) setPtr(idx uint16, val uint64) {
    assert(idx < node.nkeys())
    pos := 4 + 8*idx
    binary.LittleEndian.PutUint64(node[pos:], val)
}

خواندن زوج‌های KV

آفست شروع زوج nام از آرایهٔ آفست‌ها خوانده می‌شود.

go// read the `offsets` array
func (node BNode) getOffset(idx uint16) uint16 {
    if idx == 0 {
        return 0
    }
    pos := 4 + 8*node.nkeys() + 2*(idx-1)
    return binary.LittleEndian.Uint16(node[pos:])
}

آفست با دادهٔ قبل تنظیم می‌شود. پس node[node.kvPos(0):] جایی است که زوج‌های رمزگذاری‌شده شروع می‌شوند.

gofunc (node BNode) kvPos(idx uint16) uint16 {
    assert(idx <= node.nkeys())
    return 4 + 8*node.nkeys() + 2*node.nkeys() + node.getOffset(idx)
}

سپس دادهٔ KV بعد از رمزگشایی اندازه‌هایشان به‌صورت یک برش بایت (byte slice) برگردانده می‌شود.

text| key_size | val_size | key | val |
|    2B    |    2B    | ... | ... |
gofunc (node BNode) getKey(idx uint16) []byte {
    assert(idx < node.nkeys())
    pos := node.kvPos(idx)
    klen := binary.LittleEndian.Uint16(node[pos:])
    return node[pos+4:][:klen]
}
func (node BNode) getVal(idx uint16) []byte {
    assert(idx < node.nkeys())
    pos := node.kvPos(idx)
    klen := binary.LittleEndian.Uint16(node[pos+0:])
    vlen := binary.LittleEndian.Uint16(node[pos+2:])
    return node[pos+4+klen:][:vlen]
}

استفاده از یک گره فقط بارگذاری اعداد صحیح یا برگرداندن دادهٔ برش‌خورده است. یک برش یک ارجاع است؛ پس دادهٔ KV را می‌توان بدون کپی‌کردن منتقل کرد.

خلاصهٔ رمزگشایی گره‌های B+tree

  • btype()، nkeys(): خواندن هدر با اندازهٔ ثابت.
  • setHeader(type, nkeys): نوشتن هدر با اندازهٔ ثابت.
  • getPtr(n)، setPtr(n, ptr): خواندن و نوشتن آرایهٔ اشاره‌گر (برای گره‌های داخلی).
  • getOffset(n): خواندن آرایهٔ offsets برای یافتن کلید ام در O(1).
  • kvPos(n): برگرداندن موقعیت کلید ام با استفاده از getOffset().
  • getKey(n): گرفتن دادهٔ کلید ام به‌صورت یک برش.
  • getVal(n): گرفتن دادهٔ مقدار ام به‌صورت یک برش (برای گره‌های برگ).

۴.۳ ساخت گره‌های B+tree

ساخت یک گرهٔ B+tree

حالا که می‌توانیم داده را از یک گره بخوانیم، قدم بعدی گذاشتن داده در یک گره است. مثلاً یک گرهٔ برگ {"k1":"hi", "k3":"hello"} می‌سازیم:

gonode := BNode(make([]byte, BTREE_PAGE_SIZE))
node.setHeader(BNODE_LEAF, 2)
//             ^type       ^ number of keys
nodeAppendKV(node, 0, 0, []byte("k1"), []byte("hi"))
//                 ^ 1st KV
nodeAppendKV(node, 1, 0, []byte("k3"), []byte("hello"))
//                 ^ 2nd KV

شروع با یک صفحهٔ خالی؛ اولین کار تنظیم تعداد کلیدها با setHeader() است، چون آرایه‌های با طول متغیر به آن وابسته‌اند.

بعد، زوج‌های KV یا اشاره‌گرها را به گره اضافه کنید.

gofunc nodeAppendKV(new BNode, idx uint16, ptr uint64, key []byte, val []byte)
  • idx موقعیت آیتم (کلید، مقدار یا اشاره‌گر) است.
  • ptr اشاره‌گر فرزند ام است که برای گره‌های برگ استفاده نمی‌شود.
  • key و val زوج KV هستند. برای گره‌های داخلی از یک مقدار خالی استفاده کنید.

nodeAppendKV فرض می‌کند کلیدها به‌ترتیب اضافه می‌شوند. از مقدار قبلی آرایهٔ offsets استفاده می‌کند تا مشخص کند KV باید کجا قرار بگیرد.

gofunc nodeAppendKV(new BNode, idx uint16, ptr uint64, key []byte, val []byte) {
    // ptrs
    new.setPtr(idx, ptr)
    // KVs
    pos := new.kvPos(idx)   // uses the offset value of the previous key
    // 4-bytes KV sizes
    binary.LittleEndian.PutUint16(new[pos+0:], uint16(len(key)))
    binary.LittleEndian.PutUint16(new[pos+2:], uint16(len(val)))
    // KV data
    copy(new[pos+4:], key)
    copy(new[pos+4+uint16(len(key)):], val)
    // update the offset value for the next key
    new.setOffset(idx+1, new.getOffset(idx)+4+uint16((len(key)+len(val))))
}

گره‌های کپی-هنگام-نوشتن

کپی-هنگام-نوشتن یعنی بدون به‌روزرسانی درجا؛ به‌روزرسانی‌ها به‌جایش گره‌های جدید می‌سازند. مثال ۱، گرهٔ {"k1":"hi", "k2":"a", "k3":"hello"} با "k2":"b" به‌روز می‌شود:

gonew := BNode(make([]byte, BTREE_PAGE_SIZE))
new.setHeader(BNODE_LEAF, 3)
nodeAppendKV(new, 0, 0, old.getKey(0), old.getVal(0))
nodeAppendKV(new, 1, 0, []byte("k2"), []byte("b"))
nodeAppendKV(new, 2, 0, old.getKey(2), old.getVal(2))

مثال ۲، حذف "k2" از آن گره:

gonew := BNode(make([]byte, BTREE_PAGE_SIZE))
new.setHeader(BNODE_LEAF, 2)
nodeAppendKV(new, 0, 0, old.getKey(0), old.getVal(0))
nodeAppendKV(new, 1, 0, old.getKey(2), old.getVal(2))

مثال ۳، درج "a":"b" در آن گره:

gonew := BNode(make([]byte, 2*BTREE_PAGE_SIZE))   // larger
new.setHeader(BNODE_LEAF, 4)
nodeAppendKV(new, 0, 0, []byte("a"), []byte("b"))
nodeAppendKV(new, 1, 0, old.getKey(0), old.getVal(0))
nodeAppendKV(new, 2, 0, old.getKey(1), old.getVal(1))
nodeAppendKV(new, 3, 0, old.getKey(2), old.getVal(2))

بعد از درج، گره ممکن است از اندازهٔ صفحه تجاوز کند. به همین دلیل گرهٔ درون‌حافظه با اندازهٔ بزرگ‌تری تخصیص داده می‌شود تا بتواند قبل از شکافته‌شدن به‌طور موقت از اندازهٔ صفحه تجاوز کند.

محاسبهٔ اندازهٔ گره

دلیل ساخت یک قالب سریال‌سازی، پیش‌بینی آسان اندازهٔ سریال‌شده است؛ که برابر هدر با اندازهٔ ثابت + آرایه‌ها + زوج‌های KV رمزگذاری‌شده است.

اندازهٔ زوج‌های KV رمزگذاری‌شده برابر مجموع اندازهٔ دادهٔ هر KV به‌علاوهٔ طول‌های رمزگذاری‌شدهٔ ۴ بایتی است. اما یک میان‌بر وجود دارد: آرایهٔ offsets اندازهٔ کل زوج‌های KV رمزگذاری‌شده را به ما می‌گوید؛ پس نیازی به پیمایش آن‌ها نیست.

go// node size in bytes
func (node BNode) nbytes() uint16 {
    return node.kvPos(node.nkeys()) // uses the offset value of the last key
}

خلاصهٔ ساخت گره‌های B+tree

  • گره‌ها تغییرناپذیرند؛ فقط از گره‌های قدیمی گره‌های جدید می‌سازیم.
  • برای ساخت یک گرهٔ جدید:
    1. یک آرایهٔ بایت تخصیص دهید.
    2. تعداد کلیدها را با setHeader() تنظیم کنید.
    3. هر کلید را به‌ترتیب مرتب‌شده با nodeAppendKV() اضافه کنید.
  • nbytes() تعداد بایت‌های استفاده‌شده توسط گره را برمی‌گرداند.

۴.۴ درج یا به‌روزرسانی گرهٔ برگ

درج یا به‌روزرسانی در یک موقعیت

درج از یک گرهٔ برگ شروع می‌شود. برای درج یک کلید جدید در موقعیت idx:

gofunc leafInsert(
    new BNode, old BNode, idx uint16, key []byte, val []byte,
) {
    new.setHeader(BNODE_LEAF, old.nkeys()+1)
    nodeAppendRange(new, old, 0, 0, idx)    // copy the keys before `idx`
    nodeAppendKV(new, idx, 0, key, val)     // the new key
    nodeAppendRange(new, old, idx+1, idx, old.nkeys()-idx)  // keys from `idx`
}

nodeAppendRange() فقط یک حلقه برای کپی کلیدها، مقادیر و اشاره‌گرهاست:

go// copy multiple keys, values, and pointers into the position
func nodeAppendRange(
    new BNode, old BNode, dstNew uint16, srcOld uint16, n uint16,
) {
    for i := uint16(0); i < n; i++ {
        dst, src := dstNew+i, srcOld+i
        nodeAppendKV(new, dst,
            old.getPtr(src), old.getKey(src), old.getVal(src))
    }
}

اگر کلید از قبل وجود داشته باشد، باید به‌جایش مقدار را به‌روز کنیم:

gofunc leafUpdate(
    new BNode, old BNode, idx uint16, key []byte, val []byte,
) {
    new.setHeader(BNODE_LEAF, old.nkeys())
    nodeAppendRange(new, old, 0, 0, idx)
    nodeAppendKV(new, idx, 0, key, val)
    nodeAppendRange(new, old, idx+1, idx+1, old.nkeys()-(idx+1))
}

یافتن موقعیت درج

کلیدها مرتب‌اند؛ باید موقعیت به‌روزرسانی را طوری پیدا کنیم که ترتیب مرتب‌شدن حفظ شود.

go// find the last postion that is less than or equal to the key
func nodeLookupLE(node BNode, key []byte) uint16 {
    nkeys := node.nkeys()
    var i uint16
    for i = 0; i < nkeys; i++ {
        cmp := bytes.Compare(node.getKey(i), key)
        if cmp == 0 {
            return i
        }
        if cmp > 0 {
            return i - 1
        }
    }
    return i - 1
}

این می‌تواند به‌جای جست‌وجوی خطی، جست‌وجوی دودویی باشد؛ چون getKey(i) با آرایهٔ offsets در O(1) است.

درج یا به‌روزرسانی بعد از یک جست‌وجوی کلید

یک جست‌وجو را با یک به‌روزرسانی ترکیب کنیم:

if bytes.Equal(key, node.getKey(idx)) {
    leafUpdate(new, node, idx, key, val)   // found, update it
} else {
    leafInsert(new, node, idx+1, key, val) // not found. insert

اما اگر همهٔ موقعیت‌ها بزرگ‌تر از کلید باشند و idx برابر ‎-1 باشد چه؟ مطمئن می‌شویم این اتفاق نمی‌افتد. بعداً توضیح داده می‌شود.

۴.۵ شکافتن یک گره

شکافتن با متوازن‌کردن بایت‌ها

برای B+tree درون‌حافظه، یک گرهٔ بیش‌ازحد را می‌توان به ۲ گره تقسیم کرد که هر کدام نیمی از کلیدها را دارند. برای B+tree مبتنی بر دیسک، نیمی از کلیدها ممکن است به‌خاطر اندازه‌های نابرابر کلیدها در یک صفحه جا نگیرند. اما می‌توانیم از موقعیت نیمه به‌عنوان حدس اولیه استفاده کنیم و اگر نیمه خیلی بزرگ بود آن را به چپ یا راست حرکت دهیم.

go// Split an oversized node into 2 nodes. The 2nd node always fits.
func nodeSplit2(left BNode, right BNode, old BNode) {
    assert(old.nkeys() >= 2)
    // the initial guess
    nleft := old.nkeys() / 2
    // try to fit the left half
    left_bytes := func() uint16 {
        return 4 + 8*nleft + 2*nleft + old.getOffset(nleft)
    }
    for left_bytes() > BTREE_PAGE_SIZE {
        nleft--
    }
    assert(nleft >= 1)
    // try to fit the right half
    right_bytes := func() uint16 {
        return old.nbytes() - left_bytes() + 4
    }
    for right_bytes() > BTREE_PAGE_SIZE {
        nleft++
    }
    assert(nleft < old.nkeys())
    nright := old.nkeys() - nleft
    // new nodes
    left.setHeader(old.btype(), nleft)
    right.setHeader(old.btype(), nright)
    nodeAppendRange(left, old, 0, 0, nleft)
    nodeAppendRange(right, old, 0, nleft, nright)
    // NOTE: the left half may be still too big
    assert(right.nbytes() <= BTREE_PAGE_SIZE)
}

باز هم آرایهٔ offsets به پیش‌بینی اندازهٔ گره کمک می‌کند.

شکافتن چندباره

بعد از شکافتن، نیمهٔ چپ ممکن است همچنان خیلی بزرگ باشد؛ چون هنگام جا دادن نیمهٔ راست، اندازهٔ نیمهٔ چپ رشد می‌کند. اگر یک کلید بزرگ وسط باشد این اتفاق می‌افتد و شکافت دیگری لازم است.

text[foo...|BIG|bar...] -> [foo...|BIG] + [bar...] -> [foo...] + [BIG] + [bar...]
                         too big

محدودیت‌های اندازهٔ ما اجازه می‌دهد یک KV تنها تقریباً کل صفحه را بگیرد؛ که مورد «کلید بزرگ وسط» را ممکن می‌کند.

goconst BTREE_PAGE_SIZE = 4096
const BTREE_MAX_KEY_SIZE = 1000
const BTREE_MAX_VAL_SIZE = 3000

پس نتیجهٔ یک شکافتن یا ۲ گره است یا ۳ گره:

go// split a node if it's too big. the results are 1~3 nodes.
func nodeSplit3(old BNode) (uint16, [3]BNode) {
    if old.nbytes() <= BTREE_PAGE_SIZE {
        old = old[:BTREE_PAGE_SIZE]
        return 1, [3]BNode{old} // not split
    }
    left := BNode(make([]byte, 2*BTREE_PAGE_SIZE)) // might be split later
    right := BNode(make([]byte, BTREE_PAGE_SIZE))
    nodeSplit2(left, right, old)
    if left.nbytes() <= BTREE_PAGE_SIZE {
        left = left[:BTREE_PAGE_SIZE]
        return 2, [3]BNode{left, right} // 2 nodes
    }
    leftleft := BNode(make([]byte, BTREE_PAGE_SIZE))
    middle := BNode(make([]byte, BTREE_PAGE_SIZE))
    nodeSplit2(leftleft, middle, left)
    assert(leftleft.nbytes() <= BTREE_PAGE_SIZE)
    return 3, [3]BNode{leftleft, middle, right} // 3 nodes
}

حالت ۳ گره را می‌توان با پایین آوردن حد اندازهٔ KV حذف کرد.

۴.۶ ساختار دادهٔ B+tree

جداسازی ورودی/خروجی دیسک از ساختارهای داده

یک B+tree مبتنی بر دیسک برای ارجاع‌زدایی از اشاره‌گرها (شمارهٔ صفحه‌ها) به ورودی/خروجی دیسک وابسته است. اما ما هنوز آن را کدنویسی نکرده‌ایم. با کال‌بک‌ها (callbacks) ایزوله می‌شود تا ساختار داده به تنهایی قابل تست باشد.

gotype BTree struct {
    // root pointer (a nonzero page number)
    root uint64
    // callbacks for managing on-disk pages
    get func(uint64) []byte // read data from a page number
    new func([]byte) uint64 // allocate a new page number with data
    del func(uint64)        // deallocate a page number
}

ورودی/خروجی دیسک را می‌توان با این کال‌بک‌ها شبیه‌سازی کرد. پس یک B+tree مبتنی بر دیسک به‌سادگی می‌تواند به‌عنوان B+tree درون‌حافظه استفاده شود، در حالی که عکس آن درست نیست.

درج در درخت

درج در درخت یک بازگشت از بالا به پایین تا رسیدن به گرهٔ برگ است.

gofunc treeInsert(tree *BTree, node BNode, key []byte, val []byte) BNode {
    // The extra size allows it to exceed 1 page temporarily.
    new := BNode(make([]byte, 2*BTREE_PAGE_SIZE))
    // where to insert the key?
    idx := nodeLookupLE(node, key) // node.getKey(idx) <= key
    switch node.btype() {
    case BNODE_LEAF: // leaf node
        if bytes.Equal(key, node.getKey(idx)) {
            leafUpdate(new, node, idx, key, val)   // found, update it
        } else {
            leafInsert(new, node, idx+1, key, val) // not found, insert
        }
    case BNODE_NODE: // internal node, walk into the child node
        // ...
    }
    return new
}

حالت گره‌های داخلی فقط درج در زیردرخت، شکافتن گرهٔ فرزند جدید و سپس جایگزینی لینک با گره‌های جدید است. چون گره‌ها کپی-هنگام-نوشتن هستند، گرهٔ فرزند همیشه با گره‌های جدید جایگزین می‌شود؛ به همین دلیل است که treeInsert() گرهٔ به‌روزشده را برمی‌گرداند.

انتشار شکافتن‌ها به والدها

nodeReplaceKidN() مثل leafUpdate() است، اما با چند کلید.

go// replace a link with multiple links
func nodeReplaceKidN(
    tree *BTree, new BNode, old BNode, idx uint16,
    kids ...BNode,
) {
    inc := uint16(len(kids))
    new.setHeader(BNODE_NODE, old.nkeys()+inc-1)
    nodeAppendRange(new, old, 0, 0, idx)
    for i, node := range kids {
        nodeAppendKV(new, idx+uint16(i), tree.new(node), node.getKey(0), nil)
    }
    nodeAppendRange(new, old, idx+inc, idx+1, old.nkeys()-(idx+1))
}

بعد از شکافتن یک گرهٔ فرزند، گرهٔ والد در اندازه رشد می‌کند که ممکن است شکافت دیگری لازم کند. اگر شکافتن به گرهٔ ریشه انتشار یابد، ارتفاع درخت ۱ واحد رشد می‌کند.

۵.۱ حذف از یک گره

حذف از یک گرهٔ برگ

حذف از یک گرهٔ برگ به‌سادگی کپی همهٔ کلیدهای به‌جز کلید حذف‌شده است. در اینجا فقط یک خط کد بیشتر از leafInsert() ندارد.

    new.setHeader(BNODE_LEAF, old.nkeys()-1)
    nodeAppendRange(new, old, 0, 0, idx)

حذف از یک گرهٔ داخلی

همیشه یک گرهٔ برگ حذف را انجام می‌دهد. پس وقتی یک گرهٔ داخلی با کلید موردنظر مواجه می‌شود، فقط حذف را به گرهٔ فرزند سمت راست کلید منتقل می‌کند. (کلیدهای یک گرهٔ داخلی، شروع محدودهٔ فرزندانشان هستند، نه کلیدهای واقعی.)

gofunc treeDelete(tree *BTree, node BNode, key []byte) BNode {
    // where to find the key?
    idx := nodeLookupLE(node, key)
    // delete from the leaf node
    switch node.btype() {
    case BNODE_LEAF:
        if !bytes.Equal(key, node.getKey(idx)) {
            return BNode{} // not found
        }
        new := BNode(make([]byte, BTREE_PAGE_SIZE))
        leafDelete(new, node, idx)
        return new
    case BNODE_NODE: // internal node, recursive delete
        return nodeDelete(tree, node, idx, key)
    default:
        panic("bad node!")
    }
}

گرهٔ خالی برمی‌گردد اگر کلید یافت نشود.

اگر کلید از گرهٔ فرزند ام حذف شود، گرهٔ والد دوباره به‌سادگی لینک گرهٔ فرزند ام را با گرهٔ به‌روزشده جایگزین می‌کند. این با nodeReplaceKidN() با یک لینک انجام می‌شود.

go// delete a key from the internal node
func nodeDelete(tree *BTree, node BNode, idx uint16, key []byte) BNode {
    // recurse into the kid
    kptr := node.getPtr(idx)
    updated := treeDelete(tree, tree.get(kptr), key)
    if len(updated) == 0 {
        return BNode{} // not found
    }
    tree.del(kptr)
    new := BNode(make([]byte, BTREE_PAGE_SIZE))
    // check for merging
    if updated.nbytes() > BTREE_PAGE_SIZE/4 {
        // size still ok, just update the link
        nodeReplaceKidN(tree, new, node, idx, updated)
        return new
    }
    // merging
    if idx > 0 {
        // merge with the left sibling
        sibling := BNode(make([]byte, BTREE_PAGE_SIZE))
        nodeMerge(sibling, node.getPtr(idx-1), updated)
        if sibling.nbytes() <= BTREE_PAGE_SIZE {
            nodeReplace2KidN(tree, new, node, idx-1, sibling)
            return new
        }
    }
    // merge with the right sibling
    if idx+1 < node.nkeys() {
        // merge with the right sibling
        sibling := BNode(make([]byte, BTREE_PAGE_SIZE))
        nodeMerge(sibling, updated, node.getPtr(idx+1))
        if sibling.nbytes() <= BTREE_PAGE_SIZE {
            nodeReplace2KidN(tree, new, node, idx, sibling)
            return new
        }
    }
    // no merge
    nodeReplaceKidN(tree, new, node, idx, updated)
    return new
}

همیشه ابتدا با همسایهٔ چپ ادغام می‌شود. اگر از اندازهٔ صفحه تجاوز کرد، همسایهٔ راست امتحان می‌شود.

۵.۲ ادغام گره‌ها

ادغام دو گره

ادغام دو گره‌های مجاور (لینک‌های خواهر/برادر) را در یک گره:

go// merge 2 nodes into 1
func nodeMerge(new BNode, left BNode, right BNode) {
    new.setHeader(left.btype(), left.nkeys()+right.nkeys())
    nodeAppendRange(new, left, 0, 0, left.nkeys())
    nodeAppendRange(new, right, left.nkeys(), 0, right.nkeys())
}

الزامات برای اینکه این کار درست کار کند:

  • کلیدهای دو گره مرتب و به هم پیوسته‌اند.
  • کلیدهای گرهٔ چپ از کلیدهای گرهٔ راست کوچک‌ترند.
  • گرهٔ حاصل باید در یک صفحه جا بگیرد.

گرهٔ داخلی جدید باید اولین کلید گرهٔ راست را (که اولین کلیدِ گرهٔ چپِ ادغام‌شده‌شده بود) حذف کند و به‌جایش با اولین کلیدِ گرهٔ چپِ قدیمی جایگزین کند؛ به همین دلیل است که nodeReplace2KidN() نه یک لینک، بلکه یک KV را جایگزین می‌کند.

go// replace 2 adjacent links with 1
func nodeReplace2KidN(
    tree *BTree, new BNode, old BNode, idx uint16,
    kid BNode,
) {
    new.setHeader(BNODE_NODE, old.nkeys()-1)
    nodeAppendRange(new, old, 0, 0, idx) // copy the keys before `idx`
    nodeAppendKV(new, idx, tree.new(kid), kid.getKey(0), nil)
    nodeAppendRange(new, old, idx+1, idx+2, old.nkeys()-(idx+2))
}

ادغام می‌تواند در گره‌های والد بالا منتشر شود: گرهٔ والد دو کلید از دست می‌دهد که به‌سادگی اندازهٔ آن را کوچک می‌کند. پس انتشار رو به بالا محدود است.

۵.۳ رابط سطح بالای درخت

رابط سطح بالای درخت

درج/حذف را با قوانین درخت ریشهٔ سطح بالا ترکیب می‌کنیم؛ که شامل رسیدگی به ریشه است. این کتاب هرگز ریشه را بازنویسی نمی‌کند، فقط لینک‌ها را به‌روزرسانی می‌کند. (برخلاف برخی کتاب‌های درسی که ریشه را صریح بازنویسی می‌کنند تا منطق را ساده کنند.)

مزایای این رویکرد:

  • پیش‌نیاز ساخت یک لیست آزاد در فصل ۷.
  • نوشتن گره‌ها در دو فاز برای ماندگاری در فصل ۶.
go// insert a KV into a key in the tree
func (tree *BTree) Insert(key []byte, val []byte) {
    assert(len(key) != 0)
    assert(len(key) <= BTREE_MAX_KEY_SIZE)
    assert(len(val) <= BTREE_MAX_VAL_SIZE)
    if tree.root == 0 {
        // empty tree, create the first node
        root := BNode(make([]byte, BTREE_PAGE_SIZE))
        root.setHeader(BNODE_LEAF, 2)
        // a dummy key, this makes the tree cover the whole key space.
        // thus a lookup can always find a containing node.
        nodeAppendKV(root, 0, 0, nil, nil)
        nodeAppendKV(root, 1, 0, key, val)
        tree.root = tree.new(root)
        return
    }
    node := treeInsert(tree, tree.get(tree.root), key, val)
    nsplit, splitted := nodeSplit3(node)
    tree.del(tree.root)
    if nsplit > 1 {
        // the root was split, add a new layer.
        root := BNode(make([]byte, BTREE_PAGE_SIZE))
        root.setHeader(BNODE_NODE, nsplit)
        for i, knode := range splitted[:nsplit] {
            ptr, key := tree.new(knode), knode.getKey(0)
            nodeAppendKV(root, uint16(i), ptr, key, nil)
        }
        tree.root = tree.new(root)
    } else {
        tree.root = tree.new(splitted[0])
    }
}

ریشهٔ جدید وقتی ساخته می‌شود که گرهٔ ریشهٔ قدیمی شکافته شود.

go// delete a key from the tree
func (tree *BTree) Delete(key []byte) bool {
    assert(len(key) != 0)
    assert(len(key) <= BTREE_MAX_KEY_SIZE)
    if tree.root == 0 {
        return false
    }
    updated := treeDelete(tree, tree.get(tree.root), key)
    if len(updated) == 0 {
        return false // not found
    }
    tree.del(tree.root)
    if updated.btype() == BNODE_NODE && updated.nkeys() == 1 {
        // remove the root node.
        tree.root = updated.getPtr(0)
    } else {
        tree.root = tree.new(updated)
    }
    return true
}

زمانی که ارتفاع درخت بعد از حذف کاهش می‌یابد، گرهٔ ریشه حذف می‌شود.

پیشوند «کنترل» [بدون مقدار]

وقتی درخت خالی است یک گرهٔ برگ با ۲ کلید می‌سازیم: یک کلید «کنترل» بدون مقدار (خالی) به‌همراه اولین کلید واقعی. این کار جست‌وجوهای برگ را همیشه موفق می‌کند؛ چون جست‌وجو حداقل یک موقعیت یافته دارد، حتی وقتی کلید از همهٔ کلیدهای گره کوچک‌تر باشد.

بعد از حذف، گرهٔ ریشه ممکن است فقط کلید «کنترل» را داشته باشد. وقتی ارتفاع درخت کاهش می‌یابد و گرهٔ ریشهٔ تک‌فرزندی حذف می‌شود، کلید «کنترل» همراه با گرهٔ ریشه حذف می‌شود.

بدون کلید «کنترل»، این موارد ممکن است رخ دهد:

  • همهٔ کلیدها از ریشه حذف شوند.
  • جست‌وجو در گره‌های برگ ناموفق باشد (کلید از همهٔ کلیدها کوچک‌تر است).

۵.۴ آزمایش B+Tree

یک صفحهٔ جعلی برای B+tree

با یک صفحهٔ جعلی در حافظه می‌توانیم B+tree را بدون سیستم فایل آزمایش کنیم. کال‌بک‌ها از یک نگاشت درهمی (map) به‌عنوان فضای شمارهٔ صفحه استفاده می‌کنند.

gotype C struct {
    tree  BTree
    pages map[uint64]BNode // in-memory pages
}
func newC() *C {
    c := &C{}
    c.pages = map[uint64]BNode{}
    c.tree.get = func(ptr uint64) []byte {
        return c.pages[ptr]
    }
    c.tree.new = func(node BNode) uint64 {
        ptr := uint64(rand.Uint64())
        c.pages[ptr] = node
        return ptr
    }
    c.tree.del = func(ptr uint64) {
        delete(c.pages, ptr)
    }
    return c
}

خلاصه: قسمت اول

این بخش اول کتاب است؛ یک B+tree کارا با درج، حذف و جست‌وجو که روی صفحه‌های جعلی در حافظه اجرا می‌شود. در بخش بعد (فصل‌های ۶ و ۷) آن را با یک فایل واقعی پیوند می‌دهیم تا ماندگار شود.

فصل ۶: ذخیره‌سازی فقط-الحاقی (Append-Only)

فصل اصلی: Append-Only KV

در این فصل یک KV ماندگار را روی یک فایل واقعی پیاده می‌کنیم. این سه چیز را به B+tree از بخش قبلی اضافه می‌کند:

  1. یک نگاشت از شمارهٔ صفحه‌ها به آفست‌های فایل.
  2. تخصیص صفحات جدید فقط از انتهای فایل.
  3. یک ساختار کنترلی در پایان فایل که صفحهٔ ریشه را ذخیره می‌کند.

نتیجه: یک KV فقط-الحاقی (append-only) که هر بایت تنها یک‌بار نوشته می‌شود، برای MLC SSD ایده‌آل است. در فصل بعد آن را به یک لیست آزاد افزوده ارتقا می‌دهیم تا صفحات حذف‌شده هم استفادهٔ مجدد شوند.

۶.۱ چیدمان فایل

دو نوع فایل برای پیاده‌سازی این سیستم وجود دارد. ما دومین را استفاده می‌کنیم:

  • فایل منطقی: با یک ترجمهٔ آدرس (مثل درهم‌سازی)؛ دیرتر بحث می‌شود.
  • فایل فیزیکی: آدرسِ منطقی شمارهٔ صفحه است و آفست فایل یک تابع ساده از شمارهٔ صفحه است: آفست = شمارهٔ صفحه × اندازهٔ صفحه.

چیدمان فایل ما:

text┌─────────────┬──────────────┬──────────────┬──────────────┐
│  master page │   page 1     │   page 2     │   page 3     │
│    (root)    │   (B+tree)   │   (B+tree)   │   (B+tree)   │
└─────────────┴──────────────┴──────────────┴──────────────┘

صفحهٔ ۰ صفحهٔ اصلی (master) است که اشارهٔ صفحهٔ ریشه را ذخیره می‌کند. صفحه‌های ۱، ۲، ۳ و... گره‌های B+tree را ذخیره می‌کنند.

یک صفحهٔ اصلی فقط یک اشاره‌گر ریشهٔ ۸ بایتی نیست؛ باید شرایط بیشتری را برآورده کند:

  • شمارهٔ صفحهٔ ریشهٔ درخت B+.

۶.۲ تخصیص صفحات از انتهای فایل

چون گره‌ها کپی-هنگام-نوشتن هستند، صفحهٔ جدید همیشه از انتهای فایل تخصیص داده می‌شود و صفحهٔ قدیمی غیرقابل استفاده است. کال‌بک صفحهٔ جدید:

gofunc (db *KV) pageNew(node BNode) uint64 {
    assert(len(node) <= BTREE_PAGE_SIZE)
    ptr := db.page.nused
    assert(ptr < db.page.flushed)
    db.page.nused++
    db.pageAppend(node)
    return ptr
}

آیا نگران رشد فایل هستید؟ ما B+tree را با یک لیست آزاد در فصل بعد ارتقا می‌دهیم تا صفحات حذف‌شده استفادهٔ مجدد شوند؛ که اندازهٔ فایل را تا حدی در مرز نگه می‌دارد.

اما استفادهٔ مجدد از صفحات حذف‌شده به یک لیست آزاد نیاز دارد و یک لیست آزاد نیاز دارد که صفحات از پایین فایل نیز تخصیص داده شوند:

gofunc (db *KV) pageAlloc(node BNode) uint64 {
    if len(db.page.free.nodes) != 0 && db.page.nused+1 < db.page.flushed {
        // reuse a page from the free list
        ptr := db.page.freePop()
        db.pageAppend(node)
        return ptr
    }
    return db.pageNew(node)
}

صفحه‌های بزرگ

همان‌طور که در فصل ۴ بحث شد، KVهای بزرگ به گره‌های بزرگ تبدیل می‌شوند که می‌توانند از اندازهٔ صفحه تجاوز کنند. این کتاب از یک «صفحهٔ بزرگ» استفاده می‌کند: با شمارندهٔ صفحهٔ خودش که بخش‌های چندصفحه‌ای را مدیریت می‌کند. فعلاً فقط اعلام می‌کنیم که وجود دارد؛ در فصل ۹ پیاده می‌شود.

۶.۳ به‌روزرسانی دو فازی و فایل

به‌روزرسانی دو فازی با فایل

به‌روزرسانی دو فازی یعنی اینکه همهٔ گره‌های به‌روزشده بدون استثنا ابتدا به دیسک نوشته می‌شوند، و فقط بعد از آن صفحهٔ ریشه‌ای که به آن‌ها اشاره می‌کند نوشته می‌شود. این، به‌روزرسانی را اتمیک می‌کند: یا همهٔ گره‌های جدید با صفحهٔ ریشهٔ جدید دیدنی می‌شوند یا هیچ‌کدام.

go// update the master page. it must be atomic.
func (db *KV) masterUpdate(root uint64) {
    // if the master page needs to be updated with a new page
    // number, it's just an append-only file.
    db.page.nused++
    db.writeMaster()
}

صفحهٔ اصلی باید اتمیک باشد، چون به‌روزرسانی‌های معامله را می‌خرد یا می‌شکند.

توجه: این نسخه یک fsync در هر نوشتن انجام می‌دهد. این یک «تعادل» است: یا تعداد زیادی fsync و نوشتن‌های خیلی امن، یا کمتر fsync و نوشتن‌های کمتر امن. «تعادل» بعداً مورد بحث قرار می‌گیرد.

برای هماهنگی بافرها، دستور fsync باید قبل از masterUpdate() صدا زده شود:

مشکل

می‌خواهیم tree.get یک صفحهٔ خواناتر را برگرداند. کال‌بک‌ها فقط در طول یک Update() فعال هستند. کال‌بک get باید یک صفحهٔ تازه تخصیص‌یافته را برگرداند یا آن را از دیسک بخواند. با این ترتیب دو گزینه است:

gofunc (db *KV) pageGet(ptr uint64) BNode {
    // multiple pages
    if ptr >= db.page.flushed {
        return db.page.big[ptr-db.page.nused].node
    }
    // a big page
    if ptr < db.page.nobig {
        return db.page.big[ptr].node
    }
    // a normal page
    return db.pageGetMapped(ptr)
}

۶.۶ نکته دربارهٔ fsync

هشدار: گارانتی fsync در سیستمعامل‌ها متفاوت است، به‌خصوص در لینوکس. کتاب برای سادگی فرض می‌کند که همهٔ fsyncها کار می‌کنند، اما پیاده‌سازی‌های واقعی باید دقیق‌تر باشند.

در برخی سیستم‌ها، fsync قول نمی‌دهد که متادیتای فایل هم به دیسک رفته باشد، و fsync دایرکتوری نیز باید صدا زده شود. در نتیجه «اتمیک بودن» صفحهٔ اصلی ممکن است در عمل برقرار نباشد. برای سادگی، این کتاب فرض می‌کند مشکل وجود ندارد؛ یک پیاده‌سازی واقعی به توجه بیشتری نیاز دارد.

خلاصه

در این فصل یک KV فقط-الحاقی ساختیم که هر بایت دقیقاً یک‌بار نوشته می‌شود و برای MLC SSD عالی است. در فصل بعد، یک لیست آزاد برای استفادهٔ مجدد صفحات حذف‌شده اضافه می‌کنیم تا از رشد نامحدود فایل جلوگیری شود.

فصل ۷: لیست آزاد (Free List)

فصل اصلی: Free List

فصل قبل یک پایگاه دادهٔ فقط-الحاقی بدون استفادهٔ مجدد از فضا ساخت. این فصل آن را با یک لیست آزاد ارتقا می‌دهد که صفحات حذف‌شده را استفادهٔ مجدد می‌کند و از رشد نامحدود فایل جلوگیری می‌کند.

قوانین استفادهٔ مجدد از فضا:

  • استفادهٔ مجدد از صفحات به‌روزرسانی‌شده فقط بعد از تایید امن بودنشان.
  • صفحات حذف‌شده با لیست آزاد به‌صورت یک ساختار مرتبط پشتیبان‌گیری می‌شوند که در به‌روزرسانی‌ها پایدار می‌ماند.

۷.۱ ساختار لیست آزاد

لیست آزاد یک ساختار مرجع است که همهٔ صفحات حذف‌شده را برای استفادهٔ مجدد پیگیری می‌کند. به‌صورت یک لیست مرتبط چندصفحه‌ای پیاده می‌شود:

text┌────────────────────┐       ┌────────────────────┐
│   free list node   │       │   free list node   │
│  [head | next |  ... ]│ ──> │  [head | next |  ... ]│
│  [ptr  | ptr  | ... ]│      │  [ptr  | ptr  | ... ]│
└────────────────────┘       └────────────────────┘
         │                            │
         ▼                            ▼
      ┌─────────┐                 ┌─────────┐
      │  page   │                 │  page   │
      └─────────┘                 └─────────┘

هر گرهٔ لیست آزاد:

  • head: شمارهٔ صفحهٔ اولین صفحهٔ آزاد این گره.
  • next: اشاره‌گر به گرهٔ بعدی لیست آزاد.
  • size: تعداد اشاره‌گرها در این گره.
  • ptrs: آرایه‌ای از شمارهٔ صفحه‌های آزاد.

لیست آزاد در حافظه فقط سر گره و گرهٔ «بعدی» را نگه می‌دارد و بقیه با یک mmap خوانده می‌شوند.

}

خواندن گرهٔ لیست آزاد

یک گرهٔ لیست آزاد با همین قالب صفحه ذخیره می‌شود. می‌توانیم از همان ساختار BNode برای خواندن آن استفاده کنیم:

gofunc (fl *FreeList) readNode(node BNode) (head, next uint64, ptrs []uint64) {
    head = binary.LittleEndian.Uint64(node[0:])
    next = binary.LittleEndian.Uint64(node[8:])
    nptrs := (node.nbytes() - FREE_LIST_HEADER) / 8
    ptrs = make([]uint64, nptrs)
    for i := 0; i < len(ptrs); i++ {
        pos := FREE_LIST_HEADER + 8*i
        ptrs[i] = binary.LittleEndian.Uint64(node[pos:])
    }
    return
}

ذخیره‌کردن گرهٔ لیست آزاد

برای به‌روزرسانی یک صفحهٔ لیست آزاد، ابتدا آن را می‌خوانیم، در حافظه تغییر می‌دهیم و سپس با استفاده از کال‌بک set دوباره می‌نویسیم. این، همان کپی-هنگام-نوشتن است، اما برای صفحات لیست آزاد نیز کار می‌کند.

gofunc (fl *FreeList) writeNode(
    node BNode, head, next uint64, ptrs []uint64,
) {
    binary.LittleEndian.PutUint64(node[0:], head)
    binary.LittleEndian.PutUint64(node[8:], next)
    for i, ptr := range ptrs {
        pos := FREE_LIST_HEADER + 8*i
        binary.LittleEndian.PutUint64(node[pos:], ptr)
    }
    fl.set(node)
}

۷.۲ گرفتن و دادن صفحات

گرفتن یک صفحه از لیست آزاد

gofunc (fl *FreeList) get() uint64 {
    if fl.headPage == 0 {
        return 0 // the list is empty
    }
    node := fl.get(fl.headPage)
    head, next, ptrs := fl.readNode(node)
    if len(ptrs) == 0 {
        // use the last page, link the previous page as the new head
        fl.headPage, fl.headNext = next, 0
        fl.nptr -= 1
        fl.delPage(fl.headPage) // ...
        return head
    }
    // pop a pointer from the first page
    ptr := ptrs[len(ptrs)-1]
    ptrs = ptrs[:len(ptrs)-1]
    fl.writeNode(node, head, next, ptrs)
    return ptr
}

دادن یک صفحه به لیست آزاد

gofunc (fl *FreeList) put(ptr uint64) {
    if fl.headPage == 0 {
        // create a new node
        node := make([]byte, BTREE_PAGE_SIZE)
        fl.writeNode(node, ptr, 0, nil)
        fl.headPage = fl.new(node)
        fl.headNext = 0
        fl.nptr = 1
        return
    }
    node := fl.get(fl.headPage)
    head, next, ptrs := fl.readNode(node)
    if len(ptrs) < FREE_LIST_CAP {
        // add to the existing node
        ptrs = append(ptrs, ptr)
        fl.writeNode(node, head, next, ptrs)
        return
    }
    // create a new node
    node = make([]byte, BTREE_PAGE_SIZE)
    fl.writeNode(node, ptr, fl.headPage, nil)
    fl.headPage = fl.new(node)
    fl.headNext = next
    fl.nptr++
}

۷.۳ استفاده از لیست آزاد در به‌روزرسانی‌ها

این الگو در یک به‌روزرسانی استفاده می‌شود: اول، صفحات حذف‌شده به لیست آزاد داده می‌شوند (فاز ۱). بعد، صفحات جدید درج می‌شوند (فاز ۲). ترتیب مهم است تا لیست آزاد به‌طور نادرست صفحات حذف‌شده را ندهد:

gofunc (db *KV) Update(fn func(tx *KVTX) error) error {
    // a better approach: allow the transaction to be retried

    // stage 1: record the deleted pages in the free list
    db.freeListPut()
    // stage 2: insert the new pages and update the B+tree
    ...

بعد از درج صفحات جدید، لیست آزاد به‌روزرسانی می‌شود و صفحهٔ اصلی با ریشهٔ جدید نوشته می‌شود.

۷.۴ بازیابی لیست آزاد

برای بازیابی لیست آزاد از فایل، فقط به گرهٔ سر نیاز داریم که در صفحهٔ اصلی ذخیره شده است؛ بقیه گره‌ها با دنبال‌کردن اشاره‌گرهای next یافت می‌شوند.

gofunc (fl *FreeList) load() {
    // the free list is stored in the master page
    // ...
}

این، بازیابی درست را تضمین می‌کند حتی اگر در میانهٔ یک به‌روزرسانی خرابی رخ دهد؛ چون به‌روزرسانی اتمیک است و لیست آزاد فقط با ریشهٔ جدید به‌روزرسانی می‌شود.
