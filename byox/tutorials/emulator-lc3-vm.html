ماشین مجازی چیست؟

ماشین مجازی (VM) برنامه‌ای است که مثل یک کامپیوتر رفتار می‌کند. این برنامه یک پردازندهٔ مرکزی (CPU) را به همراه چند جزء سخت‌افزاری دیگر شبیه‌سازی می‌کند و به آن اجازه می‌دهد عملیات حسابی انجام دهد، در حافظه بخواند و بنویسد و با دستگاه‌های ورودی/خروجی (I/O) تعامل کند؛ دقیقاً مثل یک کامپیوتر فیزیکی. مهم‌تر از همه، می‌تواند زبان ماشین را بفهمد و شما می‌توانید با آن برنامه‌نویسی‌اش کنید.

میزان سخت‌افزار کامپیوتری که ماشین مجازی تلاش می‌کند شبیه‌سازی کند، به هدف آن بستگی دارد. برخی از ماشین‌های مجازی برای بازتولید رفتار یک کامپیوتر خاص طراحی شده‌اند؛ مانند شبیه‌سازهای بازی‌های ویدیویی. بیشتر مردم دیگر دستگاه NES در خانه ندارند، اما همچنان می‌توانیم بازی‌های NES را با شبیه‌سازی سخت‌افزار NES در یک برنامه اجرا کنیم. این شبیه‌سازها باید صادقانه هر جزئیات و هر جزء مهم سخت‌افزاری دستگاه اصلی را بازآفرینی کنند.

ماشین‌های مجازی دیگری هم هستند که مانند هیچ کامپیوتر واقعی رفتار نمی‌کنند و کاملاً ساخته و پرداختهٔ ذهن‌اند! این کار عمدتاً برای آسان‌تر کردن توسعهٔ نرم‌افزار انجام می‌شود. تصور کنید بخواهید برنامه‌ای بسازید که روی چند معماری کامپیوتری مختلف اجرا شود. یک ماشین مجازی می‌تواند سکوی استانداردی ارائه دهد که قابلیت انتقال (portability) را برای همهٔ آن‌ها فراهم کند. به‌جای بازنویسی یک برنامه به لهجه‌های مختلف اسمبلی برای هر معماری CPU، فقط باید برنامهٔ کوچک ماشین مجازی را به هر زبان اسمبلی بنویسید. سپس هر برنامه فقط یک بار، به زبان اسمبلی خود ماشین مجازی، نوشته می‌شود.

توجه: یک کامپایلر (compiler) مشکل مشابهی را با کامپایل یک زبان سطح بالا استاندارد به چند معماری CPU حل می‌کند؛ در حالی که ماشین مجازی یک معماری CPU استاندارد می‌سازد که روی دستگاه‌های سخت‌افزاری مختلف شبیه‌سازی می‌شود. یکی از مزیت‌های کامپایلر این است که هیچ سرباری هنگام اجرا ندارد، در حالی که ماشین مجازی دارد. حتی اگر کامپایلرها کارشان را خوب انجام می‌دهند، نوشتن یک کامپایلر جدید که سکوهای متعدد را هدف قرار دهد بسیار دشوار است؛ بنابراین ماشین‌های مجازی همچنان در این‌جا مفیدند. در عمل، ماشین‌های مجازی و کامپایلرها در سطوح مختلف با هم ترکیب می‌شوند.

ماشین مجازی جاوا (JVM) مثال بسیار موفقی است. خود JVM برنامه‌ای با اندازهٔ متوسط است که به‌قدر کافی کوچک است که یک برنامه‌نویس بتواند آن را بفهمد. همین امر نوشتن آن را برای هزاران دستگاه از جمله تلفن‌ها ممکن کرده است. به محض پیاده‌سازی JVM روی یک دستگاه جدید، هر برنامه‌ای که تا به حال به زبان جاوا، کاتلین یا Clojure نوشته شده باشد، بدون هیچ تغییری می‌تواند روی آن اجرا شود. تنها هزینهٔ آن، سربار خود ماشین مجازی و سطح انتزاع بیشتر از ماشین است. در بیشتر مواقع، این معامله‌ای نسبتاً خوب است.

ماشین مجازی برای ارائهٔ چنین مزیتی لازم نیست بزرگ یا فراگیر باشد. بازی‌های ویدیویی قدیمی اغلب از ماشین‌های مجازی کوچک برای فراهم کردن سیستم‌های اسکریپت‌نویسی ساده استفاده می‌کردند.

ماشین‌های مجازی برای اجرای امن یا ایزولهٔ کد نیز مفیدند. یکی از کاربردهای آن، جمع‌آوری زباله (Garbage Collection) است. هیچ راه پیش پا افتاده‌ای برای پیاده‌سازی جمع‌آوری خودکار زباله روی C یا C++ وجود ندارد، زیرا برنامه نمی‌تواند پشته یا متغیرهای خودش را ببیند. اما ماشین مجازی «خارج» از برنامه‌ای است که اجرا می‌کند و می‌تواند همهٔ ارجاع‌های حافظه روی پشته را مشاهده کند.

نمونهٔ دیگری از این رفتار، قراردادهای هوشمند اتریوم است. قراردادهای هوشمند برنامه‌های کوچکی هستند که هر گرهٔ اعتبارسنج (validating node) در شبکهٔ بلاک‌چین آن‌ها را اجرا می‌کند. این کار مستلزم آن است که گردانندگان گره، برنامه‌هایی را روی ماشین‌های خودشان اجرا کنند که توسط غریبه‌های کامل نوشته شده‌اند و هیچ فرصتی برای بررسی قبلی آن‌ها وجود ندارد. برای جلوگیری از کارهای مخرب قراردادها، آن‌ها در یک ماشین مجازی اجرا می‌شوند که به سیستم فایل، شبکه، دیسک و… دسترسی ندارد. اتریوم همچنین کاربرد خوبی از ویژگی‌های قابلیت انتقال ناشی از استفاده از ماشین مجازی است. از آنجا که گره‌های اتریوم می‌توانند روی انواع زیادی از کامپیوترها و سیستم‌عامل‌ها اجرا شوند، استفاده از ماشین مجازی به قراردادهای هوشمند اجازه می‌دهد بدون هیچ در نظر گرفتن سکوهای متعددی که روی آن‌ها اجرا می‌شوند، نوشته شوند.

معماری LC-3

ماشین مجازی ما LC-3 را شبیه‌سازی می‌کند؛ معماری کامپیوتری آموزشی‌ای که معمولاً برای آموزش معماری کامپیوتر و اسمبلی به دانشجویان دانشگاه استفاده می‌شود. LC-3 در مقایسه با x86 مجموعه دستور (instruction set) ساده‌شده‌ای دارد، اما ایده‌های اصلی‌ای را نشان می‌دهد که CPUهای مدرن از آن‌ها استفاده می‌کنند.

توجه: LC-3 در کتاب «Introduction to Computing Systems: From Bits & Gates to C/C++ & Beyond» نوشتهٔ Yale N. Patt و Sanjay J. Patel تعریف شده است. این آموزش بر اساس ویرایش دوم است.

برای شروع، باید اجزای سخت‌افزاری ضروری ماشین را شبیه‌سازی کنیم. سعی کنید بفهمید هر جزء چیست، اما اگر هنوز مطمئن نیستید که چگونه در تصویر بزرگ‌تر جا می‌گیرد، الان نگرانش نباشید. با ساخت یک فایل C شروع کنید. هر یک از قطعه کدهای این بخش باید در محدودهٔ سراسری (global scope) این فایل قرار بگیرند.

حافظه (Memory)

LC-3 دارای ۶۵٬۵۳۶ مکان حافظه است (حداکثر مقداری که با یک عدد صحیح بدون علامت ۱۶ بیتی، یعنی 2^16، قابل آدرس‌دهی است) و هر کدام یک مقدار ۱۶ بیتی را ذخیره می‌کند. یعنی در مجموع می‌تواند تنها ۱۲۸ کیلوبایت ذخیره کند که نسبت به آنچه عادت دارید خیلی کوچک‌تر است! در برنامهٔ ما، این حافظه در یک آرایهٔ ساده ذخیره می‌شود:

c#define MEMORY_MAX (1 << 16)
uint16_t memory[MEMORY_MAX];  /* 65536 خانه */

ثبات‌ها (Registers)

ثبات (register) جایگاهی برای ذخیرهٔ یک مقدار واحد روی CPU است. ثبات‌ها مانند «میزکار» CPU هستند. برای اینکه CPU با یک تکه داده کار کند، آن داده باید در یکی از ثبات‌ها باشد. با این حال، چون فقط چند ثبات وجود دارد، تنها مقدار کمی داده می‌تواند در هر زمان بارگذاری شود. برنامه‌ها با بارگذاری مقادیر از حافظه در ثبات‌ها، محاسبهٔ مقادیر در ثبات‌های دیگر و سپس ذخیرهٔ نتایج نهایی در حافظه، راهی برای دور زدن این محدودیت پیدا می‌کنند.

LC-3 در مجموع ۱۰ ثبات دارد که هر کدام ۱۶ بیتی‌اند. بیشتر آن‌ها همه‌منظوره (general purpose) هستند، اما چند تایی نقش‌های مشخصی دارند.

  • ۸ ثبات همه‌منظوره (R0 تا R7)
  • ۱ ثبات شمارندهٔ برنامه (PC - Program Counter)
  • ۱ ثبات نشان‌های وضعیت (COND - Condition Flags)

ثبات‌های همه‌منظوره را می‌توان برای انجام هر محاسبهٔ برنامه استفاده کرد. شمارندهٔ برنامه یک عدد صحیح بدون علامت است که آدرس دستور بعدی در حافظه را برای اجرا نگه می‌دارد. نشان‌های وضعیت اطلاعاتی دربارهٔ محاسبهٔ قبلی به ما می‌دهند.

cenum
{
    R_R0 = 0,
    R_R1,
    R_R2,
    R_R3,
    R_R4,
    R_R5,
    R_R6,
    R_R7,
    R_PC, /* شمارنده برنامه */
    R_COND,
    R_COUNT
};

دقیقاً مثل حافظه، ثبات‌ها را در یک آرایه ذخیره می‌کنیم:

cuint16_t reg[R_COUNT];

مجموعه دستورها (Instruction set)

دستور (instruction) فرمانی است که به CPU می‌گوید کاری بنیادی انجام دهد؛ مانند جمع دو عدد. دستورها هم یک کد عملیات (opcode) دارند که نوع کار را نشان می‌دهد و هم مجموعه‌ای از پارامترها که ورودی‌های کار انجام‌شده را فراهم می‌کنند.

هر کد عملیات نمایانگر یک کار است که CPU «بلد است» انجام دهد. در LC-3 فقط ۱۶ کد عملیات وجود دارد. هرچه کامپیوتر می‌تواند محاسبه کند، دنباله‌ای از همین دستورهای ساده است. هر دستور ۱۶ بیت طول دارد که ۴ بیت سمت چپ، کد عملیات را ذخیره می‌کنند. بقیهٔ بیت‌ها برای ذخیرهٔ پارامترها استفاده می‌شوند.

بعداً به‌طور مفصل دربارهٔ کار هر دستور بحث خواهیم کرد. فعلاً کدهای عملیات زیر را تعریف کنید. مطمئن شوید ترتیب آن‌ها حفظ می‌شود تا مقدار enum مناسب به آن‌ها اختصاص یابد:

cenum
{
    OP_BR = 0, /* پرش شرطی */
    OP_ADD,    /* جمع  */
    OP_LD,     /* بارگذاری */
    OP_ST,     /* ذخیره */
    OP_JSR,    /* پرش به زیرروال */
    OP_AND,    /* و بیتی */
    OP_LDR,    /* بارگذاری از طریق ثبات */
    OP_STR,    /* ذخیره از طریق ثبات */
    OP_RTI,    /* استفاده نشده */
    OP_NOT,    /* نقیض بیتی */
    OP_LDI,    /* بارگذاری غیرمستقیم */
    OP_STI,    /* ذخیره غیرمستقیم */
    OP_JMP,    /* پرش */
    OP_RES,    /* رزرو شده (استفاده نشده) */
    OP_LEA,    /* بارگذاری آدرس مؤثر */
    OP_TRAP    /* اجرای روال وقفه */
};
توجه: معماری Intel x86 صدها دستور دارد، در حالی که معماری‌هایی مانند ARM و LC-3 دستورهای بسیار کمی دارند. مجموعه دستورهای کوچک را RISC می‌نامند و مجموعه‌های بزرگ‌تر را CISC. مجموعه دستورهای بزرگ‌تر معمولاً امکانات بنیادی جدیدی ارائه نمی‌دهند، اما اغلب نوشتن اسمبلی را راحت‌تر می‌کنند. یک دستور واحد در CISC ممکن است جای چند دستور در RISC را بگیرد. با این حال، آن‌ها برای مهندسان پیچیده‌تر و پرهزینه‌تر از نظر طراحی و ساخت هستند. همین و سایر مبادله‌ها باعث می‌شود این طراحی‌ها مد شوند و مد از سرشان بیفتد.

نشان‌های وضعیت (Condition flags)

ثبات R_COND نشان‌های وضعیت را ذخیره می‌کند که اطلاعاتی دربارهٔ تازه‌ترین محاسبهٔ انجام‌شده ارائه می‌دهند. این کار به برنامه‌ها اجازه می‌دهد شرایط منطقی مانند if (x > 0) { ... } را بررسی کنند.

هر CPU نشان‌های وضعیت گوناگونی برای علامت دادن موقعیت‌های مختلف دارد. LC-3 تنها از ۳ نشان وضعیت استفاده می‌کند که علامت (مثبت/صفر/منفی) محاسبهٔ قبلی را نشان می‌دهند.

cenum
{
    FL_POS = 1 << 0, /* P */
    FL_ZRO = 1 << 1, /* Z */
    FL_NEG = 1 << 2, /* N */
};
توجه: (نماد «<<» عملگر جابه‌جایی بیتی به چپ نامیده می‌شود. «(n << k)» بیت‌های n را به اندازهٔ k خانه به چپ جابه‌جا می‌کند. بنابراین «1 << 2» برابر با «4» خواهد بود. اگر با آن آشنا نیستید آن لینک را بخوانید؛ مهم خواهد بود.)

تنظیم اجزای سخت‌افزاری ماشین مجازی ما تمام شد! پس از افزودن includeهای استاندارد (به مرجع نگاه کنید)، فایل شما باید چیزی شبیه این باشد:

c@{Includes}

@{Registers}
@{Condition Flags}
@{Opcodes}

مثال‌های اسمبلی

حالا بیایید به یک برنامهٔ اسمبلی LC-3 نگاه کنیم تا ایده‌ای از آنچه ماشین مجازی واقعاً اجرا می‌کند به دست بیاوریم. لازم نیست بلد باشید اسمبلی برنامه‌نویسی کنید یا همهٔ اتفاقات را بفهمید. فقط سعی کنید تصوری کلی از آنچه می‌گذرد به دست آورید. این یک «سلام دنیا!» (Hello World) ساده است:

asm.ORIG x3000                        ; این آدرس حافظه‌ای است که برنامه در آن بارگذاری می‌شود
LEA R0, HELLO_STR                  ; آدرس رشته HELLO_STR را در R0 بارگذاری کن
PUTs                               ; رشته‌ای را که R0 به آن اشاره می‌کند در کنسول چاپ کن
HALT                               ; برنامه را متوقف کن
HELLO_STR .STRINGZ "Hello World!"  ; این رشته را در این نقطه از برنامه ذخیره کن
.END                               ; پایان فایل را مشخص کن

دقیقاً مثل C، برنامه از بالا شروع می‌شود و هر دستور را یکی‌یکی اجرا می‌کند. با این حال، برخلاف C، هیچ محدودهٔ تو در تویی «{}» یا ساختارهای کنترلی مانند «if» یا «while» وجود ندارد؛ فقط فهرستی تخت از دستورهاست. این کار اجرا را بسیار آسان‌تر می‌کند.

توجه کنید که برخی دستورها نام‌هایی دارند که با کدهای عملیاتی که قبلاً تعریف کردیم یکی است. پیش‌تر یاد گرفتیم هر دستور ۱۶ بیت است، اما هر خط تعداد کاراکتر متفاوتی دارد. این ناسازگاری چطور ممکن است؟

علتش این است که کدی که می‌خوانیم به زبان اسمبلی نوشته شده است؛ شکل قابل‌خواندن و قابل‌نوشتن برای انسان که به‌صورت متن ساده رمزگذاری شده است. ابزاری به نام اسمبلر (assembler) برای تبدیل هر خط متن به یک دستور باینری ۱۶ بیتی که ماشین مجازی می‌فهمد استفاده می‌شود. این شکل باینری، که اساساً آرایه‌ای از دستورهای ۱۶ بیتی است، کد ماشین (machine code) نامیده می‌شود و همان چیزی است که ماشین مجازی واقعاً اجرا می‌کند.

توجه: اگرچه کامپایلر و اسمبلر نقش مشابهی در توسعه دارند، اما یکسان نیستند. اسمبلر صرفاً آنچه برنامه‌نویس به‌صورت متن نوشته را به باینری رمزگذاری می‌کند: نمادها را با نمایش دودویی‌شان جایگزین می‌کند و آن‌ها را در دستورها بسته‌بندی می‌کند.

فرمان‌های «.ORIG» و «.STRINGZ» شبیه دستور به نظر می‌رسند اما دستور نیستند. آن‌ها دستورالعمل‌های اسمبلر (assembler directives) هستند که تکه‌ای کد یا داده تولید می‌کنند (مثل ماکروها). برای مثال، «.STRINGZ» رشته‌ای از کاراکترها را در نقطه‌ای که نوشته شده در باینری برنامه درج می‌کند.

حلقه‌ها و شرایط با دستوری شبیه goto انجام می‌شوند. این هم مثال دیگری که تا ۱۰ می‌شمارد:

asmAND R0, R0, 0                      ; صفر کردن R0
LOOP                               ; برچسب بالای حلقه
ADD R0, R0, 1                      ; 1 را به R0 اضافه کن و دوباره در R0 ذخیره کن
ADD R1, R0, -10                    ; 10 را از R0 کم کن و در R1 ذخیره کن
BRn LOOP                           ; اگر نتیجه منفی بود به LOOP برگرد
... ; R0 حالا 10 است!
توجه: یادگیری نوشتن اسمبلی برای این آموزش ضروری نیست. با این حال، اگر علاقه‌مندید، می‌توانید برنامه‌های LC-3 خودتان را با ابزارهای LC-3 بنویسید و اسمبل کنید.

اجرای برنامه‌ها

باز هم می‌گویم، مثال‌های قبلی فقط برای این بودند که ایده‌ای از کاری که ماشین مجازی انجام می‌دهد به شما بدهند. برای نوشتن ماشین مجازی لازم نیست در اسمبلی مسلط باشید. تا وقتی رویهٔ درست خواندن و اجرای دستورها را دنبال کنید، هر برنامهٔ LC-3 درست اجرا می‌شود؛ مهم نیست چقدر پیچیده باشد. در تئوری حتی می‌تواند یک مرورگر وب یا یک سیستم‌عامل مثل لینوکس را اجرا کند!

اگر عمیقاً به این ویژگی فکر کنید، ایده‌ای خیره‌کننده از نظر فلسفی است. خود برنامه‌ها می‌توانند انواع کارهای هوشمندانه‌ای انجام دهند که ما هرگز پیش‌بینی نکرده بودیم و شاید نتوانیم بفهمیم، اما در عین حال، هر کاری که می‌توانند انجام دهند به کد ساده‌ای که ما می‌نویسیم محدود است! ما هم‌زمان همه‌چیز و هیچ‌چیز را دربارهٔ نحوهٔ کار هر برنامه می‌دانیم. تورینگ این ایدهٔ شگفت‌آور را مشاهده کرد:

«این دیدگاه که ماشین‌ها نمی‌توانند سبب شگفتی شوند، به باور من برخاسته از مغالطه‌ای است که فیلسوفان و ریاضی‌دانان به‌ویژه بدان مبتلا هستند. این فرض که به محض ارائهٔ یک واقعیت به ذهن، همهٔ پیامدهای آن واقعیت هم‌زمان با آن در ذهن پدیدار می‌شوند. در بسیاری از شرایط فرض بسیار مفیدی است، اما به‌راحتی فراموش می‌شود که نادرست است.» — آلن‌ام. تورینگ

رویه (Procedure)

رویه‌ای که باید بنویسیم این است:

  1. یک دستور را از حافظه، در آدرس مقدار ثبات PC، بارگذاری کن.
  2. ثبات PC را افزایش بده.
  3. به کد عملیات نگاه کن تا مشخص شود چه نوع دستوری باید انجام شود.
  4. دستور را با استفاده از پارامترهای موجود در آن اجرا کن.
  5. به مرحلهٔ ۱ برگرد.

شاید تعجب کنید: «اگر حلقه مدام PC را افزایش می‌دهد، و ما «if» یا «while» نداریم، آیا به‌سرعت دستورها تمام نمی‌شوند؟» نه. همان‌طور که پیش‌تر اشاره کردیم، برخی دستورهای شبیه goto با پرش دادن PC جریان اجرا را تغییر می‌دهند.

بیایید این فرایند را در حلقهٔ اصلی outline کنیم:

cint main(int argc, const char* argv[])
{
    @{Load Arguments}
    @{Setup}

    /* از آنجا که در هر لحظه فقط یکی از نشان‌های وضعیت باید تنظیم باشد، نشان Z را فعال می‌کنیم */
    reg[R_COND] = FL_ZRO;

    /* PC را در موقعیت شروع قرار می‌دهیم */
    /* 0x3000 مقدار پیش‌فرض است */
    enum { PC_START = 0x3000 };
    reg[R_PC] = PC_START;

    int running = 1;
    while (running)

        /* واکشی (FETCH) */
        uint16_t instr = mem_read(reg[R_PC]++);
        uint16_t op = instr >> 12;

        switch (op)
        {
            case OP_ADD:
                @{ADD}
                break;
            case OP_AND:
                @{AND}
                break;
            case OP_NOT:
                @{NOT}
                break;
            case OP_BR:
                @{BR}
                break;
            case OP_JMP:
                @{JMP}
                break;
            case OP_JSR:
                @{JSR}
                break;
            case OP_LD:
                @{LD}
                break;
            case OP_LDI:
                @{LDI}
                break;
            case OP_LDR:
                @{LDR}
                break;
            case OP_LEA:
                @{LEA}
                break;
            case OP_ST:
                @{ST}
                break;
            case OP_STI:

پیاده‌سازی دستورها

وظیفهٔ شما حالا این است که هر case از کدهای عملیات را با پیاده‌سازی درست پر کنید. این کار آسان‌تر از آن چیزی است که به نظر می‌رسد. مشخصات دقیق هر دستور در مستندات پروژه آمده است. مشخصات هر یک به‌راحتی به چند خط کد تبدیل می‌شود. من در این‌جا پیاده‌سازی دوتای آن‌ها را نشان می‌دهم. کد بقیه را در بخش بعدی پیدا خواهید کرد.

ADD (جمع)

دستور ADD دو عدد می‌گیرد، آن‌ها را با هم جمع می‌کند و نتیجه را در یک ثبات ذخیره می‌کند. مشخصات آن در صفحهٔ ۵۲۶ است. هر دستور ADD به این شکل است:

رمزگذاری دو ردیف را نشان می‌دهد، چون این دستور دو «حالت» (mode) مختلف دارد. قبل از اینکه حالت‌ها را توضیح دهم، بیایید شباهت‌های بین آن‌ها را پیدا کنیم. در هر دو ردیف می‌بینیم که با ۴ بیت، «0001» شروع می‌کنیم. این مقدار کد عملیات OP_ADD است. ۳ بیت بعدی با «DR» مشخص شده‌اند که مخفف ثبات مقصد (destination register) است. ثبات مقصد جایی است که حاصل جمع در آن ذخیره می‌شود. ۳ بیت بعدی «SR1» هستند؛ ثباتی که اولین عدد برای جمع را در خود دارد.

پس می‌دانیم نتیجه را کجا می‌خواهیم ذخیره کنیم و اولین عدد را برای جمع می‌دانیم. آخرین اطلاعات موردنیاز، دومین عدد برای جمع است. در این نقطه، دو ردیف متفاوت به نظر می‌رسند. توجه کنید در ردیف بالا بیت پنجم «0» است و در ردیف دوم «1». این بیت مشخص می‌کند که حالت مقدار مستقیم (immediate mode) است یا حالت ثبات (register mode). در حالت ثبات، دومین عدد درست مثل عدد اول در یک ثبات ذخیره می‌شود. این ثبات با «SR2» مشخص شده و در بیت‌های 0-2 قرار دارد. بیت‌های 3 و 4 استفاده نشده‌اند. در اسمبلی، این‌گونه نوشته می‌شود:

asmADD R2 R0 R1 ; محتویات R0 و R1 را با هم جمع کن و در R2 ذخیره کن.

حالت مقدار مستقیم (immediate mode) امکانی است که طول یک برنامهٔ معمولی را کاهش می‌دهد. به‌جای جمع دو مقداری که در دو ثبات جداگانه ذخیره شده‌اند، مقدار دوم در خود دستور جاسازی می‌شود؛ در نمودار با «imm5» مشخص شده است. این کار نیاز به نوشتن دستورهایی برای بارگذاری مقدار از حافظه را از بین می‌برد. هزینهٔ این کار این است که دستور فقط جا برای عدد کوچکی دارد؛ حداکثر 2^5=32 (بدون علامت) که حالت مستقیم را عمدتاً برای افزایش و کاهش (increment/decrement) مفید می‌کند. در اسمبلی می‌توان این‌گونه نوشت:

asmADD R0 R0 1 ; 1 را به R0 اضافه کن و دوباره در R0 ذخیره کن

در این‌جا خلاصه‌ای از مشخصات آمده است:

اگر بیت [5] برابر 0 باشد، عملوند منبع دوم از SR2 به دست می‌آید. اگر بیت [5] برابر 1 باشد، عملوند منبع دوم با بسط علامت (sign-extend) میدان imm5 به ۱۶ بیت به دست می‌آید. در هر دو حالت، عملوند منبع دوم به محتویات SR1 اضافه می‌شود و نتیجه در DR ذخیره می‌شود. (صفحه ۵۲۶)

این دقیقاً همان رفتاری است که درباره‌اش بحث کردیم، اما «بسط علامت» (sign extension) چیست؟ مقدار حالت مستقیم فقط ۵ بیت دارد، اما باید به یک عدد ۱۶ بیتی اضافه شود. برای انجام جمع، آن ۵ بیت باید به ۱۶ بیت گسترش یابند تا با عدد دیگر هم‌اندازه شوند. برای اعداد مثبت، به‌سادگی می‌توانیم بیت‌های اضافه را با 0 پر کنیم. برای اعداد منفی، این کار مشکل ایجاد می‌کند. برای مثال، 1- در ۵ بیت «1 1111» است. اگر فقط با 0 آن را گسترش دهیم، می‌شود «0000 0000 0001 1111» که برابر با 31 است. بسط علامت این مشکل را با پر کردن 0 برای اعداد مثبت و 1 برای اعداد منفی اصلاح می‌کند تا مقادیر اصلی حفظ شوند.

cuint16_t sign_extend(uint16_t x, int bit_count)
{
    if ((x >> (bit_count - 1)) & 1) {
        x |= (0xFFFF << bit_count);
    }
    return x;
}
توجه: اگر به این علاقه‌مندید که دقیقاً چطور می‌توان اعداد منفی را در باینری نمایش داد، دربارهٔ متمم دو (Two's Complement) بخوانید. با این حال، این موضوع ضروری نیست. می‌توانید کد بالا را کپی کنید و هر وقت مشخصات گفت عددها را بسط علامت بدهید، از آن استفاده کنید.

یک جملهٔ آخر در مشخصات هست:

کدهای وضعیت (condition codes) بر اساس اینکه نتیجه منفی، صفر یا مثبت است تنظیم می‌شوند. (صفحه ۵۲۶)

قبلاً enum نشان‌های وضعیت را تعریف کردیم و حالا وقت استفاده از آن‌هاست. هر بار که مقدار در ثباتی نوشته می‌شود، باید نشان‌ها را به‌روزرسانی کنیم تا علامت آن را نشان دهند. تابعی می‌نویسیم تا بتوان این کار را دوباره استفاده کرد:

cvoid update_flags(uint16_t r)
{
    if (reg[r] == 0)
    {
        reg[R_COND] = FL_ZRO;
    }
    else if (reg[r] >> 15) /* وجود 1 در چپ‌ترین بیت به معنای منفی بودن است */
    {
        reg[R_COND] = FL_NEG;
    }
    else
    {
        reg[R_COND] = FL_POS;
    }
}

حالا آماده‌ایم کد case مربوط به ADD را بنویسیم:

c{
    /* ثبات مقصد (DR) */
    uint16_t r0 = (instr >> 9) & 0x7;
    /* عملوند اول (SR1) */
    uint16_t r1 = (instr >> 6) & 0x7;
    /* اینکه در حالت مقدار مستقیم هستیم یا نه */
    uint16_t imm_flag = (instr >> 5) & 0x1;

    if (imm_flag)
    {
        uint16_t imm5 = sign_extend(instr & 0x1F, 5);
        reg[r0] = reg[r1] + imm5;
    }
    else
    {
        uint16_t r2 = instr & 0x7;
        reg[r0] = reg[r1] + reg[r2];
    }

    update_flags(r0);
}

این بخش اطلاعات زیادی داشت؛ بیایید خلاصه کنیم.

  • ADD دو مقدار می‌گیرد و آن‌ها را در یک ثبات ذخیره می‌کند.
  • در حالت ثبات، دومین مقدار برای جمع در یک ثبات پیدا می‌شود.
  • در حالت مقدار مستقیم، دومین مقدار در ۵ بیت سمت راستِ دستور جاسازی شده است.
  • مقادیری که کوتاه‌تر از ۱۶ بیت‌اند باید بسط علامت شوند.
  • هر بار که دستوری یک ثبات را تغییر می‌دهد، نشان‌های وضعیت باید به‌روزرسانی شوند.

ممکن است از نوشتن ۱۵ دستور دیگر احساس سردرگمی کنید. با این حال، همهٔ آنچه این‌جا یاد گرفتید دوباره استفاده خواهد شد. بیشتر دستورها از ترکیبی از بسط علامت، حالت‌های مختلف و به‌روزرسانی نشان‌ها استفاده می‌کنند.

LDI (بارگذاری غیرمستقیم)

LDI مخفف «load indirect» (بارگذاری غیرمستقیم) است. این دستور برای بارگذاری یک مقدار از یک مکان در حافظه به یک ثبات استفاده می‌شود. مشخصات آن در صفحهٔ ۵۳۲ است.

این هم چیدمان دودویی آن:

در مقایسه با ADD، هیچ حالتی نیست و پارامترهای کمتری دارد. این بار کد عملیات «1010» است که با مقدار enum OP_LDI مطابقت دارد. درست مثل ADD، شامل یک DR سه‌بیتی (ثبات مقصد) برای ذخیرهٔ مقدار بارگذاری‌شده است. بیت‌های باقی‌مانده با «PCoffset9» مشخص شده‌اند. این یک مقدار مستقیم جاسازی‌شده در دستور است (شبیه imm5). چون این دستور از حافظه بارگذاری می‌کند، می‌توانیم حدس بزنیم این عدد نوعی آدرس است که به ما می‌گوید از کجا بارگذاری کنیم. مشخصات جزئیات بیشتری ارائه می‌دهد:

آدرسی با بسط علامت بیت‌های `[8:0]` به ۱۶ بیت و افزودن این مقدار به PC افزایش‌یافته محاسبه می‌شود. آنچه در این آدرس در حافظه ذخیره شده، آدرس داده‌ای است که باید در DR بارگذاری شود. (صفحه ۵۳۲)

درست مثل قبل، باید این مقدار ۹ بیتی را بسط علامت بدهیم، اما این بار آن را به PC فعلی اضافه کنیم. (اگر به حلقهٔ اجرا برگردید، PC درست بعد از بارگذاری این دستور افزایش یافته بود.) حاصلِ جمع، آدرسی برای یک مکان در حافظه است و آن آدرس حاوی، باز هم، مقدار دیگری است که آدرس مقداری است که باید بارگذاری شود.

این ممکن است راهی غیرمستقیم برای خواندن از حافظه به نظر برسد، اما غیرقابل‌جایگزین است. دستور LD به آفست‌های آدرس ۹ بیتی محدود است، در حالی که حافظه برای آدرس‌دهی ۱۶ بیت لازم دارد. LDI برای بارگذاری مقادیری که در مکان‌های دور از PC فعلی ذخیره شده‌اند مفید است، اما برای استفاده از آن، آدرس مکان نهایی باید در همسایگی نزدیک ذخیره شده باشد. می‌توانید آن را مثل داشتن یک متغیر محلی در C در نظر بگیرید که اشاره‌گری به برخی داده‌هاست:

c// مقدار far_data یک آدرس است
// البته خود far_data (موقعیت حافظه‌ای که آدرس را در خود دارد) هم آدرسی دارد
char* far_data = "apple";

// در حافظه ممکن است این‌گونه چیده شده باشد:

// آدرس    برچسب      مقدار
// 0x123:  far_data = 0x456
// ...
// 0x456:  string   = 'a'

// اگر PC در 0x100 بود
// LDI R0 0x023
// مقدار 'a' را در R0 بارگذاری می‌کرد

مثل قبل، بعد از قرار دادن مقدار در DR باید نشان‌ها به‌روزرسانی شوند:

کدهای وضعیت بر اساس اینکه مقدار بارگذاری‌شده منفی، صفر یا مثبت است تنظیم می‌شوند. (صفحه ۵۳۲)

کد این case این است: (در بخش بعدی دربارهٔ mem_read بحث خواهیم کرد.)

c{
    /* ثبات مقصد (DR) */
    uint16_t r0 = (instr >> 9) & 0x7;
    /* PCoffset 9 */
    uint16_t pc_offset = sign_extend(instr & 0x1FF, 9);
    /* pc_offset را به PC فعلی اضافه کن؛ به آن مکان حافظه نگاه کن تا آدرس نهایی را به دست بیاوری */
    reg[r0] = mem_read(mem_read(reg[R_PC] + pc_offset));
    update_flags(r0);
}

همان‌طور که گفتم، این دستور بخش زیادی از کد و دانش آموخته‌شده از ADD را به اشتراک می‌گذارد. خواهید دید که دربارهٔ دستورهای باقی‌مانده نیز همین‌طور است.

حالا باید برگردید و بقیهٔ caseهای switch دستورها را پیاده‌سازی کنید. مشخصات را دنبال کنید و برای تکمیل بقیه از کدهایی که این‌جا آمده استفاده کنید. کد همهٔ دستورها در انتهای آموزش فهرست شده است. دو کد عملیاتی که قبلاً مشخص شدند استفاده نخواهند شد؛ آن‌ها OP_RTI و OP_RES هستند. می‌توانید این caseها را نادیده بگیرید یا اگر اجرا شدند خطا بدهید. بعد از اتمام، بخش عمدهٔ ماشین مجازی شما تکمیل خواهد شد!

}

روال‌های وقفه (Trap routines)

LC-3 چند روال از پیش تعریف‌شده برای انجام کارهای رایج و تعامل با دستگاه‌های ورودی/خروجی فراهم می‌کند. برای مثال، روال‌هایی برای دریافت ورودی از صفحه‌کلید و نمایش رشته‌ها در کنسول وجود دارد. به این‌ها روال‌های وقفه (trap routines) می‌گویند که می‌توانید آن‌ها را سیستم‌عامل یا API برای LC-3 در نظر بگیرید. به هر روال وقفه، یک کد وقفه (trap code) اختصاص داده شده که آن را شناسایی می‌کند (شبیه کد عملیات). برای اجرای یک روال، دستور TRAP با کد وقفهٔ روال موردنظر فراخوانی می‌شود.

برای هر کد وقفه یک enum تعریف کنید:

cenum
{
    TRAP_GETC = 0x20,  /* دریافت کاراکتر از صفحه‌کلید، بدون نمایش روی ترمینال */
    TRAP_OUT = 0x21,   /* خروجی یک کاراکتر */
    TRAP_PUTS = 0x22,  /* خروجی یک رشته کلمه‌ای */
    TRAP_IN = 0x23,    /* دریافت کاراکتر از صفحه‌کلید، با نمایش روی ترمینال */
    TRAP_PUTSP = 0x24, /* خروجی یک رشته بایتی */
    TRAP_HALT = 0x25   /* توقف برنامه */
};

ممکن است تعجب کنید چرا کدهای وقفه در دستورها گنجانده نشده‌اند. علتش این است که آن‌ها در واقع هیچ قابلیت جدیدی به LC-3 اضافه نمی‌کنند؛ فقط راهی راحت برای انجام یک کار فراهم می‌کنند (شبیه تماس‌های سیستمی سیستم‌عامل). در شبیه‌ساز رسمی LC-3، روال‌های وقفه به زبان اسمبلی نوشته شده‌اند. وقتی یک کد وقفه فراخوانی می‌شود، PC به آدرس آن کد منتقل می‌شود. CPU دستورهای آن روال را اجرا می‌کند و وقتی کامل شد، PC به موقعیت بعد از فراخوانی اولیه بازنشانی می‌شود.

توجه: به همین دلیل است که برنامه‌ها از آدرس 0x3000 شروع می‌شوند، نه 0x0. آدرس‌های پایین‌تر خالی می‌مانند تا برای کد روال‌های وقفه جا باز بماند.

مشخصاتی برای نحوهٔ پیاده‌سازی روال‌های وقفه وجود ندارد؛ فقط مشخص می‌کند آن‌ها قرار است چه کاری انجام دهند. در ماشین مجازی ما، کارها را کمی متفاوت انجام می‌دهیم و آن‌ها را به زبان C می‌نویسیم. وقتی کد وقفه‌ای فراخوانی می‌شود، تابعی C صدا زده می‌شود. وقتی تمام شد، اجرا به دستورها بازمی‌گردد. (اگر دربارهٔ کدهای وقفه در اسمبلی کنجکاوید، پیاده‌سازی رایان را ببینید.)

حتی اگر روال‌های وقفه را می‌توان به زبان اسمبلی نوشت و این کاری است که کامپیوتر فیزیکی LC-3 انجام می‌دهد، برای یک ماشین مجازی بهترین گزینه نیست. به‌جای نوشتن روال‌های ورودی/خروجی ابتدایی خودمان، می‌توانیم از آن‌هایی که سیستم‌عامل ما در اختیار دارد استفاده کنیم. این کار ماشین مجازی را بهتر روی کامپیوترهای ما اجرا می‌کند، کد را ساده‌تر می‌کند و سطح انتزاع بالاتری برای قابلیت انتقال فراهم می‌کند.

توجه: دریافت ورودی از صفحه‌کلید یکی از نمونه‌های مشخص این موضوع است. نسخهٔ اسمبلی از حلقه‌ای استفاده می‌کند که مدام صفحه‌کلید را برای ورودی بررسی می‌کند. این کار زمان CPU زیادی را بیهوده مصرف می‌کند! استفاده از یک تابع ورودی صحیح سیستم‌عامل به برنامه اجازه می‌دهد تا زمانی که ورودی دریافت نشده، بخوابد.

در case مربوط به کد عملیات TRAP، یک switch دیگر اضافه کنید:

creg[R_R7] = reg[R_PC];

switch (instr & 0xFF)
{
    case TRAP_GETC:
        @{TRAP GETC}
        break;
    case TRAP_OUT:
        @{TRAP OUT}
        break;
    case TRAP_PUTS:
        @{TRAP PUTS}
        break;
    case TRAP_IN:
        @{TRAP IN}
        break;
    case TRAP_PUTSP:
        @{TRAP PUTSP}
        break;
    case TRAP_HALT:
        @{TRAP HALT}
        break;
}

درست مثل دستورها، پیاده‌سازی یک روال وقفه را به شما نشان می‌دهم و بقیه را به خودتان واگذار می‌کنم.

PUTS

کد وقفهٔ PUTS برای خروجی یک رشتهٔ با پایان null (شبیه printf در C) استفاده می‌شود. مشخصات آن در صفحهٔ ۵۴۳ است.

برای نمایش یک رشته، باید به روال وقفه رشته‌ای برای نمایش بدهیم. این کار با ذخیرهٔ آدرس اولین کاراکتر در R0 قبل از شروع روال انجام می‌شود.

مشخصات می‌گوید:

رشته‌ای از کاراکترهای ASCII را در نمایشگر کنسول بنویس. کاراکترها در مکان‌های حافظهٔ پشت‌سرهم قرار دارند، در هر مکان حافظه یک کاراکتر، که از آدرس مشخص‌شده در R0 شروع می‌شود. نوشتن با وقوع x0000 در یک مکان حافظه پایان می‌یابد. (صفحه ۵۴۳)

توجه کنید که برخلاف رشته‌های C، کاراکترها در یک بایت تکی ذخیره نمی‌شوند، بلکه در یک مکان حافظهٔ تکی ذخیره می‌شوند. مکان‌های حافظه در LC-3 ۱۶ بیتی‌اند، پس هر کاراکتر در رشته ۱۶ بیت عرض دارد. برای نمایش این با یک تابع C، باید هر مقدار را به یک char تبدیل کنیم و آن‌ها را یکی‌یکی خروجی بدهیم.

c{
    /* در هر کلمه یک کاراکتر */
    uint16_t* c = memory + reg[R_R0];
    while (*c)
    {
        putc((char)*c, stdout);
        ++c;
    }
    fflush(stdout);
}

همین برای این روال کافی است. اگر با C آشنا باشید، روال‌های وقفه کاملاً سرراست‌اند. به مشخصات برگردید و بقیه را حالا پیاده‌سازی کنید. درست مثل دستورها، کد کامل را در انتهای آموزش پیدا خواهید کرد.

بارگذاری برنامه‌ها

ما خیلی دربارهٔ بارگذاری و اجرای دستورها از حافظه صحبت کرده‌ایم، اما دستورها اصلاً اولِ کار چگونه وارد حافظه می‌شوند؟ وقتی یک برنامهٔ اسمبلی به کد ماشین تبدیل می‌شود، نتیجه فایلی شامل آرایه‌ای از دستورها و داده‌هاست. این فایل را می‌توان با کپی کردن محتویات مستقیم در یک آدرس از حافظه بارگذاری کرد.

۱۶ بیت اول فایل برنامه، آدرس حافظه‌ای را مشخص می‌کند که برنامه باید از آنجا شروع شود. به این آدرس مبدأ (origin) می‌گویند. باید اول خوانده شود و بعد از آن، بقیهٔ داده‌ها را می‌توان از فایل در حافظه، از آدرس مبدأ شروع کرد.

کد خواندن یک برنامهٔ LC-3 در حافظه این است:

cvoid read_image_file(FILE* file)
{
    /* origin به ما می‌گوید که تصویر را کجا در حافظه قرار دهیم */
    uint16_t origin;
    fread(&origin, sizeof(origin), 1, file);
    origin = swap16(origin);

    /* حداکثر اندازه فایل را می‌دانیم، پس فقط به یک fread نیاز داریم */
    uint16_t max_read = MEMORY_MAX - origin;
    uint16_t* p = memory + origin;
    size_t read = fread(p, sizeof(uint16_t), max_read, file);

    /* تبدیل به little endian */
    while (read-- > 0)
    {
        *p = swap16(*p);
        ++p;
    }
}

توجه کنید که روی هر مقدار بارگذاری‌شده swap16 صدا زده می‌شود. برنامه‌های LC-3 big-endian هستند، اما بیشتر کامپیوترهای مدرن little-endian هستند. پس باید هر uint16 بارگذاری‌شده را جابه‌جا کنیم. (اگر اتفاقاً از کامپیوتر عجیبی استفاده می‌کنید، مثلاً یک PPC مک قدیمی، جابه‌جا نکنید.)

cuint16_t swap16(uint16_t x)
{
    return (x << 8) | (x >> 8);
}
توجه: ترتیب بایت‌ها (Endianness) به نحوهٔ تفسیر بایت‌های یک عدد صحیح اشاره دارد. در little-endian، اولین بایت کم‌ارزش‌ترین رقم است و در big-endian برعکس است. تا جایی که می‌دانم، این تصمیم بیشتر دلبخواهانه است. شرکت‌های مختلف تصمیم‌های متفاوتی گرفتند، پس حالا با پیاده‌سازی‌های متغیری روبه‌روییم. برای این پروژه لازم نیست چیز دیگری دربارهٔ ترتیب بایت‌ها بدانید.

همچنین یک تابع کمکی برای read_image_file اضافه کنیم که مسیر را به‌صورت رشته می‌گیرد:

cint read_image(const char* image_path)
{
    FILE* file = fopen(image_path, "rb");
    if (!file) { return 0; };
    read_image_file(file);
    fclose(file);
    return 1;
}

ثبات‌های نگاشت‌شده به حافظه (Memory mapped registers)

برخی ثبات‌های خاص از جدول ثبات‌های معمولی قابل دسترسی نیستند. به‌جای آن، آدرس خاصی برای آن‌ها در حافظه رزرو شده است. برای خواندن و نوشتن در این ثبات‌ها، فقط در مکان حافظهٔ آن‌ها می‌خوانید و می‌نویسید. به این‌ها ثبات‌های نگاشت‌شده به حافظه (memory mapped registers) می‌گویند. معمولاً برای تعامل با دستگاه‌های سخت‌افزاری خاص استفاده می‌شوند.

LC-3 دو ثبات نگاشت‌شده به حافظه دارد که باید پیاده‌سازی شوند: ثبات وضعیت صفحه‌کلید (KBSR) و ثبات دادهٔ صفحه‌کلید (KBDR). KBSR نشان می‌دهد که آیا کلیدی فشار داده شده است و KBDR مشخص می‌کند کدام کلید فشار داده شده است.

اگرچه می‌توانید ورودی صفحه‌کلید را با GETC درخواست کنید، این کار اجرا را تا دریافت ورودی مسدود می‌کند. KBSR و KBDR به شما اجازه می‌دهند وضعیت دستگاه را نظرسنجی (poll) کنید و اجرا را ادامه دهید؛ بنابراین برنامه می‌تواند در حالی که منتظر ورودی است پاسخگو بماند.

cenum
{
    MR_KBSR = 0xFE00, /* وضعیت صفحه‌کلید */
    MR_KBDR = 0xFE02  /* داده صفحه‌کلید */
};

ثبات‌های نگاشت‌شده به حافظه، دسترسی به حافظه را کمی پیچیده‌تر می‌کنند. دیگر نمی‌توانیم مستقیم در آرایهٔ حافظه بخوانیم و بنویسیم، بلکه باید توابع setter و getter را صدا بزنیم. وقتی حافظه از KBSR خوانده می‌شود، getter صفحه‌کلید را بررسی می‌کند و هر دو مکان حافظه را به‌روزرسانی می‌کند.

cvoid mem_write(uint16_t address, uint16_t val)
{
    memory[address] = val;
}

uint16_t mem_read(uint16_t address)
{
    if (address == MR_KBSR)
    {
        if (check_key())
        {
            memory[MR_KBSR] = (1 << 15);
            memory[MR_KBDR] = getchar();
        }
        else
        {
            memory[MR_KBSR] = 0;
        }
    }
    return memory[address];
}

با این کار آخرین جزء ماشین مجازی تکمیل شد! به شرطی که بقیهٔ روال‌های وقفه و دستورها را پیاده‌سازی کرده باشید، تقریباً آماده‌اید آن را امتحان کنید!

اشکال‌زدایی (Debugging)

اگر برنامه درست کار نمی‌کند، احتمالاً به این دلیل است که یکی از دستورها را اشتباه برنامه‌نویسی کرده‌اید. این کار می‌تواند برای اشکال‌زدایی مشکل‌ساز باشد. توصیه می‌کنم هم‌زمان کد منبع اسمبلی یک برنامهٔ LC-3 را بخوانید و با یک اشکال‌زدا (debugger) دستورهای ماشین مجازی را یکی‌یکی step کنید. همان‌طور که اسمبلی را می‌خوانید، مطمئن شوید ماشین مجازی به دستوری می‌رود که انتظارش را دارید. اگر ناهماهنگی رخ داد، می‌دانید کدام دستور مشکل را ایجاد کرده است. مشخصاتش را دوباره بخوانید و کدتان را دوباره بررسی کنید.

تکنیک جایگزین C++

این‌جا راه پیشرفته‌ای برای سازمان‌دهی دستورها داریم که کد را بسیار کوتاه‌تر می‌کند. این بخش کاملاً اختیاری است.

احتمالاً متوجه شده‌اید که بیشتر دستورها کارهای مشابهی را تکرار می‌کنند. مثلاً برخی از آدرس‌دهی غیرمستقیم استفاده می‌کنند یا مقداری را بسط علامت می‌دهند و به مقدار PC فعلی اضافه می‌کنند. خوب نبود اگر می‌توانستیم این کد را فقط یک بار برای همه بنویسیم؟

قسمت مشکل‌ساز این است که مشخص نیست چگونه این تکرار را در توابع اضافی فشرده کنیم، چون آن‌ها به بافت اطراف نیاز دارند. اما کاری که می‌توانیم انجام دهیم، استفاده از قدرت genericهای C++ برای به هم دوختن تکه‌های قابلیت در زمان کامپایل است. ایده این است که اجرای دستور را به‌عنوان خط لوله‌ای (pipeline) از مراحل پردازشِ کوچک‌تر در نظر بگیریم. هر نوع دستور فقط زیرمجموعه‌ای یا «ترتیب‌بندی» (permutation) از مراحل موجود است.

این کار را با استفاده از نشان‌های بیتی پیاده‌سازی می‌کنیم. وجود 1 در بیتی که با شمارهٔ دستور مطابقت دارد، به کامپایلر می‌گوید این بخش کد را برای آن دستور در نظر بگیرد؛ و 0 یعنی آن را کنار بگذارد.

cpptemplate <unsigned op>
void ins(uint16_t instr)
{
    uint16_t r0, r1, r2, imm5, imm_flag;
    uint16_t pc_plus_off, base_plus_off;

    constexpr uint16_t opbit = (1 << op);
    if (0x4EEE & opbit) { r0 = (instr >> 9) & 0x7; }
    if (0x12F3 & opbit) { r1 = (instr >> 6) & 0x7; }
    if (0x0022 & opbit)
    {
        imm_flag = (instr >> 5) & 0x1;

        if (imm_flag)
        {
            imm5 = sign_extend(instr & 0x1F, 5);
        }
        else
        {
            r2 = instr & 0x7;
        }
    }
    if (0x00C0 & opbit)
    {   // Base + offset  (پایه + آفست)
        base_plus_off = reg[r1] + sign_extend(instr & 0x3F, 6);
    }
    if (0x4C0D & opbit)
    {
        // Indirect address  (آدرس غیرمستقیم)
        pc_plus_off = reg[R_PC] + sign_extend(instr & 0x1FF, 9);
    }
    if (0x0001 & opbit)
    {
        // BR  (پرش شرطی)
        uint16_t cond = (instr >> 9) & 0x7;
        if (cond & reg[R_COND]) { reg[R_PC] = pc_plus_off; }
    }
    if (0x0002 & opbit)  // ADD  (جمع)
    {
        if (imm_flag)
        {
            reg[r0] = reg[r1] + imm5;
        }
        else
        {
            reg[r0] = reg[r1] + reg[r2];
        }
    }
    if (0x0020 & opbit)  // AND  (و بیتی)
    {
        if (imm_flag)
        {
            reg[r0] = reg[r1] & imm5;
        }
        else
        {
            reg[r0] = reg[r1] & reg[r2];
        }
    }
    if (0x0200 & opbit) { reg[r0] = ~reg[r1]; } // NOT  (نقیض بیتی)
    if (0x1000 & opbit) { reg[R_PC] = reg[r1]; } // JMP  (پرش)
    if (0x0010 & opbit)  // JSR  (پرش به زیرروال)
    {
        uint16_t long_flag = (instr >> 11) & 1;
        reg[R_R7] = reg[R_PC];
        if (long_flag)
        {
            pc_plus_off = reg[R_PC] + sign_extend(instr & 0x7FF, 11);
            reg[R_PC] = pc_plus_off;
        }
        else
        {
            reg[R_PC] = reg[r1];
        }
    }

    if (0x0004 & opbit) { reg[r0] = mem_read(pc_plus_off); } // LD  (بارگذاری)
    if (0x0400 & opbit) { reg[r0] = mem_read(mem_read(pc_plus_off)); } // LDI  (بارگذاری غیرمستقیم)
    if (0x0040 & opbit) { reg[r0] = mem_read(base_plus_off); }  // LDR  (بارگذاری از طریق ثبات)
    if (0x4000 & opbit) { reg[r0] = pc_plus_off; } // LEA  (بارگذاری آدرس مؤثر)
    if (0x0008 & opbit) { mem_write(pc_plus_off, reg[r0]); } // ST  (ذخیره)
    if (0x0800 & opbit) { mem_write(mem_read(pc_plus_off), reg[r0]); } // STI  (ذخیره غیرمستقیم)
    if (0x0080 & opbit) { mem_write(base_plus_off, reg[r0]); } // STR  (ذخیره از طریق ثبات)
    if (0x8000 & opbit)  // TRAP  (روال وقفه)
    {
         @{TRAP}
    }
    //if (0x0100 & opbit) { } // RTI
    if (0x4666 & opbit) { update_flags(r0); }
}
