مقدمه

مقالۀ «Scalachain» یک بلاک‌چین است که با زبان برنامه‌نویسی اسکالا (Scala) و مدل بازیگر (Actor Model) و با استفاده از چارچوب Akka ساخته شده است.

در این مقاله، فرایند توسعه‌ای را نشان خواهم داد که با آن این نمونهٔ اولیهٔ ساده از یک بلاک‌چین ساخته شد. این یعنی پروژه کامل و بی‌نقص نیست و ممکن است پیاده‌سازی‌های بهتری هم وجود داشته باشد. به همین دلیل هرگونه مشارکت — چه یک پیشنهاد باشد، چه یک درخواست Pull Request روی مخزن گیت‌هاب — بسیار خوش‌آمد است! :-)

بیایید با یک معرفی کوتاه از بلاک‌چین شروع کنیم. پس از آن، مدل ساده‌شده‌ای را تعریف می‌کنیم که پیاده‌سازی خواهیم کرد.

معرفی سریع بلاک‌چین

مقالات خوب زیادی وجود دارند که نحوهٔ کار بلاک‌چین را توضیح می‌دهند؛ بنابراین من فقط یک معرفی سطح بالا انجام می‌دهم تا بستری برای این پروژه فراهم شود.

بلاک‌چین یک دفتر کل توزیع‌شده (distributed ledger) است: انتقال برخی ارزش‌ها (مثل سکه‌ها) را بین یک فرستنده و یک گیرنده ثبت می‌کند. چیزی که بلاک‌چین را از یک پایگاه دادهٔ سنتی متمایز می‌کند، ماهیت غیرمتمرکز آن است: بلاک‌چین میان چندین گره (node) ارتباطی توزیع شده است که اعتبار تراکنش‌های ثبت‌شده را تضمین می‌کنند.

بلاک‌چین تراکنش‌ها را در بلاک‌هایی ذخیره می‌کند که توسط گره‌ها و با سرمایه‌گذاری توان محاسباتی ساخته می‌شوند — می‌گوییم استخراج می‌شوند (mined). هر بلاک با حل کردن یک معما‌ی رمزنگاری ساخته می‌شود که حل کردن آن سخت اما راستی‌آزمایی آن آسان است. به این ترتیب، هر بلاک بیانگر کار لازم برای حل چنین معمایی است. به همین دلیل است که این معما‌ی رمزنگاری اثبات کار (Proof of Work) نامیده می‌شود: راه‌حل معما، اثباتی است بر اینکه یک گره مقدار مشخصی کار صرف حل آن و استخراج بلاک کرده است.

چرا گره‌ها توان محاسباتی برای استخراج یک بلاک سرمایه‌گذاری می‌کنند؟ چون ساخت یک بلاک جدید با مقدار ازپیش‌تعیین‌شده‌ای از سکه پاداش داده می‌شود. به این ترتیب گره‌ها تشویق می‌شوند بلاک‌های جدیدی استخراج کنند و به رشد و استحکام بلاک‌چین کمک کنند.

بلاک‌چین ساده

راه‌حل اثبات کار به مقادیر ذخیره‌شده در آخرین بلاکِ استخراج‌شده وابسته است. به این ترتیب، هر بلاک به بلاک قبلی زنجیر می‌شود. این یعنی برای تغییر یک بلاکِ استخراج‌شده، یک گره باید همهٔ بلاک‌های بالای بلاکِ تغییرداده‌شده را دوباره استخراج کند. ازآنجاکه هر بلاک مقدار مشخصی کار را نشان می‌دهد، این عملیات زمانی که چند بلاک روی بلاکِ تغییرداده‌شده استخراج شده باشند، غیرعملی خواهد بود. این بنیان اجماع توزیع‌شده (distributed consensus) است؛ یعنی توافق همهٔ گره‌ها بر اعتبار بلاک‌های (یعنی تراکنش‌های) ذخیره‌شده در بلاک‌چین.

ممکن است گره‌های مختلف هم‌زمان یک بلاک را استخراج کنند و «شاخه‌های» متفاوتی از همان بلاک‌چین ایجاد کنند — به این وضعیت در بلاک‌چین انشعاب (fork) می‌گویند. این وضعیت وقتی حل می‌شود که یک شاخه از بقیه بلندتر شود: زنجیرهٔ بلندتر همیشه برنده است؛ پس شاخهٔ برنده به بلاک‌چین جدید تبدیل می‌شود.

مدل بلاک‌چین

Scalachain بر پایهٔ مدلی از بلاک‌چین است که ساده‌سازی مدل بیت‌کوین است.

اجزای اصلی مدل بلاک‌چین ما عبارت‌اند از: تراکنش (Transaction)، زنجیره (Chain)، الگوریتم اثبات کار (PoW) و گره (Node). تراکنش‌ها داخل بلاک‌های زنجیره ذخیره می‌شوند و با استفاده از PoW استخراج می‌گردند. گره، سروری است که بلاک‌چین را اجرا می‌کند.

مدل Scalachain

تراکنش (Transaction)

تراکنش‌ها جابه‌جایی سکه‌ها را بین دو نهاد ثبت می‌کنند. هر تراکنش از یک فرستنده، یک گیرنده و مقدار سکه تشکیل شده است. تراکنش‌ها داخل بلاک‌های بلاک‌چین ما ثبت خواهند شد.

زنجیره (Chain)

زنجیره یک لیست پیوندی از بلاک‌هاست که فهرستی از تراکنش‌ها را در خود دارد. هر بلاک از زنجیره دارای یک ایندکس (index)، اثباتِ اعتباردهنده (بعداً بیشتر در این باره)، فهرست تراکنش‌ها، هش بلاک قبلی، فهرست بلاک‌های قبلی و یک برچسب زمانی (timestamp) است. هر بلاک با هش خودش به بلاک قبلی زنجیر می‌شود؛ هش با تبدیل بلاک به یک رشتهٔ JSON و سپس هش کردن آن با تابع هش SHA-256 محاسبه می‌شود.

اثبات کار (PoW)

الگوریتم PoW برای استخراج بلاک‌های تشکیل‌دهندهٔ بلاک‌چین لازم است. ایده این است که معما‌ی رمزنگاری‌ای حل شود که حل آن سخت، اما راستی‌آزمایی آن با داشتنِ اثبات، آسان باشد. الگوریتم PoW پیاده‌سازی‌شده در Scalachain مشابه الگوریتم بیت‌کوین است (مبتنی بر Hashcash). این الگوریتم عبارت است از یافتن هشی با N صفرِ ابتدایی که از هش آخرین بلاک و یک عدد — که همان اثبات الگوریتم ماست — محاسبه می‌شود.

می‌توانیم آن را این‌گونه صورتبندی کنیم:

textNzerosHash = SHA-256(previousNodeHash + proof)

هرچه N بزرگ‌تر باشد، یافتن اثبات سخت‌تر است. در Scalachain مقدار N برابر ۴ است (در نهایت قابل تنظیم خواهد بود).

گره (Node)

گره، سروری است که بلاک‌چین ما را اجرا می‌کند. گره تعدادی REST API در اختیار می‌گذارد تا با آن تعامل کنیم و عملیات پایه‌ای مانند ارسال تراکنش جدید، دریافت فهرست تراکنش‌های معلق، استخراج یک بلاک و دریافت وضعیت فعلی بلاک‌چین را انجام دهیم.

پیاده‌سازی بلاک‌چین در اسکالا

قصد داریم مدل تعریف‌شده را با زبان برنامه‌نویسی اسکالا پیاده‌سازی کنیم. از دیدگاهی سطح بالا، چیزهایی که برای پیاده‌سازی یک بلاک‌چین لازم داریم عبارت‌اند از:

  • تراکنش‌ها
  • زنجیره‌ای از بلاک‌ها شامل فهرست‌هایی از تراکنش‌ها
  • الگوریتم PoW برای استخراج بلاک‌های جدید

این اجزا بخش‌های ضروری یک بلاک‌چین هستند.

تراکنش

تراکنش یک شیء بسیار ساده است: یک فرستنده، یک گیرنده و یک مقدار دارد. می‌توانیم آن را به‌صورت یک case class ساده پیاده‌سازی کنیم.

scalacase class Transaction(sender: String, recipient: String, value: Long)

زنجیره

زنجیره قلب بلاک‌چین ماست: یک لیست پیوندی از بلاک‌هاست که تراکنش‌ها را در خود دارد.

scalasealed trait Chain {

  val index: Int
  val hash: String
  val values: List[Transaction]
  val proof: Long
  val timestamp: Long
}

ما با ایجاد یک sealed trait شروع می‌کنیم که بلاک زنجیرهٔ ما را نشان می‌دهد. Chain می‌تواند دو نوع داشته باشد: یک EmptyChain یا یک ChainLink. نوع اول، بلاک صفرِ ما (بلاک آغازین یا genesis block) است و به‌صورت یک تابع‌مفرد (singleton) پیاده‌سازی می‌شود (یک case object)، در حالی که نوع دوم یک بلاک معمولی استخراج‌شده است.

scalacase class ChainLink(index: Int, proof: Long, values: List[Transaction], previousHash: String = "", tail: Chain = EmptyChain, timestamp: Long = System.currentTimeMillis()) extends Chain {
  val hash = Crypto.sha256Hash(this.toJson.toString)
}

case object EmptyChain extends Chain {
  val index = 0
  val hash = "1"
  val values = Nil
  val proof = 100L
  val timestamp = System.currentTimeMillis()
}

بیایید دقیق‌تر به زنجیرهٔ خود نگاه کنیم. این زنجیره یک ایندکس فراهم می‌کند که ارتفاع فعلی بلاک‌چین است. فهرست Transaction، اثباتِ اعتباردهندهٔ بلاک و برچسب زمانی ساخت بلاک وجود دارد. مقدار هش در EmptyChain روی یک مقدار پیش‌فرض قرار می‌گیرد، در حالی که در ChainLink با تبدیل شیء به نمایش JSON آن و هش کردنش با یک تابع کمکی محاسبه می‌شود (پکیج crypto را در مخزن ببینید). ChainLink همچنین هش بلاک قبلی در زنجیره (حلقهٔ اتصال ما بین بلاک‌ها) را فراهم می‌کند. فیلد tail ارجاعی به بلاک‌های قبلی‌استخراج‌شده است. این شاید کارآمدترین راه‌حل نباشد، اما برای دیدن اینکه بلاک‌چین در پیاده‌سازی ساده‌شدهٔ ما چگونه رشد می‌کند مفید است.

می‌توانیم Chain خود را با چند ابزار بهبود دهیم. می‌توانیم یک شیء همراه (companion object) به آن اضافه کنیم که یک متد apply برای ساخت یک زنجیرهٔ جدید با دریافت فهرستی از بلاک‌ها تعریف می‌کند. شیء همراه مثل یک «مجموعه متدهای استاتیک» است — برای تشبیه با جاوا — که به میدان‌ها و متدهای کلاس/صفت دسترسی کامل دارد.

scalaobject Chain {
  def apply[T](b: Chain*): Chain = {
    if (b.isEmpty) EmptyChain
    else {
      val link = b.head.asInstanceOf[ChainLink]
      ChainLink(link.index, link.proof, link.values, link.previousHash, apply(b.tail: _*))
    }
  }
}

اگر فهرست بلاک‌ها خالی باشد، به‌سادگی بلاک‌چین خود را با یک EmptyChain مقداردهی می‌کنیم. در غیر این صورت یک ChainLink جدید می‌سازیم و نتیجهٔ متد apply روی بلاک‌های باقی‌ماندهٔ فهرست را به‌عنوان tail اضافه می‌کنیم. به این ترتیب فهرست بلاک‌ها به ترتیب خود فهرست اضافه می‌شود.

خوب است که امکان اضافه‌کردن یک بلاک جدید به زنجیره را با یک عملگر جمع سادهٔ الحاقی داشته باشیم، مثل عملگری که روی List داریم. می‌توانیم عملگر الحاقی خودمان یعنی :: را داخل صفت Chain تعریف کنیم.

scalasealed trait Chain {

  val index: Int
  val hash: String
  val values: List[Transaction]
  val proof: Long
  val timestamp: Long

  def ::(link: Chain): Chain = link match {
    case l:ChainLink => ChainLink(l.index, l.proof, l.values, this.hash, this)
    case _ => throw new InvalidParameterException("Cannot add invalid link to chain")
  }
}

روی بلاکی که به‌عنوان آرگومان داده می‌شود تطبیق الگو (pattern match) انجام می‌دهیم: اگر یک شیء معتبر ChainLink باشد، آن را به‌عنوان سر زنجیرهٔ خود اضافه می‌کنیم و زنجیره را به‌عنوان tail بلاک جدید قرار می‌دهیم؛ در غیر این صورت یک استثنا پرتاب می‌کنیم.

اثبات کار (PoW)

الگوریتم PoW برای استخراج بلاک‌های جدید اساسی است. آن را به‌صورت یک الگوریتم ساده پیاده‌سازی می‌کنیم:

  1. هش آخرین بلاک و عددی را که نمایانگر اثبات است بردار.
  2. هش و اثبات را در یک رشته با هم ادغام کن.
  3. رشتهٔ حاصل را با الگوریتم SHA-256 هش کن.
  4. ۴ کاراکتر ابتدایی هش را بررسی کن: اگر چهار صفر بودند، اثبات را برگردان.
  5. در غیر این صورت الگوریتم را با افزایش اثبات به‌اندازهٔ یک تکرار کن.

این ساده‌سازی الگوریتم HashCash است که در بلاک‌چین بیت‌کوین استفاده می‌شود.

ازآنجاکه یک تابع بازگشتی است، می‌توانیم آن را به‌صورت یک تابع بازگشتی دُمی (tail recursive) پیاده‌سازی کنیم تا استفاده از منابع را بهبود دهیم.

scalaobject ProofOfWork {

  def proofOfWork(lastHash: String): Long = {
    @tailrec
    def powHelper(lastHash: String, proof: Long): Long = {
      if (validProof(lastHash, proof))
        proof
      else
        powHelper(lastHash, proof + 1)
    }

    val proof = 0
    powHelper(lastHash, proof)
  }

  def validProof(lastHash: String, proof: Long): Boolean = {
    val guess = (lastHash ++ proof.toString).toJson.toString
    val guessHash = Crypto.sha256Hash(guess)
    (guessHash take 4) == "0000"
  }
}

تابع validProof برای بررسی اینکه اثباتِ در حال آزمون، اثبات درست است یا نه به کار می‌رود. تابع powHelper یک تابع کمکی است که حلقهٔ ما را با استفاده از بازگشت دُمی اجرا می‌کند و در هر گام اثبات را افزایش می‌دهد. تابع proofOfWork همه‌چیز را در بر می‌گیرد و توسط شیء ProofOfWork در معرض دید قرار می‌گیرد.

مدل بازیگر

مدل بازیگر یک مدل برنامه‌نویسی است که برای پردازش هم‌روند (concurrent processing)، مقیاس‌پذیری (scalability) و تحمل خطا (fault tolerance) طراحی شده است. این مدل عناصر اتمیِ سازندهٔ سیستم‌های نرم‌افزاری — یعنی بازیگرها (actors) — و نحوهٔ تعامل این عناصر با یکدیگر را تعریف می‌کند. در این پروژه از مدل بازیگری استفاده می‌کنیم که توسط چارچوب Akka در اسکالا پیاده‌سازی شده است.

مدل بازیگر

بازیگر (Actor)

بازیگر واحد اتمی مدل بازیگر است. این یک واحد محاسباتی است که می‌تواند پیام ارسال و دریافت کند. هر بازیگر یک وضعیت داخلی خصوصی و یک صندوق پیام (mailbox) دارد. وقتی یک بازیگر پیامی دریافت و پردازش می‌کند، می‌تواند به سه شکل واکنش نشان دهد:

  • پیامی به بازیگر دیگری بفرستد.
  • وضعیت داخلی خود را تغییر دهد.
  • بازیگر دیگری بسازد.

ارتباطات ناهمگام (asynchronous) است و پیام‌ها از صندوق پیام خارج و به‌صورت متوالی پردازش می‌شوند. برای امکان‌پذیر کردن محاسبهٔ موازی پیام‌ها باید چندین بازیگر بسازید. بسیاری از بازیگرها با هم یک سیستم بازیگر (actor system) تشکیل می‌دهند. رفتار برنامه از تعامل بین بازیگرهایی که قابلیت‌های متفاوتی فراهم می‌کنند، پدید می‌آید.

بازیگرها مستقل هستند

بازیگرها مستقل از یکدیگرند و وضعیت داخلی خود را به اشتراک نمی‌گذارند. این واقعیت دو پیامد مهم دارد:

  1. بازیگرها می‌توانند پیام‌ها را بدون اثر جانبی (side-effect) نسبت به یکدیگر پردازش کنند.
  2. مهم نیست بازیگر کجاست — روی لپ‌تاپ شما باشد، روی یک سرور یا در ابر — تا زمانی که آدرس آن را بدانیم، با فرستادن یک پیام می‌توانیم از سرویسش درخواست کنیم.

نکتهٔ اول محاسبهٔ هم‌روند را بسیار آسان می‌کند. می‌توانیم مطمئن باشیم پردازش یک پیام در پردازش پیام دیگری دخالت نمی‌کند. برای دستیابی به پردازش هم‌روند می‌توانیم چندین بازیگر مستقر کنیم که قادر به پردازش همان نوع پیام هستند.

نکتهٔ دوم کاملاً دربارهٔ مقیاس‌پذیری است: توان محاسباتی بیشتری لازم داریم؟ مشکلی نیست: می‌توانیم یک ماشین جدید راه بیندازیم و بازیگرهای جدیدی مستقر کنیم که به سیستم بازیگر موجود ملحق می‌شوند. آدرس صندوق پیام آن‌ها توسط بازیگرهای موجود قابل کشف خواهد بود و آن‌ها شروع به ارتباط با بازیگرهای جدید می‌کنند.

بازیگرها تحت نظارت هستند

همان‌طور که در توصیف بازیگر گفتیم، یکی از واکنش‌های ممکن به یک پیام، ایجاد بازیگرهای دیگر است. در این حالت، والد، ناظر (supervisor) فرزندانش می‌شود. اگر یک فرزند از کار بیفتد، ناظر می‌تواند تصمیم بگیرد چه اقدامی انجام دهد؛ چه بسا ایجاد یک بازیگر جدید، نادیده‌گرفتن خطا، یا انتقال آن به ناظر خودش. به این ترتیب سیستم بازیگر به یک درخت سلسله‌مراتبی تبدیل می‌شود که هر گره بر فرزندانش نظارت می‌کند. این همان راهی است که مدل بازیگر تحمل خطا فراهم می‌کند.

سلسله‌مراتب بازیگرها

کارگزار (Broker)، یک بازیگر ساده

اولین بازیگری که پیاده‌سازی می‌کنیم بازیگر کارگزار (Broker Actor) است: این بازیگر مدیر تراکنش‌های بلاک‌چین ما است. مسئولیت‌هایش عبارت‌اند از افزودن تراکنش‌های جدید و بازیابی تراکنش‌های معلق (pending).

بازیگر کارگزار به سه نوع پیام واکنش نشان می‌دهد که در شیء همراه (companion object) کلاس Broker تعریف شده‌اند:

scalaobject Broker {
  sealed trait BrokerMessage
  case class AddTransaction(transaction: Transaction) extends BrokerMessage
  case object GetTransactions extends BrokerMessage
  case object Clear extends BrokerMessage

  val props: Props = Props(new Broker)
}

یک صفت BrokerMessage می‌سازیم تا پیام‌های بازیگر کارگزار را شناسایی کنیم. همهٔ پیام‌های دیگر این صفت را گسترش می‌دهند. AddTransaction یک تراکنش جدید به فهرست تراکنش‌های معلق اضافه می‌کند، GetTransactions تراکنش‌های معلق را بازیابی می‌کند و Clear فهرست را خالی می‌کند. مقدار props برای مقداردهی اولیهٔ بازیگر هنگام ایجاد شدن استفاده می‌شود.

scalaclass Broker extends Actor with ActorLogging {
  import Broker._

  var pending: List[Transaction] = List()

  override def receive: Receive = {
    case AddTransaction(transaction) => {
      pending = transaction :: pending
      log.info(s"Added $transaction to pending Transaction")
    }
    case GetTransactions => {
      log.info(s"Getting pending transactions")
      sender() ! pending
    }
    case Clear => {
      pending = List()
      log.info("Clear pending transaction List")
    }
  }
}

کلاس Broker شامل منطق تجاری واکنش به پیام‌های مختلف است. وارد جزئیات نمی‌شوم چون پیش‌پاافتاده است. جالب‌ترین نکته نحوهٔ پاسخ‌دادن به درخواست تراکنش‌های معلق است. آن‌ها را با استفاده از عملگر tell (!) به sender() پیام GetTransactions می‌فرستیم. این عملگر به معنای «پیام را بفرست و منتظر پاسخ نمان» است — به اصطلاح شلیک‌وفراموش (fire-and-forget).

استخراج‌کننده (Miner)، بازیگری با حالت‌های متفاوت

بازیگر استخراج‌کننده همان بازیگری است که بلاک‌های جدید را برای بلاک‌چین ما استخراج می‌کند. چون نمی‌خواهیم هم‌زمان با استخراج یک بلاک، بلاک دیگری استخراج کنیم، بازیگر استخراج‌کننده دو حالت خواهد داشت: ready (آماده)، وقتی آمادهٔ استخراج یک بلاک جدید است، و busy (مشغول)، وقتی در حال استخراج یک بلاک است.

بیایید با تعریفِ شیء همراه و پیام‌های بازیگر استخراج‌کننده شروع کنیم. الگو همان است: یک صفت مهروموم — MinerMessage — برای تعریف نوع پیام‌هایی که این بازیگر به آن‌ها واکنش نشان می‌دهد.

scalaobject Miner {
  sealed trait MinerMessage
  case class Validate(hash: String, proof: Long) extends MinerMessage
  case class Mine(hash: String) extends MinerMessage
  case object Ready extends MinerMessage

  val props: Props = Props(new Miner)
}

پیام Validate درخواست اعتبارسنجی یک اثبات را دارد و هش و اثبات مورد بررسی را به استخراج‌کننده می‌دهد. ازآنجاکه این مؤلفه همان مؤلفه‌ای است که با الگوریتم PoW تعامل دارد، انجام این بررسی بر عهدهٔ آن است. پیام Mine درخواست استخراج با شروع از یک هش مشخص را دارد. آخرین پیام، یعنی Ready، یک گذار حالت (state transition) را فعال می‌کند.

همان بازیگر، حالت‌های متفاوت

ویژگی این بازیگر این است که بسته به حالتش — busy یا ready — به پیام‌ها واکنش نشان می‌دهد. بیایید تفاوت رفتار را تحلیل کنیم:

  • busy: استخراج‌کننده مشغول استخراج یک بلاک است. اگر درخواست استخراج جدیدی بیاید، باید آن را رد کند. اگر از آن خواسته شود آماده شود، باید حالتش را به حالت آماده تغییر دهد.
  • ready: استخراج‌کننده بیکار است. اگر درخواست استخراج بیاید، باید استخراج یک بلاک جدید را شروع کند. اگر از آن خواسته شود آماده باشد، باید بگوید: «باشه، من آماده‌ام!»
  • هر دو حالت: استخراج‌کننده باید همیشه برای راستی‌آزمایی درستی یک اثبات در دسترس باشد، چه در حالت آماده چه در حالت مشغول.

وقت آن رسیده ببینیم چگونه می‌توانیم این منطق را در کدمان پیاده‌سازی کنیم. با تعریف رفتار مشترک، یعنی اعتبارسنجی یک اثبات، شروع می‌کنیم.

تابعی به نام validate تعریف می‌کنیم که به پیام Validate واکنش نشان می‌دهد: اگر اثبات معتبر باشد، با موفقیت و در غیر این صورت با شکست به فرستنده پاسخ می‌دهیم. حالت‌های ready و busy به‌صورت توابعی تعریف می‌شوند که تابع validate را «گسترش» می‌دهند، چون رفتاری است که در هر دو حالت می‌خواهیم.

scaladef validate: Receive = {
    case Validate(hash, proof) => {
      log.info(s"Validating proof $proof")
      if (ProofOfWork.validProof(hash, proof)){
        log.info("proof is valid!")
        sender() ! Success
      }
      else{
        log.info("proof is not valid")
        sender() ! Failure(new InvalidProofException(hash, proof))
      }
    }
  }

چند نکته برای برجسته‌کردن این‌جا هست:

  1. گذار حالت با استفاده از تابع become فعال می‌شود که توسط چارچوب Akka فراهم شده است. این تابع یک تابع را به‌عنوان آرگومان می‌گیرد که یک شیء Receive برمی‌گرداند، مثل همان‌هایی که برای حالت‌های validate، busy و ready تعریف کردیم.
  2. وقتی استخراج‌کننده درخواست استخراج دریافت می‌کند، با یک Future حاوی اجرای الگوریتم PoW پاسخ می‌دهد. به این ترتیب می‌توانیم به‌صورت ناهمگام کار کنیم و استخراج‌کننده را برای انجام کارهای دیگر، مانند اعتبارسنجی، آزاد بگذاریم.
  3. ناظر (supervisor) این بازیگر گذار حالت را کنترل می‌کند. دلیل این انتخاب این است که استخراج‌کننده نسبت به وضعیت سیستم آگاهی ندارد. نمی‌داند محاسبهٔ استخراج داخل Future چه زمانی کامل می‌شود و نمی‌تواند بداند آیا بلاکی که در حال استخراجش است قبلاً توسط گرهٔ دیگری استخراج شده است یا نه. این امر مستلزم توقف استخراج هش فعلی و شروع استخراج هش بلاک جدید است.

آخرین کار فراهم‌کردن یک حالت اولیه با بازنویسی تابع receive است.

scalaoverride def receive: Receive = {
    case Ready => become(ready)
  }

ما منتظر پیام Ready می‌مانیم. وقتی رسید، استخراج‌کنندهٔ خود را شروع می‌کنیم.

بلاک‌چین، یک بازیگر ماندگار

بازیگر بلاک‌چین با منطق تجاری بلاک‌چین تعامل دارد. می‌تواند یک بلاک جدید به بلاک‌چین اضافه کند و اطلاعاتی دربارهٔ وضعیت بلاک‌چین بازیابی کند. این بازیگر یک ابرقدرت دیگر هم دارد: می‌تواند وضعیت بلاک‌چین را ماندگار کند (persist) و بازیابی کند. این کار با پیاده‌سازی صفت PersistentActor که توسط چارچوب Akka فراهم شده امکان‌پذیر است.

scalaobject Blockchain {
  sealed trait BlockchainEvent
  case class AddBlockEvent(transactions: List[Transaction], proof: Long) extends BlockchainEvent

  sealed trait BlockchainCommand
  case class AddBlockCommand(transactions: List[Transaction], proof: Long) extends BlockchainCommand
  case object GetChain extends BlockchainCommand
  case object GetLastHash extends BlockchainCommand
  case object GetLastIndex extends BlockchainCommand

  case class State(chain: Chain)

  def props(chain: Chain, nodeId: String): Props = Props(new Blockchain(chain, nodeId))
}

می‌بینیم که شیء همراه این بازیگر عناصر بیشتری نسبت به بقیه دارد. کلاس State جایی است که وضعیت بلاک‌چین خود، یعنی Chain آن را ذخیره می‌کنیم. ایده این است که هر بار بلاک جدیدی ساخته می‌شود، وضعیت را به‌روز کنیم.

برای این منظور، دو صفت متفاوت وجود دارد: BlockchainEvent و BlockchainCommand. اولی برای مدیریت رویدادهایی است که منطق ماندگاری را فعال می‌کنند و دومی برای فرستادن دستورهای مستقیم به بازیگر استفاده می‌شود. پیام AddBlockEvent رویدادی است که وضعیت ما را به‌روز می‌کند. دستورهای AddBlockCommand، GetChain، GetLastHash و GetLastIndex همان‌هایی هستند که برای تعامل با بلاک‌چین زیرین استفاده می‌شوند.

تابع معمول props بازیگر بلاک‌چین را با Chain اولیه و nodeId گرهٔ Scalachain مقداردهی اولیه می‌کند.

scalaclass Blockchain(chain: Chain, nodeId: String) extends PersistentActor with ActorLogging{
  import Blockchain._

  var state = State(chain)

  override def persistenceId: String = s"chainer-$nodeId"

  //Code...
}

بازیگر بلاک‌چین صفت PersistentActor فراهم‌شده توسط چارچوب Akka را گسترش می‌دهد. به این ترتیب همهٔ منطق لازم برای ماندگارکردن و بازیابی وضعیت را بیرون‌ازجعبه (out-of-the-box) در اختیار داریم.

وضعیت را با استفاده از Chain ارائه‌شده به‌عنوان آرگومان هنگام ایجاد، مقداردهی می‌کنیم. nodeId بخشی از persistenceId است که آن را بازنویسی می‌کنیم. منطق ماندگاری برای شناسایی وضعیت ماندگارشده از آن استفاده می‌کند. ازآنجاکه ممکن است چندین گرهٔ Scalachain روی همان ماشین اجرا شوند، برای ماندگارسازی و بازیابی صحیح وضعیت هر گره به این مقدار نیاز داریم.

scaladef updateState(event: BlockchainEvent) = event match {
    case AddBlockEvent(transactions, proof) =>
      {
        state = State(ChainLink(state.chain.index + 1, proof, transactions) :: state.chain)
        log.info(s"Added block ${state.chain.index} containing ${transactions.size} transactions")
      }
  }

تابع updateState وقتی پیام AddBlockEvent دریافت شود، به‌روزرسانی وضعیت بازیگر را اجرا می‌کند.

scalaoverride def receiveRecover: Receive = {
    case SnapshotOffer(metadata, snapshot: State) => {
      log.info(s"Recovering from snapshot ${metadata.sequenceNr} at block ${snapshot.chain.index}")
      state = snapshot
    }
    case RecoveryCompleted => log.info("Recovery completed")
    case evt: AddBlockEvent => updateState(evt)
  }

تابع receiveRecover به پیام‌های بازیابی ارسال‌شده توسط منطق ماندگاری واکنش نشان می‌دهد. هنگام ایجاد یک بازیگر ممکن است با پیام SnapshotOffer یک وضعیت ماندگارشده (عکس فوری یا snapshot) به آن پیشنهاد شود. در این صورت وضعیت فعلی همان وضعیت ارائه‌شده توسط عکس فوری می‌شود.

پیام RecoveryCompleted به ما اطلاع می‌دهد که فرایند بازیابی با موفقیت کامل شده است. AddBlockEvent با پاس‌دادن خود رویداد، تابع updateState را فعال می‌کند.

scalaoverride def receiveCommand: Receive = {
    case SaveSnapshotSuccess(metadata) => log.info(s"Snapshot ${metadata.sequenceNr} saved successfully")
    case SaveSnapshotFailure(metadata, reason) => log.error(s"Error saving snapshot ${metadata.sequenceNr}: ${reason.getMessage}")
    case AddBlockCommand(transactions : List[Transaction], proof: Long) => {
      persist(AddBlockEvent(transactions, proof)) {event =>
        updateState(event)
      }

      // This is a workaround to wait until the state is persisted
      deferAsync(Nil) { _ =>
        saveSnapshot(state)
        sender() ! state.chain.index
      }
    }
    case AddBlockCommand(_, _) => log.error("invalid add block command")
    case GetChain => sender() ! state.chain
    case GetLastHash => sender() ! state.chain.hash
    case GetLastIndex => sender() ! state.chain.index
  }

تابع receiveCommand برای واکنش به دستورهای مستقیم ارسال‌شده به بازیگر استفاده می‌شود. دستورهای GetChain، GetLastHash و GetLastIndex را رد می‌کنیم، چون پیش‌پاافتاده‌اند. بخش جالب AddBlockCommand است: یک رویداد AddBlockEvent می‌سازد و فعال می‌کند که در ژورنال رویدادها (event journal) بازیگر ماندگار می‌شود. به این ترتیب در صورت بازیابی، رویدادها قابل پخش مجدد (replay) هستند.

تابع deferAsync منتظر می‌ماند تا وضعیت پس از پردازش رویداد به‌روز شود. پس از اجرای رویداد، بازیگر می‌تواند عکس فوری از وضعیت را ذخیره کند و آخرین ایندکس به‌روزشدهٔ Chain را به فرستندهٔ پیام اطلاع دهد. پیام‌های SaveSnapshotSuccess و SaveSnapshotFailure به ما کمک می‌کنند خطاهای احتمالی را پیگیری کنیم.

توجه: کامنت «// This is a workaround to wait until the state is persisted» داخل کد، توضیح نویسنده است مبنی بر اینکه این یک راه‌حل موقت برای صبرکردن تا ماندگارشدن وضعیت است.

گره (Node)، بازیگری برای ادارهٔ همه

بازیگر گره، ستون فقرات گرهٔ Scalachain ماست. این بازیگر ناظر همهٔ بازیگرهای دیگر (Broker، Miner و Blockchain) و همان بازیگری است که از طریق REST API با دنیای بیرون ارتباط برقرار می‌کند.

scalaobject Node {

  sealed trait NodeMessage

  case class AddTransaction(transaction: Transaction) extends NodeMessage

  case class CheckPowSolution(solution: Long) extends NodeMessage

  case class AddBlock(proof: Long) extends NodeMessage

  case object GetTransactions extends NodeMessage

  case object Mine extends NodeMessage

  case object StopMining extends NodeMessage

  case object GetStatus extends NodeMessage

  case object GetLastBlockIndex extends NodeMessage

  case object GetLastBlockHash extends NodeMessage

  def props(nodeId: String): Props = Props(new Node(nodeId))

  def createCoinbaseTransaction(nodeId: String) = Transaction("coinbase", nodeId, 100)
}

بازیگر گره باید همهٔ پیام‌های سطح بالایی که از REST API می‌آیند را مدیریت کند. به همین دلیل است که در شیء همراه کم‌وبیش همان پیام‌هایی را می‌بینیم که در بازیگرهای فرزند پیاده‌سازی کردیم. تابع props یک nodeId را به‌عنوان آرگومان می‌گیرد تا بازیگر گره ساخته شود. این همان مقداری است که برای مقداردهی اولیهٔ بازیگر بلاک‌چین استفاده خواهد شد. تابع createCoinbaseTransaction به‌سادگی یک تراکنش ایجاد می‌کند که مقدار ازپیش‌تعیین‌شده‌ای سکه را به خود گره اختصاص می‌دهد. این همان پاداش استخراج موفق یک بلاک جدید از بلاک‌چین خواهد بود.

scalaclass Node(nodeId: String) extends Actor with ActorLogging {

  import Node._

  implicit lazy val timeout = Timeout(5.seconds)

  val broker = context.actorOf(Broker.props)
  val miner = context.actorOf(Miner.props)
  val blockchain = context.actorOf(Blockchain.props(EmptyChain, nodeId))

  miner ! Ready

  //Code...
}

بیایید به مقداردهی اولیهٔ بازیگر گره نگاه کنیم. مقدار timeout توسط عملگر ask (?) استفاده می‌شود (به‌زودی توضیح داده خواهد شد). همهٔ بازیگرهای ما در context بازیگر، با استفاده از تابع props که در هر بازیگر تعریف کردیم، ایجاد می‌شوند.

بازیگر بلاک‌چین با EmptyChain و nodeId گره مقداردهی می‌شود. وقتی همه‌چیز ساخته شد، با ارسال پیام Ready به بازیگر استخراج‌کننده اطلاع می‌دهیم که برای استخراج آماده باشد. خب، حالا آماده‌ایم پیام‌هایی دریافت کنیم و به آن‌ها واکنش نشان دهیم.

    case AddTransaction(transaction) => {
      //Code...

      //Code...
    }
    case AddBlock(proof) => {
      //Code...
    }
    case Mine => {

این نمای کلی تابع معمول receive است که باید بازنویسی کنیم. منطق پیچیده‌ترین caseها را بعداً تحلیل می‌کنم؛ حالا بگذارید به چهار مورد آخر نگاه کنیم. این‌جا پیام‌ها را به بازیگر بلاک‌چین ارسالِ رو‌به‌جلو (forward) می‌کنیم، چون پردازش خاصی لازم نیست. با استفاده از عملگر forward، sender() پیام فرستندهٔ اصلی پیام خواهد بود نه بازیگر گره. به این ترتیب بازیگر بلاک‌چین به فرستندهٔ اصلی پیام (لایهٔ REST API) پاسخ می‌دهد.

scalaoverride def receive: Receive = {
    case AddTransaction(transaction) => {
      val node = sender()
      broker ! Broker.AddTransaction(transaction)
      (blockchain ? GetLastIndex).mapTo[Int] onComplete {
        case Success(index) => node ! (index + 1)
        case Failure(e) => node ! akka.actor.Status.Failure(e)
      }
    }

  //Code...
}

پیام AddTransaction منطق ذخیره‌سازی یک تراکنش جدید در فهرست تراکنش‌های معلق بلاک‌چین ما را فعال می‌کند. بازیگر گره با index بلاکی که تراکنش را در خود خواهد داشت پاسخ می‌دهد.

اول از همه «آدرس» sender() پیام را در یک مقدار node ذخیره می‌کنیم تا بعداً از آن استفاده کنیم. پیامی برای افزودن یک تراکنش جدید به بازیگر کارگزار می‌فرستیم؛ سپس با ask آخرین ایندکس زنجیره را از بازیگر بلاک‌چین می‌پرسیم. عملگر ask — که با ? بیان می‌شود — برای فرستادن یک پیام به یک بازیگر و انتظار برای پاسخ استفاده می‌شود. پاسخ (نگاشت‌شده به یک مقدار Int) می‌تواند یک Success یا یک Failure باشد.

در حالت اول، index+1 را به فرستنده (node) برمی‌گردانیم، چون ایندکس بلاک استخراج‌شدهٔ بعدی خواهد بود. در صورت خطا، با یک Failure حاوی دلیل خطا به فرستنده پاسخ می‌دهیم. این الگو را به خاطر بسپارید:

ask → منتظر پاسخ بمان → موفقیت/شکست را مدیریت کن

چون دوباره با آن مواجه خواهیم شد.

scalaoverride def receive: Receive = {
    //Code...

    case CheckPowSolution(solution) => {

      (blockchain ? GetLastHash).mapTo[String] onComplete {

این بار باید بررسی کنیم که راه‌حلی برای الگوریتم PoW درست است یا نه. هش آخرین بلاک را از بازیگر بلاک‌چین می‌پرسیم و به بازیگر استخراج‌کننده می‌گوییم راه‌حل را در برابر هش اعتبارسنجی کند. در تابع tell پیام Validate را همراه با آدرس فرستنده به استخراج‌کننده می‌دهیم تا استخراج‌کننده بتواند مستقیماً به آن پاسخ دهد. این رویکرد دیگری است، مثل رویکرد forward که قبلاً دیدیم.

scalaoverride def receive: Receive = {
    //Code...

    case AddBlock(proof) => {

      (self ? CheckPowSolution(proof)) onComplete {
        case Success(_) => {

گره‌های دیگر هم می‌توانند بلاک استخراج کنند؛ پس ممکن است درخواستی برای افزودن بلاکی دریافت کنیم که خودمان استخراج نکرده‌ایم. اثبات برای افزودن بلاک جدید کافی است، چون فرض می‌کنیم همهٔ گره‌ها همان فهرست تراکنش‌های معلق را به اشتراک می‌گذارند.

scalaoverride def receive: Receive = {
    //Code...

    case Mine => {
      val node = sender()
      (blockchain ? GetLastHash).mapTo[String] onComplete {
        case Success(hash) => (miner ? Miner.Mine(hash)).mapTo[Future[Long]] onComplete {
          case Success(solution) => waitForSolution(solution)
          case Failure(e) => log.error(s"Error finding PoW solution: ${e.getMessage}")
        }
        case Failure(e) => node ! akka.actor.Status.Failure(e)
      }
    }

    //Code...
  }

  def waitForSolution(solution: Future[Long]) = Future {
    solution onComplete {
      case Success(proof) => {
        broker ! Broker.AddTransaction(createCoinbaseTransaction(nodeId))
        self ! AddBlock(proof)
        miner ! Ready
      }
      case Failure(e) => log.error(s"Error finding PoW solution: ${e.getMessage}")
    }
  }

این یک ساده‌سازی است؛ در شبکهٔ بیت‌کوین چنین فرضی‌ای نمی‌تواند وجود داشته باشد. اول از همه باید بررسی کنیم که راه‌حل معتبر است. این کار را با فرستادن پیامی به خود گره انجام می‌دهیم: self ? CheckPowSolution(proof). اگر اثبات معتبر باشد، فهرست تراکنش‌های معلق را از بازیگر کارگزار می‌گیریم و سپس به بازیگر بلاک‌چین tell می‌کنیم بلاک جدیدی حاوی تراکنش‌ها و اثبات اعتبارسنجی‌شده به زنجیره اضافه کند. آخرین کار دستور دادن به بازیگر کارگزار برای خالی‌کردن فهرست تراکنش‌های معلق است.

آخرین پیام درخواست شروع استخراج یک بلاک جدید است. به هش آخرین بلاک زنجیره نیاز داریم؛ پس آن را از بازیگر بلاک‌چین درخواست می‌کنیم. وقتی هش را داشتیم، می‌توانیم استخراج یک بلاک جدید را شروع کنیم.

الگوریتم PoW یک عملیات طولانی است؛ بنابراین بازیگر استخراج‌کننده بلافاصله با یک Future حاوی محاسبه پاسخ می‌دهد. تابع waitForSolution منتظر کامل‌شدن محاسبه است، در حالی که بازیگر گره به کار خود ادامه می‌دهد.

وقتی راه‌حلی داریم، با افزودن تراکنش کوین‌بیس (coinbase transaction) به فهرست تراکنش‌های معلق، به خود پاداش می‌دهیم. سپس بلاک جدید را به زنجیره اضافه می‌کنیم و به بازیگر استخراج‌کننده می‌گوییم برای استخراج بلاک بعدی آماده شود.

REST API با Akka HTTP

این بخش آخر سرور و REST API را توصیف می‌کند. این «بیرونی‌ترین» بخش برنامهٔ ماست؛ بخشی که دنیای بیرون را به گرهٔ Scalachain متصل می‌کند. از کتابخانهٔ Akka HTTP که بخشی از چارچوب Akka است استفاده خواهیم کرد. بیایید با سرور، یعنی نقطهٔ ورود برنامه شروع کنیم.

scalaobject Server extends App with NodeRoutes {

  val address = if (args.length > 0) args(0) else "localhost"
  val port = if (args.length > 1) args(1).toInt else 8080

  implicit val system: ActorSystem = ActorSystem("scalachain")

  implicit val materializer: ActorMaterializer = ActorMaterializer()

  val node: ActorRef = system.actorOf(Node.props("scalaChainNode0"))

  lazy val routes: Route = statusRoutes ~ transactionRoutes ~ mineRoutes

  Http().bindAndHandle(routes, address, port)

  println(s"Server online at http://$address:$port/")

  Await.result(system.whenTerminated, Duration.Inf)

}

ازآنجاکه Server نقطهٔ ورود ماست، باید صفت App را گسترش دهد. همچنین NodeRoutes را گسترش می‌دهد؛ صفتی که همهٔ مسیرهای (routes) http به نقطه‌های پایانی مختلف گره را در خود دارد.

مقدار system جایی است که ActorSystem خود را ذخیره می‌کنیم. هر بازیگری که در این سیستم ساخته شود می‌تواند با سایر بازیگرهای داخل همان سیستم صحبت کند. Akka HTTP همچنین تعریف مقدار دیگری به نام ActorMaterializer را لازم دارد. این مقدار به ماژول Akka Streams مربوط است، اما چون Akka HTTP روی آن ساخته شده، همچنان برای راه‌اندازی سرور به این شیء نیاز داریم (اگر می‌خواهید در رابطه با جریان‌ها عمیق شوید، اینجا را ببینید).

بازیگر گره همراه با مسیرهای http گره ساخته می‌شود که با عملگر ~ به یکدیگر زنجیر می‌شوند. الان نگران مسیرها نباشید؛ کمی بعد به آن‌ها برمی‌گردیم.

آخرین کار شروع سرور با استفاده از تابع Http().bindAndHandle است که مسیرهای ارسال‌شده به آن را به‌عنوان آرگومان هم متصل (bind) می‌کند. تابع Await.result منتظر سیگنال خاتمه می‌ماند تا سرور متوقف شود.

سرور بدون مسیرهایی که منطق تجاری برنامه را فعال کنند بی‌فایده خواهد بود. مسیرها را در صفت NodeRoutes تعریف می‌کنیم و آن‌ها را بر اساس منطق متفاوتی که فعال می‌کنند متمایز می‌سازیم:

  • statusRoutes حاوی نقطه‌های پایانی برای پرسیدن وضعیت گرهٔ Scalachain است.
  • transactionRoutes همه‌چیز مربوط به تراکنش‌ها را مدیریت می‌کند.
  • mineRoutes نقطهٔ پایانی شروع فرایند استخراج را دارد.

توجه کنید که این تفکیک صرفاً منطقی است تا امور مرتب و خوانا بمانند. سه مسیر پس از مقداردهی اولیه در سرور، در یک مسیر واحد زنجیر می‌شوند.

صفت NodeRoutes صفت SprayJsonSupport را گسترش می‌دهد تا سریال‌سازی/ضدسریال‌سازی JSON اضافه شود. SprayJson یک کتابخانهٔ اسکالا است و مشابه Jackson در جاواست؛ همراه با Akka HTTP به‌صورت رایگان ارائه می‌شود.

برای تبدیل اشیای خود به یک رشتهٔ JSON، کلاس JsonSupport تعریف‌شده در پکیج utils را import می‌کنیم که برای هر شیء یک reader/writer سفارشی دارد. وارد جزئیات نمی‌شوم؛ اگر می‌خواهید پیاده‌سازی را ببینید می‌توانید کلاس را در مخزن پیدا کنید.

چند مقدار implicitly (ضمنی) داریم. از ActorSystem برای تعریف سیستم بازیگرها استفاده می‌شود، در حالی که Timeout توسط تابع onSuccess که منتظر پاسخ از بازیگرها می‌ماند استفاده می‌شود. ActorRef با بازنویسی در پیاده‌سازی سرور تعریف می‌شود.

lazy val transactionRoutes: Route = pathPrefix("transactions") {
    concat(
      pathEnd {
        concat(
          get {
            val transactionsRetrieved: Future[List[Transaction]] =
              (node ? GetTransactions).mapTo[List[Transaction]]
            onSuccess(transactionsRetrieved) { transactions =>
              complete(transactions.toList)
            }
          },
          post {
            entity(as[Transaction]) { transaction =>
              val transactionCreated: Future[Int] =
                (node ? AddTransaction(transaction)).mapTo[Int]
              onSuccess(transactionCreated) { done =>
                complete((StatusCodes.Created, done.toString))
              }
            }
          }
        )
      }
    )
  }

نتیجه‌گیری

با بخش آخر، تور خود را داخل Scalachain به پایان رساندیم. این نمونهٔ اولیهٔ بلاک‌چین با یک پیاده‌سازی واقعی فاصلهٔ زیادی دارد، اما چیزهای جالب زیادی یاد گرفتیم:

  • بلاک‌چین چگونه کار می‌کند، حداقل از دیدگاه سطح بالا.
  • چگونه از برنامه‌نویسی تابعی (اسکالا) برای ساخت یک بلاک‌چین استفاده کنیم.
  • مدل بازیگر چگونه کار می‌کند و کاربرد آن در مورد کاربرد ما با استفاده از چارچوب Akka.
  • چگونه از کتابخانهٔ Akka HTTP برای ساخت سروری جهت اجرای بلاک‌چین مان، همراه با APIهای تعامل با آن، استفاده کنیم.

کد کامل و بی‌نقص نیست و برخی چیزها را می‌توان بهتر پیاده‌سازی کرد. به همین دلیل، در مشارکت در پروژه کاملاً آزاد باشید! ;-)
