چرا باید GC را دستی بسازیم؟

مدیریت حافظهٔ خودکار (Garbage Collection) در زبان‌هایی مثل پایتون، جاوا و حتی جاوااسکریپت، کار روزمرهٔ برنامه‌نویسان است؛ اما وقتی مفسر خودتان را می‌نویسید، دیگر کسی نیست که اشیا را برایتان پاک کند. باب نیستروم در این مقاله، یک زباله‌روب سادهٔ mark-and-sweep را در C می‌سازد و نشان می‌دهد که این سیستم دقیقاً چه چیزی را «زنده» حساب می‌کند.

ایدهٔ اصلی: ریشه‌ها و گراف اشیا

در هر زبان، اشیایی که از «ریشه‌ها» (متغیرهای در دسترس، پشتهٔ فراخوانی و …) قابل دسترسی باشند زنده‌اند؛ بقیه را می‌توان پاک کرد. در این مقاله برای سادگی فرض می‌کنیم ریشه‌ها همان «پشتهٔ VM» هستند — یک لیست متصل از آبجکت‌هایی که مفسر در حال کار با آن‌هاست.

هر آبجکت یک فلگ marked دارد. زباله‌روب دو مرحله دارد: علامت‌گذاری (از ریشه‌ها شروع می‌کند و تمام آبجکت‌های قابل دسترسی با گراف تابع‌های ارجاع را علامت می‌زند) و پاکسازی (از لیست تمام آبجکت‌ها عبور می‌کند و آن‌هایی که علامت نشده‌اند را free می‌کند).

نمونهٔ کد: ساختار آبجکت و تابع جمع‌آوری

Ctypedef struct sObject {
  struct sObject* next;   // لیست پیوندی همهٔ آبجکت‌ها
  char marked;            // فلگ علامت‌گذاری
  union {
    int value;
    struct sObject* head; // برای لیست‌ها
    ...
  } data;
} Object;

void gc() {
  // ۱) علامت‌گذاری: از ریشه‌ها (پشتهٔ VM)
  for (Object* root = vm.stack; root != NULL; root = root->next)
    mark(root);

  // ۲) پاکسازی: هر آبجکتِ علامت‌نشده را آزاد کن
  Object** obj = &vm.objects;   // اشاره‌گر به لیست کل
  while (*obj != NULL) {
    if (!(*obj)->marked) {
      Object* unreached = *obj;
      *obj = unreached->next;
      free(unreached);
    } else {
      (*obj)->marked = 0;      // برای دفعهٔ بعد
      obj = &(*obj)->next;
    }
  }
}

مشکل‌ها و راه‌حل‌های عملی

بزرگ‌ترین مشکل: وقتی VM از آبجکت جدید استفاده می‌کند، هنوز به پشته وصل نشده — در این حالت GC نباید آن را پاک کند. راه‌حل مقاله: آبجکت «در حال ساخت» را هنگام ساخت مستقیم «روی ریشه» قرار می‌دهیم تا هرگز جمع‌آوری نشود.

مشکل دوم: در C می‌توانیم ریسک‌های دیگر (مثل ریشه‌های روی پشتهٔ C) را نادیده بگیریم چون آزمایش‌ها و مثال‌ها همه با heap کار می‌کنند. در پایان مقاله، راه‌های «real world» مثل conservative GC و exact GC و استفاده از shadow stack یا hand-optimization هم اشاره می‌شود.

جمع‌بندی

این مقاله یک ساعت مطالعه، بین تقریباً صفر تا GC واقعی فاصله می‌اندازد: با کمتر از ۱۰۰ خط C، سیستم مدیریت حافظهٔ مفسرتان را می‌سازید و درک می‌کنید که چرا زبان‌های سطح بالا اصرار به «جمع‌آوری زباله» دارند.
