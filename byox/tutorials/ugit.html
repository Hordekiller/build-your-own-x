ugit — درون‌های گیت را با ساختن خود گیت یاد بگیر

منبع اصلی: این صفحه ترجمه فارسی «Write yourself a Git!» اثر تیبو پولژ (Thibault Polge) است — با ساختن گام‌به‌گام یک گیت ساده به نام ugit (حدود ۴۰۰ خط پایتون) درون‌های گیت را یاد می‌گیرید: آبجکت‌های content-addressed، کامیت‌ها، شاخه‌ها، مرج، ریبیس و remote.

۱. مقدمه — چرا یک گیت بسازیم؟

گیت ابزاری است که بیشتر ما هر روز استفاده می‌کنیم، اما درون آن معمولاً جعبهٔ سیاهی می‌ماند. هدف این مقاله حل کردن یک مسئلهٔ متداول است: درک اینکه گیت واقعاً چه می‌کند. با پیاده‌سازی سادهٔ یک گیت از صفر، هم فلسفهٔ طراحی گیت را یاد می‌گیرید و هم با ذهنی روشن‌تر از آن استفاده می‌کنید.

محصول نهایی، برنامهٔ ugit است — نسخه‌ای کوچک از گیت در حدود ۴۰۰ خط پایتون تاریخچهٔ کامل یک پروژه را ذخیره و بازیابی می‌کند و شاخه‌بندی، مرج، ریبیس و کار با remote را پشتیبانی می‌کند.

سه تصمیم اصلی این مقاله را شکل می‌دهند:

  • سادگی: فقط ویژگی‌هایی که برای عملکرد ضروری‌اند؛ هر چیز اضافی به‌عنوان «تمرین» به شما واگذار می‌شود.
  • کد کم و خواناتر: حدود ۴۰۰ خط پایتون — نه به‌اندازهٔ ۴۰ هزار خط «فشنگی واقعی»!
  • چند پلتفرم: روی لینوکس و مک کار می‌کند (و «ظاهراً» ریموت روی ویندوز هم).

در پایان، فایل‌ها و فرایندهای ایجادشده را با گیت واقعی مقایسه می‌کنیم — خیلی شبیه‌اند!

۲. ذخیره‌سازی — دایرکتوری خزانه و آبجکت‌های content-addressed

گیت در هستهٔ خود یک سیستم فایل content-addressed است. یعنی هر شیء (فایل یا کامیت) با عملگر هش محتوایش آدرس‌دهی می‌شود. اگر محتوا عوض شود، آدرس (نام فایل) هم عوض می‌شود؛ اگر دو محتوا یک‌سان باشند، یک آدرس می‌گیرند — این یعنی ذخیره‌سازی یکتا و بادوامی که هویت اشیاء را تضمین می‌کند.

ugit init فقط یک پوشه خالی به نام .ugit می‌سازد. تمام داده‌ها داخل همین پوشه ذخیره می‌شوند.

ساختار یک آبجکت: نوع شیء (مثل blob یا commit)، یک بایت صفر و سپس دادهٔ خام؛ کل این رشته با zlib فشرده می‌شود. نام فایل، هش SHA-1 همان رشته است:

pythonimport hashlib, os, zlib

def hash_object(data: bytes, type_: str = "blob") -> str:
    """یک شیء بنویس و شناسه اش را برگردان"""
    raw = type_.encode() + b"\x00" + data   # قالب: <نوع>\x00<داده>
    oid = hashlib.sha1(raw).hexdigest()
    path = repo("objects", oid)
    os.makedirs(os.path.dirname(path), exist_ok=True)
    with open(path, "wb") as f:
        f.write(zlib.compress(raw))
    return oid

تابع repo("objects", oid) یک مسیر نسبی به دایرکتوری .ugit/objects می‌سازد — همهٔ اشیاء داخل این پوشه با نام هش‌شان نگهداری می‌شوند؛ مثل گیت واقعی.

گرفتن آبجکت (خواندن) عکس همین عملیات است؛ ابزار خط‌فرمان cat-file <oid> همین کار را می‌کند و برای رفع اشکال هم عالی است — می‌توانید کدش را ۱۰ خطی بنویسید:

pythondef read_object(oid: str) -> bytes:
    """یک شیء را بر اساس شناسه بخوان"""
    with open(repo("objects", oid), "rb") as f:
        return zlib.decompress(f.read())
نکتهٔ امنیتی: این هش‌ها رمزنگاری نیستند؛ فقط معیار هویت اشیاءند. گیت واقعی هم «انتقال امن» را از مکانیزم دیگری (HMAC و HTTPS) می‌گیرد، نه از هش محتوا.

۳. اولین دستورها: add و commit و log

با دو نوع شیء شروع می‌کنیم: blob برای محتوا و commit برای سوابق. ugit add <file> محتوای فایل را می‌خواند و به‌صورت blob ذخیره می‌کند؛ ugit commit یک کامیت می‌سازد که اشاره به بلابِ نسخهٔ فعلی دارد (و به کامیت قبلی — parent).

pythondef cmd_commit(tree: str, parent: str | None) -> str:
    """کامیت بساز: محتوای همهٔ بلاب‌ها به‌علاوهٔ والد"""
    data = f"tree {tree}\n".encode()
    if parent:
        data += f"parent {parent}\n".encode()
    return hash_object(data, type_="commit")

ugit log: با دنبال کردن زنجیرهٔ parent از آخرین کامیت شروع می‌کند و پیام‌های همهٔ کامیت‌ها را چاپ می‌کند — تاریخچهٔ پروژه ما! این پیمایش زنجیرهٔ والد، همان «لاگ» گیت است:

pythondef log(oid: str) -> Generator[str]:
    """پیمایش زنجیرهٔ parent از یک کامیت"""
    while oid:
        commit = get_commit(oid)
        yield oid
        oid = commit.parent   # قدم به عقب برو

تا اینجا، زیرمجموعهٔ اصلی گیت کار می‌کند؛ اما گیت کارهای بیشتری بلد است. ادامه می‌دهیم تا آن‌ها را هم دربیاوریم. تمرین‌ها: دستور show و cat-file، و پیام‌های کامیت.

۴. ارجاع به کامیت‌ها — عملگرهای ^ و ~

وقتی تاریخچه طولانی می‌شود، نوشتن هش کامل کامیت‌ها راحت نیست — و اصلاً «کامیت پدربزرگ» را نمی‌توان مستقیم نوشت! گیت ارجاع‌دادن به کامیت‌ها را با دو عملگر راحت می‌کند:

  • oid^: والدِ نسل اولِ کامیت oid. به‌طور کلی oid^n به nاُمین والد اشاره می‌کند — مثل HEAD^2 در مرج‌ها که والد دوم است.
  • oid~n: پیاده‌رویِ n قدمی در اولین والدها — با HEAD~3 سه نسل به عقب می‌روید.
pythondef get_oid(name: str) -> str:
    """یک ارجاع یا عملگر ~ و ^ را به شناسهٔ کامیت تبدیل کن"""
    if name.endswith("^"):
        return get_commit(get_oid(name[:-1])).parent   # والدِ ولد-اول
    if "~" in name:
        ref, n = name.split("~", 1)
        commit = get_commit(get_oid(ref))
        for _ in range(int(n)):
            commit = get_commit(commit.parent)         # پیاده‌روی ~n
        return commit.oid
    return name  # یا شناسهٔ کامل

دستور diff هم همین‌جا معنا پیدا می‌کند: محتوای object A را با object B مقایسه کن — از تفاضل سادهٔ محتوا (معادل diff -u) تا تفاضل درخت‌ها. در گیت، مقایسهٔ دوتایی است؛ بعداً به مرج سه‌طرفه می‌رسیم.

۵. Staging area و ignore

در گیت، فایل‌ها دو حالت دارند: `tracked` (مطمئناً بخشی از کامیت بعدی‌اند)، `untracked` (دست‌نخورده‌اند) و `ignored` (به‌طور صریح نادیده گرفته می‌شوند). برای مدیریت حالات بین این‌ها، گیت یک سطح اضافه به نام staging area دارد — «نقشه» فایل‌هایی که در کامیت بعدی قرار خواهند گرفت.

ugit ignore <file> فایل را به فهرست .ugit/ignore اضافه می‌کند؛ سپس در add و commit این فایل‌ها نادیده گرفته می‌شوند — مثل .gitignore:

pythondef will_ignore(file: str) -> bool:
    """آیا این فایل باید نادیده گرفته شود؟"""
    with open(repo("ignore"), "r") as f:
        return file in f.read().splitlines()

مرحلهٔ آتی، پیاده‌سازی کامل «index» (فهرستِ .git/index) است که با بافر کردن تغییرات، هزینهٔ ساخت درخت کامیت را کم می‌کند — در گیت واقعی همین‌جا تفاوت add و add -A معلوم می‌شود.

۶. شاخه‌ها و HEAD — چابکی در اشاره به کامیت‌ها

شاخه‌ها در گیت، برچسب‌های سبکی هستند که به یک کامیت اشاره می‌کنند. در ugit، هر شاخه یک فایل در .ugit/refs/heads/ است که محتوایش یک شناسهٔ کامیت است. این فایل‌ها را ref می‌نامیم.

branch <name> یک ref جدید به کامیت فعلی می‌سازد؛ checkout <name> خودِ شاخهٔ فعال را عوض می‌کند. شاخهٔ فعال در فایل .ugit/HEAD ذخیره می‌شود — مثل گیت واقعی که HEAD به refs/heads/master با یک «symbolic ref» اشاره می‌کند:

pythondef get_HEAD() -> str:
    """شاخهٔ فعال را بخوان"""
    with open(repo("HEAD"), "r") as f:
        return f.read().rstrip()

def create_branch(name: str, oid: str) -> None:
    """به شاخهٔ جدید یک شناسه بده"""
    with open(repo("refs", "heads", name), "w") as f:
        f.write(oid)

checkout دو کار را با هم انجام می‌دهد: HEAD را به شاخهٔ هدف تغییر می‌دهد و محتوای کاری را طبق درخت آن شاخه بازنویسی می‌کند (بنویس بلاب‌ها به مسیر خودشان، حذف کن اضافه‌ها).

۷. مرج — جادوی سه‌طرفه

مرج در گیت به متد merge-base وابسته است: نزدیک‌ترین کامیت مشترک بین دو شاخه. «مرج سه‌طرفه» یعنی مقایسهٔ base با هر دو شاخه:

  • اگر فقط یک طرف فایلی را تغییر داده باشد → همان نسخه برنده است.
  • اگر هر دو طرف یک فایل را به یک‌شکل تغییر داده باشند → همان برد.
  • اگر هر دو متفاوت تغییرش داده باشند → تعارض؛ باید حلش کنید (قلبِ صدای «CONFLICT» در گیت).
pythondef merge(ref_name: str) -> str:
    """دو شاخه را مرج کن و کامیت مرج بساز"""
    HEAD_commit = get_HEAD()
    merge_commit = get_commit(ref_name)
    base = merge_base(HEAD_commit, merge_commit)   # LOWEST COMMON ANCESTOR
    return commit_merge(base, HEAD_commit, merge_commit)

حل تعارض‌ها، در ugit به‌طور خودکار با فایل جدید .ugit/MERGE_HEAD ثبت می‌شود؛ اگر تعارض حل شود، کامیت مرج ساخته می‌شود و refها به آن اشاره می‌کنند.

۸. ریبیس — داستان ما را برو و بازکن

ریبیس، تفاوت‌ها را از شاخهٔ فعلی می‌گیرد، همگی را کنار می‌گذارد و در انتهای شاخهٔ هدف «بازپخش» (re-play) می‌کند. به‌عبارت دیگر به جای ایجاد گره مرج، تاریخچه را دوباره می‌چینید — کوبنده‌تر و کم‌پرت‌است.

ساده‌ترین پیاده‌سازی «ریبیس» یعنی: كل کامیت‌هاي شاخه را (از merge-base به بعد) در لیست بگیر، همه را به‌صورت تفاضل به شاخهٔ پایه منتقل کن و یک کامیت تازه برای هر کدام بساز. نتیجه — تاریخچهٔ چیده‌شدهٔ جدید؛ سپس کامیت‌های قدیمی را می‌توان حذف کرد:

pythondef rebase(onto: str) -> None:
    """تاریخچه را روی شاخهٔ onto بازچین"""
    oids = get_commit_chain(get_HEAD())          # کامیت های جاری
    base = merge_base(get_HEAD(), onto)
    to_replay = oids[:oids.index(base)]          # آنهایی که باید دوباره پخش شوند
    for oid in reversed(to_replay):              # از قدیمی به جدید
        onto = commit_diff(onto, oid)            # تفاضل هر کامیت را اعمال کن
    redirect_HEAD(onto)                          # و شاخه را به نتیجه بچسبان

این «ریبیس اولیه» هنوز فشرده‌سازی ندارد؛ گام بعدی «فشرده‌سازی تاریخچه» یا همان squash است که تعداد کامیت‌ها را کاهش می‌دهد.

۹. Remoteها — بردن تاریخچه به جایی دیگر

گیت جدا نمی‌تواند دو تاریخچه را با هم مقایسه کند؛ برای این کار نیاز به مدلی برای «جابجایی» objectها و «نامگذاری» آن‌هاست. در ugit از HTTP ساده استفاده می‌شود:

  • remote add origin <url> — تعریف یک remote جدید (فقط یک فایل تنظیمات).
  • push — کل تاریخچهٔ کامیت‌ها و بلاب‌های گم‌شده را به remote بفرستد (upload-pack ساده).
  • fetch — دریافت کل اشیاء از remote؛ pull یعنی fetch + merge.
pythondef push(remote: str, branch: str) -> None:
    """کامیت ها را به remote بفرست و ref دور را به‌روز کن"""
    remote_refs = fetch_remote_objects(remote, refs=())
    commit = get_commit(get_HEAD())
    while commit not in remote_refs:          # تا وقتی آنجا نداشتیم
        upload_object(remote, commit.oid)     # به remote بفرست
        commit = get_commit(commit.parent)    # و قدم عقب
    update_remote_ref(remote, branch, get_HEAD())

گام‌های بعدی: انجام fetch (دانلود همهٔ اشیاء و ثبت refهای دور به‌صورت refs/remotes/origin/...)، سپس pull = fetch + merge و در انتها squash برای فشرده کردن تاریخچه در ریبیس.

۱۰. جمع‌بندی — چه فهمیدیم؟

حالا یک گیت کوچک کامل ساخته‌ایم. در طول راه یاد گرفتیم که گیت واقعی هم دقیقاً همین ساختارها را دارد:

مفهومپیاده‌سازی ugitدر گیت واقعی
خزانه.ugit/.git/
آبجکت‌ها.ugit/objects/<sha1>.git/objects/ (و packfileها)
فهرست نادیده.ugit/ignore.gitignore
شاخه‌ها.ugit/refs/heads/<name>refs/heads/<name>
شاخهٔ فعال.ugit/HEADHEAD → symbolic ref
مرجmerge-base سه‌طرفههمان + fast-forward و recursive
ذخیرهٔ محتواtype + \x00 + data فشردهٔ zlibtype + size + \x00 + data

با این فهم، اشکال‌زدایی گیت از حدس‌وزدن به دانش واقعی تبدیل شده است — هر بار که git log --graph یا git rebase -i می‌زنید، دقیقاً می‌دانید چه اتفاقی می‌افتد. اگر feel زبانی دارید، کارهای بعدی: پیاده‌سازی squash، بهبود تعارض‌ها و index کامل.
