نوشتن یک وب سرور از صفر — با کمتر از ۶۵۰ خط کد

مقدمه

در این مقاله، گام‌به‌گام ساخت وب سرور مستند شده تا حس کنید چگونه از یک تختهٔ خالی ساخته می‌شود: تصمیم‌های طراحی و پیاده‌سازی (خوب یا بد) و کل فرایند. اولین گامِ فرایند این است که یک کلاس HttpListener کار کند. بعد کمی لاگ‌گیری اضافه می‌کنیم. سپس ساختار پایه را برای برنامهٔ وب‌مان می‌سازیم. بعد مکانیزم ساده‌ای برای مسیریابی فعل‌ها (verbs) و مسیرها به هندلرها پیاده‌سازی می‌کنیم، به احراز هویت و انقضای نشست می‌پردازیم و چند پرس‌وجوی AJAX انجام می‌دهیم.

پیکربندی فعلی این‌ها را پشتیبانی می‌کند:

  • مسیریابی (Routing)
  • مدیر نشست (Session Manager)
  • مجوز (Authorization)
  • نشست‌های منقضی‌شده (Expired Sessions)

چون وب سرور بسیار سبک است، نویسنده کاملاً غیرضروری دید کاری پیچیده مثل پیاده‌سازی پلاگین انجام دهد. سه فایل اصلی وجود دارد:

  • Listener.cs — با HttpListener گوش می‌دهد و به اتصالات پاسخ می‌دهد
  • Router.cs — مسیریابی را مدیریت می‌کند
  • SessionManager.cs — وضعیت نشست‌های اتصال را مدیریت می‌کند

سورس کد روی GitHub میزبانی می‌شود:

Bashgit clone https://github.com/cliftonm/BasicWebServer.git

گام ۱ — HttpListener

اولین گام، راه‌اندازی یک کلاس HttpListener است. نویسنده این مسیر را به‌جای مسیر سوکت سطح پایین انتخاب کرده چون HttpListener خدمات مفید زیادی مثل رمزگشایی درخواست HTML فراهم می‌کند. وب سرور به‌صورت یک کتابخانه پیاده‌سازی می‌شود. برای اولین گام، وب سرور به این‌ها نیاز دارد:

csharpusing System.Net;
using System.Net.Sockets;
using System.Threading;

چون وب سرور اساساً بی‌وضعیت است (به‌جز اشیاء نشست)، بیشتر رفتارها را می‌توان به‌صورت singleton های استاتیک پیاده‌سازی کرد:

csharpnamespace Clifton.WebServer
{
  /// <summary>
  /// یک وب سرور چابک و بی‌رحم.
  /// </summary>
  public static class Server
  {
    private static HttpListener listener;
    // ...

فرض اولیه این است که روی یک شبکهٔ داخلی (intranet) به سرور متصل می‌شویم، پس آدرس‌های IP میزبان محلی را می‌گیریم:

csharp/// <summary>
/// لیست آدرس‌های IP اختصاص‌داده‌شده به دستگاه‌های شبکهٔ localhost،
/// مثل اترنت سیمی، وایرلس و غیره را برمی‌گرداند.
/// </summary>
private static List<IPAddress> GetLocalHostIPs()
{
  IPHostEntry host;
  host = Dns.GetHostEntry(Dns.GetHostName());
  List<IPAddress> ret = host.AddressList.Where(ip => ip.AddressFamily == AddressFamily.InterNetwork).ToList();

  return ret;
}

سپس HttpListener را نمونه‌سازی می‌کنیم و پیشوندهای localhost را اضافه می‌کنیم:

csharpprivate static HttpListener InitializeListener(List<IPAddress> localhostIPs)
{
  HttpListener listener = new HttpListener();
  listener.Prefixes.Add("http://localhost/");

  // به آدرس IP هم گوش کن
  localhostIPs.ForEach(ip =>
  {
    Console.WriteLine("Listening on IP " + "http://" + ip.ToString() + "/");
    listener.Prefixes.Add("http://" + ip.ToString() + "/");
  });

  return listener;
}

با قرض‌گرفتن مفهومی از مقالهٔ «REST — A Simple REST framework»، یک سمافور می‌سازیم که منتظر تعداد مشخصی اتصال هم‌زمان مجاز می‌ماند:

csharppublic static int maxSimultaneousConnections = 20;
private static Semaphore sem = new Semaphore(maxSimultaneousConnections, maxSimultaneousConnections);

این در یک ترد کارگر پیاده‌سازی می‌شود که با Task.Run فراخوانی می‌شود:

csharp/// <summary>
/// شروع گوش‌دادن به اتصالات روی یک ترد کارگر جدا.
/// </summary>
private static void Start(HttpListener listener)
{
  listener.Start();
  Task.Run(() => RunServer(listener));
}

/// <summary>
/// شروع انتظار برای اتصالات، تا مقدار "maxSimultaneousConnections".
/// این کد در یک ترد جدا اجرا می‌شود.
/// </summary>
private static void RunServer(HttpListener listener)
{
  while (true)
  {
    sem.WaitOne();
    StartConnectionListener(listener);
  }
}

در نهایت، شنوندهٔ اتصال را به‌صورت فرایند async قابل انتظار (awaitable) پیاده‌سازی می‌کنیم:

csharp/// <summary>
/// انتظار برای اتصالات.
/// </summary>
private static async void StartConnectionListener(HttpListener listener)
{
  // منتظر اتصال بمان. در حالی که منتظریم کنترل را به فراخواننده برگردان.
  HttpListenerContext context = await listener.GetContextAsync();

  // سمافور را آزاد کن تا شنوندهٔ دیگری بلافاصله شروع شود.
  sem.Release();

  // یک اتصال داریم، یک کاری بکن...
}

پس یک کاری بکنیم:

csharpstring response = "Hello Browser!";
byte[] encoded = Encoding.UTF8.GetBytes(response);
context.Response.ContentLength64 = encoded.Length;
context.Response.OutputStream.Write(encoded, 0, encoded.Length);
context.Response.OutputStream.Close();

و یک متد عمومی Start هم لازم داریم:

csharp/// <summary>
/// وب سرور را شروع می‌کند.
/// </summary>
public static void Start()
{
  List<IPAddress> localHostIPs = GetLocalHostIPs();
  HttpListener listener = InitializeListener(localHostIPs);
  Start(listener);
}

نکتهٔ نویسنده: همیشه پنجرهٔ کنسول وب مرورگر را بازرسی کنید — دوست شماست و همهٔ کارهای غلطی که می‌کنید را به شما می‌گوید! مثلاً در تست بالا متوجه می‌شویم باید مراقب encoding باشیم که در HTML انجام می‌شود: response = "<html><head><meta http-equiv='content-type' content='text/html; charset=utf-8'/></head>Hello Browser!</html>"

گام ۲ — لاگ‌گیری

اول کمی لاگ‌گیری اضافه می‌کنیم، چون برای دیدن اینکه چه درخواست‌هایی از وب سرورمان می‌شود واقعاً مفید است:

csharpLog(context.Request);

/// <summary>
/// لاگ درخواست‌ها.
/// </summary>
public static void Log(HttpListenerRequest request)
{
  Console.WriteLine(request.RemoteEndPoint + " " + request.HttpMethod + " /" + request.Url.AbsoluteUri.RightOf('/', 3));
}

فراخوانی Log را درست بعد از آزادکردن سمافور اضافه می‌کنیم. بعد از اضافه‌کردن لاگر بلافاصله متوجه می‌شویم که مرورگر نه‌تنها صفحهٔ پیش‌فرض را درخواست می‌کند، بلکه دارد favicon.ico را هم می‌خواهد! باید کاری کنیم!

گام ۳ — سرو محتوا: مسیریابی پیش‌فرض

واضح است که نمی‌خواهیم صفحات وب‌مان را به‌صورت رشته در C# کدنویسی کنیم. پس یک ساختار پایه برای برنامهٔ وب‌مان می‌سازیم که کاملاً سلیقه‌ای است: همه‌چیز از پوشهٔ «Website» مشتق می‌شود که این زیرپوشه‌ها را دارد:

  • Pages: ریشهٔ همهٔ صفحات
  • CSS: همهٔ فایل‌های .css و مرتبط
  • Scripts: همهٔ فایل‌های .js
  • Images: همهٔ فایل‌های تصویری

برای مدیریت عملکرد پایه، به آغاز یک مسیریاب نیاز داریم. اولین نسخه فقط با فایل‌های موجود در پوشهٔ «Website» و زیرپوشه‌ها — بر اساس مسیر URL و پسوند درخواست — پاسخ می‌دهد. اول چند اطلاعات از درخواست URL استخراج می‌کنیم:

csharpHttpListenerRequest request = context.Request;
string path = request.RawUrl.LeftOf("?"); // فقط مسیر، نه پارامترها
string verb = request.HttpMethod; // get, post, delete و غیره
string parms = request.RawUrl.RightOf("?"); // پارامترهای URL بعد از ؟ می‌آیند
Dictionary<string, string> kvParams = GetKeyValues(parms); // به ورودی‌های کلید-مقدار تبدیل کن

حالا می‌توانیم این اطلاعات را به مسیریاب بدهیم: router.Route(verb, path, kvParams);

به‌جای عبارت‌های switch (که نویسنده دوست ندارد)، نگاشتی از پسوندهای شناخته‌شده و مکان‌های لودرشان مقداردهی می‌کنیم. در نظر بگیرید توابع متفاوتی چطور می‌توانند محتوا را مثلاً از پایگاه داده لود کنند:

csharppublic class Router
{
  public string WebsitePath { get; set; }

  private Dictionary<string, ExtensionInfo> extFolderMap;

  public Router()
  {
    extFolderMap = new Dictionary<string, ExtensionInfo>() 
    {
      {"ico", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/ico"}},
      {"png", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/png"}},
      {"jpg", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/jpg"}},
      {"gif", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/gif"}},
      {"bmp", new ExtensionInfo() {Loader=ImageLoader, ContentType="image/bmp"}},
      {"html", new ExtensionInfo() {Loader=PageLoader, ContentType="text/html"}},
      {"css", new ExtensionInfo() {Loader=FileLoader, ContentType="text/css"}},
      {"js", new ExtensionInfo() {Loader=FileLoader, ContentType="text/javascript"}},
      {"", new ExtensionInfo() {Loader=PageLoader, ContentType="text/html"}},
    };
  }
  // ...

توجه کنید حالت «بدون پسوند» را هم مدیریت می‌کنیم که فرض می‌کند محتوا یک صفحهٔ HTML خواهد بود. همچنین content type را تنظیم می‌کنیم — اگر نکنیم، در کنسول وب هشدار «محتوا از نوع خاصی فرض شده» می‌گیریم. در نهایت توجه کنید که تابعی برای انجام لود واقعی نشان می‌دهیم.

Image Loader

csharp/// <summary>
/// یک فایل تصویری را می‌خواند و با دادهٔ خام یک ResponsePacket برمی‌گرداند.
/// </summary>
private ResponsePacket ImageLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  FileStream fStream = new FileStream(fullPath, FileMode.Open, FileAccess.Read);
  BinaryReader br = new BinaryReader(fStream);
  ResponsePacket ret = new ResponsePacket() { Data = br.ReadBytes((int)fStream.Length), ContentType = extInfo.ContentType };
  br.Close();
  fStream.Close();

  return ret;
}

File Loader

csharp/// <summary>
/// یک فایل اساساً متنی را می‌خواند و با متن UTF8 کدشده یک ResponsePacket برمی‌گرداند.
/// </summary>
private ResponsePacket FileLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  string text = File.ReadAllText(fullPath);
  ResponsePacket ret = new ResponsePacket() { Data = Encoding.UTF8.GetBytes(text), ContentType = extInfo.ContentType, Encoding = Encoding.UTF8 };

  return ret;
}

Page Loader

Page loader باید برای مدیریت گزینه‌هایی مثل این‌ها کار بیشتری کند:

  • foo.com
  • foo.com\index
  • foo.com\index.html

همهٔ این ترکیب‌ها به لود Pages\index.html ختم می‌شوند:

csharp/// <summary>
/// یک فایل HTML را لود می‌کند؛ پسوندهای گم‌شده و IP/دامنهٔ بدون فایل را هم
/// حساب می‌کند که باید به index.html پیش‌فرض برگردد.
/// </summary>
private ResponsePacket PageLoader(string fullPath, string ext, ExtensionInfo extInfo)
{
  ResponsePacket ret = new ResponsePacket();

  if (fullPath == WebsitePath) // اگر بعد از نام دامنه یا IP چیزی نیامد، به لود index.html پیش‌فرض برو
  {
    ret = Route(GET, "/index.html", null);
  }
  else
  {
    if (String.IsNullOrEmpty(ext))
    {
      // پسوند نیست، پس ".html" می‌سازیم
      fullPath = fullPath + ".html";
    }

    // پوشهٔ "Pages" را به مسیر تزریق کن
    fullPath = WebsitePath + "\\Pages" + fullPath.RightOf(WebsitePath);
    ret = FileLoader(fullPath, ext, extInfo);
  }

  return ret;
}

دو کلاس کمکی داریم و بعد از کنار هم گذاشتن همه‌چیز، آغاز یک مسیریاب داریم که حالا محتوای موجود در فایل‌ها را برمی‌گرداند:

csharppublic ResponsePacket Route(string verb, string path, Dictionary<string, string> kvParams)
{
  string ext = path.RightOf('.');
  ExtensionInfo extInfo;
  ResponsePacket ret = null;

  if (extFolderMap.TryGetValue(ext, out extInfo))
  {
    // '/' ابتدایی را حذف کن و با جداکنندهٔ مسیر ویندوز قالب‌بندی کن
    string fullPath = Path.Combine(WebsitePath, path);
    ret = extInfo.Loader(fullPath, ext, extInfo);
  }

  return ret;
}

یک بازسازی نهایی هم لازم داریم — حذف پاسخ تست و جایگزینی با محتوای برگردانده‌شده توسط مسیریاب:

csharpprivate static void Respond(HttpListenerResponse response, ResponsePacket resp)
{
  response.ContentType = resp.ContentType;
  response.ContentLength64 = resp.Data.Length;
  response.OutputStream.Write(resp.Data, 0, resp.Data.Length);
  response.ContentEncoding = resp.Encoding;
  response.StatusCode = (int)HttpStatusCode.OK;
  response.OutputStream.Close();
}
نکته: اینجا آشکار می‌شود که مکان واقعی فایل «محتوا» می‌تواند کاملاً توسط سرور جعل شود. نویسنده همهٔ محتوای HTML را زیر پوشهٔ Pages گذاشته و بدین ترتیب مکان ریشه را جعل می‌کند. می‌توانیم کارهای دیگری هم بکنیم — لود داده از پایگاه داده، ارتباط با سرور دیگر، تولید پویای صفحه از داده... — این‌ها همه قابلیت‌هایی هستند که در ادامه‌ٔ بارگذاری محتوای پیش‌فرض بررسی می‌شوند.

گام ۴ — شیطان در جزئیات است

صفحات خطا

چند صفحهٔ خطا اضافه می‌کنیم (حتی اگر الان از همه استفاده نکنیم):

  • نشست منقضی‌شده
  • مجاز نبودن
  • پیدا نشدن صفحه
  • خطای سرور
  • نوع ناشناخته

برای اینکه برنامه بتواند تعیین کند این صفحات برای خطای داده‌شده کجا هستند، یک enum به سرور اضافه می‌کنیم:

csharppublic enum ServerError
{
  OK,
  ExpiredSession,
  NotAuthorized,
  FileNotFound,
  PageNotFound,
  ServerError,
  UnknownType,
}

حالا می‌توانیم شروع کنیم به مدیریت خطاها (بدون پرتاب استثنا). اول پسوند ناشناخته:

csharpif (extFolderMap.TryGetValue(ext, out extInfo))
{
 // ...
}
else
{
  ret = new ResponsePacket() { Error = Server.ServerError.UnknownType };
}

و مانند آن. برای مدیریت خطاها از یک callback استفاده می‌کنیم که برنامهٔ وب می‌تواند فراهم کند — به شکل صفحه‌ای که کاربر باید به آن هدایت شود:

csharpResponsePacket resp = router.Route(verb, path, kvParams);

if (resp.Error != ServerError.OK)
{
  resp = router.Route("get", onError(resp.Error), null);
}

Respond(context.Response, resp);

و یک هندلر خطای سرراست در برنامهٔ وب:

csharppublic static string ErrorHandler(Server.ServerError error)
{
  string ret = null;

  switch (error)
  {
    case Server.ServerError.ExpiredSession:
      ret= "/ErrorPages/expiredSession.html";
      break;
    case Server.ServerError.FileNotFound:
      ret = "/ErrorPages/fileNotFound.html";
      break;
    case Server.ServerError.NotAuthorized:
      ret = "/ErrorPages/notAuthorized.html";
      break;
    case Server.ServerError.PageNotFound:
      ret = "/ErrorPages/pageNotFound.html";
      break;
    case Server.ServerError.ServerError:
      ret = "/ErrorPages/serverError.html";
      break;
    case Server.ServerError.UnknownType:
      ret = "/ErrorPages/unknownType.html";
      break;
  }

  return ret;
}

البته باید هندلر خطا را هم مقداردهی کنیم: Server.onError = ErrorHandler;

هدایت (Redirects)

توجه خواهید کرد URL در پیام‌های خطای بالا برای نشان‌دادن صفحه تغییر نکرده. این به این خاطر است که redirect پاسخ را نداریم. وقت رفع این مشکل است: فرض می‌کنیم هندلر خطا همیشه ما را به صفحهٔ دیگری هدایت می‌کند، پس نحوهٔ مدیریت پاسخ را عوض می‌کنیم. به‌جای گرفتن ResponsePacket جدید و فرستادن آن محتوا به مرورگر، خصوصیت Redirect را روی صفحه‌ای می‌گذاریم که برنامهٔ وب می‌خواهد برویم. این به‌طور کلی به مکانیزم redirect یونیورسال تبدیل می‌شود:

csharpif (resp.Error != ServerError.OK)
{
  resp.Redirect = onError(resp.Error);
}

و کمی بازسازی در متد Respond:

csharpprivate static void Respond(HttpListenerRequest request, HttpListenerResponse response, ResponsePacket resp)
{
  if (String.IsNullOrEmpty(resp.Redirect))
  {
    response.ContentType = resp.ContentType;
    response.ContentLength64 = resp.Data.Length;
    response.OutputStream.Write(resp.Data, 0, resp.Data.Length);
    response.ContentEncoding = resp.Encoding;
    response.StatusCode = (int)HttpStatusCode.OK;
  }
  else
  {
    response.StatusCode = (int)HttpStatusCode.Redirect;
    response.Redirect("http://" + request.UserHostAddress + resp.Redirect);
  }

  response.OutputStream.Close();
}
نکته: بستن استریم خروجی خیلی مهم است. اگر نبندید، مرورگر می‌تواند منتظر داده بماند. و توجه کنید چون خطاها را با redirect مدیریت می‌کنیم، تنها دو کد وضعیت ممکن که وب سرورمان می‌تواند پاسخ دهد OK و Redirect است.

مدیریت استثنا

از همان مکانیزم redirect برای گرفتن استثناهای واقعی استفاده می‌کنیم — با پیچیدن ادامهٔ GetContextAsync در یک بلوک try-catch:

csharpcatch(Exception ex)
{
  Console.WriteLine(ex.Message);
  Console.WriteLine(ex.StackTrace);
  resp = new ResponsePacket() { Redirect = onError(ServerError.ServerError) };
}

حالا با فعل‌ها سروکار داریم، به‌خصوص فعل POST. این به ما اجازه می‌دهد سه مورد بعدی لیست را حل کنیم.

فعل‌ها (Verbs)

فعل‌های متعددی می‌توانند همراه درخواست HTTP باشند: OPTIONS, GET, HEAD, POST, PUT, DELETE, TRACE, CONNECT. در اصل وب سرور واقعاً به فعل کاری ندارد — فعل فقط اطلاعات اضافه‌ای می‌دهد که با کدام هندلر برای پاسخ فراخوانی شود. بالاخره به موضوعی می‌رسیم که نویسنده تا حالا از آن فرار کرده — کنترلرها (controllers). به‌جای اینکه وب سرور از الگوی Model-View-Controller خبر داشته باشد یا آن را به توسعه‌دهندهٔ برنامهٔ وب تحمیل کند، وب سرورِ پیاده‌سازی‌شده مکانیزم ساده‌ای برای مسیریابی فعل‌ها و مسیرها به هندلرها فراهم می‌کند. همهٔ کاری که باید بکند همین است. هندلر به نوبهٔ خود تعیین می‌کند مرورگر باید به صفحهٔ دیگری هدایت شود یا روی صفحهٔ فعلی بماند.

مسیرها (Routes)

با یک مسیریاب پایه شروع می‌کنیم که از یک کلاس Route تشکیل شده:

csharppublic class Route
{
  public string Verb { get; set; }
  public string Path { get; set; }
  public Func<Dictionary<string,string>, string> Action { get; set; }
}

توجه کنید خصوصیت Action یک تابع callback است که پارامترهای URL را می‌گیرد (با پارامترهای post بعداً کار داریم) و یک «URL هدایتِ» اختیاری انتظار دارد.

csharppublic void AddRoute(Route route)
{
  routes.Add(route);
}

حالا می‌توانیم فراخوانی هندلرهای خاص برنامه را پیاده‌سازی کنیم، که یک بازسازی از متد Route است:

csharppublic ResponsePacket Route(string verb, string path, Dictionary<string, string> kvParams)
{
  string ext = path.RightOfRightmostOf('.');
  ExtensionInfo extInfo;
  ResponsePacket ret = null;
  verb = verb.ToLower();

  if (extFolderMap.TryGetValue(ext, out extInfo))
  {
    string wpath = path.Substring(1).Replace('/', '\\'); // '/' ابتدایی را حذف کن و با جداکنندهٔ مسیر ویندوز قالب‌بندی کن
    string fullPath = Path.Combine(WebsitePath, wpath);

    Route route = routes.SingleOrDefault(r => verb == r.Verb.ToLower() && path == r.Path);

    if (route != null)
    {
      // برنامه برای این مسیر هندلر دارد
      string redirect = route.Action(kvParams);

      if (String.IsNullOrEmpty(redirect))
      {
        // با لودر محتوای پیش‌فرض پاسخ بده
        ret = extInfo.Loader(fullPath, ext, extInfo);
      }
      else
      {
        // با redirect پاسخ بده
        ret = new ResponsePacket() { Redirect = redirect };
      }
    }
    else
    {
      // رفتار پیش‌فرض را امتحان کن
      ret = extInfo.Loader(fullPath, ext, extInfo);
    }
  }
  else
  {
    ret = new ResponsePacket() { Error = Server.ServerError.UnknownType };
  }

  return ret;
}

حالا صفحهٔ دمو را تغییر می‌دهیم تا وقتی دکمه کلیک می‌شود یک فراخوان POST به سرور بکند و در هندلرمان به صفحهٔ دیگری هدایت شویم. بله، این کار می‌توانست کاملاً در جاوااسکریپت انجام شود، اما این‌جا داریم هندلرهای فعل-مسیر را نشان می‌دهیم، پس این رفتار را سمت سرور پیاده‌سازی می‌کنیم.

همچنین پردازش استریم ورودی درخواست به جفت‌های کلید-مقدار و لاگ پارامترها (هم URL و هم پارامترهای استریم ورودی) را اضافه می‌کنیم:

csharpprivate static async void StartConnectionListener(HttpListener listener)
{
  // ...
  Dictionary<string, string> kvParams = GetKeyValues(parms); // به ورودی‌های کلید-مقدار تبدیل کن
  string data = new StreamReader(context.Request.InputStream, context.Request.ContentEncoding).ReadToEnd();
  GetKeyValues(data, kvParams);
  Log(kvParams);
  // ...
}

private static Dictionary<string, string> GetKeyValues(string data, Dictionary<string, string> kv = null)
{
  kv.IfNull(() => kv = new Dictionary<string, string>());
  data.If(d => d.Length > 0, (d) => d.Split('&').ForEach(keyValue => kv[keyValue.LeftOf('=')] = keyValue.RightOf('=')));

  return kv;
}

private static void Log(Dictionary<string, string> kv)
{
  kv.ForEach(kvp=>Console.WriteLine(kvp.Key+" : "+kvp.Value));
}

ممکن است ترکیب پارامترهای URL و پارامترهای postback در یک مجموعهٔ جفت-کلید-مقدار عادت بدی باشد، اما فعلاً به همین پیاده‌سازی «ساده‌تر» بسنده می‌کنیم.

صفحهٔ HTML جدید /demo/redirect با یک فرم که به /demo/redirect با متد post می‌رود، و دکمهٔ «Redirect Me» با نام redirectButton می‌سازیم. اگر دقت کنید، در لاگ اول GET را هنگام لود صفحه می‌بینیم، سپس با کلیک روی دکمه POST با پارامترها را. چیز جالب نوشتن وب سرور خودتان این است که واقعاً حس عمیق‌تری از آنچه پشت صحنه می‌شود می‌گیرید.

حالا یک هندلر برای این فعل و مسیر ثبت می‌کنیم:

csharpstatic void Main(string[] args)
{
  string websitePath = GetWebsitePath();
  Server.onError = ErrorHandler;

  // ثبت یک هندلر مسیر:
  Server.AddRoute(new Route() { Verb = Router.POST, Path = "/demo/redirect", Action = RedirectMe });

  Server.Start(websitePath);

public static string RedirectMe(Dictionary<string, string> parms)
{
  return "/demo/clicked";
}

و حالا با کلیک روی دکمه هدایت می‌شویم. این آسان بود. با حداقل بازسازی، این سه مورد را حل کرده‌ایم:

  • فعل همیشه «get» فرض می‌شد
  • برنامه هیچ گزینه‌ای برای دستکاری محتوا (به‌خصوص HTML) بعد از لود نداشت
  • نمی‌شد مسیریابی را override کرد

گام ۶ — احراز هویت و انقضای نشست

در گام ۵ یک هندلر مسیر خیلی پایه پیاده کردیم. چیزی کمی پیشرفته‌تر می‌خواهیم که کارهای کاملاً رایج را مدیریت کند:

  • مطمئن شدن کاربر مجاز به دیدن صفحه است
  • بررسی اینکه نشست منقضی شده یا نه

callback های هندلر بالا را بازسازی می‌کنیم تا از یک کلاس Routing استفاده کنند که هم رفتارهای داخلی فراهم می‌کند و هم به توسعه‌دهندهٔ برنامهٔ وب اجازه می‌دهد رفتارهای اضافه خودش (مثل احراز هویت مبتنی بر نقش) را جایگزین یا اضافه کند.

مدیریت نشست

اول یک کلاس پایهٔ Session و SessionManager اضافه می‌کنیم:

csharpusing System;
using System.Collections.Generic;
using System.Linq;
using System.Net;
using System.Text;
using System.Threading.Tasks;

using Clifton.ExtensionMethods;

namespace Clifton.WebServer
{
  /// <summary>
  /// نشست‌ها با IP کلاینت مرتبط می‌شوند.
  /// </summary>
  public class Session
  {
    public DateTime LastConnection { get; set; }
    public bool Authorized { get; set; }

    /// <summary>
    /// می‌تواند توسط کنترلرها برای افزودن اطلاعات اضافه‌ای که باید در نشست بمانند استفاده شود.
    /// </summary>
    public Dictionary<string, string> Objects { get; set; }

    public Session()
    {
      Objects = new Dictionary<string, string>();
      UpdateLastConnectionTime();
    }

    public void UpdateLastConnectionTime()
    {
      LastConnection = DateTime.Now;
    }

    /// <summary>
    /// اگر آخرین درخواست از زمان انقضای مشخص‌شده (به ثانیه) گذشته باشد true برمی‌گرداند.
    /// </summary>
    public bool IsExpired(int expirationInSeconds)
    {
      return (DateTime.Now - LastConnection).TotalSeconds > expirationInSeconds;
    }
  }

  public class SessionManager
  {
    /// <summary>
    /// همهٔ نشست‌ها را پیگیری کن.
    /// </summary>
    protected Dictionary<IPAddress, Session> sessionMap = new Dictionary<IPAddress, Session>();

    public SessionManager()
    {
      sessionMap = new Dictionary<IPAddress, Session>();
    }

    /// <summary>
    /// نشست موجود برای این remote endpoint را می‌سازد یا برمی‌گرداند.
    /// </summary>
    public Session GetSession(IPEndPoint remoteEndPoint)
    {
      // پورت روی remote endpoint همیشه عوض می‌شود، پس فقط از بخش IP استفاده می‌کنیم.
      // ...
    }
  }
}

سه کلاس اضافه می‌کنیم که برنامه می‌تواند از آن‌ها استفاده کند:

  • AuthenticatedRouteHandler
  • AuthenticatedExpirableRouteHandler
csharpnamespace Clifton.WebServer
{
  /// <summary>
  /// کلاس پایهٔ هندلرهای مسیر.
  /// </summary>
  public abstract class RouteHandler
  {
    protected Func<Session, Dictionary<string, string>, string> handler;

    public RouteHandler(Func<Session, Dictionary<string, string>, string> handler)
    {
      this.handler = handler;
    }

    public abstract string Handle(Session session, Dictionary<string, string> parms);
  }

  // AuthenticatedRouteHandler و AuthenticatedExpirableRouteHandler
  // از RouteHandler مشتق می‌شوند و مدیریت وضعیت Authorized و
  // انقضای نشست را در متد Handle خود پیاده‌سازی می‌کنند.
}

و مثالی از ثبت هندلر احراز هویت‌شده:

csharpstatic void Main(string[] args)

چرا کلاس به‌جای attribute؟ نویسنده از روزهای اول کار با C# گفته: attribute ها برای دادن نکته به serializer دربارهٔ نحوهٔ سریال‌کردن فیلدها عالی‌اند؛ در غیر این صورت بیشتر طراحی بد را ترویج می‌کنند. مثلاً مسیرهای نوشته‌شده با کلاس پایهٔ Route و کلاس فرزند AuthenticatedRoute پیاده‌سازی می‌شوند. اگر احراز هویت مبتنی بر نقش می‌خواهید، کلاس مشتق‌شده می‌سازید به‌جای اینکه attribute روی تابع‌های کنترلرِ اغلب خالی بگذارید.

نتیجه‌گیری

ایده این است که وب سرور خیلی کوچک بماند. نویسنده در مجموع چهار کلاس دارد (بدون احتساب متدهای extension) و کل چیز کمی کمتر از ۶۵۰ خط کد است، با کامنت و هر چه حساب کنید.

نکتهٔ جالب (و آخرین حرف نویسنده بالای منبرش) این است که با پیاده‌سازی وب سرور خودش متوجه شده فناوری‌هایی مثل MVC Razor و Ruby on Rails چقدر سر راهِ سروکردن صفحات وب و دادن کنترل رندر محتوای غیرایستا به برنامه‌نویس می‌ایستند. با یک وب سرور ساده، او خیلی بیشتر روی جاوااسکریپت سمت کلاینت، HTML و کامپوننت‌ها تمرکز می‌کند، جایی که تنها توجه لازم به فرایند سمت سرور، هندلرهای PUT و درخواست AJAX گاه‌به‌گاه است.
