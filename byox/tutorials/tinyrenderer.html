درس ۰: شروع به کار

این یک رسترایزر (rasterizer) نرم‌افزاری کوچک است؛ اگر دنبال یک ردگیر پرتو (ray tracer) نرم‌افزاری کوچک هستید، می‌توانید آن را اینجا پیدا کنید.

کد منبع من بی‌اهمیت است. ویکی را بخوانید و رندرر خودتان را پیاده‌سازی کنید. فقط وقتی از تمام جزئیات ریز عبور کنید، درخواهید یافت چه اتفاقی در حال رخ دادن است.

من واقعاً از دریافت ایمیل برای بازخورد استقبال می‌کنم (dmitry.sokolov@univ-lorraine.fr)؛ اگر سؤالی دارید، در تماس با من تردید نکنید.

اگر معلم هستید و می‌خواهید این مطالب را برای کلاس خود استفاده/اقتباس کنید، خوش‌آمدید؛ نیازی به مجوز نیست. فقط با ایمیل به من اطلاع دهید تا به بهبود دوره کمک کنم.

چرا این دوره؟

در این سری مقاله‌ها می‌خواهم با نوشتن یک کلون (نسخه بسیار ساده‌شده) از OpenGL نشان دهم که OpenGL چطور کار می‌کند. به‌اندازه کافی جالب است که من اغلب با افرادی روبرو می‌شوم که نمی‌توانند بر مانع اولیه یادگیری OpenGL/DirectX غلبه کنند. از این رو، یک سری سخنرانی کوتاه آماده کرده‌ام که پس از آن، دانشجویانم رندررهای کاملاً خوبی نشان می‌دهند.

بنابراین، وظیفه این‌گونه فرموله می‌شود: بدون استفاده از هیچ کتابخانه شخص ثالث (به‌ویژه کتابخانه‌های گرافیکی)، چیزی شبیه به این تصویر به دست آورید:

هشدار: این یک مطلب آموزشی است که ساختار کتابخانه OpenGL را تقریباً تکرار می‌کند. این یک رندرر نرم‌افزاری خواهد بود. نمی‌خواهم نشان دهم چطور برنامه‌هایی برای OpenGL بنویسید؛ می‌خواهم نشان دهم OpenGL چگونه کار می‌کند. عمیقاً متقاعد شده‌ام که بدون درک این موضوع، نوشتن برنامه‌های کارآمد با کتابخانه‌های سه‌بعدی غیرممکن است.

سعی خواهم کرد کد نهایی را حدود ۵۰۰ خط نگه دارم. دانشجویان من برای شروع ساخت چنین رندررهایی به ۱۰ تا ۲۰ ساعت برنامه‌نویسی نیاز دارند. در ورودی، یک فایل تست با پلی‌گون سیمی + تصاویر بافت دریافت می‌کنیم. در خروجی، یک مدل رندر شده به دست می‌آوریم. هیچ رابط گرافیکی وجود ندارد؛ برنامه به‌سادگی یک تصویر تولید می‌کند.

از آنجا که هدف به حداقل رساندن وابستگی‌های خارجی است، فقط یک کلاس به دانشجویانم می‌دهم که امکان کار با فایل‌های TGA را فراهم می‌کند. این یکی از ساده‌ترین فرمت‌هایی است که از تصاویر RGB/RGBA و سیاه‌وسفید پشتیبانی می‌کند. بنابراین، به‌عنوان نقطه شروع، راهی ساده برای کار با تصاویر به دست می‌آوریم. باید توجه داشته باشید که تنها قابلیت موجود در ابتدا (علاوه بر بارگذاری و ذخیره تصاویر)، توانایی تنظیم رنگ یک پیکسل است.

هیچ تابعی برای رسم پاره‌خط و مثلث وجود ندارد. باید همه این کارها را با دست انجام دهیم. من کد منبعی را ارائه می‌دهم که به موازات دانشجویان می‌نویسم؛ اما توصیه نمی‌کنم از آن استفاده کنید، زیرا منطقی ندارد. کل کد روی گیت‌هاب در دسترس است و اینجا کد منبعی را می‌یابید که به دانشجویانم می‌دهم.

درس ۱: الگوریتم رسم خط برسنهام

تلاش اول

هدف درس اول رندر مش سیمی (wire mesh) است. برای این کار باید یاد بگیریم پاره‌خط رسم کنیم. می‌توانیم به سادگی بخوانیم الگوریتم خط برسنهام چیست، اما بیایید خودمان کد بنویسیم. ساده‌ترین کدی که یک پاره‌خط بین نقاط (x0, y0) و (x1, y1) رسم می‌کند چطور به نظر می‌رسد؟ ظاهراً چیزی شبیه به این:

cppvoid line(int x0, int y0, int x1, int y1, TGAImage &image, TGAColor color) {
    for (float t=0.; t<1.; t+=.01) {
        int x = x0 + (x1-x0)*t;
        int y = y0 + (y1-y0)*t;
        image.set(x, y, color);
    }
}

نسخه‌ای از کد در اینجا در دسترس است.

تلاش دوم

مشکل این کد (علاوه بر ناکارآمدی آن) انتخاب ثابت است که آن را برابر ۰٫۰۱ گرفتم. اگر آن را برابر ۰٫۱ بگیریم، پاره‌خط ما به این شکل خواهد بود:

می‌توانیم به‌راحتی گام لازم را پیدا کنیم: آن چیزی نیست جز تعداد پیکسل‌هایی که باید رسم شوند. ساده‌ترین (اما غلط) کد چیزی شبیه به موارد زیر است:

cppvoid line(int x0, int y0, int x1, int y1, TGAImage &image, TGAColor color) {
    for (int x=x0; x<=x1; x++) {
        float t = (x-x0)/(float)(x1-x0);
        int y = y0*(1.-t) + y1*t;
        image.set(x, y, color);
    }
}

احتیاط! اولین منبع خطا در کدهای دانشجویان من در چنین مواردی، تقسیم صحیح (integer division) است، مانند (x-x0)/(x1-x0). سپس اگر با این کد بخواهیم خطوط زیر را رسم کنیم:

cppline(13, 20, 80, 40, image, white);
line(20, 13, 40, 80, image, red);
line(80, 40, 13, 20, image, red);

معلوم می‌شود که یک خط خوب است، خط دوم سوراخ دارد و اصلاً خط سومی وجود ندارد. توجه کنید که خط اول و سوم (در کد) همان خط را با رنگ‌های مختلف و در جهت‌های مختلف رسم می‌کنند (با جابه‌جایی نقطه مبدأ و مقصد). خط سفید را قبلاً دیده‌ایم، خوب رسم شده است. امیدوار بودم رنگ خط سفید را به قرمز تغییر دهم، اما نتوانستم. این یک تست برای تقارن است: نتیجه رسم یک پاره‌خط نباید به ترتیب نقاط بستگی داشته باشد؛ پاره‌خط (a,b) باید دقیقاً همان پاره‌خط (b,a) باشد.

تلاش سوم

خط قرمز گم‌شده را با جابه‌جایی نقاط طوری که x0 همیشه کمتر از x1 باشد، درست می‌کنیم.

سوراخ‌ها در یکی از پاره‌خط‌ها به این دلیل است که ارتفاع آن بیشتر از عرضش است. دانشجویان من اغلب راه‌حل زیر را پیشنهاد می‌کنند:

cppif (dx>dy) {for (int x)} else {for (int y)}

عجب!

cppvoid line(int x0, int y0, int x1, int y1, TGAImage &image, TGAColor color) {
    bool steep = false;
    if (std::abs(x0-x1)<std::abs(y0-y1)) { // اگر خط تند است، تصویر را ترانهاده می‌کنیم
        std::swap(x0, y0);
        std::swap(x1, y1);
        steep = true;
    }
    if (x0>x1) { // آن را چپ‌به‌راست می‌کنیم
        std::swap(x0, x1);
        std::swap(y0, y1);
    }
    for (int x=x0; x<=x1; x++) {
        float t = (x-x0)/(float)(x1-x0);
        int y = y0*(1.-t) + y1*t;
        if (steep) {
            image.set(y, x, color); // اگر ترانهاده شده بود، ترانهاده‌ی معکوس
        } else {
            image.set(x, y, color);
        }
    }
}

زمان‌بندی: تلاش چهارم

هشدار: بهینه‌ساز کامپایلر (g++ -O3) اغلب در تولید کد سریع از شما (و من) بهتر است. این بخش به دلایل تاریخی/فرهنگی اینجا آمده است.

این کد عالی کار می‌کند. دقیقاً همین سطح از پیچیدگی را در نسخه نهایی رندررمان می‌خواهم. قطعاً ناکارآمد است (تقسیم‌های متعدد و چیزهایی از این دست)، اما کوتاه و خوانا است. توجه کنید که هیچ assert و بررسی‌ای برای خارج‌نشدن از مرزها ندارد، که بد است. در این مقاله‌ها سعی می‌کنم این کد خاص را بیش از حد شلوغ نکنم، چون زیاد خوانده می‌شود. در عین حال، به‌طور سیستماتیک به لزوم انجام بررسی‌ها یادآوری می‌کنم.

پس کد قبلی خوب کار می‌کند، اما می‌توانیم آن را بهینه کنیم. بهینه‌سازی چیز خطرناکی است. باید در مورد پلتفرمی که کد روی آن اجرا می‌شود شفاف باشیم. بهینه‌سازی کد برای یک کارت گرافیک یا فقط برای CPU — دو چیز کاملاً متفاوت هستند. قبل و در حین هر بهینه‌سازی، کد باید پروفایل شود. سعی کنید حدس بزنید کدام عملیات در اینجا بیشترین منابع را مصرف می‌کند؟

برای تست، ۱٬۰۰۰٬۰۰۰ بار سه پاره‌خطی را رسم می‌کنم که قبلاً رسم کردیم. CPU من Intel® Core™ i5-3450 با فرکانس 3.10GHz است. برای هر پیکسل، این کد سازنده کپی کلاس TGAColor را صدا می‌زند. یعنی 1000000 * 3 پاره‌خط * تقریباً ۵۰ پیکسل برای هر پاره‌خط. تعداد تماس‌های زیادی است، نه؟ از کجا بهینه‌سازی را شروع کنیم؟ پروفایلر به ما خواهد گفت.

ادامه تلاش چهارم

باید توجه داشته باشیم که هر تقسیم، مقسوم‌علیه یکسانی دارد. آن را از حلقه خارج کنیم. متغیر خطا (error) فاصله تا بهترین خط راست را از پیکسل فعلی (x, y) به ما می‌دهد. هر بار که خطا از یک پیکسل بیشتر شود، y را یک واحد افزایش (یا کاهش) می‌دهیم و خطا را هم یک واحد کم می‌کنیم.

کد در اینجا در دسترس است.

cppvoid line(int x0, int y0, int x1, int y1, TGAImage &image, TGAColor color) {
    bool steep = false;
    if (std::abs(x0-x1)<std::abs(y0-y1)) {
        std::swap(x0, y0);
        std::swap(x1, y1);
        steep = true;
    }
    if (x0>x1) {
        std::swap(x0, x1);
        std::swap(y0, y1);
    }
    int dx = x1-x0;
    int dy = y1-y0;
    float derror = std::abs(dy/float(dx));
    float error = 0;
    int y = y0;
    for (int x=x0; x<=x1; x++) {
        if (steep) {
            image.set(y, x, color);
        } else {
            image.set(x, y, color);
        }
        error += derror;
        if (error>.5) {
            y += (y1>y0?1:-1);
            error -= 1.;
        }
    }
}

زمان‌بندی: تلاش پنجم و پایانی

چرا به اعداد شناور نیاز داریم؟ تنها دلیل، یک تقسیم بر dx و مقایسه با ۰٫۵ در بدنه حلقه است. می‌توانیم با جایگزینی متغیر خطا با متغیری دیگر از شر اعداد شناور خلاص شویم. بیایید آن را error2 بنامیم و فرض کنیم برابر است با error * dx * 2. این کد معادل است:

    if (std::abs(x0-x1)<std::abs(y0-y1)) {

        std::swap(x0, x1);
        std::swap(y0, y1);

    int dy = y1-y0;

    int y = y0;

            image.set(y, x, color);

            image.set(x, y, color);

        error2 += derror2;

یک روش خوب رسم مثلث باید ویژگی‌های زیر را داشته باشد:

  • باید (سورپرایز!) ساده و سریع باشد.
  • باید متقارن باشد: تصویر نباید به ترتیب رئوسِ وردی به تابع رسم بستگی داشته باشد.
  • اگر دو مثلث دو رأس مشترک داشته باشند، به دلیل گردشدن رسترایزیشن نباید بین آن‌ها سوراخی باشد.
  • می‌توانستیم الزامات بیشتری اضافه کنیم، اما به همین‌ها اکتفا می‌کنیم. روش سنتی، جاروب خطی (line sweeping) است:
  • رئوس مثلث را بر اساس مختصات y مرتب کنید؛
  • ضلع چپ و راست مثلث را هم‌زمان رسترایز کنید؛
  • بین نقاط مرزی چپ و راست، یک پاره‌خط افقی رسم کنید.

در این نقطه دانشجویان من شروع به از دست دادن زمین محکم می‌کنند: کدام پاره‌خط چپی است و کدام‌یک راستی؟ علاوه بر این، مثلث سه پاره‌خط دارد... معمولاً بعد از این مقدمه، حدود یک ساعت دانشجویانم را رها می‌کنم: باز هم می‌گویم خواندن کد من بسیار کم‌ارزش‌تر از مقایسه کد خودتان با کد من است.

    // مرتب‌سازی رئوس: t0، t1، t2 از پایین به بالا (مرتب‌سازی حبابی، هورا!)
    if (t0.y>t1.y) std::swap(t0, t1);
    if (t0.y>t2.y) std::swap(t0, t2);
    if (t1.y>t2.y) std::swap(t1, t2);
    int total_height = t2.y-t0.y;
    for (int i=0; i<total_height; i++) {
        bool second_half = i>t1.y-t0.y || t1.y==t0.y;
        int segment_height = second_half ? t2.y-t1.y : t1.y-t0.y;
        float alpha = (float)i/total_height;
        float beta  = (float)(i-(second_half ? t1.y-t0.y : 0))/segment_height; // مراقب باشید: با شرایط بالا اینجا تقسیم بر صفر رخ نمی‌دهد
        Vec2i A =               t0 + (t2-t0)*alpha;
        Vec2i B = second_half ? t1 + (t2-t1)*beta : t0 + (t1-t0)*beta;
        if (A.x>B.x) std::swap(A, B);
        for (int j=A.x; j<=B.x; j++) {
            image.set(j, t0.y+i, color); // توجه: به دلیل تبدیل int، t0.y+i برابر با A.y نیست
        }

حاشیه‌رو: اگر بخواهم کدی برای بررسی تعلق نقطه به پلی‌گون پیاده‌سازی کنم و این برنامه روی یک هواپیما اجرا شود، هرگز سوار آن هواپیما نمی‌شوم. معلوم شده حل قابل‌اعتماد این مسئله به‌طرز شگفت‌آوری دشوار است. اما اینجا ما فقط پیکسل نقاشی می‌کنیم. با این کار کنار می‌آیم.

یک چیز دیگر درباره این شبه‌کد دوست دارم: تازه‌کار در برنامه‌نویسی آن را با اشتیاق می‌پذیرد؛ برنامه‌نویسان باتجربه‌تر اغلب پوزخند می‌زنند: «کدام احمقی این را نوشته؟». و متخصص گرافیک رایانه‌ای شانه‌هایش را بالا می‌اندازد و می‌گوید: «خب، در زندگی واقعی این‌طور کار می‌کند». محاسبات موازی انبوه با هزاران ریسه (اینجا از رایانه‌های معمولی مصرفی حرف می‌زنم) طرز فکر را عوض می‌کند.

cpp#include <vector>
#include <iostream>
#include "geometry.h"
#include "tgaimage.h"

const int width  = 200;
const int height = 200;

Vec3f barycentric(Vec2i *pts, Vec2i P) {
    Vec3f u = Vec3f(pts[2][0]-pts[0][0], pts[1][0]-pts[0][0], pts[0][0]-P[0])^Vec3f(pts[2][1]-pts[0][1], pts[1][1]-pts[0][1], pts[0][1]-P[1]);
    /* `pts` و `P` مختصات صحیح دارند؛
       پس اگر `abs(u[2])` کمتر از ۱ باشد یعنی `u[2]` صفر است، یعنی
       مثلث منحط است؛ در این حالت چیزی با مختصات منفی برمی‌گردانیم */
    if (std::abs(u.z)<1) return Vec3f(-1,1,1);
    return Vec3f(1.f-(u.x+u.y)/u.z, u.y/u.z, u.x/u.z);
}

void triangle(Vec2i *pts, TGAImage &image, TGAColor color) {
    Vec2i bboxmin(image.get_width()-1,  image.get_height()-1);
    Vec2i bboxmax(0, 0);
    Vec2i clamp(image.get_width()-1, image.get_height()-1);
    for (int i=0; i<3; i++) {
        bboxmin.x = std::max(0, std::min(bboxmin.x, pts[i].x));
        bboxmin.y = std::max(0, std::min(bboxmin.y, pts[i].y));

        bboxmax.x = std::min(clamp.x, std::max(bboxmax.x, pts[i].x));
        bboxmax.y = std::min(clamp.y, std::max(bboxmax.y, pts[i].y));
    }
    Vec2i P;
    for (P.x=bboxmin.x; P.x<=bboxmax.x; P.x++) {
        for (P.y=bboxmin.y; P.y<=bboxmax.y; P.y++) {
            Vec3f bc_screen  = barycentric(pts, P);
            if (bc_screen.x<0 || bc_screen.y<0 || bc_screen.z<0) continue;
            image.set(P.x, P.y, color);
        }
    }
}

cppvoid rasterize(Vec2i p0, Vec2i p1, TGAImage &image, TGAColor color, int ybuffer[]) {
    if (p0.x>p1.x) {
        std::swap(p0, p1);
    }
    for (int x=p0.x; x<=p1.x; x++) {
        float t = (x-p0.x)/(float)(p1.x-p0.x);
        int y = p0.y*(1.-t) + p1.y*t;
        if (ybuffer[x]<y) {
            ybuffer[x] = y;
            image.set(x, 0, color);
        }
    }
}

void triangle(Vec3f *pts, float *zbuffer, TGAImage &image, TGAColor color) {
    Vec2f bboxmin( std::numeric_limits<float>::max(),  std::numeric_limits<float>::max());
    Vec2f bboxmax(-std::numeric_limits<float>::max(), -std::numeric_limits<float>::max());
    Vec2f clamp(image.get_width()-1, image.get_height()-1);
    for (int i=0; i<3; i++) {
        for (int j=0; j<2; j++) {
            bboxmin[j] = std::max(0.f,      std::min(bboxmin[j], pts[i][j]));
            bboxmax[j] = std::min(clamp[j], std::max(bboxmax[j], pts[i][j]));
        }
    }
    Vec3f P;
    for (P.x=bboxmin.x; P.x<=bboxmax.x; P.x++) {
        for (P.y=bboxmin.y; P.y<=bboxmax.y; P.y++) {
            Vec3f bc_screen  = barycentric(pts[0], pts[1], pts[2], P);
            if (bc_screen.x<0 || bc_screen.y<0 || bc_screen.z<0) continue;
            P.z = 0;
            for (int i=0; i<3; i++) P.z += pts[i][2]*bc_screen[i];
            if (zbuffer[int(P.x+P.y*width)]<P.z) {
                zbuffer[int(P.x+P.y*width)] = P.z;
                image.set(P.x, P.y, color);
            }
        }
    }
}

cppvoid lookat(Vec3f eye, Vec3f center, Vec3f up) {
    Vec3f z = (eye-center).normalize();
    Vec3f x = cross(up,z).normalize();
    Vec3f y = cross(z,x).normalize();
    Matrix Minv = Matrix::identity();
    Matrix Tr   = Matrix::identity();
    for (int i=0; i<3; i++) {
        Minv[0][i] = x[i];
        Minv[1][i] = y[i];
        Minv[2][i] = z[i];
        Tr[i][3] = -eye[i];
    }
    ModelView = Minv*Tr;
}

توجه کنید z′ با بردار ce داده می‌شود (فراموش نکنید نرمال‌سازی کنید؛ بعداً کمک می‌کند). x′ را چطور حساب می‌کنیم؟ صرفاً با یک ضرب خارجی بین u و z′. سپس y′ را طوری حساب می‌کنیم که بر x′ و z′ از قبل محاسبه‌شده عمود باشد (یادآوری می‌کنم در صورت‌بندی مسئله ما ce و u لزوماً متعامد نیستند). آخرین گام، انتقال مبدأ به نقطه ناظر e است و ماتریس تبدیل‌مان آماده است. حالا کافی است هر نقطه با مختصات (x,y,z,1) در چهارچوب مدل را برداریم، در ماتریس ModelView ضرب کنیم و مختصات را در چهارچوب دوربین بگیریم! اتفاقاً، نام ModelView از اصطلاحات OpenGL آمده است.

اگر از ابتدای این دوره همراه بوده‌اید، باید خطوط عجیبی مثل این را به یاد بیاورید:

cppscreen_coords[j] = Vec2i((v.x+1.)*width/2., (v.y+1.)*height/2.);

یعنی چه؟ یعنی نقطه Vec2f v را دارم که به مربع [1,1-]×[1,1-] تعلق دارد. می‌خواهم آن را در تصویری با ابعاد (width, height) رسم کنم. مقدار (v.x+1) بین ۰ و ۲ تغییر می‌کند، (v.x+1)/2 بین ۰ و ۱ و (v.x+1)*width/2 کل تصویر را می‌پیماید. پس در عمل مربع دو-واحدی را روی تصویر نگاشت کردیم.

اما حالا از شر این ساختارهای زشت خلاص می‌شویم و می‌خواهم همه محاسبات را به فرم ماتریسی بازنویسی کنم. کد ++C زیر را در نظر بگیریم:

cppMatrix viewport(int x, int y, int w, int h) {
    Matrix m = Matrix::identity(4);
    m[0][3] = x+w/2.f;
    m[1][3] = y+h/2.f;
    m[2][3] = depth/2.f;

    m[0][0] = w/2.f;
    m[1][1] = h/2.f;
    m[2][2] = depth/2.f;
    return m;
}

این کد این ماتریس را می‌سازد:

یعنی مکعب دو-واحدی [1,1-]×[1,1-]×[1,1-] روی مکعب صفحه [x,x+w]×[y,y+h]×[0,d] نگاشت می‌شود. درست است، مکعب و نه مستطیل، این به دلیل محاسبات عمق با z-buffer است. این‌جا d وضوح z-buffer است. دوست دارم برابر ۲۵۵ باشد، چون برای اشکال‌زدایی، خروجی تصاویر سیاه‌وسفیدِ z-buffer ساده می‌شود.

در اصطلاحات OpenGL به این ماتریس «ماتریس گذرگاه دید» (viewport matrix) می‌گویند.

زنجیره تبدیل‌های مختصاتی

پس جمع‌بندی کنیم. مدل‌های ما (مثلاً شخصیت‌ها) در چهارچوب محلی خودشان ساخته می‌شوند (مختصات شیء). آن‌ها در صحنه‌ای که با مختصات دنیا بیان شده وارد می‌شوند. تبدیل از یکی به دیگری با ماتریس Model انجام می‌شود. سپس می‌خواهیم آن را در چهارچوب دوربین (مختصات چشم) بیان کنیم؛ این تبدیل View نام دارد. سپس صحنه را برای ایجاد تغییر شکل پرسپکتیو با ماتریس Projection تغییر شکل می‌دهیم (درس ۴)؛ این ماتریس صحنه را به اصطلاح مختصات برش (clip coordinates) تبدیل می‌کند. در نهایت صحنه را رسم می‌کنیم و ماتریسی که مختصات برش را به مختصات صفحه تبدیل می‌کند Viewport نام دارد.

باز هم، اگر نقطه v را از فایل .obj بخوانیم، برای رسم آن روی صفحه این زنجیره تبدیل‌ها را طی می‌کند:

textViewport * Projection * View * Model * v.

اگر به این کامیت نگاه کنید، خطوط زیر را می‌بینید:

cppVec3f v = model->vert(face[j]);
screen_coords[j] =  Vec3f(ViewPort*Projection*ModelView*Matrix(v));

چون فقط یک شیء رسم می‌کنم، ماتریس Model برابر با همانی است و آن را با ماتریس View ادغام کرده‌ام.

تبدیل بردارهای نرمال

یک واقعیت مشهور است:

cpp#include <vector>
#include <iostream>

#include "tgaimage.h"
#include "model.h"
#include "geometry.h"
#include "our_gl.h"

Model *model     = NULL;
const int width  = 800;
const int height = 800;

Vec3f light_dir(1,1,1);
Vec3f       eye(1,1,3);
Vec3f    center(0,0,0);
Vec3f        up(0,1,0);

struct GouraudShader : public IShader {
    Vec3f varying_intensity; // توسط شیدر رأس نوشته می‌شود، توسط شیدر فرگمنت خوانده می‌شود

    virtual Vec4f vertex(int iface, int nthvert) {
        varying_intensity[nthvert] = std::max(0.f, model->normal(iface, nthvert)*light_dir); // شدت نور پخش (دیفیوز) را بگیر
        Vec4f gl_Vertex = embed<4>(model->vert(iface, nthvert)); // رأس را از فایل .obj بخوان
        return Viewport*Projection*ModelView*gl_Vertex; // آن را به مختصات صفحه تبدیل کن
    }

    virtual bool fragment(Vec3f bar, TGAColor &color) {
        float intensity = varying_intensity*bar;   // شدت را برای پیکسل جاری درونیابی کن
        color = TGAColor(255, 255, 255)*intensity; // خب معلوم است
        return false;                              // نه، این پیکسل را دور نمی‌اندازیم
    }
};

int main(int argc, char** argv) {
    if (2==argc) {
        model = new Model(argv[1]);
    } else {
        model = new Model("obj/african_head.obj");
    }

    lookat(eye, center, up);
    viewport(width/8, height/8, width*3/4, height*3/4);
    projection(-1.f/(eye-center).norm());
    light_dir.normalize();

    TGAImage image  (width, height, TGAImage::RGB);
    TGAImage zbuffer(width, height, TGAImage::GRAYSCALE);

    GouraudShader shader;
    for (int i=0; i<model->nfaces(); i++) {
        Vec4f screen_coords[3];
        for (int j=0; j<3; j++) {
            screen_coords[j] = shader.vertex(i, j);
        }
        triangle(screen_coords, shader, image, zbuffer);
    }

    image.  flip_vertically(); // برای قرار دادن مبدأ در گوشه پایین-چپ تصویر
    zbuffer.flip_vertically();
    image.  write_tga_file("output.tga");
    zbuffer.write_tga_file("zbuffer.tga");

    delete model;
    return 0;
}

هدف اصلی شیدر رأس، تبدیل مختصات رئوس است. هدف ثانویه، آماده‌کردن داده برای شیدر فرگمنت.

بعد از آن چه اتفاقی می‌افتد؟ روتین رسترایزیشن را صدا می‌زنیم. درون رسترایزر چه می‌گذرد را نمی‌دانیم (خب، می‌دانیم، چون خودمان برنامه‌اش کردیم!) با یک استثنا. می‌دانیم که رسترایزر برای هر پیکسل روتین ما یعنی شیدر فرگمنت را صدا می‌زند. باز هم می‌گویم: برای هر پیکسل داخل مثلث، رسترایزر «کال‌بک» (نقطه تماس) خودمان یعنی شیدر فرگمنت را صدا می‌زند.

هدف اصلی شیدر فرگمنت تعیین رنگ پیکسل جاری است. هدف ثانویه — با برگرداندن true می‌توانیم پیکسل جاری را دور بیندازیم.

خط لوله رندر برای OpenGL 2 را می‌توان این‌گونه نشان داد (در واقع، برای نسخه‌های جدیدتر هم کم‌وبیش همین است):

به دلیل محدودیت زمانی دوره‌ام، به خط لوله OpenGL 2 و در نتیجه فقط شیدرهای فرگمنت و رأس اکتفا می‌کنم. در نسخه‌های جدیدتر OpenGL شیدرهای دیگری هم هست که مثلاً اجازه تولید هندسه در لحظه را می‌دهند.

خوب، در تصویر بالا همه مرحله‌هایی که نمی‌توانیم لمس کنیم آبی نشان داده شده‌اند و کال‌بک‌های ما نارنجی. در واقع، تابع main() ما روتین پردازش بدوی است. شیدر رأس را صدا می‌زند. اسمبلی بدوی در اینجا نداریم، چون فقط مثلث‌های احمق می‌کشیم (در کد ما با پردازش بدوی ادغام شده). تابع triangle() رسترایزر است؛ برای هر نقطه داخل مثلث شیدر فرگمنت را صدا می‌زند، سپس بررسی‌های عمق (z-buffer) و چیزهایی از این دست را انجام می‌دهد.

        Vec3f n = proj<3>(uniform_MIT*embed<4>(model->normal(uv))).normalize();

        color = c;
        for (int i=0; i<3; i++) color[i] = std::min<float>(5 + c[i]*(diff + .6*spec), 255);
        return false;
    }

درس ۶bis: نگاشت نرمال با فضای مماس

در واقع من بیشتر به جهتِ عمود بر خطوط هم‌تراز علاقه‌مندم. اگر در امتداد یک هم‌تراز حرکت کنیم، ارتفاع تغییر نمی‌کند (خب معلوم است، هم‌تراز است!). اگر کمی از هم‌تراز منحرف شویم، ارتفاع شروع به تغییر می‌کند. تندترین صعود وقتی عمود بر خطوط هم‌تراز حرکت کنیم به دست می‌آید.

یادآوری: جهت تندترین صعود برای یک تابع چیزی نیست جز گرادیان آن. برای تابع خطی f(x,y,z) = Ax + By + Cz + D، گرادیان آن بردار ثابت (A, B, C) است. یادآوری: مقادیر (A,B,C) را نمی‌دانیم. فقط سه نمونه از تابع را می‌دانیم. آیا می‌توانیم A و B و C را بازسازی کنیم؟ البته.

پس سه نقطه p0, p1, p2 و سه مقدار f0, f1, f2 داریم. باید بردار تندترین صعود (A,B,C) را پیدا کنیم. تابع دیگری بگذاریم که با g(p) = f(p) − f(p0) تعریف می‌شود:
