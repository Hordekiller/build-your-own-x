نمای کلی — معرفی توکیو (Overview)

↗ مشاهده بخش اصلی در tokio.rs

توکیو (Tokio) یک رانتایم ناهمگام (asynchronous runtime) برای زبان برنامه‌نویسی راست (Rust) است. توکیو بلوک‌های ساختمانیِ لازم برای نوشتن برنامه‌های شبکه‌ای را فراهم می‌کند و انعطافی را در اختیار شما می‌گذارد که بتوانید طیف گسترده‌ای از سیستم‌ها را هدف بگیرید؛ از سرورهای بزرگ با ده‌ها هسته تا دستگاه‌های تعبیه‌شده (embedded) کوچک.

در سطح بالا، توکیو چند مؤلفهٔ اصلی ارائه می‌دهد:

  • یک رانتایم چندنخی برای اجرای کد ناهمگام.
  • نسخهٔ ناهمگام کتابخانهٔ استاندارد.
  • اکوسیستم بزرگی از کتابخانه‌ها.

نقش توکیو در پروژهٔ شما

وقتی برنامهٔ خود را به‌صورت ناهمگام می‌نویسید، با کاهش هزینهٔ انجامِ هم‌زمانِ کارهای زیاد، امکان مقیاس‌پذیری بسیار بهتری فراهم می‌کنید. بااین‌حال، کد ناهمگامِ راست به‌تنهایی اجرا نمی‌شود؛ بنابراین باید یک رانتایم برای اجرای آن انتخاب کنید. کتابخانهٔ توکیو پرکاربردترین رانتایم است و از نظر کاربرد از مجموعِ سایر رانتایم‌ها پیشی گرفته است.

علاوه بر این، توکیو ابزارهای مفید بسیاری ارائه می‌کند. هنگام نوشتن کد ناهمگام، نمی‌توانید از رابط‌های برنامه‌نویسی مسدودکنندهٔ (blocking) معمولِ کتابخانهٔ استانداردِ راست استفاده کنید و باید به‌جای آن‌ها از نسخه‌های ناهمگامِ همان رابط‌ها بهره ببرید. این نسخه‌های جایگزین توسط توکیو فراهم شده‌اند و در جایی که منطقی باشد، رابط کتابخانهٔ استاندارد را منعکس می‌کنند.

مزایای توکیو

سریع (Fast)

توکیو سریع است؛ چراکه روی خودِ زبان راست ساخته شده که خودش سریع است. این کار با همان روحیهٔ راست انجام شده و هدفش این است که نتوانید با نوشتن کد معادل با دست، کارایی بهتری به دست آورید.

توکیو مقیاس‌پذیر است؛ چراکه روی قابلیت زبانی async/await ساخته شده که خودش مقیاس‌پذیر است. در کار با شبکه، به‌دلیل تأخیر (latency) محدودیتی در سرعتِ رسیدگی به یک اتصال وجود دارد؛ پس تنها راه مقیاس‌پذیری، رسیدگی به تعداد زیادی اتصال به‌طور هم‌زمان است. با قابلیت زبانی async/await، افزایش تعداد عملیات هم‌زمان فوق‌العاده ارزان می‌شود و می‌توانید به تعداد زیادی تسک (task) هم‌زمان مقیاس دهید.

قابل‌اعتماد (Reliable)

توکیو با راست ساخته شده است؛ زبانی که به همگان قدرت ساخت نرم‌افزارهای قابل‌اعتماد و کارآمد را می‌دهد. تعداد قابل‌توجهی از مطالعات نشان داده‌اند که تقریباً حدود ۷۰٪ از باگ‌های امنیتی با شدت بالا ناشی از ناامنی حافظه هستند. استفاده از راست این کلاس کامل از باگ‌ها را در برنامه‌های شما حذف می‌کند.

توکیو همچنین تمرکز زیادی بر ارائهٔ رفتار ثابت و بدون غافلگیری دارد. هدف اصلی توکیو این است که به کاربران اجازه دهد نرم‌افزار قابل‌پیش‌بینی‌ای مستقر کنند که روزبه‌روز یکسان عمل کند، زمان پاسخ قابل‌اعتماد داشته باشد و هیچ پیک تأخیر غیرقابل‌پیش‌بینی‌ای ایجاد نکند.

آسان (Easy)

با قابلیت زبانی async/await در راست، پیچیدگی نوشتن برنامه‌های ناهمگام به‌طور چشمگیری کاهش یافته است. همراه با ابزارهای توکیو و اکوسیستم پرنشاط آن، نوشتن برنامه‌ها بسیار آسان می‌شود.

توکیو در جایی که منطقی باشد از قرارداد نام‌گذاری کتابخانهٔ استاندارد پیروی می‌کند. این کار تبدیل کدی را که فقط با کتابخانهٔ استاندارد نوشته شده به کدی که با توکیو نوشته شده، آسان می‌کند. با سیستم نوع قوی راست، توانایی تحویل کد صحیح به‌سادگی بی‌نظیر است.

انعطاف‌پذیر (Flexible)

توکیو انواع مختلفی از رانتایم را ارائه می‌دهد؛ از یک رانتایم چندنخی با دزدی کار (work-stealing) تا یک رانتایم سبکِ تک‌نخی. هر یک از این رانتایم‌ها با گزینه‌های تنظیم فراوانی همراه هستند که به کاربران امکان می‌دهد آن‌ها را مطابق نیاز خود تنظیم کنند.

چه زمانی نباید از توکیو استفاده کرد

اگرچه توکیو برای بسیاری از پروژه‌هایی که باید هم‌زمان کارهای زیادی انجام دهند مفید است، موارد استفاده‌ای هم وجود دارد که توکیو انتخاب مناسبی نیست:

  • شتاب‌دادن به محاسباتِ وابسته به پردازنده با اجرای موازی آن‌ها روی چند نخ. توکیو برای برنامه‌های وابسته به ورودی/خروجی (I/O-bound) طراحی شده است که در آن هر تسک بیشتر وقت خود را منتظر ورودی/خروجی می‌گذراند. اگر تنها کاری که برنامهٔ شما انجام می‌دهد اجرای موازی محاسبات است، باید از rayon استفاده کنید. البته اگر به هر دو نیاز داشتید، باز هم می‌توان «ترکیب‌کردن» انجام داد. برای نمونه‌ای عملی، این نوشته را ببینید.
  • خواندن فایل‌های زیاد. اگرچه به‌نظر می‌رسد توکیو برای پروژه‌هایی که صرفاً باید فایل‌های زیادی را بخوانند مفید باشد، در این‌جا نسبت به یک استخر نخ (thread pool) معمولی مزیتی ندارد؛ زیرا سیستم‌عامل‌ها معمولاً رابط‌های ناهمگامِ فایل ارائه نمی‌کنند.
  • ارسال یک درخواست وب واحد. جایی که توکیو به شما مزیت می‌دهد، نیاز به انجام هم‌زمان کارهای زیاد است. اگر می‌خواهید از کتابخانه‌ای استفاده کنید که برای راست ناهمگام ساخته شده، مانند reqwest، ولی لازم نیست هم‌زمان کارهای زیادی انجام دهید، نسخهٔ مسدودکنندهٔ همان کتابخانه را ترجیح دهید؛ چون پروژهٔ شما را ساده‌تر می‌کند. استفاده از توکیو البته همچنان کار می‌کند، اما مزیت واقعی نسبت به رابط مسدودکننده ندارد. اگر کتابخانه رابط مسدودکننده نداشت، فصل پل‌زدن با کد همگام را ببینید.

مینی-ردیس (Mini-Redis)

پروژه‌ای که در این آموزش خواهید ساخت، به‌صورت Mini-Redis در گیت‌هاب در دسترس است. مینی-ردیس با هدف اصلی یادگیری توکیو طراحی شده و به همین دلیل کامنت‌های بسیار خوبی دارد؛ اما این بدان معناست که مینی-ردیس برخی از قابلیت‌هایی را که در یک کتابخانهٔ واقعیِ Redis انتظار دارید، ندارد. کتابخانه‌های آمادهٔ تولید را می‌توانید در crates.io پیدا کنید.

ما مستقیماً در آموزش از مینی-ردیس استفاده می‌کنیم. این کار به ما امکان می‌دهد بخش‌هایی از مینی-ردیس را در طول آموزش، پیش از آن‌که خودمان آن‌ها را پیاده‌سازی کنیم، به‌کار بگیریم.

پیش‌نیازها

انتظار می‌رود خوانندگان از قبل با زبان راست آشنا باشند. کتاب راست منبع بسیار خوبی برای شروع است.

هرچند الزامی نیست، اما کمی تجربه در نوشتن کد شبکه‌ای با کتابخانهٔ استاندارد راست یا زبان دیگر می‌تواند مفید باشد.

هیچ دانش قبلی از Redis لازم نیست.

راست (Rust)

قبل از شروع، مطمئن شوید که ابزار توسعهٔ راست را نصب و آماده به کار دارید. اگر ندارید، ساده‌ترین راه نصب آن استفاده از rustup است.

این آموزش حداقل به نسخهٔ 1.45.0 از راست نیاز دارد، اما توصیه می‌شود از جدیدترین نسخهٔ پایدار راست استفاده کنید.

برای بررسی نصب بودن راست روی رایانه، دستور زیر را اجرا کنید:

shell$ rustc --version

باید خروجی‌ای مانند rustc 1.46.0 (04488afe3 2020-08-24) ببینید.

سرور مینی-ردیس

در ادامه، سرور مینی-ردیس را نصب کنید. از این سرور برای آزمایش کلاینتِ در حال ساخت استفاده می‌شود.

shell$ cargo install mini-redis

با راه‌اندازی سرور مطمئن شوید که به‌درستی نصب شده است:

shell$ mini-redis-server

سپس در یک پنجرهٔ ترمینال جداگانه، با استفاده از mini-redis-cli تلاش کنید کلید foo را بگیرید:

shell$ mini-redis-cli get foo

باید (nil) ببینید.

آمادهٔ شروع

همین است؛ همه‌چیز آماده است. به صفحهٔ بعد بروید تا اولین برنامهٔ ناهمگامِ راست خود را بنویسید.

سلام توکیو (Hello Tokio)

با نوشتن یک برنامهٔ بسیار سادهٔ توکیو شروع می‌کنیم. این برنامه به سرور مینی-ردیس متصل می‌شود، مقدار کلید hello را روی world تنظیم می‌کند و سپس همان کلید را دوباره می‌خواند. این کار با استفاده از کتابخانهٔ کلاینت مینی-ردیس انجام می‌شود.

کد

ساخت یک پروژهٔ جدید (crate)

بیایید با ساخت یک اپ جدیدِ راست شروع کنیم:

shell$ cargo new my-redis
$ cd my-redis

افزودن وابستگی‌ها

سپس Cargo.toml را باز کنید و خطوط زیر را درست زیر [dependencies] اضافه کنید:

tomltokio = { version = "1", features = ["full"] }
mini-redis = "0.4"

نوشتن کد

حالا main.rs را باز کنید و محتوای فایل را با کد زیر جایگزین کنید:

rustuse mini_redis::{client, Result};

#[tokio::main]
async fn main() -> Result<()> {
    // یک اتصال به آدرس mini-redis باز کن
    let mut client = client::connect("127.0.0.1:6379").await?;

    // کلید "hello" را با مقدار "world" تنظیم کن
    client.set("hello", "world".into()).await?;

    // کلید "hello" را بگیر
    let result = client.get("hello").await?;

    println!("got value from the server; result={:?}", result);

    Ok(())
}

مطمئن شوید سرور مینی-ردیس در حال اجراست. در یک پنجرهٔ ترمینال جداگانه، این دستور را اجرا کنید:

shell$ mini-redis-server

اگر هنوز مینی-ردیس را نصب نکرده‌اید، می‌توانید با این دستور این کار را انجام دهید:

shell$ cargo install mini-redis

حالا برنامهٔ my-redis را اجرا کنید:

shell$ cargo run
got value from the server; result=Some(b"world")

موفق شدید!

کد کامل را می‌توانید اینجا پیدا کنید.

شکستن کد به اجزا

بیایید کمی وقت بگذاریم و مرور کنیم چه کاری انجام دادیم. کد زیادی نیست، اما اتفاقات زیادی می‌افتد.

rustlet mut client = client::connect("127.0.0.1:6379").await?;

تابع client::connect توسط crate مینی-ردیس فراهم شده است. این تابع به‌صورت ناهمگام یک اتصال TCP با آدرس راه‌دور مشخص‌شده برقرار می‌کند. پس از برقراری اتصال، یک دستگیرهٔ (handle) client برگردانده می‌شود. حتی اگرچه عملیات به‌صورت ناهمگام انجام می‌شود، کدی که می‌نویسیم به‌نظر همگام می‌رسد. تنها نشانه‌ای که عملیات ناهمگام است، عملگر .await است.

برنامه‌نویسی ناهمگام چیست؟

بیشتر برنامه‌های رایانه‌ای به همان ترتیبی اجرا می‌شوند که نوشته شده‌اند. خط اول اجرا می‌شود، بعد خط بعدی و الی آخر. در برنامه‌نویسی همگام (synchronous)، وقتی برنامه با عملیاتی مواجه می‌شود که نمی‌تواند فوراً کامل شود، تا کامل‌شدنِ عملیات مسدود می‌ماند. برای مثال، برقراری اتصال TCP مستلزم تبادل با یک همتا (peer) روی شبکه است که می‌تواند مدت زمان قابل‌توجهی طول بکشد. در این مدت، نخ (thread) مسدود است.

در برنامه‌نویسی ناهمگام، عملیاتی که نمی‌توانند فوراً کامل شوند به پس‌زمینه معلق می‌مانند. نخ مسدود نمی‌شود و می‌تواند به اجرای کارهای دیگر ادامه دهد. وقتی عملیات کامل شد، تسک از حالت تعلیق خارج می‌شود و از همان‌جا که متوقف شده بود به پردازش ادامه می‌دهد. مثال قبلی ما فقط یک تسک دارد، پس وقتی معلق است اتفاق دیگری نمی‌افتد؛ اما برنامه‌های ناهمگام معمولاً بسیاری از این تسک‌ها را دارند.

اگرچه برنامه‌نویسی ناهمگام می‌تواند به برنامه‌های سریع‌تر منجر شود، اغلب به برنامه‌های بسیار پیچیده‌تر هم می‌انجامد. برنامه‌نویس باید تمام حالت لازم برای ازسرگیری کار پس از کامل‌شدن عملیات ناهمگام را پیگیری کند. از نظر تاریخی، این کار طاقت‌فرسا و مستعد خطا بوده است.

نخ‌های سبز زمان کامپایل (Compile-time green-threading)

راست برنامه‌نویسی ناهمگام را با استفاده از قابلیتی به نام async/await پیاده‌سازی می‌کند. توابعی که عملیات ناهمگام انجام می‌دهند با کلیدواژهٔ async علامت‌گذاری می‌شوند. در مثال ما، تابع connect این‌گونه تعریف شده است:

rustuse mini_redis::Result;
use mini_redis::client::Client;
use tokio::net::ToSocketAddrs;

pub async fn connect<T: ToSocketAddrs>(addr: T) -> Result<Client> {
    // ...
}

تعریفِ async fn شبیه یک تابع همگام معمولی است، اما به‌صورت ناهمگام عمل می‌کند. راست async fn را در زمان کامپایل به یک روال (routine) که به‌صورت ناهمگام عمل می‌کند تبدیل می‌کند. هر فراخوانیِ .await درون async fn کنترل را به نخ برمی‌گرداند. نخ می‌تواند در حالی که عملیات در پس‌زمینه پردازش می‌شود، کارهای دیگری انجام دهد.

نکته: اگرچه زبان‌های دیگر هم async/await را پیاده‌سازی می‌کنند، راست رویکردی یکتا دارد. مهم‌تر از همه، عملیات ناهمگام راست تنبل (lazy) هستند. این موضوع به معناشناسیِ متفاوتِ زمان اجرا نسبت به سایر زبان‌ها منجر می‌شود.

اگر هنوز این موضوع کاملاً روشن نیست، نگران نباشید. در ادامهٔ این راهنما بیشتر به بررسی async/await خواهیم پرداخت.

استفاده از async/await

توابع ناهمگام مانند هر تابعِ راستِ دیگری صدا زده می‌شوند. اما صدازدن این توابع باعث اجرای بدنهٔ تابع نمی‌شود. در عوض، صدازدن یک async fn مقداری برمی‌گرداند که نمایانگر عملیات است. این موضوع از نظر مفهومی مشابه یک کلوژر بدون آرگومان است. برای اجرای واقعی عملیات، باید روی مقدار بازگشتی از عملگر .await استفاده کنید.

برای مثال، برنامهٔ زیر را در نظر بگیرید:

rustasync fn say_world() {
    println!("world");
}

#[tokio::main]
async fn main() {
    // صدازدن `say_world()` بدنهٔ `say_world()` را اجرا نمی‌کند
    let op = say_world();

    // این println! اول چاپ می‌شود
    println!("hello");

    // صدازدن `.await` روی `op` اجرای `say_world` را شروع می‌کند
    op.await;
}

مقدار بازگشتی یک async fn یک نوع ناشناس (anonymous type) است که تریتِ Future را پیاده‌سازی می‌کند.

تابع اصلیِ ناهمگام (Async main)

تابع اصلی که برای راه‌اندازی برنامه استفاده می‌شود با تابع معمولِ موجود در بیشتر crateهای راست تفاوت دارد.

  1. یک async fn است
  2. با #[tokio::main] علامت‌گذاری می‌شود

از یک async fn استفاده می‌شود، چون می‌خواهیم وارد بستر ناهمگام شویم. اما توابع ناهمگام باید توسط یک رانتایم اجرا شوند. رانتایم شامل زمان‌بند (scheduler) تسک‌های ناهمگام است و ورودی/خروجیِ مبتنی بر رویداد (evented I/O)، تایمرها و غیره را فراهم می‌کند. رانتایم به‌صورت خودکار شروع نمی‌شود؛ بنابراین تابع main باید آن را راه‌اندازی کند.

قابلیتِ #[tokio::main] یک ماکرو است. این ماکرو async fn main() را به یک fn main() همگام تبدیل می‌کند که یک نمونهٔ رانتایم را مقداردهی کرده و تابع main ناهمگام را اجرا می‌کند.

برای مثال، کد زیر:

rust#[tokio::main]
async fn main() {
    println!("hello");
}

به این شکل تبدیل می‌شود:

rustfn main() {
    let mut rt = tokio::runtime::Runtime::new().unwrap();
    rt.block_on(async {
        println!("hello");
    })
}

جزئیات رانتایم توکیو بعداً پوشش داده می‌شود.

ویژگی‌های Cargo (Cargo features)

وقتی برای این آموزش به توکیو وابستگی می‌دهیم، پرچمِ ویژگیِ (feature flag) full فعال می‌شود:

پذیرش سوکت‌ها (Accepting sockets)

اولین کاری که سرور Redis ما باید انجام دهد، پذیرش سوکت‌های ورودی TCP است. این کار با اتصالِ tokio::net::TcpListener به پورت 6379 انجام می‌شود.

نکته: بسیاری از نوع‌های توکیو همان نام معادل همگام خود را در کتابخانهٔ استاندارد راست دارند. در جایی که منطقی است، توکیو همان رابط‌های std را با async fn در معرض دید قرار می‌دهد.

سپس سوکت‌ها در یک حلقه پذیرفته می‌شوند. هر سوکت پردازش و سپس بسته می‌شود. فعلاً دستور را می‌خوانیم، روی خروجی استاندارد چاپ می‌کنیم و با یک خطا پاسخ می‌دهیم.

src/main.rs

rustuse tokio::net::{TcpListener, TcpStream};
use mini_redis::{Connection, Frame};

#[tokio::main]
async fn main() {
    // شنونده را به آدرس متصل کن
    let listener = TcpListener::bind("127.0.0.1:6379").await.unwrap();

    loop {
        // آیتم دوم شامل IP و پورت اتصال جدید است
        let (socket, _) = listener.accept().await.unwrap();
        process(socket).await;
    }
}

async fn process(socket: TcpStream) {
    // نوع `Connection` به ما اجازه می‌دهد به‌جای جریان بایت،
    // **قاب‌های** (frames) ردیس را بخوانیم/بنویسیم.
    // نوع `Connection` توسط mini-redis تعریف شده است.
    let mut connection = Connection::new(socket);

    if let Some(frame) = connection.read_frame().await.unwrap() {
        println!("GOT: {:?}", frame);

        // با یک خطا پاسخ بده
        let response = Frame::Error("unimplemented".to_string());
        connection.write_frame(&response).await.unwrap();
    }
}

همروندی (Concurrency)

سرور ما یک مشکل کوچک دارد (علاوه بر اینکه فقط با خطا پاسخ می‌دهد): درخواست‌های ورودی را یکی‌یکی پردازش می‌کند. وقتی اتصالی پذیرفته می‌شود، سرور داخل بلوک حلقهٔ پذیرش می‌ماند تا زمانی که پاسخ به‌طور کامل روی سوکت نوشته شود.

ما می‌خواهیم سرور Redis ما بسیاری درخواست هم‌زمان را پردازش کند. برای این کار باید کمی همروندی اضافه کنیم.

نکته: همروندی (concurrency) و موازی‌سازی (parallelism) یکسان نیستند. اگر بین دو کار در نوبت جابه‌جا شوید، روی هر دو کار به‌صورت هم‌روند کار می‌کنید، اما نه به‌صورت موازی. برای اینکه چیزی واجد شرایط موازی‌سازی باشد، به دو نفر نیاز دارید که هر کدام به یک کار اختصاص داشته باشد.
یکی از مزایای استفاده از توکیو این است که کد ناهمگام به شما اجازه می‌دهد روی بسیاری از تسک‌ها به‌صورت هم‌روند کار کنید، بدون اینکه لازم باشد با نخ‌های معمولی آن‌ها را به‌صورت موازی اجرا کنید. در واقع، توکیو می‌تواند بسیاری از تسک‌ها را به‌صورت هم‌روند روی یک نخ اجرا کند!

برای پردازش هم‌روند اتصال‌ها، برای هر اتصال ورودی یک تسک جدید ریخته می‌شود (spawn). اتصال روی همان تسک پردازش می‌شود.

حلقهٔ پذیرش این‌گونه می‌شود:

rustuse tokio::net::TcpListener;

#[tokio::main]
async fn main() {
    let listener = TcpListener::bind("127.0.0.1:6379").await.unwrap();

    loop {
        let (socket, _) = listener.accept().await.unwrap();
        // برای هر سوکت ورودی یک تسک جدید ریخته می‌شود. سوکت
        // به تسک جدید منتقل می‌شود و همان‌جا پردازش می‌شود.
        tokio::spawn(async move {
            process(socket).await;
        });
    }
}

تسک‌ها (Tasks)

یک تسکِ توکیو یک نخ سبزِ (green thread) ناهمگام است. با پاس‌دادن یک بلوک async به tokio::spawn ساخته می‌شود. تابع tokio::spawn یک JoinHandle برمی‌گرداند که فراخوان (caller) می‌تواند برای تعامل با تسک ریخته‌شده از آن استفاده کند. بلوک async می‌تواند مقدار بازگشتی داشته باشد. فراخوان می‌تواند با .await روی JoinHandle به مقدار بازگشتی دست یابد.

برای مثال:

rust#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        // کمی کار ناهمگام انجام بده
        "return value"
    });

    // کمی کار دیگر انجام بده

    let out = handle.await.unwrap();
    println!("GOT {}", out);
}

در انتظار ماندن روی JoinHandle یک Result برمی‌گرداند. وقتی تسک در حین اجرا با خطایی مواجه شود، JoinHandle یک Err برمی‌گرداند. این اتفاق می‌افتد وقتی تسک یا panic کند، یا اگر تسک به‌دلیل خاموش‌شدنِ رانتایم به‌اجبار لغو شود.

تسک‌ها واحد اجرایی هستند که توسط زمان‌بند مدیریت می‌شوند. ریختنِ تسک، آن را به زمان‌بند توکیو می‌سپارد و زمان‌بند تضمین می‌کند که وقتی تسک کاری برای انجام دارد اجرا شود. تسک ریخته‌شده ممکن است روی همان نخی اجرا شود که از آنجا ریخته شده، یا روی یک نخِ متفاوتِ رانتایم. تسک همچنین می‌تواند پس از ریخته‌شدن بین نخ‌ها جابه‌جا شود.

تسک‌ها در توکیو بسیار سبک هستند. در پس‌زمینه فقط یک تخصیص حافظه و ۶۴ بایت حافظه لازم دارند. برنامه‌ها باید راحت هزاران، بلکه میلیون‌ها تسک بریزند.

مرز 'static

وقتی تسکی را روی رانتایم توکیو می‌ریزید، طول عمر (lifetime) نوعِ آن باید 'static باشد. این بدان معناست که تسک ریخته‌شده نباید هیچ ارجاعی به داده‌ای داشته باشد که خارج از تسک مالکیت‌گذاری (owned) شده است.

نکته: یک باور غلط رایج این است که 'static همیشه به معنای «برای همیشه زنده است» است؛ اما این‌گونه نیست. صرفِ اینکه یک مقدار 'static است به این معنا نیست که نشتی حافظه دارید. می‌توانید در باورهای غلط رایج دربارهٔ طول عمر در راست بیشتر بخوانید.

برای مثال، کد زیر کامپایل نمی‌شود:

rustuse tokio::task;

#[tokio::main]
async fn main() {
    let v = vec![1, 2, 3];

    task::spawn(async {
        println!("Here's a vec: {:?}", v);
    });
}

توجه کنید پیام خطا دربارهٔ بیش‌ازحد-زنده‌ماندنِ (outliving) طول عمرِ 'static توسط نوعِ آرگومان صحبت می‌کند. این اصطلاح‌شناسی می‌تواند گیج‌کننده باشد، چون طول عمر 'static تا پایان برنامه دوام دارد؛ پس اگر چیزی بیش از آن زنده بماند، نکند نشتی حافظه داشته باشید؟ توضیح این است که این نوع است که باید از طول عمر 'static فراتر برود، نه مقدار؛ و مقدار ممکن است پیش از آن‌که نوعِ آن دیگر معتبر نباشد از بین برود.

وقتی می‌گوییم یک مقدار 'static است، فقط یعنی اینکه نگه‌داشتن آن مقدار برای همیشه اشتباه نخواهد بود. این مهم است، چون کامپایلر قادر نیست استدلال کند یک تسک تازه‌ریخته‌شده چه مدت می‌ماند. ما باید مطمئن شویم تسک مجاز است برای همیشه زنده بماند، تا توکیو بتواند تسک را تا هر مدت که لازم است اجرا کند.

مرز Send

تسک‌هایی که tokio::spawn می‌ریزد باید Send را پیاده‌سازی کنند. این به رانتایم توکیو اجازه می‌دهد تسک‌ها را در حالی که روی یک .await معلق هستند بین نخ‌ها جابه‌جا کند.

تسک‌ها زمانی Send هستند که همهٔ داده‌ای که در میان فراخوانی‌های .await نگه داشته می‌شود، Send باشد. این کمی ظریف است. وقتی .await صدا زده می‌شود، تسک کنترل را به زمان‌بند بازمی‌گرداند. دفعهٔ بعد که تسک اجرا می‌شود، از همان نقطه‌ای که آخرین بار واگذار کرد، از سر گرفته می‌شود. برای عملی‌شدنِ این کار، تمام حالتی که بعد از .await استفاده می‌شود باید توسط تسک ذخیره شود. اگر این حالت Send باشد، یعنی می‌تواند بین نخ‌ها جابه‌جا شود، خودِ تسک هم می‌تواند بین نخ‌ها جابه‌جا شود. برعکس، اگر حالت Send نباشد، تسک هم Send نیست.

برای مثال، این کار می‌کند:

rustuse tokio::task::yield_now;
use std::rc::Rc;

#[tokio::main]
async fn main() {
    tokio::spawn(async {
        // این scope باعث می‌شود `rc` قبل از `.await` رها (drop) شود
        {
            let rc = Rc::new("hello");
            println!("{}", rc);
        }

        // `rc` دیگر استفاده نمی‌شود. وقتی تسک کنترل را به
        // زمان‌بند برمی‌گرداند، **ذخیره نمی‌شود**
        yield_now().await;
    });
}

این کار نمی‌کند:

ذخیرهٔ مقادیر

حالا تابع process را برای رسیدگی به دستورهای ورودی پیاده‌سازی می‌کنیم. از یک HashMap برای ذخیرهٔ مقادیر استفاده می‌کنیم. دستورهای SET در HashMap درج می‌کنند و دستورهای GET مقدار را می‌خوانند. علاوه بر این، از یک حلقه برای پذیرش بیش از یک دستور در هر اتصال استفاده خواهیم کرد.

rustuse tokio::net::TcpStream;
use mini_redis::{Connection, Frame};

async fn process(socket: TcpStream) {
    use mini_redis::Command::{self, Get, Set};
    use std::collections::HashMap;

    // برای ذخیرهٔ داده از hashmap استفاده می‌شود
    let mut db = HashMap::new();

    // نوع `Connection` که توسط `mini-redis` فراهم شده،
    // تجزیهٔ قاب‌ها از سوکت را مدیریت می‌کند
    let mut connection = Connection::new(socket);

    // برای دریافت یک دستور از اتصال از `read_frame` استفاده کن
    while let Some(frame) = connection.read_frame().await.unwrap() {
        let response = match Command::from_frame(frame).unwrap() {
            Set(cmd) => {
                // مقدار به‌صورت `Vec<u8>` ذخیره می‌شود
                db.insert(cmd.key().to_string(), cmd.value().to_vec());
                Frame::Simple("OK".to_string())
            }
            Get(cmd) => {
                if let Some(value) = db.get(cmd.key()) {
                    // `Frame::Bulk` انتظار دارد داده از نوع `Bytes` باشد.
                    // این نوع بعداً در آموزش پوشش داده می‌شود. فعلاً
                    // `&Vec<u8>` با استفاده از `into()` به `Bytes` تبدیل می‌شود.
                    Frame::Bulk(value.clone().into())
                } else {
                    Frame::Null
                }
            }
            cmd => panic!("unimplemented {:?}", cmd),
        };

        // پاسخ را برای کلاینت بنویس
        connection.write_frame(&response).await.unwrap();
    }
}

راهبردها (Strategies)

چند راه متفاوت برای به اشتراک‌گذاشتن حالت در توکیو وجود دارد:

  1. محافظت از حالت مشترک با یک قفل (Mutex).
  2. ریختن یک تسک برای مدیریت حالت و استفاده از ارسال پیام (message passing) برای کار روی آن.

به‌طور کلی برای داده‌های ساده باید از رویکرد اول استفاده کنید و برای چیزهایی که به کار ناهمگام نیاز دارند — مانند ابزارهای ورودی/خروجی — رویکرد دوم. در این فصل، حالت مشترک یک HashMap است و عملیات‌ها insert و get هستند. هیچ‌کدام از این عملیات‌ها ناهمگام نیستند، پس از یک Mutex استفاده می‌کنیم.

رویکرد دوم در فصل بعد پوشش داده می‌شود.

افزودن وابستگیِ bytes

به‌جای Vec<u8>، crate مینی-ردیس از Bytes متعلق به crate bytes استفاده می‌کند. هدف Bytes فراهم‌کردن یک ساختار آرایهٔ بایتِ مستحکم برای برنامه‌نویسی شبکه است. بزرگ‌ترین ویژگی‌ای که نسبت به Vec<u8> اضافه می‌کند، کلونِ سطحی (shallow cloning) است. به عبارت دیگر، صدازدن clone() روی یک نمونهٔ Bytes دادهٔ زیرین را کپی نمی‌کند. در عوض، یک نمونهٔ Bytes یک دستگیره با شمارش مرجع (reference-counted) به برخی داده‌های زیرین است. نوع Bytes تقریباً یک Arc<Vec<u8>> است، اما با برخی قابلیت‌های اضافه.

برای وابستگی به bytes، موارد زیر را به بخش [dependencies] در Cargo.toml اضافه کنید:

tomlbytes = "1"

مقداردهیِ HashMap

HashMap در میان بسیاری از تسک‌ها و احتمالاً نخ‌های زیادی به اشتراک گذاشته می‌شود. برای پشتیبانی از این کار، در Arc<Mutex<_>> بسته‌بندی می‌شود.

ابتدا، برای راحتی، این نام مستعار نوع (type alias) را بعد از دستورهای use اضافه کنید:

rustuse bytes::Bytes;
use std::collections::HashMap;
use std::sync::{Arc, Mutex};

type Db = Arc<Mutex<HashMap<String, Bytes>>>;

سپس تابع main را به‌روزرسانی کنید تا HashMap را مقداردهی کند و یک دستگیرهٔ (handle) Arc به تابع process بدهد. استفاده از Arc به HashMap اجازه می‌دهد به‌صورت هم‌روند از بسیاری از تسک‌ها — که احتمالاً روی نخ‌های زیادی اجرا می‌شوند — ارجاع داده شود. در سراسر توکیو، واژهٔ دستگیره برای اشاره به مقداری استفاده می‌شود که دسترسی به برخی حالت‌های مشترک را فراهم می‌کند.

rustuse tokio::net::TcpListener;
use std::collections::HashMap;
use std::sync::{Arc, Mutex};

#[tokio::main]
async fn main() {
    let listener = TcpListener::bind("127.0.0.1:6379").await.unwrap();

    println!("Listening");

    let db = Arc::new(Mutex::new(HashMap::new()));

    loop {
        let (socket, _) = listener.accept().await.unwrap();
        // دستگیرهٔ hash map را کلون کن
        let db = db.clone();

        println!("Accepted");
        tokio::spawn(async move {
            process(socket, db).await;
        });
    }
}

دربارهٔ استفاده از std::sync::Mutex و tokio::sync::Mutex

توجه کنید برای محافظت از HashMap از std::sync::Mutex استفاده شده است و نه tokio::sync::Mutex. یک خطای رایج استفادهٔ بدون قیدوشرط از tokio::sync::Mutex درون کد ناهمگام است. یک mutex ناهمگام، mutexی است که در میان فراخوانی‌های .await قفل می‌ماند.

یک mutex همگام هنگام انتظار برای گرفتن قفل، نخِ جاری را مسدود می‌کند. این به نوبهٔ خود، پردازشِ سایر تسک‌ها را مسدود می‌کند. تغییر به tokio::sync::Mutex باعث می‌شود تسک کنترل را به اجراکننده (executor) بازگرداند؛ اما این معمولاً به کارایی کمکی نمی‌کند، چون mutex ناهمگام در داخل خودش از یک mutex همگام استفاده می‌کند.

به‌عنوان یک قاعدهٔ سرانگشتی: استفاده از یک mutex همگام درون کد ناهمگام تا زمانی خوب است که رقابت (contention) کم بماند و قفل در میان فراخوانی‌های .await نگه داشته نشود.

به‌روزرسانیِ process()

تابع process دیگر یک HashMap مقداردهی نمی‌کند. در عوض، دستگیرهٔ مشترک HashMap را به‌عنوان آرگومان می‌گیرد. همچنین باید قبل از استفاده، HashMap را قفل کند. به یاد داشته باشید که نوع مقدارِ HashMap حالا Bytes است (که می‌توانیم ارزان کلونش کنیم)، پس این مورد هم باید تغییر کند.

rustuse tokio::net::TcpStream;
use mini_redis::{Connection, Frame};

async fn process(socket: TcpStream, db: Db) {
    use mini_redis::Command::{self, Get, Set};

    // نوع `Connection` که توسط `mini-redis` فراهم شده،
    // تجزیهٔ قاب‌ها از سوکت را مدیریت می‌کند
    let mut connection = Connection::new(socket);

    while let Some(frame) = connection.read_frame().await.unwrap() {
        let response = match Command::from_frame(frame).unwrap() {
            Set(cmd) => {
                let mut db = db.lock().unwrap();
                db.insert(cmd.key().to_string(), cmd.value().clone());
                Frame::Simple("OK".to_string())
            }
            Get(cmd) => {
                let db = db.lock().unwrap();
                if let Some(value) = db.get(cmd.key()) {
                    Frame::Bulk(value.clone())
                } else {
                    Frame::Null
                }
            }
            cmd => panic!("unimplemented {:?}", cmd),
        };

        // پاسخ را برای کلاینت بنویس
        connection.write_frame(&response).await.unwrap();
    }
}

نگه‌داشتن یک MutexGuard در میان یک .await

ممکن است کدی بنویسید که این‌گونه باشد:

rustuse std::sync::{Mutex, MutexGuard};

async fn increment_and_do_stuff(mutex: &Mutex<i32>) {
    let mut lock: MutexGuard<i32> = mutex.lock().unwrap();
    *lock += 1;

    do_something_async().await;
} // قفل این‌جا از scope خارج می‌شود

وقتی تلاش می‌کنید چیزی را بریزید که این تابع را صدا می‌زند، با پیام خطای زیر مواجه می‌شوید:

rust// این کار می‌کند!
async fn increment_and_do_stuff(mutex: &Mutex<i32>) {

توجه کنید که این کار نمی‌کند:

rustuse std::sync::{Mutex, MutexGuard};

// این هم شکست می‌خورد.
async fn increment_and_do_stuff(mutex: &Mutex<i32>) {
    let mut lock: MutexGuard<i32> = mutex.lock().unwrap();
    *lock += 1;
    drop(lock);

    do_something_async().await;
}

این به این دلیل است که کامپایلر در حال حاضر صرفاً بر اساس اطلاعات scope محاسبه می‌کند که یک future آیا Send است یا نه. امید است کامپایلر در آینده به‌روزرسانی شود تا از drop صریح پشتیبانی کند؛ اما فعلاً باید صریحاً از scope استفاده کنید.

توجه کنید خطای موردبحث در این‌جا در بخش مرز Send در فصل ریختن تسک‌ها نیز بحث شده است.

نباید تلاش کنید این مشکل را با ریختن تسک به شکلی دور بزنید که به Send بودن نیاز نداشته باشد؛ زیرا اگر توکیو تسک شما را روی یک .await در حالی که تسک قفل را در دست دارد معلق کند، ممکن است تسک دیگری روی همان نخ زمان‌بندی شود و این تسکِ دیگر هم تلاش کند همان mutex را قفل کند، که به بن‌بست (deadlock) می‌انجامد؛ چون تسکی که منتظر قفل است، مانع آزادشدنِ قفل توسط تسکِ دارندهٔ قفل می‌شود.

به خاطر داشته باشید برخی از crateهای mutex برای MutexGuardهای خودشان Send را پیاده‌سازی می‌کنند. در این حالت، حتی اگر یک MutexGuard را در میان یک .await نگه دارید، خطای کامپایلر وجود ندارد. کد کامپایل می‌شود، اما بن‌بست می‌کند!

برخی رویکردها برای اجتناب از این مشکلات را در زیر بررسی می‌کنیم:

بازسازی کد برای نگه‌نداشتن قفل در میان یک .await

امن‌ترین راه برای مدیریت یک mutex این است که آن را در یک ساختار (struct) بپیچید و قفل را فقط درون متدهای غیرناهمگام همان ساختار بگیرید.

rustuse std::sync::Mutex;

struct CanIncrement {
    mutex: Mutex<i32>,
}
impl CanIncrement {
    // این تابع async علامت‌گذاری نشده است
    fn increment(&self) {
        let mut lock = self.mutex.lock().unwrap();
        *lock += 1;
    }
}

async fn increment_and_do_stuff(can_incr: &CanIncrement) {
    can_incr.increment();
    do_something_async().await;
}

این الگو تضمین می‌کند به خطای Send برنخواهید خورد، چون محافظِ قفل (mutex guard) هیچ‌جا در یک تابع ناهمگام ظاهر نمی‌شود. همچنین هنگام استفاده از crateهایی که MutexGuardشان Send را پیاده‌سازی می‌کند، از بن‌بست‌ها هم محافظت می‌شوید.

می‌توانید یک مثال با جزئیات بیشتر را در این پست وبلاگ پیدا کنید.

ریختن یک تسک برای مدیریت حالت و استفاده از ارسال پیام برای کار روی آن

این رویکرد دوم است که در ابتدای این فصل به آن اشاره شد و اغلب وقتی منبعِ مشترک یک منبع ورودی/خروجی باشد استفاده می‌شود. برای جزئیات بیشتر، فصل بعد را ببینید.

استفاده از mutex ناهمگامِ توکیو

نوع tokio::sync::Mutex که توسط توکیو فراهم شده را هم می‌توان استفاده کرد. ویژگی اصلی mutex توکیو این است که می‌توان آن را بدون هیچ مشکلی در میان یک .await نگه داشت. با این حال، یک mutex ناهمگام از یک mutex معمولی گران‌تر است و معمولاً بهتر است از یکی از دو رویکرد دیگر استفاده کنید.

rustuse tokio::sync::Mutex; // توجه کن! این از mutex توکیو استفاده می‌کند

// این کامپایل می‌شود!
// (اما در این حالت بازسازی کد بهتر است)
async fn increment_and_do_stuff(mutex: &Mutex<i32>) {
    let mut lock = mutex.lock().await;
    *lock += 1;

    do_something_async().await;
} // قفل این‌جا از scope خارج می‌شود

تسک‌ها، نخ‌ها و رقابت (Tasks, threads, and contention)

استفاده از یک mutex مسدودکننده برای محافظت از بخش‌های بحرانی کوتاه، وقتی رقابت حداقلی باشد راهبردی قابل‌قبول است. وقتی قفل رقابتی باشد، نخی که تسک را اجرا می‌کند باید مسدود شود و منتظر mutex بماند. این کار نه‌فقط تسک جاری را مسدود می‌کند، بلکه همهٔ تسک‌های دیگری را هم که روی نخِ جاری زمان‌بندی شده‌اند مسدود می‌کند.

به‌طور پیش‌فرض، رانتایم توکیو از یک زمان‌بند چندنخی استفاده می‌کند. تسک‌ها روی هر تعدادی از نخ‌ها که رانتایم مدیریت می‌کند زمان‌بندی می‌شوند. اگر تعداد زیادی تسک برای اجرا زمان‌بندی شوند و همگی به mutex نیاز داشته باشند، رقابت رخ می‌دهد. از سوی دیگر، اگر از نسخهٔ رانتایمِ current_thread استفاده شود، mutex هرگز رقابتی نخواهد شد.

نکته: نسخهٔ رانتایمِ current_thread یک رانتایم سبکِ تک‌نخی است. وقتی فقط چند تسک می‌ریزید و چند سوکت باز می‌کنید انتخاب خوبی است. برای مثال، وقتی یک پلِ رابطِ همگام (synchronous API bridge) روی یک کتابخانهٔ کلاینت ناهمگام فراهم می‌کنید، این گزینه به‌خوبی کار می‌کند.

اگر رقابت روی یک mutex همگام مشکل‌ساز شد، بهترین راه‌حل به‌ندرت تغییر به mutex توکیو است. در عوض، گزینه‌هایی که باید در نظر بگیرید این‌ها هستند:

  • این‌که یک تسک اختصاصی حالت را مدیریت کند و از ارسال پیام استفاده شود.
  • شارد کردن (shard) mutex.
  • بازسازی کد برای اجتناب از mutex.

شارد کردن قفل (Mutex sharding)

در مورد ما، چون هر کلید مستقل است، شارد کردن قفل به‌خوبی کار می‌کند. برای این کار، به‌جای یک نمونهٔ Mutex<HashMap<_, _>>، N نمونهٔ مجزا معرفی می‌کنیم.

rusttype ShardedDb = Arc<Vec<Mutex<HashMap<String, Vec<u8>>>>>;

fn new_sharded_db(num_shards: usize) -> ShardedDb {
    let mut db = Vec::with_capacity(num_shards);
    for _ in 0..num_shards {
        db.push(Mutex::new(HashMap::new()));
    }
    Arc::new(db)
}

سپس، یافتن سلولِ مربوط به هر کلید به یک فرایند دو مرحله‌ای تبدیل می‌شود. ابتدا از کلید برای شناساییِ شاردی که کلید به آن تعلق دارد استفاده می‌شود. سپس کلید در HashMap جست‌وجو می‌شود.

rustlet shard = db[hash(key) % db.len()].lock().unwrap();
shard.insert(key, value);

پیاده‌سازی ساده‌ای که در بالا آمد نیاز به استفاده از تعداد ثابتی شارد دارد و پس از ساختِ map شاردشده، دیگر نمی‌توان تعداد شاردها را تغییر داد.

crate dashmap پیاده‌سازیِ پیچیده‌تری از hash map شاردشده فراهم می‌کند. شاید هم بخواهید به پیاده‌سازی‌های جدول هشِ هم‌روند مانند leapfrog و flurry نگاه کنید؛ مورد دوم یک پورت از ساختار دادهٔ ConcurrentHashMap جاواست.

قبل از شروع استفاده از هر یک از این crateها، مطمئن شوید کدتان را طوری ساختار می‌دهید که نتوانید یک MutexGuard را در میان یک .await نگه دارید. اگر این کار را نکنید، یا خطای کامپایلر خواهید داشت (در مورد محافظ‌های غیر-Send) یا کدتان بن‌بست می‌کند (در مورد محافظ‌های Send). یک مثال کامل و زمینهٔ بیشتر را در این پست وبلاگ ببینید.

کانال‌ها (Channels)

↗ مشاهده بخش اصلی در tokio.rs

در بخش قبل تمام شد که برای دسترسی اشتراک‌گذاری‌شده، mutexها می‌توانند استفاده شوند. به‌عنوان راهکاری مکمل، می‌توان مسیر دسترسی منحصربه‌فردی به حالت مشترک با استفاده از کانال‌های توکیو در اختیار یک تسک اختصاصی قرار داد.

کانال‌ها (Channels)

یک crate موازی با توکیو به نام tokio::sync وجود دارد که شامل دو نوع کانال است:

  • mpsc — یک کانال چند-تولیدکننده، تک-مصرف‌کننده (multi-producer, single-consumer)
  • oneshot — یک کانال تک-ارسال (single-producer, single-consumer) که می‌تواند یک مقدار بفرستد

در حالی که مورد دوم فقط یک مقدار را پشتیبانی می‌کند، اولی می‌تواند جریان‌هایی از مقادیر را بفرستد. هر دو پشتیبانی می‌کنند که انتظارِ کانال بدون مسدود کردن نخ، کشیده شود. پنجرهٔ بازگشت (backpressure) هم دارند: وقتی صف خالی است، انتظارِ دریافت مسدود می‌شود؛ وقتی صف پر است، فرستنده می‌تواند منتظر بماند.

اگر نیاز به فرستادن مقادیر بین چند فرستنده و چند گیرنده دارید، می‌توانید به جای آن از کانال‌های خارج از توکیو مانند sync_channel یا crateهایی مانند crossbeam-channel یا flume استفاده کنید.

تعریف پیام (Defining the message)

در مثال خودمان، یک پایانهٔ کلید-مقدار داریم. برای عملیات‌های همگام‌سازی، از استرینگ‌های ساده استفاده می‌کنیم؛ فقط برای دو نوع عملیات، که مطابق با دستورهای Set و Get هستند. برای حوزهٔ دستورهایمان، یک نوع enum می‌سازیم:

rustuse tokio::sync::oneshot;
use bytes::Bytes;

/// چندین دستورها می‌توانند روی یک کانال فرستاده شوند.
#[derive(Debug)]
enum Command {
    Get {
        key: String,
        resp: Responder<Option<Bytes>>,
    },
    Set {
        key: String,
        value: Bytes,
        resp: Responder<()>,
    },
}

هیچ یک از این عملیات‌ها ورودی/خروجی بر روی سوکت را انجام نمی‌دهند؛ انجام این کار به کد پیچیده‌تری نیاز دارد و می‌تواند سازندهٔ تصویر را لکه‌دار کند. در این قدامی این کار را انجام نمی‌دهیم؛ به‌جای آن مدیر را طوری طراحی می‌کنیم که responses در کانال‌های oneshot فرستاده شوند.

ایجاد کانال

توابع تولیدکننده (constructor functions) سر راست هستند. برای مثال new_shared_state:

rust/// مدیر را با navigating و initialized کن
fn new_shared_state(
    num_shards: usize,
) -> (Arc<Shared>, mpsc::Sender<Command>) {
    let mut shards = Vec::with_capacity(num_shards);
    for _ in 0..=num_shards {
        shards.push(Shard::new());
    }

    let shared = Arc::new(Shared { shards });
    let (update_tx, update_rx) = mpsc::channel(num_shards);
    shared.clone().spawn_manager(update_rx);
    (shared, update_tx)
}

ارسال یک دریافت (Sending a request)

برای دریافت کردن values، یک کانال oneshot ایجاد می‌کنیم و آن را با فرستادنِ دستور GET هم‌مسیر می‌فرستیم:

rustfn get_value(
    shard: &Shard,
    key: &str,
) -> impl Future<Output = Option<Bytes>> {
    let (resp_tx, resp_rx) = oneshot::channel();
    let _ = shard.rx_tx.try_send(Command::Get {
        key: key.to_string(),
        resp: resp_tx,
    });

    async move {
        match resp_rx.await {
            Ok(res) => res,
            Err(_) => None,
        }
    }
}

برای به‌روزرسانی مقادیر، هم‌مسیر برعکس انجام می‌شود:

rustfn set_value(
    shard: &Shard,
    key: String,
    value: Bytes,
) -> impl Future<Output = ()> {
    let (resp_tx, resp_rx) = oneshot::channel();
    let _ = shard.rx_tx.try_send(Command::Set {
        key,
        value,
        resp: resp_tx,
    });

    async move {
        let _ = resp_rx.await;
    }
}

سپس می‌توانیم دستورها را دریافت کرده، به‌روزرسانی کنیم و به کلاینت‌ها پاسخ بدهیم:

rustasync fn get_value(
    shard: &Shard,
    key: &str,
) -> Option<Bytes> {
    let (resp_tx, resp_rx) = oneshot::channel();
    let _ = shard.rx_tx.try_send(Command::Get {
        key: key.to_string(),
        resp: resp_tx,
    });

    resp_rx.await.ok().flatten()
}

async fn set_value(
    shard: &Shard,
    key: String,
    value: Bytes,
) {
    let (resp_tx, resp_rx) = oneshot::channel();
    let _ = shard.rx_tx.try_send(Command::Set {
        key,
        value,
        resp: resp_tx,
    });

    let _ = resp_rx.await;
}

نتیجهٔ resp_rx.await.ok().flatten(): Option<Result<Option<Bytes>, RecvError>> اول تبدیل می‌شود و بعد flatten می‌شود. با استفاده از این موارد، map_read و map_write را این‌گونه پیاده می‌کنیم:

rustasync fn map_read(shared: &Arc<Shared>, key: String) -> Option<Bytes> {
    let shard = shard(shared, &key);
    get_value(shard, &key).await
}

async fn map_write(
    shared: &Arc<Shared>,
    key: String,
    value: Bytes,
) {
    let shard = shard(shared, &key);
    let _ = set_value(shard, key, value).await;
}

دقت کنید در این مثال، shardها را برای کوچک نگه‌داشتن مثال نادیده گرفته‌ایم؛ به‌عنوان تمرین می‌توانید اجرای شاردینگ را کامل کنید.

پایه (Backbone)

شما باید یک تسک مدیر ایجاد کرده باشید که دریافت انحصاری (mpsc::Receiver<Command>) را نگه داشته و سرآیند اجرای تسک‌های یکتا را بچرخاند.

rustuse tokio::sync::mpsc;

async fn start_manager(
    manager: mpsc::Receiver<Command>,
    shard_rxs: Vec<Shard>,
) {
    let manager = Manager::new(manager, shard_rxs);

    tokio::spawn(async move {
        manager.run().await;
    });
}

اینجاست که همهٔ تسک‌ها اجرا می‌شوند: تسک‌ها به‌صورت ناهمگام اجرا می‌شوند و تا زمانی که عملیات‌های sync (همگام) به پایان برسند یا به کانال‌ها دسترسی پیدا کنند، منتظر می‌مانند.

از این طریق — یعنی با استفاده از oneshotها برای reply کردن — کلاینت‌ها (مدیر و مشتری که از طریق خط فرمان با آنها گفت‌وگو می‌کند) می‌توانند بدون اینکه منتظر پاسخ بمانند، دستور بفرستند. مدیر هم به‌نوبهٔ خود می‌داند چه زمان‌بندیِ پاسخ برای هر دستور لازم است.

فشرده‌سازی پاسخ‌ها (Backpressure) و حلقهٔ دریافت

حلقهٔ دریافت (receive loop) یا loop زندهٔ تسک مدیر — که مدیریت یک مقدار و مدیر را بر عهده دارد — نباید به‌صورت تک‌نخی مسدودکننده اجرا شود. باید بتواند pure async دریافت کند. در این‌جا دو panic رخ می‌دهد: یکی زمانی که دریافت از receiver شکست بخورد، و دیگری وقتی که از shard شکست بخورد.

rustimpl Manager {
    async fn run(&self) {
        loop {
            match self.manager_rx.recv().await {
                Some(cmd) => self.process(cmd).await,
                None => panic!("manager_rx closed"),
            };
        }
    }

    async fn process(&self, cmd: Command) {
        match cmd {
            Command::Get { key, resp } => {
                let shard = &self.call_rxs[shard_for(&key)];
                let res = get_value(shard, &key).await;
                let _ = resp.send(res);
            }
            Command::Set { key, value, resp } => {
                let shard = &self.call_rxs[shard_for(&key)];
                set_value(shard, key, value).await;
                let _ = resp.send(());
            }
        };
    }
}

وقتی recv().await مقدار None برگرداند، یعنی تمام فرستنده‌ها بسته شده‌اند (یا کانال خالی است). با تعریف کامل پیام‌ها، همهٔ این عملیات‌ها async هستند و کد ما تا این‌جا امن است.

استفاده از کانال‌ها برای جریان‌های ناهمگام (Using channels for async streams)

مدیرهای مبتنی بر کانال می‌توانند برای مدیریت جریان‌های ناهمگام به‌کار روند؛ به این شکل که Subها یک بار در هر نوع رویداد، enabled می‌شوند. سپس، چون mpsc یک کانال چند-تولیدکننده است، فرستنده‌ها می‌توانند روی shard_txها بفرستند. برای قفل کردن enabled، فقط مدیر باید تصمیم بگیرد؛ تولیدکنندگان هم می‌توانند فقط اگر enabled باشد، بفرستند؛ پس enabled باید قبل از send بررسی شود.

این مثال‌ها برگرفته از نسخهٔ کامل‌تر پیاده‌سازیِ استفادهٔ کانال‌ها در سرور مینی-ردیس هستند.

هدر دادنِ پیام‌ها (Dropping messages)

در مدل mpsc، تنها راه برای اینکه بفهمیم همهٔ مصرف‌کننده‌ها از مصرف بازمانده‌اند، استفاده از روش «قطره (drop)» است. این موضوع می‌تواند هنگام کار با کد async، پیچیدگی‌های غیرمنتظره‌ای ایجاد کند؛ برای مثال، اگر بعد از یک send، تسک پاک شود، پیام در کانال‌های mpsc گم می‌شود و پاسخ هرگز نمی‌رسد.

در نهایت، این‌روزها معمولاً توصیه می‌شود برای ترافیک‌های «fire-and-forget» (بفرست و فراموش کن) از tokio::sync::Notify یا std::sync::Notify، که کانال‌های بیدارکنندهٔ منتظرم‌ماندگان هستند، استفاده شود. فقط مطمئن شوید ریسهٔ زندگی (lifetime) آنچه می‌فرستید را بررسی کرده‌اید. به‌طور کلی، بهتر است دریافت‌کننده، صندوق پیام‌ها (mailbox) را مدیریت کند، نه فرستنده — در غیر این صورت هر پیام می‌تواند از دست برود.

نکته: در فصل بعد، رویکرد دومِ به‌اشتراک‌گذاری حالت — یعنی ریختن یک تسک برای مدیریت حالت و استفاده از ارسال پیام برای کار روی آن — به‌طور کامل پیاده‌سازی می‌شود.

ورودی/خروجی (I/O)

↗ مشاهده بخش اصلی در tokio.rs

توکیو و سایر کتابخانه‌های async، مجموعه‌ای از traits و اجرای مفیدی را برای انجام ورودی/خروجی (I/O) فراهم می‌کنند. این traits و پیاده‌سازی‌ها به‌صورت اشتراکی استفاده می‌شوند و به شما امکان می‌دهند از یک «مدل زمینه» استفاده کنید: مثلاً یک کتابخانهٔ کلاینت TCP و یک کتابخانهٔ کلاینت HTTP هر دو می‌توانند روی یک نوع سرویس‌گیرنده (server) کار کنند، یا یک کتابخانهٔ TcpListener خودش را دارد ولی برنامه شما سرویس‌گیرندهٔ خودش را می‌نویسد.

AsyncRead و AsyncWrite

این traits جریان‌های بایتِ ناهمگام را فراهم می‌کنند. درست همان‌طور که std::io::Read و std::io::Write عمل می‌کنند، اما ناهمگام. Read مسدودکننده را با read/read_to_end مدیریت می‌کند؛ AsyncRead هم مدیریت انتظار برای آماده‌شدن داده‌ها را به‌گونه‌ای انجام می‌دهد که نخ را مسدود نکند. این traits معمولاً با ترکیب‌کننده‌ها (combinators) استفاده می‌شوند، مانند AsyncReadExt و AsyncWriteExt. برای شروع کار، از هریک از دو کارکرد زیر استفاده کنید: read() و write()، که هر دو از صراحت بیشتری برخوردارند.

مینی‌ردیس برای نوشتن قاب‌ها از AsyncWriteExt استفاده می‌کند، و برای خواندن از AsyncReadExt؛ همچنین پشتیبانی از عملیات‌های جانبی مانند read_to_end() و write_all() را هم فراهم می‌کند: می‌توانید AsyncReadExt::read_to_end() را برای خواندن همهٔ داده‌های خروجی یک جریان استفاده کنید و AsyncWriteExt::write_all() را برای نوشتن یک حرکت کامل (buffer) استفاده کنید.

برای نمونه، یک TcpStream از توکیو هر دوی AsyncRead و AsyncWrite را پیاده‌سازی می‌کند، همین‌طور File از توکیو، و Stdout از توکیو.

دو نمونهٔ کاربردی

مثال اول: یک سرور پژواک (echo server)، که ورودی را به همان شکلی که دریافت می‌کند برمی‌گرداند.

rustuse tokio::io::{self, AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:6142").await?;

    loop {
        let (mut socket, _) = listener.accept().await?;

        tokio::spawn(async move {
            let mut buf = vec![0; 1024];

            // در یک حلقه، داده را بخوان،
            // سپس آن را به عقب بنویس
            loop {
                let n = socket
                    .read(&mut buf)
                    .await
                    .expect("failed to read data from socket");

                if n == 0 {
                    return;
                }

                socket
                    .write_all(&buf[0..n])
                    .await
                    .expect("failed to write data to socket");
            }
        });
    }
}

حالا همین کار را با io::copy():

rustuse tokio::io;
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:6142").await?;

    loop {
        let (mut socket, _) = listener.accept().await?;

        tokio::spawn(async move {
            // کپی از سوکت به خودش به‌طور مستقیم
            // نخواهد کار کرد
            let (mut rd, mut wr) = socket.split();

            if io::copy(&mut rd, &mut wr).await.is_err() {
                eprintln!("failed to copy");
            }
        });
    }
}

io::copy داده را از یک خواننده (reader) به یک نویسنده (writer) می‌کپی‌کند و دو آرگومان می‌گیرد: یکی که AsyncRead را پیاده‌سازی می‌کند و دیگری که AsyncWrite را. این تابع انتظار می‌کشد تا خواندن آماده شود و سپس با read_to_end() همهٔ داده را می‌خواند. نسخهٔ io::copy با بافرهای بزرگ کار می‌کند.

دقت کنید که در این نسخه از io::copy، کل سوکت به‌عنوان قرائت‌کننده و نویسنده استفاده می‌شود؛ split() اجازه می‌دهد عملیات‌های خواندن و نوشتن به‌طور هم‌زمان انجام شوند، اما چون در این کد از آن استفاده نشده، کپی کردن از یک شیء به همان شیء در حلقه مجاز نخواهد بود... در عمل، io::copy نسخهٔ tokio::io::copy را بعداً به‌روزرسانی می‌کند.

برای حل این مشکل، به جای کل سوکت از «نیمه‌های» آن استفاده می‌کنیم:

rustuse tokio::io;
use tokio::net::TcpStream;

// از طریق یک ارتقا کوچک، می‌توانیم
// نیمی از سوکت را برای خواندن
// و نیمی را برای نوشتن داشته باشیم
async fn process(mut socket: TcpStream) {
    let (mut rd, mut wr) = socket.split();

    let _ = io::copy(&mut rd, &mut wr).await;
}

در این نسخه، split() سوکت را به دو نیمه تقسیم می‌کند: یکی که AsyncRead را پیاده می‌کند (rd) و دیگری که AsyncWrite را پیاده می‌کند (wr). حالا، چون هر دونفر روی دادهٔ یکسان کار نمی‌کنند، io::copy می‌تواند داده را از rd به wr کپی کند، و برنامه به‌عنوان یک سرور پژواک عمل می‌کند.

در نسخه‌های قدیمی‌تر توکیو، این کار باید به‌شکل let (rd, wr) = socket.split() انجام می‌شد، اما والدِ socket همین‌جا drop می‌شود؛ راه‌حل در نسخهٔ جدید، TcpStream::into_split() است:

rustuse tokio::io;
use tokio::net::TcpStream;

async fn process(socket: TcpStream) {
    let (mut rd, mut wr) = socket.into_split();

    let _ = io::copy(&mut rd, &mut wr).await;
}

io::split همچنین برای انواع دیگری مانند DuplexStream هم موجود است که می‌تواند بین server و client استفاده شود.

بیشتر درمورد AsyncRead و AsyncWrite (Manual read/write)

توکیو هر دو نقشِ «خواندن تا پر شدنِ بافر» و «خواندن همهٔ data» را با AsyncReadExt::read() و AsyncReadExt::read_to_end() مدیریت می‌کند. اگر لازم است دقیقاً تعداد مشخصی بایت بخوانید — مثل مواردی که با قاب‌ها کار می‌کنید — از AsyncReadExt::read_exact() استفاده کنید.

اگر بخواهید ببینید TcpStream آیا داده‌ای برای خواندن دارد یا نه — بدون اینکه منتظر بمانید — می‌توانید poll_read را میلی سنجید، ولی معمولاً این کار نیاز نیست. برای مثال، معماری‌های ناهمگام مبتنی بر رویداد (event-driven) با AsyncReadExt::read() که انتظار می‌کشد تا داده موجود شود، به‌خوبی کار می‌کنند.

برای نوشتن چند بافر به‌صورت یکجا، write_vectored() را امتحان کنید، که شبیه std::io::Write::write_vectored است؛ نمونهٔ استفاده از آن در mini-redis برای نوشتن یک قاب که شامل چند بخش است دیده می‌شود.

نکته: نوشتن پیوسته برای پروتکل‌های متن‌محور، مانند پروتکل‌های فریم، می‌تواند مشکلاتی ایجاد کند. برای جزئیات، به فصل «Framing» بروید.

موقعیت‌یابی در جریان‌های خواندنی/نوشتنی: هر دوی AsyncRead و AsyncWrite برای موقعیت‌یابی، از اعداد ۷۲ بیتی استفاده می‌کنند. برای جابه‌جایی موقعیت، می‌توانید از AsyncSeekExt::seek() استفاده کنید؛ Fileها از توکیو این ویژگی را پیاده‌سازی می‌کنند.

اجرا برای Serverها و Clientها

ساختن Client با TcpStream و Server با TcpListener ساده است.

برای Client، استفاده از TcpStream::connect():

rustuse tokio::net::TcpStream;
use tokio::io::AsyncWriteExt;

async fn main() -> io::Result<()> {
    let mut stream = TcpStream::connect("127.0.0.1:6142").await?;
    stream.write_all(b"hello world").await?;
    Ok(())
}

این مدل برای هر پروتکل مبتنی بر TCP — از HTTP گرفته تا وب‌سوکت‌ها و FTP — کار می‌کند. اگر از نوع بایت‌های ناهمگام (AsyncRead + AsyncWrite) پشتیبانی شود، می‌توان آن را با tokio::io استفاده کرد.

Server (Listener)

برای اینکه یک server کار کند، باید حالت قبلیِ acceptor را نگه داریم و برای هر اتصال، یک پاسخ‌گو (handler) بسازیم. این کار را می‌توان به‌وضوح این‌گونه انجام داد:(بخش نخستِ همین فصل، سرور پذیرش و پاسخ را نشان داد). برای جلوگیری از تکرار، به نمونهٔ اول فصل (echo server) مراجعه کنید.

روش‌های دیگر منتخب (Other utility functions)

در این فصل با io::copy آشنا شدیم که کپی کامل است. یک تابع مشابه دیگر، io::sink() است که همهٔ داده‌ها را دور می‌ریزد؛ برای آزمایش مفید است. توابع همه‌کارهٔ دیگری مثل repeat() و empty() هم هست.

هنگامی که برنامه بزرگ می‌شود، با دقت از tracing یا tokio-console استفاده کنید و در حین اجرا، استفادهٔ I/O را مشاهده کنید؛ این ابزارها داده‌های ارزشمندی دربارهٔ کارایی برنامه به شما می‌دهند.

نکته: در مینی‌ردیس، کد واقعیِ خواندن/نوشتن قاب‌ها در فصل «Framing» پیاده‌سازی می‌شود؛ در آن‌جا از AsyncReadExt::read()، AsyncWriteExt::write_all() و bufferها استفاده می‌کنیم.

قاب‌بندی (Framing)

↗ مشاهده بخش اصلی در tokio.rs

در فصل قبل، برنامهٔ سرورِ مینی‌ردیس داده‌ها را به‌صورت خام می‌خواند و می‌نوشت. پیاده‌سازیِ درست، «قاب» (frame)ها را می‌خواند و می‌نویسد.

قاب چیست؟ (What is framing)

وقتی دو برنامهٔ نظیر یکدیگر با هم در یک شبکه صحبت می‌کنند، نیاز به یک قرارداد برای نوع داده‌هایی دارند که مبادله می‌کنند. برای مثال، یک پروتکل ممکن است به این شکل باشد:

  • یک عدد صحیحِ ۳۲ بیتیِ آخر اینکه طول پیام است
  • به‌دنبالش بایت‌های پیام
  • سپس پیامِ بعدی

با این قرارداد، طولی که برای هر پیام می‌خوانید تعیین می‌شود. نام این فرایند جداسازی قاب‌ها (framing) است.

پروتکل‌های مختلف قوانین متفاوتی برای قاب‌بندی دارند. یک قانون بسیار ساده سرصفحه یا سرفصلِ (header) بوده و سپس پیام و... . قانون دیگری که اغلب دیده می‌شود: بر اساس ساختار، یعنی پر کردن با یک کاراکتر معین (مثل خط جدید) یا با الگوهای مبتنی بر مقدار (مثل الگوهایی که اخیراً برای عبارات JSON استفاده می‌شود).

ساده‌ترین راه برای شروع، این است که ببینید قاب‌بندی در crate مینی-ردیس چگونه انجام می‌شود؛ بعد می‌توانیم آن را برای مثال خودمان بازسازی کنیم.

هدر_valid (Frames از دید client/server)

در ابتدای آموزش، یک دادهٔ Frame را در ساختار خودمان تعریف کردیم: فریم‌های بلندی که داده را از client به server حمل می‌کنند. پاسخ‌ها از server به client نیز اگرچه داده را متفاوت هدایت می‌کنند، ولی هر دوی‌شان پروتکل قاب‌بندی مشترکی دارند: ابتدا ممکن است یک Byte خام بیاید…

بگذارید بخش واقعی‌تر را ببینیم: یک Frame در مینی-ردیس یک روی   lazily parse شده است. در اینجا نسخه‌ای است که در src/frame.rs هست:

rustuse bytes::Bytes;

enum Frame {
    Simple(String),
    Error(String),
    Integer(u64),
    Bulk(Bytes),
    Null,
    Array(Vec<Frame>),
}

قاب‌ها «بسته‌های دادهٔ کامل» هستند که peerهای یک پروتکل بین هم می‌فرستند. در سمت پایین‌تر، قرارداد ما می‌گوید هر قاب با یک بایتِ نوع شروع می‌شود، بعد بدنهٔ آن (بر اساس نوع). این قرارداد ساده، پیاده‌سازی یک پیاده‌سازی‌شدهٔ کارآمد را فراهم می‌کند.

برای یک شبکهٔ واقعی، یک قابٔ جداگانه با یک مقدار مشخص (مثل یک طول) شروع می‌شود. بیایید یک نمونه از کاربردها ببینیم:

تغییر به Bytes

در نسخهٔ قبلی مینی-ردیس، از Vec<u8> برای بدنهٔ قاب استفاده می‌شد. با Bytes، ارسال قاب‌ها بسیار کارآمدتر می‌شود: وقتی یک قاب دریافت می‌شود، دادهٔ آن می‌تواند با clone سطحی به‌اشتراک گذاشته شود.

در عمل برای پیاده‌سازی read_frame، داده را می‌خوانیم و یک Bytes می‌سازیم که به آن claimed شود. این اکنون کد معتبر مینی-ردیس است:

rustimpl Connection {
    /// یک single frame را از stream بخوان
    pub async fn read_frame(&mut self)
        -> crate::Result<Option<Frame>>
    {
        loop {
            let _len = self.buffer.len();
            if let Some(packet) = self.parse_frame()? {
                return Ok(Some(packet));
            }
            if 0 == self.stream.read_buf(&mut self.buffer).await? {
                // اگر یک frame با EOF نزدیک شده بود None را برگردان،
                // در غیر این صورت خطای اتصال را گزارش کن
                if self.buffer.is_empty() {
                    return Ok(None);
                } else {
                    return Err("connection reset by peer".into());
                }
            }
        }
    }
}

read_buf داده را از AsyncRead به BufMut می‌کشد. این ورژن، بافرِ BytesMut را به‌طور مؤثر استفاده می‌کند (می‌تواند از بافرِ تکه‌تکه استفاده کند و داده را کپی نکند). تکه‌های BytesMut به شما این امکان را می‌دهند که دقیقاً اندازهٔ buffer را مدیریت کنید و اجازهٔ رشد خودکار بدهید.

تجزیهٔ قاب (Parsing)

پیاده‌سازیِ parse_frame دو پیامد دارد:

  • اگر دادهٔ کافی برای یک قاب کامل در بافر نباشد، باید بگذاریم None برگردد تا read_frame دادهٔ بیشتری بخواند.
  • کد باید حالت پارسر را ردیابی کند.

برای این کار، قرارداد ما این‌گونه خواهد بود (که الگویِ نوشتن در هر پیاده‌سازی استفاده می‌شود): ابتدا بایتِ نوعِ قاب، سپس بدنه.

اگر پارسر فقط قبل از دادهٔ کامل برگردد، باید بتواند پیشرفت را ردیابی کند. یک راه چیست؟ پیاده‌سازی Frame::parse با امضای زیر:

rustfn parse(buffer: &[u8]) -> Result<Option<Frame>, Error>

Ok(None) یعنی دادهٔ کافی وجود ندارد؛ Ok(Some(frame)) یعنی یک قاب کامل پارس شده و اولِ بافرِ هدر؛ و Err یعنی قابِ غیرقابل‌قبول.

ساده‌ترین پیاده‌سازی‌های اولیه، اولِ خواندنِ بافر را پارس می‌کنند و نسبت به بایتِ نوع رفتار می‌کنند:

rustfn parse(buffer: &[u8]) -> Result<Option<Frame>, Error> {
    use Frame::*;

    match buffer.first() {
        Some(b'+') => {
            // خواندن تا پایان خط و بازگرداندن یک `Simple`
            ...
        }
        Some(b'-') => {
            // ... `Error`
        }
        Some(b':') => {
            // ... `Integer`
        }
        Some(b'$') => {
            // طولِ این قاب با `length` شروع می‌شود
            // سپس `\r\n`
            ...
        }
        Some(b'*') => {
            // ... `Array`
        }
        _ => {
            Err("protocol error; unexpected frame type byte".into())
        }
    }
}

در یک $ (Bulk)، قرارداد این است: $<length>\r\n<data>\r\n. پس پارسر باید این کارها را انجام دهد:

  1. تعداد بایت‌های داده را بخواند و آن را به‌صورت u64 تفسیر کند
  2. یک Bytes به‌اندازهٔ آن طول بسازد
  3. بایت‌های داده را کپی کند
  4. از قاب خارج شود

مدیریت طول‌های بزرگ: اگر ارسال‌کنندهٔ حمله‌گر طولی مثل 999_999_999_999 بفرستد، پارسر باید مراقب باشد که بافر را به‌حدی پر نکند که حافظه تمام شود؛ پس طول را محدود می‌کنیم:

rust// از تخصیص‌های بزرگ جلوگیری کن
if len > MAX_BULK_LEN { ... }

بعد از این‌که یک Frame کامل شد، باید آن را از بافر جدا کنیم؛ برای این کار، Buffer::advance مفید است:

rust// پس از پارس موفق، بایت‌های استفاده‌شده را دور بریز
self.buffer.advance(len);

همین قرارداد بین peerها و transition حالت (پیشرفت نسبی؟)، پارسر را «state machine» می‌کند.

قاب‌بندی با طول (Length-delimited framing)

روش بسیار رایج دیگر، «قاب‌بندیِ محدود به طول» است: ابتدا یک عدد (طول) فرستاده می‌شود و سپس آن تعداد بایت. در مینی-ردیس هم همین قرارداد برای Bulk و Array استفاده می‌شود.

برای پیاده‌سازی، Frame::Bulk را با طولِ دلخواه می‌فرستیم. اگر پیام‌های ما همیشه با یک «طول» شروع شوند، می‌توانیم به‌سادگی read_exact را برای خواندنِ طول صدا بزنیم، سپس «تعداد» را برای دادهٔ اصلی. با این قرارداد، اندازهٔ بافر‌ها قبل از خواندنِ کامل مشخص است.

نوشتن قاب (Writing a frame)

پس از پردازش یک درخواست، باید یک پاسخ بنویسیم. در این‌جا نسخهٔ مینی-ردیسِ write_frame آمده — با فرض اینکه هدرِ write بافر را ندارد؛ برای کارایی، کدهای واقعی از write_vectored استفاده می‌کنند:

rustasync fn write_frame(&mut self, frame: &Frame)
    -> io::Result<()>
{
    match frame {
        Frame::Simple(val) => {
            self.stream.write_all(b"+").await?;
            self.stream.write_all(val.as_bytes()).await?;
            self.stream.write_all(b"\r\n").await?;
        }
        Frame::Error(val) => {
            self.stream.write_all(b"-").await?;
            self.stream.write_all(val.as_bytes()).await?;
            self.stream.write_all(b"\r\n").await?;
        }
        Frame::Integer(val) => {
            self.stream.write_all(b":").await?;
            self.write_decimal(*val).await?;
        }
        Frame::Null => {
            self.stream.write_all(b"$-1\r\n").await?;
        }
        Frame::Bulk(val) => {
            let len = val.len();
            self.stream.write_all(b"$").await?;
            self.write_decimal(len as u64).await?;
            self.stream.write_all(val).await?;
            self.stream.write_all(b"\r\n").await?;
        }
        Frame::Array(val) => {
            self.stream.write_all(b"*").await?;
            self.write_decimal(val.len() as u64).await?;
            for frame in val {
                self.write_frame(frame).await?;
            }
        }
    }
    Ok(())
}

دقت کنید این نسخه برای سادگی از Buffer استفاده نمی‌کند؛ در نسخهٔ واقعی، از BytesMut و flush استفاده می‌شود.

بافر کردن (Buffered reads and writes)

تابع بالا داده را به‌صورت خام به سوکت می‌نویسد. برای کارآمدی، معمولاً می‌خواهیم از بافر استفاده کنیم: به‌جای یک فراخوانی syscall برای هر write_all، داده در حافظه جمع می‌شود و سپس در یک فراخوانی نوشته می‌شود. به همین ترتیب، برای خواندن‌ها از BufReader<TcpStream> استفاده می‌کنیم.

ساده‌ترین راه این است که Connection را با BufReader و BufWriter بسازیم:

rustuse tokio::io::{BufReader, BufWriter};

struct Connection {
    stream: BufReader<BufWriter<TcpStream>>,
    buffer: BytesMut,
}

سازندهٔ آن (constructor) such that:

rustimpl Connection {
    pub fn new(socket: TcpStream) -> Connection {
        let stream = BufReader::new(BufWriter::new(socket));
        Connection {
            stream,
            buffer: BytesMut::with_capacity(4 * 1024),
        }
    }
}

در نسخهٔ سادهٔ بالا از بافرها استفاده نکردیم؛ بگذارید ارتقایش بدهیم. وقتی یک Frame::Array می‌خواهیم بنویسیم، هر Frame را جداگانه می‌نویسیم؛ هر بار write_all فلاش‌کنندهٔ (flush) بافرِ داخل است. این باعث بسیاری از syscallهای کوچک می‌شود. بهتر است همهٔ داده را در یک BytesMut مونتاژ کنیم و فقط یک‌بار بنویسیم. با BufWriter، بافرها به تنهایی مدیریت می‌شوند و داده‌ها به‌طور مؤثر در یک بافر انباشته و سپس در یک فراخوانی نوشته می‌شوند.

یک پیچیدگی مهم: BufWriter::flush() باید بعد از هر قاب صدا زده شود (یا در end-of-response)، وگرنه peer ممکن است هرگز شروع قاب را نبیند. توکیو BufWriter::poll_flush را دارد، ولی اگر فقط در پایان تابع صدا زده شود، نوشتن نادرست است. در عمل بهتر است فشرده‌سازی را به لایهٔ پروتکل خودتان بدهید: قرارداد «یک قاب در هر write_frame» را نگاه دارید.

راه حل استاندارد: قاب را در یک BytesMut با ظرفیت اولیه بسازید، سپس یک‌بار با write_all به BufWriter بدهید و در پایان flush کنید:

rustasync fn write_frame(&mut self, frame: &Frame)
    -> io::Result<()>
{
    let mut buf = BytesMut::with_capacity(128);
    encode_frame(frame, &mut buf); // همهٔ بخش‌ها را مونتاژ کن
    self.stream.write_all(&buf).await?;
    self.stream.flush().await?;
    Ok(())
}

کودک‌ها (Codecs)

فریم‌بندی یک الگوی آن‌قدر رایج است که crate tokio_util::codec یک سیستم ابتکاری برای انجامش دارد، از جمله دیکودرها و انکودرها برای خط‌ها (lines). روش این است: Framed را با یک Codec روی جریان اعمال می‌کنید و سپس Framed::next() قابِ بعدی را به شما می‌دهد که در حال AsyncRead است؛ و Framed::send() یک قاب را می‌نویسد.

برای قاب‌های با طول محدود، LengthDelimitedCodec از tokio_util را می‌توانید استفاده کنید، که دقیقاً «قاب‌بندی محدود به طول» را پیاده می‌کند؛ می‌تواند پیام‌هایی با حداکثر طول مشخص را بخواند، مقدار پیش‌فرض ۸ مگابایت است. توجه کنید که با این کار، کدِ پارسِ دستی که بالاتر نوشتیم دیگر لازم نیست. اگر بخواهید به‌جای buffer از یک Codec استفاده کنید، مثالی است:

rustuse tokio_util::codec::{
    Framed, LengthDelimitedCodec,
};

let stream = TcpStream::connect("...").await?;
let mut framed = Framed::new(stream, LengthDelimitedCodec::new());
let message = framed.next().await??;
نکته: برای پروتکل‌های پیچیده، معمولاً بهتر است از tokio_util::codec استفاده کنید و روی پارس کردنِ پیام‌ها تمرکز کنید، نه روی delimiters. کدِ مینی-ردیس، برای آموزش، پارس دستی را نشان می‌دهد؛ ولی همین crate در production هم می‌تواند استفاده شود.

اگر از LengthDelimitedCodec استفاده کنید، محدودیت طولِ پیش‌فرض ۸ مگابایت مانع از تخصیص‌های بزرگ می‌شود؛ تنظیمِ max_frame_length را هم می‌توانید تغییر دهید.

پس از آشنایی با فریم‌بندی، نوبت آن است که یک سرور کامل با قاب‌بندی و بر اساس کدهای بالا بسازیم؛ ولی قبل از آن، دو فصل دیگر مهم‌اند: «Async in depth» و «select». در فصلِ «Async in depth» دربارهٔ futures و poll صحبت می‌کنیم؛ در فصلِ «select» دربارهٔ مکانیزم انتخاب بین چند عملیات ناهمگام.

بررسی عمیق ناهمگام‌ها (Async in depth)

↗ مشاهده بخش اصلی در tokio.rs

در این فصل، جزئیات داخلی async/await در راستا (Rust) را بررسی می‌کنیم. به‌جای صرفاً اینکه به شما بگوییم «از tokio::spawn استفاده کنید»، خواهیم دید که پشت پردهٔ آن چه می‌گذرد.

Futures

یک Future یک محاسبهٔ ناهمگام است. در راست، یک Future با trait Future نشان داده می‌شود:

rustuse std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

متد poll وظیفهٔ پیش‌بردن future را بر عهده دارد. اگر future به‌پایان برسد، Poll::Ready را با مقدارِ خروجی برمی‌گرداند. در غیر این صورت، Poll::Pending را برمی‌گرداند و یک «waker» را در Context ثبت می‌کند؛ وقتی future آمادهٔ پیشرفت بیشتر شد، اجراکننده (executor) باید poll را دوباره صدا بزند.

وقتی یک Future به‌صورت Poll::Pending برمی‌گردد، به این معنی است که آماده نیست؛ کار ممکن است در حال انجام باشد، یا در حال انتظار برای رویدادی خارجی. در هر صورت، اجراکننده باید آن را دوباره poll کند وقتی چیزی تغییر می‌کند، که از طریق waker مشخص می‌شود.

my_async_fn

تابع‌های async fn را در نظر بگیرید:

rustasync fn my_async_fn() -> i32 {
    println!("hello from async");
    42
}

این تابع چیزی اجرا نمی‌کند؛ در عوض یک future برمی‌گرداند که وقتی poll شود، بدنه‌اش اجرا می‌شود:

rust#[tokio::main]
async fn main() {
    let future = my_async_fn();

    println!("function returned");

    let result = future.await;
    println!("result: {}", result);
}

خروجی این برنامه این است:

textfunction returned
hello from async
result: 42

Lazy futures

در بالا دیدیم که صدازدنِ یک async fn، بدنه‌اش را اجرا نمی‌کند. این فوتورها «تنبل» (lazy) هستند. به همین دلیل، .await در واقع جایی است که poll رخ می‌دهد.

در راست، یک async fn چیزی نیست جز یک fn که یک نوع Future پنهان برمی‌گرداند. کامپایلر، بدنه را به یک state machine تبدیل می‌کند که بین pollها، state را حفظ می‌کند. به همین دلیل، وقتی .await می‌شوید، کنترل به اجراکننده برمی‌گردد و اجراکننده می‌تواند pollهای بعدی را انجام دهد؛ در واقع poll برمی‌گردد و اجرای آن از همان جا ادامه پیدا می‌کند که Pending شده بود.

Mini-Tokio

برای درک اینکه اجراکننده (executor) چگونه با futures کار می‌کند، یک «مینی-توکیو» می‌سازیم — نسخه‌ای ساده‌شده که فقط pollهای زمان‌بندی‌شده انجام می‌دهد.

ایدهٔ اصلی: آینده‌ها poll می‌شوند؛ وقتی Pending برمی‌گردانند، کنار گذاشته می‌شوند تا دوباره poll شوند.

rustuse tokio::sync::mpsc;
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct MiniTokio {
    scheduled: mpsc::Receiver<Task>,
    sender: mpsc::Sender<Task>,
}

impl MiniTokio {
    fn new() -> MiniTokio {
        let (sender, scheduled) = mpsc::channel(128);
        MiniTokio { scheduled, sender }
    }

    /// future داده‌شده را ریخته و زمان‌بندی می‌کند
    /// تا poll شود
    fn spawn<F>(&mut self, future: F)
    where
        F: Future<Output = ()> + Send + 'static,
    {
        let task = async_task::spawn(future, self.sender.clone());
        let _ = self.sender.send(task);
    }

    async fn run(&mut self) {
        while let Some(task) = self.scheduled.recv().await {
            // فرایند poll، future را اجرا می‌کند
            task.poll();
        }
    }
}

crate async-task یک Task را فراهم می‌کند که future را با poll رانده و waker را مدیریت می‌کند. run() تسک‌ها را از صف می‌گیرد و poll() را صدا می‌زند.

حالا ببینیم این به‌عنوان یک اجراکنندهٔ کامل چه چیزی کم دارد:

  • پس از poll که Pending برمی‌گرداند، task باید دوباره زمان‌بندی شود — ولی این بار فقط وقتی waker بیدارش کند.
  • waker از کجا می‌آید؟ از Context که poll می‌گیرد؛ در پیاده‌سازی‌های واقعی، waker معمولاً به صفِ زمان‌بند اشاره می‌کند.

Async readiness (و wakerها)

در برنامه‌های واقعی، poll‌های مکرر بی‌فایده‌اند. اگر یک future منتظر دریافت بایت از یک سوکت است و هنوز بایتی نرسیده، poll کردن مکررش منابع را تلف می‌کند. به همین دلیل، Future باید وضعیت آمادگی را به بیرون خبر دهد.

مکانیزم آماده‌بودن در توکیو روی دو جزء اصلی ساخته شده است: poll و waker. قرارداد این است: poll بررسی می‌کند که future آماده است یا نه؛ اگر آماده نیست، Pending برمی‌گرداند و یک waker ثبت می‌کند. بعداً، وقتی منبع آماده شد (مثلاً دادهٔ جدید رسید)، waker فراخوانی می‌شود و اجراکننده، future را دوباره poll می‌کند.

در توکیو، رابط میان زمان‌بند و منابع ورودی/خروجی، یک درایور I/O است که رویدادها را به wakerها ترجمه می‌کند. این مکانیزم همان چیزی است که به برنامه‌های async اجازه می‌دهد با تعداد زیادی اتصال هم‌زمان کار کنند، بدون نیاز به یک نخ برای هر اتصال.

تمرین: تایمرها (Timers)

برای درک بهتر، یک تایمرِ ساده می‌سازیم. تایمر یک future است که بعد از مدت زمان معین، Ready می‌شود. اگرچه توکیو tokio::time::sleep را دارد، اما ببینیم چگونه یک نسخهٔ ساده را خودمان پیاده کنیم.

روش: یک تسک که می‌خوابد و بعد پیامی را روی یک کانال oneshot می‌فرستد؛ Timer::wait منتظر آن پیام می‌ماند.

rustuse tokio::sync::oneshot;
use std::time::Duration;

struct Timer {
    rx: oneshot::Receiver<()>,
}

impl Timer {
    /// یک تسک می‌ریزد که بعد از مدتِ خواسته‌شده بیدار می‌شود
    fn new(duration: Duration) -> Timer {
        let (tx, rx) = oneshot::channel();

        tokio::spawn(async move {
            tokio::time::sleep(duration).await;
            let _ = tx.send(());
        });

        Timer { rx }
    }

    /// منتظر می‌ماند تا زمان سپری شود
    async fn wait(self) {
        let _ = self.rx.await;
    }
}

این نسخه با «یک تسک + یک کانال» ساخته شده. نسخهٔ پیچیده‌تر و واقعی‌تر — که waker را به‌طور مستقیم مدیریت می‌کند — در راهنمای توکیو وجود دارد، اما همین پیاده‌سازی برای درک ایده کافی است: future منتظر یک رویداد (پایانِ sleep) است و تا آماده‌شدن، Pending است.

ارسال به بین نخ‌ها (The Send bound)

یک تابع async fn که .await می‌شود، ممکن است به یک نخِ دیگر فرستاده شود. به همین دلیل، tokio::spawn به Future + Send + 'static نیاز دارد:

rusttokio::spawn(async move {
    // ...
});

bound Send می‌گوید future باید برای فرستادن به نخِ دیگر امن باشد. بیشتر عملیات‌های I/O توکیو این‌گونه هستند؛ اما برخی مقادیر Send نیستند. مثال معروف، std::rc::Rc است:

rustuse std::rc::Rc;

async fn my_async_fn() {
    let rc = Rc::new(123);

    // کامپایل نمی‌شود! `Rc` ارسال‌شدنی نیست
    tokio::spawn(async move {
        println!("{:?}", rc);
    });
}

Polling و Context

اجراکننده باید future را poll کند. برای این کار از Context استفاده می‌شود که waker را حمل می‌کند:

rustuse std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll, Wake};

fn poll<T>(fut: &mut Pin<&mut impl Future<Output = T>>) -> Poll<T> {
    // در عمل، waker از یک Arc<impl Wake> ساخته می‌شود
    let waker = ...;
    let mut cx = Context::from_waker(&waker);
    fut.as_mut().poll(&mut cx)
}

نکتهٔ کلیدی: وقتی یک future Pending برمی‌گرداند، این وعده را می‌دهد که waker را ثبت کرده است؛ و وقتی آن waker صدا زده می‌شود، اجراکننده باید دوباره poll کند. این قرارداد — poll + wake — هستهٔ تمام اجراکننده‌های راست است.

نکته: اگر یک future را poll کنید و Pending برگردد ولی waker را ثبت نکند، اجراکننده هرگز دوباره آن را poll نمی‌کند و برنامه معلق می‌ماند. به همین دلیل، پیاده‌سازی‌های درست همیشه قبل از برگرداندن Pending، یک waker ثبت می‌کنند.

اگر می‌خواهید با پیاده‌سازی کامل‌تر یک اجراکنندهٔ کوچک آشنا شوید، نسخهٔ انگلیسی همین فصل بخش «Implementing the poll function» را دارد که با Waker، Poll::ready و موارد دیگر سروکار دارد. فصل بعدی آموزش، یعنی «Select»، از همین دانش برای انتخاب بین چند future استفاده می‌کند.

انتخاب (Select)

↗ مشاهده بخش اصلی در tokio.rs

تا این‌جا، وقتی می‌خواستیم به سیستم هم‌روندی اضافه کنیم، یک تسک جدید ریخته‌ایم. حالا چند روش دیگر برای اجرای هم‌زمانِ کد ناهمگام با توکیو را پوشش می‌دهیم.

tokio::select!

ماکروی tokio::select! به شما اجازه می‌دهد منتظر چند محاسبهٔ ناهمگام بمانید و وقتی یک محاسبه کامل شد، برگردد.

برای مثال:

rustuse tokio::sync::oneshot;

#[tokio::main]
async fn main() {
    let (tx1, rx1) = oneshot::channel();
    let (tx2, rx2) = oneshot::channel();

    tokio::spawn(async {
        let _ = tx1.send("one");
    });

    tokio::spawn(async {
        let _ = tx2.send("two");
    });

    tokio::select! {
        val = rx1 => {
            println!("rx1 completed first with {:?}", val);
        }
        val = rx2 => {
            println!("rx2 completed first with {:?}", val);
        }
    }
}

از دو کانال oneshot استفاده شده است. هرکدام از کانال‌ها می‌توانند اول کامل شوند. عبارت select! روی هر دو کانال انتظار می‌کشد و val را به مقداری که تسک برمی‌گرداند بایند (bind) می‌کند. وقتی tx1 یا tx2 کامل شود، بلوکِ مرتبط اجرا می‌شود.

شاخه‌ای که کامل نمی‌شود drop می‌شود. در مثال بالا، محاسبات روی oneshot::Receiver هر کانال منتظر می‌مانند. oneshot::Receiver مربوط به کانالی که هنوز کامل نشده drop می‌شود.

لغوکردن (Cancellation)

در راستِ ناهمگام، لغوکردن با drop کردن یک future انجام می‌شود. از فصل «بررسی عمیق ناهمگام‌ها» به یاد بیاورید: عملیات‌های ناهمگام راست با futureها پیاده‌سازی می‌شوند و futureها تنبل هستند. عملیات فقط وقتی future poll شود پیش می‌رود. اگر future drop شود، عملیات نمی‌تواند ادامه یابد، چون همهٔ state مربوطه drop شده است.

با این حال، گاهی یک عملیات ناهمگام تسک‌های پس‌زمینه می‌ریزد یا عملیاتِ دیگری را شروع می‌کند که در پس‌زمینه اجرا می‌شود. مثلاً در مثال بالا تسکی ریخته می‌شود که پیام را ارسال کند. معمولاً تسک‌ها محاسباتی انجام می‌دهند تا مقدار را تولید کنند.

Futureها یا انواعِ دیگر می‌توانند Drop را پیاده‌سازی کنند تا منابع پس‌زمینه را تمیز کنند. oneshot::Receiver توکیو Drop را با فرستادن یک اعلانِ بسته‌شدن به نیمهٔ Sender پیاده‌سازی می‌کند. نیمهٔ فرستنده می‌تواند این اعلان را دریافت کند و با drop کردنش، عملیاتِ در حال انجام را لغو کند:

rustuse tokio::sync::oneshot;

async fn some_operation() -> String {
    // مقدار را این‌جا محاسبه کن
}

#[tokio::main]
async fn main() {
    let (mut tx1, rx1) = oneshot::channel();
    let (tx2, rx2) = oneshot::channel();

    tokio::spawn(async {
        // بین عملیات و اعلانِ `closed()` کانال oneshot انتخاب کن
        tokio::select! {
            val = some_operation() => {
                let _ = tx1.send(val);
            }
            _ = tx1.closed() => {
                // `some_operation()` لغو می‌شود،
                // تسک کامل می‌شود و `tx1` drop می‌شود.
            }
        }
    });

    tokio::spawn(async {
        let _ = tx2.send("two");
    });

    tokio::select! {
        val = rx1 => {
            println!("rx1 completed first with {:?}", val);
        }
        val = rx2 => {
            println!("rx2 completed first with {:?}", val);
        }
    }
}

پیاده‌سازیِ Future

برای درک بهترِ سازوکار select!، ببینیم یک پیاده‌سازیِ فرضیِ Future چه شکلی خواهد بود. این یک نسخهٔ ساده‌شده است؛ در عمل، select! قابلیت‌های بیشتری دارد، مثل انتخاب تصادفیِ شاخه‌ای که اول poll شود.

rustuse tokio::sync::oneshot;
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct MySelect {
    rx1: oneshot::Receiver<&'static str>,
    rx2: oneshot::Receiver<&'static str>,
}

impl Future for MySelect {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if let Poll::Ready(val) = Pin::new(&mut self.rx1).poll(cx) {
            println!("rx1 completed first with {:?}", val);
            return Poll::Ready(());
        }

        if let Poll::Ready(val) = Pin::new(&mut self.rx2).poll(cx) {
            println!("rx2 completed first with {:?}", val);
            return Poll::Ready(());
        }

        Poll::Pending
    }
}

#[tokio::main]
async fn main() {
    let (tx1, rx1) = oneshot::channel();
    let (tx2, rx2) = oneshot::channel();

    // از tx1 و tx2 استفاده کن

    MySelect {
        rx1,
        rx2,
    }.await;
}

futureِ MySelect شامل futureهای هر شاخه است. وقتی MySelect poll می‌شود، اول شاخهٔ اول poll می‌شود. اگر آماده باشد، مقدار استفاده می‌شود و MySelect کامل می‌شود. بعد از اینکه .await خروجیِ یک future را دریافت کرد، future drop می‌شود. این باعث می‌شود futureهای هر دو شاخه drop شوند. چون یکی از شاخه‌ها کامل نشده بود، عملیات عملاً لغو می‌شود.

از بخش قبل به یاد بیاورید:

وقتی future مقدار Poll::Pending برمی‌گرداند، باید مطمئن شود waker در آینده سیگنال می‌شود. فراموش کردن این کار باعث می‌شود تسک بی‌نهایت معلق بماند.

در پیاده‌سازیِ MySelect استفادهٔ صریحی از آرگومان Context نیست. در عوض، نیازِ waker با پاس‌دادن cx به futureهای داخلی برآورده می‌شود. چون future داخلی هم باید نیازِ waker را برآورده کند، با برگرداندن Poll::Pending فقط وقتی از future داخلی Poll::Pending دریافت شود، MySelect هم نیازِ waker را برآورده می‌کند.

دستور زبان (Syntax)

ماکروی select! می‌تواند بیش از دو شاخه داشته باشد. محدودیت فعلی ۶۴ شاخه است. هر شاخه این‌گونه ساختار می‌گیرد:

text<pattern> = <async expression> => <handler>,

وقتی ماکروی select ارزیابی می‌شود، همهٔ عبارت‌های ناهمگام جمع و به‌صورت هم‌زمان اجرا می‌شوند. وقتی یک عبارت کامل شود، نتیجه با <pattern> مطابقت داده می‌شود. اگر نتیجه با الگو مطابقت داشت، همهٔ عبارت‌های ناهمگامِ باقی‌مانده drop می‌شوند و <handler> اجرا می‌شود. عبارتِ <handler> به هر binding که <pattern> ایجاد کرده دسترسی دارد.

حالت پایهٔ <pattern> یک نام متغیر است؛ نتیجهٔ عبارت ناهمگام به آن بایند می‌شود و <handler> به آن متغیر دسترسی دارد. به همین دلیل است که در مثال اول، val به‌عنوان الگو استفاده شده و handler به val دسترسی داشت.

اگر <pattern> با نتیجه‌ی محاسبهٔ ناهمگام مطابقت نداشته باشد، عبارت‌های ناهمگامِ باقی‌مانده به‌صورت هم‌زمان به اجرا ادامه می‌دهند تا مورد بعدی کامل شود. در آن زمان، همان منطق روی آن نتیجه اعمال می‌شود.

چون select! هر عبارت ناهمگامی می‌پذیرد، می‌توان محاسبات پیچیده‌تری برای انتخاب تعریف کرد. در این‌جا روی خروجی یک کانال oneshot و یک اتصال TCP انتخاب می‌کنیم:

rustuse tokio::net::TcpStream;
use tokio::sync::oneshot;

#[tokio::main]
async fn main() {
    let (tx, rx) = oneshot::channel();

    // تسکی می‌ریزیم که پیامی روی oneshot بفرستد
    tokio::spawn(async move {
        tx.send("done").unwrap();
    });

    tokio::select! {
        socket = TcpStream::connect("localhost:3465") => {
            println!("Socket connected {:?}", socket);
        }
        msg = rx => {
            println!("received message first {:?}", msg);
        }
    }
}

و در این‌جا، روی oneshot و پذیرفتن سوکت از یک TcpListener انتخاب می‌کنیم:

rustuse tokio::net::TcpListener;
use tokio::sync::oneshot;
use std::io;

#[tokio::main]
async fn main() -> io::Result<()> {
    let (tx, rx) = oneshot::channel();

    tokio::spawn(async move {
        tx.send(()).unwrap();
    });

    let mut listener = TcpListener::bind("localhost:3465").await?;

    tokio::select! {
        _ = async {
            loop {
                let (socket, _) = listener.accept().await?;
                tokio::spawn(async move { process(socket) });
            }

            // به کامپایلر در استنتاج نوع کمک کن
            Ok::<_, io::Error>(())
        } => {}
        _ = rx => {
            println!("terminating accept loop");
        }
    }

    Ok(())
}

حلقهٔ پذیرش تا وقتی اجرا می‌شود که خطایی رخ دهد یا rx مقداری دریافت کند. الگوی _ نشان می‌دهد به مقدار بازگشتیِ محاسبهٔ ناهمگام علاقه‌ای نداریم.

مقدار بازگشتی (Return value)

ماکروی tokio::select! نتیجهٔ عبارتِ <handler> ارزیابی‌شده را برمی‌گرداند.

rustasync fn computation1() -> String {
    // .. محاسبه
}

async fn computation2() -> String {
    // .. محاسبه
}

#[tokio::main]
async fn main() {
    let out = tokio::select! {
        res1 = computation1() => res1,
        res2 = computation2() => res2,
    };

    println!("Got = {}", out);
}

به همین دلیل، لازم است عبارتِ <handler> برای هر شاخه به یک نوعِ یکسان ارزیابی شود. اگر به خروجیِ یک عبارت select! نیاز نیست، بهتر است عبارت به () ارزیابی شود.

خطاها (Errors)

استفاده از عملگر ? خطا را از عبارت «انتشار» می‌دهد. اینکه چطور کار می‌کند بستگی به این دارد که ? از یک عبارت ناهمگام استفاده شود یا از یک handler. استفادهٔ ? در یک عبارت ناهمگام، خطا را به بیرون از عبارت ناهمگام انتشار می‌دهد. این کار خروجیِ عبارت ناهمگام را به یک Result تبدیل می‌کند. استفاده از ? از یک handler بلافاصله خطا را به بیرون از عبارت select! انتشار می‌دهد. به مثالِ حلقهٔ پذیرش دوباره نگاه کنیم:

rustuse tokio::net::TcpListener;
use tokio::sync::oneshot;
use std::io;

#[tokio::main]
async fn main() -> io::Result<()> {
    // [راه‌اندازی کانال oneshot `rx`]

    let listener = TcpListener::bind("localhost:3465").await?;

    tokio::select! {
        res = async {
            loop {
                let (socket, _) = listener.accept().await?;
                tokio::spawn(async move { process(socket) });
            }

            // به کامپایلر در استنتاج نوع کمک کن
            Ok::<_, io::Error>(())
        } => {
            res?;
        }
        _ = rx => {
            println!("terminating accept loop");
        }
    }

    Ok(())
}

توجه کنید listener.accept().await?. عملگر ? خطا را از آن عبارت به بیرون و به bindingِ res انتشار می‌دهد. در صورت خطا، res برابر Err(_) خواهد بود. سپس در handler، دوباره از عملگر ? استفاده می‌شود. عبارتِ res? یک خطا را به بیرون از تابع main انتشار می‌دهد.

مطابقت الگو (Pattern matching)

یادتان باشد دستور زبان شاخه‌های ماکروی select! این‌گونه بود:

text<pattern> = <async expression> => <handler>,

تا این‌جا فقط از binding متغیر برای <pattern> استفاده کرده‌ایم. اما هر الگوی راست قابل استفاده است. مثلاً فرض کنید از چند کانال mpsc دریافت می‌کنیم، شاید بخواهیم این‌گونه عمل کنیم:

rustuse tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (mut tx1, mut rx1) = mpsc::channel(128);
    let (mut tx2, mut rx2) = mpsc::channel(128);

    tokio::spawn(async move {
        // کاری با `tx1` و `tx2` انجام بده
    });

    tokio::select! {
        Some(v) = rx1.recv() => {
            println!("Got {:?} from rx1", v);
        }
        Some(v) = rx2.recv() => {
            println!("Got {:?} from rx2", v);
        }
        else => {
            println!("Both channels closed");
        }
    }
}

در این مثال، عبارت select! منتظر دریافت مقدار از rx1 و rx2 می‌ماند. اگر کانالی بسته شود، recv() مقدار None برمی‌گرداند. این با الگو مطابقت ندارد و شاخه غیرفعال می‌شود. عبارت select! به انتظار روی شاخه‌های باقی‌مانده ادامه می‌دهد.

توجه کنید این عبارت select! یک شاخهٔ else دارد. عبارت select! باید به یک مقدار ارزیابی شود. هنگام استفاده از مطابقت الگو ممکن است هیچ‌کدام از شاخه‌ها با الگوی مرتبط‌شان مطابقت نکند. اگر این اتفاق بیفتد، شاخهٔ else ارزیابی می‌شود.

قرض‌گرفتن (Borrowing)

هنگام ریختن تسک، عبارت ناهمگامِ ریخته‌شده باید همهٔ داده‌هایش را مالک باشد. ماکروی select! این محدودیت را ندارد. هر شاخه می‌تواند داده‌ها را قرض بگیرد و هم‌زمان کار کند. طبق قوانین قرض‌گرفتنِ راست، چند عبارت ناهمگام می‌توانند یک تکه داده را نمی‌توانند به‌صورت متغیر (mutable) قرض بگیرند، یا اینکه یک عبارت ناهمگام می‌تواند داده را به‌صورت متغیر قرض بگیرد.

در مثال زیر، هم‌زمان دادهٔ یکسان را به دو مقصد TCP متفاوت می‌فرستیم:

rustuse tokio::io::AsyncWriteExt;
use tokio::net::TcpStream;
use std::io;
use std::net::SocketAddr;

async fn race(
    data: &[u8],
    addr1: SocketAddr,
    addr2: SocketAddr
) -> io::Result<()> {
    tokio::select! {
        Ok(_) = async {
            let mut socket = TcpStream::connect(addr1).await?;
            socket.write_all(data).await?;
            Ok::<_, io::Error>(())
        } => {}
        Ok(_) = async {
            let mut socket = TcpStream::connect(addr2).await?;
            socket.write_all(data).await?;
            Ok::<_, io::Error>(())
        } => {}
        else => {}
    };

    Ok(())
}

متغیر data از هر دو عبارت ناهمگام به‌صورت غیرمتغیر (immutable) قرض گرفته می‌شود. وقتی یکی از عملیات‌ها با موفقیت تمام شود، دیگری drop می‌شود. چون روی Ok(_) مطابقت الگو انجام می‌دهیم، اگر یک عبارت شکست بخورد، دیگری به اجرا ادامه می‌دهد.

وقتی صحبت از <handler> هر شاخه است، select! تضمین می‌کند فقط یک <handler> اجرا می‌شود. به همین دلیل، هر <handler> می‌تواند همان داده را به‌صورت متغیر قرض بگیرد.

مثلاً این‌جا out در هر دو handler تغییر می‌کند:

rustuse tokio::sync::oneshot;

#[tokio::main]
async fn main() {
    let (tx1, rx1) = oneshot::channel();
    let (tx2, rx2) = oneshot::channel();

    let mut out = String::new();

    tokio::spawn(async move {
        // مقادیری روی `tx1` و `tx2` بفرست
    });

    tokio::select! {
        _ = rx1 => {
            out.push_str("rx1 completed");
        }
        _ = rx2 => {
            out.push_str("rx2 completed");
        }
    }

    println!("{}", out);
}

حلقه‌ها (Loops)

ماکروی select! اغلب در حلقه‌ها استفاده می‌شود. با مثالی دربارهٔ انتخاب روی چند کانال شروع می‌کنیم:

rustuse tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx1, mut rx1) = mpsc::channel(128);
    let (tx2, mut rx2) = mpsc::channel(128);
    let (tx3, mut rx3) = mpsc::channel(128);

    loop {
        let msg = tokio::select! {
            Some(msg) = rx1.recv() => msg,
            Some(msg) = rx2.recv() => msg,
            Some(msg) = rx3.recv() => msg,
            else => { break }
        };

        println!("Got {:?}", msg);
    }

    println!("All channels have been closed.");
}

این مثال روی سه گیرندهٔ کانال انتخاب می‌کند. وقتی در هر کانالی پیامی دریافت شود، به STDOUT نوشته می‌شود. وقتی کانالی بسته شود، recv() با None برمی‌گردد. با استفاده از مطابقت الگو، ماکروی select! به انتظار روی کانال‌های باقی‌مانده ادامه می‌دهد. وقتی همهٔ کانال‌ها بسته شوند، شاخهٔ else ارزیابی می‌شود و حلقه خاتمه می‌یابد.

ماکروی select! شاخه‌ها را برای آمادگی به‌صورت تصادفی انتخاب می‌کند. وقتی چند کانال مقدارِ در انتظار دارند، یک کانال تصادفی برای دریافت انتخاب می‌شود. این کار برای رسیدگی به حالتی است که حلقهٔ دریافت پیام‌ها را کندتر از آنچه به کانال‌ها push می‌شوند پردازش کند؛ یعنی کانال‌ها شروع به پر شدن می‌کنند. اگر select! به‌صورت تصادفی شاخه‌ای را برای بررسی اول انتخاب نمی‌کرد، در هر تکرار حلقه، اول rx1 بررسی می‌شد. اگر rx1 همیشه پیامِ جدید داشت، کانال‌های باقی‌مانده هرگز بررسی نمی‌شدند.

وقتی select! ارزیابی می‌شود و چند کانال پیامِ در انتظار دارند، فقط از یک کانال مقدارِ pop می‌شود. همهٔ کانال‌های دیگر دست‌نخورده می‌مانند و پیام‌هایشان تا تکرار بعدی حلقه در همان کانال‌ها می‌مانند. هیچ پیامی از دست نمی‌رود.

ادامه‌دادن یک عملیات ناهمگام (Resuming an async operation)

حالا نشان می‌دهیم چگونه یک عملیات ناهمگام را در چند فراخوانیِ select! اجرا کنیم. در این مثال، یک کانال mpsc با نوع آیتمِ i32 و یک تابع ناهمگام داریم. می‌خواهیم تابع ناهمگام را اجرا کنیم تا کامل شود یا یک عدد زوج روی کانال دریافت شود.

rustasync fn action() {
    // یک منطق ناهمگام
}

#[tokio::main]
async fn main() {
    let (mut tx, mut rx) = tokio::sync::mpsc::channel(128);

    let operation = action();
    tokio::pin!(operation);

    loop {
        tokio::select! {
            _ = &mut operation => break,
            Some(v) = rx.recv() => {
                if v % 2 == 0 {
                    break;
                }
            }
        }
    }
}

توجه کنید به‌جای صدازدنِ action() در ماکروی select!، خارج از حلقه صدا زده می‌شود. مقدارِ بازگشتیِ action() به operation اختصاص داده می‌شود بدون اینکه .await شود. سپس روی operation تابع tokio::pin! را صدا می‌زنیم.

داخل حلقهٔ select!، به‌جای پاس‌دادن operation، &mut operation را پاس می‌دهیم. متغیر operation در حال ردیابی عملیات ناهمگامِ در حال اجراست. هر تکرار حلقه از همان عملیات استفاده می‌کند به‌جای اینکه فراخوانی جدیدی به action() صادر کند.

این نخستین بار است که از tokio::pin! استفاده می‌کنیم. جزئیات pinning را بررسی نمی‌کنیم. فقط توجه کنید که برای .await کردن یک مرجع، مقدارِ مرجع‌شده باید pin شده باشد یا Unpin را پیاده‌سازی کند.

تغییر یک شاخه (Modifying a branch)

به یک حلقهٔ کمی پیچیده‌تر نگاه کنیم. این‌ها را داریم:

  1. یک کانال از مقادیرِ i32.
  2. یک عملیات ناهمگام برای اجرا روی مقادیرِ i32.

منطقی که می‌خواهیم پیاده کنیم:

  1. منتظر یک عدد زوج روی کانال بمان.
  2. عملیات ناهمگام را با استفاده از عدد زوج به‌عنوان ورودی شروع کن.
  3. منتظر عملیات بمان؛ در عین حال به اعداد زوجِ بیشتر روی کانال گوش بده.
  4. اگر قبل از کامل‌شدنِ عملیاتِ موجود، عدد زوجِ جدیدی دریافت شد، عملیاتِ موجود را لغو کن و با عدد زوجِ جدید دوباره شروعش کن.
rustasync fn action(input: Option<i32>) -> Option<String> {
    // اگر ورودی `None` است، `None` را برگردان.
    // این را می‌توان با `let i = input?;` هم نوشت
    let i = match input {
        Some(input) => input,
        None => return None,
    };
    // منطق ناهمگام این‌جا
}

#[tokio::main]
async fn main() {
    let (mut tx, mut rx) = tokio::sync::mpsc::channel(128);

    let mut done = false;
    let operation = action(None);
    tokio::pin!(operation);

    tokio::spawn(async move {
        let _ = tx.send(1).await;
        let _ = tx.send(3).await;
        let _ = tx.send(2).await;
    });

    loop {
        tokio::select! {
            res = &mut operation, if !done => {
                done = true;

                if let Some(v) = res {
                    println!("GOT = {}", v);
                    return;
                }
            }
            Some(v) = rx.recv() => {
                if v % 2 == 0 {
                    // `.set` یک متد روی `Pin` است.
                    operation.set(action(Some(v)));
                    done = false;
                }
            }
        }
    }
}

از راهبردی مشابه مثال قبل استفاده می‌کنیم. تابع async خارج از حلقه صدا زده می‌شود و به operation اختصاص داده می‌شود. متغیر operation pin می‌شود. حلقه هم روی operation و هم روی گیرندهٔ کانال انتخاب می‌کند.

توجه کنید action یک Option<i32> به‌عنوان آرگومان می‌گیرد. قبل از دریافتِ اولین عدد زوج، باید operation را با چیزی مقداردهی کنیم. action را طوری می‌سازیم که Option بگیرد و Option برگرداند. اگر None پاس داده شود، None برمی‌گردد. در اولین تکرار حلقه، operation بلافاصله با None کامل می‌شود.

این مثال از برخی دستور زبان‌های جدید استفاده می‌کند. اولین شاخه , if !done را دارد. این یک پیش‌شرطِ شاخه (branch precondition) است. قبل از توضیح نحوهٔ کار، ببینیم اگر پیش‌شرط حذف شود چه می‌شود. حذفِ , if !done و اجرای مثال نتیجهٔ زیر را دارد:

textthread 'main' panicked at '`async fn` resumed after completion', src/main.rs:1:55
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

این خطا وقتی رخ می‌دهد که تلاش کنید بعد از کامل‌شدن از operation دوباره استفاده کنید. معمولاً هنگام استفاده از .await، مقدارِ await شده مصرف می‌شود. در این مثال، روی یک مرجع await می‌کنیم؛ یعنی operation بعد از کامل‌شدن هنوز وجود دارد.

برای اجتناب از این panic، باید مراقب باشیم اگر operation کامل شده، شاخهٔ اول را غیرفعال کنیم. متغیر done برای ردیابی اینکه آیا operation کامل شده یا نه استفاده می‌شود. یک شاخهٔ select! می‌تواند یک پیش‌شرط داشته باشد. این پیش‌شرط قبل از اینکه select! روی شاخه await کند بررسی می‌شود. اگر شرط false ارزیابی شود، شاخه غیرفعال می‌شود. متغیر done با false مقداردهی می‌شود. وقتی operation کامل شود، done روی true تنظیم می‌شود. تکرار بعدی حلقه، شاخهٔ operation را غیرفعال می‌کند. وقتی پیامِ زوجی از کانال دریافت شود، operation بازنشانی می‌شود و done روی false تنظیم می‌شود.

هم‌روندیِ درون تسک (Per-task concurrency)

هم tokio::spawn و هم select! اجرای هم‌زمانِ عملیات‌های ناهمگام را ممکن می‌کنند. اما راهبردِ مورد استفاده برای اجرای عملیات‌های هم‌زمان متفاوت است. تابع tokio::spawn یک عملیات ناهمگام می‌گیرد و یک تسکِ جدید برای اجرای آن می‌ریزد. یک تسک، شیءی است که رانتایم توکیو زمان‌بندی می‌کند. دو تسکِ مختلف به‌صورت مستقل توسط توکیو زمان‌بندی می‌شوند. ممکن است هم‌زمان روی نخ‌های سیستم‌عاملِ متفاوتی اجرا شوند. به همین دلیل، یک تسکِ ریخته‌شده همان محدودیتِ نخِ ریخته‌شده را دارد: بدون قرض‌گرفتن.

ماکروی select! همهٔ شاخه‌ها را هم‌زمان روی همان تسک اجرا می‌کند. چون همهٔ شاخه‌های ماکروی select! روی همان تسک اجرا می‌شوند، هرگز به‌صورت هم‌زمان اجرا نمی‌شوند. ماکروی select! عملیات‌های ناهمگام را روی یک تسکِ واحد مالتی‌پلکس می‌کند.

در فصل بعد — «Streams» — همین تکنیک‌ها را روی جریان‌های ناهمگام اعمال می‌کنیم.

جریان‌ها (Streams)

↗ مشاهده بخش اصلی در tokio.rs

یک Stream یک سری مقدارِ ناهمگام است. معادل ناهمگامِ std::iter::Iterator راست است و با trait Stream نشان داده می‌شود. جریان‌ها را می‌توان در توابع async پیمایش کرد. همچنین می‌توان با آداپترها (adapter) تبدیلشان کرد. توکیو تعدادی آداپتر رایج روی trait StreamExt فراهم می‌کند.

توکیو پشتیبانیِ stream را در یک crate جداگانه فراهم می‌کند: tokio-stream.

tomltokio-stream = "0.1"
فعلاً ابزارهای Stream توکیو در crate tokio-stream وجود دارند. وقتی trait Stream در کتابخانهٔ استاندارد راست پایدار شود، ابزارهای جریانِ توکیو به crate tokio منتقل می‌شوند.

پیمایش (Iteration)

در حال حاضر، زبان برنامه‌نویسی راست از حلقه‌های for ناهمگام پشتیبانی نمی‌کند. به‌جای آن، پیمایش جریان‌ها با حلقهٔ while let همراه با StreamExt::next() انجام می‌شود:

rustuse tokio_stream::StreamExt;

#[tokio::main]
async fn main() {
    let mut stream = tokio_stream::iter(&[1, 2, 3]);

    while let Some(v) = stream.next().await {
        println!("GOT = {:?}", v);
    }
}

مثل iteratorها، متد next() یک Option<T> برمی‌گرداند که T نوعِ مقدارِ جریان است. دریافت None نشان می‌دهد پیمایشِ جریان خاتمه یافته است.

پخش مینی-ردیس (Mini-Redis broadcast)

یک مثال کمی پیچیده‌تر با استفاده از کلاینت مینی-ردیس را بررسی کنیم. کد کامل را می‌توانید اینجا ببینید.

rustuse tokio_stream::StreamExt;
use mini_redis::client;

async fn publish() -> mini_redis::Result<()> {
    let mut client = client::connect("127.0.0.1:6379").await?;

    // داده را publish کن
    client.publish("numbers", "1".into()).await?;
    client.publish("numbers", "two".into()).await?;
    client.publish("numbers", "3".into()).await?;
    client.publish("numbers", "four".into()).await?;
    client.publish("numbers", "five".into()).await?;
    client.publish("numbers", "6".into()).await?;
    Ok(())
}

async fn subscribe() -> mini_redis::Result<()> {
    let client = client::connect("127.0.0.1:6379").await?;
    let subscriber = client.subscribe(vec!["numbers".to_string()]).await?;
    let messages = subscriber.into_stream();

    tokio::pin!(messages);

    while let Some(msg) = messages.next().await {
        println!("got = {:?}", msg);
    }

    Ok(())
}

#[tokio::main]
async fn main() -> mini_redis::Result<()> {
    tokio::spawn(async {
        publish().await
    });

    subscribe().await?;

    println!("DONE");

    Ok(())
}

یک تسک برای publish کردن پیام‌ها به سرور مینی-ردیس روی کانال «numbers» ریخته می‌شود. سپس روی تسک اصلی، مشترک کانال «numbers» می‌شویم و پیام‌های دریافتی را نمایش می‌دهیم.

بعد از اشتراک، into_stream() روی subscriberِ بازگشتی صدا زده می‌شود. این کار Subscriber را مصرف می‌کند و یک جریان برمی‌گرداند که با رسیدن پیام‌ها آنها را تولید می‌کند (yield). قبل از شروع پیمایش پیام‌ها، توجه کنید که جریان با استفاده از tokio::pin! روی پشته pin می‌شود. صدازدنِ next() روی یک جریان نیاز دارد که جریان pin شده باشد. تابع into_stream() یک جریان برمی‌گرداند که pin نشده؛ باید صریحاً آن را pin کنیم تا بتوانیم پیمایشش کنیم.

یک مقدارِ راست «pin» شده یعنی دیگر نمی‌توان در حافظه جابه‌جا شود. یک ویژگیِ کلیدیِ مقدارِ pin‌شده این است که می‌توان به دادهٔ pin‌شده اشاره‌گر گرفت و فراخوان بتواند مطمئن باشد که اشاره‌گر معتبر می‌ماند. از این ویژگی در async/await برای پشتیبانی از قرض‌گرفتن داده در میان نقاطِ .await استفاده می‌شود.

آداپترها (Adapters)

توابعی که یک Stream می‌گیرند و یک Stream دیگر برمی‌گردانند اغلب «آداپتر جریان» نامیده می‌شوند، چون نوعی از «الگوی آداپتر» هستند. آداپترهای رایج جریان شامل map، take و filter هستند.

مینی-ردیس را طوری به‌روزرسانی کنیم که خارج شود. بعد از دریافت سه پیام، پیمایشِ پیام‌ها را متوقف کنید. این کار با take انجام می‌شود. این آداپتر جریان را محدود می‌کند تا حداکثر n پیام تولید کند.

rustlet messages = subscriber
    .into_stream()
    .take(3);

برنامه را دوباره اجرا می‌کنیم، این خروجی را می‌گیریم:

textgot = Ok(Message { channel: "numbers", content: b"1" })
got = Ok(Message { channel: "numbers", content: b"two" })
got = Ok(Message { channel: "numbers", content: b"3" })

این بار برنامه تمام می‌شود.

حالا جریان را به اعداد تک‌رقمی محدود کنیم. این را با بررسیِ طول پیام بررسی می‌کنیم. از آداپتر filter برای حذف هر پیامی که با محمول (predicate) مطابقت ندارد استفاده می‌کنیم.

rustlet messages = subscriber
    .into_stream()
    .filter(|msg| match msg {
        Ok(msg) if msg.content.len() == 1 => true,
        _ => false,
    })
    .take(3);

برنامه را دوباره اجرا می‌کنیم، این خروجی را می‌گیریم:

textgot = Ok(Message { channel: "numbers", content: b"1" })
got = Ok(Message { channel: "numbers", content: b"3" })
got = Ok(Message { channel: "numbers", content: b"6" })

توجه کنید ترتیبی که آداپترها اعمال می‌شوند مهم است. صدازدنِ filter اول و بعد take، متفاوت از صدازدنِ take اول و بعد filter است.

در نهایت، با حذف قسمتِ Ok(Message { ... }) خروجی را مرتب می‌کنیم. این کار با map انجام می‌شود. چون این کار بعد از filter اعمال می‌شود، می‌دانیم پیام Ok است، پس می‌توانیم از unwrap() استفاده کنیم.

rustlet messages = subscriber
    .into_stream()
    .filter(|msg| match msg {
        Ok(msg) if msg.content.len() == 1 => true,
        _ => false,
    })
    .map(|msg| msg.unwrap().content)
    .take(3);

حالا خروجی این است:

textgot = b"1"
got = b"3"
got = b"6"

گزینهٔ دیگر این است که مراحل filter و map را با یک فراخوانیِ واحد با استفاده از filter_map ترکیب کنیم.

آداپترهای بیشتری موجودند. فهرست کامل را اینجا ببینید.

پیاده‌سازیِ Stream

trait Stream بسیار شبیه trait Future است.

rustuse std::pin::Pin;
use std::task::{Context, Poll};

pub trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;

    fn size_hint(&self) -> (usize, Option<usize>) {
        (0, None)
    }
}

تابع Stream::poll_next() خیلی شبیه Future::poll است، با این تفاوت که می‌توان بارها صدا زد تا مقادیر زیادی از جریان دریافت شود. همان‌طور که در «بررسی عمیق ناهمگام‌ها» دیدیم، وقتی جریان آمادهٔ برگرداندن مقدار نیست، به‌جایش Poll::Pending برگردانده می‌شود. wakerِ تسک ثبت می‌شود. وقتی جریان باید دوباره poll شود، waker مطلع می‌شود.

متد size_hint() به همان شکلی که با iteratorها استفاده می‌شود، استفاده می‌شود.

معمولاً وقتی Stream را به‌صورت دستی پیاده‌سازی می‌کنیم، با ترکیبِ futureها و جریان‌های دیگر انجامش می‌دهیم. به‌عنوان مثال، روی futureِ «Delay» که در «بررسی عمیق ناهمگام‌ها» پیاده کردیم کار کنیم. آن را به یک جریان تبدیل می‌کنیم که سه بار با فاصلهٔ ۱۰ میلی‌ثانیه مقدار () تولید می‌کند.

rustuse tokio_stream::Stream;
use std::pin::Pin;
use std::task::{Context, Poll};
use std::time::Duration;

struct Interval {
    rem: usize,
    delay: Delay,
}

impl Interval {
    fn new() -> Self {
        Self {
            rem: 3,
            delay: Delay { when: Instant::now() }
        }
    }
}

impl Stream for Interval {
    type Item = ();

    fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context<'_>)
        -> Poll<Option<()>>
    {
        if self.rem == 0 {
            // تأخیر دیگری باقی نمانده
            return Poll::Ready(None);
        }

        match Pin::new(&mut self.delay).poll(cx) {
            Poll::Ready(_) => {
                let when = self.delay.when + Duration::from_millis(10);
                self.delay = Delay { when };
                self.rem -= 1;
                Poll::Ready(Some(()))
            }
            Poll::Pending => Poll::Pending,
        }
    }
}

async-stream

پیاده‌سازیِ دستیِ جریان‌ها با trait Stream می‌تواند خسته‌کننده باشد. متأسفانه زبان برنامه‌نویسی راست هنوز از دستور زبانِ async/await برای تعریف جریان‌ها پشتیبانی نمی‌کند. این کار در دست انجام است، اما هنوز آماده نیست.

crate async-stream به‌عنوان راه‌حل موقت موجود است. این crate یک ماکروی stream! فراهم می‌کند که ورودی را به یک جریان تبدیل می‌کند. با استفاده از این crate، intervalِ بالا چنین پیاده‌سازی می‌شود:

rustuse async_stream::stream;
use std::time::{Duration, Instant};

stream! {
    let mut when = Instant::now();
    for _ in 0..3 {
        let delay = Delay { when };
        delay.await;
        yield ();
        when += Duration::from_millis(10);
    }
}
نکته: این آخرین فصل آموزش «مینی-ردیس» است. اگر می‌خواهید ادامه دهید، بخش «Topics» در سایت توکیو موضوعات پیشرفته‌تری مانند اتصال کد همگام/ناهمگام، خاموش‌سازیِ نرم (graceful shutdown) و تست واحد را پوشش می‌دهد.
