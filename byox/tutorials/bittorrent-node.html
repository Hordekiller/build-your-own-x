۱. مقدمه

۱.۱ درباره این راهنما

این راهنما یک کلاینت ساده بیت‌تورنت را از صفر در node.js می‌سازد. در پایان این آموزش باید بتوانید با خط فرمان، محتوای مشترک یک فایل تورنت را دانلود کنید.

دو گروه مخاطب را برای این راهنما در نظر داشتم. اول هرکسی که اصول اولیه جاوااسکریپت را یاد گرفته و دنبال یک آموزش سطح متوسط است. دوم توسعه‌دهندگان وب که شاید تسلط خوبی روی جاوااسکریپت دارند اما تجربه کمی در کار با سمت سرور (backend) دارند. این راهنما چیزهایی مثل خواندن/نوشتن روی فایل و سوکت‌های شبکه را پوشش می‌دهد.

تغییرات پروژه را با git ثبت می‌کنم، بنابراین می‌توانید ببینید پروژه قدم‌به‌قدم چگونه تکامل پیدا می‌کند. صفحه گیت‌هاب پروژه را می‌توانید اینجا پیدا کنید. اولین commit فقط یک package.json خالی، فایل .gitignore و یک فایل تورنت نمونه برای کار کردن است. در طول راهنما هم نقاطی را با لینک به commit ها علامت می‌زنم.

۱.۲ نمای کلی بیت‌تورنت

پروتکل بیت‌تورنت دو بخش اصلی دارد:

قدم ۱: باید به چیزی به نام tracker (ردیاب) درخواست بفرستید و ترکر با فهرستی از همتاها (peer) پاسخ می‌دهد. به‌طور دقیق‌تر، به ترکر می‌گویید دنبال کدام فایل‌ها هستید و ترکر آدرس IP کاربرانی را به شما می‌دهد که آن فایل‌ها را از آن‌ها دانلود می‌کنید. درخواست به ترکر، آدرس IP شما را هم به فهرست کاربرانی که می‌توانند آن فایل را به اشتراک بگذارند اضافه می‌کند.

قدم ۲: بعد از اینکه فهرست آدرس همتاها را گرفتید، می‌خواهید مستقیماً به آن‌ها متصل شوید و دانلود را شروع کنید. این کار از طریق تبادل پیام انجام می‌شود که در آن همتاها می‌گویند چه قطعه‌هایی (piece) دارند و شما می‌گویید کدام قطعه‌ها را می‌خواهید.

۳. گرفتن همتاها از ترکر

در کد بالا خاصیت announce تورنت را با console.log چاپ کردم. برای این فایل خاص مقدار آن udp://tracker.coppersurfer.tk:6969/announce است. آدرس announce همان چیزی است که من آن را «آدرس ترکر» می‌نامم؛ یعنی مکان ترکرِ این تورنت.

یک نکته جالب که متوجه می‌شوید این است که به‌جای «http» معمول در ابتدای آدرس، این آدرس «udp» دارد. یعنی به‌جای پروتکل http باید از پروتکل udp استفاده کنید. قبلاً همه ترکرها از http استفاده می‌کردند، اما امروزه تقریباً همه تورنت‌های جدید از udp استفاده می‌کنند. پس تفاوت بین دو پروتکل چیست و چرا به udp روی بیاوریم؟

۳.۱ HTTP در برابر UDP در برابر TCP

دلیل اصلی اینکه بیشتر ترکرها حالا از udp استفاده می‌کنند این است که udp عملکرد بهتری نسبت به http دارد. Http بالای پروتکل دیگری به نام tcp ساخته شده است که بعداً در همین پروژه وقتی واقعاً شروع به دانلود فایل از همتاها کردیم از آن استفاده می‌کنیم. پس تفاوت بین tcp و udp چیست؟

تفاوت اصلی این است که tcp تضمین می‌کند وقتی کاربری داده می‌فرستد، کاربر دیگر آن داده را کامل، بدون خرابی و به ترتیب درست دریافت کند — اما باید قبل از فرستادن داده، یک اتصال پایدار بین کاربران ایجاد کند و این می‌تواند tcp را خیلی کندتر از udp کند. در مورد udp، اگر داده ارسالی به اندازه کافی کوچک باشد (کمتر از ۵۱۲ بایت) لازم نیست نگران دریافت بخشی از داده یا دریافت داده به‌هم‌ریخته باشید. با این حال، همان‌طور که به‌زودی می‌بینیم، ممکن است داده ارسالی هرگز به مقصد نرسد و بنابراین گاهی مجبور می‌شوید داده را دوباره بفرستید یا دوباره درخواست کنید.

به همین دلایل، udp اغلب انتخاب خوبی برای ترکرهاست چون پیام‌های کوچک می‌فرستند؛ و tcp را برای زمانی استفاده می‌کنیم که واقعاً فایل‌ها را بین همتاها منتقل می‌کنیم، چون آن فایل‌ها بزرگ‌ترند و باید سالم برسند.

۳.۲ ارسال پیام با UDP

در کد زیر، تغییراتی داده‌ام تا نشان دهم چگونه می‌توانیم از طریق UDP پیام بفرستیم و دریافت کنیم. توجه: این مثال ممکن است پاسخی دریافت نکند چون پیام ارسالی درست قالب‌بندی نشده است. این فقط مثالی است برای نشان دادن ماژول‌های مختلفی که استفاده خواهیم کرد.

js'use strict';

const fs = require('fs');
const bencode = require('bencode');
// 1 — ماژول‌های جدید از کتابخانه استاندارد
const dgram = require('dgram');
const Buffer = require('buffer').Buffer;
const urlParse = require('url').parse;

const torrent = bencode.decode(fs.readFileSync('puppy.torrent'));
// 2 — تجزیه آدرس ترکر تا بخش‌های مختلف آن را استخراج کنیم
const url = urlParse(torrent.announce.toString('utf8'));

// 3 — ایجاد نمونه سوکت udp4
const socket = dgram.createSocket('udp4');
// 4 — پیام باید یک بافر باشد
const myMsg = Buffer.from('hello?', 'utf8');
// 5 — ارسال پیام با مشخص کردن پورت و میزبان گیرنده
socket.send(myMsg, 0, myMsg.length, url.port, url.host, () => {});
// 6 — مدیریت پیام‌های ورودی
socket.on('message', msg => {
  console.log('message is', msg);
});

در این کد اتفاقات زیادی می‌افتد، پس بیایید آن را بشکنیم.

اول ۳ ماژول دیگر اضافه می‌کنیم: dgram، buffer و url. این‌ها همه از کتابخانه استاندارد هستند.

از متد parse ماژول url روی آدرس ترکر استفاده می‌کنم. این به من اجازه می‌دهد بخش‌های مختلف آدرس مثل پروتکل، نام میزبان، پورت و... را به راحتی استخراج کنم.

ماژول dgram ماژول ما برای udp است و اینجا یک نمونه سوکت جدید می‌سازم. سوکت یک آبجکت است که ارتباط شبکه از طریق آن اتفاق می‌افتد. آرگومان «udp4» را پاس می‌دهیم، یعنی می‌خواهیم از فرمت معمول IPv4 چهاربایتی آدرس استفاده کنیم (مثل 127.0.0.1). می‌توانید برای فرمت جدیدتر IPv6 (مثل FE80:CD00:0000:0CDE:1257:0000:211E:729C) «udp6» را هم پاس دهید، اما این فرمت هنوز به‌ندرت استفاده می‌شود.

برای اینکه پیامی از طریق سوکت فرستاده شود، باید به صورت بافر باشد، نه رشته یا عدد. Buffer.from راهی آسان برای ساخت یک بافر از یک رشته است؛ برای اطلاعات بیشتر درباره بافرها راهنمای کوچک من را ببینید.

متد send سوکت برای فرستادن پیام استفاده می‌شود. آرگومان اول پیام به صورت بافر است. دو آرگومان بعدی به شما اجازه می‌دهند فقط بخشی از بافر را به‌عنوان پیام بفرستید (با مشخص کردن یک offset و یک طول) اما اگر کل بافر را می‌فرستید کافی است offset را ۰ و طول را کل طول بافر بگذارید. بعد پورت و میزبان آدرس گیرنده است. در نهایت آخرین آرگومان یک callback برای وقتی است که ارسال پیام تمام شده است.

اینجا به سوکت می‌گوییم چگونه پیام‌های ورودی را مدیریت کند. هر وقت پیامی از طریق سوکت برگردد به تابع callback پاس داده می‌شود.

۳.۳ پروتکل و قالب پیام ترکر UDP

حالا می‌دانیم چگونه از طریق UDP پیام بفرستیم و دریافت کنیم، اما برای گرفتن فهرست همتاها از ترکر، ترکر انتظار دارد پیام‌ها از یک پروتکل مشخص پیروی کنند. به طور خلاصه باید:

  1. یک درخواست connect (اتصال) بفرستید
  2. پاسخ connect را بگیرید و شناسه اتصال (connection id) را استخراج کنید
  3. از شناسه اتصال برای فرستادن درخواست announce (اعلام) استفاده کنید — این‌جاست که به ترکر می‌گوییم به کدام فایل‌ها علاقه‌مندیم
  4. پاسخ announce را بگیرید و فهرست همتاها را استخراج کنید

چون حجم کد مربوط به ترکر دارد بزرگ می‌شود، در این نقطه می‌خواهم فایل جدیدی به نام tracker.js بسازم و همه کدهای مربوط به ترکر را آنجا منتقل کنم.

۳.۳.۱ پیام اتصال (Connect messaging)

حالا بیایید نگاهی به ساخت واقعی پیام‌ها بیندازیم. هر پیام یک بافر با قالب مشخص است که در BEP توصیف شده. اول به درخواست connect نگاه کنیم.

BEP درخواست connect را این‌طور توصیف می‌کند:

textOffset  Size            Name            Value
0       64-bit integer  connection_id   0x41727101980
8       32-bit integer  action          0 // connect
12      32-bit integer  transaction_id  ? // random
16

این به ما می‌گوید پیام ما باید با یک عدد صحیح ۶۴ بیتی (یعنی ۸ بایت) در ایندکس ۰ شروع شود و مقدارش باید 0x41727101980 باشد. چون فقط ۸ بایت می‌نویسیم، ایندکس بخش بعدی ۸ است. حالا یک عدد صحیح ۳۲ بیتی (۴ بایت) با مقدار ۰ می‌نویسیم. این ما را به offset ای ۱۲ بایت می‌رساند و یک عدد صحیح تصادفی ۳۲ بیتی می‌نویسیم. پس طول کل پیام ۸ بایت + ۴ بایت + ۴ بایت = ۱۶ بایت است و باید چیزی شبیه این باشد:

text<Buffer 00 00 04 17 27 10 19 80 00 00 00 00 a6 ec 6b 7d>

ببینیم چگونه می‌توانیم این را در فایل tracker.js پیاده‌سازی کنیم.

tracker.js:

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

const crypto = require('crypto'); // 1 — ماژول داخلی برای ساخت اعداد تصادفی

function buildConnReq() {
  const buf = Buffer.alloc(16); // 2 — بافر خالی ۱۶ بایتی

  // connection id — شناسه اتصال
  buf.writeUInt32BE(0x417, 0); // 3 — نوشتن در دو بخش ۴ بایتی
  buf.writeUInt32BE(0x27101980, 4);
  // action — نوع عمل (همیشه ۰ برای درخواست اتصال)
  buf.writeUInt32BE(0, 8); // 4
  // transaction id — شناسه تراکنش تصادفی
  crypto.randomBytes(4).copy(buf, 12); // 5 — کپی بافر تصادفی در بافر اصلی

  return buf;
}

اول ماژول داخلی crypto را اضافه می‌کنیم تا به ما در ساخت یک عدد تصادفی برای بافر کمک کند. به‌زودی عملکرد آن را می‌بینیم.

بعد یک بافر خالی جدید با اندازه ۱۶ بایت می‌سازیم چون از قبل می‌دانیم کل پیام باید ۱۶ بایت باشد.

اینجا شناسه اتصال را می‌نویسیم که هنگام نوشتن درخواست اتصال باید همیشه 0x41727101980 باشد. از متد writeUInt32BE استفاده می‌کنیم که یک عدد صحیح بدون علامت ۳۲ بیتی را در قالب big-endian می‌نویسد (اطلاعات بیشتر اینجا). عدد 0x417 را با مقدار offset برابر ۰ پاس می‌دهیم و بعد دوباره عدد 0x27101980 را با offset چهار بایت.

شاید دو سؤال بپرسید: این 0x چیست؟ و چرا باید عدد را به دو نوشته تقسیم کنیم؟

0x نشان می‌دهد عدد به صورت hexadecimal (شانزده‌مبنایی) است که وقتی با بایت‌ها کار می‌کنید نمایش راحت‌تری می‌تواند باشد. در غیر این صورت اساساً همان اعداد مبنای ۱۰ هستند.

دلیل اینکه باید در تکه‌های ۴ بایتی بنویسیم این است که متدی برای نوشتن عدد صحیح ۶۴ بیتی وجود ندارد. در واقع node.js از اعداد صحیح دقیق ۶۴ بیتی پشتیبانی نمی‌کند. اما همان‌طور که می‌بینید، نوشتن یک عدد hexadecimal شصت‌وچهاربیتی به صورت ترکیبی از دو عدد سی‌ودوبیتی آسان است.

بعد ۰ را برای action در ۴ بایت بعدی می‌نویسیم و offset را روی ۸ بایت قرار می‌دهیم چون همین‌الان یک عدد ۸ بایتی نوشتیم. این مقدار برای درخواست اتصال باید همیشه ۰ باشد.

برای ۴ بایت آخر یک بافر تصادفی ۴ بایتی با crypto.randomBytes تولید می‌کنیم که راه نسبتاً کاربردی برای ساخت یک عدد صحیح تصادفی ۳۲ بیتی است. برای کپی کردن آن بافر در بافر اصلی‌مان از متد copy استفاده می‌کنیم و offset موردنظرمان برای شروع نوشتن را پاس می‌دهیم.

تجزیه پاسخ خیلی ساده‌تر است. قالب پاسخ این‌طور است:

textOffset  Size            Name            Value
0       32-bit integer  action          0 // connect
4       32-bit integer  transaction_id
8       64-bit integer  connection_id
16

و این تابع تجزیه است:

tracker.js:

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

function parseConnResp(resp) {
  return {
    action: resp.readUInt32BE(0),        // نوع عمل
    transactionId: resp.readUInt32BE(4), // شناسه تراکنش
    connectionId: resp.slice(8)          // شناسه اتصال — چون نمی‌توان ۶۴ بیت را خواند، بافر نگه می‌داریم
  }
}

می‌بینید که action و شناسه تراکنش را به‌صورت اعداد صحیح بدون علامت ۳۲ بیتی big-endian می‌خوانم و offset را پاس می‌دهم. بعد فقط از متد slice برای گرفتن ۸ بایت آخر استفاده می‌کنم. چون نمی‌توانم عدد صحیح ۶۴ بیتی بخوانم، راحت‌تر است که همان‌طور بافر نگهش دارم.

۳.۳.۲ پیام اعلام (Announce messaging)

بسیاری از مفاهیم اینجا همان‌هایی است که در درخواست و پاسخ connect داشتیم. با این حال چند نکته هست که باید مراقبشان باشم و به آن‌ها اشاره می‌کنم. درخواست announce در زیر آمده:

textOffset  Size            Name            Value
0       64-bit integer  connection_id
8       32-bit integer  action          1 // announce
12      32-bit integer  transaction_id
16      20-byte string  info_hash
36      20-byte string  peer_id
56      64-bit integer  downloaded
64      64-bit integer  left

// ببینید در یادداشت‌های پایین درباره این چیست
const torrentParser = require('./torrent-parser');
const util = require('./util');

module.exports.getPeers = (torrent, callback) => {
  // ...
  // این خط حالا تورنت را دریافت می‌کند

function buildAnnounceReq(connId, torrent, port = 6881) {
  const buf = Buffer.allocUnsafe(98);

  // connection id — شناسه اتصال
  connId.copy(buf, 0);
  // action — نوع عمل (۱ یعنی announce)
  buf.writeUInt32BE(1, 8);
  // transaction id — شناسه تراکنش تصادفی
  crypto.randomBytes(4).copy(buf, 12);
  // info hash — هش اطلاعات تورنت
  torrentParser.infoHash(torrent).copy(buf, 16);
  // peerId — شناسه همتا
  util.genId().copy(buf, 36);
  // downloaded — حجم دانلود شده (مقدار اولیه ۰)
  Buffer.alloc(8).copy(buf, 56);
  // left — حجم باقی‌مانده
  torrentParser.size(torrent).copy(buf, 64);
  // uploaded — حجم آپلود شده (مقدار اولیه ۰)
  Buffer.alloc(8).copy(buf, 72);
  // event — رویداد (۰ یعنی هیچ)
  buf.writeUInt32BE(0, 80);
  // ip address — آدرس IP (۰ یعنی پیش‌فرض)
  buf.writeUInt32BE(0, 84);
  // key — کلید تصادفی
  crypto.randomBytes(4).copy(buf, 88);
  // num want — تعداد همتای درخواستی (-۱ یعنی پیش‌فرض)
  buf.writeInt32BE(-1, 92);
  // port — پورت
  buf.writeUInt16BE(port, 96);

  return buf;
}

util.js:

js'use strict';

const crypto = require('crypto');

let id = null;

module.exports.genId = () => {
  if (!id) {
    id = crypto.randomBytes(20);              // شناسه تصادفی ۲۰ بایتی
    Buffer.from('-AT0001-').copy(id, 0);      // نام کلاینت و شماره نسخه
  }
  return id;
};

در اینجا فهرست سریعی از چیزهایی است که می‌خواهم درباره این کد بگویم:

  • «peer id» برای شناسایی یکتای کلاینت شما استفاده می‌شود. فایل جدیدی به نام util.js ساختم که برای من شناسه تولید کند. یک peer id اساساً می‌تواند هر رشته تصادفی ۲۰ بایتی باشد اما بیشتر کلاینت‌ها از یک قرارداد که اینجا شرح داده شده پیروی می‌کنند. «AT» نام کلاینت من است (allen-torrent) و 0001 شماره نسخه است.
  • همان‌طور که می‌بینید شناسه فقط یک بار تولید می‌شود. معمولاً یک شناسه هر بار که کلاینت بارگذاری می‌شود تنظیم می‌شود و باید تا بسته شدنش ثابت بماند. بعداً دوباره از این شناسه استفاده خواهیم کرد.
  • کد محاسبه «info hash» و «left» کمی پیچیده است، پس خواستم آن را در فایل جدیدی به نام torrent-parser.js جدا کنم. در بخش بعد به آن می‌پردازیم، فعلاً می‌توانید آن بخش‌ها را نادیده بگیرید.
  • توجه کنید که این تابع حالا پارامتر torrent می‌گیرد. باز هم برای فیلدهای «info hash» و «left» است که به‌زودی به آن می‌رسیم.
  • اگر به BEP این درخواست نگاه کنید، offset ها را به شما می‌گوید؛ لازم نیست خودتان آن‌ها را بشمارید!
  • انتظار دارم connId یک بافر باشد چون این‌طور در متد parseConnResp رهایش کردیم، پس فقط مستقیم در بافر کپی‌اش می‌کنم.
  • چند جا به عدد صحیح ۶۴ بیتی نیاز دارم اما چون همیشه با ۰ مقداردهی می‌شوند، فقط از Buffer.alloc(8) استفاده می‌کنم؛ این یک بافر ۸ بایتی با همه صفرها می‌سازد.
  • برای بخش «num want» اشاره می‌کنم که از writeInt32BE استفاده کردم نه writeUInt32BE (به حرف U توجه کنید). چون عدد منفی است، نمی‌توان از نسخه بدون علامت استفاده کرد.
  • و در نهایت برای پورت، مشخصات رسمی می‌گوید پورت‌های بیت‌تورنت باید بین ۶۸۸۱ و ۶۸۸۹ باشند، پس تصمیم گرفتم پیش‌فرض ۶۸۸۱ را استفاده کنم.

کمی پیچیده است چون تعداد آدرس‌هایی که برمی‌گردند ثابت نیست. آدرس‌ها در گروه‌های ۶ بایتی می‌آیند؛ ۴ بایت اول آدرس IP و ۲ بایت بعدی پورت است. پس کد ما باید بخش آدرس‌های پاسخ را درست بشکند.

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

function parseAnnounceResp(resp) {
  // گروه‌بندی مقادیر به تکه‌های ۶ بایتی
  function group(iterable, groupSize) {
    let groups = [];
    for (let i = 0; i < iterable.length; i += groupSize) {
      groups.push(iterable.slice(i, i + groupSize));
    }
    return groups;
  }

  return {
    action: resp.readUInt32BE(0),        // نوع عمل
    transactionId: resp.readUInt32BE(4), // شناسه تراکنش
    leechers: resp.readUInt32BE(8),      // تعداد لچرها (دانلودکننده‌ها)
    seeders: resp.readUInt32BE(12),      // تعداد سیدرها (آپلودکننده‌ها)
    peers: group(resp.slice(20), 6).map(address => {
      return {
        ip: address.slice(0, 4).join('.'),  // ۴ بایت اول آدرس IP
        port: address.readUInt16BE(4)       // ۲ بایت بعدی پورت
      }
    })
  }
}

بیشتر این کد کاملاً سرراست است. فکر می‌کنم می‌توانستید تابع group را بیرون یا در یک فایل جدید بگذارید تا قابل استفاده مجدد باشد، اما برای اهداف این آموزش فکر می‌کنم همین کافی است. همچنین کمی تعجب‌آور است که می‌توانید روی یک بافر join صدا بزنید. این کمی حرفه‌ای است چون بایت‌ها را به رشته تبدیل می‌کند و به نظر می‌رسد کار می‌کند و فکر می‌کنم خوب هم به نظر می‌رسد.

دفعه قبل خاصیت announce را از این آبجکت بیرون کشیدیم. می‌بینید که یک خاصیت info هم دارد؟ اگر خاصیت info را بردارید و از تابع هش SHA1 عبورش دهید، هش اطلاعات (info hash) را می‌گیرید! می‌توانید با ماژول داخلی crypto به راحتی هش SHA1 اعمال کنید.

torrent-parser.js:

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

const bencode = require('bencode');
const crypto = require('crypto');

module.exports.infoHash = torrent => {
  const info = bencode.encode(torrent.info);              // رمزگذاری دوباره خاصیت info
  return crypto.createHash('sha1').update(info).digest(); // اعمال هش SHA1
};

چرا از تابع هش SHA1 استفاده کنیم؟ SHA1 یکی از بسیاری از توابع هش است اما همانی است که بیت‌تورنت استفاده می‌کند، پس در مورد ما هیچ تابع هش دیگری کارایی ندارد. می‌خواهیم از یک هش استفاده کنیم چون راهی فشرده برای شناسایی یکتای تورنت است. یک تابع هش بافری با طول ثابت برمی‌گرداند (در این مورد ۲۰ بایت). به عنوان مثال، تورنت نمونه ما خروجی <Buffer 11 7e 3a 66 65 e8 ff 1b 15 7e 5e c3 78 23 57 8a db 8a 71 2b> می‌دهد.

چون احتمال اینکه دو ورودی مقدار هش یکسانی بدهند بسیار کم است، و چون ورودی (خاصیت info) حاوی اطلاعاتی درباره تک‌تک قطعه‌های فایل‌های تورنت است (بعداً بیشتر در این باره)، راه خوبی برای شناسایی یکتای یک تورنت است. برای همین است که باید هش اطلاعات را به‌عنوان بخشی از درخواست به ترکر بفرستیم؛ داریم می‌گوییم فهرست همتاهایی را می‌خواهیم که می‌توانند دقیقاً همین تورنت را به اشتراک بگذارند.

۳.۳.۳.۲ اندازه تورنت (Torrent Size)

وقتی درخواست announce را می‌ساختیم دیدیم که باید فیلد «left» را پر کنیم. در واقع فقط کل اندازه فایل‌های تورنت را می‌فرستیم. ببینیم چگونه می‌توانیم آن را محاسبه کنیم.

torrent-parser.js:

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

const bignum = require('bignum');

module.exports.size = torrent => {
  // اگر چند فایل باشد مجموع طول‌ها، وگرنه طول فایل تکی
  const size = torrent.info.files ?
    torrent.info.files.map(file => file.length).reduce((a, b) => a + b) :
    torrent.info.length;

  return bignum.toBuffer(size, {size: 8}); // تبدیل به بافر ۸ بایتی
};

۳.۳.۴ نکات پایانی، نوع پاسخ و تلاش مجدد

حالا تقریباً همه تکه‌های ارتباط با ترکر جمع شده است. آخرین کاری که باید بکنیم نوشتن تابع respType برای تشخیص اینکه پاسخ، پاسخ connect است یا پاسخ announce است.

بیش از یک راه برای نوشتن این متد وجود دارد. بعد از نگاه کردن به ساختار دو نوع پاسخ، متوجه شدم پاسخ connect مقدار action برابر ۰ دارد و پاسخ announce مقدار action برابر ۱.

tracker.js:

js// بقیه فایل برای صرفه‌جویی در فضا حذف شده است

function respType(resp) {
  const action = resp.readUInt32BE(0);
  if (action === 0) return 'connect';
  if (action === 1) return 'announce';
}

ممکن است وقتی برنامه را اجرا می‌کنید گیر کند. همان‌طور که قبلاً گفتم، ممکن است پیام‌های udp هنگام انتقال گم شوند؛ اگر این اتفاق افتاد فقط سعی کنید برنامه را دوباره اجرا کنید. یا می‌توانید به‌عنوان تمرین جایزه، تابع خودتان را بنویسید که بعد از یک زمان توقف (timeout) تلاش مجدد کند!

اگر این کار را امتحان کردید، طبق BEP باید بین هر درخواست 2^n × ۱۵ ثانیه صبر کنید و در کل حداکثر ۸ درخواست بفرستید. این «عقب‌نشینی نمایی» (exponential backoff) نامیده می‌شود و دلیل انجامش متعادل کردن دو نگرانی است:

  • ممکن است پیام شما هنگام انتقال گم شده باشد؛ در این صورت باید در سریع‌ترین زمان ممکن دوباره بفرستید.
  • پیام هنوز دارد می‌آید، اما شبکه ترافیک دارد. در این حالت نمی‌خواهید شبکه را با درخواست‌های بیشتر بمباران کنید.

این یک تکنیک رایج برای ارتباطات شبکه‌ای نامطمئن است.

۴. دانلود از همتاها

حالا که می‌توانیم برای فایل‌هایمان فهرست همتاها را بگیریم، می‌خواهیم واقعاً فایل‌ها را از آن‌ها دانلود کنیم. در اینجا یک نمای کلی پایه از چگونگی کار این موضوع داریم:

  1. اول باید با همه همتاهای فهرستتان یک اتصال tcp بسازید. هرچه همتای بیشتری بتوانید به‌ش متصل شوید، سریع‌تر می‌توانید فایل‌هایتان را دانلود کنید.
  2. بعد از تبادل چند پیام با همتا به‌عنوان راه‌اندازی، باید شروع به درخواست قطعه‌های فایل‌هایی که می‌خواهید کنید. همان‌طور که به‌زودی می‌بینیم، فایل‌های مشترک یک تورنت به قطعه‌ها تقسیم می‌شوند تا بتوانید بخش‌های مختلف فایل‌ها را به‌طور هم‌زمان از همتاهای مختلف دانلود کنید.
  3. به احتمال زیاد تعداد قطعه‌ها از همتاها بیشتر است، پس وقتی دریافت یک قطعه از یک همتا تمام شد، می‌خواهیم قطعه بعدی که نیاز داریم را از همان همتا درخواست کنیم. در حالت ایده‌آل می‌خواهید همه اتصال‌ها قطعه‌های متفاوت و جدید درخواست کنند، پس باید ردیابی کنید کدام قطعه‌ها را دارید و کدام‌ها را هنوز نیاز دارید.
  4. و در نهایت وقتی قطعه‌ها را دریافت می‌کنید، در حافظه ذخیره می‌شوند، پس باید داده را روی هارد دیسکتان بنویسید. امیدوارم در این نقطه کارتان تمام شده باشد!

استفاده از tcp برای فرستادن پیام‌ها شبیه استفاده از udp است که قبلاً استفاده کردیم. در این مورد به‌جای ماژول «dgram» از ماژول «net» استفاده می‌کنیم. بیایید به مثالی نگاه کنیم که چگونه کار می‌کند.

۴.۳ نمای کلی پروتکل

وقتی اتصال tcp برقرار شد، پیام‌هایی که می‌فرستید و دریافت می‌کنید باید از پروتکل زیر پیروی کنند.

اولین کاری که می‌خواهید بکنید این است که به همتای خودتان بگویید به دانلود کدام فایل‌ها علاقه‌مندید، به‌همراه چند اطلاعات شناسایی. اگر همتا فایل‌هایی را که می‌خواهید نداشته باشد، اتصال را می‌بندد، اما اگر فایل‌ها را داشته باشد باید پیام مشابهی به‌عنوان تأیید برگرداند. به این «handshake» (دست دادن) می‌گویند.

محتمل‌ترین چیزی که بعداً اتفاق می‌افتد این است که همتا به شما بگوید چه قطعه‌هایی دارد. این از طریق پیام‌های «have» و «bitfield» اتفاق می‌افتد. هر پیام «have» یک اندیس قطعه به‌عنوان payload دارد. یعنی چندین پیام have دریافت می‌کنید، برای هر قطعه‌ای که همتایتان دارد یک پیام.

پیام bitfield هدف مشابهی دارد اما به روش متفاوتی. پیام bitfield می‌تواند همه قطعه‌های همتا را فقط در یک پیام بگوید. این کار را با فرستادن یک رشته از بیت‌ها انجام می‌دهد، برای هر قطعه‌ای در فایل یک بیت. اندیس هر بیت همان اندیس قطعه است و اگر آن قطعه را داشته باشند ۱ می‌شود و اگر نداشته باشند ۰. مثلاً اگر یک bitfield دریافت کنید که با 011001... شروع می‌شود، یعنی قطعه‌های اندیس ۱، ۲ و ۵ را دارند اما قطعه‌های اندیس ۰، ۳ و ۴ را ندارند.

امکان دارد هم پیام‌های «have» و هم یک پیام bitfield را دریافت کنید؛ در این صورت باید آن‌ها را ترکیب کنید تا فهرست کامل قطعه‌ها به دست بیاید.

در واقع ممکن است نوع دیگری از پیام هم دریافت کنید؛ ممکن است همتا تصمیم بگیرد نمی‌خواهد با شما به اشتراک بگذارد! پیام‌های choke (خفه)، unchoke (رفع خفه)، interested (علاقه‌مند) و not interested (بی‌علاقه) برای همین هستند. اگر خفه (choked) شوید یعنی همتا نمی‌خواهد با شما به اشتراک بگذارد؛ اگر رفع خفه (unchoked) شوید یعنی همتا مایل به اشتراک گذاری است. از طرف دیگر، interested یعنی شما چیزی را که همتایتان دارد می‌خواهید، در حالی که not interested یعنی آنچه را دارد نمی‌خواهید.

شما همیشه خفه و بی‌علاقه شروع می‌کنید. پس اولین پیامی که می‌فرستید باید پیام interested باشد. بعد امیدوارید آن‌ها یک پیام unchoke بفرستند تا بتوانید به قدم بعدی بروید. اگر به‌جایش یک پیام choke دریافت کردید، فقط می‌توانید بگذارید اتصال بیفتد.

در این نقطه آماده شروع درخواست هستید. می‌توانید این کار را با فرستادن پیام‌های «request» انجام دهید که اندیس قطعه‌ای را که می‌خواهید دارد (جزئیات بیشتر در بخش بعد).

و در نهایت یک پیام piece دریافت می‌کنید که حاوی بایت‌های داده‌ای است که درخواست کردید.

۴.۴ انواع پیام

طبق مشخصات، پیام handshake باید بافری شبیه این باشد:

texthandshake: <pstrlen><pstr><reserved><info_hash><peer_id>

pstrlen: string length of <pstr>, as a single raw byte
pstr: string identifier of the protocol
reserved: eight (8) reserved bytes. All current implementations use all zeroes.
peer_id: 20-byte string used as a unique ID for the client.

In version 1.0 of the BitTorrent protocol, pstrlen = 19, and pstr = "BitTorrent protocol".

وقتی handshake برقرار شد، ۱۰ نوع پیام مختلف می‌توانند رد و بدل شوند که همه از یک قالب پیروی می‌کنند:

  • ۴ بایت که طول پیام را نشان می‌دهد (به‌جز همین ۴ بایت)
  • ۱ بایت برای شناسه (id) پیام
  • بقیه بافر، payload پیام است که با هر پیام فرق می‌کند

در مورد این‌ها وقتی پیش بیایند با جزئیات بیشتری بحث می‌کنم، اما می‌توانید اطلاعات بیشتر را در مشخصات پیدا کنید.

فایل جدیدی به نام message.js ساختم با چند تابع راحت برای کمک به ساخت این بافرهای پیام.

message.js:

js'use strict';

const Buffer = require('buffer').Buffer;
const torrentParser = require('./torrent-parser');

module.exports.buildHandshake = torrent => {
  const buf = Buffer.alloc(68);
  // pstrlen — طول رشته پروتکل
  buf.writeUInt8(19, 0);
  // pstr — رشته شناساگر پروتکل
  buf.write('BitTorrent protocol', 1);
  // reserved — بایت‌های رزروشده (همه صفر)
  buf.writeUInt32BE(0, 20);
  buf.writeUInt32BE(0, 24);
  // info hash — هش اطلاعات تورنت
  torrentParser.infoHash(torrent).copy(buf, 28);
  // peer id — شناسه یکتای کلاینت
  buf.write(util.genId());
  return buf;
};

module.exports.buildKeepAlive = () => Buffer.alloc(4);

module.exports.buildChoke = () => {
  const buf = Buffer.alloc(5);
  // length — طول پیام
  buf.writeUInt32BE(1, 0);
  // id — شناسه پیام (۰ یعنی خفه)
  buf.writeUInt8(0, 4);
  return buf;
};

module.exports.buildUnchoke = () => {
  const buf = Buffer.alloc(5);
  // length — طول پیام
  buf.writeUInt32BE(1, 0);
  // id — شناسه پیام (۱ یعنی رفع خفه)
  buf.writeUInt8(1, 4);
  return buf;
};

module.exports.buildInterested = () => {
  const buf = Buffer.alloc(5);
  // length — طول پیام
  buf.writeUInt32BE(1, 0);
  // id — شناسه پیام (۲ یعنی علاقه‌مند)
  buf.writeUInt8(2, 4);
  return buf;
};

module.exports.buildUninterested = () => {
  const buf = Buffer.alloc(5);
  // length — طول پیام
  buf.writeUInt32BE(1, 0);
  // id — شناسه پیام (۳ یعنی بی‌علاقه)
  buf.writeUInt8(3, 4);
  return buf;
};

module.exports.buildHave = payload => {
  const buf = Buffer.alloc(9);
  // length — طول پیام
  buf.writeUInt32BE(5, 0);
  // id — شناسه پیام (۴ یعنی have)
  buf.writeUInt8(4, 4);
  // piece index — اندیس قطعه
  buf.writeUInt32BE(payload, 5);
  return buf;
};

module.exports.buildBitfield = bitfield => {
  const buf = Buffer.alloc(14);
  // length — طول پیام
  buf.writeUInt32BE(payload.length + 1, 0);

  buf.writeUInt8(5, 4);
  // bitfield — بیت‌های قطعه‌ها

  return buf;
};

۴.۵ گروه‌بندی پیام‌ها

قبل از رفتن به تبادل واقعی پیام، یک چیز دیگر هست که باید درباره tcp به آن بپردازم. شاید فرض کرده باشید که هر بار داده‌ای از سوکت دریافت می‌کنید، یک پیام کامل و واحد است. اما این‌طور نیست. یادتان باشد کد ما برای دریافت داده شبیه این بود:

jssocket.on('data', receivedBuffer => {
  // اینجا با receivedBuffer کاری انجام بده
})

مشکل این است که callback داده را همان‌طور که در دسترس قرار می‌گیرد دریافت می‌کند و هیچ راهی برای دانستن چگونگی تکه‌تکه شدن آن داده وجود ندارد. سوکت ممکن است فقط بخشی از یک پیام را دریافت کند، یا ممکن است چند پیام را یک‌جا دریافت کند. به همین دلیل است که هر پیام با طولش شروع می‌شود تا به پیدا کردن شروع و پایان هر پیام کمک کند.

اگر هر بار که callback صدا زده می‌شد، یک پیام کامل واحد دریافت می‌کرد، همه‌چیز برای ما خیلی راحت‌تر می‌شد، پس می‌خواهم تابعی به نام onWholeMsg بنویسم که دقیقاً همین کار را برای ما کند.

مثل این:

download.js:

jsfunction download(peer) {
  const socket = net.Socket();
  socket.connect(peer.port, peer.ip, () => {
    // socket.write(...) اینجا یک پیام بنویس
  });
  onWholeMsg(socket, data => {
    // اینجا پاسخ را مدیریت کن
  });
}

اینجا پیاده‌سازی onWholeMsg است:

download.js:

jsfunction onWholeMsg(socket, callback) {
  let savedBuf = Buffer.alloc(0); // بافر ذخیره پیام‌های ناقص
  let handshake = true;           // اولین پیام همیشه handshake است

  socket.on('data', recvBuf => {
    // msgLen طول یک پیام کامل را محاسبه می‌کند
    const msgLen = () => handshake ? savedBuf.readUInt8(0) + 49 : savedBuf.readInt32BE(0) + 4;
    savedBuf = Buffer.concat([savedBuf, recvBuf]);

    while (savedBuf.length >= 4 && savedBuf.length >= msgLen()) {
      callback(savedBuf.slice(0, msgLen())); // پاس دادن یک پیام کامل به callback
      savedBuf = savedBuf.slice(msgLen());   // حذف آن پیام از بافر
      handshake = false;
    }
  });
}

این تابع چگونه کار می‌کند؟ اول به تمایز بین تابع onWholeMsg، callback پاس‌داده‌شده به onWholeMsg و callback بی‌نام پاس‌داده‌شده به socket.on توجه کنید. بعد، کلید کار کردن این‌ها استفاده از یک بستار (closure) است. چون callback سوکت داخل تابع onWholeMsg است، همیشه به متغیرهای دومی دسترسی دارد.

پس هر بار که سوکت داده دریافت می‌کند، callback سوکت صدا زده می‌شود. داده جدید را با savedBuf ترکیب می‌کند و تا وقتی savedBuf به اندازه کافی بلند باشد که حداقل یک پیام کامل را نگه دارد، آن را به callback تابع onWholeMsg پاس می‌دهد و بعد savedBuf را با بریدن آن پیام‌ها به‌روز می‌کند. اساساً savedBuf تکه‌های پیام‌های ناتمام را بین دورهای دریافت داده از سوکت نگه می‌دارد.

متغیر handshake را هم در بستار دارم. چون پیام handshake طولش را به‌عنوان بخشی از پیام نمی‌گوید. تنها راهی که می‌توانید بفهمید پیام handshake دریافت می‌کنید این است که همیشه اولین پیامی است که دریافت می‌کنید. برای همین با handshake برابر true شروع می‌کنم و اولین بار که یک پیام کامل دریافت می‌کنیم، false می‌کنمش.

اگر خیلی با بستارها آشنا نیستید، همه این‌ها شاید کمی مغز را درگیر کند، اما تشویقتان می‌کنم که ادامه دهید و کد را با دقت بخوانید. یک چیزی که شاید کمک کند این است که متوجه شوید تابع onWholeMsg فقط یک بار صدا زده می‌شود، پس متغیرهای savedBuf و handshake فقط یک بار مقداردهی می‌شوند. اما بعد callback سوکت چند بار صدا زده می‌شود و هر بار همان دو متغیر را می‌خواند و می‌نویسد.

function download(peer, torrent) {

  socket.on('error', console.log);
  socket.connect(peer.port, peer.ip, () => {
    // 1 — ارسال پیام دست دادن
    socket.write(message.buildHandshake(torrent));
  });
  // 2 — مدیریت پیام‌های ورودی با msgHandler
  onWholeMsg(socket, msg => msgHandler(msg, socket));
}

// 2 — بررسی نوع پیام و مدیریت آن
function msgHandler(msg, socket) {
  if (isHandshake(msg)) socket.write(message.buildInterested());
}

// 3 — بررسی اینکه پیام دست دادن است
function isHandshake(msg) {
  return msg.length === msg.readUInt8(0) + 49 &&
    msg.toString('utf8', 1) === 'BitTorrent protocol';
}

۴.۷ قطعه‌ها (Pieces)

بعد از برقراری دست دادن، همتایتان باید به شما بگوید چه قطعه‌هایی دارد. بیایید لحظه‌ای بفهمیم قطعه‌ها دقیقاً چه هستند.

اگر یک فایل تورنت را باز کنید، دیدیم که حاوی داده‌هایی با ویژگی‌های مختلف مثل «announce» و «info» است. یک ویژگی دیگر «piece length» است. این به شما می‌گوید طول یک قطعه چند بایت است. فرض کنیم به‌طور فرضی طول قطعه ۱۰۰۰ بایت دارید. اگر اندازه کل فایل(ها) ۱۲۰۰۰ بایت باشد، یعنی فایل باید ۱۲ قطعه داشته باشد. توجه کنید که آخرین قطعه ممکن است پر ۱۰۰۰ بایت نباشد. اگر فایل ۱۲۰۰۱ بایت بود، کل قطعه‌ها ۱۳ می‌شد که آخرین قطعه فقط ۱ بایت است.

این قطعه‌ها از ۰ ایندکس می‌شوند و این‌طور می‌دانیم کدام قطعه را می‌فرستیم یا دریافت می‌کنیم. مثلاً ممکن است قطعه اندیس ۰ را درخواست کنید؛ یعنی از مثال قبلی‌مان ۱۰۰۰ بایت اول فایل را می‌خواهیم. اگر قطعه اندیس ۱ را بخواهیم، ۱۰۰۰ بایت دوم را می‌خواهیم و الی آخر.

۴.۸ مدیریت پیام‌ها

حالا می‌خواهم مدیریت پیام‌هایی را شروع کنم که پیام handshake نیستند. چون این پیام‌ها یک قالب ثابت دارند، می‌توانم فقط شناسه‌شان را بررسی کنم تا بفهمم چه پیامی است. برای کمک به این کار تابعی به message.js اضافه کردم که بافرهای پیام را به اجزایش تجزیه می‌کند:

  const id = msg.length > 4 ? msg.readInt8(4) : null;     // پیام‌های بدون id (keep-alive)
  let payload = msg.length > 5 ? msg.slice(5) : null;     // پیام‌های بدون payload

  if (id === 6 || id === 7 || id === 8) {
    // برای request، piece و cancel: payload شامل index، begin و block/length است
    const rest = payload.slice(8);
    payload = {
      index: payload.readInt32BE(0),
      begin: payload.readInt32BE(4)
    };
    payload[id === 7 ? 'block' : 'length'] = rest;
  }

  return {
    size: msg.readInt32BE(0), // طول پیام
    id: id,                   // شناسه پیام
    payload: payload          // محتوای پیام
  }
};

۴.۹ مدیریت اتصال‌ها و قطعه‌ها

این نقطه مهمی در پروژه است چون مدیریت اتصال‌ها و قطعه‌ها شامل تصمیم‌ها و بده‌بستان‌های جالب زیادی است. تا اینجا بیشتر مستقیم از مشخصات پیروی کردیم، اما از این به بعد راه‌حل‌های ممکن زیادی وجود دارد و من فقط یکی را مرور می‌کنم. برای همین توصیه می‌کنم قبل از ادامه، کمی وقت بگذارید و فکر کنید این مدیریت‌کننده‌های پیام را خودتان چگونه پیاده می‌کنید.

البته یک نگرانی بزرگ کارایی است. می‌خواهیم دانلودهایمان هرچه سریع‌تر تمام شود. بخش سخت این است که همه همتاها همه قطعه‌ها را ندارند. همچنین همه همتاها نمی‌توانند با یک نرخ آپلود کنند. علاوه بر این‌ها، ممکن است اتصال‌ها هر لحظه بیفتند، پس به راهی برای برخورد با درخواست‌های ناموفق نیاز داریم. چگونه می‌توانیم کار به اشتراک گذاشتن قطعه‌های درست را بین همه همتاها تقسیم کنیم تا سریع‌ترین سرعت دانلود را داشته باشیم؟

۴.۹.۲ صف کار (Job queue)

بعد می‌خواهم یک فهرست per اتصال بسازم. این فهرست شامل همه قطعه‌هایی است که یک همتا دارد. چرا باید این فهرست را نگه داریم؟ چرا به محض دریافت پیام «have» یا «bitfield» برای یک قطعه درخواست بدهیم؟ مشکل این است که احتمالاً در نهایت همه قطعه‌ها را از همان اولین همتایی که به آن وصل می‌شویم درخواست می‌کنیم و بعد چون نمی‌خواهیم همان قطعه را دوبار درخواست کنیم، هیچ قطعه‌ای برای بقیه همتاها نمی‌ماند که درخواست کنند.

حتی اگر استفاده از راهبرد round-robin ممکن باشد طوری که هر همتا فقط بعد از اینکه همه همتاها حداقل یک قطعه برای درخواست گرفتند، قطعه دوم را بگیرد، باز هم یک مشکل هست. این راهبرد باعث می‌شود همه همتاها تعداد درخواست مساوی داشته باشند، اما بعضی همتاها ناگزیر سریع‌تر از بقیه آپلود می‌کنند. در حالت ایده‌آل می‌خواهیم همتاهای سریع‌تر درخواست‌های بیشتری بگیرند، نه اینکه چند درخواست به خاطر کندترین همتا گلوگاه شوند.

راه‌حل طبیعی این است که فقط یک یا چند قطعه را در یک زمان از یک همتا درخواست کنیم و فقط بعد از دریافت پاسخ، درخواست بعدی را بدهیم. این‌طور همتاهای سریع‌تر پاسخ‌هایشان را سریع‌تر می‌فرستند و بیشتر «برمی‌گردند» تا درخواست‌های بیشتری بگیرند.

اما چون پیام‌های «have» و «bitfield» را یک‌جا دریافت می‌کنیم، یعنی باید فهرست قطعه‌هایی که همتا دارد را ذخیره کنیم. این‌طور می‌توانیم صبر کنیم پاسخ یک قطعه بیاید و بعد به فهرست مراجعه کنیم تا ببینیم بعدی چه چیزی را درخواست کنیم.

من به این «صف کار» می‌گویم، چون می‌توانید این‌طور به آن فکر کنید: هر اتصال یک فهرست قطعه برای درخواست دارد. به اولین آیتم فهرست نگاه می‌کنند و بررسی می‌کنند آیا در فهرست قطعه‌های قبلاً درخواست‌شده هست یا نه. اگر نبود، قطعه را درخواست می‌کنند و منتظر پاسخ می‌مانند. وگرنه آیتم را دور می‌ریزند و به سراغ بعدی می‌روند. وقتی پاسخ دریافت می‌کنند، به سراغ آیتم بعدی فهرست می‌روند و این فرایند را تا خالی شدن فهرست تکرار می‌کنند.

این فهرست هم باید به توابع مدیریت پاس داده شود، اما باید per اتصال ساخته شود. مثل این:

download.js:

  if (m.id === 7) pieceHandler(m.payload, socket, requested, queue);

  // ...
  const pieceIndex = payload.readUInt32BE(0);
  queue.push(pieceIndex);          // افزودن قطعه به صف
  if (queue.length === 1) {        // اگر صف قبلاً خالی بود، درخواست را شروع کن
    requestPiece(socket, requested, queue);
  }

  // ...
  queue.shift();                        // حذف قطعه دریافت‌شده از صف
  requestPiece(socket, requested, queue);
}

function requestPiece(socket, requested, queue) {
  if (requested[queue[0]]) {            // اگر قبلاً درخواست شده، رد شو
    queue.shift();
  } else {
    // این شبه‌کد است؛ buildRequest در واقع آرگومان‌های کمی پیچیده‌تر می‌گیرد
    socket.write(message.buildRequest(pieceIndex));
  }
}

پس فقط وقتی روی «have» یک قطعه درخواست می‌کنیم که صف قبلاً خالی بوده باشد (برای bitfieldHandler هم باید مشابه باشد). از آن نقطه به بعد فقط وقتی پاسخ قطعه را دریافت کرده‌ایم درخواست می‌دهیم (در pieceHandler). وقتی قطعه‌ای دریافت می‌کنیم می‌توانیم آن را از صف بیرون بیاوریم. اگر قطعه قبلاً درخواست شده باشد، باز آن را از صف بیرون می‌آوریم. می‌بینید که این در تابع requestPiece اتفاق می‌افتد که ساخته‌امش چون کدی است که بین هر دو مدیریت‌کننده مشترک است.

۴.۹.۳ شکست درخواست‌ها (Request Failures)

آخرین چیزی که قبل از پیاده‌سازی کامل توابع مدیریت می‌خواهم مرور کنم شکست درخواست‌هاست. الان هر وقت درخواست می‌فرستیم اندیس قطعه را هم به آرایه requested اضافه می‌کنیم. این‌طور می‌دانیم کدام قطعه‌ها قبلاً درخواست شده‌اند و می‌توانیم جلوی درخواست تکراری همتای بعدی را بگیریم.

اما ممکن است قطعه‌ای را درخواست کنیم و هرگز دریافتش نکنیم. دلیلش این است که اتصال می‌تواند هر لحظه به هر دلیلی بیفتد. چون از درخواست قطعه‌هایی که به آرایه requested اضافه شده‌اند اجتناب می‌کنیم، این قطعه‌ها هرگز دریافت نمی‌شوند.

شاید فکر کنید کافی است قطعه‌ها را وقتی دریافت می‌کنیم به فهرست اضافه کنیم. اما بعد بین زمان درخواست قطعه و دریافتش، هر همتای دیگری هم می‌تواند همان قطعه را درخواست کند که به درخواست‌های تکراری می‌انجامد.

فهمیدم ساده‌ترین راه‌حل نگه داشتن دو فهرست است، یکی برای قطعه‌های درخواست‌شده و یکی برای قطعه‌های دریافت‌شده. فهرست requested را هنگام درخواست به‌روز می‌کنیم و فهرست received را هنگام دریافت. بعد وقتی همه قطعه‌ها را درخواست کرده‌ایم اما هنوز قطعه‌هایی هستند که دریافت نکرده‌ایم، فهرست received را در فهرست requested کپی می‌کنیم و این اجازه می‌دهد آن قطعه‌های جاافتاده را دوباره درخواست کنیم.

اما نگه داشتن چند فهرست وقتی فقط یک انتزاع داده‌ای باید کافی باشد، ناخوشایند است. پس فایل جدیدی به نام Pieces.js ساختم:

Pieces.js:

js'use strict';

module.exports = class {
  constructor(size) {
    this.requested = new Array(size).fill(false); // فهرست قطعه‌های درخواست‌شده
    this.received = new Array(size).fill(false);  // فهرست قطعه‌های دریافت‌شده
  }

  addRequested(pieceIndex) {
    this.requested[pieceIndex] = true;
  }

  addReceived(pieceIndex) {
    this.received[pieceIndex] = true;
  }

  needed(pieceIndex) {
    if (this.requested.every(i => i === true)) {
      // برای برگرداندن یک کپی از آرایه از slice استفاده کن
      this.requested = this.received.slice();
    }
    return !this.requested[pieceIndex];
  }

  isDone() {
    return this.received.every(i => i === true);
  }
};

می‌بینید که باید نمونه Pieces را با تعداد کل قطعه‌ها مقداردهی کنیم، وگرنه دانستن اینکه چه زمانی همه قطعه‌ها را گرفته‌ایم ممکن نیست. فرض می‌کنیم اندیس آرایه همان اندیس قطعه است و بعد اگر درخواست/دریافت شده باشد آن اندیس را true می‌کنیم (همه اندیس‌ها به‌طور پیش‌فرض false شروع می‌شوند). این راه خوبی برای پیدا کردن وضعیت یک قطعه بدون پیمایش آرایه‌هاست.

۴.۱۰.۱ خفه و رفع خفه (Choke and unchoke)

برخورد با حالت‌های choke و unchoke کمی پیچیده است چون نمی‌خواهیم هیچ قطعه‌ای را تا وقتی رفع خفه نشده‌ایم درخواست کنیم. فکر می‌کنم ساده‌ترین راه برای اعمال این، ساختن یک آبجکت جدید است که هم آرایه صف ما را نگه دارد و هم یک خاصیت choked.

حالا می‌توانیم این آبجکت جدید را اضافه کنیم و مدیریت‌کننده‌های choke و unchoke را بنویسیم.

  socket.on('error', console.log);
  socket.connect(peer.port, peer.ip, () => {
    socket.write(message.buildHandshake(torrent));
  });

  onWholeMsg(socket, msg => msgHandler(msg, socket, pieces, queue));

function onWholeMsg(socket, callback) {
  let savedBuf = Buffer.alloc(0);
  let handshake = true;

  socket.on('data', recvBuf => {
    // msgLen طول یک پیام کامل را محاسبه می‌کند
    const msgLen = () => handshake ? savedBuf.readUInt8(0) + 49 : savedBuf.readInt32BE(0) + 4;
    savedBuf = Buffer.concat([savedBuf, recvBuf]);

    while (savedBuf.length >= 4 && savedBuf.length >= msgLen()) {
      callback(savedBuf.slice(0, msgLen()));
      savedBuf = savedBuf.slice(msgLen());
      handshake = false;
    }
  });
}

function msgHandler(msg, socket, pieces, queue) {
  if (isHandshake(msg)) {
    socket.write(message.buildInterested());
  } else {
    const m = message.parse(msg);

    if (m.id === 0) chokeHandler(socket);
    // 1 — unchoke حالا pieces و queue را هم می‌گیرد
    if (m.id === 1) unchokeHandler(socket, pieces, queue);
    if (m.id === 4) haveHandler(m.payload);
    if (m.id === 5) bitfieldHandler(m.payload);
    if (m.id === 7) pieceHandler(m.payload);
  }
}

  return msg.length === msg.readUInt8(0) + 49 &&

}

}

۴.۱۰.۲ قطعه‌ها در برابر بلاک‌ها (Pieces vs. blocks)

تابع message.buildRequest در کد بالا باید آبجکتی با خاصیت‌های index، begin و length بگیرد. این‌ها فیلدهای الزامی payload یک پیام درخواست هستند. اما این فیلدها دقیقاً برای چه هستند؟ index که آسان است؛ همان اندیس قطعه‌ای است که الان پاس داده می‌شود. begin و length چطور؟

این دو خاصیت لازم‌اند چون گاهی یک قطعه برای یک پیام خیلی بزرگ است. هرچند درباره بهترین اندازه اختلاف نظر هست، معمولاً حدود 2^14 (۱۶۳۸۴) بایت در نظر گرفته می‌شود. به این یک «بلاک» می‌گویند، جایی که یک قطعه از یک یا چند بلاک تشکیل شده است. اگر طول قطعه بیشتر از طول یک بلاک باشد، باید به بلاک‌هایی شکسته شود و برای هر بلاک یک پیام فرستاده شود.

پس فیلد «begin» آفست صفرپایه بایت است که از شروع قطعه حساب می‌شود و «length» طول بلاک درخواست‌شده است. این همیشه 2^14 خواهد بود، به‌جز احتمالاً آخرین بلاک که شاید کمتر باشد.

برای جا دادن این موضوع به تغییرات متعددی نیاز خواهیم داشت. اما اول می‌خواهم چند تابع در torrentParser.js بنویسم که به من در تعیین طول قطعه و بلاک برای یک اندیس قطعه مشخص کمک کند.

torrent-parser.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

const bignum = require('bignum');

module.exports.BLOCK_LEN = Math.pow(2, 14); // طول استاندارد هر بلاک

module.exports.pieceLen = (torrent, pieceIndex) => {
  const totalLength = bignum.fromBuffer(this.size(torrent)).toNumber(); // اندازه کل فایل
  const pieceLength = torrent.info['piece length'];                    // طول تعیین‌شده هر قطعه

  const lastPieceLength = totalLength % pieceLength;   // طول آخرین قطعه (کوتاه‌تر)
  const lastPieceIndex = Math.floor(totalLength / pieceLength);

  return lastPieceIndex === pieceIndex ? lastPieceLength : pieceLength;
};

module.exports.blocksPerPiece = (torrent, pieceIndex) => {
  const pieceLength = this.pieceLen(torrent, pieceIndex);
  return Math.ceil(pieceLength / this.BLOCK_LEN); // تعداد بلاک‌های هر قطعه
};

module.exports.blockLen = (torrent, pieceIndex, blockIndex) => {
  const pieceLength = this.pieceLen(torrent, pieceIndex);

  const lastPieceLength = pieceLength % this.BLOCK_LEN; // طول بلاک آخر
  const lastPieceIndex = Math.floor(pieceLength / this.BLOCK_LEN);

  return blockIndex === lastPieceIndex ? lastPieceLength : this.BLOCK_LEN;
};

در pieceLen مجبور بودم از کتابخانه bignum برای برخورد با متغیر totalLength استفاده کنم چون در یک بافر ۸ بایتی است. pieceLen و blockLen مشابه‌اند؛ فقط به ترتیب طول قطعه یا طول بلاک را برمی‌گردانند، مگر اینکه اتفاقاً آخرین قطعه یا بلاک باشند؛ آن موقع شاید از یک قطعه یا بلاک کامل کوتاه‌تر باشند. طول قطعه را می‌توان در فایل تورنت پیدا کرد و طول بلاک طبق قرارداد 2^14 بایت است.

همچنین، هم آبجکت queue و هم کلاس Pieces باید تغییر کنند تا با بلاک‌ها سر و کار داشته باشند نه فقط قطعه‌ها. برای آبجکت queue فقط از یک آبجکت ساده جاوااسکریپتی با دو خاصیت استفاده کردیم، اما با پیچیدگی اضافه‌شده برخورد با بلاک‌ها، تصمیم گرفتم یک کلاس Queue جدید بسازم.

Queue.js:

js'use strict';

const tp = require('./torrent-parser');

module.exports = class {
  constructor(torrent) {
    this._torrent = torrent;
    this._queue = [];
    this.choked = true; // خاصیت عمومی
  }

  // افزودن همه بلاک‌های یک قطعه به صف
  queue(pieceIndex) {
    const nBlocks = tp.blocksPerPiece(this._torrent, pieceIndex);
    for (let i = 0; i < nBlocks; i++) {
      const pieceBlock = {
        index: pieceIndex,                       // اندیس قطعه
        begin: i * tp.BLOCK_LEN,                 // آفست شروع بلاک
        length: this.blockLen(this._torrent, pieceIndex, i) // طول بلاک
      };
      this._queue.push(pieceBlock);
    }
  }

  deque() { return this._queue.shift(); }  // خروج از صف
  peek() { return this._queue[0]; }        // نگاه به اول صف
  length() { return this._queue.length; }  // طول صف
};

حالا صف فهرستی از آبجکت‌های pieceBlock است. قبول دارم اصطلاحات کمی گیج‌کننده شده اما منظورم آبجکتی است که در متد queue ساخته می‌شود و خاصیت‌های index، begin و length دارد. این آبجکت‌های pieceBlock همان ساختار payload هنگام فرستادن پیام درخواست را دارند (به تابع buildRequest در message.js نگاه کنید)، پس می‌توانیم مستقیماً به سازنده درخواست پاس‌شان دهیم.

به‌طور کلی‌تر، از این به بعد می‌خواهیم با این آبجکت‌ها سر و کار داشته باشیم نه اندیس قطعه، چون اطلاعاتی هم درباره بلاک به ما می‌دهند. در اینجا طرحی از اینکه کجا/کی از این آبجکت‌ها استفاده می‌کنیم داریم:

  • وقتی پیام «have» دریافت می‌کنیم، یک اندیس قطعه می‌گیریم، اما صف را با این آبجکت‌های قطعه پر می‌کنیم، برای هر بلاکِ هر قطعه یکی.
  • وقتی آبجکتی را از صف خارج می‌کنیم می‌توانیم به سازنده درخواست پاس‌اش دهیم و برای بلاک مربوطه درخواست بدهیم.
  • کلاس Pieces که قطعه‌های درخواست‌شده و دریافت‌شده را ردیابی می‌کند باید بتواند یک pieceBlock اضافه کند. پیاده‌سازی‌اش را بعداً می‌بینیم.

توجه کنید که سازنده حالا باید یک آبجکت تورنت بگیرد، نه فقط تعداد قطعه‌ها.

متغیرهای خصوصی را با زیرخط (underscore) شروع می‌کنم و متدهای دیگر فقط متدهای عمومی برای تعامل با متغیر خصوصی _queue هستند. choked را بدون زیرخط گذاشتم تا نشان دهم خاصیت عمومی است. اگر با خاصیت‌های خصوصی و عمومی آشنا نیستید، اهمیت چندانی ندارد. ایده این است که کاربران این ماژول نباید از خاصیت‌های با زیرخط استفاده کنند.

اینجا کلاس Pieces است که برای مدیریت بلاک‌ها تغییر کرده:

Pieces.js:

js'use strict';

const tp = require('./torrent-parser');

module.exports = class {
  constructor(torrent) {
    // ساخت آرایه‌ای از آرایه‌ها: برای هر قطعه، آرایه‌ای از بلاک‌هایش
    function buildPiecesArray() {
      const nPieces = torrent.info.pieces.length / 20; // تعداد کل قطعه‌ها
      const arr = new Array(nPieces).fill(null);
      return arr.map((_, i) => new Array(tp.blocksPerPiece(torrent, i)).fill(false));
    }

    this._requested = buildPiecesArray(); // وضعیت بلاک‌های درخواست‌شده
    this._received = buildPiecesArray();  // وضعیت بلاک‌های دریافت‌شده
  }

  addRequested(pieceBlock) {
    const blockIndex = pieceBlock.begin / tp.BLOCK_LEN;
    this._requested[pieceBlock.index][blockIndex] = true;
  }

  addReceived(pieceBlock) {
    const blockIndex = pieceBlock.begin / tp.BLOCK_LEN;
    this._received[pieceBlock.index][blockIndex] = true;
  }

  needed(pieceBlock) {
    // اگر همه چیز درخواست شده اما بعضی دریافت نشده، اجازه درخواست دوباره بده
    if (this._requested.every(blocks => blocks.every(i => i))) {
      this._requested = this._received.map(blocks => blocks.slice());
    }
    const blockIndex = pieceBlock.begin / tp.BLOCK_LEN;
    return !this._requested[pieceBlock.index][blockIndex];
  }

  isDone() {
    return this._received.every(blocks => blocks.every(i => i));
  }
};

حالا آرایه‌های requested و received که قبلاً وضعیت یک اندیس قطعه را نگه می‌داشتند، حالا آرایه‌ای از آرایه‌ها را نگه می‌دارند که آرایه داخلی وضعیت یک بلاک در یک اندیس قطعه مشخص را نگه می‌دارد. پس اگر می‌خواستید وضعیت بلاک اندیس ۱ از قطعه اندیس ۷ را بفهمید، می‌توانید _requested[7][1] را نگاه کنید و ببینید true هست یا نه. مثل قبل، همه مقادیر اولیه false هستند.

همچنین توجه کنید که این متدها انتظار دارند یک pieceBlock پاس بگیرند، همان‌هایی که در کلاس Queue دیدیم. یعنی وقتی یک pieceBlock را از صف برمی‌داریم (peek) و درخواستش می‌کنیم، یا وقتی دریافتش کردیم از صف خارجش می‌کنیم (deque)، می‌توانیم همان pieceBlock را مستقیم به ترتیب به addRequested یا addReceived پاس دهیم.

در نهایت چند تغییر هم در download.js لازم است جایی که از کلاس‌های Queue و Pieces استفاده می‌کنیم.

function requestPiece(socket, pieces, queue) {
  if (queue.choked) return null; // اگر خفه هستیم، درخواستی نده

  while (queue.length()) {
    const pieceBlock = queue.deque();     // بیرون کشیدن بلاک بعدی
    if (pieces.needed(pieceBlock)) {      // اگر به آن نیاز داریم
      socket.write(message.buildRequest(pieceBlock)); // درخواست بلاک
      pieces.addRequested(pieceBlock);
      break;
    }
  }
}

۴.۱۰.۳ have و bitfield

این دو پیام تقریباً کار یکسانی انجام می‌دهند؛ به ما می‌گویند همتا کدام قطعه‌ها را برای اشتراک دارد. با پیام «have» شروع می‌کنیم.

download.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

function haveHandler(socket, pieces, queue, payload) {
  const pieceIndex = payload.readUInt32BE(0); // اندیس قطعه
  const queueEmpty = queue.length === 0;      // آیا صف خالی بود؟
  queue.queue(pieceIndex);                    // افزودن قطعه به صف
  if (queueEmpty) requestPiece(socket, pieces, queue); // اگر اولین آیتم بود، درخواست شروع شود
}

این اندیس قطعه را به صف اضافه می‌کند. همچنین می‌خواهیم اگر این اولین آیتم اضافه‌شده به صف است، فرایند درخواست قطعه را شروع کنیم. چرا فقط اولین؟ چون همان‌طور که قبلاً بحث کردیم، می‌خواهیم قبل از درخواست قطعه بعدی، منتظر برگشتن پاسخ قطعه بمانیم.

حالا bitfieldHandler را ببینیم:

download.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

function bitfieldHandler(socket, pieces, queue, payload) {
  const queueEmpty = queue.length === 0;
  payload.forEach((byte, i) => {
    // هر بایت ۸ بیت است؛ هر بیت نشان‌دهنده یک قطعه
    for (let j = 0; j < 8; j++) {
      if (byte % 2) queue.queue(i * 8 + 7 - j); // اگر بیت ۱ بود، همتا آن قطعه را دارد
      byte = Math.floor(byte / 2);
    }
  });
  if (queueEmpty) requestPiece(socket, pieces, queue);
}

payload اینجا یک بافر است که می‌توانید مثل یک رشته بلند از بیت‌ها به آن فکر کنید. اگر همتا قطعه اندیس-۰ را داشته باشد، بیت اول ۱ است. اگر نه، ۰ است. اگر قطعه اندیس-۱ را داشته باشند، بیت بعدی ۱ است، وگرنه ۰. و الی آخر. پس به راهی برای خواندن بیت‌های منفرد از بافر نیاز داریم.

نمی‌خواهم زیادی روی این بخش مکث کنم. فکر می‌کنم تمرین خوبی است که خواننده خودش امتحان کند. اساساً تقسیم مکرر بر ۲ و گرفتن باقی‌مانده، یک عدد مبنای ۱۰ را به عدد دودویی تبدیل می‌کند و رقم‌های عدد دودویی را از کم‌ارزش‌ترین بیت به پرارزش‌ترین (راست به چپ) به شما می‌دهد.

دقیقاً مثل haveHandler اندیس قطعه را صف می‌کنیم و فقط وقتی اولین قطعه را به صف اضافه می‌کنیم درخواست می‌دهیم.

۴.۱۰.۴ مدیریت‌کننده پاسخ قطعه (Piece response handler)

این آخرین بخش قبل از اینکه بتوانیم دانلود تورنت را شروع کنیم! فقط باید pieceHandler را بنویسیم که برای وقتی است که بایت‌های واقعی قطعه‌ای را که درخواست کرده‌ایم دریافت می‌کنیم.

کارهای اصلی که می‌خواهیم در این تابع انجام دهیم:

  1. قطعه را به فهرست قطعه‌های دریافت‌شده اضافه کنیم.
  2. بایت‌ها را روی فایل بنویسیم.
  3. قطعه بعدی موردنیاز را درخواست کنیم. یا... اگر قطعه دیگری برای دانلود در صف نمانده، اتصال سوکت را ببندیم.

download.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

function pieceHandler(socket, pieces, queue, torrent, pieceResp) {
  pieces.addReceived(pieceResp); // ثبت قطعه به‌عنوان دریافت‌شده

  // اینجا روی فایل بنویس...

  if (pieces.isDone()) {           // اگر همه قطعه‌ها دریافت شد
    socket.end();                  // بستن اتصال
    console.log('DONE!');          // تمام!
  } else {
    requestPiece(socket, pieces, queue); // درخواست قطعه بعدی
  }
}

پاسخ را pieceResp می‌نامم. کمی با pieceBlock فرق دارد چون به‌جای طول قطعه، داده واقعی قطعه را دارد. اما خاصیت‌های index و begin یکی هستند، پس می‌توانید به‌طور عادی به pieces.addReceived پاس‌اش دهید. همچنین می‌توانیم از متد pieces.isDone استفاده کنیم تا بررسی کنیم کار تمام شده یا نه. اگر تمام شده سوکت را می‌بندیم، وگرنه قطعه بعدی را درخواست می‌کنیم.

تنها کاری که حالا باید بکنیم نوشتن بایت‌ها روی فایل است. می‌توانیم با ماژول fs و با متد fs.openSync یک فایل باز کنیم. این یک توصیف‌گر فایل (file descriptor) برمی‌گرداند که به متد fs.write پاس می‌دهیم. چون می‌خواهیم همه همتاها روی یک فایل یکسان بنویسند، ساخت توصیف‌گر فایل یکی از اولین کارهایی است که باید بکنیم:

download.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

module.exports = (torrent, path) => {

متد openSync یک مسیر فایل می‌گیرد (شامل نام فایل)، جایی که فایل ساخته می‌شود. توجه کنید که این تابع export شده حالا یک آرگومان دوم path می‌گیرد. بعد از «w» یا حالت نوشتن (write) برای ساخت یک فایل جدید و نوشتن در آن استفاده می‌کنیم. می‌توانید این کد را طوری تغییر دهید که دانلودها از سر گرفته شوند (resume) به‌جای بازنویسی داده‌های قبلی، اما فعلاً همه‌چیز را ساده نگه می‌داریم. این توصیف‌گر فایل باید تا تابع pieceHandler پاس داده شود.

تابع نهایی pieceHandler باید شبیه این باشد:

download.js:

js// برخی کدها برای صرفه‌جویی در فضا حذف شده‌اند

function pieceHandler(socket, pieces, queue, torrent, file, pieceResp) {
  console.log(pieceResp);
  pieces.addReceived(pieceResp); // ثبت قطعه به‌عنوان دریافت‌شده

  // محاسبه آفست مطلق از ابتدای فایل
  const offset = pieceResp.index * torrent.info['piece length'] + pieceResp.begin;
  fs.write(file, pieceResp.block, 0, pieceResp.block.length, offset, () => {});

  if (pieces.isDone()) {
    console.log('DONE!');         // همه قطعه‌ها دریافت شد
    socket.end();                 // بستن اتصال
    try { fs.closeSync(file); } catch (e) {} // بستن فایل
  } else {
    requestPiece(socket, pieces, queue); // درخواست قطعه بعدی
  }
}

چون pieceResp.begin فقط آفست را نسبت به قطعه‌ای که در آن است به ما می‌گوید، باید آفست مطلق را خودمان حساب کنیم. بعد فقط بلوک داده را روی توصیف‌گر فایلی که قبلاً ساختیم می‌نویسیم. تمام!

۵. نتیجه‌گیری

در این آموزش یک کلاینت بیت‌تورنت کامل را از صفر در node.js ساختیم: فایل تورنت را با بنکد باز کردیم، با ترکر UDP دست دادن کردیم و فهرست همتاها را گرفتیم، با همتاها اتصال TCP برقرار کردیم، پیام‌های peer wire را رد و بدل کردیم، قطعه‌ها و بلاک‌ها را مدیریت کردیم و در نهایت فایل‌های دانلودشده را روی دیسک نوشتیم.

۵.۱ بهبودها

در حال حاضر فقط می‌توانیم فایل‌های تکی را دانلود کنیم، نه فایل‌های داخل پوشه. این کار سخت‌گیری برای پیاده‌سازی نیست. فقط باید آبجکت تورنت را بررسی کنید تا ببینید ساختار فایل چگونه است و شروع و پایان هر فایل کجاست. در واقع هنوز مشکلات جالب زیادی وجود دارد که می‌توانید برای پرداخت این پروژه رویشان کار کنید. اینجا یک فهرست است:

  • افزودن رابط کاربری گرافیکی
  • بهینه‌سازی برای سرعت دانلود بهتر و مصرف کارآمدتر CPU. مثلاً بعضی کلاینت‌ها محاسبه می‌کنند کدام قطعه‌ها کمیاب‌ترین هستند و اول همان‌ها را دانلود می‌کنند.
  • چیزی به نام جدول‌های هش توزیع‌شده (distributed hash tables) هم وجود دارد که به اشتراک گذاشتن تورنت‌ها را بدون استفاده از ترکرهای متمرکز ممکن می‌کند.
  • می‌توانید کدی بنویسید که اتصال‌های افتاده را دوباره وصل کند
  • می‌توانید به‌طور دوره‌ای همتاهای بیشتری جستجو کنید
  • می‌توانید از توقف و ادامه (pause/resume) دانلود پشتیبانی کنید
  • می‌توانید از آپلود پشتیبانی کنید چون فعلاً کلاینت ما فقط دانلود می‌کند
  • بعضی وقت‌ها همتاها نمی‌توانند به یکدیگر متصل شوند چون پشت یک NAT هستند که یک IP پروکسی می‌دهد. می‌توانید راهبردهای گذر از NAT (NAT traversal) را بررسی کنید
  • می‌توان بیت‌تورنت را با WebRTC به وب آورد که یک اتصال مستقیم همتا به همتا می‌سازد
