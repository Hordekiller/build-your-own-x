معرفی کارگاه

بیشتر ما هر روز از یک شل استفاده می‌کنیم، اما آن را بدیهی می‌دانیم و نمی‌دانیم (و اهمیت نمی‌دهیم) که چطور کار می‌کند. این کارگاه با ساخت یک شل شخصی، کمی به درون آن سر می‌کشد. تمرکز بر نحوهٔ راه‌اندازی فرایندها و کنترل ورودی/خروجی آن‌ها با pipe است؛ چیزهایی مثل گسترش متغیرهای محیطی و مدیریت سیگنال را عمداً کنار می‌گذارد و در پایان پیشنهادهایی برای ادامه می‌دهد.

قانون ۰: «هیچ علاقه‌ای به درگیر شدن با جزئیات به‌هم‌ریخته نداریم»: مدیریت حافظه، تجزیه و توکن‌سازی و مدیریت خطای «حرفه‌ای» — برای همین یک تابع آمادهٔ parse_command در اسکلت پروژه هست. توصیهٔ مهم: حتماً از یک سیستم کنترل نسخه استفاده کنید و مرتب commit بگیرید.

تمرین‌ها — قدم به قدم

۱. نام شل و خواندن ورودی

مهم‌ترین کار اول، انتخاب نام برای شل و اعلان (prompt) آن است؛ نویسنده هنگام ساخت کارگاه heeee> را انتخاب کرده بود! اولین تمرین: حلقهٔ اصلی شل را بنویسید که مدام خطی از کاربر بگیرد و تا حالا فقط آن را چاپ کند (شلی که شبیه cat شخصی‌سازی‌شده است):

cchar *line = NULL;
int capacity = 0;
getline(&line, &capacity, stdin);

۲. سیستم‌کال‌ها

برای اجرای دستور به کمک هسته نیاز داریم: برنامه با هسته از طریق سیستم‌کال‌ها حرف می‌زند؛ مثل باز کردن فایل (open)، خواندن/نوشتن (read/write)، ارسال داده از شبکه (sendto/recvfrom) و شروع برنامه (execve). تقریباً هر تعامل برنامه با «دنیای واقعی» یک سیستم‌کال است. برای ما، اجرای برنامه یعنی سیستم‌کال execve با wrapper ای به‌نام execvp.

۳. اجرای برنامه

هنگام اجرا، برنامه یک آرایهٔ آرگومان به‌نام argv می‌گیرد که طبق قرارداد اولی‌اش نام برنامه است؛ برای ls -l /tmp آرایه برابر {"ls", "-l", "/tmp"} است. تمرین ۲: بعد از خواندن خط، دستور را با آرگومان‌هایش اجرا کنید. چیزی غیرمنتظره پیش آمد؟

۴. fork — چرا شل‌تان «دود شد»؟

در تمرین قبل، بعد از پایان برنامه، به اعلان شل‌تان برنگشتید و مستقیم به شل معمولی پرت شدید! چون exec فرایند فعلی را تبدیل به دستور می‌کند — یعنی شل با ls جایگزین شد. راه‌حل، سیستم‌کال fork است: فرایندی جدید می‌سازد که کلونِ فرایند فعلی است (حتی در همان نقطهٔ اجرای برنامه). بعد در فرزندِ تازه‌ساخته exec را صدا می‌زنیم و شل زنده می‌ماند. مقدار بازگشتی fork می‌گوید کجا هستیم: 0 یعنی فرزند، و شناسهٔ فرایند یعنی والد.

cpid_t pid = fork();
if (pid == 0) {
    /* فرزند: اجرای برنامه */
    execvp(args[0], args);
} else {
    /* والد: کاری ندارد، فقط منتظر می‌ماند */
}

۵. انتظار برای فرزند

تمرین ۴: قبل از برگشتن به اعلان، با wait(NULL) منتظر فرزند شوید. حالا شل‌تان دارد واقعی رفتار می‌کند! (نویسنده عاشق cowsay است.)

چرا cd باید builtin باشد؟

توالی pwd ← cd .. ← pwd احتمالاً شما را شگفت‌زده کرد. هر فرایند حافظهٔ خودش و فراداده‌ای دارد که هسته نگه می‌دارد و فقط با سیستم‌کال می‌تواند تغییرش دهد: شناسهٔ کاربر (setuid)، گروه (setgid)، اولویت (setpriority) و دایرکتوری کاری (chdir). اگر /bin/cd را با fork/exec اجرا کنیم: والد دایرکتوری‌اش را عوض نمی‌کند، فقط فرزند که می‌میرد! یک فرایند فقط می‌تواند وضعیت خودش را تغییر دهد. پس خودِ شل باید chdir را صدا بزند: یعنی cd باید builtin باشد.

c/* تمرین ۶: افزودن builtin به نام cd */
if (strcmp(cmd->argv[0], "cd") == 0) {
    chdir(cmd->argv[1]);
}

بقیهٔ builtin ها را با man builtin ببینید؛ بعضی‌ها (مثل echo) می‌توانند برنامهٔ بیرونی هم باشند ولی برای کارایی (سربار ساخت فرایند) builtin شده‌اند.

پایپ‌لاین‌ها

ls | wc در شل ما خطا می‌دهد چون شل هنوز معنی | را نمی‌داند. در یونیکس، فایل‌ها با فایل‌دسکریپتور مدیریت می‌شوند (در لینوکس: ls -l /proc/<pid>/fd): اعداد صحیح مثبت که ۰=stdin، ۱=stdout، ۲=stderr و از ۳ به بالا فایل‌های دیگر.

سیستم‌کال pipe دو فایل‌دسکریپتور جدید با خاصیت ویژه می‌سازد: هرچه به 5 بنویسید از 4 خوانده می‌شود. برای ls | wc باید stdout لِس به ۵ و stdin دابلیوسی به ۴ برود؛ ابزار این کار سیستم‌کال dup2 است (dup2(5, 1) و dup2(4, 0)).

خلاصهٔ مراحل: (۱) ساخت pipe با pipe؛ (۲) دو بار fork (یکی برای ls و یکی برای wc)؛ (۳) در فرزندِ ls: dup2(pipe_fds[1], 1) و اجرا؛ (۴) در فرزندِ wc: dup2(pipe_fds[0], 0) و اجرا؛ (۵) بستن هر دو سر pipe در فرایند والد:

cint pipe_fds[2];
pipe(pipe_fds);            /* فرض: [4, 5] برمی‌گرداند */

/* تمرین ۷: */
void fork_and_exec_with_io(cmd* cmd, int stdout_fd, int stdin_fd);

/* تمرین ۸: پیاده‌سازی pipe دو عنصری با تابع بالا */
fork_and_exec_with_io(cmd1, pipe_fds[1], STDIN_FILENO);  /* ls → 5 */
fork_and_exec_with_io(cmd2, STDOUT_FILENO, pipe_fds[0]); /* 4 ← wc */
close(pipe_fds[0]);
close(pipe_fds[1]);

ادامه‌های پیشنهادی

  • پایپ‌لاین‌های طولانی‌تر — parse_line هر تعداد دستور پایپ‌شده برمی‌گرداند؛ ادامه با شماست
  • ریدایرکت ورودی/خروجی به فایل (grep shel > /tmp/shel_words) — به‌جای pipe از open استفاده کنید
  • ریدایرکت سایر فایل‌دسکریپتورها — مثل 2>/tmp/errors برای stderr
  • ریدایرکت به فایل‌دسکریپتور دیگر — مثل 2>&1
  • گسترش متغیر محیطی (echo $HOME) با تابع getenv
  • تنظیم متغیر محیطی برای فرزندان — TZ=Pacific/Samoa date با setenv؛ و builtin export (چون فرزند نمی‌تواند محیط والد را عوض کند!)
  • مدیریت سیگنال — فشردن ^C سیگنال SIGINT می‌فرستد؛ می‌توانید handler ثبت کنید تا شل کشته نشود
  • گلابینگ — wc -c * قبل از عبور آرگومان‌ها به فرزند انجام می‌شود؛ با تابع glob از <glob.h>
  • پس‌زمینه — دستوری که با & تمام می‌شود بدون wait روی فرزند اجرا می‌شود
