ساختار دادهٔ اصلی

بزنید بریم سراغ کد. با ساختار دادهٔ اصلی شروع می‌کنیم که یک نمونه از CHIP-8 را برای شبیه‌سازی نگه می‌دارد:

lisp(defstruct chip
  (running t :type boolean)
  ; ...بعداً موارد بیشتری اضافه می‌کنیم
  )

به‌جای کلاس CLOS از ساختار (struct) لیسپی استفاده می‌کنیم چون قرار است *خیلی زیاد* به فیلدهای این ساختار دسترسی داشته باشیم و accessorهای CLOS نسبتاً کند هستند. این یکی از معدود امتیازهایی است که به عملکرد می‌دهیم.

اولین فیلد، running است: یک بولین که نشان می‌دهد شبیه‌ساز در حال اجراست یا نه.

در نهایت چند رشتهٔ هم‌زمان (thread) با این ساختار کار می‌کنند و معمولاً کاری مثل (loop :while (chip-running chip) :do ...) انجام می‌دهند. به این ترتیب وقتی بخواهیم شبیه‌ساز را ببندیم فقط کافیست running را nil کنیم و همه‌چیز (در نهایت) متوقف می‌شود.

رجیسترها

CHIP-8 شانزده رجیستر اصلی دارد و همچنین چند رجیستر ویژهٔ دیگر:

lisp(defstruct chip
  ; ...
  (registers (make-array 16 :element-type 'int8)
             :type (simple-array int8 (16))
             :read-only t)
  (index 0 :type int16)
  (program-counter #x200 :type int12)
  ; ...
  )

رجیسترهای اصلی را در یک آرایه نگه می‌داریم و بقیه فقط slotهای جدا هستند. اعلام نوع (type declaration) در ساختار را به دو دلیل اضافه کرده‌ام:

  • با اعلام safety بالا، بسیاری از پیاده‌سازی‌ها (از جمله SBCL که من استفاده می‌کنم) در زمان اجرا چک نوع انجام می‌دهند تا مطمئن شوند مقدارها درست تنظیم می‌شوند.
  • با safety پایین و speed بالا، SBCL می‌تواند اگر نوع slotهای ساختار را بداند، کد خیلی سریع‌تری تولید کند.

برای خلاصه‌تر کردن نام نوع‌های اعداد صحیح، چند مترادف ساده تعریف کرده‌ام:

lisp(deftype int4 () '(unsigned-byte 4))
(deftype int8 () '(unsigned-byte 8))
(deftype int12 () '(unsigned-byte 12))
(deftype int16 () '(unsigned-byte 16))

پس registers یک آرایهٔ سادهٔ ۱۶ عنصری از (unsigned-byte 8) است. read-only است چون قرار است *عناصر* آرایه را تغییر دهیم، اما هرگز نباید کل آرایه را با آرایهٔ دیگری عوض کنیم.

رجیستر index ۱۶ بیتی است و برنامه‌شمار (program counter) می‌تواند تا ۱۲ بیت را نگه دارد (به دلیل اندازهٔ حافظهٔ CHIP-8 هرگز بیشتر از این نیاز نمی‌شود).

همچنین توجه کنید که برنامه‌شمار از آدرس #x200 شروع می‌شود؛ چون ROM در نهایت در همان آدرس از حافظهٔ CHIP-8 بارگذاری می‌شود.

پشته (Stack)

CHIP-8 همچنین یک پشتهٔ داخلی برای نگهداشتن آدرس‌های بازگشت هنگام فراخوانی زیربرنامه‌ها دارد. برای این کار فقط از یک بردار لیسپی با fill pointer استفاده می‌کنیم:

lisp(defstruct chip
  ; ...
  (stack (make-array 16 :element-type 'int12 :fill-pointer 0)
         :type (vector int12 16)
         :read-only t)
  ; ...
  )

حافظه

CHIP-8 چهار کیلوبایت حافظهٔ اصلی دارد:

lisp(defconstant +memory-size+ (* 1024 4))

(defstruct chip
  ; ...
  (memory (make-array +memory-size+ :element-type 'int8)
          :type (simple-array int8 (#.+memory-size+))
          :read-only t)
  ; ...
  )

خیلی ساده. به ترفند/هک ماکروی خوانندهٔ #. توجه کنید که با آن می‌توانیم جایی که معمولاً به مشخص‌گر نوع خام نیاز داریم از متغیر استفاده کنیم.

ROM بارگذاری‌شدهٔ فعلی

در آخر، یک slot برای نگهداشتن مسیر ROM فعلی اضافه می‌کنیم تا بعداً ریست‌کردن آسان شود:

lisp(defstruct chip
  ; ...
  (loaded-rom nil :type (or null string))
  ; ...
  )

فعلاً همین کافی است. بعداً که به گرافیک و صدا برسیم به slotهای بیشتری نیاز خواهیم داشت؛ اما آن‌ها را وقتی نیاز شد معرفی می‌کنم.

رجیستر پرچم (Flag)

رجیستر شمارهٔ ۱۵، یا #xF در مبنای ۱۶، ویژه است. به آن رجیستر «پرچم» می‌گویند و بعضی دستورالعمل‌ها آن را به‌صورت ویژه تنظیم می‌کنند. می‌توانستیم مثل بقیهٔ رجیسترها به آن دسترسی داشته باشیم:

lisp(setf (aref (chip-registers chip) 15) 1) ; پرچم را ۱ کن
(print (aref (chip-registers chip) #xF)) ; پرچم را چاپ کن

اما حتی با ایندکس هگز #xF برای یادآوری «F»، این کار کمی سخت‌خوان است. بیایید چند تابع خواننده و نویسندهٔ اضافه تعریف کنیم:

lisp(defun-inline chip-flag (chip)
  (aref (chip-registers chip) #xF))

(defun-inline (setf chip-flag) (new-value chip)
  (setf (aref (chip-registers chip) #xF) new-value))

defun-inline از کتابخانهٔ ابزار من است — در یک قدم هم defun می‌کند هم declaim آن را inline می‌کند. حالا همه‌چیز خیلی بهتر خوانده می‌شود:

lisp(setf (chip-flag chip) 1) ; پرچم را ۱ کن
(print (chip-flag chip)) ; پرچم را چاپ کن

حذف تکرار

آنچه تا اینجا داریم *کار می‌کند*، اما قبل از ادامه می‌خواهم یک قند اضافهٔ نحوی (syntactic sugar) هم اضافه کنم.

قرار است خیلی زیاد به slotهای ساختار chip دسترسی داشته باشیم و تکراری‌شدنِ نوشتن (chip-SLOT chip) خسته‌کننده می‌شود. مثلاً هنگام ریست‌کردن شبیه‌ساز مجبوریم کاری شبیه این بکنیم:

lisp(defun reset (chip)
  (fill (chip-memory chip) 0)
  (fill (chip-registers chip) 0)
  (setf (chip-running chip) t
        (chip-program-counter chip) #x200
        (fill-pointer (chip-stack chip)) 0))

این آزاردهنده است. زبان‌هایی مثل جاوااسکریپت و پایتون برای دسترسی به slot از . استفاده می‌کنند و در نتیجه جمع‌وجورتر می‌شود: chip.memory() به‌جای (chip-memory chip).

می‌توانستیم از with-accessors لیسپ برای تمیزکردن استفادهٔ واقعی استفاده کنیم:

lisp(defun reset (chip)
  (with-accessors ((memory chip-memory)
                   (registers chip-registers)
                   (running chip-running)
                   (program-counter chip-program-counter)
                   (stack chip-stack))
      chip
    (fill memory 0)
    (fill registers 0)
    (setf running t
          program-counter #x200
          (fill-pointer stack) 0)))

استفاده اکنون خیلی بهتر است اما چیزی را واقعاً درست نکرده‌ایم؛ فقط تایپ‌کردن را چند خط بالا بردیم. اما این لیسپ است؛ ما بهتر از این می‌توانیم!

ایده‌آل این است که بتوانیم چیزی مثل (with-chip (chip) ...) بنویسیم تا همان فرم بزرگِ with-accessors را درست کند:

lisp(defun reset (chip)
  (with-chip (chip)
    (fill memory 0)
    (fill registers 0)
    (setf running t
          program-counter #x200
          (fill-pointer stack) 0)))

این تمیز و خوانا است. بعضی‌ها ممکن است از اینکه این ماکرو bindingهای متغیر جدیدی معرفی می‌کند که در تعریف ماکرو «پنهان» هستند خوششان نیاید، اما من جمع‌وجوریِ حاصل را دوست دارم، مخصوصاً برای یک پروژهٔ کوچک مثل این.

می‌توانستیم with-chip را خودمان بنویسیم؛ چیزی شبیه این:

lisp(defmacro with-chip ((chip) &body body)
  `(with-accessors ((memory chip-memory)
                    (registers chip-registers)
                    ; ...
                    )
       ,chip
     ,@body)
)

نوشتنش سخت نیست، فقط خسته‌کننده است. اما چون از لیسپ استفاده می‌کنیم، هر چیز خسته‌کننده‌ای طلب انتزاع می‌کند! یک ماکروی دیگر از کتابخانهٔ ابزار من به نام define-with-macro وجود دارد؛ ماکرویی که ماکرو می‌سازد و با آن می‌توانیم with-chip را برای خودمان تعریف کنیم:

lisp(define-with-macro chip
  running memory stack registers index program-counter flag)

اگر پیچیدگی ماکرویِ ماکروساز شما را می‌ترساند، نگران نباشید. می‌توانستیم همان‌طور که در بالا نشان داده شد با دست هم بنویسیمش. فقط به‌اندازهٔ کافی از این ماکروهای with-FOO استفاده کرده‌ام که ارزشش را داشته باشد تا از خسته‌کنندگیِ نوشتن‌شان انتزاع بسازم.

خلاصه، حالا یک ماکروی خوب with-chip داریم که با آن می‌توانیم با نام‌های عریان به فیلدهای ساختار دسترسی داشته باشیم.

زیرساخت

قبل از اینکه سراغ پیاده‌سازی دستورالعمل‌های CPU برویم، باید کمی زیرساخت برای اجرای کارها تعریف کنیم.

ریست‌کردن

قبل از اینکه بتوانیم یک ROM را شبیه‌سازی کنیم، باید آن را در آرایهٔ حافظه‌مان بخوانیم. من تصمیم گرفتم این کار را داخل تابع reset انجام دهم تا بتوانیم فقط با (reset my-chip) همه‌چیز را یکجا دوباره بارگذاری کنیم — منطقی نیست بدون ریست‌کردن بقیهٔ وضعیت شبیه‌سازی، ROM جدیدی بارگذاری کنیم (اگرچه نتیجه می‌توانست «جالب» باشد).

reset این شکلی است:

lisp(defun reset (chip)
  (with-chip (chip)
    (fill memory 0)
    (fill registers 0)
    (replace memory (read-file-into-byte-vector loaded-rom)
             :start1 #x200)
    (setf running t
          program-counter #x200
          (fill-pointer stack) 0))
  (values))

این بخش خود توضیح است، به‌جز بخش بارگذاری ROM:

lisp(replace memory (read-file-into-byte-vector loaded-rom)
         :start1 #x200)

replace همان تابع استاندارد replace لیسپ است که محتوای یک توالی را در توالی دیگر کپی می‌کند. read-file-into-byte-vector از Alexandria است و فایلِ loaded-rom را در یک بردار بایتی می‌خواند. سپس فقط کافیست بگوییم کپی‌کردن از ایندکس #x200 در مقصد شروع شود، چون دادهٔ ROM قرار است از آنجا شروع شود (قبل از آن دادهٔ داخلی دیگری مثل اسپرایت‌های فونت وجود دارد که بعداً می‌بینیم).

یک نکتهٔ آخر: reset فقط (values) برمی‌گرداند، یعنی اصلاً چیزی برنمی‌گرداند. این کاری است که گاهی برای توابعی که در REPL به خاطر عوارض جانبی صدا می‌زنم انجام می‌دهم تا از برگرداندن یک نتیجهٔ بی‌معنی جلوگیری کنم.

بارگذاری ROM

حالا که تابع ریست داریم، تعریف تابعی برای بارگذاری ROM جدید بی‌دردسر است:

lisp(defun load-rom (chip filename)
  (setf (chip-loaded-rom chip) filename)
  (reset chip))

اینجا زحمت with-chip را به خودم ندادم چون فقط به یک فیلد دسترسی داریم.

حلقهٔ اصلی

حالا همه‌چیز را در یک رابط تمیز جمع کنیم. یک تابع سطح‌بالای run تعریف می‌کنیم که برای روشن کردن شبیه‌ساز آن را صدا می‌زنیم:

lisp(defparameter *c* nil)

(defun run (rom-filename)
  (let ((chip (make-chip)))
    (setf *c* chip)
    (load-rom chip rom-filename)
    (run-cpu chip)))

این در آینده پیچیده‌تر می‌شود، اما فعلاً خیلی ساده است: یک شیء chip جدید می‌سازیم، ROM مشخص‌شده را بارگذاری می‌کنیم و شبیه‌سازی CPU را شروع می‌کنیم.

یک متغیر سراسری *c* اضافه کرده‌ام که به شبیه‌ساز در حال اجرا اشاره می‌کند تا بتوانیم در حالی که اجرا می‌شود از NREPL یا SLIME به آن دست بزنیم.

حالا run-cpu را بنویسیم:

lisp(defconstant +cycles-per-second+ 500)
(defconstant +cycles-before-sleep+ 10)

(defun run-cpu (chip)
  (iterate
    (while (chip-running chip))
    (emulate-cycle chip)
    (for tick :every-nth +cycles-before-sleep+ :do
         (sleep (/ +cycles-before-sleep+ +cycles-per-second+)))))

CHIP-8 برای اجرا روی سخت‌افزارهای بسیار ضعیف‌تر از سخت‌افزارهای امروزی طراحی شده بود. حتی با اینکه شبیه‌سازی می‌کنیم، اگر تا حد ممکن سریع اجرا کنیم، آن‌قدر سریع خواهد بود که قابل بازی نباشد.

+cycles-per-second+ ثابتی است که سرعت ایده‌آل شبیه‌سازی را توصیف می‌کند. هر عددی از ۳۰۰ تا ۸۰۰ بسته به سرعت مورد نظرتان برای بازی‌ها قابل بازی است. فعلاً ۵۰۰ را به عنوان حد وسط انتخاب می‌کنیم.

هدر دادن اینکه بعد از هر چرخه (sleep) صدا بزنیم، اسراف است؛ بنابراین آن‌ها را دسته‌بندی می‌کنیم: ۱۰ دستورالعمل را اجرا کن، کمی بخواب، تکرار. این وظیفهٔ driver (for ... every-nth N) از iterate است که در کتابخانهٔ ابزار من هم هست. هر ۱۰ بار تکرارِ حلقه، به اندازهٔ مناسب می‌خوابد.

اندازهٔ دسته‌های چرخه دلخواه است — دسته‌های بزرگ‌تر یعنی فراخوانی‌های (sleep) کمتر، اما اگر خیلی بزرگ شوند متوجه «پرشی» شدن شبیه‌ساز می‌شوید. دستهٔ ۱۰ چرخه‌ای با سرعت ۵۰۰ چرخه در ثانیه یعنی شبیه‌ساز هر بار حدود ۱/۵۰ ثانیه می‌خوابد که خیلی محسوس نیست.

حلقهٔ اصلی آماده است و فقط باید هر چرخه را شبیه‌سازی کنیم.

چرخه‌های منفرد

هر دستورالعمل CHIP-8 دو بایت است و به‌صورت big-endian در حافظه ذخیره می‌شود. پس برای شبیه‌سازی یک چرخه:

  • دو بایتِ شروع‌شده از برنامه‌شمار را می‌خوانیم و آن‌ها را به هم می‌چسبانیم تا دستورالعمل ساخته شود.
  • برنامه‌شمار را جلو می‌بریم (تا مجبور نباشیم داخل هر دستورالعمل انجامش دهیم).
  • به کد مناسبِ دستورالعمل dispatch می‌کنیم.

emulate-cycle و چند تابع کمکی تعریف می‌کنیم:

lisp(defun-inline chop (size integer)
  (ldb (byte size 0) integer))

(defun-inline cat-bytes (high-order low-order)
  (dpb high-order (byte 8 8) low-order))

(defun emulate-cycle (chip)
  (with-chip (chip)
   (let ((instruction (cat-bytes (aref memory program-counter)
                                 (aref memory (1+ program-counter)))))
     (zapf program-counter (chop 12 (+ % 2)))
     (dispatch-instruction chip instruction))))

chop یک عدد صحیح را به تعداد بیت مشخص‌شده برش می‌دهد. cat-bytes دو بایت را به هم می‌چسباند. خیلی ساده‌اند، اما من نام‌های توصیفی را به نوشتن dpb (deposit byte) و ldb (load byte) در همه‌جا ترجیح می‌دهم.

zapf از کتابخانهٔ ابزار من است و درباره‌اش پست جداگانه‌ای نوشته‌ام.

وقتی برنامه‌شمار به ایندکس آخر حافظه رسید چه اتفاقی می‌افتد؟ هیچ‌کدام از مراجع CHIP-8 مشخص نکرده‌اند. می‌توانیم خطا صادر کنیم یا فقط به صفر برگردانیم. من دومی را انتخاب کرده‌ام با برش‌زدن (+ program-counter 2) به ۱۲ بیت؛ اما صدور خطا هم آسان بود.

Dispatch دستورالعمل

طرح دستورالعمل‌های CHIP-8 کمی با بیشتر سیستم‌های دیگری که دیده‌ام فرق دارد.

در سیستم‌هایی مثل گیم‌بوی، دستورالعمل‌ها یک اپ‌کد یک یا دو بایتی دارند و آرگومان‌ها دنبالش می‌آیند. برای این سیستم‌ها می‌توانید با یک case غول‌آسا dispatch کنید:

lisp(case opcode
  (#x00 (op-foo ...))
  (#x01 (op-bar ...))
  ; ...
  )

اما راه مؤثرتر معمولاً این است که همهٔ توابع op- را در یک آرایه بریزید و خودِ اپ‌کد را ایندکسِ آرایه کنید تا تابع پیدا شود:

lisp(funcall (aref opcodes opcode) ...)

اما CHIP-8 دستورالعمل‌ها را کمی عجیب از هم متمایز می‌کند. همهٔ دستورالعمل‌ها دو بایت‌اند، *از جمله* آرگومان‌هایشان. به‌جای اینکه فقط N بیت اول به عنوان اپ‌کد استفاده شود، بعضی دستورالعمل‌ها ترکیبی از بیت‌های بالا و پایین را به‌کار می‌برند. مثلاً AND و OR و XOR منطقی با شروعِ دستورالعمل با نیبلِ 8 و پایان با 1، 2 یا 3 مشخص می‌شوند، با «آرگومان»ها در دو نیبل وسط:

lisp8xy1 - OR Vx, Vy
8xy2 - AND Vx, Vy
8xy3 - XOR Vx, Vy

این استفاده از نوعی جدول توابع را آزاردهنده می‌کند. فقط چند ده اپ‌کد وجود دارد، بنابراین به‌جای تلاش برای درست‌کردن یک چیزی به‌هم‌چسبیده، از یک case بزرگ و قدیمی استفاده می‌کنیم:

lisp(defun dispatch-instruction (chip instruction)
  (macrolet ((call (name) `(,name chip instruction)))
    (ecase (logand #xF000 instruction)
      (#x0000 (ecase instruction
                (#x00E0 (call op-cls))
                (#x00EE (call op-ret))))
      (#x1000 (call op-jp-imm))
      (#x2000 (call op-call))
      (#x3000 (call op-se-reg-imm))
      (#x4000 (call op-sne-reg-imm))
      (#x5000 (ecase (logand #x000F instruction)
                (#x0 (call op-se-reg-reg))))
      (#x6000 (call op-ld-reg<imm))
      (#x7000 (call op-add-reg<imm))
      (#x8000 (ecase (logand #x000F instruction)
                (#x0 (call op-ld-reg<reg))
                (#x1 (call op-or))
                (#x2 (call op-and))
                (#x3 (call op-xor))
                (#x4 (call op-add-reg<reg))
                (#x5 (call op-sub-reg<reg))
                (#x6 (call op-shr))
                (#x7 (call op-subn-reg<reg))
                (#xE (call op-shl))))
      (#x9000 (ecase (logand #x000F instruction)
                (#x0 (call op-sne-reg-reg))))
      (#xA000 (call op-ld-i<imm))
      (#xB000 (call op-jp-imm+reg))
      (#xC000 (call op-rand))
      (#xD000 (call op-draw))
      (#xE000 (ecase (logand #x00FF instruction)
                (#x9E (call op-skp))
                (#xA1 (call op-sknp))))
      (#xF000 (ecase (logand #x00FF instruction)
                (#x07 (call op-ld-reg<dt))
                (#x0A (call op-ld-reg<key))
                (#x15 (call op-ld-dt<reg))
                (#x18 (call op-ld-st<reg))
                (#x1E (call op-add-index<reg))
                (#x29 (call op-ld-font<vx))
                (#x33 (call op-ld-bcd<vx))
                (#x55 (call op-ld-mem<regs))
                (#x65 (call op-ld-regs<mem)))))))

macrolet در ابتدا کمی تایپ را کم می‌کند، اما بقیه‌اش فقط یک جدول بزرگ و کسل‌کننده برای فهمیدن اینکه کدام دستورالعمل باید صدا زده شود است.

این همهٔ کار زیرساختیِ کسل‌کننده بود — برویم سراغ پیاده‌سازی دستورالعمل‌های واقعی.

دستورالعمل‌ها

CHIP-8 از سی‌وشش دستورالعمل پشتیبانی می‌کند که باید همه را پیاده‌سازی کنیم. از ساده‌ترها شروع می‌کنیم و بعضی دیگر (مربوط به گرافیک/صدا) را برای مقاله‌های بعدی می‌گذاریم.

(در مقابل، گیم‌بوی تقریباً پانصد دستورالعمل دارد؛ پس حالا می‌بینید چرا فکر می‌کردم CHIP-8 ساده‌تر است!)

اعداد تصادفی

با دستورالعمل RND شروع می‌کنیم که عدد تصادفی تولید می‌کند. ممکن است مکان عجیبی برای شروع باشد، اما می‌خواهم یک قند اضافهٔ نحوی دیگر را توضیح بدهم و RND دستورالعمل مناسبی برای مثال است.

مرجع کاگوود RND را این‌گونه توصیف می‌کند:

txtCxkk - RND Vx, byte
Vx = بایت تصادفی AND kk

مفسر عددی تصادفی از ۰ تا ۲۵۵ تولید می‌کند
که سپس با مقدار kk عملیات AND می‌شود. نتیجه
در Vx ذخیره می‌شود.

اولین تلاش برای پیاده‌سازی در لیسپ شاید این شکلی باشد:

lisp(defun op-rand (chip instruction)
  (let ((reg  (logand #x0F00 instruction))
        (mask (logand #x00FF instruction)))
    (with-chip (chip)
      (setf (aref registers reg)
            (logand (random 256) mask)))))

این کار می‌کند، اما برای چیزی که فقط با یکی دو جمله توصیف می‌شود کد زیادی است. قرار است دستورالعمل‌های زیادی تعریف کنیم؛ پس چند دقیقه وقت بگذاریم و زندگی‌مان را آسان‌تر کنیم.

Define-Instruction

یک ماکروی define-instruction می‌سازیم که بخش‌های کسل‌کننده را انتزاعی کند. هدف این است که تعریف دستورالعمل‌ها تا حد ممکن به مستندات نزدیک خوانده شود.

با حذف نیاز به ماکروی with-chip شروع می‌کنیم. هر دستورالعمل باید با ساختار chip کار کند، پس سی‌وشش بار خودمان را تکرار نکنیم. هر دستورالعمل هم آرگومان‌های chip و instruction می‌گیرد؛ پس آن‌ها را هم حذف کنیم:

lisp(defmacro define-instruction (name &body body)
  `(defun ,name (chip instruction)
      (declare (ignorable instruction))
      (with-chip (chip)
        ,@body)
      nil))

(define-instruction op-rand
  (let ((reg  (logand #x0F00 instruction))
        (mask (logand #x00FF instruction)))
    (setf (aref registers reg)
          (logand (random 256) mask))))

کمی بهتر شد. قرار است این دستورالعمل‌ها را خیلی زیاد صدا بزنیم، پس اضافه‌کردن اعلام نوع برای هر تابع ضرری ندارد. چون همه همان نوع‌ها را می‌گیرند و برمی‌گردانند، این کار آسان است:

lisp(defmacro define-instruction (name &body body)
  `(progn
    (declaim (ftype (function (chip int16) null) ,name)) ; جدید
    (defun ,name (chip instruction)
      (declare (ignorable instruction))
      (with-chip (chip)
        ,@body)
      nil)))

حالا همهٔ توابع دستورالعمل‌مان hint نوع دارند و SBCL می‌تواند آن‌ها را چک کند (اگر safety بالا باشد) یا برای تولید کد سریع‌تر استفاده کند (اگر speed بالا باشد).

خیلی زیاد به مقادیر رجیسترها دسترسی خواهیم داشت ((aref registers ...))، پس یک macrolet کوچک اضافه می‌کنیم تا خواندنش بهتر شود:

lisp(defmacro define-instruction (name &body body)
  `(progn
    (declaim (ftype (function (chip int16) null) ,name))
    (defun ,name (chip instruction)
      (declare (ignorable instruction))
      (with-chip (chip)
        (macrolet ((register (index)             ; جدید
                     `(aref registers ,index)))  ; جدید
          ,@body))
      nil)))

(define-instruction op-rand
  (let ((reg  (logand #x0F00 instruction))
        (mask (logand #x00FF instruction)))
    (setf (register reg)                         ; جدید
          (logand (random 256) mask))))

حالا به‌جای (aref registers ...) فقط (register ...) می‌نویسیم.

تنها چیزی که هنوز اذیتم می‌کند این است که باید آرگومان‌های دستورالعمل را با bitmask با دست از دستورالعمل بیرون بکشم. خیلی بهتر بود اگر فقط اعلام می‌کردیم آرگومان‌ها چه شکلی هستند و کامپیوتر کد mask کردن مناسب را برای ما تولید می‌کرد. هدف این است که بتوانیم چیزی مثل این بنویسیم:

lisp(define-instruction op-rand (_ r (mask 2))              ;; RND
  (setf (register r)
        (logand (random 256) mask)))

(_ r (mask 2)) «فهرست آرگومان» دستورالعمل است. می‌گوید:

  • یک مقدار تک‌نیبلی که به آن اهمیت نمی‌دهیم: _
  • یک مقدار تک‌نیبلی که باید به r بایند شود: r
  • یک مقدار دو نیبلی که باید به mask بایند شود: (mask 2)

کد لیسپ و مستندات کاگوود را مقایسه کنید:

txtCxkk - RND Vx, byte
Vx = بایت تصادفی AND kk

(define-instruction op-rand (_ r (mask 2))              ;; RND
  (setf (register r)
        (logand (random 256) mask)))

کاگوود از V به عنوان مخفف register استفاده می‌کند و آرگومان را به‌جای r، x می‌نامد؛ اما به‌جز آن، فکر می‌کنم این کد به‌اندازهٔ کافی به مستنداتِ کدِ واقعیِ در حال اجرا نزدیک است.

پس ماکروی parse آرگومان را پیاده‌سازی کنیم. اگر با ماکروها راحت نیستید از این بخش صرف‌نظر کنید. اما این نمایش خوبی از این است که چطور می‌توانید برای یک پروژهٔ ساده یک زبان تمیز بسازید.

اول body را در یک let می‌پیچیم:

lisp                                   ; جدید
(defmacro define-instruction (name argument-list &body body)
  `(progn
    (declaim (ftype (function (chip int16) null) ,name))
    (defun ,name (chip instruction)
      (declare (ignorable instruction))
      (with-chip (chip)
        (macrolet ((register (index)
                     `(aref registers ,index)))
          (let ,(parse-instruction-argument-bindings argument-list) ; جدید
            ,@body))
        nil))))

برای parse کردن فهرست آرگومان به فهرستی از bindingهای let، به‌جای اینکه همه‌چیز را در همین یک ماکرو بگنجانیم از یک تابع کمکی استفاده می‌کنیم. ممکن است ترسناک به نظر برسد، اما واقعاً بد نیست:

lisp(defun parse-instruction-argument-bindings (argument-list)
  (flet ((normalize-arg (arg)
           (destructuring-bind (symbol &optional (nibbles 1))
               (ensure-list arg)
             (list symbol nibbles))))
    (iterate
      (for (symbol nibbles) :in (mapcar #'normalize-arg argument-list))
      (for position :first 3 :then (- position nibbles))
      (when (not (eql symbol '_))
        (collect `(,symbol (ldb (byte ,(* nibbles 4)
                                      ,(* position 4))
                                instruction)))))))

normalize-arg هر آرگومان را از فهرست می‌گیرد و به (symbol nibbles) تبدیل می‌کند؛ پس لازم نیست طول آرگومان‌های تک‌نیبلی را این‌گونه بنویسیم: ((_ 1) (r 1) (mask 2)).

سپس روی هر جفت (symbol nibbles) در فهرست آرگومان حلقه می‌زنیم. از موقعیت 3 در بایت شروع می‌کنیم (بالاترین نیبل) چون می‌خواهیم فهرست آرگومان را از چپ به راست، از بالا به پایین، مثل مستندات بنویسیم.

برای هر جفت، اگر نماد چیزی غیر از _ بود، یک binding برای let با فراخوانی ldb مناسب جمع می‌کنیم. پس برای مثالِ (_ r (mask 2)) به دو binding می‌رسیم:

lisp(r (ldb (byte 4 8) instruction))
(mask (ldb (byte 8 0) instruction))

توجه کنید که فقط bindingهایی را parse می‌کنیم که *نیاز* داریم. برای دستورالعمل‌هایی که به هیچ آرگومانی نیاز ندارند به یک (let () ...) خالی می‌رسیم که کامپایلر آن را بهینه می‌کند.

این شاید کمی پرمو باشد. نکتهٔ خوبِ استفاده از تابع کمکی این است که می‌توانیم آن را جداگانه با انواع فهرست‌های آرگومان صدا بزنیم تا ببینیم چه چیزی تولید می‌شود:

lisp(map nil #'print
  (parse-instruction-argument-bindings '(_ r (mask 2))))

(R (LDB (BYTE 4 8) INSTRUCTION))
(MASK (LDB (BYTE 8 0) INSTRUCTION))

(map nil #'print
  (parse-instruction-argument-bindings '(_ x y _)))

(X (LDB (BYTE 4 8) INSTRUCTION))
(Y (LDB (BYTE 4 4) INSTRUCTION))

(map nil #'print
  (parse-instruction-argument-bindings '(_ (foo 3))))

(FOO (LDB (BYTE 12 0) INSTRUCTION))

و این هم از define-instruction. پس به‌جای نوشتن RND به عنوان یک تابع معمولی:

lisp(defun op-rand (chip instruction)
  (let ((reg  (logand #x0F00 instruction))
        (mask (logand #x00FF instruction)))
    (with-chip (chip)
      (setf (aref registers reg)
            (logand (random 256) mask)))))

می‌توانیم کار خیلی تمیزتری انجام دهیم:

lisp(define-instruction op-rand (_ r (mask 2))              ;; RND
  (setf (register r)
        (logand (random 256) mask)))

همین که سی‌وپنج دستورالعمل دیگر را پیاده‌سازی کنیم، این سرمایه‌گذاری جواب خواهد داد.

پرش‌ها و فراخوانی‌ها

CHIP-8 دو دستورالعمل برای پرش مستقیم به یک آدرس دارد. اولی به یک آدرس مستقیم (immediate) می‌پرد و دومی یک مقدار immediate را به محتوای رجیستر #x0 اضافه می‌کند و به نتیجه می‌پرد:

lisp(define-instruction op-jp-imm (_ (target 3))            ;; JP addr
  (setf program-counter target))

(define-instruction op-jp-imm+reg (_ (target 3))        ;; JP V0 + addr
  (setf program-counter (chop 12 (+ target (register 0)))))

ماکروی define-instruction ما دارد جوابش را می‌دهد. مقادیر immediate این آرگومان‌ها هر کدام سه نیبل‌اند، اما ماکروی ما به آن اهمیتی نمی‌دهد.

همچنین دو دستورالعمل برای پیاده‌سازی فراخوانی و بازگشت توابع سنتی با پشتهٔ CHIP-8 وجود دارد:

lisp(define-instruction op-call (_ (target 3))              ;; CALL addr
  (vector-push program-counter stack)
  (setf program-counter target))

(define-instruction op-ret ()                           ;; RET
  (setf program-counter (vector-pop stack)))

فقط از توابع داخلی vector-push و vector-pop برای مدیریت fill pointer پشته استفاده می‌کنیم.

توجه کنید که از vector-push-extend استفاده *نمی‌کنیم* چون پشتهٔ CHIP-8 طبق مشخصات فقط می‌تواند حداکثر شانزده آدرس نگه دارد — هر ROMی که بیشتر push کند خراب است.

عدد اعشاری دودویی (BCD)

بریم سراغ یک دستورالعمل مستقل دیگر: BCD که مخفف binary-coded decimal است (بعضی مراجع آن را LD B, Vx می‌نامند، اما فکر می‌کنم به‌اندازهٔ کافی متفاوت است که اسم خودش را داشته باشد).

مشکلی که این دستورالعمل برای حلش طراحی شده این‌گونه است. فرض کنید بازی‌ای دارید که در آن بازیکن امتیازی دارد که با گذر زمان تغییر می‌کند. می‌توانید امتیاز بازیکن را در یک رجیستر یا جای دیگر حافظه ذخیره کنید و با اپ‌کدهای جمع/تفریق معمولی بدون مشکل آن را تغییر دهید.

اما حالا می‌خواهید امتیاز را به بازیکن *نمایش* دهید و احتمالاً می‌خواهید این کار را در مبنای ۱۰ انجام دهید چون انسان‌ها معمولاً در خواندن باینری یا هگز بد هستند. پس چطور بایتی مثل #xA5 را بردارید و ارقام صدگان، دهگان و یکان را برای کشیدن اسپرایت «۱۶۵ امتیاز» روی صفحه تعیین کنید؟

این کارِ دستورالعمل BCD است. یک آرگومان (رجیستر) می‌گیرد و ارقام صدگان، دهگان و یکانِ مقدارِ آن رجیستر را در سه بایت جداگانهٔ حافظه، از جایی که رجیستر index فعلاً به آن اشاره می‌کند، ذخیره می‌کند:

txt    رجیستر V3        رجیستر ایندکس
    ┌───┐            ┌───┐
    │135│            │...│
    └───┘            └─┬─┘
      ┌────────────────┘
      │
      ▼
    ┌───┬───┬───┬───┬───┐
    │   │   │   │   │   │   حافظه
    └───┴───┴───┴───┴───┘

    اجرای دستورالعمل BCD V3 =================

    رجیستر V3        رجیستر ایندکس
    ┌───┐            ┌───┐
    │135│            │...│
    └───┘            └─┬─┘
      ┌────────────────┘
      │
      ▼
    ┌───┬───┬───┬───┬───┐
    │ 1 │ 3 │ 5 │   │   │   حافظه
    └───┴───┴───┴───┴───┘

برای خوانایی بهتر این را به دو بخش تقسیم می‌کنیم. اول یک تابع digit می‌سازیم که یک رقم از یک عدد را برمی‌گرداند:

lisp(defun-inline digit (position integer &optional (base 10))
  (-<> integer
    (floor <> (expt base position))
    (mod <> base)))

می‌توانستیم مبنای ۱۰ را سخت‌کد کنیم، اما بخشی از سنت Common Lisp این است که توابع منعطفی بسازیم که وقتی سختی‌اش زیاد نیست، در آینده هم قابل استفاده مجدد باشند.

مطمئن شویم خودش کار می‌کند:

lisp(digit 0 135)
5

(digit 1 135)
3

(digit 2 135)
1

(digit 0 #xD6 16)
6

(digit 1 #xD6 16)
13     ; 13 در مبنای ۱۰ برابر D در مبنای ۱۶ است

و سپس می‌توانیم عملیات واقعی را تعریف کنیم:

lisp(define-instruction op-ld-bcd<vx (_ r _ _)              ;; LD B, Vx
  (let ((number (register r)))
    (setf (aref memory (+ index 0)) (digit 2 number)
          (aref memory (+ index 1)) (digit 1 number)
          (aref memory (+ index 2)) (digit 0 number))))

عملیات حسابی

بعدی دستورالعمل‌های حسابی هستند. CHIP-8 فقط از جمع و تفریق پشتیبانی می‌کند — هیچ دستورالعمل ضرب یا تقسیمی وجود ندارد.

دو دستورالعمل اول ADD و SUB هستند:

lispADD Vx, Vy → Vx = Vx + Vy
SUB Vx, Vy → Vx = Vx - Vy

باز هم با دو تابع کمکی شروع می‌کنیم که جمع/تفریق ۸ بیتی با سرریز/زیرریز انجام می‌دهند. این توابع یک مقدار دوم برمی‌گردانند که بیت carry/borrow است:

lisp(defun-inline +_8 (x y)
  (let ((result (+ x y)))
    (values (chop 8 result)
            (if (> result 255) 1 0)))) ; carry

(defun-inline -_8 (x y)
  (let ((result (- x y)))
    (values (chop 8 result)
            (if (> x y) 1 0)))) ; borrow

و حالا خود دستورالعمل‌ها پیش پا افتاده‌اند:

lisp(define-instruction op-add-reg<reg (_ rx ry)      ;; ADD Vx, Vy (8 بیتی)
    (setf (values (register rx) flag)
          (+_8 (register rx) (register ry))))

(define-instruction op-sub-reg<reg (_ rx ry)      ;; SUB Vx, Vy (8 بیتی)
  (setf (values (register rx) flag)
        (-_8 (register rx) (register ry))))

این از این حقیقت بهره می‌برد که با (setf (values ...) ...) می‌توانید مقادیر چندگانهٔ برگشتیِ یک تابع را بدون binding کردنشان به متغیرهای محلی، تخصیص دهید.

توجه کنید که فقط به flag تخصیص می‌دهیم. در پس‌زمینه، آن flag با ماکروی with-chip ما به معنای (chip-flag chip) بایند شده که در ابتدا تعریف کردیم تا معنای (aref (chip-registers chip) #xF) را بدهد. اما آیا گفتن (setf flag ...) خیلی بهتر نیست؟

یک دستورالعمل SUBN هم هست که عملوندها را برعکس کم می‌کند (اما باز هم نتیجه را در اولی می‌ریزد):

lisp(define-instruction op-subn-reg<reg (_ rx ry)     ;; SUBN Vx, Vy (8 بیتی)
  (setf (values (register rx) flag)
        ;; ترتیب تفریق برای SUBN جابه‌جا شده
        (-_8 (register ry) (register rx))))

بعدی یک دستورالعمل ADD است که مقدار immediate می‌گیرد. برخلاف بقیهٔ دستورالعمل‌ها، این یکی به دلایلی پرچم را تنظیم *نمی‌کند* (این یک باگِ سرگرم‌کننده برای ردیابی بود):

lisp(define-instruction op-add-reg<imm (_ r (immediate 2))  ;; ADD Vx, Imm
  ;; به دلایل عجیب، اپ‌کد ADD با مقدار مستقیم پرچم را تنظیم نمی‌کند
  (zapf (register r) (+_8 % immediate)))

چون Common Lisp اگر مقادیر برگشتی اضافی را استفاده نکنیم آن‌ها را نادیده می‌گیرد، می‌توانیم از تابع کمکی +_8 استفاده کنیم و نتیجهٔ carry را نادیده بگیریم.

یک دستورالعمل ADD ۱۶ بیتی هم وجود دارد که مقدار یک رجیستر خاص را به رجیستر index اضافه می‌کند. آن هم flag را نادیده می‌گیرد:

lisp(define-instruction op-add-index<reg (_ r)        ;; ADD I, Vx (16 بیتی)
  (zapf index (chop 16 (+ % (register r)))))

جابه‌جایی بیتی (Shift)

CHIP-8 دو دستورالعمل جابه‌جایی بیتی دارد: SHR و SHL که محتوای یک رجیستر را یک بیت به راست یا چپ جابه‌جا می‌کنند. هر دو این دستورالعمل‌ها هم پرچم را به بیتی که «از انتها» بیرون افتاده تنظیم می‌کنند.

دو کمکی دیگر تعریف می‌کنیم که جابه‌جایی واقعی ۸ بیتی را انجام می‌دهند و بیتی که از انتها می‌افتد را نگه می‌دارند:

lisp(defun-inline get-bit (position integer)
  (ldb (byte 1 position) integer))

(defun-inline >>_8 (v)
  (values (ash v -1)
          (get-bit 0 v)))

(defun-inline <<_8 (v)
  (values (chop 8 (ash v 1))
          (get-bit 7 v)))

خود دستورالعمل‌ها پیش پا افتاده‌اند:

lisp(define-instruction op-shr (_ r)                    ;; SHR
  (setf (values (register r) flag)
        (>>_8 (register r))))

(define-instruction op-shl (_ r)                    ;; SHL
  (setf (values (register r) flag)
        (<<_8 (register r))))

به‌روزرسانی: همان‌طور که fernly اشاره کرد، این ممکن است رفتارِ مورد نظرِ اصلی نبوده باشد. اگر بخواهیم شبیه‌سازمان با نیت اصلی مطابقت کند، خیلی ساده است:

lisp(define-instruction op-shr (_ rx ry)                 ;; SHR
  (setf (values (register ry) flag)
        (>>_8 (register rx))))

(define-instruction op-shl (_ rx ry)                 ;; SHL
  (setf (values (register ry) flag)
        (<<_8 (register rx))))

اما گمان می‌کنم این کار احتمالاً بعضی ROMهایی را که به رفتارِ مستندِ اشتباه اتکا می‌کنند خراب می‌کند.

عملیات منطقی

بعدی دستورالعمل‌های منطقی AND/OR/XOR هستند. می‌توانستیم آن‌ها را این‌گونه تعریف کنیم:

lisp(define-instruction op-and (_ destination source _)
  (zapf (register destination) (logand % (register source))))

(define-instruction op-or (_ destination source _)
  (zapf (register destination) (logior % (register source))))

(define-instruction op-xor (_ destination source _)
  (zapf (register destination) (logxor % (register source))))

این کار می‌کند، اما به‌جز نام و عملیات، همه یکسان‌اند. چند گروه بعدی دستورالعمل‌ها هم شبیه هم خواهند بود؛ پس یک قدم به عقب برگردیم و ببینیم آیا می‌توانیم کسل‌کنندگی را انتزاعی کنیم.

ماکرو-نقشه (Macro-Map)

به‌جای تایپ‌کردن مکرر یک چیز، دوست داریم فقط یک بار بگوییم چه می‌خواهیم. روش سنتی این کار با macrolet است:

lisp(macrolet
    ((define-logical-instruction (name function)
       `(define-instruction ,name (_ destination source _)
          (zapf (register destination)
                (,function % (register source))))))
  (define-logical-instruction op-and logand)
  (define-logical-instruction op-or logior)
  (define-logical-instruction op-xor logxor))

حالا فقط یک بار عملکرد واقعی را می‌نویسیم به‌جای سه بار. بهتر است، اما هنوز راضی نیستم. استفاده از macrolet یعنی باید برای ماکرویی که فقط قرار است در همین بلاک استفاده و دور انداخته شود نامی پیدا کنم؛ و نام‌گذاری سخت است.

چیزی که *واقعاً* می‌خواهم این است که فقط یک ماکرو را روی چند آرگومان «نقشه» کنم و تمام. من کمی بازی کرده‌ام و به ماکرویی به نام macro-map رسیده‌ام که دقیقاً همین کار را می‌کند:

lisp(defmacro macro-map (lambda-list items &rest body)
  (with-gensyms (macro)
    `(macrolet ((,macro ,(ensure-list lambda-list) ,@body))
      ,@(iterate (for item :in items)
                 (collect `(,macro ,@(ensure-list item)))))))

macro-map یک lambda list، فهرستی از آرگومان‌ها و بدنه‌ای برای ماکرو می‌گیرد و همان macroletای را که با دست نوشته بودیم می‌سازد — با یک gensym برای نام، تا مجبور نباشیم برای اسمش سلول مغز بسوزانیم. حالا می‌توانیم عملیات منطقی‌مان را یکجا تعریف کنیم:

lisp(macro-map                                     ;; AND/OR/XOR
    (NAME    OP)
    ((op-and logand)
     (op-or  logior)
     (op-xor logxor))
  `(define-instruction ,name (_ destination source _)
    (zapf (register destination) (,op % (register source)))))

این در واقع یک خط از نسخهٔ کپی/پیست‌شده بلندتر است چون دوست دارم به‌سخاوت خط بشکنم، اما نکتهٔ مهم این است که هر چیزی را که باید بگوییم فقط یک بار می‌گوییم.

توجه کنید که این تقریباً شروع به شبیه‌شدن به یک جدول داده می‌کند نه کد. من از این واقعیت استفاده کرده‌ام که خوانندهٔ لیسپ همه‌چیز را به‌طور پیش‌فرض بزرگ (uppercase) می‌خواند و ردیف «header» (lambda list) را بزرگ کردم تا بیشتر خودنمایی کند.

اگر کمی چشم‌هایتان را ریز کنید، شاید تصور کنید تعریف کردن یک مجموعه از دستورالعمل‌های مرتبط تقریباً شبیه یک صفحه از دفترچهٔ CPU است.

شاخه‌ها (Branching)

حالا که راهی برای تعریف دسته‌ای از دستورالعمل‌های مشابه بدون دیوانه‌شدن داریم، می‌توانیم دستورالعمل‌های شاخه را انجام دهیم.

بیشتر CPUها نوعی دستورالعمل «پرش به جایی اگر صفر، وگرنه ادامه» برای پیاده‌سازی شاخه دارند. CHIP-8 باید همهٔ دستورالعمل‌ها را در دو بایت جا دهد، پس کار ساده‌تری می‌کند. به‌جای پرش دلخواه بر اساس شرط، یک سری دستورالعمل *رد شدن (skip)* دارد.

مثلاً SE Vx, 0 یعنی «اگر رجیستر X صفر است دستورالعمل بعدی را رد کن». ردکردنِ دستورالعمل بعدی به سادگیِ اضافه‌کردن دو بایت اضافی به برنامه‌شمار است.

چهار نوع از این دستورالعمل وجود دارد:

txtSE  Vx, Immediate → وقتی Vx برابر Immediate است رد شو
SNE Vx, Immediate → وقتی Vx برابر Immediate نیست رد شو
SE  Vx, Vy        → وقتی Vx برابر Vy است رد شو
SNE Vx, Vy        → وقتی Vx برابر Vy نیست رد شو

از macro-map برای نوشتن این به صورت جدولی از کد استفاده کنیم:

lisp(macro-map                                              ;; SE/SNE
    ((NAME            TEST X-ARG  X-FORM        Y-ARG         Y-FORM)
     ((op-se-reg-imm  =    (r 1)  (register r)  (immediate 2) immediate)
      (op-sne-reg-imm not= (r 1)  (register r)  (immediate 2) immediate)
      (op-se-reg-reg  =    (rx 1) (register rx) (ry 1)        (register ry))
      (op-sne-reg-reg not= (rx 1) (register rx) (ry 1)        (register ry))))
  `(define-instruction ,name (_ ,x-arg ,y-arg)
     (when (,test ,x-form ,y-form)
       (incf program-counter 2))))

بعد از ماکروگسترش به چیزهایی مثل این می‌رسیم:

lisp(define-instruction op-sne-reg-imm (_ (r 1) (immediate 2))
  (when (not= (register r) immediate)
    (incf program-counter 2)))

همچنین به خودِ not= نیاز داریم تا داخل بدنهٔ ماکرو کارهای کثیف نکنیم:

lisp(defun-inline not= (x y)
  (not (= x y)))

فقط یک گروه دیگر از دستورالعمل‌ها برای این پست باقی مانده.

بارگذاری‌ها (Loads)

گروه آخر دستورالعمل‌هایی که فعلاً نگاه می‌کنیم، خانوادهٔ LD است. معمولاً اول این‌ها را پیاده‌سازی می‌کنیم، اما می‌خواستم macro-map را به‌نرمی معرفی کنم.

بیشتر دستورالعمل‌های LD به سادگی یک مقدار را از منبع برمی‌دارند و در مقصد می‌گذارند؛ می‌توانیم آن‌ها را به صورت یک فرم setf واحد پیاده‌سازی کنیم:

lisp(macro-map                                              ;; LD
     (NAME           ARGLIST         DESTINATION   SOURCE)
     ((op-ld-i<imm   (_ (value 3))   index         value)
      (op-ld-reg<imm (_ r (value 2)) (register r)  value)
      (op-ld-reg<reg (_ rx ry _)     (register rx) (register ry))
      (op-ld-reg<dt  (_ r _ _)       (register r)  delay-timer)
      (op-ld-dt<reg  (_ r _ _)       delay-timer   (register r))
      (op-ld-st<reg  (_ r _ _)       sound-timer   (register r)))
  `(define-instruction ,name ,arglist
     (setf ,destination ,source)))

هنوز دربارهٔ تایمرها صحبت نکرده‌ایم؛ نگرانشان نباشید. آن‌ها را گذاشتم تا ببینید وقتی لازم است دسته‌ای از عملیات مشابه را یکجا تعریف کنید، macro-map چقدر خوب است.

دو دستورالعمل LD جالب‌تر دیگر وجود دارند که داده را بین چند رجیستر و حافظه جابه‌جا می‌کنند.

LD [I], n بایت‌های متوالی حافظه را با محتوای رجیسترهای V0 تا Vn پر می‌کند، از جایی که رجیستر index به آن اشاره می‌کند. مثلاً LD [I], 2:

txt     V0   V1   V2   V3   V4  ...
    ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
    │  │ │  │ │  │ │  │ │  │ ...
    └─┬┘ └─┬┘ └─┬┘ └──┘ └──┘
      └───┐└──┐ └─┐
          │   │   │
          ▼   ▼   ▼
    ┌───┬───┬───┬───┬───┐
    │   │   │   │   │   │   حافظه
    └───┴───┴───┴───┴───┘
          ▲  ┌───┐
          └──│...│ رجیستر ایندکس
             └───┘

LD n, [I] برعکس را انجام می‌دهد: محتوای حافظه را در رجیسترهای V0 تا Vn بارگذاری می‌کند.

چون هم برای رجیسترها و هم برای حافظه از آرایه‌های لیسپی استفاده کرده‌ایم، این دستورالعمل‌ها واقعاً دوست‌داشتنی‌اند — فقط یک فراخوانی replace می‌شوند:

lisp(define-instruction op-ld-mem<regs (_ n _ _)            ;; LD [I] < Vn
  (replace memory registers :start1 index :end2 (1+ n)))

(define-instruction op-ld-regs<mem (_ n _ _)            ;; LD Vn < [I]
  (replace registers memory :end1 (1+ n) :start2 index))

دستورالعمل‌های LD فعلاً همین‌جا تمام می‌شوند — و دستورالعمل‌ها هم!

آینده

با پیاده‌سازی این دستورالعمل‌ها (و با چند stub برای بقیه) می‌توانیم یک ROM را بارگذاری و اجرا کنیم؛ بایت‌ها را در حافظه جابه‌جا می‌کند و در بیشتر موارد کار می‌کند. در چند پست بعدی مراحل بعدی رسیدن به یک شبیه‌ساز کاملاً کاربردی را می‌بینیم، از جمله:

  • گرافیک و ورودی
  • صدا
  • اشکال‌زدایی

با تشکر از جیمز کش برای خواندن پیش‌نویس این پست.
