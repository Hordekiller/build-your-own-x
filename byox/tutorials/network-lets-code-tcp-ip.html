پشته TCP/IP را کدنویسی کنیم — قسمت ۱: اترنت و ARP (Let's code a TCP/IP stack)

۱. معرفی سری

نوشتن پشتهٔ TCP/IP خودتان در نگاه اول کاری ترسناک به نظر می‌رسد؛ TCP در طول سی سال عمرش مشخصات زیادی به خود جمع کرده است. اما مشخصاتِ هسته نسبتاً فشرده است — بخش‌های مهم: پارس هدر TCP، ماشین حالات، کنترل ازدحام و محاسبهٔ Retransmission Timeout. پروتکل‌های اترنت (لایهٔ ۲) و IP (لایهٔ ۳) در مقایسه با پیچیدگی TCP بسیار ساده‌ترند.

در این سری وبلاگی، یک پشتهٔ TCP/IP کمینه در فضای کاربر (userspace) برای لینوکس پیاده می‌کنیم. هدف، صرفاً آموزشی است: یادگیری عمیق‌تر شبکه و برنامه‌نویسی سیستم. کد کامل پروژه در گیت‌هاب: saminiir/level-ip.

۲. دستگاه‌های TUN/TAP

برای رهگیری ترافیک سطح پایین از کرنل لینوکس، از یک دستگاه TAP استفاده می‌کنیم. در یک کلام، دستگاه‌های TUN/TAP به برنامه‌های شبکه اجازه می‌دهند ترافیک لایهٔ L3 (TUN) و L2 (TAP) را مستقیماً دستکاری کنند. مثال مشهور استفادهٔ عملی: تونل‌زنی، جایی که یک بسته داخل payload بستهٔ دیگری بسته‌بندی می‌شود (مثل OpenVPN). چون می‌خواهیم پشته را از لایهٔ ۲ به بالا بسازیم، به TAP نیاز داریم:

c/* برگرفته از Kernel Documentation/networking/tuntap.txt */
int tun_alloc(char *dev)
{
    struct ifreq ifr;
    int fd, err;

    if( (fd = open("/dev/net/tap", O_RDWR)) < 0 ) {
        print_error("Cannot open TUN/TAP dev");
        exit(1);
    }

    CLEAR(ifr);

    /* پرچم‌ها:
     *   IFF_TUN - دستگاه TUN (بدون هدر اترنت)
     *   IFF_TAP - دستگاه TAP          ← ما این را می‌خواهیم
     *   IFF_NO_PI - اطلاعات بسته را جلو اضافه نکن */
    ifr.ifr_flags = IFF_TAP | IFF_NO_PI;
    if( *dev ) {
        strncpy(ifr.ifr_name, dev, IFNAMSIZ);
    }

    if( (err = ioctl(fd, TUNSETIFF, (void *) &ifr)) < 0 ){
        print_error("ERR: Could not ioctl tun: %s\n", strerror(errno));
        close(fd);
        return err;
    }

    strcpy(dev, ifr.ifr_name);
    return fd;
}

بعد از این، توصیفگر فایل برگشتی fd را می‌توان برای خواندن و نوشتن در بافر اترنت دستگاه مجازی استفاده کرد. پرچم IFF_NO_PI حیاتی است — بدون آن، اطلاعات بستهٔ غیرضروری جلوی فریم اترنت اضافه می‌شود (در کد منبعِ درایور tun در کرنل هم می‌توانید این را راستی‌آزمایی کنید).

c/* خواندن و پرچ کردن فریم دریافتی از دستگاه TAP */
if (tun_read(buf, BUFLEN) < 0) {
    print_error("ERR: Read from tun_fd: %s\n", strerror(errno));
}

struct eth_hdr *hdr = init_eth_hdr(buf);

handle_frame(&netdev, hdr);

۳. قالب فریم اترنت

تکنولوژی‌های متنوع اترنت، ستون فقرات اتصال رایانه‌ها در شبکه‌های محلی (LAN) هستند. استاندارد اترنت از نسخهٔ اولش — که Digital Equipment Corporation، Intel و Xerox در ۱۹۸۰ منتشر کردند — بسیار تکامل یافته است. نسخهٔ اول با سرعت ۱۰ مگابیت بر ثانیه و ارتباط نیمه‌دوبلکس بود؛ برای همین به پروتکل دسترسی MAC با نام CSMA/CD نیاز بود تا جریان داده ساماندهی شود. بعدها ۱۰۰BASE-T با سیم‌کشی به‌هم‌تابیده، ارتباط تمام‌دوبلکس و سرعت بالاتر را ممکن کرد و رواج سوئیچ‌های اترنت، CSMA/CD را تا حد زیادی منسوخ کرد. استانداردهای اترنت توسط گروه کاری IEEE 802.3 نگهداری می‌شوند.

هدر فریم اترنت را می‌توان در C به این شکل ساختارگذاری کرد:

c#include <linux/if_ether.h>

struct eth_hdr
{
    unsigned char dmac[6];      /* MAC مقصد */
    unsigned char smac[6];      /* MAC مبدا */
    uint16_t ethertype;         /* نوع یا طول payload */
    unsigned char payload[];    /* در مورد ما: IPv4 یا ARP */
} __attribute__((packed));
  • dmac و smac: آدرس‌های MAC طرفین ارتباط.
  • ethertype: فیلد دوبایتیِ «پربار»: اگر مقدارش بزرگ‌تر یا مساوی ۱۵۳۶ باشد نوع payload را می‌گوید (مثل IPv4 یا ARP) و اگر کوچک‌تر باشد طول payload را.
  • بعد از فیلد نوع، ممکن است تگ‌هایی برای VLAN و QoS باشد — در این پیاده‌سازی حذف شده‌اند.
  • اگر طول payload از حداقل ۴۶ بایت کمتر باشد، بایت‌های pad اضافه می‌شوند.
  • در پایان فریم، فیلد FCS برای بررسی صحت با CRC هست — در این پیاده‌سازی نادیده گرفته می‌شود.

مشخصهٔ packed به کامپایلر جی‌سی‌سی می‌گوید برای هم‌ترازی داده bytes padding اضافه نکند. دلیل این کار، سبک «پارس» ماست: یک کستِ نوعِ ساده بر روی بافر:

cstruct eth_hdr *hdr = (struct eth_hdr *) buf;

روش قابل‌حمل‌تر (و پرزحمت‌تر) «سریال‌سازی دستی» فیلدهاست تا کامپایلر برای هم‌ترازی پردازنده‌های مختلف padding اضافه نکند. جریان کلی پردازش فریم ورودی ساده است: بخوان ← کست به eth_hdr ← handle_frame که فقط به ethertype نگاه می‌کند و بر اساس آن کاری را انتخاب می‌کند.

۴. پروتکل ARP و قالب پیام آن

پروتکل تفکیک آدرس (ARP) برای نگاشت پویای آدرس ۴۸بیتی اترنت (MAC) به آدرس پروتکل (مثل IPv4) به کار می‌رود. نکتهٔ کلیدی: با ARP انواع پروتکل‌های L3 قابل استفاده‌اند — نه فقط IPv4؛ حتی CHAOS که آدرس ۱۶ بیتی دارد! حالت معمول: آدرس IP سرویسی در LAN را می‌دانید ولی برای ارتباط واقعی، آدرس سخت‌افزاری (MAC) هم لازم است؛ پس ARP در شبکه پخش (broadcast) می‌پرسد: «صاحب این IP کیست که آدرس سخت‌افزاری‌اش را اعلام کند؟»

cstruct arp_hdr
{
    uint16_t hwtype;    /* نوع لایه پیوند؛ اترنت = 0x0001 */
    uint16_t protype;   /* نوع پروتکل؛ IPv4 = 0x0800 */
    unsigned char hwsize;   /* طول آدرس سخت‌افزاری؛ 6 بایت برای MAC */
    unsigned char prosize;  /* طول آدرس پروتکل؛ 4 بایت برای IP */
    uint16_t opcode;    /* 1=ARP request, 2=ARP reply, 3/4=RARP */
    unsigned char data[];   /* payload مخصوص IPv4 */
} __attribute__((packed));

struct arp_ipv4
{
    unsigned char smac[6];      /* MAC فرستنده */
    uint32_t sip;               /* IP فرستنده */
    unsigned char dmac[6];      /* MAC گیرنده */
    uint32_t dip;               /* IP گیرنده */
} __attribute__((packed));

۵. الگوریتم تفکیک آدرس

مشخصات اصلی (RFC 826) این الگوریتم ساده را برای تفکیک آدرس بیان می‌کند:

textآیا نوع سخت‌افزاری ar$hrd را دارم؟
بله:
  [اختیاری: طول سخت‌افزار ar$hln را هم چک کن]
  آیا پروتکل ar$pro را صحبت می‌کنم؟
  بله:
    [اختیاری: طول پروتکل ar$pln را چک کن]
    اگر جفت <نوع پروتکل، آدرس پروتکل فرستنده> از قبل در
    جدول ترجمه هست، آدرس سخت‌افزاری آن ورودی را با اطلاعات
    جدید بسته به‌روز کن.
    آیا من آدرس پروتکل هدف (ar$tpa) هستم؟
    بله:
      اگر ورودی تازه بود، سه‌تایی <نوع پروتکل، آدرس
      پروتکل فرستنده، آدرس سخت‌افزاری فرستنده> را به
      جدول ترجمه اضافه کن.
      آیا opcode یک درخواست است؟  (حالا به opcode نگاه کن!)
      بله:
        فیلدهای سخت‌افزار و پروتکل را جابه‌جا کن و آدرس‌های
        محلی را در فیلدهای فرستنده بگذار.
        ar$op را به REPLY تغییر بده
        بسته را به آدرس هدفِ (جدید) بفرست.

جدول ترجمه نتایج ARP را نگه می‌دارد تا میزبان‌ها بتوانند مستقیم بررسی کنند آیا ورودی را قبلاً دارند — این از بمباران شبکه با درخواست‌های ARP تکراری جلوگیری می‌کند. پیاده‌سازی کامل این الگوریتم در فایل arp.c پروژه هست.

آزمون نهایی: آیا به درخواست ARP پاسخ می‌دهیم؟

bash[saminiir@localhost lvl-ip]$ arping -I tap0 10.0.0.4
ARPING 10.0.0.4 from 192.168.1.32 tap0
Unicast reply from 10.0.0.4 [00:0C:29:6D:50:25]  3.170ms
Unicast reply from 10.0.0.4 [00:0C:29:6D:50:25]  13.309ms

[saminiir@localhost lvl-ip]$ arp
Address         HWtype  HWaddress           Flags Mask  Iface
10.0.0.4        ether   00:0c:29:6d:50:25   C           tap0

پشتهٔ شبکهٔ کرنل، پاسخ ARPِ پشتهٔ سفارشی ما را تشخیص داد و ورودی دستگاه شبکهٔ مجازی را در کش ARP خودش ثبت کرد — موفقیت کامل!

۶. جمع‌بندی و پست بعدی

پیاده‌سازی کمینهٔ رسیدگی به فریم‌های اترنت و ARP نسبتاً آسان است و می‌تواند در چند خط کد انجام شود؛ در مقابل، پاداش آن بالاست: شما کش ARP یک میزبان لینوکس واقعی را با «دستگاه اترنت ساختگی» خودتان پر می‌کنید! گام بعدی سری (قسمت ۲): پارس بستهٔ IPv4 و ICMP echo/reply (پینگ).

قدردانی: زوان‌چن (Xiaochen Wang) که پیاده‌سازی مشابهش (پروژهٔ tapip) در شروع کار با برنامه‌نویسی شبکهٔ C و رسیدگی به پروتکل‌ها بی‌نهایت کمک‌کننده بود — برخی انتخاب‌های طراحی ما مستقیماً از پیاده‌سازی او الگوبرداری شده‌اند.

منابع: RFC 7414، مشخصات اولیه اترنت، IEEE 802.3 و tapip (چن).

کپیرایت: مقالهٔ «Let's code a TCP/IP stack, 1: Ethernet & ARP» اثر سامی نیرانن (Sami Niiranen) است. این صفحه فقط ترجمهٔ فارسی و شرح آن است؛ تمام حقوق محتوا و کدها متعلق به نویسندهٔ اصلی است. مشاهدهٔ اصل مطلب: saminiir.com و مخزن کد: level-ip.
