نوشتن یک شبیه‌ساز Game Boy — سینوپ (Cinoop)

مقدمه

همیشه دلم می‌خواست از صفر یک شبیه‌ساز (emulator) بنویسم، اما مدت طولانی‌ای آن را عقب انداختم؛ چون احتمالاً پیشرفته‌ترین پروژهٔ برنامه‌نویسی‌ای است که تاکنون خواسته‌ام انجامش دهم.

انتخاب سیستمی که قرار است شبیه‌سازی شود، انتخاب آسانی نیست؛ پروژهٔ استانداردِ اولین شبیه‌ساز معمولاً یک شبیه‌ساز CHIP-8 است. خواندن دربارهٔ CHIP-8 قطعاً به من کمک کرد مفاهیم زیادی از شبیه‌سازی را بفهمم، اما به‌نظرم کمی بیش از حد ابتدایی می‌آمد. حس می‌کردم با صرفِ خواندن شبیه‌سازهای دیگران به اندازهٔ کافی از آن بهره برده‌ام و نوشتنِ یکی برای خودم تمرینی بی‌فایده خواهد بود.

از سوی دیگر، NES و Game Boy بودند؛ که هر دوی آن‌ها برای من خیلی پیشرفته به‌نظر می‌رسیدند!

در نهایت تصمیم گرفتم یک شبیه‌ساز مفسریِ (interpreting) مینیمال برای Game Boy بنویسم؛ بدون پشتیبانی از مپرهای سفارشی (custom mappers) یا صدا (و احتمالاً با نادقتی‌های فراوان). نام پروژه را Cinoop گذاشتم.

سینوپ به زبان C نوشته شده و متن‌باز (open source) است. این برنامه روی ویندوز، DS، گیم‌کیوب، 3DS، سیستمی‌عامل‌های مبتنی بر لینوکس، PSP و PS4 قابل اجراست.

ویدیوی نمایشی: نسخهٔ ویندوزی سینوپ که تتریس را پیش از پشتیبانی از تصادفی‌سازی اجرا می‌کند — مشاهده در یوتیوب.

اگرچه خواندن شبیه‌سازی از کسی به‌بی‌تجربگیِ من را توصیه نمی‌کنم، می‌خواستم روند شروع ساخت یک شبیه‌ساز را برای بار اول تشریح کنم، دربارهٔ اسنادی که بیشترین کمک را به من کردند صحبت کنم و همچنین دربارهٔ برخی از انتخاب‌های طراحی که از آن‌ها گذشتم.

شروع کار

برای ساخت یک پنجره با کانتکست معتبر OpenGL از کتابخانهٔ خودم، LDFS، استفاده کردم. انتخاب بهتر چیزی استانداردتر و چندپلتفرمی مثل SDL بود؛ اما من LDFS را انتخاب کردم فقط به این دلیل که با آن آشنا بودم.

سپس برای دید بهتر نسبت به پروژه چند سند مربوط به Game Boy را خواندم. با نگاهی به گذشته، باید زمان بسیار بیشتری صرف این کار می‌کردم تا مجبور نباشم بعداً مدام چیزهایی را دوباره جست‌وجو کنم؛ اما هیجان‌زده بودم!

بیشتر کدهای مخصوص Game Boy که در ابتدا نوشتم، مثل بارگذاری یک رام (ROM)، به‌شدت بر پایهٔ شبیه‌سازهای دیگر بود. بررسی کردم که دو یا سه شبیه‌ساز متفاوت چگونه این کار را انجام می‌دهند و سپس آن را به سبک خودم در سینوپ نوشتم. هنوز ارزش نداشت کد را کاملاً خودم بنویسم؛ اول به پایه‌ای برای کار نیاز داشتم، تا بعد بتوانم روش خودم را تجربه کنم.

حافظه

منابع گوناگون ممکن است به مناطق حافظه به شکل‌های متفاوتی اشاره کنند. رَم بالا (High RAM) گاهی «حافظهٔ صفحهٔ صفر» (Zero Page Memory) نامیده می‌شود، دادهٔ کارتریج (Cartridge Data) گاهی به‌سادگی «رام» (ROM) خوانده می‌شود و اگر سندی فقط «RAM» بگوید، معمولاً به رَم کاری (Working RAM) اشاره دارد. آگاهی از این نکته هنگام خواندن اسنادی که توسط افراد مختلف نوشته شده‌اند ضروری است.

ثبات‌ها (Registers)

Game Boy هشت ثبات ۸ بیتی دارد: A، B، C، D، E، F، H و L، به‌همراه دو ثبات ۱۶ بیتی: SP و PC. در ابتدا ثبات‌ها را این‌گونه پیاده‌سازی کردم:

cstruct registers {
	unsigned char a;
	unsigned char b;
	unsigned char c;
	unsigned char d;
	unsigned char e;
	unsigned char h;
	unsigned char l;
	unsigned char flags;
	unsigned short sp;
	unsigned short pc;
} extern registers;

این مدل برای کار با دستورالعمل‌هایی که به ثبات‌های ۸ بیتی به‌صورت جداگانه دسترسی دارند خوب است؛ اما چیزی که متوجه نشده بودم این است که ثبات‌های ۸ بیتی اغلب با هم گروه‌بندی می‌شوند تا ثبات‌های ۱۶ بیتی AF، BC، DE و HL را بسازند.

ساختار ثبات‌هایم را بازبینی کردم تا دسترسی به ثبات‌های گروه‌بندی‌شده آسان‌تر شود:

cstruct registers {
	struct {
		union {
			struct {
				unsigned char f;
				unsigned char a;
			};
			unsigned short af;
		};
	};
	
	struct {
		union {
			struct {
				unsigned char c;
				unsigned char b;
			};
			unsigned short bc;
		};
	};
	
	struct {
		union {
			struct {
				unsigned char e;
				unsigned char d;
			};
			unsigned short de;
		};
	};
	
	struct {
		union {
			struct {
				unsigned char l;
				unsigned char h;
			};
			unsigned short hl;
		};
	};
	
	unsigned short sp;
	unsigned short pc;
} extern registers;

از ساختارها و اتحادیه‌های بینام (anonymous structs and unions) استاندارد C11 استفاده کردم تا بتوانم مستقیماً از ساختار ریشه به ثبات‌های تکی یا گروه‌بندی‌شده دسترسی داشته باشم؛ مثلاً registers.a یا registers.af.

این یکی از جنبه‌های نسبتاً یکتای شبیه‌ساز من است؛ چون بیشتر شبیه‌سازهای دیگر Game Boy با استانداردهای قدیمی‌تر C نوشته شده بودند (یا جایگزین نامطلوبی مثل C++)، به ساختارها و اتحادیه‌های بینام دسترسی نداشتند؛ یعنی مجبور بودند با یک زنجیرهٔ به‌هم‌ریخته به ثبات‌ها دسترسی پیدا کنند، مثل gameboy_proc->AF.b.h (این‌گونه است که GBE به ثبات a دسترسی پیدا می‌کند) یا به عملیات بیتی (bit operations) تکیه کنند.

پرچم‌ها (Flags)

Game Boy یک ثبات ۸ بیتی دارد که مشخص می‌کند آیا آخرین عملیات نتیجهٔ صفر، سرریز منفی (underflow)، سرریز نیم‌بایتی (nibble overflow) یا سرریز بایتی (byte overflow) داشته است؛ این‌ها به‌ترتیب پرچم صفر (zero flag)، پرچم منفی (negative flag)، پرچم نیم‌حمل (half carry flag) و پرچم حمل کامل (full carry flag) نامیده می‌شوند.

یک چیز که ابتدا مرا به خطا انداخت این بود که مطمئن نبودم آیا باید پرچم‌ها را بعد از هر دستورالعمل به‌روز کنم یا فقط بعد از بعضی از آن‌ها؛ و اگر چنین است، کدام‌ها (و چگونه این اطلاعات را ذخیره کنم). سرانجام به این سند عالی برخوردم که با جزئیات توضیح می‌دهد کدام دستورالعمل‌ها باید پرچم‌ها را و به چه مقادیری به‌روز کنند.

پیاده‌سازی CPU

برای شروع، رویکرد کلاسیک switch(instruction) { را انتخاب کردم که در آن همهٔ دستورالعمل‌ها در یک تابع قرار می‌گیرند.

هر بار که به یک دستورالعمل پیاده‌سازی‌نشده برمی‌خوردیم، مقادیر ثبات‌ها به‌همراه مقدار هگزادسیمال دستورالعمل فعلی در یک فایل اشکال‌زدایی (debug file) نوشته می‌شد.

برای تست کردن، بازی تتریس را انتخاب کردم. هنگام اجرای آن پیامی دریافت کردم که می‌گفت «Undefined instruction 0x00!» (دستورالعمل تعریف‌نشده 0x00).

برای تأیید درستی این موضوع، بازی را در NO$GMB اجرا کردم که اشکال‌زدا (debugger) فوق‌العاده‌ای دارد. همان‌طور که انتظار می‌رفت، اولین دستورالعمل تتریس 0x00 است که یک NOP است.

دستورالعمل NOP را پیاده‌سازی کردم و بازی را دوباره اجرا کردم تا دستورالعمل بعدیِ پشتیبانی‌نشده را بیابم. این روش را برای چند دستورالعمل دیگر هم ادامه دادم و هر بار بررسی می‌کردم که مقادیر ثبات‌های نمایش‌داده‌شده توسط سینوپ با مقادیر NO$GMB مطابقت داشته باشند.

بهبود مدیریت دستورالعمل‌ها

جست‌وجوی هر دستورالعمل در NO$GMB یا در یک جدول آنلاین داشت خسته‌کننده می‌شد. اگرچه نمی‌خواستم یک اشکال‌زای کامل بنویسم، چیزی کمی پرمحتاتر برای کار می‌خواستم.

از رویکرد انجامِ همه‌چیز به‌صورت مستقیم در کد هر دستورالعمل فاصله گرفتم و به سمت این ایده رفتم که اطلاعات مربوط به هر دستورالعمل را در یک ساختار (structure) ذخیره کنم تا کارهای مشترک بتوانند از کد یکسان استفاده کنند.

مثلاً به‌جای اینکه کد هر دستورالعمل مسئول واکشی عملوندهای (operands) خودش باشد، فکر کردم منطقی‌تر است طول عملوندها را در ساختار ذخیره کنیم و برای واکشی عملوندِ هر دستورالعمل از کد مشترکی استفاده کنیم.

همچنین دیساسمبلی (disassembly) هر دستورالعمل را در ساختار کپی کردم:

cstruct instruction {
	char *disassembly;
	unsigned char operandLength;
	void *execute;
	//unsigned char ticks;
} extern const instructions[256];

...

const struct instruction instructions[256] = {
	{ "NOP", 0, nop },                          // 0x00
	{ "LD BC, 0x%04X", 2, NULL },               // 0x01
	{ "LD (BC), A", 0, NULL },                  // 0x02
	...

این کار در ترکیب با ذخیره‌سازی طول عملوندها، چاپ دستورالعمل را فوق‌العاده آسان می‌کرد.

تنها کاری که باید می‌کردم اجرای بازی بود؛ نه‌تنها مقدار هگزادسیمال دستورالعمل پشتیبانی‌نشده را می‌گفت، بلکه دیساسمبلی کامل آن را هم نمایش می‌داد.

اجرای بازی حالا این پیام را به من می‌داد: «Unimplemented instruction 0x06 (LD B, 0x00)!» (دستورالعمل پیاده‌سازی‌نشده). این تنها چیزی بود که برای نوشتن دستورالعمل 0x06 نیاز داشتم؛ دیگر لازم نبود توقف کنم و آن را در یک برنامهٔ بیرونی یا سندی پیدا کنم:

c// 0x06
void ld_b_n(unsigned char operand) { registers.b = operand; }

این کار سرعت پیاده‌سازی دستورالعمل‌های جدید را به‌شدت افزایش داد و بیشتر CPU را به همین روش ادامه دادم.

همچنین این ایده را در نظر گرفتم که آیا هر دستورالعمل باید پرچم‌های مشخصی را به‌روز کند یا نه در ساختار دستورالعمل ذخیره شود؛ اما با آن مخالفت کردم، چون فقط سیستم را بی‌جهت پیچیده می‌کرد و احتمالاً اجرای آن را نیز کندتر می‌کرد.

پیاده‌سازی CPU کار چندان سختی نبود؛ فقط وقت‌گیر بود. بیشتر دستورالعمل‌ها نسبتاً سرراست‌اند و بعضی از آن‌ها جز در ثبات مقصد یکسان‌اند (مثل INC A و INC B). علاوه بر این، چندین NOP وجود دارد (LD A, A، LD B, B و...).

بااین‌حال، یک دستورالعمل بود که مدتی مرا گیج کرد: DAA که برای نمایش امتیاز در تتریس به‌کار می‌رود. پس از بررسی چند شبیه‌ساز دیگر، موفق شدم پیاده‌سازی خودم را بنویسم. یک نکته این است که برخلاف CPU اصلی Z80A، پرچم نیم‌حمل (Half Carry) همیشه پاک می‌شود که کار را کمی ساده‌تر می‌کند.

اشکال‌زدایی بلادرنگ (Real time debugging)

سرانجام متوجه شدم اجرای کل بازی تا رسیدن به یک دستورالعمل پیاده‌سازی‌نشده روش چندان منعطفی نیست.

می‌توانستم تابع cpuStep را طوری تنظیم کنم که چند نقطهٔ توقف (breakpoint) شبه‌ای به من بدهد:

cif(registers.pc == 0x300) {
	printRegisters();
}

اما باز هم استفاده از این روش چندان آسان نبود. اگر در یکی از پیاده‌سازی‌های دستورالعمل‌هایم اشتباهی وجود داشت، می‌خواستم بازی را قدم‌به‌قدم اجرا کنم تا آن را پیدا کنم. برای این کار، یک اشکال‌زای بلادرنگ پایه‌ای ساختم که می‌توانستم هم‌زمان با NO$GMB اجرایش کنم تا مطمئن شوم دستورالعمل‌ها درست اجرا می‌شوند:

همچنین توانستم در توابع readByte و writeByte نقاط توقف اضافه کنم؛ یعنی می‌توانستم بر اساس هر شرطی که می‌خواهم یک اشکال‌زای بلادرنگِ قدم‌به‌قدم فعال کنم. در ترکیب با امکان اجرای بازی در NO$GMB، این روش برای اشکال‌زدایی بیشتر مسائل کافی از آب درآمد.

تایل‌ست‌ها (Tilesets)

اجرای فهرستی بی‌پایان از دستورالعمل‌های CPU برای اطمینان از درست‌کارکردن همه‌چیز مهم است، اما خیلی سریع کسل‌کننده می‌شود. رسم تایل‌ست (tileset) اولین تأیید بصری من بود که سینوپ واقعاً به‌اندازهٔ کافی خوب کار می‌کند تا گرافیک بارگذاری کند.

تتریس را در NO$GMB اجرا کردم تا ببینم کدام دستورالعمل‌ها تایل‌ست را در VRAM کپی می‌کنند. اولین تابعی که تایل‌ها را بارگذاری می‌کند از آدرس 0x2817 شروع و در 0x282a تمام می‌شود.

در شبیه‌سازم برای شروع آن تابع یک نقطهٔ توقف گذاشتم:

cif(registers.pc == 0x2817) {
	realtimeDebugEnable = 1;
}

البته وقتی شبیه‌ساز را اجرا کردم، پیش از رسیدن به این تابع خارج می‌شد، چون به‌اندازهٔ کافی دستورالعمل پیاده‌سازی نکرده بودم؛ اما به کار ادامه دادم و سرانجام نقطهٔ توقف فعال شد! سپس چند دستورالعمل دیگر هم بود که باید پیاده‌سازی می‌کردم تا از آن تابع عبور کنم و بعد بتوانم اولین تایل را تخلیه (dump) کنم:

c// انتهای تابع بارگذاری تایل‌ست
if(registers.pc == 0x282a) {
	FILE *f = fopen("tile0.bin", "wb");
	fwrite(vram, 16, 1, f);
	fclose(f);
	
	realtimeDebugEnable = 1;
}

این را با حافظهٔ NO$GMB مقایسه کردم و داده‌ها مطابقت داشتند!

cint i, x, y;
for(i = 0; i < 8; i++) {

			framebuffer[i * 8 + x + y * 160].g = palette[tiles[i][x][y]].g;

بگذارید بازی کمی جلوتر برود و سپس هر تعداد تایل که روی صفحه جا می‌شود را کپی کردم:

c// رسم تایل‌ست روی فریم‌بافر به‌عنوان تست
int i;
for(i = 0; i < (144 / 8) * (160 / 8); i++) {
	int x;
	for(x = 0; x < 8; x++) {
		int y;
		for(y = 0; y < 8; y++) {
			framebuffer[(i * 8 % 160) + x + (y + i * 8 / 160 * 8) * 160].r = palette[tiles[i][x][y]].r;
			framebuffer[(i * 8 % 160) + x + (y + i * 8 / 160 * 8) * 160].g = palette[tiles[i][x][y]].g;
			framebuffer[(i * 8 % 160) + x + (y + i * 8 / 160 * 8) * 160].b = palette[tiles[i][x][y]].b;
		}
	}
}

نقشه‌ها (Maps)

اولین تلاش من برای خواندن نقشه‌ها (maps) به این نتیجه رسید:

مطمئن نیستم این مشکل از آموزش GPU که دنبال می‌کردم بود یا پیاده‌سازی من، اما تغییر خط زیر:

cmapOffset += ((gpu.scanline + gpu.scrollY) & 255) >> 3;

به:

cmapOffset += (((gpu.scanline + gpu.scrollY) & 255) >> 3) << 5;

مشکل را حل کرد. شبیه‌سازم حالا می‌توانست به صفحهٔ کپی‌رایت تتریس برسد!

رد شدن از صفحهٔ کپی‌رایت

سینوپ در یک حلقه گیر کرده بود و از صفحهٔ کپی‌رایت جلوتر نمی‌رفت. پس از کمی اشکال‌زدایی، متوجه شدم که مسدود کردن هرگونه نوشتن در اولین بایت رَم بالا (HRAM) یعنی آدرس 0xff80، کامل‌شدن حلقه را ممکن می‌کند:

cvoid writeByte(unsigned short address, unsigned char value) {
	// مسدود کردن نوشتن‌ها به ff80
	if(tetrisPatch && address == 0xff80) return;

استفاده از وصله‌های مخصوص بازی به‌جای درست‌کردن درست اشکال‌ها قصد من نبود؛ اما حدس می‌زدم اگر این وصله را موقتاً فعال کنم، مشکل با بهبود سینوپ بالاخره خودش حل شود (که همین‌طور هم شد).

پس از رفع موقت مشکل قبلیِ تکرار حلقه، با مشکل دیگری روبه‌رو شدم؛ بازی این سه دستورالعمل را بی‌نهایت بار تکرار می‌کرد:

shellld a, 0xff80
and a
jr z

متوجه شدم احتمالاً منتظر است مقدار آن توسط یک وقفه (interrupt) نوشته شود؛ بنابراین ثبات فعال‌سازی وقفه‌ها (interrupt enable register) را تخلیه کردم: 0x09؛ یعنی هم وقفهٔ VBlank و هم وقفهٔ سریال (Serial) فعال بودند ((1 << 0) | (1 << 3)). چون احتمالاً به وقفهٔ سریال وابسته نبود، حدس زدم کد VBlank من اشتباه است.

واقعاً هم همین‌طور بود! پس از اصلاح هندلر وقفهٔ VBlank، با چند دستورالعمل پیاده‌سازی‌نشدهٔ دیگر روبه‌رو شدم و سرانجام سینوپ به منوی تتریس رسید!

اسپرایت‌ها (Sprites)

آخرین افزودهٔ مهم به هسته، پشتیبانی از اسپرایت‌ها (sprites) بود؛ پیاده‌سازی آن پس از پیاده‌سازی نقشه‌های پس‌زمینه کار چندان سختی نبود. Game Boy می‌تواند حداکثر ۴۰ اسپرایت نمایش دهد که ویژگی‌های هرکدام در یک جدول پایهٔ OAM ذخیره می‌شود و شامل موقعیت، شمارهٔ تایل، شمارهٔ پالت (palette)، وارون‌سازی (flip) و اولویت (priority) است.

تصادفی‌سازی (Randomisation)

تتریس برای تعیین اینکه بلوک تصادفی بعدی کدام است، به خواندن ثبات تقسیم‌کننده (divider register) در آدرس 0xff04 به‌عنوان منبع آنتروپی (source of entropy) تکیه می‌کند. معمولاً این ثبات یک تایمر است که به‌صورت خطی افزایش می‌یابد تا یا سرریز کند یا با نوشتن هر مقداری در آن به صفر بازنشانی شود.

در عوض تصمیم گرفتم هنگام تلاش برای خواندن این مقدار، rand را برگردانم. چون این ثبات فقط به‌عنوان تولیدکنندهٔ اعداد تصادفی برای تتریس استفاده می‌شود، این تغییر بدون هیچ اثر نامطلوبی برای این بازی، منبع آنتروپی بهتری فراهم می‌کند.

هنگام استفاده از rand باید دانهٔ (seed) آن را با srand تغییر دهید (معمولاً با زمان فعلی)؛ در غیر این صورت، اگر با همان دانه srand کنید، بازی را با دقیقاً همان ترتیب بلوک‌ها بازی می‌کنید.

پورت کردن (Porting)

برای اینکه سینوپ کاربردی‌تر شود، تصمیم گرفتم آن را به چند سیستم دیگر پورت کنم.

DS

اولین سیستمی که سینوپ را به آن پورت کردم DS بود؛ چون با آن بسیار آشنا بودم، واقعاً زمان زیادی نبرد.

با رندر کردن به DS در حالت فریم‌بافر (framebuffer mode) شروع کردم که می‌تواند به شکل زیر انجام شود:

cvideoSetMode(MODE_FB0);
vramSetBankA(VRAM_A_LCD);
VRAM_A[x + y * 256] = RGB15(red, green, blue);

این کار ابتدا خوب بود، چون یعنی می‌توانستم کد رندر ویندوز را دوباره استفاده کنم؛ بنابراین توانستم سینوپ را نسبتاً سریع بالا بیاورم.

بااین‌حال، DS از قبل پشتیبانی از تایل‌ها و اسپرایت‌ها دارد؛ رندر کردن به فریم‌بافر کند است.

کد را برای استفاده از رندر تایل بومیِ DS بازبینی کردم. از رندر فریم‌بافر سریع‌تر اجرا می‌شد، اما روی برخی تایل‌ها گلیچ‌های گرافیکی جزئی داشت (هم روی سخت‌افزار واقعی و هم روی شبیه‌سازها اتفاق می‌افتاد):

مطمئن نیستم دقیقاً چه چیزی باعث این شد، اما فکر می‌کنم چون بیش از حد به VRAM می‌نوشتم. مشکل را با نوشتن در یک آرایه در رَم و تنظیم یک متغیر dirtyTileset حل کردم. در طول VBlank دستگاه DS بررسی می‌کردم که آیا تایل‌ست تغییر کرده است و اگر تغییر کرده بود، تایل‌ها را از رَم به VRAM کپی می‌کردم:

cvoid dsVblank(void) {
	if(dirtyTileset) {

		dirtyTileset = 0;
	}

	irqSet(IRQ_VBLANK, dsVblank);

طرز طراحی حالت‌های ویدیویی DS به‌گونه‌ای است که مانند Game Boy، اسپرایت‌ها و پس‌زمینه‌ها نمی‌توانند یک تایل‌ست مشترک داشته باشند. در نتیجهٔ این موضوع، مجبور بودم در روال dsVblank تایل‌ست را هم در حافظهٔ پس‌زمینه و هم در حافظهٔ اسپرایت‌ها کپی کنم.

در پایان، یک تایل مشکی ساده در VRAM نوشتم و از آن برای حاشیه استفاده کردم. با قرار گرفتن سیستم رندر تایل نهایی، شبیه‌ساز هیچ آرتیفکت گرافیکی نداشت و به‌طرز محسوسی سریع‌تر اجرا می‌شد (اما باز هم با سرعت کامل نه).

گیم‌کیوب (GameCube)

گیم‌کیوب سیستمی نیست که تاکنون برایش برنامه‌نویسی کرده باشم؛ بنابراین تصمیم گرفتم این پروژهٔ خوبی برای شروع باشد. اگرچه مستندات آن به‌اندازهٔ DS زیاد نیست، با کمک libogc و devkitPPC شروع کار همچنان آسان بود.

برخلاف x86 و DS، پردازندهٔ PowerPC گیم‌کیوب بیگ‌اندین (big endian) است. این یک دردسر جزئی بود، اما در نظر گرفتن آن ساده بود:

3DS

توسعه برای 3DS بسیار سخت‌تر از توسعه برای DS است، چون زمان کمتری برای بلوغ داشته است. مستندات بسیار کمتری دارد و در نتیجه توسعه برای آن احساس ناهمواری می‌کند.

مثلاً libfat دستگاه DS از خواندن فایل با روال‌های استاندارد C پشتیبانی می‌کند (fopen و...)، اما ctrulib دستگاه 3DS روش خاص خودش را برای خواندن فایل‌ها دارد (FSUSER_OpenFileDirectly و...).

صحنهٔ 3DS در حال حاضر بسیار به‌هم‌ریخته است؛ چندین لانچر وجود دارد که هنگام انتشار چیزی باید از آن‌ها پشتیبانی کنید:

  • 3ds — فلش‌کارت‌ها (Flashcards)
  • 3dsx و smdh — Homebrew Launcher
  • cia — فریم‌ورهای سفارشی (Custom firmwares)
  • elf — شبیه‌سازها

همچنین توجه کنید که برخی برنامه‌ها به‌صورت زنجیرهٔ ROP «.dat» منتشر می‌شوند، چون نیاز به اجرا در محیط یک اکسپلویت خاص دارند (معمولاً برای دسترسی به برخی فراخوانی‌های سیستم).

شبیه‌سازی 3DS هم در حال حاضر چندان خوب نیست؛ بنابراین مجبور بودم روی سخت‌افزار واقعی تست کنم که زمان‌بر بود.

به‌جز این چند دردسر جزئی، پورت 3DS زمان زیادی نبرد. در آینده امیدوارم پشتیبانی از رندر اسپرایت‌ها روی پس‌زمینه با استفاده از 3D را اضافه کنم.

اوبونتو (Ubuntu)

تعدادی توزیع لینوکس را امتحان کردم و اوبونتو را پلتفرم دلپذیری برای پورت سینوپ یافتم.

PSP

PSP به‌مراتب آسان‌ترین پلتفرم برای توسعه بود که برایم تازگی داشت.

Minimalist PSP SDK و شبیه‌ساز PPSSPP را راه‌اندازی کردم و توانستم سینوپ را فقط در یک روز پورت کنم!

PS2

برنامه‌هایی برای پورت سینوپ به PS2 داشتم، اما به دلیل مشکلات فراوان توسعه برای PS2 منصرف شدم.

اولین دلیل آن ماهیت غیرمتمرکز این صحنه است؛ هر اطلاعاتی دربارهٔ توسعهٔ PS2 که هنوز در دسترس است، مثل لگو در اتاق کودک در اینترنت پراکنده شده است.

سعی کردم زنجیرهٔ ابزار ps2dev را از GitHub نصب کنم؛ روی ویندوز ۷، اوبونتو 14.04 و مک OS X Lion امتحانش کردم. اما هر کاری کردم، با خطاهای کامپایل متعددی روبه‌رو شدم؛ بنابراین کلاً منصرف شدم.

برای هرکسی که واقعاً بتواند کیت توسعهٔ PS2 را راه‌اندازی کند، برخلاف هر سیستم دیگری که سینوپ را به آن پورت کردم، هیچ راه آسانی برای رسم مستقیم پیکسل‌ها روی فریم‌بافر وجود ندارد.

نقل‌قول از لیو وون یونگ (Liu Woon Yung):

راهی برای نوشتن مستقیم روی فریم‌بافر وجود ندارد، چون VRAM داخل رَم EE نیست و به فضای حافظهٔ EE نگاشت نشده است. تنها راه این است که یک فریم‌بافر محلی در رَم EE داشته باشیم که بتوانیم آن را در هر فریم از طریق DMA به فریم‌بافر واقعی داخل VRAM منتقل کنیم. VRAM در واقع ۴ مگابایت eRAM داخل GS است.

برای فهمیدن اینکه این کار چگونه انجام می‌شود، مهم است ابتدا بفهمیم چگونه می‌توان تکسچرها را در حین اجرای برنامه آپلود کرد. فریم‌بافر اساساً یک تکسچر بسیار بزرگ است. برخی کتابخانه‌های گرافیکی (مثل gsKit) توابع مناسبی برای تسهیل چنین فرایندهایی دارند.

فکر می‌کنم ممکن است انتقال مستقیم دادهٔ بیت‌مپ به فریم‌بافر روی GS امکان‌پذیر باشد؛ چون فکر می‌کنم FMCB (و احتمالاً چند دموی هومبروی قدیمی‌تر) همین کار را برای رسم لوگوی بوتش انجام می‌دهند. اما تاکنون فقط دادهٔ بیت‌مپ را به‌عنوان دادهٔ تکسچر به GS منتقل کرده‌ام (به بافری داخل VRAM که بیرون از فریم‌بافر است) که بعداً به‌صورت یک تکسچر دو بعدی تمام‌صفحه روی فریم‌بافر رسم می‌شود.

حالا شاید از خود بپرسید چرا انجام کاری به سادگی به‌روزرسانی فریم‌بافر این‌قدر سخت است. خب، به این دلیل است که پلی‌استیشن ۲ در درجهٔ اول برای پشتیبانی از 3D ساخته شده بود، نه 2D. همان‌طور که در بالا اشاره شد، VRAM داخل GS است که پردازنده‌ای جدا از EE است.

— Liu Woon Yung

مک OS X

همچنین برنامه‌هایی برای پورت به مک OS X داشتم، اما مانند PS2، این کار هم بیش از حد دشوار بود؛ چون نتوانستم یک کامپایلر C و محیط توسعهٔ کارا روی مک OS X نصب کنم.

در حالی که روی OS X هیچ‌چیز برایم کار نمی‌کرد، در روحیهٔ متن‌باز، nsenica موفق شد سینوپ را با XQuartz به OS X پورت کند و یک درخواست کشش (pull request) فرستاد!

PS4

پورت پلی‌استیشن ۴ احتمالاً جالب‌ترین پورت است؛ چون هومبرو هنوز روی آن رایج نشده است؛ فقط چند نفر روی PS4 اجرای کد دارند و با دسترسی‌ای که تا زمان نوشتن این مقاله داریم، هومبرو روی این کنسول از محدودیت‌های جدی رنج می‌برد.

مشکل اول کنترلر است. مطمئن نیستم چه اشکالی دارد، اما استفاده از ماژول رسمی libScePad.sprx کار نمی‌کند. شاید به این دلیل است که کنترلر از قبل در حال استفاده است و اتصال کنترلر دوم جواب می‌دهد؛ اما من فقط یک کنترلر برای تست دارم.

دو راه‌کار برای این مشکل وجود دارد: استفاده از کتابخانهٔ USB برای دریافت ورودی از یک کنترلر شخص ثالث، یا استفاده از هر دستگاه سازگار با وای‌فای که دکمه داشته باشد برای ارسال ورودی از طریق سوکت UDP. من انتخاب کردم که از یک نینتندو DS به‌صورت بی‌سیم استفاده کنم.

مشکل دوم این است که ماژول libSceVideoOut.sprx برای ما کار نمی‌کند. همهٔ چیزهایی که برای خروجی ویدیو امتحان کردم را در مقالهٔ بعدی‌ام دربارهٔ PS4 با جزئیات بیشتری توضیح خواهم داد؛ اما راه‌حلی که پیدا کردم ساخت یک بوم HTML5 (HTML5 canvas) و رندر کردن روی آن به‌جای آن است.

با این دو راه‌کار توانستم یک بازی پونگ کوچک روی PS4 بسازم:

ویدیوی نمایشی: بازی پونگ کوچکی که با دو راه‌کار یادشده روی PS4 ساخته شد — مشاهده در یوتیوب.

محدودیت نهایی این است که اجازهٔ mount کردن فلش‌درایوهای USB و خواندن آن‌ها به‌صورت عادی را نداریم.

بااین‌حال به ماژول libUsbd.sprx دسترسی داریم (که اساساً همان libusb است) و به ما امکان می‌دهد مستقیماً با دستگاه‌های USB ارتباط برقرار کنیم.

اگرچه ممکن است در آینده امکان پورت یک پیاده‌سازی کامل FAT بر پایهٔ دستورهای خام USB فراهم شود، برای حالا فقط رام تتریس را با Win32 Disk Imager به‌صورت تصویر خام فلش‌درایو USB نوشتم.

با قرار گرفتن این سه راه‌کار در جای خود، با استفاده از PS4-SDK توانستم سینوپ را به PS4 پورت کنم!
