مقدمه: کدنویسی یک پایگاه داده در ۴۵ گام

این مجموعه از معماهای کوچک کدنویسی تست‌محور (test-driven) به شما امکان می‌دهد یک پایگاه داده را از صفر (بدون هیچ وابستگی) کدنویسی کنید. از خلال این پروژه می‌توانید:

  • داخل‌مایه‌های پایگاه داده (database internals) و مبانی علوم رایانه را یاد بگیرید.
  • مهارت‌های خود را با کار چالش‌برانگیز ارتقا دهید.
  • یک پروژهٔ شخصی چشمگیر برای رزومه‌تان بسازید.

محتوای پروژه

این پروژه چند بخش کلیدی را پیاده‌سازی می‌کند:

  • موتور ذخیره‌سازی (storage engine) کلید-مقدار (KV).
  • SQL و پایگاه داده‌های رابطه‌ای.
  • ایندکس‌ها و ساختارهای داده.

دامنهٔ کار گسترده است، اما به گام‌های بسیار کوچک تقسیم شده است. هر گام ساده است و حداکثر چند ده خط کد دارد. خواهید دید که ایده‌های پیچیده چگونه از ایده‌های ساده رشد می‌کنند. از این نظر، شما یک پایگاه داده را از صفر اختراع می‌کنید.

پیش‌نیازها

  • با هر زبان برنامه‌نویسی آشنا باشید.
  • بتوانید از خط فرمان (Linux یا Windows) استفاده کنید.

زبان Go

  • یادگیری Go آسان است، بنابراین هیچ تجربهٔ قبلی لازم نیست.
  • می‌توانید از هر زبانی استفاده کنید، چون ایده‌های اصلی به زبان خاصی وابسته نیستند.
  • همچنین می‌تواند به‌عنوان پروژهٔ تمرینی برای یادگیری زبان‌های دیگر استفاده شود.

برش (slice)

در Go، slice در واقع دو کاربرد بی‌ارتباط دارد که نمایش یکسانی دارند:

  1. نمایی از یک آرایه، با یک اشاره‌گر و طول.
  2. یک آرایهٔ پویای رشدپذیر، مانند vector در C++ یا list در پایتون.
gotype sliceT struct {
    ptr *T
    len int
    cap int
}
  • len() و cap() طول و ظرفیت را برمی‌گردانند.
  • یک slice صفر (nil) برابر {ptr: nil, len: 0, cap: 0} است.

این دو کاربرد اغلب با هم اشتباه گرفته می‌شوند، بنابراین جداگانه توضیح داده می‌شوند.

الف) slice به‌عنوان نمای آرایه

go// یک آرایه
var arr [8]byte = [8]byte{0, 1, 2, 3, 4, 5, 6, 7}
// برش از آرایه
s1 := arr[1:5]      // {ptr: &arr[1], len: 4, cap: 7}
// پیمایش
for i := 0; i < len(s1); i++ {
    println(s1[i])  // 1 2 3 4
}
// به‌جای آن از `range` استفاده کنید
for i := range s1 {
    println(s1[i])
}
for i, v := range s1 {
    println(v)
}
// خروج از محدوده باعث panic می‌شود
v := s1[4]

// برش مجدد، یک slice جدید برمی‌گرداند
s2 := s1[2:3]       // {ptr: &arr[3], len: 1, cap: 5}
for _, v := range s2 {
    println(v)      // 3
}

بررسی مرزها:

  • s[i]: شرط i < len
  • s[i:j]: شرط j <= cap

معمولاً برش مجدد (reslicing) len را کوچک می‌کند، هرچند بزرگ‌شدن آن نیز مجاز است. وقتی یک slice نمای آرایه است، فقط len مهم است و cap را می‌توان نادیده گرفت.

go// شکل‌های کوتاه‌شده
s[:]    // s[0:len(s)]
s[:j]   // s[0:j]
s[i:]   // s[i:len(s)]

ب) slice به‌عنوان آرایهٔ پویا

go// تخصیص آرایه با طول ۲
arr1 := make([]byte, 2)     // {ptr: 0x100, len: 2, cap: 2}
// تخصیص آرایه با ظرفیت ۲ و طول ۰
arr2 := make([]byte, 0, 2)  // {ptr: 0x200, len: 0, cap: 2}
// افزودن عنصر
arr2 = append(arr2, 123)    // {ptr: 0x200, len: 1, cap: 2}
arr2 = append(arr2, 123)    // {ptr: 0x200, len: 2, cap: 2}
// وقتی ظرفیت پر شود، تخصیص مجدد
arr2 = append(arr2, 123)    // {ptr: 0x300, len: 3, cap: 8}
// افزودن چند عنصر
arr2 = append(arr2, 2, 3)   // {ptr: 0x300, len: 5, cap: 8}

فقط به sliceهای پویا می‌توان عنصر اضافه کرد. به sliceای که نمای آرایه است نباید عنصر اضافه کرد، زیرا آرایه را تغییر می‌دهد.

عملیات رایج slice

gocopy(dst, src)                      // کپی داده
s1 = slices.Clone(s)                // تخصیص و کپی
s = slices.Concat(s1, s2, s2)       // به‌هم الحاق کن
s = slices.Delete(s, i, j)          // حذف s[i:j]
s = slices.Insert(s, i, e1, e2)     // درج در i
idx = slices.Index(s, v)            // یافتن ایندکس
slices.Sort(s)                      // مرتب‌سازی درجا

slice به‌عنوان نمای آرایه فقط یک مرجع است و نباید به آن عنصر اضافه کرد. slice به‌عنوان آرایهٔ پویا صاحب آرایه است و هر عملیاتی می‌تواند انجام دهد. یک slice پویا می‌تواند به‌عنوان نمای آرایه استفاده شود، اما عکس آن ممکن نیست.

واسط (interface)

یک interface مجموعه‌ای از قواعد متد است. هر نوعی که این متدها را پیاده‌سازی کند می‌تواند به‌عنوان آن interface استفاده شود.

gotype Reader interface {
    Read(p []byte) (n int, err error)
}
// نوعی که interface را پیاده‌سازی می‌کند
type T struct { /* ... */ }
func (s *T) Read(p []byte) (n int, err error) { /* ... */ }
// تابعی که interface را به‌عنوان آرگومان می‌گیرد
func useReader(r Reader) { /* ... */ }

obj := &T{}         // نوع مشخص (concrete)
useReader(obj)      // تبدیل به interface

فراخوانی متدها از طریق interface به نوع مشخص وابسته نیست؛ مشابه کلاس‌های انتزاعی در برنامه‌نویسی شیءگرا. یک interface دو اشاره‌گر دارد:

gotype interfaceFoo struct {
    object   uintptr    // اشاره‌گر داده
    typeInfo uintptr    // اطلاعات نوع
}

تبدیل یک مقدار به interface، اشاره‌گر به مقدار و اطلاعات نوع آن را ذخیره می‌کند. فراخوانی متدها از اطلاعات نوع برای یافتن پیاده‌سازی استفاده می‌کند.

یک interface مقداردهی‌نشده، هر دو اشاره‌گرش nil است. این با تبدیل یک اشاره‌گر nil به interface متفاوت است.

بازیابی نوع اصلی

  • با iface.(T) می‌توان نوع T را آزمود و استخراج کرد.
  • interface{} صفر متد دارد. هر نوعی می‌تواند به آن تبدیل شود.
govar anything interface{}
anything = 1
anything = "asdf"

// تبدیل به نوع مشخص
integer, ok := anything.(int)   // ok = false
str, ok := anything.(string)    // ok = true
// switch روی نوع
switch origin := anything.(type) {
case int:
    integer = origin
case string:
    str = origin
}

۰۱ — KV مبتنی بر لاگ

۰۱۰۱: رابط‌های KV

حافظه در برابر دیسک

نرم‌افزارهایی که پایگاه داده نامیده می‌شوند اشکال گوناگونی دارند. برخی صرفاً درون‌حافظه‌ای هستند؛ مانند Redis و Memcached. برخی مبتنی بر دیسک هستند؛ مانند MySQL و SQLite.

پایگاه داده‌های درون‌حافظه‌ای به اندازهٔ RAM محدودند، بنابراین پایگاه داده‌های سنتی مبتنی بر دیسک هستند. اما حتی پایگاه داده‌های مبتنی بر دیسک نیز اغلب ساختارهای دادهٔ درون‌حافظه‌ای دارند. پس انواع مختلف پایگاه داده بی‌ارتباط نیستند. می‌توانیم از یک KV درون‌حافظه‌ای شروع کنیم و با افزودن کد گام‌به‌گام پروژه را بسازیم.

یک پایگاه داده کاربرد ساختارهای داده است. اینکه داده در حافظه ذخیره شود یا روی دیسک، در اصل فرقی ندارد؛ اما مسائل بسیاری در پیاده‌سازی ظاهر می‌شوند. این موضوعات را به‌ندرت در کتاب‌ها می‌بینید، اما در یک پروژه می‌توانید آن‌ها را یاد بگیرید.

کلید-مقدار در برابر جدول

پایگاه داده‌ها را می‌توان بر اساس رابط‌هایشان دسته‌بندی کرد: کلید-مقدار (KV)، رابطه‌ای (relational) و انواع خاص دیگر. KV مانند map یا dict در زبان‌های برنامه‌نویسی است، با عملیاتی مانند get و set و del. پایگاه داده‌های رابطه‌ای از جدول‌ها (ردیف‌ها و ستون‌ها) استفاده می‌کنند و معمولاً با SQL کار می‌کنند.

از نظر امکانات، به‌نظر می‌رسد پایگاه داده‌های رابطه‌ای کار بیشتری انجام می‌دهند. با این حال، پایگاه داده‌های رابطه‌ای پیچیده‌تر بر روی سیستم‌های KV ساده‌تری ساخته می‌شوند که اغلب موتور ذخیره‌سازی (storage engine) نامیده می‌شوند. مثلاً LevelDB و RocksDB می‌توانند به‌صورت مستقل به‌عنوان فروشگاه KV استفاده شوند و پایگاه داده‌های SQL نیز روی آن‌ها ساخته می‌شوند. بنابراین پیاده‌سازی پایگاه داده از KV شروع می‌شود.

OLAP در برابر OLTP

پایگاه داده‌ها را می‌توان بر اساس کاربرد به ۲ نوع تقسیم کرد: پردازش تحلیلی برخط (OLAP — Online Analytical Processing) و پردازش تراکنشی برخط (OLTP — Online Transaction Processing). این واژه‌ها فقط نام هستند؛ «تحلیلی» و «تراکنشی» معنای دقیقی ندارند. OLAP بر تحلیل حجم زیادی از داده متمرکز است، در حالی‌که OLTP بر بازگرداندن نتایج در زمان واقعی با استفاده از ایندکس‌ها تمرکز دارد. برای مثال:

  • OLAP: برای شمارش کاربران فعال، باب (Bob) یک پرس‌وجوی SQL اجرا می‌کند و کاربران منطبق را COUNT() می‌کند.
  • OLTP: برای نمایش تعداد کاربران به‌صورت واقعی‌زمان در یک اپ. اما کاربران زیاد هستند؛ بنابراین یک شمارندهٔ اضافی نگهداری می‌شود.

OLTP به نتایج واقعی‌زمان نیاز دارد، بنابراین هر عملیات برای مصرف منابع (CPU، IO، حافظه) سقف بالایی دارد. اگر ساختارهای داده را بدانید، این سقف معمولاً O(log N) است. یک ایندکس از اطلاعات اضافی برای پشتیبانی از پرس‌وجوهای واقعی‌زمان استفاده می‌کند؛ یعنی مبادلهٔ فضا با زمان. در کاربردها، «ایندکس» همیشه به معنی قابلیت ایندکس پایگاه داده نیست. در مثال بالا، اپ ایندکس اضافی خودش را برای شمارش نگهداری می‌کند.

بار کاری OLAP ممکن است منابع زیادی مصرف کند، بنابراین اغلب جدا از OLTP ذخیره می‌شود. پایگاه داده‌های سنتی مانند MySQL و PG از نوع OLTP هستند. پس از ظهور «داده‌های بزرگ» (big data)، پایگاه داده‌های متخصص در OLAP محبوب شدند.

اگرچه هر دو پایگاه دادهٔ رابطه‌ای نامیده می‌شوند، OLAP معمولاً داده را ستون‌محور ذخیره می‌کند، در حالی‌که OLTP ردیف‌محور ذخیره می‌کند. فناوری پایه و موارد استفادهٔ آن‌ها متفاوت است. این پروژه فقط OLTP را در نظر می‌گیرد. هنگام یادگیری آن‌ها را با هم اشتباه نگیرید.

KV درون‌حافظه‌ای

gotype KV struct {
    mem map[string][]byte
}

func (kv *KV) Open() error {
    kv.mem = map[string][]byte{} // خالی
    return nil
}

func (kv *KV) Close() error { return nil }

func (kv *KV) Get(key []byte) (val []byte, ok bool, err error)
func (kv *KV) Set(key []byte, val []byte) (updated bool, err error)
func (kv *KV) Del(key []byte) (deleted bool, err error)

  • ورودی/خروجی دیسک بعداً اضافه خواهد شد، بنابراین این رابط‌ها error برمی‌گردانند.

ACID

اتمی بودن (Atomicity)، سازگاری (Consistency)، ایزوله بودن (Isolation) و ماندگاری (Durability) — اصطلاحاً ACID — اغلب برای توصیف پایگاه داده‌ها به‌کار می‌روند، گویی ۴ خاصیت پایگاه داده هستند. خیلی‌ها فکر می‌کنند فهمیدن آن‌ها سخت است. دلیلش این است که این‌ها ایده‌های مبهمی بدون تعریف روشن هستند و اغلب معانی متفاوتی دارند.

اتمی بودن در لغت یعنی تقسیم‌ناپذیر. مثلاً نوشتن n بایت در یک فایل:

  1. با خواندن همزمان (concurrent reads)، یک خواننده ممکن است دادهٔ نیمه‌نوشته‌شده را ببیند.
  2. اگر در میانهٔ نوشتن برق قطع شود، پس از بازیابی ممکن است فقط نیمی از داده موجود باشد.

هر دو را می‌توان فقدان اتمی بودن توصیف کرد و پایگاه داده باید به آن‌ها بپردازد. اما یکی دربارهٔ همزمانی (concurrency) و دیگری دربارهٔ ماندگاری است. آن‌ها مسائل بی‌ربطی هستند.

سازگاری برای توصیف منطق داخلی پایگاه داده، منطق کسب‌وکار، یا سیستم‌های توزیع‌شده استفاده می‌شود، بدون اینکه حتی تعریف مبهمی داشته باشد.

ایزوله بودن به این اشاره دارد که آیا یک تراکنش تحت تأثیر تراکنش‌های همزمان دیگر قرار می‌گیرد یا نه.

ماندگاری یعنی وقتی پایگاه داده موفقیت را گزارش کرد، می‌توان به ناپدید نشدن داده اعتماد کرد. در پیاده‌سازی، این را نمی‌توان به‌تنهایی بررسی کرد؛ زیرا اتمی بودن نیز درگیر است.

رفتار پایگاه داده پیچیده است و ACID آن را به‌طور کامل توصیف نمی‌کند. در عمل، باید رفتار خاص هر پایگاه داده را یاد بگیرید. وقتی خودتان پایگاه داده پیاده‌سازی می‌کنید، مستقیماً با مسائل واقعی‌ای که پایگاه داده‌ها باید حل کنند و راه‌حل‌هایشان روبه‌رو خواهید شد.

۰۱۰۲: سریال‌سازی باینری

سریال‌سازی

برای ذخیرهٔ انواع دادهٔ یک زبان برنامه‌نویسی روی دیسک یا ارسال آن‌ها از طریق شبکه، باید به دنباله‌ای از بایت‌ها تبدیل شوند. این را سریال‌سازی (serialization) می‌نامند.

مثلاً یک جفت KV:

gotype Entry struct {
    key []byte
    val []byte
}

func (ent *Entry) Encode() []byte

Encode() را با استفاده از قالب زیر پیاده‌سازی کنید:

text| key size | val size | key data | val data |
| 4 bytes  | 4 bytes  |   ...    |   ...    |

مثلاً برای key=a و val=bb خروجی []byte(1, 0, 0, 0, 2, 0, 0, 0, 'a', 'b', 'b') است.

برای sliceها، رشته‌ها و سایر انواع طول‌متغیر، اندازه باید اول بیاید. در این‌جا اندازه به‌صورت uint32 با ترتیب بایت کوچک (little-endian) ذخیره می‌شود. برای تبدیل اعداد صحیح به ۴ بایت از binary.LittleEndian.PutUint32() استفاده کنید.

gofunc (ent *Entry) Encode() []byte {
    data := make([]byte, 4+4+len(ent.key)+len(ent.val))
    binary.LittleEndian.PutUint32(data[0:4], uint32(len(ent.key)))
    binary.LittleEndian.PutUint32(data[4:8], uint32(len(ent.val)))
    copy(data[8:], ent.key)
    copy(data[8+len(ent.key):], ent.val)
    return data
}

سریال‌زدایی

سریال‌زدایی (deserialization) دنبالهٔ بایت‌ها را دوباره به داده تبدیل می‌کند. سپس این را پیاده‌سازی کنید:

gofunc (ent *Entry) Decode(r io.Reader) error

هنگام فراخوانی Decode()، فراخواننده نمی‌داند چند بایت لازم است، بنابراین نمی‌توان یک slice پاس داد. به‌جای آن از واسط کتابخانهٔ استاندارد io.Reader استفاده می‌شود:

gotype Reader interface {
    Read(p []byte) (n int, err error)
}

داخل Decode()، برای خواندن داده مانند خواندن از یک فایل، r.Read() را صدا می‌زنید. اما چون این یک واسط است، پیاده‌سازی زیرین لزوماً فایل نیست.

io.Reader و io.Writer

io.Reader برای ورودی استفاده می‌شود و واسط متناظر خروجی io.Writer است.

gotype Writer interface {
    Write(p []byte) (n int, err error)
}

هر نوعی که Read() یا Write() را پیاده‌سازی کند می‌تواند به‌عنوان io.Reader یا io.Writer استفاده شود. مزیت این واسط‌ها انعطاف‌پذیری است. مثلاً پارامتر Decode() یک نوع مشخص نیست. در گام بعد، از یک فایل لاگ می‌خواند، در حالی‌که در این گام موارد تست از حافظه می‌خوانند. برای یادگیری نحوهٔ کار bytes.Buffer می‌توانید موارد تست را بررسی کنید.

در واقع Encode() هم می‌توانست به‌جای بازگرداندن slice از io.Writer استفاده کند، هرچند لازم نیست.

فراخوانی‌های سیستمی یونیکس read و write طراحی مشابهی دارند. آن‌ها می‌توانند روی منابع بسیار متفاوتی کار کنند: فایل‌ها، سوکت‌های شبکه، لوله‌ها (pipes) و IPC. وجه مشترک آن‌ها ورودی و خروجی است.

روش‌های سریال‌سازی

همهٔ روش‌های سریال‌سازی مشابه‌اند و فقط در جزئیات تفاوت دارند. برای سریال‌سازی دادهٔ طول‌متغیر مانند رشته، ساده‌ترین راه این است که اول طول بیاید و بعد داده. طول یک عدد صحیح است و روش‌های بسیاری برای رمزگذاری آن وجود دارد. برخی فرمت‌ها از ۲ بایت، برخی از ۴ بایت، برخی از varint طول‌متغیر و برخی مانند Redis از ارقام دهدهی استفاده می‌کنند.

جدای از این فرمت باینری، فرمت‌های متنی مانند JSON و XML نیز وجود دارند. «باینری» هیچ ربطی به مبناهای عددی ندارد؛ فقط متضاد «متن» است. بیشتر فرمت‌های متنی طول رشته را رمزگذاری نمی‌کنند، بلکه از جداکننده‌ها (delimiters) برای علامت‌گذاری پایان داده استفاده می‌کنند. JSON از علامت نقل‌قول و XML از تگ استفاده می‌کند.

فرمت‌های متنی شهودی به‌نظر می‌رسند اما پیاده‌سازی آن‌ها سخت است. چون دادهٔ رمزگذاری‌شده نمی‌تواند شامل جداکننده باشد، فرمت‌های متنی به فرار کردن (escaping) پیچیده نیاز دارند. حتی JSON ساده در پیاده‌سازی‌های مختلف باگ‌های زیادی دارد. فرمت‌های متنی در مقایسه با سریال‌سازی باینری ساده، CPU هم بیشتر هدر می‌دهند.

فراتر از پیچیدگی، فرمت‌های متنی اغلب محدودیت‌های خودسرانه‌ای دارند. مثلاً JSON نمی‌تواند دادهٔ باینری دلخواه را پشتیبانی کند، بنابراین از base64 استفاده می‌شود که هدرروی بیشتری دارد. بسیاری از کتابخانه‌های JSON اعداد صحیح ۶۴ بیتی را پشتیبانی نمی‌کنند. پس مگر در صورت ضرورت، از فرمت‌های متنی استفاده نکنید.

برای سریال‌سازی باینری، پیاده‌سازی‌هایی مانند Protobuf و MsgPack وجود دارند، اما به اندازهٔ JSON پرکاربرد نیستند. بسیاری از پروژه‌های سطح‌پایین فرمت خودشان را اختراع می‌کنند. دلیلش این است که سریال‌سازی باینری ساده است و ارزش افزودن وابستگی کتابخانه را ندارد. فرمت‌های متنی به دلیل پیچیدگی‌شان بهتر است توسط یک کتابخانه مدیریت شوند.

۰۱۰۳: ذخیره‌سازی لاگ

لاگ‌های فقط‌الحاقی (Append-only)

مانند لاگ‌های متنی، یک لاگ پایگاه داده فقط ورودی‌ها را به انتهای فایل اضافه می‌کند و هرگز ورودی‌های موجود را تغییر نمی‌دهد یا حذف نمی‌کند. ورودی‌های لاگ هر به‌روزرسانی پایگاه داده را ثبت می‌کنند. مثلاً یک لاگ با ۴ رکورد:

عملیات وضعیت
0 {}
1 set k1=x {k1=x}
2 set k2=y {k1=x, k2=y}
3 set k1=z {k1=z, k2=y}
4 del k2 {k1=z}

وقتی پایگاه داده شروع به کار می‌کند، لاگ را می‌خواند و به‌ترتیب به‌روزرسانی‌ها را اعمال می‌کند و وضعیت نهایی {k1=z} را تولید می‌کند. این به‌روزرسانی افزایشی (incremental updates) را پیاده‌سازی می‌کند. این یکی از دلایل استفاده از لاگ است. کاربردهای دیگر بعداً ظاهر می‌شوند.

شاید بپرسید: رکوردهای قدیمی لاگ چگونه حذف می‌شوند؟ این بعداً حل می‌شود: وقتی لاگ به اندازهٔ معینی رسید، در ساختار دادهٔ اصلی (درخت LSM یا درخت B+) ادغام می‌شود.

لاگ هر تغییر وضعیت را ثبت می‌کند. حتی با تراکنش‌های همزمان، تا وقتی سیستم توزیع‌شده نباشد، تغییرات وضعیت را می‌توان در لاگ سری‌سازی کرد. بنابراین لاگ‌ها می‌توانند برای تکرار (replication) و بازگردانی (rollback) استفاده شوند. اما یک لاگ نمی‌تواند بی‌نهایت رشد کند، بنابراین نمی‌تواند ذخیره‌گاه اصلی باشد و فقط کمکی است. لاگ به‌طور سخت‌گیرانه الزامی نیست؛ یک پایگاه داده را می‌توان بر ساختارهای دادهٔ کپی-هنگام-نوشتن (copy-on-write) با رفتاری لاگ‌مانند نیز بنا کرد.

رکوردهای لاگ

از مثال بالا، لاگ ۲ نوع رکورد دارد: به‌روزرسانی و حذف. بنابراین یک پرچم به Entry اضافه می‌شود تا آن‌ها را متمایز کند.

gotype Entry struct {
    key     []byte
    val     []byte
    deleted bool
}

فرمت سریال‌سازی به این شکل در می‌آید:

text| key size | val size | deleted | key data | val data |
| 4 bytes  | 4 bytes  | 1 byte  |   ...    |   ...    |

این ۲ تابع را تغییر دهید:

gofunc (ent *Entry) Encode() []byte
func (ent *Entry) Decode(r io.Reader) error

خواندن و نوشتن فایل لاگ

تعریف ساختار:

gotype Log struct {
    FileName string
    fp       *os.File
}

func (log *Log) Open() (err error) {
    log.fp, err = os.OpenFile(log.FileName, os.O_RDWR|os.O_CREATE, 0o644)
    return err
}

func (log *Log) Close() error {
    return log.fp.Close()
}

رابط‌های ورودی/خروجی لاگ:

gofunc (log *Log) Write(ent *Entry) error {
    _, err := log.fp.Write(ent.Encode())
    return err
}

func (log *Log) Read(ent *Entry) (eof bool, err error) {
    err = ent.Decode(log.fp)
    if err == io.EOF {
        return true, nil
    } else if err != nil {
        return false, err
    } else {
        return false, nil
    }
}

وقتی پایگاه داده شروع می‌کند، مکرراً Log.Read() را تا پایان فایل صدا می‌زند. پس از آن، هر به‌روزرسانی Log.Write() را برای افزودن به انتهای فایل صدا می‌زند.

Log.Read() پایان فایل را با io.EOF (پایان فایل — End Of File) تشخیص می‌دهد. پس Entry.Decode() باید خطاهای برگشتی io.Reader را منتشر کند.

خلاصه

لاگ به‌روزرسانی‌های افزایشی را روی دیسک ماندگار می‌کند. اما این لاگ همچنان مشکلاتی دارد. اگر در حین کار برق پایگاه داده قطع شود چه اتفاقی می‌افتد؟ این مسئلهٔ بعدی است.

۰۱۰۴: fsync

هشدار: نسخهٔ وب از فصل ۰۴ به بعد فقط دستورالعمل‌های ساده دارد؛ توضیحات مفصل و اطلاعات زمینه‌ای در کتاب کامل آمده است.

اطمینان از رسیدن نوشته‌ها به دیسک

از آنجا که داده روی دیسک ذخیره می‌شود، باید مطمئن شویم واقعاً روی دیسک نوشته شده است. اگر فقط در یک فایل بنویسیم، قطع برق می‌تواند باعث ناپدید شدن فایل یا پر شدن آن از 0x00 شود. این‌ها مشکلاتی هستند که یک پایگاه داده باید حل کند.

یک پایگاه داده تضمین می‌کند دادهٔ نوشته‌شده از بین نمی‌رود. این معمولاً ماندگاری (durability) نامیده می‌شود. این تضمین با بازگشت موفق به فراخواننده تعریف می‌شود. اگر پایگاه داده قبل از بازگشت خراب شود، وضعیت برای فراخواننده نامعلوم است. اما اگر فراخواننده موفقیت دریافت کند، می‌تواند به ناپدید نشدن نوشته اعتماد کند.

کش و fsync

هر نوشتن فایل مستقیماً به نوشتن دیسک نگاشت نمی‌شود. سیستم‌عامل یک کش حافظه دارد. نوشته‌ها اول به کش می‌روند و بعداً به دیسک همگام می‌شوند. این امکان ادغام نوشته‌های تکراری را می‌دهد و توان عملیاتی (throughput) را بهبود می‌بخشد. خواندن‌های تکراری نیز سود می‌برند.

این کش، کش صفحه (page cache) نامیده می‌شود. «صفحه» در این‌جا با صفحهٔ حافظهٔ مجازی CPU هم‌خوانی دارد. یک صفحه کوچک‌ترین واحد ورودی/خروجی است و اندازهٔ ثابتی دارد (معمولاً 4K یا 16K). شاید بپرسید کش ورودی/خروجی دیسک چه ربطی به حافظهٔ مجازی دارد. به mmap نگاه کنید. همچنین توجه کنید که مستندات پایگاه داده اغلب گره‌های درخت B را «صفحه» می‌نامند. آن‌ها را با هم اشتباه نگیرید.

علاوه بر کش صفحه، دیسک‌ها ممکن است کش RAM خودشان را هم داشته باشند. برای اطمینان از رسیدن داده به دیسک، یک عملیات باید همهٔ لایه‌های کش را تخلیه کند و منتظر تکمیل بماند. این همان فراخوانی سیستمی fsync در لینوکس است. در Go، آن را از طریق Sync() روی *os.File صدا می‌زنید.

gofunc (log *Log) Write(ent *Entry) error {
    if _, err := log.fp.Write(ent.Encode()); err != nil {
        return err
    }
    return log.fp.Sync() // فراخوانی fsync
}

ویندوز عملیات متناظری دارد، بنابراین Sync() در آنجا هم کار می‌کند.

برخی رابط‌های فایل نیز کش‌هایی دارند که باید تخلیه شوند؛ مانند fflush() در C. ورودی/خروجی فایل Go مستقیماً به رابط‌های سیستم‌عامل نگاشت می‌شود و کش اضافی ندارد.

fsync روی پوشهٔ والد

در لینوکس، fsync نوشته‌شدن دادهٔ فایل را تضمین می‌کند، اما وجود خود فایل را تضمین نمی‌کند. این به این دلیل است که یک فایل توسط پوشهٔ والدش ثبت می‌شود. اگر ورودی دایرکتوری (ایجاد فایل) اضافه شود اما قبل از قطع برق روی دیسک نوشته نشود، حتی اگر دادهٔ آن روی دیسک باشد، نمی‌توان به فایل دسترسی یافت. برای رفع این مشکل، fsync را روی پوشه صدا بزنید.

یعنی: ایجاد فایل، تغییر نام فایل و حذف فایل — همه به fsync روی پوشهٔ حاوی آن‌ها نیاز دارند.

این مخصوص یونیکس است. ویندوز به آن نیاز ندارد. کتابخانهٔ استاندارد Go متدی برای fsync کردن یک پوشه ندارد، بنابراین باید مستقیماً فراخوانی‌های سیستمی را صدا بزنید:

gofunc createFileSync(file string) (*os.File, error) {
    fp, err := os.OpenFile(file, os.O_RDWR|os.O_CREATE, 0o644)
    if err != nil {
        return nil, err
    }
    if err = syncDir(path.Base(file)); err != nil {
        _ = fp.Close()
        return nil, err
    }
    return fp, err
}

func syncDir(file string) error {
    flags := os.O_RDONLY | syscall.O_DIRECTORY
    dirfd, err := syscall.Open(path.Dir(file), flags, 0o644)
    if err != nil {
        return err
    }
    defer syscall.Close(dirfd)
    return syscall.Fsync(dirfd)
}

os.OpenFile() را با این تابع جایگزین کنید:

gofunc (log *Log) Open() (err error) {
    log.fp, err = createFileSync(log.FileName)
    return err
}

مبانی یونیکس

open یک فایل را باز یا ایجاد می‌کند و در صورت موفقیت یک عدد برمی‌گرداند. این عدد فایل را شناسایی می‌کند و برای عملیات بعدی مانند fsync استفاده می‌شود. این عدد توصیفگر فایل (file descriptor یا fd) نامیده می‌شود.

توصیفگر فایل فقط به فایل‌ها محدود نیست. می‌تواند به منابع دیگر سیستم‌عامل اشاره کند، مانند سوکت‌های شبکه یا پوشه‌ها. در یونیکس، open می‌تواند پوشه‌ها را باز کند، هرچند fd برگشتی را نمی‌توان مانند یک فایل خواند یا نوشت. همهٔ fdها باید بسته شوند.

می‌توانید کد منبع os.File را در کتابخانهٔ استاندارد بخوانید. عمدتاً فراخوانی‌های سیستمی مختلف را در خود می‌پیچد.

خلاصه

ماندگاری از طریق fsync به دست می‌آید. اما این هنوز برای موارد قطع برق کافی نیست: ممکن است یک رکورد لاگ قبل از خرابی فقط نیمه‌نوشته باشد (مسئلهٔ اتمی بودن). این را در گام بعدی حل می‌کنیم.

۰۱۰۵: جمع کنترلی (Checksum)

هشدار: نسخهٔ وب از فصل ۰۴ به بعد فقط دستورالعمل‌های ساده دارد؛ توضیحات مفصل و اطلاعات زمینه‌ای در کتاب کامل آمده است.

نوشتن‌های ناقص

هنگام افزودن یک رکورد به لاگ، می‌خواهیم یا کاملاً نوشته شود یا اصلاً نوشته نشود. این را می‌توان اتمی بودن (atomicity) نامید. نوشتن‌های ناقص به نام torn writes (نوشتن‌های پاره‌پاره) شناخته می‌شوند. اما نوشتن فایل در صورت قطع برق اتمی بودن را تضمین نمی‌کند. نه‌تنها دادهٔ افزوده‌شده اتمی نیست، بلکه حتی اندازهٔ فایل هم ممکن است نادرست باشد. مثلاً افزودن یک رکورد ۱۰۰۰ بایتی ممکن است به یکی از وضعیت‌های زیر منجر شود:

  1. اندازهٔ فایل ۱۰۰۰ افزایش می‌یابد، اما داده کاملاً نوشته نشده است.
  2. اندازهٔ فایل ۱۰۰۰ افزایش می‌یابد، اما هیچ داده‌ای نوشته نمی‌شود و فضای جدید با ۰ها یا زباله پر می‌شود.
  3. اندازهٔ فایل ۵۰۰ افزایش می‌یابد.

در هر صورت، فقط آخرین رکورد تحت تأثیر قرار می‌گیرد، در حالی‌که رکوردهایی که قبلاً fsync شده‌اند دست‌نخورده می‌مانند. این دلیل دیگری برای استفاده از لاگ در پایگاه داده‌هاست.

اتمی بودن نوشتن دیسک

CPU عملیات اتمی خواندن/نوشتن حافظه را فراهم می‌کند که داده‌ای به اندازهٔ یک عدد صحیح را مدیریت می‌کند. در حالی‌که عملیات اتمی CPU بر همزمانی تمرکز دارد، ما اتمی بودن برای ماندگاری در صورت قطع برق را در نظر می‌گیریم. در سطح سخت‌افزار، نوشتن یک سکتور واحد به احتمال زیاد اتمی است. سکتور کوچک‌ترین واحد خواندن/نوشتن دیسک است که معمولاً 512B یا 4K است.

بسیاری از سیستم‌های نرم‌افزاری برای رسیدن به اتمی بودن در مقیاس بزرگ‌تر به اتمی بودن در سطح سکتور تکیه می‌کنند. مثلاً هنگام نوشتن لاگ، می‌توان یک سکتور در ابتدای لاگ رزرو کرد تا موقعیت آخرین ورودی لاگ را ذخیره کند. پس از اینکه لاگ با موفقیت fsync شد، سکتور به‌روزرسانی می‌شود (از جمله fsync کردن همین سکتور). این اتمی بودن کل لاگ را تضمین می‌کند.

حتی بدون اتمی بودن در سطح سخت‌افزار، نرم‌افزار می‌تواند بدون نیاز به ۲ بار fsync به اتمی بودن برسد.

جمع کنترلی

فرض کنید نوشتن‌های لاگ اتمی نیستند، اما اگر بتوانیم نوشتن ناقص را تشخیص دهیم، به‌سادگی آن را نادیده می‌گیریم. آخرین رکوردِ آسیب‌دیده، رکوردِ قبل از آخرین fsync موفق خواهد بود. یک جمع کنترلی (checksum) این‌جا کمک می‌کند. جمع کنترلی یک هش است و داده‌های مختلف تقریباً به‌طور قطع جمع کنترلی‌های متفاوتی دارند. با ذخیرهٔ جمع کنترلی برای هر رکورد، می‌توانیم نوشتن‌های ناقص را شناسایی کنیم.

برای محاسبهٔ جمع کنترلی رکوردهای لاگ از crc32.ChecksumIEEE() کتابخانهٔ استاندارد استفاده کنید و آن را به ابتدای رکورد بچسبانید:

text|  crc32  | key size | val size | deleted | key data | val data |
| 4 bytes | 4 bytes  | 4 bytes  | 1 byte  |   ...    |   ...    |

این توابع را تغییر دهید:

gofunc (ent *Entry) Encode() []byte
func (ent *Entry) Decode(r io.Reader) error

var ErrBadSum = errors.New("bad checksum")

Entry.Decode() باید خطاهای مناسب را برگرداند:

  • ErrBadSum: عدم تطابق جمع کنترلی (داده کامل نوشته نشده است).
  • io.EOF: به پایان فایل رسیدیم (همهٔ رکوردها معتبرند).
  • io.ErrUnexpectedEOF: فایل زودتر از موعد تمام شد (اندازهٔ فایل نادرست است، داده کامل نوشته نشده است).

io.ReadFull()

واسط io.Reader اجازه می‌دهد بایت‌های کمتری از طول خواسته‌شدهٔ buf برگردد. مثلاً درخواست ۴ بایت ممکن است فقط ۳ بایت برگرداند، اما این به معنی پایان داده (eof) نیست. هرچند هنگام خواندن از فایل معمولاً این اتفاق نمی‌افتد، در منابعی مانند سوکت‌های TCP رایج است. پس هنگام استفاده از io.Reader باید حلقه بزنید تا تعداد بایت‌های برگشتی اندازهٔ بافر را پر کند. io.ReadFull() کتابخانهٔ استاندارد می‌تواند جای این حلقه را بگیرد:

gofunc ReadFull(r Reader, buf []byte) (n int, err error)

اگر بافر فقط تا حدی پر شود و به eof برسیم، io.ReadFull() io.ErrUnexpectedEOF برمی‌گرداند. این دقیقاً با الزام‌های تابع Decode() هم‌خوانی دارد.

مدیریت رکوردهای ناقص لاگ

خطای برگشتی از Entry.Decode() را بررسی کنید تا آخرین رکورد ناقص لاگ را نادیده بگیرید؛ یعنی eof=true.

gofunc (log *Log) Read(ent *Entry) (eof bool, err error)

مورد تست این گام، بازیابی از آخرین نوشتن ناقص لاگ را شبیه‌سازی می‌کند.

شاید بپرسید: از کجا بدانیم جمع کنترلی ناموفق مربوط به آخرین ورودی لاگ است؟ هیچ راهی برای دانستن نیست، زیرا سربرگ اندازهٔ رکورد ممکن است نادرست باشد.

کاربرد جمع کنترلی

علاوه بر نوشتن‌های ناقص، جمع کنترلی‌ها می‌توانند خرابی دادهٔ ناشی از نقص سخت‌افزار را هم تشخیص دهند؛ مانند بیت‌های برگشته (flipped bits) به دلیل خطای دیسک یا حافظه. این اتفاق با سخت‌افزار معمولی نادر است. با این حال، این هدف جمع کنترلی در پایگاه داده نیست، زیرا پایگاه داده نمی‌تواند از چنین تلفات خاموش داده‌ای بازیابی کند. اگر رکوردی در میانهٔ لاگ خراب شود، دانستن اینکه رکوردهای بعدی وجود دارند یا نه غیرممکن است.

توابع هش رمزنگاری (مانند sha256 یا md5) نیز می‌توانند به‌عنوان جمع کنترلی استفاده شوند. اما دلیلی برای استفاده از آن‌ها وجود ندارد، زیرا توابع جمع کنترلی تخصصی کوچک‌تر و سریع‌ترند. حتی روش‌های سادهٔ جمع کنترلی، مانند جمع ۱۶ بیتی عدد صحیحی که در TCP/IP استفاده می‌شود، کافی‌اند. اما باید مراقب حالت همه‌صفر بودن بایت‌ها بود. در چنین حالتی، جمع کنترلی نباید ۰ باشد و crc32 این مشکل را ندارد.

خلاصه

با لاگ + جمع کنترلی + fsync، پایگاه داده می‌تواند پس از قطع برق بازیابی کند و تضمین کند نوشته‌های موفق قبلی از بین نمی‌روند. این هستهٔ عملکرد یک پایگاه داده است. به همین دلیل SQLite معمولاً برای ذخیره‌سازی دادهٔ موبایل استفاده می‌شود، نه صرفاً نوشتن JSON در یک فایل. فقط برای سهولت پرس‌وجو نیست؛ بلکه به این دلیل است که عملیات فایل پایه نمی‌توانند ماندگاری و اتمی بودن را تضمین کنند.

فعلاً فقط یک لاگ داریم. اگر در آینده ساختارهای داده اضافه شوند، اتمی بودن و ماندگاری (A و D در ACID) باید از نو بررسی شوند.

۰۲ — جدول‌ها

۰۲۰۱: انواع داده

یونیون (Union)

این گام استفاده از KV برای ساخت یک پایگاه دادهٔ رابطه‌ای را شروع می‌کند. مانند اکسل، یک پایگاه داده می‌تواند جدول‌های زیادی داشته باشد. یک جدول ردیف‌ها و ستون‌ها دارد. هر ستون می‌تواند یک نوع داده انتخاب کند، برخلاف KV که فقط string/bytes دارد. ما ۲ نوع داده را پیاده‌سازی می‌کنیم: int64 و []byte.

gotype CellType uint8

const (
    TypeI64 CellType = 1
    TypeStr CellType = 2
)

type Cell struct {
    Type CellType
    I64  int64
    Str  []byte
}

Cell انواع دادهٔ مختلف را نشان می‌دهد. بر اساس Type متمایز می‌شود و داده یا I64 است یا Str. Go نوع یونیون ندارد، بنابراین کمی فضا هدر می‌رود.

سریال‌سازی

این گام سریال‌سازی و سریال‌زدایی Cell را پیاده‌سازی می‌کند:

gofunc (cell *Cell) Encode(toAppend []byte) []byte {
    switch cell.Type {
    case TypeI64:
        // TODO
    case TypeStr:
        // TODO
    }
}

func (cell *Cell) Decode(data []byte) (rest []byte, err error)

الزام‌ها:

  • Cell.Encode() نتیجهٔ سریال‌شده را به slice ورودی می‌چسباند. وقتی بعداً یک ردیف را سریال می‌کنیم، چند مقدار Cell به هم می‌چسبند. می‌توان از همان slice برای جلوگیری از تخصیص حافظهٔ تکراری استفاده مجدد کرد.
  • Cell.Decode() از slice ورودی سریال‌زدایی می‌کند و دادهٔ باقی‌مانده را برمی‌گرداند.
  • int64 از binary.LittleEndian استفاده می‌کند. []byte از این قالب استفاده می‌کند:
text| length  | data |
| 4 bytes | ...  |

ترتیب بایت‌ها (Endianness)

یک CPU از اعداد دودویی اندازه‌ثابت استفاده می‌کند، معمولاً ۸، ۱۶، ۳۲ یا ۶۴ بیت. بیت ۰ کم‌ارزش‌ترین بیت است. مثلاً 0b0101 = 4 + 1 = 5. از بیت ۰ تا بیت ۳، مقادیر ۱، ۰، ۱، ۰ هستند. وقتی عددی را روی کاغذ می‌نویسیم، ارقام کم‌ارزش در سمت راست و ارقام پرارزش در سمت چپ قرار می‌گیرند. وقتی آرایه‌ای را می‌نویسیم، عنصر ۰ در سمت چپ است و آدرس‌های حافظهٔ بالاتر در سمت راست. این تفاوت به اندین بزرگ (big endian) و اندین کوچک (little endian) منجر می‌شود.

یک عدد صحیح ۳۲ بیتی در ثبات CPU فقط ۳۲ بیت است. وقتی در حافظه ذخیره می‌شود، به ۴ بایت گروه‌بندی می‌شود. اگر بایت‌ها از ترتیب طبیعی پیروی کنند (بیت‌های کم‌ارزش در بایت ۰ و بیت‌های پرارزش در بایت ۳)، اندین کوچک است. اگر از ترتیب نوشتاری پیروی کنند (بیت‌های کم‌ارزش در بایت ۳ و پرارزش در بایت ۰)، اندین بزرگ است. مثلاً 0x11223344 در هگزادسیمال: اندین کوچک 44 33 22 11 و اندین بزرگ 11 22 33 44 است.

از نظر تاریخی، برخی رایانه‌ها از اندین بزرگ استفاده می‌کردند. به همین دلیل بسیاری از پروتکل‌های شبکه مانند TCP/IP از اندین بزرگ استفاده می‌کنند. امروزه اندین کوچک غالب است. یک CPU اندین کوچک باید دادهٔ اندین بزرگ را تبدیل کند که کار اضافی است. فرمت‌ها و پروتکل‌های جدید داده بیشتر از اندین کوچک استفاده می‌کنند. اندین بزرگ هنوز یک کاربرد خاص دارد (مرتب‌سازی) که بعداً ظاهر می‌شود.

اعداد صحیح علامت‌دار و بی‌علامت

شاید متوجه شوید که binary.LittleEndian فقط متدهایی با uint64 دارد و هیچ متدی برای int64 ندارد. این به این دلیل است که اعداد صحیح علامت‌دار و بی‌علامت را می‌توان مستقیماً تبدیل کرد:

gocell.I64 = int64(binary.LittleEndian.Uint64(data[0:8]))

باید بدانید اعداد منفی چگونه رمزگذاری می‌شوند. با int64 به‌عنوان مثال:

  • اعداد مثبت [0, 263) از همان رمزگذاری uint64 استفاده می‌کنند.
  • اعداد منفی [−263, 0) با [263, 264) در uint64 هم‌خوانی دارند.

تبدیل بین uint64 و int64 یعنی هیچ کاری نکردن. اثر آن:

  • محدودهٔ uint64 به دو نیم تقسیم می‌شود. اعداد مثبت int64 و ۰ به نیمهٔ اول نگاشت می‌شوند. اعداد منفی به نیمهٔ دوم نگاشت می‌شوند.
  • برای اعداد مثبت کوچک، uint64 و int64 در بیت‌ها یکسان به‌نظر می‌رسند.

تفاوت اعداد صحیح علامت‌دار و بی‌علامت فقط در نحوهٔ تفسیر بیت‌ها توسط CPU است. از آنجا که تبدیل واقعی وجود ندارد، می‌توانیم آزادانه از تبدیل نوع استفاده کنیم.

بیت علامت

بالاترین بیت یک عدد صحیح علامت‌دار نشان می‌دهد که آیا منفی است. خیلی‌ها ساده‌لوحانه فرض می‌کنند رایانه‌ها اعداد را به‌صورت علامت + قدر مطلق ذخیره می‌کنند. آن روش فقط توسط برخی ماشین‌های قدیمی استفاده می‌شد. رایانه‌های مدرن از روش بالا استفاده می‌کنند که مکمل دو (two's complement) نامیده می‌شود. اگر علامت + قدر مطلق استفاده می‌شد، هم +0 و هم -0 وجود داشت که فقط در اعداد اعشاری (floating point) وجود دارد، نه در اعداد صحیح.

۰۲۰۲: طرحوارهٔ جدول

ساختارها

نام جدول، نام ستون‌ها، نوع ستون‌ها، کلید اصلی:

gotype Schema struct {
    Table string
    Cols  []Column
    PKey  []int // کدام ستون‌ها کلید اصلی هستند؟
}
type Column struct {
    Name string
    Type CellType
}

مثلاً این جدول:

sqlcreate table `link` (
    `time` int64 not null,
    `src` string not null,
    `dst` string not null,
    primary key (`src`, `dst`)
);

این‌گونه نمایش داده می‌شود:

go    schema := &Schema{
        Table: "link",
        Cols: []Column{
            {Name: "time", Type: TypeI64},
            {Name: "src", Type: TypeStr},
            {Name: "dst", Type: TypeStr},
        },
        PKey: []int{1, 2}, // (src, dst)
    }

کلید اصلی

کلید اصلی (primary key) شناسهٔ یکتای یک ردیف است. از ۱ ستون یا بیشتر ساخته می‌شود. برای کار با یک ردیف، ابتدا باید آن را با کلید اصلی پیدا کنید. بنابراین کلید اصلی همان K در KV است و ستون‌های غیرکلیداصلی در V ذخیره می‌شوند. این به یک فروشگاه KV اجازه می‌دهد یک پایگاه دادهٔ رابطه‌ای (از نوع OLTP) پیاده‌سازی کند.

علاوه بر کلیدهای اصلی، ایندکس‌ها نیز با KV ساخته می‌شوند. یک ایندکس به شما اجازه می‌دهد کلید اصلی K را پیدا کنید و سپس با آن به V برسید. مانند یک کتاب: شمارهٔ صفحه کلید اصلی است، در حالی‌که «فهرست مطالب» و «نمایه» (index) ایندکس‌ها هستند. آن‌ها به شما کمک می‌کنند شمارهٔ صفحه را پیدا کنید و سپس محتوا را. در برخی موارد، یک ایندکس از قبل دادهٔ کافی دارد، بنابراین لازم نیست V خوانده شود؛ مانند اینکه فقط فهرست مطالب را بخوانید.

هم کلیدهای اصلی و هم ایندکس‌ها KV هستند. تفاوت این است که کلید اصلی اجباری است. بنابراین ایندکس‌ها را ایندکس ثانویه (secondary index) نیز می‌نامند و کلید اصلی را کلید اصلی می‌نامند. برخی پایگاه داده‌ها مانند SQLite به جدول‌هایی بدون کلید اصلی تعریف‌شده توسط کاربر اجازه می‌دهند. این به این دلیل است که جدول‌های SQLite یک کلید اصلی پنهان و خودکارتولیدشده دارند. کلیدهای اصلی قابل‌مشاهده برای کاربر فقط ایندکس‌های عادی هستند و تفاوت واقعی بین اصلی و ثانویه وجود ندارد.

رمزگذاری یک ردیف به‌صورت KV

یک ردیف در پایگاه داده این‌گونه نمایش داده می‌شود:

gotype Row []Cell

func (schema *Schema) NewRow() Row {
    return make(Row, len(schema.Cols))
}

Schema.NewRow() ردیفی با اندازهٔ درست برمی‌گرداند، بدون مقداردهی.

سپس سریال‌سازی و سریال‌زدایی را پیاده‌سازی کنید:

gofunc (row Row) EncodeKey(schema *Schema) (key []byte)
func (row Row) EncodeVal(schema *Schema) (val []byte)
func (row Row) DecodeKey(schema *Schema, key []byte) (err error)
func (row Row) DecodeVal(schema *Schema, val []byte) (err error)

الزام‌ها:

  • ردیف‌های ورودی یا خروجی باید با طرحواره (schema) مطابقت داشته باشند.
  • از Cell.Encode() و Cell.Decode() گام قبل استفاده کنید.
  • ترتیب ستون‌های تعریف‌شده در طرحواره را دنبال کنید.

پیشوند کلید

یک پایگاه داده جدول‌های زیادی دارد، بنابراین کلیدهای رمزگذاری‌شده به پیشوندی نیاز دارند تا جدول‌ها را از هم متمایز کند. از نام جدول استفاده می‌کنیم:

gofunc (row Row) EncodeKey(schema *Schema) (key []byte) {
    key = append([]byte(schema.Table), 0x00)
    // TODO
}

بعد از نام جدول یک جداکنندهٔ 0x00 اضافه می‌شود تا از تداخل کلیدهای ناشی از پیشوند نام‌ها جلوگیری شود. مثلاً نام جدول‌های ab و abc پیشوندهای "ab\x00" و "abc\x00" دارند.

در عمل، می‌توانید یک شناسهٔ عدد صحیح به‌عنوان پیشوند اختصاص دهید. این فضا را ذخیره می‌کند و به شما امکان تغییر نام جدول‌ها را می‌دهد.

۰۲۰۳: حالت‌های به‌روزرسانی

اکنون می‌توانیم عملیات SQL را به KV نگاشت کنیم. مثلاً select → get و delete → del.

اما عملیات set در KV به‌نظر هم درج (insert) است و هم به‌روزرسانی (update). در واقع همان insert ... on duplicate update است. این یک مورد استفادهٔ رایج است. PostgreSQL یک عبارت upsert اضافه می‌کند تا با عملیات set در KV هم‌خوانی داشته باشد.

ما باید رفتار insert و update را به KV اضافه کنیم. SetEx() را اضافه کنید:

gotype UpdateMode int

const (
    ModeUpsert UpdateMode = 0 // درج یا به‌روزرسانی
    ModeInsert UpdateMode = 1 // درج جدید
    ModeUpdate UpdateMode = 2 // به‌روزرسانی دادهٔ موجود
)

func (kv *KV) SetEx(key []byte, val []byte, mode UpdateMode) (bool, error)

الزام‌ها:

  • ModeInsert: اگر کلید از قبل وجود دارد، به‌روزرسانی نکنید و false برگردانید.
  • ModeUpdate: فقط کلیدهای موجود را به‌روزرسانی کنید.
  • ModeUpsert: مانند Set() قدیمی، درج یا بازنویسی:
gofunc (kv *KV) Set(key []byte, val []byte) (updated bool, err error) {
    return kv.SetEx(key, val, ModeUpsert)
}

۰۲۰۴: CRUD

افزودن رابط‌های CRUD

این گام CRUD مبتنی بر کلید اصلی (create، read، update، delete) را پیاده‌سازی می‌کند که با insert و select و update و delete هم‌خوانی دارد.

gotype DB struct {
    KV KV
}

func (db *DB) Open() error  { return db.KV.Open() }
func (db *DB) Close() error { return db.KV.Close() }

با استفاده از get، set و del در KV این‌ها را پیاده‌سازی کنید:

gofunc (db *DB) Select(schema *Schema, row Row) (ok bool, err error)
func (db *DB) Insert(schema *Schema, row Row) (updated bool, err error)
func (db *DB) Upsert(schema *Schema, row Row) (updated bool, err error)
func (db *DB) Update(schema *Schema, row Row) (updated bool, err error)
func (db *DB) Delete(schema *Schema, row Row) (deleted bool, err error)

الزام‌ها:

  • select و delete: ردیف ورودی شامل کلید اصلی است.
  • insert و upsert و update: ردیف ورودی کامل است.

مثلاً insert:

gofunc (db *DB) Insert(schema *Schema, row Row) (updated bool, err error) {
    key := row.EncodeKey(schema)
    val := row.EncodeVal(schema)
    return db.KV.SetEx(key, val, ModeInsert)
}

برای جدول create table t (a int64, b int64, primary key (b))، Select() یک Row به طول ۲ می‌گیرد. ستون ۲ کلید اصلی است. ستون ۱ مقداری است که از KV برگشته است.

ویژگی‌های اصلی پایگاه داده‌های رابطه‌ای

علاوه بر دسترسی تک‌ردیفی با کلید اصلی، گام‌های بعدی ممکن است اضافه کنند:

  • پیمایش کامل جدول (full table scan).
  • پرس‌وجو با ایندکس.
  • پرس‌وجوی بازه‌ای (range query) با ایندکس یا کلید اصلی.
  • فیلتر کردن نتایج پرس‌وجو.

۰۳ — SQL ساده

۰۳۰۱: توکنایزر

رشته ← توکن‌ها ← ساختار

یک رشتهٔ SQL قبل از پردازش باید به دادهٔ برنامه تجزیه شود. مثلاً:

sqlselect a,b from t where c=1;

این‌گونه نمایش داده می‌شود:

goStmtSelect{
    table: "t",
    cols:  []string{"a", "b"},
    keys:  []NamedCell{{column: "c", value: Cell{Type: TypeI64, I64: 1}}},
}

SQL شبیه انگلیسی است و واژه‌ها و دستور زبان خودش را دارد. در زبان‌های برنامه‌نویسی، واژه‌ها توکن (token) نامیده می‌شوند. قبل از تجزیهٔ دستور زبان، رشته به توکن‌ها تقسیم می‌شود. این گام توکنایز کردن (tokenizing) یا واژه‌گذاری (lexing) نامیده می‌شود.

توکن‌های SQL را می‌توان گروه‌بندی کرد:

  • کلمه‌های کلیدی (keywords): select، from و مانند آن.
  • نام‌ها (names): نام جدول‌ها، نام ستون‌ها و مانند آن.
  • نمادها (symbols): =; و کاما و مانند آن.
  • اعداد، رشته‌ها و مانند آن.

هر نوع قواعد متفاوتی دارد و در توابع مختلف کدنویسی می‌شود.

تجزیه‌گر دستور زبان (Syntax Parser)

بیشتر تجزیه با مصرف توکن‌ها از چپ به راست و ساخت ساختارهای داده کار می‌کند. بنابراین باید موقعیت فعلی در رشته را پیگیری کنیم.

gotype Parser struct {
    buf string
    pos int
}
func NewParser(s string) Parser {
    return Parser{buf: s, pos: 0}
}

تجزیهٔ نام‌ها (نام جدول‌ها، نام ستون‌ها)

gofunc (p *Parser) tryName() (string, bool)

الزام‌ها:

  • از فاصله‌های ابتدایی عبور کند.
  • کاراکتر اول یک حرف یا _ باشد؛ کاراکترهای بعدی حرف، رقم یا _ باشند.
  • در صورت موفقیت، true برگرداند و pos را جلو ببرد.
  • در صورت شکست، false برگرداند و pos را حفظ کند.

مثلاً ورودی Parser {buf: " hi ", pos: 0}. بعد از tryName()، مقدار pos = 3 و خروجی "hi" است.

از این توابع کمکی استفاده کنید:

gofunc isSpace(ch byte) bool {
    switch ch {
    case '\t', '\n', '\v', '\f', '\r', ' ':
        return true
    }
    return false
}
func isAlpha(ch byte) bool {
    return 'a' <= (ch|32) && (ch|32) <= 'z'
}
func isDigit(ch byte) bool {
    return '0' <= ch && ch <= '9'
}
func isNameStart(ch byte) bool {
    return isAlpha(ch) || ch == '_'
}
func isNameContinue(ch byte) bool {
    return isAlpha(ch) || isDigit(ch) || ch == '_'
}

تجزیهٔ کلمه‌های کلیدی

gofunc (p *Parser) tryKeyword(kw string) bool

الزام‌ها:

  • از فاصله‌های ابتدایی عبور کند.
  • کلمهٔ کلیدی را بدون حساسیت به بزرگ/کوچک‌بودن حروف تطبیق دهد. در صورت موفقیت، pos را جلو ببرد و true برگرداند.
  • در غیر این صورت false برگرداند.
  • کلمه‌های کلیدی باید با فاصله یا نشانهٔ نقطه‌گذاری جدا شوند.

برای تشخیص جداکننده‌ها از این استفاده کنید:

gofunc isSeparator(ch byte) bool {
    return ch < 128 && !isNameContinue(ch)
}

۰۳۰۲: تجزیهٔ مقادیر

فعلاً فقط ۲ نوع داده پیاده‌سازی شده است: int64 و رشته. آن‌ها با کاراکتر اول متمایز می‌شوند:

gofunc (p *Parser) parseValue(out *Cell) error {
    p.skipSpaces()
    if p.pos >= len(p.buf) {
        return errors.New("expect value")
    }
    ch := p.buf[p.pos]
    if ch == '"' || ch == '\'' {
        return p.parseString(out)
    } else if isDigit(ch) || ch == '-' || ch == '+' {
        return p.parseInt(out)
    } else {
        return errors.New("expect value")
    }
}

وقتی بعداً تجزیهٔ دستور زبان را پیاده‌سازی می‌کنید، خواهید دید که بسیاری از زبان‌ها می‌توانند بر اساس چند توکن اول تصمیم بگیرند که بعدش چه چیزی را تجزیه کنند.

تجزیهٔ int64

قواعد int64 ساده است: ممکن است با - یا + شروع شود و بعد ارقام بیایند.

gofunc (p *Parser) parseInt(out *Cell) error

تجزیهٔ رشته‌ها

gofunc (p *Parser) parseString(out *Cell) error

قواعد پیچیده‌ترند:

  • با نقل‌قول تکی یا دوتایی محصور می‌شود.
  • نقل‌قول‌های داخل رشته باید با اسلش فرار شوند (escape).
  • یک اسلش نیز باید با اسلش فرار شود.

مثلاً "isn\'t" و 'isn\'t' هر دو یعنی isn't.

برای کاربردی‌کردن این، فرارهای بیشتری لازم است؛ مانند \n، \xFF و \u3412. اما موضوعات مهم‌تری برای یادگیری داریم، پس این‌جا متوقف می‌شویم.

۰۳۰۳: تجزیهٔ SELECT

ساختارها

از آنجا که فقط مجموعهٔ کوچکی از قابلیت‌ها پیاده‌سازی شده، عبارت SELECT ما فقط یک شکل ثابت را پشتیبانی می‌کند: پرس‌وجوی یک ردیف منفرد با کلید اصلی. مثلاً برای جدولی با کلید اصلی (c, d)، تنها پرس‌وجوی پشتیبانی‌شده این است:

sqlselect a,b from t where c=1 and d='e';

که به‌صورت ساختارهای داده نمایش داده می‌شود:

goStmtSelect{
    table: "t",
    cols: []string{"a", "b"},
    keys: []NamedCell{
        {column: "c", value: Cell{Type: TypeI64, I64: 1}},
        {column: "d", value: Cell{Type: TypeStr, Str: []byte("e")}},
    },
}

ساختارها فعلاً این‌گونه تعریف می‌شوند و بعداً گسترش می‌یابند:

gotype StmtSelect struct {
    table string
    cols  []string
    keys  []NamedCell
}
type NamedCell struct {
    column string
    value  Cell
}

تجزیهٔ دستور زبان

تجزیهٔ دستور زبان توکن‌ها را از چپ به راست مصرف می‌کند و هم‌زمان ساختارهای داده را می‌سازد. مثلاً تجزیهٔ a = 123 یک NamedCell تولید می‌کند. به‌ترتیب tryName()، tryPunctuation() و parseValue() را صدا می‌زند:

gofunc (p *Parser) parseEqual(out *NamedCell) error {
    var ok bool
    out.column, ok = p.tryName()
    if !ok {
        return errors.New("expect column")
    }
    if !p.tryPunctuation("=") {
        return errors.New("expect =")
    }
    return p.parseValue(&out.value)
}

یک تابع جدید tryPunctuation() این‌جا اضافه می‌شود. مانند tryKeyword() است، اما یک کاراکتر نقطه‌گذاری مصرف می‌کند. قواعد آن ساده‌تر از کلمه‌های کلیدی است.

هنگام تجزیهٔ بخش WHERE، parseEqual() در یک حلقه صدا زده می‌شود. حتی دستور زبان پیچیده هم پس از تقسیم به بخش‌ها آسان می‌شود.

تجزیهٔ عبارت‌های SELECT

کلمهٔ کلیدی آغازین select برای تمایز عبارت‌های SQL استفاده می‌شود، هرچند فعلاً فقط یکی پشتیبانی می‌شود. سپس فهرستی از نام ستون‌ها می‌آید که با کاما جدا شده‌اند و به from ختم می‌شوند.

gofunc (p *Parser) parseSelect(out *StmtSelect) error {
    if !p.tryKeyword("SELECT") {
        return errors.New("expect keyword")
    }
    for !p.tryKeyword("FROM") {
        if len(out.cols) > 0 && !p.tryPunctuation(",") {
            return errors.New("expect comma")
        }
        if name, ok := p.tryName(); ok {
            out.cols = append(out.cols, name)
        } else {
            return errors.New("expect column")
        }
    }
    if len(out.cols) == 0 {
        return errors.New("expect column list")
    }
    var ok bool
    if out.table, ok = p.tryName(); !ok {
        return errors.New("expect table name")
    }
    return p.parseWhere(&out.keys)
}

تجزیهٔ WHERE

این بخش فقط a = 123 را با جداکنندهٔ AND پشتیبانی می‌کند. مانند SELECT a,b است، با این تفاوت که کاما با AND جایگزین می‌شود و tryName() با parseEqual() جایگزین می‌شود. می‌توانید خودتان پیاده‌سازی کنید:

gofunc (p *Parser) parseWhere(out *[]NamedCell) error

سایر عبارت‌ها

sqlcreate table t (

فعلاً فقط عملیات تک‌ردیفی با کلید اصلی پشتیبانی می‌شود، بنابراین بخش WHERE به keys نگاشت می‌شود. پرس‌وجوهای بازه‌ای و ایندکس‌ها بعداً با دستور زبان پیچیده‌تر اضافه خواهند شد.

شناسایی عبارت‌های SQL

parseStmt() را اضافه کنید که با interface{} انواع عبارت متفاوت را برمی‌گرداند:

gofunc (p *Parser) parseStmt() (out interface{}, err error) {
    if p.tryKeyword("SELECT") {
        stmt := &StmtSelect{}
        err = p.parseSelect(stmt)
        out = stmt
    } else if p.tryKeyword("CREATE", "TABLE") {
        stmt := &StmtCreatTable{}
        err = p.parseCreateTable(stmt)
        out = stmt
    } else if p.tryKeyword("INSERT", "INTO") {
        stmt := &StmtInsert{}
        err = p.parseInsert(stmt)
        out = stmt
    } else if p.tryKeyword("UPDATE") {
        stmt := &StmtUpdate{}
        err = p.parseUpdate(stmt)
        out = stmt
    } else if p.tryKeyword("DELETE", "FROM") {
        stmt := &StmtDelete{}
        err = p.parseDelete(stmt)
        out = stmt
    } else {
        err = errors.New("unknown statement")
    }
    if err != nil {
        return nil, err
    }
    return out, nil
}

تابع tryKeyword() به‌روزرسانی می‌شود تا چند توکن را به‌صورت متوالی تطبیق دهد:

gofunc (p *Parser) tryKeyword(kws ...string) bool

از آنجا که parseStmt() توکن‌های آغازین را مصرف می‌کند، parseSelect() قبلی باید به‌روزرسانی شود.

این نشان می‌دهد که هنگام تجزیهٔ SQL، نگاه کردن به ۱ یا ۲ توکن بعدی برای تصمیم‌گیری کافی است. بسیاری از زبان‌ها به همین سادگی قابل تجزیه هستند و به نظریهٔ ساخت کامپایلر نیاز ندارند. حتی با دستور زبانی مانند select a+b*c هم بازگشت کافی است.

۰۳۰۵: اجرای SQL

اجرای SQL تجزیه‌شده

برخی رابط‌های پایگاه دادهٔ رابطه‌ای قبلاً پیاده‌سازی شدند:

gofunc (db *DB) Select(schema *Schema, row Row) (ok bool, err error)
func (db *DB) Insert(schema *Schema, row Row) (updated bool, err error)
func (db *DB) Update(schema *Schema, row Row) (updated bool, err error)
func (db *DB) Delete(schema *Schema, row Row) (deleted bool, err error)

اکنون SQL به انواع StmtXXX تجزیه می‌شود، بنابراین این ۲ بخش می‌توانند به هم متصل شوند:

gotype SQLResult struct {
    Updated int
    Header  []string
    Values  []Row
}

func (db *DB) ExecStmt(stmt interface{}) (r SQLResult, err error) {
    switch ptr := stmt.(type) {
    case *StmtCreatTable:
        err = db.execCreateTable(ptr)
    case *StmtSelect:
        r.Header = ptr.cols
        r.Values, err = db.execSelect(ptr)
    case *StmtInsert:
        r.Updated, err = db.execInsert(ptr)
    case *StmtUpdate:
        r.Updated, err = db.execUpdate(ptr)
    case *StmtDelete:
        r.Updated, err = db.execDelete(ptr)
    default:
        panic("unreachable")
    }
    return
}

SQLResult نتیجهٔ یک عبارت را برمی‌گرداند:

  • SELECT، Header و Values را برمی‌گرداند. این یک slice است چون بعداً چند ردیف برمی‌گرداند.
  • سایر عبارت‌های به‌روزرسانی، Updated یعنی تعداد ردیف‌های متأثر را برمی‌گردانند. فعلاً فقط می‌تواند ۰ یا ۱ باشد.

ذخیرهٔ طرحواره‌های جدول

همهٔ عملیات به طرحواره‌ها وابسته‌اند، بنابراین اول execCreateTable() را پیاده‌سازی کنید. طرحوارهٔ جدول را سریال کنید و آن را زیر یک کلید ذخیره کنید. DB یک کش map اضافه می‌کند که با نام جدول کلید می‌خورد:

gotype DB struct {
    KV     KV
    tables map[string]Schema
}
gofunc (db *DB) GetSchema(table string) (Schema, error) {
    schema, ok := db.tables[table]
    if !ok {
        val, ok, err := db.KV.Get([]byte("@schema_" + table))
        if err == nil && ok {
            err = json.Unmarshal(val, &schema)
        }
        if err != nil {
            return Schema{}, err
        }
        if !ok {
            return Schema{}, errors.New("table is not found")
        }
        db.tables[table] = schema
    }
    return schema, nil
}

execCreateTable() را پیاده‌سازی کنید:

  1. StmtCreatTable را به Schema تبدیل کنید.
  2. Schema را زیر کلید @schema_ + نام جدول ذخیره کنید.
  3. آن را به map DB.tables اضافه کنید.
gofunc (db *DB) execCreateTable(stmt *StmtCreatTable) (err error)

اجرای SELECT

بهتر است این را به توابع کمکی کوچک تقسیم کنید که توسط سایر عبارت‌ها هم قابل استفاده مجدد باشند:

  1. lookupColumns(): نام ستون‌ها (select a,b) را بررسی می‌کند و ایندکس‌هایشان را در schema.Cols برمی‌گرداند.
  2. makePKey(): بررسی می‌کند WHERE با کلید اصلی مطابقت دارد یا نه و یک Row با کلیدِ پر شده برمی‌گرداند.
  3. subsetRow(): فقط ستون‌های موجود در select a,b را برمی‌گرداند.
gofunc (db *DB) execSelect(stmt *StmtSelect) ([]Row, error) {
    schema, ok := db.tables[stmt.table]
    if !ok {
        return nil, errors.New("table is not found")
    }
    indices, err := lookupColumns(schema.Cols, stmt.cols)
    if err != nil {
        return nil, err
    }

    row, err := makePKey(&schema, stmt.keys)
    if err != nil {
        return nil, err
    }
    if ok, err = db.Select(&schema, row); err != nil {
        return nil, err
    }
    if !ok {
        return nil, nil
    }

    row = subsetRow(row, indices)
    return []Row{row}, nil
}

اجرای INSERT، UPDATE و DELETE

سایر عبارت‌های SQL را با صدازدن DB.Insert()، DB.Update() و DB.Delete() پیاده‌سازی کنید:

gofunc (db *DB) execInsert(stmt *StmtInsert) (count int, err error)
func (db *DB) execUpdate(stmt *StmtUpdate) (count int, err error)
func (db *DB) execDelete(stmt *StmtDelete) (count int, err error)

الزام‌ها:

  • اگر KV به‌روزرسانی شد، count = 1 برگردانید؛ در غیر این صورت ۰.
  • بررسی کنید که StmtXXX با Schema مطابقت دارد.

برای UPDATE، به‌روزرسانی کلیدهای اصلی را پشتیبانی نمی‌کنیم. UPDATE فقط بخش V از KV را تغییر می‌دهد. به‌روزرسانی یک کلید اصلی یعنی حذف کلید قدیمی و درج یک کلید جدید، که به‌ندرت لازم است.

۰۴ — پرس‌وجوی بازه‌ای

۰۴۰۱: مرتب‌سازی و جست‌وجو

مرتب‌سازی و پرس‌وجوهای بازه‌ای

SQL فعلی فقط می‌تواند روی یک ردیف منفرد با کلید اصلی کار کند. این توسط رابط‌های KV که فقط عملیات get و set و del دارند محدود شده است. اکنون قابلیت‌ها را اضافه کنید:

  • پیمایش یک جدول.
  • پرس‌وجوی بازهٔ کلید اصلی، مانند a > 123 یا 123 < a AND a < 456.
  • مرتب‌سازی نتایج (ORDER BY).

این‌ها یک ایدهٔ مشترک دارند: پیمایش به ترتیب مرتب.

  • پیمایش جدول: همان بازهٔ -∞ < a AND a < +∞ است.
  • پرس‌وجوی بازه‌ای: مرزها را پیدا کن، سپس به‌ترتیب پیمایش کن.
  • مرتب‌سازی: ORDER BY فقط جهت را کنترل می‌کند.

حالا map موجود در KV را با یک آرایهٔ ساده جایگزین کنید که بعداً به درخت LSM تبدیل خواهد شد.

gotype KV struct {
    log  Log
    keys [][]byte
    vals [][]byte
}

جست‌وجوی دودویی

کتابخانهٔ استاندارد جست‌وجوی دودویی (binary search) دارد، اما باید حداقل یک بار خودتان آن را پیاده‌سازی کنید. ساده به‌نظر می‌رسد، اما خیلی‌ها برای کدنویسی آن مشکل دارند.

gofunc BinarySearchFunc(x S, target T, cmp func(E, T) int) (pos int, ok bool)

اگر کلید پیدا شود، ok=true برگردانید.

gofunc (kv *KV) Get(key []byte) (val []byte, ok bool, err error) {
    if idx, ok := slices.BinarySearchFunc(kv.keys, key, bytes.Compare); ok {
        return kv.vals[idx], true, nil
    }
    return nil, false, nil
}

مقداردهی پایگاه داده

۰۴۰۲: تکرارگرها

واسط تکرارگر

برای پیمایش یک آرایه، فقط یک ایندکس را جابه‌جا می‌کنید. با ساختارهای دادهٔ دیگر، پیمایش به این سادگی نیست. ساختارهای مختلف به روش‌های متفاوتی نیاز دارند. بنابراین به یک واسط مشترک برای پیمایش KV نیاز داریم که معمولاً تکرارگر (iterator) نامیده می‌شود:

gofunc (kv *KV) Seek(key []byte) (*KVIterator, error)
// آیا پیمایش پایان یافته است؟
func (iter *KVIterator) Valid() bool
// عنصر فعلی
func (iter *KVIterator) Key() []byte
func (iter *KVIterator) Val() []byte
// حرکت به عنصر بعدی/قبلی
func (iter *KVIterator) Next() error
func (iter *KVIterator) Prev() error

کاربرد:

gofor iter, err = kv.Seek(start); err == nil && iter.Valid(); err = iter.Next() {
    key, val := iter.Key(), iter.Val()
    // ...
}

وقتی این بعداً مبتنی بر دیسک شود، ممکن است خطاهای ورودی/خروجی رخ دهند، بنابراین آن‌ها error برمی‌گردانند.

تعریف تکرارگر

KVIterator باید موقعیت فعلی را پیگیری کند. برای یک آرایه، این فقط یک ایندکس است:

gotype KVIterator struct {
    keys [][]byte
    vals [][]byte
    pos  int // موقعیت
}

همچنین ارجاع‌هایی به sliceها نگه می‌دارد. اگر ساختار داده بعداً تغییر کند، این پیاده‌سازی کاملاً تغییر خواهد کرد.

پیاده‌سازی تکرارگر

KV.Seek() تکرارگری برمی‌گرداند که در نتیجهٔ جست‌وجوی دودویی روی key قرار گرفته است؛ یعنی اولین موقعیتی که در آن key >= target برقرار است.

gofunc (kv *KV) Seek(key []byte) (*KVIterator, error) {
    pos, _ := slices.BinarySearchFunc(kv.keys, key, bytes.Compare)
    return &KVIterator{keys: kv.keys, vals: kv.vals, pos: pos}, nil
}

این موقعیت ممکن است خارج از محدوده باشد، بنابراین قبل از استفاده با Valid() بررسی کنید:

gofunc (iter *KVIterator) Valid() bool {
    return 0 <= iter.pos && iter.pos < len(iter.keys)
}
func (iter *KVIterator) Key() []byte { return iter.keys[iter.pos] }
func (iter *KVIterator) Val() []byte { return iter.vals[iter.pos] }

موقعیت‌های -1 و len(keys) یعنی خارج از محدوده. با این طراحی، وقتی خارج از محدوده هستید، یک قدم به عقب می‌تواند به محدوده برگرداند.

gofunc (iter *KVIterator) Next() error {
    if iter.pos < len(iter.keys) {
        iter.pos++
    }
    return nil
}
func (iter *KVIterator) Prev() error {
    if iter.pos >= 0 {
        iter.pos--
    }
    return nil
}

۰۴۰۳: ترتیب مرتب

ترتیب کلید اصلی

کلیدهای KV به‌صورت رشته با bytes.Compare() مقایسه می‌شوند. دادهٔ رابطه‌ای نوع دارد و کلیدهای سریال‌شده ممکن است در ترتیب اشتباه مقایسه شوند.

یک راه‌حل این است که قبل از مقایسه، کلیدها را سریال‌زدایی کنیم و سپس بر اساس نوع داده مقایسه کنیم. اما این باعث می‌شود KV به طرحواره وابسته شود که اتصال محکمی اضافه می‌کند. بنابراین برخی پایگاه داده‌ها راه دیگری را انتخاب می‌کنند: طراحی یک فرمت سریال‌سازی که ترتیب مرتب را حفظ کند.

  • Cell.Encode() قدیمی را برای مقادیر KV به Cell.EncodeVal() تغییر نام دهید.
  • Cell.EncodeKey() را برای کلیدهای KV اضافه کنید که یک فرمت جدید پیاده‌سازی می‌کند.
  • Cell.Decode() را متناسباً به‌روزرسانی کنید.
go// جدید
func (cell *Cell) EncodeKey(toAppend []byte) []byte
func (cell *Cell) DecodeKey(data []byte) (rest []byte, err error)
// موجود
func (cell *Cell) EncodeVal(toAppend []byte) []byte
func (cell *Cell) DecodeVal(data []byte) (rest []byte, err error)

متدهای Row را بازکاری کنید تا متدهای جدید Cell را صدا بزنند:

gofunc (row Row) EncodeKey(schema *Schema) (key []byte)
func (row Row) DecodeKey(schema *Schema, key []byte) (err error)

روش سریال‌سازی زیر ترتیب مرتب int64 را حفظ می‌کند. توضیح آن در کتاب کامل است.

رشته‌های ختم‌شده به null

رشته‌ها را به‌صورت رشته‌های ختم‌شده به null رمزگذاری کنید و از طرح فرار زیر برای حذف بایت‌های null استفاده کنید. توضیح آن در کتاب کامل است.

  • 0x00 ⇔ 0x01 0x01
  • 0x01 ⇔ 0x01 0x02
gofunc encodeStrKey(toAppend []byte, input []byte) []byte {
    for _, ch := range input {
        if ch == 0x00 || ch == 0x01 {
            toAppend = append(toAppend, 0x01, ch+1)
        } else {
            toAppend = append(toAppend, ch)
        }
    }
    return append(toAppend, 0x00)
}

تابع رمزگشایی را پیاده‌سازی کنید:

gofunc decodeStrKey(data []byte) (out []byte, rest []byte, err error)

مقایسهٔ چندستونه

یک کلید اصلی می‌تواند چند ستون داشته باشد. مقایسه مانند رشته‌ها ستون‌به‌ستون است، مثل tuple در پایتون. برای (a, b) > (c, d)، یعنی a > c || (a == c && b > d). سؤال: اگر ستون‌ها را سریال کنید و به هم بچسبانید، آیا این همچنان کار می‌کند؟ جواب بله است.

واسط تکرارگر

حالا که ترتیب مرتب درست است، می‌توانیم پرس‌وجوهای بازه‌ای را روی KV.Seek() بسازیم:

این جفت‌های KV را از KVIterator به ردیف تبدیل می‌کند. یک مشکل وجود دارد: کلیدهای جدول‌های مختلف با پیشوندها جدا می‌شوند، بنابراین در طول پیمایش باید بررسی کنیم که آیا کلیدی متعلق به جدول است یا نه. Row.DecodeKey() را به‌روزرسانی کنید تا وقتی کلید به جدول تعلق ندارد، ErrOutOfRange برگرداند:

        return ErrOutOfRange

        return ErrOutOfRange

    // ...
}

پیاده‌سازی تکرارگر

RowIterator یک پوستهٔ دور KVIterator است. بعد از جابه‌جایی KVIterator، باید KV را رمزگشایی کنیم و ErrOutOfRange را بررسی کنیم؛ بنابراین ردیفِ رمزگشایی‌شده باید جایی ذخیره شود.

gotype RowIterator struct {
    schema *Schema
    iter   *KVIterator
    valid  bool // نتیجهٔ رمزگشایی (err != ErrOutOfRange)
    row    Row  // نتیجهٔ رمزگشایی
}

Valid() و Row() فقط نتایج ذخیره‌شده را برمی‌گردانند:

gofunc (iter *RowIterator) Valid() bool { return iter.valid }
func (iter *RowIterator) Row() Row    { return iter.row }

بعد از جابه‌جایی یا ایجاد تکرارگر، نتیجه را رمزگشایی کنید:

gofunc (iter *RowIterator) Next() (err error) {
    if err = iter.iter.Next(); err != nil {
        return err
    }
    iter.valid, err = decodeKVIter(iter.schema, iter.iter, iter.row)
    return err

توابع باقی‌مانده به خواننده واگذار می‌شوند:

خلاصه

یکی دیگر از قابلیت‌های هستهٔ پایگاه داده تمام شد: پرس‌وجوی بازه‌ای. گام‌های بعدی:

  • افزودن پشتیبانی SQL برای قابلیت جدید پرس‌وجوی بازه‌ای.
  • پیاده‌سازی یک ساختار دادهٔ واقعی (درخت LSM).

۰۴۰۵: پرس‌وجوی بازه‌ای

پرس‌وجوی بازه‌ای KV

تابع Seek() فقط پرس‌وجوهای بازهٔ باز را پشتیبانی می‌کند (key >= 123):

gofunc (kv *KV) Seek(key []byte) (*KVIterator, error)

حالا یک رابط پرس‌وجوی بازهٔ بسته اضافه کنید:

gofunc (kv *KV) Range(start, stop []byte, desc bool) (*RangedKVIter, error)

پرچم desc ترتیب پیمایش را کنترل می‌کند و می‌تواند برای ORDER BY استفاده شود:

  • desc == false: پرس‌وجو start <= key && key <= stop.
  • desc == true: پرس‌وجو start >= key && key >= stop.

RangedKVIter فقط KVIterator اصلی را می‌پیچد:

gotype RangedKVIter struct {
    iter KVIterator
    stop []byte
    desc bool
}

func (iter *RangedKVIter) Key() []byte {
    return iter.iter.Key()
}

func (iter *RangedKVIter) Val() []byte {
    return iter.iter.Val()
}

با یک شرط توقف در طول پیمایش:

gofunc (iter *RangedKVIter) Valid() bool {
    if !iter.iter.Valid() {
        return false
    }

    r := bytes.Compare(iter.iter.Key(), iter.stop)
    if iter.desc && r < 0 {
        return false
    } else if !iter.desc && r > 0 {
        return false

}

    if iter.desc {

    } else {

مقایسهٔ پیشوندی

حالا یک رابط Range() مشابه به DB اضافه کنید. یک مسئلهٔ جدید ظاهر می‌شود: یک کلید اصلی یا ایندکس می‌تواند از چند ستون تشکیل شده باشد و یک پرس‌وجو ممکن است فقط از یک پیشوند استفاده کند. مثلاً اگر کلید اصلی (a، b، c) باشد، این پرس‌وجوها معتبرند:

  • (a، b، c) ≤ (123، 4، 5) — با کل کامل. مقایسهٔ چندتایی در گام ۰۴۰۳ را ببینید.
  • (a، b) ≤ (123، 4) — با پیشوند (a، b) از (a، b، c)، معادل (a، b، c) ≤ (123، 4، +∞).
  • a ≤ 123 — با پیشوند (a، ) از (a، b، c)، معادل (a، b، c) ≤ (123، +∞).

اگر پیشوند (123، 4) رمزگذاری شود و برای K ≤ (123، 4) در KV استفاده شود، نتیجهٔ واقعی (a، b، c) < (123، 4) است. بنابراین بی‌نهایت (infinity) را معرفی می‌کنیم و پیشوند را به یک کل کامل می‌انباشیم. هر ۴ مقایسهٔ پیشوندی را می‌توان به مقایسهٔ کل کامل تبدیل کرد:

پیشوند کل کامل
(a, b) < (1, 2) (a, b, c) ≤ (1, 2, −∞)
(a, b) ≤ (1, 2) (a, b, c) ≤ (1, 2, +∞)
(a, b) > (1, 2) (a, b, c) ≥ (1, 2, +∞)
(a, b) ≥ (1, 2) (a, b, c) ≥ (1, 2, −∞)

اگر بی‌نهایت را در رمزگذاری کلید KV وارد کنیم، مقایسهٔ پیشوندی ممکن می‌شود. تابعی برای رمزگذاری پیشوندهای کلید اضافه کنید:

gofunc EncodeKeyPrefix(schema *Schema, prefix []Cell, positive bool) []byte

بی‌نهایت را این‌گونه رمزگذاری کنید:

  • رشتهٔ خالی یعنی −∞، کوچک‌ترین رشته. این مستلزم آن است که دادهٔ سریال‌شده هرگز "" نباشد، که همین الان درست است.
  • "\xff" یعنی +∞، حداکثر بایت. این مستلزم آن است که دادهٔ سریال‌شده هرگز با "\xff" شروع نشود، که با پیشوند کردن ۱ بایت به هر ستون قابل اعمال است.
gofunc (row Row) EncodeKey(schema *Schema) []byte {
    key := append([]byte(schema.Table), 0x00)
    for _, idx := range schema.PKey {
        cell := row[idx]
        key = append(key, byte(cell.Type))  // اجتناب از 0xff
        key = cell.EncodeKey(key)
    }
    return append(key, 0x00)                // > منهای بی‌نهایت
}

از آنجا که −∞ به‌صورت یک رشتهٔ خالی رمزگذاری می‌شود، باید با افزودن یک بایت انتهایی 0x00 که بزرگ‌تر از −∞ است، از تداخل بین (a، b) و (a، b، −∞) جلوگیری کنیم.

gofunc EncodeKeyPrefix(schema *Schema, prefix []Cell, positive bool) []byte {
    key := append([]byte(schema.Table), 0x00)
    for i, cell := range prefix {
        key = append(key, byte(cell.Type))  // اجتناب از 0xff
        key = cell.EncodeKey(key)
    }
    if positive {
        key = append(key, 0xff)             // +بی‌نهایت
    }                                       // -بی‌نهایت
    return key
}

۰۵ — SQL بیشتر

۰۵۰۱: عبارت‌های میانی (Infix)

نمایش عبارت‌ها به‌صورت درخت

برای افزودن پرس‌وجوی بازه‌ای به SQL، باید دستور زبان پیچیده‌تری را تجزیه کنیم. قبلاً فقط می‌توانستیم این شکل ثابت از WHERE را تجزیه کنیم:

sqlselect a, b from t where a = 123 and b = 456;

حالا باید این شکل‌ها را پشتیبانی کنیم:

sqlselect a, b from t where a > 123;
select a, b from t where (a, b) > (123, 0);

برای نمایش عبارت‌های داخل WHERE به یک ساختار داده نیاز داریم:

gotype ExprBinOp struct {
    op    ExprOp
    left  interface{}
    right interface{}
}

مثلاً:

go// a = 123 و b = 456
ExprBinOp{op: OP_AND,
    left:  &ExprBinOp{op: OP_EQ,
        left: "a",
        right: &Cell{Type: TypeI64, I64: 123}},
    right: &ExprBinOp{op: OP_EQ,
        left: "b",
        right: &Cell{Type: TypeI64, I64: 456}}}
// a > 123
ExprBinOp{op: OP_GT,
    left:  "a",
    right: &Cell{Type: TypeI64, I64: 123}}

استفاده از interface{} می‌تواند به هر نوع داده‌ای اشاره کند. مانند void * در C/C++ است، اما اطلاعات نوع را حفظ می‌کند، بنابراین می‌توان آن را بررسی و به نوع اولیه بازگرداند. این‌جا از ۳ نوع استفاده می‌کنیم:

  • یک string نمایانگر نام ستون است.
  • &Cell{} نمایانگر یک ثابت (constant) است.
  • &ExprBinOp{} نمایانگر یک عبارت تو در تو است.

تجزیهٔ عبارت‌های میانی

در این گام، اولویت عملگرها را نادیده می‌گیریم و فقط عبارت‌های + و - را تجزیه می‌کنیم:

go// a
"a"
// a + b
&ExprBinOp{op: OP_ADD, left: "a", right: "b"}
// a + b - 3
&ExprBinOp{op: OP_SUB,
    left:  &ExprBinOp{op: OP_ADD, left: "a", right: "b"},
    right: &Cell{Type: TypeI64, I64: 123}}

عملوندها شامل نام ستون‌ها و ثابت‌ها هستند و interface{} برمی‌گردانند:

gofunc (p *Parser) parseAtom() (interface{}, error) {
    if name, ok := p.tryName(); ok {
        return name, nil
    }
    cell := &Cell{}
    if err := p.parseValue(cell); err != nil {
        return nil, err
    }
    return cell, nil
}

تابع parseAdd() را پیاده‌سازی کنید. حلقه می‌زند و parseAtom() و tryPunctuation() را صدا می‌زند:

gofunc (p *Parser) parseAdd() (interface{}, error)

مفسر

اکنون می‌توانیم محاسبه را به عبارت‌های SELECT و UPDATE اضافه کنیم:

۰۵۰۳: اولویت عملگرها

سطح‌های چندگانهٔ اولویت

این گام * و / را اضافه می‌کند که اولویت بیشتری از + و - دارند. فعلاً پرانتزها نادیده گرفته می‌شوند. در عبارتی که شامل + - * / است، جمع و تفریق باید در سطح بالایی (ریشه) درخت باشند. یعنی زیردرخت‌های + و - می‌توانند * و / داشته باشند. اما بدون پرانتز، زیردرخت‌های * و / نمی‌توانند + یا - داشته باشند. آن‌ها فقط می‌توانند یک مقدار یا نام ستون باشند؛ همان‌طور که قبلاً parseAtom() مدیریت می‌کرد. پس به ۲ تغییر نیاز داریم:

  1. parseAdd() را کپی کنید و کمی تغییرش دهید تا parseMul() ساخته شود؛ تابعی که عبارت‌های فقط با * و / را تجزیه می‌کند.
  2. در parseAdd()، parseAtom() را با parseMul() جایگزین کنید تا * و / زیردرخت‌های + و - شوند.

برای تجزیهٔ یک عبارت میانی با چند سطح اولویت، از کم‌اولویت‌ترین شروع کنید. بالاترین اولویت در عمیق‌ترین سطح زنجیرهٔ فراخوانی است. حالا parseExpr() را به‌عنوان نقطهٔ ورود تجزیهٔ عبارت اضافه کنید:

gofunc (p *Parser) parseExpr() (interface{}, error) {
    return p.parseAdd()
}
func (p *Parser) parseAdd() (interface{}, error) {
    // فراخوانی parseMul()
}
func (p *Parser) parseMul() (interface{}, error) {
    // فراخوانی parseAtom()
}

اینجا فقط ۲ سطح اولویت هست. برای افزودن بیشتر، همان الگو را تکرار کنید.

پرانتزها

حالا پرانتزها را اضافه کنید تا ترتیب عملیات تغییر کند. پرانتز را می‌توان بالاترین اولویت در نظر گرفت، پس باید در عمیق‌ترین فراخوانی یعنی parseAtom() مدیریت شود. وقتی پرانتز پیدا شد، parseExpr() سطح بالا را صدا بزنید.

gofunc (p *Parser) parseAtom() (expr interface{}, err error)

استخراج توابع مشترک

مانند parseAdd() گام قبل، هر سطح اولویت به یک تابع parseXXX() نگاشت می‌شود که تابع بعدی parseYYY() را صدا می‌زند. قبلاً parseMul() از parseAdd() کپی شده بود. حالا با وجود توابع زیاد، می‌توانیم منطق مشترک را استخراج کنیم:

gofunc (p *Parser) parseOr() (interface{}, error) {
    return p.parseBinop([]string{"OR"}, []ExprOp{OP_OR}, p.parseAnd)
}
func (p *Parser) parseAnd() (interface{}, error) {
    return p.parseBinop([]string{"AND"}, []ExprOp{OP_AND}, p.parseNot)
}
func (p *Parser) parseNot() (expr interface{}, err error)
func (p *Parser) parseCmp() (interface{}, error) {
    return p.parseBinop(
        []string{"=", "!=", "<>", "<=", ">=", "<", ">"},
        []ExprOp{OP_EQ, OP_NE, OP_NE, OP_LE, OP_GE, OP_LT, OP_GT},
        p.parseAdd)
}

    return p.parseBinop([]string{"+", "-"}, []ExprOp{OP_ADD, OP_SUB}, p.parseMul)
}

۰۵۰۵: عبارت SELECT

تغییر ساختارها

در این گام، به عبارت‌ها در SELECT و UPDATE اجازه می‌دهیم:

sqlselect a * 4 - b, d + c from t where d = 123;
update t set a = a - b, b = a, c = d + c where d = 123;

در StmtSelect، cols از string به interface{} تغییر می‌کند. StmtUpdate نیز به‌روزرسانی می‌شود و ExprAssign اضافه می‌شود:

gotype StmtSelect struct {
    table string
    // cols  []string
    cols  []interface{} // ExprUnOp | ExprBinOp | string | *Cell
    keys  []NamedCell
}
type StmtUpdate struct {
    table string
    keys  []NamedCell
    // value []ExprEqual
    value []ExprAssign
}
type ExprAssign struct {
    column string
    expr   interface{} // ExprUnOp | ExprBinOp | string | *Cell
}

تغییر تجزیه‌گر

  • در parseSelect()، tryName() را با parseExpr() جایگزین کنید.
  • در parseUpdate()، parseEqual() را با parseAssign() جایگزین کنید.
gofunc (p *Parser) parseAssign(out *ExprAssign) (err error) {
    var ok bool
    out.column, ok = p.tryName()
    if !ok {
        return errors.New("expect column")
    }
    if !p.tryPunctuation("=") {
        return errors.New("expect =")
    }
    out.expr, err = p.parseExpr()
    return err
}

func matchPKey(schema *Schema, cond interface{}) (Row, error) {
    if keys, ok := matchAllEq(cond, nil); ok {
        return makePKey(schema, keys)
    }
    return nil, errors.New("unimplemented WHERE")
}

matchAllEq() عبارت‌هایی مانند a = 123 AND b = 456 AND ... را تشخیص می‌دهد و نام ستون‌ها و مقادیر را خروجی می‌دهد. به‌صورت بازگشتی در عبارت قدم می‌زند. این را پیاده‌سازی کنید:

gofunc matchAllEq(cond interface{}, out []NamedCell) ([]NamedCell, bool)

فعلاً فقط پرس‌وجوهای کلید اصلی که یک ردیف منفرد برمی‌گردانند پشتیبانی می‌شوند. برای افزودن انواع دیگر پرس‌وجو، باید شکل‌های دیگر عبارت را بشناسید؛ مانند پرس‌وجوهای بازه‌ای در گام بعد.

تشخیص پرس‌وجوهای بازه‌ای

پرس‌وجوی a = 123 همان 123 <= a AND a <= 123 است، بنابراین پرس‌وجوهای تک‌کلیداصلی هم می‌توانند از پرس‌وجوی بازه‌ای استفاده کنند. DB.Select() قدیمی می‌تواند از این میان‌بر استفاده کند.

gofunc makeRange(schema *Schema, cond interface{}) (*RangeReq, error) {
    if keys, ok := matchAllEq(cond, nil); ok {
        if pkey, ok := extractPKey(schema, keys); ok {
            return &RangeReq{
                StartCmp: OP_GE,
                StopCmp:  OP_LE,
                Start:    pkey,
                Stop:     pkey,
            }, nil
        }
    }
    if req, ok := matchRange(schema, cond); ok {
        return req, nil
    }
    return nil, errors.New("unimplemented WHERE")
}

gofunc matchRange(schema *Schema, cond interface{}) (*RangeReq, bool) {
    binop, ok := cond.(*ExprBinOp)

۰۶ — لاگ و داده

۰۶۰۰: به‌روزرسانی‌های اتمی

همین حالا پایگاه دادهٔ ما «لاگ + آرایهٔ درون‌حافظه» است. این یک پایگاه دادهٔ درون‌حافظه با ماندگاری است. اندازهٔ داده به حافظه محدود است، بنابراین به ساختارهای دادهٔ مبتنی بر دیسک نیاز داریم. آرایه ساده‌ترین ساختار است. فرمتی طراحی خواهیم کرد تا آرایهٔ مرتبِ درون‌حافظه را روی دیسک ذخیره کنیم.

اما آرایه یک ساختار دادهٔ کاربردی نیست، زیرا درج و حذف در آن O(N) است. فقط ۲ انتخاب کاربردی وجود دارد: درخت B+ و درخت LSM. هر دو می‌توانند از آرایه‌های ساده تکامل یابند، بنابراین می‌توانیم در گام‌های ریز پیش برویم و درک ایده‌های کامل را آسان‌تر کنیم.

چالش‌های به‌روزرسانی ساختارهای دادهٔ مبتنی بر دیسک و راه‌حل‌هایشان را بررسی خواهیم کرد؛ از جمله کپی-هنگام-نوشتن (copy-on-write)، بافر دوگانه (double buffering)، لاگ فیزیکی و درخت LSM. این بخش در کتاب کامل گنجانده شده است.

۰۶۰۱: ساخت SSTableها

قالب SSTable

در این گام، آرایهٔ مرتبِ درون‌حافظه را در یک فایل ماندگار می‌کنیم. این فایل در ابتدا با تخلیهٔ ساختار دادهٔ درون‌حافظه (آینهٔ لاگ) ایجاد می‌شود. بعداً، هر بار که لاگ به حد اندازه برسد، با فایل قدیمی در یک فایل جدید ادغام می‌شود و سپس فایل قدیمی جایگزین می‌شود.

در درخت LSM، ساختار دادهٔ روی دیسک معمولاً SSTable (جدول رشتهٔ مرتب — sorted string table) نامیده می‌شود. یک SSTable فقط جزئیات پیاده‌سازی است؛ حتی با همان ساختار داده هم می‌توان از قالب‌های متفاوت روی دیسک استفاده کرد. ما این قالب را برمی‌گزینیم:

text[ n keys | offset1 | offset2 | ... | offsetn | KV1 | KV2 | ... | KVn ]
  8bytes   8bytes

اول آرایه‌ای می‌آید که آفست هر کلید را در فایل ثبت می‌کند. اندازهٔ آرایه (n) در ابتدا ذخیره می‌شود. این آرایه برای جست‌وجوی دودویی و پیمایش استفاده می‌شود. هر KV در قالب زیر ذخیره می‌شود:

text[ key length | val length | key data | val data ]
    4bytes       4bytes

ساخت یک SSTable

SSTable اولیه با تخلیهٔ ساختار دادهٔ درون‌حافظه (MemTable) ایجاد می‌شود. هنگام ساخت SSTable، دادهٔ ورودی از طریق یک تکرارگر تغذیه می‌شود، بنابراین کد به نوع دادهٔ مشخص وابسته نیست.

واسط ورودی همچنین تعداد کلیدها را فراهم می‌کند. با این، اندازهٔ آرایهٔ آفست‌ها و در نتیجه آفست اولین KV را می‌دانیم. می‌توانیم هم آرایهٔ آفست‌ها و هم دادهٔ KV را در یک پاس بنویسیم. برای نوشتن در موقعیت مشخص از WriteAt() استفاده کنید:

۰۶۰۳: بازسازی کد

اگر SSTableها به KV اضافه شوند، پرس‌وجوها باید هم ساختار درون‌حافظه (MemTable) و هم SSTableها را بخوانند و سپس نتایج را ادغام کنند. ساختار درون‌حافظهٔ فعلی فقط ۲ آرایه است:

gotype KV struct {
    log  Log
    keys [][]byte
    vals [][]byte

این گام قابلیت جدیدی اضافه نمی‌کند. ساختار درون‌حافظه را به یک نوع جداگانه منتقل می‌کند تا برای گام بعد آماده شود. همچنین جایگزینی ساختار داده را در آینده آسان‌تر می‌کند.

gotype KV struct {
    log Log
    mem SortedArray
}

    keys [][]byte
    vals [][]byte

SortedArray استخراج‌شده، واسط SortedKV را پیاده‌سازی می‌کند و می‌تواند به‌عنوان ورودی SSTableها استفاده شود:

gofunc (arr *SortedArray) Size() int { return len(arr.keys) }
func (arr *SortedArray) Iter() (SortedKVIter, error) {

۰۶۰۴: ادغام دادهٔ مرتب

ادغام KV

اگر SSTableها اضافه شوند، ۲ ساختار داده وجود خواهد داشت. کلیدها اول وارد MemTable می‌شوند و بعداً در SSTableها ادغام می‌شوند، بنابراین پرس‌وجوها ممکن است نیاز به ادغام نتایج از هر دو داشته باشند.

یک کلید ممکن است هم در MemTable و هم در یک SSTable وجود داشته باشد؛ MemTable اولویت بالاتر دارد. در درخت LSM که بعداً پیاده‌سازی می‌شود، می‌توان چند سطح SSTable وجود داشته باشد. SSTableهای سطح پایین‌تر از سطح‌های بالاتر ادغام می‌شوند. هنگام پرس‌وجوی یک کلید منفرد، از بالا به پایین و سطح‌به‌سطح جست‌وجو کنید. به همین دلیل اولین پایگاه دادهٔ محبوب LSM-Tree، LevelDB نامیده شد.

ادغام بازه‌ها

پرس‌وجوهای تک‌کلیدی می‌توانند هر سطح را به‌ترتیب بررسی کنند. پرس‌وجوهای بازه‌ای نمی‌توانند، زیرا کلید بعدی ممکن است از هر سطحی بیاید. برای پیمایش صعودی، باید کوچک‌ترین کلید را بین همهٔ تکرارگرهای سطح انتخاب کنید. این دقیقاً مرتب‌سازی ادغامی (merge sort) است.

ادغام k بازه را پیاده‌سازی می‌کنیم که بعداً برای درخت LSM قابل استفاده مجدد است. این از ادغام ۲ بازه پیچیده‌تر نیست.

gotype MergedSortedKV []SortedKV

func (m MergedSortedKV) Iter() (iter SortedKVIter, err error) {
    levels := make([]SortedKVIter, len(m))
    for i, sub := range m {
        if levels[i], err = sub.Iter(); err != nil {
            return nil, err
        }
    }
    return &MergedSortedKVIter{levels, levelsLowest(levels)}, nil
}

type MergedSortedKVIter struct {
    levels []SortedKVIter
    which  int
}
func (iter *MergedSortedKVIter) Valid() bool {
    return iter.which >= 0
}
func (iter *MergedSortedKVIter) Key() []byte {
    return iter.levels[iter.which].Key()
}
func (iter *MergedSortedKVIter) Val() []byte {
    return iter.levels[iter.which].Val()
}
func (iter *MergedSortedKVIter) Next() error
func (iter *MergedSortedKVIter) Prev() error

which تکرارگری را ثبت می‌کند که کلید فعلیِ کوچک‌ترین یا بزرگ‌ترین را دارد. الزام‌ها:

  • سطح‌های بالاتر نسبت به سطح‌های پایین‌تر اولویت دارند.
  • کلیدهای تکراری خروجی داده نشوند.
  • جهت می‌تواند در میانه تغییر کند.

۰۶۰۵: لاگ + SSTable

SSTableها را در این گام اضافه می‌کنیم. پرس‌وجوها باید نتایج را از MemTable و SSTable ادغام کنند. KV.Compact() را معرفی می‌کنیم که MemTable (آینهٔ لاگ) و SSTable را ادغام می‌کند تا یک SSTable جدید تولید کند.

حالا که ۲ سطح ساختار داده وجود دارد، کلیدهای حذف‌شده باید در سطح بالاتر ثبت شوند؛ در غیر این صورت پرس‌وجوها کلید را از سطح پایین‌تر برمی‌گردانند.

ادغام پرس‌وجوهای بازه‌ای

پیرو MergedSortedKV.Scan()، MergedSortedKV.Seek() را اضافه کنید که تکرارگر را با Seek() هر سطح مقداردهی می‌کند:

gofunc (m MergedSortedKV) Seek(key []byte) (iter SortedKVIter, err error)

پرس‌وجوی بازهٔ ادغامی:

gofunc (kv *KV) Seek(key []byte) (SortedKVIter, error) {
    m := MergedSortedKV{&kv.mem, &kv.main}
    iter, err := m.Seek(key)
    if err != nil {
        return nil, err
    }
    return filterDeleted(iter)
}

خروجی باید کلیدهای حذف‌شده را فیلتر کند. می‌توانیم تکرارگر را برای انجام این کار بپیچیم:

gofunc filterDeleted(iter SortedKVIter) (SortedKVIter, error) {
    for iter.Valid() && iter.Deleted() {
        if err := iter.Next(); err != nil {
            return nil, err
        }
    }
    return NoDeletedIter{iter}, nil
}

type NoDeletedIter struct {
    SortedKVIter    // همهٔ متدها را به ارث می‌برد
}

// بازنویسی Next() و Prev()
func (iter NoDeletedIter) Next() (err error)

تغییر قالب SSTable

هنگام ساخت یک SSTable در یک پاس، برای تخصیص آرایهٔ آفست‌ها باید تعداد کلیدها را بدانیم. با این حال، پس از ادغام، کلیدهای تکراری و حذف‌شده حذف می‌شوند، بنابراین تعداد نهایی کلیدها از مجموع تعداد کلیدهای همهٔ سطح‌ها کوچک‌تر است. بنابراین اندازهٔ آرایهٔ آفست فقط یک تخمین است، اما همچنان کار می‌کند تا وقتی که تعداد واقعی کلیدها را بعد از پیمایش بنویسیم. باید SortedFile.CreateFromSorted() را کمی تغییر دهیم. همچنین SortedKV.Size() به نام مناسب‌تری تغییر نام می‌یابد.

gotype SortedKV interface {
    EstimatedSize() int                     // تغییر نام یافته
    Iter() (SortedKVIter, error)
    Seek(key []byte) (SortedKVIter, error)  // افزوده شده
}

func (m MergedSortedKV) EstimatedSize() (total int) {
    for _, sub := range m {
        total += sub.EstimatedSize()
    }
    return total
}

تخصیص بیش از حد آرایهٔ آفست، یک شکاف بلااستفاده در فایل ایجاد می‌کند:

text[ n keys | offset1 | offset2 | ... | offsetn | gap | KV1 | KV2 | ... | KVn ]

انتقال لاگ به SSTable

KV.Compact() MemTable را در ۳ گام در SSTable ادغام می‌کند:

gofunc (kv *KV) Compact() error {
    // ۱. ادغام MemTable و SSTable؛ خروجی به یک فایل موقت
    path := randomTempPath()
    defer os.Remove(path)
    file := SortedFile{FileName: path}
    m := MergedSortedKV{&kv.mem, &kv.main}
    if err := file.CreateFromSorted(m); err != nil {
        return err
    }
    // ۲. جایگزینی SSTable اصلی (عملیات اتمی)
    if err := renameSync(file.FileName, kv.main.FileName); err != nil {
        _ = file.Close()
        return err
    }
    file.FileName = kv.main.FileName
    _ = kv.main.Close()
    kv.main = file
    // ۳. پاک کردن MemTable و لاگ
    kv.mem.Clear()
    return kv.log.Truncate()
}

در صورت قطع برق، فراخوانی سیستمی rename() لینوکس اتمی بودن فایل مقصد را تضمین می‌کند. اما برای ماندگار کردن آن، باید پوشهٔ والد را نیز fsync کنید (گام ۰۱۰۴ را ببینید).

gofunc syncDir(file string) error

func renameSync(src string, dst string) error {
    if err := os.Rename(src, dst); err != nil {
        return err
    }
    return syncDir(dst)
}

۰۷ — درخت LSM

۰۷۰۰: مقدمه‌ای بر درخت LSM

درخت LSM چیست؟

درخت ادغام-ساختاریافتهٔ لاگ (Log-structured Merge Tree یا LSM-Tree) و درخت B+ تنها ۲ انتخاب برای ساخت یک پایگاه دادهٔ همه‌منظوره هستند. LSM-Tree را می‌توان با B+Tree مقایسه کرد، اما یک ساختار دادهٔ عینی نیست. این یک روش است که «به‌روزرسانی» ساختارهای داده را با «ادغام» جایگزین می‌کند. نامش گمراه‌کننده است، زیرا ایدهٔ آن هیچ ربطی به درخت یا لاگ ندارد.

پایگاه دادهٔ ما ۲ سطح دارد: MemTable و SSTable. MemTable برای ماندگاری از یک لاگ استفاده می‌کند، در حالی‌که SSTable هرگز تغییر نمی‌کند و فقط با فایل‌های جدید جایگزین می‌شود. برای پرس‌وجوها، نتایج ادغام می‌شوند و MemTable بالایی اولویت بالاتر دارد. برای به‌روزرسانی‌ها، داده اول به سطح بالایی می‌رود و بعد به سطح‌های پایین‌تر.

این ساختار ۲ سطحی را می‌توان به k سطح گسترش داد؛ این همان LSM-Tree است. اینکه هر سطح چه چیزی دارد برای اصل LSM-Tree بی‌ربط است. هر سطح فقط باید مجموعه‌ای از KV مرتب باشد، که می‌تواند آرایه یا درخت باشد. اگر ترتیب لازم نباشد، حتی می‌تواند جدول هش باشد. بنابراین LSM-Tree مجموعه‌ای از ساختارهای داده است، نه یک ساختار واحد.

textlevel 1     [x=1, z=3]
level 2     [a=8, y=2, z=(deleted)]
...
level k     [a=0, b=2, c=3, d=4, z=456]

توضیح مفصل را در کتاب کامل ببینید.

۰۷۰۱: ذخیرهٔ اتمی

بافر دوگانه

گام قبل فقط ۱ سطح SSTable داشت، با یک نام فایل ثابت که با rename() جایگزین می‌شد. یک LSM-Tree چند سطح SSTable و چند فایل دارد، بنابراین نام‌های ثابت کار نمی‌کنند. فهرست نام فایل‌های سطح‌ها باید توسط پایگاه داده ثبت شود.

از آنجا که تعداد سطح‌ها از log *N* تجاوز نمی‌کند، فهرست نام فایل‌ها به به‌روزرسانی افزایشی نیاز ندارد. می‌توانیم از بافر دوگانهٔ ۰۶۰۰ برای دستیابی به به‌روزرسانی‌های اتمی استفاده کنیم. یعنی ۲ نسخه با نسخه (version) و جمع کنترلی نگه داریم و آن‌ها را به‌نوبت به‌روزرسانی کنیم. پس از قطع برق، می‌توانیم به نسخهٔ سالم بازیابی کنیم.

textslot 0 -> [ version 124 | data yyy | crc32 ]
slot 1 -> [ version 123 | data zzz | crc32 ]

متاداده

این ۲ رکورد می‌توانند ۲ فایل باشند. ساختارها را این‌گونه تعریف کنید:

    slots [2]KVMetaItem
}
type KVMetaItem struct {
    FileName string
    fp       *os.File
    data     KVMetaData
}
type KVMetaData struct {
    Version uint64
    SSTable string  // نام فایل
}
func (meta *KVMetaStore) Open() error
func (meta *KVMetaStore) Close() error
func (meta *KVMetaStore) Get() KVMetaData
func (meta *KVMetaStore) Set(data KVMetaData) error

KVMetaData داده‌ای است که باید ذخیره شود؛ دارای یک نسخهٔ یکنواخت (monotonic) و یک نام فایل SSTable است. آن را با هر روش سریال‌سازی (JSON کافی است) در فایل بنویسید. الزام‌ها:

  • Open() نسخهٔ خراب را نادیده می‌گیرد؛ از جمله خطاهای سریال‌زدایی و عدم تطابق جمع کنترلی.
  • Get() نسخه‌ای را برمی‌گرداند که نسخهٔ بزرگ‌تری دارد.
  • Set() نسخه‌ای را بازنویسی می‌کند که نسخهٔ کوچک‌تری دارد و fsync را صدا می‌زند.

۰۷۰۴: ادغام سطح‌ها

پارامترهای LSM-Tree

در گام قبل، لاگ به SSTable سطح بالا تبدیل شد. حالا عملیات ادغام از ۰۷۰۰ را پیاده‌سازی کنید. ۲ پارامتر اضافه کنید:

gotype KVOptions struct {
    Dirpath string
    // LSM-Tree
    LogShreshold int
    GrowthFactor float32
}
  • LogShreshold حداکثر تعداد کلید در لاگ است. وقتی از آن تجاوز شد، به SSTable تبدیل می‌شود.
  • GrowthFactor نسبت اندازه (تعداد کلید) بین سطح‌های مجاور است.

ادغام SSTableها

تابع KV.Compact() از این ۲ پارامتر برای تصمیم‌گیری دربارهٔ زمان ادغام SSTableها استفاده می‌کند:

gofunc (kv *KV) Compact() error {
    if kv.mem.Size() >= kv.Options.LogShreshold {
        if err := kv.compactLog(); err != nil {
            return err
        }
    }
    for i := 0; i < len(kv.main)-1; i++ {
        if kv.shouldMerge(i) {
            if err := kv.compactSSTable(i); err != nil {
                return err
            }
            i--
            continue
        }
    }
    return nil
}
  • KV.compactLog() همان KV.Compact() گام قبل است.
  • KV.shouldMerge() با قاعدهٔ رشد نمایی تصمیم می‌گیرد سطح i با i+1 ادغام شود یا نه.
  • KV.compactSSTable() ۲ SSTable مجاور را ادغام می‌کند و نسخه‌های اصلی را جایگزین می‌کند.

توجه کنید که آخرین سطح باید کلیدهای حذف‌شده را دور بریزد. می‌توانید تکرارگر ورودی را بپیچید:

gotype NoDeletedSortedKV struct {
    SortedKV
}

func (kv NoDeletedSortedKV) Iter() (iter SortedKVIter, err error) {
    if iter, err = kv.SortedKV.Iter(); err != nil {
        return nil, err
    }
    return NoDeletedIter{iter}, nil
}
gofunc (kv *KV) compactSSTable(level int) error {
    // ...
    file := SortedFile{FileName: filename}
    m := SortedKV(MergedSortedKV{&kv.main[level], &kv.main[level+1]})
    if len(kv.main) == level+2 {
        m = NoDeletedSortedKV{m}
    }
    err := file.CreateFromSorted(m)
    // ...
}
