مقدمه — نمای کلی (Overview)

این بخش از سایت کدسلینجر به شبیه‌سازی گیم‌بوی اختصاص دارد و همهٔ آنچه برای شبیه‌سازی این سیستم لازم است را توضیح می‌دهد. شبیه‌ساز خودِ نویسنده حدود ۹۵٪ سازگاری دارد، البته بدون صدا.

دانلود کد منبع

اگر می‌خواهید وضعیت فعلی شبیه‌ساز را ببینید، می‌توانید کد منبع را از اینجا دانلود کنید؛ هر طور دوست دارید از کد استفاده کنید، فقط تا زمانی که اعتبار آن به نویسنده داده شود. کد منبع هم در Visual Studio (ویندوز) و هم با CodeBlocks (لینوکس) کامپایل می‌شود. این نسخه از شبیه‌ساز هیچ امکاناتی مانند GUI یا تخلیهٔ حافظه (memory dump) ندارد و برای اجرای یک بازی باید نام فایل را در Gameboy.cpp تغییر دهید و دوباره کامپایل کنید. به یاد داشته باشید برای استفاده از این کد و اجرای بازی‌ها باید واقعاً یک گیم‌بوی و بازی‌های آن را داشته باشید (نویسنده هیچ ROM و لینکی به آن‌ها ارائه نمی‌دهد). هر کار دیگری خلاف قانون است.

شروع کار (Getting Started)

تعریف انواع داده (Type Definitions)

مثل همهٔ ماشین‌ها، گیم‌بوی از انواع داده با اندازه‌های مختلف استفاده می‌کند؛ عمدتاً بایت (۸ بیت) و کلمه (۱۶ بیت). مجموعهٔ دستورالعمل z80-مانند آن همچنین از بایت‌ها و کلمه‌های علامت‌دار استفاده می‌کند. برای آسان‌ترشدن فهم کد، این انواع را typedef کرده‌ایم:

cpptypedef unsigned char BYTE ;
typedef char SIGNED_BYTE ;
typedef unsigned short WORD ;
typedef signed short SIGNED_WORD ;

اکیداً توصیه می‌شود همین کار را بکنید؛ فهمیدن اینکه یک متغیر چه بازهٔ مقداری می‌تواند نگه دارد آسان‌تر می‌شود و خطاهای سرریز (overflow) راحت‌تر ردیابی می‌شوند.

بارگذاری بازی (Loading In The Game)

حداکثر اندازهٔ یک ROM گیم‌بوی 0x200000 بایت است؛ پس اگر آرایه‌ای به این اندازه داشته باشیم، می‌توانیم بازی را آنجا ذخیره کنیم. این آرایه نمایانگر کارتریج گیم‌بوی خواهد بود. همان‌طور که در بخش «کنترل و نقشهٔ حافظه» خواهید خواند، حافظهٔ داخلی گیم‌بوی فقط 0x8000 بایت اول کارتریج را در خود نگه می‌دارد و بقیه در کارتریج می‌ماند (شبیه‌ساز باید در صورت نیاز داده را از کارتریج به حافظه جابه‌جا کند):

cpp// تعریف حافظهٔ کارتریج
BYTE m_CartridgeMemory[0x200000] ;

// بارگذاری بازی در حافظهٔ کارتریج
memset(m_CartridgeMemory,0,sizeof(m_CartridgeMemory)) ;

FILE *in;
in = fopen( "Tetris.gb", "rb" );
fread(m_CartridgeMemory, 1, 0x200000, in);
fclose(in);

حلقهٔ شبیه‌سازی (The Emulation Loop)

برخلاف chip8، زمان‌بندی گیم‌بوی کاملاً مستند شده است و شبیه‌سازی صحیح سرعت آن حیاتی است. سند گیم‌بوی که نویسنده میزبانی می‌کند، زمان‌بندی هر اپکد را برحسب چرخهٔ ساعت (clock cycles) می‌دهد. پس اگر بدانیم هر دستورالعمل در سخت‌افزار اصلی چند چرخه طول می‌کشد، می‌توانیم آن را به یک شمارندهٔ جمع‌شونده اضافه کنیم تا زمان‌بندی را پیگیری کنیم. یکی از مزیت‌های اصلی پیگیری مدت زمان هر دستورالعمل، همگام‌سازی آن با شبیه‌سازی گرافیک و تایمرهای گیم‌بوی با همان نرخ CPU است.

برای شبیه‌سازی گرافیک از SDL استفاده می‌شود که قابلیت محدودکردن نرخ فریم دارد. نرخ فریم ۶۰ فریم بر ثانیه انتخاب شده؛ زیرا گیم‌بوی صفحه را ۶۰ بار در ثانیه تازه‌سازی می‌کند. طبق pandocs مقدار چرخه‌های ساعتی که گیم‌بوی می‌تواند در هر ثانیه اجرا کند 4194304 است؛ یعنی اگر هر فریم شبیه‌ساز را ۶۰ بار در ثانیه به‌روزرسانی کنیم، هر فریم باید 69905 (4194304/60) چرخهٔ ساعت اجرا کند. این کار سرعت صحیح شبیه‌ساز را تضمین می‌کند.

cppvoid Emulator::Update( )
{
  const int MAXCYCLES = 69905 ;
  int cyclesThisUpdate = 0 ;

  while (cyclesThisUpdate < MAXCYCLES)
  {
     int cycles = ExecuteNextOpcode( ) ;
     cyclesThisUpdate += cycles ;
     UpdateTimers(cycles) ;
     UpdateGraphics(cycles) ;
     DoInterupts( ) ;
  }

  RenderScreen( ) ;
}

اگر تابع بالا ۶۰ بار در ثانیه صدا زده شود، RenderScreen هم ۶۰ بار در ثانیه صدا زده می‌شود که همان نرخ گیم‌بوی است. حلقهٔ while تضمین می‌کند مقدار صحیحی از دستورالعمل‌ها در هر فریم اجرا شود (البته به شرطی که تابع ExecuteNextOpcode چرخه‌های ساعتی صحیح اپکد اجراشده را برگرداند). تایمرها و گرافیک هم تعداد چرخهٔ اپکد را دریافت می‌کنند تا با همان نرخ CPU به‌روزرسانی شوند. بعد از هر دستورالعمل باید وقفه‌ها بررسی و در صورت نیاز پردازش شوند.

سخت‌افزار (The Hardware)

همهٔ اطلاعات این بخش مستقیماً از pandocs ناکش (nocash) گرفته شده است:

  • CPU: ۸ بیتی (مشابه پردازندهٔ z80)
  • سرعت ساعت: 4.194304MHz
  • وضوح صفحه: 160x144
  • همگام‌سازی عمودی: 59.73Hz
  • اندازهٔ حافظهٔ داخلی: 0x10000

CPU بسیار شبیه پردازندهٔ z80 است (چند دستورالعمل اضافه دارد و همهٔ پرچم‌ها استفاده نمی‌شوند). همهٔ دستورالعمل‌ها همراه با توضیح و تعداد چرخه‌های ساعت آن‌ها در فایل PDF گیم‌بوی موجود است. شبیه‌سازی وضوح صفحه جالب است: با یک آرایهٔ سه‌بعدی انجام شده — بعد اول محور X صفحه، بعد دوم محور Y و بعد سوم رنگ (سه عنصر برای قرمز، سبز و آبی):

cppBYTE m_ScreenData[160][144][3] ;

مثلاً برای قرمزکردن پیکسل وسط صفحه:

cppm_ScreenData[160/2][144/2][0] = 0xFF ;
m_ScreenData[160/2][144/2][1] = 0 ;
m_ScreenData[160/2][144/2][2] = 0 ;

CPU هشت بیتی است و حافظه 0x10000 بایت است؛ پس تعریف حافظهٔ اصلی:

cppBYTE m_Rom[0x10000] ;

ثبات‌ها (The Registers)

گیم‌بوی ۸ ثبات به نام‌های A,B,C,D,E,F,H,L دارد که هر کدام ۸ بیت هستند. اما این ثبات‌ها اغلب جفت می‌شوند تا ۴ ثبات ۱۶ بیتی بسازند: AF، BC، DE و HL. جفت AF کمتر از بقیه استفاده می‌شود؛ زیرا A ثبات انباشتگر (accumulator) و F ثبات پرچم است و کار کردن با آن‌ها به‌صورت جفت کمتر اتفاق می‌افتد. جفت HL خیلی زیاد استفاده می‌شود، عمدتاً برای اشاره به حافظهٔ بازی.

راه‌های زیادی برای شبیه‌سازی ثبات‌ها وجود دارد؛ یک راه این است که هر جفت را با یک متغیر کلمه نمایش دهیم و برای بایت بالا/پایین ثبات‌های منفرد تابع بسازیم. راه دیگر برعکس است: ۸ متغیر بایتی برای هر ثبات و سپس تابعی برای ترکیب آن‌ها به یک کلمه. اما نویسنده ترجیح می‌دهد با union این کار را کند:

cppunion Register
{
  WORD reg ;
  struct
  {
   BYTE lo ;
   BYTE hi ;
  };
};

Register m_RegisterAF ;
Register m_RegisterBC ;
Register m_RegisterDE ;
Register m_RegisterHL ;

هر فیلد یک union همان ناحیهٔ حافظه را اشغال می‌کند. اگر m_RegisterAF.reg = 0xAABB کنید، m_RegisterAF.hi برابر 0xAA و m_RegisterAF.lo برابر 0xBB می‌شود. سپس می‌توانید m_RegisterAF.lo = 0xCC بدهید؛ m_RegisterAF.hi همچنان 0xAA می‌ماند اما m_RegisterAF.reg برابر 0xAACC می‌شود. این برای نمایش ثبات‌ها عالی است؛ چون هم دسترسی آسان به ثبات‌های منفرد (با فیلدهای hi/lo) و هم به‌صورت جفت (با فیلد reg) می‌دهد. شاید بپرسید چرا BYTE lo قبل از BYTE hi اعلام شده؛ به دلیل endianness است.

پرچم‌ها (The Flags)

ثبات F نقش ثبات پرچم را هم دارد. CPU از ۴ پرچم استفاده می‌کند (برخلاف z80 واقعی که ۸ پرچم دارد): «پرچم نقلی (carry)»، «پرچم نقلی نیمه (half carry)»، «پرچم تفریق (subtract)» و «پرچم صفر (zero)». پرچم نقلی بعد از یک دستورالعمل ریاضی که نتیجه‌اش در محدودهٔ نوع داده جا نمی‌شود تنظیم می‌شود. مثلاً اگر دستورالعمل مقدار 250+7 را در ثبات A بگذارد، A برابر 257 می‌شود؛ اما چون A یک بایت بدون علامت است فقط می‌تواند ۰ تا ۲۵۵ را نگه دارد، پس به ۱ می‌پیچد (wrap) و پرچم نقلی تنظیم می‌شود تا نشان دهد نتیجه سرریز شده است.

پرچم نقلی نیمه شبیه پرچم نقلی است با این تفاوت که وقتی یک دستورالعمل ریاضی از نیبل پایین به نیبل بالا سرریز کند (یا در عملیات ۱۶ بیتی از بایت پایین به بایت بالا) تنظیم می‌شود. این پرچم توسط دستورالعمل‌های زیادی تنظیم می‌شود اما فقط با DAA استفاده می‌شود. پرچم صفر وقتی تنظیم می‌شود که نتیجهٔ یک دستورالعمل ریاضی صفر شود (مثل 4-4). پرچم تفریق وقتی تنظیم می‌شود که عملیات ریاضی یک تفریق باشد؛ این هم فقط با DAA استفاده می‌شود.

cpp#define FLAG_Z 7
#define FLAG_N 6
#define FLAG_H 5
#define FLAG_C 4

هر مقدار، بیتِ همان پرچم در ثبات F است.

شمارندهٔ برنامه و اشاره‌گر پشته

شمارندهٔ برنامه (program counter) آدرس اپکد بعدی برای اجرا در حافظه است. برخی اپکدها به یک یا دو بایت بعدی در حافظه به‌عنوان آرگومان نیاز دارند؛ در این حالت شمارندهٔ برنامه باید از آن‌ها عبور کند تا به اپکد واقعی بعدی برسد. حافظهٔ گیم‌بوی 0x10000 بایت است (بازهٔ ۰ تا 0xFFFF) که دقیقاً همان محدودهٔ نوع دادهٔ unsigned word است؛ برای نمایش شمارندهٔ برنامه عالی است. شمارندهٔ برنامه با دستورهای پرش، فراخوانی و اجرای وقفه‌ها تغییر می‌کند و به‌صورت اولیه 0x100 تنظیم می‌شود.

پشته (stack) ناحیه‌ای در حافظه است که داده در آن بارگذاری می‌شود؛ آخرین داده‌ای که روی پشته گذاشته شود، اول از آن گرفته می‌شود. اشاره‌گر پشته (stack pointer) به بالاترین نقطهٔ پشته در حافظه اشاره می‌کند؛ یعنی همان جایی که دادهٔ بعدیِ اضافه‌شونده به پشته قرار می‌گیرد. مثل شمارندهٔ برنامه، اشاره‌گر پشته به آدرس حافظه اشاره می‌کند؛ پس نوع WORD برای آن مناسب است. اما برخی اپکدها از بایت بالا/پایین اشاره‌گر پشته استفاده می‌کنند؛ پس بهتر است مانند ثبات‌ها شبیه‌سازی شود. مقدار اولیهٔ آن 0xFFFE است:

cppWORD m_ProgramCouner ;
Register m_StackPointer

کنترل و نقشهٔ حافظه (Memory Control and Map)

نقشهٔ حافظه

برگرفته از pandocs ناکش، نقشهٔ حافظه به این صورت است:

text  0000-3FFF   16KB ROM Bank 00     (در کارتریج، ثابت در بانک 00)
  4000-7FFF   16KB ROM Bank 01..NN (در کارتریج، بانک قابل تعویض)
  8000-9FFF   8KB Video RAM (VRAM) (بانک قابل تعویض 0-1 در حالت CGB)
  A000-BFFF   8KB External RAM     (در کارتریج، بانک قابل تعویض، اگر باشد)
  C000-CFFF   4KB Work RAM Bank 0 (WRAM)
  D000-DFFF   4KB Work RAM Bank 1 (WRAM)  (بانک قابل تعویض 1-7 در حالت CGB)
  E000-FDFF   همان C000-DDFF (ECHO)       (معمولاً استفاده نمی‌شود)
  FE00-FE9F   جدول مشخصات اسپرایت (OAM)
  FEA0-FEFF   قابل استفاده نیست
  FF00-FF7F   پورت‌های ورودی/خروجی
  FF80-FFFE   RAM پرسرعت (HRAM)
  FFFF        ثبات فعال‌سازی وقفه (Interrupt Enable)

همان‌طور که قبلاً گفته شد، حافظهٔ داخلی فقط برای 0x8000 (0x0000-0x7FFF) از حافظهٔ بازی جا دارد؛ اما بیشتر بازی‌ها بزرگ‌تر از 0x8000 هستند و به همین دلیل بانک‌بندی حافظه لازم است.

اولین 0x4000 بایت جایی است که 0x4000 بایت اول حافظهٔ بازی (بانک ROM 0) قرار می‌گیرد. دومین 0x4000 (0x4000-0x7FFF) هم برای حافظهٔ بازی است؛ اما این ناحیه ناحیهٔ بانک ROM است؛ یعنی بسته به وضعیت فعلی بازی، این ناحیه بانک‌های مختلفی از حافظهٔ بازی را نگه می‌دارد. بانک‌بندی در بخش «بانک‌بندی ROM و RAM» مفصل بحث می‌شود. ناحیهٔ 0xA000-0xBFFF هم برای بانک‌بندی است اما این بار بانک‌بندی RAM. ناحیهٔ ECHO (0xE000-0xFDFF) متفاوت است؛ هر داده‌ای که اینجا نوشته شود در ناحیهٔ معادل RAM یعنی 0xC000-0xDDFF هم نوشته می‌شود؛ برای همین اسمش echo است. شاید بپرسید آیا نوشتن در RAM هم در ECHO منعکس می‌شود؟ نویسنده می‌گوید نمی‌داند؛ فکر می‌کند بله، اما هر وقت آن را شبیه‌سازی کرده هیچ‌وقت درست کار نکرده، پس آن را برداشته و هیچ مشکلی هم پیش نیامده. HRAM جایی است که پشته داده‌هایش را ذخیره می‌کند؛ اشاره‌گر پشته از 0xFFFE شروع می‌شود و هر بار که چیزی push شود در حافظه پایین می‌آید.

کنترل حافظه

حالا که اجزای حافظهٔ داخلی را می‌دانیم، مشخص است که دسترسی خواندن/نوشتن به حافظه باید به‌خوبی کنترل شود. مثلاً 0x8000 بایت اول فقط‌خواندنی است و هیچ‌چیز نباید آنجا نوشته شود. همچنین هر چیزی که در حافظهٔ ECHO نوشته شود باید در Work RAM هم منعکس شود. علاوه بر این هنگام خواندن از یکی از بانک‌ها مهم است که از بانک صحیح خوانده شود. بهترین راه کنترل دسترسی خواندن/نوشتن به حافظه، ساخت توابع ReadMemory و WriteMemory است. هر بار که می‌خواهید در حافظه بخوانید/بنویسید حتماً باید از این دو تابع استفاده کنید تا مطمئن باشید دسترسی به حافظه درست کنترل می‌شود. تنها استثنا مقداردهی اولیهٔ ROM است که در بخش سخت‌افزار نشان داده شد. نمونه‌ای از کمک WriteMemory به کنترل دسترسی حافظه:

cppvoid Emulator::WriteMemory(WORD address, BYTE data)
{
   // اجازهٔ نوشتن در حافظهٔ فقط‌خواندنی را نده
   if ( address < 0x8000 )
   {
   }

   // نوشتن در ECHO یعنی نوشتن در RAM هم
   else if ( ( address >= 0xE000 ) && (address < 0xFE00) )
   {
     m_Rom[address] = data ;
     WriteMemory(address-0x2000, data) ;
   }

   // این ناحیه محدود است
   else if ( ( address >= 0xFEA0 ) && (address < 0xFEFF) )
   {
   }

   // این ناحیه نیازی به کنترل ندارد؛ پس بنویس
   else
   {
     m_Rom[address] = data ;
   }
}

این نسخهٔ خیلی ساده‌شدهٔ WriteMemory است اما ایدهٔ اصلی اهمیت آن را می‌رساند. این تابع در بخش‌های بعدی گسترش پیدا می‌کند. ReadMemory در بخش بعدی یعنی «بانک‌بندی ROM و RAM» مفصلاً بحث می‌شود.

بانک‌بندی ROM و RAM (ROM and RAM Banking)

تشخیص حالت بانک ROM

دو نوع بانک‌بندی ROM شبیه‌سازی شده: MBC1 و MBC2. اکثر بازی‌ها (۸۰٪) MBC1 هستند؛ پس برای داشتن یک شبیه‌ساز خوب این الزامی است. برخی بازی‌ها مثل Tetris و Bubble Ghost اصلاً بانک‌بندی ROM ندارند؛ کل بازی را در ناحیهٔ 0x0-0x8000 بارگذاری می‌کنند و هرگز نیازی به تعویض حافظه نیست. برای تشخیص حالت ROM بازی باید بعد از بارگذاری بازی در حافظه، خانهٔ 0x147 را بخوانید. اگر 0x147 برابر 0 باشد بازی بانک‌بندی حافظه ندارد (مثل تتریس)؛ اگر 1، 2 یا 3 باشد MBC1 و اگر 5 یا 6 باشد MBC2 است:

cppm_MBC1 = false ;
m_MBC2 = false ;
switch (m_CartridgeMemory[0x147])
{
   case 1 : m_MBC1 = true ; break ;
   case 2 : m_MBC1 = true ; break ;
   case 3 : m_MBC1 = true ; break ;
   case 5 : m_MBC2 = true ; break ;
   case 6 : m_MBC2 = true ; break ;
   default : break ;
}

همچنین به یک متغیر نیاز داریم که مشخص کند کدام بانک ROM در حال حاضر در آدرس 0x4000-0x7FFF بارگذاری شده است. چون بانک ROM 0 ثابت در 0x0-0x3FFF است، این متغیر هرگز نباید 0 باشد؛ حداقل باید 1 باشد. این متغیر هنگام بارگذاری شبیه‌ساز باید 1 مقداردهی شود:

cppm_CurrentROMBank = 1 ; // از نوع BYTE

تشخیص بانک RAM

آدرس 0x148 از حافظهٔ کارتریج می‌گوید بازی چند بانک RAM دارد. حداکثر ۴ بانک است. اندازهٔ هر بانک RAM برابر 0x2000 بایت است؛ پس اگر آرایه‌ای به اندازهٔ 0x8000 داشته باشیم، جا برای همهٔ بانک‌های RAM کافی است. مثل بانک ROM به یک متغیر هم برای اشاره به بانک RAM فعلی (بین 0 تا 3) نیاز داریم:

cppBYTE m_RAMBanks[0x8000] ;
BYTE m_CurrentRAMBank ;

memset(&m_RAMBanks,0,sizeof(m_RAMBanks)) ;
m_CurrentRAMBank = 0 ;

بانک RAM در MBC2 استفاده نمی‌شود؛ پس m_CurrentRAMBank همیشه 0 است!

کنترل خواندن از ROM و RAM

همان‌طور که در بخش «کنترل و نقشهٔ حافظه» گفته شد، باید خواندن و نوشتن از حافظهٔ داخلی را کنترل کنیم. دلیل اصلی کنترل خواندن این است که مطمئن شویم همه‌چیز از بانک‌های ROM و RAM صحیح خوانده می‌شود:

cpp// read memory نباید هیچ‌وقت متغیرهای عضو را تغییر دهد؛ پس const
BYTE Emulator::ReadMemory(WORD address) const
{
   // آیا از بانک حافظهٔ ROM می‌خوانیم؟
   if ((address>=0x4000) && (address <= 0x7FFF))
   {
     WORD newAddress = address - 0x4000 ;
     return m_CartridgeMemory[newAddress + (m_CurrentROMBank*0x4000)] ;
   }

   // آیا از بانک حافظهٔ RAM می‌خوانیم؟
   else if ((address >= 0xA000) && (address <= 0xBFFF))
   {
     WORD newAddress = address - 0xA000 ;
     return m_RAMBanks[newAddress + (m_CurrentRAMBank*0x2000)] ;
   }

   // در غیر این صورت حافظه را برگردان
   return m_Rom[address] ;
}

راحت بود، نه؟ امیدوارم حالا ببینید چرا هنگام دسترسی به حافظهٔ داخلی گیم‌بوی حتماً باید از ReadMemory و WriteMemory استفاده کنید.

تغییر بانک‌های ROM و RAM فعلی

حالا که می‌دانیم از بانک‌های صحیح بخوانیم، سؤال این است: بازی چگونه درخواست تغییر بانک می‌دهد؟ به نظر نویسنده این یکی از سخت‌ترین بخش‌های شبیه‌سازی گیم‌بوی است؛ کدنویسی‌اش سخت نیست اما فهم اینکه باید چه کار کنید سخت است. نحوهٔ کار این‌طور است: بازی تلاش می‌کند مستقیم در ROM بنویسد، اما تابع WriteMemory ما این نوشتن را به دام می‌اندازد و رمزگشایی می‌کند که چرا بازی می‌خواهد در ROM بنویسد. بسته به آدرسِ نوشتن در ROM اقدام متفاوتی لازم است:

  • آدرس 0x2000-0x4000: تغییر بانک ROM است.
  • آدرس 0x4000-0x6000: بسته به حالت ROM/RAM فعلی، تغییر بانک RAM یا ROM است (در ادامه توضیح داده می‌شود).
  • آدرس 0x0-0x2000: فعال‌سازی نوشتن در بانک RAM (در ادامه توضیح داده می‌شود).
cppvoid Emulator::WriteMemory(WORD address, BYTE data)
{
   if (address < 0x8000)
   {
     HandleBanking(address,data) ;
   }

   else if ((address >= 0xA000) && (address < 0xC000))
   {
     if (m_EnableRAM)
     {
       WORD newAddress = address - 0xA000 ;
       m_RAMBanks[newAddress + (m_CurrentRAMBank*0x2000)] = data ;
     }
   }
   // بقیهٔ این تابع مثل قبل ادامه پیدا می‌کند
}

///////////////////////////////////////////////////////////////

void Emulator::HandleBanking(WORD address, BYTE data)
{
   // فعال‌سازی RAM
   if (address < 0x2000)
   {
     if (m_MBC1 || m_MBC2)
       DoRamBankEnable(address,data) ;
   }

   // تغییر بانک ROM
   else if ((address >= 0x200) && (address < 0x4000))
   {
     if (m_MBC1 || m_MBC2)
       DoChangeLoROMBank(data) ;
   }

   // تغییر بانک ROM یا RAM
   else if ((address >= 0x4000) && (address < 0x6000))
   {
     // در MBC2 بانک RAM وجود ندارد؛ پس همیشه بانک 0 استفاده می‌شود
     if (m_MBC1)
     {
       if(m_ROMBanking)
         DoChangeHiRomBank(data) ;
       else
         DoRAMBankChange(data) ;
     }
   }

   // این بخش تعیین می‌کند با if بالا تغییر بانک ROM انجام شود یا RAM
   else if ((address >= 0x6000) && (address < 0x8000))
   {
     if (m_MBC1)
       DoChangeROMRAMMode(data) ;
   }
}

فعال‌سازی RAM

برای نوشتن در بانک‌های RAM، بازی باید صریحاً درخواست فعال‌سازی نوشتن در RAM بدهد. این کار را با تلاش برای نوشتن در آدرس 0 تا 0x2000 حافظهٔ ROM انجام می‌دهد. در MBC1 اگر نیبل پایین دادهٔ نوشته‌شده برابر 0xA باشد، نوشتن در RAM فعال می‌شود و اگر نیبل پایین برابر 0 باشد غیرفعال می‌شود. MBC2 دقیقاً مثل همین است، فقط یک شرط اضافه دارد: بیت ۴ از بایت آدرس باید 0 باشد:

cppvoid Emulator::DoRAMBankEnable(WORD address, BYTE data)
{
   if (m_MBC2)
   {
     if (TestBit(address,4) == 1) return ;
   }

   BYTE testData = data & 0xF ;
   if (testData == 0xA)
     m_EnableRAM = true ;
   else if (testData == 0x0)
     m_EnableRAM = false ;
}

تغییر بانک ROM — بخش ۱

اگر بانک حافظه MBC1 باشد، تغییر بانک ROM فعلی دو بخش دارد. راه اول: اگر بازی در آدرس 0x2000-0x3FFF بنویسد، ۵ بیت پایین بانک ROM فعلی تغییر می‌کند، نه بیت‌های 5 و 6. راه دوم: نوشتن در آدرس 0x4000-0x5FFF در حالت ROM banking (که بعداً توضیح داده می‌شود) فقط بیت‌های 5 و 6 را تغییر می‌دهد، نه بیت‌های 0-4. پس با ترکیب این دو روش می‌توانید بیت‌های 0-6 بانک ROM فعلی را تغییر دهید. اما اگر بازی MBC2 باشد خیلی آسان‌تر است: نوشتن در آدرس 0x2000-0x3FFF بیت‌های 0-3 بانک ROM فعلی را تغییر می‌دهد و بیت‌های 5-6 هرگز تنظیم نمی‌شوند؛ یعنی نوشتن در آدرس 0x4000-0x5FFF در حالت MBC2 هیچ کاری نمی‌کند.

cppvoid Emulator::DoChangeLoROMBank(BYTE data)
{
   if (m_MBC2)
   {
     m_CurrentROMBank = data & 0xF ;
     if (m_CurrentROMBank == 0) m_CurrentROMBank++ ;
     return ;
   }

   BYTE lower5 = data & 31 ;
   m_CurrentROMBank &= 224 ; // ۵ بیت پایین را خاموش کن
   m_CurrentROMBank |= lower5 ;
   if (m_CurrentROMBank == 0) m_CurrentROMBank++ ;
}

پس اگر MBC2 استفاده می‌کنیم، بانک ROM فعلی برابر نیبل پایین داده می‌شود. اما در MBC1 باید ۵ بیت پایین بانک ROM فعلی را به ۵ بیت پایین داده تنظیم کنیم در حالی که ۳ بیت بالای آن ثابت می‌ماند. شاید بپرسید چرا وقتی m_CurrentROMBank صفر می‌شود آن را یکی زیاد می‌کنیم؟ چون بانک ROM 0 ثابت است و همیشه در آدرس 0x000-0x4000 یافت می‌شود؛ پس بانک 0 هرگز نباید در حافظهٔ 0x4000-0x8000 بارگذاری شود. اگر m_CurrentROMBank هیچ‌وقت صفر شود، به‌عنوان بانک 1 رفتار می‌شود تا بانک 1 یا بیشتر در ناحیهٔ 0x4000-0x8000 قرار بگیرد.

تغییر بانک ROM — بخش ۲

همان‌طور که گفتیم، در حالت MBC1 دو راه برای تغییر بانک ROM فعلی وجود دارد. این یکی بیت‌های 5 و 6 را هنگام نوشتن در آدرس 0x4000-0x6000 (وقتی m_RomBanking true است) تغییر می‌دهد:

cppvoid Emulator::DoChangeHiRomBank(BYTE data)
{
   // ۳ بیت بالای بانک ROM فعلی را خاموش کن
   m_CurrentROMBank &= 31 ;

   // ۵ بیت پایین داده را خاموش کن
   data &= 224 ;
   m_CurrentROMBank |= data ;
   if (m_CurrentROMBank == 0) m_CurrentROMBank++ ;
}

تغییر بانک RAM

در MBC2 نمی‌توانید بانک RAM را تغییر دهید؛ چون RAM خارجی روی کارتریج دارد. برای تغییر بانک RAM در MBC1، بازی باید دوباره در آدرس 0x4000-0x6000 بنویسد اما این بار m_RomBanking باید false باشد. بانک RAM فعلی به ۲ بیت پایین داده تنظیم می‌شود:

cppvoid Emulator::DoRAMBankChange(BYTE data)
{
   m_CurrentRAMBank = data & 0x3 ;
}

انتخاب حالت بانک ROM یا RAM

آخرین بخش این ماراتن بانک‌بندی، همان m_RomBanking است که مدام درباره‌اش صحبت می‌شود. این متغیر مشخص می‌کند وقتی بازی در آدرس 0x4000-0x6000 می‌نویسد چه اتفاقی بیفتد. مقدار پیش‌فرض این متغیر true است اما در حالت MBC1 وقتی بازی در آدرس 0x6000-0x8000 می‌نویسد تغییر می‌کند. اگر کم‌ارزش‌ترین بیت دادهٔ نوشته‌شده در این بازه برابر 0 باشد، m_RomBanking برابر true می‌شود؛ در غیر این صورت false می‌شود، یعنی قرار است تغییر بانک RAM رخ دهد. مهم است هر بار m_RomBanking را true می‌کنید m_CurrentRAMBank را 0 کنید؛ چون گیم‌بوی در این حالت فقط می‌تواند از بانک RAM 0 استفاده کند:

cppvoid Emulator::DoChangeROMRAMMode(BYTE data)
{
   BYTE newData = data & 0x1 ;
   m_RomBanking = (newData == 0)?true:false ;
   if (m_RomBanking)
     m_CurrentRAMBank = 0 ;
}

بانک‌بندی تمام شد. بخش بعدی یعنی تایمرها از این آسان‌تر است!

تایمرها (The Timers)

این بخش را با زمان‌بندیِ بخش «شروع کار» اشتباه نگیرید. آن تایمرها دربارهٔ تنظیم سرعت صحیح شبیه‌سازی و همگام‌سازی CPU با گرافیک بود. گیم‌بوی یک تایمر در حافظه دارد که با فرکانس مشخصی شمارش می‌کند و هنگام سرریز درخواست وقفه می‌دهد؛ این تایمر موضوع این بخش است.

تایمر در آدرس 0xFF05 قرار دارد و با فرکانس تنظیم‌شده شمارش می‌کند. فرکانس توسط کنترل‌کنندهٔ تایمر در آدرس 0xFF07 تنظیم می‌شود. هر بار که تایمر سرریز می‌شود (به یاد داشته باشید همهٔ عناصر حافظه بایت بدون علامت هستند؛ پس سرریز یعنی بزرگ‌تر از 255)، یک وقفهٔ تایمر درخواست می‌کند و خودش به مقدار تعدیل‌گر تایمر (timer modulator) در آدرس 0xFF06 بازنشانی می‌شود:

cpp#define TIMA 0xFF05
#define TMA 0xFF06
#define TMC 0xFF07

شبیه‌سازی زمان

۴ فرکانس وجود دارد که کنترل‌کنندهٔ تایمر (TMC) می‌تواند تایمر (TIMA) را با آن‌ها شمارش کند:

text4096 Hz
262144 Hz
65536 Hz
16384 Hz

مثلاً 4096Hz یعنی تایمر باید 4096 بار در ثانیه افزایش یابد؛ یعنی اگر تعدیل‌گر همیشه 0 باشد، تایمر 16 بار در ثانیه سرریز می‌شود (4096/256). این برای اطمینان از دقت شبیه‌سازی تایمر مهم است (به شرطی که وقفهٔ تایمر فعال باشد که در فصل بعد بحث می‌شود). با فرکانس 4096 چطور آن را شبیه‌سازی کنیم؟ خوشبختانه چون زمان‌بندی CPU را با جمع‌کردن چرخه‌های ساعت هر اپکد در هر فریم دقیق شبیه‌سازی می‌کنیم، اگر فرکانس فعلی تایمر را بدانیم می‌توانیم محاسبه کنیم چند چرخهٔ ساعت باید بگذرد تا ثبات تایمر را افزایش دهیم:

cpp#define CLOCKSPEED 4194304 ;
m_TimerCounter = CLOCKSPEED/frequency ;

m_TimerCounter از نوع int است و در شروع شبیه‌سازی باید 1024 تنظیم شود (در ادامه توضیح داده می‌شود). پس اگر فرکانس فعلی 4096Hz باشد، شمارندهٔ تایمر برابر 1024 (4194304/4096) می‌شود؛ یعنی «به ازای هر 1024 چرخهٔ ساعت CPU، تایمر باید یک بار افزایش یابد». اما اگر فرکانس 16384 بود، شمارنده 256 (4194304/16384) می‌شود؛ یعنی «به ازای هر 256 چرخهٔ ساعت CPU، تایمر یک بار افزایش می‌یابد».

اگر به حلقهٔ اصلی به‌روزرسانی شبیه‌ساز نگاه کنید (بخش «شروع کار») می‌بینید که تایمرها با تابع UpdateTimers در نظر گرفته شده‌اند و چرخهٔ ساعت آخرین اپکد به آن پاس داده می‌شود. پیاده‌سازی UpdateTimers:

cppvoid Emulator::UpdateTimers( int cycles )
{
   DoDividerRegister(cycles) ;
   // ساعت باید فعال باشد تا به‌روزرسانی انجام شود
   if (IsClockEnabled())
   {
     m_TimerCounter -= cycles ;

     // تعداد کافی چرخهٔ ساعت CPU برای به‌روزرسانی تایمر گذشته است
     if (m_TimerCounter <= 0)
     {
       // m_TimerCounter را به مقدار صحیح بازنشانی کن
       SetClockFreq( ) ;

       // تایمر در آستانهٔ سرریز است
       if (ReadMemory(TIMA) == 255)
       {
         WriteMemory(TIMA,ReadMemory(TMA)) ;
         RequestInterupt(2) ;
       }
       else
       {
         WriteMemory(TIMA, ReadMemory(TIMA)+1) ;
       }
     }
   }
}

توابع DoDividerRegister و IsClockEnabled کمی بعد پیاده‌سازی می‌شوند. IsClockEnabled اساساً تنظیمی در کنترل‌کنندهٔ تایمر (TMC) است که شمارش تایمر را متوقف یا ادامه می‌دهد. اگر false برگرداند، نه تایمر خودش را بازنشانی می‌کند و نه شمارندهٔ تایمر؛ هر دو فقط مکث می‌کنند تا دوباره فعال شوند. هدف SetClockFreq بازنشانی m_TimerCounter هنگام رسیدن به صفر با مقدار صحیح برای فرکانس ساعت فعلی است تا با نرخ درست دوباره شمارش معکوس را شروع کند. بقیهٔ کد فقط مقدار فعلی تایمر (TIMA) را افزایش می‌دهد و بررسی می‌کند که در آستانهٔ سرریز هست یا نه. اگر سرریز شود، تایمر (TIMA) به مقدار تعدیل‌گر تایمر (TMA) بازنشانی و یک وقفهٔ تایمر درخواست می‌شود. وقفهٔ تایمر بیت ۲ از ثبات درخواست وقفه است که در فصل بعد کاملاً توضیح داده می‌شود.

کنترل‌کنندهٔ تایمر

کنترل‌کنندهٔ تایمر (TMC) یک ثبات ۳ بیتی است که تایمر را کنترل می‌کند. بیت‌های 1 و 0 با هم مشخص می‌کنند تایمر با چه فرکانسی افزایش یابد:

text00: 4096 Hz
01: 262144 Hz
10: 65536 Hz
11: 16384 Hz

بیت 2 مشخص می‌کند تایمر فعال(1) یا غیرفعال(0) است. با این اطلاعات تابع IsClockEnabled:

cppbool Emulator::IsClockEnabled() const
{
   return TestBit(ReadMemory(TMC),2)?true:false ;
}

همان‌طور که گفته شد، فرکانس پیش‌فرض 4096Hz است اما باید راهی برای تشخیص تغییر آن داشته باشیم. ساده‌ترین راه این است که تابع WriteMemory را طوری ویرایش کنیم که تغییر کنترل‌کنندهٔ تایمر را تشخیص دهد. اگر بازی در حال تغییر کنترل‌کنندهٔ تایمر است، باید بررسی کنیم فرکانس ساعت فعلی با فرکانس جدید فرق دارد یا نه؛ اگر فرق دارد باید شمارندهٔ تایمر را بازنشانی کنیم تا با فرکانس جدید شمارش کند:

{

همان‌طور که قبلاً گفتیم، m_TimerCounter برابر CLOCKSPEED/frequency تنظیم می‌شود.

ثبات تقسیم‌کننده (Divider Register)

آخرین ناحیهٔ مرتبط با زمان‌بندی که باید شبیه‌سازی شود، ثبات تقسیم‌کننده است. خیلی شبیه تایمرها کار می‌کند؛ به همین دلیل در این بخش گنجانده شده و کدش داخل تابع UpdateTimers است. طرز کار: دائماً از 0 تا 255 شمارش می‌کند و وقتی سرریز شد دوباره از 0 شروع می‌کند. هنگام سرریز وقفه ایجاد نمی‌کند و مثل تایمرها نمی‌توان آن را متوقف کرد. با فرکانس 16382 شمارش می‌کند؛ یعنی هر 256 چرخهٔ ساعت CPU باید یک بار افزایش یابد. مثل m_TimerCounter به یک شمارندهٔ int دیگر برای پیگیری زمان افزایش نیاز داریم؛ اسمش m_DividerCounter است که ابتدا 0 تنظیم می‌شود و مدام تا 255 افزایش و بعد دوباره شروع می‌کند. ثبات تقسیم‌کننده در آدرس 0xFF04 است. تابع DoDividerRegister که در UpdateTimers صدا زده می‌شود این‌طور شبیه‌سازی می‌شود:

cppvoid Emulator::DoDividerRegister(int cycles)
{
   m_DividerCounter += cycles ;
   if (m_DividerCounter >= 255)
   {
     m_DividerCounter = 0 ;
     m_Rom[0xFF04]++ ;
   }
}

شاید بپرسید چرا ثبات تقسیم‌کننده مستقیم افزایش می‌یابد و از WriteMemory استفاده نمی‌شود. پاسخ: سخت‌افزار گیم‌بوی اجازهٔ نوشتن در ثبات تقسیم‌کننده را نمی‌دهد و هر وقت بازی تلاش کند، ثبات تقسیم‌کننده به 0 بازنشانی می‌شود. باید این رفتار را خودمان در WriteMemory پیاده کنیم؛ به همین دلیل نمی‌توانیم از این تابع برای افزایش ثبات تقسیم‌کننده استفاده کنیم، چون همیشه آن را 0 می‌کند! پس باید تابع نوشتن حافظه را طوری ویرایش کنیم که ثبات تقسیم‌کننده را به دام بیندازد:

cpp// ثبات تقسیم‌کننده را به دام بینداز
else if (0xFF04 == address)
   m_Rom[0xFF04] = 0 ;

این همهٔ ماجرای تایمرها بود. بروید سراغ بخش بعدی یعنی وقفه‌ها.

وقفه‌ها (Interrupts)

چون سیستم chip8 هیچ وقفه‌ای نداشت، اول توضیح می‌دهیم وقفه چیست و چه هدفی دارد. وقفه معمولاً یک سیگنال سخت‌افزاری است که به CPU می‌گوید اتفاق خاصی افتاده است. CPU تنظیماتش را بررسی می‌کند تا ببیند می‌تواند به آن وقفه پاسخ دهد یا نه. نحوهٔ پاسخ CPU به وقفه این‌طور است: شمارندهٔ برنامهٔ فعلی را روی پشته ذخیره می‌کند و به آدرس روال سرویس وقفه (interrupt service routine) مناسب می‌پرد. سپس تا پایان روال به سرویس وقفه ادامه می‌دهد و بعد شمارندهٔ برنامهٔ قدیمی را بارگذاری می‌کند و اجرا را از همان‌جا که قطع شده بود ادامه می‌دهد؛ برای همین اسمش وقفه (interrupt) است.

دو ثبات ویژه برای وضعیت مدیریت وقفه در گیم‌بوی وجود دارد. اولی ثبات فعال‌سازی وقفه (Interrupt Enable یا IE) در آدرس 0xFFFF است؛ بازی با نوشتن در آن وقفه‌های خاصی را فعال/غیرفعال می‌کند. مثلاً ممکن است رویدادی مثل سرریز تایمر، وقفه‌ای را تحریک کند، اما این وقفه فقط در صورتی سرویس می‌شود که بیت متناظرش در IE فعال باشد. اگر فعال باشد سرویس می‌شود اما اگر نباشد، وقفه منتظر می‌ماند تا فعال شود یا بازی درخواستش را بازنشانی کند. دومی ثبات درخواست وقفه (Interrupt Request یا IF) در آدرس 0xFF0F است. باز هم با مثال وقفهٔ تایمر: هر بار تایمر سرریز می‌شود، بیت متناظرش را در IF تنظیم می‌کند و آن بیت تا شروع سرویس وقفه یا بازنشانی توسط بازی تنظیم‌شده می‌ماند. آخرین نکتهٔ مدیریت وقفه، کلید اصلی فعال‌سازی وقفه (master interrupt enabled switch) است. این بخشی از حافظهٔ بازی نیست و فقط یک bool است که بازی روشن/خاموشش می‌کند. وقتی این bool false باشد هیچ وقفه‌ای سرویس نمی‌شود. معیارهای مدیریت وقفه:

  1. وقتی رویدادی رخ می‌دهد که باید وقفهٔ خودش را تحریک کند، باید با تنظیم بیت متناظرش در ثبات درخواست وقفه (0xFF0F) درخواست وقفه بدهد.
  2. یک وقفه فقط وقتی سرویس می‌شود که کلید اصلی فعال‌سازی وقفه true باشد.
  3. اگر دو شرط بالا درست باشد و وقفهٔ دیگری با اولویت بالاتر در انتظار سرویس نباشد، ثبات فعال‌سازی وقفه (0xFFFF) بررسی می‌شود تا بیت متناظر آن وقفه 1 باشد تا سرویس این وقفه مجاز شود.

کلید اصلی با دستورهای CPU یعنی EI و DI به‌ترتیب true و false می‌شود. اگر شرط 2 یا 3 false باشد، وقفه همچنان منتظر می‌ماند تا هر دو درست شوند و بازی درخواست وقفه را با بازنشانی بیت متناظرش در IF خاموش نکرده باشد.

وقفه‌های گیم‌بوی

چند بار اشاره شد که هر وقفه بیت متناظری در ثبات فعال‌سازی و درخواست وقفه دارد؛ همچنین ۴ وقفهٔ گیم‌بوی را شبیه‌سازی می‌کنیم. لیست وقفه‌ها و بیت متناظرشان:

textBit 0: وقفهٔ V-Blank
Bit 1: وقفهٔ LCD
Bit 2: وقفهٔ تایمر
Bit 4: وقفهٔ جوای‌پد

این هم ترتیب اولویت وقفه‌هاست؛ هر چه بیت کمتر باشد اولویت بالاتر است. پس V-Blank بالاترین اولویت را دارد؛ یعنی اگر این وقفه و وقفهٔ دیگری هم‌زمان در IF درخواست شوند، اول V-Blank سرویس می‌شود.

  • V-BLANK: گیم‌بوی نمایشگر را خط‌به‌خط رسم می‌کند. نمایشگر ۱۴۴ خط اسکن دارد و وقتی آخرین خط رسم شد، از اول شروع می‌کند. زمان بین رسم خط ۱۴۴ و شروع دوباره از خط 0، دورهٔ V-Blank نام دارد و همین‌جاست که وقفهٔ v-blank درخواست می‌شود. این مهم‌ترین وقفه برای شبیه‌سازی صحیح است؛ چون در طول V-Blank بازی می‌تواند از حافظه‌ای که قبلاً محدود بود (عمدتاً حافظهٔ ویدیویی) بخواند. گیم‌بوی نرخ تازه‌سازی عمودی ۶۰ فریم در ثانیه دارد؛ یعنی اگر شرایط 2 و 3 همیشه درست باشد، باید ۶۰ وقفهٔ V-Blank در ثانیه داشته باشیم. برای اطمینان از دقت شبیه‌سازی V-Blank این را کنترل کنید.
  • LCD: دلایل زیادی برای درخواست وقفه توسط LCD وجود دارد که در فصل بعد (LCD) مفصل بررسی می‌شوند. نکتهٔ اصلی این است که وقفهٔ LCD به بازی می‌گوید LCD در چه وضعیتی است؛ چون بسته به وضعیت، برخی نواحی حافظه محدود می‌شوند. بازی همچنین می‌تواند متغیر هم‌زمانی (coincidence) تنظیم کند؛ یعنی «وقتی خط اسکن فعال‌ات به X رسید به من خبر بده». یکی از چیزهایی که نویسنده را گیج کرده بود این بود که وقفهٔ LCD می‌تواند هر بار V-Blank اتفاق بیفتد درخواست شود. نمی‌فهمید چرا دو وقفهٔ v-blank وجود دارد؛ یکی اصلی که بالا توضیح داده شد و یکی تو‌در‌تو‌ی وقفهٔ LCD. باید به یاد داشته باشید که در طول V-Blank اگر بازی اجازه دهد، دو وقفهٔ V-Blank درخواست می‌شود: اولی وقفهٔ اصلی V-Blank و دومی وقفهٔ LCD. اما وقفهٔ اول اولویت بالاتری دارد.
  • TIMER: این وقفه قبلاً در بخش تایمرها بحث شد. خلاصه: تایمر گیم‌بوی با فرکانس پویا شمارش می‌کند و وقتی به ۲۵۵ رسید و در آستانهٔ سرریز بود، با درخواست وقفهٔ تایمر به بازی خبر می‌دهد.
  • JOYPAD: جوای‌پد در فصل جوای‌پد بحث می‌شود. این وقفه هر بار که یکی از دکمه‌ها از حالت فشرده‌نشده به فشرده‌شده تغییر کند درخواست می‌شود.

درخواست وقفه

در سراسر بخش گیم‌بوی این سایت، تابع RequestInterupt استفاده می‌شود. هر وقت رویدادی رخ دهد که نیاز به درخواست وقفه دارد، این تابع با بیت شناسهٔ وقفهٔ موردنظر صدا زده می‌شود:

cppvoid Emulator::RequestInterupt(int id)
{
   BYTE req = ReadMemory(0xFF0F) ;
   req = BitSet(req,id) ;
   WriteMemory(0xFF0F,id) ;
}

بررسی وقفه‌ها

حالا که می‌دانیم وقفه در چه شرایطی درخواست می‌شود، باید نحوهٔ مدیریتش را هم بدانیم. به حلقهٔ اصلی به‌روزرسانی در فصل «شروع کار» برگردید؛ بعد از هر اپکد تابعی به نام DoInterupts صدا زده می‌شود. این تابع اول بررسی می‌کند کلید اصلی فعال‌سازی وقفه true است یا نه. اگر true بود، بررسی می‌کند وقفه‌ای در ثبات درخواست وقفه در انتظار است یا نه. اگر بود، همهٔ وقفه‌ها را به ترتیب اولویت بررسی می‌کند تا ببیند کدام درخواست شده. اگر درخواست شده باشد، بررسی می‌کند این وقفه خاص در ثبات فعال‌سازی وقفه فعال است یا نه؛ اگر بود سرویسش می‌کند و اگر نه، به بررسی وقفه‌های با اولویت پایین‌تر ادامه می‌دهد:

cppvoid Emulator::DoInterupts( )
{
   if (m_InteruptMaster == true)
   {
     BYTE req = ReadMemory(0xFF0F) ;
     BYTE enabled = ReadMemory(0xFFFF) ;
     if (req > 0)
     {
       for (int i = 0 ; i < 5; i++)
       {
         if (TestBit(req,i) == true)
         {
           if (TestBit(enabled,i))
             ServiceInterupt(i) ;
         }
       }
     }
   }
}

سرویس وقفه‌ها

حالا که تشخیص دادیم وقفه‌ای باید سرویس شود، چه اتفاقی می‌افتد؟ اول کلید اصلی فعال‌سازی وقفه false می‌شود و بیت متناظرش در ثبات درخواست وقفه هم خاموش می‌شود. هر وقفه یک روال سرویس وقفهٔ مشخص در حافظهٔ بازی دارد که شمارندهٔ برنامه به آن تنظیم می‌شود و اجرا از آنجا ادامه پیدا می‌کند. وقتی سرویس وقفه تمام شد، شمارندهٔ برنامه به جای قبلی‌اش بازگردانده می‌شود و اجرای بازی ادامه می‌یابد. محل روال سرویس هر یک از ۴ وقفه:

textV-Blank: 0x40
LCD: 0x48
TIMER: 0x50
JOYPAD: 0x60
cppvoid Emulator::ServiceInterupt(int interupt)
{
   m_InteruptMaster = false ;
   BYTE req = ReadMemory(0xFF0F) ;
   req = BitReset(req,interupt) ;
   WriteMemory(0xFF0F,req) ;

   // باید آدرس اجرای فعلی را با push کردنش روی پشته ذخیره کنیم
   PushWordOntoStack(m_ProgramCounter) ;

   switch (interupt)
   {
     case 0: m_ProgramCounter = 0x40 ; break ;
     case 1: m_ProgramCounter = 0x48 ; break ;
     case 2: m_ProgramCounter = 0x50 ; break ;
     case 4: m_ProgramCounter = 0x60 ; break ;
   }
}

وقفه‌های تو‌در‌تو (Nested Interrupts)

این بخش مهم است چون دانستنش لازم است، اما چیزی نیست که باید شبیه‌سازی کنید. ممکن است در طول سرویس یکی از وقفه‌ها، وقفه کلید اصلی فعال‌سازی را دوباره فعال کند. با این کار وقفهٔ فعلی می‌تواند توسط وقفهٔ دیگری قطع شود و وقتی وقفهٔ جدید سرویسش تمام شد، وقفهٔ قبلی ادامهٔ سرویس خودش را تمام می‌کند. اگر وقفه‌ها را مثل نویسنده شبیه‌سازی کرده باشید، این قابلیت به‌صورت خودکار کار می‌کند؛ اما دانستنش مفید است؛ مثلاً اگر در لاگ‌های دیباگ ببینید یک وقفه قبل از تمام‌شدن وقفهٔ دیگر، دارد وقفه‌ای را سرویس می‌کند.

خطوط اسکن (Scanlines)

وضوح صفحه 160x144 است؛ یعنی ۱۴۴ خط اسکن قابل‌مشاهده وجود دارد. گیم‌بوی هر خط اسکن را یک‌به‌یک از 0 تا 153 رسم می‌کند؛ یعنی ۱۴۴ خط قابل‌مشاهده و ۸ خط نامرئی. وقتی خط اسکن فعلی بین 144 و 153 باشد، دورهٔ خالی عمودی (vertical blank) است. خط اسکن فعلی در ثبات 0xFF44 ذخیره می‌شود. طبق pandocs رسم هر خط اسکن و رفتن به خط بعدی ۴۵۶ چرخهٔ ساعت CPU طول می‌کشد؛ پس به یک شمارنده نیاز داریم تا بدانیم چه وقت به خط بعدی برویم؛ اسمش را m_ScanlineCounter می‌گذاریم. مثل ثبات‌های تایمر و تقسیم‌کننده می‌توانیم شمارندهٔ خط اسکن را با کم‌کردن تعداد چرخهٔ ساعت آخرین اپکد کنترل کنیم. در حلقهٔ اصلی به‌روزرسانی (فصل شروع کار) تابع UpdateGraphics تعداد چرخهٔ آخرین اپکد را دریافت می‌کند تا گرافیک را دقیقاً با CPU همگام نگه دارد:

cppvoid Emulator::UpdateGraphics(int cycles)
{
   SetLCDStatus( ) ;

   if (IsLCDEnabled())
     m_ScalineCounter -= cycles ;
   else
     return ;

   if (m_ScalineCounter <= 0)
   {
     // وقت رفتن به خط اسکن بعدی است
     m_Rom[0xFF44]++;
     BYTE currentline = ReadMemory(0xFF44) ;

     m_ScalineCounter = 456 ;

     // وارد دورهٔ vertical blank شده‌ایم
     if (currentline == 144)
       RequestInterupt(0) ;

     // اگر از خط اسکن 153 رد شده‌ایم به 0 بازنشانی کن
     else if (currentline > 153)
       m_Rom[0xFF44]=0 ;

     // خط اسکن فعلی را رسم کن
     else if (currentline < 144)
       DrawScanLine() ;
   }
}

اجرای بخش‌هایی از این کد را بعداً می‌دهیم؛ فعلاً توضیح می‌دهیم. اگر نمایشگر LCD فعال باشد باید شمارندهٔ خط اسکن را با کم‌کردن زمان چرخهٔ اپکد آخر به‌روزرسانی کنیم. اگر این باعث منفی‌شدن m_ScanlineCounter شود، وقت رفتن به خط اسکن بعدی است. ثبات 0xFF44 خط اسکن فعلی است؛ پس آن را به خط بعدی افزایش می‌دهیم. اگر خط اسکن جدید 144 باشد، آغاز وقفهٔ vertical blank است؛ پس باید این وقفه را درخواست کنیم (یادتان باشد وقفهٔ vblank بیت 0 است). اگر شک دارید چرا، فصل وقفه‌ها را دوباره بخوانید. اگر خط اسکن فعلی بزرگ‌تر از 153 بود باید به 0 بازنشانی شود. اما اگر کمتر از 144 باشد، یکی از خطوط قابل‌مشاهده است و باید روی صفحه رندر شود؛ این در فصل «شبیه‌سازی گرافیک» توضیح داده می‌شود.

دلیل دسترسی مستقیم به حافظه هنگام نوشتن در آدرس خط اسکن فعلی (0xFF44) به‌جای WriteMemory این است که وقتی بازی تلاش می‌کند در 0xFF44 بنویسد، خط اسکن فعلی به 0 بازنشانی می‌شود؛ پس نمی‌توانیم از WriteMemory برای افزایش خط اسکن استفاده کنیم چون همیشه آن را 0 می‌کند. در همین رابطه باید این کد به WriteMemory اضافه شود:

cpp// اگر بازی تلاش کرد در خط اسکن فعلی بنویسد، آن را بازنشانی کن
else if (address == 0xFF44)
{
   m_Rom[address] = 0 ;
}

تنظیم وضعیت LCD

آدرس 0xFF41 وضعیت فعلی LCD را نگه می‌دارد. LCD از ۴ حالت عبور می‌کند: «دورهٔ V-Blank»، «دورهٔ H-Blank»، «جستجوی مشخصات اسپرایت» و «انتقال داده به درایور LCD». بیت‌های 1 و 0 از وضعیت LCD در آدرس 0xFF41 حالت فعلی LCD را نشان می‌دهند:

text00: H-Blank
01: V-Blank
10: جستجوی مشخصات اسپرایت‌ها
11: انتقال داده به درایور LCD

وقتی خط اسکن جدیدی شروع می‌شود، وضعیت LCD روی 2 تنظیم می‌شود، بعد به 3 و بعد به 0 می‌رود. سپس به حالت 2 برمی‌گردد و این الگو تا شروع دورهٔ v-blank ادامه می‌یابد؛ آنجا روی حالت 1 می‌ماند. وقتی دورهٔ v-blank تمام شد به حالت 2 برمی‌گردد و این الگو بارها و بارها تکرار می‌شود. همان‌طور که قبلاً گفته شد، رسم یک خط اسکن قبل از رفتن به خط بعدی ۴۵۶ چرخهٔ ساعت طول می‌کشد. این مقدار به بخش‌های مختلفی تقسیم می‌شود که نمایانگر حالت‌های مختلف است. حالت 2 (جستجوی مشخصات اسپرایت‌ها) ۸۰ چرخهٔ اول از ۴۵۶ را می‌گیرد. حالت 3 (انتقال به درایور LCD) ۱۷۲ چرخه از ۴۵۶ را می‌گیرد و چرخه‌های باقی‌مانده برای حالت 0 (H-Blank) است.

وقتی وضعیت LCD به حالت 0، 1 یا 2 تغییر می‌کند، ممکن است درخواست وقفهٔ LCD رخ دهد. بیت‌های 3، 4 و 5 از ثبات وضعیت LCD (0xFF41) پرچم‌های فعال‌سازی وقفه هستند (مثل ثبات فعال‌سازی وقفه 0xFFFF). این بیت‌ها توسط بازی تنظیم می‌شوند نه شبیه‌ساز:

textBit 3: فعال‌سازی وقفهٔ حالت 0
Bit 4: فعال‌سازی وقفهٔ حالت 1
Bit 5: فعال‌سازی وقفهٔ حالت 2

پس وقتی حالت به 0، 1 یا 2 تغییر کند، اگر بیت متناظر 3/4/5 تنظیم شده باشد وقفهٔ LCD درخواست می‌شود. این فقط هنگام تغییر حالت به 0/1/2 بررسی می‌شود نه در طول آن حالت‌ها.

یک نکتهٔ مهم در شبیه‌سازی حالت‌های LCD: وقتی LCD غیرفعال است، حالت باید روی حالت 1 تنظیم شود. اگر این کار را نکنید ساعت‌ها وقت تلف می‌کنید (مثل نویسنده) که چرا Mario2 از صفحهٔ عنوان جلوتر نمی‌رود. همچنین باید m_ScanlineCounter و خط اسکن فعلی را بازنشانی کنید.

آخرین بخش ثبات وضعیت LCD (0xFF41) پرچم هم‌زمانی (Coincidence) است. بیت 2 از ثبات وضعیت اگر ثبات 0xFF44 برابر 0xFF45 باشد 1 می‌شود و در غیر این صورت 0. بیت 6 از ثبات وضعیت LCD (0xFF44) مثل بیت‌های فعال‌سازی 3-5 است، اما به حالت فعلی LCD ربطی ندارد و مربوط به پرچم هم‌زمانی بیت 2 است. اگر پرچم هم‌زمانی (بیت 2) تنظیم شده و پرچم فعال‌سازی وقفهٔ هم‌زمانی (بیت 6) هم تنظیم شده باشد، وقفهٔ LCD درخواست می‌شود. پرچم هم‌زمانی یعنی خط اسکن فعلی (0xFF44) با خطی که بازی به آن علاقه دارد (0xFF45) یکی است. دلیل علاقهٔ بازی به خط اسکن فعلی، افکت‌های ویژه است. پس وقتی 0xFF44 برابر 0xFF45 شد می‌توان وقفه درخواست کرد تا به بازی خبر بدهد مقادیر یکی شده‌اند.

حالا اطلاعات کافی برای کنار هم گذاشتن همهٔ این‌ها و پیاده‌سازی SetLCDStatus داریم:

cppvoid Emulator::SetLCDStatus( )
{
   BYTE status = ReadMemory(0xFF41) ;
   if (false == IsLCDEnabled())
   {
     // هنگام غیرفعال‌بودن LCD حالت را 1 کن و خط اسکن را بازنشانی کن
     m_ScanlineCounter = 456 ;
     m_Rom[0xFF44] = 0 ;
     status &= 252 ;
     status = BitSet(status, 0) ;
     WriteMemory(0xFF41,status) ;
     return ;
   }

   BYTE currentline = ReadMemory(0xFF44) ;
   BYTE currentmode = status & 0x3 ;

   BYTE mode = 0 ;
   bool reqInt = false ;

   // در vblank هستیم؛ پس حالت را 1 کن
   if (currentline >= 144)
   {
     mode = 1;
     status = BitSet(status,0) ;
     status = BitReset(status,1) ;
     reqInt = TestBit(status,4) ;
   }
   else
   {
     int mode2bounds = 456-80 ;
     int mode3bounds = mode2bounds - 172 ;

     // حالت 2
     if (m_ScanlineCounter >= mode2bounds)
     {
       mode = 2 ;
       status = BitSet(status,1) ;
       status = BitReset(status,0) ;
       reqInt = TestBit(status,5) ;
     }
     // حالت 3
     else if(m_ScanlineCounter >= mode3bounds)
     {
       mode = 3 ;
       status = BitSet(status,1) ;
       status = BitSet(status,0) ;
     }
     // حالت 0
     else
     {
       mode = 0;
       status = BitReset(status,1) ;
       status = BitReset(status,0) ;
       reqInt = TestBit(status,3) ;
     }
   }

   // تازه وارد حالت جدیدی شده‌ایم؛ پس وقفه درخواست کن
   if (reqInt && (mode != currentmode))
     RequestInterupt(1) ;

   // پرچم هم‌زمانی را بررسی کن
   if (ReadMemory(0xFF44) == ReadMemory(0xFF45))
   {
     status = BitSet(status,2) ;
     if (TestBit(status,6))
       RequestInterupt(1) ;
   }
   else
   {
     status = BitReset(status,2) ;
   }
   WriteMemory(0xFF41,status) ;
}

امیدوارم همهٔ این‌ها منطقی باشد. اگر نه، این بخش را دوباره بخوانید تا منطقی شود. خود نویسنده مدتی طول کشید تا بفهمد وضعیت LCD چطور کار می‌کند.

کنترل LCD

ثبات کنترل LCD (0xFF40) در فصل «شبیه‌سازی گرافیک» مفصل پوشش داده می‌شود؛ اما کد بالا خیلی از تابع IsLCDEnabled استفاده می‌کند که هنوز پیاده‌سازی نشده و به ثبات کنترل LCD وابسته است. بیت 7 این ثبات مسئول فعال/غیرفعال‌کردن LCD است؛ پس IsLCDEnabled این‌طور پیاده می‌شود:

cppbool Emulator::IsLCDEnabled() const
{
   return TestBit(ReadMemory(0xFF40),7) ;
}

فصل LCD تمام شد؛ برویم سراغ انتقال DMA.

انتقال DMA

دسترسی مستقیم به حافظه (Direct Memory Access)

همان‌طور که در فصل LCD توضیح داده شد، CPU فقط در طول یکی از حالت‌های LCD (حالت 2) می‌تواند به جدول مشخصات اسپرایت‌ها دسترسی داشته باشد. DMA راهی است برای کپی‌کردن داده به RAM اسپرایت در زمان مناسب، بدون هیچ مسئولیتی برای برنامهٔ اصلی.

بازی وقتی DMA را شروع می‌کند که تلاش کند در آدرس 0xFF46 بنویسد؛ پس باید این را به WriteMemory اضافه کنیم تا نوشتن در این آدرس به دام بیفتد:

cppelse if (address == 0xFF46)
{
   DoDMATransfer(data) ;
}

پیاده‌سازی انتقال DMA

کد پشت انتقال DMA واقعاً خیلی ساده است؛ اما فهمیدن اینکه چه چیزی لازم است کمی پیچیده است.

همان‌طور که قبلاً اشاره شد، آدرس مقصد DMA همان RAM اسپرایت بین 0xFE00-0xFE9F است؛ یعنی در مجموع 0xA0 بایت به این ناحیه کپی می‌شود. آدرس مبدأ با داده‌ای که در 0xFF46 نوشته می‌شود مشخص می‌شود؛ با این تفاوت که این مقدار، آدرس مبدأ تقسیم بر 0x100 است. پس برای به‌دست‌آوردن آدرس شروع صحیح، داده را در 0x100 ضرب می‌کنیم (برای سرعت، به‌جای ضرب در 0x100، ۸ جا شیفت چپ می‌دهیم که همان کار است):

cppvoid Emulator::DoDMATransfer(BYTE data)
{
   WORD address = data << 8 ; // آدرس مبدأ برابر data * 0x100 است
   for (int i = 0 ; i < 0xA0; i++)
   {
     WriteMemory(0xFE00+i, ReadMemory(address+i)) ;
   }
}

این همهٔ ماجرای DMA بود. فصل بعدی دربارهٔ شبیه‌سازی گرافیک است؛ بهتر است قبل از شروع یک ساندویچ و نوشیدنی بردارید!

شبیه‌سازی گرافیک (Graphics Emulation)

گیم‌بوی برای ذخیره‌سازی و رسم گرافیک روی صفحه از روش تایل‌ها (tiles) و اسپرایت‌ها (sprites) استفاده می‌کند. تایل‌ها چیزی هستند که پس‌زمینه را می‌سازند و تعاملی نیستند. هر تایل 8x8 پیکسل است. اسپرایت‌ها گرافیک تعاملی روی نمایشگرند؛ مثلاً در بازی ماریو، شخصیت ماریو یک اسپرایت است. گرافیک می‌تواند حرکت کند و با بقیهٔ اسپرایت‌ها برخورد داشته باشد. دشمن‌ها هم اسپرایت هستند چون می‌توانند پرواز کنند و به ماریو حمله کنند. تایل‌ها همان پس‌زمینه‌ای هستند که سطح بازی و زمینش را تعریف می‌کنند.

همان‌طور که قبلاً گفته شد، وضوح گیم‌بوی 160x144 است اما این فقط چیزی است که روی صفحه نمایش داده می‌شود. وضوح واقعی 256x256 (32x32 تایل) است. نمایشگر می‌تواند هر 160x144 پیکسلی از پس‌زمینهٔ 256x256 را نشان دهد؛ این امکان اسکرول‌کردن ناحیهٔ دید روی پس‌زمینه را می‌دهد.

علاوه بر پس‌زمینهٔ 256x256 و ناحیهٔ دید 160x144، گیم‌بوی یک پنجره (window) هم دارد که بالای پس‌زمینه و پشت اسپرایت‌ها ظاهر می‌شود (مگر اینکه مشخصات اسپرایت غیر از این بگوید). هدف پنجره این است که یک پنل ثابت روی پس‌زمینه بگذارد که اسکرول نمی‌شود. مثلاً بعضی بازی‌ها پنلی روی صفحه دارند که جان شخصیت و آیتم‌های جمع‌شده را نشان می‌دهد (مخصوصاً Link's Awakening) و این پنل با حرکت شخصیت اسکرول نمی‌شود؛ این همان پنجره است.

این بخش نشان می‌دهد چگونه همهٔ این‌ها را شبیه‌سازی کنیم. مثال‌های زیر برای آسان‌ترین درک ممکن از سیستم تایل و اسپرایت طراحی شده‌اند اما به‌هیچ‌وجه کارآمد نیستند. خوشبختانه شبیه‌سازی گرافیک ناحیه‌ای است که با کمترین تلاش (مثلاً با مستطیل‌های کثیف/dirty rectangles) می‌توان بیشترین بهینه‌سازی سرعت را در آن انجام داد؛ اما این کار نمایش خوبی برای آموزش نمی‌داد.

ثبات کنترل LCD

در فصل LCD به ثبات کنترل LCD اشاره شد. این ثبات دادهٔ زیادی دارد که قبل از شبیه‌سازی گرافیک باید بفهمیم. تفکیک این ثبات ۸ بیتی (برگرفته از pandocs):

text Bit 7 - فعال‌سازی نمایش LCD             (0=خاموش، 1=روشن)
 Bit 6 - انتخاب نقشهٔ تایل پنجره         (0=9800-9BFF، 1=9C00-9FFF)
 Bit 5 - فعال‌سازی نمایش پنجره           (0=خاموش، 1=روشن)
 Bit 4 - انتخاب دادهٔ تایل BG و پنجره     (0=8800-97FF، 1=8000-8FFF)
 Bit 3 - انتخاب نقشهٔ تایل BG             (0=9800-9BFF، 1=9C00-9FFF)
 Bit 2 - اندازهٔ OBJ (اسپرایت)            (0=8x8، 1=8x16)
 Bit 1 - فعال‌سازی نمایش OBJ (اسپرایت)    (0=خاموش، 1=روشن)
 Bit 0 - نمایش BG                         (0=خاموش، 1=روشن)
  • Bit 7: قبلاً بحث شد؛ می‌گوید LCD فعال است یا نه؛ اگر نه، چیزی رسم نمی‌کنیم. این در UpdateGraphics مدیریت شده است.
  • Bit 6: برای رسم روی پنجره، شمارهٔ شناسایی تایل باید از اینجا خوانده شود.
  • Bit 5: اگر 0 باشد پنجره فعال نیست؛ پس رسمش نمی‌کنیم.
  • Bit 4: برای تایل‌های پنجره و پس‌زمینه که باید روی صفحه رسم شوند، شمارهٔ شناسایی را در اینجا برای گرفتن دادهٔ تایل موردنظر استفاده می‌کنید. نکتهٔ مهم: اگر این بیت 0 باشد (یعنی خواندن از 0x8800)، شمارهٔ شناسایی تایلِ جستجو‌شده یک بایت علامت‌دار است نه بدون علامت (بعداً کاملاً توضیح داده می‌شود).
  • Bit 3: مثل Bit 6 اما برای پس‌زمینه نه پنجره.
  • Bit 2: اندازهٔ اسپرایت‌هایی است که باید رسم شوند. برخلاف تایل‌ها که همیشه 8x8 هستند، اسپرایت‌ها می‌توانند 8x16 باشند.
  • Bit 1: مثل Bit 5 اما برای اسپرایت‌ها.
  • Bit 0: مثل Bit 5 و 1 اما برای پس‌زمینه.

یادتان باشد تابع UpdateGraphics تابع DrawScanLine را صدا می‌زد که هنوز پیاده‌سازی نشده. اما با اطلاعات ثبات کنترل LCD بالا حالا می‌توانیم:

cppvoid Emulator::DrawScanLine( )
{
   BYTE control = ReadMemory(0xFF40) ;
   if (TestBit(control,0))
     RenderTiles( ) ;
   if (TestBit(control,1))
     RenderSprites( ) ;
}

همان‌طور که قبلاً گفته شد، پس‌زمینه از 256x256 پیکسل (32x32 تایل) ساخته شده؛ اما چون فقط 160x144 پیکسل نمایش می‌دهیم، نیازی به رسم بقیه نیست. قبل از شروع رسم پس‌زمینه باید بدانیم کجا را رسم کنیم؛ یعنی کدام 160x144 از پس‌زمینهٔ 256x256 نمایش داده می‌شود؟

textScrollY (0xFF42): موقعیت Y از پس‌زمینه که رسم ناحیهٔ دید از آنجا شروع می‌شود
ScrollX (0xFF43): موقعیت X از پس‌زمینه که رسم ناحیهٔ دید از آنجا شروع می‌شود
WindowY (0xFF4A): موقعیت Y از ناحیهٔ دید که رسم پنجره از آنجا شروع می‌شود
WindowX (0xFF4B): موقعیت X منهای 7 از ناحیهٔ دید که رسم پنجره از آنجا شروع می‌شود

حالا می‌دانیم ناحیهٔ دید را نسبت به پس‌زمینه کجا رسم کنیم و پنجره را نسبت به ناحیهٔ دید کجا. منهای 7 برای موقعیت پنجره لازم است. اگر می‌خواستید رسم پنجره از گوشهٔ بالا-چپ ناحیهٔ دید (مختصات 0,0) شروع شود، باید WindowY را 0 و WindowX را 7 بگذارید. ضمناً اگر پنجره در گوشهٔ بالا-چپ رسم شود کاملاً روی پس‌زمینه را می‌پوشاند. اگر پنجره فقط نیمهٔ پایین پس‌زمینه را بپوشاند، WindowY باید 72 (144/2) و WindowX برابر 7 باشد.

حالا که می‌دانیم پس‌زمینه و پنجره را کجا رسم کنیم، باید مشخص کنیم چه چیزی را رسم کنیم. گیم‌بوی دو ناحیهٔ حافظه برای چیدمان پس‌زمینه دارد که پنجره هم از آن‌ها استفاده می‌کند: 0x9800-0x9BFF و 0x9C00-0x9FFF. باید بیت 3 از ثبات کنترل LCD را بررسی کنیم تا ببینیم از کدام ناحیه برای پس‌زمینه استفاده می‌کنیم و بیت 6 برای پنجره. هر بایت در این ناحیهٔ حافظه یک شمارهٔ شناسایی تایل است که باید رسم شود. این شمارهٔ شناسایی برای جستجوی دادهٔ تایل در video RAM استفاده می‌شود تا بدانیم چطور رسمش کنیم.

با نگاه به بیت 4 از ثبات کنترل LCD می‌بینیم دو مکان برای دادهٔ تایل‌ها وجود دارد: 0x8000-0x8FFF و 0x8800-0x97FF. هر کدام از این ناحیه‌ها 4096 (0x1000) بایت داده برای ذخیرهٔ همهٔ تایل‌ها می‌دهد. هر تایل به‌صورت 16 بایت در حافظه ذخیره می‌شود. یادتان باشد یک تایل 8x8 پیکسل است و هر خط از تایل در حافظه به دو بایت نیاز دارد؛ از اینجا عدد 16 بایت برای هر تایل می‌آید. پس حالا می‌دانیم دادهٔ تایل کجا ذخیره می‌شود و چیدمان پس‌زمینه کجاست. چیدمان پس‌زمینه شمارهٔ شناسایی تایل را برای جستجو در ناحیهٔ دادهٔ تایل می‌دهد. اما اینجا بخش پیچیدهٔ ماجراست: اگر ناحیهٔ دادهٔ تایل 0x8000-0x8FFF باشد، شناسهٔ تایل خوانده‌شده از نواحی چیدمان پس‌زمینه یک بایت بدون علامت است؛ یعنی شناسه از 0 تا 255 خواهد بود. اما اگر از ناحیهٔ دادهٔ تایل 0x8800-0x97FF استفاده می‌کنیم، شناسهٔ تایل خوانده‌شده از چیدمان پس‌زمینه یک بایت علامت‌دار است؛ یعنی از 127- تا 127. الگوریتم یافتن تایل در ناحیهٔ حافظهٔ 0x8000-0x8FFF:

cppconst WORD memoryRegion = 0x8000 ;
const int sizeOfTileInMemory = 16 ;

WORD tileDataAddress = memoryRegion + (tileIdentifier*sizeOfTileInMemory) ;

اگر چیدمان پس‌زمینه شناسهٔ بدون علامت 0 بدهد، دادهٔ تایل بین 0x8000-0x800F است. اما اگر لازم بود شناسهٔ تایل 37 جستجو شود، در ناحیهٔ 0x8250-0x825F است. الگوریتم محاسبهٔ محل دادهٔ تایل در ناحیهٔ 0x8800-0x97FF:

cppconst WORD memoryRegion = 0x8800 ;
const int sizeOfTileInMemory = 16 ;
const int offset = 128 ;

WORD tileDataAddress = memoryRegion + ((tileIdentifier+offset)*sizeOfTileInMemory) ;

پس اگر شناسهٔ تایل 0 بود، تایل در ناحیهٔ 0x9000-0x900F است.

چگونه یک تایل/اسپرایت از حافظه رسم کنیم

این ناحیه ادامهٔ رندر دادهٔ تایل است اما برای اسپرایت‌ها هم صادق است؛ همان‌طور که بعداً خواهید دید.

پس حالا دربارهٔ دادهٔ تایل چه می‌دانیم؟ اول اینکه ناحیهٔ چیدمان پس‌زمینه هر تایلِ لازم برای رسم در پس‌زمینهٔ فعلی را مشخص می‌کند. شمارهٔ شناسایی تایل به‌دست‌آمده از چیدمان پس‌زمینه برای جستجوی دادهٔ تایل در ناحیهٔ دادهٔ تایل استفاده می‌شود. می‌دانیم هر تایل 8x8 پیکسل است و هر خط افقی در تایل 8x8 در حافظه دو بایت می‌گیرد؛ یعنی هر تایل در حافظه به ۱۶ بایت داده نیاز دارد.

پس اگر دو بایت داده یک خط از تایل را بسازند، باید این دو بایت را ترکیب کنیم تا تفکیک هر پیکسل از خط ۸ پیکسلی به‌دست آید. مثلاً اگر بایت 1 برابر 00110101 و دادهٔ 2 برابر 10101110 باشد، می‌توانیم آن‌ها را ترکیب کنیم و اطلاعات رنگ زیر را بگیریم:

textشمارهٔ پیکسل = 1 2 3 4 5 6 7 8
داده 2       = 1 0 1 0 1 1 1 0
داده 1       = 0 0 1 1 0 1 0 1

شناسهٔ رنگ پیکسل 2: 00
شناسهٔ رنگ پیکسل 3: 11
شناسهٔ رنگ پیکسل 4: 01
شناسهٔ رنگ پیکسل 5: 10
شناسهٔ رنگ پیکسل 6: 11

همان‌طور که می‌بینید فقط ۴ شناسهٔ رنگ ممکن وجود دارد (00,01,10,11) که به ۴ رنگ گیم‌بوی نگاشت می‌شوند (سفید، خاکستری روشن، خاکستری تیره، سیاه). اما هنوز باید مشخص کنیم شناسه‌های رنگ پیکسل را چطور به رنگ‌های صحیح نگاشت کنیم؛ این کار با پالت‌ها (palettes) انجام می‌شود. پالت‌ها ثابت نیستند و برنامه‌نویس می‌تواند نگاشت را تغییر دهد؛ یعنی می‌توان رنگ تایل‌ها و اسپرایت‌ها را بدون تغییر دادن دادهٔ تایل عوض کرد؛ چون در یک حالت شناسهٔ رنگ 00 ممکن است خاکستری تیره باشد و در حالت دیگر سفید. این‌طور است که افکت‌های ویژهٔ جالبی انجام می‌شود؛ مثلاً وقتی ماریو شکست‌ناپذیر می‌شود، هر نیم ثانیه رنگ‌هایش معکوس می‌شود تا افکت چشمک‌زن بگیرد.

تایل‌های پس‌زمینه فقط یک پالت رنگی تک‌رنگ دارند که در آدرس 0xFF47 ذخیره شده. اما اسپرایت‌ها می‌توانند دو پالت داشته باشند (بعداً بحث می‌شود). آن‌ها دقیقاً مثل پالت‌های پس‌زمینه کار می‌کنند، فقط رنگ سفید شفاف است. پالت‌های اسپرایت در 0xFF48 و 0xFF49 هستند.

هر دو بیت از بایت دادهٔ پالت یک رنگ را نشان می‌دهد. بیت‌های 7-6 به شناسهٔ رنگ 11، بیت‌های 5-4 به شناسهٔ رنگ 10، بیت‌های 3-2 به شناسهٔ رنگ 01 و بیت‌های 1-0 به شناسهٔ رنگ 00 نگاشت می‌شوند. هر دو بیت رنگی که باید استفاده شود را می‌دهد:

حالا شناسه‌های رنگ پیکسل و راه نگاشت آن‌ها به رنگ‌ها را داریم. با مثال شناسه‌های رنگ بالا و فرض اینکه بایت دادهٔ پالت برابر 11001001 باشد، می‌توانیم رنگ هر پیکسل را محاسبه کنیم:

رندر تایل‌ها — بخش ۲

حالا همهٔ اطلاعات لازم برای رندر پس‌زمینه و پنجره را داریم. با کنار هم گذاشتن همهٔ این اطلاعات می‌توانیم پیاده‌سازی کنیم:

cppvoid Emulator::RenderTiles( )
{
   WORD tileData = 0 ;
   WORD backgroundMemory = 0 ;
   bool unsig = true ;

   // کجا ناحیهٔ دید و پنجره رسم شود
   BYTE scrollY = ReadMemory(0xFF42) ;
   BYTE scrollX = ReadMemory(0xFF43) ;
   BYTE windowY = ReadMemory(0xFF4A) ;
   BYTE windowX = ReadMemory(0xFF4B) - 7 ;

   bool usingWindow = false ;

   // آیا پنجره فعال است؟
   if (TestBit(lcdControl,5))
   {
     // آیا خط اسکن فعلی که رسم می‌کنیم
     // داخل موقعیت Y پنجره است؟
     if (windowY <= ReadMemory(0xFF44))
       usingWindow = true ;
   }

   // از کدام دادهٔ تایل استفاده می‌کنیم؟
   if (TestBit(lcdControl,4))
   {
     tileData = 0x8000 ;
   }
   else
   {
     // مهم: این ناحیهٔ حافظه از بایت‌های
     // علامت‌دار به‌عنوان شناسهٔ تایل استفاده می‌کند
     tileData = 0x8800 ;
     unsig = false ;
   }

   // کدام حافظهٔ پس‌زمینه؟
   if (false == usingWindow)
   {
     if (TestBit(lcdControl,3))
       backgroundMemory = 0x9C00 ;
     else
       backgroundMemory = 0x9800 ;
   }
   else
   {
     // کدام حافظهٔ پنجره؟
     if (TestBit(lcdControl,6))
       backgroundMemory = 0x9C00 ;
     else
       backgroundMemory = 0x9800 ;
   }

   BYTE yPos = 0 ;

   // yPos برای محاسبهٔ اینکه خط اسکن فعلی
   // داخل کدام‌یک از ۳۲ تایل عمودی است استفاده می‌شود
   if (!usingWindow)
     yPos = scrollY + ReadMemory(0xFF44) ;
   else
     yPos = ReadMemory(0xFF44) - windowY ;

   // خط اسکن روی کدام‌یک از ۸ پیکسل عمودی
   // تایل فعلی قرار دارد؟
   WORD tileRow = (((BYTE)(yPos/8))*32) ;

   // وقت شروع رسم ۱۶۰ پیکسل افقی
   // برای این خط اسکن است
   for (int pixel = 0 ; pixel < 160; pixel++)
   {
     BYTE xPos = pixel+scrollX ;

     // در صورت نیاز موقعیت x فعلی را به فضای پنجره ترجمه کن
     if (usingWindow)
     {
       if (pixel >= windowX)
       {
         xPos = pixel - windowX ;
       }
     }

     // این xPos داخل کدام‌یک از ۳۲ تایل افقی قرار می‌گیرد؟
     WORD tileCol = (xPos/8) ;
     SIGNED_WORD tileNum ;

     // شمارهٔ شناسایی تایل را بگیر. یادت باشد می‌تواند
     // علامت‌دار یا بدون علامت باشد
     WORD tileAddrss = backgroundMemory+tileRow+tileCol ;
     if(unsig)
       tileNum = (BYTE)ReadMemory(tileAddrss) ;
     else
       tileNum = (SIGNED_BYTE)ReadMemory(tileAddrss) ;

     // مشخص کن این شناسهٔ تایل در حافظه کجاست. یادت باشد
     // این الگوریتم را قبلاً نشان دادم
     WORD tileLocation = tileData ;

     if (unsig)
       tileLocation += (tileNum * 16) ;
     else
       tileLocation += ((tileNum+128) *16) ;

     // خط عمودی صحیحی که روی آن هستیم را
     // از تایل پیدا کن تا دادهٔ تایل را
     // از حافظه بگیریم
     BYTE line = yPos % 8 ;
     line *= 2; // هر خط عمودی دو بایت از حافظه می‌گیرد
     BYTE data1 = ReadMemory(tileLocation + line) ;
     BYTE data2 = ReadMemory(tileLocation + line + 1) ;

     // پیکسل 0 در تایل، بیت 7 از data1 و data2 است.
     // پیکسل 1 بیت 6 و الی آخر...
     int colourBit = xPos % 8 ;
     colourBit -= 7 ;
     colourBit *= -1 ;

     // data2 و data1 را ترکیب کن تا شناسهٔ رنگ این پیکسل
     // در تایل به‌دست آید
     int colourNum = BitGetVal(data2,colourBit) ;
     colourNum <<= 1;
     colourNum |= BitGetVal(data1,colourBit) ;

     // حالا که شناسهٔ رنگ را داریم، رنگ واقعی را
     // از پالت 0xFF47 بگیر
     COLOUR col = GetColour(colourNum, 0xFF47) ;
     int red = 0;
     int green = 0;
     int blue = 0;

     // مقادیر RGB را تنظیم کن
     switch(col)
     {
       case WHITE:     red = 255; green = 255 ; blue = 255; break ;
       case LIGHT_GRAY: red = 0xCC; green = 0xCC ; blue = 0xCC; break ;
       case DARK_GRAY:  red = 0x77; green = 0x77 ; blue = 0x77; break ;
     }

     int finaly = ReadMemory(0xFF44) ;

     // بررسی ایمنی برای اطمینان از اینکه چیزی که
     // می‌خواهم تنظیم کنم داخل مرزهای 160x144 است
     if ((finaly<0)||(finaly>143)||(pixel<0)||(pixel>159))
     {
       continue ;
     }

     m_ScreenData[pixel][finaly][0] = red ;
     m_ScreenData[pixel][finaly][1] = green ;
     m_ScreenData[pixel][finaly][2] = blue ;
   }
}

می‌دانم اول ممکن است ترسناک به نظر برسد؛ اما تا وقتی منطق رسم تایل‌ها را بفهمید، فقط به کد بالا نگاه کنید تا منطقی شود. تابع GetColour که در کد بالا استفاده شده هنوز پیاده‌سازی نشده. این تابع یک شناسهٔ رنگ می‌گیرد و با پالت تک‌رنگ تشخیص می‌دهد این شناسه به چه رنگی مربوط است. یادتان باشد این یک پالت پویاست؛ پس شناسه‌های رنگ در بخش‌های مختلف بازی به رنگ‌های مختلفی نگاشت می‌شوند:

cppCOLOUR Emulator::GetColour(BYTE colourNum, WORD address) const
{
   COLOUR res = WHITE ;
   BYTE palette = ReadMemory(address) ;
   int hi = 0 ;
   int lo = 0 ;

   // شناسهٔ رنگ به کدام بیت‌های پالت نگاشت می‌شود؟
   switch (colourNum)
   {
     case 0: hi = 1 ; lo = 0 ; break ;
     case 1: hi = 3 ; lo = 2 ; break ;
     case 2: hi = 5 ; lo = 4 ; break ;
     case 3: hi = 7 ; lo = 6 ; break ;
   }

   // از پالت استفاده کن تا رنگ به‌دست آید
   int colour = 0;
   colour = BitGetVal(palette, hi) << 1;
   colour |= BitGetVal(palette, lo) ;

   // رنگ بازی را به رنگ شبیه‌ساز تبدیل کن
   switch (colour)
   {
     case 0: res = WHITE ; break ;
     case 1: res = LIGHT_GRAY ; break ;
     case 2: res = DARK_GRAY ; break ;
     case 3: res = BLACK ; break ;
   }

   return res ;
}

رندر اسپرایت‌ها

رندر اسپرایت‌ها کمی سخت‌تر از تایل‌هاست؛ اما خوشبختانه دادهٔ اسپرایت در آدرس 0x8000-0x8FFF است؛ یعنی شناسه‌های اسپرایت همه بدون علامت‌اند که پیدا کردنشان را آسان‌تر می‌کند. در ناحیهٔ حافظهٔ 0x8000-0x8FFF، ۴۰ تایل وجود دارد و باید همه را اسکن کنیم و مشخصاتشان را بررسی کنیم تا بفهمیم کجا باید رسم شوند. مشخصات اسپرایت در جدول مشخصات اسپرایت (Sprin Attribute Table) در ناحیهٔ حافظهٔ 0xFE00-0xFE9F است. در این ناحیهٔ حافظه هر اسپرایت ۴ بایت مشخصات دارد:

text0: موقعیت Y اسپرایت: موقعیت اسپرایت روی محور Y نمایشگر منهای 16
1: موقعیت X اسپرایت: موقعیت اسپرایت روی محور X نمایشگر منهای 8
2: شمارهٔ پترن: شناسهٔ اسپرایت برای جستجوی دادهٔ اسپرایت در ناحیهٔ 0x8000-0x8FFF
3: مشخصات: مشخصات اسپرایت که بعداً بحث می‌شود

یک اسپرایت یا 8x8 پیکسل است یا 8x16؛ این را می‌توان از مشخصات اسپرایت تشخیص داد. تفکیک مشخصات اسپرایت:

textBit7: اولویت اسپرایت نسبت به پس‌زمینه
Bit6: قرینه‌سازی Y (Y flip)
Bit5: قرینه‌سازی X (X flip)
Bit4: شمارهٔ پالت
Bit3: در گیم‌بوی استاندارد استفاده نمی‌شود
Bit2-0: در گیم‌بوی استاندارد استفاده نمی‌شود
  • اولویت اسپرایت نسبت به پس‌زمینه: اگر این پرچم 0 باشد، اسپرایت همیشه بالای پس‌زمینه و پنجره رندر می‌شود. اما اگر 1 باشد، اسپرایت پشت پس‌زمینه و پنجره پنهان می‌شود، مگر اینکه رنگ پس‌زمینه یا پنجره سفید باشد؛ در آن صورت همچنان روی آن‌ها رندر می‌شود.
  • Y flip: اگر این بیت تنظیم شده باشد، اسپرایت به‌صورت عمودی قرینه می‌شود؛ در بازی برای وارونه‌کردن اسپرایت‌ها استفاده می‌شود.
  • X flip: اگر تنظیم شده باشد، اسپرایت افقی قرینه می‌شود؛ در بازی برای تغییر جهت شخصیت‌ها و غیره استفاده می‌شود.
  • شمارهٔ پالت: اسپرایت‌ها می‌توانند پالت تک‌رنگشان را از 0xFF48 یا 0xFF49 بگیرند. اگر این بیت 0 باشد پالت از 0xFF48 است وگرنه از 0xFF49.

نویسنده بهترین راه مدیریت قرینهٔ X و Y را خواندن معکوس دادهٔ اسپرایت می‌داند؛ این کار افکت قرینه را می‌دهد.

حالا اطلاعات کافی برای رندر اسپرایت‌ها داریم. این کار تقریباً دقیقاً مثل رندر تایل‌هاست؛ فقط به‌جای پیمایش ناحیهٔ چیدمان برای گرفتن شناسهٔ بعدی تایل، باید هر ۴۰ اسپرایت را پیمایش کنیم و آن‌هایی که قابل‌مشاهده‌اند و با خط اسکن فعلی تقاطع دارند را تشخیص دهیم:

cppvoid Emulator::RenderSprites( )
{

   if (TestBit(lcdControl,2))
     use8x16 = true ;

   for (int sprite = 0 ; sprite < 40; sprite++)
   {
     // هر اسپرایت ۴ بایت در جدول مشخصات اسپرایت‌ها اشغال می‌کند
     BYTE index = sprite*4 ;

     BYTE xPos = ReadMemory(0xFE00+index+1)-8;
     BYTE tileLocation = ReadMemory(0xFE00+index+2) ;
     BYTE attributes = ReadMemory(0xFE00+index+3) ;

     bool yFlip = TestBit(attributes,6) ;
     bool xFlip = TestBit(attributes,5) ;

     int scanline = ReadMemory(0xFF44) ;

     int ysize = 8 ;
     if (use8x16)
       ysize = 16;

     // آیا این اسپرایت با خط اسکن تقاطع دارد؟
     if ((scanline >= yPos) && (scanline < (yPos+ysize)))
     {
       int line = scanline - yPos ;

       // اسپرایت را در محور y به‌صورت معکوس بخوان
       if (yFlip)
       {
         line -= ysize ;
         line *= -1 ;
       }

       line *= 2; // مثل تایل‌ها
       WORD dataAddress = (0x8000 + (tileLocation * 16)) + line ;
       BYTE data1 = ReadMemory( dataAddress  ) ;
       BYTE data2 = ReadMemory( dataAddress +1 ) ;

       // بیت 7 در دادهٔ رنگ است و پیکسل 1 بیت 6 و الی آخر...
       for (int tilePixel = 7; tilePixel >= 0; tilePixel--)
       {
         int colourbit = tilePixel ;
         // اسپرایت را برای محور x به‌صورت معکوس بخوان
         if (xFlip)
         {
           colourbit -= 7 ;
           colourbit *= -1 ;
         }

         // بقیه مثل تایل‌هاست
         int colourNum = BitGetVal(data2,colourbit) ;
         colourNum <<= 1;
         colourNum |= BitGetVal(data1,colourbit) ;

         WORD colourAddress = TestBit(attributes,4)?0xFF49:0xFF48 ;
         COLOUR col = GetColour(colourNum, colourAddress ) ;

         // سفید برای اسپرایت‌ها شفاف است.
         if (col == WHITE)
           continue ;

         int red = 0;
         int green = 0;
         int blue = 0;

         switch(col)
         {
           case WHITE:     red=255;green=255;blue=255;break ;
           case LIGHT_GRAY:red=0xCC;green=0xCC;blue=0xCC;break ;
           case DARK_GRAY: red=0x77;green=0x77;blue=0x77;break ;
         }

         int xPix = 0 - tilePixel ;
         xPix += 7 ;

         int pixel = xPos+xPix ;

         // بررسی سلامت
         if ((scanline<0)||(scanline>143)||(pixel<0)||(pixel>159))
         {
           continue ;
         }

         m_ScreenData[pixel][scanline][0] = red ;
         m_ScreenData[pixel][scanline][1] = green ;
         m_ScreenData[pixel][scanline][2] = blue ;
       }
     }
   }
}

شبیه‌سازی جوای‌پد (Joypad Emulation)

گیم‌بوی یک جوای‌پد داخلی با ۸ دکمه دارد: ۴ دکمهٔ جهتی (بالا، پایین، چپ، راست) و دکمه‌های استاندارد (start، select، A و B). ثبات جوای‌پد در آدرس 0xFF00 است و این‌طور تفکیک می‌شود (برگرفته از pandocs):

text  Bit 7 - استفاده نشده
  Bit 6 - استفاده نشده
  Bit 5 - P15 انتخاب دکمه‌ها (Buttons)   (0=انتخاب‌شده)
  Bit 4 - P14 انتخاب دکمه‌های جهتی      (0=انتخاب‌شده)
  Bit 3 - P13 ورودی پایین  یا Start     (0=فشرده‌شده) (فقط‌خواندنی)
  Bit 2 - P12 ورودی بالا   یا Select    (0=فشرده‌شده) (فقط‌خواندنی)
  Bit 1 - P11 ورودی چپ     یا دکمهٔ B   (0=فشرده‌شده) (فقط‌خواندنی)
  Bit 0 - P10 ورودی راست   یا دکمهٔ A   (0=فشرده‌شده) (فقط‌خواندنی)

بیت‌های 0-3 توسط شبیه‌ساز تنظیم می‌شوند تا وضعیت جوای‌پد را نشان دهند. همان‌طور که می‌بینید دکمه‌های جهتی و دکمه‌های استاندارد در این بازهٔ بیت‌ها مشترک‌اند؛ پس بازی چطور می‌فهمد بیت 3 یعنی دکمهٔ جهت‌دار پایین یا دکمهٔ استاندارد start؟ راهش این است که بازی بیت‌های 4 و 5 را بسته به اینکه می‌خواهد دکمه‌های جهتی را بررسی کند یا استاندارد، تنظیم می‌کند.

نحوهٔ کار در سخت‌افزار اصلی گیم‌بوی (به نظر نویسنده): بازی در حافظهٔ 0xFF00 با بیت 4 یا 5 تنظیم‌شده می‌نویسد (هرگز هر دو). بعد از 0xFF00 می‌خواند؛ و به‌جای خواندن همان چیزی که نوشته، وضعیت جوای‌پد برمی‌گردد، بسته به اینکه بیت 4 تنظیم شده یا 5. مثلاً اگر بازی می‌خواست بررسی کند کدام دکمهٔ جهتی فشرده شده، بیت 4 را 1 می‌کند و بعد از 0xFF00 می‌خواند. اگر کلید بالا فشرده شده باشد، هنگام خواندن 0xFF00 بیت 2 برابر 0 می‌شود تا علامت دهد دکمهٔ جهتی بالا فشرده شده (0 یعنی فشرده، 1 یعنی فشرده‌نشده). اما اگر بالا فشرده نشده بود ولی دکمهٔ select فشرده شده بود، بیت 2 روی 1 می‌ماند یعنی چیزی فشرده نشده؛ حتی اگر دکمهٔ select واقعاً فشرده شده باشد که روی بیت 2 نگاشت می‌شود. دلیل اینکه بیت 2 روی 1 می‌ماند (علامت فشرده‌نشدن) حتی وقتی فشرده شده، این است که بیت 4 روی 1 تنظیم شده؛ یعنی بازی فقط به وضعیت دکمه‌های جهتی علاقه دارد.

نحوهٔ شبیه‌سازی نویسنده: متغیر بایتی m_JoypadState که هر بیتش وضعیت جوای‌پد را نشان می‌دهد (۸ دکمه و ۸ بیت؛ خوب جواب می‌دهد). هر بار دکمه‌ای فشرده می‌شود، بیت متناظر در m_JoypadState 0 می‌شود و اگر فشرده نباشد 1 است. اگر بیتی در m_JoypadState از 1 به 0 تغییر کند، یعنی این دکمه همین الان فشرده شده؛ پس یک وقفهٔ جوای‌پد درخواست می‌شود.

هر بار بازی از 0xFF00 می‌خواند، با ReadMemory به دام می‌افتد و تابعی صدا زده می‌شود که به آدرس 0xFF00 نگاه می‌کند تا ببیند بازی به دکمه‌های جهتی علاقه دارد یا استاندارد و سپس یک بایت برمی‌گرداند که ترکیبی از m_JoypadState و 0xFF00 است تا بازی وضعیت صحیح جوای‌پد را بگیرد. یادتان باشد این را به ReadMemory اضافه کنیم:

cppvoid Emulator::KeyPressed(int key)
{
   bool previouslyUnset = false ;

   // اگر از 1 به 0 تغییر کند ممکن است لازم باشد وقفه درخواست کنیم
   if (TestBit(m_JoypadState, key)==false)
     previouslyUnset = true ;

   // یادت باشد اگر کلیدی فشرده شود بیتش 0 است نه 1
   m_JoypadState = BitReset(m_JoypadState, key) ;

   // دکمه فشرده شده
   bool button = true ;

   // آیا این یک دکمهٔ استاندارد است یا دکمهٔ جهتی؟
   if (key > 3)
     button = true ;
   else // دکمهٔ جهتی فشرده شده
     button = false ;

   BYTE keyReq = m_Rom[0xFF00] ;
   bool requestInterupt = false ;

   // فقط اگر دکمهٔ تازه فشرده‌شده از نوعی باشد که
   // بازی به آن علاقه دارد وقفه درخواست کن
   if (button && !TestBit(keyReq,5))
     requestInterupt = true ;

   // مثل بالا اما برای دکمهٔ جهتی
   else if (!button && !TestBit(keyReq,4))
     requestInterupt = true ;

   // درخواست وقفه
   if (requestInterupt && !previouslyUnset)
     RequestInterupt(4) ;
}

cppBYTE Emulator::GetJoypadState() const
{
   BYTE res = m_Rom[0xFF00] ;
   // همهٔ بیت‌ها را معکوس کن
   res ^= 0xFF ;

   // آیا به دکمه‌های استاندارد علاقه داریم؟
   if (!TestBit(res, 4))
   {
     BYTE topJoypad = m_JoypadState >> 4 ;
     topJoypad |= 0xF0 ; // ۴ بیت بالا را روشن کن
     res &= topJoypad ; // نشان بده کدام دکمه‌ها فشرده شده‌اند
   }
   else if (!TestBit(res,5)) // دکمه‌های جهتی
   {
     BYTE bottomJoypad = m_JoypadState & 0xF ;
     bottomJoypad |= 0xF0 ;
     res &= bottomJoypad ;
   }
   return res ;
}

اگر گیج شده‌اید که چرا هنگام بررسی دکمه‌های استاندارد m_JoypadState چهار بار شیفت چپ می‌شود، به این دلیل است که دکمه‌های استاندارد در نیبل بالای m_JoypadState ذخیره می‌شوند اما برای OR منطقی باید در نیبل پایین باشند.

مثال‌های اپکد (Example Opcodes)

ExecuteNextOpcode

تا اینجا آموزش روی نحوهٔ کنار هم قرار گرفتن اجزای داخلی گیم‌بوی و شبیه‌سازی هر کدام متمرکز بود. بارها اشاره شد که دانستن مدت اجرای هر دستورالعمل در سخت‌افزار اصلی به همگام‌سازی گرافیک و تایمرها کمک می‌کند. این اطلاعات در حلقهٔ اصلی به‌روزرسانی از تابع ExecuteNextOpcode به دست می‌آمد؛ اما پیاده‌سازی این تابع هنوز داده نشده، چون مربوط به شبیه‌سازی پردازندهٔ z80-مانند بود و برای آخر نگه داشته شده بود. حالا که بقیهٔ جنبه‌های گیم‌بوی بحث شده، می‌توانیم تعریف این تابع را بدهیم:

cppint Emulator::ExecuteNextOpcode( )
{
   int res = 0 ;
   BYTE opcode = ReadMemory(m_ProgramCounter) ;
   m_ProgramCounter++ ;
   res = ExecuteOpcode(opcode) ;
   return res ;
}

کوتاه و مفید بود. اما حالا باید تابع ExecuteOpcode را پیاده کنیم که یک دستور switch بزرگ است. حدود ۳۰۰ اپکد برای CPU گیم‌بوی وجود دارد؛ پس نمایش کل switch در این صفحه مسخره است. به‌جایش فقط اپکدهایی را نشان می‌دهیم که در ادامه مثال می‌زنیم:

cppint Emulator::ExecuteOpcode(BYTE opcode)
{
   switch(opcode)
   {
   case 0x06:
     CPU_8BIT_LOAD(m_RegisterBC.hi) ;
     return 8;

   case 0x80:
     CPU_8BIT_ADD(m_RegisterAF.hi, m_RegisterBC.hi,false,false) ;
     return 4;

   case 0x90:
     CPU_8BIT_SUB(m_RegisterAF.hi, m_RegisterBC.hi,false,false) ;
     return 4 ;

   case 0xAF:
     CPU_8BIT_XOR(m_RegisterAF.hi, m_RegisterAF.hi, false) ;
     return 4;

   case 0x20 :
     CPU_JUMP_IMMEDIATE( true, FLAG_Z, false ) ;
     return 8;

   case 0xCC :
     CPU_CALL( true, FLAG_Z, true) ;
     return 24;

   case 0xD0:
     CPU_RETURN( true, FLAG_C, false ) ;
     return 8;

   case 0xCB:
     return ExecuteExtendedOpcode( ) ;

   default:
     assert(false); return 0 ; // اپکد مدیریت‌نشده
   }
}

اپکد 0xCB اپکد گسترده (extended) است؛ یعنی هر بار اپکد 0xCB را ببینیم باید بایت فوری بعدی در حافظه را رمزگشایی کنیم و آن را به‌عنوان اپکد در نظر بگیریم. اپکد 0xAB با 0xCB 0xAB فرق دارد. این یعنی می‌توانیم اپکدهای بیشتری از 0x0-0xFF استاندارد داشته باشیم. تابع ExecuteExtendedOpcode همان ساختار ExecuteOpcode را دارد فقط با اپکدهای گسترده سروکار دارد:

بارگذاری‌های ۸ بیتی (8-Bit Loads)

بارگذاری‌های ۸ بیتی، یک بایت دادهٔ فوری از حافظه را در یکی از ۸ ثبات می‌گذارند. اگر تابع CPU_8BIT_LOAD یک ارجاع (reference) از یکی از ثبات‌ها بگیرد، مثل اپکد 0x06، برای همهٔ ۸ ثبات قابل استفاده است. اپکد 0x06 یک بایت فوری را در ثبات B بارگذاری می‌کند:

cppvoid Emulator::CPU_8BIT_LOAD( BYTE& reg )
{
   BYTE n = ReadMemory(m_ProgramCounter) ;
   m_ProgramCounter++ ;
   reg = n ;
}

این تابع برای همهٔ ۸ ثبات قابل استفاده است، نه فقط B.

ADD هشت بیتی

این تابع یک بایت به یکی از ثبات‌ها اضافه می‌کند و پرچم‌ها را تنظیم می‌کند. مثل CPU_8BIT_LOAD اگر ارجاع را پارامتر کنیم برای همهٔ ۸ ثبات قابل استفاده است نه فقط ثبات A مثل مثال (اپکد 0x80). این تابع در مجموع ۴ آرگومان دارد:

textآرگومان 1: ارجاع ثباتی که نتیجهٔ ADD در آن قرار می‌گیرد
آرگومان 2: بایتی که باید به ثبات اضافه شود (اگر دادهٔ فوری نباشد)
آرگومان 3: اینکه چیزی که اضافه می‌کنیم دادهٔ فوری است یا نه
آرگومان 4: اینکه پرچم نقلی را هم اضافه کنیم یا نه

دو نوع دستورالعمل ADD ۸ بیتی z80 وجود دارد. اولی یک بایت به ثبات اضافه می‌کند و دومی یک بایت به‌علاوهٔ پرچم نقلی (از این رو آرگومان چهارم)؛ به این دستورالعمل ADC می‌گویند.

شرایط تنظیم پرچم‌ها:

textFLAG_Z: اگر بعد از جمع نتیجه 0 باشد
FLAG_N: برابر 0 تنظیم می‌شود
FLAG_C: اگر نتیجه بزرگ‌تر از حداکثر بایت (255) باشد
FLAG_H: اگر از نیبل پایین به نیبل بالا نقلی رخ دهد

FLAG_C باید نتیجه را قبل از جمع بررسی کند؛ وگرنه چطور می‌دانید نتیجه بزرگ‌تر از 255 بود وقتی به 0 برمی‌گردد (wrap)؟

cppvoid Emulator::CPU_8BIT_ADD(BYTE& reg, BYTE toAdd, bool useImmediate, bool addCarry)
{
   BYTE before = reg ;
   BYTE adding = 0 ;

   // آیا دادهٔ فوری اضافه می‌کنیم یا پارامتر دوم؟
   if (useImmediate)
   {
     BYTE n = ReadMemory(m_ProgramCounter) ;
     m_ProgramCounter++ ;
     adding = n ;
   }
   else
   {
     adding = toAdd ;
   }

   // آیا پرچم نقلی را هم اضافه می‌کنیم؟
   if (addCarry)
   {
     if (TestBit(m_RegisterAF.lo, FLAG_C))
       adding++ ;
   }

   reg += adding ;

   // پرچم‌ها را تنظیم کن
   m_RegisterAF.lo = 0 ;

   if (reg == 0)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_Z) ;

   WORD htest = (before & 0xF) ;
   htest += (adding & 0xF) ;

   if (htest > 0xF)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_H) ;

   if ((before + adding) > 0xFF)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_C) ;
}

SUB هشت بیتی

این تقریباً دقیقاً مثل 8-Bit Add است فقط برای تفریق. باز هم می‌تواند از دادهٔ فوری یا آرگومان دوم استفاده کند و می‌تواند پرچم نقلی را هم کم کند. نحوهٔ تأثیر بر پرچم‌ها:

textFLAG_Z: اگر بعد از تفریق نتیجه 0 باشد
FLAG_N: برابر 1 تنظیم می‌شود
FLAG_C: اگر نتیجه کمتر از 0 باشد
FLAG_H: اگر از نیبل بالا به نیبل پایین نقلی رخ دهد
cppvoid Emulator::CPU_8BIT_SUB(BYTE& reg, BYTE subtracting, bool useImmediate, bool subCarry)
{
   BYTE before = reg ;
   BYTE toSubtract = 0 ;

   if (useImmediate)
   {
     BYTE n = ReadMemory(m_ProgramCounter) ;
     m_ProgramCounter++ ;
     toSubtract = n ;
   }
   else
   {
     toSubtract = subtracting ;
   }

   if (subCarry)
   {
     if (TestBit(m_RegisterAF.lo, FLAG_C))
       toSubtract++ ;
   }

   reg -= toSubtract ;

   m_RegisterAF.lo = 0 ;

   if (reg == 0)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_Z) ;

   m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_N) ;

   // اگر وام نباشد تنظیم کن
   if (before < toSubtract)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_C) ;

   SIGNED_WORD htest = (before & 0xF) ;
   htest -= (toSubtract & 0xF) ;

   if (htest < 0)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_H) ;
}

XOR هشت بیتی

همهٔ عملگرهای منطقی AND، OR و XOR مثل ADD و SUB کار می‌کنند، فقط به پرچم نقلی اهمیت نمی‌دهند (پس آرگومان چهارم وجود ندارد). پرچم‌های XOR این‌طور تنظیم می‌شوند:

textFLAG_Z: اگر نتیجه 0 باشد
FLAG_N: برابر 0 تنظیم می‌شود
FLAG_C: برابر 0 تنظیم می‌شود
FLAG_H: برابر 0 تنظیم می‌شود
cppvoid Emulator::CPU_8BIT_XOR(BYTE& reg, BYTE toXOr, bool useImmediate)
{
   BYTE myxor = 0 ;

   if (useImmediate)
   {
     BYTE n = ReadMemory(m_ProgramCounter) ;
     m_ProgramCounter++ ;
     myxor = n ;
   }
   else
   {
     myxor = toXOr ;
   }

   reg ^= myxor ;

   m_RegisterAF.lo = 0 ;

   if (reg == 0)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_Z) ;
}

پرش‌ها (Jumps)

تعداد مناسبی دستورالعمل پرش وجود دارد اما همه کار یکسانی می‌کنند: پرش به یک آدرس مشخص؛ فقط بیشتر دستورالعمل‌های پرش فقط در صورت درست‌بودن یک شرط می‌پرند. برخی به آدرسی می‌پرند که دو بایت بعدیِ دادهٔ فوری به آن اشاره می‌کنند؛ برخی دیگر به شمارندهٔ برنامهٔ فعلی + بایت فوری بعدی می‌پرند (به آن Jump Immediate می‌گویند). یکی از دستورهای پرش به آدرسی که ثبات HL اشاره می‌کند می‌پرد. پیاده‌سازی دستور JUMP_IMMEDIATE:

cppvoid Emulator::CPU_JUMP_IMMEDIATE(bool useCondition, int flag, bool condition)
{
   SIGNED_BYTE n = (SIGNED_BYTE)ReadMemory(m_ProgramCounter) ;

   if (!useCondition)
   {
     m_ProgramCounter += n;
   }
   else if (TestBit(m_RegisterAF.lo, flag) == condition)
   {
     m_ProgramCounter += n ;
   }

   m_ProgramCounter++ ;
}

همان‌طور که می‌بینید، اگر از شرط پرش استفاده کنیم (مثلاً پرش اگر پرچم Z تنظیم شده) به آدرس m_ProgramCounter+ReadMemory(m_ProgramCounter) می‌پریم.

فراخوانی‌ها (Calls)

دستورالعمل call همانند jump است که به آدرس دو بایت فوری بعدی می‌پرد. اما تفاوت این است که call یک زیرروال (subroutine) است و در نهایت به آدرس فعلی‌اش برمی‌گردد؛ در حالی که jump برنمی‌گردد. پس برای اینکه بدانیم به کجا برگردیم، باید شمارندهٔ برنامهٔ فعلی را روی پشته push کنیم:

cppvoid Emulator::CPU_CALL(bool useCondition, int flag, bool condition)
{
   WORD nn = ReadWord( ) ;
   m_ProgramCounter += 2;

   if (!useCondition)
   {
     PushWordOntoStack(m_ProgramCounter) ;
     m_ProgramCounter = nn ;
     return ;
   }

   if (TestBit(m_RegisterAF.lo, flag)==condition)
   {
     PushWordOntoStack(m_ProgramCounter) ;
     m_ProgramCounter = nn ;
   }
}

یادتان باشد این مثل دستور jump دیگر است (نه jump immediate) فقط با این تفاوت که دستور jump هیچ‌چیزی روی پشته push نمی‌کند.

بازگشت‌ها (Returns)

حالا که فراخوانی زیرروال‌ها را مدیریت کردیم باید از آن‌ها بازگردیم. راه بازگشت این است که یک کلمه از پشته pop کنیم و به شمارندهٔ برنامه اختصاص دهیم (یادتان باشد با تابع call شمارندهٔ برنامه را روی پشته push کردید). باز هم می‌توانیم روی بازگشت شرط بگذاریم:

cppvoid Emulator::CPU_RETURN(bool useCondition, int flag, bool condition)
{
   if (!useCondition)
   {
     m_ProgramCounter = PopWordOffStack( ) ;
     return ;
   }

   if (TestBit(m_RegisterAF.lo, flag) == condition)
   {
     m_ProgramCounter = PopWordOffStack( ) ;
   }
}

گسترده: چرخش به راست از طریق نقلی (RRC)

این دستورالعمل ثبات A را به راست می‌چرخاند و پرچم نقلی را با کم‌ارزش‌ترین بیت قبل از چرخش تنظیم می‌کند. چرخش به راست یعنی همه‌چیز یک واحد به راست شیفت می‌شود و پرچم نقلی روی همان چیزی تنظیم می‌شود که کم‌ارزش‌ترین بیت قبل از چرخش بود. همهٔ پرچم‌ها 0 می‌شوند به‌جز پرچم نقلی که همان‌طور که گفته شد روی کم‌ارزش‌ترین بیت ثبات A قبل از چرخش تنظیم می‌شود:

cppvoid Emulator::CPU_RRC(BYTE& reg)
{
   bool isLSBSet = TestBit(reg, 0) ;

   m_RegisterAF.lo = 0 ;

   reg >>= 1;

   if (isLSBSet)
   {
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_C) ;
     reg = BitSet(reg,7) ;
   }

   if (reg == 0)
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_Z) ;
}

گسترده: تست بیت (TestBit)

این دستور بیتِ یک بایت را تست می‌کند و پرچم‌های مناسب را تنظیم می‌کند:

textFLAG Z: اگر بیت 0 باشد تنظیم می‌شود
FLAG_N: برابر 0 تنظیم می‌شود
FLAG_C: بدون تغییر
FLAG_H: برابر 1 تنظیم می‌شود
cppvoid Emulator::CPU_TEST_BIT(BYTE reg, int bit)
{
   if (TestBit(reg, bit))
     m_RegisterAF.lo = BitReset(m_RegisterAF.lo, FLAG_Z) ;
   else
     m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_Z) ;

   m_RegisterAF.lo = BitReset(m_RegisterAF.lo, FLAG_N) ;
   m_RegisterAF.lo = BitSet(m_RegisterAF.lo, FLAG_H) ;
}

نکتهٔ مهم دربارهٔ دستورالعمل TEST_BIT (و همین‌طور SET_BIT و RESET_BIT): مستندات می‌گویند اپکد گستردهٔ 0x40 بیت 0 از ثبات B را تست می‌کند؛ اما اپکدهای تست بیت‌های 1 یا 2 را نمی‌دهد. خوشبختانه فقط کافی است 0x8 اضافه کنید تا مقدار هگز سایر اپکدها به‌دست آید. پس برای تست بیت 1 از ثبات B اپکد 0x48 و برای تست بیت 2 از ثبات B اپکد 0x50 است. این برای بقیهٔ ثبات‌ها هم کار می‌کند؛ مثلاً مستندات می‌گویند اپکد 0x41 بیت 0 از ثبات C را تست می‌کند. از اینجا می‌توانیم نتیجه بگیریم 0x49 بیت 1 از ثبات C را تست می‌کند و الی آخر. باید همهٔ این دستورالعمل‌ها را شبیه‌سازی کنید تا همهٔ ۷ بیت همهٔ ۸ ثبات تست شوند. همین کار برای شبیه‌سازی توابع SET_BIT و RESET_BIT لازم است.

محصول نهایی (The Finished Product)

کدنویسی این شبیه‌ساز زمان زیادی برد و نوشتن بخش گیم‌بوی سایت هم به همان اندازه؛ اما بالاخره تمام شد. البته به‌جز صدا :-).

امیدواریم حالا درک کاملی از گیم‌بوی و نحوهٔ شبیه‌سازی آن داشته باشید. می‌توانید کد منبع شبیه‌ساز نویسنده را از اینجا دانلود کنید؛ هر طور دوست دارید از کد استفاده کنید فقط تا زمانی که اعتبارش به نویسنده داده شود. کد منبع هم در Visual Studio (ویندوز) و هم با CodeBlocks (لینوکس) کامپایل می‌شود. این نسخه هیچ امکاناتی مثل GUI یا تخلیهٔ حافظه ندارد و برای اجرای بازی باید نام فایل را در Gameboy.cpp تغییر دهید و دوباره کامپایل کنید. یادتان باشد برای استفاده از این کد و اجرای بازی‌ها باید واقعاً یک گیم‌بوی و بازی‌های آن را داشته باشید (نویسنده هیچ ROM و لینکی ارائه نمی‌دهد). هر کار دیگری خلاف قانون است. لذت ببرید!

خواهید دید کد منبع شبیه‌ساز دقیقاً با مثال‌های این آموزش یکی نیست؛ چون وقتی نویسنده شبیه‌ساز را می‌نوشت مطمئن نبود چه چیزی کار می‌کند و چه چیزی نه. اما وقتی تمام کرد، آموزش‌ها بر اساس بهترین راه شبیه‌سازی گیم‌بوی نوشته شدند؛ با دانشی که بعد از موفقیت در نوشتن شبیه‌ساز به دست آورد.

پروژهٔ بعدی نویسنده شبیه‌سازی Master System بود؛ با یک نگاه سریع به معماری‌اش خیلی سخت به نظر نمی‌رسید. قصد داشت بعد از Master System دوباره به گیم‌بوی برگردد و صدای گیم‌بوی را شبیه‌سازی کند؛ ظاهراً شبیه‌سازی صدای Master System آسان‌تر از گیم‌بوی است، پس اول از آنجا شروع می‌کند و بعد که یاد گرفت، صدا را در گیم‌بوی پیاده می‌کند.
