مقدمه

وب در دو دههٔ گذشته جامعه را به شکل‌های بی‌شماری تغییر داده، اما هستهٔ آن خیلی کم تغییر کرده. بیشتر سیستم‌ها همچنان از قوانینی پیروی می‌کنند که تیم برنرز-لی ربع قرن پیش گذاشت. به‌ویژه، بیشتر وب سرورها همچنان همان انواع پیام‌هایی را پردازش می‌کنند که در آن زمان پردازش می‌کردند، با همان روش.

این فصل بررسی می‌کند آنها چگونه این کار را می‌کنند. در عین حال، بررسی می‌کند که توسعه‌دهندگان چگونه می‌توانند سیستم‌های نرم‌افزاری بسازند که برای افزودن قابلیت‌های جدید نیازی به بازنویسی نداشته باشند.

گرگ ویلسون بنیان‌گذار Software Carpentry است و ۳۰ سال در صنعت و دانشگاه کار کرده؛ نویسندهٔ چند کتاب رایانشی از جمله برندهٔ جایزهٔ Jolt سال ۲۰۰۸ یعنی Beautiful Code و دو جلد اول The Architecture of Open Source Applications است.

پیش‌زمینه

تقریباً هر برنامه‌ای در وب روی خانواده‌ای از استانداردهای ارتباطی به نام Internet Protocol (IP) اجرا می‌شود. عضوی از این خانواده که به ما مربوط می‌شود Transmission Control Protocol (TCP/IP) است که ارتباط بین کامپیوترها را شبیه خواندن و نوشتن فایل‌ها می‌کند.

برنامه‌های IP از طریق سوکت‌ها ارتباط برقرار می‌کنند. هر سوکت یک سر از یک کانال ارتباطی نقطه‌به‌نقطه است، دقیقاً مثل اینکه تلفن یک سر یک تماس تلفنی باشد. یک سوکت شامل یک آدرس IP است که یک ماشین خاص را شناسایی می‌کند و یک شمارهٔ پورت روی آن ماشین. آدرس IP از چهار عدد ۸ بیتی تشکیل شده مثل 174.136.14.108؛ سامانهٔ نام دامنه (DNS) این اعداد را به نام‌های نمادینی مثل aosabook.org که برای انسان‌ها راحت‌ترند مطابقت می‌دهد.

شمارهٔ پورت عددی در بازهٔ 0-65535 است که سوکت را روی ماشین میزبان به‌طور یکتا شناسایی می‌کند. (اگر آدرس IP مثل شمارهٔ تلفن شرکت باشد، شمارهٔ پورت مثل داخلی است.) پورت‌های 0-1023 برای استفادهٔ سیستم‌عامل رزرو شده‌اند؛ بقیه می‌توانند از پورت‌های باقی‌مانده استفاده کنند.

پروتکل انتقال ابرمتن (HTTP) یکی از روش‌هایی را توصیف می‌کند که برنامه‌ها با آن می‌توانند داده را روی IP مبادله کنند. HTTP عمداً ساده است: کلاینت روی یک اتصال سوکت درخواستی می‌فرستد که مشخص می‌کند چه می‌خواهد و سرور در پاسخ داده می‌فرستد. داده می‌تواند از فایلی روی دیسک کپی شود، به‌صورت پویا توسط برنامه تولید شود یا ترکیبی از هر دو باشد.

مهم‌ترین چیز دربارهٔ یک درخواست HTTP این است که فقط متن است: هر برنامه‌ای که بخواهد می‌تواند یکی بسازد یا پارس کند. اما برای فهمیده‌شدن، آن متن باید بخش‌هایی نشان‌داده‌شده در شکل زیر را داشته باشد.

متد HTTP تقریباً همیشه «GET» (برای گرفتن اطلاعات) یا «POST» (برای ارسال دادهٔ فرم یا آپلود فایل) است. URL مشخص می‌کند کلاینت چه می‌خواهد؛ اغلب مسیری به یک فایل روی دیسک مثل /research/experiments.html است، اما (و این نکتهٔ کلیدی است) این کاملاً به سرور بستگی دارد که با آن چه کند. نسخهٔ HTTP معمولاً «HTTP/1.0» یا «HTTP/1.1» است.

هدرهای HTTP جفت‌های کلید/مقدار هستند مثل این سه نمونه:

HTTPAccept: text/html
Accept-Language: en, fr
If-Modified-Since: 16-May-2005

برخلاف کلیدهای جدول‌های هش، کلیدها می‌توانند در هدرهای HTTP چند بار ظاهر شوند. این به درخواست اجازه می‌دهد مثلاً مشخص کند چند نوع محتوا را می‌پذیرد. در نهایت، بدنهٔ درخواست هر دادهٔ اضافهٔ مرتبط با درخواست است؛ هنگام ارسال دادهٔ فرم‌های وب، آپلود فایل و مانند آن استفاده می‌شود. باید یک خط خالی بین آخرین هدر و شروع بدنه باشد تا پایان هدرها را نشان دهد. هدری به نام Content-Length به سرور می‌گوید چند بایت باید در بدنهٔ درخواست بخواند.

پاسخ‌های HTTP مثل درخواست‌های HTTP قالب‌بندی می‌شوند: نسخه، هدرها و بدنه همان شکل و معنی را دارند. کد وضعیت عددی است که نشان می‌دهد هنگام پردازش درخواست چه اتفاقی افتاد: 200 یعنی «همه‌چیز درست بود»، 404 یعنی «پیدا نشد» و کدهای دیگر معانی دیگری دارند. عبارت وضعیت همان اطلاعات را به شکلی خوانا برای انسان تکرار می‌کند مثل «OK» یا «not found».

برای این فصل فقط دو چیز دیگر لازم است دربارهٔ HTTP بدانیم:

اول اینکه HTTP بی‌وضعیت (stateless) است: هر درخواست به‌تنهایی پردازش می‌شود و سرور چیزی بین دو درخواست به خاطر نمی‌سپارد. اگر برنامه‌ای بخواهد چیزی مثل هویت کاربر را دنبال کند، باید خودش این کار را بکند. روش معمول، کوکی است: رشتهٔ کوتاهی که سرور برای کلاینت می‌فرستد و کلاینت بعداً به سرور برمی‌گرداند. وقتی کاربر کاری انجام می‌دهد که به ذخیرهٔ وضعیت در چند درخواست نیاز دارد، سرور کوکی جدیدی می‌سازد، در پایگاه داده ذخیره‌اش می‌کند و به مرورگر می‌فرستد. هر بار که مرورگر کوکی را برمی‌گرداند، سرور از آن برای جستوجوی اطلاعات دربارهٔ کار کاربر استفاده می‌کند.

دوم اینکه URL می‌تواند با پارامترها تکمیل شود تا اطلاعات بیشتری بدهد. این کار با افزودن '؟' به URL و بعد جفت‌های 'key=value' جدا شده با '&' انجام می‌شود. مثلاً URL http://www.google.ca?q=Python از گوگل می‌خواهد صفحات مرتبط با پایتون را جستوجو کند. استاندارد کدگذاری URL کاراکترهای خاص را با '%' و یک کد دو رقمی نشان می‌دهد و فاصله‌ها را با '+' جایگزین می‌کند.

بازکردن سوکت‌ها، ساخت درخواست‌های HTTP و پارس‌کردن پاسخ‌ها کسل‌کننده است، پس بیشتر مردم بیشتر کار را با کتابخانه‌ها انجام می‌دهند. پایتون کتابخانه‌ای به نام urllib2 دارد، اما جزئیات زیادی را در معرض دید می‌گذارد که بیشتر مردم به آن‌ها کاری ندارند. کتابخانهٔ Requests جایگزین ساده‌تری است:

سلام، وب!

حالا آماده‌ایم اولین وب سرور ساده‌مان را بنویسیم. ایدهٔ پایه ساده است:

  1. منتظر بمانیم کسی به سرور متصل شود و یک درخواست HTTP بفرستد؛
  2. آن درخواست را پارس کنیم؛
  3. بفهمیم چه چیزی می‌خواهد؛
  4. آن داده را بیاوریم (یا پویا تولید کنیم)؛
  5. داده را به‌صورت HTML قالب‌بندی کنیم؛ و
  6. بازش بفرستیم.

گام‌های ۱، ۲ و ۶ از برنامه‌ای به برنامهٔ دیگر یکسان‌اند، پس کتابخانهٔ استاندارد پایتون ماژولی به نام BaseHTTPServer دارد که آن‌ها را برایمان انجام می‌دهد. فقط باید گام‌های ۳-۵ را انجام دهیم:

pythonimport BaseHTTPServer

class RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):
    '''پردازش درخواست‌های HTTP با برگرداندن یک «صفحه» ثابت.'''

    # صفحه‌ای که برمی‌گردانیم
    Page = '''\
<html>
<body>
<p>Hello, web!</p>
</body>
</html>
'''

    # پردازش درخواست GET
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.send_header("Content-Length", str(len(self.Page)))
        self.end_headers()
        self.wfile.write(self.Page)

#----------------------------------------------------------------------

if __name__ == '__main__':
    serverAddress = ('', 8080)
    server = BaseHTTPServer.HTTPServer(serverAddress, RequestHandler)
    server.serve_forever()

کلاس BaseHTTPRequestHandler کتابخانه، پارس‌کردن درخواست HTTP ورودی و تشخیص متد آن را انجام می‌دهد. اگر متد GET باشد، کلاس متدی به نام do_GET را صدا می‌زند. کلاس RequestHandler ما این متد را override می‌کند تا یک صفحهٔ ساده تولید کند: متن در متغیر سطح کلاس Page ذخیره شده و بعد از ارسال کد پاسخ 200 و هدر Content-Type (که به کلاینت می‌گوید داده را به‌عنوان HTML تفسیر کند) و طول صفحه، به کلاینت برمی‌گردد.

اما RequestHandler تمام داستان نیست؛ برای راه‌اندازی واقعی سرور به سه خط آخر نیاز داریم. اولین خط آدرس سرور را به‌صورت یک tuple تعریف می‌کند: رشتهٔ خالی یعنی «روی همین ماشین اجرا کن» و 8080 پورت است. بعد نمونه‌ای از BaseHTTPServer.HTTPServer را با آن آدرس و نام کلاس هندلر درخواست به‌عنوان پارامتر می‌سازیم و از آن می‌خواهیم برای همیشه اجرا شود (تا وقتی با Control-C بکشیمش).

اگر برنامه را از خط فرمان اجرا کنیم، چیزی نمایش نمی‌دهد:

Bash$ python server.py

اگر در مرورگر به http://localhost:8080 برویم «Hello, web!» را می‌بینیم و این لاگ در شل چاپ می‌شود:

Console127.0.0.1 - - [24/Feb/2014 10:26:28] "GET / HTTP/1.1" 200 -
127.0.0.1 - - [24/Feb/2014 10:26:28] "GET /favicon.ico HTTP/1.1" 200 -

خط اول ساده است: چون فایل خاصی نخواسته‌ایم، مرورگر «/» را خواسته. خط دوم چون مرورگر خودکار درخواست دوم را برای فایل تصویری /favicon.ico می‌فرستد.

سرو صفحات ایستا

قدم واضح بعدی، سرو صفحات از دیسک به‌جای تولید هنگام درخواست است. با بازنویسی do_GET شروع می‌کنیم:

python    def do_GET(self):
        try:

            # بفهم دقیقاً چه چیزی درخواست شده
            full_path = os.getcwd() + self.path

            # وجود ندارد...
            if not os.path.exists(full_path):
                raise ServerException("'{0}' not found".format(self.path))

            # ...فایل است...
            elif os.path.isfile(full_path):
                self.handle_file(full_path)

            # ...چیزی است که مدیریت نمی‌کنیم.
            else:
                raise ServerException("Unknown object '{0}'".format(self.path))

        # مدیریت خطاها
        except Exception as msg:
            self.handle_error(msg)

این متد فرض می‌کند می‌تواند هر فایلی را در دایرکتوری جاری یا زیرپوشه‌هایش سرو کند (که با os.getcwd می‌گیرد). آن را با مسیرِ URL ترکیب می‌کند (که کتابخانه خودکار در self.path می‌گذارد و همیشه با '/' شروع می‌شود) تا مسیر فایلِ مورد نظر کاربر به دست آید. اگر وجود نداشته باشد یا فایل نباشد، با پرتاب و گرفتن یک استثنا خطا گزارش می‌شود. اگر مسیر به فایلی برسد، متد کمکی handle_file صدا زده می‌شود که فایل را می‌خواند و با send_content برمی‌گرداند:

python    def handle_file(self, full_path):
        try:
            with open(full_path, 'rb') as reader:
                content = reader.read()
            self.send_content(content)
        except IOError as msg:
            msg = "'{0}' cannot be read: {1}".format(self.path, msg)
            self.handle_error(msg)

توجه کنید فایل را در حالت باینری باز می‌کنیم تا پایتون سعی نکند دنباله‌های بایتی شبیه پایان خط ویندوز را تغییر دهد. همچنین، خواندن کل فایل در حافظه برای فایل‌های چند گیگابایتی ویدیو ایدهٔ بدی است؛ مدیریت آن از حوصلهٔ این فصل خارج است.

برای تمام‌کردن این کلاس، متد مدیریت خطا و الگوی صفحهٔ گزارش خطا را می‌نویسیم:

python    Error_Page = """\
        <html>
        <body>
        <h1>Error accessing {path}</h1>
        <p>{msg}</p>
        </body>
        </html>
        """

    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content)

این برنامه کار می‌کند، اما فقط اگر دقیق نگاه نکنیم. مشکل این است که همیشه کد وضعیت 200 را برمی‌گرداند، حتی وقتی صفحهٔ درخواستی وجود ندارد. صفحهٔ برگشتی در آن حالت پیام خطا دارد، اما مرورگر نمی‌فهمد درخواست واقعاً شکست خورده. برای روشن‌کردن این موضوع، باید handle_error و send_content را این‌طور تغییر دهیم:

python    # مدیریت اشیاء ناشناخته
    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content, 404)

    # ارسال محتوای واقعی
    def send_content(self, content, status=200):
        self.send_response(status)
        self.send_header("Content-type", "text/html")
        self.send_header("Content-Length", str(len(content)))
        self.end_headers()
        self.wfile.write(content)
نکته: وقتی فایلی پیدا نمی‌شود ServerException پرتاب نمی‌کنیم، بلکه صفحهٔ خطا می‌سازیم. ServerException برای خطای داخلی کد سرور است — چیزی که ما اشتباه انجام دادیم. صفحهٔ خطای ساخته‌شده توسط handle_error وقتی ظاهر می‌شود که کاربر چیزی اشتباه خواسته، مثلاً URL فایلی را داده که وجود ندارد.

فهرست‌کردن دایرکتوری‌ها

قدم بعدی: آموزشِ نمایش فهرست محتویات یک دایرکتوری وقتی مسیر URL یک دایرکتوری است. حتی می‌توانیم یک قدم جلوتر برویم و به دنبال فایل index.html در آن دایرکتوری بگردیم و فقط اگر نبود، فهرست را نشان دهیم.

اما ساختن این قوانین داخل do_GET اشتباه است، چون متد حاصل به یک درهم پیچیدهٔ عبارت‌های if تبدیل می‌شود که رفتارهای خاص را کنترل می‌کنند. راه‌حل درست عقب‌ایستادن و حل مسئلهٔ عمومی است: فهمیدن اینکه با یک URL چه باید کرد. این بازنویسی do_GET است:

python    def do_GET(self):
        try:

            # بفهم دقیقاً چه چیزی درخواست شده
            self.full_path = os.getcwd() + self.path

            # بفهم چگونه آن را مدیریت کنیم
            for case in self.Cases:
                handler = case()
                if handler.test(self):
                    handler.act(self)
                    break

        # مدیریت خطاها
        except Exception as msg:
            self.handle_error(msg)

اولین گام همان است: فهمیدن مسیر کاملِ چیزِ درخواستی. اما بعد از آن، کد خیلی متفاوت است. به‌جای تست‌های داخلی، این نسخه روی مجموعه‌ای از case ها در یک لیست حلقه می‌زند. هر case یک شیء با دو متد است: test، که می‌گوید آیا می‌تواند درخواست را مدیریت کند، و act، که واقعاً کاری انجام می‌دهد. به محض یافتن case درست، اجازه می‌دهیم درخواست را مدیریت کند و از حلقه خارج می‌شویم.

این سه کلاس case رفتار سرور قبلی ما را تکرار می‌کنند:

pythonclass case_no_file(object):
    '''فایل یا دایرکتوری وجود ندارد.'''

    def test(self, handler):
        return not os.path.exists(handler.full_path)

    def act(self, handler):
        raise ServerException("'{0}' not found".format(handler.path))


class case_existing_file(object):
    '''فایل وجود دارد.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path)

    def act(self, handler):
        handler.handle_file(handler.full_path)


class case_always_fail(object):
    '''case پایه اگر چیز دیگری کار نکرد.'''

    def test(self, handler):
        return True

    def act(self, handler):
        raise ServerException("Unknown object '{0}'".format(handler.path))

و این‌طور لیست case handler ها را بالای کلاس RequestHandler می‌سازیم:

pythonclass RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):
    '''
    اگر مسیر درخواستی به فایلی برسد، همان فایل سرو می‌شود.
    اگر چیزی اشتباه برود، صفحهٔ خطا ساخته می‌شود.
    '''

    Cases = [case_no_file(),
             case_existing_file(),
             case_always_fail()]

    # ... بقیه مانند قبل ...

از نظر ظاهری این کار سرور را پیچیده‌تر کرده، نه ساده‌تر: فایل از 74 خط به 99 خط رسیده و یک سطح غیرمستقیمی اضافه شده بدون قابلیت جدید. فایده وقتی می‌آید که به کارِ شروع‌کنندهٔ این فصل برمی‌گردیم: آموزش سرو صفحهٔ index.html برای دایرکتوری‌ها، و فهرست‌کردن دایرکتوری اگر نبود. هندلر مورد اول:

pythonclass case_directory_index_file(object):
    '''سرو صفحهٔ index.html برای یک دایرکتوری.'''

    def index_path(self, handler):
        return os.path.join(handler.full_path, 'index.html')

    def test(self, handler):
        return os.path.isdir(handler.full_path) and \
               os.path.isfile(self.index_path(handler))

    def act(self, handler):
        handler.handle_file(self.index_path(handler))

تنها تغییر لازم در RequestHandler افزودن شیء case_directory_index_file به لیست Cases است:

python    Cases = [case_no_file(),
             case_existing_file(),
             case_directory_index_file(),
             case_always_fail()]

دربارهٔ دایرکتوری‌هایی که صفحهٔ index.html ندارند چه؟ تست همان است با یک not به‌جا، اما متد act چه باید بکند؟ منطقاً باید فهرست دایرکتوری را بسازد و برگرداند، اما کد فعلی ما اجازهٔ این کار را نمی‌دهد: RequestHandler.do_GET با act تماس می‌گیرد اما از آن مقدار برگشتی دریافت یا مدیریت نمی‌کند. فعلاً متدی به RequestHandler اضافه می‌کنیم تا فهرست دایرکتوری بسازد:

pythonclass case_directory_no_index_file(object):
    '''سرو فهرست برای دایرکتوری بدون صفحهٔ index.html.'''

    # ... index_path و test مانند بالا ...

    def act(self, handler):
        handler.list_dir(handler.full_path)


class RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):

    # ... بقیهٔ کد ...

    # نحوهٔ نمایش فهرست دایرکتوری
    Listing_Page = '''\
        <html>
        <body>
        <ul>
        {0}
        </ul>
        </body>
        </html>
        '''

    def list_dir(self, full_path):
        try:
            entries = os.listdir(full_path)
            bullets = ['<li>{0}</li>'.format(e) 
                for e in entries if not e.startswith('.')]
            page = self.Listing_Page.format('\n'.join(bullets))
            self.send_content(page)
        except OSError as msg:
            msg = "'{0}' cannot be listed: {1}".format(self.path, msg)
            self.handle_error(msg)

پروتکل CGI

البته، بیشتر مردم نمی‌خواهند برای افزودن قابلیت، سورس وب سرورشان را ویرایش کنند. به همین دلیل، سرورها از ابتدا مکانیزمی به نام Common Gateway Interface (CGI) را پشتیبانی کرده‌اند که راهی استاندارد برای اجرای یک برنامهٔ خارجی برای برآوردن یک درخواست فراهم می‌کند.

مثلاً فرض کنید می‌خواهیم سرور بتواند زمان محلی را در یک صفحهٔ HTML نمایش دهد. این کار را در یک برنامهٔ مستقل با چند خط انجام می‌دهیم:

pythonfrom datetime import datetime
print '''\
<html>
<body>
<p>Generated {0}</p>
</body>
</html>'''.format(datetime.now())

برای اینکه وب سرور این برنامه را برایمان اجرا کند، این case handler را اضافه می‌کنیم:

pythonclass case_cgi_file(object):
    '''چیزی قابل اجرا.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path) and \
               handler.full_path.endswith('.py')

    def act(self, handler):
        handler.run_cgi(handler.full_path)

تست ساده است: آیا مسیر فایل به .py ختم می‌شود؟ اگر بله، RequestHandler این برنامه را اجرا می‌کند:

python    def run_cgi(self, full_path):
        cmd = "python " + full_path
        child_stdin, child_stdout = os.popen2(cmd)
        child_stdin.close()
        data = child_stdout.read()
        child_stdout.close()
        self.send_content(data)
هشدار: این فوق‌العاده ناامن است: اگر کسی مسیر یک فایل پایتون را در سرور شما بداند، فقط اجازه می‌دهید بدون نگرانی دربارهٔ داده‌هایی که به آن دسترسی دارد یا حلقهٔ بی‌نهایت احتمالی، آن را اجرا کند. (ضمناً popen2 در نسخه‌های جدید به نفع ماژول subprocess منسوخ شده.)

کنار گذاشتن این مسئله، ایدهٔ اصلی ساده است:

  1. برنامه را در یک زیرفرایند اجرا کن.
  2. هرچه زیرفرایند به خروجی استاندارد می‌فرستد را بگیر.
  3. آن را به کلاینتی که درخواست کرده برگردان.

پروتکل کامل CGI خیلی غنی‌تر از این است — به‌ویژه اجازهٔ پارامتر در URL را می‌دهد که سرور به برنامهٔ در حال اجرا می‌دهد — اما این جزئیات روی معماری کلی سیستم اثری ندارند... که دوباره دارد درهم‌پیچیده می‌شود. RequestHandler ابتدا یک متد handle_file برای محتوا داشت. حالا دو حالت خاص به‌صورت list_dir و run_cgi اضافه کرده‌ایم. این سه متد واقعاً جایشان اینجا نیست، چون عمدتاً توسط دیگران استفاده می‌شوند.

راه‌حل ساده است: یک کلاس والد برای همهٔ case handler ها بسازید و متدهای دیگر را فقط وقتی به آن کلاس منتقل کنید که دو یا چند handler از آن استفاده می‌کنند. وقتی تمام شد، کلاس RequestHandler این‌طور می‌شود:

pythonclass RequestHandler(BaseHTTPServer.BaseHTTPRequestHandler):

    Cases = [case_no_file(),
             case_cgi_file(),
             case_existing_file(),
             case_directory_index_file(),
             case_directory_no_index_file(),
             case_always_fail()]

    # نحوهٔ نمایش خطا
    Error_Page = """\
        <html>
        <body>
        <h1>Error accessing {path}</h1>
        <p>{msg}</p>
        </body>
        </html>
        """

    # طبقه‌بندی و مدیریت درخواست
    def do_GET(self):
        try:

            # بفهم دقیقاً چه درخواست شده
            self.full_path = os.getcwd() + self.path

            # بفهم چگونه مدیریتش کنیم
            for case in self.Cases:
                if case.test(self):
                    case.act(self)
                    break

        # مدیریت خطاها
        except Exception as msg:
            self.handle_error(msg)

    # مدیریت اشیاء ناشناخته
    def handle_error(self, msg):
        content = self.Error_Page.format(path=self.path, msg=msg)
        self.send_content(content, 404)

    # ارسال محتوای واقعی
    def send_content(self, content, status=200):
        self.send_response(status)
        self.send_header("Content-type", "text/html")
        self.send_header("Content-Length", str(len(content)))
        self.end_headers()
        self.wfile.write(content)

در حالی که کلاس والد برای case handler ها این است:

pythonclass base_case(object):
    '''والد case handler ها.'''

    def handle_file(self, handler, full_path):
        try:
            with open(full_path, 'rb') as reader:
                content = reader.read()
            handler.send_content(content)
        except IOError as msg:
            msg = "'{0}' cannot be read: {1}".format(full_path, msg)
            handler.handle_error(msg)

    def index_path(self, handler):
        return os.path.join(handler.full_path, 'index.html')

    def test(self, handler):
        assert False, 'Not implemented.'

    def act(self, handler):
        assert False, 'Not implemented.'

و هندلر فایل موجود (فقط به‌عنوان یک مثال) این است:

pythonclass case_existing_file(base_case):
    '''فایل وجود دارد.'''

    def test(self, handler):
        return os.path.isfile(handler.full_path)

    def act(self, handler):
        self.handle_file(handler, handler.full_path)

بحث

تفاوت‌های بین کد اصلی ما و نسخهٔ بازسازی‌شده دو ایدهٔ مهم را منعکس می‌کنند. اولی این است که به کلاس به‌عنوان مجموعه‌ای از خدمات مرتبط نگاه کنیم. RequestHandler و base_case تصمیم نمی‌گیرند و اقدام نمی‌کنند؛ آن‌ها ابزارهایی فراهم می‌کنند که کلاس‌های دیگر برای انجام این کارها استفاده می‌کنند.

دومی قابلیت گسترش است: افراد می‌توانند قابلیت جدیدی به وب سرور اضافه کنند یا با نوشتن یک برنامهٔ CGI خارجی، یا با افزودن یک کلاس case handler. حالت دوم به یک تغییر یک‌خطی در RequestHandler نیاز دارد (درج case handler در لیست Cases)، اما می‌توانیم با خواندن یک فایل پیکربندی و بارگذاری کلاس‌های handler از آن، از شر آن هم خلاص شویم. در هر دو حالت، می‌توانند بیشتر جزئیات سطح پایین را نادیده بگیرند، دقیقاً همان‌طور که نویسندگان کلاس BaseHTTPRequestHandler به ما اجازه داده‌اند جزئیات مدیریت اتصال سوکت و پارس‌کردن درخواست‌های HTTP را نادیده بگیریم.

این ایده‌ها به‌طور کلی مفیدند؛ ببینید می‌توانید راه‌هایی برای استفاده از آن‌ها در پروژه‌های خودتان پیدا کنید.
