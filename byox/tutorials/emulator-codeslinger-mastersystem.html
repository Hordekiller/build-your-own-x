مقدمه — نمای کلی (Overview)

این بخش از سایت به شبیه‌سازی سگا مستر سیستم اختصاص دارد. نویسنده همهٔ آنچه در شبیه‌سازی این سیستم دخیل است را توضیح می‌دهد و در طول مسیر از تجربه‌هایش در شبیه‌سازی گیم‌بوی استفاده می‌کند؛ پس اگر قبلاً آموزش شبیه‌سازی گیم‌بوی را خوانده باشید، خیلی از مطالب برایتان آشنا خواهد بود.

دانلود کد منبع

اگر می‌خواهید وضعیت فعلی شبیه‌ساز را ببینید، می‌توانید کد منبع را دانلود کنید؛ هر طور دوست دارید از کد استفاده کنید، فقط تا زمانی که اعتبار آن به نویسنده داده شود. به یاد داشته باشید برای استفاده از کد و اجرای بازی‌ها باید واقعاً یک مستر سیستم و بازی‌های آن را داشته باشید. اجرای بازی‌ها بدون داشتن‌شان خلاف قانون است و نویسنده هیچ مسئولیتی در این باره نمی‌پذیرد.

شروع کار (Getting Started)

در این بخش کد را با یک حلقهٔ شبیه‌سازی ساده شروع می‌کنیم و در بخش‌های بعدی به ترتیب شبیه‌سازی حافظه، Z80 و VDP را اضافه می‌کنیم.

cppvoid Emulator::MainLoop( )
{
  while (notQuitting)
  {
    Update( ) ;
  }
}

void Emulator::Update( )
{
  // تا وقتی بازیکن خارج نشده حلقه بزن
  m_Z80.ExecuteNextInst() ;
  // بقیهٔ دستگاه‌ها بعداً اینجا اضافه می‌شوند
}

این در واقع ساده‌ترین حلقهٔ شبیه‌سازی ممکن است. اما مشکلی دارد: بدون محدودکردن سرعت، شبیه‌ساز بسیار سریع‌تر از مستر سیستم واقعی اجرا می‌شود و بازی‌ها با سرعت چند برابر کار می‌کنند. این موضوع در بخش «سخت‌افزار» حل می‌شود، وقتی زمان‌بندی را کامل در نظر بگیریم.

زمان‌بندی (Timing)

برای اینکه شبیه‌ساز سازگاری خوبی داشته باشد، همگام‌سازی صحیح سه تراشهٔ اصلی (پردازنده، VDP و صدا) حیاتی است. این کار با دانستن تعداد تیک ماشین (machine clicks) در ثانیه در مستر سیستم و تعداد چرخهٔ ساعت هر دستورالعمل Z80 کنترل می‌شود. با ترکیب این‌ها می‌توانیم Z80 را مجبور کنیم همان تعداد دستورالعمل در ثانیه را اجرا کند که مستر سیستم واقعی. کلید این کار دانستن تعداد چرخه‌های ساعت Z80 برای آخرین دستورالعمل شبیه‌سازیشده است؛ سپس می‌توانیم آن را به تیک‌های ماشین و بعد به چرخه‌های تراشهٔ VDP و در نهایت چرخه‌های تراشهٔ صدا تبدیل کنیم.

ساعت اصلی مستر سیستم با 10.738580 MHz کار می‌کند؛ یعنی 10738580 تیک ماشین در هر ثانیه. پردازندهٔ Z80 با یک‌سوم سرعت ساعت اصلی (3.58 MHz) کار می‌کند. VDP با نصف سرعت ساعت اصلی (5.36 MHz) کار می‌کند. ساعت صدا هم با همان سرعت پردازندهٔ Z80 (3.58 MHz) است.

یک اطلاعات نهایی لازم قبل از ساخت حلقهٔ اصلی شبیه‌سازی: VDP صفحه را ۶۰ بار در ثانیه تازه‌سازی می‌کند؛ یعنی هر ثانیه صفحه ۶۰ بار رسم می‌شود. پس اگر ساعت اصلی هر ثانیه 10738580 تیک ماشین اجرا کند، هر فریم از VDP برابر 10738580/60 تیک ماشین است. شبیه‌ساز ما هم باید ۶۰ فریم در ثانیه اجرا کند؛ اما چون کامپیوترهای امروزی خیلی سریع‌تر از مستر سیستم‌اند، باید حلقهٔ شبیه‌سازی را کند کنیم تا بازی‌ها با سرعت صحیح اجرا شوند. این کار آسان است: اگر حلقهٔ اصلی شبیه‌سازی طوری باشد که هر بار یک فریم را شبیه‌سازی کند، بعد از اتمام فریم صبر می‌کند تا 1/60 ثانیه بگذرد و بعد فریم بعدی را شبیه‌سازی می‌کند. به این ترتیب شبیه‌ساز دقیقاً ۶۰ فریم در هر ثانیه رسم می‌کند:

cppvoid Emulator::MainLoop( )
{
  const double SIXTYTH = 1000/60 ; // با میلی‌ثانیه کار می‌کنیم
  double lastFrameTime = 0 ;
  while (notQuitting) // تا وقتی بازیکن خارج نشود حلقه بزن
  {
    double currentTime = getCurrentTime( ) ;

    // هر 1/60 ثانیه یک فریم رسم کن
    if ((lastFrameTime + SIXTYTH) <= currentTime)
    {
      lastFrameTime = currentTime ;
      Update( ) ; // این یک فریم را رسم می‌کند
    }
  }
}

// این مسئول شبیه‌سازی یک فریم است
void Emulator::Update( )
{
  const double MACHINE_CLICKS_PER_FRAME = 10738580 / 60 ;
  unsigned int clicksThisUpdate = 0 ;

  // مقدار تیک ماشینِ 1/60 ثانیه را شبیه‌سازی کن
  while (clicksThisUpdate < MACHINE_CLICKS_PER_FRAME)
  {
    int z80ClockCycles = m_Z80.ExecuteNextInst();

    // ساعت ماشین ۳ برابر سریع‌تر از ساعت Z80 است
    int machineClicks = z80ClockCycles * 3 ;

    // ساعت VDP نصف سرعت ساعت ماشین است
    float vdpCycles = machineClicks / 2 ;

    // ساعت صدا همان سرعت Z80 است
    int soundCycles = z80ClockCycles ;

    m_VDP.Update(vdpCycles) ;
    m_Sound.Update(soundCycles) ;

    clicksThisUpdate += machineClicks ;
  }
}

کد بالا نشان می‌دهد سه تراشهٔ اصلی چگونه با هم همگام می‌شوند. توجه کنید نوع vdpCycles float است نه int؛ تا دقت شبیه‌سازی VDP در طول زمان از بین نرود.

پورت‌ها (Ports)

راه ارتباط بازی‌ها با چهار دستگاه اصلی، دستورالعمل‌های IN و OUT از Z80 است. این دستورالعمل‌ها برای صحبت با چهار دستگاه اصلی هستند؛ دستگاه‌ها شمارهٔ پورت دارند و خواندن/نوشتن بایت‌های داده از این پورت‌ها عبور می‌کند. مثلاً دستور Z80 زیر: "INA 0x7e" پورت 0x7E را می‌خواند و مقدار برگشتی را در ثبات A می‌گذارد. در بخش‌های بعدی آموزش بیشتر دربارهٔ پورت‌ها بحث می‌شود؛ فعلاً فقط لازم است بدانید خواندن و نوشتن با چهار دستگاه اصلی از طریق پورت‌ها انجام می‌شود.

تفکیک شمارهٔ پورت‌های هر دستگاه:

text0x7E : خواندن: شمارندهٔ V را از VDP برمی‌گرداند. نوشتن: داده به تراشهٔ صدا
0x7F : خواندن: شمارندهٔ H را از VDP برمی‌گرداند. نوشتن: داده به تراشهٔ صدا (آینهٔ بالا)
0xBE : خواندن: پورت دادهٔ VDP. نوشتن: پورت دادهٔ VDP
0xBF : خواندن: وضعیت VDP. نوشتن: پورت کنترل VDP
0xDC : خواندن: جوی‌پد 1. نوشتن: امکان‌پذیر نیست
0xDD : خواندن: جوی‌پد 2. نوشتن: امکان‌پذیر نیست

پورت 0xBD همان کار 0xBF را می‌کند؛ پورت 0xC0 همان کار 0xDC را؛ و پورت 0xC1 همان کار 0xDD را.

پس حالا می‌دانید چطور اجرای دستگاه‌ها را کنترل کنید و درک پایه‌ای از تعامل بازی‌ها با آن‌ها دارید. در بخش‌های بعدی خیلی عمیق‌تر با پورت‌ها کار می‌کنیم. حالا وقت حرکت به جلو و شروع شبیه‌سازی مستر سیستم است.

حافظه (Memory)

نقشهٔ حافظه

فضای آدرس‌دهی مستر سیستم در مقایسه با سایر سیستم‌های بازی ویدیویی (مثل گیم‌بوی) واقعاً ساده است. نقشهٔ حافظه:

text0x0000-0x3FFF : ROM Slot 1
0x4000-0x7FFF : ROM Slot 2
0x8000-0xBFFF : ROM Slot 3 / RAM Slot
0xC000-0xDFFF : RAM
0xE000-0xFFFF : RAM آینه‌شده (Mirrored)

وقتی بازی مقداردهی می‌شود، صفحهٔ 0 باید در slot0، صفحهٔ 1 در slot 2 و صفحهٔ 2 در slot 3 باشد. مهم است به یاد داشته باشید حتی اگر این صفحه‌ها هر لحظه تعویض شوند، 0x400 بایت اول slot 1 هرگز خارج نمی‌شود؛ چون روال‌های مدیریت وقفه (interrupt handler) در همین فضای آدرس هستند و باید همیشه حاضر باشند تا وقفه‌ها درست مدیریت شوند. یعنی بازهٔ آدرس 0x0-0x400 همیشه دادهٔ صفحهٔ 0 در همان آدرس است.

نمی‌توانید در بازهٔ 0x0-0x8000 بنویسید؛ چون این ناحیه برای حافظهٔ فقط‌خواندنی است و فقط می‌توانید داده را داخل و خارج این ناحیه صفحه‌بندی (page) کنید. اما slot 0x8000-0xBFFF (Slot 3) هم فقط‌خواندنی در نظر گرفته می‌شود، مگر اینکه یکی از دو بانک RAM آنجا صفحه‌بندی شده باشد؛ که بعداً درباره‌اش بحث می‌شود.

نگاشت‌گرهای حافظه (Memory Mappers)

همان‌طور که گفته شد، فضاهای آدرس ROM سه slot با اندازهٔ 0x4000 دارند که برای حافظهٔ بازی در دسترس‌اند. از این سه، slot سوم می‌تواند یک بانک RAM را هم صفحه‌بندی کند. دو بانک RAM با اندازهٔ 0x4000 وجود دارد. بازی‌های مختلف تعداد صفحهٔ ROM متفاوتی دارند؛ قانون سرانگشتی این است که هرچه بازی بزرگ‌تر باشد، صفحه‌های بیشتری برای انتخاب دارد.

ثبات‌های نگاشت حافظه در آدرس‌های 0xFFFC-0xFFFF هستند:

text0xFFFC: ثبات کنترل حافظه (Memory Control Register)
0xFFFD: نوشتن مقدار در این آدرس، همان صفحه را به slot 1 نگاشت می‌کند
0xFFFE: نوشتن مقدار در این آدرس، همان صفحه را به slot 2 نگاشت می‌کند
0xFFFF: نوشتن مقدار در این آدرس، همان صفحه را به slot 3 نگاشت می‌کند

ثبات کنترل حافظه را لحظه‌ای دیگر بحث می‌کنیم. سه ثبات دیگر مسئول صفحه‌بندی حافظه به داخل و خارج slotهای مربوطه‌شان‌اند. پس نوشتن مقدار 0 در آدرس 0xFFFE باعث می‌شود صفحهٔ 0 در slot 2 صفحه‌بندی شود. نوشتن مقدار 0xA در 0xFFFD باعث می‌شود صفحهٔ 10 در slot 1 صفحه‌بندی شود، به‌جز 0x400 بایت اول که همان‌طور که گفتیم قابل خارج‌شدن نیست. نوشتن در 0xFFFF معمولاً یک صفحهٔ ROM را به slot 3 نگاشت می‌کند؛ اما بسته به ثبات کنترل حافظه، اگر بانک RAM در slot 3 فعال باشد ممکن است نادیده گرفته شود. بانک‌بندی RAM همیشه بر بانک‌بندی ROM اولویت دارد.

به‌دلیل آینه‌سازی RAM، نوشتن در بازهٔ 0xDFFC-0xDFFF در ثبات‌های نگاشت 0xFFFC-0xFFFF هم آینه می‌شود. نویسنده شخصاً آدرس 0xDFFC-0xDFFF را روی ثبات‌های کنترل حافظه آینه نمی‌کند؛ چون نتیجهٔ بدی گرفته است.

ثبات کنترل حافظه

بیت‌های مختلف در بایت دادهٔ ثبات کنترل حافظه (آدرس 0xFFFC) تنظیمات مختلفی را برای کنترل نگاشت‌گر نشان می‌دهند. هرچند تمام نرم‌افزارهای شناخته‌شده فقط از بیت‌های 2 و 3 استفاده می‌کنند. اگر بیت 3 تنظیم شود، RAM به Page Slot 3 نگاشت می‌شود که همیشه بر هر بانک ROM آنجا غلبه می‌کند. اگر بیت 3 تنظیم نشود، بانک ROM در slot 3 اتفاق می‌افتد. اگر بانک RAM فعال باشد، بیت 2 از 0xFFFC انتخاب می‌کند کدام‌یک از دو بانک RAM به slot 3 بانک می‌شود: اگر بیت «1» باشد از بانک RAM دوم استفاده می‌شود وگرنه بانک اول.

هرچند ثبات کنترل حافظه می‌تواند کاربردهای بیشتری داشته باشد، چون هیچ بازی‌ای از آن‌ها استفاده نمی‌کند، نویسنده آن‌ها را شبیه‌سازی نکرده و در اینجا هم بحث نمی‌کند.

نوشتن در حافظه

بسیاری از دستورالعمل‌های Z80 باعث نوشتن داده در حافظه می‌شوند. عادت خوب این است که همیشه از یک تابع برای نوشتن در حافظه استفاده کنید؛ به این ترتیب می‌توانید به‌راحتی دسترسی به حافظه را به دام بیندازید و زیر نظر بگیرید. این‌طور می‌توانیم مطمئن شویم هیچ داده‌ای در ROM نوشته نمی‌شود، آینه‌سازی درست مدیریت می‌شود و دستورالعمل‌های صفحه‌بندی هم مدیریت می‌شوند. نحوهٔ مدیریت نوشتن در حافظه توسط نویسنده:

cppvoid Emulator::WriteMemory(const WORD& address, const BYTE& data)
{
   // نگاشت حافظهٔ codemasters را مدیریت کن
   if (m_IsCodeMasters)
   {
     if (address == 0x0 || address == 0x4000 || address == 0x8000)
       DoMemPageCM(address,data) ;
   }

   // نمی‌توان در ROM نوشت
   if (address < 0x8000)
     return ;

   // اگر بانک RAM به slot 3 نگاشت شده باشد اینجا نوشتن مجاز است
   else if (address < 0xC000)
   {
     BYTE controlMap = m_InternalMemory[0xFFFC] ;
     if (m_CurrentRam > -1)
     {
       m_RamBank[m_CurrentRam][address-0x8000] = data ;
       return ;
     }
     else
     {
       // اینجا ROM است؛ پس برگرد
       return ;
     }
   }

   // نوشتن در حافظه خوب به نظر می‌رسد
   m_InternalMemory[address] = data ;

   // صفحه‌بندی استاندارد حافظه را مدیریت کن
   if (address >= 0xFFFC)
   {
     if (!m_IsCodeMasters)
       DoMemPage(address, data) ;
   }

   // آینه‌سازی را مدیریت کن
   if (address >= 0xC000 && address < 0xDFFC)
     m_InternalMemory[address+0x2000] = data ;
   if (address >= 0xE000)
     m_InternalMemory[address-0x2000] = data ;
}

بخش codemasters بالای کد را فعلاً نادیده بگیرید و روی بقیه تمرکز کنید. اولین چیزی که باید بررسی شود این است که آیا بازی می‌خواهد در ROM slot های 1 یا 2 بنویسد؛ اگر بله بلافاصله برمی‌گردیم چون بازی نمی‌تواند آنجا بنویسد. بعد بررسی می‌کنیم آیا بازی می‌خواهد در slot 3 بنویسد. فقط در صورتی می‌توانیم اجازهٔ نوشتن در slot 3 را بدهیم که بانک RAM آنجا فعال باشد؛ پس باید ثبات کنترل حافظه را در آدرس 0xFFFC بررسی کنیم. اگر RAM به slot 3 بانک شده، در بانک RAM بنویس و خارج شو؛ وگرنه باید خارج شویم، چون اگر RAM آنجا بانک نشده باشد ROM است و نمی‌توان آنجا نوشت. اگر بازی تلاش نمی‌کند در هیچ‌کدام از سه slot بنویسد، اجازهٔ نوشتن در RAM را می‌دهیم و بعد بررسی می‌کنیم آیا لازم است صفحه‌بندی حافظه انجام شود (تابع DoMemPage). بعد از صفحه‌بندی، در نهایت آینه‌سازی RAM را مدیریت می‌کنیم. امیدواریم این‌قدر ساده بود.

صفحه‌بندی حافظه

حالا که می‌دانیم صفحه‌بندی حافظه چطور کار می‌کند، ببینیم چطور پیاده‌سازی می‌شود. داده‌ای که به ثبات‌های صفحه‌بندی نوشته می‌شود شامل شمارهٔ صفحهٔ مورداستفاده است. همهٔ بازی‌ها از بیت‌های 5-0 از بایت داده برای گرفتن شمارهٔ صفحه استفاده می‌کنند، به‌جز بازی‌های ۱ مگابایتی که از بیت‌های 6-0 استفاده می‌کنند. بعد از دانستن شمارهٔ صفحه باید آن را برای slot درست ذخیره کنیم تا هنگام خواندن از slotها بدانیم از کدام صفحه بخوانیم. مثلاً اگر شمارهٔ صفحه 5 باشد و بازی در آدرس 0xFFFE بنویسد، صفحهٔ 5 به slot 2 نگاشت می‌شود. خوب است که به‌سادگی داده را از صفحهٔ 5 به slot 2 کپی کنیم (memcpy)؛ اما این کار کند است؛ پس بهتر است فقط متغیری به نام m_SecondBankPage داشته باشیم و آن را 5 کنیم. به این ترتیب هر وقت بازی بخواهد از slot 2 بخواند، می‌توانیم از این متغیر برای پیدا کردن صفحهٔ درست در حافظهٔ کارتریج استفاده کنیم و مقدار درست را برگردانیم.

تنها بخش باقی‌مانده برای مدیریت، نوشتن در ثبات کنترل حافظه (0xFFFC) است. اگر این ثبات نوشته شود باید بانک RAM فعلی را به‌روزرسانی کنیم:

cppvoid Emulator::DoMemPage(WORD address, BYTE data )
{
   BYTE page = m_OneMegCartridge ? data & 0x3F : data & 0x1F ;

   switch(address)
   {
     case 0xFFFC:
     {
       // بانک RAM در slot 2 را بررسی کن
       if (TestBit(data,3))
         // کدام‌یک از دو بانک RAM را تعویض می‌کنیم؟
         TestBit(data,2) ? m_CurrentRam = 1 : m_CurrentRam = 0 ;
       else
         m_CurrentRam = -1 ;
     }
     break ;

     case 0xFFFD: m_FirstBankPage = page ; break ;
     case 0xFFFE: m_SecondBankPage = page ; break ;
     case 0xFFFF:
     {
       // فقط اگر RAM به آنجا نگاشت نشده باشد اجازهٔ بانک ROM در slot 2 را بده!
       if (false == TestBit(m_InternalMemory[0xFFFC],3))
         m_ThirdBankPage = page ;
     }
     break ;
   }
}

صفحه‌بندی حافظه — بازی‌های CodeMasters

بازی‌های codemasters از نگاشت‌گر مخصوص خودشان استفاده می‌کنند که خوشبختانه ساده‌تر از نگاشت‌گر استاندارد سگا است. اول اینکه بانک RAM وجود ندارد؛ فقط ROM به slot های 1-3 نگاشت می‌شود. دوم اینکه نیازی به محافظت از آدرس 0x0-0x400 در slot 1 نیست؛ چون نگاشت‌گر می‌تواند آن را بیرون و داخل ببرد. این نگاشت‌گر از ثبات‌های 0xFFFC-0xFFFF برای مدیریت نگاشت‌گر استفاده نمی‌کند؛ به‌جایش از ثبات‌های 0x0، 0x4000 و 0x8000 استفاده می‌کند. نوشتن در آدرس 0x0 صفحهٔ slot 1 را تغییر می‌دهد، نوشتن در 0x4000 صفحهٔ slot 2 را و نوشتن در 0x8000 صفحهٔ slot 3 را. خارج از این موارد، نگاشت‌گرها یکسان‌اند که پیاده‌سازی زیر را می‌دهد:

cppvoid Emulator::DoMemPageCM(WORD address, BYTE data )
{
   BYTE page = m_OneMegCartridge ? data & 0x3F : data & 0x1F ;
   switch(address)
   {
     case 0x0:     m_FirstBankPage = page ; break ;
     case 0x4000:  m_SecondBankPage = page ; break ;
     case 0x8000:  m_ThirdBankPage = page ; break ;
   }
}

خواندن از حافظه

به همان دلیل که نوشتن در حافظه را کنترل می‌کنیم، باید خواندن از حافظه را هم کنترل کنیم. نقشهٔ حافظه z80 را قبلاً نشان دادم؛ اما می‌شد آن را به شکل ساده‌تر هم نشان داد:

text0x0000-0xBFFF: حافظهٔ کارتریج
0xC000-0xFFFF: RAM

پس هر وقت z80 می‌خواهد از حافظه بخواند، همیشه از حافظهٔ داخلی‌اش می‌خواند. یادتان باشد اکثر اندازه‌های ROM بزرگ‌تر از 0xC000 بایت هستند؛ پس کل ROM در ناحیهٔ آدرس حافظهٔ کارتریج جا نمی‌شود. به همین دلیل صفحه‌بندی لازم است تا حافظهٔ ROM درست در زمان نیاز در ناحیهٔ آدرس حافظهٔ کارتریج باشد. یعنی مستر سیستم همیشه از حافظهٔ داخلی می‌خواند، چه بخواهد حافظهٔ کارتریج را بخواند چه RAM، و برای اطمینان از در دسترس بودن حافظهٔ کارتریجِ درست باید صفحه‌بندی حافظه انجام دهد.

نویسنده شخصاً این را متفاوت از طرز کار واقعی SMS شبیه‌سازی می‌کند. به‌جای کپی‌کردن (memcpy) حافظهٔ کارتریج به حافظهٔ داخلی هر بار که صفحه تغییر می‌کند، فقط متغیری از صفحهٔ فعال جدید را ذخیره می‌کند. سپس هر وقت ROM می‌خواهد از فضای آدرس حافظهٔ کارتریج داخل حافظهٔ داخلی بخواند، داده را مستقیم از حافظهٔ کارتریج جستجو می‌کند. دلیل این کار اجتناب از memcpy های کند است. این‌طور تابع ReadMemory نوشته می‌شود:

cppBYTE Emulator::ReadMemory(const WORD& address)
{
   WORD addr = address ;

   // از آینهٔ 0xDFFC-0xDFFF بخوان نه از ثبات‌های نقشهٔ حافظه
   if (addr>=0xFFFC)
     addr-=0x2000 ;

   // آدرس ثابت حافظه در slot 1
   else if (!m_IsCodeMasters && (addr < 0x400))
   {
     return m_InternalMemory[addr] ;
   }
   // slot 1
   else if (addr < 0x4000)
   {
     // آدرس را به آدرس صفحهٔ صحیح تبدیل کن
     unsigned int bankaddr = addr + (0x4000 * m_FirstBankPage) ;
     return m_CartridgeMemory[bankaddr] ;
   }
   // slot 2
   else if (addr < 0x8000)
   {
     // آدرس را به آدرس صفحهٔ صحیح تبدیل کن
     unsigned int bankaddr = addr + (0x4000 * m_SecondBankPage) ;
     // آفست را بردار
     bankaddr -= 0x4000 ;
     return m_CartridgeMemory[bankaddr] ;
   }
   // slot 3
   else if (addr < 0xC000)
   {
     // آیا بانک RAM در این slot نگاشت شده است؟
     if (m_CurrentRam > -1)
     {
       return m_RamBank[m_CurrentRam][addr-0x8000] ; // آفست 0x8000
     }
     else
     {
       // آدرس را به آدرس صفحهٔ صحیح تبدیل کن
       unsigned int bankaddr = addr + (0x4000 * m_ThirdBankPage) ;
       // آفست را بردار
       bankaddr -= 0x8000 ;
       return m_CartridgeMemory[bankaddr] ;
     }
   }

   return m_InternalMemory[addr] ;
}

اول ممکن است کد بالا عجیب به نظر برسد و راستش همین‌طور است. باید به یاد داشته باشید متغیرهای صفحه یک بلوک 0x4000 بایتی در حافظهٔ کارتریج را نشان می‌دهند. پس صفحهٔ 0 از آدرس 0x0 در حافظهٔ کارتریج شروع می‌شود و صفحهٔ 2 از آدرس 0x8000 (0x4000*2). این‌طور صفحهٔ درست در حافظه را پیدا می‌کنیم؛ کاری که متغیر bankaddr انجام می‌دهد. می‌بینید برای slot های 2 و 3 یک آفست از bankaddr کم می‌شود. یادتان باشد هر صفحه 0x4000 بایت است و فقط می‌خواهیم یکی از این بایت‌ها را بخوانیم. اگر می‌خواستیم بایت 0x50 را در slot 1 بخوانیم، کافی بود bankAddr + 0x50 را برگردانیم بدون هیچ آفستی. اما اگر می‌خواستیم بایت 0x4050 را بخوانیم، یعنی می‌گوییم می‌خواهیم بایت 0x50 از slot 2 را بخوانیم؛ برای همین 0x4000 از آدرس بانک کم می‌شود. یک مثال دیگر: برای خواندن بایت 0xA از slot 3 آدرس 0x800A است. پس صفحهٔ درست را با addr + (0x4000 * m_ThirdBankPage) می‌گیریم تا نقطهٔ شروع آن صفحه به‌دست آید. آدرس 0x800A است؛ بخش 0x8000 آن برای تعیین slot استفاده شده و از آنجا می‌توانیم صفحه (bankaddr) را تعیین کنیم؛ بعد باید مشخص کنیم کدام بایت از این صفحه ارجاع شده. جواب 0x800A - 0x8000 یعنی 0xA است. به همین دلیل از آفست استفاده می‌شود.

با این روش هر وقت بازی نیاز به خواندن از ROM داشته باشد، همیشه دادهٔ درست از صفحهٔ فعلی در slot مربوطه برمی‌گردد. اگر خواندن خارج از ناحیهٔ slot ها (0xC000-0xFFFF) باشد، از فضای آدرس z80 (حافظهٔ داخلی) برمی‌گردد نه از حافظهٔ کارتریج. همچنین می‌بینید هر وقت از slot 3 می‌خوانم بررسی می‌کنم که از ROM (حافظهٔ کارتریج) بخوانم یا بانک RAM.

Z80

اطلاعات Z80

Z80 یک ریزپردازندهٔ ۸ بیتی است که در بسیاری از سیستم‌های بازی ویدیویی اولیه (و خیلی سیستم‌های دیگر) استفاده می‌شود. هشت ثبات استاندارد، ۸ ثبات سایه (shadow)، ۲ ثبات اندیس، یک ثبات تازه‌سازی (refresh) و یک ثبات بردار وقفه دارد. همچنین یک پشته، شمارندهٔ برنامه و ۸ پرچم دارد (فقط ۶ تای آن در Z80 مستر سیستم استفاده می‌شود).

ثبات‌ها

۸ ثبات استاندارد A,B,C,D,E,F,H,L نام دارند. همه ۸ بیتی‌اند و کاربردهای مختلفی دارند:

textA: انباشتگر (Accumulator)
B: همه‌منظوره
C: همه‌منظوره
D: همه‌منظوره
E: همه‌منظوره
F: ثبات پرچم
H: ثبات آدرس
L: ثبات آدرس

اما این ثبات‌ها می‌توانند جفت شوند تا ۴ مجموعه ثبات ۱۶ بیتی بسازند: AF، BC، DE و HL. استفاده از H و L به‌صورت جفت رایج‌تر از جداگانه است؛ چون فضای آدرس z80 ۱۶ بیتی است.

هرچند این ثبات‌ها کاربردهای مختلفی دارند، لازم نیست نگران استفاده‌شان باشیم؛ چون این ROM است که از آن‌ها استفاده می‌کند. فقط باید بدانیم کدام‌یک استفاده می‌شود و دستورالعمل‌های z80 این را به ما می‌گویند. تنها ثباتی که باید با آن کار کنیم ثبات پرچم است. هنگام شبیه‌سازی دستورالعمل‌های z80 باید بررسی کنیم دستورالعمل کدام پرچم‌ها را (اگر اصلاً) تحت تأثیر قرار می‌دهد و ثبات پرچم را مطابق آن تنظیم کنیم.

همچنین ۸ ثبات سایه به نام A',B',C',D',E',F',H',L' وجود دارد. آن‌ها هم می‌توانند جفت شوند: AF',BC',DE',HL'. هیچ دستورالعمل z80 نمی‌تواند مستقیم آن‌ها را تغییر دهد؛ کارشان تعویض با ثبات‌های استاندارد متناظرشان است. مثلاً اگر مقدار جفت ثبات AF برابر 0xABCD و جفت AF' برابر 0x1234 باشد، با یک دستورالعمل تعویض (exchange) مقادیر جابه‌جا می‌شوند: AF برابر 0x1234 و AF' برابر 0xABCD. برنامه‌نویس با دستورالعمل‌های Z80 از ثبات‌های AF استفاده می‌کند؛ پس مقدار AF دیگر 0x1234 نیست و بعد می‌تواند ثبات‌ها را دوباره تعویض کند تا AF به مقدار اصلی‌اش 0xABCD برگردد. باز هم لازم نیست نگران جزئیات استفاده از این ثبات‌های سایه باشید؛ فقط مطمئن شوید دستورالعمل‌های تعویض را درست شبیه‌سازی می‌کنید.

ثبات تازه‌سازی (refresh) شمارنده‌ای است که هر بار اپکدی واکشی می‌شود (شامل پیشوندهای اپکد که بعداً توضیح داده می‌شود) یک واحد افزایش می‌یابد. کار این ثبات معمولاً تولید اعداد تصادفی است.

ثبات وقفه (interrupt register) با حالت وقفهٔ 2 کار می‌کند که بعداً توضیح داده می‌شود در SMS استفاده نمی‌شود؛ پس نیازی به شبیه‌سازی آن نیست.

دو ثبات اندیس IX و IY با دو پیشوند اپکد استفاده می‌شوند (بعداً توضیح داده می‌شود) که در دستورالعمل‌های استفاده‌کننده از ثبات‌های HL، جایگزین H و L می‌شوند. مثلاً ADD HL,HL با یک پیشوند اپکد ADD IX,IX و با پیشوند دیگر ADD IY,IY می‌شود. وقتی دستورالعمل‌ای از HL برای آدرس حافظه استفاده می‌کند (با (HL) نمایش داده می‌شود)، یک آفست ۸ بیتی فوری به ثبات‌های IX و IY اضافه می‌شود. این همه بعداً توضیح داده می‌شود.

پرچم‌ها

هر بیت در ثبات پرچم ۸ بیتی (به‌جز بیت‌های 5 و 3 که استفاده نمی‌شوند) یک پرچم را نشان می‌دهد:

textBit 7 = (S) پرچم علامت (Sign)
Bit 6 = (Z) پرچم صفر (Zero)
Bit 5 = استفاده نمی‌شود
Bit 4 = (H) پرچم نقلی نیمه (Half Carry)
Bit 3 = استفاده نمی‌شود
Bit 2 = (P/V) پرچم برابری یا سرریز (Parity/Overflow)
Bit 1 = (N) پرچم تفریق (Subtract)
Bit 0 = (C) پرچم نقلی (Carry)
  • پرچم علامت: کپی سادهٔ بیت 7 از نتیجهٔ یک دستورالعمل ریاضی Z80 است. اما با بعضی دستورالعمل‌های ۱۶ بیتی کپی بیت 15 از نتیجهٔ عملیات است.
  • پرچم صفر: وقتی نتیجهٔ یک عملیات صفر باشد تنظیم می‌شود.
  • پرچم نقلی نیمه: اگر یک عملیات تفریق از بیت 4 به بیت 3 نقلی انجام دهد تنظیم می‌شود (یا در عملیات ۱۶ بیتی از بیت 12 به 11). در عملیات جمع اگر از بیت 3 به 4 نقلی باشد تنظیم می‌شود (یا در جمع ۱۶ بیتی از 11 به 12).
  • پرچم برابری یا سرریز: دو معنا دارد. بعضی دستورالعمل‌ها از پرچم برابری استفاده می‌کنند؛ یعنی اگر نتیجهٔ عملیات تعداد زوجی بیت روشن داشته باشد تنظیم می‌شود. پرچم سرریز را بعضی دستورالعمل‌ها استفاده می‌کنند وقتی متمم دو (2's complement) نتیجه در ثبات جا نشود.
  • پرچم تفریق: فقط وقتی تنظیم می‌شود که دستورالعمل یک تفریق باشد.
  • پرچم نقلی: وقتی دستورالعمل از حد بالایی یا پایینی‌اش سرریز کند تنظیم می‌شود.

نحوهٔ شبیه‌سازی تنظیم بعضی از این پرچم‌ها را هنگام نمایش مثال‌های شبیه‌سازی اپکد در ادامه می‌بینید.

شمارندهٔ برنامه و اشاره‌گر پشته

شمارندهٔ برنامه به آدرس اپکد بعدی برای اجرا در حافظه اشاره می‌کند. اشاره‌گر پشته به فضای آدرس بعدی اشاره می‌کند که مقداری که به پشته اضافه می‌شود آنجا ذخیره می‌شود. پشته در فضای آدرس رو به پایین کار می‌کند و به آدرس 0xDFF0 مقداردهی می‌شود؛ پس اگر مقداری روی پشته push شود، به همین آدرس اضافه می‌شود و اشاره‌گر پشته به 0xDFEF کاهش می‌یابد. پاپ‌کردن مقادیر از پشته، اشاره‌گر پشته را افزایش می‌دهد و مقدار موجود در موقعیت جدید را برمی‌گرداند.

چون فضای آدرس z80 برابر 0x10000 (0x0-0xFFFF) است، هم شمارندهٔ برنامه و هم اشاره‌گر پشته باید اندازهٔ WORD داشته باشند.

همان‌طور که اشاره شد، شمارندهٔ برنامه و اشاره‌گر پشته هر دو به اندازهٔ WORD هستند؛ ثبات تازه‌سازی و ثبات وقفه هم همین‌طور. به‌راحتی با اعلام‌های زیر شبیه‌سازی می‌شوند:

cppWORD m_ProgramCounter ;
WORD m_StackPointer ;
WORD m_RegisterR ;
WORD m_RegisterI ;

راه‌های زیادی برای شبیه‌سازی ثبات‌ها در کد وجود دارد. یکی این است که هر جفت ثبات را با یک متغیر کلمه نشان دهیم و تابعی برای گرفتن بایت‌های hi و lo برای ثبات‌های منفرد بسازیم. راه دیگر برعکس است: ۸ متغیر بایتی برای هر ثبات و بعد تابعی برای ترکیب آن‌ها به یک کلمه. اما نویسنده ترجیح می‌دهد با union این کار را کند:

cppunion Register
{
  WORD reg ;
  struct
  {
   BYTE lo ;
   BYTE hi ;
  };
};

Register m_RegisterAF ;
Register m_RegisterBC ;
Register m_RegisterDE ;
Register m_RegisterHL ;
Register m_RegisterAFShadow ;
Register m_RegisterBCShadow ;
Register m_RegisterDEShadow ;
Register m_RegisterHLShadow ;
Register m_RegisterIX ;

هر فیلد یک union همان ناحیهٔ حافظه را اشغال می‌کند. پس اگر m_RegisterAF.reg = 0xAABB کنید، m_RegisterAF.hi برابر 0xAA و m_RegisterAF.lo برابر 0xBB می‌شود. سپس می‌توانید m_RegisterAF.lo = 0xCC بدهید؛ m_RegisterAF.hi همچنان 0xAA می‌ماند اما m_RegisterAF.reg برابر 0xAACC می‌شود. این برای نمایش ثبات‌ها عالی است. شاید بپرسید چرا BYTE lo قبل از BYTE hi اعلام شده؛ به دلیل endianness است و شاید لازم شود hi را قبل از lo اعلام کنید.

دستورالعمل‌ها (Instructions)

همان‌طور که قبلاً اشاره شد، شمارندهٔ برنامه به اپکد بعدی برای اجرا در حافظه اشاره می‌کند. شمارندهٔ برنامه 0x0 مقداردهی می‌شود. SMS اپکد بعدی را از حافظه می‌گیرد، اپکد را اجرا می‌کند و بعد شمارندهٔ برنامه را افزایش می‌دهد تا به اپکد بعدی برای اجرا اشاره کند. اما نویسنده ترجیح می‌دهد این‌طور شبیه‌سازی کند: اپکد بعدی را از حافظه بگیر و بلافاصله شمارنده را قبل از اجرای اپکد افزایش بده. دلیلش این است که دستورالعمل‌های call و jump شمارندهٔ برنامه را تنظیم می‌کنند و نویسنده نمی‌خواهد بعد از تنظیم‌کردن call و jump، شمارندهٔ برنامه دوباره افزایش یابد.

cppint Z80::ExecuteNextInst( )
{
   m_Context.m_OpcodeCycles = 0 ;
   BYTE instruction = ReadMemory(m_InternalMemory[m_Context.m_ProgramCounter]) ;
   m_Context.m_ProgramCounter++ ;
   ExecuteOpcode(instruction) ;
   assert(m_Context.m_OpcodeCycles > 0) ;
   return m_Context.m_OpcodeCycles ;
}

متغیر m_Context فقط یک ساختار بزرگ شامل همهٔ متغیرهایی است که برای شبیه‌سازی Z80 استفاده می‌شود؛ مثل ثبات‌ها، شمارندهٔ برنامه و غیره. همچنین یک int به نام m_OpcodeCycles دارد که به تعداد چرخه‌های ساعت Z80ِ دستورالعمل اجراشده تنظیم می‌شود. assert راه خوبی برای تشخیص اینکه آیا یکی از دستورالعمل‌های شبیه‌سازی‌شده فراموش کرده شمارش چرخه‌اش را تنظیم کند است.

تابع ExecuteOpcode اپکد را به‌عنوان پارامتر می‌گیرد و اپکد z80 را شبیه‌سازی می‌کند. فقط شامل یک دستور switch بزرگ است که جستجو می‌کند اپکد قرار است چه کند و آن را شبیه‌سازی می‌کند. با جدول اپکد که در بخش «منابع» آموزش به آن لینک داده شد، می‌توان این قطعه از رفتار تابع ExecuteOpcode را داد:

cppvoid Z80::ExecuteOpcode(BYTE opcode)
{
   IncrementRegR() ;
   switch (opcode)
   {
     case 0x0:  m_Context.m_OpcodeCycle = 4 ; break ; // no-op
     case 0x8:  Exchange(m_Context.m_RegisterAF.reg, m_Context.m_RegisterAFShadow.reg); break;
     case 0x87: ADD_8BIT(m_Context.m_RegisterAF.hi, m_Context.m_RegisterAF.hi) ; break ;
     case 0xC9: RETURN( ) ; break ;
     case 0xBE: COMPARE(ReadMemory(m_Context.m_RegisterHL.reg)) ; break ;
     case 0xCB: ExecuteCBOpcode( ) ; break ;
     default:   assert(false); break ; // اپکد مدیریت‌نشده
   }
}

این فقط یک قطعه از switch است؛ نسخهٔ واقعی چند صد case دارد. امیدواریم با منبع اپکدهای هگز که اشاره شد همهٔ بلوک switch را بفهمید. همان‌طور که قبلاً اشاره شد، ثبات R هر بار که اپکدی یا پیشوند اپکدی خوانده شود افزایش می‌یابد؛ اما وقتی ۶ بیت پایین ثبات R به 127 برسد، ۶ بیت پایین ثبات R همه 0 می‌شوند.

پیشوندهای اپکد (Opcode Prefixes)

چون اپکدهای Z80 یک بایت‌اند، فقط ۲۵۶ دستورالعمل ممکن وجود دارد. اما توسعه‌دهندگان با پیشوندهای اپکد از این محدودیت رد شدند. اپکد 0xCB یک پیشوند اپکد است؛ یعنی دستورالعمل بعدی از حافظه خوانده می‌شود و این مقدار نمایانگر یک دستورالعمل متفاوت است. مثلاً اگر اپکد 0x8 از حافظه خوانده شود و اجرا شود، این دستورالعمل یعنی «تعویض AF با AFShadow». اما اگر دستورالعمل 0xCB خوانده شود، بلافاصله اپکد دیگری خوانده می‌شود و اگر این اپکد جدید 0x8 بود، دستور تعویض نیست؛ دستور RRC است. به این ترتیب با پیشوند اپکد 0xCB، توسعه‌دهندگان به ۲۵۶ دستورالعمل اضافه دسترسی پیدا کردند؛ چون می‌توانستند مقادیر را دوباره استفاده کنند. به منبع مقادیر هگز اپکدها نگاه کنید: اپکد 0x8 در جدول اول (جدول اپکد استاندارد) یعنی «EX AF,AF'» و در جدول دوم (جدول پیشوند CB) اپکد 0x8 یعنی «RRC b». پس تابع ExecuteCBOpcode که در بلوک switch بالا استفاده شد این‌طور پیاده می‌شود:

cppvoid Z80::ExecuteCBOpcode()
{
   BYTE opcode = ReadMemory(m_InternalMemory[m_Context.m_ProgramCounter]) ;
   m_Context.m_ProgramCounter++;
   IncrementRegR() ;
   switch (opcode)
   {
     case 0x8: RRC(m_Context.m_RegisterB.hi); break ;
     default: assert(false); break ; // اپکد مدیریت‌نشده
   }
}

امیدواریم قطعهٔ کد بالا پیشوندها را روشن کرده باشد. پیشوندهای اپکد بیشتری هم وجود دارند که مثل پیشوند 0xCB رفتار می‌کنند: 0xED، 0xDD و 0xFD. اولی یعنی 0xED اپکدهای منحصربه‌فرد خودش را دارد مثل 0xCB و این‌ها را می‌توانید در همان منبع ببینید. 0xDD و 0xFD کمی عجیب‌اند؛ این پیشوندها دقیقاً مثل اپکد استاندارد رفتار می‌کنند، فقط به‌جای ثبات‌های HL باید از ثبات‌های IX (برای پیشوند 0xDD) و IY (برای پیشوند 0xFD) استفاده کنیم. مثلاً اپکد استاندارد 0x2B یعنی «DEC HL»؛ پس اپکدهای 0xDD 0x2B یعنی «DEC IX». فقط یک نکتهٔ دیگر: اگر اپکد استاندارد به آدرس حافظه‌ای با HL اشاره می‌کرد (می‌توانید بگویید چون اپکد HL را داخل پرانتز نشان می‌دهد مثل (HL))، همان برای IX و IY هم صدق می‌کند اما یک آفست ۸ بیتی به آدرس‌های IX و IY اضافه می‌شود. مثلاً اپکد استاندارد 0xBE یعنی «CP (HL)» در حالی که اپکد پیشوندی 0xFD 0xBE یعنی «CP (IY+offset)». آفست همان بایت بعدی در حافظه است که شمارندهٔ برنامه به آن اشاره می‌کند؛ اما باید به‌عنوان یک بایت علامت‌دار در نظر گرفته شود:

cppvoid Z80::ExecuteDDOpcode()
{
   BYTE opcode = ReadMemory(m_InternalMemory[m_Context.m_ProgramCounter]) ;
   m_Context.m_ProgramCounter++;
   IncrementRegR() ;
   switch (opcode)
   {
     case 0x2B: DEC(m_Context.m_RegisterIX); break;
     case 0xBE: COMPARE(ReadMemory(GetIXIYOffset(m_Context.m_RegisterIX))) ; break ;
     default: assert(false); break ; // اپکد مدیریت‌نشده
   }
}

WORD Z80::GetIXIYAddress(WORD ixiy)
{
   SIGNED_BYTE offset = ReadMemory(m_InternalMemory[m_Context.m_ProgramCounter]) ;
   m_Context.m_ProgramCounter++;
   return ixiy + offset ;
}

همان‌طور که می‌بینید، آرگومان دستور مقایسه، ثبات IX به‌علاوهٔ آفست است (که از تابع GetIXIYAddress گرفته می‌شود) و به‌عنوان آدرس تابع ReadMemory استفاده می‌شود. اگر به پیاده‌سازی اپکد 0xBE نسبت به پیاده‌سازی‌ای که قبلاً در بلوک switch استاندارد دادیم نگاه کنید، امیدواریم منطقی باشد.

البته با همهٔ قاعده‌ها چند استثنا وجود دارد. «JMP (HL)» برای پیشوندهای 0xDD و 0xFD آفست نمی‌گیرد؛ پس «JMP (IX)» و «JMP (IY)» است. همچنین دستور «EX DE,HL» تحت تأثیر پیشوندهای 0xDD و 0xFD قرار نمی‌گیرد (یعنی HL همان HL می‌ماند).

آگاهی از پرچم‌ها (Flag awareness)

چند اپکد وجود دارند که بر اساس وضعیت پرچم فعلی رفتار متفاوتی دارند. مثلاً «JMP z» اگر پرچم z تنظیم شده باشد به آدرس خاصی می‌پرد وگرنه نمی‌پرد. به همین ترتیب «CALL nc» اگر پرچم نقلی تنظیم نشده باشد تابعی را فراخوانی می‌کند وگرنه نه. توجه داشته باشید این دستورالعمل‌ها اگر یک طرف بروند تعداد چرخهٔ ساعت متفاوتی دارند. برای گرفتن تعداد چرخهٔ ساعت اپکدها به T-States مستندات «Z80 info» شان یانگ در بخش منابع نگاه کنید.

همچنین چند دستورالعمل عجیب مثل «JMP m» و «CALL pe» می‌بینید. معنی حروف این‌ها این است:

textm  = پرچم S تنظیم شده است
po = پرچم P/V خاموش است
p  = پرچم S خاموش است
pe = پرچم P/V تنظیم شده است

مثال‌های اپکد

حالا که بلوک‌های switch را راه‌اندازی کردیم، وقت شبیه‌سازی توابعی است که صدا می‌زنند. در بلوک switch اول، تابع EXCHANGE صدا زده می‌شود و پیاده‌سازی‌اش این است:

cppvoid Z80::Exchange(WORD& ex1, WORD& ex2)
{
   WORD temp = ex1 ;
   ex1 = ex2 ;
   ex2 = temp ;
   m_Context.m_OpcodeCycle = 4;
}

تابع Exchange بالا نحوهٔ شبیه‌سازی دستورالعمل‌های تعویض Z80 را نشان می‌دهد؛ هم برای EX AF,AF' و هم سایر دستورالعمل‌های تعویض قابل استفاده است.

تابع بعدی نحوهٔ شبیه‌سازی JR (دستور پرش فوری) را نشان می‌دهد. دو نوع JR وجود دارد: اولی همیشه می‌پرد و دومی فقط در صورت درست‌بودن شرطی می‌پرد. این‌طور شبیه‌سازی می‌کنیم:

cppvoid Z80::CPU_JUMP_IMMEDIATE(bool useCondition, int flag, bool condition)
{
   m_Context.m_OpcodeCycle = 12 ;

   if (!useCondition)
   {
     SIGNED_BYTE n = (SIGNED_BYTE)ReadMemory(m_Context.m_ProgramCounter) ;
     m_Context.m_ProgramCounter += n;
   }
   else if (TestBit(m_Context.m_RegisterAF.lo, flag) == condition)
   {
     SIGNED_BYTE n = (SIGNED_BYTE)ReadMemory(m_Context.m_ProgramCounter) ;
     m_Context.m_ProgramCounter += n ;
   }
   else
   {
     m_Context.m_OpcodeCycle = 7 ;
   }

   m_Context.m_ProgramCounter++ ;
}

پس تابع بالا اگر شرطی استفاده نشود همیشه می‌پرد؛ وگرنه شرط را تست می‌کند (تست اینکه پرچمی تنظیم شده یا نه) و اگر درست بود می‌پرد وگرنه نه. توجه کنید اگر نپرد شمارندهٔ چرخهٔ اپکد کمتر تنظیم می‌شود؛ چون هرگز از حافظه نمی‌خواند که به چرخهٔ ساعت بیشتری نیاز دارد.

مثال بعدی نحوهٔ کار تابع کاهش ۸ بیتی را نشان می‌دهد: ثباتی که به‌عنوان آرگومان داده شده را کاهش می‌دهد و بعد همهٔ پرچم‌ها را تنظیم می‌کند:

cppvoid Z80::CPU_8BIT_DEC(BYTE& reg, int cycles)
{
   m_Context.m_OpcodeCycle = cycles ;

   BYTE before = reg ;

   reg-- ;

   // اگر نتیجه صفر باشد پرچم z را تنظیم کن
   if (reg == 0)
     m_Context.m_RegisterAF.lo = BitSet(m_Context.m_RegisterAF.lo, FLAG_Z) ;
   else
     m_Context.m_RegisterAF.lo = BitReset(m_Context.m_RegisterAF.lo, FLAG_Z) ;

   // اگر نیبل پایین 0 باشد پرچم h را تنظیم کن؛ یعنی از بیت 4 نقلی رخ می‌دهد
   if ((before & 0x0F) == 0)
     m_Context.m_RegisterAF.lo = BitSet(m_Context.m_RegisterAF.lo, FLAG_H) ;
   else
     m_Context.m_RegisterAF.lo = BitReset(m_Context.m_RegisterAF.lo, FLAG_H) ;

   // v محاسبه می‌شود نه p
   if (before == 128)
     m_Context.m_RegisterAF.lo = BitSet(m_Context.m_RegisterAF.lo, FLAG_PV) ;
   else
     m_Context.m_RegisterAF.lo = BitReset(m_Context.m_RegisterAF.lo, FLAG_PV) ;

   // پرچم تفریق را تنظیم کن
   m_Context.m_RegisterAF.lo = BitSet(m_Context.m_RegisterAF.lo, FLAG_N) ;

   // پرچم علامت را به بیت 7 نتیجه تنظیم کن
   if (TestBit(reg,7))
     m_Context.m_RegisterAF.lo = BitSet(m_Context.m_RegisterAF.lo, FLAG_S) ;
   else
     m_Context.m_RegisterAF.lo = BitReset(m_Context.m_RegisterAF.lo, FLAG_S) ;
}

اطلاعات VDP

شبیه‌سازی Texas Instruments TMS9918a در ابتدا می‌تواند ترسناک‌تر از VDP گیم‌بوی باشد؛ چون چیزهای خیلی بیشتری دارد. اما اگر هر بخش VDP را جدا کنید، آنقدرها هم بد نیست. اول با نقشهٔ حافظهٔ VDP شروع می‌کنیم:

text0x0000 - 0x1FFF = پترن‌های اسپرایت/تایل (شماره‌های 0 تا 255)
0x2000 - 0x37FF = پترن‌های اسپرایت/تایل (شماره‌های 256 تا 447)
0x3800 - 0x3EFF = جدول نام‌ها (Name Table)
0x3F00 - 0x3FFF = جدول اطلاعات اسپرایت (Sprite Info Table)

در ابتدا نقشهٔ حافظه ساده به نظر می‌رسد اما یک نکته دارد: جدول نام‌ها و جدول اطلاعات اسپرایت همیشه از آدرس 0x3800 و 0x3F00 شروع نمی‌شوند و قابل تغییرند (بعداً می‌بینیم). همچنین RAM رنگ (CRAM) وجود دارد که می‌تواند دو مجموعه از ۱۶ پالت رنگی را نگه دارد. این اعلام‌های حافظهٔ VDP را می‌دهد:

cppBYTE m_VRAM[0x4000] ;
BYTE m_ColourRam[32] ;

اگر از پایه‌های رندر تایل و اسپرایت مطمئن نیستید، توضیحش واقعاً ساده است. صفحه از «تایل‌هایی» ساخته شده که پس‌زمینه را نشان می‌دهند (مثلاً در سونیک: زمینی که رویش می‌دود، آسمان، درختان نخل و غیره). هر تایل در حافظه از ۶۴ پیکسل ساخته شده؛ ۸ پیکسل افقی و ۸ پیکسل عمودی. برای رسم پس‌زمینه محتوای جدول نام‌ها را می‌خوانید که همهٔ شماره‌های تایل را از چپ به راست و بالا به پایین صفحه می‌دهد. هر شمارهٔ تایل را می‌توان در جدول پترن‌های اسپرایت/تایل جستجو کرد که رنگ هر ۶۴ پیکسل آن تایل را می‌دهد. صفحه همچنین از اسپرایت‌ها ساخته شده که اشیاء فعال‌اند (باز هم با مثال سونیک: سونیک، دشمن‌ها، حلقه‌ها و غیره). اسپرایت‌ها معمولاً روی پس‌زمینه رسم می‌شوند و می‌توانند مثل تایل‌های پس‌زمینه 8x8 باشند یا 16x16. امکان بزرگ‌نمایی اسپرایت‌ها هم هست که اندازه را دو برابر می‌کند؛ 8x8 می‌شود 16x16 و 8x16 می‌شود 32x32. جدول اطلاعات اسپرایت مشخص می‌کند پترن اسپرایتی که به آن اشاره می‌کند کجای صفحه رسم شود. پترن اسپرایت در جدول پترن اسپرایت جستجو می‌شود و مثل پس‌زمینه رسم می‌شود.

VDP ۱۱ ثبات کنترل و یک ثبات وضعیت دارد. ثبات‌های کنترل را بعداً مفصل‌تر بررسی می‌کنیم. ثبات وضعیت یک بایت است اما فقط بیت‌های 5-7 استفاده می‌شوند. چیدمان ثبات وضعیت (معنی‌هایشان را بعداً می‌گوییم):

textBIT 7 = وقفهٔ VSync در انتظار
BIT 6 = سرریز اسپرایت (Sprite Overflow)
BIT 5 = برخورد اسپرایت (Sprite Collision)
BIT 4-0 = استفاده نشده

VDP می‌تواند حالتش عوض شود که نحوهٔ رندر تایل‌ها و اسپرایت‌ها و همچنین تفسیر ثبات وضعیت و ثبات‌های کنترل را تغییر می‌دهد. SMS فقط از حالت 2 و حالت 4 استفاده می‌کند؛ پس فقط دربارهٔ همین دو بحث می‌کنیم. همهٔ بازی‌های SMS از حالت 4 استفاده می‌کنند به‌جز F-16 Fighter که از حالت 2 استفاده می‌کند.

مثل همهٔ سخت‌افزارهای SMS، CPU با VDP از طریق پورت‌ها ارتباط برقرار می‌کند و این پورت‌ها هستند که برنامه‌نویس برای کنترل VDP استفاده می‌کند:

text0x7E = VCounter (فقط‌خواندنی)
0x7F = HCounter (فقط‌خواندنی)
0xBE = پورت داده (خواندنی/نوشتنی)
0xBF = پورت کنترل (خواندنی/نوشتنی)

اگر ROM تلاش کند در پورت‌های 0x7E-0x7F بنویسد، در واقع با تراشهٔ صدا ارتباط برقرار می‌کند نه VDP. هنگام خواندن از پورت‌های 0x7E-0x7F، VDP است نه تراشهٔ صدا. اگر از پورت 0x7E بخوانید، vcounter از VDP برمی‌گردد (یعنی خط فعلی که از قاب فعال یا غیرفعال در حال رسم است). خواندن پورت 0x7F برمی‌گرداند کدام پیکسل از خطِ در حال رسم (همان vcounter) در حال رسم است. دو پورت دیگر (داده و کنترل) را بعداً بحث می‌کنیم.

وقفه‌ها (Interrupts)

صفحه خودش را با نرخ 50Hz یا 60Hz (بسته به PAL یا NTSC بودن، که بعداً بحث می‌شود) رسم می‌کند؛ یعنی صفحه ۵۰ یا ۶۰ بار در ثانیه دوباره رسم می‌شود. هر کدام از این بازرسم‌ها یک فریم نامیده می‌شود. هر فریم یک دورهٔ فعال و یک دورهٔ غیرفعال دارد. دورهٔ فعال وقتی است که VDP واقعاً یکی از خطوط قابل‌مشاهدهٔ صفحه را رسم می‌کند و دورهٔ غیرفعال وقتی است که همهٔ خطوط قابل‌مشاهدهٔ صفحه را رسم کرده. دورهٔ غیرفعال برای برنامه‌نویس‌ها خیلی مهم است؛ چون می‌توانند VDP را طوری برنامه‌ریزی کنند که در دورهٔ فعال امکان‌پذیر نبود (مثل تغییر مقدار اسکرول عمودی، که بعداً بحث می‌شود). پس هر بار VDP از دورهٔ فعال خارج و وارد دورهٔ غیرفعال می‌شود، تلاش می‌کند وقفه‌ای سیگنال کند تا ROM از این موضوع آگاه شود. همان‌طور که در بخش وقفه‌ها می‌بینید، وقفه‌های VDP را می‌توان نادیده گرفت. وقتی VDP وارد دورهٔ نمایش غیرفعال می‌شود، بیت 7 از ثبات وضعیت را تنظیم می‌کند تا نشان دهد وقفهٔ VSync در انتظار است. اما وقفهٔ vsync فقط در صورتی درخواست می‌شود که بیت 7 از ثبات وضعیت تنظیم شده باشد و بیت 5 از ثبات کنترل 1 تنظیم شده باشد (این پرچمی است که برنامه‌نویس برای فعال‌سازی وقفه‌های vertical sync تنظیم می‌کند، بعداً بحث می‌شود). اگر هر دو پرچم تنظیم شده باشند، VDP وقفهٔ vsync درخواست می‌کند و CPU یا به آن پاسخ می‌دهد یا نادیده‌اش می‌کند.

یک وقفهٔ VDP دیگر به نام وقفهٔ خط (line interrupt) وجود دارد. این مقداری است که برنامه‌نویس تنظیم می‌کند و در طول دورهٔ نمایش فعال (و اولین خط دورهٔ نمایش غیرفعال) هر بار VDP به خط اسکن جدیدی می‌رود یکی کم می‌شود؛ تا برنامه‌نویس از زمان شروع رسم یک خط اسکن خاص مطلع شود. وقتی شمارندهٔ خط به زیر صفر برود، VDP وقفه درخواست می‌کند (فقط اگر وقفه‌های خط با تنظیم بیت 4 از ثبات کنترل 0 فعال شده باشند) و شمارندهٔ خط به مقدار ثبات 10 بازنشانی می‌شود. اگر CPU تصمیم بگیرد وقفهٔ VDP را نادیده بگیرد، درخواست از بین می‌رود؛ پس این وقفه یا فوراً مدیریت می‌شود یا اصلاً نه. مقدار شمارندهٔ خط به مقدار ثبات 10 تنظیم می‌شود؛ اما فقط وقتی خط اسکن فعلی از اولین خط دورهٔ نمایش غیرفعال گذشته باشد.

پیاده‌سازی هر دو وقفه را در بخش «چرخهٔ به‌روزرسانی» همین صفحه می‌بینیم.

نواحی (Regions)

دو ناحیهٔ متفاوت وجود دارد: PAL و NTSC. در بقیهٔ این سند با NTSC کار می‌کنیم؛ اما این بخش جزئیات هر دو را می‌دهد. همان‌طور که توضیح داده شد، هر فریم VDP از یک بخش فعال و یک بخش غیرفعال تشکیل شده. مجموع فعال+غیرفعال به ما تعداد کل خطوط اسکن هر فریم را می‌دهد. PAL 313 خط اسکن و NTSC 262 خط دارد. به‌خاطر این تفاوت، تعداد فریم‌های رسم‌شده در هر ثانیه در NTSC بیشتر از PAL است. NTSC می‌تواند ۶۰ فریم در ثانیه و PAL ۵۰ فریم رسم کند. چون هر دو ناحیه تعداد خطوط اسکن متفاوتی دارند، تعداد خطوط دورهٔ فعال و دورهٔ غیرفعال هم برای هر ناحیه فرق می‌کند. نه فقط این، هر ناحیه می‌تواند وضوح صفحه‌اش را تغییر دهد (یعنی تعداد خطوط اسکن فعال صفحه تغییر می‌کند اما نه تعداد کل خطوط). سه وضوح صفحهٔ مختلف را «کوچک» (small)، «متوسط» (medium) و «بزرگ» (large) می‌نامیم. پیش‌فرض استفاده‌شده توسط اکثر بازی‌ها «کوچک» است.

تیزبین‌ها متوجه شده‌اند اگر خواندن پورت 0x7E یک بایت برمی‌گرداند که vcounter است اما تعداد کل خطوط اسکن 262 یا 313 است (بسته به ناحیه)، پس همهٔ خطوط اسکن را نمی‌توان برگرداند؛ چون حداکثر مقدار یک بایت بدون علامت 255 است. مثلاً اگر vcounter برابر 260 باشد، نمی‌توان در محدودهٔ بایت نمایشش داد. پاسخ خیلی ساده است: هرچند VDP از 262 یا 313 خط اسکن عبور می‌کند، فقط با تکرار برخی خطوط اسکن در هر فریم می‌تواند. یعنی vcounter از 0 تا 255 می‌رود اما بعضی از این مقادیر تکرار می‌شوند و مجموع 262 یا 313 می‌شود. برای کمک به توضیح، ببینیم وضوح کوچک ntsc چگونه شکسته می‌شود:

۱۱ ثبات کنترل وجود دارد و فقط‌نوشتنی‌اند. در بخش بعدی می‌بینید داده چگونه به VRAM، CRAM و ثبات‌های کنترل نوشته می‌شود. هر ثبات یک بایت است و همه کاربردهای متفاوتی دارند. اکثر بیت‌های ثبات استفاده نمی‌شوند؛ پس فقط بیت‌های استفاده‌شده هر ثبات و کارشان را نشان می‌دهیم.

پورت‌ها (Ports)

داده باید در سه جا به VDP نوشته شود: VRAM، CRAM و ثبات‌های VDP. دو پورت برای نوشتن داده به VDP استفاده می‌شود. پورت 0xBE جایی است که دادهٔ ذخیره‌شونده در VRAM، CRAM یا ثبات‌های VDP نوشته می‌شود. پورت 0xBF مشخص می‌کند داده‌ای که به پورت 0xBE نوشته می‌شود برای کدام‌یک از این سه ناحیهٔ حافظه در نظر گرفته شده.

طرز کار پورت کنترل (0xBF): برنامه‌نویس دو بایت داده به این پورت می‌نویسد که به آن کلمهٔ کنترل (control word) می‌گویند. در کلمهٔ کنترل، بیت‌های 15-14 مشخص می‌کنند داده‌ای که به پورت 0xBE نوشته می‌شود برای کجاست؛ این کد کلمهٔ کنترل (control word code) نامیده می‌شود. بیت‌های 13-0 بر اساس کد کلمهٔ کنترل تفسیر می‌شوند. مقادیر کد کلمهٔ کنترل:

text0 = یک بایت داده از ثبات آدرس بخوان و در بافر خواندن ذخیره کن. ثبات آدرس را افزایش بده.
    با این کد، هر نوشتنی در پورت 0xBE به VRAM در آدرسِ اشاره‌شده توسط ثبات آدرسِ تازه‌افزایش‌یافته می‌رود
1 = نوشتن در پورت 0xBE به VRAM در آدرسِ اشاره‌شده توسط ثبات آدرس می‌رود
2 = نوشتن در پورت 0xBE به VRAM در آدرسِ اشاره‌شده توسط ثبات آدرس می‌رود.
    اما این کد داده را به ثبات‌های VDP هم می‌نویسد
3 = نوشتن در پورت 0xBE به CRAM می‌رود

می‌بینید که از ثبات آدرس (address register) نام بردم. ثبات آدرس، بیت‌های 13-0 از ثبات کنترل است. ثبات آدرس به آدرس حافظه در VRAM اشاره می‌کند که نوشتن داده در پورت 0xBE آنجا نوشته شود. از نقشهٔ حافظه می‌دانیم VRAM برابر 0x4000 بایت است؛ یعنی ثبات آدرس وقتی از 0x3FFF رد شود می‌پیچد. بافر خواندن (read buffer) یک متغیر بایتی است که وقتی ROM از پورت 0xBE می‌خواند برگردانده می‌شود. CRAM مثل VRAM کار می‌کند فقط با این تفاوت که فقط ۳۲ بایت است؛ پس فقط از بیت‌های 5-0 ثبات آدرس به‌عنوان اشاره‌گر CRAM استفاده می‌کنید. همان‌طور که اشاره کردم، کد کلمهٔ کنترل 2 همچنین یکی از ثبات‌های VDP را همان‌جا به‌روزرسانی می‌کند: بیت‌های 11-8 ثبات VDP را برای به‌روزرسانی می‌دهند و بیت‌های 7-0 بایتی را که باید ثبات با آن به‌روزرسانی شود.

نکته‌ای که قبل از نشان‌دادن پیاده‌سازی نوشتن پورت 0xBF باید روشن کنم این است که کلمهٔ کنترل چگونه به‌روزرسانی می‌شود. چون کلمهٔ کنترل ۲ بایت است و فقط می‌توانید هر بار ۱ بایت بنویسید، کلمهٔ کنترل در دو مرحله به‌روزرسانی می‌شود. اولین بایت نوشته‌شده کم‌ارزش‌ترین بایت کلمهٔ کنترل (بیت‌های 7-0) را به‌روزرسانی می‌کند و دومین بایت نوشته‌شده پرارزش‌ترین بایت (بیت‌های 15-8) را. فقط وقتی بایت دوم نوشته می‌شود روی کد کلمهٔ کنترل اقدام می‌شود. اگر بایت اول نوشته شود ولی بایت دوم نه، کلمهٔ کنترل ترکیبی از بایت جدید و بایت قدیمی است. همان‌طور که بعداً می‌بینید، امکان بازنشانی کلمهٔ کنترل هم هست تا بایت بعدی بازنویسی‌شده اولین بایت باشد، حتی اگر قبلاً منتظر نوشته‌شدن بایت دوم بود:

   if (m_IsSecondControlWrite)
   {
     // بایت بالا را به‌روزرسانی کن
     m_ControlWord &= 0xFF ;
     m_ControlWord |= data << 8 ;
     m_IsSecondControlWrite = false ;

     // روی کد کنترل اقدام کن
     switch (GetCodeRegister())
     {
       case 0: m_ReadBuffer = m_VRAM[GetAddressRegister()];
         IncrementAddress(); break ;
       case 2: SetRegData() ; break ;
       default: break ;
     }
   }
   else
   {
     // بایت پایین را به‌روزرسانی کن
     m_IsSecondControlWrite = true ;
     m_ControlWord &= 0xFF00 ;
     m_ControlWord |= data ;
   }
}

void TMS9918A::IncrementAddress( )
{
   // ثبات آدرس را در 0x3FFF بپیچان
   if (GetAddressRegister() == 0x3FFF)
     m_ControlWord &= 0xC000 ; // کد کلمهٔ کنترل را بدون تغییر نگه دار
   else
     m_ControlWord++ ;
}

WORD TMS9918A::GetAddressRegister( ) const
{
   return m_ControlWord & 0x3FFF ;
}

void TMS9918A::SetRegData( )
{
   // دادهٔ ثبات جدید بایت پایین است
   BYTE data = m_ControlWord & 0xFF ;
   // ثبات ۴ بیت پایین بایت بالا است
   BYTE reg = m_ControlWord >> 8 ;
   reg &= 0xF ;

   if (reg > 11)
     return ;

   m_VDPRegisters[reg] = data ;

   // آیا این نوشتن ثبات، وقفه‌های vsync را فعال می‌کند؟
   // اگر بله، آیا وقفه‌ای در انتظار داریم؟
   if (reg == 1)
   {
     if (TestBit(m_Status,7) && IsRegBitSet(1,5))
       m_RequestInterupt = true ;
   }
}

BYTE TMS9918A::GetCodeRegister() const
{
   WORD w = m_ControlWord >> 14 ;
   return (BYTE)w ;
}

امیدوارم چیز ترسناکی در توابع بالا نباشد. یک توضیح سریع دربارهٔ WriteVDPAddress: این تابعی است که نوشتن یک بایت داده در 0xBF به آن ختم می‌شود. بایت نوشته‌شده یا بایت پایین کلمهٔ کنترل را به‌روزرسانی می‌کند یا بایت بالا، بسته به bool م.اگر بایت بالا نوشته شود، این بایت کد کلمهٔ کنترل جدید را هم دارد و بسته به کد ممکن است اقدام لازم باشد. اگر کد کنترل 0 باشد، بافر خواندن باید با محتوای VRAM که ثبات آدرس به آن اشاره می‌کند به‌روزرسانی شود و بعد ثبات آدرس افزایش یابد. اگر کد کلمهٔ کنترل 2 باشد، باید یکی از مقادیر ثبات VDP به‌روزرسانی شود. اگر کلمهٔ کنترل 1 یا 3 باشد نیازی به اقدام نیست؛ چون ثبات آدرس به‌روز است و به محل صحیح حافظه در VRAM یا CRAM اشاره می‌کند و نوشتن در پورت 0xBE در واقع داده را به VRAM یا CRAM می‌نویسد.

بحث شبیه‌سازی پورت 0xBF (پورت کنترل) تمام شد و حالا باید توضیح دهم پورت 0xBE (پورت داده) چگونه شبیه‌سازی می‌شود. این پورت مقادیری را به VRAM یا CRAM می‌نویسد، بسته به کد کلمهٔ کنترل. شبیه‌سازی‌اش واقعاً خیلی ساده است؛ چون بر اساس کد کلمهٔ کنترل می‌دانیم به VRAM بنویسیم یا CRAM و بر اساس آدرس کلمهٔ کنترل می‌دانیم مقادیر را کجا بنویسیم. بعد از اینکه بایتی از طریق پورت 0xBE در حافظه نوشته شد، ثبات آدرس کنترل افزایش می‌یابد. این برای برنامه‌نویس خیلی مفید است؛ چون می‌تواند کلی داده در حافظه بنویسد بدون اینکه مدام آدرس کلمهٔ کنترل را برای اشاره به ناحیهٔ بعدی حافظه به‌روزرسانی کند. وقتی مقداری در حافظه نوشته می‌شود، بافر خواندن هم به مقدار نوشته‌شده تنظیم می‌شود. نوشتن در پورت داده همچنین پرچم m_IsSecondControlWrite را به false بازنشانی می‌کند تا هر نوشتن بعدی در پورت کنترل، کلمهٔ کنترل را از کم‌ارزش‌ترین بایت شروع به به‌روزرسانی کند:

cppvoid TMS9918A::WriteDataPort(BYTE data)
{
   m_IsSecondControlWrite = false ;
   BYTE code = GetCodeRegister( ) ;

   switch (code)
   {
     case 0: m_VRAM[ GetAddressRegister() ] = data ; break ;
     case 1: m_VRAM[ GetAddressRegister() ] = data ; break ;
     case 2: m_VRAM[ GetAddressRegister() ] = data ; break ;
     case 3: m_CRAM[ GetAddressRegister() & 31 ] = data ; break ;
   }

   m_ReadBuffer = data ;

   IncrementAddress( ) ;
}

شبیه‌سازی پورت داده واقعاً خیلی ساده است. اگر می‌پرسید چرا نوشتن در CRAM ثبات آدرس را با 31 AND می‌کند، چون فقط ۵ بیت اول ثبات آدرس برای CRAM استفاده می‌شود؛ چون CRAM فقط ۳۲ بایت است.

حالا می‌دانیم وقتی پورت‌های VDP نوشته می‌شوند چه اتفاقی می‌افتد؛ اما وقتی خوانده می‌شوند چه؟ خواندن پورت داده (0xBE) بافر خواندن را برمی‌گرداند. بعد مقداری جدید به بافر خواندن اختصاص می‌دهد که آدرسِ افزایش‌یافتهٔ آدرس کلمهٔ کنترل است. دلیل افزایش هنگام خواندن همان دلیل افزایش هنگام نوشتن است: تا برنامه‌نویس مجبور نباشد مدام کلمهٔ کنترل را برای اشاره به مکان بعدی حافظه به‌روزرسانی کند. خواندن پورت کنترل (0xBF) ثبات وضعیت را برمی‌گرداند که قبلاً درباره‌اش بحث شد. فقط بیت‌های 7-5 در ثبات وضعیت استفاده می‌شوند و این‌ها همه هنگام خواندن پورت کنترل بازنشانی می‌شوند، به‌جز حالت VDP 2 که فقط بیت‌های 7 و 5 بازنشانی می‌شوند. علاوه بر بازنشانی ثبات وضعیت هنگام خواندن پورت کنترل، m_IsSecondControlWrite و وقفه‌ها هم بازنشانی می‌شوند:

cppBYTE TMS9918A::GetStatus( )
{
   BYTE res = m_Status ;
   if (GetVDPMode() == 2)
   {
     m_Status &= 0x2F; // بیت‌های 7 و 5 را خاموش کن
   }
   else
   {
     m_Status &= 0x1F; // ۳ بیت بالا را خاموش کن
   }
   m_IsSecondControlWrite = false ;
   m_RequestInterupt = false ;

   return res ;
}

BYTE TMS9918A::ReadDataPort( )
{
   m_IsSecondControlWrite = false ;

   BYTE res = m_ReadBuffer ;

   m_ReadBuffer = m_VRAM[ GetAddressRegister() ] ;

   IncrementAddress( ) ;

   return res ;
}

زمان‌بندی (Timing)

VDP نصف سرعت ساعت ماشین است. برای رفتن به خط اسکن بعدی باید بدانیم هر خط اسکن چقدر طول می‌کشد. این‌جاست که باید شمارندهٔ افقی (hcounter) را شبیه‌سازی کنیم. hcounter با همان نرخ ساعت ماشین افزایش می‌یابد؛ یعنی به ازای هر چرخهٔ VDP دو بار افزایش می‌یابد. hcounter قبل از رفتن به خط اسکن بعدی ۶۸۴ چرخهٔ ماشین طول می‌کشد. چون می‌دانیم هر خط اسکن چقدر طول می‌کشد و چند خط اسکن در یک فریم وجود دارد، گرفتن زمان‌بندی VDP نسبتاً ساده است. فقط باید مطمئن شویم در زمان درست به خط اسکن بعدی می‌رویم و تعداد صحیح خطوط اسکن را رسم می‌کنیم. وقتی فریم رسم شد، فریم بعدی را فقط وقتی زمان لازم گذشته رسم می‌کنیم (1/50 ثانیه برای PAL با 50Hz و 1/60 ثانیه برای NTSC با 60Hz)؛ اما این چیزی است که قبلاً در چرخهٔ به‌روزرسانی اصلی شبیه‌سازی (فصل «سخت‌افزار») شبیه‌سازی کردیم. در بخش بعدی نحوهٔ شبیه‌سازی این را همراه با هر چیز دیگری که به‌روزرسانی VDP باید انجام دهد نشان می‌دهیم.

چرخهٔ به‌روزرسانی (Update Cycle)

cppvoid TMS9918A::Update(float nextCycle)
{
   m_RequestInterupt = false ;
   WORD hcount = m_HCounter ;
   bool nextline = false ;
   m_IsVBlank = false ;
   m_Refresh = false ;

   m_RunningCycles += nextCycle ;

   // همه‌چیز بعد از اعشار را نادیده بگیر
   int clockInfo = floorf(m_RunningCycles) ;

   // چرخهٔ ماشین دو برابر سرعت vdp است و این همان سرعتی است
   // که hcounter با آن افزایش می‌یابد
   int cycles = clockInfo * 2 ;

   // آیا از این خط اسکن به خط بعدی می‌رویم؟
   if ((hcount + cycles) > 684)
     nextline = true ;

   // اگر خط اسکن جدیدی شروع می‌کنیم hcounter را بازنشانی کن
   m_HCounter = (m_HCounter + cycles) % 685 ;

   // داریم به خط اسکن بعدی می‌رویم
   if (nextline)
   {
     // خط اسکن فعلی را ذخیره کن
     BYTE vcount = m_VCounter ;
     m_VCounter++ ; // به خط اسکن بعدی برو

     // آیا به انتهای تازه‌سازی عمودی رسیده‌ایم؟
     // اگر بله، فریم جدیدی از خط اسکن 0 شروع می‌کنیم
     if (vcount == 255)
     {
       m_VCounter = 0 ;
       m_VCounterFirst = true ;
       Render( ) ;
       m_Refresh = true ;
     }
     // وقت پرش vcounter به عقب است؟
     else if ((vcount == GetVJump()) && m_VCounterFirst)
     {
       m_VCounterFirst = false ;
       m_VCounter = GetVJumpTo() ;
     }

     // تازه می‌خواهیم وارد تازه‌سازی عمودی شویم؟
     else if (m_VCounter == m_Height)
     {
       m_IsVBlank = true ;
       m_Status = BitSet(m_Status, 7) ; // وقفه در انتظار
     }

     if (m_VCounter >= m_Height)
     {
       // وقفهٔ خط را تا وقتی از اولین خط دورهٔ
       // نمایش غیرفعال رد نشده‌ایم دوباره بارگذاری نکن
       if (m_VCounter != m_Height)
         m_LineInterupt = m_VDPRegisters[0xA] ;

       // حالا می‌توانیم مقدار اسکرول عمودی را به‌روزرسانی کنیم
       m_VScroll = m_VDPRegisters[0x9] ;
       BYTE mode = GetVDPMode( ) ;

       // آیا وضوح صفحه را عوض می‌کنیم؟
       if (mode == 11)
         m_Height = NUM_RES_VERT_MED ;
       else if (mode == 14)
         m_Height = NUM_RES_VERT_HIGH ;
       else
         m_Height = NUM_RES_VERTICAL ;
     }

     // اگر در نمایش فعال هستیم خط اسکن بعدی را رسم کن
     if (m_VCounter < m_Height)
     {
       m_ScreenDisabled = !IsRegBitSet(1,6) ;
       Render( ) ;
     }

     // شمارندهٔ وقفهٔ خط را در طول دورهٔ فعال کم کن،
     // شامل اولین خط دورهٔ نمایش غیرفعال
     if (m_VCounter <= m_Height)
     {
       bool underflow = false ;
       if (m_LineInterupt == 0)
       {
         underflow = true ;
       }
       m_LineInterupt-- ;

       // قرار است سرریز شود
       if (underflow)
       {
         m_LineInterupt = m_VDPRegisters[0xA] ;
         if (IsRegBitSet(0,4))
           m_RequestInterupt = true ;
       }
     }
   }
   // آیا می‌خواهیم وقفه سیگنال کنیم؟
   if (TestBit(m_Status,7) && IsRegBitSet(1,5))
     m_RequestInterupt = true ;
}

اول ترسناک به نظر می‌رسد اما مثل همه‌چیز وقتی به قطعات کوچک‌تر بشکنیدش خیلی قابل‌مدیریت‌تر می‌شود. همهٔ کد بالا قبل از خط «if (nextline)» زمان‌بندی vdp را کنترل می‌کند. hcounter را با دو برابر سرعت ساعت vdp حرکت می‌دهد و وقتی از مقدار 684 رد شد به خط بعدی می‌رود. وقتی از این مقدار رد شد به خط اسکن بعدی می‌رود. متغیر m_RunningCycles یک float است تا هنگام تبدیل از چرخه‌های ماشین به چرخه‌های ساعت vdp دقت را از دست ندهیم. هرچند هنگام تعیین تعداد چرخه‌هایی که باید به hcounter اضافه شود اعشار را نادیده می‌گیریم، اما باز هم آن‌ها را برای به‌روزرسانی بعدی نگه می‌داریم تا دقت از بین نرود.

هنگام رفتن به خط اسکن بعدی، اولین کاری که باید بکنیم افزایش vcounter برای نشان‌دادن خط اسکنِ در حال رسم است. اگر vcounter قبلی 255 (0xFF) بود، به انتهای دورهٔ نمایش غیرفعال رسیده‌ایم و آمادهٔ رسم اولین خط دورهٔ نمایش فعال هستیم.

همان‌طور که در بخش «نواحی» بحث شد، برای جا دادن ۲۶۲ خط اسکن در یک متغیر بایتی، vcounter باید وقتی به خط اسکن خاصی رسید به عقب بپرد؛ بخش بعدی همین کار را می‌کند. مثلاً وضوح کوچک استاندارد NTSC بعد از رسم خط اسکن 0xDA به 0xD5 برمی‌گردد و بعد تا 255 ادامه می‌دهد. پرچم m_VCounterFirst هم همین کار را می‌کند تا هر بار به 0xDA رسید دوباره به 0xD5 برنگردد؛ چون فقط یک بار در هر فریم می‌خواهیم این پرش انجام شود.

هر بار که اولین خط دورهٔ نمایش غیرفعال را شروع می‌کنیم (یعنی همهٔ خطوط اسکن فعال که مقدار m_Height است را رسم کرده‌ایم)، باید بیت 7 از ثبات وضعیت را تنظیم کنیم تا علامت دهد وقفه‌ای در انتظار داریم.

وقتی در دورهٔ نمایش غیرفعال هستیم (m_VCounter >= m_Height) مجازیم مقدار اسکرول عمودی را به محتوای ثبات 9 بازنشانی کنیم (بعداً بحث می‌شود) و همچنین وضوح صفحه را به بزرگ، متوسط یا کوچک تغییر دهیم. در بخش بعدی بحث می‌شود حالت vdp را چگونه تشخیص دهیم.

بدیهی است اگر هنوز در دورهٔ نمایش فعال هستیم (m_VCounter < m_Height)، می‌خواهیم خط اسکن بعدی را رسم کنیم اما فقط اگر صفحه فعال باشد.

در نهایت می‌خواهیم هر بار که در دورهٔ نمایش فعال (شامل اولین خط دورهٔ نمایش غیرفعال) به خط جدیدی می‌رویم، شمارندهٔ خط را کم کنیم و اگر سرریز شد و وقفه‌های خط فعال بودند وقفه درخواست کنیم.

بعد باقی می‌ماند بررسی اینکه آیا وقفهٔ vdp درخواست شود یا نه.

حالت‌های نمایش (Display Modes)

همان‌طور که قبلاً اشاره شد، دو حالت vdp وجود دارد که مستر سیستم از آن‌ها استفاده می‌کند (همهٔ بازی‌ها از حالت 4 استفاده می‌کنند به‌جز F-16 Fighter که از حالت 2 استفاده می‌کند). اما حالت vdp بیشتر از حالت 4 یا 2 بودن را نشان می‌دهد؛ وضوح صفحه را هم نشان می‌دهد. حالت vdp از ۴ بیت زیر تشکیل شده:

textBit 3: حالت 4 (همان بیت 2 از ثبات کنترل 0)
Bit 2: حالت 3 (همان بیت 3 از ثبات کنترل 1)
Bit 1: حالت 2 (همان بیت 1 از ثبات کنترل 0)
Bit 0: حالت 1 (همان بیت 4 از ثبات کنترل 1)

ترکیب‌هایی که باید بدانید:

text0010 = حالت 2
1000 = حالت 4
1010 = حالت 4
1011 = حالت 4 با وضوح نمایش متوسط
1100 = حالت 4
1110 = حالت 4 با وضوح نمایش بزرگ
1111 = حالت 4

این‌طور تابع GetVDP را که در تابع Update استفاده کردم شبیه‌سازی می‌کنید:

cppBYTE TMS9918A::GetVDPMode( ) const
{
   BYTE res = 0 ;
   res |= BitGetVal(m_VDPRegisters[0x0],2) << 3 ;
   res |= BitGetVal(m_VDPRegisters[0x1],3) << 2 ;
   res |= BitGetVal(m_VDPRegisters[0x0],1) << 1 ;
   res |= BitGetVal(m_VDPRegisters[0x1],4) ;
   return res ;
}

Codemasters

قبلاً اشاره شد که وضوح صفحه را می‌توان تغییر داد تا تعداد خطوط اسکن دورهٔ نمایش فعال عمودی بزرگ‌تر شود. تنها بازی‌هایی که واقعاً از این قابلیت استفاده می‌کنند بازی‌های Codemasters هستند. لازم نیست نگران تشخیص بازی codemasters باشید؛ فقط باید هنگام نوشتن مقادیر مناسب در ثبات‌های کنترل، تغییر را مدیریت کنید. یادتان باشد آدرس نام‌بیس (namebase) هنگام استفاده از وضوح بالاتر متفاوت تفسیر می‌شود؛ این در بخش ثبات‌های کنترل بحث شد.

رندر (Rendering)

حالا توضیح می‌دهیم رندر فقط برای حالت 4 انجام می‌شود نه حالت 2؛ چون همه‌چیزی که برای رندر حالت 2 لازم دارید در حالت 4 پوشش می‌دهیم. برای مقابلهٔ خودتان با حالت 2 باید مستندات VDP شان یانگ را بخوانید که در بخش «منابع» آموزش لینک شده. در بخش چرخهٔ به‌روزرسانی به تابع Render اشاره کردم؛ پیاده‌سازی‌اش:

cppvoid TMS9918A::Render( )

دلیل اینکه اسپرایت‌ها را قبل از پس‌زمینه رندر می‌کنم را در بخش بعدی توضیح می‌دهم.

رندر اسپرایت — حالت 4

قبل از پرداختن به جزئیات رندر اسپرایت‌ها هنوز چند نکتهٔ باقی‌مانده را باید روشن کنم. اول اینکه VDP نمی‌تواند در هر خط اسکن بیشتر از ۸ اسپرایت رسم کند و اگر تلاش کند بیشتر از ۸ اسپرایت رسم کند، پرچم سرریز اسپرایت را در ثبات وضعیت تنظیم می‌کند و رسم بقیهٔ اسپرایت‌ها را روی خط اسکن متوقف می‌کند.

۶۴ اسپرایت برای رسم در دسترس است که در جدول مشخصات اسپرایت ارجاع می‌شوند. ترتیب رسم اسپرایت‌ها همان ترتیبی است که در جدول مشخصات اسپرایت ظاهر می‌شوند. بدیهی است که اسپرایت فقط اگر موقعیت فعلی‌اش در محدودهٔ vcounter فعلی باشد رسم می‌شود. اما اگر هنگام وضوح «کوچک» با اسپرایتی مواجه شویم که موقعیت محور Y آن 0xD0 است، این اسپرایت و همهٔ اسپرایت‌های باقی‌مانده رسم نمی‌شوند.

اگر دو اسپرایت روی هم بیفتند، پرچم مناسب در ثبات وضعیت تنظیم می‌شود. شاید بپرسید چرا قبل از بحث تایل‌ها، نحوهٔ شبیه‌سازی اسپرایت‌ها را توضیح می‌دهم. دو دلیل دارد: اول اینکه رندر اسپرایت‌ها آسان‌تر است چون نمی‌توانند اسکرول شوند (که سخت‌ترین بخش شبیه‌سازی این VDP است)؛ دوم اینکه تشخیص برخورد اسپرایت‌ها با رندر اول اسپرایت‌ها آسان‌تر است. روش شبیه‌سازی رندر VDP: در شروع هر فریم بافر رندر را پاک می‌کنم تا هر پیکسل با یک رنگ شناخته‌شده تنظیم شود. بعد هر بار یک خط را رسم می‌کنم؛ اول اسپرایت‌های روی آن خط و بعد تایل‌ها. وقتی یکی از پیکسل‌های بافر رندر را برای اسپرایتِ در حال رسم رنگ می‌کنم، تست می‌کنم رنگ فعلی پیکسل همان رنگی است که هنگام رسم فریم جدید از پیش تنظیم کردم یا نه. اگر همان رنگ باشد برخورد اسپرایت نیست؛ اما اگر رنگ متفاوتی باشد حتماً برخورد اسپرایت است. وقتی به رسم تایل‌ها می‌رسم، فقط اگر رنگ فعلی پیکسل همان رنگی باشد که از پیش تنظیم کردم پیکسل را رسم می‌کنم؛ وگرنه اسپرایتی آنجا رسم شده و اسپرایت‌ها به‌طور پیش‌فرض اولویت بالاتری از تایل‌ها دارند. اما ممکن است تایلی اولویت بالاتری از اسپرایت داشته باشد و در این صورت اسپرایت رسم‌شده را بازنویسی می‌کنم.

حالا به اطلاعات کافی برای شروع شبیه‌سازی اسپرایت‌ها مجهز شده‌ایم. اول باید بدانیم کدام‌یک از ۶۴ اسپرایت باید در خط اسکن فعلی رسم شود (اگر اصلاً). پس اول جدول مشخصات اسپرایت را اسپرایت‌به‌اسپرایت پیمایش می‌کنیم و مشخص می‌کنیم موقعیت اسپرایت در محدودهٔ خط اسکن فعلی است یا نه. اندازهٔ اسپرایت را هم باید در نظر بگیریم؛ چون روی محدودهٔ خطوط اسکنی که ظاهر می‌شود اثر می‌گذارد. حالا وقت خوبی است کد تعیین محل سکونت جدول مشخصات اسپرایت و اطلاعات قابل‌گرفتن برای هر اسپرایت را نشان دهیم.

ثبات کنترل 0x5 برای تنظیم پایهٔ جدول مشخصات اسپرایت استفاده می‌شود. همان‌طور که قبلاً اشاره شد، در این مقدار ثبات ۸ بیتی بیت‌های 7 و 0 نادیده گرفته می‌شوند و ۷ جا شیفت چپ می‌شود تا آدرس شروع جدول مشخصات اسپرایت به‌دست آید:

cppWORD TMS9918A::GetSATBase( ) const
{
   BYTE reg5 = m_VDPRegisters[0x5] ;

   // بیت‌های 7 و 0 نادیده گرفته می‌شوند
   reg5 &= 0x7E ;
   WORD res = reg5 ;
   return (res << 7) ;
}

حالا که می‌دانیم SAT کجاست، محتوایش را چگونه تفسیر کنیم؟ هر اسپرایت ۴ بایت حافظه در SAT می‌گیرد: بایت اول موقعیت y، دومی موقعیت x، سومی اندیس پترن و بایت آخر استفاده نشده. اما برای سخت‌کردن کارمان، دادهٔ یک اسپرایت در حافظه کنار هم قرار ندارد. همهٔ پترن‌های y اسپرایت‌ها در ۶۴ بایت اول حافظهٔ SAT کنار هم یافت می‌شوند. موقعیت x اسپرایت ۱۲۸ بایت بعد از پایهٔ SAT به‌علاوهٔ شمارهٔ اسپرایت ضرب‌در 2 است (int x = m_VDPMemory[GetSATBase() + 128 + (sprite*2)]). اندیس پترن ۱ بایت بعد از موقعیت x است.

حالا موقعیت x و y اسپرایت را می‌دانیم؛ باید یادمان باشد اگر بیت 3 از ثبات کنترل 0 تنظیم شده باشد، موقعیت x می‌تواند ۸ پیکسل به چپ شیفت شود. همچنین موقعیت y در واقع موقعیت y + 1 را نشان می‌دهد؛ پس اگر موقعیت y برابر 0 باشد، اسپرایت از خط اسکن 1 شروع می‌شود.

اندیس پترن برای جستجوی پترن واقع در حافظهٔ vdp 0x0-0x37FF است. پترن داده‌ای است که برای رسم واقعی اسپرایت/تایل مشخص‌شده لازم است. ۴۴۸ پترن در جدول پترن‌ها به دو جدول تقسیم می‌شوند. جدول پترن اول اندیس‌های پترن 0-255 و جدول دوم اندیس‌های 256-447 را ذخیره می‌کند. مقدار اندیس پترن که از SAT گرفته می‌شود یا به جدول اول اشاره می‌کند یا دوم. اگر به جدول دوم اشاره کند، مقدار اندیس پترن ۲۵۶ افزایش می‌یابد؛ پس مقدار اندیس پترن 7 اگر از جدول دوم استفاده کند 263 می‌شود. برای تعیین اینکه از کدام جدول پترن استفاده شود مقدار بیت 2 از ثبات کنترل 6 است. اگر مقدار 1 باشد از جدول پترن دوم استفاده می‌شود وگرنه اول. همچنین اگر از جدول پترن دوم استفاده شود و اسپرایت 8x16 باشد، باید بیت 0 اندیس پترن را هم بازنشانی کنید.

هر پترن ۳۲ بایت حافظه می‌گیرد و در مجموع ۴۴۸ پترن وجود دارد. پس یافتن آدرس پترن در حافظه به همین سادگی است: اندیس پترن را در ۳۲ ضرب کنید. این ۳۲ بایت هر رنگ پیکسل پترن 8x8 را نشان می‌دهد. هر ۴ بایت از مجموع ۳۲ بایت، توصیفی از رنگ یک خط از پترن می‌دهد. چون ۸ خط است و برای هر خط ۴ بایت، عدد جادویی ۳۲ به دست می‌آید. پس ۴ بایت اول دادهٔ خط اول، ۴ بایت دوم دادهٔ خط دوم و الی آخر. پس این ۴ بایت چگونه رنگ یک خط پترن را می‌دهند؟ اول باید بفهمید ۳۲ بایت داده رنگ پیکسل را کد نمی‌کنند؛ بلکه یک پالت را. مقدار به‌دست‌آمده از ۳۲ بایت داده به‌عنوان جستجو در پالت برای یافتن رنگ دقیق استفاده می‌شود. دلیلش این است که برنامه‌نویس می‌تواند رنگ‌های پالت را بدون تغییر دادهٔ پترن عوض کند؛ یعنی پترن با تغییر کامل رنگ‌ها تغییر کند. یک خط پترن ۸ پیکسل دارد و از چپ به راست رسم می‌شود. یک بایت ۸ بیت دارد؛ پس هر بیت می‌تواند یکی از ۸ پیکسل را نشان دهد. بیت 7 چپ‌ترین پیکسل، بیت 6 چپ‌ترین+1 و ... بیت 0 راست‌ترین پیکسل را نشان می‌دهد. پس برای گرفتن اندیس جستجوی پالتِ چپ‌ترین پیکسل، همهٔ مقادیر بیت 7 از ۴ بایت را ترکیب می‌کنید:

cppBYTE palette = 0 ;
BYTE bit = BitGetVal(data4,col) ;
palette = (bit << 3) ;
bit = BitGetVal(data3,col) ;
palette |= (bit << 2) ;
bit = BitGetVal(data2,col) ;
palette |= (bit << 1) ;
bit = BitGetVal(data1, col) ;
palette |= bit ;

BitGetVal بسته به تنظیم‌بودن بیت متناظر، مقدار 0 یا 1 برمی‌گرداند. سپس این مقدار پالت برای جستجوی رنگ درست برای پیکسل استفاده می‌شود. (نویسنده معتقد است پالت 0 یعنی اسپرایت شفاف است و نباید رسم شود؛ اما نتوانسته سندی برای این ادعا پیدا کند، پس شاید بخواهید آزمایش کنید.) برای جستجوی رنگ درست به سادگی مقدار پالت را در CRAM قرار می‌دهید؛ اما اسپرایت‌ها از پالت دوم CRAM استفاده می‌کنند؛ هر پالت ۱۶ بایت است؛ پس این را می‌گیریم:

cppBYTE colour = m_CRAM[palette+16] ;

این بایت رنگ چه چیزی را نشان می‌دهد؟ بیت‌های 1-0 این بایت رنگ قرمز را نشان می‌دهند. بیت‌های 3-2 رنگ سبز را. بیت‌های 5-4 رنگ آبی را. نویسنده هرگز دقیقاً پیدا نکرد این‌ها چطور به رنگ‌های خاص نگاشت می‌شوند؛ پس حدس زد و به‌نظر کاملاً کار می‌کند (اگر باور نمی‌کنید به تصاویرش نگاه کنید). روش او: اگر هر یک از سایه‌های قرمز، سبز و آبی با ۲ بیت نمایش داده شوند، ۴ سایهٔ متفاوت از رنگ (مقادیر 0-3) ممکن است. هر سایه بین 0 تا 255 خواهد بود. مقدار 0 سایهٔ 0 می‌دهد، مقدار 3 سایهٔ 255 و دو سایهٔ دیگر مقادیری در این بین. مقادیر منطقی 85 برای مقدار 1 و 170 برای مقدار 2 است. اگر می‌پرسید چرا این‌ها منطقی‌اند، چون 85 و 170 دو نقطهٔ میانی محدودهٔ 0-255 را به‌طور مساوی فاصله می‌دهند:

cppBYTE TMS9918A::GetColourShade(BYTE val) const
{
   switch (val)
   {
     case 0: return 0 ; break ;
     case 3: return 255 ; break ;
     case 1: return 85 ; break ;
     case 2: return 170 ; break ;
     default: assert(false); return 0 ; break ;
   }
}

امیدوارم همه‌چیز لازم برای شبیه‌سازی رندر اسپرایت‌های حالت 4 را توضیح داده باشم. چون کد شبیه‌سازی نویسنده برای جا شدن در این صفحه خیلی بزرگ است، شما را به یک فایل متنی ارجاع می‌دهد که کد را نشان می‌دهد: مشاهدهٔ کد.

می‌بینید در رندر اسپرایت و تایل از تابع WriteToScreen استفاده می‌کنم؛ پیاده‌سازی‌اش:

cppvoid TMS9918A::WriteToScreen(BYTE x, BYTE y, BYTE red, BYTE green, BYTE blue)

همان‌طور که می‌بینید، برای سه وضوح مختلف سه بافر صفحهٔ متفاوت دارد. آخرین نکته: برای تشخیص برخورد اسپرایت، رنگ فعلی پیکسلی که می‌خواهم رنگ کنم را می‌گیرم و اگر برابر SCREENBLANKCOLOUR نبود، پرچم برخورد اسپرایت را تنظیم می‌کنم. تابع GetScreenPixelColour فقط برای موقعیت x و y بافر صفحهٔ فعلی، رنگی برمی‌گرداند. در شروع هر فریم همهٔ پیکسل‌ها را به SCREENBLANKCOLOUR که برابر 0x01 است تنظیم می‌کنم.

رندر پس‌زمینه — حالت 4

رندر تایل‌های پس‌زمینه خیلی شبیه اسپرایت‌هاست. همچنان یک شمارهٔ پترن می‌گیرد و مثل اسپرایت‌ها رسم می‌شود؛ اما پیچیدگی اضافهٔ اولویت‌ها، اسکرول و ماسک را دارد. این‌ها چیزهایی هستند که مفصل به آن‌ها می‌پردازم و بقیهٔ شبیه‌سازی در بخش اسپرایت پوشش داده شد.

اول مشخص کنیم تایل‌ها در حافظهٔ vdp چگونه ذخیره می‌شوند. اطلاعات تایل در جدول نام‌های حافظهٔ vdp ذخیره می‌شود. اندازهٔ جدول نام‌ها برای هر تایل ۲ بایت است (وضوح «کوچک» 32x28 تایل دارد و بقیه 32x32). تفسیر ۲ بایت هر تایل:

textBit 15 - 13: استفاده نشده
Bit 12: پرچم اولویت
Bit 11: کدام پالت استفاده شود
Bit 10: پرچم قرینهٔ عمودی
Bit 09: پرچم قرینهٔ افقی
Bit 08 - 00: اندیس پترن

جدول نام‌ها آدرس ثابتی ندارد؛ معمولاً در 0x3800-0x3EFF است اما می‌تواند تغییر کند. وقتی قبلاً در این آموزش دربارهٔ ثبات 2 مفصل صحبت کردم، الگوریتم تبدیل ثبات 2 به جدول نام‌ها را دادم؛ پیاده‌سازی‌اش:

cppWORD TMS9918A::GetNameBase( ) const
{
   BYTE reg2 = m_VDPRegisters[0x2] ;

   if (m_Height == 192) // وضوح کوچک
   {
     // بیت 0 نادیده گرفته می‌شود؛ نیبل بالا هم همین‌طور
     reg2 &= 0xF ;
     reg2 = BitReset(reg2,0) ;
     return ((WORD)reg2) << 10 ;
   }

   // باید وضوح متوسط یا بزرگ باشد
   reg2 &= 0xC ;
   WORD res = reg2 ;
   res <<= 10 ;
   res |= 0x700 ;
   return res ;
}

حالا آدرس جدول پایهٔ نام‌ها را داریم؛ فقط باید برای هر تایلی که رسم می‌کنیم آن را پیمایش کنیم و بعد تایل مناسب را رسم کنیم. تفاوت رسم تایل و اسپرایت این است که ترتیب منطقی برای رسم اسپرایت وجود ندارد؛ یعنی اسپرایت شمارهٔ 1 می‌تواند پایین-راست باشد در حالی که اسپرایت شمارهٔ 2 وسط صفحه است. به همین دلیل باید هر اسپرایت را بررسی کنیم که آیا در محدودهٔ vcounter فعلی ماست قبل از رسمش. اما با رسم تایل‌ها، تایل شمارهٔ 0 بالا-چپ رسم می‌شود، تایل شمارهٔ 1 سمت راستش و الی آخر برای کل 32x28 (یا 32x32 در وضوح متوسط یا بزرگ)؛ توجه کنید این فقط وقتی درست است که اسکرول فعال نباشد، که بعداً می‌بینیم. جدا از این، تقریباً به همان شکل رسم می‌شوند.

معمولاً تایل همیشه پشت اسپرایت رسم می‌شود؛ اما اگر پرچم اولویت دادهٔ تایل (بیت 12) تنظیم شده باشد، جلوی اسپرایت ظاهر می‌شود. تنها استثنای این قاعده این است که پالت تایل 0 باشد؛ یعنی تایل شفاف است و نباید رسم شود.

همچنین باید از ماسک ستون اول آگاه باشیم. اگر پرچم ماسک تنظیم شده باشد (بیت 5 از ثبات 0)، ۸ پیکسل اول هر خط اسکن با رنگ پس‌زمینهٔ مشخص‌شده در ثبات 07 تنظیم می‌شوند. ماسک ستون اول بالاترین اولویت را دارد و اگر بیت 5 از ثبات 0 تنظیم شده باشد، همیشه جلوی تایل‌ها و اسپرایت‌ها ظاهر می‌شود.

به نظر نویسنده پیچیده‌ترین بخش شبیه‌سازی VDP اسکرول پس‌زمینه است. بهترین شانس شما برای فهمیدنش خواندن مستندات VDP چارلز مک‌دونالد است که در بخش منابع آموزش مستر سیستم لیست شده. چارلز اسکرول افقی را به دو بخش تقسیم می‌کند: ستون شروع (starting column) و مقدار اسکرول ریز (fine scroll). نویسنده این‌طور تفسیرش می‌کند: ستون شروع یعنی از کدام ستون در جدول نام‌ها شروع به رسم کنیم. پس ممکن است به عدد دلخواه 4 (از 32) تنظیم شود؛ یعنی تایل چهارم در لبهٔ چپ صفحه رسم می‌شود. بعد از رسم هر ستون، ستون شروع افزایش می‌یابد تا به 32 برسد و بعد دوباره از 0 شروع می‌کند. مقدار اسکرول ریز هم به‌سادگی مشخص می‌کند از کدام پیکسل داخل ستون شروع، رسم را شروع کنیم. مثلاً اگر ستون شروع 4 و اسکرول ریز 3 باشد، سومین پیکسل ستون چهارم در لبهٔ چپ صفحه رسم می‌شود. ستون شروع از ۵ بیت بالای ثبات 0x8 و مقدار اسکرول ریز از ۳ بیت پایین گرفته می‌شود. تنها بخش دیگر اسکرول افقی: اگر بیت 6 از ثبات 0 تنظیم شود، ردیف اول صفحه ثابت می‌ماند و افقی اسکرول نمی‌شود.

اسکرول عمودی شبیه اسکرول افقی کار می‌کند با این استثنا که به‌جای ستون شروع، ردیف شروع (starting row) دارد. مثل ستون شروع کار می‌کند، فقط مشخص می‌کند کدام ردیف بالای صفحه رسم شود. پس اگر ردیف شروع 5 باشد، ردیف پنجم بالای صفحه رسم می‌شود و بعد از رسم ردیف پنجم، به ردیف 6 افزایش می‌یابد و الی آخر تا وقتی به 28 (برای وضوح کوچک) یا 32 (برای متوسط و بزرگ) برسد که دوباره از 0 شروع می‌کند. مقدار اسکرول ریز مثل اسکرول افقی کار می‌کند: مشخص می‌کند کدام پیکسل از ردیف شروع اول رسم می‌شود. اگر بیت 7 از ثبات 0 تنظیم شود، ستون‌های 24-32 ثابت می‌مانند و عمودی اسکرول نمی‌شوند. ردیف شروع از ۵ بیت بالای ثبات 9 و اسکرول ریز از ۳ بیت پایین گرفته می‌شود. هر تغییری در این ثبات تا بعد از دورهٔ نمایش فعال به‌روزرسانی نمی‌شود.

تقریباً با جمع‌آوری اطلاعات شبیه‌سازی تایل تمام شدیم؛ تنها بخش‌های باقی‌مانده این است که تایل می‌تواند بر اساس داده‌های تایلش عمودی یا افقی (یا هر دو) قرینه شود و می‌تواند از پالت‌های تایل پس‌زمینه یا پالت‌های اسپرایت استفاده کند که از دادهٔ تایل هم قابل‌گرفتن است. شبه‌کد جمع‌آوری دادهٔ یک تایل:

cppWORD nameBaseOffset = GetNameBase() ;
nameBaseOffset += currentRow * 64 ; // هر خط اسکن ۳۲ تایل دارد که در حافظه ۲ بایت است
nameBaseOffset += currentCol * 2 ; // هر تایل در حافظه دو بایت است

WORD tileData = m_VRAM[nameBaseOffset+1] << 8 ;
tileData |= m_VRAM[nameBaseOffset] ;

bool hiPriority = TestBit(tileData,12) ;
bool useSpritePalette = TestBit(tileData,11) ;
bool vertFlip = TestBit(tileData,10) ;
bool horzFlip = TestBit(tileData,9) ;
WORD tileDefinition = tileData & 0x1FF ;

چند پاراگراف بالاتر دقیقاً توضیح دادم دادهٔ تایل چگونه به‌دست می‌آید. بقیهٔ رسم تایل نسبت به اسپرایت باید یکسان باشد. این tileDefinition است که دادهٔ پترن لازم برای رسم تایل را می‌دهد (یادتان باشد هر خط ۴ بایت و ۸ خط است؛ پس برای رسم یک پترن ۳۲ بایت لازم است. اگر مطمئن نیستید، پاراگراف بخش رندر اسپرایت که با «هر پترن ۳۲ بایت حافظه می‌گیرد» شروع می‌شود را دوباره بخوانید). حالا آمادهٔ بررسی کد کامل شبیه‌سازی تایل‌ها هستیم که در این فایل متنی موجود است.

جوی‌پدها (Joypads)

این یکی از ساده‌ترین دستگاه‌های SMS برای شبیه‌سازی است. هر دکمهٔ جوی‌پد بیت مخصوص خودش را در یک ثبات وضعیت جوی‌پد دارد. دو ثبات وضعیت جوی‌پد وجود دارد که بازی با خواندن شمارهٔ پورت مناسب‌شان می‌تواند بخواند. این پورت‌ها محافظت‌شده در برابر نوشتن‌اند؛ پس فقط بازی‌هایی می‌بینید که از آن‌ها می‌خوانند نه می‌نویسند. PortA شمارهٔ پورت 0xDC است و در 0xC0 آینه می‌شود. PortB شمارهٔ پورت 0xDD است و در 0xC1 آینه می‌شود. معنی بیت‌های هر یک از دو بایت نمایانگر وضعیت:

textPortA:
Bit 7: دکمهٔ پایین جوی‌پد 2
Bit 6: دکمهٔ بالا جوی‌پد 2
Bit 5: Fire B جوی‌پد 1
Bit 4: Fire A جوی‌پد 1
Bit 3: دکمهٔ راست جوی‌پد 1
Bit 2: دکمهٔ چپ جوی‌پد 1
Bit 1: دکمهٔ پایین جوی‌پد 1
Bit 0: دکمهٔ بالا جوی‌پد 1

PortB:
Bit 7: استفاده نشده... لایت‌گان؟
Bit 6: استفاده نشده... لایت‌گان؟
Bit 5: استفاده نشده
Bit 4: دکمهٔ Reset
Bit 3: Fire B جوی‌پد 2
Bit 2: Fire A جوی‌پد 2
Bit 1: دکمهٔ راست جوی‌پد 2
Bit 0: دکمهٔ چپ جوی‌پد 2

اما هر بیت از این دو بایت وقتی دکمه‌ای فشرده نباشد 1 است. وقتی دکمه فشرده شود، بیت 0 می‌شود. همچنین توجه کنید وضعیت جوی‌پد 2 هم در PortA هم PortB است. بهترین راه شبیه‌سازی جوی‌پدها: دو متغیر BYTE که ابتدا 0xFF تنظیم می‌شوند (همهٔ 1ها یعنی هیچ دکمه‌ای فشرده نشده). سپس هر بار دکمه‌ای از صفحه‌کلید فشرده شود، بیت متناظر را در PortA یا PortB 0 کنید و وقتی کلید رها شد به 1 برگردانید. سپس هر وقت بازی بخواهد ورودی جوی‌پد را بررسی کند، پورت IO 0xDC یا 0xDD را می‌خواند و شبیه‌ساز به‌ترتیب بایت PortA یا PortB را برمی‌گرداند.

دکمهٔ Reset

آخرین بخش شبیه‌سازی جوی‌پد دکمهٔ Reset است. دکمهٔ Reset یک وقفهٔ غیرقابل‌ماسک (none maskable interrupt) را تحریک می‌کند؛ یعنی هیچ راهی وجود ندارد بازی بتواند جلوی ثبت این وقفه را بگیرد. حتی اگر همهٔ وقفه‌ها غیرفعال باشند، یک وقفهٔ غیرقابل‌ماسک همچنان سرویس می‌شود. سیستم وقفه‌ها را در بخش بعدی آموزش مفصل‌تر توضیح می‌دهیم؛ فعلاً فقط هر بار که دکمهٔ Reset فشرده می‌شود (اما نه رهاشده) یک پرچم تنظیم کنید. این به شبیه‌ساز علامت می‌دهد که یک وقفهٔ reset باید در اسرع وقت سرویس شود.

وقفه‌ها (Interrupts)

سه مکانیزم مختلف وقفه وجود دارد که Z80 می‌تواند استفاده کند اما SMS فقط از یکی استفاده می‌کند (حالت وقفهٔ 1).

سگا مستر سیستم ۳ وقفهٔ سخت‌افزاری دارد. وقفهٔ سخت‌افزاری راهی است که سخت‌افزار می‌تواند به CPU علامت دهد از کاری که دارد می‌کند دست بردارد و کار دیگری را شروع کند؛ راهی برای رسیدن به چندوظیفگی (multitasking). دو نوع وقفه وجود دارد: وقفه‌های قابل‌ماسک (maskable) و غیرقابل‌ماسک (none-maskable). تفاوت این است که می‌توانید وقفه‌های قابل‌ماسک را از قطع‌کردن CPU غیرفعال کنید اما نمی‌توانید یک وقفهٔ غیرقابل‌ماسک را متوقف کنید. هر بار وقفهٔ غیرقابل‌ماسک رخ دهد، CPU کارش را متوقف می‌کند و سرویسش می‌کند. یک وقفه با push کردن شمارندهٔ برنامهٔ فعلی روی پشته و پرش به آدرس مدیریت‌کنندهٔ وقفه (Interrupt Handler) سرویس می‌شود. وقتی سرویس مدیریت‌کنندهٔ وقفه تمام شد، شمارندهٔ برنامه را به مقدار قبل از وقفه برمی‌گرداند و از همان‌جا ادامه می‌دهد.

وقفه‌های قابل‌ماسک (Maskable Interrupts)

Z80 دو فلیپ‌فلاپ وضعیت وقفه دارد که FF1 و FF2 می‌نامیم. اگر FF1 تنظیم شود، وقفه‌های قابل‌ماسک فعال‌اند و می‌توانند هر لحظه سیگنال شوند. وقتی FF1 تنظیم نباشد، وقفه‌های قابل‌ماسک تا وقتی FF1 تنظیم نشود سرویس نمی‌شوند. اما مهم است بدانید اگر FF1 تنظیم نباشد و وقفه‌ای در حال درخواست باشد، تا وقتی FF1 دوباره تنظیم شود ممکن است همان وقفه دیگر درخواست سرویس ندهد؛ پس آن وقفه هرگز سرویس نمی‌شود. قبل از توضیح FF2 اشاره کنم که وقفهٔ غیرقابل‌ماسک همیشه بر وقفهٔ قابل‌ماسک اولویت دارد. پس وقتی وقفهٔ غیرقابل‌ماسک سیگنال شود، FF1 خاموش می‌شود تا هیچ وقفهٔ قابل‌ماسکی نتواند سرویس فعلی وقفهٔ غیرقابل‌ماسک را قطع کند. وقتی وقفهٔ غیرقابل‌ماسک سیگنال شود، FF2 مقدار FF1 را می‌گیرد و FF1 خاموش می‌شود. به این ترتیب وقتی وقفهٔ غیرقابل‌ماسک تمام شد و با دستور RETI از Z80 برگشت، FF1 به مقداری که قبل از سرویس وقفهٔ غیرقابل‌ماسک بود برمی‌گردد؛ همان مقدار FF2. دستورهای Z80 چگونه بر فلیپ‌فلاپ‌ها اثر می‌گذارند:

textEI (فعال‌سازی وقفه‌ها): FF1 = روشن و FF2 = روشن
DI (غیرفعال‌سازی وقفه‌ها): FF1 = خاموش و FF2 = خاموش
RETI (بازگشت از روال وقفه): FF1 = FF2

در واقع EI مقدار FF1 و FF2 را تا دستورالعمل بعد از EI «روشن» نمی‌کند.

دو وقفهٔ قابل‌ماسک در SMS رخ می‌دهد و هر دو از VDP سیگنال می‌شوند. اولین وقفهٔ همگام‌سازی عمودی (vertical sync) است؛ وقتی v counter اول از ناحیهٔ نمایش فعال به ناحیهٔ نمایش غیرفعال خارج شود رخ می‌دهد. همان‌طور که در بخش VDP این آموزش بحث شد، وقتی این اتفاق بیفتد بیتی در ثبات وضعیت VDP تنظیم می‌شود که نشان دهد VDP درخواست وقفه دارد. اما فقط اگر وقفه‌های vertical sync در ثبات مناسب VDP فعال شده باشند وقفه درخواست می‌شود؛ این هم در بخش VDP بحث و پیاده‌سازی شد.

دومین وقفهٔ قابل‌ماسک شمارندهٔ خط (line counter) است. بازی می‌تواند شمارندهٔ خط را وقتی VDP خارج از دورهٔ نمایش فعال است (به‌جز اولین خط دورهٔ نمایش غیرفعال) روی هر مقداری تنظیم کند. وقتی VDP در دورهٔ نمایش فعال است (همچنین اولین خط دورهٔ نمایش غیرفعال)، مقدار شمارندهٔ خط هر بار که v counter به خط بعدی می‌رود یکی کم می‌شود. وقتی مقدار شمارندهٔ خط کمتر از 0 شود، به مقداری که شروع کرده بود بازنشانی می‌شود و یک وقفهٔ خط درخواست می‌شود. همهٔ این‌ها در بخش VDP این آموزش مفصل‌تر بحث شد.

یک تفاوت مهم بین وقفهٔ vsync و وقفهٔ خط: وقفهٔ vsync تا وقتی بیت vsync در ثبات وضعیت VDP تنظیم شده و وقفه‌های vsync در ثبات VDP مناسب فعال‌اند، دائماً درخواست سرویس می‌دهد. اما وقفهٔ خط فقط یک بار درخواست می‌شود و تا وقتی دوباره رخ ندهد فراموش می‌شود.

VDP می‌تواند به درخواست وقفه ادامه دهد اما تا وقتی FF1 «روشن» نشود هیچ‌کدام سرویس نمی‌شوند. وقتی وقفه‌ای برای سرویس پذیرفته شد (FF1 روشن است)، شمارندهٔ برنامهٔ فعلی روی پشته push می‌شود و شمارندهٔ برنامه به 0x38 تنظیم می‌شود که آدرس روال مدیریت وقفه است.

وقفه‌های غیرقابل‌ماسک (None Maskable Interrupts)

فقط یک وقفهٔ غیرقابل‌ماسک وجود دارد به نام «وقفهٔ Reset». وقتی بازیکن دکمهٔ reset را روی کنترل پد فشار دهد رخ می‌دهد. راه شبیه‌سازی: یک متغیر bool (از این به بعد m_ResetInterrupt) که وقتی دکمهٔ reset فشرده شود true می‌شود و بعد حلقهٔ اصلی شبیه‌سازی باید بعد از هر دستورالعملِ شبیه‌سازی‌شده این متغیر را بررسی کند. همان‌طور که قبلاً اشاره شد، نمی‌توانید وقفه‌های غیرقابل‌ماسک را خاموش کنید و آن‌ها اولویت بالاتری از وقفه‌های قابل‌ماسک دارند. وقتی وقفهٔ غیرقابل‌ماسک سیگنال شود، CPU شمارندهٔ برنامه‌اش را روی پشته push می‌کند و به مدیریت‌کنندهٔ وقفهٔ غیرقابل‌ماسک می‌پرد که آدرس 0x66 است.

مدیریت وقفه‌ها (Handling Interrupts)

در بخش «شروع کار» این آموزش اشاره شد که هنوز باید تابع HandleInterrupts را در حلقهٔ اصلی شبیه‌سازی پیاده کنیم. حالا که به همهٔ اطلاعات لازم برای پیاده‌سازی این تابع مجهز شده‌ایم، بالاخره می‌توانیم:

cppvoid Emulator::HandleInterrupts()
{
  if (m_ResetInterrupt && !m_ServicingReset)
  {
    m_ServicingReset = true ;
    m_ResetInterrupt = false ;
    FF1 = false ;
    m_Halted = false ;
    PushWordOntoStack(m_ProgramCounter) ;
    m_ProgramCounter = 0x66 ;
  }

  if (m_GraphicsChip.IsRequestingInterupt())
  {
    if (FF1 && m_InteruptMode == 1)
    {
      m_Halted = false ;
      PushWordOntoStack(m_ProgramCounter) ;
      m_ProgramCounter = 0x38 ;
      m_IFF1 = false ;
      m_IFF2 = false ;
    }
  }
}

یادتان باشد بازی می‌تواند با صدازدن دستور HALT بنشیند و منتظر وقفه بماند. یعنی هیچ دستورالعمل دیگری اجرا نمی‌شود تا وقفه‌ای رخ دهد. به همین دلیل متغیر m_Halted را به false برمی‌گردانیم تا CPU بتواند دوباره اجرای دستورالعمل‌ها را شروع کند. همچنین می‌بینید یک متغیر bool اضافه به نام m_ServicingReset دارم؛ فقط جلوی رخدادن یک وقفهٔ reset دیگر را در حالی که وقفهٔ reset قبلی در حال سرویس است می‌گیرد.

صدا (Sound)

اطلاعات PSG

PSG یک SN79489 ساخت Texas Instruments است. این تراشهٔ صدا ۴ کانال مختلف دارد: سه کانال تُن (tone) و یکی کانال نویز (noise). با موج مربعی (square wave) صدا تولید می‌کند که بعداً بحث می‌شود. یعنی می‌توان آن را طوری برنامه‌ریزی کرد که هم حجم هر کانال و هم فرکانس هر کانال را تغییر دهد. برای تغییر حجم و فرکانس کانال‌ها، داده به پورت 0x7F نوشته می‌شود که در 0x7E هم آینه می‌شود.

ساعت PSG همان ساعت پردازندهٔ Z80 است که سه برابر کندتر از ساعت اصلی سیستم است. هر کانال یک شمارنده دارد که به فرکانس‌اش تنظیم می‌شود. هر 224KHz شمارندهٔ هر کانال کم می‌شود و بعد خروجی همهٔ کانال‌ها ترکیب و به بافر پخش اضافه می‌شود. وقتی یکی از شمارنده‌ها به 0 رسید، به مقدار فرکانس کانال بازنشانی می‌شود و قطبیت (polarity) خروجی این کانال تغییر می‌کند. این پایهٔ موج مربعی است.

موج مربعی (Square Waves)

موج مربعی اسمش را از این گرفته که خروجی کانال‌ها همیشه یکی از دو مقدار است؛ این قطبیت فعلی کانال است. موج‌های مربعی علامت‌دار مقادیر +1 و -1 خروجی می‌دهند و موج‌های مربعی بدون علامت +1 و 0. ماهیت موج مربعی علامت‌دار و بدون علامت یکی است؛ اما نویسنده تصمیم گرفت از موج مربعی علامت‌دار استفاده کند؛ چون ترکیب خروجی‌های هر ۴ کانال فقط جمع‌کردن آن‌هاست که از موج مربعی بدون علامت آسان‌تر است. دلیل اینکه خروجی فقط دو مقدار از کانال‌ها موج مربعی است این است که الگوی موج مربعی به نظر می‌رسد. مثلاً اگر فرکانس کانال 1 برابر 5 تنظیم شود، این یعنی هر نیمه از موج مربعی با 5 نمونهٔ 224kHz پخش می‌شود. پس 5 نمونهٔ 224kHz با یکی از قطبیت‌ها پخش می‌شود و بعد 5 نمونهٔ 224kHz دیگر با قطبیت دیگر. این یعنی هر موج کامل 10 نمونهٔ 224kHz دارد.

text1  |#####         #####         #####
0  |---------------------------------------------------------------
-1 |        #####         #####         #####

همان‌طور که می‌بینید، اگر فرکانس 5 تنظیم شده باشد، 5 نمونه با قطبیت 1 و بعد 5 نمونه با قطبیت -1 خروجی می‌شود. به همین دلیل به آن موج مربعی می‌گویند؛ چون الگوی موج لبه‌های مربعی دارد. خروجی هر کانال (+1 یا -1) در حجمش ضرب می‌شود تا دادهٔ پخش‌شده به‌دست آید. دادهٔ پخش هر ۴ کانال با هم جمع می‌شود (چون از موج مربعی علامت‌دار استفاده می‌کنیم) و این دادهٔ پخش نهایی است که به بافر پخش اضافه می‌شود.

ثبات‌های PSG

هر یک از ۴ کانال ۲ ثبات دارد؛ یعنی در مجموع ۸ ثبات. اولین ثبات کانال، حجم کانال است که یک ثبات ۴ بیتی است؛ ثبات دوم ثبات تُن (فرکانس) کانال است؛ این‌ها ثبات‌های ۱۰ بیتی هستند به‌جز کانال نویز که ۴ بیتی است.

وقتی به کانال 0 اشاره می‌کنیم، منظور اولین کانال از ۴ کانال است؛ کانال 1 یعنی دومین و الی آخر. دلیل: وقتی داده به PSG نوشته می‌شود، کانالی که برایش در نظر گرفته شده به‌صورت باینری 00,01,10 و 11 نشان داده می‌شود.

ثبات‌های حجم هنگام راه‌اندازی 0xF تنظیم می‌شوند و ثبات‌های تُن 0x0.

حجم کانال PSG

هرچند ثبات‌های حجم ۸ بیتی‌اند، فقط ۴ بیت پایین همیشه استفاده می‌شوند؛ یعنی حجم محدودهٔ 0x0 تا 0xF دارد. 0x0 یعنی حجم کامل و 0xF یعنی سکوت. هر مقدار حجم ۲ دسی‌بل کم‌صداتر است؛ پس حجم 0x1 از 0x0 دو دسی‌بل کم‌صداتر است و حجم 0x2 از 0x1. همان‌طور که در بخش موج مربعی اشاره شد، از کانال‌ها مقادیر +1 و -1 خروجی می‌گیریم که در حجم کانال ضرب می‌شود و این مقدار برای هر ۴ کانال با هم جمع و به بافر پخش اضافه می‌شود. ضروری است مقداری که به بافر پخش اضافه می‌شود از حداکثر و حداقل مقادیر سرریز نکند. رایج‌ترین نوع مقدار برای بافر پخش نمونه‌های ۱۶ بیتی علامت‌دار است. حداقل و حداکثر یک عدد ۱۶ بیتی علامت‌دار به‌ترتیب 32768- تا 32767+ است. یعنی هنگام ترکیب مقادیر پخش هر ۴ کانال، مقدار نمی‌تواند از این مقادیر رد شود. چون مقادیر پخش هر ۴ کانال را با هم جمع می‌کنیم، با حداکثر حجم کانالِ 8000 می‌توانیم تضمین کنیم از این مقادیر رد نمی‌شویم. یعنی اگر هر ۴ کانال با حداکثر حجم خروجی بدهند و همه با قطبیت مثبت خروجی بدهند، همه مقادیر پخش 8000 خروجی می‌دهند و با ترکیب‌شان حداکثر مقدار پخش 32000 به‌دست می‌آید که در محدودهٔ 32767 است. به همین ترتیب اگر همهٔ کانال‌ها با حجم کامل و همه با قطبیت منفی باشند، همه مقدار پخش 8000- خروجی می‌دهند و با ترکیب‌شان مقدار پخش 32000- به‌دست می‌آید که در محدودهٔ 32768- جا می‌شود. این تضمین می‌کند هرچه قطبیت کانال‌ها و حجم‌هایشان باشد، مقدار پخش ترکیبی کانال هرگز از حداکثر یا حداقل محدوده رد نمی‌شود.

وقتی تراشهٔ PSG شبیه‌سازی‌شده را می‌سازیم باید جدول حجم را تنظیم کنیم که برای دانستن اینکه خروجی کانال را در چه چیزی ضرب کنیم تا حجم درست به‌دست آید استفاده می‌شود. همان‌طور که قبلاً گفته شد، حجم 0x0 حداکثر و حجم 0xF حداقل است. هر مقدار حجم از قبلی ۲ دسی‌بل کمتر است. جدول حجم این‌طور تنظیم می‌شود:

cppconst int MAXVOLUME = 8000 ;
const float twodb = 0.8f ;

float currentVolume = MAXVOLUME ;
for (int i = 0 ; i < NUMVOLUMES; i++)
{
  m_VolumeTable[i] = currentVolume ;
  currentVolume *= twodb ;
}

m_VolumeTable[0xF] = 0; // سکوت

نوشتن داده در PSG

همان‌طور که قبلاً اشاره شد، بازی دادهٔ صدا را از طریق پورت‌های 0x7F و 0x7E به PSG می‌نویسد. PSG یک لچ (latch) دارد که ثبات فعلی‌ای است که بایت داده برایش در نظر گرفته شده. ثبات لچ‌شدهٔ اولیه، ثبات تُن کانال 0 است. بایت دادهٔ نوشته‌شده یکی از دو شکل را دارد. شکل اول ثبات لچ‌شدهٔ فعلی را تغییر می‌دهد و داده‌اش را به‌روزرسانی می‌کند. شکل دوم داده‌ای است که برای نوشتن در ثبات لچ‌شدهٔ فعلی در نظر گرفته شده. تفسیر دو نوع دادهٔ مختلف:

textنوع1:  1ccrdddd
نوع2:  0xdddddd

همان‌طور که می‌بینید، دو بایت داده را می‌توان با مقدار بیت 7 تشخیص داد.

نوع 1: اگر بایت داده‌ای که به پورت PSG نوشته می‌شود بیت 7 تنظیم‌شده داشته باشد، تفسیر داده این‌طور است. اول این بایت داده برای به‌روزرسانی ثبات لچ‌شدهٔ فعلی و بعد به‌روزرسانی داده‌اش طراحی شده. بیت‌های 6 و 5 با هم نشان می‌دهند کدام کانال باید لچ شود و بیت 4 نشان می‌دهد باید ثبات حجم را لچ کنید یا ثبات تُن. مقدار 1 یعنی ثبات حجم و مقدار 0 یعنی ثبات تُن. ۴ بیت باقی‌مانده داده‌ای است که چهار بیت پایین ثباتِ تازه‌لچ‌شده را به‌روزرسانی می‌کند. پس اگر ثبات تازه‌لچ‌شده یک ثبات حجم باشد، ۴ بیت پایین ثبات ۸ بیتی به‌روزرسانی می‌شود در حالی که ۴ بیت بالا بدون تغییر می‌ماند. اما اگر ثبات تُن لچ شود، ۴ بیت پایین ثبات ۱۰ بیتی به‌روزرسانی می‌شود و ۶ بیت بالاتر بدون تغییر می‌ماند؛ به‌جز ثبات نویز که فقط ۴ بیتی است و کل ثبات به‌روزرسانی می‌شود.

نوع 2: اگر ثبات لچ‌شدهٔ فعلی یک ثبات تُن باشد، ۶ بیت پایین بایت داده برای به‌روزرسانی ۶ بیت بالای ثبات ۱۰ بیتی استفاده می‌شود و ۴ بیت پایین بدون تغییر می‌ماند. استثنا دوباره ثبات نویز است که فقط ۴ بیتی است؛ پس ۴ بیت پایین بایت داده کاملاً ثبات نویز ۴ بیتی را به‌روزرسانی می‌کند. اگر ثبات لچ‌شدهٔ فعلی یک ثبات حجم باشد، ۴ بیت پایین بایت داده، ۴ بیت پایین ثبات حجم ۸ بیتی را به‌روزرسانی می‌کند.

برای منظم ماندن محتوای این صفحه، کد شبیه‌سازی این بخش از شبیه‌سازی PSG به یک فایل متنی اضافه شده به‌جای شلوغ‌کردن صفحه؛ چون کد بزرگی است. این قطعه کد باید خودتوضیح باشد به‌جز متغیر m_LFSR که در بخش کانال نویز همین صفحه توضیح داده می‌شود. این قطعه کد از ۴ متغیر عضو استفاده می‌کند که هنوز توضیح نداده‌ام: m_Tones، m_Volume، m_LatchedChannel و m_IsToneLatched:

cppbool m_IsToneLatched ;
BYTE m_LatchedChannel ;
WORD m_Tones[4] ;
BYTE m_Volumes[4] ;

m_LatchedChannel شناسهٔ کانالِ لچ‌شدهٔ فعلی است. اگر 0 باشد، کانال لچ‌شدهٔ فعلی اولین کانال (کانال 0) است. اگر 1 باشد دومین کانال (کانال 1) و اگر 3 باشد کانال نویز (کانال 3)؛ این همان چیزی است که ثابت TONES_NOISE به آن تنظیم شده. m_IsToneLatched یک bool برای تشخیص اینکه کانال لچ‌شدهٔ فعلی ثبات تُن‌اش لچ شده یا ثبات حجم‌اش. ثبات‌های تُن ۱۰ بیتی هستند و چون ۴ کانال داریم، تعریف m_Tones همین است. این ثبات فقط فرکانس نمونهٔ هر کانال را ذخیره می‌کند. m_Volumes مثل m_Tones است فقط برای ثبات‌های حجم ۸ بیتی.

پخش تُن PSG

حالا که همهٔ کانال‌ها با شبیه‌سازی نوشتن‌های psg درست تنظیم شده‌اند، می‌توانیم پخش صدا را شروع کنیم. قبلاً توضیح دادم PSG چگونه با موج مربعی صدا می‌سازد؛ پس این پیاده‌سازی شبیه‌سازی پخش است. چون کانال نویز با سه کانال اول متفاوت کار می‌کند، پیاده‌سازی کانال نویز را بعداً بحث می‌کنم. فعلاً سه کانال اول را شبیه‌سازی می‌کنم. چند متغیر در این قطعه کد استفاده شده که هنوز تعریف نشده‌اند:

متغیر m_Polarity که قطبیت هر کانال را نگه می‌دارد؛ یا 1 است یا -1. در ابتدا برای هر کانال 1 تنظیم می‌شود. m_Counters که ابتدا به فرکانس متغیر تنظیم و تا 0 شمارش معکوس می‌شود. وقتی به 0 رسید، قطبیت تغییر می‌کند و شمارنده به فرکانس همان کانال بازنشانی می‌شود. m_CurrentPosition جایی است که دادهٔ پخش در آرایهٔ بافر پخش می‌رود. وقتی کارت صدا بافر پخش ما را درخواست کند، این متغیر به 0 بازنشانی می‌شود. m_PlaybackBuffer بافری است که کارت صدا برای پخش درخواست می‌کند:

cppBYTE m_Polarity[4] ;
int m_Counters[4] ;
int m_CurrentPosition ;
signed int m_PlaybackBuffer[1024] ;

دلیل ۱۰۲۴ عنصری بودن بافر پخش این است که نویسنده از کتابخانهٔ صوتی SDL استفاده می‌کند و این همان اندازه‌ای است که به SDL گفته بود بافر پخش‌اش است تا بداند هر چند وقت بافر را درخواست کند:

cppvoid SN79489::Playback( float cyclesMac )
{
  int floor = 0 ;
  if (NotTimeToUpdate(cyclesMac,floor))
    return ;

  // پخش تُن
  signed short int tone = 0 ;

  for (int i = 0 ; i < 3; i++)
  {
    if (m_Tones[i] == 0)
      continue ;

    m_Counters[i] -= floor;

    if (m_Counters[i] <= 0) // وقت تغییر قطبیت است
    {
      m_Counters[i] = m_Tones[i] ; // شمارنده را بازنشانی کن
      m_Polarity[i] *= -1 ; // قطبیت را تغییر بده
    }

    tone += m_VolumeTable[m_Volume[i]] * m_Polarity[i] ;
  }

  signed short int noiseTone = 0 ;
  // کد گرفتن خروجی نویز اینجا می‌آید
  m_PlaybackBuffer[m_CurrentPosition] = tone + noiseTone ;
  m_CurrentPosition++ ;
}

می‌بینید وقتی تُن 0 تنظیم شود صدا تولید نمی‌شود. امیدواریم همهٔ کد بالا روشن باشد. جایی که کد خروجی کانال نویز می‌آید را با کامنت نشان دادم. تابع NotTimeToUpdate مطمئن می‌شود بافر پخش فقط هر 224khz به‌روزرسانی می‌شود. اگر false برگرداند داده‌ای محاسبه نمی‌شود؛ اما اگر true برگرداند، متغیر floor به تعداد چرخه‌هایی تنظیم می‌شود که شمارنده‌ها باید با آن کم شوند.

پخش نویز PSG

پخش نویز کمی با پخش سه کانال دیگر فرق دارد. هرچند از شمارنده‌ای برای تغییر قطبیت کانال نویز استفاده می‌شود، به‌جای خوراک مستقیم این خروجی به بافر پخش مثل بقیهٔ کانال‌ها، این خروجی به‌عنوان ورودی یک ثبات تغییر خطی بازخوردی (linear feedback shift register) برای تولید نویز استفاده می‌شود. کانال نویز یا نویز سفید تولید می‌کند یا نویز دوره‌ای، بر اساس مقدار بیت 2 از ثبات نویز. اگر مقدار 1 باشد نویز سفید وگرنه نویز دوره‌ای تولید می‌شود. ثبات تغییر خطی بازخوردی یک آرایهٔ ۱۶ بیتی است که بیتش هر بار که قطبیت از -1 به 1 تغییر کند (در پایان یک موج مربعی کامل) به چپ یا راست شیفت می‌شود (مهم نیست). بیتی که از آرایه خارج می‌شود به‌عنوان ورودی میکسر استفاده می‌شود.

نویسنده به راهنمای maxims برای جزئیات تولید نویز ارجاع می‌دهد؛ چون بهتر از او توضیحش می‌دهد. پیاده‌سازی تولید نویز از روی راهنمای Maxim:

cppif (m_Tones[TONES_NOISE] != 0)
{
  m_Counters[TONES_NOISE] -= floor ;

  if (m_Counters[TONES_NOISE] <= 0)
  {
    // ۲ بیت آخر ثبات نویز یک جستجوی فرکانس دارند
    WORD freq = m_Tones[TONES_NOISE] ;
    freq &= 0x3 ;

    // شمارندهٔ نویز را بازنشانی کن
    int count = 0 ;
    switch(freq)
    {
      case 0: count = 0x10; break ;
      case 1: count = 0x20; break ;
      case 2: count = 0x40; break ;
      case 3: count = m_Tones[CHANNEL_TWO]; break ;
    }

    m_Counters[TONES_NOISE] = count ;
    m_Polarity[TONES_NOISE] *= -1 ;

    // اگر قطبیت از -1 به 1 تغییر کرد، عدد تصادفی را شیفت بده
    if (m_Polarity[TONES_NOISE] == 1)
    {
      bool isWhiteNoise = TestBit(m_Tones[TONES_NOISE],2) ;
      BYTE tappedBits = BitGetVal(m_Tones[TONES_NOISE], 0) ;
      tappedBits |= (BitGetVal(m_Tones[TONES_NOISE], 3) << 3);

      m_LFSR = (m_LFSR>>1) | ((isWhiteNoise?parity(m_LFSR&tappedBits):m_LFSR&1)<<15);
    }
  }

  noiseTone = m_VolumeTable[m_Volume[TONES_NOISE]] * (m_LFSR & 1) ;
}

کد بالا در تابع Playback که در بخش قبلی این صفحه دادم، جایی که کامنت «کد گرفتن خروجی نویز اینجا می‌آید» بود، قرار می‌گیرد. تابع parity اگر داده تعداد زوجی بیت روشن داشته باشد 1 برمی‌گرداند و اگر تعداد فردی بیت روشن داشته باشد 0.

زمان‌بندی PSG

قبلاً گفتیم تابع پخش باید با نرخ 224khz صدا زده شود. اگر با سرعت درست صدا زده نشود، هرچند آهنگی که پخش می‌شود درست به نظر می‌رسد، تُن نت‌ها نادرست خواهد بود. تابع NotTimeToUpdate برای همین استفاده می‌شود. با آن محاسبه می‌کنیم وقت به‌روزرسانی بافر پخش و کاهش شمارنده‌های کانال است یا نه. متغیر floor به عددی تنظیم می‌شود که شمارنده‌ها باید با آن کاهش یابند. صدا زدن تابع پخش دقیقاً با 224khz تقریباً غیرممکن است؛ پس باید دقت را حفظ کنید. به همین دلیل floor یک int است؛ هرچند با int کردن دقت ممیز شناور از بین می‌رود، باز هم مقدار شناور را نگه می‌دارم و دفعهٔ بعدِ صدا زدن تابع پخش در نظر می‌گیرم. می‌بینید تابع پخش آرگومانی برای تعداد machineCycles اجراشده از آخرین بارِ صدا زدن تابع دارد. همان‌طور که قبلاً گفتیم، ساعت PSG سه برابر کندتر از ساعت ماشین است؛ پس تابع NotTimeToUpdate بلافاصله این مقدار را بر 3 تقسیم می‌کند. اما PSG با نرخی ۱۶ برابر کندتر از ساعتش کار می‌کند؛ پس این مقدار باید بعد بر 16 هم تقسیم شود.

پخش بافر پخش

چند راه برای پخش بافر پخش وجود دارد؛ مثلاً DirectSound، OpenAl یا استفاده از کتابخانهٔ صدای SDL. نویسنده شخصاً با کتابخانهٔ صدای SDL رفته و از نتیجه راضی است. انتخاب API را به خودتان واگذار می‌کند؛ همان‌طور که با رندر گرافیک کرد. اگر با کتابخانهٔ SDL بروید به ساختار SDL_AudioSpec نگاه کنید. اگر هنوز مشکل دارید، نگاه کنید نویسنده در کد منبع‌اش (که در لینک «پروژهٔ تمام‌شده» سمت راست صفحه است) چطور استفاده‌اش کرده.

پروژهٔ تمام‌شده (The Finished Project)

شبیه‌سازی مستر سیستم تمام شد؛ با تلاش زیاد اما نتیجه‌ای رضایت‌بخش. نویسنده امیدوار است حالا درک کامل‌تری از مستر سیستم و نحوهٔ شبیه‌سازی آن داشته باشید. او کد منبع شبیه‌ساز را ارائه می‌دهد؛ با این شرط که هر طور دوست دارید از کد استفاده کنید فقط تا زمانی که اعتبار آن به او داده شود. به یاد داشته باشید برای استفاده از کد و اجرای بازی‌ها باید واقعاً یک مستر سیستم و بازی‌های آن را داشته باشید؛ هر کار دیگری خلاف قانون است.

خواهید دید کد منبع شبیه‌ساز دقیقاً با مثال‌های این آموزش یکی نیست؛ چون وقتی نویسنده شبیه‌ساز را می‌نوشت مطمئن نبود چه چیزی کار می‌کند و چه چیزی نه. اما آموزش‌ها بر اساس بهترین راه شبیه‌سازی مستر سیستم نوشته شدند؛ با دانشی که بعد از موفقیت در نوشتن شبیه‌ساز به دست آورد.
