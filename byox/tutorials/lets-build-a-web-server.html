۱. مقدمه — داستان سه بنا

یک روز، زنی در حال قدم‌زدن به یک کارگاه ساختمانی رسید و سه مرد را دید که مشغول کارند. از مرد اول پرسید: «چه کار می‌کنی؟» مرد اول که از سؤال عصبانی شده بود گفت: «مگر نمی‌بینی دارم آجر می‌چینم؟» زن که از پاسخ راضی نشده بود از مرد دوم پرسید چه می‌کند. مرد دوم جواب داد: «دارم دیوار آجری می‌سازم.» بعد رو به مرد اول کرد و گفت: «هی، تازه از انتهای دیوار رد شدی. باید آن آجر آخر را بردارید.» باز هم زن از پاسخ راضی نشد و از مرد سوم پرسید. مرد سوم در حالی که به آسمان نگاه می‌کرد گفت: «من دارم بزرگ‌ترین کلیسای جامعی را می‌سازم که این دنیا به خودش دیده.» در حالی که او همین‌طور ایستاده بود و به آسمان نگاه می‌کرد، دو مرد دیگر سرِ همان آجر سرگردان شروع به جر و بحث کردند. مرد رو به آن دو کرد و گفت: «بچه‌ها، نگران آن آجر نباشید. آجر دیوار داخلی است، رویش گچ‌کاری می‌شود و هیچ‌کس هرگز آن را نخواهد دید. فقط بروید سراغ لایه بعدی.»

پند این داستان این است که وقتی کل سیستم را بشناسید و بفهمید اجزای مختلف (آجرها، دیوارها، کلیسای جامع) چگونه به هم می‌چسبند، می‌توانید مشکلات را سریع‌تر شناسایی و حل کنید (آجر سرگردان).

این چه ربطی به ساخت وب سرور از صفر دارد؟ نویسنده معتقد است برای اینکه توسعه‌دهنده بهتری شوید، باید درک بهتری از سیستم‌های نرم‌افزاری زیربنایی که هر روز استفاده می‌کنید به دست آورید — زبان‌های برنامه‌نویسی، کامپایلرها و مفسرها، پایگاه‌های داده و سیستم‌عامل‌ها، وب سرورها و فریم‌ورک‌های وب. و برای رسیدن به این درک عمیق‌تر باید آن‌ها را از صفر بازسازی کنید: آجر به آجر، دیوار به دیوار.

کنفوسیوس این‌طور بیانش کرده:

«می‌شنوم و فراموش می‌کنم.»
«می‌بینم و به یاد می‌آورم.»
«انجام می‌دهم و می‌فهمم.»

امیدوارم تا اینجا قانع شده باشید که شروع به بازسازی سیستم‌های نرم‌افزاری مختلف برای یادگیری نحوه کارشان، ایده خوبی است. در این مجموعه سه‌قسمتی نشانتان می‌دهم چگونه وب سرور پایه خودتان را بسازید. بزنید بریم.

۲. وب سرور چیست؟

به زبان ساده، یک وب سرور یک سرور شبکه‌ای است که روی یک سرور فیزیکی می‌نشیند (آخ، سرور روی سرور!) و منتظر می‌ماند تا یک کلاینت درخواستی بفرستد. وقتی درخواست را دریافت می‌کند، یک پاسخ تولید می‌کند و برای کلاینت برمی‌فرستد. ارتباط بین کلاینت و سرور با پروتکل HTTP انجام می‌شود. کلاینت می‌تواند مرورگر شما یا هر نرم‌افزار دیگری باشد که HTTP صحبت می‌کند.

یک پیاده‌سازی بسیار ساده از وب سرور چه شکلی است؟ این برداشت نویسنده است. مثال به زبان پایتون (تست‌شده روی Python 3.7+) — حتی اگر پایتون بلد نیستید (زبان بسیار ساده‌ای است، امتحانش کنید!)، باید بتوانید مفاهیم را از کد و توضیحات زیر بفهمید:

python# Python3.7+
import socket

HOST, PORT = '', 8888

listen_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
listen_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
listen_socket.bind((HOST, PORT))
listen_socket.listen(1)
print(f'Serving HTTP on port {PORT} ...')
while True:
    client_connection, client_address = listen_socket.accept()
    request_data = client_connection.recv(1024)
    print(request_data.decode('utf-8'))

    http_response = b"""\
HTTP/1.1 200 OK

Hello, World!
"""
    client_connection.sendall(http_response)
    client_connection.close()

کد بالا را به‌عنوان webserver1.py ذخیره کنید یا مستقیم از گیت‌هاب دانلودش کنید و در خط فرمان اجرا کنید:

bash$ python webserver1.py
Serving HTTP on port 8888 ...

حالا این آدرس را در نوار آدرس مرورگرتان تایپ کنید: http://localhost:8888/hello، Enter بزنید و جادو را در عمل ببینید. باید «Hello, World!» در مرورگر نمایش داده شود. فقط انجامش دهید — جدی می‌گویم. در حالی که تست می‌کنید منتظرتان می‌مانم.

این‌طور به مرورگرتان می‌گویید آدرس وب سروری که باید پیدا کند و به آن وصل شود، و کدام صفحه (مسیر) را روی سرور برایتان واکشی کند چیست. اما قبل از اینکه مرورگر بتواند درخواست HTTP بفرستد، اول باید یک اتصال TCP با وب سرور برقرار کند. بعد یک درخواست HTTP روی آن اتصال TCP به سرور می‌فرستد و منتظر می‌ماند تا سرور پاسخ HTTP را برگرداند. و وقتی مرورگر پاسخ را دریافت می‌کند، آن را نمایش می‌دهد — در این حالت «Hello, World!».

۴. سوکت‌ها: برقراری اتصال TCP

بگذارید با جزئیات بیشتری ببینیم کلاینت و سرور قبل از فرستادن درخواست و پاسخ HTTP چگونه یک اتصال TCP برقرار می‌کنند. برای این کار هر دو از اصطلاحاً سوکت (Socket) استفاده می‌کنند. به‌جای استفاده مستقیم از مرورگر، مرورگر را به‌صورت دستی با telnet در خط فرمان شبیه‌سازی می‌کنید.

روی همان کامپیوتری که وب سرور را اجرا کرده‌اید، یک نشست telnet در خط فرمان باز کنید، هاست localhost و پورت 8888 را مشخص کنید و Enter بزنید:

bash$ telnet localhost 8888
Trying 127.0.0.1 ...
Connected to localhost.

تا اینجا یک اتصال TCP با سروری که روی هاست محلی اجرا می‌شود برقرار کرده‌اید و آماده فرستادن و دریافت پیام‌های HTTP هستید. در تصویر زیر، رویه استانداردی که یک سرور برای توانایی پذیرفتن اتصال‌های TCP جدید باید طی کند را می‌بینید:

در همان نشست telnet رشته GET /hello HTTP/1.1 را تایپ کنید و Enter بزنید:

bash$ telnet localhost 8888
Trying 127.0.0.1 ...
Connected to localhost.
GET /hello HTTP/1.1

HTTP/1.1 200 OK
Hello, World!

همین الان مرورگر را به‌صورت دستی شبیه‌سازی کردید! یک درخواست HTTP فرستادید و یک پاسخ HTTP دریافت کردید. این هم ساختار پایه یک درخواست HTTP:

درخواست HTTP از خطی تشکیل شده که نشان‌دهنده متد HTTP است (GET، چون از سرور می‌خواهیم چیزی برایمان برگرداند)، مسیر /hello که «صفحه» موردنظر ما روی سرور را نشان می‌دهد و نسخه پروتکل.

برای سادگی، وب سرور ما در این مرحله خط درخواست بالا را کاملاً نادیده می‌گیرد. می‌توانستید هر چیز بی‌ربطی به‌جای «GET /hello HTTP/1.1» تایپ کنید و باز هم پاسخ «Hello, World!» دریافت کنید.

۵. آناتومی پاسخ HTTP

به‌محض تایپ خط درخواست و زدن Enter، کلاینت درخواست را می‌فرستد، سرور خط درخواست را می‌خواند، چاپش می‌کند و پاسخ HTTP مناسب را برمی‌گرداند.

این پاسخی است که سرور به کلاینت‌تان (در این‌جا telnet) برمی‌گرداند:

تشریحش کنیم. پاسخ از یک خط وضعیت به‌شکل HTTP/1.1 200 OK تشکیل شده، بعد از آن یک خط خالی اجباری و سپس بدنه پاسخ HTTP.

خط وضعیت پاسخ از نسخه HTTP، کد وضعیت HTTP و عبارت دلیل کد وضعیت (OK) تشکیل شده. وقتی مرورگر پاسخ را دریافت می‌کند، بدنه پاسخ را نمایش می‌دهد و به همین دلیل است که «Hello, World!» را در مرورگر می‌بینید.

۶. جمع‌بندی: مدل پایه وب سرور

و این هم مدل پایه کارکرد یک وب سرور. برای جمع‌بندی: وب سرور یک سوکت شنود می‌سازد و در یک حلقه شروع به پذیرفتن اتصال‌های جدید می‌کند. کلاینت یک اتصال TCP را آغاز می‌کند و بعد از برقراری موفق آن، درخواست HTTP را برای سرور می‌فرستد و سرور با یک پاسخ HTTP جواب می‌دهد که به کاربر نمایش داده می‌شود. برای برقراری اتصال TCP، هم کلاینت‌ها و هم سرورها از سوکت استفاده می‌کنند.

حالا یک وب سرور پایه و کار دارید که می‌توانید با مرورگر یا هر کلاینت HTTP دیگری تستش کنید. همان‌طور که دیدید — و امیدوارم امتحانش کردید — می‌توانید خودتان هم یک کلاینت HTTP انسانی باشید: با telnet و تایپ دستی درخواست‌های HTTP.

سؤال: «چطور می‌شود یک اپلیکیشن Django، یک اپلیکیشن Flask و یک اپلیکیشن Pyramid را بدون اینکه حتی یک تغییر در سرور تازه‌ساخت خودتان بدهید، زیر آن اجرا کنید تا همه آن فریم‌ورک‌های وب مختلف را پشتیبانی کند؟» دقیقاً همین را در قسمت ۲ این مجموعه نشانتان می‌دهم. منتظر باشید.
