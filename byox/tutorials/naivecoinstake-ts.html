۱. بلاک‌چین کاری حداقلی (Minimal working blockchain)

مرور کلی

مفهوم پایهٔ بلاک‌چین بسیار ساده است: یک پایگاه دادهٔ توزیع‌شده که فهرستی پیوسته‌درحال‌رشد از رکوردهای مرتب را نگهداری می‌کند. در این فصل نسخهٔ آزمایشی (اسباب‌بازی) از چنین بلاک‌چینی را پیاده‌سازی می‌کنیم. در پایان فصل این قابلیت‌های پایه را خواهیم داشت:

  • ساختار مشخص بلاک و بلاک‌چین
  • متدهایی برای افزودن بلاک‌های جدید به بلاک‌چین با داده‌های دلخواه
  • گره‌های بلاک‌چین که با گره‌های دیگر ارتباط برقرار می‌کنند و بلاک‌چین را همگام‌سازی می‌کنند
  • یک API سادهٔ HTTP برای کنترل گره

این فصل از آموزش اصلی Naivecoin نوشتهٔ Lauri Hartikka کپی شده و برای سازوکار اجماع «اثبات سهام» (Proof of Stake) تطبیق داده شده است. صفحهٔ اصلی آن را اینجا ببینید.

ساختار بلاک

کار را با تعریف ساختار بلاک آغاز می‌کنیم. در این مرحله فقط اساسی‌ترین ویژگی‌ها در بلاک قرار می‌گیرند:

  • index: ارتفاع بلاک در بلاک‌چین
  • data: هر داده‌ای که در بلاک قرار می‌گیرد
  • timestamp: برچسب زمانی
  • hash: هش sha256 گرفته‌شده از محتوای بلاک
  • previousHash: ارجاع به هش بلاک قبلی؛ این مقدار بلاک قبلی را به‌صراحت مشخص می‌کند

کد ساختار بلاک به این صورت است:

typescript// کلاس بلاک: ساختار پایه هر بلاک در بلاک‌چین
class Block {

    public index: number;          // ارتفاع بلاک در زنجیره
    public hash: string;           // هش بلاک (شناسه یکتا)
    public previousHash: string;   // هش بلاک قبلی
    public timestamp: number;      // برچسب زمانی (ثانیه)
    public data: string;           // داده‌های ذخیره‌شده در بلاک

    constructor(index: number, hash: string, previousHash: string, timestamp: number, data: string) {
        this.index = index;
        this.previousHash = previousHash;
        this.timestamp = timestamp;
        this.data = data;
        this.hash = hash;
    }
}

هش بلاک

هش بلاک یکی از مهم‌ترین ویژگی‌های آن است. هش روی تمام داده‌های بلاک محاسبه می‌شود؛ یعنی اگر هر چیزی در بلاک تغییر کند، هش اصلی دیگر معتبر نیست. هش بلاک را می‌توان شناسهٔ یکتای بلاک هم در نظر گرفت؛ برای مثال ممکن است بلاک‌هایی با index یکسان وجود داشته باشند، اما همهٔ آن‌ها هش‌های یکتا دارند.

هش بلاک را با کد زیر محاسبه می‌کنیم:

typescript// محاسبه هش بلاک با تابع SHA256 بر اساس محتوای بلاک
const calculateHash = (index: number, previousHash: string, timestamp: number, data: string): string =>
    CryptoJS.SHA256(index + previousHash + timestamp + data).toString();

باید توجه داشت که هش بلاک هنوز هیچ ارتباطی با استخراج (mining) ندارد، چون هیچ مسئلهٔ «اثبات کار» برای حل وجود ندارد. ما از هش بلاک برای حفظ یکپارچگی (integrity) بلاک و ارجاع صریح به بلاک قبلی استفاده می‌کنیم.

یک پیامد مهم ویژگی‌های hash و previousHash این است که نمی‌توان بلاکی را تغییر داد بدون آنکه هشِ همهٔ بلاک‌های متوالی بعدی تغییر کند.

این موضوع در مثال زیر نشان داده شده است: اگر دادهٔ بلاک ۴۴ از «DESERT» به «STREET» تغییر کند، باید هش همهٔ بلاک‌های بعدی نیز تغییر کند. علت این است که hash هر بلاک به مقدار previousHash (در میان چیزهای دیگر) وابسته است.

این ویژگی به‌ویژه وقتی اثبات کار معرفی شود اهمیت دارد: هرچه بلاک در اعماق بلاک‌چین باشد، تغییر آن سخت‌تر است، چون مستلزم تغییر همهٔ بلاک‌های متوالی است.

بلاک پیدایش (Genesis block)

بلاک پیدایش اولین بلاک در بلاک‌چین است و تنها بلاکی است که previousHash ندارد. بلاک پیدایش را به‌صورت ثابت (hard code) در کد منبع قرار می‌دهیم: 

typescript// بلاک پیدایش: اولین بلاک زنجیره که بلاک قبلی ندارد
const genesisBlock: Block = new Block(
    0, '816534932c2b7154836da6afc367695e6337db8a921823784c14378abed4f7d7', null, 1465154705, 'my genesis block!!'
);

تولید یک بلاک

برای تولید بلاک باید هش بلاک قبلی را بدانیم و بقیهٔ محتوای لازم (یعنی index، hash، data و timestamp) را بسازیم. دادهٔ بلاک توسط کاربر نهایی ارائه می‌شود، اما بقیهٔ پارامترها با کد زیر تولید می‌شوند: 

typescript// تولید بلاک بعدی بر اساس آخرین بلاک زنجیره و داده ورودی
const generateNextBlock = (blockData: string) => {
    const previousBlock: Block = getLatestBlock();               // آخرین بلاک فعلی
    const nextIndex: number = previousBlock.index + 1;           // ارتفاع بلاک بعدی
    const nextTimestamp: number = new Date().getTime() / 1000;   // زمان فعلی به ثانیه
    const nextHash: string = calculateHash(nextIndex, previousBlock.hash, nextTimestamp, blockData);
    const newBlock: Block = new Block(nextIndex, nextHash, previousBlock.hash, nextTimestamp, blockData);
    return newBlock;
};

ذخیره‌سازی بلاک‌چین

فعلاً برای ذخیرهٔ بلاک‌چین فقط از یک آرایهٔ جاوااسکریپتی در حافظه استفاده می‌کنیم؛ یعنی وقتی گره خاموش شود، داده‌ها ماندگار نخواهند بود. 

typescript// بلاک‌چین: آرایه‌ای در حافظه که با بلاک پیدایش شروع می‌شود
const blockchain: Block[] = [genesisBlock];

اعتبارسنجی یکپارچگی بلاک‌ها

در هر لحظه باید بتوانیم اعتبار یک بلاک یا زنجیره‌ای از بلاک‌ها را از نظر یکپارچگی بررسی کنیم. این موضوع به‌ویژه وقتی بلاک‌های جدیدی از گره‌های دیگر دریافت می‌کنیم و باید تصمیم بگیریم که آن‌ها را بپذیریم یا نه، اهمیت دارد.

برای معتبر بودن یک بلاک باید این شرایط برقرار باشد:

  • شمارهٔ index بلاک باید دقیقاً یک عدد بزرگ‌تر از بلاک قبلی باشد
  • previousHash بلاک باید با hash بلاک قبلی یکسان باشد
  • hash خود بلاک باید معتبر باشد

این بررسی‌ها با کد زیر انجام می‌شود:

typescript// بررسی اعتبار یک بلاک جدید نسبت به بلاک قبلی
const isValidNewBlock = (newBlock: Block, previousBlock: Block) => {
    if (previousBlock.index + 1 !== newBlock.index) {
        console.log('invalid index');              // شاخص نامعتبر است
        return false;
    } else if (previousBlock.hash !== newBlock.previousHash) {
        console.log('invalid previoushash');       // هش بلاک قبلی مطابقت ندارد
        return false;
    } else if (calculateHashForBlock(newBlock) !== newBlock.hash) {
        console.log(typeof (newBlock.hash) + ' ' + typeof calculateHashForBlock(newBlock));
        console.log('invalid hash: ' + calculateHashForBlock(newBlock) + ' ' + newBlock.hash);
        return false;
    }
    return true;
};

باید ساختار بلاک را هم اعتبارسنجی کنیم تا محتوای خرابی که یک همتا (peer) می‌فرستد باعث از کار افتادن گره نشود: 

typescript// بررسی اعتبار ساختار بلاک (انواع فیلدها)
const isValidBlockStructure = (block: Block): boolean => {
    return typeof block.index === 'number'
        && typeof block.hash === 'string'
        && typeof block.previousHash === 'string'
        && typeof block.timestamp === 'number'
        && typeof block.data === 'string';
};

حالا که ابزار اعتبارسنجی یک بلاک را داریم، می‌توانیم سراغ اعتبارسنجی کل زنجیره برویم. ابتدا بررسی می‌کنیم که اولین بلاک زنجیره با genesisBlock یکسان باشد و سپس همهٔ بلاک‌های متوالی را با روش‌های قبلاً شرح‌داده‌شده اعتبارسنجی می‌کنیم: 

typescript// اعتبارسنجی کل زنجیره بلاک‌ها
const isValidChain = (blockchainToValidate: Block[]): boolean => {
    const isValidGenesis = (block: Block): boolean => {
        return JSON.stringify(block) === JSON.stringify(genesisBlock);  // بلاک اول باید با بلاک پیدایش یکسان باشد
    };

    if (!isValidGenesis(blockchainToValidate[0])) {
        return false;
    }

    // اعتبارسنجی تک‌تک بلاک‌های بعدی نسبت به بلاک قبلی
    for (let i = 1; i < blockchainToValidate.length; i++) {
        if (!isValidNewBlock(blockchainToValidate[i], blockchainToValidate[i - 1])) {
            return false;
        }
    }
    return true;
};

انتخاب بلندترین زنجیره

در هر لحظه باید فقط یک مجموعهٔ صریح از بلاک‌ها در زنجیره وجود داشته باشد. در صورت بروز تعارض (مثلاً دو گره هر دو بلاک شمارهٔ ۷۲ را تولید کنند)، زنجیره‌ای را انتخاب می‌کنیم که تعداد بلاک‌های بیشتری دارد. در مثال زیر، دادهٔ معرفی‌شده در بلاک ۷۲ یعنی a350235b00 در بلاک‌چین لحاظ نخواهد شد، چون توسط زنجیرهٔ بلندتر بازنویسی می‌شود.

این منطق با کد زیر پیاده‌سازی می‌شود:

typescript// جایگزینی زنجیره فعلی با زنجیره جدید اگر معتبرتر و بلندتر باشد
const replaceChain = (newBlocks: Block[]) => {
    if (isValidChain(newBlocks) && newBlocks.length > getBlockchain().length) {
        console.log('Received blockchain is valid. Replacing current blockchain with received blockchain');
        blockchain = newBlocks;   // زنجیره دریافتی معتبر است؛ زنجیره فعلی جایگزین می‌شود
        broadcastLatest();        // اعلام جدیدترین بلاک به شبکه
    } else {
        console.log('Received blockchain invalid');
    }
};

ارتباط با گره‌های دیگر

بخش اساسی هر گره، به اشتراک‌گذاری و همگام‌سازی بلاک‌چین با گره‌های دیگر است. برای همگام نگه‌داشتن شبکه این قوانین به کار می‌روند:

  • وقتی گره بلاک جدیدی تولید می‌کند، آن را به شبکه پخش (broadcast) می‌کند
  • وقتی گره به همتای جدیدی متصل می‌شود، آخرین بلاک را از آن می‌پرسد
  • وقتی گره به بلاکی برخورد می‌کند که index آن بزرگ‌تر از بلاک شناخته‌شدهٔ فعلی است، آن بلاک را به زنجیرهٔ فعلی خود اضافه می‌کند یا کل بلاک‌چین را درخواست می‌کند

برای ارتباط همتا به همتا از وب‌سوکت (websocket) استفاده می‌کنیم. سوکت‌های فعال هر گره در متغیر const sockets: WebSocket[] ذخیره می‌شوند. هیچ کشف خودکار همتا استفاده نمی‌شود و آدرس‌ها (= URLهای وب‌سوکت) همتایان باید به‌صورت دستی اضافه شوند.

کنترل گره

کاربر باید بتواند به نحوی گره را کنترل کند. این کار با راه‌اندازی یک سرور HTTP انجام می‌شود:

typescript// راه‌اندازی سرور HTTP برای کنترل گره
const initHttpServer = ( myHttpPort: number ) => {
    const app = express();
    app.use(bodyParser.json());

    // دریافت لیست تمام بلاک‌ها
    app.get('/blocks', (req, res) => {
        res.send(getBlockchain());
    });

    // تولید بلاک جدید با داده ارسال‌شده
    app.post('/mintBlock', (req, res) => {
        const newBlock: Block = generateNextBlock(req.body.data);
        res.send(newBlock);
    });

    // دریافت لیست همتایان متصل
    app.get('/peers', (req, res) => {
        res.send(getSockets().map(( s: any ) => s._socket.remoteAddress + ':' + s._socket.remotePort));
    });

    // افزودن همتای جدید
    app.post('/addPeer', (req, res) => {
        connectToPeers(req.body.peer);
        res.send();
    });

    app.listen(myHttpPort, () => {
        console.log('Listening http on port: ' + myHttpPort);
    });
};

همان‌طور که دیده می‌شود، کاربر به این روش‌ها می‌تواند با گره تعامل کند:

  • فهرست کردن همهٔ بلاک‌ها
  • ساخت بلاک جدید با محتوایی که کاربر تعیین می‌کند
  • فهرست کردن یا افزودن همتاها

ساده‌ترین راه کنترل گره مثلاً با Curl است:

bash# دریافت همه بلاک‌ها از گره

معماری

باید توجه داشت که گره در واقع دو وب‌سرور را در معرض دید قرار می‌دهد: یکی برای کنترل گره توسط کاربر (سرور HTTP) و یکی برای ارتباط همتا به همتا بین گره‌ها (سرور وب‌سوکت HTTP).

جمع‌بندی

Naivecoin در حال حاضر فقط یک بلاک‌چین «همه‌منظوره»ٔ آزمایشی است. این فصل نشان می‌دهد که می‌توان برخی از اصول پایهٔ بلاک‌چین را به روشی نسبتاً ساده پیاده‌سازی کرد. در فصل بعد، الگوریتم اثبات سهام (minting) را به naivecoin اضافه می‌کنیم.

۲. اثبات سهام (Proof of Stake)

مرور کلی

در این فصل اجماعی را پیاده‌سازی می‌کنیم که به‌صورت توزیع‌شده تصمیم می‌گیرد کدام بلاک باید بعدی در بلاک‌چین باشد. الگوریتم‌های اجماع گوناگونی با قواعد متفاوت برای رسیدن به این هدف وجود دارد (اطلاعات بیشتر اینجا). دو اجماع مشهور «اثبات کار» (Proof of Work یا PoW) و «اثبات سهام» (Proof of Stake یا PoS) هستند.

در اثبات کار، هرچه توان محاسباتی گره شما بیشتر باشد، شانس بیشتری برای یافتن بلاک بعدی دارید؛ گره‌ها برای یافتن بلاک باید هش‌های بسیار زیادی محاسبه کنند. این فرایند «استخراج» (mining) نام دارد و برق زیادی مصرف می‌کند. برای جلوگیری از این اتلاف، کوین Peercoin اجماع «اثبات سهام» را معرفی کرد که به گره‌هایی که کوین بیشتری در اختیار دارند، شانس بیشتری برای یافتن بلاک می‌دهد. این فرایند «ضراب‌زنی» (minting) نام دارد. الگوریتم اثبات سهام پیاده‌سازی‌شده در اینجا بر اساس این مقاله از Vitalik Buterin است. همچنین به یاد داشته باشید که پیاده‌سازی‌های گوناگونی از اثبات سهام وجود دارد.

این فصل همچنین نشان می‌دهد که چگونه می‌توان با تغییر سختی (difficulty)، بازهٔ تولید بلاک را کنترل کرد.

باید توجه داشت که در این فصل هنوز تراکنش‌ها را معرفی نمی‌کنیم؛ یعنی در واقع انگیزه‌ای برای ضراب‌زن‌ها (minters) جهت تولید بلاک وجود ندارد. معمولاً در ارزهای دیجیتال، گره برای یافتن بلاک پاداش می‌گیرد، اما هنوز در بلاک‌چین ما چنین نیست.

اگر به دنبال پیاده‌سازی اجماع اثبات کار هستید، توصیه می‌کنیم آموزش اصلی Naivecoin را بخوانید: https://lhartikk.github.io/jekyll/update/2017/07/13/chapter2.html.

سختی و معمای اثبات سهام

سه ویژگی به ساختار بلاک اضافه می‌کنیم:

  • difficulty: عددی که برای ثابت نگه‌داشتن فاصلهٔ زمانی بین بلاک‌ها استفاده می‌شود
  • minterBalance: موجودی گره‌ای که در حال ضراب‌زنی است (بلاک را می‌یابد)
  • minterAddress: آدرس گره‌ای که در حال ضراب‌زنی است (بلاک را می‌یابد)

توجه کنید که minterBalance و minterAddress برای ساده‌سازی کد اضافه شده‌اند؛ برای minterAddress می‌توان آن را با استفاده از اطلاعات coinbase حذف کرد و minterBalance نیز با خروجی‌های مصرف‌نشده (UnspentOutput) در شمارهٔ بلاک مشخص قابل محاسبه است و باید محاسبه شود.

ساختار فعلی بلاک به این صورت است:

typescript// کلاس بلاک با ویژگی‌های اثبات سهام
class Block {

    public index: number;
    public hash: string;
    public previousHash: string;
    public timestamp: number;
    public data: Transaction[];
    public difficulty: number;                 // سختی شبکه در این بلاک
    public nonce: number;
    public minterBalance: number;              // موجودی ضراب‌زن — برای اجتناب از محاسبه مجدد موجودی در ارتفاع دقیق
    public minterAddress: string;              // آدرس ضراب‌زن

    constructor(index: number, hash: string, previousHash: string,
                timestamp: number, data: Transaction[], difficulty: number, minterBalance: number, minterAddress: string) {
        this.index = index;
        this.previousHash = previousHash;
        this.timestamp = timestamp;
        this.data = data;
        this.hash = hash;
        this.difficulty = difficulty;
        this.minterBalance = minterBalance;
        this.minterAddress = minterAddress;
    }
}

همچنین محاسبهٔ هش باید با داده‌های جدید به‌روزرسانی شود:

typescript// محاسبه هش با در نظر گرفتن سختی، موجودی و آدرس ضراب‌زن
const calculateHash = (index: number, previousHash: string, timestamp: number, data: Transaction[],
                       difficulty: number, minterBalance: number, minterAddress: string): string =>
    CryptoJS.SHA256(index + previousHash + timestamp + data + difficulty + minterBalance + minterAddress).toString();

حالا معمای اثبات سهام را که برای تصمیم‌گیری دربارهٔ یافتن بلاک به کار می‌رود، در کد شبه (pseudo code) از Vitalik Buterin ببینیم: https://blog.ethereum.org/2014/07/05/stake/ 

text// معمای اثبات سهام: هش باید کوچک‌تر یا مساوی مقدار هدف باشد
SHA256(prevhash + address + timestamp) <= 2^256 * balance / diff

و در ادامه، پیاده‌سازی آن در TypeScript:

typescript// بررسی اعتبار ضراب‌زنی: هش حاصل باید از مقدار هدف کوچک‌تر باشد
const isBlockStakingValid = (prevhash: string, address: string, timestamp: number, balance: number, difficulty: number, index: number): boolean => {
    difficulty = difficulty + 1;

    // برای چند بلاک اول، ضراب‌زنی بدون کوین مجاز است
    if(index <= mintingWithoutCoinIndex) {
        balance = balance + 1;
    }

    // مقدار هدف: (2^256) * balance / difficulty
    const balanceOverDifficulty = new BigNumber(2).exponentiatedBy(256).times(balance).dividedBy(difficulty);
    const stakingHash: string = CryptoJS.SHA256(prevhash + address + timestamp);
    const decimalStakingHash = new BigNumber(stakingHash, 16);   // تبدیل هش به عدد پایه ۱۶
    const difference = balanceOverDifficulty.minus(decimalStakingHash).toNumber();

    return difference >= 0;   // اگر هش از هدف کوچک‌تر باشد، بلاک یافت شده است
};

چون این معما اعداد بسیار بزرگی را مقایسه می‌کند، باید از کتابخانه‌ای استفاده کنیم که توانایی کار با این اعداد را داشته باشد.

همچنین همان‌طور که می‌بینید تابع SHA256() سه ورودی می‌گیرد: prevhash که قابل تغییر نیست، address که بدون تغییر balance قابل تغییر نیست و timestamp که فقط هر یک ثانیه تغییر می‌کند. به همین دلیل هر ثانیه یک‌بار می‌توانید برای یافتن بلاک تلاش کنید که انرژی بسیار کمتری نسبت به اثبات کار مصرف می‌کند.

توجه کنید که اثبات سهام یک محدودیت بزرگ دارد: وقتی بلاک‌چین را با موجودی صفر برای همهٔ حساب‌ها شروع کنید، هیچ‌کس نمی‌تواند کوین خود را stake کند و بلاک بیابد. راه‌های گوناگونی برای حل این مشکل وجود دارد:

  • تولید مقدار مشخصی کوین در بلاک پیدایش و توزیع دستی آن بین گره‌ها (یا فروش آن)
  • استفاده از اجماع اثبات سهام در کنار اثبات کار تا حساب‌های بدون کوین هم شانس موفقیت داشته باشند
  • شبیه‌سازی افزایش موجودی در تعداد محدودی بلاک (که در کد بالا می‌بینیم)

همچنین توجه کنید که گره‌ها همچنان می‌توانند با تغییر timestamp تقلب کنند. برای جلوگیری از این کار، برخی ارزهای دیجیتال نقطه‌های بازرسی (checkpoints) اضافه می‌کنند (که متمرکز هستند و توسط یک مرجع ارسال می‌شوند).

یافتن بلاک

همان‌طور که در بالا شرح داده شد، برای یافتن بلاک باید هر ثانیه معما را امتحان کنیم. این کار با کد زیر انجام می‌شود:

typescript// حلقه یافتن بلاک: هر ثانیه یک بار تلاش برای ضراب‌زنی
const findBlock = (index: number, previousHash: string, data: Transaction[], difficulty: number): Block => {
    let pastTimestamp: number = 0;
    while (true) {
        let timestamp: number = getCurrentTimestamp();   // زمان فعلی
        if(pastTimestamp !== timestamp) {                // فقط یک بار در هر ثانیه تلاش کن
            let hash: string = calculateHash(index, previousHash, timestamp, data, difficulty, getAccountBalance(), getPublicFromWallet());
            if (isBlockStakingValid(previousHash, getPublicFromWallet(), timestamp, getAccountBalance(), difficulty, index)) {
                // بلاک پیدا شد؛ آن را بازگردان
                return new Block(index, hash, previousHash, timestamp, data, difficulty, getAccountBalance(), getPublicFromWallet());
            }
            pastTimestamp = timestamp;   // برای اینکه تا ثانیه بعد دوباره تلاش نشود
        }
    }
};

اجماع روی سختی

حالا ابزار یافتن و بررسی هش برای یک سختی مشخص را داریم، اما سختی چگونه تعیین می‌شود؟ باید راهی وجود داشته باشد که گره‌ها روی سختی فعلی شبکه توافق کنند. برای این کار قواعد جدیدی معرفی می‌کنیم که برای محاسبهٔ سختی فعلی شبکه استفاده می‌شوند.

ثابت‌های جدید شبکه را این‌گونه تعریف می‌کنیم:

  • BLOCK_GENERATION_INTERVAL: مشخص می‌کند هر چند وقت یک‌بار باید بلاک یافت شود (در بیت‌کوین این مقدار ۱۰ دقیقه است)
  • DIFFICULTY_ADJUSTMENT_INTERVAL: مشخص می‌کند سختی هر چند وقت یک بار باید با افزایش یا کاهش نرخ هش شبکه تنظیم شود (در بیت‌کوین این مقدار ۲۰۱۶ بلاک است)

بازهٔ تولید بلاک را ۱۰ ثانیه و بازهٔ تنظیم سختی را ۱۰ بلاک قرار می‌دهیم. این ثابت‌ها با گذشت زمان تغییر نمی‌کنند و به‌صورت ثابت در کد قرار دارند: 

typescript// بازه تولید بلاک (بر حسب ثانیه)
const BLOCK_GENERATION_INTERVAL: number = 10;

// بازه تنظیم سختی (بر حسب بلاک)
const DIFFICULTY_ADJUSTMENT_INTERVAL: number = 10;

حالا ابزار توافق روی سختی بلاک را داریم. برای هر ۱۰ بلاکی که تولید می‌شود بررسی می‌کنیم که زمان صرف‌شده برای تولید این بلاک‌ها از زمان مورد انتظار بزرگ‌تر است یا کوچک‌تر. زمان مورد انتظار این‌گونه محاسبه می‌شود: BLOCK_GENERATION_INTERVAL * DIFFICULTY_ADJUSTMENT_INTERVAL. زمان مورد انتظار حالتی را نشان می‌دهد که نرخ هش دقیقاً با سختی فعلی یکسان باشد.

اگر زمان صرف‌شده حداقل دو برابر بزرگ‌تر یا کوچک‌تر از زمان مورد انتظار باشد، سختی را یک واحد زیاد یا کم می‌کنیم. تنظیم سختی با کد زیر انجام می‌شود: 

typescript// دریافت سختی فعلی شبکه
const getDifficulty = (aBlockchain: Block[]): number => {
    const latestBlock: Block = aBlockchain[blockchain.length - 1];
    if (latestBlock.index % DIFFICULTY_ADJUSTMENT_INTERVAL === 0 && latestBlock.index !== 0) {
        return getAdjustedDifficulty(latestBlock, aBlockchain);   // وقت تنظیم سختی است
    } else {
        return latestBlock.difficulty;                            // سختی را تغییر نده
    }
};

// محاسبه سختی تنظیم‌شده بر اساس زمان واقعی تولید بلاک‌ها
const getAdjustedDifficulty = (latestBlock: Block, aBlockchain: Block[]) => {
    const prevAdjustmentBlock: Block = aBlockchain[blockchain.length - DIFFICULTY_ADJUSTMENT_INTERVAL];
    const timeExpected: number = BLOCK_GENERATION_INTERVAL * DIFFICULTY_ADJUSTMENT_INTERVAL;  // زمان مورد انتظار
    const timeTaken: number = latestBlock.timestamp - prevAdjustmentBlock.timestamp;          // زمان واقعی
    if (timeTaken < timeExpected / 2) {
        return prevAdjustmentBlock.difficulty + 1;   // بلاک‌ها خیلی سریع ساخته شدند؛ سختی را زیاد کن
    } else if (timeTaken > timeExpected * 2) {
        return prevAdjustmentBlock.difficulty - 1;   // بلاک‌ها خیلی کند ساخته شدند؛ سختی را کم کن
    } else {
        return prevAdjustmentBlock.difficulty;       // در حد انتظار بود؛ تغییر نده
    }
};

اعتبارسنجی برچسب زمانی

در نسخهٔ فصل ۱ بلاک‌چین، برچسب زمانی هیچ نقشی و اعتبارسنجی نداشت؛ در واقع هر چیزی که کلاینت تصمیم می‌گرفت تولید می‌شد. حالا که تنظیم سختی معرفی شده است، این موضوع تغییر می‌کند، چون متغیر timeTaken (در کد قبلی) بر اساس برچسب‌های زمانی بلاک‌ها محاسبه می‌شود.

برای کاهش حملهٔ درج برچسب زمانی جعلی با هدف دستکاری سختی، این قواعد معرفی می‌شوند:

  • بلاک معتبر است اگر برچسب زمانی آن حداکثر ۱ دقیقه در آینده، نسبت به زمانی که ما درک می‌کنیم، باشد.
  • بلاک در زنجیره معتبر است اگر برچسب زمانی آن حداکثر ۱ دقیقه در گذشتهٔ بلاک قبلی باشد.
typescript// اعتبارسنجی برچسب زمانی بلاک جدید نسبت به بلاک قبلی و زمان فعلی
const isValidTimestamp = (newBlock: Block, previousBlock: Block): boolean => {
    return ( previousBlock.timestamp - 60 < newBlock.timestamp )
        && newBlock.timestamp - 60 < getCurrentTimestamp();

سختی تجمعی (Cumulative difficulty)

در نسخهٔ فصل ۱ بلاک‌چین، همیشه «بلندترین» بلاک‌چین را معتبر انتخاب می‌کردیم. حالا که سختی معرفی شده، این موضوع باید تغییر کند. از این پس زنجیرهٔ «صحیح»، بلندترین زنجیره نیست، بلکه زنجیره‌ای است که بیشترین سختی تجمعی را دارد. به عبارت دیگر، زنجیرهٔ صحیح زنجیره‌ای است که تولیدش بیشترین منابع (= نرخ هش × زمان) را نیاز داشته است.

برای به‌دست آوردن سختی تجمعی یک زنجیره، برای هر بلاک 2^difficulty را محاسبه و مجموع همهٔ این اعداد را می‌گیریم. باید از 2^difficulty استفاده کنیم، چون سختی را به‌صورت تعداد صفرهایی که باید در ابتدای هش (در قالب دودویی) باشد تعریف کرده‌ایم. برای مثال در مقایسهٔ سختی‌های ۵ و ۱۱، برای یافتن بلاک با سختی بیشتر، به 2^(11-5) = 2^6 برابر کار بیشتر نیاز داریم.

این ویژگی به «اجماع ناکاموتو» (Nakamoto consensus) نیز معروف است و یکی از مهم‌ترین اختراعاتِ ساتوشی هنگام ساخت بیت‌کوین بوده است. در صورت وقوع fork، ضراب‌زن‌ها باید تصمیم بگیرند منابع فعلی خودشان (= نرخ هش) را روی کدام زنجیره بگذارند. از آنجا که در منافع ضراب‌زن‌هاست بلاکی تولید کنند که در بلاک‌چین قرار بگیرد، آن‌ها در نهایت ترغیب می‌شوند زنجیرهٔ یکسانی را انتخاب کنند.

جمع‌بندی

اجماع اثبات سهام جایگزین نسبتاً جالبی برای اثبات کار است، چون انرژی زیادی مصرف نمی‌کند. البته حملات مختلفی هم ممکن است انجام شود، مانند تغییر برچسب زمانی که naivecoin فعلی در برابر آن محافظت ندارد.

همچنین در پیاده‌سازی فعلی، موجودی حساب بر اساس بلاک‌چین محاسبه نمی‌شود، بلکه از خود زنجیره خوانده و نوشته می‌شود (برای ساده‌سازی، چون بیشتر به خود معما علاقه‌مند بودم). این اصلاً خوب نیست و باید حل شود!

۳. تراکنش‌ها (Transactions)

مرور کلی

در این فصل مفهوم تراکنش‌ها را معرفی می‌کنیم. با این تغییر، پروژه‌مان از یک بلاک‌چین «همه‌منظوره» به یک ارز دیجیتال واقعی تبدیل می‌شود. در نتیجه می‌توانیم کوین‌ها را به آدرس‌ها بفرستیم، به شرط آنکه ابتدا ثابت کنیم مالک آن‌ها هستیم.

برای ممکن‌شدن همهٔ این‌ها باید مفاهیم تازهٔ زیادی معرفی شود، از جمله رمزنگاری کلید عمومی، امضاها و ورودی‌ها و خروجی‌های تراکنش.

این فصل از آموزش اصلی Naivecoin نوشتهٔ Lauri Hartikka کپی شده و برای اجماع اثبات سهام تطبیق داده شده است. صفحهٔ اصلی آن را اینجا ببینید.

رمزنگاری کلید عمومی و امضاها

در رمزنگاری کلید عمومی یک جفت کلید دارید: یک کلید خصوصی و یک کلید عمومی. کلید عمومی را می‌توان از کلید خصوصی استخراج کرد، اما کلید خصوصی را نمی‌توان از کلید عمومی استخراج کرد. کلید عمومی (همان‌طور که از نامش پیداست) می‌تواند با خیال راحت با هر کسی به اشتراک گذاشته شود.

هر پیامی را می‌توان با کلید خصوصی امضا کرد تا یک امضا ایجاد شود. با این امضا و کلید عمومی متناظر، هر کسی می‌تواند تأیید کند که امضا توسط کلید خصوصیِ منطبق با آن کلید عمومی تولید شده است.

برای رمزنگاری کلید عمومی از کتابخانه‌ای به نام elliptic استفاده می‌کنیم که از منحنی‌های بیضوی استفاده می‌کند. (= ECDSA)

خلاصه اینکه در ارز دیجیتال از دو تابع رمزنگاری متفاوت برای دو هدف متفاوت استفاده می‌شود:

  • تابع هش (SHA256) برای استخراج اثبات کار (هش برای حفظ یکپارچگی بلاک هم استفاده می‌شود)
  • رمزنگاری کلید عمومی (ECDSA) برای تراکنش‌ها (که در همین فصل پیاده‌سازی می‌کنیم)

کلیدهای خصوصی و عمومی (در ECDSA)

یک کلید عمومی معتبر «04» به‌همراه یک رشتهٔ ۶۴ بایتی است، مثلاً 04bfcab8722991ae774db48f934ca79cfb7dd991229153b9f732ba5334aafcd8e7266e47076996b55a14bf9913ee3145ce0cfc1372ada8ada74bd287450313534a

کلید عمومی را می‌توان از کلید خصوصی استخراج کرد. کلید عمومی به‌عنوان «گیرنده» (= آدرس) کوین‌ها در تراکنش استفاده می‌شود.

مرور کلی تراکنش‌ها

قبل از نوشتن هر کدی، نگاهی به ساختار تراکنش‌ها بیندازیم. تراکنش‌ها از دو مؤلفه تشکیل شده‌اند: ورودی‌ها (inputs) و خروجی‌ها (outputs). خروجی‌ها مشخص می‌کنند کوین‌ها به کجا فرستاده می‌شوند و ورودی‌ها اثبات می‌کنند که کوین‌های واقعاً ارسال‌شده از ابتدا وجود داشته‌اند و متعلق به «فرستنده» هستند. ورودی‌ها همیشه به یک خروجی موجود (مصرف‌نشده) ارجاع می‌دهند.

خروجی‌های تراکنش

خروجی‌های تراکنش (txOut) از یک آدرس و یک مقدار کوین تشکیل شده‌اند. آدرس یک کلید عمومی ECDSA است؛ یعنی کاربری که کلید خصوصی کلید عمومیِ ارجاع‌داده‌شده (= آدرس) را دارد، می‌تواند به کوین‌ها دسترسی پیدا کند. 

typescript// کلاس خروجی تراکنش: آدرس گیرنده و مقدار کوین
class TxOut {
    public address: string;   // آدرس گیرنده (کلید عمومی ECDSA)
    public amount: number;    // مقدار کوین

    constructor(address: string, amount: number) {
        this.address = address;
        this.amount = amount;
    }
}

ورودی‌های تراکنش

ورودی‌های تراکنش (txIn) اطلاعات «از کجا» بودن کوین‌ها را فراهم می‌کنند. هر txIn به یک خروجی قبلی ارجاع می‌دهد و با امضا، آن کوین‌ها «قفل‌گشایی» (unlock) می‌شوند. این کوین‌های قفل‌گشایی‌شده حالا برای txOutها «در دسترس» هستند. امضا اثبات می‌کند فقط کاربری که کلید خصوصی کلید عمومی ارجاع‌داده‌شده (= آدرس) را دارد می‌توانسته این تراکنش را ایجاد کند. 

typescript// کلاس ورودی تراکنش: ارجاع به خروجی قبلی و امضای مالک
class TxIn {
    public txOutId: string;     // شناسه تراکنش حاوی خروجی مصرف‌شده
    public txOutIndex: number;  // اندیس خروجی در آن تراکنش
    public signature: string;   // امضای ایجادشده با کلید خصوصی
}

باید توجه داشت که txIn فقط امضا (که با کلید خصوصی ساخته شده) را شامل می‌شود و هرگز خود کلید خصوصی را ندارد. بلاک‌چین شامل کلیدهای عمومی و امضاهاست، نه کلیدهای خصوصی.

    public txOuts: TxOut[];   // خروجی‌ها
}

شناسهٔ تراکنش

شناسهٔ تراکنش با گرفتن هش از محتوای تراکنش محاسبه می‌شود. البته امضاهای ورودی‌ها در هش تراکنش لحاظ نمی‌شوند، چون بعداً به تراکنش اضافه می‌شوند. 

typescript// محاسبه شناسه تراکنش با هش گرفتن از محتوای ورودی‌ها و خروجی‌ها
const getTransactionId = (transaction: Transaction): string => {
    // ترکیب محتوای ورودی‌ها (شناسه خروجی + اندیس)
    const txInContent: string = transaction.txIns
        .map((txIn: TxIn) => txIn.txOutId + txIn.txOutIndex)
        .reduce((a, b) => a + b, '');

    // ترکیب محتوای خروجی‌ها (آدرس + مقدار)
    const txOutContent: string = transaction.txOuts
        .map((txOut: TxOut) => txOut.address + txOut.amount)
        .reduce((a, b) => a + b, '');

    return CryptoJS.SHA256(txInContent + txOutContent).toString();
};

امضای تراکنش

مهم است که محتوای تراکنش پس از امضا شدن قابل تغییر نباشد. چون تراکنش‌ها عمومی هستند، هر کسی حتی قبل از اینکه در بلاک‌چین قرار بگیرند به آن‌ها دسترسی دارد.

هنگام امضای ورودی‌های تراکنش فقط txId امضا می‌شود. اگر هر یک از محتویات تراکنش تغییر کند، txId باید تغییر کند و در نتیجه تراکنش و امضا نامعتبر می‌شوند. 

typescript// امضای یک ورودی تراکنش با کلید خصوصی
const signTxIn = (transaction: Transaction, txInIndex: number,
                  privateKey: string, aUnspentTxOuts: UnspentTxOut[]): string => {
    const txIn: TxIn = transaction.txIns[txInIndex];
    const dataToSign = transaction.id;   // فقط شناسه تراکنش امضا می‌شود
    const referencedUnspentTxOut: UnspentTxOut = findUnspentTxOut(txIn.txOutId, txIn.txOutIndex, aUnspentTxOuts);
    const referencedAddress = referencedUnspentTxOut.address;   // آدرس مالک خروجی مصرف‌نشده
    const key = ec.keyFromPrivate(privateKey, 'hex');
    const signature: string = toHexString(key.sign(dataToSign).toDER());
    return signature;
};

ببینیم اگر کسی بخواهد تراکنش را تغییر دهد چه اتفاقی می‌افتد:

  1. مهاجم یک گره اجرا می‌کند و تراکنشی با محتوای «۱۰ کوین از آدرس AAA به BBB بفرست» با txId برابر 0x555.. دریافت می‌کند
  2. مهاجم آدرس گیرنده را به CCC تغییر می‌دهد و تراکنش را در شبکه پخش می‌کند. حالا محتوای تراکنش «۱۰ کوین از آدرس AAA به CCC بفرست» است
  3. اما چون آدرس گیرنده تغییر کرده، txId دیگر معتبر نیست. یک txId معتبر جدید 0x567… خواهد بود
  4. اگر txId به مقدار جدید تغییر داده شود، امضا معتبر نیست؛ امضا فقط با txId اصلی 0x555.. مطابقت دارد
  5. تراکنش تغییرداده‌شده توسط گره‌های دیگر پذیرفته نمی‌شود، چون در هر صورت نامعتبر است

خروجی‌های تراکنش مصرف‌نشده (uTxO)

ورودی تراکنش همیشه باید به یک خروجی تراکنش مصرف‌نشده (unspent transaction output) ارجاع دهد. در نتیجه وقتی صاحب کوین‌هایی در بلاک‌چین هستید، چیزی که واقعاً دارید فهرستی از خروجی‌های تراکنش مصرف‌نشده است که کلید عمومی‌شان با کلید خصوصیِ در اختیار شما مطابقت دارد.

از نظر اعتبارسنجی تراکنش‌ها، برای فهمیدن معتبر بودن یک تراکنش فقط می‌توانیم روی فهرست خروجی‌های مصرف‌نشده تمرکز کنیم. این فهرست همیشه قابل استخراج از بلاک‌چین فعلی است. در این پیاده‌سازی، فهرست خروجی‌های مصرف‌نشده را هنگام پردازش و افزودن تراکنش‌ها به بلاک‌چین به‌روزرسانی می‌کنیم.

ساختار دادهٔ یک خروجی تراکنش مصرف‌نشده این‌گونه است:

typescript// کلاس خروجی تراکنش مصرف‌نشده: با آدرس و مقدار
class UnspentTxOut {
    public readonly txOutId: string;     // شناسه تراکنش حاوی خروجی
    public readonly txOutIndex: number;  // اندیس خروجی در تراکنش
    public readonly address: string;     // آدرس مالک
    public readonly amount: number;      // مقدار کوین

    constructor(txOutId: string, txOutIndex: number, address: string, amount: number) {
        this.txOutId = txOutId;
        this.txOutIndex = txOutIndex;
        this.address = address;
        this.amount = amount;
    }
}

ساختار دادهٔ آن به‌سادگی یک فهرست است:

typescript// فهرست خروجی‌های تراکنش مصرف‌نشده
let unspentTxOuts: UnspentTxOut[] = [];

به‌روزرسانی خروجی‌های تراکنش مصرف‌نشده

هر بار که بلاک جدیدی به زنجیره اضافه می‌شود، باید فهرست خروجی‌های مصرف‌نشده خود را به‌روزرسانی کنیم؛ چون تراکنش‌های جدید برخی از خروجی‌های موجود را مصرف می‌کنند و خروجی‌های مصرف‌نشدهٔ جدیدی معرفی می‌کنند.

برای این کار، ابتدا همهٔ خروجی‌های مصرف‌نشدهٔ جدید (newUnspentTxOuts) را از بلاک جدید استخراج می‌کنیم:

typescript    // استخراج خروجی‌های جدید هر تراکنش به‌صورت خروجی مصرف‌نشده
    const newUnspentTxOuts: UnspentTxOut[] = newTransactions
        .map((t) => {
            return t.txOuts.map((txOut, index) => new UnspentTxOut(t.id, index, txOut.address, txOut.amount));
        })
        .reduce((a, b) => a.concat(b), []);

همچنین باید بدانیم کدام خروجی‌ها توسط تراکنش‌های جدید بلاک مصرف شده‌اند (consumedTxOuts). این کار با بررسی ورودی‌های تراکنش‌های جدید حل می‌شود: 

typescript    // پیدا کردن خروجی‌های مصرف‌شده از طریق ورودی‌های تراکنش‌های جدید
    const consumedTxOuts: UnspentTxOut[] = newTransactions
        .map((t) => t.txIns)
        .reduce((a, b) => a.concat(b), [])
        .map((txIn) => new UnspentTxOut(txIn.txOutId, txIn.txOutIndex, '', 0));

در نهایت، با حذف consumedTxOuts و افزودن newUnspentTxOuts به خروجی‌های مصرف‌نشدهٔ موجودمان، فهرست جدید را می‌سازیم: 

typescript    // فهرست نهایی: حذف موارد مصرف‌شده و افزودن موارد جدید
    const resultingUnspentTxOuts = aUnspentTxOuts
        .filter(((uTxO) => !findUnspentTxOut(uTxO.txOutId, uTxO.txOutIndex, consumedTxOuts)))
        .concat(newUnspentTxOuts);

کد و عملکرد توصیف‌شده در متد updateUnspentTxOuts قرار دارد. توجه کنید این متد فقط بعد از اعتبارسنجیِ تراکنش‌های بلاک (و خود بلاک) فراخوانی می‌شود.

ساختار صحیح تراکنش

typescript    // بررسی صحت ساختار تراکنش
    const isValidTransactionStructure = (transaction: Transaction) => {
        if (typeof transaction.id !== 'string') {

        }
        ...
       // بقیه اعضای کلاس نیز بررسی شوند
    }

شناسهٔ معتبر تراکنش

شناسه در تراکنش باید به‌درستی محاسبه شده باشد:

typescript    // محاسبه مجدد شناسه و مقایسه با شناسه ارسالی

ورودی‌های معتبر

امضاهای txInها باید معتبر باشند و خروجی‌های ارجاع‌داده‌شده نباید قبلاً مصرف شده باشند:

typescript// اعتبارسنجی یک ورودی تراکنش
const validateTxIn = (txIn: TxIn, transaction: Transaction, aUnspentTxOuts: UnspentTxOut[]): boolean => {
    // پیدا کردن خروجی مصرف‌نشده ارجاع‌داده‌شده
    const referencedUTxOut: UnspentTxOut =
        aUnspentTxOuts.find((uTxO) => uTxO.txOutId === txIn.txOutId && uTxO.txOutId === txIn.txOutId);
    if (referencedUTxOut == null) {
        console.log('referenced txOut not found: ' + JSON.stringify(txIn));   // خروجی ارجاعی پیدا نشد
        return false;
    }
    const address = referencedUTxOut.address;

    // تأیید امضا با کلید عمومی مالک
    const key = ec.keyFromPublic(address, 'hex');
    return key.verify(transaction.id, txIn.signature);
};

مقادیر معتبر خروجی‌ها

مجموع مقادیر مشخص‌شده در خروجی‌ها باید با مجموع مقادیر ورودی‌ها برابر باشد. اگر به خروجی‌ای ارجاع دهید که ۵۰ کوین دارد، مجموع مقادیر خروجی‌های جدید هم باید ۵۰ کوین باشد. 

typescript    // مجموع مقادیر ورودی‌ها

        .map((txIn) => getTxInAmount(txIn, aUnspentTxOuts))
        .reduce((a, b) => (a + b), 0);

    const totalTxOutValues: number = transaction.txOuts
        .map((txOut) => txOut.amount)
        .reduce((a, b) => (a + b), 0);

    if (totalTxOutValues !== totalTxInValues) {

تراکنش Coinbase

ورودی‌های تراکنش همیشه باید به خروجی‌های مصرف‌نشده ارجاع دهند، اما کوین‌های اولیه از کجا وارد بلاک‌چین می‌شوند؟ برای حل این مشکل، نوع خاصی از تراکنش معرفی می‌شود: تراکنش coinbase.

تراکنش coinbase فقط یک خروجی دارد و هیچ ورودی ندارد؛ یعنی تراکنش coinbase کوین‌های جدیدی به گردش اضافه می‌کند. مقدار خروجی coinbase را ۵۰ کوین تعیین می‌کنیم: 

typescript// مقدار پاداش تراکنش coinbase
const COINBASE_AMOUNT: number = 50;

تراکنش coinbase همیشه اولین تراکنش بلاک است و توسط ضراب‌زن بلاک ایجاد می‌شود. پاداش coinbase به‌عنوان انگیزهٔ گره‌ها عمل می‌کند: اگر بلاک را پیدا کنید، می‌توانید ۵۰ کوین جمع کنید.

ارتفاع بلاک را به ورودی تراکنش coinbase اضافه می‌کنیم تا هر تراکنش coinbase یک txId یکتا داشته باشد. بدون این قاعده، مثلاً تراکنش coinbase «۵۰ کوین به آدرس 0xabc بده» همیشه یک txId یکسان داشت.

اعتبارسنجی تراکنش coinbase کمی با تراکنش «عادی» تفاوت دارد:

typescript// اعتبارسنجی تراکنش coinbase
const validateCoinbaseTx = (transaction: Transaction, blockIndex: number): boolean => {
    if (getTransactionId(transaction) !== transaction.id) {
        console.log('invalid coinbase tx id: ' + transaction.id);   // شناسه coinbase نامعتبر است
        return false;
    }
    if (transaction.txIns.length !== 1) {
        console.log('one txIn must be specified in the coinbase transaction');   // دقیقاً یک ورودی لازم است
        return;
    }
    if (transaction.txIns[0].txOutIndex !== blockIndex) {
        console.log('the txIn index in coinbase tx must be the block height');   // اندیس ورودی باید برابر ارتفاع بلاک باشد
        return false;
    }
    if (transaction.txOuts.length !== 1) {
        console.log('invalid number of txOuts in coinbase transaction');   // تعداد خروجی‌ها نامعتبر است
        return false;
    }
    if (transaction.txOuts[0].amount != COINBASE_AMOUNT) {
        console.log('invalid coinbase amount in coinbase transaction');   // مقدار coinbase نامعتبر است
        return false;
    }
    return true;
};

جمع‌بندی

مفهوم تراکنش‌ها را به بلاک‌چین اضافه کردیم. ایدهٔ پایه بسیار ساده است: در ورودی‌های تراکنش به خروجی‌های مصرف‌نشده ارجاع می‌دهیم و از امضاها برای نشان دادن معتبر بودن قفل‌گشایی استفاده می‌کنیم؛ سپس با خروجی‌ها، آن‌ها را برای آدرس گیرنده دوباره «قفل» می‌کنیم.

با این حال، ساخت تراکنش‌ها همچنان بسیار دشوار است: باید به‌صورت دستی ورودی‌ها و خروجی‌های تراکنش را بسازیم و با کلیدهای خصوصی‌مان امضا کنیم. این موضوع با معرفی کیف پول در فصل بعد تغییر می‌کند.

هنوز پخش تراکنش (transaction relaying) هم وجود ندارد: برای قرار دادن تراکنش در بلاک‌چین، باید خودتان آن را ضراب‌زنی کنید. این هم دلیل معرفی‌نشدن مفهوم کارمزد تراکنش است.

۴. کیف پول (Wallet)

مرور کلی

هدف کیف پول، ایجاد رابط انتزاعی‌تر برای کاربر نهایی است.

کاربر نهایی باید بتواند:

  • کیف پول جدید بسازد (= در این مورد کلید خصوصی)
  • موجودی کیف پولش را ببیند
  • کوین به آدرس‌های دیگر بفرستد

همهٔ موارد بالا باید طوری کار کنند که کاربر نهایی نیازی به درک کارکرد txIn و txOut نداشته باشد؛ درست مثل مثلاً بیت‌کوین: کوین‌ها را به آدرس‌ها می‌فرستید و آدرس خودتان را منتشر می‌کنید تا بقیه به آن کوین بفرستند.

این فصل از آموزش اصلی Naivecoin نوشتهٔ Lauri Hartikka کپی شده و برای اجماع اثبات سهام تطبیق داده شده است. صفحهٔ اصلی آن را اینجا ببینید.

تولید و ذخیره‌سازی کلید خصوصی

در این آموزش از ساده‌ترین روش ممکن برای تولید و ذخیرهٔ کیف پول استفاده می‌کنیم: یک کلید خصوصی رمزنشده در فایل node/wallet/private_key تولید می‌کنیم. 

typescript// محل ذخیره کلید خصوصی
const privateKeyLocation = 'node/wallet/private_key';

// تولید کلید خصوصی تصادفی
const generatePrivatekey = (): string => {
    const keyPair = EC.genKeyPair();
    const privateKey = keyPair.getPrivate();
    return privateKey.toString(16);   // تبدیل به قالب هگز
};

// مقداردهی اولیه کیف پول
const initWallet = () => {
    // کلیدهای خصوصی موجود بازنویسی نشوند
    if (existsSync(privateKeyLocation)) {
        return;
    }
    const newPrivateKey = generatePrivatekey();

    writeFileSync(privateKeyLocation, newPrivateKey);   // ذخیره کلید جدید در فایل
    console.log('new wallet with private key created');
};

و همان‌طور که گفته شد، کلید عمومی (= آدرس) از کلید خصوصی قابل محاسبه است:

typescript// استخراج کلید عمومی (آدرس) از کلید خصوصی
const getPublicFromWallet = (): string => {
    const privateKey = getPrivateFromWallet();
    const key = EC.keyFromPrivate(privateKey, 'hex');
    return key.getPublic().encode('hex');
};

باید توجه داشت که ذخیرهٔ کلید خصوصی به‌صورت رمزنشده بسیار ناامن است. این کار را فقط برای ساده نگه‌داشتن اوضاع فعلاً انجام می‌دهیم. همچنین کیف پول فقط از یک کلید خصوصی پشتیبانی می‌کند؛ بنابراین برای دریافت یک آدرس عمومی جدید باید کیف پول جدیدی بسازید.

موجودی کیف پول

یادآوری از فصل قبل: وقتی صاحب کوین‌هایی در بلاک‌چین هستید، چیزی که واقعاً دارید فهرستی از خروجی‌های تراکنش مصرف‌نشده است که کلید عمومی‌شان با کلید خصوصیِ در اختیار شما مطابقت دارد.

یعنی محاسبهٔ موجودی یک آدرس بسیار ساده است: کافی است مجموع همهٔ تراکنش‌های مصرف‌نشدهٔ «مالک» آن آدرس را حساب کنید: 

typescript// محاسبه موجودی یک آدرس از روی خروجی‌های مصرف‌نشده
const getBalance = (address: string, unspentTxOuts: UnspentTxOut[]): number => {
    return _(unspentTxOuts)
        .filter((uTxO: UnspentTxOut) => uTxO.address === address)  // فقط خروجی‌های متعلق به این آدرس
        .map((uTxO: UnspentTxOut) => uTxO.amount)
        .sum();   // مجموع مقادیر
};

همان‌طور که در کد مشخص است، برای پرسوجوی موجودی آدرس به کلید خصوصی نیازی نیست؛ یعنی هر کسی می‌تواند موجودی یک آدرس معین را محاسبه کند.

تولید تراکنش‌ها

هنگام ارسال کوین، کاربر باید بتواند مفاهیم ورودی‌ها و خروجی‌های تراکنش را نادیده بگیرد. اما اگر کاربر A موجودی ۵۰ کوین داشته باشد (در یک خروجی تراکنش تکی) و بخواهد ۱۰ کوین به کاربر B بفرستد، چه باید کرد؟

  2. کاربر C سه تراکنش به ارزش ۱۰، ۲۰ و ۳۰ کوین دریافت می‌کند
  3. کاربر C می‌خواهد ۵۵ کوین به کاربر D بفرستد. تراکنش چگونه خواهد بود؟

در این حالت هر سه خروجی باید استفاده شوند و خروجی‌ها باید شامل ۵۵ کوین برای کاربر D و ۵ کوین برای کاربر C باشند.

منطق توصیف‌شده را به کد تبدیل کنیم. ابتدا ورودی‌های تراکنش را می‌سازیم. برای این کار روی خروجی‌های مصرف‌نشدهٔ خودمان حلقه می‌زنیم تا مجموع این خروجی‌ها بزرگ‌تر یا مساوی مبلغ موردنظر برای ارسال شود:

typescript// یافتن خروجی‌های مصرف‌نشده لازم برای پوشش مبلغ درخواستی
const findTxOutsForAmount = (amount: number, myUnspentTxOuts: UnspentTxOut[]) => {
    let currentAmount = 0;
    const includedUnspentTxOuts = [];
    for (const myUnspentTxOut of myUnspentTxOuts) {
        includedUnspentTxOuts.push(myUnspentTxOut);
        currentAmount = currentAmount + myUnspentTxOut.amount;
        if (currentAmount >= amount) {                 // به اندازه کافی جمع شد
            const leftOverAmount = currentAmount - amount;   // مبلغ باقی‌مانده برای بازگشت
            return {includedUnspentTxOuts, leftOverAmount}
        }
    }
    throw Error('not enough coins to send transaction');   // کوین کافی برای تراکنش وجود ندارد
};

همان‌طور که دیده می‌شود، leftOverAmount را هم محاسبه می‌کنیم؛ مقداری که به آدرس خودمان بازگردانده می‌شود.

حالا که فهرست خروجی‌های مصرف‌نشده را داریم، می‌توانیم ورودی‌های (txIn) تراکنش را بسازیم:

typescript// تبدیل یک خروجی مصرف‌نشده به ورودی تراکنش (بدون امضا)
const toUnsignedTxIn = (unspentTxOut: UnspentTxOut) => {
    const txIn: TxIn = new TxIn();
    txIn.txOutId = unspentTxOut.txOutId;       // شناسه خروجی
    txIn.txOutIndex = unspentTxOut.txOutIndex; // اندیس خروجی
    return txIn;
};

// انتخاب خروجی‌های لازم و محاسبه مبلغ باقی‌مانده
const {includedUnspentTxOuts, leftOverAmount} = findTxOutsForAmount(amount, myUnspentTxouts);
const unsignedTxIns: TxIn[] = includedUnspentTxOuts.map(toUnsignedTxIn);   // ورودی‌های بدون امضا

در ادامه دو خروجی تراکنش ساخته می‌شود: یک خروجی برای گیرندهٔ کوین‌ها و یک خروجی برای leftOverAmount. اگر ورودی‌ها دقیقاً مبلغ موردنظر را داشته باشند (leftOverAmount صفر باشد)، خروجی «باقی‌مانده» را ایجاد نمی‌کنیم: 

typescript// ساخت خروجی‌های تراکنش: یکی برای گیرنده و در صورت نیاز یکی برای بازگشت باقی‌مانده
const createTxOuts = (receiverAddress:string, myAddress:string, amount, leftOverAmount: number) => {
    const txOut1: TxOut = new TxOut(receiverAddress, amount);   // خروجی گیرنده
    if (leftOverAmount === 0) {
        return [txOut1]   // اگر باقی‌مانده صفر است فقط یک خروجی
    } else {
        const leftOverTx = new TxOut(myAddress, leftOverAmount);   // بازگرداندن باقی‌مانده به خودمان
        return [txOut1, leftOverTx];
    }
};

در نهایت شناسهٔ تراکنش را محاسبه و ورودی‌ها را امضا می‌کنیم:

typescript    const tx: Transaction = new Transaction();
    tx.txIns = unsignedTxIns;   // ورودی‌های بدون امضا
    tx.txOuts = createTxOuts(receiverAddress, myAddress, amount, leftOverAmount);   // خروجی‌ها
    tx.id = getTransactionId(tx);   // محاسبه شناسه تراکنش

    // امضای همه ورودی‌ها با کلید خصوصی
    tx.txIns = tx.txIns.map((txIn: TxIn, index: number) => {
        txIn.signature = signTxIn(tx, index, privateKey, unspentTxOuts);
        return txIn;
    });

جمع‌بندی

کیف پول رمزنشدهٔ ساده‌ای با تولید تراکنش ساده پیاده‌سازی کردیم. اگرچه این الگوریتم تولید تراکنش هیچ‌وقت تراکنشی با بیش از ۲ خروجی نمی‌سازد، باید توجه داشت که خود بلاک‌چین از هر تعداد خروجی پشتیبانی می‌کند. می‌توانید تراکنش معتبری با ورودی ۵۰ کوین و خروجی‌های ۵، ۱۵ و ۳۰ کوین بسازید، اما این خروجی‌ها باید به‌صورت دستی با رابط /mintRawBlock ساخته شوند.

۵. پخش تراکنش (Transaction relaying)

مرور کلی

در این فصل پخش تراکنش‌هایی را پیاده‌سازی می‌کنیم که هنوز در بلاک‌چین قرار نگرفته‌اند. در بیت‌کوین به این تراکنش‌ها «تراکنش‌های تأییدنشده» (unconfirmed transactions) هم گفته می‌شود. معمولاً وقتی کسی می‌خواهد تراکنشی در بلاک‌چین قرار بگیرد (= کوین به آدرسی بفرستد)، تراکنش را در شبکه پخش می‌کند و امیدوار است گره‌ای آن را ضراب‌زنی و به بلاک‌چین اضافه کند.

این قابلیت برای یک ارز دیجیتال کاری بسیار مهم است، چون یعنی برای قرار دادن یک تراکنش در بلاک‌چین لازم نیست خودتان بلاک را ضراب‌زنی کنید.

در نتیجه، گره‌ها هنگام ارتباط با یکدیگر دو نوع داده به اشتراک می‌گذارند:

  • وضعیت بلاک‌چین (= بلاک‌ها و تراکنش‌هایی که در بلاک‌چین قرار گرفته‌اند)
  • تراکنش‌های تأییدنشده (= تراکنش‌هایی که هنوز در بلاک‌چین قرار نگرفته‌اند)

این فصل از آموزش اصلی Naivecoin نوشتهٔ Lauri Hartikka کپی شده و برای اجماع اثبات سهام تطبیق داده شده است. صفحهٔ اصلی آن را اینجا ببینید.

استخر تراکنش (Transaction pool)

تراکنش‌های تأییدنشده را در موجودیت جدیدی به نام «استخر تراکنش» ذخیره می‌کنیم (در بیت‌کوین به «مم‌پول» یا mempool معروف است). استخر تراکنش ساختاری است که همهٔ «تراکنش‌های تأییدنشدهٔ» شناخته‌شده توسط گره را شامل می‌شود. در این پیاده‌سازی ساده فقط از یک فهرست استفاده می‌کنیم: 

typescript// استخر تراکنش: فهرست تراکنش‌های تأییدنشده
let transactionPool: Transaction[] = [];

یک نقطهٔ پایانی جدید هم به گره اضافه می‌کنیم: POST /sendTransaction. این متد بر اساس قابلیت‌های موجود کیف پول، تراکنشی را در استخر تراکنش محلی ما ایجاد می‌کند. از این پس وقتی می‌خواهیم تراکنش جدیدی در بلاک‌چین قرار بگیرد، از این روش به‌عنوان رابط «ترجیحی» استفاده می‌کنیم. 

typescript    // نقطه پایانی ارسال تراکنش به استخر تراکنش
    app.post('/sendTransaction', (req, res) => {
        ...
    })

تراکنش را دقیقاً مثل فصل ۴ می‌سازیم؛ فقط به‌جای اینکه بلافاصله تلاش کنیم بلاکی ضراب‌زنی کنیم، تراکنش ساخته‌شده را به استخر اضافه می‌کنیم: 

typescript// ایجاد تراکنش و افزودن آن به استخر تراکنش
const sendTransaction = (address: string, amount: number): Transaction => {
    const tx: Transaction = createTransaction(address, amount, getPrivateFromWallet(), getUnspentTxOuts(), getTransactionPool());
    addToTransactionPool(tx, getUnspentTxOuts());   // افزودن به استخر تراکنش
    return tx;
};

پخش (Broadcasting)

نکتهٔ اصلی تراکنش‌های تأییدنشده این است که در سراسر شبکه پخش می‌شوند و در نهایت گره‌ای آن‌ها را ضراب‌زنی می‌کند و وارد بلاک‌چین می‌کند. برای این کار قواعد سادهٔ زیر را برای شبکه‌سازی تراکنش‌های تأییدنشده معرفی می‌کنیم:

  • وقتی گره تراکنش تأییدنشده‌ای دریافت می‌کند که قبلاً ندیده است، کل استخر تراکنش را به همهٔ همتایان پخش می‌کند.
  • وقتی گره برای اولین بار به گرهٔ دیگری متصل می‌شود، استخر تراکنش آن گره را درخواست می‌کند. دو نوع پیام جدید MessageType برای این منظور اضافه می‌کنیم: QUERY_TRANSACTION_POOL و RESPONSE_TRANSACTION_POOL.

پَسوایند (enum) MessageType حالا این‌گونه خواهد بود:

typescript// انواع پیام‌های شبکه بین گره‌ها
enum MessageType {
    QUERY_LATEST = 0,                 // درخواست آخرین بلاک
    QUERY_ALL = 1,                    // درخواست کل بلاک‌چین
    RESPONSE_BLOCKCHAIN = 2,          // پاسخ بلاک‌چین
    QUERY_TRANSACTION_POOL = 3,       // درخواست استخر تراکنش
    RESPONSE_TRANSACTION_POOL = 4     // پاسخ استخر تراکنش
}

پیام‌های استخر تراکنش به این شکل ساخته می‌شوند:

typescript// ساخت پیام پاسخ استخر تراکنش

    'type': MessageType.RESPONSE_TRANSACTION_POOL,
    'data': JSON.stringify(getTransactionPool())   // استخر تراکنش به‌صورت JSON
});

// ساخت پیام درخواست استخر تراکنش
const queryTransactionPoolMsg = (): Message => ({
    'type': MessageType.QUERY_TRANSACTION_POOL,
    'data': null
});

برای پیاده‌سازی منطق پخش تراکنشِ توصیف‌شده، کد مربوط به نوع پیام MessageType.RESPONSE_TRANSACTION_POOL را اضافه می‌کنیم. هر بار که تراکنش‌های تأییدنشده دریافت می‌کنیم، سعی می‌کنیم آن‌ها را به استخر تراکنش خود اضافه کنیم. اگر موفق به افزودن تراکنش به استخر شدیم، یعنی تراکنش معتبر است و گره ما قبلاً آن را ندیده است. در این صورت استخر تراکنش خودمان را به همهٔ همتایان پخش می‌کنیم.

            broadCastTransactionPool();

اعتبارسنجی تراکنش‌های تأییدنشدهٔ دریافتی

چون همتایان می‌توانند هر نوع تراکنشی برای ما بفرستند، باید تراکنش‌ها را قبل از افزودن به استخر تراکنش اعتبارسنجی کنیم. همهٔ قواعد اعتبارسنجی تراکنش قبلی اعمال می‌شوند؛ مثلاً تراکنش باید قالب صحیح داشته باشد و ورودی‌ها، خروجی‌ها و امضاها با هم مطابقت داشته باشند.

علاوه بر قواعد موجود، قاعدهٔ جدیدی اضافه می‌کنیم: اگر هر یک از ورودی‌های تراکنش از قبل در استخر تراکنش موجود باشد، نمی‌توان آن تراکنش را به استخر اضافه کرد. این قاعدهٔ جدید در کد زیر آمده است: 

typescript// بررسی اینکه ورودی‌های تراکنش از قبل در استخر نباشند
const isValidTxForPool = (tx: Transaction, aTtransactionPool: Transaction[]): boolean => {
    const txPoolIns: TxIn[] = getTxPoolIns(aTtransactionPool);   // همه ورودی‌های موجود در استخر

    // بررسی وجود یک ورودی مشخص در استخر
    const containsTxIn = (txIns: TxIn[], txIn: TxIn) => {
        return _.find(txPoolIns, (txPoolIn => {
            return txIn.txOutIndex === txPoolIn.txOutIndex && txIn.txOutId === txPoolIn.txOutId;
        }))
    };

    for (const txIn of tx.txIns) {
        if (containsTxIn(txPoolIns, txIn)) {
            console.log('txIn already found in the txPool');   // این ورودی قبلاً در استخر است
            return false;
        }
    }
    return true;
};

هیچ راه صریحی برای حذف تراکنش از استخر تراکنش وجود ندارد؛ اما استخر تراکنش هر بار که بلاک جدیدی یافت می‌شود به‌روزرسانی می‌شود.

از استخر تراکنش تا بلاک‌چین

حالا راهی پیاده‌سازی کنیم که تراکنش تأییدنشده از استخر تراکنش محلی به بلاکی که توسط همان گره ضراب‌زنی می‌شود راه پیدا کند. این کار ساده است: وقتی گره شروع به ضراب‌زنی یک بلاک می‌کند، تراکنش‌های استخر تراکنش را در بلاک کاندیدای جدید قرار می‌دهد. 

typescript// تولید بلاک بعدی شامل coinbase و همه تراکنش‌های استخر
const generateNextBlock = () => {
    // تراکنش coinbase به‌عنوان پاداش ضراب‌زن
    const coinbaseTx: Transaction = getCoinbaseTransaction(getPublicFromWallet(), getLatestBlock().index + 1);
    // ترکیب coinbase با همه تراکنش‌های استخر
    const blockData: Transaction[] = [coinbaseTx].concat(getTransactionPool());
    return generateRawNextBlock(blockData);
};

چون تراکنش‌ها قبل از افزودن به استخر از قبل اعتبارسنجی شده‌اند، در این مرحله اعتبارسنجی دیگری انجام نمی‌دهیم.

به‌روزرسانی استخر تراکنش

با ضراب‌زنی بلاک‌های جدیدِ دارای تراکنش به بلاک‌چین، باید استخر تراکنش را هر بار که بلاک جدیدی یافت می‌شود دوباره اعتبارسنجی کنیم. ممکن است بلاک جدید حاوی تراکنش‌هایی باشد که برخی تراکنش‌های استخر را نامعتبر می‌کند؛ مثلاً در این موارد:

  • تراکنشی که در استخر بود ضراب‌زنی شده باشد (توسط خود گره یا گره‌ای دیگر)
  • خروجی مصرف‌نشده‌ای که در تراکنش تأییدنشده ارجاع شده، توسط تراکنش دیگری مصرف شده باشد

استخر تراکنش با کد زیر به‌روزرسانی می‌شود:

typescript// حذف تراکنش‌های نامعتبر از استخر تراکنش
const updateTransactionPool = (unspentTxOuts: UnspentTxOut[]) => {
    const invalidTxs = [];
    for (const tx of transactionPool) {
        for (const txIn of tx.txIns) {
            // اگر ورودی به خروجی مصرف‌نشده معتبری ارجاع ندهد، تراکنش نامعتبر است
            if (!hasTxIn(txIn, unspentTxOuts)) {
                invalidTxs.push(tx);
                break;
            }
        }
    }
    if (invalidTxs.length > 0) {
        console.log('removing the following transactions from txPool: %s', JSON.stringify(invalidTxs));
        transactionPool = _.without(transactionPool, ...invalidTxs)   // حذف تراکنش‌های نامعتبر
    }
};

همان‌طور که دیده می‌شود، برای تصمیم‌گیری دربارهٔ حذف یک تراکنش از استخر فقط دانستن خروجی‌های مصرف‌نشدهٔ فعلی کافی است.

این فصل از آموزش اصلی Naivecoin نوشتهٔ Lauri Hartikka کپی شده و برای اجماع اثبات سهام تطبیق داده شده است. صفحهٔ اصلی آن را اینجا ببینید.

نقطه‌های پایانی جدید

نقطهٔ پایانی‌ای اضافه می‌کنیم که کاربر با دانستن هش بتواند یک بلاک مشخص را پرس‌وجو کند:

typescript    // دریافت یک بلاک مشخص بر اساس هش آن
    app.get('/block/:hash', (req, res) => {
        const block = _.find(getBlockchain(), {'hash' : req.params.hash});
        res.send(block);
    });

همین کار برای پرس‌وجوی یک تراکنش مشخص:

typescript    // دریافت یک تراکنش مشخص بر اساس شناسه آن (جستجو در همه بلاک‌ها)
    app.get('/transaction/:id', (req, res) => {
        const tx = _(getBlockchain())
            .map((blocks) => blocks.data)     // استخراج تراکنش‌های همه بلاک‌ها
            .flatten()
            .find({'id': req.params.id});     // پیدا کردن تراکنش با شناسه درخواستی
        res.send(tx);
    });

دوست داریم اطلاعاتی هم دربارهٔ یک آدرس مشخص نشان دهیم. فعلاً فهرست خروجی‌های مصرف‌نشدهٔ آن آدرس را برمی‌گردانیم، چون از این اطلاعات می‌توان مثلاً کل موجودی آن آدرس را محاسبه کرد: 

typescript    // دریافت خروجی‌های مصرف‌نشده متعلق به یک آدرس
    app.get('/address/:address', (req, res) => {
        const unspentTxOuts: UnspentTxOut[] =
            _.filter(getUnspentTxOuts(), (uTxO) => uTxO.address === req.params.address)
        res.send({'unspentTxOuts': unspentTxOuts});
    });

می‌توانیم اطلاعات خروجی‌های مصرف‌شدهٔ یک آدرس را هم اضافه کنیم تا تاریخچهٔ کامل یک آدرس نمایش داده شود.

فناوری‌های فرانت‌اند

برای پیاده‌سازی بخش‌های رابط کاربری کیف پول و کاوشگر بلاک‌چین از Vue.js استفاده می‌کنیم. چون این آموزش دربارهٔ توسعهٔ فرانت‌اند نیست، بخش فرانت‌اند را به‌صورت کد مرور نمی‌کنیم. مخزن کد رابط کاربری را اینجا می‌توانید ببینید.

کاوشگر بلاک‌چین

کاوشگر بلاک‌چین وب‌سایتی است که برای نمایش وضعیت بلاک‌چین استفاده می‌شود. کاربرد نمونهٔ آن بررسی آسان موجودی یک آدرس یا تأیید اینکه یک تراکنش مشخص در بلاک‌چین قرار گرفته است.

در مورد ما، به‌سادگی درخواست‌های HTTP به گره می‌فرستیم و پاسخ‌ها را به شکلی معنادار نمایش می‌دهیم. هرگز درخواستی که وضعیت بلاک‌چین را تغییر دهد نمی‌فرستیم؛ بنابراین ساخت کاوشگر بلاک‌چین فقط دربارهٔ نمایش معنادار اطلاعاتی است که گره ارائه می‌دهد.
