شل چیست و چطور کار می‌کند؟

به زبان ساده: «شل رابطی است که به شما اجازه می‌دهد با هستهٔ سیستمعامل تعامل کنید». جریان کار شل این است: راه‌اندازی ← انتظار برای ورودی کاربر ← تجزیهٔ ورودی ← اجرای دستور و برگرداندن نتیجه ← بازگشت به مرحلهٔ ۲.

اما یک نکتهٔ مهم هست: فرایندها. شل فرایند والد است (رشتهٔ main که منتظر ورودی است)، اما نمی‌توانیم دستور را در خودِ main اجرا کنیم؛ چون (۱) دستورِ خراب، کل شل را از کار می‌اندازد — می‌خواهیم از این بپرهیزیم؛ و (۲) دستورهای مستقل باید بلوک فرایندی خودشان را داشته باشند — این «انزوا» بخشی از تحمل‌پذیری خطاست.

فهمیدن fork با چهار خط کد

نویسنده می‌گوید: «فکر می‌کردم fork را می‌فهمم تا وقتی چهار خط کد با آن نوشتم». fork کپی‌ای از فرایند فعلی می‌سازد (به‌نام child) و هر فرایند یک شناسهٔ منحصربه‌فرد (pid) دارد:

c#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    pid_t child_pid = fork();

    if (child_pid == 0) {   /* فرایند فرزند */
        printf("### Child ###\nCurrent PID: %d and Child PID: %d\n",
               getpid(), child_pid);
    } else {                /* فرایند والد */
        printf("### Parent ###\nCurrent PID: %d and Child PID: %d\n",
               getpid(), child_pid);
    }
    return 0;
}

سیستم‌کال fork دوبار برمی‌گردد — برای هر فرایند یک بار! این در نگاه اول متناقض است، اما پشت پرده: fork کپی‌ای از فرایند فعلی می‌سازد و در والد، مقدارِ child_pid همان pid فرزندِ تازه‌ساخته است؛ در خودِ فرزند اما این مقدار 0 است چون فرزند، فرزندی ندارد. بلافاصله بعد از fork، هر دو فرایند همزمان اجرا می‌شوند و ترتیب اجرا به زمان‌بند سیستمعامل بستگی دارد. خروجی نمونه:

ترمینال### Parent ###
Current PID: 85247 and Child PID: 85248
### Child ###

(نکته: بزرگ‌تر بودن pid فرزند معمول است ولی تضمینی نیست — سیستم‌عامل می‌تواند شناسه‌های قدیمی را بازیافت کند.)

قطعیت با wait، نه با sleep

با sleep(1) در بلوک والد، فرزند تقریباً همیشه اول اجرا می‌شود و خروجی قطعی می‌شود؛ اما sleep راه‌حل خوبی نیست: (۱) چه تضمینی هست که منتظرِ چه چیزی، در n ثانیه تمام شود؟ (۲) اگر زودتر تمام شود بیهوده بیکار می‌مانیم. راه درست، سیستم‌کال wait و بهتر از آن waitpid است که سه پارامتر دارد: pid فرایند موردانتظار، متغیری که وضعیت پایان را پر می‌کند، و فلگ‌های سفارشی:

c#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main() {
    pid_t child_pid, wait_result;
    int stat_loc;

    child_pid = fork();
    if (child_pid == 0) {
        printf("### Child ###\nCurrent PID: %d and Child PID: %d\n",
               getpid(), child_pid);
        sleep(1);
    } else {
        wait_result = waitpid(child_pid, &stat_loc, WUNTRACED);
        printf("### Parent ###\nCurrent PID: %d and Child PID: %d\n",
               getpid(), child_pid);
    }
    return 0;
}

والد تا پایان کار فرزند صبر می‌کند و بعد دستورهای خودش را اجرا می‌کند.

اجرای دستور با execvp

خانوادهٔ exec شامل execl، execv، execle، execve، execlp و execvp است. ما execvp را می‌گیریم: «vp» یعنی نام فایل را می‌پذیرد و آن را در متغیر $PATH سیستم جست‌وجو می‌کند، به‌همراه آرایه‌ای از آرگومان‌ها. اجرای ls -l -h -a:

c#include <unistd.h>

int main() {
    char *argv[] = {"ls", "-l", "-h", "-a", NULL};
    execvp(argv[0], argv);
    return 0;
}

سه نکته: آرگومان اول نام دستور است؛ آرگومان دوم نام دستور به‌همراه آرگومان‌هایش است و باید با NULL پایان یابد؛ و execvp تصویر فرایندِ فعلی را با برنامهٔ موردنظر عوض می‌کند — در موفقیت هرگز برنمی‌گردد.

تجزیهٔ ورودی و حلقهٔ اصلی

ورودی را با strtok به‌وسیلهٔ جداکنندهٔ فاصله می‌شکنیم و آرایه‌ای که با NULL تمام می‌شود می‌سازیم؛ بعد در حلقهٔ بی‌نهایت: ورودی را با readline می‌گیریم، fork می‌کنیم، فرزند execvp می‌زند و والد waitpid می‌کند:

cchar **get_input(char *input) {
    char **command = malloc(8 * sizeof(char *));
    char *separator = " ";
    char *parsed;
    int index = 0;

    parsed = strtok(input, separator);
    while (parsed != NULL) {
        command[index] = parsed;
        index++;
        parsed = strtok(NULL, separator);
    }
    command[index] = NULL;
    return command;
}

int main() {
    char **command, *input;
    pid_t child_pid;
    int stat_loc;

    while (1) {
        input = readline("unixsh> ");
        command = get_input(input);

        child_pid = fork();
        if (child_pid == 0) {
            execvp(command[0], command);   /* موفق که بشود برنمی‌گردد */
            printf("This won't be printed if execvp is successful\n");
        } else {
            waitpid(child_pid, &stat_loc, WUNTRACED);
        }
        free(input);
        free(command);
    }
    return 0;
}

نکته: fork فقط بعد از وارد شدن دستور صدا زده می‌شود؛ یعنی فرایند والد همانی است که اعلانِ دریافت ورودی را نمایش می‌دهد. با این کد (کامپایل با gcc -g -lreadline shell.c) یک شل مینیمالِ کارا دارید که pwd و ls -lha را اجرا می‌کند.

مدیریت خطا

  • fork — اگر سیستم حافظه تمام کند یا به سقف تعداد فرایندها برسد، -1 برمی‌گردد: perror("Fork failed"); exit(1);
  • execvp — فقط در شکست برمی‌گردد: if (execvp(...) < 0) { perror(command[0]); exit(1); } — این exit فقط فرزند را می‌میراند.
  • malloc — می‌تواند NULL برگرداند: خطا و خروج.
  • بافر آرگومان‌ها — فقط ۸ بلاک است؛ دستورهای بیش از ۸ کلمه درست کار نمی‌کنند (تمرینی برای خواننده).

تمرین‌های بیشتر: اگر sleep را به فرزند بدهید، خروجی والد فوراً چاپ می‌شود ولی بعداً خروجی فرزند وسط ترمینال ریخته می‌شود — چون والد بعد از printf کاری ندارد و می‌میرد.

Builtin ها — ماجرای cd

اجرای cd در شلِ تازه‌ساخته خطای «No such file or directory» می‌دهد؛ چون cd برنامهٔ سیستمی مثل ls نیست. فرض کنید بود: fork می‌شود، در فرزند اجرا و تمام می‌شود، و دایرکتوری کاری والد دست‌نخورده می‌ماند — یعنی cd گرچه موفق است، نتیجهٔ دلخواه را ندارد! پس باید خودمان پیاده‌اش کنیم و به‌جای fork، مستقیم اجرا کنیم:

cint cd(char *path) {
    return chdir(path);
}

/* در حلقهٔ main */
if (strcmp(command[0], "cd") == 0) {
    if (cd(command[1]) < 0) {
        perror(command[1]);
    }
    continue;   /* fork نمی‌زنیم */
}

خلاصه و ادامهٔ مسیر

شما حالا: fork را فهمیده‌اید (با مثال و بحث قطعیت/زمان‌بند)، execvp را به کار گرفته‌اید، ورودی را تجزیه کرده‌اید، خطاها را مدیریت می‌کنید و builtin دارید. بخش سوم همین مجموعه به سیگنال‌ها و مدیریت Ctrl-C می‌پردازد. همهٔ کدها در مخزن وبلاگ (پوشهٔ shell-part-1 و shell-part-2) موجود است.
