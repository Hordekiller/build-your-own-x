۱. مقدمه

این مقاله تلاشی است برای توضیح سیستم کنترل نسخه گیت از پایین به بالا — یعنی شروع از بنیادی‌ترین سطح و صعود از آنجا. کار ساده‌ای به نظر نمی‌رسد و بارها با موفقیت مشکوک امتحان شده. اما راه آسانی هم هست: برای فهمیدن درون‌های گیت همه چیز لازم است آن را از صفر بازپیاده‌سازی کنیم. نه، فرار نکنید.

شوخی نیست و واقعاً پیچیده نیست: اگر این مقاله را از بالا به پایین بخوانید و کد را بنویسید (یا فقط ZIP آن را دانلود کنید — اما واقعاً بهتر است خودتان کد را بنویسید)، به برنامه‌ای به نام wyag می‌رسید که همه ویژگی‌های بنیادین گیت را پیاده می‌کند: init، add، rm، status، commit، log... به شکلی کاملاً سازگار با خود گیت.

اینکه گیت پیچیده است، به نظر من باوری نادرست است. گیت برنامه بزرگ پر از ویژگی است، درست؛ اما هسته آن فوق‌العاده ساده است. ظاهراً پیچیدگی‌اش اول از همه از اینجا می‌آید که غالباً عمیقاً ضدشهود است. اما شاید گیج‌کننده‌ترین چیز، سادگی و قدرت مفرط مدل اصلی‌اش باشد: ترکیب سادگی هسته و کاربردهای قدرتمند درک را سخت می‌کند، چون جهش ذهنی لازم است که از سادگی انتزاع بنیادین به تنوع کاربردها برسید.

پیاده‌سازی گیت، بنیادهای آن را با تمام برهنگی‌شان آشکار می‌کند.

۲. ساخت مخازن: init

جدا از یک GitRepository به دو یا سه تابع کمکی مسیر هم نیاز داریم:

pythonclass GitRepository (object):
    """A git repository"""

    worktree = None
    gitdir = None
    conf = None

    def __init__(self, path, force=False):
        self.worktree = path
        self.gitdir = os.path.join(path, ".git")

        if not (force or os.path.isdir(self.gitdir)):
            raise Exception(f"Not a Git repository {path}")

        # فایل تنظیمات .git/config را بخوان
        self.conf = configparser.ConfigParser()
        cf = repo_file(self, "config")
        if cf and os.path.exists(cf):
            self.conf.read([cf])
        elif not force:
            raise Exception("Configuration file missing")

        if not force:
            vers = int(self.conf.get("core", "repositoryformatversion"))
            if vers != 0:
                raise Exception(f"Unsupported repositoryformatversion: {vers}")

def repo_path(repo, *path):
    """Compute path under repo's gitdir."""
    return os.path.join(repo.gitdir, *path)

def repo_file(repo, *path, mkdir=False):
    """Same as repo_path, but create dirname(*path) if absent."""
    if repo_dir(repo, *path[:-1], mkdir=mkdir):
        return repo_path(repo, *path)

def repo_dir(repo, *path, mkdir=False):
    """Same as repo_path, but mkdir *path if absent if mkdir."""
    path = repo_path(repo, *path)
    if os.path.exists(path):
        if (os.path.isdir(path)):
            return path
        else:
            raise Exception(f"Not a directory {path}")
    if mkdir:
        os.makedirs(path)
        return path
    else:
        return None

۳. اشیا: hash-object و cat-file

در هسته خود، گیت یک «فایل‌سیستم آدرس‌دهی‌شده با محتوا» است. برخلاف فایل‌سیستم‌های معمولی که نام فایل‌ها دلخواه و بی‌ربط به محتواست، نام فایل‌های گیت به‌صورت ریاضی از محتوایشان مشتق می‌شود. اگر یک بایت فایل تغییر کند، نام داخلی‌اش هم تغییر می‌کند: شما فایل را در گیت «ویرایش» نمی‌کنید، بلکه فایل جدیدی در جای مختلف می‌سازید.

مسیر ذخیره یک شیء از هش SHA-1 محتوایش محاسبه می‌شود: دو کاراکتر اول به‌عنوان نام پوشه و بقیه به‌عنوان نام فایل (۲۵۶ پوشه میانی ممکن، متوسط تعداد فایل در پوشه را ۲۵۶ برابر کم می‌کند).

قالب ذخیره اشیاء: هدری با نوع شیء (blob، commit، tree یا tag)، یک فاصله ASCII (0x20)، اندازه شیء به بایت به‌صورت عدد ASCII، یک بایت null (0x00) و سپس محتوای شیء. کل این‌ها با zlib فشرده می‌شود. بایت‌های اول یک شیء commit: commit 1086\x00tree ....

خواندن اشیاء

pythondef object_read(repo, sha):
    """Read object sha from Git repository repo.  Return a
    GitObject whose exact type depends on the object."""
    path = repo_file(repo, "objects", sha[0:2], sha[2:])

    if not os.path.isfile(path):
        return None

    with open (path, "rb") as f:
        raw = zlib.decompress(f.read())

        # نوع شیء را بخوان
        x = raw.find(b' ')
        fmt = raw[0:x]

        # اندازه را بخوان و اعتبارسنجی کن
        y = raw.find(b'\x00', x)
        size = int(raw[x:y].decode("ascii"))
        if size != len(raw)-y-1:
            raise Exception(f"Malformed object {sha}: bad length")

        # سازنده را انتخاب کن
        match fmt:
            case b'commit' : c=GitCommit
            case b'tree'   : c=GitTree
            case b'tag'    : c=GitTag
            case b'blob'   : c=GitBlob
            case _:
                raise Exception(f"Unknown type {fmt.decode('ascii')} for object {sha}")

        return c(raw[y+1:])

نوشتن اشیاء

pythondef object_write(obj, repo=None):
    # داده شیء را سریال کن
    data = obj.serialize()
    # هدر را اضافه کن
    result = obj.fmt + b' ' + str(len(data)).encode() + b'\x00' + data
    # هش را محاسبه کن
    sha = hashlib.sha1(result).hexdigest()

    if repo:
        # مسیر را محاسبه کن
        path=repo_file(repo, "objects", sha[0:2], sha[2:], mkdir=True)
        if not os.path.exists(path):
            with open(path, 'wb') as f:
                # فشرده کن و بنویس
                f.write(zlib.compress(result))
    return sha

۴. خواندن تاریخچه: log

قالب شیء commit شبیه پیام‌های ایمیل (RFC 2822) است: مجموعه‌ای از جفت‌های کلید-مقدار با جداکننده فاصله، و در پایان پیام commit (چند خطی). فیلدها: tree (ارجاع به درخت — محتوای واقعی commit)، parent (می‌تواند تکرار شود: merge commitها چند والد دارند؛ در commit اول غایب است)، author و committer (جدا از هم، چون نویسنده لزوماً کسی نیست که commit می‌کند)، gpgsig (امضای PGP). مقادیر می‌توانند چند خط شوند؛ خطوط بعدی با فاصله شروع می‌شوند.

کد kvlm_parse — «Key-Value List با Message» — برای commit و tag مشترک است:

pythondef kvlm_parse(raw, start=0, dct=None):
    if not dct:
        dct = dict()
        # هرگز آرگومان پیش‌فرض را dct=dict() نکنید:
        # همه فراخوانی‌ها همان dict را بی‌نهایت بزرگ می‌کنند

    # جست‌وجوی فضای بعدی و خط جدید بعدی
    spc = raw.find(b' ', start)
    nl = raw.find(b'\n', start)

    # حالت پایه
    # =========
    # اگر خط جدید اول باشد، پیام نهایی است: با کلید None ذخیره و برگرد
    if (spc < 0) or (nl < spc):
        assert nl == start
        dct[None] = raw[start+1:]
        return dct

    # حالت بازگشتی
    # =============
    key = raw[start:spc]

    # پایان مقدار را پیدا کن؛ خطوط ادامه با فاصله شروع می‌شوند
    end = start
    while True:
        end = raw.find(b'\n', end+1)
        if raw[end+1] != ord(' '): break

    # مقدار را بگیر و فاصله اول خطوط ادامه را حذف کن
    value = raw[spc+1:end].replace(b'\n ', b'\n')

    # داده موجود را رونویسی نکن
    if key in dct:
        if type(dct[key]) == list:
            dct[key].append(value)
        else:
            dct[key] = [ dct[key], value ]
    else:
        dct[key]=value

    return kvlm_parse(raw, start=end+1, dct=dct)

pythondef log_graphviz(repo, sha, seen):
    if sha in seen:
        return
    seen.add(sha)

    commit = object_read(repo, sha)
    message = commit.kvlm[None].decode("utf8").strip()
    message = message.replace("\\", "\\\\")
    message = message.replace("\"", "\\\"")

    if "\n" in message: # فقط خط اول را نگه دار
        message = message[:message.index("\n")]

    print(f"  c_{sha} [label=\"{sha[0:7]}: {message}\"]")
    assert commit.fmt==b'commit'

    if not b'parent' in commit.kvlm.keys():
        # حالت پایه: کامیت اولیه
        return

    parents = commit.kvlm[b'parent']
    if type(parents) != list:
        parents = [ parents ]

    for p in parents:
        p = p.decode("ascii")
        print (f"  c_{sha} -> c_{p};")

نظریه: تاریخچه گیت یک Merkle DAG است

ساختار داده نگهدارنده تاریخچه commit یک گراف است. با دو ویژگی اضافی: یال‌ها جهت دارند (از بچه به والد — پس commitها به والدهایشان اشاره می‌کنند، نه بچه‌هایشان) و هیچ حلقه‌ای وجود ندارد؛ از هر commit می‌توان به والدش رفت و در نهایت به commit ریشه بدون والد رسید. اعضا هم به همین دلیل اسمش «گراف جهت‌دار بدون دور» — DAG — است. ویژگی سوم: برخلاف گراف‌های معمولی، والدهای یک گره بخشی از هویت آن گره‌اند، چون نام commit هش رمزنگارانه محتوایش است و محتوا شامل نام والدها هم می‌شود. پس نام هر commit به جایگاهش در کل تاریخچه، تا اولین commit، گره خورده است. «هاستینگ از برگ به ریشه» است: هر commit جدید به کل تاریخچه قبل از خود پیوند می‌خورد، بدون تغییر آن.

۵. خواندن داده commit: checkout

یک tree فهرست blobها (فایل‌ها) و درخت‌های دیگر (پوشه‌ها) است. قالب entry tree: mode، فاصله، path، بایت null، هش (۲۰ بایت خام). هر خط یک entry است.

pythonclass GitTreeLeaf(object):
    def __init__(self, mode, path, sha):
        self.mode = mode
        self.path = path
        self.sha = sha

def tree_parse_one(raw, start=0):
    # یک entry tree را پیدا کن: mode SP path NUL sha
    x = raw.find(b' ', start)
    assert x-start == 5 or x-start == 6
    mode = raw[start:x]

    y = raw.find(b'\x00', x)
    path = raw[x+1:y]

    sha = hex(
        int.from_bytes(raw[y+1:y+21], "big")
    )[2:]  # هگز
    return y+21, GitTreeLeaf(mode, path.decode("utf8"), sha)

def tree_parse(raw):
    pos = 0
    max = len(raw)
    ret = list()
    while pos < max:
        pos, data = tree_parse_one(raw, pos)
        ret.append(data)
    return ret

۷. ناحیه stage و فایل index

فایل index وضعیت ناحیه stage را نگه می‌دارد: نسخه‌های فایل‌ها که برای commit بعدی انتخاب شده‌اند، به‌همراه فراداده (زمان، اندازه...). قالب: ۱۲ بایت هدر (امضای DIRC، نسخه، تعداد ورودی‌ها)، ورودی‌های ۶۲ بایتی + مسیر + padding، و در پایان هش SHA-1 کل فایل.

ls-files محتوای index را چاپ می‌کند. check-ignore قاعده‌های .gitignore را بر اساس فیلترهای fnmatch اعمال می‌کند. status وضعیت «HEAD در برابر index» و «index در برابر شاخه کاری» را مقایسه می‌کند و فایل‌های ستج‌شده/تغییرنیافته/جدا (untracked) را نشان می‌دهد.

بخش ۲ ناحیه stage: index_write (معکوس index_read)، rm، add (خواندن فایل، ذخیره آن به‌عنوان blob و افزودن ورودی به index) و commit:
