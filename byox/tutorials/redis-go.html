ساخت Redis از صفر در Go

مقدمه

در مجموعه مقالات پیشِ رو، گام‌به‌گام توضیح خواهیم داد که چگونه یک پایگاه دادهٔ درون‌حافظه‌ای (in-memory database) مانند Redis بسازیم. هدف این است که جزئیات سطح پایینِ (low-level) دخیل در پایگاه‌های داده، ساختمان داده‌ها و الگوریتم‌ها را ساده کنیم و توضیح دهیم. Redis را انتخاب کرده‌ایم؛ زیرا به‌عنوان یک ابزار ساده است و درک آن آسان است.

چه چیزی قرار است بسازیم؟

هدف این مجموعه، راهنمایی شما در ساختن یک پایگاه دادهٔ درون‌حافظه‌ای شبیه به Redis است. منظور از «شبیه به Redis» این است که برخی از دستورهای موجود در Redis را خواهد داشت. بخش مهم، نحوهٔ ذخیره‌سازی این داده‌ها روی دیسک و خواندن دوبارهٔ آن‌ها به حافظه هنگام اجرای سرور است.

ما از زبان Go استفاده خواهیم کرد؛ زیرا کد آن ساده است و پیش از این نیز پایگاه‌های دادهٔ زیادی با Go نوشته شده‌اند، مانند boltdb و diskv.

کاری که انجام خواهیم داد این است:

  • یک نسخهٔ مشابه Redis (Redis clone) می‌سازیم که به شما اجازه می‌دهد از رشته‌ها (strings) و هش‌ها (hashes) استفاده کنید.
  • یک تجزیه‌گر (parser) برای فهمیدن RESP می‌نویسیم که به سرور اجازه می‌دهد دستورها را دریافت کند و با پاسخ‌ها جواب بدهد.
  • برای مدیریت هم‌زمان چندین اتصال از گوروتین‌ها (goroutines) استفاده می‌کنیم.
  • با استفاده از فایل فقط‌الحاقی (Append Only File — AOF)، که یکی از روش‌هایی است که Redis برای ماندگاری (persistence) استفاده می‌کند، داده‌ها را روی دیسک می‌نویسیم. به این ترتیب، اگر سرور از کار بیفتد یا راه‌اندازی مجدد شود، می‌توانیم داده‌ها را بازیابی کنیم.

اگر الان بعضی از اصطلاح‌ها را نمی‌فهمید، نگران نباشید. در ادامه، هنگام عبور از هر بخش، آن‌ها را توضیح خواهیم داد.

در پایان، کد ما از چهار فایل ساده که خواندن و فهمیدنشان آسان است تشکیل می‌شود:

text.
├── aof.go
├── handler.go
├── main.go
└── resp.go

چرا باید این مقاله‌ها را بخوانید؟

اگر توسعه‌دهندهٔ نرم‌افزار هستید، قطعاً در کار روزانهٔ خود با پایگاه‌های داده سروکار دارید. پایگاه‌های دادهٔ خودشان می‌توانند پیچیده باشند و مفاهیم بسیاری دارند تا کار ذخیره‌سازی و دستکاری داده‌ها را برای شما به‌عنوان کاربر نهایی آسان‌تر کنند؛ چه عملیات پیچیده انجام دهید و چه عملیات ساده. بیشتر مقاله‌ها و دوره‌هایی که پایگاه‌های داده را توضیح می‌دهند، روی جزئیات سطح بالا و نحوهٔ استفاده از آن‌ها تمرکز می‌کنند؛ اما مقاله‌های کمی وجود دارند که توضیح می‌دهند آن‌ها در داخل چگونه کار می‌کنند. مثلاً ایندکس‌ها (indexes) چگونه ساخته و ذخیره می‌شوند؟ پایگاه داده بر اساس کوئری، چگونه تصمیم می‌گیرد از کدام ایندکس استفاده کند؟

پس از تحقیق و مطالعهٔ کتاب‌های گوناگون مانند Database Internals و مقاله‌هایی مانند «بیایید یک پایگاه دادهٔ ساده بسازیم (نسخهٔ مشابه SQLite)»، تصمیم گرفتم ساختن پایگاه دادهٔ خودم را شروع کنم و مفاهیمی را که به آن‌ها علاقه دارم به کار بگیرم و از اصل «آنچه نمی‌توانم بسازم، درک نمی‌کنم» — ریچارد فاینمن (Richard Feynman) — پیروی کنم.

می‌خواستم این تجربه را به زبان عربی به اشتراک بگذارم؛ زیرا محتوای کمی دربارهٔ این موضوع در دسترس است. چیزی که در این مقاله‌ها می‌سازیم، پایهٔ مناسبی برای نوشتن مقاله‌های بیشتر دربارهٔ پایگاه‌های دادهٔ پیچیده مانند SQLite، MySQL، PostgreSQL و MongoDB خواهد بود.

آیا این مقاله‌ها برای من مناسب‌اند و آیا می‌توانم آن‌ها را درک کنم؟

هنگام نوشتن این مقاله‌ها سعی کرده‌ام زبان را ساده و مستقیم نگه دارم. کد به بخش‌هایی تقسیم شده است تا بتوانید بفهمید هر بخش چه کاری انجام می‌دهد و کد آن چگونه است؛ پیش از آنکه همهٔ کدها را کنار هم بگذاریم و به‌صورت یک چیز واحد اجرا کنیم. بااین‌حال، خواننده باید دانش زمینه‌ای زیر را داشته باشد:

  • ✅ آشنایی با خواندن و درک کد Go، حتی در سطح پایه.
  • ✅ تجربهٔ قبلی با Redis و آشنایی با دستورهای آن.

حتی اگر Go یا Redis را نمی‌دانید، باز هم می‌توانید مقاله‌ها را بخوانید و اطلاعات مفیدی بیابید.

راه‌اندازی کلاینت

پایگاه دادهٔ درون‌حافظه‌ای که قرار است بنویسیم، همیشه با عنوان «سرور» (Server) شناخته می‌شود؛ زیرا یک سرور پایگاه داده است، مشابه MySQL یا سرور Redis.

و چون سرور همیشه برای ارتباط به یک «کلاینت» (Client) نیاز دارد، ما هم به یک کلاینت نیاز خواهیم داشت تا کدی را که می‌نویسیم آزمایش کنیم و ببینیم چگونه کار می‌کند. ساده‌ترین گزینه برای امتحان، یک کلاینت Redis است؛ هم به‌دلیل آسانی استفاده از آن و هم به‌دلیل اینکه سروری که قرار است بنویسیم با Redis سازگار (compatible) خواهد بود.

منظور از سازگاری این است که هر کلاینتی که بتواند با Redis ارتباط برقرار کند، بتواند با سرور ما هم ارتباط برقرار کند.

می‌توانید Redis و کلاینت آن را از وب‌سایت رسمی Redis نصب کنید.

پس از آن، بلافاصله اجرای دستور زیر را امتحان کنید:

shell$ redis-cli ping

PONG

آخرین قدمی که باید بعد از آن بردارید، خاموش کردن سرور Redis است؛ زیرا کد ما و سرور ما از همان پورت استفاده خواهند کرد.

  • اگر از macOS استفاده می‌کنید:
shell$ brew services stop redis
  • اگر از لینوکس استفاده می‌کنید:
shell$ sudo systemctl stop redis

Redis چگونه کار می‌کند؟

اول با چند مثال توضیح دهیم که Redis چگونه کار می‌کند. برای مثال، می‌توانید جفت‌های کلید-مقدار (key-value) را با استفاده از رشته‌ها ذخیره کنید.

کلید یک رشته خواهد بود و مقدار می‌تواند یک شیء سریال‌شده از هر نوعی باشد؛ مانند آرایه، عدد صحیح یا بولی.

SET admin ahmed

shell> GET admin

"ahmed"

Redis این دستورها را از طریق یک پروتکل سریال‌سازی (serialization protocol) به نام RESP (پروتکل سریال‌سازی Redis — Redis Serialization Protocol) دریافت می‌کند.

پس اگر نگاه کنیم که SET admin ahmed به‌صورت یک پیام سریال‌شده چگونه به Redis ارسال می‌شود، این‌گونه خواهد بود:

*3\r\n$3\r\nset\r\n$5\r\nadmin\r\n$5\r\nahmed

و برای ساده‌تر شدن هرچه بیشتر:

text*3
$3
set
$5
admin
$5
ahmed

اگر به RESP نگاه کنیم، معنای هر نماد را به ما می‌گوید:

  • '*' نشان می‌دهد که یک آرایه (array) با اندازهٔ ۳ داریم. بنابراین ۶ خط خواهیم خواند. هر جفت خط، نوع و اندازهٔ شیء را نشان می‌دهد و خط دوم حاوی مقدار آن شیء است.
  • '$' نشان می‌دهد که یک رشته با طول ۵ داریم. پس خط بعدی دقیقاً ۵ کاراکتر خواهد داشت.

به‌طور مشابه، وقتی GET admin را می‌گوییم، همان ساختار شیء را با مقادیر متفاوت برمی‌گرداند:

$5\r\nahmed\r\n

text$5
ahmed

کاری که قرار است بکنیم، ساختن همین سریال‌ساز است؛ و به کمک آن، با هر کلاینتی از Redis و با ارسال دستورها دقیقاً مانند Redis، می‌توانیم با سرور خودمان ارتباط برقرار کنیم.

و با این کار، آمادهٔ شروع ساختن پایگاه دادهٔ خودمان هستیم.

اولین قدم، شروع یک شنوندهٔ TCP (TCP listener) است تا هر کلاینت بتواند با آن ارتباط برقرار کند.

defer conn.Close() // پس از پایان، اتصال را ببند

توجه کنید که در خط آخر، بدون توجه به دستوری که از کلاینت دریافت کرده‌ایم، با «OK» پاسخ می‌دهیم.

بنابراین کد کامل به‌صورت زیر خواهد بود:

gopackage main

import (
	"fmt"
	"io"
	"net"
	"os"
)

func main() {
	fmt.Println("Listening on port :6379")

	// ساخت یک سرور جدید
	l, err := net.Listen("tcp", ":6379")
	if err != nil {
		fmt.Println(err)
		return
	}

	// گوش دادن برای اتصال‌ها
	conn, err := l.Accept()
	if err != nil {
		fmt.Println(err)
		return
	}

	defer conn.Close()

	for {
		buf := make([]byte, 1024)

		// خواندن پیام از کلاینت
		_, err = conn.Read(buf)
		if err != nil {
			if err == io.EOF {
				break
			}
			fmt.Println("error reading from client: ", err.Error())
			os.Exit(1)
		}

		// نادیده گرفتن درخواست و فرستادن یک PONG
		conn.Write([]byte("+OK\r\n"))
	}
}

خواندن RESP (Reading RESP)

در بخش اولین قدم‌ها بحث کردیم که سرور چگونه دستورها را از کلاینت دریافت می‌کند و درخواست چگونه ساختاربندی شده است. حالا توضیح می‌دهیم که چگونه RESP را بخوانیم و آن را تجزیه (parse) کنیم.

چگونه با ورودی/خروجی (IO) کار کنیم

برای نوشتن تجزیه‌گر، باید قالب ورودی‌ای را که دریافت خواهیم کرد بفهمیم تا بتوانیم آن را تجزیه کنیم. در GoLang کتابخانه‌های متعددی وجود دارند که به ما در مدیریت ورودی/خروجی کمک می‌کنند؛ اما ما از Bufio استفاده خواهیم کرد؛ زیرا متدهایی دارد که کار با داده‌ها را سریع‌تر می‌کند؛ مانند ReadLine و ReadByte.

برای مثال، اگر داده‌ای به‌صورت یک رشتهٔ RESP مانند این از کلاینت دریافت کنیم:

$5\r\nAhmed\r\n

کاری که باید بکنیم این است که اولین بایت را بخوانیم که '$' است تا نوع داده‌ای را که شروع به خواندنش می‌کنیم تعیین کنیم. سپس عدد را می‌خوانیم تا تعداد بایت‌هایی را که باید بخوانیم مشخص کنیم؛ یعنی ۵ به‌علاوهٔ ۲ بایت اضافی، '\r\n'.

«\r\n» CRLF نامیده می‌شود و پایان یک خط را نشان می‌دهد.

ببینیم چگونه انجام می‌شود

یک رشته می‌سازیم و آن را به یک بافر bufio تبدیل می‌کنیم.

goinput := "$5\r\nAhmed\r\n"

reader := bufio.NewReader(strings.NewReader(input))

حالا برای خواندن نام از رشتهٔ RESP باید این مراحل را دنبال کنیم:

  • نوع داده را بخوانید که اولین بایت در بافر است.
  • سپس عدد را بخوانید تا تعداد کاراکترهایی را که باید بخوانیم تعیین کنیم؛ یعنی ۵ به‌علاوهٔ ۲ بایت اضافی، «\r\n».
gob, _ := reader.ReadByte()

if b != '$' {

gosize, _ := reader.ReadByte()

strSize, _ := strconv.ParseInt(string(size), 10, 64)

// مصرف /r/n
reader.ReadByte()

با این کار، بایتی را خوانده‌ایم که نوع داده را تعیین می‌کند و سپس عددی که تعداد کاراکترهای رشته را نشان می‌دهد. بعد از آن، ۲ بایت اضافی می‌خوانیم تا از شر «\r\n» که به‌دنبال عدد می‌آید خلاص شویم.

به این ترتیب تجزیه‌گر را می‌سازیم تا بتوانیم همهٔ دستورهای RESP را مدیریت کنیم. کد کامل مراحل بالا به‌صورت زیر است:

gopackage main

import (
    "bufio"
    "fmt"
    "strings"
    "os"
    "strconv"
)

func main() {
    input := "$5\r\nAhmed\r\n"
    reader := bufio.NewReader(strings.NewReader(input))

    b, _ := reader.ReadByte()

    if b != '$' {
      fmt.Println("Invalid type, expecting bulk strings only")
      os.Exit(1)
    }

    size, _ := reader.ReadByte()

    strSize, _ := strconv.ParseInt(string(size), 10, 64)

    // مصرف /r/n
    reader.ReadByte()
    reader.ReadByte()

    name := make([]byte, strSize)
    reader.Read(name)

    fmt.Println(string(name))
}

نوشتن RESP

بیایید یک فایل جدید به نام resp.go بسازیم که همهٔ کدهای مربوط به سریال‌سازی (serializing) و ضدسریال‌سازی (deserializing) روی بافر را در خود داشته باشد.

اول، برای آسان‌تر شدن کار با انواع داده، ثابت‌هایی تعریف می‌کنیم که نمایانگر هر نوع هستند.

goconst (
	STRING  = '+'
	ERROR   = '-'
	INTEGER = ':'
	BULK    = '$'
	ARRAY   = '*'
)

gotype Value struct {
	typ   string
	str   string
	num   int
	bulk  string
	array []Value
}

  • typ برای تعیین نوع داده‌ای که مقدار (value) حمل می‌کند استفاده می‌شود.
  • str مقدار رشتهٔ دریافت‌شده از رشته‌های ساده (simple strings) را نگه می‌دارد.
  • num مقدار عدد صحیح دریافت‌شده از اعداد صحیح (integers) را نگه می‌دارد.
  • bulk برای ذخیرهٔ رشتهٔ دریافت‌شده از رشته‌های انبوه (bulk strings) استفاده می‌شود.
  • array همهٔ مقادیر دریافت‌شده از آرایه‌ها (arrays) را نگه می‌دارد.

حالا که struct مقدار (Value) را داریم که تجزیه/ضدسریال‌سازی دستورهای RESP را آسان‌تر می‌کند، بیایید Reader را بسازیم تا همهٔ متدهایی را که به ما در خواندن از بافر و ذخیرهٔ آن در struct مقدار کمک می‌کنند در خود داشته باشد.

فرآیند تجزیه یا ضدسریال‌سازی

structها و متدهایی را ساخته‌ایم که خواندن از بافر را آسان‌تر می‌کنند. حالا بیایید متدهایی بسازیم که به‌صورت بازگشتی (recursively) از بافر می‌خوانند. باید برای هر مرحله از ورودی‌ای که دریافت می‌کنیم، دوباره مقدار (Value) را بخوانیم تا بتوانیم آن را بر اساس کاراکترِ ابتدای خط تجزیه کنیم.

gofunc (r *Resp) Read() (Value, error) {
	_type, err := r.reader.ReadByte()

	if err != nil {
		return Value{}, err
	}

	switch _type {
	case ARRAY:
		return r.readArray()
	case BULK:
		return r.readBulk()
	default:
		fmt.Printf("Unknown type: %v", string(_type))
		return Value{}, nil
	}
}

همان‌طور که در اولین قدم انجام دادیم، اولین بایت را می‌خوانیم تا نوع RESP را که تجزیه خواهیم کرد تعیین کنیم. سپس از یک دستور switch استفاده می‌کنیم تا بر اساس نوع، آن را تجزیه کنیم.

فعلاً فقط با آرایه (Array) و رشتهٔ انبوه (Bulk) سروکار خواهیم داشت.

حالا ReadArray را پیاده‌سازی کنیم؛ زیرا اولین دستوری است که از کلاینت‌ها دریافت می‌کنیم.

قبل از نوشتن متد، به یاد داشته باشید که آرایهٔ RESP این‌گونه است:

*2\r\n$5\r\nhello\r\n$5\r\nworld\r\n

برای آسان‌تر شدن فهم، به‌جای «\r\n» می‌توانیم آن را به خطوط تقسیم کنیم:

text*2
$5
hello
$5
world

برای خواندن آرایه این مراحل را دنبال می‌کنیم:

  • اولین بایت را رد می‌کنیم؛ زیرا قبلاً در متد Read خوانده‌ایم.
  • عدد صحیحی را می‌خوانیم که تعداد عناصر آرایه را نشان می‌دهد.
  • روی آرایه پیمایش می‌کنیم و برای هر خط، متد Read را صدا می‌زنیم تا نوع را بر اساس کاراکتر ابتدای خط تجزیه کند.
  • در هر پیمایش، مقدار تجزیه‌شده را به آرایه در شیء Value اضافه می‌کنیم و آن را برمی‌گردانیم.
gofunc (r *Resp) readArray() (Value, error) {
	v := Value{}
	v.typ = "array"

	// خواندن طول آرایه
	length, _, err := r.readInteger()
	if err != nil {
		return v, err
	}

	// برای هر خط، مقدار را تجزیه و بخوان
	v.array = make([]Value, length)
	for i := 0; i < length; i++ {
		val, err := r.Read()
		if err != nil {
			return v, err
		}

		// افزودن مقدار تجزیه‌شده به آرایه
		v.array[i] = val
	}

	return v, nil
}

حالا که کد کامل است و تجزیه‌گر کار می‌کند، باید نوع Bulk را پیاده‌سازی کنیم تا readArray بداند مقدار را چگونه برگرداند.

قبلاً رشته‌های انبوه را پوشش داده‌ایم؛ اما بیایید قالب آن‌ها را به‌سرعت مرور کنیم:

$5\r\nhello\r\n

text$5
hello

برای خواندن Bulk این مراحل را دنبال می‌کنیم:

  • اولین بایت را رد می‌کنیم؛ زیرا قبلاً در متد Read خوانده‌ایم.
  • عدد صحیحی را می‌خوانیم که تعداد بایت‌های رشتهٔ انبوه را نشان می‌دهد.
  • رشتهٔ انبوه را می‌خوانیم و بعد از آن «\r\n» که پایان رشتهٔ انبوه را نشان می‌دهد.
  • شیء Value را برمی‌گردانیم.
gofunc (r *Resp) readBulk() (Value, error) {
	v := Value{}

	v.typ = "bulk"

	len, _, err := r.readInteger()
	if err != nil {
		return v, err
	}

	bulk := make([]byte, len)

	r.reader.Read(bulk)

	v.bulk = string(bulk)

	// خواندن CRLF پایانی
	r.readLine()

	return v, nil
}
نکته: توجه کنید که بعد از خواندن رشته، r.readLine() را صدا می‌زنیم تا «\r\n»ای را که به‌دنبال هر رشتهٔ انبوه می‌آید بخوانیم. اگر این کار را نکنیم، اشاره‌گر (pointer) در «\r» باقی می‌ماند و متد Read قادر نخواهد بود رشتهٔ انبوه بعدی را درست بخواند.

نوشتن RESP (Writing RESP)

در مقالهٔ قبلی، بخش اول RESP را نوشتیم که همان تجزیه است و مسئول تبدیل RESP به اشیاء Value است. از این طریق می‌توانیم بفهمیم کلاینت چه دستورهایی فرستاده است. در این بخش، می‌بینیم که چگونه با RESP به کلاینت پاسخ دهیم و Writer را بنویسیم.

از آنجا که برای تبدیل RESP به struct گو از Value استفاده می‌کنیم، می‌توانیم بفهمیم چه چیزی لازم است. همچنین از Value استفاده می‌کنیم تا پاسخی را که قرار است به کلاینت بفرستیم ثبت کنیم؛ چه یک رشته باشد، چه Bulk و چه آرایه.

اولین قدمی که باید برداریم، نوشتن Marshal است که Value را به بایت‌هایی تبدیل می‌کند که پاسخ RESP را نشان می‌دهند.

رشته‌های ساده (Simple Strings)

اولین نوع، رشتهٔ ساده خواهد بود؛ زیرا آسان است.

gofunc (v Value) marshalString() []byte {
	var bytes []byte
	bytes = append(bytes, STRING)
	bytes = append(bytes, v.str...)
	bytes = append(bytes, '\r', '\n')

	return bytes
}

به‌سادگی، یک آرایهٔ بایت می‌سازیم و رشته را اضافه می‌کنیم و سپس CRLF (بازگشت به ابتدای خط و خط جدید). توجه کنید که بدون CRLF مشکل پیش می‌آید؛ زیرا کلاینت RESP بدون آن پاسخ را نمی‌فهمد.

رشتهٔ انبوه (Bulk String)

gofunc (v Value) marshalBulk() []byte {
	var bytes []byte
	bytes = append(bytes, BULK)
	bytes = append(bytes, strconv.Itoa(len(v.bulk))...)
	bytes = append(bytes, '\r', '\n')
	bytes = append(bytes, v.bulk...)
	bytes = append(bytes, '\r', '\n')

	return bytes
}

آرایه (Array)

gofunc (v Value) marshalArray() []byte {
	len := len(v.array)
	var bytes []byte
	bytes = append(bytes, ARRAY)
	bytes = append(bytes, strconv.Itoa(len)...)
	bytes = append(bytes, '\r', '\n')

	for i := 0; i < len; i++ {
		bytes = append(bytes, v.array[i].Marshal()...)
	}

	return bytes
}

توجه کنید که در مورد آرایه، متد Marshal را روی شیء Value داخل حلقه صدا می‌زنیم تا صرف‌نظر از نوعش تبدیل شود. این همان چیزی است که از بازگشت (recursion) منظور داریم؛ همان‌طور که در بخش اول هنگام انجام Parse به آن اشاره کردیم.

برای ساخت Writer بسیار ساده است. تنها چیزی که نیاز داریم یک struct Writer است که io.Writer بگیرد.

gotype Writer struct {

}

func NewWriter(w io.Writer) *Writer {
	return &Writer{writer: w}

سپس متدی می‌سازیم که Value می‌گیرد و بایت‌هایی را که از متد Marshal می‌گیرد روی Writer می‌نویسد.

gofunc (w *Writer) Write(v Value) error {

	_, err := w.writer.Write(bytes)
	if err != nil {
		return err

	return nil
}

نوشتن دستورهای Redis (Writing Redis Commands)

سریال‌ساز را نوشته‌ایم و یاد گرفته‌ایم که پس از دریافت هر دستوری، چگونه به کلاینت پاسخ دهیم.

حالا Handler دستورها را می‌سازیم و شروع به نوشتن برخی دستورهای Redis می‌کنیم.

Handler دستورها (CommandsHandler)

همان‌طور که قبلاً اشاره کردیم، درخواستی که از کلاینت دریافت می‌کنیم یک آرایهٔ RESP است که به ما می‌گوید کلاینت می‌خواهد کدام دستور را بفرستد.

پس ما همیشه Handler را بر اساس نام دستور تعریف می‌کنیم که اولین عنصر در آرایهٔ RESP است و بقیهٔ عناصر آرگومان‌ها خواهند بود.

بیایید فایل جدیدی به نام handler.go بسازیم و Handler خود را تعریف کنیم:

govar Handlers = map[string]func([]Value) Value

حالا اولین دستور را بنویسیم که همان PING است:

gofunc ping(args []Value) Value {
	return Value{typ: "string", str: "PONG"}
}

و دستور PING را به نقشهٔ handler که ساخته بودیم اضافه کنیم:

govar Handlers = map[string]func([]Value) Value{
	"PING": ping,
}

توجه کنید که نام دستور را با حروف بزرگ نوشته‌ایم؛ زیرا دستورهای Redis به حروف بزرگ و کوچک حساس نیستند (case-insensitive).

برای آزمایش دستور PING، بیایید main.go را تغییر دهیم تا شیء Value را به handler بفرستد:

gofor {
	resp := NewResp(conn)
	value, err := resp.Read()
	if err != nil {
		fmt.Println(err)
		return
	}

	if value.typ != "array" {
		fmt.Println("Invalid request, expected array")
		continue
	}

	if len(value.array) == 0 {
		fmt.Println("Invalid request, expected array length > 0")
		continue
	}

	command := strings.ToUpper(value.array[0].bulk)
	args := value.array[1:]

	writer := NewWriter(conn)

	handler, ok := Handlers[command]
	if !ok {
		fmt.Println("Invalid command: ", command)
		writer.Write(Value{typ: "string", str: ""})
		continue
	}

	result := handler(args)
	writer.Write(result)
}

کاری که اینجا انجام دادیم این است که اولین درخواست را دریافت می‌کنیم و شیء Value را از آن خارج می‌کنیم. سپس برخی اعتبارسنجی‌ها انجام می‌دهیم تا مطمئن شویم دستور یک آرایه است و خالی نیست. بعد از آن، اولین عنصر آرایه را برمی‌داریم و به حروف بزرگ تبدیل می‌کنیم که نام دستور خواهد بود. بقیهٔ عناصر آرگومان‌ها خواهند بود.

اگر توضیح برایتان واضح نیست، اینجا مثالی از یک شیء Value است وقتی می‌گوییم SET name Ahmed:

goValue{
	typ: "array",
	array: []Value{
		Value{typ: "bulk", bulk: "SET"},
		Value{typ: "bulk", bulk: "name"},
		Value{typ: "bulk", bulk: "Ahmed"},
	},
}

پس کد بالا باعث می‌شود دستور و آرگومان‌ها این‌گونه باشند:

gocommand := Value{typ: "bulk", bulk: "SET"}.bulk // "SET"

args := []Value{
	Value{typ: "bulk", bulk: "name"},
	Value{typ: "bulk", bulk: "Ahmed"},
}

حالا در Redis، دستور PING یک آرگومان می‌گیرد و اگر ارائه شده باشد، به‌جای کلمهٔ «PONG» همان آرگومان را برمی‌گرداند. پس بیایید این را اعمال کنیم:

gofunc ping(args []Value) Value {
	if len(args) == 0 {
		return Value{typ: "string", str: "PONG"}
	}

	return Value{typ: "string", str: args[0].bulk}
}

دستورهای SET و GET

قدم‌های بعدی آسان خواهند بود و به دانش شما از Go و ساختمان داده‌ها وابسته‌اند؛ زیرا بخش سخت کار وقتی پیاده‌سازی RESP و Handler را انجام دادیم تمام شده است.

دستور SET در Redis یک جفت کلید-مقدار است. می‌توانید در هر زمانی یک کلید را با یک مقدار مشخص تنظیم کنید و بعداً با دستور GET آن را بازیابی کنید.

ساختمان داده‌ای که استفاده خواهیم کرد یک نقشهٔ هش (Hash Map) یا map[string]string است.

بیایید به handler.go برویم و دستور SET را تعریف کنیم:

govar SETs = map[string]string{}
var SETsMu = sync.RWMutex{}

func set(args []Value) Value {
	if len(args) != 2 {
		return Value{typ: "error", str: "ERR wrong number of arguments for 'set' command"}
	}

	key := args[0].bulk
	value := args[1].bulk

	SETsMu.Lock()
	SETs[key] = value
	SETsMu.Unlock()

	return Value{typ: "string", str: "OK"}
}

ما از sync.RWMutex استفاده می‌کنیم؛ زیرا سرور ما قرار است درخواست‌ها را به‌صورت هم‌زمان (concurrent) مدیریت کند. از RWMutex استفاده می‌کنیم تا مطمئن شویم نقشهٔ SETs هم‌زمان توسط چند نخ (thread) اصلاح نمی‌شود.

احتمالاً می‌توانید تصور کنید که دستور GET چگونه کار خواهد کرد. اگر کلید را پیدا کنیم، مقدارش را برمی‌گردانیم؛ در غیر این صورت nil برمی‌گردانیم.

gofunc get(args []Value) Value {
	if len(args) != 1 {
		return Value{typ: "error", str: "ERR wrong number of arguments for 'get' command"}
	}

	key := args[0].bulk

	SETsMu.RLock()
	value, ok := SETs[key]
	SETsMu.RUnlock()

	if !ok {
		return Value{typ: "null"}
	}

	return Value{typ: "bulk", bulk: value}
}

پس از پیاده‌سازی دستورهای SET و GET، باید آن‌ها را در نقشهٔ Handlers ثبت کنیم:

govar Handlers = map[string]func([]Value) Value{
	"PING": ping,
	"SET":  set,
	"GET":  get,
}

دستورهای HSET و HGET

به زبان ساده، این دستورها یک نقشهٔ هش داخل یک نقشهٔ هش هستند؛ یعنی map[string]map[string]string. نام هش را می‌گیرند و سپس کلید و مقدار. این به ما اجازه می‌دهد داده‌هایی مانند این ذخیره کنیم:

json{
	"users": {
		"u1": "Ahmed",
		"u2": "Mohamed",
	},
	"posts": {
		"p1": "Hello World",
		"p2": "Welcome to my blog",
	},
}

برای مثال، اگر بخواهیم کاربری به نام Ahmed با شناسهٔ u1 ذخیره کنیم، از دستور HSET استفاده می‌کنیم:

HSET users u1 Ahmed

و اگر بخواهیم پستی به نام Hello World با شناسهٔ p1 ذخیره کنیم، از دستور HSET استفاده می‌کنیم:

HSET posts u1 Hello World

برای بازیابی کاربر Ahmed از دستور HGET استفاده می‌کنیم:

HGET users u1

کد بسیار شبیه به دستورهای SET و GET خواهد بود. تفاوت در این است که HSETها map[string]map[string]string خواهند بود.

govar HSETs = map[string]map[string]string{}
var HSETsMu = sync.RWMutex{}

func hset(args []Value) Value {
	if len(args) != 3 {
		return Value{typ: "error", str: "ERR wrong number of arguments for 'hset' command"}
	}

	hash := args[0].bulk
	key := args[1].bulk
	value := args[2].bulk

	HSETsMu.Lock()
	if _, ok := HSETs[hash]; !ok {
		HSETs[hash] = map[string]string{}
	}
	HSETs[hash][key] = value
	HSETsMu.Unlock()

	return Value{typ: "string", str: "OK"}
}

و دستور HGET این‌گونه خواهد بود:

gofunc hget(args []Value) Value {
	if len(args) != 2 {
		return Value{typ: "error", str: "ERR wrong number of arguments for 'hget' command"}
	}

	hash := args[0].bulk
	key := args[1].bulk

	HSETsMu.RLock()
	value, ok := HSETs[hash][key]
	HSETsMu.RUnlock()

	if !ok {
		return Value{typ: "null"}
	}

	return Value{typ: "bulk", bulk: value}
}

همچنین باید این دستورها را در نقشهٔ Handlers ثبت کنیم:

govar Handlers = map[string]func([]Value) Value{
	"PING":    ping,
	"SET":     set,
	"GET":     get,
	"HSET":    hset,
	"HGET":    hget,
	"HGETALL": hgetall,
}

جمع‌بندی

تا این نقطه، یک پایگاه دادهٔ درون‌حافظه‌ای ساخته‌ایم که برای دستورهای پشتیبانی‌شده با سرور Redis سازگار است. تفاوت با Redis، دستورهای باقیمانده‌ای است که هنوز پیاده‌سازی نکرده‌ایم. این می‌تواند چالشی برای شما باشد تا خودتان آن‌ها را بررسی کنید و سعی کنید خودتان پیاده‌سازی‌شان کنید.

مشکل فعلی این است که داده‌ها را از دست می‌دهیم؛ زیرا فقط به حافظه تکیه می‌کنیم. در بخش بعدی، آخرین قدمی را که نیاز داریم پوشش می‌دهیم: ماندگاری داده‌ها. خواهیم دید که چگونه می‌توانیم از AOF برای ذخیرهٔ داده‌ها روی دیسک استفاده کنیم و هنگام بالا آمدن سرور، آن‌ها را دوباره بخوانیم.

نوشتن داده‌ها روی دیسک (Writing Data to Disk)

در بخش‌های قبلی، یک پایگاه دادهٔ درون‌حافظه‌ای پیاده‌سازی کردیم و با استفاده از پروتکل RESP آن را با Redis سازگار ساختیم.

در این بخش، ماندگاری داده‌ها (data persistence) را روی پایگاه دادهٔ خودمان اعمال می‌کنیم. ماندگاری داده‌ها برای هر پایگاه داده‌ای ویژگی مهمی است؛ حتی برای پایگاه دادهٔ درون‌حافظه‌ای؛ زیرا موارد زیادی وجود دارد که ممکن است بخواهید عملیات‌های مختلفی روی داده‌ها انجام دهید؛ اما ابزار می‌تواند با ذخیرهٔ داده‌ها روی دیسک دوام (durability) را هم فراهم کند تا در صورت از کار افتادن یا راه‌اندازی مجدد سرور، داده‌ها را از دست ندهید.

مفهوم ماندگاری گسترده است و بسته به نحوهٔ ذخیره‌سازی و مدیریت داده‌ها متفاوت است. برای مثال، پایگاه‌های دادهٔ SQL مانند SQLite و MySQL اجازه نمی‌دهند هیچ رکوردی به هر شکلی از دست برود. کد این بخش برای تضمین این موضوع بسیار پیچیده است.

همین موضوع دربارهٔ Redis صدق می‌کند. بسته به نیازتان، روش‌های مختلفی برای ماندگاری داده‌ها وجود دارد:

  • RDB (پایگاه دادهٔ Redis): این یک عکس فوری (snapshot) از داده‌هاست که در بازه‌های منظم بر اساس پیکربندی ساخته می‌شود. مثلاً هر ۳ دقیقه یا هر ۱۰ دقیقه، بسته به اینکه چگونه پیکربندی کنید. در این روش، Redis یک نسخهٔ کامل از داده‌های داخل حافظه می‌گیرد و آن را در یک فایل ذخیره می‌کند. هنگام راه‌اندازی مجدد یا از کار افتادن، داده‌ها از فایل RDB بارگذاری مجدد می‌شوند.
  • AOF (فایل فقط‌الحاقی — Append Only File): در این روش، Redis هر دستور را به‌صورت RESP در فایل ثبت می‌کند. هنگام راه‌اندازی مجدد، Redis همهٔ دستورهای RESP را از فایل AOF می‌خواند و آن‌ها را در حافظه اجرا می‌کند.

AOF

روشی که استفاده خواهیم کرد ساده است؛ زیرا می‌توانیم آن را به struct RESP که ساخته بودیم پیوند بزنیم. هر بار که یک دستور را اجرا می‌کنیم، نمایش RESP آن را در فایل ثبت می‌کنیم. وقتی سرور/کد شروع به کار می‌کند، از فایل AOF می‌خواند و این دستورها را به reader می‌فرستد که آن‌ها را در حافظه اجرا می‌کند.

نوشتن struct AOF

اولین قدم این است که فایلی به نام aof.go بسازیم که همهٔ کدهای مربوط به AOF را در خود داشته باشد.

  • اول، struct Aof را می‌سازیم که فایل ذخیره‌شده روی دیسک و یک bufio.Reader را برای خواندن دستورهای RESP از فایل نگه می‌دارد.
gotype Aof struct {
	file *os.File
	rd   *bufio.Reader
	mu   sync.Mutex
}

سپس متد NewAof را می‌سازیم که هنگام شروع سرور در main.go استفاده می‌شود.

gofunc NewAof(path string) (*Aof, error) {
	f, err := os.OpenFile(path, os.O_CREATE|os.O_RDWR, 0666)
	if err != nil {
		return nil, err
	}

	aof := &Aof{
		file: f,
		rd:   bufio.NewReader(f),
	}

	// شروع یک گوروتین برای همگام‌سازی AOF روی دیسک هر ۱ ثانیه
	go func() {
		for {
			aof.mu.Lock()

			aof.file.Sync()

			aof.mu.Unlock()

			time.Sleep(time.Second)
		}
	}()

	return aof, nil
}
  • آنچه در اینجا اتفاق می‌افتد این است که اول، اگر فایل وجود نداشته باشد آن را می‌سازیم یا اگر وجود داشته باشد بازش می‌کنیم.
  • سپس bufio.Reader را می‌سازیم تا از فایل بخوانیم.
  • در حالی که سرور در حال اجراست، یک گوروتین شروع می‌کنیم تا فایل AOF را هر ۱ ثانیه با دیسک همگام (sync) کند.

ایدهٔ همگام‌سازی هر ثانیه تضمین می‌کند که تغییراتی که انجام داده‌ایم همیشه روی دیسک موجود باشند. بدون همگام‌سازی، این تصمیم به خودِ سیستم‌عامل واگذار می‌شود که چه زمانی فایل را روی دیسک خالی کند. با این رویکرد، تضمین می‌کنیم که داده‌ها حتی در صورت از کار افتادن، همیشه در دسترس باشند. اگر هر داده‌ای از دست برود، فقط در همان ثانیهٔ از کار افتادن خواهد بود که نرخ قابل قبولی است.

اگر دوام ۱۰۰٪ می‌خواهید، به گوروتین نیاز نخواهیم داشت؛ در عوض، فایل را هر بار که یک دستور اجرا می‌شود همگام می‌کنیم. اما این باعث عملکرد ضعیف در عملیات‌های نوشتن می‌شود؛ زیرا عملیات‌های ورودی/خروجی (IO) گران‌قیمت هستند.

متد بعدی Close است که تضمین می‌کند هنگام خاموش شدن سرور، فایل به‌درستی بسته شود.

gofunc (aof *Aof) Close() error {
	aof.mu.Lock()
	defer aof.mu.Unlock()

	return aof.file.Close()
}

بعد از آن، متد Write را می‌سازیم که هر بار درخواستی از کلاینت دریافت کنیم، برای نوشتن دستور در فایل AOF استفاده می‌شود.

gofunc (aof *Aof) Write(value Value) error {
	aof.mu.Lock()
	defer aof.mu.Unlock()

	_, err := aof.file.Write(value.Marshal())
	if err != nil {
		return err
	}

	return nil
}

توجه کنید که از v.Marshal() برای نوشتن دستور در فایل استفاده می‌کنیم؛ در همان قالب RESP که دریافت می‌کنیم. به این ترتیب، وقتی بعداً فایل را می‌خوانیم، می‌توانیم این خطوط RESP را تجزیه کنیم و آن‌ها را دوباره در حافظه بنویسیم.

نوشتن در AOF

تنها کاری که باید بکنیم این است که در main.go از NewAof استفاده کنیم و با هر درخواستی از کلاینت، در فایل AOF بنویسیم.

gofunc main() {
	fmt.Println("Listening on port :6379")

	// ساخت یک سرور جدید
	l, err := net.Listen("tcp", ":6379")
	if err != nil {
		fmt.Println(err)
		return
	}

	aof, err := NewAof("database.aof")
	if err != nil {
		fmt.Println(err)
		return
	}
	defer aof.Close()

	// گوش دادن برای اتصال‌ها
	conn, err := l.Accept()
	if err != nil {
		fmt.Println(err)
		return
	}

	defer conn.Close()

	for {
		resp := NewResp(conn)
		value, err := resp.Read()
		if err != nil {
			fmt.Println(err)
			return
		}

		if value.typ != "array" {
			fmt.Println("Invalid request, expected array")
			continue
		}

		if len(value.array) == 0 {
			fmt.Println("Invalid request, expected array length > 0")
			continue
		}

		command := strings.ToUpper(value.array[0].bulk)
		args := value.array[1:]

		writer := NewWriter(conn)

		handler, ok := Handlers[command]
		if !ok {
			fmt.Println("Invalid command: ", command)
			writer.Write(Value{typ: "string", str: ""})
			continue
		}

		if command == "SET" || command == "HSET" {
			aof.Write(value)
		}

		result := handler(args)
		writer.Write(result)
	}
}
نکته: توجه کنید که فقط دستورهای SET را می‌نویسیم؛ زیرا دستورهای دیگری مانند GET، HGET و HGETALL نیازی به ذخیره‌سازی ندارند و تفاوتی ایجاد نمی‌کنند؛ به‌جز افزایش اندازهٔ فایل AOF.

اگر سرور را اجرا کنیم و دستوری مانند:

را اجرا کنیم، متوجه می‌شویم که فایل database.aof حاوی محتوای زیر است:

$4

$5
ahmed

همین بود برای بخش نوشتن. حالا باید دستورها را از فایل AOF بخوانیم.

خواندن AOF

هنگام خواندن فایل AOF، در این مثال می‌توانیم فرض کنیم که فایل معتبری است؛ زیرا خودمان آن را ساخته‌ایم. در دنیای واقعی، همیشه این‌طور نخواهد بود؛ زیرا ممکن است فایل خراب (corrupted) شده باشد. اول باید یک متد Read به struct AOF اضافه کنیم.

gofunc (aof *Aof) Read(callback func(value Value)) error {
	aof.mu.Lock()
	defer aof.mu.Unlock()

	resp := NewResp(aof.file)

	for {
		value, err := resp.Read()
		if err == nil {
			callback(value)
		}
		if err == io.EOF {
			break
		}
		return err
	}

	return nil
}

متد Read ما در اینجا یک تابع بازگشتی (callback) با آرگومان از نوع Value می‌گیرد. یک حلقهٔ بی‌نهایت شروع می‌کنیم تا فایل aof را بخوانیم. مهم است بدانید که فایل‌ها رابط io.Reader را پیاده‌سازی می‌کنند؛ به همین دلیل می‌توانیم در main.go یک اتصال (connection) عبور دهیم و در اینجا یک فایل. در این حلقه، شرایط خروج ما به‌این‌صورت است: خطای برگشتی io.EOF نشان می‌دهد که به پایان فایل رسیده‌ایم. این برای ما در اینجا یک خطای «خوب» است و می‌توانیم فقط break بزنیم تا حلقهٔ بی‌نهایت پایان یابد. اگر خطای دیگری برگردد، آن را به فراخواننده برمی‌گردانیم.

تنها کاری که باید بکنیم این است که در ابتدای main.go مقدار aof.Read را صدا بزنیم.

gofunc main() {
	fmt.Println("Listening on port :6379")

	// ساخت یک سرور جدید
	l, err := net.Listen("tcp", ":6379")
	if err != nil {
		fmt.Println(err)
		return
	}

	aof, err := NewAof("database.aof")
	if err != nil {
		fmt.Println(err)
		return
	}
	defer aof.Close()

	aof.Read(func(value Value) {
		command := strings.ToUpper(value.array[0].bulk)
		args := value.array[1:]

		handler, ok := Handlers[command]
		if !ok {
			fmt.Println("Invalid command: ", command)
			return
		}

		handler(args)
	})

	// ...
}

همان‌طور که می‌بینید، از همان کدی که قبلاً برای اجرای دستورها استفاده کردیم، استفاده می‌کنیم. اما این بار، در فایل AOF نمی‌نویسیم؛ زیرا از آن می‌خوانیم.

جمع‌بندی

با این کار، پیاده‌سازی AOF را کامل کردیم و یاد گرفتیم چگونه داده‌ها را روی دیسک ماندگار کنیم. جالب است بدانید که Redis از همین رویکرد برای ماندگاری استفاده می‌کند. می‌توانید این مقاله را بخوانید تا دربارهٔ تفاوت‌های RDB و AOF بیشتر بدانید.
