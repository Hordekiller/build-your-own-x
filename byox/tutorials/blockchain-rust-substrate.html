مقدمه

آموزشی دوستانه برای مبتدیان دربارهٔ چگونگی ساخت زیرساخت‌های جدی و سخت‌کورانهٔ بلاک‌چین در ساب‌ستریت (Substrate)، چارچوبی منبع‌باز.

در این آموزش خودراهبر، از صفر یک بلاک‌چین شبه‌بیت‌کوین و بدون گاز (gas-less) می‌سازید و یاد می‌گیرید که بلاک‌چین بسیار قدرتمندتر از صرفاً قراردادهای هوشمند است.

آزاد باشید که هر بخش از این محتوا را برای برگزاری کارگاه‌های آموزشی خودتان بازسازی کنید!

آنچه یاد خواهید گرفت:

  • پیاده‌سازی مدل دفتر کل UTXO، سازوکار حسابداری بیت‌کوین
  • تغییر منطق استخر تراکنش (transaction pool) شبکه
  • پیکربندی یک بلاک مبدأ (genesis block) و نوشتن چند آزمون
  • استقرار زنجیرهٔ خود و تعامل با گرهٔ زنده با استفاده از یک کلاینت وب

پیش‌نیازها:

  • به هیچ دانشی از بلاک‌چین و Rust نیاز نیست
  • آشنایی مقدماتی با برنامه‌نویسی
  • زمان تخمینی: ۳ ساعت

برای یک راهنمای جزئی‌تر که در آن به‌طور کامل توضیح می‌دهم چرا هر گام را برمی‌داریم و در آن وقت می‌گذاریم تا دربارهٔ ویژگی‌ها (traits) زبان راست بحث کنیم، این ویدیوی همراه آموزش را ببینید:

دورهٔ فشردهٔ مدل دفتر کل UTXO

اگر حساب بانکی دارید، از قبل با مدل دفتر کل «مبتنی بر حساب» (accounts based) آشنا هستید. در این مدل، حساب بانکی شما یک ماندهٔ کلی دارد که در هر تراکنش به آن اعتبار یا از آن بدهکار می‌شود.

بیت‌کوین یک مدل دفتر کل کاملاً متفاوت به نام UTXO یا خروجی‌های تراکنش هزینه‌نشده (Unspent Transaction Outputs) ارائه می‌دهد.

UTXO مانند چک‌های مسافرتی کار می‌کند، از این جهت که:

  1. هر کسی که چک را به‌طور فیزیکی در دست داشته باشد می‌تواند پول را خرج کند. به عبارت دیگر، مجوز خرج‌کردن به خود پول گره خورده است، نه به شمارهٔ حساب.
  2. نمی‌توانید یک چک را پاره کنید و بخش‌هایی از آن را خرج کنید. باید کل چک را خرج کنید و هر باقی‌مانده (change) را در قالب یک چک جدید دریافت کنید.

در مثال زیر، باب یک UTXO به ارزش ۵۰ دلار دارد. او می‌خواهد ۰.۵ دلار به آلیس بدهد؛ پس UTXOهای ۵۰ دلاری خود را نابود می‌کند و دو UTXO جدید به ارزش‌های ۰.۵ دلار (برای آلیس) و ۴۹.۵ دلار (به‌عنوان باقی‌مانده) ایجاد می‌کند.

منبع تصویر: https://freedomnode.com/

رمزنگاری سازوکار بنیادینی است که تنها به باب و نه هیچ‌کس دیگر اجازه می‌دهد UTXOهای خود را خرج کند.

این اطلاعات در یکی از ۳ فیلد هر UTXO ذخیره می‌شود:

  1. یک هش ارجاعی (reference hash) از جایی که UTXO در آن وجود دارد؛ چیزی شبیه یک اشاره‌گر آدرس در پایگاه‌داده
  2. ارزش پولی UTXO، به‌عنوان مثال ۵۰ دلار
  3. کلید عمومیِ «مالک» آن

کلید عمومی با یک «کلید خصوصی» (private key) محرمانه در ارتباط است که فقط مالک آن را دارد. بنابراین برای خرج‌کردن UTXO، مالک باید یک تراکنش را با کلید خصوصی متناظرش به‌صورت رمزنگاری‌شده «امضا» کند. می‌توان امضا را بعداً در برابر «کلید عمومی» بررسی کرد تا اعتبار آن تأیید شود.

برای مثال، وقتی آلیس UTXO خود را خرج می‌کند، به این شکل خواهد بود:

او یک تراکنش جدید (با زمینهٔ خاکستری) ایجاد می‌کند، UTXO خود را به‌عنوان ورودی برای خرج‌شدن فراهم می‌کند و در فیلد sigscript امضای خود را قرار می‌دهد.

توجه: آلیس جزئیات کل تراکنش را «امضا می‌کند». این کار این مزیت را دارد که جزئیات خروجی تراکنش قفل می‌شود تا از دستکاری در سطح شبکه جلوگیری شود. بعداً بلاک‌چین تأیید خواهد کرد که آلیس واقعاً تمام جزئیات این تراکنش را مجاز کرده است.

پیامدهای امنیتی را در بخش ۲ با جزئیات بیشتری پوشش می‌دهیم، آن‌جا که بلاک‌چین خود را در برابر حملات خرابکارانه (malicious attacks) ایمن می‌کنید.

دورهٔ فشردهٔ چارچوب ساب‌ستریت (Substrate)

شما از یک چارچوب بلاک‌چین منبع‌باز به نام Substrate استفاده می‌کنید. Substrate مبتنی بر Rust است و به یک فرمت دستورالعمل‌های باینری به نام وب‌اسمبلی (WebAssembly یا به اختصار Wasm) کامپایل می‌شود.

از همان ابتدا، اجزای اصلی بلاک‌چین مانند یک پایگاه‌دادهٔ توزیع‌شده، یک لایهٔ شبکهٔ همتا‌به‌همتا (peer-to-peer) و سازوکارهای اجماع مختلفی که می‌توانیم از بین آن‌ها انتخاب کنیم را دریافت می‌کنید.

در این آموزش با صف تراکنش و لایه‌های ماژول زمان اجرا (runtime) بسیار آشنا خواهیم شد

بخش ۱: ساخت لایهٔ منطقی بلاک‌چین

۱. در ترمینال، یک بررسی سریع کامپایلر Rust انجام دهید تا مطمئن شوید همه‌چیز به‌درستی دانلود شده است:

shellcargo check -p utxo-runtime
# نگران نباشید اگر این کار مدتی طول بکشد؛ فقط بگذارید اجرا شود!
# باید چند هشدار ببینید اما هیچ خطای ازکاراندازی نبینید

۲. پروژه را در IDE سازگار با Rust موردعلاقهٔ خود باز کنید. برای هایلایت نحوی Rust، IntelliJ یا VSCode را پیشنهاد می‌کنم.

۳. زیرپوشهٔ Runtime را باز کنید که زمان اجرای بلاک‌چین را در خود جای داده است. سپس فایل utxo.rs را باز کنید؛ جایی که بیشتر منطق UTXO بیت‌کوین خود را خواهید ساخت.

یک قالب آغازین استاندارد Substrate می‌بینید، با کامنت‌های درون‌خطی که توضیح می‌دهند چگونه از SDK استفاده کنید. پایین‌تر، همچنین باید ببینید کجا می‌توانید آزمون‌های واحد بنویسید.

۴. درست بعد از خطوط import وابستگی‌ها، ساختارهای داده‌ای را ایجاد کنید که برای نمایش UTXOها و یک تراکنش UTXO لازم‌اند.

rust/// تراکنش منفردی که باید توزیع شود
#[cfg_attr(feature = "std", derive(Serialize, Deserialize))]
#[derive(PartialEq, Eq, PartialOrd, Ord, Default, Clone, Encode, Decode, Hash, Debug)]
pub struct Transaction {
    /// UTXOهایی که باید به‌عنوان ورودی برای تراکنش جاری استفاده شوند
    pub inputs: Vec<TransactionInput>,
    
    /// UTXOهایی که در نتیجهٔ توزیع تراکنش جاری باید ایجاد شوند
    pub outputs: Vec<TransactionOutput>,
}

/// ورودی تراکنش منفرد که به یک UTXO ارجاع می‌دهد
#[cfg_attr(feature = "std", derive(Serialize, Deserialize))]
#[derive(PartialEq, Eq, PartialOrd, Ord, Default, Clone, Encode, Decode, Hash, Debug)]
pub struct TransactionInput {
    /// ارجاع به یک UTXO که باید خرج شود
    pub outpoint: H256,
    
    /// اثبات اینکه مالک تراکنش مجاز به خرج‌کردن UTXO ارجاع‌شده است و
    /// اینکه کل تراکنش دست‌کاری نشده است
    pub sigscript: H512,
}

/// خروجی تراکنش منفردی که باید پس از توزیع تراکنش ایجاد شود
#[cfg_attr(feature = "std", derive(Serialize, Deserialize))]
#[derive(PartialEq, Eq, PartialOrd, Ord, Default, Clone, Encode, Decode, Hash, Debug)]
pub struct TransactionOutput {
    /// ارزش مرتبط با این خروجی
    pub value: Value,

    /// کلید عمومی مرتبط با این خروجی. برای خرج‌کردن این خروجی،
    /// مالک باید با هش‌کردنِ کل «Transaction» و امضای آن
    /// با کلید خصوصی متناظر، اثبات ارائه کند.
    pub pubkey: H256,
}

برای یک راهنمایی دقیق‌تر و توضیح خط‌به‌خط موارد بالا، این ویدیوی همراه را بررسی کنید.

۵. تعیین کنید چه چیزی روی وضعیت زنجیره (chain-state) بلاک‌چین ذخیره شود. این کار درون یک ماکروی Rust به نام decl_storage انجام می‌شود. یک هش‌مپ (hashmap) از اشاره‌گرهای ۲۵۶ بیتی به UTXOها به‌عنوان کلید و خود ساختار UTXO به‌عنوان مقدار ذخیره خواهید کرد. موارد زیر را پیاده‌سازی کنید:

rustdecl_storage! {
    trait Store for Module<T: Trait> as Utxo {
        /// همهٔ خروجی‌های تراکنش هزینه‌نشدهٔ معتبر در این نقشه ذخیره می‌شوند.
        /// مجموعهٔ اولیهٔ UTXO از فهرست ذخیره‌شده در genesis پر می‌شود.
        UtxoStore build(|config: &GenesisConfig| {
            config.genesis_utxos
                .iter()
                .cloned()
                .map(|u| (BlakeTwo256::hash_of(&u), u))
                .collect::<Vec<_>>()
        }): map H256 => Option<TransactionOutput>;

        /// ارزش کل پاداشی که باید میان مراجع تأیید توزیع شود.
        /// این ارزش در طول اجرای بلاک از تراکنش‌ها انباشته می‌شود
        /// و سپس هنگام نهایی‌سازی بلاک میان اعتبارسنج‌ها توزیع می‌شود.
        pub RewardTotal get(reward_total): Value;
    }

    add_extra_genesis {
        config(genesis_utxos): Vec<TransactionOutput>;
    }
}

توجه کنید که علاوه‌بر پیکربندی ذخیره‌سازی، همچنین پیکربندی کردیم که این ذخیره‌سازی در بلاک مبدأ (genesis block) چگونه پر شود. در بلاک ۰، می‌توانید بلاک‌چین خود را با یک بردار موجود از UTXOها بذرپاشی (seed) کنید تا خرج شوند!

۶. امضاهای تراکنش را ایجاد کنید که به کاربران بلاک‌چین بیت‌کوینی شما اجازه می‌دهند UTXOها را خرج کنند. بیایید تابع spend را پیاده‌سازی کنیم:

rust// توابع خارجی: قابل فراخوانی توسط کاربر نهایی
decl_module! {
    pub struct Module<T: Trait> for enum Call where origin: T::Origin {
        fn deposit_event() = default;

        /// یک تراکنش منفرد را توزیع کن و مجموعهٔ UTXO را بر همین اساس به‌روزرسانی کن
        pub fn spend(_origin, transaction: Transaction) -> DispatchResult {
                                    // TransactionValidity{}
            let transaction_validity = Self::validate_transaction(&transaction)?;
            
            Self::update_storage(&transaction, transaction_validity.priority as u128)?;

            Self::deposit_event(Event::TransactionSuccess(transaction));

            Ok(())
        }
}

توجه کنید، به‌زودی چند تابع کمکی برای این منطق تراکنش spend پیاده‌سازی خواهیم کرد.

۷. بلاک‌چین‌ها همچنین می‌توانند هر زمان که تراکنش‌هایی درون‌زنجیره (on-chain) رخ می‌دهد، رویداد (event) منتشر کنند. بلاک‌چین خود را طوری تنظیم کنید که یک نوع رویداد TransactionSuccess را شناسایی کند.

rustdecl_event!(
    pub enum Event {
        /// تراکنش با موفقیت اجرا شد
        TransactionSuccess(Transaction),
    }
);

توجه کنید، در گام ۲، شما از قبل این رویداد را پس از هر تراکنش موفق spend منتشر می‌کنید.

برای توضیح بیشتر خط‌به‌خط موارد بالا، این ویدیوی همراه را بررسی کنید.

بخش ۲: ایمن‌سازی زنجیره در برابر حملات خرابکارانه

در بخش ۱، بستر اصلی ساخت UTXOها را فراهم کردیم. در این بخش، وارد امنیت رمزنگاری زنجیرهٔ خود می‌شویم و منطق تراکنش UTXO را پیاده‌سازی می‌کنیم.

در واقع، آسیب‌پذیری‌های بسیاری وجود دارد که بلاک‌چین بیت‌کوین در برابر آن‌ها دفاع می‌کند:

  • ورودی‌ها و خروجی‌ها خالی نیستند
  • هر ورودی وجود دارد و دقیقاً یک‌بار استفاده می‌شود
  • هر خروجی دقیقاً یک‌بار تعریف می‌شود و ارزش غیرصفر دارد
  • ارزش کل خروجی‌ها نباید از ارزش کل ورودی‌ها تجاوز کند
  • خروجی‌های جدید با خروجی‌های موجود برخورد (collide) نمی‌کنند
  • حملات تکرار (replay attacks) ممکن نیستند
  • امضاهای ورودی ارائه‌شده معتبرند
  • UTXO ورودی واقعاً توسط مالک امضا شده است
  • تراکنش‌ها در برابر دست‌کاری مقاوم‌اند (tamperproof)

۱. حالا بیایید تابع validate_transaction را برای تضمین این بررسی‌های امنیتی پیاده‌سازی کنیم.

rust// توابع «داخلی»، قابل فراخوانی توسط کد.
impl<T: Trait> Module<T> {
    pub fn validate_transaction(transaction: &Transaction) -> Result<ValidTransaction, &'static str> {
        // بررسی الزامات پایه
        ensure!(!transaction.inputs.is_empty(), "no inputs");
        ensure!(!transaction.outputs.is_empty(), "no outputs");

        {
            let input_set: BTreeMap<_, ()> =transaction.inputs.iter().map(|input| (input, ())).collect();
            ensure!(input_set.len() == transaction.inputs.len(), "each input must only be used once");
        }
        {
            let output_set: BTreeMap<_, ()> = transaction.outputs.iter().map(|output| (output, ())).collect();
            ensure!(output_set.len() == transaction.outputs.len(), "each output must be defined only once");
        }

        let mut total_input: Value = 0;
        let mut total_output: Value = 0;
        let mut output_index: u64 = 0;
        let simple_transaction = Self::get_simple_transaction(transaction);

        // متغیرهایی که به استخر تراکنش فرستاده می‌شوند
        let mut missing_utxos = Vec::new();
        let mut new_utxos = Vec::new();
        let mut reward = 0;

        // بررسی اینکه ورودی‌ها معتبرند
        for input in transaction.inputs.iter() {
            if let Some(input_utxo) = <UtxoStore>::get(&input.outpoint) {
                ensure!(sp_io::crypto::sr25519_verify(
                    &Signature::from_raw(*input.sigscript.as_fixed_bytes()),
                    &simple_transaction,
                    &Public::from_h256(input_utxo.pubkey)
                ), "signature must be valid" );
                total_input = total_input.checked_add(input_utxo.value).ok_or("input value overflow")?;
            } else {
                missing_utxos.push(input.outpoint.clone().as_fixed_bytes().to_vec());
            }
        }

        // بررسی اینکه خروجی‌ها معتبرند
        for output in transaction.outputs.iter() {
            ensure!(output.value > 0, "output value must be nonzero");
            let hash = BlakeTwo256::hash_of(&(&transaction.encode(), output_index));
            output_index = output_index.checked_add(1).ok_or("output index overflow")?;
            ensure!(!<UtxoStore>::exists(hash), "output already exists");
            total_output = total_output.checked_add(output.value).ok_or("output value overflow")?;
            new_utxos.push(hash.as_fixed_bytes().to_vec());
        }
        
        // اگر وضعیت رقابتی وجود نداشت، حساب‌وکتاب را بررسی کن
        if missing_utxos.is_empty() {
            ensure!( total_input >= total_output, "output value must not exceed input value");
            reward = total_input.checked_sub(total_output).ok_or("reward underflow")?;
        }

        // جزئیات تراکنش را برمی‌گرداند
        Ok(ValidTransaction {
            requires: missing_utxos,
            provides: new_utxos,
            priority: reward as u64,
            longevity: TransactionLongevity::max_value(),
            propagate: true,
        })
    }
}

اوف، کد زیادی بود! برای دریافت توضیح خط‌به‌خط این‌که چه اتفاقی دارد می‌افتد، بخش ۲ ویدیوی همراه را ببینید.

۲. در بخش ۱، استفاده از چند تابع کمکی داخلی را فرض کردیم؛ به‌طور مشخص مرحله‌ای که وقتی تراکنش‌هایمان اعتبارسنجی می‌شوند، ذخیره‌سازی بلاک‌چین را به‌روزرسانی می‌کنیم. در همان محدودهٔ impl<T: Trait> Module<T> موارد زیر را انجام دهید:

rust/// ذخیره‌سازی را به‌روزرسانی کن تا تغییرات اعمال‌شده توسط تراکنش را منعکس کند
    /// که در آن هر کلید utxo هشی از کل تراکنش و ترتیب آن در بردار TransactionOutputs است
    fn update_storage(transaction: &Transaction, reward: Value) -> DispatchResult {
        // محاسبهٔ مجموع پاداش جدید
        let new_total = <RewardTotal>::get()
            .checked_add(reward)
            .ok_or("Reward overflow")?;
        <RewardTotal>::put(new_total);

        // حذف UTXOهای خرج‌شده
        for input in &transaction.inputs {
            <UtxoStore>::remove(input.outpoint);
        }

        let mut index: u64 = 0;
        for output in &transaction.outputs {
            let hash = BlakeTwo256::hash_of(&(&transaction.encode(), index));
            index = index.checked_add(1).ok_or("output index overflow")?;
            <UtxoStore>::insert(hash, output);
        }

        Ok(())
    }

۲. یک آزمون واحد ساده بنویسید که یک تراکنش ساده را آزمایش می‌کند:

rust    #[test]
    fn test_simple_transaction() {
        new_test_ext().execute_with(|| {
            let alice_pub_key = sp_io::crypto::sr25519_public_keys(SR25519)[0];

            // آلیس می‌خواهد یک utxo جدید به ارزش ۵۰ را برای خودش بفرستد.
            let mut transaction = Transaction {
                inputs: vec![TransactionInput {
                    outpoint: H256::from(GENESIS_UTXO),
                    sigscript: H512::zero(),
                }],
                outputs: vec![TransactionOutput {
                    value: 50,
                    pubkey: H256::from(alice_pub_key),
                }],
            };
            
            let alice_signature = sp_io::crypto::sr25519_sign(SR25519, &alice_pub_key, &transaction.encode()).unwrap();
            transaction.inputs[0].sigscript = H512::from(alice_signature);
            let new_utxo_hash = BlakeTwo256::hash_of(&(&transaction.encode(), 0 as u64)); 
            
            assert_ok!(Utxo::spend(Origin::signed(0), transaction));
            assert!(!UtxoStore::exists(H256::from(GENESIS_UTXO)));
            assert!(UtxoStore::exists(new_utxo_hash));
            assert_eq!(50, UtxoStore::get(new_utxo_hash).unwrap().value);
        });
    }

بخش ۴: پیکربندی منطق استخر تراکنش

در این بخش، تغییر می‌دهید که شبکهٔ شما چگونه تراکنش‌های ورودی را اولویت‌بندی می‌کند و چگونه با یک وضعیت رقابتی (race condition) آزاردهندهٔ UTXO که بیت‌کوین نیز تجربه می‌کند کنار می‌آید. به‌طور خاص، یاد می‌گیرید که بدون کدنویسی زیاد، منطق صف‌بندی تراکنش‌های بلاک‌چین را تغییر دهید.

وضعیت رقابتی زیر را در نظر بگیرید که در آن آلیس UTXO آ (A) خود را برای باب می‌فرستد و UTXO جدیدی به نام ب (B) متعلق به باب ایجاد می‌کند.

آنچه در پشت صحنه رخ می‌دهد این است که تراکنش آلیس شروع به انتشار در میان گره‌های شبکه می‌کند:

بلافاصله، باب تصمیم می‌گیرد این UTXO ب (B) را خرج کند و UTXO ج (C) ایجاد می‌کند.

بنابراین تراکنش او شروع به انتشار در شبکه به سمت گره‌هایی می‌کند که هنوز اخباری از آلیس نشنیده‌اند! این می‌تواند به‌دلیل تأخیر معمول شبکه و سایر محدودیت‌های دنیای واقعی رایج باشد.

گره‌هایی که از باب شنیده‌اند اما هنوز از آلیس نشنیده‌اند، تراکنش او را رد خواهند کرد، زیرا UTXO ب (B) هنوز در وضعیت بلاک‌چین آن‌ها وجود ندارد. اما تراکنش باب معتبر است؛ بنابراین این خطای ناشی از وضعیت رقابتی ایدئال نیست.

در حالت ایده‌آل، می‌توانیم تراکنش‌های معتبر را در یک استخر شبکه صف‌بندی کنیم و منتظر بمانیم تا شرایط پیش‌نیاز برآورده شوند.

۱. خوشبختانه Substrate یک فراخوانی API واحد در اختیار شما می‌گذارد تا منطق ترتیب‌بندی تراکنش را تغییر دهید. تریت (trait) مربوط به runtime_api::TaggedTransactionQueue را به‌صورت زیر پیکربندی کنید:

rust    impl sp_transaction_pool::runtime_api::TaggedTransactionQueue<Block> for Runtime {
        fn validate_transaction(tx: <Block as BlockT>::Extrinsic) -> TransactionValidity {            
            // برون‌گزاره‌هایی (extrinsics) که تراکنش UTXO را نشان می‌دهند به رسیدگی ویژه‌ای نیاز دارند
            if let Some(&utxo::Call::spend(ref transaction)) = IsSubType::<utxo::Module<Runtime>, Runtime>::is_sub_type(&tx.function) {
                match <utxo::Module<Runtime>>::validate_transaction(&transaction) {
                    // اعتبارسنجی تراکنش ناموفق بود
                    Err(e) => {
                        sp_runtime::print(e);
                        return Err(TransactionValidityError::Invalid(InvalidTransaction::Custom(1)));
                    }
                    // وضعیت رقابتی، یا تراکنش آمادهٔ اجراست
                    Ok(tv) => { return Ok(tv); }
                }                
            }

            // برای برون‌گزاره‌های غیر utxo::execute به منطق پیش‌فرض برگرد
            Executive::validate_transaction(tx)
        }
    }

به‌طور مؤثر، به صف تراکنش می‌گوییم که پیش از پردازش تراکنش جدیدی که این UTXO را خرج می‌کند، منتظر وجود داشتنِ هشِ UTXO موردنیاز بماند. استخر تراکنش، UTXOهای رقابتی را تا زمانی که این شرط برای یک بازهٔ زمانی مشخص برآورده شود، در دست نگه می‌دارد.
