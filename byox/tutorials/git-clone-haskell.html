بازپیاده‌سازی «git clone» در Haskell از پایه

⚙ زبان: Haskell ✅ ترجمه شده 🔗 منبع اصلی
منبع اصلی: این صفحه ترجمه فارسی مقاله «Reimplementing git clone in Haskell from the bottom up» از استفان ساسن (مارس ۲۰۱۳) است — بازپیاده‌سازی git clone بدون استفاده از هیچ‌یک از دستورات plumbing گیت. کد منبع در Bitbucket موجود است.
↗ مشاهده منبع اصلی

انگیزه

برای اینکه به بررسی‌هایم درباره ساختارهای داده، پروتکل‌ها و پیاده‌سازی گیت نظم بدهم، تصمیم گرفتم git clone را بدون استفاده از هیچ‌یک از دستورات plumbing گیت یا کتابخانه‌های موجود گیت بازپیاده‌سازی کنم. در این مسیر یادداشت‌هایی نگه داشتم که به فهم اجزای لازم برای بازتولید قابلیت clone کمک می‌کند.

پیاده‌سازی به‌دست‌آمده طبیعتاً ارزش عملی محدودی دارد، اما نیازمند بررسی حوزه‌هایی از گیت بود که کاربر معمولی گیت به‌ندرت با آن‌ها روبه‌رو می‌شود. هدف این تمرین، گسترده‌رفتن بود نه عمیق‌رفتن؛ برای اجرای یک دستور clone مینیمال اما کارا، میان‌برهای خاصی برداشتم.

مرور

برای پیاده‌سازی git clone این حوزه‌ها پوشش داده می‌شوند:

  • پروتکل گیت — پروتکلی که به مشتری گیت اجازه می‌دهد مجموعه تغییرات لازم را با مکانیزم‌های انتقال مختلف (پروتکل بومی گیت، ssh، http) از سرور راه‌دور بگیرد
  • فرمت فایل pack — فرمت انتقال حداقل داده از سرور به مشتری (و به‌طور کلی ذخیره‌سازی کارآمد اشیای بسته‌بندی‌شده در مخازن)
  • ذخیره‌گاه اشیا — مخزن زیربنایی که گیت برای ذخیره commits، trees، tags و محتوای واقعی فایل‌ها به شکل blobs از آن استفاده می‌کند
  • فرمت index — برای ردیابی تغییرات فایل‌ها در شاخه کاری

در پایان مقاله می‌توانیم این‌ها را اجرا کنیم:

ترمینال$> hgit clone git://github.com/juretta/git-pastiche.git

و یک مخزن گیت معتبر می‌گیریم که با مشتری معمولی گیت هم کار می‌کند — بدون استفاده از گیت یا کتابخانه‌های گیت برای بخش clone و راه‌اندازی مخزن. برای متمرکز نگه‌داشتن پیاده‌سازی، فقط پروتکل انتقال git:// پشتیبانی می‌شود و مشتری فقط clone کامل (نه shallow) انجام می‌دهد.

روش کلی: بررسی/مهندسی معکوس رفتار واقعی هنگام اجرای دستور clone، جمع‌آوری اطلاعات دیباگ (متغیرهای محیط دیباگ گیت، ثبت بسته‌های شبکه، Dtrace)، تحقیق درباره پروتکل‌ها و ساختارهای داده و خواندن مستندات رسمی در کد منبع گیت و خود کد منبع گیت.

فرآیند clone

عملیات clone مراحلی دارد که با فراخوانی دستور با یک URL گیت شروع می‌شود:

  1. تجزیه URL برای استخراج host، port و مسیر مخزن
  2. اتصال TCP به سرور گیت با استفاده از پروتکل انتقال بومی
  3. مذاکره بر سر اشیایی که باید منتقل شوند — شامل دریافت وضعیت فعلی مخزن راه‌دور (به شکل آگهی refها) که refهای سرور و هش commit هر ref را نشان می‌دهد
  4. درخواست refهای لازم و دریافت فایل pack که همه اشیای قابل‌دسترسی از refهای درخواستی سرور را شامل می‌شود
  5. ساخت ساختار معتبر پوشه/فایل مخزن روی دیسک
  6. ذخیره اشیا و refها روی دیسک
  7. آماده‌سازی شاخه کاری با فایل‌ها و پوشه‌هایی که نمایانگر نوک ref موردنظرند
  8. ساخت فایل index (ناحیه stage) متناظر با آن نوک و فایل‌های روی دیسک

پروتکل انتقال و سیم بسته pack گیت

برای انتقال داده مخزن (commits، tags، محتوای فایل، اطلاعات ref) فرآیندهای مشتری و سرور گیت درباره حداقل داده لازم برای به‌روزرسانی طرف مقابل مذاکره می‌کنند.

گیت چهار پروتکل انتقال اصلی دارد: پروتکل محلی (دسترسی از طریق فایل‌سیستم)، و سه پروتکل دسترسی راه‌دور: SSH، پروتکل بومی گیت و HTTP. همه این‌ها رویکرد زیربنایی مشترکی دارند: اتصال فرآیندهای مختلف *-pack اجراشده روی مشتری و سرور. برای fetch این یعنی اتصال git fetch-pack روی مشتری به git upload-pack روی سرور؛ برای push، git send-pack مشتری به git receive-pack سرور متصل می‌شود.

کشف refها

فاز کشف ref به مشتری اجازه می‌دهد بفهمد سرور چه داده‌ای دارد. سرور این اطلاعات را در فهرستی از refها ارائه می‌دهد؛ برای هر ref (شاخه‌ها و برچسب‌ها) جدیدترین commitش را می‌نویسد:

ظرفیت‌ها (Capabilities)

به‌عنوان بخشی از کشف ref، مشتری و سرور درباره ظرفیت‌هایی که سرور پشتیبانی می‌کند تبادل اطلاعات می‌کنند. ظرفیت‌ها به‌عنوان بخشی از اولین ref سرور، جدا از جفت hhash/نام ref توسط یک بایت NUL منتقل می‌شوند:

ترمینال3b1031798a00fdf9b574b5857b1721bc4b0e6bac HEAD\0multi_ack thin-pack
  side-band side-band-64k ofs-delta shallow no-progress include-tag
  multi_ack_detailed agent=git/1.8.1

فرمت pkt-line

بسته عملیاتی پروتکل گیت به‌شدت از قالب «pkt-line» استفاده می‌کند: رشته باینری با طول متغیر که طولش در چهار بایت اول pkt-line کد شده است.

ترمینال003f3b1031798a00fdf9b574b5857b1721bc4b0e6bac refs/heads/master\n

چهار بایت اول 003f طول کل رشته (شامل ۴ بایت طول) به هگزادسیمال است (003f = ۶۳ دهدهی).

در Haskell:

haskell-- یک pkt-line با طول کلی پیشونددار بساز. طول ۴ بایت، هگز، با 0 پرشده
pktLine :: String -> String
pktLine msg = printf "%04s%s" (toHex . (4 +) $ length msg) msg

pkt-line با طول صفر یعنی 0000 «flush-pkt» نامیده می‌شود؛ یک pkt-line خاص که برای علامت‌دادن نقطه تحویل موردتوافق در مبادله ارتباط استفاده می‌شود.

مبادله مشتری-سرور

با یک سرور گیت ساده (دستور git daemon) و GIT_TRACE_PACKET=1 می‌توان مبادله واقعی را دید:

ترمینال$> git ls-remote git://127.0.0.1/git-bottom-up
packet:          git> git-upload-pack /git-bottom-up\0host=127.0.0.1\0
packet:          git< 3b1031798a00fdf9b574b5857b1721bc4b0e6bac HEAD\0multi_ack ...
packet:          git< 3b1031798a00fdf9b574b5857b1721bc4b0e6bac refs/heads/master
packet:          git< c4bf7555e2eb4a2b55c7404c742e7e95017ec850 refs/remotes/origin/master
packet:          git< 0000

پیاده‌سازی کشف ref — مشتری اتصال TCP برقرار می‌کند، یک درخواست در قالب pkt-line می‌فرستد، پاسخ را می‌خواند، flush-pkt می‌فرستد و پاسخ را parse می‌کند:

haskelldata Remote = Remote {
    getHost         :: String
  , getPort         :: Maybe Int
  , getRepository   :: String
} deriving (Eq, Show)

lsRemote' :: Remote -> IO [PacketLine]
lsRemote' Remote{..} = withSocketsDo $
    withConnection getHost (show $ fromMaybe 9418 getPort) $ \sock -> do
        let payload = gitProtoRequest getHost getRepository
        send sock payload
        response <- receive sock
        send sock flushPkt -- به سرور بگو قطع شود
        return $ parsePacket $ L.fromChunks [response]

خواندن یک pkt-line — ۴ بایت طول را می‌خوانیم تا بفهمیم چند بایت باید بخوانیم؛ تابع بازگشتی readFully تضمین می‌کند تعداد بایت درخواستی واقعاً خوانده شود (قرارداد recv تضمینی برای یکجا خواندن نمی‌دهد):

haskellreadPacketLine :: Socket -> IO (Maybe C.ByteString)
readPacketLine sock = do
        len <- readFully mempty 4
        if C.null len then return Nothing else
            case readHex $ C.unpack len of
                ((l,_):_) | l > 4 -> do
                     line <- readFully mempty (l-4)
                     return $ Just line
                _                 -> return Nothing
    where readFully acc expected = do
            line <- recv sock expected
            let len  = C.length line
                acc' = acc `mappend` line
                cont = len /= expected && not (C.null line)
            if cont then readFully acc' (expected - len) else return acc'

اگر طول «خط خالی» (0004) یا flush-pkt (0000) باشد، خواندن متوقف شده و Nothing برمی‌گردد.

مذاکره بر سر فایل pack

حالا که مشتری همه refهای آگهی‌شده را می‌داند، می‌تواند refهای لازم را بخواهد. clone ساده‌ترین حالت است: همه refهای سرور را می‌خواهد. جریان کلی:

ترمینالClient -> درخواست بومی
          آگهی ref                          <- Server
Client -> درخواست مذاکره (فهرست refهای خواسته‌شده)
          ارسال packfile                     <- Server

مشتری همه شناسه‌های commit خواسته‌شده را با پیشوند want در قالب pkt-line فهرست می‌کند. پروتکل الزام می‌کند حداقل یک فرمان want فرستاده شود و مشتری نمی‌تواند commit-idای را بخواهد که سرور آگهی نکرده:

ترمینال0077want 8c25759f3c2b14e9eab301079c8b505b59b3e1ef multi_ack_detailed side-band-64k thin-pack ofs-delta agent=git/1.8.2
0032want 8c25759f3c2b14e9eab301079c8b505b59b3e1ef
0032want 4574b4c7bb073b6b661abd0558a639f7a32b3f8f

سرور بر اساس refهای خواسته‌شده، packfile شاملهمه refها و اشیای قابل‌دسترسی از آن‌ها تولید می‌کند (کد کامل در مقاله اصلی):

haskellreceivePack :: Remote -> IO ([Ref], B.ByteString)
receivePack Remote{..} = withSocketsDo $
    withConnection getHost (show $ fromMaybe 9418 getPort) $ \sock -> do
        let payload = gitProtoRequest getHost getRepository
        send sock payload
        response <- receive sock
        let pack = parsePacket $ L.fromChunks [response]
            request = createNegotiationRequest ["multi_ack_detailed",
                        "side-band-64k",
                        "agent=git/1.8.1"] pack ++ flushPkt ++ pktLine "done\n"
        send sock request
        !rawPack <- receiveWithSideband sock (printSideband . C.unpack)
        return (mapMaybe toRef pack, rawPack)

ظرفیت side-band به سرور اجازه می‌دهد گزارش پیشرفت و پنجره اطلاعات خطا را در کنار همان packfile بفرستد (به‌صورت مالتی‌پلکس). بایت اول بعد از طول pkt-line کانال sideband را نشان می‌دهد: 1 تکه‌ای از packfile است (کانال داده)، 2 اطلاعات پیشرفت (چاپ روی stderr با پیشوند remote:)، 3 اطلاعات خطا.

فرمت فایل pack

فایل pack برای انتقال یا ذخیره‌سازی کارآمد تعداد زیادی از اشیای گیت استفاده می‌شود؛ شامل:

  • هدر ۱۲ بایتی: ۴ بایت جادویی 'P' 'A' 'C' 'K'، ۴ بایت نسخه فایل pack و ۴ بایت تعداد اشیا
  • n شیء که هرکدام: هدر طول متغیر (نوع شیء و طول داده بازشده)، برای اشیای دلتایی ۲۰ بایت نام شیء پایه یا افست نسبی، و داده فشرده zlib
  • checksum ۲۰ بایتی SHA1 همه موارد بالا به‌عنوان دنباله

شیء دلتایی اشاره‌گری به شیء پایه دارد و بارش دلتای بین نسخه پایه و نسخه بعدی آن شیء است.

ابزارهای مفید برای بررسی: git verify-pack (اعتبارسنجی packfile‌های ایندکس‌شده) و git unpack-objects (تبدیل packfile به اشیای loose).

هدر packfile

haskellparsePackFile :: I.Iteratee ByteString IO Packfile
parsePackFile = do
    magic       <- endianRead4 MSB -- 4 بایت، big-endian
    version'    <- endianRead4 MSB
    numObjects' <- endianRead4 MSB
    if packMagic == magic
                then parseObjects version' numObjects'
                else return InvalidPackfile
  where packMagic = fromOctets $ map (fromIntegral . ord) "PACK"

هدر شیء pack — اعداد صحیح طول متغیر

هدر شیء از نوعی کدگذاری عدد صحیح بدون علامت با طول متغیر استفاده می‌کند که نوع شیء در بایت اول است:

  • MSB تعیین می‌کند آیا بایت‌های بیشتری برای طول داده لازم است،
  • ۳ بیت نوع شیء: OBJ_COMMIT=1، OBJ_TREE=2، OBJ_BLOB=3، OBJ_TAG=4، OBJ_OFS_DELTA=6، OBJ_REF_DELTA=7،
  • ۴ بیت بخشی از طول (اگر MSB تنظیم باشد بخشی از طول است)

بایت‌های بعدی بخش‌های باقی‌مانده طول را در ۷ بیت کم‌ارزش خود دارند. نسخه C آن بسیار موجز است:

ctype = (c >> 4) & 7;
size = (c & 15);
shift = 4;
while (c & 0x80) {
	pack = fill(1);
	c = *pack;
	use(1);
	size += (c & 0x7f) << shift;
	shift += 7;
}

دلتا‌سازی

بازنمایی‌های دلتایی در packfile از فشرده‌سازی دلتا استفاده می‌کنند تا مقدار داده‌ای که باید منتقل/ذخیره شود کمینه شود. فشرده‌سازی دلتا نمایش محتوای نسخه هدف به‌عنوان «جهش» (دلتا) از محتوای منبع موجود است. الگوریتم دلتای گیت کپی/درج (copy/insert) است: دنباله‌ای از عملیات کپی (افست در بافر منبع + تعداد بایت‌ها) و درج (بایت‌های افزوده‌شده) روی بافر موردنظر اعمال می‌شود.

بافر دلتا با هدری شروع می‌شود که طول بافر منبع و هدف را دارد (دوباره اعداد صحیح طول متغیر):

جدول| Varint - طول بافر منبع/پایه  |
| Varint - طول بافر هدف       |
| n دستور کپی/درج              |

دستور کپی وقتی MSB بایت opcode تنظیم باشد؛ ۴ بیت برای افست و ۳ بیت برای طول، که بایت‌های بعدی را مشخص می‌کنند. دستور درج وقتی MSB تنظیم نباشد: خود opcode تعداد بایت‌هایی است که از بافر دلتا به هدف باید کپی شوند.

haskellpatch :: B.ByteString -- ^ منبع/پایه
      -> B.ByteString -- ^ دلتا
      -> Either String B.ByteString
patch base delta = do
        header <- decodeDeltaHeader delta
        if B.length base == sourceLength header then
            fst $ runGet (run (getOffset header) base delta) delta
        else Left "Source length check failed"

Ref vs. Ofs delta

دو نوع شیء دلتایی وجود دارد: OBJ_REF_DELTA که نام شیء پایه ۲۰ بایتی دارد و OBJ_OFS_DELTA که افست نسبی (منفی) از موقعیت خود شیء دلتا در pack دارد. چک‌سوم‌ها با git verify-pack قابل مشاهده‌اند:

ذخیره‌گاه اشیا

اشیای گیت به‌شکل یک فایل در هر شیء ذخیره می‌شوند (با zlib فشرده): هدر با نوع و اندازه، null byte و سپس داده. نزدیک به دورهٔ داستان گیت از کد داخلی .git استفاده می‌کند:

جدولobject-type SP object-size NUL object-contents
    مثال:  commit 1086 \0 tree 29ff16c9...

refها

refها نام‌هایی برای هش‌های commit هستند؛ فایل‌هایی محتوایشان یا هش است یا ref دیگر (مثل HEAD که ref: refs/heads/master است). پیاده‌سازی آنها ساده است: خواندن فایل‌های refs/heads و refs/tags.

شاخه کاری و index

قالب index (ناحیه stage) فرمت باینری سفارشی با هدر، ورودی‌ها و checksum است؛ هر ورودی شامل مسیر فایل، زمان تغییر، هش SHA-1 و موارد دیگر است.

دستور clone بازپیاده‌شده

کل فرایند در یک تابع:

haskellclone' :: GitRepository -> Remote -> IO ()
clone' repo remote@Remote{..} = do
        (refs,packFile) <- receivePack remote
        let dir = pathForPack repo
            tmpPack = dir </> "tmp_pack_incoming"
        _ <- createDirectoryIfMissing True dir
        B.writeFile tmpPack packFile
        _ <- runReaderT (createGitRepositoryFromPackfile tmpPack refs) repo
        removeFile tmpPack
        runReaderT checkoutHead repo
  1. دریافت packfile و فهرست refهای آگهی‌شده
  2. نوشتن packfile در یک مکان موقت مشخص
  3. تجزیه packfile و ساخت مخزن محلی از روی آن
  4. checkout کردن HEAD در شاخه کاری

برای سادگی، به‌جای نگه‌داشتن packfile، آن را به اشیای loose (یک فایل به ازای هر شیء) باز می‌کنیم.

چه چیزی کم است؟

  • پشتیبانی از پروتکل‌های http و ssh
  • clone های shallow
  • optimization های ایندکس packfile

هدف این تمرین درک {building blocks}گیت بود؛ پیاده‌سازی کامل یک مشتری گیت کار بزرگی است که فراتر از این مقاله است.
