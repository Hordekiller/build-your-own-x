مقدمه

GitHub Apps که قبلاً با نام «Integrations» شناخته می‌شدند، دیروز راه‌اندازی شدند. آن‌ها افزودن خودکارسازی‌ها (automations)، سرویس‌ها و ربات‌ها به مخازن شما را آسان‌تر می‌کنند و امکان به‌اشتراک‌گذاری این موارد با دیگران را نیز فراهم می‌آورند.

مستندات GitHub برای توسعهٔ App در سطح جزئیات عالی است؛ با این حال، درک اینکه دقیقاً به کدام بخش‌ها نیاز دارید و همهٔ آن‌ها چگونه به یکدیگر متصل می‌شوند می‌تواند چالش‌برانگیز باشد. همچنین چندان آسان نیست که بفهمیم این روش چه تفاوتی با «دنیای قدیمی» وب‌هوک‌های پیکربندی‌شدهٔ دستی و حساب‌های ربات دارد.

این پست وبلاگ توسعهٔ gifbot را توصیف می‌کند؛ یک GitHub App ساده که به کامنت‌ها با GIFهای متحرک پاسخ می‌دهد:

آزاد باشید این App را در مخزن خود نصب کنید، از طریق این لینک https://github.com/integration/gifbot.

Appها در برابر ربات‌ها (Apps vs. Bots)

قبل از افزوده‌شدن GitHub Apps، می‌توانستید کارهای خودکار را از طریق GitHub API انجام دهید. روش‌های (methods) موجود گسترده هستند و به شما اجازه می‌دهند تقریباً هر جنبه‌ای از تعاملات خود با GitHub را خودکار کنید. می‌توانید مجموعه‌ای بسیار محدود از عملیات را بدون احراز هویت انجام دهید، اما برای هر عملیات غیرخواندنی باید یک توکن دسترسی شخصی (personal access token) از حساب GitHub خود تولید کنید. این توکن که همهٔ درخواست‌های API را همراهی می‌کند، به ربات اجازه می‌دهد اقداماتی را با استفاده از هویت شما انجام دهد.

بیشتر کارهای خودکارسازی از طریق یک وب‌هوک (webhook) فعال می‌شوند؛ یک URL که برای فراخوانی هنگام وقوع رویدادهای خاص (مثلاً ایجاد issue، ایجاد کامنت) ثبت شده است. ترکیب وب‌هوک‌ها و API به ربات‌ها اجازه می‌دهد طیف کاملی از کارهای خودکارسازی را انجام دهند.

با این حال، این روش یکپارچه‌سازی اگر در حال ساختن رباتی برای استفادهٔ دیگران باشید، محدودیت‌های متعددی دارد. این موارد عبارت‌اند از:

  • توکن دسترسی شخصی «شخصی» است؛ یعنی ربات هویت شما را به خود می‌گیرد.
  • باید مجوزهای (permissions) مناسب برای هر مخزنی که ربات شما روی آن کار می‌کند داشته باشید؛ که ممکن است به این معنا باشد که باید به‌عنوان همکار (collaborator) به مخزن اضافه شوید.
  • وب‌هوک‌ها و مجوزهای موردنیاز آن‌ها باید به‌صورت دستی به هر مخزنی که از ربات استفاده می‌کند اضافه شوند.
  • کاربران احراز هویت‌شده یک محدودیت نرخ (rate limit) بر استفادهٔ خود از API دارند: ۵۰۰۰ درخواست در ساعت. این موضوع محدود می‌کند که ربات شما چقدر می‌تواند محبوب شود!

می‌توانید یک حساب GitHub دیگر برای ارائهٔ هویتی متفاوت بسازید؛ هرچند فقط مجاز به داشتن یک حساب کاربری و یک حساب ربات هستید. این موضوع اولین مشکل را حل می‌کند، اما بقیهٔ آن‌ها همچنان باقی می‌مانند.

در اینجا چند نمونه ربات آورده شده است:

  • mention-bot — رباتی از فیسبوک برای ذکر کردن بازبینان بالقوه.
  • ReadmeCritic — رباتی که کارهای مختلفی برای مرتب‌کردن فایل‌های readme انجام می‌دهد.

ربات‌های فوق Pull Request ایجاد می‌کنند و کامنت اضافه می‌کنند، بنابراین به دسترسی نوشتن (write) در مخازنی که روی آن‌ها کار می‌کنند نیازی ندارند.

نمونهٔ دیگری از سرویس‌های ربات‌مانند، semantic-release است که فرایند انتشار شما را (به npm و GitHub) خودکار می‌کند. به دلیل پیچیدگی راه‌اندازی وب‌هوک‌ها و ایجاد توکن‌های دسترسی (این ربات به دسترسی نوشتن نیاز دارد)، semantic-release یک ابزار CLI دارد که پیکربندی را خودکار می‌کند.

GitHub Apps اخیراً از مرحلهٔ پیش‌انتشار (pre-release، با نام Integrations) به انتشار عمومی گذر کردند؛ دقیقاً دیروز. آن‌ها به توسعه‌دهندگان اجازه می‌دهند خودکارسازی انجام دهند و ربات‌هایی بسازند که از همان GitHub API استفاده می‌کنند، اما با چند مزیت:

  • Appها «هویت» (identity) خودشان را دارند، بنابراین دیگر نیازی به ایجاد حساب ربات ندارید.
  • یک جریان کاری مبتنی بر وب وجود دارد که به کاربران اجازه می‌دهد Appها را اضافه کنند، مجوزهای درخواستی را بررسی کنند و آن‌ها را روی چندین مخزن / سازمان (organisation) اعمال کنند.
  • وب‌هوکی که App شما استفاده می‌کند فقط یک بار پیکربندی می‌شود.
  • محدودیت نرخ ۵۰۰۰ درخواست همچنان اعمال می‌شود، اما این بار برای هر نصب (per-installation).

به‌وضوح GitHub Apps راه آینده است!

در ادامهٔ این پست وبلاگ، روند ایجاد یک ربات GitHub و نحوهٔ تبدیل آن به یک App را بررسی خواهم کرد.

ساخت یک ربات (Building a Bot)

رباتی که برای اهداف نمایشی ساخته‌ام روی AWS به‌عنوان یک تابع Lambda میزبانی می‌شود؛ اگر به نحوهٔ توسعه، بسته‌بندی و استقرار (deploy) در AWS علاقه‌مندید، پست وبلاگ قبلی من را ببینید. در این پست، فقط به کد می‌چسبم!

gifbot به رویدادهای وب‌هوکی پاسخ می‌دهد که هنگام افزوده‌شدن کامنت‌ها به یک مخزن رخ می‌دهند. منطق آن بسیار ساده است: یافتن کامنت‌های حاوی متن جادویی [gifbot:search]، استفاده از Giphy برای یافتن یک GIF مناسب (و گاهی نامناسب!) و سپس ارسال یک پاسخ.

کد زیر از یک wrapper کوچک حول ماژول request نود برای ایجاد یک رابط مبتنی بر promise استفاده می‌کند و چند تابع را تعریف می‌کند؛ یکی که Giphy را جست‌وجو می‌کند و دیگری که یک کامنت ارسال می‌کند:

jsconst requestp = require('./requestAsPromise');

const searchGifs = (searchTerm) =>
  requestp({
    url: 'http://api.giphy.com/v1/gifs/search',
    json: true,
    qs: {
      q: searchTerm,
      api_key: 'dc6zaTOxFJmzC'
    }
  });

const addComment = (url, body, token) =>
  requestp({
    json: true,
    headers: {
      'Authorization': 'token ' + token,
      'User-Agent': 'ColinEberhardt',
      'Accept': 'application/vnd.github.machine-man-preview+json'
    },
    method: 'POST',
    url,
    body: {
      body
    }
  });

هدرها و کلیدهای مختلف موردنیاز هر API در مستندات مربوطهٔ آن‌ها توصیف شده‌اند؛ من وارد جزئیات آن‌ها در این‌جا نمی‌شوم. می‌توانید ببینید که در حالی که Giphy به درخواست‌های ناشناس اجازه می‌دهد، GitHub به یک توکن دسترسی نیاز دارد.

با تعریف این توابع، منطقی که وب‌هوک را مدیریت می‌کند واقعاً بسیار ساده است:

jsconst regex = /\[gifbot:(.*?)\]/g;

const accessToken = process.env.GITHUB_ACCESS_TOKEN;

exports.handler = ({ body }, lambdaContext, callback) => {

  // ۱. بررسی اینکه آیا این اکشن یک کامنت اضافه می‌کند
  if (body.action !== 'created') {
    callback(null, {'message': 'ignored action of type ' + body.action});
    return;
  }

  // ۲. بررسی اینکه آیا متن '[gifbot:search]' در کامنت ظاهر شده است
  const matches = regex.exec(webhook.comment.body);
  if (!matches) {
    callback(null, `The comment didn't summon the almighty gifbot`);
    return;
  }

  const searchTerm = matches[1];

  // ۳. جست‌وجو در Giphy
  searchGifs(searchTerm)
    .then((results) => {
      // ۴. دریافت اولین نتیجه و افزودن یک کامنت
      const gifUrl = results.data[0].images.fixed_height.url;
      comment = `![animated gif of ${searchTerm}](${gifUrl})`;
      return addComment(body.issue.comments_url, comment, accessToken);
    })
    .then(() => callback(null, 'added comment'))
    .catch((err) => callback(err.toString()));
};

فکر می‌کنم کامنت‌های داخل کد بالا کاملاً خودتوضیحی هستند! متوجه خواهید شد که توکن دسترسی به‌صورت خارجی و به‌عنوان یک متغیر محیطی (environment variable) تأمین می‌شود.

برای زنده‌کردن این ربات، باید سه کار انجام دهید:

  1. آن را در جایی مناسب مستقر کنید؛ من از AWS استفاده می‌کنم، اما شما به همان اندازه می‌توانید روی Heroku یا سایر میزبان‌های node مستقر کنید.
  2. یک توکن دسترسی شخصی از حساب GitHub خود، یا یک حساب ربات اختصاصی ایجاد کنید. هنگام ایجاد توکن، scopeها را تعریف می‌کنید که به شما اجازه می‌دهند عملکردهایی را که یک ربات می‌تواند انجام دهد محدود کنید. در این مورد فقط scope «public_repo» لازم است.
  3. برای یکپارچه‌سازی ربات در یک پروژه، به Settings / Webhooks بروید و یک وب‌هوک اضافه کنید که به محل استقرار ربات شما اشاره می‌کند. در این مرحله می‌توانید در مورد انواع رویدادهایی که وب‌هوک شما دریافت می‌کند انتخابی باشید.

این مقدار زیادی تلاش پیکربندی است؛ مخصوصاً چون مراحل ۲ و ۳ باید برای هر مخزنی که ربات با آن یکپارچه می‌شود تکرار شوند.

پس از پیکربندی، این ربات وظیفه‌شناسانه GIFهای متحرک را در صورت درخواست سرو می‌کند:

توجه کنید که ربات در تصویر بالا از هویت من استفاده می‌کند که ایده‌آل نیست.

ساخت یک App (Creating an App)

می‌توانید Appهای جدید را از طریق Settings / Developer Settings / GitHub Apps ایجاد کنید. این فرایند کاملاً ساده است و فقط کمی فرم‌پرکردن نیاز دارد؛ مثلاً نام، توضیحات، صفحهٔ اصلی (homepage). همچنین یک Webhook و مجوزهایی که App شما هنگام نصب به آن‌ها نیاز دارد را مشخص می‌کنید. این موضوع اطلاعاتی را که در مراحل ۲ و ۳ بالا شرح داده شد، اما به‌صورت متمرکز، پوشش می‌دهد.

هنگامی که App شما ایجاد شد، می‌توانید آن را از طریق یک لینک عمومی به اشتراک بگذارید. برای مثال، gifbot از طریق https://github.com/integration/gifbot قابل اشتراک‌گذاری است.

این صفحه به کاربران نهایی این فرصت را می‌دهد که ویژگی‌های ربات/App شما را بررسی کنند و گزینهٔ نصب آن را داشته باشند. وقتی روی دکمهٔ Install کلیک می‌کنند، می‌توانند مجوزهای درخواستی را با جزئیات بیشتری بررسی کنند و تصمیم بگیرند که این App با کدام مخازن یکپارچه شود:

همان‌طور که می‌بینید، این رویکرد امکان نصب ربات را در بسیاری از مخازن با یک کلیک فراهم می‌کند. همچنین، اگر کاربر مجوزهای مدیریتی مناسب داشته باشد، می‌تواند آن را در چندین سازمان نیز نصب کند.

هنگامی که کاربری App را نصب می‌کند، شروع به دریافت رویدادهای وب‌هوک خواهید کرد. این رویدادها دقیقاً همان رویدادهای وب‌هوکی هستند که قبلاً توصیف شدند، با یک افزودهٔ مهم: هر رویداد همچنین یک شناسهٔ نصب (installation ID) را در خود دارد:

json{
  "action": "created",
  "issue": {
    ...
  },
  "installation": {
    "id": 26269
  }
}

همان‌طور که از نام آن پیداست، هر بار که کاربری App شما را نصب می‌کند، یک نصب جدید و یکتا ایجاد می‌شود. محدودیت‌های نرخ استفاده از API برای هر نصب به‌طور مستقل اعمال می‌شوند.

جریان احراز هویت App (App Authentication Flow)

حالا که App ایجاد و نصب شده است، ربات باید با یک جریان کاری احراز هویت / مجوزدهی متفاوت به‌روزرسانی شود. به‌جای توکن دسترسی شخصی که با یک حساب کاربری GitHub (یا ربات) مرتبط است، باید یک توکن دسترسی نصب (installation access token) به‌دست آورید که با یک نصب یکتا مرتبط است.

فرایند به‌دست‌آوردن این توکن شامل ایجاد یک JSON Web Token (JWT) است که «ادعای» (claim) اینکه درخواست از طرف App می‌آید را تأیید می‌کند. برای ارائهٔ این ادعا به دو قطعه اطلاعات نیاز دارید: اولی شناسهٔ این App است که در صفحهٔ تنظیمات نمایش داده می‌شود، و یک کلید خصوصی (private key) که می‌توانید آن را از صفحهٔ تنظیمات تولید و دانلود کنید.

با استفاده از این اطلاعات، یک توکن ایجاد می‌کنید که ویژگی iss آن هویت این App را نشان می‌دهد و سپس با استفاده از کلید خصوصی امضا می‌شود. من از پکیج jsonwebtoken برای ایجاد JWT استفاده می‌کنم، اما هر کتابخانه‌ای که با مشخصات سازگار باشد باید کار کند.

jsconst fs = require('fs');
const jwt = require('jsonwebtoken');
const appId = 2429;

const cert = fs.readFileSync('gifbot-private-key.pem');
const token = jwt.sign({ iss: appId },
  cert, {
    algorithm: 'RS256',
    expiresIn: '10m'
  });

هنگامی که JWT ایجاد شد، از متد API /installations/${installationId}/access_tokens برای درخواست توکن برای نصب داده‌شده استفاده می‌شود:

jsconst requestp = require('./requestAsPromise');

const installationToken = (installationId) => requestp({
  url: `https://api.github.com/installations/${installationId}/access_tokens`,
  json: true,
  headers: {
    'Authorization': 'Bearer ' + token,
    'User-Agent': 'ColinEberhardt',
    'Accept': 'application/vnd.github.machine-man-preview+json'
  },
  method: 'POST'
})
.then(({token}) => token);

در این‌جا یک نمونه پاسخ آورده شده است:

json{
  token: 'v1.3cd2ef6a62...............e062bd73',
  expires_at: '2017-05-21T22:12:38Z'
}

استفاده از این توکن به App اجازه می‌دهد عملیات را، با مجوزهای درخواستی، برای نصب داده‌شده انجام دهد.

یکپارچه‌سازی این منطق در ربات بسیار ساده است. در حال حاضر، ربات با استفاده از یک توکن دسترسی شخصی یک درخواست API واحد انجام می‌دهد، به این شکل:

jsreturn addComment(issueOrPull.comments_url, comment, accessToken);

این می‌تواند به‌روزرسانی شود تا ابتدا توکن دسترسی نصب را به‌دست آورد و سپس از آن برای درخواست‌های API بعدی استفاده کند:

jsreturn installationToken(body.installation.id)
       .then((token) => addComment(issueOrPull.comments_url, comment, token));

از دیدگاه کاربر نهایی، App دقیقاً مانند نسخهٔ یکپارچه‌شده با وب‌هوک کار می‌کند:

با این حال، App حالا هویت خودش را دارد و به‌وضوح به‌عنوان یک «ربات» برچسب‌گذاری شده است.

و همین! پس از به‌دست‌آوردن توکن نصب، می‌توانید از هر یک از متدهای API که برای استفاده به آن‌ها دسترسی (permission) داشته‌اید استفاده کنید.

جمع‌بندی (Conclusions)

امیدوارم این معرفی مفیدی برای GitHub Apps بوده باشد. تعدادی ربات، ابزار و یکپارچه‌سازی وجود دارند که من با آن‌ها روی GitHub کار کرده‌ام و فکر می‌کنم تبدیل آن‌ها به App سودمند خواهد بود. مشتاقم در آینده تعداد بیشتری از این‌ها را ببینم!

با تمرین یکپارچه‌سازی مداوم و استقرار مداوم (Continuous Integration & Deployment — CI/CD) می‌توانیم ویژگی‌های جدید را سریع‌تر به کاربران برسانیم و حلقه‌های بازخورد خود را محکم‌تر کنیم. در این معرفی CI/CD، یک مثال از جریان کاری GitHub Actions را معرفی و توضیح می‌دهم که فرانت‌اند شما را می‌سازد و آن را با GitHub Pages مستقر می‌کند.
