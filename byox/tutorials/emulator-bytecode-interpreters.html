مفسرهای بایت‌کد خانگی

مقدمه

در دهه‌های اخیر استفاده از ماشین‌های مجازی زبان‌های برنامه‌نویسی (virtual programming language machines) بسیار فراگیر شده است. مدتی از نخستین راه‌اندازی ماشین مجازی جاوا در نیمهٔ دوم دههٔ ۹۰ میلادی می‌گذرد؛ بنابراین می‌توانیم با اطمینان بگوییم که مفسرهای بایت‌کد (bytecode interpreters) اکنون کاملاً یک واقعیت‌اند، نه صرفاً یک چشم‌انداز آینده.

به‌نظر من، امروزه استفاده از این فناوری تقریباً جهانی است و درک اصول پایهٔ توسعهٔ مفسرهای بایت‌کد چیزی است که نه‌تنها برای خالقِ نامزدِ بعدیِ «زبان سال» سایت TIOBE، بلکه واقعاً برای هر برنامه‌نویسی مفید خواهد بود.

به‌طور خلاصه، اگر علاقه‌مندید بدانید زبان‌های برنامه‌نویسی محبوب ما اعداد را چگونه جمع می‌زنند، توسعه‌دهندگان ماشین مجازی هنوز بر سر چه مسائلی بحث می‌کنند، یا چگونه رشته‌ها را با عبارات باقاعده (regular expression) تطبیق می‌دهیم، ادامهٔ مقاله را بخوانید.

این مقاله بخشی از یک مجموعه است:

  • بخش ۲ — وقتی خوک‌ها پرواز می‌کنند: بهینه‌سازی مفسرهای بایت‌کد
  • بخش ۳ — مفسر بایت‌کد عبارت باقاعده: جستجوی سوزن‌ها در انبار کاهِ جلسه‌ها

پیش‌زمینه (Background)

یکی از سیستم‌هایی که واحد هوش تجاری (Business Intelligence) ما به‌صورت داخلی توسعه داده، رابطی به شکل یک زبان پرس‌وجوی ساده دارد. نسخهٔ اول سیستم این زبان را «در حال حرکت» تفسیر می‌کرد، بدون کامپایل، و مستقیماً بر اساس رشتهٔ ورودی حاوی پرس‌وجو. نسخهٔ دوم مفسر از یک بایت‌کد میانی استفاده می‌کند که جداسازی زبان پرس‌وجو از اجرای پرس‌وجو را ممکن می‌سازد و در نتیجه کد را ساده‌تر می‌کند.

هنگام کار روی نسخهٔ دوم سیستم، مدتی مرخصی داشتم؛ طی آن هر روز یکی دو ساعت، دور از خانواده، مطالب مربوط به معماری و کارایی مفسرهای بایت‌کد را مطالعه می‌کردم. تصمیم گرفتم یادداشت‌ها و نمونه‌مفسرهای حاصل را در قالب یک سری مقاله به اشتراک بگذارم.

در این مقاله، که اولین مقاله از این سری است، شما را با پنج ماشین مجازی کوچک‌مقیاس (حداکثر تا حدود صد خط کد ساده به زبان C) آشنا می‌کنم که هر یک جنبه‌ای مشخص از توسعهٔ مفسر را آشکار می‌کنند.

خاستگاه بایت‌کدها در زبان‌های برنامه‌نویسی

در طول بیست سال گذشته تعداد عظیمی از ماشین‌های مجازی و مجموعه دستورالعمل‌های مجازی (virtual instruction sets) متنوع ابداع شده‌اند. طبق ویکی‌پدیا، نخستین زبان‌های برنامه‌نویسی از دههٔ ۱۹۶۰ میلادی به فرمت‌های میانی ساده‌شدهٔ مختلفی کامپایل می‌شدند. برخی از این نخستین بایت‌کدها به کد ماشین کامپایل می‌شدند و توسط پردازنده‌های واقعی اجرا می‌شدند؛ برخی دیگر «در حال حرکت» و با استفاده از پردازنده‌های مجازی تفسیر می‌شدند.

محبوبیت مجموعه دستورالعمل‌های مجازی را می‌توان با سه عامل توضیح داد:

  1. مهاجرت مفسرهای بایت‌کد به پلتفرم‌های جدید آسان است.
  2. مفسرهای بایت‌کد سریع‌تر از مفسرهای درخت نحوی (syntax tree) هستند.
  3. توسعهٔ یک ماشین مجازی ساده، به معنای واقعی کلمه، فقط چند ساعت طول می‌کشد.

پس بیایید چند ماشین مجازی ساده به زبان C بسازیم و با استفاده از این مثال‌ها، جنبه‌های فنی اصلی پیاده‌سازی ماشین مجازی را بررسی کنیم.

کدهای مربوط به مثال‌ها را به‌طور کامل می‌توانید در GitHub بیابید. می‌توانید مثال‌ها را با هر کامپایلر GCC نسبتاً جدیدی بسازید:

shellgcc interpreter-basic-switch.c -o interpreter

./interpreter

همهٔ مثال‌ها ساختار یکسانی دارند: ابتدا کد مربوط به خود ماشین مجازی و سپس تابع main با assertهایی که درستی کار کد را بررسی می‌کنند. سعی کرده‌ام opcodeها و کد کلیدی مفسر را به‌شکلی قابل‌دسترس کامنت‌گذاری کنم. امیدوارم حتی کسانی که هر روز به زبان C کد نمی‌نویسند هم از این مقاله بهره‌ای ببرند.

ساده‌ترین مفسر بایت‌کد جهان

همان‌طور که گفتم، ساخت یک مفسر پایه بسیار آسان است. توضیحات بلافاصله پس از فهرست کد آمده‌اند؛ اما بیایید مستقیماً با خود کد شروع کنیم:

cstruct {

 uint8_t *ip;

 uint64_t accumulator;

} vm;
typedef enum {

 /* افزایش ثبات */

 OP_INC,

 /* کاهش ثبات */

 OP_DEC,

 /* توقف اجرا */

 OP_DONE

} opcode;
typedef enum interpret_result {

 SUCCESS,

 ERROR_UNKNOWN_OPCODE,

} interpret_result;
void vm_reset(void)

{

 puts("Reset vm state");

 vm = (typeof(vm)) { NULL };

}
interpret_result vm_interpret(uint8_t *bytecode)

{

 vm_reset();
 puts("Start interpreting");

 vm.ip = bytecode;

 for (;;) {

 uint8_t instruction = *vm.ip++;

 switch (instruction) {

 case OP_INC: {

 vm.accumulator++;

 break;

 }

 case OP_DEC: {

 vm.accumulator--;

 break;

 }

 case OP_DONE: {

 return SUCCESS;

 }

 default:

 return ERROR_UNKNOWN_OPCODE;

 }

 }
 return SUCCESS;

}

اینجا کمتر از صد خط کد وجود دارد، اما همهٔ ویژگی‌های مشخصهٔ یک ماشین مجازی حضور دارند. ماشین یک ثبات (register) منفرد (vm.accumulator)، سه عملیات (افزایش ثبات، کاهش ثبات و خاتمهٔ برنامه) و یک اشاره‌گر به دستورالعمل جاری (vm.ip) دارد.

هر کد عملیات (opcode) با یک بایت رمزگذاری می‌شود و توزیع (dispatch) دستورالعمل‌ها با یک switch معمولی در تابع vm_interpret انجام می‌شود. شاخه‌های switch شامل منطق عملیات‌ها هستند؛ یعنی یا وضعیت ثبات را تغییر می‌دهند یا برنامه را خاتمه می‌دهند.

عملیات‌ها به‌شکل یک آرایهٔ بایتی — بایت‌کد — به تابع vm_interpret فرستاده می‌شوند و به‌صورت ترتیبی اجرا می‌شوند تا اینکه در بایت‌کد به عملیاتی خاتمه‌دهندهٔ ماشین مجازی (OP_DONE) برسیم.

معناشناسی (semantics) جنبهٔ کلیدی هر ماشین مجازی است؛ یعنی مجموعهٔ عملیاتی که می‌توان روی آن انجام داد. در این مورد فقط دو عملیات وجود دارد که مقدار ثبات منفرد را تغییر می‌دهند.

در سال ۲۰۰۹ برخی محققان (Virtual-machine Abstraction and Optimization Techniques) پیشنهاد کردند ماشین‌های مجازی را بسته به اینکه معناشناسی آن‌ها چقدر به معناشناسی سخت‌افزار (ماشین) که بایت‌کد روی آن اجرا می‌شود نزدیک است، به دو دستهٔ سطح‌بالا (high-level) یا سطح‌پایین (low-level) دسته‌بندی کنند.

در حالت افراطی، بایت‌کد ماشین‌های مجازی سطح‌پایین ممکن است کد ماشین سخت‌افزار را به‌طور کامل بازتولید کند؛ با RAM شبیه‌سازی‌شده، مجموعهٔ کاملی از ثبات‌ها، دستورالعمل‌هایی برای کار با پشته و غیره. برای مثال، ماشین مجازی Bochs مجموعه دستورالعمل‌های معماری x86 را بازتولید می‌کند.

و برعکس: عملیات ماشین‌های مجازی سطح‌بالا معناشناسی زبان برنامه‌نویسی تخصصیِ کامپایل‌شده به بایت‌کد را به‌طور نزدیک منعکس می‌کنند. به‌عنوان مثال، SQLite، Gawk و بسیاری از نسخه‌های Prolog این‌گونه کار می‌کنند.

به‌طور کلی، ماشین‌های مجازی زبان‌های برنامه‌نویسی یک سازوکار میانی‌اند که هم عناصر سطح‌بالا و هم سطح‌پایین دارند. ماشین مجازی جاوا که بسیار محبوب است، هم دستورالعمل‌های سطح‌پایین برای کار با پشته دارد و هم پشتیبانی داخلی برای برنامه‌نویسی شیءگرا با تخصیص خودکار حافظه.

کد مثال ارائه‌شده را می‌توان جزو ابتدایی‌ترین ماشین‌های سطح‌پایین دسته‌بندی کرد: هر دستورالعمل مجازی، پوششی بر یک یا دو دستورالعمل سخت‌افزاری است؛ ثبات مجازی کاملاً با یک ثبات سخت‌افزاری پردازنده مطابقت دارد.

آرگومان‌های دستورالعمل‌ها در بایت‌کد

می‌توان گفت ثبات منفرد در مثال ماشین مجازی ما هم‌زمان آرگومان و مقدار بازگشتی همهٔ دستورالعمل‌هایی است که باید اجرا شوند. با این حال، خوب است امکان فرستادن آرگومان به دستورالعمل‌ها را داشته باشیم. یکی از راه‌های انجام این کار، قرار دادن آن‌ها مستقیماً در بایت‌کد است.

بیایید مثال را گسترش دهیم و دستورالعمل‌هایی (OP_ADDI، OP_SUBI) اضافه کنیم که آرگومانی به‌شکل یک بایت، بلافاصله پس از opcode، می‌پذیرند:

cstruct {

 uint8_t *ip;

 uint64_t accumulator;

} vm;
typedef enum {

 /* افزایش ثبات */

 OP_INC,

 /* کاهش ثبات */

 OP_DEC,

 /* افزودن آرگومان مستقیم به ثبات */

 OP_ADDI,

 /* کسر آرگومان مستقیم از ثبات */

 OP_SUBI,

 /* توقف اجرا */

 OP_DONE

} opcode;
typedef enum interpret_result {

 SUCCESS,

 ERROR_UNKNOWN_OPCODE,

} interpret_result;
void vm_reset(void)

{

 puts("Reset vm state");

 vm = (typeof(vm)) { NULL };

}
interpret_result vm_interpret(uint8_t *bytecode)

{

 vm_reset();
 puts("Start interpreting");

 vm.ip = bytecode;

 for (;;) {

 uint8_t instruction = *vm.ip++;

 switch (instruction) {

 case OP_INC: {

 vm.accumulator++;

 break;

 }

 case OP_DEC: {

 vm.accumulator--;

 break;

 }

 case OP_ADDI: {

 /* دریافت آرگومان */

 uint8_t arg = *vm.ip++;

 vm.accumulator += arg;

 break;

 }

 case OP_SUBI: {

 /* دریافت آرگومان */

 uint8_t arg = *vm.ip++;

 vm.accumulator -= arg;

 break;

 }

 case OP_DONE: {

 return SUCCESS;

 }

 default:

 return ERROR_UNKNOWN_OPCODE;

 }

 }
 return SUCCESS;

}

دستورالعمل‌های جدید (رجوع کنید به تابع vm_interpret) آرگومان را از بایت‌کد می‌خوانند و آن را به ثبات اضافه می‌کنند / از ثبات کم می‌کنند.

به این نوع آرگومان، آرگومان مستقیم (immediate argument) می‌گویند، زیرا مستقیماً درون آرایهٔ opcodeها قرار دارد. پیاده‌سازی ما از این جهت محدود است که آرگومان یک بایت منفرد را نشان می‌دهد و فقط می‌تواند ۲۵۶ مقدار بگیرد.

در ماشین مجازی ما، بازهٔ مقادیر ممکن برای آرگومان‌های دستورالعمل اهمیت چندانی ندارد. با این حال، اگر قرار است ماشین مجازی به‌عنوان مفسر یک زبان واقعی استفاده شود، منطقی است بایت‌کد را پیچیده‌تر کنیم: جدولی از ثابت‌ها (constants) جدا از آرایهٔ opcodeها اضافه کنیم و دستورالعمل‌هایی با آرگومان مستقیمِ متناظر با آدرس آرگومان جاری در جدول ثابت‌ها داشته باشیم.

ماشین پشته‌ای (Stack machine)

دستورالعمل‌های ماشین مجازی سادهٔ ما همیشه با یک ثبات کار می‌کنند و هیچ راهی برای فرستادن داده به یکدیگر ندارند. علاوه بر این، دستورالعملِ دارای آرگومان فقط می‌تواند آرگومان مستقیم داشته باشد، در حالی که مثلاً عملیات جمع و ضرب دو آرگومان می‌پذیرند.

به بیان ساده‌تر، ما قادر به ارزیابی عبارت‌های پیچیده نیستیم. برای رفع این مشکل به یک ماشین پشته‌ای (stack machine) نیاز داریم؛ یعنی ماشین مجازی‌ای با پشتهٔ داخلی:

c#define STACK_MAX 256
struct {

 uint8_t *ip;

 /* پشتهٔ با اندازهٔ ثابت */

 uint64_t stack[STACK_MAX];

 uint64_t *stack_top;

 /* یک ثبات منفرد که نتیجه را نگه می‌دارد */

 uint64_t result;

} vm;
typedef enum {

 /* فشردن آرگومان مستقیم روی پشته */

 OP_PUSHI,

 /* گرفتن ۲ مقدار از پشته، جمع و فشردن نتیجه روی پشته */

 OP_ADD,

 /* گرفتن ۲ مقدار از پشته، تفریق و فشردن نتیجه روی پشته */

 OP_SUB,

 /* گرفتن ۲ مقدار از پشته، تقسیم و فشردن نتیجه روی پشته */

 OP_DIV,

 /* گرفتن ۲ مقدار از پشته، ضرب و فشردن نتیجه روی پشته */

 OP_MUL,

 /* گرفتن بالای پشته و قرار دادن آن به‌عنوان نتیجهٔ اجرا */

 OP_POP_RES,

 /* توقف اجرا */

 OP_DONE,

} opcode;
typedef enum interpret_result {

 SUCCESS,

 ERROR_DIVISION_BY_ZERO,

 ERROR_UNKNOWN_OPCODE,

} interpret_result;
void vm_reset(void)

{

 puts("Reset vm state");

 vm = (typeof(vm)) { NULL };

 vm.stack_top = vm.stack;

}
void vm_stack_push(uint64_t value)

{

 *vm.stack_top = value;

 vm.stack_top++;

}
uint64_t vm_stack_pop(void)

{

 vm.stack_top--;

 return *vm.stack_top;

}
interpret_result vm_interpret(uint8_t *bytecode)

{

 vm_reset();
 puts("Start interpreting");

 vm.ip = bytecode;

 for (;;) {

 uint8_t instruction = *vm.ip++;

 switch (instruction) {

 case OP_PUSHI: {

 /* دریافت آرگومان و فشردن آن روی پشته */

 uint8_t arg = *vm.ip++;

 vm_stack_push(arg);

 break;

 }

 case OP_ADD: {

 /* گرفتن ۲ مقدار، جمع آن‌ها و فشردن نتیجه روی پشته */

 uint64_t arg_right = vm_stack_pop();

 uint64_t arg_left = vm_stack_pop();

 uint64_t res = arg_left + arg_right;

 vm_stack_push(res);

 break;

 }

 case OP_SUB: {

 /* گرفتن ۲ مقدار، تفریق آن‌ها و فشردن نتیجه روی پشته */

 uint64_t arg_right = vm_stack_pop();

 uint64_t arg_left = vm_stack_pop();

 uint64_t res = arg_left - arg_right;

 vm_stack_push(res);

 break;

 }

 case OP_DIV: {

 /* گرفتن ۲ مقدار، تقسیم آن‌ها و فشردن نتیجه روی پشته */

 uint64_t arg_right = vm_stack_pop();

 /* فراموش نکنید خطای تقسیم بر صفر را مدیریت کنید */

 if (arg_right == 0)

 return ERROR_DIVISION_BY_ZERO;

 uint64_t arg_left = vm_stack_pop();

 uint64_t res = arg_left / arg_right;

 vm_stack_push(res);

 break;

 }

 case OP_MUL: {

 /* گرفتن ۲ مقدار، ضرب آن‌ها و فشردن نتیجه روی پشته */

 uint64_t arg_right = vm_stack_pop();

 uint64_t arg_left = vm_stack_pop();

 uint64_t res = arg_left * arg_right;

 vm_stack_push(res);

 break;

 }

 case OP_POP_RES: {

 /* گرفتن بالای پشته و قرار دادن آن به‌عنوان مقدار نتیجه */

 uint64_t res = vm_stack_pop();

 vm.result = res;

 break;

 }

 case OP_DONE: {

 return SUCCESS;

 }

 default:

 return ERROR_UNKNOWN_OPCODE;

 }

 }
 return SUCCESS;

}

این مثال از قبل عملیات بیشتری دارد و تقریباً همهٔ آن‌ها صرفاً با پشته کار می‌کنند. OP_PUSHI آرگومان مستقیم خود را روی پشته می‌فشارد. دستورالعمل‌های OP_ADD، OP_SUB، OP_DIV و OP_MUL یک جفت مقدار از پشته می‌گیرند، نتیجه را محاسبه می‌کنند و نتیجه را به پشته برمی‌گردانند. OP_POP_RES مقداری را از پشته می‌گیرد و در ثبات نتایج که برای نتایج کار ماشین مجازی در نظر گرفته شده قرار می‌دهد.

در مورد عملیات تقسیم (OP_DIV)، خطای «تقسیم بر صفر» به‌درستی مدیریت می‌شود (که در غیر این صورت کار ماشین مجازی را متوقف می‌کرد).

این ماشین دامنهٔ عملکرد بسیار وسیع‌تری از ماشین قبلی با ثبات منفرد دارد. این یکی به شما اجازه می‌دهد مثلاً عبارت‌های حسابی پیچیده را محاسبه کنید. مزیت دیگر (و نه کم‌اهمیت) سادگی کامپایل زبان‌های برنامه‌نویسی به بایت‌کد ماشین پشته‌ای است.

ماشین‌های ثبات‌محور (Register machines)

ماشین‌های مجازی پشته‌ای به لطف سادگی‌شان در میان توسعه‌دهندگان زبان‌های برنامه‌نویسی بسیار فراگیر شده‌اند. ماشین مجازی JVM و ماشین مجازی پایتون از این دسته‌اند.

با این حال، این ماشین‌ها معایب خود را هم دارند: باید دستورالعمل‌های ویژه‌ای برای کار با پشته اضافه کنید — همهٔ آرگومان‌ها هنگام محاسبهٔ عبارت‌ها بارها از تنها ساختار داده عبور می‌کنند؛ و تعداد زیادی دستورالعمل اضافی به‌ناچار در کد پشته‌ای ظاهر می‌شود.

علاوه بر این، اجرای هر دستورالعمل اضافی به کار توزیع (dispatch) مربوطه نیاز دارد؛ یعنی رمزگشایی opcode و انتقال به بدنهٔ دستورالعمل.

جایگزین ماشین پشته‌ای، ماشین مجازی ثبات‌محور (register-based) است. این ماشین‌ها از بایت‌کد پیچیده‌تری استفاده می‌کنند: تعداد ثبات‌ها/آرگومان‌ها و تعداد ثبات‌های نتیجه به‌صراحت در هر دستورالعمل کدگذاری می‌شوند. بر این اساس، به‌جای پشته، مجموعهٔ گسترده‌ای از ثبات‌ها به‌عنوان مخزن مقادیر میانی عمل می‌کند.

c#define REGISTER_NUM 16
struct {

 uint16_t *ip;

 /* آرایهٔ ثبات‌ها */

 uint64_t reg[REGISTER_NUM];

 /* یک ثبات منفرد که نتیجه را نگه می‌دارد */

 uint64_t result;

} vm;
typedef enum {

 /* بارگذاری مقدار مستقیم در r0 */

 OP_LOADI,

 /* جمع مقادیر ثبات‌های r0 و r1 و قرار دادن آن در r2 */

 OP_ADD,

 /* تفریق مقادیر ثبات‌های r0 و r1 و قرار دادن آن در r2 */

 OP_SUB,

 /* تقسیم مقادیر ثبات‌های r0 و r1 و قرار دادن آن در r2 */

 OP_DIV,

 /* ضرب مقادیر ثبات‌های r0 و r1 و قرار دادن آن در r2 */

 OP_MUL,

 /* انتقال مقدار از ثبات r0 به ثبات نتیجه */

 OP_MOV_RES,

 /* توقف اجرا */

 OP_DONE,

} opcode;
typedef enum interpret_result {

 SUCCESS,

 ERROR_DIVISION_BY_ZERO,

 ERROR_UNKNOWN_OPCODE,

} interpret_result;
void vm_reset(void)

{

 puts("Reset vm state");

 vm = (typeof(vm)) { NULL };

}
void decode(uint16_t instruction,

 uint8_t *op,

 uint8_t *reg0, uint8_t *reg1, uint8_t *reg2,

 uint8_t *imm)

{

 *op = (instruction & 0xF000) >> 12;

 *reg0 = (instruction & 0x0F00) >> 8;

 *reg1 = (instruction & 0x00F0) >> 4;

 *reg2 = (instruction & 0x000F);

 *imm = (instruction & 0x00FF);

}
interpret_result vm_interpret(uint16_t *bytecode)

{

 vm_reset();

 puts("Start interpreting");

 vm.ip = bytecode;

 uint8_t op, r0, r1, r2, immediate;

 for (;;) {

 /* دریافت (fetch) دستورالعمل */

 uint16_t instruction = *vm.ip++;

 /* رمزگشایی آن */

 decode(instruction, &op, &r0, &r1, &r2, &immediate);

 /* توزیع */

 switch (op) {

 case OP_LOADI: {

 vm.reg[r0] = immediate;

 break;

 }

 case OP_ADD: {

 vm.reg[r2] = vm.reg[r0] + vm.reg[r1];

 break;

 }

 case OP_SUB: {

 vm.reg[r2] = vm.reg[r0] - vm.reg[r1];

 break;

 }

 case OP_DIV: {

 /* فراموش نکنید خطای تقسیم بر صفر را مدیریت کنید */

 if (vm.reg[r1] == 0)

 return ERROR_DIVISION_BY_ZERO;

 vm.reg[r2] = vm.reg[r0] / vm.reg[r1];

 break;

 }

 case OP_MUL: {

 vm.reg[r2] = vm.reg[r0] * vm.reg[r1];

 break;

 }

 case OP_MOV_RES: {

 vm.result = vm.reg[r0];

 break;

 }

 case OP_DONE: {

 return SUCCESS;

 }

 default:

 return ERROR_UNKNOWN_OPCODE;

 }

 }
 return SUCCESS;

}

مثال یک ماشین ثبات‌محور با ۱۶ ثبات را نشان می‌دهد. دستورالعمل‌ها هر یک ۱۶ بیت استفاده می‌کنند و می‌توانند به ۳ روش کدگذاری شوند:

  1. ۴ بیت برای کد عملیات + ۴ بیت برای نام ثبات + ۸ بیت برای آرگومان.
  2. ۴ بیت برای کد عملیات + (۳ × ۴ بیت) برای نام ثبات‌ها.
  3. ۴ بیت برای کد عملیات + ۴ بیت برای نام یک ثبات منفرد + ۸ بیت استفاده‌نشده.

ماشین مجازی کوچک ما عملیات بسیار کمی دارد، بنابراین ۴ بیت (یا ۱۶ عملیات ممکن) برای opcode کاملاً کافی است. خود عملیاتِ مربوطه تعیین می‌کند که بیت‌های باقی‌ماندهٔ دستورالعمل دقیقاً چه چیزی را نشان می‌دهند.

نوع اول کدگذاری (4 + 4 + 8) برای بارگذاری داده در ثبات‌ها با استفاده از عملیات OP_LOADI لازم است. نوع دوم (4 + 4 + 4 + 4) برای عملیات حسابی استفاده می‌شود که باید بدانند جفت آرگومان‌ها را از کجا بیاورند و نتیجهٔ محاسبه را کجا بگذارند. و در نهایت (4 + 4 + 8 بیت استفاده‌نشده) برای دستورالعمل‌هایی با یک ثبات منفرد به‌عنوان آرگومان استفاده می‌شود؛ در مورد ما OP_MOV_RES.

اکنون به منطق ویژه‌ای (تابع decode) برای کدگذاری و رمزگشایی دستورالعمل‌ها نیاز داریم. از طرف دیگر، به لطف اشارهٔ صریح به محل قرارگیری آرگومان‌ها، منطق دستورالعمل‌ها ساده‌تر می‌شود؛ عملیات با پشته حذف می‌شود.

تفاوت‌های کلیدی: در بایت‌کد ماشین ثبات‌محور دستورالعمل‌های کمتری وجود دارد؛ دستورالعمل‌های منفرد دامنهٔ وسیع‌تری دارند؛ کامپایل به این نوع بایت‌کد پیچیده‌تر است؛ و کامپایلر باید تصمیم بگیرد که چگونه از ثبات‌های موجود استفاده کند.

لازم به ذکر است که در عمل — در مورد ماشین‌های مجازی ثبات‌محور — معمولاً یک پشته هم وجود دارد که مثلاً آرگومان‌های توابع در آن ریخته می‌شوند؛ و از ثبات‌ها برای محاسبهٔ عبارت‌های منفرد استفاده می‌شود. حتی اگر پشتهٔ واقعی وجود نداشته باشد، یک آرایه برای پیاده‌سازی پشته استفاده می‌شود؛ آرایه‌ای که همان نقش RAM را در ماشین‌های سخت‌افزاری ایفا می‌کند.

پشته در برابر ثبات: یک مقایسه

یک تحقیق جالب (Virtual machine showdown: Stack versus registers) که در سال ۲۰۰۸ انجام شد، تأثیر بزرگی بر تمام توسعه‌های بعدی در حوزهٔ ماشین‌های مجازی زبان‌های برنامه‌نویسی گذاشته است. نویسندگان آن راهی برای کامپایل کد پشته‌ای استاندارد JVM به کد ثبات‌محور توسعه دادند و سپس تفاوت‌های بهره‌وری را اندازه‌گیری کردند.

مسیر رسیدن به این هدف به‌هیچ‌وجه ساده نیست: کد ابتدا کامپایل و سپس به‌شکلی نسبتاً پیچیده بهینه‌سازی می‌شود. با این حال، مقایسهٔ بعدی بهره‌وری نسبی هر برنامه نشان داد که چرخه‌های پردازندهٔ اضافیِ صرف‌شده برای رمزگشایی دستورالعمل‌ها کاملاً با کاهش تعداد کل دستورالعمل‌ها جبران می‌شوند. به بیان کوتاه، ماشین ثبات‌محور مؤثرتر از ماشین پشته‌ای از آب درآمد.

همان‌طور که قبلاً اشاره شد، این اثربخشی کاملاً مقرون‌به‌صرفه نیست: کامپایلر خودش باید ثبات‌ها را تخصیص دهد و ترجیحاً به یک بهینه‌سازِ مخصوصاً توسعه‌یافته هم مجهز باشد.

بحث دربارهٔ اینکه کدام معماری بهتر است همچنان ادامه دارد. در زمینهٔ کامپایلرهای جاوا، بایت‌کد ماشین مجازی Dalvik که تا همین اواخر روی هر دستگاه اندرویدی اجرا می‌شد، معماری ثبات‌محور دارد؛ در حالی که خود JVM مجموعه دستورالعمل پشته‌ای را حفظ کرده است. ماشین مجازی لوا از معماری ثبات‌محور استفاده می‌کند، اما ماشین مجازی پایتون یک ماشین پشته‌ای باقی مانده است. و به همین ترتیب.

بایت‌کد در مفسرهای عبارت باقاعده

در نهایت، و برای لحظه‌ای رها کردن ماشین‌های مجازی سطح‌پایین، بیایید به یک مفسر تخصصی نگاه کنیم که رشته‌ها را با عبارات باقاعده تطبیق می‌دهد:

ctypedef enum {

 /* تطبیق یک کاراکتر با آرگومان مستقیم از رشته و جلو بردن ip و cp، یا لغو */

 OP_CHAR,

 /* پرش و تلاش برای تطبیق عبارت چپ یا راست؛ اگر هیچ‌کدام مطابقت نکرد، لغو */

 OP_OR,

 /* پرش مطلق به آفست در آرگومان مستقیم */

 OP_JUMP,

 /* توقف اجرا و گزارش تطبیق موفق */

 OP_MATCH,

} opcode;
typedef enum match_result {

 MATCH_OK,

 MATCH_FAIL,

 MATCH_ERROR,

} match_result;
match_result vm_match_recur(uint8_t *bytecode, uint8_t *ip, char *sp)

{

 for (;;) {

 uint8_t instruction = *ip++;

 switch (instruction) {

 case OP_CHAR:{

 char cur_c = *sp;

 char arg_c = (char)*ip ;

 /* مطابقت ندارد؟ شکست در تطبیق */

 if (arg_c != cur_c)

 return MATCH_FAIL;

 /* جلو بردن هر دو اشاره‌گر دستورالعمل جاری و کاراکتر */

 ip++;

 sp++;

 continue;

 }

 case OP_JUMP:{

 /* خواندن آفست و پرش به دستورالعمل */

 uint8_t offset = *ip;

 ip = bytecode + offset;

 continue;

 }

 case OP_OR:{

 /* دریافت آفست هر دو شاخه */

 uint8_t left_offset = *ip++;

 uint8_t right_offset = *ip;

 /* بررسی اینکه آیا دنبال کردن آفست اول به تطبیق می‌رسد */

 uint8_t *left_ip = bytecode + left_offset;

 if (vm_match_recur(bytecode, left_ip, sp) == MATCH_OK)

 return MATCH_OK;

 /* مطابقت ندارد؟ شاخهٔ دوم را بررسی کن */

 ip = bytecode + right_offset;

 continue;

 }

 case OP_MATCH:{

 /* موفقیت */

 return MATCH_OK;

 }

 }

 return MATCH_ERROR;

 }

}
match_result vm_match(uint8_t *bytecode, char *str)

{

 printf("Start matching a string: %s\n", str);

 return vm_match_recur(bytecode, bytecode, str);

}

دستورالعمل اصلی OP_CHAR است. آرگومان مستقیم خود را می‌گیرد و آن را با کاراکتر جاری رشته (char *sp) مقایسه می‌کند. اگر نماد مورد انتظار با نماد جاری در رشته مطابقت داشت، به دستورالعمل بعدی و نماد بعدی می‌رود.

ماشین همچنین عملیات پرش (OP_JUMP) را می‌فهمد که یک آرگومان مستقیم منفرد می‌پذیرد. آرگومان پرش به موقعیت مطلق در بایت‌کد را مشخص می‌کند و محاسبه از آن نقطه ادامه می‌یابد.

آخرین عملیات مهم OP_OR است. دو پرش می‌پذیرد و تلاش می‌کند کد را ابتدا روی اولی اعمال کند و در صورت خطا، روی دومی. این کار با یک فراخوانی بازگشتی انجام می‌شود؛ یعنی دستورالعمل یک جستجوی عمقی (depth-first search) برای همهٔ گزینه‌های ممکن عبارت باقاعده انجام می‌دهد.

ممکن است تعجب‌آور باشد، اما ۴ کد عملیات و ۷۰ خط کد برای بیان عبارت‌های باقاعده از شکل‌های «abc»، «a?bc»، «(ab|bc)d»، «a*bc» کافی است. در این ماشین مجازی حتی یک حالت صریح وجود ندارد، زیرا هر آنچه لازم است — اشاره‌گر به شروع جریان دستورالعمل، دستورالعمل جاری و نماد جاری — از طریق آرگومان‌های بازگشتی تابع ارسال می‌شود.

اگر به جزئیات نحوهٔ کار موتورهای عبارت باقاعده علاقه‌مندید، برای شروع با سری مقالات راس کاکس (Russ Cox)، نویسندهٔ موتور کار با عبارات باقاعده از RE2 گوگل، آشنا شوید.

نتیجه‌گیری

چه نتیجه‌هایی می‌توانیم بگیریم.

برای زبان‌های برنامه‌نویسی عمومی، به‌عنوان یک قاعده، دو معماری وجود دارد: پشته‌ای و ثبات‌محور.

در مدل پشته‌ای، ساختار دادهٔ اصلی و وسیلهٔ ارسال آرگومان بین دستورالعمل‌ها، پشته است؛ در حالی که در مدل ثبات‌محور، برای محاسبهٔ عبارت‌ها از مجموعهٔ ثبات‌ها استفاده می‌شود، اما برای ذخیرهٔ آرگومان‌های توابع همچنان به‌هرحال از یک پشتهٔ صریح یا ضمنی استفاده می‌شود.

پشتهٔ صریح و مجموعهٔ ثبات‌ها، ماشین‌هایی از این دست را شبیه ماشین‌های سطح‌پایین و حتی سخت‌افزاری می‌کند. فراوانی دستورالعمل‌های سطح‌پایین در بایت‌کدی از این دست به این معناست که منابع عمدهٔ پردازندهٔ سخت‌افزاری صرف رمزگشایی و توزیع دستورالعمل‌های مجازی خواهد شد.

از طرف دیگر، در مورد ماشین‌های مجازی محبوب، دستورالعمل‌های سطح‌بالا نیز نقش عمده‌ای دارند. در جاوا، برای مثال، این‌ها دستورالعمل‌های فراخوانی تابع چندریختی (polymorphic)، تخصیص اشیاء و جمع‌آوری زباله (garbage collection) هستند.

ماشین‌های مجازی صرفاً سطح‌بالا — برای مثال، مفسرهای بایت‌کد زبان‌هایی با معناشناسی توسعه‌یافته که از سخت‌افزار فاصله زیادی دارند — بیشتر زمان خود را نه در توزیع‌کننده (dispatcher) یا رمزگشا، بلکه در بدنه‌های دستورالعمل‌ها صرف می‌کنند و در نتیجه نسبتاً مؤثرند.

توصیه‌های عملی:

  1. اگر لازم است هر نوع بایت‌کدی را در بازهٔ زمانی معقولی اجرا کنید، سعی کنید با دستورالعمل‌هایی کار کنید که تا حد امکان متناسب با وظیفهٔ شما باشند؛ هرچه سطح معناشناسی بالاتر باشد، بهتر. این کار هم هزینه‌های توزیع را کاهش می‌دهد و هم تولید کد را ساده می‌کند.
  2. اگر انعطاف‌پذیری و معناشناسی متنوع لازم است، حداقل باید سعی کنید مخرج مشترک بایت‌کد را برجسته کنید، تا دستورالعمل‌های حاصل تقریباً در سطح میانی باشند.
  3. اگر آیندهٔ بالقوه‌ای را پیش‌بینی می‌کنید که در آن ممکن است نیاز به ارزیابی عبارت‌ها داشته باشید، سراغ ماشین پشته‌ای بروید؛ این کار هنگام کامپایل بایت‌کد به «سردرد»های کمتری منجر می‌شود.
  4. اگر فکر نمی‌کنید به عبارت‌ها نیاز داشته باشید، یک ماشین ثبات‌محور ساده بسازید تا از صرف هزینه برای پشته پرهیز کنید و خود دستورالعمل‌ها را ساده‌تر کنید.

در مقالات بعدی، بهینه‌سازی مفسرهای بایت‌کد را بررسی خواهم کرد و به شما خواهم گفت چرا واحد هوش تجاری Badoo به بایت‌کد نیاز داشت.

کپیرایت: مقالهٔ «Home-grown bytecode interpreters» اثر «ولادیمیر کازانوف (Vladimir Kazanov)» از «Bumble Tech» است. این صفحه فقط ترجمهٔ فارسی آن است و تمام حقوق محتوا، تصاویر و کدها متعلق به نویسندهٔ اصلی است. برای مشاهدهٔ اصل مطلب به سایت اصلی مراجعه کنید.
