مرور کلی (Overview)

در طول سال‌ها کلاس‌های گرافیک زیادی برگزار کرده‌ام. اغلب آن‌ها را با ردیابی پرتو (ray tracing) برگزار می‌کنم، چون مجبور می‌شوید همهٔ کد را خودتان بنویسید، اما بدون هیچ API هم می‌توانید تصاویر جذابی بسازید. تصمیم گرفتم یادداشت‌های درس‌هایم را به یک آموزش «چگونه» تبدیل کنم تا در سریع‌ترین زمان ممکن به یک برنامهٔ جذاب برسید. این برنامه یک ردیاب پرتوی کامل‌ویژگی نخواهد بود، اما روشنایی غیرمستقیم (indirect lighting) را دارد که ردیابی پرتو را به ستون اصلی فیلم‌ها تبدیل کرده است. این مراحل را دنبال کنید؛ معماری ردیاب پرتویی که می‌سازید آن‌قدر خوب است که اگر هیجان‌زده شدید و خواستید ادامه بدهید، بستر مناسبی برای گسترش به یک ردیاب پرتوی کامل‌تر خواهد بود.

وقتی کسی می‌گوید «ردیابی پرتو» می‌تواند معانی زیادی داشته باشد. چیزی که من توصیف می‌کنم از نظر فنی یک ردیاب مسیر (path tracer) است، و یک ردیاب مسیر تقریباً عمومی. هرچند کد بسیار ساده خواهد بود (بگذارید کامپیوتر کار را انجام دهد!) فکر می‌کنم از تصاویری که می‌توانید بسازید بسیار خوشحال خواهید شد.

شما را قدم‌به‌قدم در نوشتن یک ردیاب پرتو همراهی می‌کنم — دقیقاً به همان ترتیبی که خودم می‌نویسم — همراه با چند نکتهٔ اشکال‌زدایی. در پایان، یک ردیاب پرتو خواهید داشت که تصاویر عالی تولید می‌کند. باید بتوانید این کار را در یک آخر هفته انجام دهید. اگر بیشتر طول کشید، نگران نباشید. من از C++ به‌عنوان زبان اصلی استفاده می‌کنم، اما شما مجبور نیستید. با این‌حال پیشنهاد می‌کنم همین کار را بکنید، چون سریع و قابل‌انتقال است و بیشتر رندررهای فیلم‌های سینمایی و بازی‌های ویدیویی با C++ نوشته می‌شوند. توجه کنید که من بیشتر «ویژگی‌های مدرن» C++ را کنار می‌گذارم، اما وراثت (inheritance) و سرریز عملگر (operator overloading) آن‌قدر برای ردیاب‌های پرتو مفید هستند که نمی‌شود از آن‌ها گذشت.

توجه نویسنده: «من کد را به‌صورت آنلاین ارائه نمی‌دهم، اما کد واقعی است و همه‌اش را نشان می‌دهم به‌جز چند عملگر ساده در کلاس vec3. من عمیقاً به تایپ‌کردن کد برای یادگیری اعتقاد دارم، اما وقتی کد در دسترس باشد از آن استفاده می‌کنم؛ پس فقط وقتی کد در دسترس نیست به حرف خودم عمل می‌کنم. پس نپرسید!»

آن بخش آخر را نگه داشته‌ام چون خنده‌دار است که چقدر نظر من ۱۸۰ درجه چرخیده است. چند خواننده به خطاهای ظریفی خوردند که با مقایسهٔ کدها برطرف شد. پس لطفاً کدها را تایپ کنید، اما می‌توانید کد نهایی هر کتاب را در پروژهٔ RayTracing در گیت‌هاب پیدا کنید.

خروجی تصویر

فرمت تصویر PPM

وقتی یک رندرر را شروع می‌کنید، به راهی برای دیدن تصویر نیاز دارید. سرراست‌ترین راه، نوشتن آن در یک فایل است. مشکل این است که فرمت‌ها بسیار زیادند و بسیاری از آن‌ها پیچیده. من همیشه با یک فایل متنی سادهٔ ppm شروع می‌کنم. این هم یک توصیف خوب از ویکی‌پدیا:

بیایید کدی در C++ بنویسیم که چنین چیزی را خروجی بدهد:

cpp#include <iostream>

int main() {

    // تصویر
    int image_width = 256;
    int image_height = 256;

    // رندر
    std::cout << "P3\n" << image_width << ' ' << image_height << "\n255\n";

    for (int j = 0; j < image_height; j++) {
        for (int i = 0; i < image_width; i++) {
            auto r = double(i) / (image_width-1);
            auto g = double(j) / (image_height-1);
            auto b = 0.0;

            int ir = int(255.999 * r);
            int ig = int(255.999 * g);
            int ib = int(255.999 * b);

            std::cout << ir << ' ' << ig << ' ' << ib << '\n';
        }
    }
}

نکاتی در این کد وجود دارد:

  1. پیکسل‌ها به‌صورت ردیفی نوشته می‌شوند.
  2. هر ردیف از پیکسل‌ها از چپ به راست نوشته می‌شود.
  3. این ردیف‌ها از بالا به پایین نوشته می‌شوند.
  4. طبق قرارداد، هر یک از مؤلفه‌های قرمز/سبز/آبی به‌صورت داخلی با متغیرهای حقیقی‌مقدار در بازهٔ ۰.۰ تا ۱.۰ نمایش داده می‌شوند. این مؤلفه‌ها باید پیش از چاپ، به مقادیر صحیح بین ۰ تا ۲۵۵ مقیاس شوند.
  5. قرمز از چپ به راست از خاموشِ کامل (سیاه) به روشنِ کامل (قرمز روشن) می‌رود، و سبز از بالا (سیاه) به پایین (سبز روشن) از خاموش به روشن می‌رود. جمع نور قرمز و سبز زرد می‌سازد، پس باید انتظار داشته باشیم گوشهٔ پایین‌راست زرد باشد.

ساخت فایل تصویر

چون خروجی در جریان خروجی استاندارد (standard output) نوشته می‌شود، باید آن را به یک فایل تصویر هدایت کنید. معمولاً این کار از خط فرمان با عملگر هدایت > انجام می‌شود.

در ویندوز، بیلد دیباگ را با CMake و این دستور می‌گیرید:

bashcmake -B build
cmake --build build

سپس برنامهٔ تازه‌ساخته‌شده را این‌طور اجرا کنید:

bashbuild\Debug\inOneWeekend.exe > image.ppm

بعداً، برای سرعت بهتر است بیلدهای بهینه (optimized) اجرا کنید. در آن صورت این‌طور می‌سازید:

bashcmake --build build --config release

و برنامهٔ بهینه را این‌طور اجرا می‌کنید:

bashbuild\Release\inOneWeekend.exe > image.ppm

مثال‌های بالا فرض می‌کنند که با CMake می‌سازید و از همان شیوهٔ فایل CMakeLists.txt در کدهای همراه استفاده می‌کنید. از هر محیط ساخت (و زبانی) که با آن راحت‌ترید استفاده کنید.

کلاس vec3

تقریباً همهٔ برنامه‌های گرافیک کلاس‌هایی برای ذخیرهٔ بردارهای هندسی و رنگ‌ها دارند. در بسیاری از سیستم‌ها این بردارها چهاربعدی هستند (موقعیت سه‌بعدی به‌علاوهٔ مختصات همگن برای هندسه، یا RGB به‌علاوهٔ مؤلفهٔ شفافیت آلفا برای رنگ‌ها). برای منظور ما، سه مختصه کافی است. ما از یک کلاس برای همه‌چیز استفاده می‌کنیم: رنگ‌ها، مکان‌ها، جهت‌ها، جابه‌جایی‌ها. بعضی‌ها این را دوست ندارند چون جلوی کارهای احمقانه را نمی‌گیرد، مثلاً کم‌کردن یک موقعیت از یک رنگ. حرف درستی دارند، اما ما همیشه وقتی اشتباهِ واضحی نیست، مسیر «کد کمتر» را می‌رویم. با این‌حال، دو نام مستعار برای vec3 تعریف می‌کنیم: point3 و color. چون این دو نوع فقط نام مستعار vec3 هستند، اگر یک color به تابعی بدهید که منتظر point3 است هشدار نمی‌گیرید، و هیچ‌چیز شما را از جمع‌کردن یک point3 با یک color باز نمی‌دارد؛ اما این کار خواندن و فهمیدن کد را کمی آسان‌تر می‌کند.

کلاس vec3 را در نیمهٔ بالایی فایل هدر جدید vec3.h تعریف می‌کنیم و مجموعه‌ای از توابع کمکی برداری را در نیمهٔ پایینی:

cpp#ifndef VEC3_H
#define VEC3_H

#include <cmath>
#include <iostream>

class vec3 {
  public:
    double e[3];

    vec3() : e{0,0,0} {}
    vec3(double e0, double e1, double e2) : e{e0, e1, e2} {}

    double x() const { return e[0]; }
    double y() const { return e[1]; }
    double z() const { return e[2]; }

    vec3 operator-() const { return vec3(-e[0], -e[1], -e[2]); }
    double operator[](int i) const { return e[i]; }
    double& operator[](int i) { return e[i]; }

    vec3& operator+=(const vec3& v) {
        e[0] += v.e[0];
        e[1] += v.e[1];
        e[2] += v.e[2];
        return *this;
    }

    vec3& operator*=(double t) {
        e[0] *= t;
        e[1] *= t;
        e[2] *= t;
        return *this;
    }

    vec3& operator/=(double t) {
        return *this *= 1/t;
    }

    double length() const {
        return std::sqrt(length_squared());
    }

    double length_squared() const {
        return e[0]*e[0] + e[1]*e[1] + e[2]*e[2];
    }
};

// point3 فقط نام مستعاری برای vec3 است، اما برای وضوح هندسی در کد مفید است.
using point3 = vec3;


// توابع کمکی بردار

    return out << v.e[0] << ' ' << v.e[1] << ' ' << v.e[2];
}

    return vec3(u.e[0] + v.e[0], u.e[1] + v.e[1], u.e[2] + v.e[2]);
}

پرتوها، یک دوربین ساده و پس‌زمینه

کلاس پرتو (ray)

تنها چیزی که همهٔ ردیاب‌های پرتو دارند، یک کلاس پرتو و محاسبهٔ رنگِ دیده‌شده در طول پرتو است. پرتو را تابعی در نظر بگیریم: P(t) = A + t·b. در این‌جا P یک موقعیت سه‌بعدی در طول یک خط در فضای سه‌بعدی است. A مبدأ پرتو و b جهت پرتو است. پارامتر t عددی حقیقی است (در کد double). با جای‌گذاری tهای مختلف، P(t) نقطه را در طول پرتو جابه‌جا می‌کند. با tهای منفی، می‌توانید به هر جای خط سه‌بعدی بروید. با t مثبت، فقط بخش‌های جلوی A را می‌گیرید؛ به همین چیزی معمولاً نیم‌خط یا پرتو می‌گویند.

می‌توانیم ایدهٔ پرتو را به‌صورت یک کلاس نمایش دهیم و تابع P(t) را به‌صورت تابعی که نامش را ray::at(t) می‌گذاریم:

cpp#ifndef RAY_H
#define RAY_H

#include "vec3.h"

class ray {
  public:
    ray() {}

    ray(const point3& origin, const vec3& direction) : orig(origin), dir(direction) {}

    const point3& origin() const  { return orig; }
    const vec3& direction() const { return dir; }

    point3 at(double t) const {
        return orig + t*dir;
    }

  private:
    point3 orig;
    vec3 dir;
};

#endif

فرستادن پرتوها به صحنه

حالا آماده‌ایم که دور را بزنیم و یک ردیاب پرتو بسازیم. در هستهٔ خود، یک ردیاب پرتو پرتوهایی از میان پیکسل‌ها می‌فرستد و رنگِ دیده‌شده در جهتِ آن پرتوها را محاسبه می‌کند. مراحل دخیل عبارت‌اند از:

  1. محاسبهٔ پرتو از «چشم» به‌طرف پیکسل،
  2. تعیین اینکه پرتو با کدام اشیا برخورد می‌کند، و
  3. محاسبهٔ رنگ برای نزدیک‌ترین نقطهٔ برخورد.

وقتی برای اولین بار یک ردیاب پرتو می‌سازم، همیشه برای راه‌اندازی سریع کد، یک دوربین ساده می‌سازم.

اغلب با تصویرهای مربعی به دردسر افتاده‌ام چون زیاد x و y را جابه‌جا می‌کنم؛ پس از یک تصویر غیرمربعی استفاده می‌کنیم. تصویر مربع نسبت تصویر ۱:۱ دارد چون عرضش با ارتفاعش برابر است. از آن‌جایی که تصویر غیرمربعی می‌خواهیم، ۱۶:۹ را انتخاب می‌کنیم چون خیلی رایج است. نسبت تصویر ۱۶:۹ یعنی نسبت عرض تصویر به ارتفاع آن ۱۶:۹ است. به بیان دیگر، برای تصویری با نسبت تصویر ۱۶:۹:

width / height = 16 / 9 = 1.7778

برای یک مثال عملی، تصویری با عرض ۸۰۰ پیکسل و ارتفاع ۴۰۰ پیکسل نسبت تصویر ۲:۱ دارد.

نسبت تصویر را می‌توان از نسبت عرض به ارتفاع تعیین کرد. اما چون یک نسبت تصویر مشخص در نظر داریم، آسان‌تر است که عرض تصویر و نسبت تصویر را بگذاریم و از آن ارتفاع را محاسبه کنیم. این‌طور می‌توانیم با تغییر عرض، تصویر را بزرگ یا کوچک کنیم و نسبت تصویر موردنظرمان به هم نمی‌خورد. فقط باید مطمئن شویم هنگام محاسبهٔ ارتفاع تصویر، ارتفاع حاصل حداقل ۱ باشد.

علاوه بر تنظیم ابعاد پیکسلی تصویر رندر، باید یک viewport (دریچهٔ دید) مجازی هم تنظیم کنیم که پرتوهای صحنه از آن عبور می‌کنند. viewport یک مستطیل مجازی در دنیای سه‌بعدی است که شبکهٔ مکان‌های پیکسلی تصویر را در بر می‌گیرد. اگر پیکسل‌ها در جهت افقی و عمودی به یک فاصله از هم باشند، viewportی که آن‌ها را محصور می‌کند همان نسبت تصویر تصویرِ رندرشده را خواهد داشت. فاصلهٔ بین دو پیکسل مجاور را فاصلهٔ پیکسل می‌نامند و پیکسل مربعی استاندارد است.

برای شروع، یک ارتفاع دلخواه ۲.۰ برای viewport انتخاب می‌کنیم و عرض viewport را طوری مقیاس می‌کنیم که نسبت تصویر موردنظرمان به دست آید. این هم یک تکه از کدی است که خواهیم داشت:

بعد، مرکز دوربین را تعریف می‌کنیم: نقطه‌ای در فضای سه‌بعدی که همهٔ پرتوهای صحنه از آنجا شروع می‌شوند (که معمولاً نقطهٔ چشم هم نامیده می‌شود). بردارِ از مرکز دوربین به مرکز viewport عمود بر viewport خواهد بود. ابتدا فاصلهٔ بین viewport و مرکز دوربین را یک واحد می‌گذاریم. به این فاصله معمولاً فاصلهٔ کانونی می‌گویند.

برای سادگی، مرکز دوربین را در (0,0,0) می‌گذاریم. همچنین محور y را رو به بالا، محور x را به راست و محور z منفی را در جهت دید قرار می‌دهیم. (به این معمولاً مختصات راست‌دست می‌گویند.)

حالا بخش ناگزیرِ پیچیده. در حالی که فضای سه‌بعدی ما قراردادهای بالا را دارد، این با مختصات تصویرمان در تعارض است، جایی که می‌خواهیم پیکسل صفرم در بالا-چپ باشد و تا آخرین پیکسل در پایین-راست ادامه دهیم. یعنی محور Y مختصات تصویر معکوس است: Y با پایین‌رفتن در تصویر افزایش می‌یابد.

وقتی تصویرمان را اسکن می‌کنیم، از پیکسل بالا-چپ (پیکسل 0,0) شروع می‌کنیم، در هر ردیف از چپ به راست اسکن می‌کنیم و بعد ردیف‌به‌ردیف از بالا به پایین. برای پیمایش شبکهٔ پیکسل‌ها از بردار Vu (از لبهٔ چپ به لبهٔ راست) و بردار Vv (از لبهٔ بالا به لبهٔ پایین) استفاده می‌کنیم.

افزودن یک کره

بیایید یک شیء منفرد به ردیاب پرتومان اضافه کنیم. مردم اغلب در ردیاب‌های پرتو از کره استفاده می‌کنند چون محاسبهٔ اینکه آیا پرتو به کره برخورد می‌کند نسبتاً ساده است.

برخورد پرتو و کره

معادلهٔ کره‌ای به شعاع r که در مبدأ مختصات متمرکز است، یک معادلهٔ ریاضی مهم است:

x² + y² + z² = r²

همچنین می‌توانید این‌طور فکر کنید: اگر نقطهٔ داده‌شدهٔ (x, y, z) روی سطح کره باشد، آن‌گاه x² + y² + z² = r². اگر نقطهٔ داده‌شدهٔ (x, y, z) داخل کره باشد، x² + y² + z² < r²، و اگر نقطهٔ داده‌شدهٔ (x, y, z) خارج کره باشد، x² + y² + z² > r².

اگر بخواهیم مرکز کره در نقطهٔ دلخواه (Cx, Cy, Cz) باشد، معادله خیلی کمتر زیبا می‌شود:

(Cₓ − x)² + (Cᵧ − y)² + (C_z − z)² = r²

در گرافیک تقریباً همیشه می‌خواهید فرمول‌هایتان برحسب بردار باشند تا همهٔ چیزهای x/y/z به‌سادگی با کلاس vec3 نمایش داده شوند. شاید متوجه شده باشید که بردارِ از نقطهٔ P = (x, y, z) به مرکز C = (Cₓ, Cᵧ, C_z) برابر (C − P) است.

اگر از تعریف ضرب داخلی (dot product) استفاده کنیم:

(C − P)·(C − P) = (Cₓ − x)² + (Cᵧ − y)² + (C_z − z)²

آن‌گاه می‌توانیم معادلهٔ کره را به شکل برداری بازنویسی کنیم:

(C − P)·(C − P) = r²

می‌توانیم این‌طور بخوانیمش: «هر نقطهٔ P که این معادله را برآورده کند روی کره است». می‌خواهیم بدانیم آیا پرتوی P(t) = Q + t·d اصلاً جایی به کره برخورد می‌کند یا نه. اگر برخورد کند، یک t وجود دارد که برای آن P(t) معادلهٔ کره را برآورده می‌کند. پس دنبال هر t می‌گردیم که این درست باشد:

(C − P(t))·(C − P(t)) = r²

که با جای‌گذاری شکل بسط‌یافتهٔ P(t) پیدا می‌شود:

(C − (Q + t·d))·(C − (Q + t·d)) = r²

در سمت چپ سه بردار داریم که در سه بردار سمت راست ضرب داخلی شده‌اند. اگر ضرب داخلی کامل را حل کنیم، نه بردار می‌گرفتیم. مطمئناً می‌توانید همه‌چیز را بنویسید و باز کنید، اما لازم نیست این‌قدر زحمت بکشیم. اگر یادتان باشد، می‌خواهیم t را به دست آوریم؛ پس عبارت‌ها را بر اساس اینکه t دارند یا نه جدا می‌کنیم:

(−t·d + (C − Q))·(−t·d + (C − Q)) = r²

و حالا طبق قواعد جبر برداری، ضرب داخلی را پخش می‌کنیم:

t²·(d·d) − 2t·(d·(C − Q)) + (C − Q)·(C − Q) = r²

مربع شعاع را به سمت چپ می‌بریم:

t²·(d·d) − 2t·(d·(C − Q)) + (C − Q)·(C − Q) − r² = 0

تشخیص اینکه این معادله دقیقاً چیست سخت است، اما بردارها و r در آن معادله همگی ثابت و معلوم‌اند. علاوه بر این، تنها بردارهایی که داریم با ضرب داخلی به اسکالر کاهش یافته‌اند. تنها مجهول t است و یک t² هم داریم، یعنی این معادله درجه دوم است. می‌توانید معادلهٔ درجه دوم ax² + bx + c = 0 را با فرمول درجه دوم حل کنید:

(−b ± √(b² − 4ac)) / 2a

پس حل t در معادلهٔ برخورد پرتو-کره این مقادیر را برای a، b و c می‌دهد:

a = d·d

b = −2·d·(C − Q)

c = (C − Q)·(C − Q) − r²

با استفاده از همهٔ موارد بالا می‌توانید t را حل کنید، اما یک بخش رادیکال وجود دارد که می‌تواند مثبت باشد (یعنی دو جواب حقیقی)، منفی (یعنی بدون جواب حقیقی) یا صفر (یعنی یک جواب حقیقی). در گرافیک، جبر تقریباً همیشه خیلی مستقیم به هندسه ربط دارد. چیزی که داریم این است:

سایه‌زنی با نرمال سطح

اول، بگذارید یک نرمال سطح به دست بیاوریم تا بتوانیم سایه بزنیم. این بردارِ عمود بر سطح در نقطهٔ برخورد است.

برای بردارهای نرمال در کدمان یک تصمیم طراحی کلیدی داریم: آیا بردارهای نرمال طول دلخواه خواهند داشت یا به طول واحد نرمال می‌شوند.

وسوسه‌انگیز است که عملیات گرانِ ریشهٔ دومِ دخیل در نرمال‌سازی بردار را نادیده بگیریم، چون شاید لازم نباشد. اما در عمل سه مشاهدهٔ مهم وجود دارد. اول، اگر نرمالِ واحد هرگز لازم شود، بهتر است همین اول یک‌بار انجامش دهید، به‌جای اینکه «فقط احتیاطاً» برای هر جا که به طول واحد نیاز است، بارها و بارها انجامش دهید. دوم، در چندین جای کد واقعاً به نرمال واحد نیاز داریم. سوم، اگر بردارهای نرمال را واحدِ اجباری کنید، اغلب می‌توانید با درک کلاس هندسیِ خاص، آن بردار را کارآمد تولید کنید — در سازنده‌اش یا در تابع hit(). مثلاً نرمال کره را می‌توان به‌سادگی با تقسیم بر شعاع کره واحد کرد و کاملاً از ریشهٔ دوم اجتناب کرد.

با توجه به همهٔ این‌ها، این سیاست را می‌پذیریم که همهٔ بردارهای نرمال طول واحد داشته باشند.

برای کره، نرمال رو به بیرون در جهتِ نقطهٔ برخورد منهاي مرکز است:

روی زمین، این یعنی بردارِ از مرکز زمین به شما مستقیم رو به بالا اشاره می‌کند. بگذارید الآن این را در کد بیندازیم و سایه‌زنی‌اش کنیم. هنوز هیچ نور یا چیزی نداریم، پس فقط بیایید نرمال‌ها را با یک نقشهٔ رنگی بصری کنیم. یک ترفند رایج برای بصری‌سازی نرمال‌ها (چون ساده است و تا حدی شهودی فرض کنیم n بردار واحد است — پس هر مؤلفه بین −۱ و ۱ است) این است که هر مؤلفه را به بازهٔ ۰ تا ۱ نگاشت کنیم و سپس (x, y, z) را به (قرمز، سبز، آبی) نگاشت کنیم. برای نرمال، به نقطهٔ برخورد نیاز داریم، نه فقط برخورد کردن یا نکردن (که فعلاً تنها چیزی است که محاسبه می‌کنیم). فقط یک کره در صحنه داریم و دقیقاً جلوی دوربین است؛ پس فعلاً نگران مقادیر منفی t نیستیم. فقط فرض می‌کنیم نزدیک‌ترین نقطهٔ برخورد (کوچک‌ترین t) همانی است که می‌خواهیم. این تغییرهای کد به ما امکان می‌دهند n را محاسبه و بصری کنیم:

یک انتزاع برای اشیای قابل‌برخورد (Hittable)

حالا، چطور است بیش از یک کره؟ با اینکه داشتن یک آرایه از کره‌ها وسوسه‌انگیز است، یک راه‌حل خیلی تمیز ساختن یک «کلاس انتزاعی» برای هر چیزی است که پرتو ممکن است به آن برخورد کند، و ساختنِ همِ کره و همِ لیستِ کره‌ها به‌عنوان چیزی که «قابل‌برخورد» است. این که آن کلاس چه نامیده شود یک معماست — اگر برنامه‌نویسیِ «شیء‌گرا» نبود، نامیدنش «object» خوب بود. «Surface» (سطح) اغلب استفاده می‌شود، با این ضعف که شاید ما حجم‌ها را بخواهیم (مه، ابر، چیزهایی از این دست). «hittable» (قابل‌برخورد) بر تابعِ عضوی که آن‌ها را متحد می‌کند تأکید دارد. هیچ‌کدام از این‌ها را دوست ندارم، اما با «hittable» می‌رویم.

این کلاس انتزاعی hittable یک تابع hit خواهد داشت که یک پرتو می‌گیرد. بیشتر ردیاب‌های پرتو افزودن یک بازهٔ معتبر برای برخوردها از tmin تا tmax را راحت یافته‌اند، طوری که برخورد فقط وقتی «به حساب می‌آید» که tmin < t < tmax. برای پرتوهای اولیه این t مثبت است، اما همان‌طور که خواهیم دید، داشتن یک بازهٔ tmin تا tmax می‌تواند کدمان را ساده کند. یک سؤال طراحی این است که آیا کارهایی مثل محاسبهٔ نرمال را وقتی به چیزی برخورد کردیم انجام بدهیم یا نه. ممکن است در جست‌وجومان به چیزی نزدیک‌تر برخورد کنیم و فقط به نرمالِ نزدیک‌ترین چیز نیاز داشته باشیم. من با راه‌حل ساده می‌روم و یک بستهٔ چیز که در ساختاری ذخیره می‌کنم محاسبه می‌کنم. کلاس انتزاعی این است:

cpp#ifndef SPHERE_H
#define SPHERE_H

#include "hittable.h"
#include "vec3.h"

class sphere : public hittable {
  public:
    sphere(const point3& center, double radius) : center(center), radius(std::fmax(0,radius)) {}

    bool hit(const ray& r, double ray_tmin, double ray_tmax, hit_record& rec) const override {
        vec3 oc = center - r.origin();
        auto a = r.direction().length_squared();
        auto h = dot(r.direction(), oc);
        auto c = oc.length_squared() - radius*radius;

        auto discriminant = h*h - a*c;
        if (discriminant < 0)
            return false;

        auto sqrtd = std::sqrt(discriminant);

        // نزدیک‌ترین ریشه‌ای را پیدا کن که در بازهٔ قابل‌قبول باشد.
        auto root = (h - sqrtd) / a;
        if (root <= ray_tmin || ray_tmax <= root) {
            root = (h + sqrtd) / a;
            if (root <= ray_tmin || ray_tmax <= root)
                return false;
        }

        rec.t = root;
        rec.p = r.at(rec.t);
        rec.normal = (rec.p - center) / radius;

        return true;
    }

  private:
    point3 center;
    double radius;
};

#endif

رویِ جلو در برابر رویِ پشت

دومین تصمیم طراحی برای نرمال‌ها این است که آیا باید همیشه به سمت بیرون باشند. در حال حاضر، نرمالِ پیدا‌شده همیشه در جهتِ مرکز به نقطهٔ برخورد خواهد بود (نرمال به بیرون اشاره می‌کند). اگر پرتو از بیرون به کره برخورد کند، نرمال خلاف پرتو است. اگر پرتو از داخل به کره برخورد کند، نرمال (که همیشه به بیرون اشاره می‌کند) هم‌جهت با پرتو است. از طرف دیگر، می‌توانیم نرمال را همیشه خلاف پرتو کنیم. اگر پرتو خارج کره باشد، نرمال به بیرون اشاره می‌کند، اما اگر پرتو داخل کره باشد، نرمال به داخل اشاره می‌کند.

باید یکی از این امکان‌ها را انتخاب کنیم، چون در نهایت می‌خواهیم تعیین کنیم پرتو از کدام سمت سطح می‌آید. این برای اشیایی مهم است که هر طرفشان متفاوت رندر می‌شود — مثل متن روی یک برگ کاغذ دوطرفه — یا اشیایی که داخل و خارج دارند، مثل گوی شیشه‌ای.

اگر تصمیم بگیریم نرمال‌ها همیشه به بیرون باشند، باید وقتی پرتو را رنگ می‌کنیم تعیین کنیم پرتو در کدام سمت است. می‌توانیم این را با مقایسهٔ پرتو و نرمال بفهمیم. اگر پرتو و نرمال در یک جهت باشند، پرتو داخل شیء است؛ اگر پرتو و نرمال در جهت‌های مخالف باشند، پرتو خارج از شیء است. این را می‌توان با ضرب داخلی دو بردار تعیین کرد؛ اگر ضرب داخلی‌شان مثبت باشد، پرتو داخل کره است.

یک لیست از اشیای قابل‌برخورد

یک شیء عمومی داریم به نام hittable که پرتو می‌تواند با آن برخورد کند. حالا کلاسی اضافه می‌کنیم که یک لیست از hittableها را ذخیره می‌کند:

cpp#ifndef HITTABLE_LIST_H
#define HITTABLE_LIST_H

#include "hittable.h"

#include <vector>

using std::make_shared;
using std::shared_ptr;

class hittable_list : public hittable {
  public:
    std::vector<shared_ptr<hittable>> objects;

    hittable_list() {}
    hittable_list(shared_ptr<hittable> object) { add(object); }

    void clear() { objects.clear(); }

    void add(shared_ptr<hittable> object) {
        objects.push_back(object);
    }

    bool hit(const ray& r, double ray_tmin, double ray_tmax, hit_record& rec) const override {
        hit_record temp_rec;
        bool hit_anything = false;
        auto closest_so_far = ray_tmax;

        for (const auto& object : objects) {
            if (object->hit(r, ray_tmin, closest_so_far, temp_rec)) {
                hit_anything = true;
                closest_so_far = temp_rec.t;
                rec = temp_rec;
            }
        }

        return hit_anything;
    }
};

چند ویژگی جدید C++

کد کلاس hittable_list از چند ویژگی C++ استفاده می‌کند که اگر معمولاً برنامه‌نویس C++ نیستید ممکن است به آن‌ها گیر بدهید: vector، shared_ptr و make_shared.

shared_ptr<type> یک اشاره‌گر به یک نوع تخصیص‌داده‌شده با معناشناسی شمارش ارجاع (reference counting) است. هر بار که مقدارش را به یک اشاره‌گر اشتراکی دیگر نسبت دهید (معمولاً با یک تخصیص ساده)، شمارندهٔ ارجاع افزایش می‌یابد. وقتی اشاره‌گرهای اشتراکی از دامنه خارج می‌شوند (مثل انتهای یک بلاک یا تابع)، شمارندهٔ ارجاع کاهش می‌یابد. وقتی شمارنده به صفر برسد، شیء با خیال راحت حذف می‌شود.

معمولاً یک اشاره‌گر اشتراکی ابتدا با یک شیء تازه‌تخصیص‌یافته مقداردهی اولیه می‌شود، چیزی شبیه این:

cppshared_ptr<double> double_ptr = make_shared<double>(0.37);
shared_ptr<vec3>   vec3_ptr   = make_shared<vec3>(1.414214, 2.718281, 1.618034);
shared_ptr<sphere> sphere_ptr = make_shared<sphere>(point3(0,0,0), 1.0);

پیش از ادامه، یک کلاس بازه پیاده‌سازی می‌کنیم تا بازه‌های حقیقی‌مقدار با یک حداقل و یک حداکثر را مدیریت کند. در ادامهٔ کار خیلی وقت‌ها از این کلاس استفاده خواهیم کرد.

cpp#ifndef INTERVAL_H
#define INTERVAL_H

class interval {
  public:
    double min, max;

    interval() : min(+infinity), max(-infinity) {} // بازهٔ پیش‌فرض خالی است

    interval(double min, double max) : min(min), max(max) {}

    double size() const {
        return max - min;
    }

    bool contains(double x) const {
        return min <= x && x <= max;
    }

    bool surrounds(double x) const {
        return min < x && x < max;
    }

    static const interval empty, universe;
};

const interval interval::empty    = interval(+infinity, -infinity);
const interval interval::universe = interval(-infinity, +infinity);

#endif

انتقال کد دوربین به کلاس خودش

پیش از ادامه، حالا وقت خوبی است که کد دوربین و رندر صحنه‌مان را در یک کلاس جدید واحد تثبیت کنیم: کلاس camera. کلاس دوربین مسئول دو کار مهم خواهد بود:

  1. ساخت و پرتاب پرتوها به دنیا.
  2. استفاده از نتایج این پرتوها برای ساخت تصویر رندرشده.

در این بازسازی (refactoring)، تابع ray_color() را به‌همراه بخش‌های تصویر، دوربین و رندر برنامهٔ اصلی‌مان جمع می‌کنیم. کلاس دوربین جدید دو متد عمومی initialize() و render() خواهد داشت، به‌علاوهٔ دو متد کمکی خصوصی get_ray() و ray_color().

در نهایت، دوربین ساده‌ترین الگوی استفاده‌ای که به ذهنمان رسید را دنبال می‌کند: بدون آرگومان به‌صورت پیش‌فرض ساخته می‌شود، سپس کد مالک با تخصیص ساده، متغیرهای عمومی دوربین را تغییر می‌دهد، و در پایان همه‌چیز با فراخوانی تابع initialize() مقداردهی می‌شود. این الگو به‌جای اینکه مالک با سازنده‌ای با انبوهی پارامتر صدا بزند یا یک دسته متد setter تعریف و صدا بزند، انتخاب شده است. در عوض، کد مالک فقط باید چیزی را بگذارد که صریحاً به آن اهمیت می‌دهد. در نهایت، می‌توانیم یا کد مالک initialize() را صدا بزند، یا فقط دوربین این تابع را به‌طور خودکار در شروع render() صدا بزند. ما از روش دوم استفاده می‌کنیم.

ضدآلیاسینگ (Antialiasing)

اگر تا حالا در تصاویر رندرشده بزرگ‌نمایی کنید، ممکن است ماهیت خشنِ «پلکانی» لبه‌ها را در تصاویر رندرشدهٔ ما ببینید. به این پلکانی‌شدن معمولاً «آلیاسینگ» یا «دندانه‌دارگی» (jaggies) می‌گویند. وقتی یک دوربین واقعی عکس می‌گیرد، معمولاً در لبه‌ها دندانه‌دارگی نیست، چون پیکسل‌های لبه ترکیبی از مقداری پیش‌زمینه و مقداری پس‌زمینه‌اند. در نظر بگیرید که برخلاف تصاویر رندرشدهٔ ما، یک تصویر واقعی از دنیا پیوسته است. به بیان دیگر، دنیا (و هر تصویر واقعی از آن) به‌طور مؤثر وضوح بی‌نهایت دارد. می‌توانیم با میانگین‌گیریِ یک دسته نمونه برای هر پیکسل، همان اثر را بگیریم.

با یک پرتوی تکی از مرکز هر پیکسل، کاری انجام می‌دهیم که معمولاً نمونه‌برداری نقطه‌ای نامیده می‌شود. مشکل نمونه‌برداری نقطه‌ای را می‌توان با رندر یک صفحهٔ شطرنجی کوچکِ دور نشان داد. اگر این صفحهٔ شطرنجی از یک شبکهٔ 8×8 از خانه‌های سیاه و سفید تشکیل شده باشد، اما فقط چهار پرتو به آن بخورند، هر چهار پرتو ممکن است فقط به خانه‌های سفید برخورد کنند، یا فقط سیاه، یا ترکیبی عجیب. در دنیای واقعی، وقتی با چشم‌هایمان یک صفحهٔ شطرنجی را از دور می‌بینیم، آن را به‌صورت یک رنگ خاکستری درک می‌کنیم، نه نقطه‌های تیز سیاه و سفید. علتش این است که چشم‌هایمان به‌طور طبیعی همان کاری را می‌کنند که می‌خواهیم ردیاب پرتومان بکند: انتگرال‌گیری از (تابع پیوستهٔ) نوری که روی یک ناحیهٔ (گسستهٔ) خاص از تصویر رندرشده‌مان می‌افتد.

به‌وضوح با نمونه‌برداری دوبارهٔ همان پرتو از مرکز پیکسل چند بار چیزی به دست نمی‌آوریم — هر بار همان نتیجه را می‌گرفتیم. در عوض، می‌خواهیم از نوری که اطراف پیکسل می‌افتد نمونه برداریم و سپس آن نمونه‌ها را انتگرال بگیریم تا نتیجهٔ پیوستهٔ واقعی تقریب زده شود. پس، چطور نورِ اطراف پیکسل را انتگرال می‌گیریم؟

ساده‌ترین مدل را می‌پذیریم: نمونه‌برداری از ناحیهٔ مربعیِ متمرکز بر پیکسل که تا نیمهٔ راه به هر چهار پیکسل همسایه امتداد می‌یابد. این رویکرد بهینه نیست، اما سرراست‌ترین است. (برای غواصی عمیق‌تر در این موضوع به مقالهٔ A Pixel is Not a Little Square مراجعه کنید.)

برای یک پیکسلِ متشکل از چند نمونه، از ناحیهٔ اطراف پیکسل نمونه انتخاب می‌کنیم و مقادیر نور (رنگ) حاصل را با هم میانگین می‌گیریم.

مواد مات (Diffuse)

حالا که اشیا و چند پرتو بر پیکسل داریم، می‌توانیم مواد واقع‌نمایی بسازیم.

با مواد مات شروع می‌کنیم (که به آن‌ها مت (matte) هم می‌گویند). یک سؤال این است که آیا هندسه و مواد را جداگانه نگه می‌داریم (طوری که بتوانیم یک ماده را به چند کره اختصاص دهیم، یا برعکس) یا هندسه و مواد به‌هم گره می‌خورند (که برای اشیای رویه‌ای (procedural) که هندسه و ماده در آن‌ها پیوند دارند می‌تواند مفید باشد). ما با حالت جداگانه می‌رویم — که در بیشتر رندررها معمول است — اما توجه داشته باشید رویکردهای جایگزین هم وجود دارند.

یک مادهٔ مات ساده

اشیای ماتِ بدونِ نوردهیِ خود، صرفاً رنگ محیط‌شان را می‌گیرند، اما آن را با رنگ ذاتی خودشان تعدیل می‌کنند. نوری که از یک سطح مات بازمی‌تابد، جهت‌اش تصادفی می‌شود؛ پس اگر سه پرتو به یک شکاف بین دو سطح مات بفرستیم، هرکدام رفتار تصادفی متفاوتی خواهند داشت:

آن‌ها ممکن است به‌جای بازتاب، جذب شوند. هرچه سطح تیره‌تر باشد، احتمال جذب پرتو بیشتر است (به همین دلیل تیره است!). واقعاً هر الگوریتمی که جهت را تصادفی کند، سطوحی می‌سازد که مت به نظر می‌رسند. با شهودی‌ترین حالت شروع می‌کنیم: سطحی که پرتو را به‌طور یکسان در همهٔ جهت‌ها بازمی‌تاباند. برای این ماده، پرتویی که به سطح برخورد می‌کند احتمال یکسانی برای بازتاب در هر جهتی دور از سطح دارد.

این مادهٔ بسیار شهودی ساده‌ترین نوع مات است و — در واقع — بسیاری از اولین مقاله‌های ردیابی پرتو از همین روش مات استفاده می‌کردند (قبل از پذیرش روش دقیق‌تری که کمی بعد پیاده‌سازی می‌کنیم). فعلاً راهی برای بازتاب تصادفی پرتو نداریم؛ پس باید چند تابع به هدر ابزارهای برداری‌مان اضافه کنیم. اولین چیزی که نیاز داریم توانایی تولید بردارهای تصادفی دلخواه است:

بعد باید بفهمیم چطور یک بردار تصادفی را طوری دستکاری کنیم که فقط نتایجی بگیریم که روی سطح یک نیم‌کره هستند. روش‌های تحلیلی برای این کار وجود دارد، اما درک آن‌ها واقعاً به‌شکل حیرت‌آوری پیچیده است و پیاده‌سازی‌شان هم کاملاً پیچیده. در عوض، از چیزی استفاده می‌کنیم که معمولاً آسان‌ترین الگوریتم است: روش طرد (rejection). روش طرد با تولید مکرر نمونه‌های تصادفی کار می‌کند تا وقتی نمونه‌ای تولید کنیم که معیارهای خواسته‌شده را برآورده کند. به بیان دیگر، به طردِ نمونه‌های بد ادامه بده تا یک نمونهٔ خوب پیدا کنی.

روش‌های به‌یکسان معتبر بسیاری برای تولید یک بردار تصادفی روی نیم‌کره با روش طرد وجود دارد، اما برای مقصود ما با ساده‌ترین‌شان می‌رویم که این است:

  1. یک بردار تصادفی داخل کرهٔ واحد تولید کن
  2. این بردار را نرمال کن تا به سطح کره برسد
  3. اگر بردار نرمال‌شده روی نیم‌کرهٔ اشتباه افتاد، معکوسش کن

    vec3 on_unit_sphere = random_unit_vector();
    if (dot(on_unit_sphere, normal) > 0.0) // در همان نیم‌کره‌ای که نرمال است
        return on_unit_sphere;

}

درست‌کردن آکنهٔ سایه (Shadow Acne)

همچنین یک باگ ظریف هست که باید به آن رسیدگی کنیم. یک پرتو وقتی با سطحی برخورد می‌کند، تلاش می‌کند نقطهٔ برخورد را دقیق محاسبه کند. متأسفانه برای ما، این محاسبه مستعد خطاهای گردکردن ممیز شناور است که می‌تواند باعث شود نقطهٔ برخورد به‌سختیِ ناچیز جا به‌جا شود. این یعنی مبدأ پرتوی بعدی — پرتویی که به‌طور تصادفی از سطح پراکنده می‌شود — به‌احتمال زیاد کاملاً هم‌سطح با سطح نخواهد بود. شاید کمی بالای سطح باشد. شاید کمی پایین سطح. اگر مبدأ پرتو کمی پایین سطح باشد، ممکن است دوباره با همان سطح برخورد کند. یعنی نزدیک‌ترین سطح را در t=0.00000001 یا هر تقریب ممیز شناوری که تابع برخورد به ما می‌دهد پیدا می‌کند. ساده‌ترین هک برای رفع این، نادیده‌گرفتن برخوردهایی است که خیلی به نقطهٔ برخوردِ محاسبه‌شده نزدیک‌اند:

بازتاب واقعی لامبرتین

پراکندن یکنواخت پرتوهای بازتابی دور نیم‌کره، یک مدل مات نرمِ خوب می‌سازد، اما قطعاً می‌توانیم بهتر انجامش دهیم. نمایش دقیق‌تر اشیای مات واقعی توزیع لامبرتین است. این توزیع پرتوهای بازتابی را به‌نسبت cos(φ) پراکنده می‌کند، جایی که φ زاویهٔ بین پرتوی بازتابی و نرمال سطح است. این یعنی پرتوی بازتابی به‌احتمال زیاد در جهتی نزدیک به نرمال سطح پراکنده می‌شود و به‌احتمال کمتر در جهت‌های دور از نرمال. این توزیع لامبرتین غیریکنواخت کار بهتری در مدل‌کردن بازتاب ماده در دنیای واقعی می‌کند تا پراکندگی یکنواخت قبلی‌مان.

می‌توانیم این توزیع را با اضافه‌کردن یک بردار واحد تصادفی به بردار نرمال بسازیم. در نقطهٔ برخورد روی سطح، نقطهٔ برخورد p را داریم و نرمال سطح n را. در نقطهٔ برخورد، این سطح دقیقاً دو طرف دارد؛ پس فقط می‌توانند دو کرهٔ واحدِ یکتا مماس بر هر نقطهٔ برخورد باشند (برای هر طرف سطح یک کرهٔ یکتا). این دو کرهٔ واحد به اندازهٔ طول شعاع‌شان از سطح جابه‌جا خواهند شد که برای کرهٔ واحد دقیقاً یک است.

یک کره در جهت نرمال سطح (n) جابه‌جا می‌شود و کرهٔ دیگر در جهت مخالف (−n). این ما را با دو کرهٔ واحد می‌گذارد که فقط در نقطهٔ برخورد دقیقاً سطح را لمس می‌کنند. از این‌جا، یکی از کره‌ها مرکزش در (P + n) و دیگری مرکزش در (P − n) خواهد بود. کره‌ای که مرکز آن در (P − n) است داخل سطح در نظر گرفته می‌شود، در حالی که کرهٔ با مرکز (P + n) خارج سطح در نظر گرفته می‌شود.

می‌خواهیم کرهٔ واحد مماسی را انتخاب کنیم که در همان سمت سطحِ مبدأ پرتو است. یک نقطهٔ تصادفی S روی این کرهٔ واحدِ شعاع‌دار انتخاب کن و پرتویی از نقطهٔ برخورد P به نقطهٔ تصادفی S بفرست (این بردار (S−P) است):

دلایل خوب زیادی برای اینکه تصویرها باید در فضای گاما ذخیره شوند وجود دارد، اما برای مقصود ما فقط باید از آن آگاه باشیم. داده‌هایمان را به فضای گاما تبدیل می‌کنیم تا نمایشگر تصویرمان بتواند تصویر را دقیق‌تر نمایش دهد. به‌عنوان یک تقریب ساده، می‌توانیم از «گامای ۲» به‌عنوان تبدیل‌مان استفاده کنیم، که توانی است که هنگام رفتن از فضای گاما به فضای خطی استفاده می‌کنید. ما باید از فضای خطی به فضای گاما برویم، یعنی معکوس «گامای ۲» را بگیریم، یعنی توان ۱/گاما، که فقط ریشهٔ دوم است. همچنین می‌خواهیم مطمئن شویم ورودی‌های منفی را به‌طور مقاوم مدیریت می‌کنیم.

cppinline double linear_to_gamma(double linear_component)
{
    if (linear_component > 0)
        return std::sqrt(linear_component);

    return 0;
}

    auto g = pixel_color.y();
    auto b = pixel_color.z();

    r = linear_to_gamma(r);

    static const interval intensity(0.000, 0.999);

    int bbyte = int(256 * intensity.clamp(b));

}

بازتاب فازی (Fuzzy)

همچنین می‌توانیم جهت بازتابی را با استفاده از یک کرهٔ کوچک و انتخاب یک نقطهٔ پایانی جدید برای پرتو تصادفی کنیم. از یک نقطهٔ تصادفی از سطح کره‌ای که روی نقطهٔ پایانی اصلی متمرکز است، مقیاس‌شده با ضریب فازی (fuzz) استفاده می‌کنیم.

هرچه کرهٔ فازی بزرگ‌تر باشد، بازتاب‌ها فازی‌تر خواهند بود. این افزودن یک پارامتر فازی‌بودن را پیشنهاد می‌کند که فقط شعاع کره است (پس صفر یعنی بدون اختلال). مشکل این است که برای کره‌های بزرگ یا پرتوهای مماسی (grazing)، ممکن است پایین سطح پراکنده شویم. می‌توانیم فقط سطح آن‌ها را جذب کند.

همچنین توجه کنید که برای اینکه کرهٔ فازی معنا بدهد، باید در مقایسه با بردار بازتابی — که طولش می‌تواند دلخواه باشد — پیوسته مقیاس شود. برای رسیدگی به این، باید پرتوی بازتابی را نرمال کنیم.

cppclass metal : public material {
  public:
    metal(const color& albedo, double fuzz) : albedo(albedo), fuzz(fuzz < 1 ? fuzz : 1) {}

    bool scatter(const ray& r_in, const hit_record& rec, color& attenuation, ray& scattered)
    const override {
        vec3 reflected = reflect(r_in.direction(), rec.normal);
        reflected = unit_vector(reflected) + (fuzz * random_unit_vector());
        scattered = ray(rec.p, reflected);
        attenuation = albedo;
        return (dot(scattered.direction(), rec.normal) > 0);
    }

  private:
    color albedo;
    double fuzz;
};

دیالکتریک‌ها (Dielectrics)

مواد شفافی مثل آب، شیشه و الماس دیالکتریک هستند. وقتی پرتوی نور به آن‌ها می‌خورد، به یک پرتوی بازتابی و یک پرتوی شکستی (عبورکرده) تقسیم می‌شود. ما با انتخاب تصادفی بین بازتاب و شکست به آن رسیدگی می‌کنیم و فقط یک پرتوی پراکنده بر هر برهم‌کنش تولید می‌کنیم.

به‌عنوان مرور سریع اصطلاح‌ها: پرتوی بازتابی به سطح می‌خورد و بعد در جهت جدیدی «بازمی‌پرد».

پرتوی شکستی وقتی از محیط اطراف ماده وارد خود ماده می‌شود خم می‌شود (مثل شیشه یا آب). به همین دلیل است که مداد وقتی تا نیمه در آب فرو می‌رود، خم‌دیده به نظر می‌رسد.

میزان خم‌شدن پرتوی شکستی با ضریب شکست ماده تعیین می‌شود. عموماً این یک مقدار واحد است که توصیف می‌کند نور وقتی از خلأ وارد ماده می‌شود چقدر خم می‌شود. شیشه ضریب شکستی حدود ۱.۵ تا ۱.۷ دارد، الماس حدود ۲.۴، و هوا ضریب شکست کوچکی معادل ۱.۰۰۰۲۹۳ دارد.

وقتی یک مادهٔ شفاف در مادهٔ شفافِ دیگری جاسازی شده است، می‌توانید شکست را با یک ضریب شکست نسبی توصیف کنید: ضریب شکستِ مادهٔ شیء تقسیم بر ضریب شکست مادهٔ اطراف. مثلاً اگر بخواهید یک گوی شیشه‌ای زیر آب رندر کنید، گوی شیشه‌ای ضریب شکست مؤثری معادل ۱.۱۲۵ خواهد داشت. این از تقسیم ضریب شکست شیشه (۱.۵) بر ضریب شکست آب (۱.۳۳۳) به دست می‌آید.

ضریب شکست بیشتر مواد رایج را می‌توانید با یک جست‌وجوی سریع اینترنتی پیدا کنید.

شکست (Refraction)

سخت‌ترین بخش برای اشکال‌زدایی پرتوی شکستی است. معمولاً اول کاری که می‌کنم این است که اگر اصلاً پرتوی شکستی وجود داشته باشد، همهٔ نور را شکست بدهم. برای این پروژه، سعی کردم دو گوی شیشه‌ای در صحنه‌مان بگذارم و این را گرفتم (هنوز به شما نگفته‌ام چطور این کار را درست یا غلط انجام دهید، اما به‌زودی!):

آیا این درست است؟ گوی‌های شیشه‌ای در زندگی واقعی عجیب به نظر می‌رسند. اما نه، درست نیست. دنیا باید وارونه شود و هیچ چیز سیاهِ عجیبی نباشد. من فقط پرتو را مستقیم از وسط تصویر چاپ کردم و به‌وضوح غلط بود. این کار اغلب جواب می‌دهد.

قانون اسنل (Snell's Law)

شکست با قانون اسنل توصیف می‌شود:

η·sinθ = η′·sinθ′

جایی که θ و θ′ زاویه‌های از نرمال هستند و η و η′ (تلفظ «اتا» و «اتای اول») ضریب‌های شکست‌اند. هندسه این است:

برای تعیین جهت پرتوی شکستی، باید sinθ′ را حل کنیم:

sinθ′ = (η/η′)·sinθ

در سمت شکستی سطح، یک پرتوی شکستی R′ و یک نرمال n′ وجود دارد و زاویهٔ θ′ بین آن‌ها برقرار است. می‌توانیم R′ را به بخش‌هایِ عمود بر n′ و موازی با n′ پرتو تجزیه کنیم:

R′ = R′⊥ + R′∥

اگر برای R′⊥ و R′∥ حل کنیم به این می‌رسیم:

R′⊥ = (η/η′)·(R + |R|·cos(θ)·n)

R′∥ = −√(1 − |R′⊥|²)·n

اگر خواستید، می‌توانید خودتان این را اثبات کنید، اما ما آن را به‌عنوان یک واقعیت می‌پذیریم و ادامه می‌دهیم. بقیهٔ کتاب از شما نمی‌خواهد اثبات را بفهمید.

مقدار هر جملهٔ سمت راست را می‌دانیم به‌جز cosθ. به‌خوبی معلوم است که ضرب داخلی دو بردار را می‌توان برحسب کسینوس زاویهٔ بین آن‌ها توضیح داد:

a·b = |a|·|b|·cosθ

اگر a و b را به بردارهای واحد محدود کنیم:

a·b = cosθ

حالا می‌توانیم R′⊥ را برحسب کمیت‌های معلوم بازنویسی کنیم:

R′⊥ = (η/η′)·(R + (−R·n)·n)

وقتی آن‌ها را دوباره ترکیب کنیم، می‌توانیم تابعی بنویسیم که R′ را محاسبه می‌کند:

cpp...

    return v - 2*dot(v,n)*n;
}

inline vec3 refract(const vec3& uv, const vec3& n, double etai_over_etat) {
    auto cos_theta = std::fmin(dot(-uv, n), 1.0);
    vec3 r_out_perp =  etai_over_etat * (uv + cos_theta*n);
    vec3 r_out_parallel = -std::sqrt(std::fabs(1.0 - r_out_perp.length_squared())) * n;
    return r_out_perp + r_out_parallel;
}

بازتاب داخلی کلی (Total Internal Reflection)

یک مسئلهٔ عملی دردسرساز در شکست این است که زاویه‌های پرتویی وجود دارند که با قانون اسنل هیچ راه‌حلی ممکن نیست. وقتی پرتویی با زاویهٔ به‌اندازهٔ کافیِ مماسی وارد محیطی با ضریب شکست پایین‌تر می‌شود، می‌تواند با زاویه‌ای بیش از ۹۰ درجه شکست بخورد. اگر به قانون اسنل و اشتقاق sinθ′ برگردیم:

تقریب شلیک (Schlick)

حالا شیشهٔ واقعی بازتاب‌دهندگی‌ای دارد که با زاویه تغییر می‌کند — به پنجره از یک زاویهٔ تند نگاه کنید و آینه می‌شود. یک معادلهٔ بزرگ و زشت برای آن وجود دارد، اما تقریباً همه از یک تقریب چندجمله‌ای ارزان و به‌طور شگفت‌آوری دقیق از کریستف شلیک استفاده می‌کنند. این مادهٔ شیشهٔ کامل ما را می‌دهد:

cppclass dielectric : public material {
  public:
    dielectric(double refraction_index) : refraction_index(refraction_index) {}

    bool scatter(const ray& r_in, const hit_record& rec, color& attenuation, ray& scattered)
    const override {
        attenuation = color(1.0, 1.0, 1.0);
        double ri = rec.front_face ? (1.0/refraction_index) : refraction_index;

        vec3 unit_direction = unit_vector(r_in.direction());
        double cos_theta = std::fmin(dot(-unit_direction, rec.normal), 1.0);
        double sin_theta = std::sqrt(1.0 - cos_theta*cos_theta);

        bool cannot_refract = ri * sin_theta > 1.0;
        vec3 direction;

        if (cannot_refract || reflectance(cos_theta, ri) > random_double())
            direction = reflect(unit_direction, rec.normal);
        else
            direction = refract(unit_direction, rec.normal, ri);

        scattered = ray(rec.p, direction);
        return true;
    }

  private:
    // ضریب شکست در خلأ یا هوا، یا نسبت ضریب شکست ماده بر ضریب شکست محیطِ دربرگیرنده
    double refraction_index;

    static double reflectance(double cosine, double refraction_index) {
        // از تقریب شلیک برای بازتاب‌دهندگی استفاده کن.
        auto r0 = (1 - refraction_index) / (1 + refraction_index);
        r0 = r0*r0;
        return r0 + (1-r0)*std::pow((1 - cosine),5);
    }
};

جابه‌جایی و جهت‌دهی دوربین

برای رسیدن به یک نقطه‌دید دلخواه، اول بگذارید نقاطی را که به آن‌ها اهمیت می‌دهیم نام‌گذاری کنیم. مکانِ قرارگیری دوربین را lookfrom و نقطه‌ای را که به آن نگاه می‌کنیم lookat می‌نامیم. (بعداً، اگر خواستید، می‌توانید به‌جای نقطه‌ای که به آن نگاه می‌کنید، یک جهت نگاه تعریف کنید.)

همچنین به راهی برای مشخص‌کردن چرخش، یا کج‌شدن پهلو، دوربین نیاز داریم: چرخش دور محور lookat-lookfrom. یک راه دیگر برای فکرکردن به آن این است که حتی اگر lookfrom و lookat را ثابت نگه دارید، باز هم می‌توانید سرتان را دور بینی‌تان بچرخانید. چیزی که نیاز داریم راهی برای مشخص‌کردن بردار «بالا» برای دوربین است.

می‌توانیم هر بردار بالایی که می‌خواهیم مشخص کنیم، تا وقتی موازی جهت دید نباشد. این بردار بالا را روی صفحهٔ عمود بر جهت دید تصویر می‌کنیم تا بردار بالایِ نسبت‌به‌دوربین بگیریم. من از قرارداد رایجِ نامیدن این بردار به‌عنوان بردار «نمای بالا» (vup) استفاده می‌کنم. بعد از چند ضرب خارجی و نرمال‌سازی برداری، حالا یک پایهٔ کامل متعامد یکه (u, v, w) داریم که جهت‌گیری دوربین‌مان را توصیف می‌کند. u بردار واحدِ اشاره‌کننده به راست دوربین است، v بردار واحدِ اشاره‌کننده به بالای دوربین، w بردار واحدِ اشاره‌کننده به خلاف جهت دید (چون از مختصات راست‌دست استفاده می‌کنیم)، و مرکز دوربین در مبدأ است.

مثل قبل که دوربین ثابت‌مان رو به −Z بود، دوربین دید دلخواه‌مان رو به −w است. به خاطر داشته باشید که می‌توانیم — اما لازم نیست — از بالای دنیا (0,1,0) برای مشخص‌کردن vup استفاده کنیم. این راحت است و به‌طور طبیعی دوربین‌تان را هم‌ترازِ افقی نگه می‌دارد تا وقتی تصمیم بگیرید با زاویه‌های دیوانه‌وار دوربین آزمایش کنید.

تاری حرکت (Defocus Blur)

حالا آخرین ویژگی‌مان: تاری خارج‌ازفوکوس. توجه کنید که عکاس‌ها به این می‌گویند عمق میدان (depth of field)؛ پس مطمئن باشید واژهٔ defocus blur را فقط بین دوستان ردیاب‌پرتو‌ای‌تان به کار ببرید.

دلیل اینکه در دوربین‌های واقعی تاری خارج‌ازفوکوس داریم این است که آن‌ها به یک سوراخ بزرگ (به‌جای فقط یک سوراخ سوزنی) نیاز دارند تا نور جمع کنند. یک سوراخ بزرگ همه‌چیز را خارج‌ازفوکوس می‌کرد، اما اگر یک لنز جلوی فیلم/سنسور بگذاریم، فاصلهٔ مشخصی وجود خواهد داشت که در آن همه‌چیز در فوکوس است. اشیایی که در آن فاصله قرار بگیرند در فوکوس ظاهر می‌شوند و هرچه از آن فاصله دورتر باشند، به‌طور خطی تارتر ظاهر می‌شوند. می‌توانید این‌طور به لنز فکر کنید: همهٔ پرتوهای نوری که از یک نقطهٔ خاص در فاصلهٔ فوکوس می‌آیند — و به لنز می‌خورند — به سمت یک نقطهٔ واحد روی سنسور تصویر خم می‌شوند.

به فاصلهٔ بین مرکز دوربین و صفحه‌ای که همه‌چیز در آن در فوکوس کامل است، فاصلهٔ فوکوس می‌گوییم. توجه داشته باشید فاصلهٔ فوکوس معمولاً با فاصلهٔ کانونی یکسان نیست — فاصلهٔ کانونی فاصلهٔ بین مرکز دوربین و صفحهٔ تصویر است. اما برای مدل ما، این دو مقدار یکسان خواهند داشت، چون شبکهٔ پیکسل‌هایمان را دقیقاً روی صفحهٔ فوکوس می‌گذاریم که به اندازهٔ فاصلهٔ فوکوس از مرکز دوربین فاصله دارد.

در یک دوربین فیزیکی، فاصلهٔ فوکوس با فاصلهٔ بین لنز و فیلم/سنسور کنترل می‌شود. به همین دلیل است که وقتی چیزی را که در فوکوس است تغییر می‌دهید، می‌بینید لنز نسبت به دوربین حرکت می‌کند (شاید در دوربین گوشی‌تان هم این اتفاق بیفتد، اما آن‌جا سنسور حرکت می‌کند). «دیافراگم» سوراخی برای کنترل این است که لنز عملاً چقدر بزرگ است. برای یک دوربین واقعی، اگر نور بیشتری نیاز دارید دیافراگم را بزرگ‌تر می‌کنید و برای اشیای دور از فاصلهٔ فوکوس، تاری بیشتری می‌گیرید. برای دوربین مجازی‌مان، می‌توانیم یک سنسور کامل داشته باشیم و هرگز به نور بیشتری نیاز نداشته باشیم؛ پس فقط وقتی تاری خارج‌ازفوکوس می‌خواهیم از دیافراگم استفاده می‌کنیم.

تقریب لنز نازک

یک دوربین واقعی لنز ترکیبی پیچیده‌ای دارد. برای کدمان، می‌توانستیم ترتیبِ سنسور، بعد لنز و بعد دیافراگم را شبیه‌سازی کنیم. بعد می‌توانستیم بفهمیم پرتوها را کجا بفرستیم و تصویر را بعد از محاسبه، وارونه کنیم (تصویر روی فیلم به‌صورت وارونه پخش می‌شود). اما اهالی گرافیک معمولاً از تقریب لنز نازک استفاده می‌کنند:

نیازی به شبیه‌سازی داخل دوربین نداریم — برای مقصود رندرشدن تصویرِ بیرونِ دوربین، آن پیچیدگیِ غیرضروری است. در عوض، من معمولاً پرتوها را از یک «لنز» دایره‌ایِ بی‌نهایت نازک شروع می‌کنم و آن‌ها را به‌سوی پیکسلِ موردنظر روی صفحهٔ فوکوس می‌فرستم (focal_length دور از لنز)، جایی که هر چیزی روی آن صفحه در دنیای سه‌بعدی در فوکوس کامل است.

در عمل، این را با قراردادن viewport در همین صفحه انجام می‌دهیم. با کنار هم گذاشتن همه‌چیز:

  1. صفحهٔ فوکوس عمود بر جهت دید دوربین است.
  2. فاصلهٔ فوکوس، فاصلهٔ بین مرکز دوربین و صفحهٔ فوکوس است.
  3. viewport روی صفحهٔ فوکوس قرار دارد و روی بردار جهت دید دوربین متمرکز است.
  4. شبکهٔ مکان‌های پیکسلی داخل viewport قرار دارد (در دنیای سه‌بعدی واقع شده).
  5. مکان‌های نمونهٔ تصویرِ تصادفی از ناحیهٔ اطراف مکان پیکسل فعلی انتخاب می‌شوند.
  6. دوربین پرتوها را از نقاط تصادفی روی لنز، از میانِ مکان نمونهٔ تصویرِ فعلی شلیک می‌کند.

تولید پرتوهای نمونه

بدون تاری خارج‌ازفوکوس، همهٔ پرتوهای صحنه از مرکز دوربین (یا lookfrom) شروع می‌شوند. برای دستیابی به تاری خارج‌ازفوکوس، یک دیسک متمرکز بر مرکز دوربین می‌سازیم. هرچه شعاع بزرگ‌تر باشد، تاری خارج‌ازفوکوس بیشتر است. می‌توانید دوربین اصلی‌مان را دوربینی با دیسک خارج‌ازفوکوسِ شعاع صفر (بدون هیچ تارشدگی) در نظر بگیرید؛ پس همهٔ پرتوها از مرکز دیسک (lookfrom) شروع می‌شدند.

پس، دیسک خارج‌ازفوکوس چقدر باید بزرگ باشد؟ چون اندازهٔ این دیسک کنترل می‌کند چقدر تاری خارج‌ازفوکوس می‌گیریم، باید پارامتری از کلاس دوربین باشد. می‌توانستیم فقط شعاع دیسک را پارامتر دوربین بگیریم، اما تاری بسته به فاصلهٔ پخش‌شدن تغییر می‌کرد. پارامتر کمی آسان‌تر مشخص‌کردن زاویهٔ مخروطی است که رأسش در مرکز viewport و قاعده‌اش (دیسک خارج‌ازفوکوس) در مرکز دوربین است. این باید برای یک نما، با تغییر فاصلهٔ فوکوس نتایج سازگارتری به شما بدهد.

    double pixel_samples_scale;  // ضریب مقیاس رنگ برای جمع نمونه‌های پیکسل
    point3 center;               // مرکز دوربین
    point3 pixel00_loc;          // مکان پیکسل ۰، ۰
    vec3   pixel_delta_u;        // جابه‌جایی به پیکسل سمت راست
    vec3   pixel_delta_v;        // جابه‌جایی به پیکسل پایین
    vec3   u, v, w;              // بردارهای پایهٔ قاب دوربین
    vec3   defocus_disk_u;       // شعاع افقی دیسک خارج‌ازفوکوس
    vec3   defocus_disk_v;       // شعاع عمودی دیسک خارج‌ازفوکوس

    void initialize() {
        image_height = int(image_width / aspect_ratio);
        image_height = (image_height < 1) ? 1 : image_height;

        pixel_samples_scale = 1.0 / samples_per_pixel;

        center = lookfrom;        // ابعاد viewport را تعیین کن.
        auto theta = degrees_to_radians(vfov);
        auto h = std::tan(theta/2);
        auto viewport_height = 2 * h * focus_dist;
        auto viewport_width = viewport_height * (double(image_width)/image_height);

        // بردارهای پایهٔ واحد u,v,w را برای قاب مختصات دوربین حساب کن.
        w = unit_vector(lookfrom - lookat);
        u = unit_vector(cross(vup, w));
        v = cross(w, u);

        // بردارهای عرضی (افقی) و رو به پایین (عمودی) لبه‌های viewport را حساب کن.
        vec3 viewport_u = viewport_width * u;    // بردار عرض لبهٔ افقی viewport
        vec3 viewport_v = viewport_height * -v;  // بردار پایین لبهٔ عمودی viewport

        // بردارهای دلتای افقی و عمودی تا پیکسل بعدی را حساب کن.
        pixel_delta_u = viewport_u / image_width;
        pixel_delta_v = viewport_v / image_height;

        // مکان پیکسل بالا-چپ را حساب کن.
        auto viewport_upper_left = center - (focus_dist * w) - viewport_u/2 - viewport_v/2;
        pixel00_loc = viewport_upper_left + 0.5 * (pixel_delta_u + pixel_delta_v);

        // بردارهای پایهٔ دیسک خارج‌ازفوکوس دوربین را حساب کن.
        auto defocus_radius = focus_dist * std::tan(degrees_to_radians(defocus_angle / 2));
        defocus_disk_u = u * defocus_radius;
        defocus_disk_v = v * defocus_radius;
    }

    ray get_ray(int i, int j) const {
        // یک پرتوی دوربین بساز که از دیسک خارج‌ازفوکوس می‌آید و به نقطهٔ تصادفیِ
        // نمونه‌شده اطراف مکان پیکسل i, j هدف گرفته است.

        auto offset = sample_square();
        auto pixel_sample = pixel00_loc
                          + ((i + offset.x()) * pixel_delta_u)
                          + ((j + offset.y()) * pixel_delta_v);

        auto ray_origin = (defocus_angle <= 0) ? center : defocus_disk_sample();
        auto ray_direction = pixel_sample - ray_origin;

        return ray(ray_origin, ray_direction);
    }

    vec3 sample_square() const {
        ...
    }

    point3 defocus_disk_sample() const {
        // یک نقطهٔ تصادفی در دیسک خارج‌ازفوکوس دوربین برمی‌گرداند.
        auto p = random_in_unit_disk();
        return center + (p[0] * defocus_disk_u) + (p[1] * defocus_disk_v);
    }

کتاب ۲: Ray Tracing: The Next Week

کتاب دوم این مجموعه بر ردیاب پرتویی که این‌جا توسعه داده‌اید بنا می‌شود. این شامل ویژگی‌های جدیدی مثل:

  • تاری حرکت (Motion blur) — رندر واقع‌گرایانهٔ اشیای متحرک.
  • سلسله‌مراتب حجم محدود (bounding volume hierarchies) — سرعت‌بخشیدن به رندر صحنه‌های پیچیده.
  • نقشه‌های بافت (Texture maps) — قراردادن تصاویر روی اشیا.
  • نویز پرلین (Perlin noise) — یک مولد نویز تصادفی که برای تکنیک‌های زیادی بسیار مفید است.
  • چهارضلعی‌ها — چیزی برای رندر کردن غیر از کره‌ها! همچنین پایهٔ پیاده‌سازی دیسک‌ها، مثلث‌ها، حلقه‌ها یا تقریباً هر ابتدایی دوبعدی دیگر.
  • نورها — افزودن منبع‌های نور به صحنه.
  • تبدیل‌ها (Transforms) — مفید برای جای‌گذاری و چرخش اشیا.
  • رندر حجمی — رندر دود، ابر و دیگر حجم‌های گازی.

کتاب ۳: Ray Tracing: The Rest of Your Life

این کتاب دوباره بر محتوای کتاب دوم گسترش می‌یابد. بخش زیادی از این کتاب دربارهٔ بهبود هم کیفیت تصویر رندرشده و هم کارایی رندرر است و روی تولید پرتوهای درست و انباشت مناسب آن‌ها تمرکز دارد.

این کتاب برای خواننده‌ای است که جداً به نوشتن ردیاب‌های پرتو در سطح حرفه‌ای علاقه‌مند است و/یا به پایه‌های پیاده‌سازی افکت‌های پیشرفته مثل پراکندگی زیرسطحی یا دی‌الکتریک‌های تو در تو علاقه دارد.

جهت‌های دیگر

از این‌جا مسیرهای اضافی بی‌شماری پیش رو دارید، از جمله تکنیک‌هایی که (تا حالا؟) در این مجموعه پوشش نداده‌ایم. این‌ها عبارت‌اند از:

مثلث‌ها — بیشتر مدل‌های جذاب به شکل مثلث هستند. ورودی/خروجی مدل بدترین بخش است و تقریباً همه سعی می‌کنند از کد شخص دیگری برای این کار استفاده کنند. این شامل مدیریت کارآمد مش‌های بزرگ از مثلث‌ها هم می‌شود که چالش‌های خودشان را دارند.

موازی‌سازی — N نسخه از کدتان را روی N هسته با seedهای تصادفی متفاوت اجرا کنید. N اجرا را میانگین بگیرید. این میانگین‌گیری را می‌توان سلسله‌مراتبی هم انجام داد، جایی که N/2 جفت را میانگین می‌گیریم تا N/4 تصویر بگیریم و جفت‌های آن‌ها را هم میانگین بگیریم. آن روش موازی‌سازی باید با کدنویسی بسیار کم تا هزاران هسته به‌خوبی گسترش یابد.

پرتوهای سایه — وقتی به‌سوی منابع نور پرتو شلیک می‌کنید، می‌توانید دقیقاً تعیین کنید یک نقطهٔ خاص چگونه سایه می‌گیرد. با این کار، می‌توانید سایه‌های تیز یا نرم رندر کنید و درجهٔ دیگری از واقع‌گرایی به صحنه‌هایتان اضافه کنید.
