#0: مقدمه

در این آموزش برخی از مفاهیم پایه‌ای لازم برای یک ارز دیجیتالِ کارا را از صفر کدنویسی می‌کنیم. رویکرد ما همیشه این است که کارها را به ساده‌ترین شکل ممکن پیاده‌سازی کنیم.

پروژه‌ای که در این آموزش می‌سازیم «Naivecoin» نام دارد. زبان برنامه‌نویسی آن TypeScript است. Naivecoin به نوعی گسترش پروژه Naivechain — بلاک‌چین در ۲۰۰ خط کد محسوب می‌شود.

نسخه نهایی Naivecoin به هیچ وجه یک پیاده‌سازی «آماده برای تولید» از یک ارز دیجیتال نیست، بلکه صرفاً تلاشی است برای نشان دادن این‌که اصول پایه‌ای یک ارز دیجیتال را می‌توان به‌صورتی موجز پیاده‌سازی کرد.

امیدوارم این آموزش به شما کمک کند جنبه‌های فنی ارز دیجیتال را بهتر درک کنید.

نکته: پیش از ادامه، بهتر است فصل‌ها را به‌ترتیب بخوانید؛ هر فصل بر پایه مفاهیم فصل قبلی ساخته شده است. کد نهایی هر فصل در ریپازیتوری گیت‌هاب lhartikk/naivecoin (شاخه‌های chapter1 تا chapter6) موجود است.

#1: بلاک‌چین کارآمدِ حداقلی

مرور کلی

مفهوم پایه‌ای بلاک‌چین کاملاً ساده است: یک پایگاه‌داده توزیع‌شده که فهرستی به‌صورت پیوسته در حال رشد از رکوردهای مرتب را نگهداری می‌کند. در این فصل نسخه اسباب‌بازی از چنین بلاک‌چینی را پیاده‌سازی می‌کنیم. در انتهای این فصل این قابلیت‌های پایه‌ای بلاک‌چین را خواهیم داشت:

  • ساختار تعریف‌شده‌ای برای بلاک و بلاک‌چین
  • روش‌هایی برای افزودن بلاک‌های جدید با داده دلخواه به بلاک‌چین
  • گره‌های بلاک‌چینی که با سایر گره‌ها ارتباط برقرار کرده و بلاک‌چین را همگام‌سازی می‌کنند
  • یک رابط API ساده HTTP برای کنترل گره

کد کامل این فصل را می‌توانید اینجا پیدا کنید.

ساختار بلاک

با تعریف ساختار بلاک شروع می‌کنیم. در این مرحله فقط ضروری‌ترین ویژگی‌ها در بلاک قرار داده می‌شوند:

  • index: ارتفاع بلاک در بلاک‌چین
  • data: هر داده‌ای که در بلاک قرار می‌گیرد
  • timestamp: یک برچسب زمانی
  • hash: یک هش SHA256 که از محتوای بلاک گرفته می‌شود
  • previousHash: ارجاعی به هش بلاک قبلی. این مقدار بلاک قبلی را به‌صراحت مشخص می‌کند

کد ساختار بلاک به شکل زیر است:

typescriptclass Block {

    public index: number;          // ارتفاع بلاک در زنجیره
    public hash: string;           // هش بلاک
    public previousHash: string;   // هش بلاک قبلی
    public timestamp: number;      // برچسب زمانی
    public data: string;           // داده داخل بلاک

    constructor(index: number, hash: string, previousHash: string, timestamp: number, data: string) {
        this.index = index;
        this.previousHash = previousHash;
        this.timestamp = timestamp;
        this.data = data;
        this.hash = hash;
    }
}

هش بلاک

هش بلاک یکی از مهم‌ترین ویژگی‌های بلاک است. هش از روی تمام داده‌های بلاک محاسبه می‌شود. این یعنی اگر هر چیزی در بلاک تغییر کند، هش اصلی دیگر معتبر نیست. همچنین می‌توان هش بلاک را شناسه یکتای بلاک در نظر گرفت؛ برای مثال بلاک‌هایی با index یکسان ممکن است وجود داشته باشند، اما همه آن‌ها هش‌های یکتا دارند.

هش بلاک را با کد زیر محاسبه می‌کنیم:

typescript// محاسبه هش: ترکیب شاخص، هش قبلی، زمان و داده سپس هش SHA256
const calculateHash = (index: number, previousHash: string, timestamp: number, data: string): string =>
    CryptoJS.SHA256(index + previousHash + timestamp + data).toString();

لازم به ذکر است که هش بلاک هنوز هیچ ارتباطی با استخراج (ماینینگ) ندارد، زیرا هیچ مسئله اثبات کار (proof-of-work) برای حل وجود ندارد. ما از هش بلاک برای حفظ یکپارچگی بلاک و ارجاع صریح به بلاک قبلی استفاده می‌کنیم.

یک نتیجه مهم ویژگی‌های hash و previousHash این است که بدون تغییر هش همه بلاک‌های بعدی، امکان تغییر یک بلاک وجود ندارد.

این موضوع در مثال زیر نشان داده شده است. اگر داده بلاک ۴۴ از «DESERT» به «STREET» تغییر کند، باید همه هش‌های بلاک‌های بعدی تغییر کنند؛ زیرا هش هر بلاک به مقدار previousHash (در میان چیزهای دیگر) وابسته است.

این ویژگی به‌خصوص وقتی اثبات کار معرفی می‌شود اهمیت پیدا می‌کند. هرچه بلاک در بلاک‌چین عمیق‌تر باشد، تغییر آن سخت‌تر است، زیرا مستلزم تغییر همه بلاک‌های بعدی است.

بلاک پیدایش (Genesis)

بلاک پیدایش اولین بلاک بلاک‌چین است. تنها بلاکی است که previousHash ندارد. بلاک پیدایش را به‌صورت ثابت در کد منبع قرار می‌دهیم: 

typescript// بلاک پیدایش: بلاک اول زنجیره، بدون هش قبلی
const genesisBlock: Block = new Block(
    0, '816534932c2b7154836da6afc367695e6337db8a921823784c14378abed4f7d7', null, 1465154705, 'my genesis block!!'
);

تولید یک بلاک

برای تولید یک بلاک باید هش بلاک قبلی را بدانیم و بقیه محتوای لازم (یعنی index، هش، داده و برچسب زمانی) را بسازیم. داده بلاک چیزی است که کاربر نهایی فراهم می‌کند اما بقیه پارامترها با کد زیر تولید می‌شوند: 

typescript// تولید بلاک بعدی بر اساس داده ورودی کاربر
const generateNextBlock = (blockData: string) => {
    const previousBlock: Block = getLatestBlock();               // آخرین بلاک زنجیره
    const nextIndex: number = previousBlock.index + 1;           // شاخص = شاخص قبلی + ۱
    const nextTimestamp: number = new Date().getTime() / 1000;   // زمان فعلی به ثانیه
    const nextHash: string = calculateHash(nextIndex, previousBlock.hash, nextTimestamp, blockData);
    const newBlock: Block = new Block(nextIndex, nextHash, previousBlock.hash, nextTimestamp, blockData);
    return newBlock;
};

ذخیره‌سازی بلاک‌چین

فعلاً برای ذخیره بلاک‌چین فقط از یک آرایه جاوااسکریپتی در حافظه استفاده می‌کنیم. یعنی وقتی گره خاتمه می‌یابد، داده‌ها ماندگار نخواهند ماند. 

typescript// بلاک‌چین فعلی؛ فقط در حافظه نگهداری می‌شود و با خاتمه گره از بین می‌رود
const blockchain: Block[] = [genesisBlock];

اعتبارسنجی یکپارچگی بلاک‌ها

در هر لحظه باید بتوانیم اعتبار یک بلاک یا زنجیره‌ای از بلاک‌ها را از نظر یکپارچگی بررسی کنیم. این موضوع به‌خصوص وقتی از گره‌های دیگر بلاک جدید دریافت می‌کنیم و باید تصمیم بگیریم که آن‌ها را بپذیریم یا نه، اهمیت دارد.

برای معتبر بودن یک بلاک موارد زیر باید برقرار باشند:

  • شاخص بلاک باید یک عدد بزرگ‌تر از بلاک قبلی باشد
  • previousHash بلاک باید با hash بلاک قبلی مطابقت داشته باشد
  • hash خود بلاک باید معتبر باشد

این موضوع با کد زیر نشان داده می‌شود:

typescript// بررسی معتبر بودن یک بلاک جدید نسبت به بلاک قبلی
const isValidNewBlock = (newBlock: Block, previousBlock: Block) => {
    if (previousBlock.index + 1 !== newBlock.index) {
        console.log('invalid index');                     // شاخص اشتباه است
        return false;
    } else if (previousBlock.hash !== newBlock.previousHash) {
        console.log('invalid previoushash');              // هش قبلی مطابقت ندارد
        return false;
    } else if (calculateHashForBlock(newBlock) !== newBlock.hash) {
        console.log(typeof (newBlock.hash) + ' ' + typeof calculateHashForBlock(newBlock));
        console.log('invalid hash: ' + calculateHashForBlock(newBlock) + ' ' + newBlock.hash); // هش نادرست
        return false;
    }
    return true;
};

همچنین باید ساختار بلاک را اعتبارسنجی کنیم تا محتوای خرابی که یک هم‌تا (peer) می‌فرستد باعث از کار افتادن گره ما نشود. 

typescript// بررسی صحت ساختار بلاک (انواع فیلدها)
const isValidBlockStructure = (block: Block): boolean => {
    return typeof block.index === 'number'
        && typeof block.hash === 'string'
        && typeof block.previousHash === 'string'
        && typeof block.timestamp === 'number'
        && typeof block.data === 'string';
};

حالا که ابزار اعتبارسنجی یک بلاک را داریم، می‌توانیم سراغ اعتبارسنجی یک زنجیره کامل از بلاک‌ها برویم. ابتدا بررسی می‌کنیم که اولین بلاک زنجیره با genesisBlock مطابقت دارد یا نه؛ سپس با روش‌هایی که شرح داده شد هر بلاک بعدی را اعتبارسنجی می‌کنیم: 

typescript// اعتبارسنجی کل زنجیره
const isValidChain = (blockchainToValidate: Block[]): boolean => {
    // بلاک اول باید دقیقاً بلاک پیدایش باشد
    const isValidGenesis = (block: Block): boolean => {
        return JSON.stringify(block) === JSON.stringify(genesisBlock);
    };

    if (!isValidGenesis(blockchainToValidate[0])) {
        return false;
    }

    // بررسی بلاک‌های پیاپی
    for (let i = 1; i < blockchainToValidate.length; i++) {
        if (!isValidNewBlock(blockchainToValidate[i], blockchainToValidate[i - 1])) {
            return false;
        }
    }
    return true;
};

انتخاب بلندترین زنجیره

در هر لحظه فقط باید یک مجموعه صریح از بلاک‌ها در زنجیره وجود داشته باشد. در صورت بروز تعارض (مثلاً وقتی دو گره هر دو بلاک شماره ۷۲ را تولید کنند) زنجیره‌ای را انتخاب می‌کنیم که تعداد بلاک‌های بیشتری دارد. در مثال زیر، داده‌ای که در بلاک ۷۲: a350235b00 معرفی شده در بلاک‌چین قرار نخواهد گرفت، زیرا با زنجیره بلندتر جایگزین می‌شود.

این منطق با کد زیر پیاده‌سازی می‌شود:

typescript// جایگزینی زنجیره فعلی با زنجیره جدید در صورت معتبر و بلندتر بودن
const replaceChain = (newBlocks: Block[]) => {
    if (isValidChain(newBlocks) && newBlocks.length > getBlockchain().length) {
        console.log('Received blockchain is valid. Replacing current blockchain with received blockchain');
        blockchain = newBlocks;
        broadcastLatest();   // زنجیره جدید را به بقیه گره‌ها اطلاع می‌دهیم
    } else {
        console.log('Received blockchain invalid');  // زنجیره دریافتی نامعتبر است
    }
};

ارتباط با سایر گره‌ها

بخش اساسی هر گره، به اشتراک گذاشتن و همگام‌سازی بلاک‌چین با گره‌های دیگر است. برای همگام نگه داشتن شبکه از قوانین زیر استفاده می‌کنیم:

  • وقتی یک گره بلاک جدید تولید می‌کند، آن را به شبکه پخش (broadcast) می‌کند
  • وقتی یک گره به هم‌تای جدیدی متصل می‌شود، آخرین بلاک را پرس‌وجو می‌کند
  • وقتی گره‌ای بلاکی را می‌بیند که شاخص آن بزرگ‌تر از آخرین بلاک شناخته‌شده است، یا آن بلاک را به زنجیره فعلی خود اضافه می‌کند یا کل بلاک‌چین را درخواست می‌کند

برای ارتباط همتا-به-همتا از وب‌سوکت استفاده می‌کنیم. سوکت‌های فعال هر گره در متغیر const sockets: WebSocket[] نگهداری می‌شوند. هیچ مکانیزم کشف خودکار هم‌تا استفاده نمی‌شود؛ آدرس (یعنی URL وب‌سوکت) هم‌تاها باید به‌صورت دستی اضافه شود.

کنترل گره

کاربر باید بتواند به نحوی گره را کنترل کند. این کار با راه‌اندازی یک سرور HTTP انجام می‌شود:

typescript// راه‌اندازی سرور HTTP برای کنترل گره
const initHttpServer = ( myHttpPort: number ) => {
    const app = express();
    app.use(bodyParser.json());

    // لیست همه بلاک‌ها
    app.get('/blocks', (req, res) => {
        res.send(getBlockchain());
    });
    // استخراج یک بلاک جدید با داده دلخواه
    app.post('/mineBlock', (req, res) => {
        const newBlock: Block = generateNextBlock(req.body.data);
        res.send(newBlock);
    });
    // لیست هم‌تایان متصل
    app.get('/peers', (req, res) => {
        res.send(getSockets().map(( s: any ) => s._socket.remoteAddress + ':' + s._socket.remotePort));
    });
    // افزودن یک هم‌تای جدید
    app.post('/addPeer', (req, res) => {
        connectToPeers(req.body.peer);
        res.send();
    });

    app.listen(myHttpPort, () => {
        console.log('Listening http on port: ' + myHttpPort);
    });
};

همان‌طور که دیده می‌شود، کاربر می‌تواند به روش‌های زیر با گره تعامل کند:

  • فهرست کردن همه بلاک‌ها
  • ساخت بلاک جدید با محتوایی که کاربر مشخص می‌کند
  • فهرست کردن یا افزودن هم‌تایان

ساده‌ترین راه کنترل گره مثلاً با Curl است:

bash# دریافت همه بلاک‌ها از گره
> curl http://localhost:3001/blocks

لازم به ذکر است که گره در واقع دو وب‌سرور در معرض دید قرار می‌دهد: یکی برای کنترل گره توسط کاربر (سرور HTTP) و یکی برای ارتباط همتا-به-همتا بین گره‌ها (سرور وب‌سوکت HTTP).

جمع‌بندی

Naivecoin فعلاً یک بلاک‌چین اسباب‌بازی «همه‌منظوره» است. همچنین این فصل نشان می‌دهد برخی اصول پایه‌ای بلاک‌چین را می‌توان به‌طریقی نسبتاً ساده پیاده‌سازی کرد. در فصل بعد الگوریتم اثبات کار (استخراج) را به naivecoin اضافه می‌کنیم.

کد کامل و نهایی فصل ۱ را می‌توانید اینجا بیابید.

#2: اثبات کار (Proof of Work)

مرور کلی

در این فصل یک طرح ساده از اثبات کار (Proof-of-Work) را به نسخه اسباب‌بازی بلاک‌چین اضافه می‌کنیم. در نسخه فصل ۱ هر کسی می‌توانست بدون هزینه‌ای بلاک به زنجیره اضافه کند. با اثبات کار، یک معما‌ی محاسباتی معرفی می‌کنیم که باید قبل از افزودن بلاک به بلاک‌چین حل شود. تلاش برای حل این معما معمولاً با نام «استخراج» (mining) شناخته می‌شود.

با اثبات کار همچنین می‌توانیم (تقریباً) فاصله زمانی ورود بلاک‌ها به بلاک‌چین را کنترل کنیم. این کار با تغییر دشواری (difficulty) معما انجام می‌شود. اگر بلاک‌ها بیش از حد سریع استخراج شوند، دشواری معما افزایش می‌یابد و برعکس.

لازم به ذکر است که در این فصل هنوز تراکنش‌ها را معرفی نمی‌کنیم؛ یعنی در واقع هیچ انگیزه‌ای برای استخراج‌کنندگان جهت تولید بلاک وجود ندارد. معمولاً در ارزهای دیجیتال، استخراج‌کننده برای یافتن بلاک پاداش می‌گیرد، اما هنوز در بلاک‌چین ما این‌طور نیست.

کد کامل این فصل را می‌توانید اینجا پیدا کنید.

دشواری، nonce و معما‌ی اثبات کار

دو ویژگی جدید به ساختار بلاک اضافه می‌کنیم: difficulty و nonce. برای درک معنی آن‌ها ابتدا باید معما‌ی اثبات کار را معرفی کنیم.

معما‌ی اثبات کار این است که هش بلاکی پیدا کنیم که تعداد مشخصی صفر در ابتدای آن داشته باشد. ویژگی difficulty مشخص می‌کند که هش بلاک باید چند صفر ابتدایی داشته باشد تا بلاک معتبر باشد. صفرهای ابتدایی از فرمت دودویی هش بررسی می‌شوند.

در ادامه چند نمونه از هش‌های معتبر و نامعتبر برای دشواری‌های مختلف آورده شده است:

کدی که صحت هش را از نظر دشواری بررسی می‌کند:

typescript// بررسی اینکه هش با دشواری مطابقت دارد یا نه (تعداد صفرهای ابتدایی دودویی)
const hashMatchesDifficulty = (hash: string, difficulty: number): boolean => {
    const hashInBinary: string = hexToBinary(hash);              // تبدیل هش به دودویی
    const requiredPrefix: string = '0'.repeat(difficulty);       // پیشوند موردنیاز
    return hashInBinary.startsWith(requiredPrefix);
};

برای یافتن هشی که دشواری را برآورده کند، باید بتوانیم هش‌های متفاوتی برای همان محتوای بلاک محاسبه کنیم. این کار با تغییر پارامتر nonce انجام می‌شود. چون SHA256 یک تابع هش است، هر بار که چیزی در بلاک تغییر کند، هش کاملاً متفاوت می‌شود. «استخراج» در اصل فقط امتحان کردن nonceهای مختلف است تا هش بلاک با دشواری مطابقت کند.

حالا که difficulty و nonce اضافه شده‌اند، ساختار بلاک به این شکل است:

typescriptclass Block {

    public index: number;          // ارتفاع بلاک
    public hash: string;           // هش بلاک
    public previousHash: string;   // هش بلاک قبلی
    public timestamp: number;      // برچسب زمانی
    public data: string;           // داده بلاک
    public difficulty: number;     // دشواری: تعداد صفرهای ابتدایی موردنیاز
    public nonce: number;          // مقدار غیرس (nonce) برای یافتن هش معتبر

    constructor(index: number, hash: string, previousHash: string,
                timestamp: number, data: string, difficulty: number, nonce: number) {
        this.index = index;
        this.previousHash = previousHash;
        this.timestamp = timestamp;
        this.data = data;
        this.hash = hash;
        this.difficulty = difficulty;
        this.nonce = nonce;
    }
}

فراموش نکنیم که بلاک پیدایش (genesis) را هم به‌روزرسانی کنیم!

یافتن یک بلاک

همان‌طور که شرح داده شد، برای یافتن هش معتبر باید nonce را افزایش دهیم تا به هش معتبر برسیم. یافتن هش دلخواه کاملاً یک فرایند تصادفی است؛ فقط باید به‌اندازه کافی روی nonceها حلقه بزنیم تا هش دلخواه پیدا شود: 

typescript// استخراج: حلقه روی nonce تا یافتن هشی که با دشواری مطابقت دارد
const findBlock = (index: number, previousHash: string, timestamp: number, data: string, difficulty: number): Block => {
    let nonce = 0;
    while (true) {
        const hash: string = calculateHash(index, previousHash, timestamp, data, difficulty, nonce);
        if (hashMatchesDifficulty(hash, difficulty)) {
            // هش پیدا شد؛ بلاک معتبر ساخته می‌شود
            return new Block(index, hash, previousHash, timestamp, data, difficulty, nonce);
        }
        nonce++;
    }
};

وقتی بلاک پیدا شد، همان‌طور که در فصل ۱ بود، به شبکه پخش می‌شود.

اجماع روی دشواری

حالا ابزار یافتن و تأیید هش برای یک دشواری مشخص را داریم، اما دشواری چگونه تعیین می‌شود؟ باید راهی وجود داشته باشد که گره‌ها روی دشواری فعلی به توافق برسند. برای این کار قوانین جدیدی برای محاسبه دشواری فعلی شبکه معرفی می‌کنیم.

ثابت‌های جدید زیر را برای شبکه تعریف می‌کنیم:

  • BLOCK_GENERATION_INTERVAL، مشخص می‌کند که بلاک هر چند وقت یک‌بار باید یافت شود. (در بیت‌کوین این مقدار ۱۰ دقیقه است)
  • DIFFICULTY_ADJUSTMENT_INTERVAL، مشخص می‌کند که دشواری هر چند وقت یک‌بار باید با نرخ هش افزایش‌یافته یا کاهش‌یافته شبکه تطبیق یابد. (در بیت‌کوین این مقدار ۲۰۱۶ بلاک است)

فاصله تولید بلاک را ۱۰ ثانیه و فاصله تنظیم دشواری را ۱۰ بلاک قرار می‌دهیم. این ثابت‌ها در طول زمان تغییر نمی‌کنند و به‌صورت ثابت در کد قرار دارند. 

typescript// فاصله تولید بلاک (به ثانیه)
const BLOCK_GENERATION_INTERVAL: number = 10;

// فاصله تنظیم دشواری (به تعداد بلاک)
const DIFFICULTY_ADJUSTMENT_INTERVAL: number = 10;

حالا ابزار توافق روی دشواری هر بلاک را داریم. برای هر ۱۰ بلاکی که تولید می‌شود، بررسی می‌کنیم که زمان تولید آن بلاک‌ها بزرگ‌تر است یا کوچک‌تر از زمان مورد انتظار. زمان مورد انتظار به این شکل محاسبه می‌شود: BLOCK_GENERATION_INTERVAL * DIFFICULTY_ADJUSTMENT_INTERVAL. زمان مورد انتظار حالتی را نشان می‌دهد که نرخ هش دقیقاً با دشواری فعلی مطابقت دارد.

اگر زمان گرفته‌شده حداقل دو برابر بزرگ‌تر یا کوچک‌تر از زمان مورد انتظار باشد، دشواری را یک واحد کاهش یا افزایش می‌دهیم. تنظیم دشواری با کد زیر انجام می‌شود: 

typescript// محاسبه دشواری فعلی زنجیره
const getDifficulty = (aBlockchain: Block[]): number => {
    const latestBlock: Block = aBlockchain[blockchain.length - 1];  // آخرین بلاک
    // هر چند بلاک یک‌بار (طبق فاصله تنظیم) دشواری بازبینی می‌شود
    if (latestBlock.index % DIFFICULTY_ADJUSTMENT_INTERVAL === 0 && latestBlock.index !== 0) {
        return getAdjustedDifficulty(latestBlock, aBlockchain);
    } else {
        return latestBlock.difficulty;
    }
};

// محاسبه دشواری تنظیم‌شده بر اساس زمان سپری‌شده
const getAdjustedDifficulty = (latestBlock: Block, aBlockchain: Block[]) => {
    // بلاک مرجعِ تنظیم قبلی (۱۰ بلاک قبل)
    const prevAdjustmentBlock: Block = aBlockchain[blockchain.length - DIFFICULTY_ADJUSTMENT_INTERVAL];
    const timeExpected: number = BLOCK_GENERATION_INTERVAL * DIFFICULTY_ADJUSTMENT_INTERVAL; // زمان مورد انتظار
    const timeTaken: number = latestBlock.timestamp - prevAdjustmentBlock.timestamp;        // زمان واقعی
    if (timeTaken < timeExpected / 2) {
        // بلاک‌ها خیلی سریع یافت شده‌اند؛ دشواری را زیاد می‌کنیم
        return prevAdjustmentBlock.difficulty + 1;
    } else if (timeTaken > timeExpected * 2) {
        // بلاک‌ها خیلی کند یافت شده‌اند؛ دشواری را کم می‌کنیم
        return prevAdjustmentBlock.difficulty - 1;
    } else {
        return prevAdjustmentBlock.difficulty;
    }
};

اعتبارسنجی برچسب زمانی

در نسخه فصل ۱، برچسب زمانی نه نقشی داشت نه اعتبارسنجی؛ در واقع می‌توانست هر چیزی باشد که کلاینت تولید می‌کرد. حالا که تنظیم دشواری معرفی شده، این موضوع تغییر می‌کند، زیرا متغیر timeTaken (در قطعه کد قبلی) بر اساس برچسب‌های زمانی بلاک‌ها محاسبه می‌شود.

برای کاهش خطر حمله‌ای که در آن برچسب زمانی جعلی برای دستکاری دشواری وارد می‌شود، قوانین زیر معرفی می‌شوند:

  • یک بلاک معتبر است اگر برچسب زمانی آن حداکثر ۱ دقیقه در آینده از زمانی که ما درک می‌کنیم باشد
  • یک بلاک در زنجیره معتبر است اگر برچسب زمانی آن حداکثر ۱ دقیقه عقب‌تر از بلاک قبلی باشد
typescript// اعتبارسنجی برچسب زمانی بلاک جدید نسبت به بلاک قبلی و زمان فعلی
const isValidTimestamp = (newBlock: Block, previousBlock: Block): boolean => {
    return ( previousBlock.timestamp - 60 < newBlock.timestamp )

دشواری تجمعی (Cumulative difficulty)

در نسخه فصل ۱، همیشه «بلندترین» بلاک‌چین را معتبر انتخاب می‌کردیم. حالا که دشواری معرفی شده، این موضوع باید تغییر کند. از این پس زنجیره «صحیح» بلندترین زنجیره نیست، بلکه زنجیره‌ای است که بیشترین دشواری تجمعی را دارد. به عبارت دیگر، زنجیره صحیح زنجیره‌ای است که تولید آن به بیشترین منابع (= نرخ هش × زمان) نیاز داشته است.

برای به‌دست آوردن دشواری تجمعی یک زنجیره، برای هر بلاک 2^difficulty را محاسبه و مجموع همه این اعداد را می‌گیریم. باید از 2^difficulty استفاده کنیم، زیرا دشواری را به‌عنوان تعداد صفرهای ابتدایی هش در فرمت دودویی تعریف کرده‌ایم. مثلاً اگر دشواری‌های ۵ و ۱۱ را مقایسه کنیم، برای یافتن بلاک با دشواری دوم، به ۲^(11-5) = 2^6 برابر کار بیشتر نیاز است.

فقط دشواری بلاک اهمیت دارد، نه خود هش (به شرط معتبر بودن هش). مثلاً اگر دشواری ۴ باشد و هش بلاک 000000a34c… باشد (که هم‌زمان دشواری ۶ را هم برآورده می‌کند)، هنگام محاسبه دشواری تجمعی فقط دشواری ۴ در نظر گرفته می‌شود.

این ویژگی با نام «اجماع ناکاموتو» (Nakamoto consensus) نیز شناخته می‌شود و یکی از مهم‌ترین اختراعات ساتوشی هنگام طراحی بیت‌کوین بود. در صورت انشعاب (fork)، استخراج‌کنندگان باید تصمیم بگیرند منابع فعلی خود (= نرخ هش) را روی کدام زنجیره بگذارند. از آنجا که به نفع استخراج‌کنندگان است بلاکی تولید کنند که در بلاک‌چین قرار گیرد، در نهایت انگیزه می‌یابند که زنجیره یکسانی را انتخاب کنند.

جمع‌بندی

یک ویژگی مهم معما‌ی اثبات کار این است که حل آن دشوار اما بررسی آن آسان است. یافتن هش‌های SHA256 مشخص، مثال خوب و ساده‌ای از چنین مسئله‌ای است.

جنبه دشواری را پیاده‌سازی کردیم و حالا گره‌ها باید برای افزودن بلاک جدید به زنجیره «استخراج» کنند. در فصل بعد تراکنش‌ها را پیاده‌سازی می‌کنیم.

#3: تراکنش‌ها

مرور کلی

در این فصل مفهوم تراکنش‌ها را معرفی می‌کنیم. با این تغییر، در واقع پروژه خود را از یک بلاک‌چین «همه‌منظوره» به یک ارز دیجیتال تبدیل می‌کنیم. در نتیجه می‌توانیم سکه‌هایی به آدرس‌ها بفرستیم، به شرطی که بتوانیم اثبات کنیم در وهله اول مالک آن‌ها هستیم.

برای فعال‌سازی همه این‌ها، مفاهیم جدید زیادی باید معرفی شوند: رمزنگاری کلید عمومی، امضاها و ورودی‌ها و خروجی‌های تراکنش.

کد کامل این فصل را می‌توانید اینجا پیدا کنید.

رمزنگاری کلید عمومی و امضاها

در رمزنگاری کلید عمومی یک جفت کلید دارید: یک کلید خصوصی و یک کلید عمومی. کلید عمومی را می‌توان از کلید خصوصی استخراج کرد، اما کلید خصوصی را نمی‌توان از کلید عمومی استخراج کرد. کلید عمومی (همان‌طور که از نامش پیداست) به‌صورت امن به هر کسی قابل اشتراک‌گذاری است.

هر پیامی را می‌توان با کلید خصوصی برای ساخت یک امضا امضا کرد. با این امضا و کلید عمومی متناظر، هر کسی می‌تواند تأیید کند که امضا توسط کلید خصوصیِ هم‌خوانِ آن کلید عمومی تولید شده است.

برای رمزنگاری کلید عمومی از کتابخانه‌ای به نام elliptic استفاده می‌کنیم که از منحنی‌های بیضوی بهره می‌برد. (= ECDSA)

در مجموع، دو تابع رمزنگاری مختلف برای اهداف مختلف در ارز دیجیتال استفاده می‌شود:

  • تابع هش (SHA256) برای استخراج اثبات کار (هش همچنین برای حفظ یکپارچگی بلاک استفاده می‌شود)
  • رمزنگاری کلید عمومی (ECDSA) برای تراکنش‌ها (که در این فصل پیاده‌سازی خواهیم کرد)

کلیدهای خصوصی و عمومی (در ECDSA)

یک کلید خصوصی معتبر هر رشته ۳۲ بایتی تصادفی است، مثلاً 19f128debc1b9122da0635954488b208b829879cf13b3d6cac5d1260c0fd967c

یک کلید عمومی معتبر «04» است که به یک رشته ۶۴ بایتی الحاق شده است، مثلاً 04bfcab8722991ae774db48f934ca79cfb7dd991229153b9f732ba5334aafcd8e7266e47076996b55a14bf9913ee3145ce0cfc1372ada8ada74bd287450313534a

کلید عمومی را می‌توان از کلید خصوصی استخراج کرد. کلید عمومی به‌عنوان «گیرنده» (= آدرس) سکه‌ها در یک تراکنش استفاده خواهد شد.

مرور کلی تراکنش‌ها

قبل از نوشتن هر کدی، اجازه دهید مروری بر ساختار تراکنش‌ها داشته باشیم. تراکنش‌ها از دو مؤلفه تشکیل می‌شوند: ورودی‌ها (inputs) و خروجی‌ها (outputs). خروجی‌ها مشخص می‌کنند که سکه‌ها به کجا فرستاده می‌شوند و ورودی‌ها اثبات می‌کنند که سکه‌های فرستاده‌شده در وهله اول وجود دارند و متعلق به «فرستنده» هستند. ورودی‌ها همیشه به یک خروجی موجود (و هزینه‌نشده) ارجاع می‌دهند.

خروجی‌های تراکنش

خروجی تراکنش (txOut) از یک آدرس و مقدار سکه تشکیل شده است. آدرس یک کلید عمومی ECDSA است. یعنی کاربری که کلید خصوصیِ کلید عمومی ارجاع‌داده‌شده (= آدرس) را داشته باشد، می‌تواند به سکه‌ها دسترسی پیدا کند.

class TxOut {
    public address: string;   // آدرس گیرنده (کلید عمومی ECDSA)
    public amount: number;    // مقدار سکه

    constructor(address: string, amount: number) {
        this.address = address;
        this.amount = amount;
    }
}

ورودی‌های تراکنش

ورودی تراکنش (txIn) اطلاعات «از کجا» بودن سکه‌ها را فراهم می‌کند. هر txIn به یک خروجی قبلی ارجاع می‌دهد که سکه‌های آن با امضا «قفل‌گشایی» می‌شوند. این سکه‌های قفل‌گشایی‌شده حالا برای txOutها «در دسترس» هستند. امضا اثبات می‌کند که فقط کاربرِ دارای کلید خصوصیِ کلید عمومی ارجاع‌داده‌شده (= آدرس) می‌توانسته تراکنش را ساخته باشد. 

typescript// ورودی تراکنش: ارجاع به خروجی قبلی و امضای مالکیت
class TxIn {
    public txOutId: string;    // شناسه تراکنشی که خروجی در آن است
    public txOutIndex: number; // شاخص خروجی در آن تراکنش
    public signature: string;  // امضای دیجیتال (اثبات مالکیت)
}

لازم به ذکر است که txIn فقط امضا (که با کلید خصوصی ساخته شده) را شامل می‌شود، هرگز خود کلید خصوصی را. بلاک‌چین شامل کلیدهای عمومی و امضاهاست، هرگز کلیدهای خصوصی.

در مجموع می‌توان این‌طور در نظر گرفت که txInها سکه‌ها را قفل‌گشایی می‌کنند و txOutها سکه‌ها را دوباره «قفل» می‌کنند:

ساختار تراکنش

ساختار تراکنش خودش کاملاً ساده است، حالا که txInها و txOutها را تعریف کرده‌ایم:

typescript// ساختار تراکنش: شامل شناسه، ورودی‌ها و خروجی‌ها
class Transaction {
    public id: string;      // شناسه تراکنش (هش محتوا)
    public txIns: TxIn[];   // ورودی‌ها (منبع سکه‌ها)
    public txOuts: TxOut[]; // خروجی‌ها (مقصد سکه‌ها)
}

شناسه تراکنش

شناسه تراکنش با گرفتن هش از محتوای تراکنش محاسبه می‌شود. با این حال، امضاهای txInها در هش تراکنش شامل نمی‌شوند، زیرا امضاها بعداً به تراکنش اضافه می‌شوند. 

typescript// محاسبه شناسه تراکنش از محتوای ورودی‌ها و خروجی‌ها (بدون امضاها)
const getTransactionId = (transaction: Transaction): string => {
    // ترکیب محتوای ورودی‌ها: شناسه خروجی مرجع + شاخص خروجی
    const txInContent: string = transaction.txIns
        .map((txIn: TxIn) => txIn.txOutId + txIn.txOutIndex)
        .reduce((a, b) => a + b, '');

    // ترکیب محتوای خروجی‌ها: آدرس + مقدار
    const txOutContent: string = transaction.txOuts
        .map((txOut: TxOut) => txOut.address + txOut.amount)
        .reduce((a, b) => a + b, '');

    return CryptoJS.SHA256(txInContent + txOutContent).toString();
};

امضاهای تراکنش

مهم است که محتوای تراکنش پس از امضا شدن نتواند تغییر کند. چون تراکنش‌ها عمومی هستند، هر کسی می‌تواند به آن‌ها دسترسی یابد، حتی قبل از اینکه در بلاک‌چین قرار گیرند.

هنگام امضای ورودی‌های تراکنش، فقط txId امضا می‌شود. اگر هر یک از محتویات تراکنش اصلاح شود، txId باید تغییر کند و این تراکنش و امضا را نامعتبر می‌کند. 

typescript// امضای یک ورودی تراکنش با کلید خصوصی
const signTxIn = (transaction: Transaction, txInIndex: number,
                  privateKey: string, aUnspentTxOuts: UnspentTxOut[]): string => {
    const txIn: TxIn = transaction.txIns[txInIndex];
    const dataToSign = transaction.id;   // فقط شناسه تراکنش امضا می‌شود
    // خروجی هزینه‌نشده‌ای که این ورودی به آن ارجاع می‌دهد
    const referencedUnspentTxOut: UnspentTxOut = findUnspentTxOut(txIn.txOutId, txIn.txOutIndex, aUnspentTxOuts);
    const referencedAddress = referencedUnspentTxOut.address;
    // ساخت کلید خصوصی از رشته هگز و امضای داده
    const key = ec.keyFromPrivate(privateKey, 'hex');
    const signature: string = toHexString(key.sign(dataToSign).toDER());
    return signature;
};

بگذارید ببینیم اگر کسی بخواهد تراکنش را دستکاری کند چه اتفاقی می‌افتد:

  1. حمله‌کننده یک گره اجرا می‌کند و تراکنشی با محتوای «۱۰ سکه از آدرس AAA به BBB بفرست» با txId برابر 0x555.. دریافت می‌کند
  2. حمله‌کننده آدرس گیرنده را به CCC تغییر می‌دهد و آن را در شبکه جلو می‌فرستد. حالا محتوای تراکنش «۱۰ سکه از آدرس AAA به CCC بفرست» است
  3. اما چون آدرس گیرنده تغییر کرده، txId دیگر معتبر نیست. txId معتبر جدید 0x567... خواهد بود
  4. اگر txId به مقدار جدید تغییر کند، امضا معتبر نیست. امضا فقط با txId اصلی 0x555.. مطابقت دارد
  5. تراکنش دستکاری‌شده توسط گره‌های دیگر پذیرفته نمی‌شود، چون در هر صورت نامعتبر است

خروجی‌های تراکنش هزینه‌نشده (UTXO)

ورودی تراکنش همیشه باید به یک خروجی تراکنش هزینه‌نشده (uTxO) ارجاع دهد. در نتیجه، وقتی در بلاک‌چین سکه‌ای دارید، در واقع چیزی که دارید فهرستی از خروجی‌های تراکنش هزینه‌نشده است که کلید عمومی آن‌ها با کلید خصوصیِ شما مطابقت دارد.

از نظر اعتبارسنجی تراکنش، فقط با تمرکز بر فهرست خروجی‌های هزینه‌نشده می‌توانیم تشخیص دهیم تراکنش معتبر است یا نه. فهرست خروجی‌های هزینه‌نشده همیشه از بلاک‌چین فعلی قابل استخراج است. در این پیاده‌سازی، هنگام پردازش و افزودن تراکنش‌ها به بلاک‌چین، فهرست خروجی‌های هزینه‌نشده را به‌روزرسانی می‌کنیم.

ساختار داده یک خروجی تراکنش هزینه‌نشده به این شکل است:

typescript// خروجی تراکنش هزینه‌نشده (UTXO): سکه‌ای که هنوز خرج نشده است
class UnspentTxOut {
    public readonly txOutId: string;    // شناسه تراکنش مبدأ
    public readonly txOutIndex: number; // شاخص خروجی در آن تراکنش
    public readonly address: string;    // آدرس مالک
    public readonly amount: number;     // مقدار سکه

    constructor(txOutId: string, txOutIndex: number, address: string, amount: number) {
        this.txOutId = txOutId;
        this.txOutIndex = txOutIndex;
        this.address = address;
        this.amount = amount;
    }
}

ساختار داده آن‌ها در کل فقط یک فهرست است:

typescript// فهرست خروجی‌های هزینه‌نشده شبکه
let unspentTxOuts: UnspentTxOut[] = [];

به‌روزرسانی خروجی‌های تراکنش هزینه‌نشده

هر بار که بلاک جدیدی به زنجیره اضافه می‌شود، باید فهرست خروجی‌های هزینه‌نشده خود را به‌روزرسانی کنیم؛ زیرا تراکنش‌های جدید برخی خروجی‌های موجود را خرج می‌کنند و خروجی‌های هزینه‌نشده جدیدی معرفی می‌کنند.

برای این کار، ابتدا همه خروجی‌های هزینه‌نشده جدید (newUnspentTxOuts) را از بلاک جدید استخراج می‌کنیم: 

typescript    // استخراج خروجی‌های هزینه‌نشده جدید از تراکنش‌های بلاک
    const newUnspentTxOuts: UnspentTxOut[] = newTransactions
        .map((t) => {
            return t.txOuts.map((txOut, index) => new UnspentTxOut(t.id, index, txOut.address, txOut.amount));
        })
        .reduce((a, b) => a.concat(b), []);

همچنین باید بدانیم کدام خروجی‌ها توسط تراکنش‌های جدید بلاک مصرف شده‌اند (consumedTxOuts). این را با بررسی ورودی‌های تراکنش‌های جدید حل می‌کنیم: 

typescript    // پیدا کردن خروجی‌هایی که توسط ورودی‌های تراکنش‌های جدید مصرف شده‌اند
    const consumedTxOuts: UnspentTxOut[] = newTransactions
        .map((t) => t.txIns)
        .reduce((a, b) => a.concat(b), [])
        .map((txIn) => new UnspentTxOut(txIn.txOutId, txIn.txOutIndex, '', 0));

در نهایت می‌توانیم فهرست جدید خروجی‌های هزینه‌نشده را با حذف consumedTxOuts و افزودن newUnspentTxOuts به خروجی‌های موجود تولید کنیم: 

typescript    // حذف خروجی‌های مصرف‌شده و افزودن خروجی‌های جدید
    const resultingUnspentTxOuts = aUnspentTxOuts
        .filter(((uTxO) => !findUnspentTxOut(uTxO.txOutId, uTxO.txOutIndex, consumedTxOuts)))
        .concat(newUnspentTxOuts);

کد و عملکرد شرح‌داده‌شده در متد updateUnspentTxOuts قرار دارد. لازم به ذکر است که این متد فقط بعد از اعتبارسنجی تراکنش‌های بلاک (و خود بلاک) فراخوانی می‌شود.

ساختار صحیح تراکنش

شناسه تراکنش معتبر

شناسه تراکنش باید به‌درستی محاسبه شده باشد:

typescript    // بررسی صحت شناسه تراکنش
    if (getTransactionId(transaction) !== transaction.id) {

ورودی‌های معتبر

امضاهای موجود در txInها باید معتبر باشند و خروجی‌های ارجاع‌داده‌شده نباید قبلاً خرج شده باشند:

typescript// اعتبارسنجی یک ورودی تراکنش: پیدا کردن UTXO مرجع و بررسی امضا
const validateTxIn = (txIn: TxIn, transaction: Transaction, aUnspentTxOuts: UnspentTxOut[]): boolean => {
    // یافتن خروجی هزینه‌نشده‌ای که این ورودی به آن ارجاع می‌دهد
    const referencedUTxOut: UnspentTxOut =
        aUnspentTxOuts.find((uTxO) => uTxO.txOutId === txIn.txOutId && uTxO.txOutId === txIn.txOutId);
    if (referencedUTxOut == null) {
        console.log('referenced txOut not found: ' + JSON.stringify(txIn));  // خروجی مرجع یافت نشد
        return false;
    }
    const address = referencedUTxOut.address;

    // بررسی امضا با کلید عمومی (آدرس) مالک
    const key = ec.keyFromPublic(address, 'hex');
    return key.verify(transaction.id, txIn.signature);
};

مقادیر معتبر خروجی‌ها

مجموع مقادیر مشخص‌شده در خروجی‌ها باید با مجموع مقادیر مشخص‌شده در ورودی‌ها برابر باشد. اگر به خروجی‌ای ارجاع دهید که ۵۰ سکه دارد، مجموع مقادیر خروجی‌های جدید هم باید ۵۰ سکه باشد: 

typescript    // مجموع مقادیر ورودی‌ها
    const totalTxInValues: number = transaction.txIns
        .map((txIn) => getTxInAmount(txIn, aUnspentTxOuts))
        .reduce((a, b) => (a + b), 0);

    const totalTxOutValues: number = transaction.txOuts
        .map((txOut) => txOut.amount)
        .reduce((a, b) => (a + b), 0);

    if (totalTxOutValues !== totalTxInValues) {

        return false;
    }

تراکنش کوین‌بیس (Coinbase)

ورودی‌های تراکنش همیشه باید به خروجی‌های هزینه‌نشده ارجاع دهند، اما سکه‌های اولیه از کجا وارد بلاک‌چین می‌شوند؟ برای حل این مسئله، نوع خاصی از تراکنش معرفی می‌شود: تراکنش کوین‌بیس.

تراکنش کوین‌بیس فقط یک خروجی دارد و هیچ ورودی‌ای. یعنی تراکنش کوین‌بیس سکه‌های جدیدی وارد گردش می‌کند. مقدار خروجی کوین‌بیس را ۵۰ سکه تعیین می‌کنیم: 

typescript// مقدار پاداش استخراج هر بلاک
const COINBASE_AMOUNT: number = 50;

تراکنش کوین‌بیس همیشه اولین تراکنش بلاک است و توسط استخراج‌کننده بلاک اضافه می‌شود. پاداش کوین‌بیس به‌عنوان انگیزه برای استخراج‌کنندگان عمل می‌کند: اگر بلاک را پیدا کنید، می‌توانید ۵۰ سکه جمع کنید.

ارتفاع بلاک را به ورودی تراکنش کوین‌بیس اضافه می‌کنیم تا اطمینان حاصل شود هر تراکنش کوین‌بیس یک txId یکتا دارد. بدون این قانون، مثلاً تراکنش کوین‌بیسِ «به آدرس 0xabc ۵۰ سکه بده» همیشه همان txId را داشت.

اعتبارسنجی تراکنش کوین‌بیس کمی با اعتبارسنجی تراکنش «عادی» متفاوت است:

typescript// اعتبارسنجی تراکنش کوین‌بیس (تراکنش پاداش استخراج)
const validateCoinbaseTx = (transaction: Transaction, blockIndex: number): boolean => {
    // شناسه تراکنش باید معتبر باشد
    if (getTransactionId(transaction) !== transaction.id) {
        console.log('invalid coinbase tx id: ' + transaction.id);
        return false;
    }
    // تراکنش کوین‌بیس باید دقیقاً یک ورودی داشته باشد
    if (transaction.txIns.length !== 1) {
        console.log('one txIn must be specified in the coinbase transaction');
        return;
    }
    // شاخص ورودی کوین‌بیس باید برابر ارتفاع بلاک باشد (تا txId یکتا شود)
    if (transaction.txIns[0].txOutIndex !== blockIndex) {
        console.log('the txIn index in coinbase tx must be the block height');
        return false;
    }
    // تراکنش کوین‌بیس باید دقیقاً یک خروجی داشته باشد
    if (transaction.txOuts.length !== 1) {
        console.log('invalid number of txOuts in coinbase transaction');
        return false;
    }
    // مقدار خروجی باید دقیقاً برابر پاداش کوین‌بیس باشد
    if (transaction.txOuts[0].amount != COINBASE_AMOUNT) {
        console.log('invalid coinbase amount in coinbase transaction');
        return false;
    }
    return true;
};

جمع‌بندی

مفهوم تراکنش‌ها را به بلاک‌چین اضافه کردیم. ایده پایه‌ای کاملاً ساده است: در ورودی‌های تراکنش به خروجی‌های هزینه‌نشده ارجاع می‌دهیم و از امضاها برای نشان دادن معتبر بودن بخش قفل‌گشایی استفاده می‌کنیم. سپس از خروجی‌ها برای «قفل دوباره» سکه‌ها روی آدرس گیرنده استفاده می‌کنیم.

با این حال، ساخت تراکنش‌ها هنوز بسیار دشوار است: باید به‌صورت دستی ورودی‌ها و خروجی‌های تراکنش را بسازیم و با کلید خصوصی امضا کنیم. این موضوع وقتی در فصل بعد کیف پول را معرفی کنیم تغییر می‌کند.

هنوز رله تراکنش (relaying) هم وجود ندارد: برای افزودن تراکنش به بلاک‌چین، باید خودتان آن را استخراج کنید. این هم دلیلی است که هنوز مفهوم کارمزد تراکنش (transaction fee) را معرفی نکرده‌ایم.

کد کامل این فصل را می‌توانید اینجا بیابید.

#4: کیف پول (Wallet)

مرور کلی

هدف کیف پول ایجاد یک رابط انتزاعی‌تر برای کاربر نهایی است.

کاربر نهایی باید بتواند:

  • یک کیف پول جدید بسازد (= در اینجا یک کلید خصوصی)
  • موجودی کیف پول خود را مشاهده کند
  • به آدرس‌های دیگر سکه بفرستد

همه موارد بالا باید طوری کار کنند که کاربر نهایی نیازی به درک نحوه کار txInها یا txOutها نداشته باشد. دقیقاً مثل بیت‌کوین: سکه‌ها را به آدرس‌ها می‌فرستید و آدرس خودتان را منتشر می‌کنید تا دیگران بتوانند برای شما سکه بفرستند.

کد کامل این فصل را می‌توانید اینجا پیدا کنید.

تولید و ذخیره کلید خصوصی

در این آموزش از ساده‌ترین روش ممکن برای مدیریت تولید و ذخیره کیف پول استفاده می‌کنیم: یک کلید خصوصی بدون رمزنگاری در فایل node/wallet/private_key تولید می‌کنیم. 

typescript// مسیر فایل ذخیره کلید خصوصی
const privateKeyLocation = 'node/wallet/private_key';

// تولید یک کلید خصوصی تصادفی جدید
const generatePrivatekey = (): string => {
    const keyPair = EC.genKeyPair();
    const privateKey = keyPair.getPrivate();
    return privateKey.toString(16);
};

// راه‌اندازی کیف پول
const initWallet = () => {
    // اجازه ندهیم کلید خصوصی موجود بازنویسی شود
    if (existsSync(privateKeyLocation)) {
        return;
    }
    const newPrivateKey = generatePrivatekey();

    // ذخیره کلید خصوصی جدید در فایل
    writeFileSync(privateKeyLocation, newPrivateKey);
    console.log('new wallet with private key created');
};

و همان‌طور که گفته شد، کلید عمومی (= آدرس) از کلید خصوصی قابل محاسبه است:

typescript// استخراج کلید عمومی (آدرس) از کلید خصوصی کیف پول
const getPublicFromWallet = (): string => {
    const privateKey = getPrivateFromWallet();
    const key = EC.keyFromPrivate(privateKey, 'hex');
    return key.getPublic().encode('hex');
};

لازم به ذکر است که ذخیره کلید خصوصی به‌صورت بدون رمزنگاری بسیار ناامن است. این کار را فقط برای ساده نگه داشتن کارها انجام می‌دهیم. همچنین کیف پول فقط از یک تک کلید خصوصی پشتیبانی می‌کند، بنابراین برای گرفتن آدرس عمومی جدید باید کیف پول جدیدی تولید کنید.

هشدار: در دنیای واقعی هرگز کلید خصوصی را رمزنگاری‌نشده ذخیره نکنید؛ هر کسی به آن دسترسی داشته باشد، به تمام سکه‌های شما دسترسی دارد.

موجودی کیف پول

یادآوری از فصل قبل: وقتی در بلاک‌چین سکه‌ای دارید، در واقع چیزی که دارید فهرستی از خروجی‌های تراکنش هزینه‌نشده است که کلید عمومی آن‌ها با کلید خصوصیِ شما مطابقت دارد.

یعنی محاسبه موجودی یک آدرس بسیار ساده است: فقط کافی است مجموع همه خروجی‌های هزینه‌نشده‌ای را بگیرید که «مالک» آن‌ها این آدرس است: 

typescript// محاسبه موجودی یک آدرس: مجموع سکه‌های تمام UTXOهای متعلق به آن آدرس
const getBalance = (address: string, unspentTxOuts: UnspentTxOut[]): number => {
    return _(unspentTxOuts)
        .filter((uTxO: UnspentTxOut) => uTxO.address === address)
        .map((uTxO: UnspentTxOut) => uTxO.amount)
        .sum();
};

همان‌طور که در کد دیده می‌شود، برای پرس‌وجوی موجودی یک آدرس نیازی به کلید خصوصی نیست. این یعنی هر کسی می‌تواند موجودی هر آدرسی را محاسبه کند.

تولید تراکنش‌ها

هنگام ارسال سکه، کاربر باید بتواند مفاهیم ورودی و خروجی تراکنش را نادیده بگیرد. اما اگر کاربر A موجودی ۵۰ سکه داشته باشد که در یک خروجی تراکنش واحد است و بخواهد ۱۰ سکه به کاربر B بفرستد، چه باید کرد؟

در این حالت، راه‌حل این است که ۱۰ سکه به آدرس کاربر B و ۴۰ سکه برگشت به خود کاربر A فرستاده شود. خروجی تراکنش همیشه باید کامل خرج شود، بنابراین بخش «تقسیم» باید هنگام تخصیص سکه‌ها به خروجی‌های جدید انجام شود. این حالت ساده در تصویر زیر نشان داده شده است (txInها نمایش داده نشده‌اند):

یک سناریوی تراکنش کمی پیچیده‌تر را بررسی کنیم:

  1. کاربر C در ابتدا ۰ سکه دارد
  2. کاربر C سه تراکنش به‌ارزش ۱۰، ۲۰ و ۳۰ سکه دریافت می‌کند
  3. کاربر C می‌خواهد ۵۵ سکه به کاربر D بفرستد. تراکنش چگونه خواهد بود؟

در این حالت هر سه خروجی باید استفاده شوند و خروجی‌ها باید مقادیر ۵۵ سکه به کاربر D و ۵ سکه برگشت به کاربر C را داشته باشند.

منطق شرح‌داده‌شده را به کد تبدیل می‌کنیم. ابتدا ورودی‌های تراکنش را می‌سازیم.

برای این کار روی خروجی‌های هزینه‌نشده خود حلقه می‌زنیم تا مجموع این خروجی‌ها بزرگ‌تر یا مساوی مقداری شود که می‌خواهیم بفرستیم: 

typescript// یافتن خروجی‌های هزینه‌نشده لازم برای یک مقدار مشخص
const findTxOutsForAmount = (amount: number, myUnspentTxOuts: UnspentTxOut[]) => {
    let currentAmount = 0;                 // مقدار جمع‌شده تاکنون
    const includedUnspentTxOuts = [];      // خروجی‌های انتخابی
    for (const myUnspentTxOut of myUnspentTxOuts) {
        includedUnspentTxOuts.push(myUnspentTxOut);
        currentAmount = currentAmount + myUnspentTxOut.amount;
        if (currentAmount >= amount) {     // به مقدار کافی رسیدیم
            const leftOverAmount = currentAmount - amount;   // مبلغ باقی‌مانده (برگشت به خودمان)
            return {includedUnspentTxOuts, leftOverAmount}
        }
    }
    throw Error('not enough coins to send transaction');  // سکه کافی برای ارسال تراکنش نیست
};

همان‌طور که نشان داده شد، leftOverAmount را هم محاسبه می‌کنیم؛ مقداری که برگشت به آدرس خودمان می‌فرستیم.

حالا که فهرست خروجی‌های هزینه‌نشده را داریم، می‌توانیم ورودی‌های تراکنش را بسازیم:

typescript// تبدیل یک UTXO به ورودی بدون امضا

    const txIn: TxIn = new TxIn();
    txIn.txOutId = unspentTxOut.txOutId;
    txIn.txOutIndex = unspentTxOut.txOutIndex;
    return txIn;
};
// انتخاب خروجی‌های لازم و ساخت ورودی‌های بدون امضا
const {includedUnspentTxOuts, leftOverAmount} = findTxOutsForAmount(amount, myUnspentTxouts);
const unsignedTxIns: TxIn[] = includedUnspentTxOuts.map(toUnsignedTxIn);

سپس دو خروجی تراکنش ساخته می‌شود: یک خروجی برای گیرنده سکه‌ها و یک خروجی برای leftOverAmount. اگر ورودی‌ها دقیقاً مقدار موردنظر را داشته باشند (یعنی leftOverAmount صفر باشد)، تراکنش «برگشتی» را نمی‌سازیم: 

typescript// ساخت خروجی‌های تراکنش: یکی برای گیرنده و یکی (در صورت لزوم) برای برگشت
const createTxOuts = (receiverAddress:string, myAddress:string, amount, leftOverAmount: number) => {
    const txOut1: TxOut = new TxOut(receiverAddress, amount);   // خروجی گیرنده
    if (leftOverAmount === 0) {
        return [txOut1]
    } else {
        // خروجی برگشت به آدرس خودمان
        const leftOverTx = new TxOut(myAddress, leftOverAmount);
        return [txOut1, leftOverTx];
    }
};

در نهایت شناسه تراکنش را محاسبه و ورودی‌ها را امضا می‌کنیم:

typescript    const tx: Transaction = new Transaction();
    tx.txIns = unsignedTxIns;                              // ورودی‌های بدون امضا
    tx.txOuts = createTxOuts(receiverAddress, myAddress, amount, leftOverAmount); // خروجی‌ها
    tx.id = getTransactionId(tx);                          // محاسبه شناسه تراکنش

    // امضای همه ورودی‌ها با کلید خصوصی
    tx.txIns = tx.txIns.map((txIn: TxIn, index: number) => {
        txIn.signature = signTxIn(tx, index, privateKey, unspentTxOuts);

#5: رله تراکنش (Transaction relaying)

مرور کلی

در این فصل رله (بازپخش) تراکنش‌هایی را پیاده‌سازی می‌کنیم که هنوز در بلاک‌چین قرار نگرفته‌اند. در بیت‌کوین به این تراکنش‌ها «تراکنش‌های تأییدنشده» (unconfirmed transactions) نیز گفته می‌شود. معمولاً وقتی کسی می‌خواهد تراکنشی را در بلاک‌چین قرار دهد (= سکه‌ای به آدرسی بفرستد)، تراکنش را به شبکه پخش می‌کند و امیدوار است برخی گره‌ها تراکنش را استخراج کرده و وارد بلاک‌چین کنند.

این قابلیت برای یک ارز دیجیتال کارا بسیار مهم است، زیرا یعنی برای قرار دادن تراکنش در بلاک‌چین لازم نیست خودتان بلاک استخراج کنید.

در نتیجه، گره‌ها هنگام ارتباط با یکدیگر حالا دو نوع داده را به اشتراک می‌گذارند:

  • وضعیت بلاک‌چین (= بلاک‌ها و تراکنش‌های قرارگرفته‌شده در بلاک‌چین)
  • تراکنش‌های تأییدنشده (= تراکنش‌هایی که هنوز در بلاک‌چین قرار نگرفته‌اند)

کد کامل این فصل را می‌توانید اینجا پیدا کنید.

استخر تراکنش (Transaction pool)

تراکنش‌های تأییدنشده خود را در موجودیت جدیدی به نام «استخر تراکنش» ذخیره می‌کنیم (در بیت‌کوین به آن «مِم‌پول» یا mempool می‌گویند). استخر تراکنش ساختاری است که شامل همه «تراکنش‌های تأییدنشده‌ای» است که گره ما از آن‌ها خبر دارد. در این پیاده‌سازی ساده فقط از یک فهرست استفاده می‌کنیم: 

typescript// استخر تراکنش: تراکنش‌های تأییدنشده (هنوز در بلاک‌چین قرار نگرفته‌اند)
let transactionPool: Transaction[] = [];

همچنین یک endpoint جدید به گره خود اضافه می‌کنیم: POST /sendTransaction. این متد بر اساس قابلیت‌های کیف پول موجود، تراکنشی در استخر تراکنش محلی می‌سازد. از این پس این متد را به‌عنوان رابط «ترجیحی» هنگام قرار دادن تراکنش جدید در بلاک‌چین استفاده می‌کنیم. 

typescript    app.post('/sendTransaction', (req, res) => {
        ...
    })

تراکنش را دقیقاً مثل فصل ۴ می‌سازیم، فقط به‌جای تلاش فوری برای استخراج بلاک، تراکنش ساخته‌شده را به استخر اضافه می‌کنیم: 

typescript// ساخت تراکنش و افزودن آن به استخر تراکنش (به‌جای استخراج فوری)
const sendTransaction = (address: string, amount: number): Transaction => {
    // ایجاد تراکنش با کلید خصوصی کیف پول
    const tx: Transaction = createTransaction(address, amount, getPrivateFromWallet(), getUnspentTxOuts(), getTransactionPool());
    // افزودن تراکنش به استخر
    addToTransactionPool(tx, getUnspentTxOuts());
    return tx;
};

پخش (Broadcasting)

کل هدف تراکنش‌های تأییدنشده این است که در سراسر شبکه پخش شوند و در نهایت برخی گره‌ها تراکنش را استخراج کرده و وارد بلاک‌چین کنند. برای این کار قوانین ساده زیر را برای شبکه‌سازی تراکنش‌های تأییدنشده معرفی می‌کنیم:

  • وقتی گره‌ای تراکنش تأییدنشده‌ای دریافت می‌کند که قبلاً ندیده است، کل استخر تراکنش را به همه هم‌تایان پخش می‌کند
  • وقتی گره‌ای ابتدا به گره دیگری متصل می‌شود، استخر تراکنش آن گره را پرس‌وجو می‌کند

دو MessageType جدید برای این منظور اضافه می‌کنیم: QUERY_TRANSACTION_POOL و RESPONSE_TRANSACTION_POOL. شمارنده MessageType حالا به این شکل است: 

typescript// انواع پیام‌های شبکه بین گره‌ها
enum MessageType {
    QUERY_LATEST = 0,             // پرس‌وجوی آخرین بلاک
    QUERY_ALL = 1,                // پرس‌وجوی کل بلاک‌چین
    RESPONSE_BLOCKCHAIN = 2,      // ارسال بلاک‌چین
    QUERY_TRANSACTION_POOL = 3,   // پرس‌وجوی استخر تراکنش
    RESPONSE_TRANSACTION_POOL = 4 // ارسال استخر تراکنش
}

پیام‌های استخر تراکنش به شکل زیر ساخته می‌شوند:

برای پیاده‌سازی منطق پخش تراکنش شرح‌داده‌شده، کدی برای مدیریت نوع پیام MessageType.RESPONSE_TRANSACTION_POOL اضافه می‌کنیم. هر زمان تراکنش‌های تأییدنشده‌ای دریافت می‌کنیم، سعی می‌کنیم آن‌ها را به استخر تراکنش خود اضافه کنیم. اگر بتوانیم تراکنشی را به استخر اضافه کنیم، یعنی تراکنش معتبر است و گره ما قبلاً آن را ندیده است. در این حالت استخر تراکنش خودمان را به همه هم‌تایان پخش می‌کنیم:

اعتبارسنجی تراکنش‌های تأییدنشده دریافتی

چون هم‌تایان می‌توانند هر نوع تراکنشی برای ما بفرستند، باید تراکنش‌ها را قبل از افزودن به استخر تراکنش اعتبارسنجی کنیم. همه قوانین اعتبارسنجی تراکنشِ موجود اعمال می‌شوند؛ برای مثال تراکنش باید درست قالب‌بندی شده باشد و ورودی‌ها، خروجی‌ها و امضاهای تراکنش باید درست باشند.

علاوه بر قوانین موجود، یک قانون جدید اضافه می‌کنیم: اگر هر یک از ورودی‌های تراکنش قبلاً در استخر تراکنش موجود پیدا شود، نمی‌توان تراکنش را به استخر اضافه کرد. این قانون جدید در کد زیر تجسم یافته است: 

typescript// بررسی اینکه تراکنش برای استخر قابل افزودن است یا نه
const isValidTxForPool = (tx: Transaction, aTtransactionPool: Transaction[]): boolean => {
    // جمع‌آوری همه ورودی‌های تراکنش‌های موجود در استخر
    const txPoolIns: TxIn[] = getTxPoolIns(aTtransactionPool);

    // بررسی اینکه ورودی مشخصی از قبل در استخر وجود دارد یا نه
    const containsTxIn = (txIns: TxIn[], txIn: TxIn) => {
        return _.find(txPoolIns, (txPoolIn => {
            return txIn.txOutIndex === txPoolIn.txOutIndex && txIn.txOutId === txPoolIn.txOutId;
        }))
    };

    // اگر هر یک از ورودی‌های تراکنش جدید قبلاً در استخر باشد، نامعتبر است
    for (const txIn of tx.txIns) {
        if (containsTxIn(txPoolIns, txIn)) {
            console.log('txIn already found in the txPool');  // این ورودی از قبل در استخر است
            return false;
        }
    }
    return true;
};

راه صریحی برای حذف تراکنش از استخر تراکنش وجود ندارد. با این حال، استخر تراکنش هر بار که بلاک جدیدی یافت می‌شود به‌روزرسانی خواهد شد.

از استخر تراکنش تا بلاک‌چین

حالا راهی پیاده‌سازی کنیم که تراکنش تأییدنشده از استخر تراکنش محلی به بلاکی که توسط همان گره استخراج می‌شود برسد. این کار ساده است: وقتی گره‌ای شروع به استخراج بلاک می‌کند، تراکنش‌های استخر تراکنش را در بلاک کاندیدای جدید قرار می‌دهد: 

typescript// تولید بلاک بعدی شامل تراکنش کوین‌بیس + همه تراکنش‌های استخر
const generateNextBlock = () => {
    // تراکنش کوین‌بیس (پاداش) برای آدرس خودمان
    const coinbaseTx: Transaction = getCoinbaseTransaction(getPublicFromWallet(), getLatestBlock().index + 1);
    // داده بلاک: کوین‌بیس + همه تراکنش‌های استخر
    const blockData: Transaction[] = [coinbaseTx].concat(getTransactionPool());
    return generateRawNextBlock(blockData);

چون تراکنش‌ها قبل از افزودن به استخر اعتبارسنجی شده‌اند، در این مرحله اعتبارسنجی دیگری انجام نمی‌دهیم.

به‌روزرسانی استخر تراکنش

هر بار که بلاک جدیدی با تراکنش‌هایش استخراج و به بلاک‌چین اضافه می‌شود، باید استخر تراکنش را دوباره اعتبارسنجی کنیم. ممکن است بلاک جدید شامل تراکنش‌هایی باشد که برخی تراکنش‌های استخر را نامعتبر می‌کنند. این اتفاق مثلاً در این موارد رخ می‌دهد:

  • تراکنشی که در استخر بود استخراج شد (توسط خود گره یا گره دیگری)
  • خروجی هزینه‌نشده‌ای که در تراکنش تأییدنشده به آن ارجاع شده بود، توسط تراکنش دیگری خرج شد

استخر تراکنش با کد زیر به‌روزرسانی می‌شود:

typescript// حذف تراکنش‌های نامعتبر از استخر پس از استخراج بلاک جدید
const updateTransactionPool = (unspentTxOuts: UnspentTxOut[]) => {
    const invalidTxs = [];   // تراکنش‌های نامعتبر
    for (const tx of transactionPool) {
        for (const txIn of tx.txIns) {
            // اگر ورودی تراکنش دیگر UTXO مرجع ندارد، تراکنش نامعتبر است
            if (!hasTxIn(txIn, unspentTxOuts)) {
                invalidTxs.push(tx);
                break;
            }
        }
    }
    if (invalidTxs.length > 0) {
        console.log('removing the following transactions from txPool: %s', JSON.stringify(invalidTxs));
        // حذف تراکنش‌های نامعتبر از استخر
        transactionPool = _.without(transactionPool, ...invalidTxs)
    }
};

همان‌طور که دیده می‌شود، برای تصمیم‌گیری درباره حذف یک تراکنش از استخر، فقط به خروجی‌های هزینه‌نشده فعلی نیاز داریم.

جمع‌بندی

حالا می‌توانیم تراکنش‌ها را بدون اینکه واقعاً خودمان بلاک استخراج کنیم، وارد بلاک‌چین کنیم. با این حال هنوز انگیزه‌ای برای گره‌ها جهت قرار دادن تراکنش دریافتی در بلاک وجود ندارد، زیرا مفهوم کارمزد تراکنش را پیاده‌سازی نکرده‌ایم.

در فصل بعد یک رابط کاربری برای کیف پول و یک مرورگر ساده بلاک‌چین می‌سازیم.

#6: رابط کاربری کیف پول و مرورگر بلاک‌چین

مرور کلی

در این فصل برای کیف پول یک رابط کاربری (UI) اضافه می‌کنیم و یک مرورگر بلاک‌چین برای بلاک‌چین خودمان می‌سازیم. گره ما از قبل قابلیت‌هایش را با endpoints های HTTP در معرض دید قرار می‌دهد، بنابراین یک صفحه وب می‌سازیم که به آن endpoints ها درخواست می‌فرستد و نتایج را نمایش می‌دهد.

برای رسیدن به همه این‌ها، باید چند endpoint و منطق اضافی به گره اضافه کنیم، مثلاً:

  • پرس‌وجوی اطلاعات درباره بلاک‌ها و تراکنش‌ها
  • پرس‌وجوی اطلاعات درباره یک آدرس خاص

کد کامل این فصل را می‌توانید اینجا و بخش UI را اینجا پیدا کنید.

Endpoints جدید

یک endpoint اضافه می‌کنیم که کاربر از طریق آن می‌تواند در صورت دانستن هش، یک بلاک خاص را پرس‌وجو کند:

typescript    // دریافت بلاک با هش مشخص
    app.get('/block/:hash', (req, res) => {
        const block = _.find(getBlockchain(), {'hash' : req.params.hash});
        res.send(block);
    });

همین کار برای پرس‌وجوی یک تراکنش خاص:

typescript    // دریافت تراکنش با شناسه مشخص
    app.get('/transaction/:id', (req, res) => {
        const tx = _(getBlockchain())
            .map((blocks) => blocks.data)   // استخراج داده همه بلاک‌ها
            .flatten()                       // تبدیل به لیست تک‌بعدی از تراکنش‌ها
            .find({'id': req.params.id});    // پیدا کردن تراکنش با شناسه خواسته‌شده
        res.send(tx);
    });

همچنین می‌خواهیم اطلاعات یک آدرس خاص را نمایش دهیم. فعلاً فهرست خروجی‌های هزینه‌نشده آن آدرس را برمی‌گردانیم، چون از این اطلاعات می‌توانیم مثلاً موجودی کل آن آدرس را محاسبه کنیم: 

typescript    // دریافت اطلاعات یک آدرس: فهرست خروجی‌های هزینه‌نشده آن
    app.get('/address/:address', (req, res) => {
        const unspentTxOuts: UnspentTxOut[] =
            _.filter(getUnspentTxOuts(), (uTxO) => uTxO.address === req.params.address)
        res.send({'unspentTxOuts': unspentTxOuts});
    });

همچنین می‌توانستیم اطلاعات خروجی‌های هزینه‌شده یک آدرس را هم اضافه کنیم تا تاریخچه کامل یک آدرس نمایش داده شود.

فناوری‌های فرانت‌اند

برای پیاده‌سازی بخش‌های UI کیف پول و مرورگر بلاک‌چین از Vue.js استفاده می‌کنیم. چون این آموزش درباره توسعه فرانت‌اند نیست، بخش فرانت‌اند را از نظر کد مرور نمی‌کنیم. مخزن کد UI را می‌توانید اینجا پیدا کنید.

مرورگر بلاک‌چین

مرورگر بلاک‌چین وب‌سایتی است که برای نمایش وضعیت بلاک‌چین استفاده می‌شود. مورد استفاده معمول یک مرورگر بلاک‌چین، بررسی آسان موجودی یک آدرس مشخص یا تأیید اینکه یک تراکنش مشخص در بلاک‌چین قرار گرفته است، می‌باشد.

در مورد ما فقط به گره درخواست HTTP می‌فرستیم و پاسخ‌ها را به‌شکلی معنادار نمایش می‌دهیم. ما هرگز درخواستی نمی‌فرستیم که وضعیت بلاک‌چین را تغییر دهد، بنابراین ساختن مرورگر بلاک‌چین تماماً درباره نمایش معنادار اطلاعاتی است که گره فراهم می‌کند.

جمع‌بندی دوره

در این مجموعه، یک ارز دیجیتال ساده اما کامل از صفر ساختیم: بلاک‌چین با بلاک پیدایش و اعتبارسنجی زنجیره (فصل ۱)، الگوریتم اثبات کار و تنظیم دشواری (فصل ۲)، تراکنش‌ها با امضای دیجیتال و UTXO (فصل ۳)، کیف پول (فصل ۴)، رله تراکنش و استخر تراکنش (فصل ۵) و در نهایت رابط کاربری و مرورگر بلاک‌چین (فصل ۶).

گام بعدی برای علاقه‌مندان: می‌توانید مفهوم کارمزد تراکنش، کشف خودکار هم‌تایان (peer discovery) و ذخیره‌سازی ماندگار بلاک‌چین را به‌عنوان تمرین به این پروژه اضافه کنید؛ این‌ها گام‌های طبیعی برای نزدیک شدن به یک پیاده‌سازی واقعی‌تر هستند.

نگاه کلی به کد کامل گره (main.ts)

برای جمع‌بندی، کد کامل فایل src/main.ts نسخه نهایی (فصل ۶) را — که همه endpoints های آموزش‌داده‌شده در فصل‌های ۱ تا ۶ را در یک‌جا به هم متصل می‌کند — با کامنت فارسی می‌بینید. این کد از ریپازیتوری رسمی پروژه گرفته شده است: 

typescript// import های کتابخانه‌های عمومی
import * as  bodyParser from 'body-parser';
import * as express from 'express';
import * as _ from 'lodash';
// import های ماژول‌های داخلی پروژه
import {
    Block, generateNextBlock, generatenextBlockWithTransaction, generateRawNextBlock, getAccountBalance,
    getBlockchain, getMyUnspentTransactionOutputs, getUnspentTxOuts, sendTransaction
} from './blockchain';
import {connectToPeers, getSockets, initP2PServer} from './p2p';
import {UnspentTxOut} from './transaction';
import {getTransactionPool} from './transactionPool';
import {getPublicFromWallet, initWallet} from './wallet';

// پورت‌ها از متغیر محیطی خوانده می‌شوند یا پیش‌فرض می‌گیرند
const httpPort: number = parseInt(process.env.HTTP_PORT) || 3001;
const p2pPort: number = parseInt(process.env.P2P_PORT) || 6001;

// راه‌اندازی سرور HTTP برای کنترل گره
const initHttpServer = (myHttpPort: number) => {
    const app = express();
    app.use(bodyParser.json());

    // خطاهای ورودی را به‌صورت 400 برمی‌گردانیم
    app.use((err, req, res, next) => {
        if (err) {
            res.status(400).send(err.message);
        }
    });

    // (فصل ۱) دریافت کل بلاک‌چین
    app.get('/blocks', (req, res) => {
        res.send(getBlockchain());
    });

    // (فصل ۶) دریافت یک بلاک با هش مشخص
    app.get('/block/:hash', (req, res) => {
        const block = _.find(getBlockchain(), {'hash' : req.params.hash});
        res.send(block);
    });

    // (فصل ۶) دریافت یک تراکنش با شناسه مشخص
    app.get('/transaction/:id', (req, res) => {
        const tx = _(getBlockchain())
            .map((blocks) => blocks.data)   // داده تراکنش‌های همه بلاک‌ها
            .flatten()                       // تبدیل به فهرست تخت
            .find({'id': req.params.id});    // جستجوی شناسه
        res.send(tx);
    });

    // (فصل ۶) دریافت خروجی‌های هزینه‌نشده یک آدرس
    app.get('/address/:address', (req, res) => {
        const unspentTxOuts: UnspentTxOut[] =
            _.filter(getUnspentTxOuts(), (uTxO) => uTxO.address === req.params.address);
        res.send({'unspentTxOuts': unspentTxOuts});
    });

    // (فصل ۳) دریافت همه خروجی‌های هزینه‌نشده شبکه
    app.get('/unspentTransactionOutputs', (req, res) => {
        res.send(getUnspentTxOuts());
    });

    // (فصل ۴) دریافت خروجی‌های هزینه‌نشده متعلق به کیف پول
    app.get('/myUnspentTransactionOutputs', (req, res) => {
        res.send(getMyUnspentTransactionOutputs());
    });

    // (فصل ۴) استخراج بلاک با داده خام دلخواه (برای تراکنش‌های دستی)
    app.post('/mineRawBlock', (req, res) => {
        if (req.body.data == null) {
            res.send('data parameter is missing');   // پارامتر data ارسال نشده
            return;
        }
        const newBlock: Block = generateRawNextBlock(req.body.data);
        if (newBlock === null) {
            res.status(400).send('could not generate block');  // تولید بلاک ممکن نشد
        } else {
            res.send(newBlock);
        }
    });

    // (فصل ۲) استخراج بلاک جدید شامل تراکنش‌های استخر تراکنش
    app.post('/mineBlock', (req, res) => {
        const newBlock: Block = generateNextBlock();
        if (newBlock === null) {
            res.status(400).send('could not generate block');
        } else {
            res.send(newBlock);
        }
    });

    // (فصل ۴) دریافت موجودی کیف پول
    app.get('/balance', (req, res) => {
        const balance: number = getAccountBalance();
        res.send({'balance': balance});
    });

    // (فصل ۴) دریافت آدرس (کلید عمومی) کیف پول
    app.get('/address', (req, res) => {
        const address: string = getPublicFromWallet();
        res.send({'address': address});
    });

    // (فصل ۴) استخراج بلاکی که شامل تراکنش ارسال سکه است
    app.post('/mineTransaction', (req, res) => {
        const address = req.body.address;  // آدرس گیرنده
        const amount = req.body.amount;    // مقدار سکه
        try {
            const resp = generatenextBlockWithTransaction(address, amount);
            res.send(resp);
        } catch (e) {
            console.log(e.message);
            res.status(400).send(e.message);
        }
    });

    // (فصل ۵) افزودن تراکنش به استخر تراکنش (بدون استخراج فوری)
    app.post('/sendTransaction', (req, res) => {
        try {
            const address = req.body.address;
            const amount = req.body.amount;

            if (address === undefined || amount === undefined) {
                throw Error('invalid address or amount');  // آدرس یا مقدار نامعتبر
            }
            const resp = sendTransaction(address, amount);
            res.send(resp);
        } catch (e) {
            console.log(e.message);
            res.status(400).send(e.message);
        }
    });

    // (فصل ۵) دریافت استخر تراکنش
    app.get('/transactionPool', (req, res) => {
        res.send(getTransactionPool());
    });

    // (فصل ۱) دریافت فهرست هم‌تایان متصل
    app.get('/peers', (req, res) => {
        res.send(getSockets().map((s: any) => s._socket.remoteAddress + ':' + s._socket.remotePort));
    });
    // (فصل ۱) افزودن هم‌تای جدید
    app.post('/addPeer', (req, res) => {
        connectToPeers(req.body.peer);
        res.send();
    });

    // توقف گره
    app.post('/stop', (req, res) => {
        res.send({'msg' : 'stopping server'});
        process.exit();
    });

    app.listen(myHttpPort, () => {
        console.log('Listening http on port: ' + myHttpPort);
    });
};

// راه‌اندازی سرور HTTP، سرور همتا-به-همتا و کیف پول
initHttpServer(httpPort);
initP2PServer(p2pPort);
initWallet();

همان‌طور که می‌بینید، این فایل در واقع «چکیده» ای از همه مفاهیم آموزش است: هر endpoint که در طول فصل‌ها اضافه کردیم، در نهایت در این‌جا در کنار هم قرار می‌گیرد و گره را به ابزاری کامل برای مدیریت یک ارز دیجیتال ساده تبدیل می‌کند. اگر این فایل را با کد فصل ۱ مقایسه کنید، خواهید دید که ساختار کلی گره ثابت مانده و هر فصل فقط برخی بخش‌ها را گسترش داده است: فهرست بلاک‌ها، verifier ها، استخر تراکنش و کیف پول. این «رشد تدریجی و کم‌هزینه» دقیقاً همان چیزی است که این مجموعه را به یک بستر عالی برای یادگیری مفاهیم ارز دیجیتال تبدیل می‌کند.

توجه کنید که هر گره فایل کلید خصوصی خودش را می‌سازد (کیف پول مستقل)، پس آدرس هر دو گره متفاوت خواهد بود.

۲. اتصال گره‌ها به یکدیگر

طبق فصل ۱ هیچ کشف خودکار هم‌تایی وجود ندارد؛ آدرس هم‌تا را دستی اضافه می‌کنیم: 

bash# از گره ۱ به گره ۲ متصل می‌شویم
curl -H "Content-type:application/json" --data '{"peer" : "ws://localhost:6002"}' http://localhost:3001/addPeer

# بررسی هم‌تایان متصل
curl http://localhost:3001/peers

حالا دو گره از طریق وب‌سوکت با هم ارتباط دارند و هر بلاک یا تراکنش جدیدی را با هم ردوبدل می‌کنند (پیام‌های QUERY_LATEST، QUERY_ALL و RESPONSE_BLOCKCHAIN از فصل ۱ و پیام‌های استخر تراکنش از فصل ۵).

۳. استخراج و مشاهده همگام‌سازی

bash# استخراج یک بلاک روی گره ۱
curl -X POST http://localhost:3001/mineBlock

# بلاک جدید باید در هر دو گره دیده شود
curl http://localhost:3001/blocks
curl http://localhost:3002/blocks

تعداد بلاک‌های دو گره باید یکسان باشد. اگر گره ۲ زنجیره کوتاه‌تری داشته باشد، طبق فصل ۱ زنجیره معتبرِ بلندتر را جایگزین می‌کند. برای دیدن اثر «اثبات کار» (فصل ۲)، چند بلاک پشت سر هم استخراج کنید؛ هر بلاک باید چند لحظه‌ای زمان ببرد و در difficulty بلاک‌های بعدی می‌بینید که دشواری با نرخ استخراج تنظیم می‌شود.

۴. ارسال تراکنش و پخش آن در شبکه

bash# آدرس (کلید عمومی) گره ۲ را بگیرید
curl http://localhost:3002/address

# از گره ۱ به آدرس گره ۲ سکه بفرستید
curl -H "Content-type: application/json" --data '{"address": "آدرس_به_دست_آمده", "amount" : 10}' http://localhost:3001/sendTransaction

# تراکنش تأییدنشده باید به استخر تراکنش گره ۲ هم پخش شده باشد
curl http://localhost:3002/transactionPool

طبق فصل ۵، گره ۲ با دریافت تراکنشِ تازه، کل استخر تراکنش خود را برای گره ۱ پخش می‌کند؛ یعنی تراکنش در هر دو گره قابل مشاهده است. حالا تراکنش را استخراج کنید: 

bash# استخراج بلاکِ شامل تراکنش استخر
curl -X POST http://localhost:3001/mineBlock

# موجودی گره ۲ باید ۱۰ سکه بیشتر شده باشد
curl http://localhost:3002/balance

اگر بخواهید دقیقاً تراکنش کوین‌بیس (۵۰ سکه پاداش استخراج) را هم ببینید، داده بلاک استخراج‌شده را با endpoint فصل ۶ بررسی کنید: 

bash# بلاک‌ها و تراکنش‌های درونشان را با جزئیات ببینید
curl http://localhost:3001/blocks

# جستجوی یک تراکنش خاص با شناسه آن (فصل ۶)
curl http://localhost:3001/transaction/شناسه_تراکنش

# خروجی‌های هزینه‌نشده یک آدرس (فصل ۶)
curl http://localhost:3001/address/آدرس_کیف_پول
نکته: این سناریوی آزمایش، همان مسیری است که در فایل main.ts مشاهده کردید؛ هر endpoint که این‌جا فراخوانی شد، قبلاً در بخش کد کامل گره دیدید. درک این ارتباط، بهترین راه برای تثبیت مطالب مجموعه است.

مقایسه Naivecoin با بیت‌کوین

همان‌طور که در مقدمه آموزش گفته شد، Naivecoin یک پیاده‌سازی «آماده برای تولید» نیست، بلکه نمایشی از اصول پایه است. برای درک بهتر جایگاه هر تصمیم، در جدول زیر ساده‌سازی‌های Naivecoin را در مقابل معادل آن‌ها در بیت‌کوین می‌بینید (همه موارد سمت چپ در همین آموزش به‌صراحت اشاره شده‌اند):

ویژگی Naivecoin (در این آموزش) بیت‌کوین
فاصله تولید بلاک ۱۰ ثانیه (ثابت BLOCK_GENERATION_INTERVAL) ۱۰ دقیقه
فاصله تنظیم دشواری هر ۱۰ بلاک هر ۲۰۱۶ بلاک
پاداش استخراج ۵۰ سکه ثابت در هر بلاک متغیر و نیم‌شونده (هالوینگ)
کارمزد تراکنش وجود ندارد (طبق فصل ۵) بخشی اساسی از انگیزه استخراج‌کنندگان
کشف هم‌تایان دستی و صریح (addPeer) خودکار (seed nodes و IRC/DNS)
ذخیره کلید خصوصی فایل ساده بدون رمزنگاری + یک کلید کیف پول‌های امن، عبارت بازیابی و چند کلید
ذخیره بلاک‌چین آرایه در حافظه (با خاتمه گره از بین می‌رود) پایگاه داده ماندگار (LevelDB)
وضعیت آماده تولید خیر — صرفاً اهداف آموزشی بله
نکته: نکته‌ای که باید در ذهن بماند این است که همه مینیاتورسازی‌های بالا آگاهانه انجام شده‌اند تا پیاده‌سازی ساده بماند؛ ساختار اصلی (بلاک، اثبات کار، UTXO، امضاها و اجماع ناکاموتو) در بیت‌کوین دقیقاً همان چیزی است که در این آموزش ساختیم.

واژه‌نامه مفاهیم

خلاصه‌ای از اصطلاحات کلیدی که در طول آموزش با آن‌ها آشنا شدیم:

  • بلاک (Block): واحد داده بلاک‌چین شامل فهرست تراکنش‌ها یا داده دلخواه، که با هش خود و هش بلاک قبلی به زنجیره متصل می‌شود.
  • بلاک پیدایش (Genesis Block): اولین بلاک زنجیره که هیچ بلاک قبلی ندارد و در کد منبع ثابت ثبت شده است.
  • اثبات کار (Proof of Work): معما‌ی محاسباتی (یافتن هش با صفرهای ابتدایی مشخص) که باید قبل از افزودن بلاک حل شود.
  • استخراج (Mining): فرایند حل معما‌ی اثبات کار با تغییر nonce تا یافتن هش معتبر.
  • دشواری (Difficulty): تعداد صفرهای ابتدایی موردنیاز هش (در فرمت دودویی) برای معتبر بودن بلاک.
  • nonce: عددی که در هر تلاش استخراج تغییر می‌کند تا هش متفاوتی برای همان محتوای بلاک تولید شود.
  • دشواری تجمعی (Cumulative Difficulty): مجموع 2^difficulty همه بلاک‌های یک زنجیره؛ مبنای انتخاب زنجیره «صحیح» هنگام انشعاب.
  • اجماع ناکاموتو (Nakamoto Consensus): قاعده انتخاب زنجیره با بیشترین کار محاسباتی (دشواری تجمعی).
  • کلید خصوصی (Private Key): رشته ۳۲ بایتی تصادفی که مالکیت سکه‌ها را اثبات می‌کند و هرگز نباید فاش شود.
  • کلید عمومی / آدرس (Public Key / Address): رشته ۶۵ بایتی مشتق‌شده از کلید خصوصی که گیرنده سکه‌هاست.
  • امضای دیجیتال (Digital Signature): امضای شناسه تراکنش با کلید خصوصی که مالکیت ورودی‌ها را اثبات می‌کند.
  • ورودی تراکنش (TxIn): ارجاع به یک خروجی هزینه‌نشده قبلی به‌همراه امضای مالک.
  • خروجی تراکنش (TxOut): آدرس گیرنده و مقدار سکه‌ای که به آن آدرس قفل می‌شود.
  • خروجی تراکنش هزینه‌نشده (UTXO): سکه‌ای که تاکنون خرج نشده و به آدرسی خاص تعلق دارد.
  • تراکنش کوین‌بیس (Coinbase Transaction): اولین تراکنش هر بلاک بدون ورودی که ۵۰ سکه پاداش استخراج‌کننده را ایجاد می‌کند.
  • استخر تراکنش (Transaction Pool / Mempool): مجموعه تراکنش‌های تأییدنشده‌ای که گره می‌شناسد.
  • رله تراکنش (Transaction Relaying): پخش تراکنش‌های تأییدنشده بین گره‌ها تا در نهایت توسط یک استخراج‌کننده به بلاک‌چین اضافه شوند.
  • هم‌تا (Peer): گره دیگری که گره ما از طریق وب‌سوکت به آن متصل است.
  • پخش (Broadcast): ارسال یک پیام (بلاک جدید یا استخر تراکنش) به همه هم‌تایان متصل.

پرسش‌های متداول (برگرفته از محتوای آموزش)

در ادامه به پرتکرارترین پرسش‌هایی که هنگام خواندن این مجموعه مطرح می‌شوند، بر اساس همان مفاهیم مطرح‌شده در فصل‌ها پاسخ داده می‌شود:

چرا تغییر داده یک بلاک، کل زنجیره را خراب می‌کند؟

چون هش هر بلاک از روی همه محتوای آن بلاک محاسبه می‌شود (index، previousHash، timestamp و data) و هر بلاک به‌طور صریح هش بلاک قبلی را در خود نگه می‌دارد. اگر داده یک بلاک میانی تغییر کند، هش آن تغییر می‌کند و دیگر با previousHash بلاک بعدی مطابقت ندارد؛ همین‌طور تا انتهای زنجیره ادامه می‌یابد. در عمل باید همه بلاک‌های بعدی دوباره استخراج شوند (فصل ۱ و ۲).

هش بلاک چه ربطی به استخراج دارد؟

در نسخه فصل ۱ هش فقط برای حفظ یکپارچگی و ارجاع به بلاک قبلی بود و هیچ هزینه‌ای نداشت. از فصل ۲ به بعد، استخراج یعنی یافتن هشی که در قالب دودویی با تعداد مشخصی صفر (معادل difficulty) شروع شود؛ برای این کار nonce را تغییر می‌دهیم تا هش‌های متفاوت امتحان شوند (فصل ۲).

چرا بلاک‌ها نباید خیلی سریع یا خیلی کند تولید شوند؟

برای کنترل نرخ تولید بلاک، دشواری به‌صورت دوره‌ای بازبینی می‌شود: اگر ۱۰ بلاک (DIFFICULTY_ADJUSTMENT_INTERVAL) در زمانی کمتر از نصف زمان مورد انتظار تولید شوند، دشواری یک واحد افزایش می‌یابد و اگر بیش از دو برابر زمان ببرند، یک واحد کاهش می‌یابد (فصل ۲).

چرا به‌جای «بلندترین زنجیره» از «دشواری تجمعی بیشتر» استفاده می‌شود؟

چون با معرفی دشواری، تعداد بلاک‌ها دیگر هزینه واقعی تولید زنجیره را نشان نمی‌دهد. زنجیره‌ای با چند بلاک پرمشقت ممکن است کار محاسباتی بیشتری از زنجیره‌ای با بلاک‌های فراوان و آسان داشته باشد. دشواری تجمعی (مجموع 2^difficulty بلاک‌ها) هزینه واقعی یعنی نرخ هش × زمان را نمایندگی می‌کند (فصل ۲).

امضای دیجیتال دقیقاً چه چیزی را اثبات می‌کند؟

امضا با کلید خصوصی روی شناسه تراکنش (txId) ساخته می‌شود و هر کسی می‌تواند با کلید عمومی (= آدرس) صحت آن را بررسی کند. این اثبات می‌کند که سازنده تراکنش، کلید خصوصیِ متناظر با آدرسِ خروجی هزینه‌نشده مرجع را دارد؛ یعنی مالک واقعی سکه‌هاست (فصل ۳).

چرا دستکاری یک تراکنش امضاشده شکست می‌خورد؟

چون امضا روی txId زده می‌شود و txId از روی txInها و txOutها محاسبه می‌شود. تغییر هر بخش از تراکنش، txId را تغییر می‌دهد؛ اگر txId جدید را جایگزین کنیم، امضا با آن مطابقت نمی‌کند (فصل ۳، سناریوی پنج‌مرحله‌ای دستکاری).

سکه‌های اولیه از کجا می‌آیند؟

از تراکنش کوین‌بیس: اولین تراکنش هر بلاک که هیچ ورودی‌ای ندارد و ۵۰ سکه (COINBASE_AMOUNT) به‌عنوان پاداش برای استخراج‌کننده ایجاد می‌کند. ارتفاع بلاک به ورودی آن اضافه می‌شود تا txId هر کوین‌بیس یکتا بماند (فصل ۳).

چرا هنگام ارسال ۱۰ سکه از موجودی ۵۰ سکه‌ای، دو خروجی ساخته می‌شود؟

چون یک خروجی تراکنش (UTXO) همیشه باید کامل خرج شود و قابل تقسیم نیست. پس ۱۰ سکه به گیرنده و ۴۰ سکه باقی‌مانده (leftOverAmount) به آدرس خودِ فرستنده برگشت داده می‌شود تا موجودی او در قالب یک UTXO جدید حفظ شود (فصل ۴).

چرا ذخیره کلید خصوصی به‌صورت فایل ساده ناامن است؟

چون کلید خصوصی تنها مدرک مالکیت سکه‌هاست؛ هر کس به فایل node/wallet/private_key دسترسی داشته باشد، می‌تواند به‌جای ما تراکنش بسازد و تمام سکه‌ها را بردارد. نویسنده این کار را صرفاً برای سادگی آموزش انجام داده و در دنیای واقعی هرگز چنین نگهداری‌ای توصیه نمی‌شود (فصل ۴).

تراکنش تأییدنشده چیست و چه‌طور وارد بلاک‌چین می‌شود؟

تراکنشی که هنوز در هیچ بلاکی قرار نگرفته «تأییدنشده» است. فرستنده آن را از طریق /sendTransaction به استخر تراکنش گره خود اضافه می‌کند؛ گره‌ها با پیام‌های QUERY/RESPONSE_TRANSACTION_POOL آن را پخش می‌کنند و در نهایت استخراج‌کننده‌ای آن را در بلاک بعدی خود قرار می‌دهد (فصل ۵).

چرا وقتی بلاک جدیدی استخراج می‌شود، استخر تراکنش پاکسازی می‌شود؟

چون ممکن است بلاک جدید تراکنش‌های استخر را مصرف کرده باشد (تراکنش استخر به زنجیره اضافه شده) یا UTXO مرجع یک تراکنش استخر را خرج کرده باشد؛ در هر دو حالت آن تراکنش‌ها دیگر معتبر نیستند و باید از استخر حذف شوند (فصل ۵، متد updateTransactionPool).

آیا برای افزودن هر تراکنش باید خودمان بلاک استخراج کنیم؟

از فصل ۵ به بعد خیر؛ فقط کافی است تراکنش را به استخر تراکنش اضافه کنیم تا در شبکه پخش شود و استخراج‌کننده‌ای (خودمان یا گره دیگری) آن را در بلاک خود بگنجاند. اما به‌دلیل نداشتن «کارمزد تراکنش» در این آموزش، انگیزه اقتصادی برای استخراج تراکنش‌های دیگران وجود ندارد (فصل ۵).

آیا مرورگر بلاک‌چین وضعیت شبکه را تغییر می‌دهد؟

خیر. مرورگر فقط درخواست‌های خواندنی (مانند /block/:hash، /transaction/:id و /address/:address) به گره می‌فرستد و پاسخ‌ها را به‌شکلی خوانا نمایش می‌دهد؛ هرگز درخواستی که وضعیت بلاک‌چین را تغییر دهد ارسال نمی‌کند (فصل ۶).

جمع‌بندی و مطالعه بیشتر

در طول این مجموعه، مفاهیم اصلی یک ارز دیجیتال را به‌ترتیب و به‌صورت عملی پیاده‌سازی کردیم:

  1. بلاک‌چینی که بلاک‌ها را با هش و ارجاع صریح به بلاک قبلی به هم متصل می‌کند و با قواعد اعتبارسنجی و قانون بلندترین زنجیره خودکار عمل می‌کند (فصل ۱).
  2. سیستم اثبات کار که تولید بلاک را پرهزینه، پخش تراکنش را آسان و توافق روی دشواری را ممکن می‌کند؛ همراه با قاعده ناکاموتو برای حل انشعاب (فصل ۲).
  3. تراکنش‌های مبتنی بر خروجی‌های هزینه‌نشده (UTXO) با امضای ECDSA که امکان ارسال سکه‌ها را به‌شکلی امن و قابل راستی‌آزمایی فراهم می‌کند (فصل ۳).
  4. کیف پولی که پیچیدگی ورودی‌ها و خروجی‌ها را برای کاربر نهایی پنهان می‌کند (فصل ۴).
  5. شبکه‌ای که تراکنش‌های تأییدنشده را بین گره‌ها رله می‌کند و آن‌ها را به استخراج درون‌زنجیره‌ای می‌رساند (فصل ۵).
  6. رابط کاربری و مرورگر بلاک‌چینی که تعامل با گره را بصری و خوانا می‌کند (فصل ۶).
