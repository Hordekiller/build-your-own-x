شلِ خودت را بساز (Build Your Own Shell) — کارگاه مرحله‌ای

⚙ زبان: C ✅ ترجمه شده 🔗 منبع اصلی
منبع اصلی: این صفحه ترجمه فارسی «Build Your Own Shell» از جولیان اسکوئلِز (Julian Squires) است — مجموعه کارگاه‌های مرحله‌ای ساخت یک شل یونیکس: از fork/exec/wait تا کنترل کارها، سیگنال‌ها، نقل‌قول، توسعه متغیرها و تعاملی شدن — همراه با یک اسکریپت «اعتبارسنجی» که پیشرفت شما را تست می‌کند.

۱. چرا شل خودمان را بنویسیم؟

شل قلب یونیکس است؛ چسبی است که همه ابزارهای کوچک یونیکس را کنار هم نگه می‌دارد. درکِ آن، بسیاری از ایده‌های مهم یونیکس را روشن می‌کند و بهترین راهِ رسیدن به آن درک، نوشتن شل خودمان است. این کارگاه سه هدف دارد:

  1. درک بهتر از فرایندهای یونیکس — این شما را در طراحی و فهم نرم‌افزارهایی که روی یونیکس اجرا می‌شوند بهتر می‌کند.
  2. روشن کردن سوءبرداشت‌های رایج درباره شل‌های POSIX — این شما را در استفاده و اسکریپت‌نویسی با شل‌های فراگیر مثل bash مؤثرتر می‌کند.
  3. ساخت یک پیاده‌سازی کار از شل — شلی که واقعاً می‌توانید درباره ادامه کار روی آن هیجان‌زده باشید؛ سفارشی‌سازی‌های شخصی بی‌پایانی می‌توانید روی شل خودتان انجام دهید.
«همه شل‌های شکسته... خیلی شل‌های شکسته... در تپه‌های صدفیِ ما» — از شعر «Shellmounds» گروه Grayceon؛ کارگاه از این‌جا اسم‌اش را گرفته.

۲. چطور از مخزن استفاده کنیم؟

مطالب به مراحل پیشرونده (Stages) تقسیم شده که هر کدام موضوعی تقریباً مستقل را پوشش می‌دهند. هر مرحله شامل: توصیف امکاناتی که بررسی می‌شود، فهرست manpageهایی که باید ببینید و مجموعه‌ای از تست‌هاست. در ریشه مخزن، اسکریپتی به نام validate وجود دارد که همه تست‌ها را علیه شل در حال ساخت شما اجرا می‌کند — فقط مسیر اجرایی شل‌تان را بدهید:

bash$ ./validate ../mysh/mysh

می‌توانید یک مرحله یا حتی یک تست را جدا اجرا کنید:

bash$ ./validate ../mysh/mysh stage_2
$ ./validate ../mysh/mysh stage_3 03

برای اجرای تست‌ها به expect و یک کامپایلر C نیاز دارید. تست‌ها فرض می‌کنند یک شل بورن‌خانواده با تأثیراتی از ksh می‌سازید. جالب است که bash و ksh باید از همه تست‌ها رد شوند (با ./validate /bin/bash تستش کنید) و cat باید در همه شکست بخورد! dash هم همه‌چیز به‌جز مرحله ۵ را پاس می‌کند.

مراحل:

  1. fork/exec/wait — مبانی فرایندهای یونیکس و ساده‌ترین شل ممکن.
  2. فایل‌ها و پایپ‌ها — افزودن پایپ و بازنویسی توصیفگرهای فایل (fd).
  3. کنترل کار و سیگنال‌ها — پشتیبانی از ^C، ^\ و ^Z.
  4. نقل‌قول و توسعه (Expansion) — محیط، متغیرها، glob و مفاهیم اغلب بدفهمیده شل.
  5. تعاملی‌سازی — صیقل دادن شل برای کار تعاملی روزمره.

۳. مرحله ۱: fork / exec / wait

در این مرحله با فرایند یونیکس آشنا می‌شوید: اجرای یک برنامه یعنی ساختن یک فرایند جدید (fork)، تبدیل آن به برنامه موردنظر (exec) و انتظار برای پایانش (wait). ساده‌ترین شل ممکن، یک حلقه است:

c#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    char *line = NULL;
    size_t capacity = 0;

    for (;;) {
        printf("mysh> ");
        if (getline(&line, &capacity, stdin) < 0)
            break;

        pid_t pid = fork();
        if (pid == 0) {
            /* فرزند: خودمان را به برنامه تبدیل کن */
            execlp(line, line, (char *)NULL);
            perror("exec");
            _exit(127);
        }
        /* والد: منتظر فرزند باش */
        wait(NULL);
    }
    return 0;
}

نکته‌های مرحله: fork در فرزند ۰ و در والد شناسه فرزند را برمی‌گرداند؛ exec* فرایند جاری را تبدیل می‌کند (اگر موفق شود دیگر برنمی‌گردد)؛ و wait والد را متوقف می‌کند تا فرزند تمام شود. کارگاه اشاره می‌کند که برای افزایش لذت، اول شل‌تان را نام‌گذاری و پرامپت مخصوصش را بسازید.

۴. مرحله ۲: فایل‌ها و پایپ‌ها

اینجا بازنویسی توصیفگرهای فایل و پایپ اضافه می‌شود. توصیفگرهای فایل (fd) اعداد صحیحی هستند که به باز شدن فایل‌ها اشاره می‌کنند؛ ۰ = ورودی استاندارد، ۱ = خروجی استاندارد، ۲ = خطای استاندارد. پایپ دو fd می‌سازد که هرچه در یکی نوشته شود از دیگری خوانده می‌شود:

cint pipe_fds[2];
pipe(pipe_fds);   /* فرض کنیم [4, 5] برمی‌گرداند */

/* هرچه به 5 نوشته شود از 4 خوانده می‌شود */

برای اجرای ls | wc: پایپ بساز، دو بار fork کن (یکی برای ls و یکی برای wc)، در فرزند اول dup2(pipe_fds[1], 1) (خروجی استاندارد = سر نوشتنی پایپ)، در فرزند دوم dup2(pipe_fds[0], 0) (ورودی استاندارد = سر خواندنی پایپ) و در والد هر دو سر را ببند. بازنویسی fd با dup2 کار می‌کند:

c/* در فرزندِ طرف ls: خروجی استاندارد را به سر نوشتنی پایپ وصل کن */
dup2(pipe_fds[1], STDOUT_FILENO);
execvp("ls", args_ls);
/* در فرزندِ طرف wc: ورودی استاندارد را به سر خواندنی پایپ وصل کن */
dup2(pipe_fds[0], STDIN_FILENO);
execvp("wc", args_wc);
/* در والد: */
close(pipe_fds[0]);
close(pipe_fds[1]);

همچنین «بازنویسی به فایل» (> و <) با همین dup2 و open انجام می‌شود — پس از مرحله ۲ می‌توانید grep shel /usr/share/dict/words > /tmp/shel_words را هم اجرا کنید.

۵. مرحله ۳: کنترل کار و سیگنال‌ها

در این مرحله با سیگنال‌ها و کنترل کار آشنا می‌شوید. وقتی ^C می‌زنید، SIGINT به فرایند می‌رسد؛ در حالت پیش‌فرض فرایند را می‌کشد. اما در یک شل تعاملی، باید این سیگنال فقط به فرایند در حال اجرا برسد، نه خودِ شل. نکته‌های کلیدی:

  • شل باید در گروه فرایندی جدا (process group) با setpgid کار کند و با tcsetpgrp آن را به ترمینال بدهد.
  • سیگنال‌های ^C (SIGINT)، ^\ (SIGQUIT) و ^Z (SIGTSTP) را شل باید برای خودش نادیده بگیرد اما به فرزندانش منتقل کند.
  • با waitpid و گزینه WNOHANG می‌توانید خبر پایان کارها را ببینید، و SIGCHLD شل را از پایان یک فرزند باخبر می‌کند.
  • کنترل کار یعنی امکان ^Z و fg / bg و jobs: فرایندها را موقع ایجاد در گروه خودشان قرار دهید و با tcsetpgrp تعیین کنید کدام گروه از ترمینال استفاده می‌کند.
c#include <signal.h>

/* شل سیگنال‌های ترمینال را برای خودش نادیده می‌گیرد */
signal(SIGINT, SIG_IGN);
signal(SIGQUIT, SIG_IGN);
signal(SIGTSTP, SIG_IGN);

/* هنگام اجرای یک کار:
   - فرزند setpgid می‌شود تا گروه خودش را بسازد
   - والد با tcsetpgrp گروه فرزند را صاحب ترمینال می‌کند
   - بعد از waitpid، کنترل ترمینال به شل برمی‌گردد */

۶. مرحله ۴: نقل‌قول و توسعه

این مرحله مفاهیم اغلب بدفهمیده شل را روشن می‌کند: محیط (environment)، متغیرها، globbing و نقل‌قول. نکته‌های اصلی:

  • توسعه متغیرها: $HOME با getenv در فرایند شل حل می‌شود و سپس exec* اتفاق می‌افتد — پس مرحله ۴ یعنی «توسعه» قبل از اجرا.
  • Globbing: *.c توسط خود شل با glob(3) به فهرست فایل‌ها تبدیل می‌شود؛ کودک فقط فایل‌های نهایی را می‌بیند.
  • نقل‌قول: '...' و "..." و \\ تعیین می‌کنند کدام قسمتها توسعه ببینند و کدام نه — و جالب‌تر، کدام رشته‌ها «یک آرگومان» می‌شوند (مثل echo "a b").
  • متغیرهای محیطی: VAR=value cmd متغیری موقت برای یک فرمان می‌سازد؛ چون فرزند نمی‌تواند محیط والد را عوض کند، export باید داخلی (builtin) خودِ شل باشد.
c/* توسعه متغیر قبل از اجرا: */
char *val = getenv(name);
/* سپس در argv قرار می‌گیرد */

/* glob کردن قبل از اجرا: */
glob_t g;
if (glob("*.c", 0, NULL, &g) == 0) {
    /* g.gl_pathv آرگومان‌های نهایی است */
}

۷. مرحله ۵: تعاملی‌سازی

مرحله نهایی شل را برای کار تعاملی روزمره صیقل می‌دهد — چیزهایی که در حالت غیرتعاملی حس نمی‌کنید: خواندن و ویرایش خط فرمان (خط‌فرمان، تکمیل خودکار با Tab)، پرامپت مناسب با وضعیت آخرین فرمان ($?)، ^C در پرامپت که باید خط فعلی را پاک کند نه شل را، و اعلان درست پایانِ کارها. این بخش همان چیزی است که کارگاه اصرار دارد کار را برای استفاده واقعی رضایت‌بخش می‌کند.

نکته: اگر کد C از جایی به بعد اذیت‌تان کرد، کارگاه پیشنهاد می‌کند اول با یک زبان سطح‌بالاتر با پشتیبانی خوب از سیستم‌عامل (Python با os و subprocess، Ruby با Process، Rust با nix، یا حتی OCaml/Scheme) شروع کنید — در مرحله ۲ با پایتون یادتان باشد فایل‌های توصیفگر را با os.set_inheritable(fd, True) به‌صورت صریح ارث‌پذیر کنید (از پایتون 3.4).

۸. کجا برویم؟

برای مطالعه بیشتر، کارگاه این منابع را پیشنهاد می‌کند: کتاب کلاسیک APUE (استیونز)، The Linux Programming Interface (کریسک)، مقاله «Bourne-Again Shell» در معماری نرم‌افزارهای منبع‌باز، آموزش «Write a Shell in C» استفان برنان (موج ۳ همین مجموعه!)، کتاب‌های کنترل کار در مستندات glibc و مقاله‌های سیگنال و کنترل کار. و در پایان: یک سری شل‌های واقعی برای خواندن کدشان — from busybox/ash و mksh تا rc، zsh، fish و حتی شل اصلی تامپسون در تاریخچه یونیکس.

کپیرایت: مجموعه کارگاه «Build Your Own Shell» اثر جولیان اسکوئلز (Julian Squires) است. این صفحه فقط ترجمه فارسی آن است و تمام حقوق محتوا و کدها متعلق به نویسنده اصلی است. برای مشاهده اصل مطلب به ریپوی گیت‌هاب مراجعه کنید.
