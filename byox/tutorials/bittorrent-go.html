مقدمه: بیت‌تورنت چیست و چرا آن را می‌سازیم؟

بیت‌تورنت (BitTorrent) یک پروتکل برای دانلود و توزیع فایل‌ها در سراسر اینترنت است. در تقابل با رابطه سنتی کلاینت/سرور (مثل تماشای فیلم در نتفلیکس یا بارگذاری همین صفحه وب که می‌خوانید) که در آن دانلودکننده‌ها به یک سرور مرکزی متصل می‌شوند، شرکت‌کنندگان در شبکه بیت‌تورنت که همتا (peer) نامیده می‌شوند، قطعه‌های فایل را از یکدیگر دانلود می‌کنند؛ همین موضوع باعث می‌شود بیت‌تورنت یک پروتکل نظیربه‌نظیر (peer-to-peer) باشد. در این آموزش بررسی می‌کنیم این کار چگونه انجام می‌شود و کلاینتی می‌سازیم که می‌تواند همتاها را پیدا کند و بین آن‌ها داده ردوبدل کند.

این پروتکل طی ۲۰ سال گذشته به‌صورت ارگانیک تکامل پیدا کرده و افراد و سازمان‌های مختلفی افزونه‌هایی برای قابلیت‌هایی مثل رمزنگاری، تورنت‌های خصوصی و راه‌های جدید پیدا کردن همتا اضافه کرده‌اند. ما مشخصات اصلی سال ۲۰۰۱ را پیاده‌سازی می‌کنیم تا پروژه در حد یک آخر هفته بماند.

من از فایل ISO دبیان به‌عنوان آزمون استفاده می‌کنم، چون بزرگ است اما خیلی بزرگ نه — حدود ۳۵۰ مگابایت. دبیان به‌عنوان یک توزیع لینوکسی محبوب، همتاهای سریع و خوش‌برخورد زیادی برای اتصال دارد. به این ترتیب از مسائل حقوقی و اخلاقی مربوط به دانلود محتوای دزدی هم دور می‌مانیم.

در مقاله اصلی، نویسنده یادآوری می‌کند که فعالان اعتراضات اجتماعی (مثل جنبش‌های عدالت نژادی) به وثیقه و کمک حقوقی نیاز دارند و از خوانندگان می‌خواهد به صندوق‌های وثیقه محلی کمک کنند — پیوند: communityjusticeexchange.org/nbfn-directory.

پیدا کردن همتاها

این‌جا یک مشکل داریم: می‌خواهیم با بیت‌تورنت فایلی را دانلود کنیم، اما این یک پروتکل نظیربه‌نظیر است و ما هیچ ایده‌ای نداریم که همتاها را کجا پیدا کنیم. این خیلی شبیه جابه‌جایی به یک شهر جدید و تلاش برای پیدا کردن دوست است — شاید سراغ یک میخانه محلی یا گروه ملاقات برویم! مکان‌های متمرکز مثل این‌ها، ایده اصلی پشت ترکرها (tracker) هستند؛ سرورهای مرکزی که همتاها را به یکدیگر معرفی می‌کنند. آن‌ها فقط وب‌سرورهایی هستند که روی HTTP اجرا می‌شوند * بعضی ترکرها برای صرفه‌جویی در پهنای باند از یک پروتکل باینری UDP استفاده می‌کنند؛ ترکر دبیان را در http://bttracker.debian.org:6969/ می‌بینید.

البته این سرورهای مرکزی اگر تبادل محتوای غیرقانونی را تسهیل کنند، ممکن است توسط ماموران فدرال جمع شوند. احتمالاً درباره توقیف و تعطیلی ترکرهایی مثل TorrentSpy، Popcorn Time و KickassTorrents خوانده‌اید. روش‌های جدید، میان‌بر را حذف می‌کنند و حتی کشف همتا را هم به یک فرایند توزیع‌شده تبدیل می‌کنند. ما آن‌ها را پیاده‌سازی نمی‌کنیم، اما اگر علاقه‌مندید، این کلمات را جست‌وجو کنید: DHT، PEX و مگنت‌لینک (magnet links).

این درهم‌وبرهم با قالبی به نام Bencode (تلفظ: بی‌-انکود) کدگذاری شده و ما باید آن را کدگشایی کنیم. Bencode تقریباً همان نوع ساختارهایی را می‌تواند کدگذاری کند که JSON — رشته‌ها، اعداد صحیح، لیست‌ها و دیکشنری‌ها. داده بنکدشده به اندازه JSON برای انسان خواناتر و قابل‌نوشتن نیست، اما می‌تواند داده باینری را کارآمد مدیریت کند و تجزیه آن از یک جریان (stream) واقعاً ساده است. رشته‌ها با پیشوند طول می‌آیند و این‌طور دیده می‌شوند: 4:spam. اعداد صحیح بین دو نشانگر شروع و پایان قرار می‌گیرند؛ بنابراین 7 به‌صورت i7e کدگذاری می‌شود. لیست‌ها و دیکشنری‌ها هم به شکلی مشابه کار می‌کنند: l4:spami7ee یعنی ['spam', 7] و d4:spami7ee یعنی {spam: 7}.

در این فایل، نشانی URL ترکر، تاریخ ساخت (به‌صورت زمان‌سنج یونیکس)، نام و اندازه فایل، و یک بلاب باینری بزرگ شامل هش SHA-1 هر قطعه را می‌بینیم. قطعه‌ها (pieces) بخش‌های هم‌اندازه فایلی هستند که می‌خواهیم دانلود کنیم. اندازه دقیق هر قطعه در تورنت‌های مختلف فرق دارد، اما معمولاً جایی بین ۲۵۶ کیلوبایت و ۱ مگابایت است. این یعنی یک فایل بزرگ ممکن است از هزاران قطعه تشکیل شده باشد. ما این قطعه‌ها را از همتاهایمان دانلود می‌کنیم، آن‌ها را با هش‌های داخل فایل تورنت چک می‌کنیم، کنار هم می‌چینیم و ... بوم! یک فایل داریم!

این سازوکار به ما اجازه می‌دهد یکپارچگی هر قطعه را هنگام دریافت بررسی کنیم. این ویژگی بیت‌تورنت را در برابر خرابی اتفاقی یا مسموم‌سازی عمدی تورنت مقاوم می‌کند. مگر اینکه مهاجمی بتواند SHA-1 را با حمله پیش‌تصویر (preimage attack) بشکند، ما دقیقاً همان محتوایی را می‌گیریم که خواسته‌ایم.

نوشتن یک پارسر بنکد خیلی سرگرم‌کننده است، اما امروز تمرکز ما روی تجزیه نیست. پارسر ۵۰ خطی فردریک لوند (Fredrik Lundh) را واقعاً روشنگر پیدا کردم. برای این پروژه از github.com/jackpal/bencode-go استفاده کردم: 

goimport (
    "github.com/jackpal/bencode-go"
)

// bencodeInfo اطلاعات داخل بخش info فایل تورنت را نگه می‌دارد
type bencodeInfo struct {
    Pieces      string `bencode:"pieces"`       // بلاب باینری هش‌های همه قطعه‌ها
    PieceLength int    `bencode:"piece length"` // طول هر قطعه به بایت
    Length      int    `bencode:"length"`       // طول کل فایل به بایت
    Name        string `bencode:"name"`         // نام فایل
}

// bencodeTorrent ساختار ریشه یک فایل تورنت بنکدشده است
type bencodeTorrent struct {
    Announce string      `bencode:"announce"` // نشانی ترکر
    Info     bencodeInfo `bencode:"info"`     // دیکشنری info
}

// Open یک فایل تورنت را تجزیه می‌کند
func Open(r io.Reader) (*bencodeTorrent, error) {
    bto := bencodeTorrent{}
    err := bencode.Unmarshal(r, &bto)
    if err != nil {
        return nil, err
    }
    return &bto, nil
}

چون دوست دارم ساختارهایم نسبتاً تخت باشند و ساختارهای کاربردی برنامه را از ساختارهای سریال‌سازی جدا نگه دارم، یک ساختار تخت‌تر و متفاوت به نام TorrentFile صادر کردم و چند تابع کمکی برای تبدیل بین این دو نوشتم.

نکته مهم: فیلد pieces (که قبلاً یک رشته بود) را به یک برش (slice) از هش‌ها (هرکدام [20]byte) تقسیم کردم تا بعداً راحت به هش‌های تکی دسترسی داشته باشم. همچنین هش SHA-1 کل دیکشنری بنکدشده info (همان دیکشنری که نام، اندازه و هش قطعه‌ها را داشت) را محاسبه کردم. ما این را infohash می‌شناسیم و وقتی با ترکرها و همتاها حرف می‌زنیم، فایل‌ها را یکتا شناسایی می‌کند. بعداً بیشتر درباره‌اش صحبت می‌کنیم.

دریافت همتاها از ترکر

حالا که درباره فایل و ترکر آن اطلاعات داریم، بیایید با ترکر صحبت کنیم تا حضورمان را به‌عنوان یک همتا اعلام کنیم و فهرست همتاهای دیگر را بگیریم. فقط کافی است یک درخواست GET به نشانی announce داخل فایل .torrent بفرستیم، با چند پارامتر کوئری: 

go// buildTrackerURL نشانی درخواست به ترکر را با پارامترهای لازم می‌سازد
func (t *TorrentFile) buildTrackerURL(peerID [20]byte, port uint16) (string, error) {
    base, err := url.Parse(t.Announce)
    if err != nil {
        return "", err
    }
    params := url.Values{
        "info_hash":  []string{string(t.InfoHash[:])}, // هش فایل مورد نظر
        "peer_id":    []string{string(peerID[:])},     // شناسه ما به‌عنوان همتا
        "port":       []string{strconv.Itoa(int(Port))}, // پورتی که به آن گوش می‌دهیم
        "uploaded":   []string{"0"},     // حجم آپلودشده
        "downloaded": []string{"0"},     // حجم دانلودشده
        "compact":    []string{"1"},     // پاسخ فشرده (باینری) بخواه
        "left":       []string{strconv.Itoa(t.Length)}, // حجم باقی‌مانده برای دانلود
    }
    base.RawQuery = params.Encode()
    return base.String(), nil
}

مهم‌ترین‌های این پارامترها:

  • info_hash: فایلی را که می‌خواهیم دانلود کنیم شناسایی می‌کند. همان infohash است که قبلاً از دیکشنری بنکدشده info محاسبه کردیم. ترکر از این برای فهمیدن اینکه کدام همتاها را به ما نشان بدهد استفاده می‌کند.
  • peer_id: یک نام ۲۰ بایتی برای معرفی خودمان به ترکرها و همتاها. ما فقط ۲۰ بایت تصادفی برای آن می‌سازیم. کلاینت‌های واقعی بیت‌تورنت شناسه‌هایی مثل -TR2940-k8hj0wgej6ch دارند که نرم‌افزار و نسخه کلاینت را شناسایی می‌کند — در این مورد TR2940 یعنی کلاینت Transmission نسخه 2.94.

تجزیه پاسخ ترکر

یک پاسخ بنکدشده برمی‌گردد:

  8:interval
    i900e
  5:peers
    252:(یک بلاب باینری طولانی دیگر)
e

interval به ما می‌گوید چند وقت یک‌بار باید دوباره به ترکر وصل شویم تا فهرست همتاهایمان را تازه کنیم. مقدار ۹۰۰ یعنی باید هر ۱۵ دقیقه (۹۰۰ ثانیه) دوباره متصل شویم.

peers یک بلاب باینری طولانی دیگر شامل آدرس IP هر همتاست و از گروه‌های شش‌بایتی ساخته شده است. چهار بایت اول هر گروه آدرس IP همتا را نشان می‌دهد — هر بایت یک عدد از IP است. دو بایت آخر هم پورت را به‌صورت یک uint16 بیگ-اندین (big-endian) نشان می‌دهند. بیگ-اندین یا ترتیب شبکه یعنی می‌توانیم یک گروه بایت را به‌صورت یک عدد صحیح تفسیر کنیم فقط با فشردن آن‌ها کنار هم از چپ به راست. مثلاً بایت‌های 0x1A و 0xE1 می‌شوند 0x1AE1 یا در مبنای ۱۰ برابر ۶۸۸۱ * تفسیر همین بایت‌ها به‌صورت لیتل-اندین (little-endian) می‌شود 0xE11A = 57626. 

go// Peer اطلاعات اتصال یک همتا را کدگذاری می‌کند
type Peer struct {
    IP   net.IP
    Port uint16
}

// Unmarshal آدرس‌های IP و پورت همتاها را از یک بافر تجزیه می‌کند
func Unmarshal(peersBin []byte) ([]Peer, error) {
    const peerSize = 6 // ۴ بایت برای IP، ۲ بایت برای پورت
    numPeers := len(peersBin) / peerSize
    if len(peersBin)%peerSize != 0 {
        err := fmt.Errorf("Received malformed peers")
        return nil, err
    }
    peers := make([]Peer, numPeers)
    for i := 0; i < numPeers; i++ {
        offset := i * peerSize
        peers[i].IP = net.IP(peersBin[offset : offset+4])
        peers[i].Port = binary.BigEndian.Uint16(peersBin[offset+4 : offset+6])
    }
    return peers, nil
}

دانلود از همتاها

حالا که فهرست همتاها را داریم، وقت آن است که به آن‌ها متصل شویم و دانلود قطعه‌ها را شروع کنیم! می‌توانیم فرایند را به چند گام بشکنیم. برای هر همتا می‌خواهیم:

  1. یک اتصال TCP با همتا شروع کنیم. این مثل شروع یک تماس تلفنی است.
  2. یک دست‌دهی (handshake) دوطرفه بیت‌تورنت انجام دهیم. «الو؟» «الو.»
  3. برای دانلود قطعه‌ها پیام مبادله کنیم. «قطعه شماره ۲۳۱ را می‌خواهم، لطفاً.»

شروع یک اتصال TCP

go// یک اتصال TCP به همتا برقرار می‌کنیم؛ تایم‌اوت تعیین شده تا وقت کمتری برای
// همتاهایی که اجازه اتصال نمی‌دهند هدر بدهیم
conn, err := net.DialTimeout("tcp", peer.String(), 3*time.Second)
if err != nil {
    return nil, err
}

در بیشتر موارد، این یک اتصال TCP کاملاً استاندارد است.

تکمیل دست‌دهی (Handshake)

تازه با یک همتا اتصال برقرار کرده‌ایم، اما می‌خواهیم دست‌دهی انجام دهیم تا فرض‌هایمان را تأیید کنیم که همتا:

  • می‌تواند با پروتکل بیت‌تورنت ارتباط برقرار کند
  • می‌تواند پیام‌های ما را بفهمد و به آن‌ها پاسخ دهد
  • فایلی که می‌خواهیم را دارد، یا حداقل می‌فهمد درباره چه چیزی حرف می‌زنیم

پدرم به من گفت راز یک دست‌دهی خوب، گرفتن محکم دست و تماس چشمی است. راز دست‌دهی خوب بیت‌تورنت هم این است که از پنج بخش تشکیل شده است:

  1. طول شناسه پروتکل که همیشه ۱۹ است (0x13 در مبنای شانزده)
  2. شناسه پروتکل که pstr نامیده می‌شود و همیشه BitTorrent protocol است
  3. هشت بایت رزرو که همگی ۰ هستند. بعضی‌شان را ۱ می‌کردیم تا بگوییم از بعضی افزونه‌ها پشتیبانی می‌کنیم. اما ما پشتیبانی نمی‌کنیم، پس آن‌ها را ۰ نگه می‌داریم.
  4. همان infohash که قبلاً محاسبه کردیم تا مشخص شود کدام فایل را می‌خواهیم
  5. شناسه همتا (Peer ID) که ساختیم تا خودمان را معرفی کنیم

ارسال و دریافت پیام‌ها

بعد از تکمیل دست‌دهی اولیه، می‌توانیم پیام ارسال و دریافت کنیم. راستش، نه کاملاً — اگر همتای دیگر آماده دریافت پیام نباشد، تا وقتی نگوید آماده است نمی‌توانیم چیزی بفرستیم. در این حالت، می‌گوییم توسط همتای دیگر خفه شده‌ایم (choked). آن‌ها یک پیام unchoke می‌فرستند تا بفهمانند می‌توانیم درخواست داده بدهیم. به‌صورت پیش‌فرض فرض می‌کنیم خفه شده‌ایم، مگر اینکه خلافش ثابت شود.

وقتی unchoke شدیم، می‌توانیم درخواست قطعه‌ها را بفرستیم و آن‌ها هم می‌توانند پیام‌هایی حاوی قطعه‌ها برایمان بفرستند.

یک پیام یک طول (length)، یک شناسه (ID) و یک بار (payload) دارد. روی سیم، این‌طور دیده می‌شود:

یک پیام با نشانگر طول شروع می‌شود که به ما می‌گوید پیام چند بایت طول دارد. این یک عدد صحیح ۳۲ بیتی است، یعنی از چهار بایت فشرده‌شده با ترتیب بیگ-اندین ساخته شده. بایت بعدی، یعنی شناسه، به ما می‌گوید چه نوع پیامی دریافت می‌کنیم — مثلاً بایت ۲ یعنی «علاقه‌مند (interested)». در نهایت، بار اختیاری بقیه طول پیام را پر می‌کند. 

go// messageID نوع شناسه پیام‌های پروتکل همتا است
type messageID uint8

const (
    MsgChoke         messageID = 0 // خفه کردن (اجازه درخواست نده)
    MsgUnchoke       messageID = 1 // رفع خفگی (اجازه درخواست بده)
    MsgInterested    messageID = 2 // علاقه‌مند به فایل
    MsgNotInterested messageID = 3 // بی‌علاقه به فایل
    MsgHave          messageID = 4 // دارا بودن یک قطعه
    MsgBitfield      messageID = 5 // بیت‌فیلد قطعه‌های در اختیار
    MsgRequest       messageID = 6 // درخواست یک بلاک
    MsgPiece         messageID = 7 // ارسال یک بلاک (قطعه)
    MsgCancel        messageID = 8 // لغو درخواست
)

// Message شناسه و بار یک پیام را نگه می‌دارد
type Message struct {
    ID      messageID
    Payload []byte
}

// Serialize یک پیام را به بافری به شکل
// <پیشوند طول><شناسه پیام><بار>
// سریال می‌کند. مقدار nil به‌عنوان پیام keep-alive تفسیر می‌شود
func (m *Message) Serialize() []byte {
    if m == nil {
        return make([]byte, 4) // طول صفر یعنی keep-alive
    }
    length := uint32(len(m.Payload) + 1) // +1 برای شناسه
    buf := make([]byte, 4+length)
    binary.BigEndian.PutUint32(buf[0:4], length)
    buf[4] = byte(m.ID)
    copy(buf[5:], m.Payload)
    return buf
}

برای خواندن یک پیام از جریان، فقط قالب پیام را دنبال می‌کنیم: چهار بایت می‌خوانیم و به‌صورت uint32 تفسیرشان می‌کنیم تا طول پیام به‌دست آید. سپس همان تعداد بایت را می‌خوانیم تا شناسه (بایت اول) و بار (بقیه بایت‌ها) را بگیریم. 

go// Read یک پیام را از جریان می‌خواند. برای پیام keep-alive مقدار nil برمی‌گرداند
func Read(r io.Reader) (*Message, error) {
    lengthBuf := make([]byte, 4)
    _, err := io.ReadFull(r, lengthBuf)
    if err != nil {
        return nil, err
    }
    length := binary.BigEndian.Uint32(lengthBuf)

    // پیام keep-alive
    if length == 0 {
        return nil, nil
    }

    messageBuf := make([]byte, length)
    _, err = io.ReadFull(r, messageBuf)
    if err != nil {
        return nil, err
    }

    m := Message{
        ID:      messageID(messageBuf[0]),
        Payload: messageBuf[1:],
    }

    return &m, nil
}

یکی از جالب‌ترین انواع پیام، بیت‌فیلد (bitfield) است؛ یک ساختار داده که همتاها با آن به‌شکل کارآمد کدگذاری می‌کنند که کدام قطعه‌ها را می‌توانند برایمان بفرستند. بیت‌فیلد شبیه یک آرایه بایت است و برای چک کردن اینکه کدام قطعه‌ها را دارند، فقط باید به موقعیت بیت‌های ۱ نگاه کنیم. می‌توانید به آن مثل معادل دیجیتالی کارت وفاداری یک کافی‌شاپ فکر کنید. با یک کارت خالی از همه صفر شروع می‌کنیم و بیت‌ها را به ۱ می‌کنیم تا موقعیت‌شان را به‌عنوان «مهر خورده» علامت بزنیم.

این ساختار داده با کار روی بیت‌ها به‌جای بایت‌ها فوق‌العاده فشرده است. می‌توانیم اطلاعات هشت قطعه را در فضای یک بایت تنها جا بدهیم — اندازه یک bool. بهایش این است که دسترسی به مقادیر کمی پیچیده‌تر می‌شود. کوچک‌ترین واحد حافظه‌ای که کامپیوترها می‌توانند آدرس‌دهی کنند بایت است، پس برای رسیدن به بیت‌هایمان باید کمی دستکاری بیتی انجام دهیم: 

go// Bitfield قطعه‌هایی را نشان می‌دهد که یک همتا دارد
type Bitfield []byte

// HasPiece می‌گوید که آیا بیت‌فیلد ایندکس مشخصی را به‌صورت ۱ (دارد) دارد یا نه
func (bf Bitfield) HasPiece(index int) bool {
    byteIndex := index / 8 // کدام بایت
    offset := index % 8    // کدام بیت در آن بایت
    return bf[byteIndex]>>(7-offset)&1 != 0
}

// SetPiece یک بیت را در بیت‌فیلد به ۱ می‌کند
func (bf Bitfield) SetPiece(index int) {
    byteIndex := index / 8
    offset := index % 8
    bf[byteIndex] |= 1 << (7 - offset)
}

کنار هم قرار دادن همه‌چیز

حالا همه ابزارهای لازم برای دانلود یک تورنت را داریم: فهرستی از همتاها از ترکر گرفته‌ایم و می‌توانیم با آن‌ها ارتباط برقرار کنیم — با برقراری اتصال TCP، شروع دست‌دهی، و فرستادن و دریافت پیام. آخرین مشکلات بزرگ‌مان، مدیریت هم‌زمانی (concurrency) در صحبت با چند همتا به‌طور هم‌زمان و مدیریت وضعیت همتاها هنگام تعامل با آن‌هاست. هر دو از مشکلات کلاسیک دشوارند.

در Go، حافظه را با ارتباط به اشتراک می‌گذاریم و می‌توانیم یک کانال Go را یک صف امن-رشته‌ای ارزان فکر کنیم. دو کانال برای هم‌گام‌سازی کارگرهای هم‌زمان‌مان برپا می‌کنیم: یکی برای توزیع کار (قطعه‌هایی که باید دانلود شوند) بین همتاها و یکی دیگر برای جمع‌آوری قطعه‌های دانلودشده. وقتی قطعه‌های دانلودشده از کانال results می‌آیند، می‌توانیم آن‌ها را در یک بافر کپی کنیم تا شروع به سرهم‌کردن فایل کامل کنیم. 

go// صف‌ها را برای اینکه کارگرها کار بگیرند و نتیجه بدهند آماده می‌کنیم
workQueue := make(chan *pieceWork, len(t.PieceHashes))
results := make(chan *pieceResult)
for index, hash := range t.PieceHashes {
    length := t.calculatePieceSize(index)
    workQueue <- &pieceWork{index, hash, length}
}

// کارگرها را راه‌اندازی می‌کنیم
for _, peer := range t.Peers {
    go t.startDownloadWorker(peer, workQueue, results)
}

// نتیجه‌ها را در بافر جمع می‌کنیم تا پر شود
buf := make([]byte, t.Length)
donePieces := 0
for donePieces < len(t.PieceHashes) {
    res := <-results
    begin, end := t.calculateBoundsForPiece(res.index)
    copy(buf[begin:end], res.buf)
    donePieces++
}
close(workQueue)

برای هر همتایی که از ترکر گرفته‌ایم یک goroutine کارگر می‌سازیم. کارگر به همتا متصل می‌شود و دست‌دهی می‌کند، بعد شروع به گرفتن کار از workQueue می‌کند، تلاش می‌کند آن را دانلود کند و قطعه‌های دانلودشده را از کانال results می‌فرستد. 

go// startDownloadWorker دانلود قطعه‌ها از یک همتا را مدیریت می‌کند
func (t *Torrent) startDownloadWorker(peer peers.Peer, workQueue chan *pieceWork, results chan *pieceResult) {
    c, err := client.New(peer, t.PeerID, t.InfoHash)
    if err != nil {
        log.Printf("Could not handshake with %s. Disconnecting\n", peer.IP)
        return
    }
    defer c.Conn.Close()
    log.Printf("Completed handshake with %s\n", peer.IP)

    c.SendUnchoke()
    c.SendInterested()

    for pw := range workQueue {
        if !c.Bitfield.HasPiece(pw.index) {
            workQueue <- pw // همتا این قطعه را ندارد؛ دوباره به صف برگردان
            continue
        }

        // قطعه را دانلود کن
        buf, err := attemptDownloadPiece(c, pw)
        if err != nil {
            log.Println("Exiting", err)
            workQueue <- pw // قطعه را دوباره به صف برگردان
            return
        }

        err = checkIntegrity(pw, buf)
        if err != nil {
            log.Printf("Piece #%d failed integrity check\n", pw.index)
            workQueue <- pw // قطعه را دوباره به صف برگردان
            continue
        }

        c.SendHave(pw.index)
        results <- &pieceResult{pw.index, buf}
    }
}

هر همتا را در یک ساختار پیگیری می‌کنیم و هنگام خواندن پیام‌ها آن را به‌روز می‌کنیم. این ساختار داده‌هایی مثل اینکه چقدر از همتا دانلود کرده‌ایم، چقدر از آن درخواست کرده‌ایم و اینکه خفه شده‌ایم یا نه را نگه می‌دارد. اگر بخواهیم این را بیشتر مقیاس‌پذیر کنیم، می‌توانیم آن را به‌صورت یک ماشین حالت متناهی رسمی کنیم. اما یک ساختار و یک switch فعلاً کافی است. 

go// pieceProgress وضعیت پیشرفت دانلود یک قطعه را دنبال می‌کند
type pieceProgress struct {
    index      int            // ایندکس قطعه
    client     *client.Client // کلاینت متصل به همتا
    buf        []byte         // بافر قطعه در حال دانلود
    downloaded int            // چند بایت دانلود شده
    requested  int            // چند بایت درخواست شده
    backlog    int            // تعداد درخواست‌های برآورده‌نشده در خط لوله
}

// readMessage یک پیام از همتا می‌خواند و وضعیت را به‌روز می‌کند
func (state *pieceProgress) readMessage() error {
    msg, err := state.client.Read() // این فراخوانی بلاک می‌شود
    switch msg.ID {
    case message.MsgUnchoke:
        state.client.Choked = false // دیگر خفه نیستیم
    case message.MsgChoke:
        state.client.Choked = true // خفه شدیم
    case message.MsgHave:
        index, err := message.ParseHave(msg)
        state.client.Bitfield.SetPiece(index) // همتا این قطعه را دارد
    case message.MsgPiece:
        n, err := message.ParsePiece(state.index, state.buf, msg)
        state.downloaded += n // پیشرفت دانلود
        state.backlog--
    }
    return nil
}

فایل‌ها، قطعه‌ها و هش قطعه‌ها کل داستان نیستند — می‌توانیم جلوتر برویم و قطعه‌ها را به بلاک‌ها (blocks) بشکنیم. بلاک بخشی از یک قطعه است و می‌توانیم آن را کاملاً با ایندکس قطعه‌ای که بخشی از آن است، آفست بایتی‌اش درون قطعه و طولش تعریف کنیم. وقتی از همتاها داده درخواست می‌کنیم، در واقع بلاک درخواست می‌کنیم. یک بلاک معمولاً ۱۶ کیلوبایت است؛ یعنی یک قطعه ۲۵۶ کیلوبایتی ممکن است واقعاً به ۱۶ درخواست نیاز داشته باشد.

اگر همتا درخواستی برای بلاکی بزرگ‌تر از ۱۶ کیلوبایت دریافت کند باید اتصال را قطع کند. با این حال، بر اساس تجربه من، آن‌ها اغلب با کمال میل درخواست‌های تا ۱۲۸ کیلوبایت را برآورده می‌کنند. من فقط بهره‌های متوسطی در سرعت کلی با بلاک‌های بزرگ‌تر دیدم، پس احتمالاً بهتر است به مشخصات (spec) پایبند بمانیم.

رفت‌وبرگشت‌های شبکه گران‌اند و درخواست تک‌تک هر بلاک، عملکرد دانلودمان را کاملاً نابود می‌کند. بنابراین مهم است درخواست‌هایمان را خط‌لوله (pipeline) کنیم طوری که فشار ثابتی از تعدادی درخواست برآورده‌نشده نگه داریم. این می‌تواند گذردهی اتصال‌مان را یک مرتبه بزرگی افزایش دهد.

به‌صورت کلاسیک، کلاینت‌های بیت‌تورنت یک صف پنج‌تایی از درخواست‌های خط‌لوله‌شده نگه می‌داشتند و این همان مقداری است که من استفاده می‌کنم. دریافتم که افزایش آن می‌تواند سرعت دانلود را تا دو برابر کند. کلاینت‌های جدیدتر از اندازه صف تطبیقی استفاده می‌کنند تا بهتر با سرعت‌ها و شرایط شبکه مدرن جور شوند. این قطعاً پارامتری است که ارزش تنظیم کردن دارد و یک میوه آویزان پایین برای بهینه‌سازی عملکرد آینده است. 

go// MaxBlockSize بزرگ‌ترین تعداد بایتی است که یک درخواست می‌تواند بخواهد
const MaxBlockSize = 16384

// MaxBacklog تعداد درخواست‌های برآورده‌نشده‌ای است که کلاینت می‌تواند در خط لوله داشته باشد
const MaxBacklog = 5

// attemptDownloadPiece تمام بلاک‌های یک قطعه را از همتا دانلود و سرهم می‌کند
func attemptDownloadPiece(c *client.Client, pw *pieceWork) ([]byte, error) {
    state := pieceProgress{
        index:  pw.index,
        client: c,
        buf:    make([]byte, pw.length),
    }

    // تعیین ددلاین به آزاد شدن همتاهای بی‌پاسخ کمک می‌کند.
    // ۳۰ ثانیه برای دانلود یک قطعه ۲۶۲ کیلوبایتی بیش از اندازه کافی است
    c.Conn.SetDeadline(time.Now().Add(30 * time.Second))
    defer c.Conn.SetDeadline(time.Time{}) // ددلاین را غیرفعال کن

    for state.downloaded < pw.length {
        // اگر خفه نیستیم، درخواست بفرست تا درخواست‌های برآورده‌نشده کافی داشته باشیم
        if !state.client.Choked {
            for state.backlog < MaxBacklog && state.requested < pw.length {
                blockSize := MaxBlockSize
                // آخرین بلاک ممکن است کوتاه‌تر از بلاک معمولی باشد
                if pw.length-state.requested < blockSize {
                    blockSize = pw.length - state.requested
                }

                err := c.SendRequest(pw.index, state.requested, blockSize)
                if err != nil {
                    return nil, err
                }
                state.backlog++
                state.requested += blockSize
            }
        }

        err := state.readMessage()
        if err != nil {
            return nil, err
        }
    }

    return state.buf, nil
}

نویسنده این مقاله با «CodeCrafters» همکاری می‌کند؛ سرویسی که چالش‌های برنامه‌نویسی برای مهندسان باتجربه می‌سازد (مثل Build your own Git، Docker و Redis). آن‌ها یک چالش بیت‌تورنت دارند که همه‌چیز این مقاله را قدم‌به‌قدم جلو می‌برد — تجزیه بنکد، کشف همتاها و دانلود قطعه‌ها — با قاب‌های تست و کد داربست برای زبان‌های مختلف.
کپیرایت: مقاله «Building a BitTorrent client from the ground up in Go» اثر Jesse Li (blog.jse.li) است. این صفحه فقط ترجمه فارسی آن است و تمام حقوق محتوا، تصاویر و کدها متعلق به نویسنده اصلی است. برای مشاهده اصل مطلب به سایت اصلی مراجعه کنید.
