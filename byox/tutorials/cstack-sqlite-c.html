مقدمه — یک پایگاه داده چگونه کار می‌کند؟

به‌عنوان یک توسعه‌دهندهٔ وب، هر روز در محل کارم از پایگاه‌های دادهٔ رابطه‌ای (relational databases) استفاده می‌کنم، اما آن‌ها برای من یک جعبهٔ سیاه‌اند. سؤال‌هایی که دارم:

  • داده‌ها با چه قالبی ذخیره می‌شوند؟ (در حافظه و روی دیسک)
  • چه زمانی از حافظه به دیسک منتقل می‌شوند؟
  • چرا هر جدول فقط می‌تواند یک کلید اصلی (primary key) داشته باشد؟
  • بازگشت تراکنش (rolling back a transaction) چگونه کار می‌کند؟
  • ایندکس‌ها (indexes) با چه قالبی قالب‌بندی می‌شوند؟
  • اسکن کامل جدول (full table scan) چه زمانی و چگونه اتفاق می‌افتد؟
  • یک عبارت آماده‌شده (prepared statement) با چه قالبی ذخیره می‌شود؟

به‌طور خلاصه: یک پایگاه داده چگونه کار می‌کند؟

برای فهمیدن این‌ها، دارم یک پایگاه داده را از صفر می‌نویسم. این پایگاه داده از sqlite الگوبرداری شده است؛ چون sqlite طوری طراحی شده که کوچک باشد و ویژگی‌های کمتری نسبت به MySQL یا PostgreSQL دارد، پس شانس بهتری برای فهمیدنش دارم. کل پایگاه داده در یک فایل منفرد ذخیره می‌شود!

«هر آنچه را نتوانم بسازم، نمی‌فهمم.» — ریچارد فاینمن (Richard Feynman)

معماری sqlite (https://www.sqlite.org/arch.html)

یک پرس‌وجو (query) برای بازیابی یا اصلاح داده از زنجیره‌ای از کامپوننت‌ها عبور می‌کند. مقدم (front-end) از این موارد تشکیل شده است:

  • توکن‌کننده (tokenizer)
  • تجزیه‌گر (parser)
  • تولیدکنندهٔ کد (code generator)

ورودی مقدم، یک پرس‌وجوی SQL است و خروجی آن، بایت‌کد (bytecode) ماشین مجازی sqlite است (در اصل یک برنامهٔ کامپایل‌شده که می‌تواند روی پایگاه داده عملیات انجام دهد).

پسین (back-end) از این موارد تشکیل شده است:

  • ماشین مجازی (virtual machine)
  • درخت B (B-tree)
  • صفحه‌بند (pager)
  • رابط سیستم‌عامل (os interface)

ماشین مجازی بایت‌کد تولیدشده توسط مقدم را به‌عنوان دستورالعمل می‌گیرد. سپس می‌تواند روی یک یا چند جدول یا ایندکس عملیات انجام دهد؛ هر کدام در ساختار داده‌ای به نام درخت B ذخیره شده‌اند. VM در اصل یک دستور switch بزرگ روی نوع دستورالعمل بایت‌کد است.

هر درخت B از گره‌های (nodes) زیادی تشکیل شده است. طول هر گره یک صفحه (page) است. درخت B می‌تواند با صدور فرمان به صفحه‌بند، یک صفحه را از دیسک بازیابی کند یا آن را به دیسک بازگرداند.

صفحه‌بند فرمان‌های خواندن یا نوشتن صفحات داده را دریافت می‌کند. او مسئول خواندن/نوشتن در آفست‌های (offsets) مناسب در فایل پایگاه داده است. همچنین کش (cache) صفحاتی را که اخیراً به آن‌ها دسترسی شده در حافظه نگه می‌دارد و تعیین می‌کند چه زمانی باید آن صفحات به دیسک نوشته شوند.

رابط سیستم‌عامل لایه‌ای است که بسته به اینکه sqlite برای کدام سیستم‌عامل کامپایل شده باشد متفاوت است. در این آموزش قصد ندارم از چند پلتفرم پشتیبانی کنم.

«سفر هزار مایلی با یک قدم آغاز می‌شود»، پس بیایید با چیزی کمی ساده‌تر شروع کنیم: حلقهٔ REPL.

ساخت یک REPL ساده

sqlite وقتی از خط فرمان شروع می‌شود، یک حلقهٔ read-execute-print (بخوان-اجرا-چاپ) را آغاز می‌کند:

shell~ sqlite3
SQLite version 3.16.0 2016-11-04 19:09:39
Enter ".help" for usage hints.
Connected to a transient in-memory database.
Use ".open FILENAME" to reopen on a persistent database.
sqlite> create table users (id int, username varchar(255), email varchar(255));
sqlite> .tables
users
sqlite> .exit
~

برای انجام همین کار، تابع main ما یک حلقهٔ بی‌نهایت خواهد داشت که درخواست (prompt) را چاپ می‌کند، یک خط ورودی می‌گیرد و سپس آن خط ورودی را پردازش می‌کند:

cint main(int argc, char* argv[]) {
  InputBuffer* input_buffer = new_input_buffer();
  while (true) {
    print_prompt();
    read_input(input_buffer);

    if (strcmp(input_buffer->buffer, ".exit") == 0) {
      close_input_buffer(input_buffer);
      exit(EXIT_SUCCESS);
    } else {
      printf("Unrecognized command '%s'.\n", input_buffer->buffer);
    }
  }
}

InputBuffer را به‌عنوان یک پوشش‌دهندهٔ کوچک (wrapper) دور وضعیتی که برای تعامل با getline() نیاز داریم تعریف می‌کنیم. (بیشتر در یک لحظه)

ctypedef struct {
  char* buffer;
  size_t buffer_length;
  ssize_t input_length;
} InputBuffer;

InputBuffer* new_input_buffer() {
  InputBuffer* input_buffer = (InputBuffer*)malloc(sizeof(InputBuffer));
  input_buffer->buffer = NULL;
  input_buffer->buffer_length = 0;
  input_buffer->input_length = 0;

  return input_buffer;
}

در ادامه، print_prompt() یک درخواست به کاربر چاپ می‌کند. این کار را قبل از خواندن هر خط ورودی انجام می‌دهیم.

cvoid print_prompt() { printf("db > "); }

برای خواندن یک خط ورودی، از getline() استفاده کنید:

cssize_t getline(char **lineptr, size_t *n, FILE *stream);

lineptr: اشاره‌گری به متغیری که برای اشاره به بافر حاوی خط خوانده‌شده استفاده می‌کنیم. اگر روی NULL تنظیم شود، توسط getline malloc می‌شود و در نتیجه باید توسط کاربر آزاد شود، حتی اگر فرمان شکست بخورد.

n: اشاره‌گری به متغیری که برای ذخیرهٔ اندازهٔ بافر تخصیص‌داده‌شده استفاده می‌کنیم.

stream: جریان ورودی که باید از آن خوانده شود. ما از ورودی استاندارد (standard input) می‌خوانیم.

return value: تعداد بایت‌های خوانده‌شده، که ممکن است کمتر از اندازهٔ بافر باشد.

به getline می‌گوییم خط خوانده‌شده را در input_buffer->buffer و اندازهٔ بافر تخصیص‌داده‌شده را در input_buffer->buffer_length ذخیره کند. مقدار بازگشتی را در input_buffer->input_length ذخیره می‌کنیم.

buffer ابتدا null است، بنابراین getline حافظهٔ کافی برای نگه‌داشتن خط ورودی تخصیص می‌دهد و buffer را به آن اشاره می‌دهد.

cvoid read_input(InputBuffer* input_buffer) {
  ssize_t bytes_read =
      getline(&(input_buffer->buffer), &(input_buffer->buffer_length), stdin);

  if (bytes_read <= 0) {
    printf("Error reading input\n");
    exit(EXIT_FAILURE);
  }

  // نادیده گرفتن خط جدید انتهایی
  input_buffer->input_length = bytes_read - 1;
  input_buffer->buffer[bytes_read - 1] = 0;
}

حالا مناسب است تابعی تعریف کنیم که حافظهٔ تخصیص‌داده‌شده برای یک نمونه از InputBuffer * و عنصر buffer ساختار مربوطه را آزاد کند (getline در read_input برای input_buffer->buffer حافظه تخصیص می‌دهد).

cvoid close_input_buffer(InputBuffer* input_buffer) {
    free(input_buffer->buffer);
    free(input_buffer);
}

در نهایت، فرمان را تجزیه و اجرا می‌کنیم. در حال حاضر فقط یک فرمان شناخته‌شده وجود دارد: .exit که برنامه را خاتمه می‌دهد. در غیر این صورت یک پیام خطا چاپ می‌کنیم و حلقه را ادامه می‌دهیم.

قسمت ۲ — ساده‌ترین کامپایلر SQL و ماشین مجازی دنیا

ما در حال ساختن یک کلون از sqlite هستیم. «مقدم» sqlite یک کامپایلر SQL است که یک رشته را تجزیه می‌کند و یک نمایش داخلی به نام بایت‌کد خروجی می‌دهد.

این بایت‌کد به ماشین مجازی داده می‌شود که آن را اجرا می‌کند.

شکستن کارها به این دو مرحله مزیت‌هایی دارد:

  • پیچیدگی هر بخش را کاهش می‌دهد (مثلاً ماشین مجازی نگران خطاهای نحوی نیست)
  • اجازه می‌دهد پرس‌وجوهای رایج یک بار کامپایل شوند و بایت‌کد برای بهبود کارایی کش شود

با این فکر، بیایید تابع main خود را بازسازی (refactor) کنیم و در این فرآیند از دو کلیدواژهٔ جدید پشتیبانی کنیم:

عبارت‌های غیر SQL مانند .exit «فرمان‌های فرامتاداده» (meta-commands) نامیده می‌شوند. همهٔ آن‌ها با یک نقطه شروع می‌شوند، بنابراین آن‌ها را بررسی می‌کنیم و در یک تابع جداگانه مدیریت می‌کنیم.

قالب فعلی فایل

چهار بایت اول، شناسهٔ سطر اول است (۴ بایت؛ چون یک uint32_t ذخیره می‌کنیم). در ترتیب بایتی little-endian ذخیره شده است؛ بنابراین کم‌ارزش‌ترین بایت اول می‌آید (01) و بعد بایت‌های باارزش‌تر (00 00 00). ما برای کپی کردن بایت‌ها از ساختار Row خود به کش صفحه از memcpy() استفاده کردیم؛ یعنی ساختار در حافظه با ترتیب بایتی little-endian چیده شده بود. این ویژگی ماشینی است که برنامه را برایش کامپایل کردم. اگر می‌خواستیم فایل پایگاه داده‌ای روی ماشین من بنویسیم و بعد روی ماشینی big-endian بخوانیم، باید متدهای serialize_row() و deserialize_row() خود را تغییر می‌دادیم تا همیشه بایت‌ها را در یک ترتیب ذخیره و بخوانند.

۳۳ بایت بعدی نام‌کاربری را به‌صورت یک رشتهٔ null-terminated ذخیره می‌کنند. ظاهراً «cstack» در هگز ASCII برابر 63 73 74 61 63 6b است و بعد از آن یک کاراکتر null (00) می‌آید. بقیهٔ ۳۳ بایت استفاده نشده‌اند.

۲۵۶ بایت بعدی ایمیل را به همان شکل ذخیره می‌کنند. این‌جا بعد از کاراکتر null پایانی مقداری آشغال تصادفی می‌بینیم. این به احتمال زیاد به‌خاطر حافظهٔ مقداردهی‌نشده در ساختار Row ماست. کل بافر ایمیل ۲۵۶ بایتی را در فایل کپی می‌کنیم، ازجمله هر بایتی که بعد از پایان رشته قرار دارد. هرچه در حافظه بود وقتی آن ساختار را تخصیص دادیم، هنوز آن‌جاست. اما چون از کاراکتر null پایانی استفاده می‌کنیم، هیچ اثری روی رفتار ندارد.

قسمت ۶ — انتزاع نشانگر (The Cursor Abstraction)

این قسمت باید از قسمت قبل کوتاه‌تر باشد. فقط کمی بازسازی می‌کنیم تا شروع پیاده‌سازی درخت B آسان‌تر شود.

یک شیء Cursor اضافه می‌کنیم که یک موقعیت در جدول را نمایان می‌کند. کارهایی که شاید با نشانگرها بخواهید انجام دهید:

  • ساخت یک نشانگر در ابتدای جدول
  • ساخت یک نشانگر در انتهای جدول
  • دسترسی به سطری که نشانگر به آن اشاره می‌کند
  • پیش بردن نشانگر به سطر بعدی

قسمت ۷ — مقدمه‌ای بر درخت B (Introduction to the B-Tree)

درخت B ساختار داده‌ای است که SQLite برای نمایش هم جدول‌ها و هم ایندکس‌ها از آن استفاده می‌کند؛ بنابراین ایدهٔ نسبتاً مرکزی‌ای است. این مقاله فقط ساختار داده را معرفی می‌کند؛ پس کدی نخواهد داشت.

چرا درخت ساختار دادهٔ خوبی برای یک پایگاه داده است؟

  • جست‌وجوی یک مقدار مشخص سریع است (زمان لگاریتمی)
  • درج/حذف مقداری که قبلاً پیدا کرده‌اید سریع است (زمان تقریباً ثابت برای بازتعادل)
  • پیمایش یک بازهٔ از مقادیر سریع است (برخلاف جدول هش)

درخت B با درخت دودویی (binary tree) متفاوت است (حرف «B» احتمالاً از نام مخترع است، اما می‌تواند مخفف «balanced» یعنی متعادل هم باشد). این هم یک مثال درخت B:

برخلاف درخت دودویی، هر گره در درخت B می‌تواند بیش از ۲ فرزند داشته باشد. هر گره می‌تواند حداکثر m فرزند داشته باشد، که m «مرتبه» (order) درخت نامیده می‌شود. برای اینکه درخت تقریباً متعادل بماند، همچنین می‌گوییم گره‌ها باید حداقل m/2 فرزند داشته باشند (گردشده به بالا).

استثناها:

  • گره‌های برگ ۰ فرزند دارند
  • گرهٔ ریشه می‌تواند کمتر از m فرزند داشته باشد اما باید حداقل ۲ فرزند داشته باشد
  • اگر گرهٔ ریشه یک گرهٔ برگ باشد (تنها گره)، باز هم ۰ فرزند دارد

تصویر بالا یک درخت B است که SQLite برای ذخیرهٔ ایندکس‌ها استفاده می‌کند. برای ذخیرهٔ جدول‌ها، SQLite از تغییردهنده‌ای به نام درخت B+ استفاده می‌کند.

گرهٔ داخلی ۱ کلید و ۲ اشاره‌گر به گره‌های فرزند دارد. اگر بخواهیم کلیدی را که کوچک‌تر یا مساوی ۵ است جست‌وجو کنیم، در فرزند چپ نگاه می‌کنیم. اگر بخواهیم کلیدی بزرگ‌تر از ۵ را جست‌وجو کنیم، در فرزند راست نگاه می‌کنیم.

به افزودن کلیدها ادامه می‌دهیم. ۱۸ و ۲۱. به جایی می‌رسیم که باید دوباره تقسیم کنیم؛ اما در گرهٔ والد جایی برای یک جفت کلید/اشاره‌گر دیگر نیست.

راه‌حل این است که گرهٔ ریشه را به دو گرهٔ داخلی تقسیم کنیم و سپس یک گرهٔ ریشهٔ جدید بسازیم که والد آن‌ها باشد.

عمق درخت فقط وقتی افزایش می‌یابد که گرهٔ ریشه را تقسیم می‌کنیم. همهٔ گره‌های برگ عمق یکسان و تقریباً همان تعداد جفت کلید/مقدار را دارند؛ بنابراین درخت متعادل می‌ماند و جست‌وجو سریع است.

بحث دربارهٔ حذف کلیدها از درخت را تا بعد از پیاده‌سازی درج کنار می‌گذارم.

وقتی این ساختار داده را پیاده‌سازی کنیم، هر گره با یک صفحه متناظر خواهد بود. گرهٔ ریشه در صفحهٔ ۰ وجود خواهد داشت. اشاره‌گرهای فرزند به سادگی شمارهٔ صفحه‌ای هستند که گرهٔ فرزند را در خود دارد.

دفعهٔ بعد، شروع به پیاده‌سازی btree می‌کنیم!

قسمت ۸ — قالب گرهٔ برگ درخت B (B-Tree Leaf Node Format)

داریم قالب جدول خود را از یک آرایهٔ نامرتب از ردیف‌ها به یک درخت B تغییر می‌دهیم. این تغییر نسبتاً بزرگی است که پیاده‌سازی آن چندین مقاله طول می‌کشد. تا پایان این مقاله، چیدمان یک گرهٔ برگ را تعریف می‌کنیم و از درج جفت‌های کلید/مقدار در یک درخت تک‌گره‌ای پشتیبانی می‌کنیم. اما اول، بیایید دلایل سوئیچ به ساختار درختی را مرور کنیم.

قالب‌های جایگزین جدول (Alternative Table Formats)

با قالب فعلی، هر صفحه فقط ردیف ذخیره می‌کند (بدون متاداده)، پس از نظر فضا کارآمد است. درج هم سریع است؛ چون فقط به انتها اضافه می‌کنیم. با این حال، پیدا کردن یک ردیف مشخص فقط با اسکن کل جدول ممکن است. و اگر بخواهیم یک ردیف را حذف کنیم، باید با جابه‌جا کردن هر ردیفی که بعد از آن می‌آید، حفره را پر کنیم.

اگر جدول را به‌صورت یک آرایه ذخیره می‌کردیم اما ردیف‌ها را بر اساس شناسه مرتب نگه می‌داشتیم، می‌توانستیم برای پیدا کردن یک شناسهٔ خاص از جست‌وجوی دودویی استفاده کنیم. با این حال درج کند می‌شد؛ چون برای جا دادن باید تعداد زیادی ردیف جابه‌جا کنیم.

در عوض، با یک ساختار درختی پیش می‌رویم. هر گره در درخت می‌تواند تعداد متغیری ردیف داشته باشد؛ پس باید در هر گره اطلاعاتی ذخیره کنیم تا بدانیم چند ردیف دارد. به علاوه هزینهٔ ذخیره‌سازی همهٔ گره‌های داخلی را داریم که هیچ ردیفی ذخیره نمی‌کنند. در ازای یک فایل پایگاه دادهٔ بزرگ‌تر، درج، حذف و جست‌وجوی سریع می‌گیریم.
